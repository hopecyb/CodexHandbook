При первом использовании Codex многих больше всего беспокоит вопрос: можно ли вернуться назад, если он изменит что-то неправильно?

В большинстве случаев можно, но откатываться лучше безопасным способом.

Если результат вышел за границы или оказался недостаточно качественным:

1. Используйте предоставленную клиентом функцию отмены или восстановления изменений с учётом текущего UI.
2. Если проект находится под управлением Git, отбросьте изменения рабочей области знакомым вам способом. Начинающие могут пока обойтись без Git и использовать учебный каталог.
3. Откройте новый тред, сузьте ограничения и повторите попытку.

Часто заранее сузить область проще: разрешить менять лишь несколько файлов, явно записать запреты, сначала просмотреть план и только затем выполнять.

## Разница между отменой и восстановлением

- **Отмена**: откатить только что внесённые неудовлетворительные изменения.
- **Восстановление**: вернуть проект в состояние, безопасность которого вы подтвердили.

При работе с одним небольшим файлом отмена обычно проста. Сложности возникают, если:

- Codex изменил несколько файлов;
- затем вы внесли часть изменений вручную;
- уже непонятно, кто изменил каждую часть.

Сначала остановите дальнейшие изменения и сузьте область воздействия.

## Порядок действий после первой ошибки

1. Остановите дальнейшие изменения: не просите Codex менять ещё больше в состоянии паники.
2. Определите, какие файлы были изменены.
3. Если в продукте есть функция отмены, сначала воспользуйтесь ею.
4. Если проект уже находится под управлением Git, откатитесь знакомым способом Git.
5. Вернувшись в безопасное состояние, повторите задачу с более ясными указаниями.

## Если вы не знакомы с Git

Слово «восстановление» пугает многих начинающих: кажется, что сначала нужно выучить множество команд Git. На первых шагах это необязательно.

Можно действовать проще:

- практиковаться в учебном каталоге;
- разрешать менять только один небольшой файл за раз;
- при неудовлетворительном результате сразу отменять изменение.

Перед работой с настоящими проектами стоит систематически изучить откат в Git.

## Профилактика важнее исправления

Следующие приёмы заметно уменьшают вероятность того, что ошибку будет трудно устранить:

- явно писать, какой именно файл можно изменить;
- сначала запрашивать план и только затем выполнять;
- проверять каждый завершённый шаг, не накапливая множество изменений;
- подтверждать действие с высоким риском до выполнения.

## Используйте точки восстановления для исследования

Восстановление полезно не только после ошибки. Точку восстановления можно создать заранее, прежде чем исследовать разные варианты.

Это особенно уместно, если вы собираетесь:

- сравнить два подхода к реализации;
- поручить Agent достаточно крупный рефакторинг;
- опробовать скрипт автоматизации или массовую замену;
- работать с требованиями, которые могут быстро изменить направление.

Более надёжный ритм:

```text
Подтвердить текущее безопасное состояние
→ Попросить Codex перечислить затрагиваемые файлы
→ Создать точку восстановления или проверить состояние Git
→ Выполнить работу в небольшой области
→ Провести Review diff и проверить результат
→ Решить: сохранить, откатить или выбрать другой подход
```

Если клиент поддерживает контрольные точки или воспроизведение, сначала можно использовать встроенные возможности продукта. Если проект находится под управлением Git, точкой восстановления может служить ветка, stash или небольшой commit. Главное — не запомнить конкретную команду, а не расширять изменения, пока область воздействия остаётся неясной.

Сама ошибка не страшна. Намного хуже продолжать изменения, не разобравшись в уже затронутой области.
