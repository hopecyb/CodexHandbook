У каждого чата в настольном приложении ChatGPT есть терминал, область которого ограничена текущим проектом или Worktree. Это не просто место для просмотра журналов, но и окно с доказательствами, по которым можно проверить выводы Codex.

Откройте терминал значком в правом верхнем углу приложения или одновременно нажмите `Ctrl` и клавишу с обратной кавычкой. ChatGPT может читать текущий вывод терминала, поэтому его можно попросить проанализировать неудачную сборку или работающий сервер разработки.

## Минимальный процесс проверки

В JavaScript-проекте можно последовательно выполнить:

```bash
git status --short
pnpm test
pnpm run lint
```

Команды различаются между проектами. Сначала изучите `README.md`, `package.json` или правила проекта. Включите уже проверенные команды в промпт:

```text
После изменений выполни pnpm test и pnpm run lint.
Для каждой команды сообщи статус завершения. Если хотя бы одна завершится ошибкой, не заявляй, что задача выполнена.
```

При приёмке зафиксируйте как минимум: что именно выполнялось, был ли код завершения успешным, первую значимую ошибку и список пропущенных проверок.

## Как работать с длительными процессами

Сервер разработки продолжает работать постоянно — это не означает, что команда зависла. После запуска проверьте:

- появился ли в выводе локальный адрес;
- открывается ли страница в браузере;
- появились ли затем в терминале ошибки времени выполнения.

Отправляйте сигнал прерывания только тогда, когда сервер нужно остановить. Не запускайте несколько серверов повторно лишь из-за временного отсутствия нового вывода.

## Многоразовый Action

Если одни и те же команды выполняются часто, в локальной среде можно определить Action. Он появится в Desktop App как быстрое действие и будет выполняться во встроенном терминале. Это удобно для низкорисковых проверок `test`, `lint` и `build`, но не для сокрытия операций публикации в production или очистки базы данных.

## Границы безопасности

- Не вставляйте производственные секреты в чат или историю терминала;
- Для непонятной команды сначала запросите объяснение цели, области воздействия и способа отката;
- Не повторяйте вслепую команды удаления, миграции и публикации в производственной среде;
- Техническая возможность выполнить команду не означает, что операция одобрена с точки зрения бизнеса.

В официальной документации среди типичных команд приводятся `git status`, `git pull --rebase`, тесты и lint. Окончательным источником команд для конкретного проекта должна быть его собственная документация.
