Модель угроз помогает обдумать риски до того, как они реализуются:

> **Если Codex действительно подключён к нашему коду, командам и внешним инструментам, что с наибольшей вероятностью пойдёт не так?**

**Моделирование угроз** раскладывает этот вопрос на части. Codex — не просто ещё одно окно чата: он может **читать код, выполнять команды и вызывать внешние инструменты**. Эта глава описывает основные поверхности риска; меры контроля приведены в [матрице разрешений](/ru/guide/reference/permission-matrix/) и разделе о [песочнице](/ru/guide/foundations/sandbox-and-network/).

## О чём эта страница

- Активы и границы доверия
- Типовые угрозы и направления снижения риска
- Распределение ответственности между правилами, Hook и CI

## Это задача не только службы безопасности

Риски важны и разработчикам, и платформенным инженерам, и техническим писателям, и руководителям проектов, если команда:

- выдаёт автоматизации токены с избыточными разрешениями;
- выполняет высокорисковые действия на недоверенных входных данных;
- не знает, какие данные можно просматривать или выносить за пределы организации;
- добавляет расширения только ради функций, не проверяя разрешения и происхождение.

Моделирование угроз помогает установить границы до инцидента.

## Активы и границы

| Актив | Примеры |
|---|---|
| Исходный код и интеллектуальная собственность | Закрытые репозитории, ещё не выпущенные проекты |
| Учётные данные | API-ключи, `.env`, облачный IAM |
| Пользовательские данные | PII, содержимое тикетов клиентов |
| Инфраструктура | CI, конвейеры развёртывания в производственной среде |

**Граница доверия:** модель и расширения по умолчанию находятся на стороне, которой **не доверяют полностью**; на границе действуют проверка человеком и политика.

## Два основных вопроса

Перед развёртыванием во всей команде спросите:

1. Что мы ни в коем случае не должны потерять?
2. Что Codex ни в коем случае не должен сделать по ошибке?

Первый вопрос выявляет важные активы, второй — опасные действия. Большинство мер контроля строится вокруг них.

## Сценарий

- Codex читает закрытый репозиторий.
- Получает доступ к системе тикетов с разграничением разрешений.
- Выполняет shell-команды.
- Публикует результат в комментариях.

В этом случае следите за тем, чтобы система:

- не увидела то, чего видеть не должна;
- не сделала то, чего делать не должна;
- не вынесла внутреннюю информацию наружу.

Такой взгляд превращает моделирование угроз в контрольный список рисков перед запуском.

## Обзор угроз

| Угроза | Описание | Направление защиты |
|---|---|---|
| Инъекция промпта | Вредоносная задача или веб-страница направляет систему на выход за границы | Очистка входных данных, CI только для чтения, [раздел об инъекциях](/ru/guide/team-enterprise/security/prompt-injection/) |
| Избыточные разрешения | У токена или песочницы слишком широкие права | Минимальные привилегии, защита веток |
| Утечка данных | Команды или MCP выводят данные репозитория наружу | Сетевая политика, DLP, аудит через Hook |
| Вредоносное расширение | Непроверенный Plugin/MCP | [Риски расширений](/ru/guide/team-enterprise/security/plugin-and-mcp-risk/) |
| Цепочка поставок | Подмена зависимости или скрипта | Существующие SCA и Code Review |
| Ошибочное действие | Agent удаляет базу данных или выполняет push не туда | Запрет команд, отсутствие push в CI |

## Что считать приоритетным в модели угроз

В первую очередь рассматривайте возможности, которые одновременно:

- затрагивают важные активы;
- выполняют реальные действия.

Примеры: чтение закрытых репозиториев, вызов производственных API, MCP с правом записи, автоматический push кода.

## Не пытайтесь охватить всё в первый день

Многие команды стараются сразу написать все политики и в итоге ничего не выпускают.

Для первого развёртывания часто достаточно:

1. Трёх важнейших классов активов
2. Трёх действий, которых вы опасаетесь больше всего
3. Одной прямой меры контроля для каждого пункта

Примеры:

- Опасаетесь утечки производственной базы данных → ограничьте производственные учётные данные и пути экспорта.
- Опасаетесь ошибочного push в main → включите защиту веток и подтверждение.
- Опасаетесь управления через задачи или веб-страницы → ограничьте внешние входные данные и используйте Review только для чтения.

Это не полный набор мер, но он полезнее огромного документа, который никто не читает.

## Рекомендуемые уровни защиты

```text
L1 Идентификация и арендатор (SSO, группы)
L2 Управляемая организацией конфигурация и политика моделей
L3 Правила репозитория + AGENTS.md
L4 Песочница / подтверждение / Hook
L5 Проверка человеком и защита веток
```

## Распространённые ошибки

- Ограничиваться обучением без технических мер
- Предполагать, что «модель достаточно умна»
- Хранить производственные секреты по путям, доступным Agent для записи
- Сводить все риски к надежде, что «проверка человеком всё заметит»

## Минимально достаточная версия

Установите правила:

- высокорисковые действия требуют подтверждения;
- доступ к конфиденциальным данным по умолчанию запрещён;
- автоматизация по умолчанию работает только на чтение.

Уже это снижает значительную часть командных рисков; уточнить управление можно позже.

## Контрольный список приёмки

- [ ] Можно перечислить три важнейших актива организации, вызывающих опасения.
- [ ] Для каждой угрозы есть мера контроля или запись о принятом риске.
- [ ] Назначены ответственные за реагирование на инциденты.
