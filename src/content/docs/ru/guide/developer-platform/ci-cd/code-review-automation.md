Codex в **конвейере pull request** может обнаруживать очевидные проблемы до проверки человеком, но **не заменяет** ответственное Review и тесты. На этой странице описаны практические схемы автоматизации.

## О чём эта страница

- Как безопасно вызывать Codex в CI
- Что включить в промпт для Review
- Как опубликовать результат в PR без автоматического слияния

## Сначала определите роль

Считайте «автоматизацию Code Review» первичной проверкой, которую Codex выполняет для команды. Окончательное решение всё равно принимает человек.

Лучше всего она подходит для следующих задач:

- заранее отмечать очевидные риски;
- кратко выделять важное в diff;
- выполнять повторяющиеся проверки.

Не стоит поручать ей решение «этот PR точно можно безопасно слить».

См. также: [Неинтерактивный режим](/ru/guide/cli/non-interactive-mode/) · [Обзор SDK](/ru/guide/developer-platform/sdk-overview/)

## Рекомендуемая архитектура

```text
PR открыт / обновлён
    → задание CI (токен только для чтения)
    → codex exec или API проверяет diff
    → загрузка отчёта / комментарий в PR
    → человек решает, выполнять ли слияние
```

## Распространённые заблуждения

### Автоматическое Review — не автоматическое одобрение

Команды нередко переоценивают автоматизацию: если она способна автоматически проверить изменения, значит ли это, что она может и сама принять решение?

Точнее считать её уровнем **рекомендаций** и **первичной сортировки**, а не последним уровнем ответственности.

### Не каждому PR с первого дня нужна глубокая проверка

Для небольших малозначимых PR или до окончательного согласования правил тяжёлое автоматическое Review часто лишь создаёт шум.

Хорошая отправная точка — лёгкая проверка diff, которая стабильно экономит время команды.

## Что должно быть в шаблоне промпта

```text
Ты — помощник по Code Review. Проверяй только diff относительно базовой ветки.
Вывод: критические проблемы / рекомендации / мелкие замечания; для каждого укажи файл и строку.
Не изменяй репозиторий и не выполняй сетевые запросы.
Если diff слишком велик, проверь только <список путей>.
```

Храните версии в `prompts/ci-review.md`.

## Разрешения и безопасность

| Принцип | Практика |
|---|---|
| Только чтение | Токен CI без права push либо бот, способный только оставлять комментарии |
| Фиксированная модель | Упрощает сравнение качества Review со временем |
| Защита от инъекций | Не вставляйте неочищенное описание PR в системный промпт |
| Секреты | Храните токены в GitHub Secrets |

## Контрольные этапы качества

- Сбой задания Review не обязан блокировать слияние: на первом этапе проверка может быть рекомендательной.
- Разделяйте обязательные проверки статуса: красные тесты должны блокировать слияние, а замечания AI могут оставаться предупреждениями.
- Периодически выборочно сравнивайте результат с человеческим Review, оценивая пропуски и ложные срабатывания.

## Связь с Cloud

В сложных репозиториях перед Review можно выполнить полные тесты в [Cloud](/ru/guide/web-and-cloud/); запуск внутри CI лучше подходит для **лёгкой проверки diff**.

## Распространённые ошибки

- У CI есть право записи, а в промпт внедрено «please push fix».
- Результат Review настолько длинный, что мешает проверке человеком.
- Нет ограничения размера diff, из-за чего возникают тайм-ауты и расходуется квота.

Главная ценность автоматизации Code Review — находить очевидные проблемы до проверки человеком, а не брать на себя ответственность за слияние.

## Контрольный список приёмки

- [ ] CI безопасно обрабатывает PR из форков, не раскрывая секреты.
- [ ] Результат Review структурирован и при необходимости пригоден для машинного разбора.
- [ ] В командной документации объяснена роль AI-Review.
