После завершения задачи внутреннюю систему можно уведомить через возвращаемое значение программы, статус процесса, поток событий или HTTP-обратный вызов. Сначала определите отправителя и протокол, а затем решайте, нужен ли вебхук.

## Не смешивайте три разных механизма

| Механизм | Как получается результат | Граница |
|---|---|---|
| Локальное выполнение через SDK или CLI | Результат программы или статус процесса | Это не размещённый API HTTP-обратных вызовов |
| События App Server | Уведомления JSON-RPC по установленному соединению | Подключитесь, выполните инициализацию и обрабатывайте сообщения согласно протоколу |
| Обратный вызов собственного исполнителя | HTTP-запрос, отправленный вашей службой | Вы сами определяете имена событий, подписи, повторы и хранение |

`turn/completed` в App Server — уведомление протокола. Итоговый статус может означать завершение, прерывание или сбой. Прежде чем запускать развёртывание только по имени события, проверьте статус и бизнес-результат. См. [официальную документацию по событиям](https://learn.chatgpt.com/docs/app-server).

На этой странице не подтверждены единая конечная точка регистрации вебхуков Codex Cloud, заголовок подписи или контракт события `task.completed`. Поэтому здесь нет URL, заголовка или таблицы событий, представленных как официальный интерфейс. Если конкретный продукт предлагает вебхуки, интегрируйтесь по версионированной документации этого продукта.

## Когда полезен собственный обратный вызов

Одиночное задание CI обычно может продолжить работу, опираясь на код завершения и сохранённый вывод. Публичный приёмник ему не нужен только потому, что задание «асинхронное».

Если ваша система распределяет работу между процессами и по завершении задачи обновляет тикет, можно спроектировать такой внутренний поток:

```text
Ваша очередь → контролируемый исполнитель запускает SDK/CLI → сохраняет результат и статус
                                                          → ваша служба уведомлений → внутренний тикет
```

Это архитектурная рекомендация руководства, а не встроенная в SDK функция развёртывания. Границы среды выполнения и интеграции описаны в [обзоре SDK](/ru/guide/developer-platform/sdk-overview/).

## Что должен определять собственный протокол

- **Идентификация и целостность:** укажите, как получатель аутентифицирует отправителя по проверенной схеме; не выдумывайте «официальный заголовок подписи».
- **Стабильные идентификаторы и дедупликация:** записывайте идентификаторы задачи и события, а также номер попытки, чтобы повторная доставка не повторила внешнее действие.
- **Статус и версия:** различайте завершение выполнения, сбой, прерывание и бизнес-приёмку; записывайте версию полезной нагрузки.
- **Надёжный приём:** подтверждайте получение только после надёжного сохранения события или помещения его в очередь. При сбое повторяйте попытку, а не возвращайте успех с последующей потерей события.
- **Объём данных:** отправляйте только сводку результата и безопасные ссылки, необходимые последующим шагам; не допускайте попадания учётных данных в журналы.
- **Условия остановки:** установите предел повторов, путь передачи человеку и способ отменить последующие действия.

Это требования к проектированию, которые нужно реализовать и проверить, а не готовый пример. Страница не подключает систему тикетов, не отправляет сообщения и не создаёт процесс развёртывания автоматически.

## Минимальные сценарии приёмки

В тестовом окружении проверьте успешный результат, сбой выполнения, отмену, повторные события, недействительную идентификацию и временно недоступного получателя. Убедитесь, что повторная доставка создаёт только один бизнес-эффект, отмена не считается успехом, а непринятый сгенерированный результат не публикуется автоматически.

Для практики начните с кейсов [сортировки задач](/ru/cases/use-cases/team-automation/issue-triage-suggestions/) и [проверки ссылок по расписанию](/ru/cases/use-cases/team-automation/scheduled-link-check/). Статус материалов указан на каждой странице.
