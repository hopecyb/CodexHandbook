Здесь Codex превращается из разового действия в **шаги, которые команда может повторить, проверить и передать другому исполнителю**.

Скрипты определяют процесс, а конвейеры повторяют его по расписанию или в ответ на события.

На этой странице показано, как включить [codex exec](/ru/guide/developer-platform/non-interactive/codex-exec/) в shell, Makefile или конвейер CI.

## О чём эта страница

- Локальные скрипты и задания CI
- Управление промптами и секретами
- Сочетание с [автоматизацией Code Review](/ru/guide/developer-platform/ci-cd/code-review-automation/)

## Какую проблему это решает

«Скрипты и конвейеры» превращают «сегодня я сделал это вручную» в «команда сможет надёжно повторить то же самое позже».

Три главных свойства:

- повторяемость;
- проверяемость;
- удобство передачи работы.

## Почему команды не вставляют промпты в интерфейс CI

Такой подход трудно сопровождать:

- новые владельцы не знают исходного замысла;
- изменения логики нельзя провести через обычное Code Review;
- трудно понять, вызван ли сбой промптом, окружением или скриптом.

Промпты, скрипты и правила в Git дают автоматизации контроль версий.

## Распространённые заблуждения

### Сначала стабилизируйте процесс, потом автоматизируйте

Многие команды связывают всё в один процесс ещё до стабилизации промптов, ясных критериев успеха и строгих разрешений. В результате диагностика становится мучительной.

### Скрипты делают процесс повторяемым

Хороший скрипт превращает шаги, которые люди держат в памяти, в файлы, доступные для чтения и Review всей команде.

## Минимальный shell-скрипт

```bash
#!/usr/bin/env bash
set -euo pipefail
ROOT="$(git rev-parse --show-toplevel)"
cd "$ROOT"
PROMPT_FILE="prompts/ci/security-review.md"
codex exec --cd "$ROOT" --ephemeral "$(cat "$PROMPT_FILE")"
```

Храните `prompts/ci/security-review.md` в Git и проводите изменения через Review.

## Какие привычки стоит выработать сначала

Не пытайтесь охватить всё сразу. Сначала зафиксируйте три вещи:

1. Где хранятся файлы промптов
2. Как называется входной скрипт
3. Как определяется успех или сбой

После этого добавить журналы, схему и уведомления будет гораздо проще.

## GitHub Actions: используйте официальный Action

```yaml
jobs:
  codex-review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
      - name: Run review
        uses: openai/codex-action@v1
        with:
          openai-api-key: ${{ secrets.OPENAI_API_KEY }}
          prompt-file: prompts/ci/pr-review.md
```

:::caution
В GitHub Actions предпочитайте официальный `openai/codex-action`. Не предоставляйте API-ключ всему заданию, которое также выполняет код репозитория. Если последующему шагу нужно записать что-либо в PR, разделите право записи и ключ по разным заданиям и передавайте между ними артефакт с патчем.
:::

## Рекомендуемые уровни

| Уровень | Содержимое |
|---|---|
| Репозиторий | `prompts/`, `tools/run-codex.sh` |
| CI | Checkout только для чтения, закреплённая версия CLI, загрузка журналов как артефактов |
| Обратный вызов | Необязательный [вебхук](/ru/guide/developer-platform/webhooks/overview/) для обновления внутренних систем |

## Как принять решение

Хорошие кандидаты для скриптов или конвейеров:

- действия, которые вы регулярно повторяете;
- процессы, где каждый запуск должен идти одним и тем же путём.

Примеры: Review PR, сводки изменений, сканирование безопасности, проверка документации.

Не спешите переходить к полной автоматизации до стабилизации процесса. Обычно безопаснее сначала написать скрипт и только затем создать конвейер.

## Распространённые ошибки

- Динамический промпт из `${{ github.event.pull_request.body }}` без экранирования — это инъекция.
- Нет управления параллелизмом для одного PR, а повторные запуски расходуют квоту.
- Локально всё работает, но в CI не хватает зависимостей, например не выполняется `npm ci`.
- «Успех» означает лишь «завершено», а структурированное заключение не разбирается.
- Автоматизации слишком рано предоставили право записи.

## Границы безопасности

- Токен CI должен иметь минимальные привилегии; не разрешайте `git push` без отдельного задания подтверждения.
- Процессы для PR из форков, использующие секреты, требуют проверки безопасности (`pull_request_target`).

## Контрольный список приёмки

- [ ] Промпты и скрипты версионируются в Git.
- [ ] Если этого требует политика, сбой CI блокирует слияние.
- [ ] Срок хранения артефактов отвечает требованиям соответствия.
- [ ] Поведение совпадает с локальным `make review`.
