В первых попытках автоматизации часто предполагают, что Codex вернёт «вполне разумный текст». Для человека это удобно, для скрипта — нет.

Структурированный вывод решает прямую задачу: Codex возвращает результат в заданном вами формате.

Если неинтерактивная задача выдаёт только свободный текст, последующим шагам трудно определить успех, число проблем и их серьёзность. Структурированный вывод упрощает машинную обработку результата.

## О чём эта страница

- Когда требовать JSON, таблицу Markdown или фиксированные поля
- Как определять схему в промпте
- Что делать при ошибке разбора

## Распространённые заблуждения

### Структурированный вывод нужен следующему шагу

JSON и схема — не инженерная придирка. Они важны, когда скрипт оценивает результат, бот публикует комментарий или панель отображает данные. Нужна стабильная структура, а не догадки при каждом запуске.

### Стабильный формат ≠ надёжное заключение

Структурированный вывод гарантирует форму, но не правильность понимания.

Он решает задачу интерфейса вывода, а не постановки и проверки самой задачи.

## Простое разделение

- Свободный текст — для людей
- Структурированный вывод — для программ

Если следующий потребитель — `jq`, скрипт, панель, правило контрольного этапа или бот автокомментариев, не полагайтесь только на свободный естественный язык.

## Минимальный вариант

Зафиксируйте требования к формату в конце промпта:

```text
…(текст задачи)…

Требования к выводу:
- Выведи только один объект JSON без ограждения кода Markdown
- Поля: {"pass": boolean, "findings": [{"severity":"P0|P1|P2", "file":"", "message":""}]}
- Если проблем нет, findings должен быть пустым массивом
```

Разбор в оболочке (эскиз):

```bash
result=$(codex exec --cd . "$(cat prompts/structured-review.md)")
echo "$result" | jq -e '.pass == true'
```

## Типичные проблемы

### 1. Указано «вывести JSON», но не «только JSON»

Вводная фраза перед JSON ломает парсер.

### 2. Имена полей меняются каждый день

Как только от полей зависят скрипты, считайте схему интерфейсом.

### 3. Ожидание, что структура исправит нечёткую задачу

Она стабилизирует формат. Если задача неясна, JSON будет лишь стабильно неправильным.

## Рекомендуемый процесс

```text
Определить схему (версия v1)
    → промпт ссылается на файл схемы @schemas/review-output.json
    → запуск exec
    → jq / собственный валидатор
    → exit 1 при сбое
```

Для большого вывода потребуйте поле с путём к файлу: Agent записывает данные в `artifacts/`, а CI загружает артефакт.

## Как принять решение

Если следующий потребитель — программа, предпочитайте структуру.
Если результат предназначен главным образом для чтения и обсуждения людьми, свободного текста часто достаточно.

Когда результат передаётся другой программе, просите Codex стабильно возвращать согласованные поля.

## Сравнение с SDK

| | CLI + промпт JSON | SDK |

| Стоимость интеграции | Низкая | Средняя |
| Безопасность типов | Соглашения + валидация | Типы SDK |
| Лучше всего подходит для | Скриптов CI | Многопользовательских служб |

## Распространённые ошибки

- Модель добавляет пояснение, и разбор JSON завершается сбоем — подчеркните в промпте требование «только JSON».
- Схема меняется без повышения версии, и старый CI неверно разбирает результат.
- В журнал попадают секреты из полей JSON.
- При ошибке разбора не определено явное поведение завершения.

## Контрольный список приёмки

- [ ] Есть файл схемы или документированные поля.
- [ ] CI явно сообщает о сбое разбора.
- [ ] В `fixtures/` есть пример вывода для регрессионной проверки.
- [ ] Стратегия согласована с [кодами завершения](/ru/guide/developer-platform/non-interactive/exit-codes-and-retries/).
