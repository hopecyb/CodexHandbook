Если интерактивный `codex` — это диалог в процессе работы, то **`codex exec`** больше похож на передачу разового задания с получением результата после завершения.

Это основа [неинтерактивного режима](/ru/guide/cli/non-interactive-mode/): никакого диалога и уточнений во время выполнения — процесс заканчивается результатом или сбоем. Эта глава предназначена для интеграторов [платформы для разработчиков](/ru/guide/developer-platform/) и тех, кто впервые подключает Codex к скриптам или CI.

## О чём эта страница

- Чем `exec` отличается от интерактивного `codex`
- Минимальная форма команды и рабочий каталог
- Требования к подтверждениям и песочнице при выполнении без наблюдения

## Что делает `exec`

Рассматривайте `codex exec` как способ:

- выдать разовое рабочее задание;
- выполнить его до конца и вернуть результат.

После того как инструкции заданы, команда выполняет их, возвращает результат и завершает работу.

Поэтому она подходит, когда:

- границы задачи зафиксированы;
- уточнения в процессе не нужны;
- выполнение потребуется повторять.

## Зачем нужна эта команда

В CI вы не ведёте диалог с Codex и не ожидаете, что он десять раз остановится ради уточнений.

Типичные применения `codex exec`:

- автоматизация Code Review;
- задания по расписанию;
- пакетные скрипты;
- отдельные шаги анализа или генерации в конвейере.

Команда подходит, когда **границы задачи уже ясны**. Пока вы исследуете варианты, обычно лучше интерактивный режим.

:::note
**Имена команд и флаги соответствуют официальному CLI.** После обновления выполняйте `codex --help` и `codex exec --help`.
:::

## Минимальный рабочий вариант

```bash
cd /path/to/repo
codex exec --cd . "Только чтение: сравни diff текущей ветки с main, перечисли три главных риска безопасности, не изменяй файлы"
```

По умолчанию выполнение происходит в песочнице только для чтения. Чтобы явно разрешить запись в рабочую область:

```bash
codex exec --cd . --sandbox workspace-write "Исправь падающий тест; изменяй только src/auth и tests/auth"
```

Ход выполнения записывается в `stderr`, а итоговый ответ — в `stdout`. Используйте `--json` для полного машиночитаемого потока событий, `-o` / `--output-last-message` — чтобы записать в файл только итоговый ответ, а `--output-schema` — когда последующему коду нужны стабильные поля.

Основные принципы:

- в shell-скриптах сначала переходите через `cd` в чистый Worktree;
- храните промпты в версионируемом каталоге `prompts/` или в heredoc, чтобы избежать проблем с экранированием в оболочке;
- в CI определяйте успех или сбой по **коду завершения**.

## Реальность, о которой легко забыть

В интерактивном режиме можно сказать: «Я имел в виду другое».
В `exec`, **если первый промпт неверен, всё выполнение может пойти не по плану**.

В промптах для `exec` точнее обычного указывайте:

- что нужно сделать;
- чего делать нельзя;
- формат вывода;
- критерии завершения;
- как сообщить о сбое.

## Распространённые заблуждения

### `exec` подходит для фиксированных задач

Многие считают его «продвинутым режимом CLI».

Точнее сказать, что он предназначен для **стабильных, повторяемых** запусков.

### Короткий промпт не всегда понятен

В интерактивном режиме неясную формулировку можно уточнить позже.

В `exec` короткий промпт без границ, ограничений и критериев успеха чаще не элегантен, а рискован.

## Рекомендуемый процесс

```text
Подготовить репозиторий (checkout, установка, токен только для чтения)
    → Зафиксировать версию промпта (git sha)
    → codex exec
    → Собрать stdout / артефакты
    → Ненулевой код завершения означает сбой CI; не повторять бесконечно
```

См. [«Скрипты и конвейеры»](/ru/guide/developer-platform/non-interactive/scripts-and-pipelines/).

## Как воспринимать `exec`

- Как команду для программируемого выполнения разовой задачи
- Как инструмент для скриптов, CI или cron

Поэтому многие команды помещают её за `make review`, GitHub Actions, cron или кнопками внутренней платформы.

## Сравнение с интерактивным режимом

| | Интерактивный `codex` | `codex exec` |
|---|---|---|
| Уточнения | Несколько реплик | Всё должно быть понятно заранее |
| Подтверждение | Человек присутствует | Политику нужно заранее ужесточить |
| Лучше всего подходит для | Обучения и исследования | CI и cron |

## Если вы не уверены

- Требования ещё исследуются и вы можете часто менять решение: выберите интерактивный режим.
- Задача стала шаблоном, который нужно многократно запускать: используйте `codex exec`.

`codex exec` подходит для уже ясных задач, которые имеет смысл повторять. Если вы пока размышляете вслух, не спешите переводить их в неинтерактивный процесс.

## Распространённые ошибки

- Помещать длинную историю чата в один вызов exec
- Использовать в CI токен с правом записи и включать в промпт неочищенный текст PR
- Не фиксировать версию CLI и внезапно ломать конвейер
- Игнорировать ненулевые коды завершения и отмечать проверку зелёным
- Втискивать сложные задачи, требующие человеческого суждения, в выполнение без наблюдения

## Границы безопасности

- Выполнение без наблюдения означает ослабленное [подтверждение человеком](/ru/cases/workflows/human-approval-patterns/); по умолчанию используйте только чтение.
- См. [учётные данные безопасности](/ru/guide/developer-platform/ci-cd/code-review-automation/#разрешения-и-безопасность) — перекрёстную ссылку в этой же главе.

## Контрольный список приёмки

- [ ] Локально и в CI используется один и тот же файл промпта.
- [ ] CI правильно обрабатывает коды завершения.
- [ ] Журналы не содержат ключей и PII.
- [ ] Песочница и правила не слабее, чем при интерактивной разработке.
