**Дочерний Agent (Subagent)** — это независимая рабочая единица, которую основной Agent запускает для решения конкретной подзадачи. У неё собственный контекст; после завершения она возвращает выводы и доказательства в основной тред. Ответственность за общие решения и окончательную приёмку по-прежнему несёт основной Agent.

![Архитектура координации дочерних Agent в Codex: основной Agent распределяет ограниченные подзадачи, дочерние Agent возвращают доказательства, а основной Agent объединяет и проверяет результаты](/illustrations/flow-subagents.webp)

## Сначала разберитесь в трёх уровнях

| Уровень | Изолирован? | Что это означает |
|---|---|---|
| Контекст диалога | Да | Каждый дочерний Agent сосредоточен на собственной задаче и не обязан получать все подробности основного треда |
| Режим песочницы и разрешений | Наследуется | Независимое выполнение не даёт дочернему Agent дополнительных разрешений |
| Файлы рабочей области | Необязательно | Несколько Agent могут видеть одну рабочую область; параллельная запись в один файл приведёт к конфликту |

Самое важное: **изоляция контекста не означает изоляцию файлов.** Для параллельного изменения кода сначала разделите зоны ответственности по каталогам, компонентам или Worktree.

## Где это доступно сейчас

В текущих версиях Codex возможность запускать дочерние Agent предоставляется по умолчанию, а их активность можно просматривать в соответствующих интерфейсах настольного App, CLI и IDE. Детали интерфейса меняются, но устойчивый способ использования таков: явно попросите Codex передать независимые подзадачи, а объединение результатов оставьте основному треду.

В CLI команда `/agent` позволяет просматривать треды и переключаться между ними. В поддерживаемых интерфейсах IDE отображаются фоновые Agent, а настольный App показывает активность тредов в задаче. Наличие конкретного элемента управления зависит от текущего клиента и возможностей учётной записи.

## Когда задачу стоит разделить

Рассмотрите выделение подзадачи, если выполняются хотя бы два из трёх условий:

1. Её можно описать независимо, без частой синхронизации с подробностями основной работы.
2. У неё есть ясный результат: например, список файлов, результаты тестов или краткое заключение.
3. Она может выполняться параллельно другим задачам либо отдельное глубокое исследование заметно уменьшит шум в основном треде.

### Что подходит для параллельной работы

- Отдельно исследовать клиентскую часть, серверную часть и покрытие тестами в режиме только для чтения
- Параллельно изучить несколько независимых падающих тестов
- Собрать доказательства для двух технических решений по отдельности
- Поручить специализированной роли проверку безопасности, анализ производительности или сверку документации

### Что лучше оставить в основном треде

- Требования ещё не уточнены, поэтому нужно постоянно общаться с пользователем
- Несколько шагов должны выполняться строго последовательно
- Изменения сосредоточены в одном файле или фрагменте кода
- У подзадачи нет ясного критерия завершения — предлагается лишь «посмотреть в целом»

Дочерние Agent увеличивают расход токенов и стоимость объединения результатов. Небольшую задачу, которую можно выполнить в одном ясном треде, не нужно распараллеливать только ради параллельности.

## Ответственность основного Agent сохраняется

Основной Agent всегда должен отвечать за четыре аспекта:

- Общую цель, ограничения пользователя и окончательные решения
- Границы подзадач и владение файлами
- Выбор при противоречии между результатами
- Тесты и сборку после объединения, а также описание рисков

Сообщение дочернего Agent «готово» означает только завершение подзадачи, но не доказывает завершение всей работы.

## Составьте проверяемый контракт делегирования

Ниже приведён пример исследовательской задачи только для чтения:

```text
Запусти один дочерний Agent для анализа логики обновления сеанса в packages/auth в режиме только для чтения.

Область: packages/auth и соответствующие тесты; файлы не изменять.
Вопрос: может ли старый token снова использоваться после ошибки обновления?
Результат: вывод, ключевые файлы и номера строк, способ воспроизведения, рекомендуемый тест.
Проверка: каждый вывод должен подтверждаться исходным кодом или существующими тестами.
Ответ: не более 500 слов; решение об изменениях принимает основной тред.
```

Здесь чётко указаны шесть аспектов: зона ответственности, область просмотра, вопрос, запреты, способ проверки и тот, кто принимает решение.

## Пример трёх параллельных направлений

Предположим, во входе в систему периодически возникает регрессия. Основной Agent может разделить исследование так:

| Подзадача | Разрешения и область | Результат |
|---|---|---|
| A: путь в коде | Только чтение `src/auth/` | Цепочка вызовов от точки входа до ветви с ошибкой |
| B: доказательства в тестах | Только чтение тестов и журналов | Минимальный тест со стабильным воспроизведением |
| C: недавние изменения | Только чтение связанной истории Git | Наиболее вероятное изменение, вызвавшее регрессию, и обоснование |

Получив все три результата, основной Agent должен сначала сопоставить доказательства и только затем выбрать способ исправления. Не поручайте A, B и C одновременно изменять `src/auth/session.ts`.

## Как изолировать параллельную запись

Снижайте риск конфликтов в следующем порядке:

1. Разделите задачи записи между непересекающимися каталогами или компонентами.
2. Выделите для параллельной реализации отдельные Worktree или ветки.
3. Явно перечислите файлы, которые разрешено изменять каждому Agent.
4. Поручите основному Agent единое объединение и повторную проверку после него.

Даже если тесты каждой подзадачи проходят отдельно, объединённый результат может оказаться нерабочим, поэтому итоговую проверку нельзя пропускать.

## Контрольный список приёмки

- Отвечает ли результат на исходный вопрос, не расширяя область
- Приложены ли проверяемые доказательства: расположение файлов, журналы или тесты
- Соблюдены ли ограничения на чтение, каталоги и команды
- Противоречат ли результаты друг другу и разрешены ли эти противоречия явно
- Перезапущены ли полные тесты и сборка после объединения
- Указаны ли нерешённые вопросы и оставшиеся риски

## Сочетание с другими возможностями

- **Skill** закрепляет метод подзадачи и формат результата — например, контрольный список проверки кода.
- **MCP** предоставляет дочернему Agent контролируемые внешние инструменты или данные.
- **Hook** добавляет защитные правила при запуске, остановке или вызове инструментов дочерним Agent.
- **Worktree** изолирует параллельные изменения файлов. Он решает проблему конфликтов рабочей области, а не контекста.
