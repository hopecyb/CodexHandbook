Расширение IDE особенно удобно для **небольших и точечных** изменений: выделите фрагмент кода, объясните намерение, и Codex внесёт правку с учётом соседнего контекста. Здесь рассматривается, как с помощью выделения и открытых файлов сузить область и не изменить не то место.

Назначение выделения простое: указать Codex, на чём сосредоточиться, не позволяя самостоятельно расширять область задачи.

## На этой странице

- Как выбрать между выделением, целым файлом и путём через `@`
- Как организовать контекст при рефакторинге нескольких файлов
- Как избежать изменений множества посторонних файлов

## Три способа ограничить область

| Способ | Когда использовать | Пример |
|---|---|---|
| **Выделение** | Одна функция, один компонент, место рядом со стеком ошибки | Выделить `parseUser()` и запросить обработку `null` |
| **Открытые файлы** | Нужно понять несколько взаимосвязанных мест в файлах | Открыть `auth.ts` и `auth.test.ts` |
| **Путь через `@`** | Файл в другом каталоге или ещё не открыт | Согласовать типы `@src/api/client.ts` с серверной частью |

Подробнее: [Контекст файлов и каталогов](/ru/guide/context/file-and-folder-context/)

## Минимальный рабочий процесс

1. Выделите **минимальный относящийся к задаче фрагмент** — обычно 10–80 строк — и укажите в промпте цель и [критерии завершения](/ru/prompts/define-done/)
2. Если затронуты вызывающие стороны, откройте или добавьте через `@` ещё 1–2 вышестоящих файла
3. Попросите: «Изменяй только файлы, относящиеся к X; сначала перечисли файлы, которые собираешься изменить»
4. Принимайте блоки по одному в diff IDE, а не все сразу

## Задачи с несколькими файлами

```text
Открыть: файл реализации + файл тестов + определения типов
Выделение: необязательно — можно начать с функции входа
Промпт: указать границы модуля и каталоги, которые запрещено менять
```

Для крупного рефакторинга лучше использовать [Worktree в Desktop App](/ru/guide/desktop-app/worktrees/) или [режим планирования](/ru/guide/agent-work/planning/). IDE удобнее для завершения работы и небольших коммитов.

## Частые вопросы

### 1. Нужно ли всегда выделять код?

Необязательно. Но если вы уже знаете, что ключевой участок невелик, выделение обычно надёжнее фразы «измени эту функцию» без дополнительных указаний.

### 2. Большее выделение не всегда безопаснее

Слишком большое выделение снова размывает границы, а слишком маленькое может не содержать нужного контекста. Практический критерий — «ровно столько, сколько необходимо».

### 3. Чем открытый файл отличается от пути через `@`?

Различие простое:

- **Открытый файл** показывает, что вы сейчас просматриваете
- **Путь через `@`** явно требует включить конкретный файл

Главная цель выделений и открытых файлов — не добавлять в задачу постороннюю область.

## Сочетание с Review

Перед принятием сверьтесь с разделом [Проверка diff](/ru/guide/quality/review-diffs/):

- Изменились ли только согласованные файлы
- Нет ли неожиданных удалений за пределами выделения
- Покрывают ли тесты новую ветвь

Возможности продукта: [Review изменений в IDE](/ru/guide/ide/reviewing-changes/)

## Частые ошибки

| Ошибка | Последствие |
|---|---|
| Выделить целый файл на тысячи строк | Контекст расходуется впустую, область изменений становится слишком большой |
| Ничего не выделить и попросить только «оптимизировать» | Модель самостоятельно расширяет область задачи |
| Принять все предложения, не прочитав diff | Отклонение стиля или уязвимость безопасности |
