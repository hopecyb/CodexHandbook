На одном небольшом примере корзины покупок выполните четыре вида работы: объясните код, исправьте ошибку, проведите Review различий и передайте свидетельства. Предварительно осваивать все клиенты, конфигурацию или возможности нескольких Agent не требуется.

Предварительные условия: вы умеете читать простой JavaScript и выполнять тесты Node.js в локальном терминале. Эталонная среда — Node.js 22.16.0; устанавливать сторонние зависимости не нужно. Можно использовать CLI, IDE или другую точку входа с доступом к локальным файлам и терминалу; поведение тестов определяется Node.js.

## Подготовка кода и каталога записей

Используйте `examples/complete-workflows/developer/verified-bug-fix/` из [исходного репозитория руководства](https://github.com/hopecyb/CodexHandbook). Сначала прочитайте `brief.md` и `README.md`, не открывая `solution/`. Полный учебный процесс описан в разделе [Исправление ошибки с проверкой](/ru/cases/use-cases/software-development/fix-a-bug-with-verification/).

Выполните в каталоге упражнения:

```sh
# work/ ещё не должна существовать; если там уже находится ваше упражнение, выберите другое имя и не перезаписывайте его.
cp -R starter work
mkdir -p evidence
```

Исправляйте код в `work/`, сохранив в `starter/` исходное состояние с ошибкой, а в `solution/` — эталонный ответ. Сохраните приведённые ниже шаблоны в `evidence/`. Загружаемые шаблоны руководства не содержат полный код и должны использоваться вместе с упражнением из указанного репозитория.

| Этап | Входные данные | Результат | Критерии завершения |
|---|---|---|---|
| 1. Чтение кода | brief и starter | code-map.md | Входные данные, путь данных, сбой и первопричина подтверждаются файлами |
| 2. Исправление и проверка | Первопричина и неизменённые тесты | work/cart.js, red.txt, green.txt | Сначала воспроизведён сбой, затем пройден тот же набор тестов |
| 3. Review различий | Изменение и вывод двух запусков тестов | review.md и различия реализации | Ожидания не изменены, API сохранён, посторонних изменений нет |
| 4. Передача | Свидетельства первых трёх этапов | handoff.md | Следующий исполнитель может найти текущие файлы и повторить следующий шаг |

## 1. Сначала прочитайте код и составьте проверяемую карту

[Загрузите шаблон чтения кода](/downloads/developer-path/code-map-template.md). Попросите Codex прочитать `brief.md`, `starter/cart.js` и `starter/cart.test.js` и, пока только в режиме чтения, объяснить точку входа, путь данных, входные данные, вызывающие сбой, фактическое и ожидаемое значение, строку первопричины и ограничения области.

Сохраните результат в `evidence/code-map.md`. В упражнении всего два ключевых файла, поэтому сложная архитектурная диаграмма не нужна. Критерии завершения: ясно объяснено, что `10` означает десять процентов, почему ошибочная реализация превращает промежуточную сумму 40 в итог -360 и почему правильный результат равен 36.

При проверке можно обратиться к [авторской справке чтения](/downloads/developer-path/code-map-reference.md), но собственные выводы всё равно нужно сверить с настоящим кодом. Только после успешной проверки изменяйте реализацию.

## 2. Сохраните красный тест, затем внесите минимальное исправление

Все следующие команды выполняются в каталоге `verified-bug-fix/`:

```sh
node --test work/cart.test.js > evidence/red.txt 2>&1
```

Ожидаемый код завершения — 1, один из трёх тестов падает. Откройте `evidence/red.txt` и убедитесь, что тест скидки показывает фактическое значение -360 и ожидаемое 36. Если проходят все тесты, сначала проверьте, не использован ли эталонный ответ и не был ли файл изменён заранее; не продолжайте, считая красный тест воспроизведённым.

В описании задачи можно сразу задать полную область выполнения:

```text
На основании brief.md и evidence/code-map.md исправь только преобразование процентов в work/cart.js.
Сохрани сигнатуру функции и утверждения work/cart.test.js без изменений, не добавляй зависимости и не выполняй рефакторинг.
После завершения выполни node --test work/cart.test.js и сохрани настоящий вывод в evidence/green.txt.
Если результат отличается от ожидаемого, сохрани свидетельство сбоя и найди причину; не меняй утверждения ради соответствия реализации.
Передай описание изменения и результат теста, ничего не фиксируй и не отправляй.
```

Критерии завершения: все три исходных теста проходят, код завершения равен 0, а изменение затрагивает только первопричину. Команда теста может создать журнал даже при сбое, поэтому само наличие green.txt не доказывает успешность.

## 3. Проведите Review различий и пропусков

[Загрузите шаблон Review](/downloads/developer-path/review-template.md) и укажите фактическую область сравнения. В этом упражнении сравниваются сохранённая `starter/` и ваша `work/`; по умолчанию не используется сравнение с main и не предполагается какое-либо состояние незафиксированных изменений репозитория.

```sh
diff -u starter/cart.js work/cart.js
diff -u starter/cart.test.js work/cart.test.js
```

Первая команда должна показать различие в преобразовании процентов. Код завершения 1 означает наличие различий, а не ошибку команды. Вторая команда не должна выводить ничего и должна завершиться с кодом 0. Попросите Codex провести Review только для чтения на основании настоящих различий и журналов красного и зелёного тестов, а затем записать находки, свидетельства, непокрытые случаи и решение в `evidence/review.md`.

Критерии завершения: тесты не ослаблены, API не изменён, лишние зависимости и посторонние правки отсутствуют. Явно укажите, что упражнение не покрывает точность денежных вычислений, налоги и недопустимые входные данные; успешность трёх тестов не доказывает безопасность производственной среды. Для сравнения доступна [авторская справка Review](/downloads/developer-path/review-reference.md).

## 4. Подготовьте передачу и восстановите состояние по файлам

[Загрузите шаблон передачи](/downloads/developer-path/handoff-template.md). В `evidence/handoff.md` запишите текущий каталог, изменённые файлы, всё ещё действующие ограничения, пути к свидетельствам, следующую команду и ожидаемый результат. В настоящем проекте Git также нужно записать текущую ветку, commit и состояние рабочей области.

Задачу только для чтения после передачи можно сформулировать так:

```text
Прочитай evidence/handoff.md и сначала проверь, соответствует ли текущее содержимое work/ описанию передачи.
Выполни node --test work/cart.test.js в корне упражнения и запиши фактический код завершения и сводку.
Сравни реализацию и тесты в work и starter. Если состояние отличается, укажи различия и не полагайся на старый зелёный тест.
Больше не изменяй код, ничего не фиксируй и не отправляй.
```

Эту задачу можно выполнить в новом треде или передать другому участнику для проверки. Если вы просто самостоятельно открыли новую задачу, это считается учебным восстановлением, а не независимым человеческим Review. Эталонный формат см. в [авторской записи передачи](/downloads/developer-path/handoff-reference.md).

Критерии завершения: одного файла передачи достаточно, чтобы найти код, тесты и границы и фактически получить текущий результат. Если этот запуск не выполнялся, оставьте в записи состояние «ожидает проверки следующим исполнителем».

## К какому шагу вернуться при проблеме

- Файл не найден: проверьте текущий каталог терминала и наличие `work/`, затем вернитесь к подготовке.
- Нет красного теста: проверьте исходное состояние и тесты; не заменяйте воспроизведение зелёным тестом эталонного ответа.
- Тест проходит только после изменения: восстановите исходные утверждения и вернитесь к анализу первопричины.
- Найдены посторонние изменения: сначала сохраните различия, сузьте исправление и повторно выполните тесты.
- Передача не соответствует файлам: считайте текущие файлы источником истины, обновите запись и только затем продолжайте.

В настоящем проекте добавьте к этой структуре свидетельств принятые в репозитории lint, проверку типов и полный набор тестов. Их необходимость и конкретные команды определяются документацией реального проекта; в этом упражнении дополнительных проверок нет, поэтому нельзя заявлять об их успешном прохождении.
