После завершения задачи Cloud сначала проверьте сводку и diff. Создавайте Pull Request, только если результат соответствует области и критериям проверки; иначе продолжите исправления в том же чате.

## От задачи к PR

```text
Выбрать среду и начальную ветку
  → Выполнить задачу Cloud
  → Проверить сводку, журналы и diff
  → При необходимости отправить follow-up
  → Create Pull Request
  → CI + дополнительный Review Codex + ручной Review
  → Человек решает, выполнять ли слияние
```

Явно укажите в промпте «создать PR, но не выполнять слияние», однако не полагайтесь только на ограничение естественным языком. В репозитории также должны быть включены защита веток и required checks.

## Многоразовый шаблон задачи

```text
Цель: исправить регрессию тайм-аута входа из #42.
Начальная точка: main.
Область: только packages/auth/** и соответствующие тесты.
Запрещено: обновлять зависимости, менять публичный API, записывать напрямую в main.
Проверка: pnpm test --filter auth; pnpm typecheck.
Результат: создать PR в main, но не выполнять слияние.
В описании PR указать первопричину, сводку изменений, команды тестирования и результаты, риски и способ отката.
```

## Проверка перед созданием

- [ ] Начальный commit выбран правильно, локальные неотправленные входные данные не пропущены
- [ ] Diff содержит только изменения в области задачи
- [ ] Имя новой ветки понятно и не перезаписывает чужую работу
- [ ] Тесты действительно выполнялись, а ошибки не скрыты в сводке
- [ ] Нет учётных данных, временных журналов, кешей и постороннего форматирования
- [ ] Крупные изменения разделены на независимо проверяемые PR

## Описание PR должно отвечать как минимум на пять вопросов

1. Зачем нужно изменение;
2. Что фактически изменено;
3. Как это проверено, включая команды и результаты;
4. Каковы риски, ограничения и способ отката;
5. Что явно не делалось.

Для изменений интерфейса приложите настоящий снимок экрана, для изменений поведения — шаги воспроизведения, а для миграций — сведения о совместимости и откате.

## После создания

Дождитесь required checks, запросите дополнительный Review через `@codex review`, затем попросите человека с нужным контекстом проверить основной diff. Для исправлений передавайте конкретные комментарии в ту же ветку PR; не создавайте постороннюю ветку с дублирующим результатом.

Создание PR и слияние — две отдельные границы разрешений. Возможность Cloud создать PR не означает, что он должен обходить правила слияния команды.
