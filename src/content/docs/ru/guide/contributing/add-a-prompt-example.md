Примеры промптов хранятся в каталоге [`examples/prompts/`](https://github.com/hopecyb/CodexHandbook/tree/main/examples/prompts) в корне репозитория; на них ссылаются страницы руководства. См. [систему промптов, Skill и кейсов](https://github.com/hopecyb/CodexHandbook/blob/main/docs/planning/examples-system.md).

## О чём эта страница

Типичные затруднения:

- Какой промпт «стоит включить»
- В каком формате другие смогут его повторно использовать

Страница объясняет, как добавить материал, который **другие смогут попробовать, изучить и воспроизвести**.

## Критерии включения

Мы собираем не вдохновляющие фразы, а воспроизводимые примеры с контекстом, границами и критериями приёмки.

Хороший пример отвечает на вопросы:

- Когда его применять
- Что именно написать
- Как затем оценить успех

Остроумная однострочная команда без предварительных условий и проверки — это заметка, а не пример.

## Имена файлов

```text
examples/prompts/<category>/<slug>.md
```

Примеры `category`: `development`, `research`, `meta-workflows`, `team`.

## Обязательные метаданные (YAML frontmatter)

```yaml
---
id: prompt.fix-bug-with-tests
title: Исправить ошибку и добавить тесты
content_type: prompt
audience: [beginner, developer]
difficulty: beginner
products: [app, cli, ide]
capabilities: [planning, file-editing, testing]
status: draft
last_verified: YYYY-MM-DD
---
```

## Обязательные разделы

1. **Сценарий использования**
2. **Предварительные условия** — разрешения, ветка и файлы контекста
3. **Рекомендуемый промпт** — полный и готовый к копированию
4. **Критерии приёмки** — объективно проверяемый список
5. **Распространённые причины сбоя**
6. **Связанные страницы руководства** — ссылки на `src/content/docs/`

Дополнительно можно включить минимальный вариант, учебный разбор и заменяемые переменные.

## Распространённые заблуждения

### Не прячьте промпт

Контекст и теория полезны, но сначала приведите **готовый к копированию промпт**, затем предварительные условия, причины сбоев и объяснение.

### Один запуск ≠ готовый пример

Читатели не знают ваших неявных предположений. Укажите:

- через какой продукт выполняется задача;
- какие нужны файлы, снимки экрана или контекст;
- предполагаются ли разрешёнными правки, команды и сеть.

### Не добавляйте в примеры реальные секреты

Реальным токенам, учётным записям, внутренним URL и данным клиентов не место в открытом репозитории.

Объясняйте метод, а не свою производственную среду.

## Пример критериев приёмки

```markdown
## Критерии приёмки

- [ ] Ранее падавший тест проходит
- [ ] Согласованный набор тестов проходит
- [ ] Diff затрагивает только файлы, относящиеся к задаче
- [ ] `git push` не выполнялся
```

## Планка качества

- Чёткая цель и определение завершённости
- Явно указанные границы разрешений и безопасности
- Отсутствие реальных ключей и PII
- Для статуса `verified` нужна [независимая проверка](/ru/guide/contributing/verify-technical-content/)

## Процесс добавления

1. Определите реальный класс задач, который решает пример.
2. Напишите готовый к копированию промпт.
3. Укажите минимальные предварительные условия и границы.
4. Определите признаки успеха.
5. Проверьте отсутствие секретов и правильность каталога.

## Контрольный список PR

- [ ] Если индекс поддерживается, путь нового файла добавлен в `examples/README.md`.
- [ ] На пример ссылается хотя бы одна страница кейса или процесса — необязательно, но рекомендуется.

Хороший пример промпта позволяет другому человеку воспроизвести сходный результат.
