**Личные предпочтения** — это настройки, которые действуют на вашем компьютере в разных проектах: модель по умолчанию, тема, привычки подтверждения, пути к личным Skill и другое. В отличие от `AGENTS.md` в репозитории, личные предпочтения **не должны** предполагать такие же настройки у коллег.

## Содержание

- Что хранить на личном уровне, а что — на уровне проекта
- Как переключать сценарии с помощью [Profile](/ru/guide/customization/configuration/profiles/)
- Как не допустить попадания ослабленных личных настроек в репозиторий команды

Обзор приоритетов: [Персонализация и конфигурация проекта](/ru/guide/customization/) · [Область действия и приоритет](/ru/guide/customization/agents-md/scope-and-precedence/)

## Зачем выделять этот уровень

Многие поначалу смешивают три категории:

- Как лично мне удобно работать
- Как принято работать в этом репозитории
- Что обязательно требует компания или команда

Если их не разделить, возникают проблемы:

- На вашем компьютере всё удобно, но коллега не может воспроизвести результат
- Вы считаете, что правило действует, хотя на самом деле его обеспечивает только локальная настройка
- Ослабленные настройки случайно переходят в более строгий проект

## Что подходит для личных предпочтений

| Содержимое | Пример |
|---|---|
| Модель и уровень рассуждений по умолчанию | Возможности личного компьютера и тарифа |
| Тема UI, шрифт, уведомления | [Настройки](/ru/guide/desktop-app/settings/) настольного App |
| Личный MCP — закрытый инструмент | Локальная база данных только для чтения, с осторожным предоставлением доступа |
| Путь к личной библиотеке Skill | Не конфликтует с Plugin команды |
| Псевдонимы терминала, привычный стартовый каталог `codex` | См. [Конфигурация CLI](/ru/guide/cli/configuration/) |

## Что из правил команды нельзя хранить только на личном уровне

- Стиль кода, команды тестирования, структура каталогов → **проектный `AGENTS.md`**
- Обязательная политика песочницы → **конфигурация проекта или управляемая политика организации**
- Требования соответствия для репозитория клиента → **документация + CI**, а не личная память

## Рекомендуемые практики

1. **Разделяйте рабочий и личный Profile**: для проекта клиента используйте строгий Profile, а для учебного проекта допустим более свободный
2. **В новом репозитории сначала прочитайте правила проекта**, а затем решайте, нужно ли временно переопределить личное значение по умолчанию
3. **Регулярно очищайте** личные MCP и Skill, удаляя неиспользуемые сторонние источники
4. При смене компьютера или переустановке экспортируйте список настроек без значений ключей

## Распространённые заблуждения

### 1. Удобную привычку не всегда следует делать глобальным значением по умолчанию

Ослабленная личная настройка может не подходить для проекта клиента или командного репозитория.

### 2. Личные предпочтения и правила проекта примерно одинаковы?

Между ними большая разница.  
Личное предпочтение означает «мне удобно так», а правило проекта — «в этом репозитории всем следует по возможности работать так».

### 3. Отсутствия проблем на моём компьютере недостаточно, чтобы признать настройку правильной

Более подходящие критерии:

- Она не загрязняет репозиторий
- Она не зависит от известного только вам значения по умолчанию
- Она не приводит к ошибке при переходе в строгий проект

## Как понять, подходит ли личный уровень

Если вы сомневаетесь, спросите себя:

1. Это привычка, важная только для меня?
2. Повлияет ли она на способность других воспроизвести результат?
3. Уместно ли переносить её во все проекты?

Если второй или третий ответ указывает на риск, не устанавливайте настройку как глобальную без необходимости.

Личные предпочтения делают работу удобнее именно для вас. Они не заменяют правила команды, а ослабленные настройки не следует переносить во все проекты.

## Связь с памятью

Если продукт предоставляет Memory или постоянные предпочтения, см. [Память и постоянный контекст](/ru/guide/customization/memories-and-persistent-context/). Память подходит для стабильных привычек, но **ограничения конкретного проекта по-прежнему должны определяться файлами репозитория**.

## Распространённые ошибки

- Жёстко записать ключ API компании в личной конфигурации
- Глобально автоматически подтверждать shell-команды при работе с кодом клиента
- После clone репозитория жаловаться, что у коллеги «не действуют правила», которые никогда не добавлялись в репозиторий

- [ ] В репозитории нет личных ключей
