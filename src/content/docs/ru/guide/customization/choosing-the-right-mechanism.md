Многие проблемы команд возникают потому, что **информация помещена не туда**: правило, которое должно храниться в репозитории, остаётся в чате; процесс, который следует оформить как Skill, записан в `AGENTS.md`; данным, для которых достаточно чтения, предоставлен MCP с широкими разрешениями.

Здесь рассматривается практический вопрос:

> Если вы понимаете, что ситуация будет повторяться, на каком уровне следует её закрепить?

## Краткая таблица

| Механизм | Для чего подходит лучше всего |
|---|---|
| Одноразовый промпт | Цель, ограничения и критерии приёмки только текущей задачи |
| `AGENTS.md` | Правила совместной работы и долговременные ограничения на уровне репозитория |
| Память | Личные предпочтения или небольшое число нечувствительных фактов, повторяющихся между сеансами |
| Skill | Повторно используемый рабочий процесс, контрольный список или специализированная методика |
| MCP | Доступ к внешним инструментам, источникам данных и системным возможностям |

Если этой таблицы недостаточно, используйте следующую схему.

## Пять шагов выбора

### 1. Информация действует только в текущей задаче

Поместите её в **промпт текущей задачи**.

Подходящие примеры:

- «В этот раз изменяй только `docs/`, код не трогай»
- «Подготовь сводку на русском языке и в конце добавь один вопрос для подтверждения»
- «Сначала проанализируй причину, не изменяй файлы сразу»

Неподходящие примеры:

- Команда всегда требует выполнять `pnpm test`
- В репозитории есть запрещённый для изменений каталог
- Каждая проверка PR должна возвращать результат по одному шаблону

Такие долговременные правила следует закрепить глубже.

### 2. Это правило проекта или личная привычка?

Если правило должны знать **все участники**, поместите его в [`AGENTS.md`](/ru/guide/customization/agents-md/what-is-agents-md/).

Например:

- Команды тестирования, lint и сборки
- Каталоги, которые нельзя изменять
- Правила сообщений commit или приёмки PR
- Особые соглашения для разных подкаталогов Monorepo

Если это только **ваше личное предпочтение** — например, «объясняй по-русски» или «сначала давай вывод, затем подробности», — лучше использовать [память](/ru/guide/customization/memories-and-persistent-context/) или личную конфигурацию.

Практическое правило:

- То, что должно проходить Review в PR, прежде всего храните в репозитории
- Личный уровень подходит только для того, что необязательно видеть другим

### 3. Это правило или последовательность шагов?

Документами трудно пользоваться, когда правила и процедуры смешаны.

| Если это… | Лучше использовать |
|---|---|
| «Не выполняй push непосредственно в main» | `AGENTS.md` |
| «При Review сначала проверь тесты, затем риски, затем регрессии» | Skill |
| «Перед выпуском выполни эти четыре команды» | Skill или скрипт |
| «Разрешён доступ только к данным Issue в режиме чтения» | MCP + конфигурация разрешений |

Различайте два вопроса:

- **Правило** отвечает: «Что можно и чего нельзя делать?»
- **Процедура** отвечает: «Как обычно выполняется задача этого типа?»

Повторно используемую процедуру обычно лучше оформить как [Skill](/ru/skills/overview/).

## Типичные сочетания вместо взаимоисключающего выбора

Зрелая команда обычно сочетает механизмы, а не ограничивается одним.

### Сочетание 1: `AGENTS.md` + Skill

Подходит для проверки кода, подготовки выпуска и диагностики сбоев.

Распределение ответственности:

- В `AGENTS.md` записываются жёсткие ограничения: запрет автоматического слияния, обязательные проверки
- Skill описывает процесс: как проводить Review, в каком формате выдавать результат, как классифицировать проблемы

### Сочетание 2: Skill + MCP

Подходит для чтения задач, запросов к базе данных, загрузки макета или подготовки еженедельного отчёта.

Распределение ответственности:

- Skill определяет порядок выполнения и формат результата
- MCP задаёт, к чему можно подключиться, что читать и что изменять

Иными словами:

> Skill напоминает рабочую инструкцию, а MCP — подключённый набор инструментов.

### Сочетание 3: `AGENTS.md` + память

Подходит, когда правила команды стабильны, но у каждого участника свои предпочтения в общении.

Распределение ответственности:

- В `AGENTS.md` хранятся общие правила команды
- Память сохраняет личные предпочтения: язык, стиль объяснений, структуру результата по умолчанию

Не меняйте эти роли местами. Правила команды не должны существовать только в памяти одного человека.

## Практическая матрица выбора

| Вопрос | Да | Нет |
|---|---|---|
| Влияет только на текущую задачу? | Промпт | Продолжить оценку |
| Должны соблюдать все участники? | `AGENTS.md` / конфигурация проекта | Продолжить оценку |
| Это повторяемый процесс? | Skill | Продолжить оценку |
| Требуются актуальные внешние данные или действие? | MCP | Продолжить оценку |
| Это только долговременное личное предпочтение? | Память / пользовательская конфигурация | Промпт |

Если требование одновременно попадает в два столбца, его, как правило, нужно **разделить по уровням**, а не втиснуть в один механизм.

## Три типичных примера

### Пример 1. Команда постоянно забывает запускать регрессионные тесты

Недостаточно написать в чате: «Не забудьте тесты».

Надёжнее:

1. Указать в `AGENTS.md`: «При изменении бизнес-логики обязательно выполнять `pnpm test`»
2. Если процесс сложен, дополнить его Skill для запуска тестов
3. Оставить CI последним уровнем защиты

### Пример 2. При каждом Review PR нужен результат в одинаковом формате

Не вставляйте один и тот же шаблон каждый раз.

Надёжнее:

1. Оформить структуру результата как Skill
2. Указать в `description`, что Skill применяется, когда пользователь говорит «review», «проверка» или «проверка перед слиянием»
3. Если Skill единообразно используется командой, добавить его путь в документацию проекта

### Пример 3. Перед изменением кода нужно прочитать задачу Linear

Не вставляйте token API в диалог.

Надёжнее:

1. Подключить Linear через MCP
2. По умолчанию предоставить разрешение только для чтения
3. Если требуется постоянный процесс, закрепить в Skill: «Сначала прочитать задачу, затем изучить код и предложить решение»

## Самые распространённые ловушки

### Превращение `AGENTS.md` в энциклопедию

Жёсткие ограничения перестают выделяться, а важные команды и запретные области тонут в тексте. `AGENTS.md` должен быть кратким, строгим и применимым на практике.

### Использование Skill как универсального хранилища

Если один Skill одновременно охватывает Review, выпуск, отладку и ежедневный отчёт, его трудно запускать и сопровождать.

### Использование MCP как ответа по умолчанию

Не нужно подключать внешний инструмент ради сложности, если сведения можно прочитать непосредственно в репозитории. MCP расширяет возможности, а не вознаграждает усложнение.

### Хранение фактов команды в памяти

Правило, известное только учётной записи одного человека, исчезнет после его ухода или смены компьютера. Такие сведения должны вернуться в репозиторий.

## Рекомендуемый порядок внедрения

Если правила команды сейчас не упорядочены:

1. Сначала создайте минимально полезный `AGENTS.md`
2. Оформите как Skill процессы, повторившиеся не менее трёх раз
3. Подключайте MCP только при реальной необходимости во внешней системе
4. В конце упорядочите личную память и предпочтения

Так вы сначала стабилизируете **общие правила совместной работы**, а затем постепенно расширите возможности.
