При командной работе с Codex **политика правил** отвечает на вопросы: какие ограничения едины для всей компании, какие поддерживает репозиторий и что отдельный пользователь может ослабить. Эта глава рассматривает управление [правилами команд](/ru/guide/customization/rules/command-rules/) и [разрешающими и запрещающими правилами](/ru/guide/customization/rules/allow-and-deny-patterns/).

## Содержание

- Управляемая политика организации, правила проекта и личные предпочтения
- Как проводить Review и выпуск изменений правил
- Как согласовать правила с `AGENTS.md`, Hook и CI

## Назначение политики правил команды

Политика определяет, какие границы компания устанавливает централизованно, какие выбирает проект и какие являются личными привычками.

Без ясного разделения легко получить две проблемы:

- Правило, которое должно действовать для всей команды, существует только на компьютере одного человека
- Временная личная настройка ошибочно считается стандартом команды

## Распространённые заблуждения

### Правила команды необязательно унифицировать полностью

Некоторые границы действительно должны быть общими для всей организации — например, deny для высокорисковых действий.

Но одинаковые правила для всех репозиториев создают другую проблему: политика оказывается слишком широкой или узкой, и ей перестают доверять.

Главное — разделить уровни организации, проекта и пользователя, а не сделать все правила одинаковыми.

### Личное дополнение не должно ослаблять обязательные границы команды

На своём компьютере можно добавить удобные настройки, но нельзя обходить границы, уже установленные командой или организацией.

Иначе локальная «эффективность» создаст скрытый риск для совместной работы.

## Рекомендуемая модель уровней

```text
L1 Управляемая политика организации (Managed) → проект и пользователь не могут переопределить
L2 Репозиторий шаблонов команды              → фрагмент Rules, наследуемый новым репозиторием
L3 Rules проекта + AGENTS.md                 → Review через PR в Git
L4 Личная конфигурация                       → только локально, не может ослабить L1
L5 Промпт одной задачи                       → может временно ужесточить, ослабление ограничено L1
```

Сопоставьте с [областью действия AGENTS.md](/ru/guide/customization/agents-md/scope-and-precedence/): **Rules отвечают прежде всего за принудительное выполнение, а AGENTS.md — за описание поведения**. Они должны быть согласованы, а не задавать противоречащие требования.

## Основной подход

1. **Сначала составьте список «никогда не разрешать»** — deny: `git push --force`, чтение `~/.ssh`, отправка содержимого репозитория через POST во внешнюю сеть
2. **Затем составьте список «разрешено ежедневно»** — allow: тесты, lint, операции Git только для чтения
3. **Назначьте L1 централизованно**, если в организации включена Managed configuration
4. **Каждый сервис или пакет Monorepo** может дополнить L3, не вступая в конфликт с L1
5. **Ежеквартально пересматривайте** повторяющиеся ложные блокировки и ошибочные разрешения из журналов подтверждений и возвращайте исправления через PR правил

## Рекомендуемый процесс изменения правил

```text
Предложение (Issue или RFC) → Review безопасности / платформы → PR с изменением файла правил
    → пробный запуск типовых задач в staging-репозитории → слияние → объявление + обновление страницы руководства
```

При крупном изменении — например, разрешении внешней сети — одновременно обновите [аудит Hook](/ru/skills/hooks/hooks-overview/) и [правила допустимого использования](/ru/guide/team-enterprise/governance/acceptable-use/).

## Согласование с Hook и CI

| Механизм | Назначение |
|---|---|
| Rules | Разрешение или запрет до выполнения |
| Hook | Сложная проверка, журналирование, формат соответствия требованиям |
| CI | Проверка перед слиянием, скрипты из одного источника с локальными правилами |

Не создавайте три независимые реализации одной логики. Предпочтителен **единый источник истины**, например `tools/codex-rules.json`, используемый и CLI, и CI.

## Распространённые ошибки

- Устно договориться «не выполнять push», но не обновить файл правил
- Ослабить песочницу локально и считать снимок экрана «стандартом команды»
- Использовать один слишком широкий глобальный allowlist для разных подпроектов Monorepo
- Изменить правила без объявления, внезапно вызвав множество ошибок подтверждения у коллег

## Как выбрать уровень правила

Ответьте на три вопроса:

1. Это обязательная граница для всех репозиториев?
2. Правило относится только к текущему проекту?
3. Это лишь моё личное дополнение для удобства?

Обычно ответы соответствуют:

- Уровню организации
- Уровню проекта
- Личному уровню

## Границы безопасности

- Правила не заменяют [модель угроз](/ru/guide/team-enterprise/security/threat-model/) и процесс реагирования на инциденты
- Для регулируемых данных правила должны проходить Review вместе с классификацией данных и политикой хранения
- Для аварийного обхода обязательны **запись аудита** и последующий разбор

## Контрольный список приёмки

- [ ] Вы можете изобразить разделение L1–L3 в организации
- [ ] Для файла правил в репозитории назначен ответственный и определены требования Review
- [ ] Нет противоречий с `AGENTS.md`, Hook и CI
- [ ] Есть канал обратной связи по ложным блокировкам — шаблон Issue или внутренняя форма

Главное в политике правил команды — сначала определить, кто устанавливает границы каждого уровня, и лишь затем решать, как записать правила.
