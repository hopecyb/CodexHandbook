**Rules (правила)** в конфигурации или файлах проекта определяют, какие shell-команды, пути и вызовы инструментов **разрешены или запрещены**. Они сокращают число ручных подтверждений и одновременно предотвращают автоматизацию опасных действий.

## Содержание

- Как работают правила Allow / Deny
- Как они связаны с песочницей, диалогами подтверждения и `AGENTS.md`
- Примеры правил команды

## Что делают правила

Правила — это заранее установленные соглашения о том, что Codex может и чего не может делать, чтобы не принимать решение и не нажимать подтверждение вручную каждый раз.

Они дают два основных преимущества:

- Сокращают повторные подтверждения для низкорисковых действий, выполняемых ежедневно
- Заранее блокируют высокорисковые действия, которые не должны запускаться автоматически

## Типы правил — концептуально

| Тип | Пример |
|---|---|
| Allowlist команд | Разрешить `npm test`, `git status` |
| Denylist команд | Запретить `rm -rf`, `curl \| bash` |
| Пути | Запретить запись в `../` и чтение `~/.ssh` |
| Сеть | Запретить внешнюю сеть или разрешить только домены registry |

Сопоставьте с [матрицей разрешений](/ru/guide/reference/permission-matrix/): правила — это **настраиваемое принудительное ограничение**, а матрица описывает **типичные значения по умолчанию**.

## Рекомендуемые уровни

```text
Управляемая политика организации (не переопределяется)
    ↓
Rules проекта + AGENTS.md (Review через Git)
    ↓
Дополнительный личный allowlist (только локально)
    ↓
Ограничения промпта одной задачи
```

## Распространённые заблуждения

### Правила нужны не только для уменьшения числа диалогов

Услышав об allowlist, легко решить, что его цель — реже видеть диалоги подтверждения и меньше отвлекаться.

Это лишь часть задачи. Важнее пропустить низкорисковые действия и заблокировать высокорисковые.

### Правила не равны песочнице

Песочница ограничивает максимальную область доступа, а правила определяют действия, которые в принципе не следует выполнять.

Используйте оба механизма вместе, а не вместо друг друга.

### Обязательные правила команды нельзя хранить только локально

Если только ваш компьютер знает о запрете push и доступа к `.env`, остальные участники всё равно могут нарушить эту границу.

Обязательные правила команды следует хранить там, где они могут пройти Review.

## Пример команды — схема, не готовая конфигурация

**Разрешить:**

- Устанавливать зависимости **внутри проекта** через менеджер пакетов
- Запускать тестовые скрипты из документации

**Запретить:**

- `git push`, `git reset --hard`
- Чтение и запись `.env*`, если этого явно не требует задача
- Отправку во внешнюю сеть POST-запросов с содержимым репозитория

Записывайте правила в доступном для командного Review файле, а не оставляйте устной договорённостью.

## Распространённые ошибки

- Слишком широкий Allowlist: разрешить `bash` фактически означает разрешить всё
- Только Deny без Allow, из-за чего подтверждений по-прежнему слишком много
- Противоречие между правилами и `AGENTS.md`

## С чего начать

Необязательно сразу создавать исчерпывающую политику. Достаточно двух шагов:

1. Явно перечислить 3–5 низкорисковых команд, которые выполняются ежедневно
2. Явно перечислить несколько высокорисковых действий, которые никогда не должны запускаться автоматически

Сначала отладьте минимальные границы, затем постепенно уточняйте их.

## Границы безопасности

- Правила **не заменяют** Review кода и защиту веток
- Вредоносный промпт может склонить Agent к попытке обойти правила — оставляйте песочницу строгой по умолчанию
- Изменяйте правила через PR и относитесь к этому как к изменению CI

Хорошие правила allow/deny заранее и ясно определяют, какие действия допустимы, а какие не должны происходить.
