В Monorepo одновременно существуют несколько App, общие пакеты и разные технологические стеки. Один огромный `AGENTS.md` легко приводит к тому, что Agent **изменяет не тот пакет** или запускает не те тесты. На этой странице приведён повторно используемый пример **многоуровневых инструкций**, который следует адаптировать к репозиторию.

## О чём эта страница

- Как распределить инструкции между корнем и дочерними пакетами
- Как согласовать ссылки @ и ограничения путей с границами пакетов
- Как сохранить единообразие команд с CI и средой Cloud

## Почему таким репозиториям особенно нужны уровни инструкций

Если обычный репозиторий похож на квартиру, то Monorepo — на многоквартирный дом.

В нём разные помещения, жильцы и правила.  
Если повесить у входа одно длинное общее руководство, Codex легко столкнётся с двумя проблемами:

- Он видит все правила, но не понимает, какой уровень относится к текущей задаче
- Нужно изменить один пакет, а затрагиваются и другие

Важно прояснять правила вместе с границами каталогов, а не механически создавать больше файлов `AGENTS.md`.

## Рекомендуемая структура — пример

```text
repo-root/
  AGENTS.md              # Глобально: стратегия веток, правила commit, запреты
  apps/web/AGENTS.md     # Клиентская часть: фреймворк, команды тестов, соглашения маршрутов
  apps/api/AGENTS.md     # Серверная часть: стиль API, дисциплина миграций
  packages/shared/       # Можно дать ссылку только из корневого документа или добавить краткую локальную инструкцию
```

Корневой `AGENTS.md` должен содержать:

- Каталоги, которые Agent **запрещено** изменять, например `infra/prod/`
- **Ответственного или ссылку на документацию** для каждого дочернего пакета
- Глобальную команду установки: `pnpm install` выполняется в корне

## Распространённые заблуждения

### 1. С ростом числа каталогов не помещайте все инструкции в корень

При первой настройке Monorepo легко по привычке записать все ограничения в корневой `AGENTS.md`.

Последствия:

- Файл становится длинным
- Правила текущей задачи не выделяются
- Особые соглашения пакета теряются среди общего текста

Надёжнее хранить общий консенсус в корне, а особые локальные правила — в пакете.

### Инструкция пакета сужает область ошибочных изменений, а не повторяет корневые правила

Если команды разработки, тестирования и ограничения для `apps/web` и `apps/api` различаются, описание этих различий в соответствующих каталогах помогает Codex избежать лишней работы.

## Фрагмент шаблона AGENTS.md для пакета

```markdown
## Область
Изменяйте только `apps/web/**`, если задача явно не требует изменений в нескольких пакетах.

## Разработка
- Установка: `pnpm install` в корне репозитория
- Разработка: `pnpm --filter web dev`
- Тесты: `pnpm --filter web test`
- Проверка типов: `pnpm --filter web typecheck`

## Зависимости
Импортируйте общие типы из `@acme/shared`, не копируйте их.
```

## Сочетание с промптом задачи

При рефакторинге нескольких пакетов **явно перечислите пути**:

```text
Цель: использовать новый клиент API в apps/web
Разрешено изменять: apps/web/**, packages/api-client/**
Запрещено: непосредственно изменять сервер apps/api
Приёмка: pnpm --filter web test && pnpm --filter api-client test
```

См. [Контекст файлов и каталогов](/ru/guide/context/file-and-folder-context/)

## Cloud и CI

Monorepo в Cloud часто не проходит сборку, если зависимости установлены не из корня или неверно задан filter. В корневом `AGENTS.md` укажите:

- Что рабочим каталогом по умолчанию является корень репозитория
- Команды filter для задач одного пакета
- Стратегию кэша — при использовании turborepo или nx опишите граф задач

См. [Среды Cloud](/ru/guide/web-and-cloud/cloud-environments/)

## Распространённые ошибки

- Инструкции есть только в `apps/web`, поэтому Agent изменяет lockfile в корне без ограничений
- Команды тестирования пакетов различаются, но это не задокументировано
- AGENTS.md пакета противоречит корневому документу

## Как выбрать между корнем и каталогом пакета

Если вы не уверены, задайте вопросы:

1. Это общее правило для всех пакетов?
2. Оно действует только в конкретном каталоге?
3. Может ли неправильное расположение правила заставить Agent изменить не ту область?

Если ближе первое, используйте корень. Если второе или третье — каталог пакета.

## Контрольный список приёмки

- [ ] И в корне, и в пакете есть хотя бы одна понятная инструкция об области действия
- [ ] Команду тестирования можно успешно запустить отдельно для любого пакета
- [ ] В промпте задачи для нескольких пакетов явно перечислены разрешённые пути

AGENTS.md в Monorepo необязательно сосредоточивать в одном месте. Лучше хранить общий консенсус и локальные правила каталогов на подходящих им уровнях.
