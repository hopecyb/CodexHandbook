`AGENTS.md` — это **инструкции проекта в формате Markdown**, расположенные в репозитории или его подкаталоге. Codex читает их при входе в проект, чтобы согласовать стиль кода, требования к тестам, правила коммитов и запретные области.

Воспринимайте `AGENTS.md` как руководство о том, как проект ожидает совместной работы с Codex.

Это не расширенный архитектурный документ и не полное руководство для нового сотрудника, а правила взаимодействия Codex с проектом.

![Иллюстрация: в разрезе каталогов репозитория в корне лежит руководство, а в подкаталогах прикреплены короткие заметки; маленький помощник сначала читает руководство, затем ближайшую заметку](/illustrations/agents-md.webp)

## Основная идея

Представьте его как **краткую версию руководства для нового сотрудника**: только о том, как работать в этом репозитории, без истории компании.

| Подходит для AGENTS.md | Не подходит |
|---|---|
| Команды тестирования, lint и сборки | Полная документация API — лучше дать ссылку на официальный документ |
| Соглашения о каталогах и стиле имён | Тысячи строк исторических проектных решений |
| Запреты — например, не изменять `main` и не добавлять ключи | Временные требования, меняющиеся в каждой задаче |
| Сообщения commit и контрольный список PR | Личные предпочтения, не связанные с кодом |

## Минимально полезный вариант

Создайте `AGENTS.md` в корне репозитория:

```md
# Инструкции проекта

## Сборка и тестирование
- Установка: `pnpm install`
- Тесты: `pnpm test` (обязательно после изменения логики)
- Проверка типов: `pnpm typecheck`

## Стиль кода
- Используйте строгий режим TypeScript
- Новые компоненты размещайте в `src/components/`, имена файлов — PascalCase

## Запрещено
- Не изменяйте `pnpm-lock.yaml`, если зависимости не меняются
- Не добавляйте `.env` и ключи API в репозиторий
- Не выполняйте `git push` без подтверждения

## Критерии завершения
- Связанные тесты проходят
- Новых ошибок lint нет
- В описании PR указаны шаги проверки
```

После сохранения в новой задаче достаточно указать только **отличия текущего случая**. Например: «Исправь макет страницы входа в Safari и проведи приёмку по AGENTS.md».

## Распространённые заблуждения

### 1. Нужно ли повторять эти правила вручную в каждой задаче?

Обычно нет.  
В этом и заключается одна из функций `AGENTS.md`: хранить **стабильные правила проекта**, чтобы не объяснять их при каждом новом запуске.

### 2. Если правило записано, Codex обязательно выполнит его на сто процентов?

`AGENTS.md` важен, но действует вместе с другими механизмами:

- Явными требованиями текущей задачи
- Разрешениями и подтверждениями продукта
- Песочницей, сетью и политиками команды

Точнее считать его средством согласования, а не универсальным принудительным механизмом.

### 3. Если я не программист, нужно ли мне знать об этом файле?

Нужно понимать основную идею.  
Даже если вы не пишете код самостоятельно, при постоянной работе Codex над проектом `AGENTS.md` сокращает повторные объяснения и отклонения от требований.

## Где разместить файл

| Расположение | Область действия |
|---|---|
| `AGENTS.md` в корне репозитория | По умолчанию весь проект |
| `AGENTS.md` в подкаталоге | Этот каталог и вложенные пути — часто встречается в Monorepo |
| Инструкции пользователя | Используйте личную конфигурацию или глобальные предпочтения, не смешивая их с инструкциями проекта |

Подробнее о конфликтах: [Область действия и приоритет](/ru/guide/customization/agents-md/scope-and-precedence/)

## Отличия от Skill и команд с косой чертой

| Механизм | Суть | Типичное применение |
|---|---|---|
| AGENTS.md | Постоянные пассивные правила проекта | Стиль, тесты, запретные области |
| Skill | Пакет повторно используемого рабочего процесса — `SKILL.md` | Контрольный список выпуска, специализированный процесс Review |
| Команда с косой чертой | Быстрая точка входа, которую вы запускаете сами | `/review`, одноразовый рабочий процесс |

Для правил проекта используйте `AGENTS.md`, а **повторяемую и доступную другим последовательность шагов** лучше оформить как [Skill](/ru/skills/overview/).

## Как выбрать место для инструкции

Если вы не уверены, используйте такое правило:

- **Правило действует долго**: поместите его в `AGENTS.md`
- **Это особое требование только текущей задачи**: укажите в её промпте
- **Это последовательность повторно используемых шагов**: рассмотрите Skill

Например:

- «Для проверки в этом репозитории всегда используется `pnpm test`» -> `AGENTS.md`
- «В этот раз изменяй только страницу входа, регистрацию не трогай» -> текущая задача
- «Перед каждым выпуском выполняй одинаковую последовательность проверок» -> Skill

## Распространённые ошибки

- Слишком длинный файл, который модель читает лишь частично — **помещайте жёсткие ограничения в первые 30 строк**
- Высокорисковая инструкция вроде «всегда автоматически выполнять push», конфликтующая с [разрешениями и подтверждениями](/ru/guide/foundations/permissions-and-approvals/)
- Документ никто не сопровождает, и его команды расходятся с настоящими скриптами

## Границы безопасности

`AGENTS.md` **не заменяет** песочницу и подтверждения. Даже если в нём написано «можно выполнять любые команды», продукт всё равно может запросить подтверждение, а управляемая политика команды — ввести более строгие ограничения.

`AGENTS.md` сообщает Codex, как обычно работают в проекте, но не описывает конкретную текущую задачу.
