Эффективные инструкции проекта больше похожи на **контрольный список**. Их цель — помочь Codex уже с первой попытки избежать предсказуемых ошибок.

При создании первых инструкций проекта часто записывают много идей, но формулируют ключевые ограничения недостаточно ясно.

## Содержание

- Как должны выглядеть инструкции проекта
- Что означает «кратко, строго и выполнимо»
- Какие формулировки сильнее всего запутывают Codex и людей

## Рекомендуемая структура

```md
# Инструкции проекта

## Быстрый старт — 3–5 строк
Установка, сервер разработки, самая частая команда тестирования

## Обязательные правила
Пронумерованный список правил, которые нельзя нарушать

## Код и каталоги
Имена, расположение, соглашения о зависимостях

## Критерии завершения
Что означает «готово к коммиту»

## Запрещённые действия
Явно укажите, чего делать нельзя
```

## Принципы написания

### 1. Помещайте жёсткие ограничения в начало

Перенесите слова «обязательно» и «запрещено» в первую часть файла. При ограниченном контексте начало имеет больший вес для модели — по той же логике, что и [приоритеты контекста](/ru/guide/context/context-priority/).

### 2. Команды должны быть готовы к копированию

Приводите **реальные выполнимые** команды вместо «запусти тесты»:

```md
# Хорошо
pnpm test --filter @app/web

# Плохо
Убедитесь, что тесты проходят
```

### 3. Задавайте проверяемые критерии завершения

```md
## Критерии завершения
- `pnpm lint` и `pnpm test` завершаются без ошибок
- Для нового API есть соответствующий модульный тест
- Для видимых пользователю изменений приведены шаги ручной проверки — браузер + мобильное устройство
```

### 4. Объясняйте причину не более чем одним предложением

```md
- Не изменяйте `generated/`: этот каталог создаётся из кода, и ручные изменения будут перезаписаны при следующей сборке
```

Для длинного контекста давайте ссылку на официальный документ в `docs/`.

## Что такое хорошая инструкция

Она помогает человеку и Codex сразу понять:

- Что сделать первым
- Чего делать нельзя
- Какой результат считается завершённым

Если после чтения непонятно, какую команду запускать сначала, какие области не следует затрагивать и что означает «готово», инструкция недостаточно полезна.

## Пример фрагмента playbook команды

```md
## PR и Git
- Имена веток начинаются с `feat/`, `fix/` или `docs/`
- Один PR решает одну задачу; масштабный рефакторинг оформляется отдельным PR
- Перед слиянием человек обязательно проводит Review diff, даже если Codex запустил тесты

## Совместная работа с Codex
- Для большой задачи сначала запросите план и дождитесь подтверждения до изменения кода
- Для миграции базы данных сначала предоставьте SQL миграции для ручной проверки
```

## Распространённые ошибки

| Ошибка | Последствие |
|---|---|
| Энциклопедия о фреймворке | Ключевая команда тестирования остаётся без внимания |
| Противоречивые правила | Модель произвольно выбирает одно из них |
| Только абстрактные слова вроде «делай красиво» | Результат невозможно принять |
| Ключи или внутренний URL | Риск раскрытия |

## Распространённые заблуждения

### 1. Чем подробнее инструкции, тем лучше

Разрозненный, длинный, энциклопедический текст скрывает действительно приоритетные правила.

### 2. Фраза «соблюдай стандарты» уже является инструкцией?

Обычно она недостаточно выполнима.  
Лучше указать:

- Настоящую команду
- Конкретный каталог
- Точный критерий завершения

### 3. Можно свободно смешивать контекст и правила выполнения?

Это тоже нежелательно.  
Лучше:

- Разместить правила в начале
- Сжать пояснение до одного предложения
- Перенести подробности в docs

## Как улучшить существующие инструкции

Если текущий документ разрознен:

1. Перенесите «обязательно / запрещено» в начало
2. Замените общие слова конкретными командами или пунктами проверки
3. Сократите длинный контекст и замените его ссылкой
4. Добавьте минимальный набор критериев завершения

## Как превратить опыт одной задачи в правило проекта

Не каждый хороший промпт следует сразу переносить в `AGENTS.md`. Сначала определите подходящий уровень:

| Повторяющееся требование | Как лучше закрепить |
|---|---|
| «Не изменяйте каталог generated в этом репозитории» | Запрещённые действия в `AGENTS.md` |
| «Перед каждым PR проводите проверку по фиксированному формату» | Skill или шаблон промпта |
| «После записи файла автоматически форматируйте его» | Hook |
| «Перед работой с задачей прочитайте Linear/Jira» | MCP + соответствующий Skill |
| «Лично я предпочитаю объяснения на русском» | Память или личные предпочтения |

`AGENTS.md` лучше всего подходит для долговременных, общих и проверяемых правил команды. Процедуры можно вынести в Skill, автоматические проверки — в Hook, а доступ к внешним системам — в MCP.

Хорошие инструкции проекта ценны не объёмом, а ясностью ключевых ограничений, команд и критериев завершения, которые можно непосредственно выполнить.

## Ритм сопровождения

- При каждом изменении команды CI **одновременно обновляйте** `AGENTS.md`
- Ежеквартально удаляйте устаревшие правила
- Первый шаг onboarding нового участника — прочитать AGENTS.md и пройти «Быстрый старт»
