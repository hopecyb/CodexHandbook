При выполнении задачи Agent может создавать **артефакты**: отчёты, скрипты, статические сайты, тестовые данные и другие материалы. Они не всегда проходят привычный вам процесс проверки кода, поэтому требуют отдельной процедуры приёмки.

То, что Codex создал новый файл, ещё не означает, что файл готов к использованию.

## Содержание страницы

- Чем приёмка созданного артефакта отличается от проверки изменений существующего кода
- Контрольный список
- Когда отклонить результат и потребовать переделку

## Типы артефактов

| Тип | Главное при приёмке |
|---|---|
| Скрипт `.sh`, `.py` | Выполнимость, безопасность, идемпотентность |
| Отчёт `.md`, `.html` | Точность фактов, рабочие ссылки |
| Результат сборки `dist/` | Нужно ли добавить в gitignore |
| Тестовые фикстуры | Отсутствие реальных персональных данных |
| Шаблон конфигурации | Отсутствие слабого пароля по умолчанию |

## Что здесь называется артефактом

Под артефактами понимаются:

- Новые файлы, которые Codex написал для вас
- Экспортированные отчёты
- Собранные страницы, каталоги или пакеты

Они отличаются от изменения нескольких строк существующего кода тем, что фактическое содержимое легче оставить без внимания.

## Процесс приёмки

```text
1. Откройте артефакт — не ограничивайтесь текстовой сводкой Agent
2. Сопоставьте его с «критериями завершения» задачи
3. Запустите соответствующие тесты или команду предпросмотра
4. Проверьте путь, разрешения и размер
5. Примите решение: принять / частично исправить / отклонить и переделать
```

Подробнее: [Проверка артефактов](/ru/guide/quality/verify-artifacts/) и [Критерии завершения](/ru/guide/quality/definition-of-done/)

## Распространённые заблуждения

### 1. Даже если Agent сообщил «готово», нужно посмотреть на результат

Сводка сообщает лишь, что Agent считает выполненным. Она не заменяет открытие файла и проверку фактического результата.

### 2. Новый файл не обязательно безопаснее изменения старого

Он тоже может содержать:

- Ошибочные сведения
- Лишние зависимости
- Раскрытую информацию
- Крупные данные, которые не следует добавлять в репозиторий

### 3. Если результат запускается, его не всегда стоит коммитить

Некоторые артефакты предназначены только для временного локального использования и не должны попадать в Git.

## Связь с Git

- Явно укажите, какие артефакты **нужно коммитить**, а какие добавлять в `.gitignore`
- Не включайте в один PR мегабайты кэша сборки
- Для крупных артефактов используйте CI artifact или внешнее хранилище

## Полезный порядок приёмки

Получив набор новых артефактов:

1. Сначала выясните, какие файлы созданы
2. Откройте самый важный из них
3. Убедитесь, что он находится в разрешённом каталоге
4. Определите, нужно ли добавлять его в репозиторий
5. Затем решите: принять, изменить или переделать

## Недоверенные артефакты

Для задач из недоверенного репозитория или на основе внешних данных:

- Прочитайте скрипт до выполнения
- Остерегайтесь `curl | bash` и обфусцированных payload
- Выполняйте предпросмотр в песочнице или контейнере

Недостаточно убедиться, что артефакт создан. Его нужно открыть, проверить и понять, следует ли добавлять в репозиторий.

## Распространённые ошибки

- Читать только маркированную сводку Agent и не открывать файл
- Коммитить одноразовый отладочный вывод в main
- Оставлять в HTML-отчёте пиксель отслеживания или непроверенный внешний скрипт

## Контрольный список приёмки

- [ ] Путь каждого нового файла находится в разрешённой области
- [ ] Основное содержимое открыто и просмотрено
- [ ] Автоматизированные проверки — lint, test, link check — выполнены
- [ ] Нет secrets и лишних созданных каталогов
