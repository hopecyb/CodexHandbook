Не пытайтесь предсказать разрешения по фиксированной таблице «покажет ли App, CLI, IDE или Cloud диалог подтверждения». Фактическое поведение совместно определяется местом выполнения, эффективной конфигурацией, требованиями организации, операционной системой и запрошенным действием.

![Схема принятия решения между ограничением песочницы, подтверждением человеком и выполненным результатом](/illustrations/flow-sandbox-approval.webp)

## Сначала разделите три механизма

| Механизм | Область | Основное управление |
|---|---|---|
| Локальные Permission Profiles (Beta) | Локальные команды в macOS, Linux, WSL и нативной Windows | Чтение, запись и запрет в файловой системе; сетевые назначения |
| Прежние настройки песочницы | Локальный Codex | `read-only`, `workspace-write`, `danger-full-access` и политика подтверждений |
| Политика окружения Cloud | Codex Cloud | Изолированный контейнер, сеть во время setup, список разрешённых направлений и HTTP-методов для Agent |

Permission Profiles не объединяются с прежним `sandbox_mode`. Если загруженная конфигурация содержит `sandbox_mode`, командная строка передаёт `--sandbox` или Profile конфигурации задаёт песочницу, Codex использует прежние настройки песочницы вместо `default_permissions`.

## Встроенные локальные Permission Profiles

| Имя | Граница | Подходит для |
|---|---|---|
| `:read-only` | Локальные команды работают только на чтение | Понимание кода, Review, первое знакомство с репозиторием |
| `:workspace` | Запись в корни рабочей области и системные временные каталоги | Обычные задачи разработки |
| `:danger-full-access` | Снимает ограничения локальной песочницы | Только при внешней изоляции и явной необходимости |

Пользовательский Profile может задавать для путей `read`, `write` или `deny` и исключать из широкой области чувствительные файлы, например `.env`, с помощью более конкретных правил. При конфликте для одного пути `deny` имеет приоритет над `write`, а `write` — над `read`.

## Пример минимальных привилегий

```toml
default_permissions = "project-edit"

[features]
network_proxy = true

[permissions.project-edit.filesystem]
":minimal" = "read"

[permissions.project-edit.filesystem.":workspace_roots"]
"." = "write"
".devcontainer" = "read"
"**/*.env" = "deny"

[permissions.project-edit.network]
enabled = true

[permissions.project-edit.network.domains]
"api.openai.com" = "allow"
"tracking.example.com" = "deny"
```

`network.enabled = true` лишь разрешает командам доступ к сети. Чтобы доменные правила принудительно применялись через прокси, также нужно включить `features.network_proxy`.

## Оценивайте по действию

| Действие | Основной риск | Минимальная граница |
|---|---|---|
| Читать исходный код | Чувствительные файлы попадают в контекст | Чтение рабочей области с явным запретом учётных данных |
| Изменять файлы | Перезапись или удаление за пределами области | Запись только в целевую рабочую область; проверка diff |
| Запускать тесты | Побочные эффекты скрипта | Review скриптов и контролируемое окружение |
| Устанавливать зависимости | Цепочка поставок и сеть | Фиксация версий и ограничение доменов |
| Git push / PR | Изменение внешнего состояния | Отдельная ветка, защита веток и человеческое Review |
| Инструмент MCP/Plugin | Сторонние данные и запись | Минимальная область, подтверждение каждого действия и журналы |

`AGENTS.md` может требовать «не выполнять push», но не является технической границей принудительного применения. Сочетайте правила с песочницей и разрешениями, доступом GitHub и человеческим Review.

## Командная проверка

1. Запишите версии клиента и Codex.
2. Перечислите все загруженные уровни конфигурации.
3. Подтвердите, активны ли Permission Profile или прежняя песочница.
4. В тестовом каталоге без конфиденциальных данных отдельно проверьте чтение, запись, запрет и сеть.
5. Только после этого подключите реальный репозиторий, сохранив контрольные механизмы Git и организации.

Permission Profiles по-прежнему находятся в Beta. Повторяйте эту проверку после обновлений.
