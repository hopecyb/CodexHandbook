Сначала сохраните ошибку. Определите уровень сбоя, затем измените только одну переменную и запустите повторно. На этой странице процесс показан на пяти фиксированных входных данных. Автор намеренно создал сбои; журналы получены из реальных запусков командной строки, а не из инцидентов клиентов.

[Скачать полный комплект упражнений](/downloads/failure-recovery/failure-recovery-1.0.0.zip) · [README](/downloads/failure-recovery/README.md)

## Сначала воспроизведите сбои

Нужна только стандартная библиотека Python 3.10+; учётная запись и сеть не требуются. Выполните в распакованном пакете:

```sh
python3 scripts/reproduce.py --output my-recovery-logs
```

Каталог вывода не должен существовать, чтобы прежние доказательства нельзя было перезаписать. Скрипт использует временные копии. Каждый из пяти неудачных запусков должен завершиться с ненулевым кодом, а каждый исправленный — с кодом 0 при неизменных исходных данных. В каждом журнале есть команда, код завершения, стандартный вывод и стандартный поток ошибок. Временные пути нормализованы как `<WORK>`.

## 1. Несовпадение хеша источника

**Симптом:** `FAIL: Source changed: P`, код завершения 1.

**Диагноз:** в фиксированный файл источника непреднамеренно добавлен фрагмент, а индекс источников остался прежним. Сначала сравните с исходным материалом; не обновляйте хеш только ради успешной проверки.

**Единственное изменение:** восстановите известные исходные байты одного файла источника. Не меняйте остальные материалы, статью и индекс. Повторный запуск завершается с кодом 0.

[Журнал сбоя](/downloads/failure-recovery/validation/01-source-changed-before.json) · [Журнал восстановления](/downloads/failure-recovery/validation/01-source-changed-after.json)

Если реальный источник действительно изменился, заново проверьте его версию, содержимое и сделанные на его основе выводы, а также сохраните новую запись источника. В этом упражнении уместно восстановить старый файл только потому, что правка заведомо была случайной.

## 2. Ссылка в статье отсутствует в таблице фактов

**Симптом:** `FAIL: Unmapped or unused claim ID`, код завершения 1.

**Диагноз:** статья использует F99 вместо F1, но в таблице фактов F99 отсутствует. Проверка P1 подтверждает, что предложение по-прежнему относится к F1.

**Единственное изменение:** исправьте опечатку в идентификаторе на F1 и запустите повторно; команда завершится с кодом 0. Не создавайте новую запись таблицы фактов ради неизвестной ссылки.

[Журнал сбоя](/downloads/failure-recovery/validation/02-unmapped-citation-before.json) · [Журнал восстановления](/downloads/failure-recovery/validation/02-unmapped-citation-after.json)

Правильный идентификатор не доказывает, что формулировка подтверждается источником. Сверьте с ним и само предложение. См. [Skill для написания](/ru/skills/examples/writing-skill/).

## 3. Предложение по сортировке не соответствует входным данным

**Симптом:** `FAIL: Stale input hash`, код завершения 1.

**Диагноз:** хеш входных данных в предложении не совпадает с текущим фиксированным Issue. В упражнении хеш предложения намеренно повреждён, чтобы запустить проверку привязки входных данных.

**Единственное изменение:** замените предложение полной эталонной версией, уже проверенной по текущим входным данным. Не меняйте входные данные и схему, затем запустите повторно; команда завершится с кодом 0. Модель не запускалась для повторной сортировки Issue, а старый вывод не использовался повторно после простого пересчёта хеша.

[Журнал сбоя](/downloads/failure-recovery/validation/03-stale-proposal-before.json) · [Журнал восстановления](/downloads/failure-recovery/validation/03-stale-proposal-after.json)

Если реальный Issue изменился, заново оцените влияние изменения на вывод. См. [кейс сортировки Issue](/ru/cases/use-cases/team-automation/issue-triage-suggestions/).

## 4. Повторное использование файла состояния для другого каталога

**Симптом:** `State version/site mismatch`, код завершения 3.

**Диагноз:** файл состояния привязан к фиксированному сайту, но команда направляет `--site` на повреждённый сайт. Ошибка возникает при проверке области и не означает, что сами ссылки внезапно перестали работать.

**Единственное изменение:** снова направьте `--site` на исходный каталог, сохранив файл состояния и остальные аргументы. Повторный запуск завершается с кодом 0. Ошибочный запуск не перезаписал существующее состояние.

[Журнал сбоя](/downloads/failure-recovery/validation/04-wrong-site-scope-before.json) · [Журнал восстановления](/downloads/failure-recovery/validation/04-wrong-site-scope-after.json)

Если действительно нужно отслеживать другой сайт, создайте для него отдельное состояние. Не удаляйте старое состояние ради обхода защиты области.

## 5. Повреждённый JSON состояния

**Симптом:** разбор JSON завершается сбоем; исполнитель сообщает `stopped` и выходит с кодом 3.

**Диагноз:** файл состояния был обрезан. Историю и базовую линию дедупликации больше нельзя безопасно прочитать. Отказавшись продолжать, программа сохраняет повреждённое содержимое, а не сбрасывает состояние незаметно до пустого.

**Единственное изменение:** восстановите заведомо исправную резервную копию, сохранённую до упражнения. Не меняйте команду и сайт. Повторный запуск завершается с кодом 0.

[Журнал сбоя](/downloads/failure-recovery/validation/05-corrupt-state-before.json) · [Журнал восстановления](/downloads/failure-recovery/validation/05-corrupt-state-after.json)

Если резервной копии нет, сначала сохраните повреждённый файл и изучите записи запусков, а затем восстановите состояние вручную. Простое удаление файла может потерять ожидающие доставки события и создать повторные кандидаты. См. [Skill автоматизации](/ru/skills/examples/automation-skill/).

## Примените метод к своей задаче

Сохраните версию входных данных, фактическую команду и полную ошибку. Определите, относится ли сбой к входным данным, структуре, области или состоянию. Запишите одну проверяемую причину, измените только соответствующую переменную, затем повторите ту же проверку и сохраните результат. После восстановления убедитесь, что исходная цель достигнута: одного кода завершения недостаточно.

Упражнения не охватывают реальные сбои входа, несрабатывание Skill в клиенте, сетевые ограничения и отказы подтверждения. В таких случаях вернитесь к [индексу диагностики по симптомам](/ru/guide/reference/troubleshooting/) и сохраните сведения о фактическом окружении. Не считайте поведение скриптов здесь гарантией поведения клиента.
