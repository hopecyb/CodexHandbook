Переменные окружения часто воспринимают одним из двух способов: как «слишком низкоуровневые» или как место, куда можно свалить всё. Проще говоря, они передают значения программам во время выполнения — прежде всего секреты и переключатели.

Используйте их, чтобы **передавать ключи, переопределять переключатели и адаптировать CI**, не записывая секреты в файлы конфигурации или Git. Это концептуальный индекс; точные имена сверяйте с [официальной документацией](https://developers.openai.com/codex) и `codex --help`.

## О чём эта страница

- Что хранить в переменных окружения, а что — в конфигурации
- Разделение пользовательского и проектного уровней, Cloud Secrets и CI
- Распространённые риски имён и утечек

## Правило принятия решения

Предпочитайте переменные окружения, если выполняется хотя бы одно условие:

- значение нельзя хранить в Git;
- оно различается между машинами, пользователями или окружениями;
- оно нужно только для текущего запуска.

Поэтому токены, временные переключатели и значения CI часто передаются через окружение, а не жёстко записываются в файлы.

О конфигурации: [справочник конфигурации](/ru/guide/reference/configuration-reference/); о Cloud: [секреты и переменные](/ru/guide/web-and-cloud/secrets-and-variables/).

## Что подходит для переменных окружения

| Тип | Пример назначения | Не следует |
|---|---|---|
| Токен аутентификации | API-ключ, GitHub PAT | Добавлять в репозиторий |
| Временный переключатель | Уровень отладочного журнала | Использовать как долгосрочную бизнес-конфигурацию |
| Передача через CI | Режим Review только для чтения | Передавать производственный токен с правом записи |
| Дочерний процесс MCP | Ключ сторонней службы | Хранить открытым текстом в `AGENTS.md` |

## Не универсальный ящик

Не следуйте правилу «если можно, помести в env».

- **Конфиденциальное и зависящее от запуска** → переменные окружения
- **Долгосрочное командное соглашение** → конфигурация или документация
- **Правила рабочего процесса** → `AGENTS.md` или Skill

Позже это упростит диагностику.

## Что такое `.env`

`.env` — не ещё один центр конфигурации, а распространённый способ для инструментов **пакетно загружать переменные окружения** при локальной разработке.

- Переменная окружения — значение.
- `.env` — локальный контейнер для таких значений.

Следовательно:

- удобство ≠ безопасность;
- `.env.example` показывает имена, но не реальные секреты;
- в производственной среде и CI обычно используются диспетчеры Secret платформы.

## Что плохо подходит для одного env

- Стандарты кода и структура каталогов → `AGENTS.md`
- Командная модель по умолчанию → проектная конфигурация для неконфиденциальных частей
- Сложные списки разрешений → [правила](/ru/guide/customization/rules/allow-and-deny-patterns/)

## Распространённые заблуждения

### 1. Переменные окружения предназначены не для всей конфигурации

Они подходят для значений, а не для полных командных правил и длинного текста.

### 2. `.env` на диске ≠ безопасность

Если `.env` добавлен в репозиторий, показан на экране или записан в журнал, секреты всё равно утекут.

### 3. `unset` ≠ риск исчез

Значение может остаться в истории shell, дочерних процессах, журналах, файлах и снимках экрана.

### 4. Локальная схема `.env` ≠ производственная схема

В CI, Cloud и управляемых платформах обычно:

- Secrets настраиваются в консоли;
- значения передаются во время выполнения;
- реальные значения не хранятся в файлах репозитория.

## Уровни и приоритет (концептуально)

```text
Обязательная политика организации (если есть)
    ↓ переопределяет
Переменные окружения, переданные через shell / CI
    ↓ объединяются с файлами конфигурации по официальным правилам
Пользовательские / проектные файлы конфигурации
```

Если один ключ задан в нескольких местах, следуйте **официальному приоритету**; для диагностики выведите эффективную конфигурацию или проверьте журналы.

## Практический порядок решения

1. Значение конфиденциально?
2. Оно нужно локально или в CI/Cloud?
3. Оно долгосрочное или только для этого запуска?
4. Выбрать локальное окружение, CI Secret или Cloud Secret?

Так реже возникает ситуация «правильное значение находится не там».

## Распространённые сценарии

| Сценарий | Более безопасный подход |
|---|---|
| Локальная отладка стороннего API | Локальное окружение или `.env`, исключённый из Git |
| Общий пример для команды | Добавить `.env.example`, но не реальные значения |
| GitHub Actions / CI | Secrets платформы |
| Задача Cloud вызывает закрытую службу | Cloud Secret |
| Серверу MCP нужен ключ | Родительское окружение или передача Secret |

Практическое правило: реальные ключи не должны долго храниться открытым текстом в файлах репозитория.

## Типичные применения

### Локальная разработка

Экспортируйте личный токен в `~/.zshrc` или `.envrc` direnv и **не добавляйте** `.env` в репозиторий.

### Неинтерактивный CLI

CI передаёт значение из хранилища секретов, затем запускает `codex exec`. См. [неинтерактивный режим](/ru/guide/cli/non-interactive-mode/).

### Серверы MCP

Процессы MCP часто наследуют родительское окружение; ссылайтесь в конфигурации на `$VAR`, а не записывайте значение жёстко. См. [подключение MCP](/ru/skills/mcp/connect-an-mcp-server/).

### Cloud

Secrets уровня репозитория настраиваются в консоли Cloud; имена должны совпадать со ссылками из задач.

Переменные окружения подходят для значений, которые меняются, являются конфиденциальными или нужны только во время выполнения, а не для долгосрочных правил и документации.

## Контрольный список безопасности

- [ ] `.env` добавлен в `.gitignore`.
- [ ] Токены скрываются перед записью в журнал.
- [ ] Утёкшие ключи заменяются.
- [ ] Области соответствуют принципу минимальных привилегий, например токен CI доступен только для чтения.

## Распространённые ошибки

- Реальные ключи в добавленном в репозиторий `.env.example`
- Видимая команда `export` во время демонстрации экрана
- Предположение, что `unset` делает дочерние процессы безопасными, без проверки дерева процессов
