Конфигурация CLI задаёт **модель по умолчанию, рабочий каталог, строгость одобрений, серверы MCP** и другие параметры. Общие принципы описаны в разделе [Основы конфигурации](/ru/guide/customization/configuration/config-basics/); здесь основное внимание уделено настройкам, которые чаще всего меняют пользователи терминала.

## На этой странице

При первом знакомстве конфигурацию CLI легко принять за «панель расширенных настроек». Из этого возникают два типичных заблуждения:

- можно ничего не настраивать, хотя затем при каждом запуске приходится вручную повторять один и тот же выбор;
- чем больше настроек, тем профессиональнее конфигурация, поэтому личные предпочтения, правила команды и временные эксперименты смешиваются в одном месте и затрудняют диагностику.

Главное — понять, **какие настройки стоит закрепить надолго, а какие следует менять только временно**.

## Что определяет конфигурация CLI

Считайте её набором рабочих привычек Codex по умолчанию в терминале.

- Модель: определяет, какая модель обычно выполняет задачи
- Песочница и одобрения: определяют, до какого шага Codex может дойти самостоятельно и где потребуется ваше согласие
- Рабочий каталог: определяет, в каком проекте Codex обычно работает
- MCP и расширения: определяют, какие дополнительные внешние возможности ему доступны

Codex работает и без конфигурации, но тогда вам придётся чаще повторять один и тот же выбор.

## Где хранится конфигурация

| Уровень | Назначение |
|---|---|
| Пользовательский | Личные значения по умолчанию для всех проектов |
| Проектный | Общие правила команды, которые нужно проверить перед коммитом |
| Переменные среды | Секреты и переключатели, передаваемые в CI |

**Пути и имена файлов** могут меняться между версиями CLI; сверяйтесь с [официальной документацией](https://developers.openai.com/codex). Обычно используется `config.toml` в домашнем каталоге пользователя или эквивалентный файл.

## Распространённые заблуждения

### Не всякую настройку следует хранить в проекте

Новички часто смешивают «предпочитаемую мной модель по умолчанию», «путь на моей машине» и «политику одобрений, обязательную для команды».

Разделяйте их так:

- долговременные личные предпочтения — на пользовательском уровне;
- единые для всех правила данного репозитория — на проектном;
- временные значения для CI, скрипта или отдельного запуска — в переменных среды.

### Конфигурация не означает немедленного снятия ограничений

Если политика записана в конфигурации, это не означает, что в дальнейшем все действия будут безусловно разрешены. На фактическое поведение также влияют точка входа в продукт, среда выполнения, управляемые политики и сама задача.

Поэтому конфигурация задаёт предпочтительное поведение, а не постоянные привилегии.

## Часто изменяемые настройки

### Модель и интенсивность рассуждений по умолчанию

Они влияют на скорость, стоимость и вероятность успешного выполнения сложной задачи. В сценариях со скриптами рекомендуется **зафиксировать модель**, чтобы журналы можно было корректно сравнивать.

### Песочница и сеть

| Назначение настройки | Описание |
|---|---|
| Строгая | Для недоверенных репозиториев |
| Стандартная | Для повседневной разработки |
| Ослабленная | Только для личной доверенной среды и в рамках политики компании |

Основные понятия: [Песочница и сеть](/ru/guide/foundations/sandbox-and-network/)

### Политика одобрений

CLI может запрашивать разрешение перед выполнением shell-команд, записью на диск или доступом к сети. В `AGENTS.md` команда должна указать, какие команды ожидаемо можно одобрять автоматически, — это работает только при соответствии реальному поведению продукта.

### Список серверов MCP

Он используется совместно с настройками из раздела [Подключение сервера MCP](/ru/skills/mcp/connect-an-mcp-server/). После изменения перезапустите сеанс.

## Практичный порядок настройки

При первом запуске не нужно изучать сразу все поля. Удобнее действовать так:

1. Зафиксировать наиболее часто используемую модель
2. Убедиться, что рабочим каталогом по умолчанию служит текущий проект
3. Выбрать консервативную или ослабленную политику одобрений и песочницы
4. Только затем добавить MCP, автоматизацию и более продвинутые расширения

Первые два пункта относятся к повседневной работе, а последние два — прежде всего к управлению риском.

## Согласование проекта и CLI

Чтобы избежать ситуации «в App работает, в CI завершается ошибкой»:

1. Укажите в README рекомендуемую минимальную версию CLI
2. Храните в проектной конфигурации только настройки, согласованные командой
3. Никогда не добавляйте секреты в репозиторий

## Диагностика

| Симптом | Что проверить |
|---|---|
| Конфигурация не применяется | Тот ли уровень изменён; нужен ли перезапуск |
| MCP не загружается | Синтаксис JSON/TOML и пути |
| Слишком частые запросы одобрения | Режим песочницы и allowlist |

Подробнее: [Диагностика CLI](/ru/guide/cli/troubleshooting/)

Относитесь к конфигурации CLI как к набору рабочих привычек по умолчанию. Закрепляйте только то, что вы выбираете **почти при каждом запуске**; расширенные возможности можно добавить позже.
