В неинтерактивном режиме Codex выполняет задачу **без диалога через TTY**. Именно так разработчики подключают Agent к скриптам и CI.

Иными словами, вместо переписки вы один раз передаёте задачу на выполнение.

Это больше похоже на обычный вызов команды.

## На этой странице

- Когда выбирать неинтерактивный режим вместо сеанса `codex`
- Какие дополнительные требования возникают к безопасности и одобрениям без оператора
- Как этот режим связан с [конфигурацией](/ru/guide/cli/configuration/)

## Подходящие сценарии

| Подходит | Не подходит |
|---|---|
| Проверка в CI по фиксированному промпту | Требования нужно уточнять в несколько этапов |
| Ночная проверка ссылок в документации | Исследовательский рефакторинг |
| Генерация кода по заранее заданному шаблону | Продуктовые решения с высокой неоднозначностью |

## Основной принцип

Неинтерактивный запуск обычно:

1. Получает **полное описание задачи** из параметра или stdin
2. Работает в заданном каталоге
3. Сообщает об успехе или ошибке кодом завершения
4. Выводит журнал или структурированный результат для следующего этапа

Текущая точка входа — `codex exec`. После обновления CLI снова выполните `codex exec --help` и проверьте параметры, используемые скриптом.

## Минимальный пример

```bash
# Однократная проверка только для чтения из корня репозитория
codex exec --cd . "Перечисли риски безопасности в diff относительно main, не изменяя файлы"
```

По умолчанию `codex exec` работает в песочнице только для чтения. Во время запуска сведения о ходе работы выводятся в `stderr`, а итоговый ответ Agent — в `stdout`, поэтому его можно безопасно перенаправить следующему этапу:

```bash
codex exec --cd . "Составь примечания к выпуску по последним 10 коммитам" > release-notes.md
```

Практические рекомендации:

- в shell-скрипте сначала переходите через `cd` в чистую рабочую копию;
- храните текст задачи в heredoc или версионируемом файле в `prompts/`;
- проверяйте код завершения и помечайте этап CI как неуспешный при ошибке.

## Проектирование безопасности

Работа без оператора означает, что рядом **нет человека, который нажмёт «Отклонить»**:

| Принцип | Реализация |
|---|---|
| Минимальные привилегии | Token только для чтения и ограниченная песочница |
| Без push | CI лишь открывает PR или загружает artifact |
| Фиксированный промпт | Не подставлять напрямую неочищенный текст из описания PR из-за риска инъекции |
| Аудит | Сохранять журналы и artifact с diff |

См. [Сценарии одобрения человеком](/ru/cases/workflows/human-approval-patterns/) и раздел дорожной карты `08-developer-platform/non-interactive/`.

## Сравнение с интерактивным режимом

| | Интерактивный режим | Неинтерактивный режим |
|---|---|---|
| Точка входа | TUI `codex` | `exec` / конвейер |
| Участие человека | Активное | Ограниченное, требует предварительного проектирования |
| Подходит для обучения | Да | Нет |
| Подходит для CI | Нет | Да |

Интерактивный процесс: [Интерактивный режим CLI](/ru/guide/cli/interactive-mode/)

## Как преобразовать интерактивную задачу в неинтерактивную

Не передавайте скрипту всю историю диалога. Надёжнее сжать её до небольшой спецификации:

| Элемент | Что указать |
|---|---|
| Цель | Что именно нужно сделать в этом запуске |
| Входные данные | Какие файлы, diff, журналы или stdin следует прочитать |
| Запреты | Не изменять файлы, не обращаться к сети, не выполнять push, не прерывать CI и т. п. |
| Выходные данные | Текстовая сводка, JSON, файл отчёта или код завершения |
| Приёмка | Какие команды должны пройти и какие ключевые слова не должны появиться |

Неинтерактивный промпт должен быть похож на задачу в трекере: чёткие границы, полные входные данные и однозначные условия ошибки. Задачи, где всё ещё нужно продуктовое решение, выбор дизайна или подтверждение разрешений, оставляйте в интерактивном режиме.

## Распространённые заблуждения

### 1. Неинтерактивный режим эффективнее — значит, его нужно освоить первым?

Не рекомендуется.

Для новичка этот режим обычно слишком быстр и жёсток: по ходу выполнения почти нет возможности уточнить задачу.

### 2. В чём главное отличие от интерактивного режима?

Коротко:

- **Интерактивный режим**: по ходу работы можно задавать вопросы, менять направление и выдавать одобрения
- **Неинтерактивный режим**: однократное выполнение заранее определённого процесса

### 3. Когда пока не стоит его использовать?

Сначала освойте базовые навыки, если вы ещё:

- не умеете формулировать промпты;
- не знаете, как проверять результат;
- не понимаете основы одобрений, песочницы и разрешений.

Неинтерактивный режим предназначен для автоматизации, а не для первых экспериментов. Сначала уверенно освойте интерактивный режим, затем подключайте Codex к скриптам.

## Частые ошибки

- Передавать длинную историю интерактивного диалога в однократный вызов `exec` без изменений
- Использовать в CI производственные учётные данные и разрешение на запись
- Не фиксировать версию CLI, из-за чего поведение конвейера внезапно меняется
