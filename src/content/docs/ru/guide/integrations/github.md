GitHub — самая распространённая среда совместной работы Codex над кодом: Cloud-задачи, проверка PR, Actions и локальный push используют одну систему веток и разрешений.

Здесь рассматривается подключение Codex к процессу совместной работы с репозиторием, ветками, PR и Review.

Даже если у вас пока мало опыта разработки, начните с основных вопросов:

- Где хранится код
- Как изменения предлагаются другим участникам
- Как проходит проверка и слияние

## Рекомендуемые правила команды

```md
## GitHub × Codex (можно добавить в AGENTS.md)

- Защитить ветку main по умолчанию; Codex отправляет изменения только в feature-ветки
- PR должен содержать ссылку на Issue, а описание — сведения о тестах
- Запретить Codex выполнять слияние PR, если release bot не предоставил явное разрешение
- Хранить ключи в GitHub Secrets / environment secrets и не помещать их в промпт
```

## Cloud и локальный Git

| | Локальный clone | Cloud |
|---|---|---|
| Источник кода | Рабочая область на вашем компьютере | Удалённый clone |
| Commit, не отправленный через push | Виден | Не виден — сначала требуется push |
| Среда | Ваша версия Node и системы | Настроенный образ среды |
| Подходит для | Повседневной разработки | Асинхронных длительных задач и стандартизированной сборки |

## Процесс Review

1. Codex или человек открывает PR
2. Человек читает diff — или использует Skill `$pr-review`
3. CI запускает тесты
4. Комментарии приводят к исправлениям — можно создать новую задачу Codex «Обработай только комментарии Review»
5. Человек выполняет слияние

## Распространённые заблуждения

### 1. Интеграция GitHub не означает, что Codex автоматически выполнит всю разработку за вас

Чаще её используют, чтобы:

- Читать контекст репозитория
- Систематизировать diff или Review
- Помогать открыть PR и исправить комментарии

### 2. Что делать, если я ещё плохо понимаю термины PR и Review?

Для начала достаточно следующего:

- **PR**: официально предложить свои изменения для проверки другими людьми
- **Review**: проверка этих изменений другим участником

Этого уровня понимания достаточно для большей части страницы.

### 3. Что важнее всего различать при первом знакомстве с интеграцией GitHub?

В первую очередь различайте не token и не Actions, а следующее:

> **Локальные изменения, удалённый репозиторий и Review в PR — разные вещи.**

Главная задача интеграции GitHub — включить Codex в существующий процесс совместной работы с кодом.

## Безопасность

- Минимизируйте scope GitHub Token
- Соблюдайте осторожность с чувствительными режимами Actions, такими как `pull_request_target`, из-за поверхности для инъекций
- Для автоматизации в PR из Fork нужна дополнительная стратегия изоляции

## Распространённые ошибки

- Cloud-задача предполагает наличие локальных незафиксированных изменений
- Codex выполняет необработанные инструкции из описания PR — инъекция промптов
- Один PR смешивает форматирование и функциональные изменения
