Когда требований много, их легко изложить бессистемно: материалов достаточно, но результат, границы и критерии приёмки перемешаны, поэтому Codex приходится самостоятельно заполнять пробелы.

На этой странице приведена карточка задачи, которую можно использовать как готовый шаблон. Вы узнаете, какую проблему решает каждая её часть и как описание задачи замыкается в цикл «исследование, планирование, выполнение, проверка».

## Для кого предназначен этот материал

- Для читателей, которые уже умеют запускать Codex, но часто сталкиваются с тем, что он «изменил лишнее», «не довёл работу до конца» или «выдал результат, который невозможно оценить»
- Для разработчиков, авторов и команд, которые собираются поручить Agent выполнение задачи, сформулированной устно
- Для тех, кому нужно задать объём длительной задачи, разрешения и условия остановки

## Структура задачи

Информацию можно расположить в следующем порядке:

- Какой результат требуется
- Зачем это нужно
- Какие материалы необходимы
- Где проходят границы
- Как определить, что работа завершена

Строго следовать этому порядку необязательно, но задача станет гораздо надёжнее, если ясно описать все эти пункты.

## Рекомендуемый шаблон

```text
Цель: … (каким должен быть конечный результат)
Контекст: … (почему это важно, каково текущее состояние)
Входные данные: … (связанные файлы / ссылки / вставленный текст)
Ограничения: … (допустимая область изменений, стиль, запреты)
Критерии приёмки: … (проверяемые условия завершения)
Границы полномочий: … (можно ли выходить в интернет, устанавливать зависимости и изменять конфигурацию)
Если информации недостаточно: сначала задай вопрос, не пытайся угадать.
```

![Цикл от описания задачи до проверяемого результата](/illustrations/flow-task-loop.webp)

Шесть пунктов слева на схеме нужны не для того, чтобы сделать промпт длиннее, а чтобы сократить число критически важных пробелов. После начала работы результаты проверки определяют следующий шаг: результат передаётся только после успешной проверки; при неудаче сведения об ошибке возвращаются в описание задачи или план, вместо того чтобы продолжать вносить изменения вслепую.

## Роль каждой части

- **Цель**: не позволяет задаче состоять только из действий без ожидаемого результата
- **Контекст**: помогает Codex понять, почему нужно действовать именно так
- **Входные данные**: передают необходимые файлы, ссылки и материалы
- **Ограничения**: предотвращают выход за границы задачи и необязательные сопутствующие изменения
- **Критерии приёмки**: превращают вопрос «работа завершена?» в проверяемое условие
- **Границы полномочий**: заранее определяют, можно ли выходить в интернет, устанавливать зависимости и изменять конфигурацию

## Распространённые заблуждения

### 1. Каждую часть нужно заполнить подробно

Этот шаблон ближе к контрольному списку, чем к форме с обязательными полями.  
Некоторые задачи не требуют длинного контекста, но при его исключении оснований для принятия решений станет меньше.

### 2. Цель и приёмка — одно и то же

Это разные вещи.

- **Цель** описывает, какой результат вы хотите получить
- **Приёмка** определяет, как убедиться, что результат действительно достигнут

### 3. Входные данные — это все материалы, собранные в одном месте

Важен не объём входных данных, а их релевантность.  
Главное — явно передать материалы, которые Agent обязательно должен изучить.

## Минимальный шаблон задачи

Если сначала нужен просто рабочий вариант, шаблон можно сократить:

```text
Цель: что и во что нужно превратить
Входные данные: связанные файлы или страницы находятся здесь
Ограничения: что именно можно изменять, а чего касаться нельзя
Приёмка: как я проверю, что задача действительно завершена
Если что-то неясно: сначала спроси
```

## От расплывчатого запроса к выполнимой задаче

### Исходный запрос

```text
Помоги оптимизировать главную страницу документации.
```

Здесь не указаны целевая аудитория, допустимая область изменений и критерии того, что после «оптимизации» стало лучше. Даже если Codex подготовит результат, вам будет трудно понять, вышел ли он за границы задачи.

### Выполнимая версия

```text
Цель: переписать текст первого экрана главной страницы документации так, чтобы читатель, впервые знакомящийся с Codex, за 30 секунд понял, что это такое и с чего начать.
Контекст: текущая главная страница предполагает, что читатель уже понимает Agent, контекст и Skill; описание точек входа недостаточно прямое.
Входные данные: src/content/docs/guide/index.md
Ограничения: изменять только этот файл; не менять навигацию, стили и компоненты; при первом упоминании Agent добавить короткое объяснение простыми словами.
Критерии приёмки:
- Первый экран ясно объясняет назначение руководства, целевую аудиторию и первую точку входа для чтения
- Сохранены существующие frontmatter и уровни заголовков
- Не добавлены профессиональные термины без объяснения
- pnpm build выполняется успешно
Границы полномочий: можно читать связанные страницы сайта; нельзя выходить в интернет, устанавливать зависимости и создавать коммиты Git.
Если информации недостаточно: сначала перечисли недостающие сведения и предполагаемую область изменений, затем дождись моего подтверждения.
```

### Ожидаемый процесс выполнения

1. Сначала прочитать главную и соседние страницы входа и описать текущую проблему.
2. Предложить короткий план, затрагивающий только один файл.
3. Изменить текст и показать краткую сводку diff.
4. Выполнить `pnpm build`.
5. По каждому из четырёх критериев приёмки привести подтверждающие свидетельства.

## Как проверить собственное описание задачи

Перед отправкой спросите себя:

- Цель описывает результат или содержит только действия вроде «оптимизировать», «обработать», «посмотреть»?
- Входные данные содержат только действительно относящиеся к делу файлы и материалы?
- В ограничениях указано, чего нельзя касаться?
- Может ли другой человек определить по критериям приёмки, «пройдена проверка или нет»?
- Нужно ли заранее разрешить выход в интернет, установку зависимостей, запись во внешние системы и создание коммитов?
- Если информации недостаточно, Agent должен сначала спросить, изучить доступные материалы или остановиться?

Шаблон можно сокращать в зависимости от масштаба задачи, но исключение каждого раздела уменьшает объём оснований для принятия решений. Для исправления опечатки в одном файле не нужен длинный контекст; для миграции между модулями одной цели недостаточно.
