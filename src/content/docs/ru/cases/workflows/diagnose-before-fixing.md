Если сразу попросить Codex исправить баг, часто приходится переделывать работу. Диагностический процесс строится иначе: **симптом → гипотеза → доказательство → минимальное исправление**.

## Когда применять

- Причина падения теста неизвестна.
- Пришло production-уведомление или пользователь сообщает о «периодической» ошибке.
- После предыдущего исправления проблема сохранилась.

## Шаги

### 1. Заморозьте изменения

```text
Пока не изменяй бизнес-логику. Перечисли шаги воспроизведения, связанные журналы и последние относящиеся к проблеме commit.
```

### 2. Сузьте область поиска

- Бинарный поиск: какой commit внёс проблему?
- Изоляция: минимальный репозиторий или тестовый пример для воспроизведения.

### 3. Сформулируйте гипотезы

Попросите Codex вывести:

```text
Гипотеза A: … Способ проверки: …
Гипотеза B: … Способ проверки: …
```

### 4. Проверьте гипотезы, по возможности только для чтения

Запустите целевые тесты, добавьте временные журналы в одноразовой ветке, изучите мониторинг.

### 5. Внесите минимальное исправление

Исправляйте по одной первопричине; не выполняйте попутный рефакторинг.

### 6. Проведите регрессионную проверку

Запустите исходный падающий сценарий, соседние сценарии и тест, предотвращающий повторение проблемы.

## Шаблон промпта

```text
Следуй принципу «сначала диагностика, затем исправление»:
1. Прочитай @path/to/failing-test и реализацию, объясни причину сбоя со ссылками на строки стека.
2. Предложи 2 гипотезы и способы проверить их только для чтения.
3. Вноси исправление только после того, как я подтвержу гипотезу; затем запусти лишь связанные тесты.
```

## Связь с EPXV

Диагностику можно считать углублённым вариантом этапа **Исследование**. На этапе планирования также нужно явно указать, как откатиться, если гипотеза окажется неверной.

## Распространённые ошибки

- Код изменён до воспроизведения проблемы.
- Один patch одновременно исправляет три проблемы, поэтому его невозможно качественно проверить.
- Временные журналы удалены, но постоянный тест не добавлен.
