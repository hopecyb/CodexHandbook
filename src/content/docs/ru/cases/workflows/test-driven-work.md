При **разработке через тестирование** — TDD, или подходе «сначала тест» — тест сначала должен упасть, после чего минимальная реализация делает его зелёным. Подход хорошо работает в кодовых базах с готовой тестовой инфраструктурой и напрямую применим к таким сценариям, как [исправление бага с проверкой](/ru/cases/use-cases/software-development/fix-a-bug-with-verification/).

## Главное на этой странице

- Когда требовать «сначала написать или запустить тест»
- Как не позволить Codex пропустить этап тестирования
- Как откатиться после падения теста

## Для каких задач подходит

- Репозитории с модульными или интеграционными тестами
- Регрессионные баги, изменения поведения API, рефакторинг

Подход не подходит для прототипов без тестовой инфраструктуры и разовых изменений на сайте только с текстом. В таких задачах лучше использовать ручную проверку в процессе [EPXV](/ru/cases/workflows/explore-plan-execute-verify/).

## Минимальный рабочий вариант

```text
1. Написать падающий тест ожидаемого поведения или указать существующий падающий тест
2. Реализовать только минимальный код, необходимый для прохождения этого теста
3. Запустить связанный набор тестов, затем полный набор
4. Не удалять утверждения и не подменять настоящую логику mock-объектами только ради прохождения теста
```

Промпт:

```text
Работай по TDD: сначала напиши падающий тест для поведения @src/foo.ts «при пустом вводе возвращает []».
Запусти тест и подтверди падение, затем измени реализацию; на каждом шаге запускай только связанный файл тестов.
```

## Рекомендуемый процесс

| Этап | Результат |
|---|---|
| Красный | Падающий тест + объяснение причины падения |
| Зелёный | Минимальная реализация + пройденный тест |
| Рефакторинг | Улучшение кода под защитой тестов — необязательный отдельный шаг |

Сочетайте подход с принципом [Сначала диагностика, затем исправление](/ru/cases/workflows/diagnose-before-fixing/): прежде чем изменять реализацию, прочитайте упавшее утверждение и стек.

## Распространённые ошибки

- Работа объявлена завершённой без запуска теста.
- Тест изменён, чтобы подстроиться под ошибочную реализацию.
- Запущен только один тест, но заявлено, что весь набор зелёный.
- Полный медленный набор E2E запускается на каждом шаге; применяйте `-t` или фильтр по файлу.

## Границы безопасности

- Тестовые команды должны находиться в разрешённых [правилами команд](/ru/guide/customization/rules/command-rules/) границах.
- Если интеграционный тест обращается к production API, запретите это в спецификации или используйте mock.

## Checklist приёмки

- [ ] Есть доказательство перехода теста от падения к успеху — журнал или CI.
- [ ] Проходит полный или согласованный набор тестов.
- [ ] Diff не содержит постороннего удаления тестов.
- [ ] Результат соответствует [критериям завершения](/ru/prompts/define-done/).
