При **работе по спецификации** до массового изменения файлов готовится короткий документ с целью, границами, интерфейсами и критериями приёмки. Этот этап может следовать за [мозговым штурмом](/ru/cases/workflows/brainstorm-before-building/) или сразу переводить уже уточнённые требования в процесс [EPXV](/ru/cases/workflows/explore-plan-execute-verify/).

## Главное на этой странице

- Насколько подробной должна быть спецификация
- Как добиться выполнения спецификации без самовольного расширения области со стороны Codex
- Как спецификация связана с описанием PR и issue

## Минимальный шаблон спецификации

```markdown
## Цель
Пользовательская ценность в одном предложении

## Область
- Включено: …
- Не включено: …

## Интерфейс / поведение
- Входные данные / результат / ошибки

## Критерии приёмки
- [ ] Пункт, проверяемый автоматически
- [ ] Пункт, требующий ручной проверки

## Ограничения
- Неизменяемые модули, производительность, совместимость
```

Шаблон можно хранить в `docs/specs/` репозитория или в тексте issue и ссылаться на него в задаче через `@`.

## Рекомендуемый процесс

```text
① Подготовить черновик спецификации — Codex может помочь, человек проводит Review
② Подтвердить спецификацию → ответить «выполняй по спецификации»
③ Выполнять по шагам, сверяя каждый с критериями приёмки
④ При изменении спецификации явно обновлять номер версии или changelog
```

Пример промпта:

```text
Прочитай @docs/specs/export-csv.md. Сначала сопоставь требования со своим планом реализации и перечисли риски.
Не добавляй функции, которых нет в спецификации. Дождись моего подтверждения и лишь затем пиши код.
```

## Сочетание с разработкой через тестирование

Критерии приёмки в спецификации должны быть по возможности **тестируемыми**. Для пунктов, которые можно выразить тестом, сначала напишите тест; см. [Разработка через тестирование](/ru/cases/workflows/test-driven-work/).

## Распространённые ошибки

- Спецификация разрослась до проектного документа, и ключевые ограничения в ней трудно найти.
- В процессе выполнения область незаметно расширилась, а спецификация не обновилась.
- Расплывчатые критерии приёмки вроде «сделать удобнее» приводят к спорам.
- Спецификация противоречит архитектурным соглашениям из `AGENTS.md`.

## Границы безопасности

- Разрешением на сетевую реализацию считается только явно указанная в спецификации возможность вызывать внешний API.
- Обработка полей с PII должна быть отдельно отмечена в спецификации.

## Checklist приёмки

- [ ] Пункты за пределами области явно исключены.
- [ ] Есть как минимум три проверяемых критерия приёмки.
- [ ] Перед выполнением получено ручное или письменное подтверждение.
- [ ] Изменения отражены в файле спецификации.
