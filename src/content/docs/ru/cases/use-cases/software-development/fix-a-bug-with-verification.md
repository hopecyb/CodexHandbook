Это не шаблон промпта, где для завершения достаточно заменить имя файла. Вы будете работать с настоящим начальным кодом из репозитория: сначала увидите падение теста, а затем проверите, как эталонное исправление позволяет тому же набору тестов пройти успешно.

## Общая информация

| Поле | Значение |
|---|---|
| Для кого | Разработчики |
| Клиент | CLI или IDE — локальный репозиторий |
| Расчётное время | 25–45 минут |
| Предварительные знания | Умение выполнить одну команду Node.js в терминале и прочитать простой JavaScript |
| Зависимости примера | Встроенный в Node.js модуль `node:test`; сторонние пакеты устанавливать не нужно |
| Дата проверки | 2026-08-25 |

## 1. Цель и контекст

**Бизнес-контекст:** функция корзины `calculateTotal` принимает скидку в процентах. Без скидки результат верен, но значение `10`, обозначающее скидку 10%, функция напрямую использует `10` как коэффициент умножения и получает отрицательное число.

**Цель:** найти ошибку расчёта скидки, внести минимальное исправление и тем же набором тестов доказать переход от красного результата к зелёному.

**Критерии успеха:**

- В исходном наборе стабильно падает 1 тест; утверждение показывает: «ожидалось 36, получено -360».
- После исправления проходят все 3 теста.
- Изменено только преобразование процента скидки; API корзины не переписан.
- Вы можете объяснить, почему зелёный результат после исправления нужно сохранять вместе с красным результатом до исправления.

**За рамками:** библиотеки точных денежных расчётов, налоги, конвертация валют, обновление зависимостей и UI.

![Рабочий процесс исправления бага с проверкой](/illustrations/flow-bug-fix.webp)

На схеме особенно важны два обратных перехода: если связанный тест не проходит, вернитесь к минимальному исправлению; если не проходит полная регрессионная проверка или Review diff, вернитесь к анализу первопричины. Не удаляйте утверждения и не расширяйте область изменений только ради скорейшего зелёного результата.

Для полной последовательности обучения используйте [маршрут разработчика](/ru/guide/learning-paths/developer/). В добавленной [сводке запуска от 2026-09-18](/downloads/developer-path/run-record.json) записана повторная проверка начального и эталонного состояний; дата 2026-08-25 ниже относится к исходной проверке примера.

Каталог примера:

```text
examples/complete-workflows/developer/verified-bug-fix/

├── starter/
│   ├── cart.js
│   └── cart.test.js
```

`starter/` — начальная точка упражнения с намеренно оставленным багом; `solution/` — независимо запускаемое эталонное решение. Не выполняйте упражнение непосредственно в эталонном решении.

## 3. Шаг первый — воспроизведите красный тест

Выполните в корне репозитория:

```bash
node --test examples/complete-workflows/developer/verified-bug-fix/starter/cart.test.js
```

Ожидаемый результат: команда завершается с ненулевым кодом, падает 1 из 3 тестов. Ключевой фрагмент вывода выглядит примерно так:

```text
Expected values to be strictly equal:

-360 !== 36
```

Если тест не падает, остановитесь. Проверьте, действительно ли запущен вариант из `starter/`, версию Node.js и не был ли файл изменён заранее. Без стабильного красного теста нет исходного доказательства проблемы.

## 4. Шаг второй — исследуйте только для чтения

### Исследование

```text
Пока не изменяй файлы. Прочитай:
- examples/complete-workflows/developer/verified-bug-fix/starter/cart.js
- examples/complete-workflows/developer/verified-bug-fix/starter/cart.test.js

Не более чем в 6 пунктах объясни:
1. какие входные данные вызывают сбой;
2. каковы ожидаемое и фактическое значения;
3. чем процент отличается от коэффициента в формуле;
4. в какой строке должно находиться минимальное исправление;
5. какое публичное поведение менять нельзя;
6. какие проверки нужно выполнить после исправления.
```

Корректное объяснение первопричины должно отметить: вызывающая сторона передаёт `10` в значении 10%, а реализация напрямую вычисляет `subtotal * 10`, не выполняя деление на `100`.

## 5. Шаг третий — спланируйте и внесите минимальное исправление

```text
Измени только преобразование процента скидки в starter/cart.js.
Не меняй имя функции, параметры, утверждения тестов или структуру файлов и не добавляй зависимости.

После исправления последовательно:
1. запусти starter/cart.test.js;
2. покажи фактическую сводку тестов;
3. кратко опиши изменённую строку и причину изменения;
4. не выполняй commit или push в Git.
```

Суть минимального исправления:

```js
const discount = subtotal * (discountPercent / 100);
```

Не добивайтесь зелёного результата заменой `36` на `-360` в тесте: это лишь перепишет ожидаемый результат, но не исправит бизнес-правило.

## 6. Шаг четвёртый — подтвердите зелёный тест

Если не хотите изменять начальную точку упражнения, можно сразу запустить эталонное решение:

```bash
node --test examples/complete-workflows/developer/verified-bug-fix/solution/cart.test.js
```

Ожидаемый результат: проходят все 3 теста, процесс завершается с кодом 0.

Журнал проверки должен как минимум содержать:

| Доказательство | На какой вопрос оно отвечает |
|---|---|
| Команда, завершившаяся ошибкой до исправления | Можно ли стабильно воспроизвести исходную проблему? |
| Упавшее утверждение | Действительно ли тест покрывает этот баг? |
| Diff кода | Затрагивает ли изменение только первопричину? |
| Связанный тест после исправления | Стало ли то же поведение корректным? |
| Более широкий набор тестов | Не нарушены ли соседние функции? |

В каталоге упражнения есть только один набор тестов. В реальном проекте дополнительно выполните lint, проверку типов и полный набор тестов согласно `AGENTS.md`.

## 7. Review

```text
Проведи Review исправления, не изменяя файлы. Сначала перечисли замечания, затем дай итог:
- действительно ли исправлено преобразование процентов, а не ослаблены тесты;
- изменились ли сигнатура функции или посторонняя логика;
- покрыты ли пустая корзина, отсутствие скидки и скидка 10%;
- какие риски точности денежных расчётов остаются за рамками этого примера.
```

Вручную также убедитесь, что не добавлены зависимости, отладочные журналы, форматирование всего файла и операции Git.

## 8. Сбои и восстановление

| Проблема | Решение |
|---|---|
| Исходный тест не падает | Убедиться, что запускается `starter/cart.test.js`, и восстановить неизменённую начальную точку |
| После изменения теста результат стал зелёным | Восстановить утверждение теста и изменить только преобразование процентов в реализации |
| Связанный тест по-прежнему падает | Сравнить ошибочное значение и проверить положение `/ 100` |
| В полном наборе тестов появились новые ошибки | Вернуться к анализу первопричины и проверить публичное поведение и область изменений |
| Тест падает время от времени | Сначала стабилизировать тестовую среду; один зелёный запуск не считается доказательством |

## 9. Перенесите подход в реальный репозиторий

Замените пути из примера своими файлами, сохранив структуру доказательств:

```text
Цель: исправить [наблюдаемое ошибочное поведение].
Команда воспроизведения: [точная команда]; текущая стабильная ошибка: [ключевое утверждение].
Область: изменяй только [файл реализации] и необходимые тесты; не выполняй рефакторинг и не обновляй зависимости.
Приёмка: исходный падающий тест проходит; новый тест граничного случая проходит; [полная команда] проходит; в diff нет посторонних изменений.
Права: не выполняй push, публикацию или изменение production-данных; если нужны дополнительные права, остановись и объясни.
Сначала только для чтения определи первопричину и риски; дождись моего подтверждения плана и лишь затем вноси изменения.
```

## 10. Закрепите процесс

- Если подобные баги повторяются, добавьте соответствующее правило в `AGENTS.md`.
- Можно выделить Skill `regression-guard`, который требует фиксировать красный тест, зелёный тест и регрессионные доказательства.
- Добавьте часто используемые тесты граничных случаев в CI, а не оставляйте их только в диалоге.
