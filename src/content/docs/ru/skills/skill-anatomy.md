При первом знакомстве с каталогом Skill часто кажется: «Все эти папки мне знакомы, но непонятно, зачем раскладывать файлы именно так».

На этой странице показано, как разделить основной процесс, длинные пояснения, шаблоны и скрипты, чтобы не складывать всё в один файл.

Так содержимое удобнее читать, изменять и использовать повторно, а структура не превращается со временем в беспорядок.

## Структура каталога

```text
my-skill/
├── SKILL.md          # обязательно
├── scripts/          # необязательно: детерминированные шаги
├── references/       # необязательно: объёмная справочная документация
└── templates/        # необязательно: шаблоны результата
```

## Назначение каждого уровня

- `SKILL.md`: основная инструкция, которая объясняет Codex, что это за Skill, когда его применять и по каким шагам действовать
- `references/`: хранилище объёмных материалов, позволяющее не перегружать основной файл фоновыми сведениями
- `templates/`: готовые каркасы результата, чтобы не придумывать структуру заново при каждом запуске
- `scripts/`: скрипты для детерминированных шагов, которые не стоит описывать только естественным языком

Вначале может быть достаточно одного `SKILL.md`.  
Разделяйте `references/`, `templates/` и `scripts/` лишь после реального усложнения процесса.

## Загрузка по мере необходимости, а не всего сразу

Поддерживаемый Skill обычно состоит из трёх уровней:

| Уровень | Содержимое | Когда используется |
|---|---|---|
| Метаданные | Имя, описание, сценарии запуска | Помогают Codex решить, применять ли Skill |
| Основная инструкция | Обязательные шаги, запреты, критерии завершения | Читается первой после запуска Skill |
| Приложения | Шаблоны, справочные материалы, скрипты, примеры | Открываются или запускаются лишь тогда, когда действительно нужны задаче |

Так в обычном состоянии видна только короткая инструкция по запуску, а подробности загружаются непосредственно при выполнении. Чем больше Skill, тем важнее такое разделение.

## Минимальный пример SKILL.md

```md
---
name: pr-review
description: Проверьте diff текущей ветки относительно main, отметьте риски и пробелы в тестах. Используйте, когда пользователь просит выполнить review, проверить PR или провести проверку перед слиянием.
---

## Шаги
1. Получите diff относительно main
2. Разделите замечания по файлам и категориям: логические ошибки, безопасность, производительность, тесты
3. Выведите список по уровням: блокирует / рекомендуется / nit
4. Не выполняйте push или слияние автоматически
```

## Распространённые заблуждения

### 1. С самого начала нужно создать все каталоги

Многие хорошие Skill сначала состоят только из `SKILL.md`. Остальные каталоги появляются постепенно, по мере повторного использования.

### 2. `references/` нужен просто для дополнительного содержимого

Главное не количество материалов, а возможность вынести длинные пояснения, которые не должны постоянно отвлекать от основного процесса, и читать их только по необходимости.

### 3. Лучше по возможности обходиться без `scripts/`

Если шаг должен быть стабильным, детерминированным и воспроизводимым, скрипт обычно надёжнее постоянного описания естественным языком.

## Ответственность каталогов

| Каталог | Назначение |
|---|---|
| `SKILL.md` | Основной процесс, условия запуска, запреты |
| `references/` | Объёмная документация, стандарты, описание API |
| `templates/` | Формат результата, каркасы отчётов |
| `scripts/` | Детерминированные команды и проверки |

## Когда разделять каталоги

Ответьте по порядку на следующие вопросы:

1. Не стал ли основной процесс слишком длинным для первого прочтения?
2. Есть ли большой блок материалов, который нужен не при каждом запуске?
3. Повторяется ли один и тот же формат результата?
4. Стал ли один из шагов настолько устойчивым, что его пора перенести в скрипт?

Если на один или два вопроса ответ «да», можно начинать разделение.

## Как шаблон превращается в Skill

Многие команды начинают не с «проектирования Skill», а с фрагмента промпта, который приходится постоянно копировать. Развивайте его в таком порядке:

| Этап | Форма | Когда переходить дальше |
|---|---|---|
| Разовый промпт | Находится в текущем диалоге | Используется один раз, повторное применение не нужно |
| Шаблон | Хранится в шаблонах промптов или командной документации | Однотипные задачи повторяются, но шаги ещё меняются |
| Skill в одном файле | Один `SKILL.md` | Процесс стабилен, условия запуска ясны |
| Полный каталог Skill | `SKILL.md` + `templates/` + `references/` + `scripts/` | Формат результата, объёмные справочные материалы и детерминированные проверки стали устойчивыми |

Не спешите превращать каждый шаблон в Skill. Закрепления заслуживают процессы, которые уже повторялись, имеют ясные критерии успеха и должны выполняться командой единообразно.

## Типичные компоненты многократно используемого Skill

| Компонент | Подходящее содержимое |
|---|---|
| Основная инструкция | Условия запуска, шаги выполнения, запреты, критерии завершения |
| Шаблоны | Результат Review PR, структура документа, формат отчёта о рисках |
| Справочные материалы | Стандарты кода, глоссарии, правила предметной области, описание API |
| Скрипты | Анализ сложности, проверка ссылок, статистика покрытия тестами, проверка формата |

Хороший Skill — не просто «более длинный промпт», а многократно используемый процесс, разделённый на читаемые, тестируемые и сопровождаемые части.

Сначала добейтесь работы `SKILL.md`, а затем, по мере реального усложнения, выносите материалы, шаблоны и скрипты в отдельные каталоги.
