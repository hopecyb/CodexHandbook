При первом знакомстве со Skill часто возникает вопрос: стоит ли вообще оформлять эту задачу как отдельный Skill?

Если превращать в Skill всё подряд, система станет слишком тяжёлой. Если же не закреплять процессы, которые этого заслуживают, придётся снова и снова вручную повторять одни и те же указания. Эта страница поможет понять, когда рабочий процесс стоит зафиксировать.


![Иллюстрация: конвейер доставляет карточки задач к развилке; повторяющиеся, чёткие и многошаговые задачи отправляются в светящийся набор инструментов, а разовые и неясные — в обычное облако диалога](/illustrations/skills-when.webp)

## Когда стоит создать Skill

- Один и тот же процесс вручную повторяется уже в третий раз
- Нужен подробный контрольный список, который не хочется каждый раз помещать в контекст
- Модель должна сама определять момент запуска по `description`
- Команде требуется общий версионируемый рабочий процесс

## Критерии подходящей задачи

О создании Skill стоит серьёзно задуматься, если одновременно выполняются два условия:

- Вы будете выполнять задачу снова
- Вы хотите в следующий раз придерживаться того же подхода

Многие Skill создаются для таких сценариев:

- Review diff
- Создание changelog
- Проверка перед выпуском
- Публикация документации

Эти задачи несложны, но хорошо подходят для многократного использования.

## Когда Skill подходит хуже

- Разовая задача, которая никогда прежде не повторялась
- Очень короткая фиксированная команда, которую легко запомнить (рассмотрите slash-команду)
- Задача зависит от быстро меняющегося состояния внешней системы в реальном времени (рассмотрите MCP)

## Распространённые заблуждения

### 1. Важную задачу обязательно нужно оформить как Skill

Важность ещё не означает пригодность для повторного использования.  
Если задача представляет собой особый разовый случай, Skill может лишь увеличить затраты на сопровождение.

### 2. Чем больше Skill, тем лучше

Большое число Skill с размытыми границами повышает риск неверного применения моделью и усложняет сопровождение для команды.

### 3. Если можно подключить внешнюю систему, сначала нужен Skill

Подключение внешней системы часто относится к MCP. Skill отвечает за «процесс», а связь с внешней системой всё равно обеспечивает MCP.

## Как проверить идею

Если вы не уверены, стоит ли закреплять процесс, сначала несколько раз выполните его так:

1. Два или три раза завершите задачу вручную
2. Проследите, повторяете ли вы каждый раз одну и ту же последовательность проверок
3. Если да, оформите её как Skill

Такой Skill будет надёжнее, потому что основан на реальном повторяющемся процессе, а не придуман с нуля.

## Сравнение с другими способами расширения

| Способ | Для чего подходит |
|---|---|
| Skill | Многократно используемые процессы, прогрессивное раскрытие |
| MCP | Подключение внешних API и источников данных |
| Hooks | Автоматическое выполнение в определённые моменты событий |
| `AGENTS.md` | Постоянные соглашения уровня проекта |

Skill лучше всего закрепляет процесс, который «повторяется, должен выполняться единообразно и не должен каждый раз объясняться заново».
