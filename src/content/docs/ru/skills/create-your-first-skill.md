Если вы уже умеете ставить задачи, но ещё не создавали Skill, на этой странице описан базовый процесс разработки первого из них.

Вместо долгого изучения теории полезнее за 15–30 минут собрать небольшой Skill с чёткими границами, который **можно многократно использовать в репозитории**.

![Иллюстрация: маленький помощник собирает первый Skill на верстаке, словно конструктор — вставляет карточку с инструкциями, проверяет diff через лупу, отмечает пункты списка и устанавливает флажок на готовую папку](/illustrations/skills-first-skill.webp)

## Для кого это упражнение

Для тех, кто уже выполнил [первую задачу](/ru/cases/first-task/) и готов экспериментировать в тестовом репозитории.

## Почему лучше начать с `pr-review`

У такого Skill несколько преимуществ:

- Относительно понятные входные данные
- Меньший риск, чем при прямом изменении кода
- Результат легко оценить
- Заодно можно разобраться в способах запуска Skill и описании его границ

На этом примере удобно учиться превращать рабочий процесс в многократно используемый инструмент.

## Ожидаемый результат

В `.agents/skills/pr-review/` находится Skill, который выдаёт структурированные замечания Review по текущим изменениям.

## Минимальная цель

Для первого Skill достаточно трёх свойств:

1. Он обнаруживается системой
2. Стабильно выполняет один чётко определённый процесс
3. Не совершает опасных действий заодно с основной задачей

После этого дальнейшие итерации пойдут гораздо легче.

## Шаги

### 1. Создайте каталог

```bash
mkdir -p .agents/skills/pr-review
```

### 2. Напишите SKILL.md

```md
---
name: pr-review
description: Проведите Review git diff, перечислите блокирующие проблемы, пробелы в тестах и рекомендации по стилю. Используйте, когда пользователь упоминает review, проверку или проверку перед слиянием. Не используйте для разработки новых возможностей.
---

# Review PR

## Входные данные
- Ветка для сравнения по умолчанию: main (если её нет, используйте ветку по умолчанию)

## Процесс
1. Перечислите изменённые файлы и виды изменений (функциональность / исправление / рефакторинг / документация)
2. Для каждого изменения логики проверьте, не отсутствуют ли тесты и не нарушен ли API
3. Проверьте наличие секретов, отладочных журналов и слишком большого нерелевантного diff
4. Выведите:
   - 🔴 Блокирует: необходимо исправить
   - 🟡 Рекомендуется: следует исправить
   - 🟢 Пройдено: требования AGENTS.md выполнены

## Запрещено
- Не выполняйте git push
- Не изменяйте публичные API, которые не обсуждались
```

### 3. Испытайте локально

Откройте репозиторий в Codex и попробуйте:

```text
$pr-review Проверьте мои текущие незакоммиченные изменения
```

Или сформулируйте естественным языком: «Проведи Review diff по правилам команды, уделив особое внимание тестам».

### 4. Сначала проверьте явный запуск, затем неявный

Не начинайте с проверки автоматического запуска.

Используйте такой порядок:

1. Явно вызовите `$pr-review`
2. Убедитесь, что процесс и результат верны
3. Затем попробуйте запустить Skill естественным языком

Так проще понять, проблема в содержимом Skill или в недостаточно ясных условиях запуска в `description`.

### 5. Уточняйте description

Если модель **никогда не выбирает Skill автоматически**, сузьте или дополните слова запуска в `description`. Если она **слишком часто применяет его не к месту**, укажите, когда Skill использовать не следует.

### 6. Закоммитьте для команды

```bash
git add .agents/skills/pr-review
git commit -m "docs: add pr-review skill for Codex"
```

Добавьте в командный README или `AGENTS.md` строку: «Перед слиянием можно использовать `$pr-review`».

## Распространённые заблуждения

### 1. Первый Skill должен охватывать как можно больше

Чаще верно обратное. Чем меньше и конкретнее первый Skill, тем проще понять, действительно ли он полезен.

### 2. Главное — написать «умный» Skill

Гораздо важнее **чётко задать границы**.

Что Skill должен и чего не должен делать — важнее внешней сложности.

### 3. Если Skill запускается, значит он готов

Полезный Skill как минимум должен отвечать следующим требованиям:

- Другим понятно, когда его использовать
- У результата есть постоянная структура
- Skill не совершает опасных действий заодно с основной задачей

## Контрольный список приёмки

- [ ] `$pr-review` успешно выполняется и не запускает опасные операции git
- [ ] Результат содержит выводы по уровням серьёзности, а не общие рассуждения
- [ ] `description` описывает сценарий запуска одним предложением
- [ ] Потребность в скриптах проверена по разделу [«Разрешения и подтверждения»](/ru/guide/permissions-and-sandbox/) (в этом примере скриптов нет)

Начав с небольшого и надёжного Skill, проще последовательно применять один ясный рабочий процесс.
