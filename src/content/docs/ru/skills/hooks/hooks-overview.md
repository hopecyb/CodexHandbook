Hooks позволяют запускать в цикле Agent Codex командные скрипты или инструменты подключённого сервера MCP. Типичные применения: поиск секретов в промптах, политики вызова инструментов, аудит, сводки сеанса и проверка перед остановкой.

![Жизненный цикл Hook в Codex: события сеанса, раунда задачи, вызова инструмента, сжатия и дочернего Agent](/illustrations/flow-hook-lifecycle.webp)

Главное различие на схеме: `PreToolUse` может отклонить или изменить входные данные до выполнения поддерживаемого локального инструмента; `PostToolUse` происходит после завершения инструмента и не способен отменить уже возникшие побочные эффекты.

## Откуда берётся конфигурация

Codex ищет конфигурацию рядом с активными уровнями:

- `~/.codex/hooks.json`
- `~/.codex/config.toml`, секцию `[hooks]`
- `<repo>/.codex/hooks.json`
- `<repo>/.codex/config.toml`, секцию `[hooks]`
- Hook из включённого Plugin
- Управляемый Hook, распространённый администратором через систему, MDM, Cloud или `requirements.toml`

Проектный `.codex/` загружается только для доверенного проекта. Совпадающие Hook из нескольких источников выполняются вместе; конфигурация с более высоким приоритетом не переопределяет целиком Hook с более низкого уровня.

Если на одном уровне одновременно присутствуют `hooks.json` и встроенный `[hooks]`, они объединяются, а при запуске появляется предупреждение. По возможности используйте на одном уровне только один способ представления.

## Неуправляемый Hook необходимо проверить

Codex регистрирует доверие по хешу определения Hook. Новый или изменённый неуправляемый Hook помечается как ожидающий Review и пропускается, пока пользователь не признает новое определение доверенным.

Команда `/hooks` в CLI позволяет просмотреть источник, проверить изменения, признать доверенным или отключить отдельный неуправляемый Hook. Hook из Plugin проходит тот же процесс доверия. Доверие к управляемому Hook задаётся политикой организации; пользователь не может отключить его в личном каталоге Hook.

## Два исполняемых обработчика

| Обработчик | Назначение | Ключевое ограничение |
|---|---|---|
| `command` | Запускает локальный скрипт, получающий JSON события через stdin | Сам скрипт обладает возможностями локального процесса; необходимо проверить зависимости и вывод |
| `mcp_tool` | Вызывает инструмент подключённого сервера MCP | Не запускает и не переподключает сервер самостоятельно; `SessionEnd` не поддерживается |

Согласно текущей официальной документации, обработчики `prompt` и `agent` могут быть разобраны, но будут пропущены; их не следует помещать в рабочую конфигурацию.

## Поведение во время выполнения

- Несколько совпадающих командных Hook запускаются параллельно; один Hook не может помешать запуску другого, который уже совпал.
- По умолчанию `timeout` большинства Hook равен 600 секундам; для `SessionEnd` значение по умолчанию — 1 секунда, максимум — 3 секунды. В рабочих защитных скриптах всё равно следует явно задавать короткий тайм-аут.
- Рабочий каталог командного Hook — `cwd` сеанса. Скрипт репозитория должен определять корень Git, чтобы относительный путь находился и при запуске из подкаталога.
- Асинхронный Hook подходит для журналов и аналитики, но не может блокировать, подтверждать, изменять или контролировать вызвавшую его операцию.

## Связь с другими уровнями безопасности

| Уровень | Ответственность |
|---|---|
| Песочница | Границы доступа к файлам, сети и системным возможностям |
| Подтверждение | Решение человека до выполнения высокорискового действия |
| Правила команд | Декларативное разрешение или запрещение известных шаблонов команд |
| Hook | Пользовательская тестируемая логика в точке жизненного цикла |
| Серверные разрешения | Окончательные права чтения и записи во внешней системе |

Охват инструментов в Hook не образует полной границы безопасности. Официальная документация прямо указывает, что некоторые специализированные пути инструментов могут обходить стандартный маршрут Hook; размещённые инструменты (Hosted tools), например WebSearch, также не проходят через локальные `PreToolUse` / `PostToolUse`.

## Порядок внедрения

1. Начните с обезличенного журнала в `PostToolUse` или `SessionEnd`, чтобы увидеть фактическое поведение.
2. Для проблем с высокой уверенностью используйте напоминание через `systemMessage` или дополнительный контекст.
3. Блокируйте в `PreToolUse` только при однозначном правиле, наличии фиксированных тестовых данных для скрипта и приемлемом уровне ложных срабатываний.
4. Согласуйте Hook с CI, проверками перед коммитом и серверными разрешениями, чтобы не возникло трёх противоречащих друг другу политик.

## Сторонний инструмент для рассмотрения

Если вы не хотите писать защитный скрипт с нуля, в качестве кандидата можно оценить [HOL Guard](https://github.com/hashgraph-online/hol-guard). Это сторонний проект с открытым исходным кодом под лицензией Apache-2.0. Согласно [руководству по интеграции с Codex 3.x](https://hol.org/guard/docs/guard/codex-harness), установщик регистрирует `PreToolUse`, `PermissionRequest` и другие Hook, а также использует стартовую обёртку (shim) и прокси для части MCP. Для поддерживаемых путей он отклоняет, сопровождает предупреждением или передаёт человеку на подтверждение shell-команды, чтение чувствительных данных, вызовы MCP и операции с пакетами в соответствии с локальной политикой, а не всегда приостанавливает их в ожидании подтверждения. Guard Cloud — отдельная необязательная платная услуга; локальная защита не требует входа в Cloud.

Это не официальный инструмент OpenAI, и сайт не проверял независимо ни коэффициент перехвата, ни безопасность. Перед испытанием выполните `hol-guard install codex --dry-run`, проверьте изменения в `~/.codex/config.toml`, команде запуска и конфигурации MCP, а затем сверьтесь с актуальным описанием [охвата и поведения при сбоях](https://github.com/hashgraph-online/hol-guard/blob/main/docs/guard/harness-support.md). Отрепетируйте ситуации, когда ошибка Hook, тайм-аут или неверный формат ответа могут привести к разрешению операции, а также порядок удаления и возврата к исходному состоянию. Как и самостоятельно написанный Hook, инструмент ограничен охватом инструментов Codex и не заменяет песочницу, минимальные разрешения, управление секретами или серверный контроль.

## Контрольный список приёмки

- [ ] Имя события взято из актуального официального списка
- [ ] matcher охватывает только необходимые инструменты или источники
- [ ] Для скрипта есть тесты с фиксированными входными данными и понятные сообщения об ошибках
- [ ] В журнале не сохраняются токены, полные промпты или чувствительные аргументы инструментов
- [ ] Проверены пути сбоя, тайм-аута и отключения Hook
- [ ] Команда понимает значение изменений доверия в `/hooks`
