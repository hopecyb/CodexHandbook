Из этой главы удалены условные имена событий и поля конфигурации устаревшей версии. Пример соответствует текущей официальной структуре `hooks.json` и сопровождается исполняемыми тестами.

Полные файлы находятся в [`examples/hooks/secret-guard/`](https://github.com/hopecyb/CodexHandbook/tree/main/examples/hooks/secret-guard).

## Цель и границы

Цель: отклонить вызов до выполнения инструмента, если входная команда `Bash` или `apply_patch` содержит тестовую строку, похожую на AWS Access Key ID.

Пример предназначен только для демонстрации входных и выходных данных Hook и структуры тестов:

- Не заменяет профессиональный сканер секретов
- Регулярное выражение даёт ложные срабатывания и пропуски
- Не сканирует размещённые инструменты (Hosted tools)
- Не должен записывать в журнал полные входные данные инструмента

## 1. Настройте hooks.json

```json
{
  "description": "Block obvious secret-shaped strings before local writes.",
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|apply_patch",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"$(git rev-parse --show-toplevel)/examples/hooks/secret-guard/pre_tool_use_guard.py\"",
            "timeout": 3,
            "statusMessage": "Checking tool input for secret-shaped strings"
          }
        ]
      }
    ]
  }
}
```

При реальном использовании в репозитории конфигурацию обычно помещают в `.codex/hooks.json`, а скрипт — в `.codex/hooks/`. Здесь сохранён путь examples, чтобы полные материалы из репозитория руководства можно было проверить напрямую.

## 2. Результат отклонения

Скрипт читает JSON события из stdin и проверяет только `tool_input.command`. При совпадении он выводит:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Secret-shaped string blocked by example hook."
  }
}
```

Если совпадения нет, скрипт завершается с кодом `0` и ничего не выводит. Обычный текст stdout не считается допустимым решением `PreToolUse`.

## 3. Запустите тесты

```bash
python3 -m unittest discover examples/hooks/secret-guard -p 'test_*.py'
```

Ожидаемый результат: успешно пройдены три теста — для обычной команды, строки, похожей на секрет, и `tool_input`, который не является словарём.

Тестовый пример также можно передать вручную:

```bash
printf '%s\n' '{"hook_event_name":"PreToolUse","tool_name":"Bash","tool_input":{"command":"git status"}}' \
  | python3 examples/hooks/secret-guard/pre_tool_use_guard.py
```

Для обычных входных данных stdout остаётся пустым.

## 4. Включите в проекте

1. Поместите конфигурацию и скрипт в целевой репозиторий, заменив путь на устойчивый путь внутри него.
2. В изолированном репозитории запустите модульные тесты и одну настоящую безопасную команду.
3. Запустите Codex, откройте `/hooks` и проверьте источник и точное определение.
4. После предоставления доверия отдельно проверьте «обычный вызов разрешён» и «тестовая строка отклонена».
5. После изменения скрипта снова выполните Review: новый хеш вернёт неуправляемый Hook в состояние ожидания доверия.

## От предупреждения к блокировке

В рабочих командах обычно начинают с неблокирующего аудита или дополнительного контекста и лишь затем переходят к deny. Перед переходом ответьте как минимум на следующие вопросы:

- Охватывают ли тестовые данные известные ложные срабатывания?
- Поймёт ли пользователь сообщение при тайм-ауте или сбое скрипта?
- Подстраховывается ли правило также политикой CI или сервера?
- Можно ли проверить обход и аварийное восстановление по журналам?
