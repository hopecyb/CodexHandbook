При первом знакомстве со Skill часто думают: «После установки он начнёт действовать сам». Использовать Skill — значит поручить Codex выполнить задачу по заранее описанному рабочему процессу.

Вы можете **явно назвать** нужный Skill, но в подходящем сценарии модель способна **выбрать его автоматически**. Если различать эти два способа запуска, диагностика станет намного проще.


![Иллюстрация: два способа запуска рядом — слева рука прямо указывает на определённый набор инструментов (явный вызов), справа помощник читает метки и сам выбирает подходящий набор (неявный запуск)](/illustrations/skills-trigger.webp)

## Способы запуска

1. **Явный**: в поддерживаемой среде вызовите `$skill-name` (имя должно совпадать с `name` во frontmatter)
2. **Неявный**: модель определяет применимость к текущей задаче по смыслу `description`

## Как различать способы запуска

- **Явный запуск**: вы прямо говорите: «Используй этот Skill»
- **Неявный запуск**: вы не называете Skill, но описание задачи совпадает со сценарием его применения

В начале работы со Skill лучше использовать **явный запуск**. Так проще проверить:

- Обнаружен ли Skill
- Соответствует ли его поведение ожиданиям
- Правильно ли заданы имя и описание

## Пример

```text
$pr-review Проверьте мои текущие незакоммиченные изменения
```

Можно использовать и естественный язык: «Проведи Review diff по правилам команды, уделив особое внимание тестам».

## Распространённые заблуждения

### 1. Если я создал Skill, он обязательно запустится автоматически

Автоматический запуск зависит от ясности `description` и от того, насколько текущая задача похожа на описанный сценарий применения.

### 2. Запуск естественным языком и через `$name` всегда даёт одинаковый результат

Это не гарантируется.

`$name` однозначнее и подходит для проверки или принудительного применения. Естественный язык удобнее, но иногда модель выбирает не тот Skill или не использует ни одного.

### 3. Если Skill не запустился, проблема обязательно в нём

Причина может быть и другой:

- Неверное имя
- Слишком общее `description`
- В описании задачи нет слов, совпадающих с условиями запуска

Поэтому при диагностике проверяйте не только наличие файла, но и то, выглядит ли его содержимое как описание инструмента, который модель способна выбрать.

## Типичный порядок проверки

Чтобы сначала добиться одного успешного запуска:

1. Явно вызовите `$skill-name`
2. Проверьте, соответствует ли результат ожиданиям
3. Скорректируйте `description`
4. Лишь затем проверьте запуск естественным языком

Так можно отделить проблему самого Skill от неудачно сформулированного условия автоматического запуска.

## Как составить хорошее description

- Укажите, когда Skill следует и когда не следует использовать
- Включите слова, которые может употребить пользователь (review, выпуск, changelog)
- Избегайте расплывчатых формулировок вроде «помогайте пользователю писать код»
- Помещайте основной сценарий запуска в самое **начало** (у списка Skill есть ограничение по числу символов)

## Как понять, достаточно ли ясно description

Удобный критерий:  
прочитав `description`, можно сразу понять, когда использовать Skill, а когда не использовать.

Если после чтения кажется, что описание подходит почти для любой задачи, оно, скорее всего, слишком общее.

Дополнительные понятия см. в [обзоре Skills](/ru/skills/overview/).
