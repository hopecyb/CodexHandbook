Главная сложность задачи по расписанию не в выборе времени запуска, а в том, чтобы каждый автономный запуск имел стабильные входные данные, узкие разрешения, проверяемый результат и условия остановки.

![Безопасный цикл от ручной проверки к запуску по расписанию, проверке человеком и корректировке](/illustrations/flow-scheduled-safety.webp)

## Для кого это руководство

- Для пользователей, которые хотят ежедневно или еженедельно создавать отчёты, проверять документацию или отслеживать PR
- Для разработчиков, которым нужно периодически выполнять обслуживание в локальном проекте или изолированном Worktree
- Для сопровождающих, которые оценивают разрешения, обработку сбоев и командные Skill

## Границы поддержки

| Среда | Возможности | Основные ограничения |
|---|---|---|
| ChatGPT Web | Создание, управление и просмотр запусков; использование загруженных файлов, подключённых инструментов, Skills и Plugins | Нет прямого доступа к локальным папкам компьютера |
| Настольное App ChatGPT | Создание и управление; можно выбрать локальный проект или Git Worktree | Для задач с локальными файлами компьютер должен быть включён, App — работать, а проект — существовать |
| Codex CLI | Подготовка и ручное тестирование промптов, Skill и скриптов | Нет интерфейса управления Scheduled |
| Расширение IDE | Проверка команд и изменений в рабочей области | Нет интерфейса управления Scheduled |

## 1. Выберите отдельную задачу или задачу внутри чата

### Отдельная Scheduled task

Каждый запуск начинается с сохранённого промпта и отображается в Scheduled как отдельный запуск. Подходит для независимых ежедневных и еженедельных отчётов или проверки состояния проектов; одна задача может охватывать несколько проектов.

### Scheduled task внутри чата

По расписанию задача возвращается в тот же чат и продолжает использовать существующий контекст. Подходит для опроса состояния долгой задачи, отслеживания PR, продолжительного исследования и другой работы, где нужно сохранять предыдущие обсуждения.

Критерий выбора: если каждый запуск должен «начинаться заново», создайте отдельную задачу; если нужен контекст одной и той же проблемы, используйте задачу внутри чата.

## 2. Выберите материалы для запуска

### Запуск в Web

Поместите устойчивые инструкции в промпт задачи или Skill, а необходимые материалы — в загруженные файлы, Project либо подключённый сервис. Не пишите «прочитай latest.csv на моём рабочем столе»: Web не имеет прямого доступа к локальному пути.

### Локальный проект в настольном App

Для Git-репозитория можно выбрать:

- **Локальный проект**: работа выполняется прямо в основной рабочей копии и может затронуть файлы, которые вы редактируете.
- **Выделенный Worktree**: фоновые изменения изолированы от незавершённой работы; подходит для задач, изменяющих файлы.

Проект без Git запускается непосредственно из каталога проекта. Частые задачи с Worktree накапливают рабочие деревья; архивируйте ненужные запуски, чтобы не сохранять множество Worktree по неосторожности.

## 3. Сначала проверьте вручную

Сначала выполните в обычном чате абсолютно тот же промпт с той же моделью, интенсивностью рассуждений и инструментами. Как минимум убедитесь, что:

- Входные данные понятны без дополнительных пояснений в момент запуска
- При отсутствии изменений задача завершается без лишнего шума
- Человек может быстро проверить результат
- Команды, Skill и подключённые инструменты работают
- При нехватке разрешений или материалов задача останавливается и объясняет проблему, а не делает предположения

Просмотрите первые несколько запусков по расписанию и только затем меняйте промпт или частоту.

## 4. Готовый промпт задачи для адаптации

```text
Создай отдельную Scheduled task:

Название: еженедельная проверка битых ссылок в документации
Время: каждый понедельник в 09:00 по текущему часовому поясу
Место запуска: выделенный Worktree текущего Git-проекта

При каждом запуске:
1. Читай только docs/, src/content/docs/, examples/ и public/diagrams/.
2. Выполни pnpm check:links.
3. Если проверка успешна, сообщи только число проверенных файлов и ссылок, не изменяй файлы.
4. Если проверка не пройдена, перечисли результаты в формате «исходный файл, недоступная цель, рекомендуемое исправление»; не исправляй ссылки автоматически.
5. Не выходи в сеть, не устанавливай зависимости, не выполняй commit и push, не создавай PR.
6. Если команда отсутствует, зависимости недоступны или результат неоднозначен, остановись и точно укажи, что должен сделать человек.

Условие завершения: закончи текущий запуск после создания проверяемого отчёта, не повторяй попытки.
```

Здесь явно указаны время, проект, область чтения, команда, ветви успеха и сбоя, запрещённые действия и условие завершения. Расписание лишь запускает задачу повторно и не заменяет её описание.

## 5. Разрешения и проверка человеком

Задачи по расписанию выполняются автономно с настройками песочницы по умолчанию.

| Режим песочницы | Типичный результат |
|---|---|
| read-only | Попытки изменить файл, выйти в сеть или управлять локальным App завершаются ошибкой |
| workspace-write | Рабочую область можно изменять; запись за её пределами, выход в сеть и управление App по умолчанию запрещены |

Начинайте с самых узких разрешений, достаточных для задачи. Если нужен доступ к сети или более широкой области файлов, задайте явный список разрешённых ресурсов; не повышайте разрешения для всей задачи только ради устранения одного сбоя.

Сохраняйте проверку человеком для следующих действий:

- Отправка внешних сообщений или публикация материалов
- Изменение производственного состояния
- Слияние PR или push в основную ветку
- Массовое удаление, миграция или изменение разрешений
- Diff вышел за ожидаемые границы либо тесты не пройдены

## 6. Спроектируйте ветви «без изменений», сбоя и остановки

В устойчивой задаче должны быть определены три пути:

1. **Обнаружены изменения**: выведите доказательства, серьёзность и следующий шаг.
2. **Изменений нет**: кратко сообщите область проверки, не придумывая проблем.
3. **Завершить невозможно**: укажите недостающие материалы или разрешения, остановитесь и дождитесь человека.

Для опроса внутри чата также задайте условие завершения, например: «Остановись, если PR слит или закрыт, три раза подряд повторяется одна и та же ошибка либо требуется подтверждение человека».

## Scheduled task не заменяет событийный CI

Если задача должна выполняться сразу после `push`, создания PR, завершения выпуска или другого события репозитория, используйте GitHub Actions, CI, webhook или событийную точку входа Codex SDK. Не пытайтесь заменить точный запуск по событию «опросом каждую минуту».

## Контрольный список приёмки

- [ ] Промпт полностью и успешно выполнен в обычном чате
- [ ] Выбрана отдельная задача или задача внутри чата
- [ ] Материалы Web или локальный проект доступны во время запуска
- [ ] Песочницы по умолчанию достаточно, дополнительные разрешения обоснованы
- [ ] Описаны ветви с находками, без изменений и при сбое, а также условия остановки
- [ ] Первые три запуска выборочно проверены человеком
- [ ] Для часто создаваемых Worktree есть правила архивации и очистки
- [ ] Критические операции записи по-прежнему требуют подтверждения человека
