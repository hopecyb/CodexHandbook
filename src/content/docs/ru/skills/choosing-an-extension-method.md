Чем больше механизмов расширения, тем чаще сначала выбирают модный технический термин, а уже затем пытаются подогнать под него проблему. Надёжнее начать с вопроса: **что именно я хочу сохранить или запускать автоматически?**

Чаще всего путают следующие понятия:

- Промпт
- AGENTS.md
- Skill
- MCP
- Plugin
- Scheduled task

Во всех случаях речь идёт о «расширении Codex», однако иногда достаточно одного промпта, а более тяжёлый механизм нужен лишь в отдельных ситуациях.

## Схема выбора

![Схема выбора способа расширения Codex](/illustrations/map-extension-selection.webp)

Это не дерево взаимоисключающих решений. Зрелый рабочий процесс может одновременно использовать `AGENTS.md`, Skill и MCP. Схема помогает не возлагать на механизм несвойственную ему ответственность.

## Семь вопросов для выбора

### 1. Изменение касается только текущей задачи?

Начните с промпта. Чётко задайте цель, входные данные, границы, критерии приёмки и разрешения. Это самый дешёвый вариант, на котором проще всего увидеть реальные проблемы.

### 2. Правило нужно соблюдать при каждой работе с этим репозиторием?

Запишите его в `AGENTS.md`. Например, укажите команды тестирования, стиль кода, каталоги, которые нельзя изменять, и правила установки зависимостей. Не превращайте разовое требование в постоянное правило проекта.

### 3. У однотипных задач есть устойчивые шаги и результат?

Создайте Skill. В нём удобно хранить многократно используемые инструкции, а при необходимости — шаблоны, справочные материалы, ресурсы и вспомогательные скрипты. Если у процесса ещё нет фиксированных критериев успеха, продолжайте проверять его с помощью промптов.

### 4. Нужны данные или действия за пределами репозитория?

Рассмотрите MCP или Connector. Сначала перечислите действительно необходимые инструменты и данные; отдавайте предпочтение доступу только для чтения, минимальной области и аудируемой конфигурации. Если задачу решают локальные файлы или имеющиеся команды, дополнительное внешнее подключение не требуется.

### 5. Проверку нужно выполнять в определённой точке жизненного цикла?

Используйте Hook. Например, до вызова инструмента проверяйте опасные команды, после записи сканируйте патч, а в конце сеанса сохраняйте сводку. Hook запускается автоматически, поэтому обязательно протестируйте тайм-ауты, сбои и ложные срабатывания.

### 6. Нужно единообразно передать набор возможностей другим людям?

Рассмотрите Plugin. Это уровень объединения и распространения, в который могут входить Skills, коннекторы, MCP, Hooks и шаблоны Scheduled task. Установка Plugin не означает автоматического доверия к его подключениям, скриптам или Hook.

### 7. Задача уже стабильно выполняется вручную и должна повторяться по времени?

Только тогда создавайте Scheduled task. Сначала проверьте промпт, Skill, разрешения и формат результата в обычной задаче. После включения расписания проследите за первыми запусками и сохраните ручной шлюз перед публикацией или слиянием.

## Сопоставление сценариев

| Сценарий | Рекомендуемая комбинация |
|---|---|
| Единые правила тестирования и коммитов | AGENTS.md |
| Контрольный список перед каждым слиянием | Skill `pr-review` |
| Получение контекста задачи из Linear | MCP + промпт задачи |
| Еженедельный отчёт о зависимостях | Scheduled task → создать черновик Issue |
| Сканирование патча на секреты после записи файла | Hook или CI; в сценариях высокого риска — оба механизма |
| Единая установка процесса Review и инструментов GitHub для команды | Plugin (перед установкой проверить разрешения и Hooks) |
| Еженедельное создание отчёта о рисках зависимостей | Проверенный Skill + Scheduled task + проверка человеком |
| Параллельный Review безопасности, тестов и сопровождаемости | Несколько дочерних Agent в режиме чтения; основной Agent сводит результаты |

## Виды затрат

| Механизм | Стоимость создания | Стоимость сопровождения | Риск безопасности |
|---|---|---|---|
| Промпт | Низкая | Низкая | Низкий |
| AGENTS.md | Средняя | Средняя | Низкий |
| Skill | Средняя | Средняя | Низкий–средний |
| MCP | Высокая | Высокая | Средний–высокий |
| Hook | Средняя | Средняя–высокая | Средний–высокий |
| Plugin | Низкая (установка) / высокая (самостоятельная разработка) | Средняя–высокая | Средний–высокий |
| Scheduled task | Средняя | Высокая | Высокий |

## Антипаттерны

- **Разрастание Skills**: установлены десятки Skill с пересекающимися description, которые конкурируют при сопоставлении
- **MCP как универсальный молоток**: API подключается даже для задачи, которую можно решить через `git`
- **Запуск по расписанию без приёмки**: код меняется автоматически, но нет условий завершения, свидетельств запуска и проверки человеком
- **Повторное изобретение колеса**: собственный MCP создаётся, хотя уже существует официальный Connector
- **Неуместное правило**: разовое требование попадает в `AGENTS.md`, и старое ограничение сопровождает все последующие задачи
- **Перегруженный Hook**: долгий бизнес-процесс выполняется при каждом вызове инструмента, замедляя обычные задачи или ошибочно блокируя их

## Частые вопросы

### 1. Нужно ли сразу установить Plugin и подключить MCP?

Многие задачи решаются хорошо составленным промптом, контролем границ и грамотным `AGENTS.md`.

### 2. Сколько раз должна повториться задача, чтобы для неё стоило создать Skill?

Фиксированного числа нет. Повторение — лишь сигнал; важнее устойчивость шагов, ясность критериев успеха и достаточная цена ошибки, чтобы оправдать автоматическую проверку.

### 3. С чего обычно начинают при первом использовании?

В большинстве случаев достаточно одной из трёх категорий:

- Промпт
- `AGENTS.md`
- Skill

Обычно на старте не нужны ни MCP, ни автономная автоматизация.

Главное не «продвинутость» механизма, а соответствие ответственности, минимальность разрешений и проверяемость результата.

## Минимальное практическое задание

Рассмотрим Review текущего diff перед слиянием:

1. Дважды выполните задачу с помощью промпта и запишите пункты проверки, которые приходится повторять каждый раз.
2. Внесите постоянные команды репозитория в `AGENTS.md`, например `pnpm test`, и запретите изменять каталоги со сгенерированными файлами.
3. Оформите шаги Review, уровни серьёзности и формат вывода как Skill `pr-review`.
4. Добавляйте MCP/Connector только тогда, когда нужны комментарии в GitHub PR или состояние CI.
5. Добавляйте Hook или Scheduled task только тогда, когда проверка должна автоматически выполняться по определённому событию.
6. Если набор требуется нескольким командам, упакуйте возможности в Plugin.

При добавлении каждого уровня снова ответьте на три вопроса: какие разрешения появились, как проверить результат и как отключить или откатить механизм.
