第一次看 Skill 目录时，常见的感觉是“文件夹我都认识，但不知道为什么要这样放”。

这页说明怎么把“主流程、长说明、模板、脚本”分开放，避免全塞进一个文件。

这样更方便阅读、修改和复用，也不容易越写越乱。

# Skill 结构

## 目录结构

```text
my-skill/
├── SKILL.md          # 必需
├── scripts/          # 可选：确定性步骤
├── references/       # 可选：长参考文档
└── templates/        # 可选：输出模板
```

## 每一层分别做什么

- `SKILL.md`：主说明书，先告诉 Codex“这是什么、什么时候用、按什么步骤做”
- `references/`：长资料柜，不把所有背景知识硬塞进主文件
- `templates/`：现成输出骨架，避免每次临场发挥
- `scripts/`：能确定执行的步骤交给脚本，别全靠自然语言描述

最开始甚至只需要一个 `SKILL.md`。  
后面真的变复杂了，再拆 `references/`、`templates/`、`scripts/`。

## 按需加载，而不是一次全塞进去

一个可维护的 Skill 通常分三层：

| 层级 | 放什么 | 什么时候用 |
|---|---|---|
| 元信息 | 名称、描述、触发场景 | 让 Codex 判断是否该用 |
| 主说明 | 必做步骤、禁止事项、完成定义 | Skill 被触发后先读 |
| 附件 | 模板、参考资料、脚本、示例 | 只有任务真的需要时再打开或运行 |

这样做的好处是：平时只暴露很短的触发说明，真正执行时再加载细节。Skill 越多，这种分层越重要。

## SKILL.md 最小示例

```md
---
name: pr-review
description: 审查当前分支相对 main 的 diff，标出风险与测试缺口。在用户要求 review、审查 PR 或合并前检查时使用。
---

## 步骤
1. 获取相对 main 的 diff
2. 按文件分类：逻辑错误、安全、性能、测试
3. 输出分级清单：阻断 / 建议 / nit
4. 不要自动 push 或合并
```

## 常见误区

### 1. 一开始就要把所有目录都建全

很多好 Skill 一开始只有一个 `SKILL.md`，是后来随着复用次数增加，才慢慢拆出别的目录。

### 2. `references/` 就是为了多放一点内容

重点不在“多放”，而在于把不该总占主流程注意力的长说明放到需要时再读。

### 3. `scripts/` 能不用就别用

如果某一步本来就该稳定、确定、可重复，写成脚本往往比一直用自然语言描述更可靠。

## 各目录职责

| 目录 | 用途 |
|---|---|
| `SKILL.md` | 主流程、触发条件、禁止项 |
| `references/` | 长文档、规范、API 说明 |
| `templates/` | 输出格式、报告骨架 |
| `scripts/` | 确定性命令与检查 |

## 何时拆分目录

可以按下面的顺序判断要不要拆目录：

1. 主流程是不是已经太长，第一次读不下去
2. 是否有一大段资料不是每次都要看
3. 是否有固定输出格式总在重复
4. 是否有某个步骤已经稳定到适合脚本化

如果这四个问题里有一两个答“是”，就可以开始拆。

## 从模板长成 Skill

很多团队一开始不是“设计 Skill”，而是先有一段反复复制的提示词。可以按这个顺序演进：

| 阶段 | 形态 | 何时升级 |
|---|---|---|
| 一次性提示 | 写在当前对话里 | 只用一次，不需要复用 |
| 模板 | 放进提示词模板或团队文档 | 同类任务反复出现，但步骤还在调整 |
| 单文件 Skill | 一个 `SKILL.md` | 流程稳定，触发条件清楚 |
| 完整 Skill 目录 | `SKILL.md` + `templates/` + `references/` + `scripts/` | 输出格式、长参考、确定性检查都稳定下来 |

不要急着把每个模板都变成 Skill。真正值得沉淀的，是那些已经反复出现、成功标准清楚、团队愿意按同一套流程执行的任务。

## 可复用 Skill 常见组件

| 组件 | 适合放什么 |
|---|---|
| 主说明 | 触发条件、执行步骤、禁止事项、完成定义 |
| 模板 | PR 审查输出、文档结构、风险报告格式 |
| 参考资料 | 代码规范、术语表、领域规则、API 说明 |
| 脚本 | 复杂度分析、链接检查、测试覆盖统计、格式校验 |

一个好 Skill 不只是“更长的 prompt”，而是把可复用流程拆成可读、可测、可维护的几个部分。

可以先用 `SKILL.md` 跑通，再在真的变复杂时，把资料、模板和脚本逐步拆出去。
