刚开始做 Skill 时，常见做法是把所有东西都写进 `SKILL.md`。简单流程可以这么做，但只要某一步需要**稳定、重复、可验证**地执行，脚本比纯文字说明更可靠。

固定动作适合交给脚本，判断和协作流程留给 Skill。

# scripts/ 与测试

当某步骤必须确定性执行（跑测试、生成 diff、校验格式）时，在 `scripts/` 中提供脚本，并在 `SKILL.md` 中说明何时调用。

## 示例

```text
my-skill/
├── SKILL.md
└── scripts/
    └── run-checks.sh
```

## 什么情况下该考虑 `scripts/`

如果某一步满足下面任意一种，就适合优先考虑脚本：

- 每次都应该完全一样地执行
- 退出码本身就有意义
- 用自然语言描述会很啰嗦
- 你希望它以后还能被 CI 或别的工具复用

像“跑检查”“生成 diff”“验证格式”“固定导出报告”这类动作，都适合放进脚本。

## 测试建议

- 在练习仓库中手动运行脚本，确认退出码与输出
- 用 Skill 触发端到端流程，检查是否按预期调用脚本
- 团队场景：在 CI 或 pre-commit 中验证脚本仍可用

## 常见误解

### 1. 写了脚本，Skill 就会变复杂，所以别用

如果脚本把原本很不稳定的一步固定住了，整体反而会更简单。

### 2. 只要脚本本地能跑，Skill 就一定没问题

还要看：

- Skill 有没有正确触发它
- 审批策略会不会拦它
- 在团队环境或 CI 里是否还能正常跑

### 3. “测试 Skill” 就是测脚本

不够。

脚本测试的是一个动作；  
Skill 还要测试“什么时候调用、怎么调用、输出是否符合预期”。

## 常见验证顺序

刚开始做时，可以按这个顺序：

1. 先单独跑脚本
2. 看退出码和输出是否清楚
3. 再让 Skill 调一次完整流程
4. 再在更贴近真实环境的地方测一遍

这样更容易把“脚本本身坏了”和“Skill 集成方式不对”分开排查。

能稳定重复执行的动作，不要只靠文字描述。先把脚本跑通，再确认 Skill 调用没问题。

脚本继承当前审批策略；见 [命令规则](/guide/customization/rules/command-rules/) 与 [Skill 安全](/skills/security/)。
