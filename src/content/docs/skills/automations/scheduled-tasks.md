定时任务真正困难的部分不是“几点运行”，而是让每次无人值守运行都有稳定输入、窄权限、可审查输出和停止条件。

![从手动验证到定时运行、人工复核和调整的安全闭环](/diagrams/scheduled-task-safety-loop-zh-cn.svg)

## 适合谁

- 想按日或按周生成报告、检查文档、跟进 PR 的个人用户
- 需要在本地项目或隔离 worktree 中定期运行维护任务的开发者
- 负责评估权限、失败处理和团队共享 Skill 的维护者

## 支持边界

| 表面 | 能做什么 | 关键限制 |
|---|---|---|
| ChatGPT Web | 创建、管理、查看运行；使用上传文件、连接工具、Skills、Plugins | 不能直接访问本机文件夹 |
| ChatGPT 桌面 App | 创建、管理；可选本地项目或 Git worktree | 本地文件任务需要机器开机、App 运行、项目存在 |
| Codex CLI | 准备和手动测试提示词、Skill、脚本 | 没有 Scheduled 管理界面 |
| IDE 扩展 | 在工作区验证命令和修改 | 没有 Scheduled 管理界面 |

## 1. 选择独立任务还是聊天内任务

### 独立 Scheduled task

每次运行从保存的提示词开始，并作为单独运行进入 Scheduled。适合互相独立的日报、周报、项目健康检查；一个任务也可以覆盖多个项目。

### 聊天内 Scheduled task

按计划回到同一聊天，沿用现有上下文。适合轮询长任务、跟进 PR 状态、持续研究或需要保留前次讨论的工作。

选择标准：每次运行应该“重新开始”就选独立任务；需要延续同一问题的上下文就选聊天内任务。

## 2. 选择运行材料

### Web 上运行

把耐久指令写进任务提示词或 Skill，把需要的资料放在上传文件、Project 或连接服务中。不要写“读取我桌面上的 latest.csv”，Web 无法直接访问本地路径。

### 桌面 App 使用本地项目

Git 仓库可以选择：

- **本地项目**：直接在主 checkout 工作，可能碰到你正在编辑的文件。
- **专用 worktree**：把后台修改与未完成工作隔离，适合会改文件的任务。

非 Git 项目直接在项目目录运行。高频 worktree 任务会积累工作树；归档不再需要的运行，避免无意保留大量 worktree。

## 3. 先手动验证

在普通聊天中先运行完全相同的提示词、模型、推理强度和工具。至少确认：

- 输入在没有临场解释时仍然清楚
- “无变化”时会安静结束
- 输出可被人快速审查
- 命令、Skill 和连接工具都能工作
- 缺少权限或材料时会停止并说明，而不是猜测

查看前几次定时运行，再调整提示词或频率。

## 4. 一份可直接改写的任务提示词

```text
请创建一个独立 Scheduled task：

名称：每周文档死链检查
时间：每周一 09:00，使用当前时区
运行位置：当前 Git 项目的专用 worktree

每次运行都执行：
1. 只读取 docs/、src/content/docs/、examples/ 和 public/diagrams/。
2. 运行 pnpm check:links。
3. 如果检查通过，只报告检查文件数和链接数，不修改文件。
4. 如果检查失败，按“来源文件、失效目标、建议修复”列出结果；不要自动改链接。
5. 不联网，不安装依赖，不提交、不 push、不创建 PR。
6. 命令不存在、依赖缺失或结果不确定时停止，并说明需要人工处理的具体事项。

完成条件：输出一份可审查报告后结束本次运行，不重复尝试。
```

这里把时间、项目、读取范围、命令、成功/失败分支、禁止动作和退出条件全部写明。调度只负责再次触发，不能替代任务说明。

## 5. 权限和人工复核

定时任务无人值守运行，并使用默认沙箱设置。

| 沙箱模式 | 常见结果 |
|---|---|
| read-only | 修改文件、联网或控制本机 App 的调用失败 |
| workspace-write | 可写工作区；工作区外写入、联网或控制 App 默认失败 |

从能完成任务的最窄权限开始。需要网络或更宽文件访问时，明确 allowlist；不要为了消除一次失败就把整个任务改成高权限。

人工复核建议保留在：

- 对外发送消息或发布内容
- 修改生产状态
- 合并 PR 或 push 主分支
- 批量删除、迁移、改权限
- diff 超出预期范围或测试失败

## 6. 设计“无变化”、失败和停止

耐久任务必须定义三条路径：

1. **有发现**：输出证据、严重性和下一步。
2. **无变化**：简短报告检查范围，不制造伪问题。
3. **无法完成**：说明缺少的材料/权限，停止并等待人。

聊天内轮询还要写终止条件，例如“PR 合并、关闭、连续 3 次相同错误或需要人工审批时停止”。

## Scheduled task 不是事件驱动 CI

如果任务必须在 `push`、PR 创建、发布完成等仓库事件发生后立即运行，应使用 GitHub Actions、CI、webhook 或 Codex SDK 等事件入口。不要把“每分钟轮询”当成精确事件触发器。

## 验收清单

- [ ] 提示词已在普通聊天完整跑通
- [ ] 已选择独立任务或聊天内任务
- [ ] Web 材料或本地项目在运行时可用
- [ ] 默认沙箱足够，额外权限有明确理由
- [ ] 写明有发现、无变化、失败和停止条件
- [ ] 首三次运行已人工抽查
- [ ] 高频 worktree 有归档与清理策略
- [ ] 关键写操作仍保留人工确认
