刚接触 Skill 时，常见误解是“装好了以后，它会自己生效”。使用 Skill，就是让 Codex 按某个预先写好的工作套路来做事。

Skill 既可以由你**明确点名**调用，也可能在合适场景下被模型**自动选用**。分清这两种触发方式，能少走一些排查弯路。

# 使用 Skill

## 触发方式

1. **显式**：在支持的环境中用 `$skill-name` 调用（名称与 frontmatter `name` 一致）
2. **隐式**：模型根据 `description` 语义判断当前任务是否适用

## 怎么区分两种触发方式

- **显式触发**：你直接说“就用这个 Skill”
- **隐式触发**：你没点名，但你的任务描述刚好很像它的适用场景

刚开始试 Skill 时，建议优先用**显式触发**。这样更容易判断：

- Skill 有没有被识别到
- 它的行为是不是你预期的
- 名称和说明有没有写对

## 示例

```text
$pr-review 请审查我当前未提交的改动
```

或自然语言：「按团队习惯审查一下 diff，重点看测试。」

## 常见误解

### 1. 我写了 Skill，它就一定会自动触发

自动触发依赖 `description` 写得是否清楚，也依赖当前任务是不是足够像它的适用场景。

### 2. 自然语言触发和 `$name` 触发效果一定一样

两者不一定完全一样。

`$name` 更明确，适合验证和强制使用。自然语言更方便，但有时模型会选错 Skill，或者根本不用。

### 3. Skill 没触发，就一定是它有问题

也可能只是：

- 名称不对
- `description` 太泛
- 任务描述没有打中它的触发词

所以排查时不要只盯着“文件在不在”，也要看“它写得像不像一个会被选中的工具”。

## 常见测试顺序

如果想先跑通一次，可以这样试：

1. 先用 `$skill-name` 显式调用
2. 看它输出是否符合预期
3. 再改 `description`
4. 最后再测试自然语言是否能触发

这样能把“Skill 本身有问题”和“自动触发条件没写好”分开看。

## 写好 description

- 写清「何时用」和「何时不用」
- 包含用户可能说的关键词（review、发版、changelog）
- 避免空泛的「帮助用户写代码」
- 把核心触发场景写在**最前面**（Skill 列表有字符预算）

## 判断 description 是否清楚

一个常用的标准是：  
读完这句 `description`，就能知道“什么时候该用它，什么时候别用它”。

如果一句 description 读完后还是觉得“好像什么都能做”，那多半就太泛了。
