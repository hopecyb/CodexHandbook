刚接触 Skill 时，常见问题是：这件事到底值不值得专门做成一个 Skill。

如果什么都做成 Skill，会越来越重；如果该沉淀的不沉淀，又会一直重复手工说同样的话。这里主要帮你判断什么时候该把流程固化下来。

# 何时使用 Skills

## 适合封装为 Skill

- 同一流程第三次被手动重复
- 需要详细检查清单，但不想每次占满上下文
- 希望模型根据 `description` 自动判断何时启用
- 团队需要共享、版本化的工作流

## 适合做成 Skill 的条件

如果一个任务同时满足下面两条，就很值得考虑做成 Skill：

- 你未来还会再做
- 你希望下次做法尽量一致

很多 Skill 最后会落在这些场景里：

- 审查 diff
- 生成 changelog
- 发布前检查
- 文档发布流程

这些任务不复杂，但很适合复用。

## 不太适合

- 一次性、从未重复的任务
- 极短、你记得住的固定命令（考虑斜杠命令）
- 需要实时外部系统状态且变化极快（考虑 MCP）

## 常见误区

### 1. 只要任务重要，就应该做成 Skill

重要，不等于适合复用。  
如果它是一次性的特殊任务，做成 Skill 可能只会增加维护负担。

### 2. Skill 越多越好

太多边界模糊的 Skill，反而会让模型误用、让团队更难维护。

### 3. 只要能连外部系统，就应该先做 Skill

很多时候外部系统接入更偏 MCP 的问题，Skill 负责的是“流程”，外部系统怎么连通还是要靠 MCP。

## 可以怎么试

如果还不确定一套流程值不值得沉淀，可以先这样试几次：

1. 手动完成两到三次
2. 观察自己每次是不是都在重复同一套检查顺序
3. 如果答案是“对”，再把它收成 Skill

这样做出来的 Skill 会更扎实，因为它来自真实重复，而不是凭空设计。

## 与其他扩展方式对比

| 方式 | 适合 |
|---|---|
| Skill | 可复用流程、渐进式披露 |
| MCP | 连接外部 API 与数据源 |
| Hooks | 在特定事件点自动执行 |
| `AGENTS.md` | 项目级常驻约定 |

Skill 更适合沉淀“会重复、要一致、又不想每次重新讲一遍”的流程。
