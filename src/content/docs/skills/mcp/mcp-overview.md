MCP 把“模型想使用一个外部能力”变成结构化工具调用。它适合接入第三方文档、浏览器、Figma、工单系统或内部服务。

## 一条调用链

```text
任务中的 Codex
  -> MCP 客户端（由 Codex host 提供）
  -> MCP 服务器（本地进程或远程服务）
  -> 外部系统（文档、设计、工单、内部 API）
  -> 结构化结果返回任务
```

| 组件 | 负责什么 | 不负责什么 |
|---|---|---|
| Codex host | 读取配置、连接服务器、把工具提供给 Agent | 不替服务器定义业务权限 |
| MCP 服务器 | 定义工具、鉴权、参数和结构化结果 | 不自动保证工具安全 |
| Skill | 规定何时、按什么步骤使用工具 | 不建立网络连接 |
| Plugin | 组合并分发 Skills、连接器、MCP 等能力 | 不是另一种工具协议 |

## 当前支持的服务器方式

### STDIO

Codex 启动一个本地进程，通过标准输入输出通信。适合本地开发工具和只在当前机器运行的服务。

风险重点：这个进程继承本机执行环境；命令、依赖来源和转发的环境变量都需要审查。

### Streamable HTTP

Codex 连接一个远程地址。当前官方文档确认支持 Bearer token、OAuth，以及受信任第一方服务器的 ChatGPT 会话鉴权。

风险重点：远端服务会收到工具参数；必须确认 TLS、身份、日志、数据保留和工具权限。

## MCP、Skill、Plugin 怎么组合

以“每周检查高优先级工单”为例：

| 层 | 内容 |
|---|---|
| MCP | 提供 `search_issues`、`get_issue` 等工具 |
| Skill | 规定筛选条件、证据要求与报告格式 |
| Plugin | 把 Skill、连接器和 MCP 定义交给团队安装 |
| Scheduled task | 在固定时间运行已经验证过的任务 |

它们是正交职责，不是从低到高的升级阶梯。完整关系见[扩展能力地图](/skills/capability-map/)。

## 什么时候值得接 MCP

| 值得 | 暂时不值得 |
|---|---|
| 反复查询同一外部系统 | 一次性公开网页查询 |
| 需要结构化工具参数与结果 | 仓库内文件操作已足够 |
| 需要 OAuth 或细粒度工具控制 | 只有高权限写接口、没有测试环境 |
| 团队需要统一复用连接 | 服务器来源无法审查 |

## 安全分级

1. **只读试用**：公开文档或测试租户，只启用查询工具。
2. **团队验证**：限定项目、角色与工具 allowlist，记录失败和耗时。
3. **有限写入**：可回滚的小范围写操作，保留人工审批。
4. **治理运行**：授权可回收、配置可审查、日志脱敏、按环境隔离。

不要把 token 写入提示词、Git 或静态 HTTP header。优先使用 OAuth、`bearer_token_env_var` 或环境变量转发。

## 接入前检查表

- [ ] 服务器来源、版本与启动命令可审查
- [ ] 工具清单已区分读操作和写操作
- [ ] 使用测试租户或最小权限账号
- [ ] 明确哪些参数与结果会进入远端日志
- [ ] 写操作有审批、回滚和审计路径
- [ ] 团队知道怎样禁用服务器和回收授权
