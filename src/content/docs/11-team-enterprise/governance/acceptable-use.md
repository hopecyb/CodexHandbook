**可接受使用政策（AUP）**把「能不能用 Codex 做这件事」写成组织共识，避免仅靠个人判断。它与 [威胁模型](/11-team-enterprise/security/threat-model/) 互补：威胁模型讲风险，AUP 讲**行为边界**。

## 这篇解决什么问题

- AUP 应覆盖的议题
- 与 HR/合规、技术控制的衔接
- starter 条款示例（需法务本地化）

:::caution
以下为**教育性提纲**，不构成法律意见。正式发布前须经法务与合规评审。
:::

## 建议覆盖的议题

| 议题 | 要点 |
|---|---|
| 允许用途 | 开发、文档、研究、内部自动化 |
| 禁止用途 | 未授权访问、骚扰内容、规避安全控制 |
| 数据分级 | 哪些 repo/数据可用；客户 PII 规则 |
| 输出责任 | 人审后合并；不将输出当法律/医疗建议对外 |
| 扩展 | 仅批准清单内 Plugin/MCP |
| 账号 | 禁止共享个人席位；离职回收 |
|  incident | 报告可疑行为的路径 |

## 最小 starter 结构

1. **目的与范围**
2. **允许的使用场景**（链到 [能力地图](/00-start-here/codex-capability-map/)）
3. **禁止的使用场景**
4. **数据与保密**
5. **人类监督要求**（合并、生产变更）
6. **违规后果**（引用现有员工手册）
7. **联系人与更新日期**

## 与技术控制对齐

| AUP 条款 | 技术落实 |
|---|---|
| 不得 exfiltrate 源码 | 网络策略、MCP 批准 |
| 生产变更需审批 | 分支保护、deny `git push` |
| 仅用批准模型 | 组织托管配置 |

## 常见错误

- AUP 写完无人培训
- 与技术 reality 脱节（政策禁止但工具允许）
- 多年不更新，与新功能（Computer Use 等）脱节

## 验收清单

- [ ] 员工 onboarding 包含 AUP 确认
- [ ] 与 [团队规则](/06-customization/rules/team-rules/) 无矛盾
- [ ] 每年或重大功能发布时复审
