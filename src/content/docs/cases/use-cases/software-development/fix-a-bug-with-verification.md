## 1. 目标与背景

**业务背景：** 购物车 `calculateTotal` 接收折扣百分比。无折扣时结果正确，但传入 `10` 表示九折时，函数把 `10` 当成比例直接相乘，产生负数。

**目标：** 找到折扣计算错误，做最小修复，并用同一组测试证明问题从红灯变为绿灯。

**成功标准：**

- 起始测试稳定出现 1 个失败，断言显示“期望 36，实际 -360”
- 修复后 3 个测试全部通过
- 修复只改变折扣百分比换算，不重写购物车 API
- 能解释为什么“修复后绿灯”必须和“修复前红灯”一起保存

**不在范围：** 金额精度库、税费、货币换算、依赖升级和 UI。

![带验证的 Bug 修复工作流](/diagrams/verified-bug-fix-workflow-zh-cn.svg)

图中最关键的是两条返回路径：相关测试失败时回到最小修复；全量回归或 diff 审查失败时回到根因分析。不要为了尽快变绿而删除断言或扩大改动。

`starter/` 是练习起点，包含一个故意保留的 Bug；`solution/` 是独立可运行的参考答案。不要直接在参考答案上练习。

## 3. 第一步：复现红灯

在仓库根目录运行：

```bash
node --test examples/complete-workflows/developer/verified-bug-fix/starter/cart.test.js
```

预期：命令以非零状态退出，3 个测试中 1 个失败。关键证据类似：

```text
Expected values to be strictly equal:

-360 !== 36
```

如果测试没有失败，先停下。检查是否运行了 `starter/`、Node.js 版本和文件是否被提前修改。没有稳定红灯，就没有原问题的基线证据。

## 4. 第二步：只读探索

### 探索

```text
先不要修改文件。阅读：
- examples/complete-workflows/developer/verified-bug-fix/starter/cart.js
- examples/complete-workflows/developer/verified-bug-fix/starter/cart.test.js

请用不超过 6 条说明：
1. 哪个输入触发失败；
2. 期望值与实际值；
3. 百分比和比例在公式中的差异；
4. 最小修复应落在哪一行；
5. 哪些公开行为不能改变；
6. 修复后要运行哪些验证。
```

合格的根因解释应指出：调用方传入 `10` 表示 10%，实现却直接计算 `subtotal * 10`，缺少除以 `100` 的换算。

## 5. 第三步：计划并执行最小修复

```text
只修改 starter/cart.js 中折扣百分比换算。
不要更改函数名、参数、测试断言或文件结构，不要增加依赖。

修复后依次：
1. 运行 starter/cart.test.js；
2. 展示实际测试摘要；
3. 总结修改行及其原因；
4. 不要提交或推送 Git。
```

最小修复的核心是：

```js
const discount = subtotal * (discountPercent / 100);
```

不要通过把测试中的 `36` 改成 `-360` 获得绿灯，那只是在改写期望，并没有修复业务规则。

## 6. 第四步：验证绿灯

如果你不想修改练习起点，也可以直接运行参考答案：

```bash
node --test examples/complete-workflows/developer/verified-bug-fix/solution/cart.test.js
```

预期：3 个测试全部通过，进程退出状态为 0。

验证记录至少包含：

| 证据 | 要回答的问题 |
|---|---|
| 修复前失败命令 | 原问题能稳定复现吗？ |
| 失败断言 | 测试真的覆盖这个 Bug 吗？ |
| 代码 diff | 改动是否只触及根因？ |
| 修复后相关测试 | 同一个行为现在正确吗？ |
| 更大范围测试 | 是否破坏相邻功能？ |

这个练习目录只有一组测试；在真实项目中，还要按 `AGENTS.md` 运行 lint、类型检查和全量测试。

## 7. 第五步：Review

```text
审查这次修复，不要改文件。先列 findings，再给结论：
- 是否真的修复百分比换算，而不是放宽测试；
- 是否改变了函数签名或无关逻辑；
- 空购物车、无折扣和 10% 折扣是否都有覆盖；
- 还剩哪些金额精度风险不在本案例范围。
```

人工还要确认：没有额外依赖、调试日志、格式化整文件或 Git 操作。

## 8. 失败与恢复

| 问题 | 处理 |
|---|---|
| 起始测试不失败 | 确认运行的是 `starter/cart.test.js`，恢复未修改起点 |
| 修改测试后变绿 | 恢复测试断言，只修改实现中的百分比换算 |
| 相关测试仍失败 | 对比失败值，检查是否把 `/ 100` 放错位置 |
| 全量测试出现新失败 | 回到根因分析，检查公开行为和改动范围 |
| 测试偶发失败 | 先稳定测试环境，不能把一次绿灯当证据 |

## 9. 从练习迁移到真实仓库

把示例路径替换成你的文件，但保留证据结构：

```text
目标：修复【可观察的错误行为】。
复现命令：【精确命令】；当前稳定失败为【关键断言】。
范围：只修改【实现文件】和必要测试；不做重构或依赖升级。
验收：原失败测试通过；新增边界测试通过；【全量命令】通过；diff 无无关改动。
权限：不得 push、发布或修改生产数据；需要额外权限时先停下说明。
先只读定位根因和风险，等我确认计划后再改。
```

## 10. 沉淀

- 若此类 bug 重复出现，在 `AGENTS.md` 加一条约定
- 可提取 `regression-guard` Skill：强制记录红灯、绿灯和回归证据
- 将高频边界测试加入 CI，而不是只保留在对话里
