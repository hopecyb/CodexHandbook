**失败恢复**讲的是任务跑偏或中断后，怎么把现场收住，再继续往前走。本章给出一套可重复的 **检测 → 止损 → 恢复 → 复盘** 步骤，可和 [撤销与恢复](/guide/getting-started/undo-and-recover/) 以及 [长任务管理](/cases/workflows/long-running-task-management/) 配合使用。

## 这页重点

- 何时该 `git stash`、回退 commit、开新线程
- 如何把失败信息整理进下一轮 prompt
- 团队如何记录复发问题

## 失败信号

| 信号 | 可能动作 |
|---|---|
| 测试大面积失败 | 停止执行，缩小 diff |
| 改错目录/分支 | 撤销，重新 `@` 正确路径 |
| 计划与实现严重偏离 | 回到探索或计划阶段 |
| 上下文过长、遗忘约束 | 新线程 + 摘要交接 |
| 审批/规则反复拒绝 | 检查规则与任务是否矛盾 |

## 最小可用恢复流程

```text
1. 停止继续改（明确说「先不要写代码」）
2. 保存现状：git status / stash / 记录 thread ID
3. 用 5 条以内总结：目标、已做、失败现象、假设
4. 选择：回退 / 缩小范围 / 新线程继续
5. 成功后写入 AGENTS.md 或案例复盘
```

提示词示例：

```text
当前改动让 12 个测试失败。先不要继续修。
列出最近 3 个 commit 影响的文件，建议最小回退点，
并给出一个更小的修复计划。
```

## 推荐工作流

```text
检测（测试/人工/CI）
    → 止损（停写、隔离分支）
    → 诊断（见「先诊断再修复」）
    → 小步重试
    → 复盘沉淀
```

多 Agent 场景见 [多 Agent 协作](/cases/workflows/multi-agent-coordination/)：失败时要明确哪个子任务负责回滚。

## 常见错误

- 在错误方向上「再加一点」堆补丁
- 不保存失败日志，新线程重复同样错误
- 强制 `git push` 挽回局面
- 未区分环境（本地 vs Cloud）导致恢复步骤无效

## 安全边界

- 恢复操作本身受 [命令规则](/guide/customization/rules/command-rules/) 约束
- 生产事故先回滚再根因分析，不让 Agent 直接连生产修数据

## 验收清单

- [ ] 能说明本次选择的恢复策略及原因
- [ ] 仓库回到可构建/可测试状态
- [ ] 失败原因与教训已记录（issue 或 AGENTS.md）
- [ ] 若需新线程，有关键约束摘要
