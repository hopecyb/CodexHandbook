**规格驱动**就是在大量改文件之前，先准备一份短规格，写清目标、范围、接口和验收标准。它可以接在 [头脑风暴](/cases/workflows/brainstorm-before-building/) 之后，也可以直接配合已经澄清过的需求进入 [EPXV](/cases/workflows/explore-plan-execute-verify/)。

## 这页重点

- 规格要写多细才够
- 如何让 Codex 按规格执行而不擅自扩 scope
- 规格与 PR 描述、issue 的关系

## 最小可用规格模板

```markdown
## 目标
一句话用户价值

## 范围
- 包含：…
- 不包含：…

## 接口/行为
- 输入 / 输出 / 错误情况

## 验收标准
- [ ] 可自动验证的项
- [ ] 需人工检查的项

## 约束
- 不可改动的模块、性能、兼容性
```

可把模板放进仓库 `docs/specs/` 或 issue 正文，任务中 `@` 引用。

## 推荐工作流

```text
① 起草规格（Codex 可协助，人审）
② 确认规格 → 回复「按规格执行」
③ 分步执行，每步对照验收项
④ 规格变更必须显式改版号或 changelog
```

提示词示例：

```text
阅读 @docs/specs/export-csv.md。先对照规格列出实现计划与风险；
规格未列出的功能不要加。等我确认后再写代码。
```

## 与测试驱动配合

规格中的验收项应尽量**可测试**；能写成测试的先写测试，见 [测试驱动工作](/cases/workflows/test-driven-work/)。

## 常见错误

- 规格过长如设计文档，关键约束反而找不到
- 执行中范围悄悄变大，却没更新规格
- 验收标准模糊（「更好用」）导致争论
- 规格与 `AGENTS.md` 架构约定冲突

## 安全边界

- 规格里写明的「允许调用外部 API」才授权网络相关实现
- 涉及 PII 的字段处理必须在规格中标注

## 验收清单

- [ ] 范围外事项已明确排除
- [ ] 至少 3 条可检查的验收标准
- [ ] 执行前有人工或书面确认
- [ ] 变更已同步回规格文件
