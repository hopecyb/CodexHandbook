description: 生产问题与顽固 bug——先建立证据链，再动刀。
---


直接让 Codex 上来就修 bug，返工率通常很高。诊断工作流更强调：**症状 → 假设 → 证据 → 最小修复**。

## 何时用

- 测试失败原因不明
- 生产告警、用户报告「偶发」
- 上次修复后问题仍在

## 步骤

### 1. 冻结改动

```text
先不要改业务代码。列出：复现步骤、相关日志、最近相关 commit。
```

### 2. 缩小范围

- 二分：哪次提交引入？
- 隔离：最小复现仓库或测试用例

### 3. 形成假设

要求 Codex 输出：

```text
假设 A：… 验证方式：…
假设 B：… 验证方式：…
```

### 4. 验证假设（只读优先）

跑针对性测试、加临时日志（可丢弃分支）、读监控。

### 5. 最小修复

一次只修一个根因；避免「顺手重构」。

### 6. 回归验证

原失败用例 + 相邻场景 + 防止复发的测试。

## 提示词模板

```text
按「先诊断再修复」：
1. 阅读 @path/to/failing-test 与实现，解释失败原因（引用堆栈行号）
2. 给出 2 个假设及如何用只读方式验证
3. 我确认假设后再写修复，修复后只跑相关测试
```

## 与 EPXV 的关系

诊断可以看作 **探索** 阶段的加深版；到了计划阶段，还要写清楚“如果假设错了怎么回退”。

## 常见错误

- 未复现就改代码
- 一次 patch 同时修三个问题，无法 review
- 删掉临时日志却不补永久测试
