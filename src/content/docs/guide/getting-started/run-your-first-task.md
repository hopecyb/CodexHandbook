以下示例默认 **桌面 App**；CLI/IDE 同样可用同一段提示词。

很多人第一次用 Codex，就想直接让它“做个完整网站”或者“重构整个项目”。这样很容易一下子失控。

第一次任务做小一点会更稳妥。把整套流程走通，比一开始就做大更重要。

## 为什么第一次任务要选这么小

第一次任务最好满足这三个条件：

- 改动范围小
- 结果一眼能检查
- 就算做错也容易撤回

所以这里用的是一个很小的练习例子。

## 示例任务

在练习项目中对 Codex 说：

```text
目标：在 hello.md 末尾追加一节「今日练习」，包含三行要点列表。
约束：只修改 hello.md；不要删除已有内容；不要运行网络请求。
验收：文件末尾出现该标题与恰好三个列表项。
若信息不足请先问我，不要猜测。
```

## 提示词各部分的作用

这段提示词把几件关键的事分开写清楚了：

- **目标**：告诉它要做什么
- **约束**：告诉它不能乱改哪里
- **验收**：告诉它“怎样才算做完”
- **若信息不足请先问我**：防止它自作主张猜测

这不是固定模板，只是把最容易说不清的部分写明白。

## 常见误会

### 1. 第一次任务越大，越能学到真本事

第一次更重要的是把完整闭环走一遍，而不是一口气把事情做大。

### 2. prompt 写出来了，后面就交给它自己发挥

第一次任务里，重点是看住三件事：

- 范围有没有超
- 它是不是在按你说的文件动手
- 最后结果是不是符合验收

### 3. 第一次如果做错，说明我不会用

第一次任务本来就包括这些内容：

- 发现哪里不对
- 能指出问题
- 知道怎么让它收回来

## 执行时注意

1. 让它给出简短计划（或你主动要求计划）
2. 审批文件写入时确认路径正确
3. 完成后进入 [检查结果](/guide/getting-started/review-the-result/)

## 执行顺序

可以按这 5 步来：

1. 选一个安全练习项目
2. 给一个只改一个文件的小任务
3. 批准前看清它要动哪里
4. 做完后检查范围和结果
5. 不满意就撤销或继续精确纠偏

这 5 步走完后，你对整个协作节奏就会更熟一点。

## 做完以后你应该检查什么

重点看这三件事：

1. 它是不是只改了 `hello.md`
2. 文件末尾是不是真的多出那一节
3. 列表项数量是不是正好三个

这三项都对，这次小任务基本就算跑顺了。

## 如果它做错了

第一次做错很正常。你可以直接这样继续：

```text
你改多了。请撤回对其他文件的改动，只保留 hello.md 的修改。
```

或者：

```text
先不要继续改。告诉我你刚才改了哪些地方。
```
