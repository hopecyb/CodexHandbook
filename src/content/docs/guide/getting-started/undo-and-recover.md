第一次用 Codex 时，很多人最担心的是：它改错了，我还能不能回去？

多数情况下可以，但最好按安全的方法回退。

当结果越界或质量不行：

1. 使用客户端提供的撤销 / 还原变更能力（以当前 UI 为准）
2. 若项目在 Git 下：用你熟悉的方式丢弃工作区改动（初学者可先不用 Git，依赖练习目录）
3. 新开线程，收紧约束后重试

很多时候，提前把范围收小会省事一些，比如只动少量文件、写清禁止项、先看计划再执行。

## 区分“撤销”和“恢复”

- **撤销**：把刚才那次不满意的改动退回去
- **恢复**：把项目带回一个你确认安全的状态

练习一个小文件的话，撤销一般不难。更麻烦的情况是：

- 它改了不止一个文件
- 你自己后来又手动改了一些内容
- 你已经记不清哪部分是谁改的

先暂停继续修改，把影响范围缩小。

## 第一次做错时的处理顺序

1. 先暂停继续修改，不要一边慌一边让它再改更多
2. 先确认它改了哪些文件
3. 能用产品里的撤销就优先用撤销
4. 如果项目本来就在 Git 下，再用你熟悉的 Git 方法回退
5. 回到安全状态后，再重新下更清楚的指令

## 不熟 Git 的话，可以先这么做

很多新手会被“恢复”两个字吓到，以为必须先懂很多 Git 命令。刚开始不必这样。

可以先这么做：

- 在练习目录里练
- 一次只让它改一个小文件
- 结果不满意就直接撤销

等开始处理正式项目，再系统学习 Git 回退。

## 预防比补救更重要

下面这些做法，会明显降低“改错后很难收拾”的概率：

- 明确写“只改哪个文件”
- 先让它给计划，再执行
- 每做完一步就检查，不要积累很多改动再一起看
- 高风险操作前先确认

## 把恢复点当成探索工具

恢复不只是出错后的补救，也可以在探索不同方案前主动使用。

适合先留恢复点的情况：

- 要比较两种实现路线
- 要让 Agent 做一次较大范围重构
- 要尝试自动化脚本或批量替换
- 你不确定需求会不会很快改方向

更稳的节奏是：

```text
确认当前安全状态
→ 让 Codex 说明将要影响的文件
→ 建立恢复点或确认 Git 状态
→ 小范围执行
→ 审查 diff 与验证结果
→ 决定保留、回退或换方案
```

如果客户端支持检查点或回放能力，可以优先使用产品内置能力；如果项目在 Git 下，也可以用分支、stash 或小 commit 做恢复点。关键不是记住某个命令，而是不要在看不清影响范围时继续扩大改动。

做错本身不可怕。没看清改动范围就继续往下改，才更麻烦。
