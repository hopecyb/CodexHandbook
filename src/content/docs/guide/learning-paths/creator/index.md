用一组资料完成一篇文章，再把它做成可编辑演示稿，最后保存下次可复用的任务说明。每一步都留下文件；你可以根据这些文件判断自己是否完成。

需要能在 Codex 中打开本地文件夹。生成演示稿还需要可创建 PPTX 的工具和可打开它的演示软件；具体环境见案例，不要求所有客户端具备相同工具。不熟悉文件操作时，先完成[处理文件](/guide/learning-paths/beginner/02-work-with-files/)。

## 路线与材料

| 步骤 | 前置输入 | 本步产物 | 完成后去哪里 |
|---|---|---|---|
| 1. 整理证据 | 三份合成资料与来源索引 | 事实表、冲突与缺失清单 | 写文章 |
| 2. 写作与修改 | 事实表、受众与提纲 | 文章、事实映射、修订说明 | 制作演示稿 |
| 3. 制作演示稿 | 文章、事实映射与汇报目标 | 八页 PPTX、八页预览、备注与检查记录 | 保存复用说明 |
| 4. 保存复用说明 | 前三步的产物与实际经验 | 任务模板、验收清单、一次迁移记录 | 用新资料再试一次 |

[下载文章练习包](/downloads/source-backed-article/source-backed-article-1.0.0.zip) · [下载演示稿练习包](/downloads/article-to-slides/article-to-slides-1.0.0.zip)

两个包都能独立使用。连续学习时，第 3 步优先使用自己完成的文章；演示稿包内的 `input/` 是参考输入，供尚未完成文章或需要对照时使用。全部产品、人物与访谈均为合成教学资料。

## 1. 整理证据，保留冲突

前置：解压文章包，读 `brief.md`、`sources/index.csv` 和列出的三份资料。按[文章案例第一步](/cases/write-an-article/#1-先整理事实和冲突)整理，不急着写成文稿。

把输出放进文章包的 `my-output/`，保留原始来源。事实表记录资料 ID、小节、支持的说法和证据类型；另外写 `unresolved.md`，列出资料没有解决的问题。

完成条件：能找到 P3 与 C2 关于诊断默认设置的矛盾，且没有擅自选一方作为最终答案；合成访谈仍标为合成，没有生成来源未提供的准确率或省时数字。

如果来源打不开或编号不匹配，先恢复文件与索引；不能凭文件名猜内容。通过后进入下一步。

## 2. 写文章，再对照来源修改

前置：上一阶段的事实与未决清单。继续[文章案例](/cases/write-an-article/)，明确受众后完成提纲，在已明确范围内连续写稿，再做事实审查和表达修改。

交付 `article.md`、`claim-map.csv`、`unresolved.md` 和一份修订说明。至少指出一项事实修正和一项表达修正；参考包中已有设计初稿与实际文本 diff，不能把设计反例当成真实模型失败。

完成条件：关键事实可定位、作者建议与资料支持分开，诊断冲突保留。能运行 Python 时，可按案例执行结构校验；即使通过，仍需逐句判断来源是否支持结论。

保留这批文件作为下一步输入。你的文章可以与参考稿不同，但不能丢掉关键限制。

## 3. 把文章变成八页演示稿

前置：完成的文章与事实表。按[演示稿案例](/cases/create-a-slide-deck/)确定受众、约五分钟的目标和八页主线，先用主题页与限制页确认版式，再完成其余页面。

把文章与事实表复制到演示任务的输入目录，说明它们是你自己的版本；不要一边引用自己的文章，一边默认沿用参考稿所有结论。

交付八页 PPTX、八页预览、逐页说明和验证记录。完成条件：在你记录的演示软件环境中可打开，关键文字可编辑，每页都检查中文与边界，来源冲突在压缩后仍清楚可见。

没有 PPTX 工具时先保存大纲，记录尚缺的能力；这一步保持未完成，之后在具备工具的环境继续。通过后进入复用阶段。

## 4. 保存下次能复用的任务说明

前置：已经完成并检查过的文章与演示稿。创建 `workflow.md`，按下面的模板写入自己实际用过的方法；不要只保存最后一轮“继续”提示词。

```md
# 资料到汇报

## 本次任务
- 受众与用途：
- 输入目录、来源索引及不可改动的原始文件：
- 输出目录与要求的文件格式：

## 顺序
1. 先列事实、推断、冲突和缺失，再写正文。
2. 明确受众和结构后连续写稿，对照来源修改。
3. 将文章压缩为八页，先检查主题页与限制页。
4. 检查原生文字、中文字体、全部预览和备注。

## 验收
- 关键事实能定位到原文，未决问题仍可见。
- 作者建议与产品事实区分，合成素材未冒充真实证言。
- PPTX 可以打开和编辑；逐页检查并记录软件与字体环境。
- 明确实际做过、没有做过的检查，交付停在本地。

## 本次经验
- 实际遇到的问题、改了什么、如何确认恢复：
- 下次可以保留的步骤：
- 下次必须重新确认的事实与环境：
```

接着做一次小范围迁移：把受众从“首次试用的个人作者”改为“准备审阅材料的同事”，保留同一组来源，仅重新生成提纲。保存 `reuse-check.md`，记录受众改变后标题、重点和顺序如何变化，以及哪些事实边界保持不变。这个练习检查模板能否适应新任务，不宣称完成了新的事实研究。

完成条件：别人拿到 `workflow.md` 能找到输入与输出、知道何时算完成；迁移记录包含具体差异，没有继续写成面向原受众的文章。如果顺序已稳定，再阅读[把工作流沉淀为 Skill](/cases/workflows/turn-a-workflow-into-a-skill/)。[写作 Skill 示例](/skills/examples/writing-skill/)已提供完整下载包，可复用风格样本、事实表和冲突处理方式；结构检查不能替代人工事实审阅。

## 可选：先做一个数字明确的任务

更偏办公分析的读者，可以先做[销售周报](/cases/analyze-a-spreadsheet/)。它包含 CSV、退款和重复行、参考汇总及独立核对脚本。完成后可以把“关键数字需独立计算、异常口径需写清”加入自己的验收清单，不必把它强行并入虚构产品文章。

整条路径完成后，你应留下来源材料、文章与事实表、可编辑演示稿、验证记录和复用说明。单纯读完链接或下载参考答案，不等于完成练习。
