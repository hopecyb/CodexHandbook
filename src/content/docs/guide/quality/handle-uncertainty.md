title: 处理不确定性
description: 信息不足时要求提问而非臆造。
---


信息不够时，先确认，再继续。

使用 Codex 时，最麻烦的情况之一，就是它把缺失的信息补成了看起来合理的答案。
前提一旦错了，后面的步骤也会一起偏掉。

## 什么叫“不确定”

这里说的“不确定性”，主要是指：

- 它现在没有足够证据确认
- 相关信息不在当前上下文里
- 这个判断如果继续猜，风险会变大

更合适的做法，是提前把“什么时候先停下来确认”说清楚。

在提示词中固定：

```text
信息不足时先提问；不要编造文件路径、API 或业务规则。
```

发现臆造：停下、纠正事实、必要时新开线程。

## 判断方式

如果一个结论满足下面任意一条，就不该靠猜继续往下走：

- 当前文件里找不到证据
- 你没有明确提供这条业务规则
- 需要外部事实，但还没核来源
- 一旦猜错，会影响后面多步执行

## 常见误会

### 1. 回答完整，不等于它真的知道

内容完整，有时只是补得顺，不代表这些内容真的存在于你的项目里。

### 2. 信息不完整时，重点不是把空白补满

信息尽量给全当然更好，但实际协作里，信息不完整很常见。

更重要的是两件事：

- 缺信息时，它要先停下来确认
- 允许它提问，而不是强行猜完

### 3. 它提出问题，不一定会拖慢效率

表面上多了一步，通常反而会减少返工。

很多问题，都是从“先猜着做”开始放大的。

### 4. 发现它猜了，先停住再继续

先把错误停住，再继续。处理顺序如下：

1. 明确指出哪一条不对
2. 补上真实信息
3. 必要时让它基于更正后的事实重新开始

## 可直接补充的句式

如果你想减少它乱猜，可以直接这样写：

```text
如果你不能从现有文件或我提供的信息中确认，请先提问，不要自行补全。
```

## 再补一条

还可以加一句：

```text
如果存在多个可能解释，请先列出你不确定的点，再继续。
```

更麻烦的情况，是把猜测当成事实继续往下推进。
