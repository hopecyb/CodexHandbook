“配置项参考”这类页面很容易一上来就把人看晕，因为到处都是键、层级、覆盖关系。先把一个问题想清楚，会好懂很多：

> **哪些行为应该改配置，哪些不该靠配置解决？**

配置文件常用来统一 **模型、沙盒、审批、MCP** 等行为。本页是**概念索引**；具体文件路径、TOML/YAML 键名必须以 [OpenAI Codex 文档](https://developers.openai.com/codex) 与你安装的版本为准。

## 一个判断原则

配置里一般放“**希望它长期影响行为**”的东西，不适合拿来放这些内容：

- 敏感值
- 团队规则全文
- 临时一次性的任务说明

把它分成三类会比较清楚：

- **长期行为偏好**，一般放在配置里
- **具体任务要求**，一般放在 prompt / `AGENTS.md` / Skill 里
- **敏感值**，一般放在环境变量或 Secret 里

如果一时分不清，就想一件事：你是在改 Codex 的长期习惯，还是在交代这次任务？

- 长期习惯一般进配置
- 当前任务说明一般进 prompt、`AGENTS.md` 或任务描述

## 配置层级

| 层级 | 位置（概念） | 典型内容 |
|---|---|---|
| 用户级 | `~/.codex/` 等 | 默认模型、个人审批习惯 |
| 项目级 | 仓库内配置文件 | 团队沙盒、MCP 列表 |
| 环境变量 | Shell / CI 注入 | 密钥、临时开关 |
| 托管 | 组织下发 | 不可覆盖的强制策略 |

## 这些层级分别在管什么

- **用户级**：你自己的默认习惯
- **项目级**：这个仓库希望大家共享的默认行为
- **环境变量**：运行时临时带进去的值
- **托管策略**：组织直接定死，你本地改不了的部分

刚开始看时，不需要先背“谁一定覆盖谁”，先知道每层大概管什么就可以了：

- 用户级：这是“我个人平时就喜欢这么用”
- 项目级：这是“这个仓库希望大家都尽量这样用”
- 环境变量：这是“这次运行临时带进去的值”
- 托管策略：这是“组织已经替你定死的边界”

## 常见误会

### 1. 不是所有能配的东西都该进配置文件

有些内容放在下面这些地方会更合适：

- `AGENTS.md`
- 环境变量
- Skill
- 当前任务描述

配置不是万能容器。

### 2. 不需要一开始就弄懂每个配置键

大多数人一开始只需要搞懂：

- 模型
- 沙盒
- 审批
- MCP

这四类已经能覆盖绝大多数实际疑问。

### 3. 配了项目级设置，就能完全替代团队文档？

配置适合表达“系统行为默认值”，不适合替代“为什么这么做、什么时候别这么做”这类说明。

### 4. 官方配置键很多，也不用一次全学完

大多数人一开始先碰到的，基本就这四类：

- 默认模型
- 沙盒范围
- 审批策略
- MCP 连接

把这四类弄明白，已经能覆盖大部分入门阶段的问题。

## 与环境变量

| 类型 | 放哪 |
|---|---|
| API key、token | 环境变量或 Secret 管理器 |
| 非敏感开关 | 环境变量或配置 |
| 编码规范 | `AGENTS.md`，不是 config |

## 判断是否该进配置

遇到“这个东西到底该不该写进配置”的问题，可以先用这 4 句判断：

1. 它是不是希望长期默认生效？
2. 它是不是敏感信息？
3. 它是我个人习惯，还是项目共享规则？
4. 它是在调系统行为，还是只是在交代这次任务？

按这 4 句看，通常就不容易放错位置。

## 调整行为时的判断方法

遇到“想调整 Codex 行为”的需求时，可以按下面几项判断：

1. 这是长期默认行为，还是这次任务的临时要求？
2. 这是敏感值，还是普通配置？
3. 这是个人偏好，还是项目共享规则？

这样看，基本就能判断它该放到：

- 配置文件
- 环境变量
- `AGENTS.md`
- Skill
- 当前 prompt

## 常见场景

下面这几种情况，新手最容易拿不准：

| 你想做什么 | 一般放哪 |
|---|---|
| 想长期固定某个模型 | 用户级或项目级配置 |
| 团队要求改代码前先跑测试 | `AGENTS.md` |
| 这次任务只允许改 `docs/` | 当前 prompt |
| API key / token | 环境变量或 Secret |
| 连接某个 MCP 服务 | 项目配置 + 环境变量 |

这样看，比一直盯着配置键名列表更容易理清。

Cloud Secrets：[Secrets 与环境变量](/guide/web-and-cloud/secrets-and-variables/)

## 变更纪律

1. 一次只改一类配置，观察一周
2. 项目级变更走 PR review
3. 升级 CLI 后 diff 官方 migration 说明
4. 勿把密钥写入配置文件提交 Git

配置主要放长期默认行为，不放敏感值，也不拿来代替任务说明和团队规则。

## 常见错误

- 文档中的键名与旧版 CLI 不匹配
- 个人本机放宽沙盒，却用于客户仓库
- 与 `AGENTS.md` 指令矛盾（配置允许但文档禁止）
