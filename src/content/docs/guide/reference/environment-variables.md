“环境变量”常让人走到两个极端：要么觉得它很底层，要么觉得所有配置都能往里面塞。直接点说，环境变量就是一种在运行时把值交给程序的方法，特别适合放敏感信息和开关。

环境变量常用于**注入密钥、覆盖开关、适配 CI**，而不把敏感值写进配置文件或 Git。本页是概念索引；具体变量名以 [官方文档](https://developers.openai.com/codex) 与 `codex --help` 为准。

## 本页内容

- 哪些东西应该用环境变量而不是 config 文件
- 用户级、项目级、Cloud Secrets、CI 如何分工
- 常见命名与泄露风险

## 判断方式

如果一个值满足下面任意一条，就优先考虑环境变量：

- 不想写进 Git
- 会因机器、用户、环境不同而变化
- 只想在这次运行时生效

这也是为什么 token、临时开关、CI 注入值经常走环境变量，而不是直接写死。

配置键概念见 [配置项参考](/guide/reference/configuration-reference/)；Cloud 见 [Secrets 与变量](/guide/web-and-cloud/secrets-and-variables/)。

## 适合放环境变量的内容

| 类型 | 示例意图 | 不要 |
|---|---|---|
| 认证 token | API key、GitHub PAT | 提交到仓库 |
| 临时开关 | 调试日志级别 | 长期业务配置 |
| CI 注入 | 只读审查模式 | 生产写权限 token |
| MCP 子进程 | 第三方服务 key | 明文写在 `AGENTS.md` |

## 不要把环境变量当万能抽屉

很多团队用着用着会走偏：“反正能放，就塞环境变量里。”

更稳妥的做法是分清：

- **敏感值、运行时差异**：环境变量
- **团队长期约定**：配置文件或文档
- **工作流程规则**：`AGENTS.md` 或 Skill

这样以后排查问题时，你也更容易知道该去哪里找。

## `.env` 到底是什么

很多人第一次接触环境变量，最先碰到的常常是 `.env` 文件。这里也最容易出误解。

`.env` 不是另一种配置中心。它只是很多工具为了方便本地开发，提供的一种**批量加载环境变量**的方法。

可以这样理解：

- 环境变量是“值本身”
- `.env` 是“本地装这些值的一个常见容器”

所以：

- `.env` 方便，不等于安全
- `.env.example` 用来放示例名，不该放真实密钥
- 上线或进 CI 时，一般还是走 Secret 管理器

## 不适合仅靠环境变量的内容

- 编码规范、目录结构 → `AGENTS.md`
- 团队共识的模型默认值 → 项目配置（非密钥部分）
- 复杂 allowlist → [规则](/guide/customization/rules/allow-and-deny-patterns/)

## 常见误会

### 1. 环境变量不适合拿来装所有配置

它很适合放“值”，不适合承载整套团队规则和长期说明。

### 2. 只要写进 `.env` 就安全了？

如果 `.env` 被提交、被共享屏幕看到、被日志打出来，一样会泄露。

### 3. `unset` 之后就绝对没风险？

风险还可能存在于：

- shell 历史
- 子进程继承
- 日志
- 之前保存过的文件或截图

### 4. 本地能用 `.env`，线上也照样传一个 `.env` 就行？

很多时候并不是这样。在 CI、Cloud、托管平台里，更常见的做法是：

- 在平台后台配置 Secret
- 在运行时注入环境变量
- 不把真实值落到仓库文件里

## 分层与优先级（概念）

```text
组织强制策略（若有）
    ↓ 覆盖
Shell / CI 注入的环境变量
    ↓ 与配置文件合并（具体规则以官方为准）
用户级 / 项目级 config 文件
```

同一键多处设置时，以**官方文档说明的优先级**为准；排障时打印「有效配置」或查日志。

## 一个常用判断顺序

刚开始配置时，可以按这个顺序判断：

1. 这个值是不是敏感
2. 它是个人本地用，还是 CI / Cloud 用
3. 它需要长期保存，还是只在这次运行时存在
4. 它该放本地环境变量、CI Secret，还是 Cloud Secret

这样不容易出现“值是对的，但放错地方”的问题。

## 常见场景

| 场景 | 更稳的做法 |
|---|---|
| 本机调试第三方 API | 本地环境变量或 `.env`，并忽略提交 |
| 团队共享示例配置 | 提交 `.env.example`，不提交真实值 |
| GitHub Actions / CI | 平台 Secret |
| Cloud 任务调用私有服务 | Cloud Secret |
| MCP 服务器要读 key | 父进程环境变量或 Secret 注入 |

如果一时分不清，可以按这个原则处理：真实密钥尽量不要长期以普通文件内容的形式留在仓库里。

## 常用场景

### 本地开发

在 `~/.zshrc` 或 direnv `.envrc` 中导出个人 token——**勿 commit** `.env`。

### CLI 非交互

CI 通过 secret store 注入变量后跑 `codex exec`。见 [非交互模式](/guide/cli/non-interactive-mode/)。

### MCP 服务器

MCP 进程常继承父进程环境；在配置中引用 `$VAR` 而非写死值。见 [连接 MCP](/skills/mcp/connect-an-mcp-server/)。

### Cloud

仓库级 Secrets 在 Cloud 控制台配置，名称与任务内引用一致。

环境变量适合放会变、敏感、只在运行时需要的值，不拿来承载长期规则或说明。

## 安全清单

- [ ] `.env` 在 `.gitignore` 中
- [ ] 日志打印前脱敏 token
- [ ] 轮换泄露过的 key
- [ ] 最小权限 scope（只读 CI token 等）

## 常见错误

- 把 `.env.example` 填成真实 key 并提交
- 在 screen 共享时 `export` 可见 token
- 假设 `unset` 后子进程仍安全——需查进程树
