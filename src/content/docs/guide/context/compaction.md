title: 上下文压缩
description: 长对话压缩后保留什么、丢失什么。
---


“上下文压缩”可以理解成：对话太长后，系统会把前面的内容缩成更短的版本继续保留。它的目的，是让任务还能继续；但代价是，**细节可能会丢。**

## 为什么这会影响结果

很多新手会默认觉得：

“前面说过的话，它应该一直记得很完整。”

现实里并不总是这样。  
长任务进入压缩后，通常更容易丢失的是：

- 很细的小限制
- 某个临时但重要的例外
- 你前面点名过的文件白名单
- 验收标准里的边角条件

所以压缩不是错误，而是一种需要你配合的机制。

## 压缩后最该重申什么

压缩会丢掉细节。关键约束、验收标准、文件白名单应在压缩后 **重新声明**，或写在项目说明里。

尤其建议优先重申这几类：

- 只允许改哪些文件
- 哪些内容绝对不要动
- 怎样才算完成
- 当前已经完成到哪一步

## 常见误会

### 1. 压缩是不是等于“它忘了全部内容”

更准确地说，是会保留主干，但不保证所有细枝末节都原样保留。

### 2. 也不用每次都从头重说

也不用。

把最关键、最容易丢、最不能错的那部分重新说明，通常就够用。

### 3. 什么信息最不该赌它“应该还记得”

通常是这类：

- 文件范围
- 禁止项
- 验收标准
- 你确认过的重要决策

## 压缩后怎么补救

如果任务已经很长，可以在中途自己写一个短摘要，例如：

```text
当前有效约束：
1. 只改 docs 目录
2. 不要调整路由结构
3. 完成标准是首页文案更新且构建通过
```

这会比继续依赖整条长对话更稳。

概念层：[Token、上下文与压缩](/guide/foundations/tokens-context-and-compaction/)

长任务里，最关键的限制不要只说一次；压缩后，重要规则值得主动再说一遍。
