description: 密钥、隐私与不可分享材料。

凡是你不希望被随便看到、复制、外发或长期留在任务记录里的内容，都要先当成敏感信息处理。

## 为什么要先判断

很多安全问题不是因为有人故意违规，而是因为当时只想着“先把问题解决”。

比如：

- 为了排错，直接贴整份 `.env`
- 为了让它看懂，直接贴客户原始数据
- 为了省事，把带真实令牌的报错原文原样贴出来

这些做法在当下看起来方便，事后往往最难补救。

不要提供给 Codex（练习或生产）：

- API 密钥、密码、会话 Cookie
- 未脱敏的客户数据、身份证号等
- 内部未公开且合同禁止外传的材料

用占位符：`YOUR_API_KEY`。若已泄露，按组织流程轮换密钥。

## 拿不准时怎么判断

如果你拿不准某段内容算不算敏感，就先问自己两个问题：

1. 这段内容如果被无关的人看到，会不会有风险？
2. 这段内容如果长期留在任务记录里，我会不会不放心？

只要有一个答案是“会”，就先按敏感信息处理。

## 不要靠“应该没事吧”

很多人第一次用工具型 AI 时，会下意识觉得：

- “我只是临时贴一下”
- “它只是帮我看看”
- “这个文件又不会真的发出去”

但只要信息已经进入任务流程，就应该按敏感信息来对待。安全控制最好放在事前。

## 最容易被忽略的内容

除了密码和密钥，下面这些也常常算敏感：

- 客户名单
- 手机号、邮箱、身份证号
- 内部截图、未发布方案
- 带真实生产地址或访问令牌的配置文件

也就是说，敏感信息不只是一串 `sk-...` 密钥。

## 脱敏到什么程度才够用

不是所有信息都要删光，而是要保留“解决问题需要的最小信息”。

可以按这个思路处理：

- 保留结构
- 替换真实值
- 去掉身份标识
- 删除与当前问题无关的字段

比如你可以保留：

- 字段名
- 报错类型
- 调用顺序

但把下面这些替掉：

- 真密钥
- 真实邮箱
- 真实手机号
- 真实客户名称

## 必须提供时，怎么做更稳

更稳妥的做法：

- 用假值或占位符替换密钥
- 对真实用户数据做脱敏
- 只保留排查问题真正需要的字段
- 能描述现象，就尽量别整段贴原始敏感内容

例如：

```text
把真实 API Key 换成 YOUR_API_KEY，把真实邮箱换成 user@example.com。
```

## 如果已经不小心给出去了

按风险级别处理：

1. 先停止继续扩散
2. 立即轮换密钥、密码或令牌
3. 按组织流程报备和补救

解决问题时，默认只给“排查所必需的最小信息”；能脱敏就脱敏，能占位就占位。
