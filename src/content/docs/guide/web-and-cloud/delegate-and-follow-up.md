委托不是“把问题扔出去”，而是把目标、约束、环境和完成标准交给一个独立 Cloud 聊天。任务可在后台运行；你可以看日志、追加上下文、要求修改，并在最后审查 diff。

## 什么时候适合委托

- 任务需要较长构建或测试；
- 输入已经存在于远程仓库；
- 环境能够脚本化重建；
- 任务可以与当前工作独立推进；
- 你愿意在结果出来后审查，而不是直接合并。

依赖本地未提交状态、本机服务或持续人工操作的任务，先留在本地。

## 一个完整委托

```text
目标：修复 #42 中登录请求在 30 秒后仍未释放连接的问题。
起点：acme/api 的 fix/42-timeout 分支。
范围：packages/auth/** 与对应测试。
禁止：升级依赖、修改公共 API、推送 main。
验证：pnpm test --filter auth；pnpm typecheck。
完成：展示根因、diff、命令及退出结果；不要自动合并。
```

发起后先确认环境和分支正确。运行中只有在发现前提缺失或方向跑偏时才跟进：

```text
补充约束：不要修改全局 HTTP client；修复限制在 auth adapter。
先说明这会如何改变当前方案，再继续。
```

同一聊天保留已有上下文，适合修正同一目标；完全独立的目标应另开聊天。并行任务不要写同一个分支或文件集合。

## 结果出来后

1. 阅读摘要和完整 diff；
2. 对照任务允许路径；
3. 查看每条验证命令的真实输出；
4. 对失败或未运行项要求解释；
5. 需要修改时在同一聊天给出具体 follow-up；
6. 达到标准后创建 PR，并让 CI 与人工审查接管。

Cloud 可从 Web、IDE、GitHub、GitLab（Beta）、Linear 或 Slack 发起；官方 Cloud 页面还说明可以从 Codex CLI 开始和审查工作。不同入口不改变仓库、环境、网络与审查边界。

## 失败的跟进方式

不要只说“再试一次”。应提供失败证据和下一步：

```text
测试失败于 retry.test.ts:48。先解释失败是否由本次改动引起；
若是，只修复该回归并重跑 auth 测试；若不是，保留失败并明确记录。
```
