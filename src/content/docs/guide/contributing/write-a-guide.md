本页说明如何在 `src/content/docs/` 添加或改写**指南型**页面（非纯案例、非纯参考表）。

## 本页内容

常见卡点包括：

- 不知道一页指南该长成什么样
- 不确定自己是在写“教程”、写“规范”，还是写“目录摘要”
- 不知道怎么写才真的对新手有帮助

这里把这些问题拆开说明，方便你写出后续好维护、读者也看得懂的指南页。

## 指南页的作用

这里说的“指南页”，不是把资料堆上去就算完成。它要帮读者从“我知道这个主题存在”，走到“我大概知道什么时候该用、先看什么、别踩什么坑”。

所以它通常不只是知识点列表，也不只是命令清单，还要让读者知道下一步怎么继续。

## Frontmatter

```yaml
---
title: 页面标题
description: 一句话说明本文解决的问题
---
```

可选在文末使用统一页脚（与现有页一致）：

```markdown
---

**状态：** planned | draft | review | verified | outdated | archived
**适用产品：** App / CLI / IDE / Cloud
**最近核验：** YYYY-MM-DD
```

## 推荐结构

按 [外部资料整合模板](/docs/planning/external-source-integration.md#6-推荐页面模板) 选用小节，常见组合：

- 页面要解决什么问题
- 适合谁
- 最小可用做法
- 推荐工作流
- 常见错误
- 安全边界
- 验收清单
- 参考来源

产品操作页可偏步骤；概念页可偏表格与示意图。

## 常见误会

### 不是每页都要写成百科

第一次写指南页时，很容易把所有知道的内容全塞进去，结果重点反而没了。

更常见的写法是：

- 先讲页面主要解决什么问题
- 再讲读者最容易误解什么
- 再给一个够用的做法或判断法

这样通常比一次塞满所有细节更能帮到新人。

### 不能只顾自己会写，也要考虑别人怎么读

你自己当然知道上下文，但第一次来的读者不知道。

所以需要刻意补上这些桥接信息：

- 页面适合谁
- 读完后应该能解决什么
- 如果只想先上手，先抓哪一点

### 指南页不能替代官方文档

社区手册可以帮读者理解、串联、落地，但涉及会变化的事实，还是要回到官方文档核验。

## 交叉链接

- 站内链接用根路径：`/cases/workflows/explore-plan-execute-verify/`
- 链接到权威页，避免大段重复
- 新页在章节 `index.md` 与 `astro.config.mjs` sidebar 中登记

## 语气

- 简体中文，面向实践者
- 承认不确定性（「以官方文档为准」）
- 不用「万能提示词」叙事

## 写作顺序

可以按下面的顺序写：

1. 先写页面到底解决什么问题
2. 再写读者最容易误解或跳步的点
3. 再补最小可用做法、工作流或判断法
4. 最后补交叉链接和参考来源

## 核验

提交 PR 前阅读 [核验技术内容](/guide/contributing/verify-technical-content/)。命令、价格、权限等易变信息必须复核。

好的指南页不在于“把资料写全”，而在于让第一次来的读者知道页面为什么存在、先看什么、下一步往哪走。
