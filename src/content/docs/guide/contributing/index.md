**Codex 指南手册**是社区维护的文档站。欢迎修正错误、补充页面、添加可复现案例与 [examples/](/examples/README.md) 中的提示词实例。

## 本页内容

- 贡献类型与入口
- 写作与核验标准
- PR 与发布预期

## 什么样的贡献最有价值

如果你看到站里有：

- 你自己读不懂的地方
- 目录里有入口，但内容不够带路
- 命令、截图、说明已经过时

那就已经是很有价值的贡献线索了。

你不需要先变成“这个领域最懂的人”才能开始帮忙。很多真正有用的改进，恰恰来自第一次上手的人指出“这里默认你懂，但我其实没看明白”。

## 贡献类型

| 类型 | 说明 | 指南 |
|---|---|---|
| 修正/小改 | 错别字、链接、过时一句 | 直接 PR |
| 新指南页 | `src/content/docs/` 下章节正文 | [撰写指南](/guide/contributing/write-a-guide/) |
| 案例 | `10-use-cases/` | [案例模板](/cases/use-cases/case-study-template/) |
| 提示词实例 | `examples/prompts/` | [添加提示词示例](/guide/contributing/add-a-prompt-example/) |
| 技术核验 | 标 `verified`、更新日期 | [核验技术内容](/guide/contributing/verify-technical-content/) |
| 翻译 | `en/`、`zh-tw/` 等 | 路线图 M6；先稳定源文 |

## 常见误会

### 贡献不等于一定要新写一大章

很多第一次参与的人会把“贡献”想成必须补一整套重内容。

其实下面这些都很有价值：

- 补一段让新手看得懂的解释
- 修一个误导人的表述
- 补一个漏掉的目录入口
- 把过时命令降级或标注日期

### “我不是专家”不等于“我的反馈没用”

如果你的目标读者本来就包含初学者，那你在阅读时卡住的地方，本身就是高价值信号。

前提只是：把问题说具体，并尽量补成更清楚的表达，而不只是留一句“这里看不懂”。

## 基本原则

1. **简体中文 `root` 为源文**（除非另有说明）
2. **不复制**外部教程原文；参考 [外部资料整合计划](/docs/planning/external-source-integration.md)
3. **易变事实**须标 `最近核验` 日期
4. **每个 sidebar slug** 必须有对应 markdown，否则 `npm run build` 失败
5. 新增页面须同步更新 `astro.config.mjs` sidebar

## 第一次贡献，可以这样开始

如果你是第一次贡献，最稳的切入顺序是：

1. 先挑一个你刚刚真实卡住的点
2. 判断它属于修正文案、补页面、补示例还是核验过时信息
3. 只改这一小块，但把前提和读者视角讲清楚
4. 跑构建，确认没有把站点结构弄坏

这样比一上来就大改整章更容易成功，也更容易被 review。

## 行为准则

- 尊重他人劳动；讨论对事不对人
- 不提交真实密钥、客户数据
- 大范围重构前先 issue 或 RFC 讨论

第一笔贡献不必追求写得多。把一个真实会卡住新手的地方补清楚，再确认能通过构建验证，就已经很有价值。
