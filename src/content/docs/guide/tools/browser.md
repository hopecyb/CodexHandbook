**浏览器工具**让 Agent 在受控环境中访问真实网页：读取 DOM、截图，有时也能做简单交互。它适合前端验收、文档链接检查、对照设计稿，不适合替代安全审计，也不该拿去随便操作生产后台。

它和搜索是两类不同工具：搜索用于找网页信息，浏览器工具用于把网页真正打开。

## 它适合解决什么问题

这类工具常用于下面这些问题：

- 这个页面现在到底长什么样
- 这个按钮点下去会发生什么
- 这个布局在真实宽度下有没有坏

这类问题只读代码或看文字描述通常不够，还是要把页面真正打开。

## 能力概览

| 适合 | 不适合 |
|---|---|
| 打开本地 dev server 页面看布局 | 批量爬取受 ToS 限制的网站 |
| 验证公开文档链接 404 | 在未授权系统上自动登录 |
| 对照静态页面与实现 | 替代完整 E2E 测试框架 |
| 读取页面可见文本辅助调试 | 处理需复杂人机验证的站点 |

选型背景：[工具选择](/guide/tools/tool-selection/)

## 与其他工具对比

| 工具 | 输入 | 输出 |
|---|---|---|
| Web 搜索 | 查询词 | 摘要与链接 |
| 浏览器 | URL / 本地地址 | 页面结构、截图、交互结果 |
| Computer Use | 整屏 GUI | 任意应用操作（更重、更敏感） |

## 常见误会

### 1. 浏览器工具不是自动化测试的替代品

它可以帮你检查页面、截图、点一些交互，但不能替代完整测试体系。

### 2. 页面能打开，不等于页面没问题

能打开，只说明“页面存在”；布局、文案、交互、链接是否正确，还要继续看。

### 3. 什么情况下该用它？

最常见的场景有：

- 看本地页面有没有布局问题
- 检查链接是不是 404
- 核对页面和设计稿的大方向是否一致
- 确认“代码看起来对了，但真实页面是不是也对了”

## 判断标准

如果你的问题是在问：

- “真实渲染出来是什么样”
- “页面上到底看见了什么”
- “这个交互点完后页面反馈是什么”

浏览器工具一般比纯文本分析更合适。

## 推荐工作流

1. **本地前端**：先 `npm run dev`，再给 `http://localhost:PORT/path`
2. **明确任务**：「检查登录表单在 375px 宽度下是否溢出」，而非「看看网页」
3. **写清边界**：禁止访问外网、禁止提交表单到生产
4. **验收**：对照 [验证产物](/guide/quality/verify-artifacts/) 与截图

## 可直接使用的写法

可以直接这样提：

```text
请只访问 http://localhost:4321/guide/foundations/local-vs-cloud/ ，检查首屏布局和题图观感。
不要访问外网，不要提交任何表单。
如果发现问题，请给出截图依据和修改建议。
```

## 安全边界

- 默认假设浏览器可访问**你机器或环境能访问的一切**——包括内网 admin
- 任务中声明：`仅访问 localhost` 或允许域名白名单
- 勿在已登录个人账号的浏览器配置里跑不可信仓库任务
- Cloud 环境浏览器策略由 [Cloud 环境](/guide/web-and-cloud/cloud-environments/) 与网络策略决定

审批概念：[权限与审批](/guide/foundations/permissions-and-approvals/)

## 常见错误

- 给生产 URL 且未限制只读
- 把浏览器截图当「测试通过」却不跑自动化测试
- 与 Web 搜索混用：搜索不能代替真实渲染检查

## 验收清单

- [ ] 访问范围在 prompt 中写死
- [ ] 关键视觉问题有截图或文字说明
- [ ] 与单元/E2E 测试结论一致或已知差异已记录
