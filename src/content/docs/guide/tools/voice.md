部分 Codex 客户端支持**语音**：你说出任务，或听取回复摘要。它适合双手占用、快速口述想法的场景，**不**适合朗读密钥，也不能替代书面验收记录。

语音更适合表达方向、补充背景或快速跟进；涉及精确、可检索、可复查的细节时，还是要回到文字。

## 本页内容

- 语音适合哪些任务形态
- 与文字 prompt 如何配合
- 隐私与准确率注意

## 适用场景

| 适合 | 不适合 |
|---|---|
| 口述高层目标、头脑风暴 | 精确到变量名的代码指令 |
| 移动端简短跟进 | 宣读 API key、密码 |
|  accessibility 需求 | 需要可搜索、可 diff 的规范文档 |

口述后建议让 Codex **复述理解**或生成文字计划，再由你确认。见 [请求计划](/prompts/ask-for-a-plan/)。

## 语音适合做什么

语音的主要优点：

- 快
- 省手
- 适合把脑子里的想法先倒出来

常见问题：

- 容易漏字
- 容易听错
- 不适合承载精确路径、变量名、命令行参数

常见做法是先口述方向，再补成文字确认。

## 使用建议

1. 安静环境、简短句子，分段说清「目标 / 约束 / 完成标准」
2. 涉及文件路径、分支名时**改用打字**或让 Agent 复述拼写
3. 敏感项目关闭语音云端处理（若产品提供本地/禁用选项）
4. 重要决策保留文字记录在 issue 或 PR

## 常见误会

### 1. 语音是不是可以完全替代打字？

不行。  
下面这些内容，最好还是打字：

- 文件路径
- 分支名
- 命令
- 参数
- 验收标准

### 2. 说得越多越详细，也不一定越不容易出错

长篇口述如果没有结构，反而更容易把重点说散。

### 3. 语音回复是不是可以替代结果审查？

不能。  
语音摘要可以帮助你快速了解大意，但确认改动、文件、diff、测试结果时，仍然要回到文字和产物本身。

## 一个常用说法顺序

要先用语音提任务时，可以按这个顺序说：

1. 我要做什么
2. 不要做什么
3. 做完怎么验

说完后，再让它整理成文字版供你确认。

## 隐私

- 语音可能经过云端转写；勿读客户 PII、凭证
- 公共场所注意旁人旁听
- 团队政策可能禁止录音类功能处理机密代码名

## 与多模态的关系

- **输入图像**：设计稿、截图 → [图像提示](/prompts/prompting-with-images/)
- **输入语音**：本页
- **输出**：仍以代码、文件、文字 diff 为主；语音摘要不能代替审查

## 常见错误

- 长篇口述无结构，Agent 漏约束
- 用语音接受大批量代码变更却不看 diff
- 在语音里描述未脱敏的生产事故细节

语音适合起步和跟进，不适合代替精确指令、敏感信息处理和最终验收。
