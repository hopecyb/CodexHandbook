这里处理的是一个很常见的问题：

> **这次没做完，下一次怎么接着干？**

如果你不做交接，下一次重新打开时，很容易发生三件事：

- 你自己忘了已经做到哪
- Codex 不知道哪些约束还有效
- 新一轮对话把旧上下文说散了，又从头兜圈子

## 交接到底在留什么

交接与恢复，就是给“下一次继续工作的人”留一张说明卡。

这个“人”可能是：

- 几小时后的你自己
- 新开的另一个任务
- 另一个协作的人
- 继续接手的 Codex

所以交接不是写长篇总结，而是把**继续干活真正需要的信息**留下来。

## 交接时至少要留下什么

交接摘要建议至少包含：

- 目标与当前状态
- 已改文件
- 仍有效约束
- 下一步唯一动作
- 如何验证

如果还能再补一句，最好写清：

- 为什么停在这里

这样下一次继续时，不会只看到“做到一半”，却不知道是因为时间不够、需要审批，还是遇到了真实阻塞。

## 常见误会

### 1. 把整段旧对话转发过去就算交接

通常不算。

旧对话里有很多已经失效的探索、试错和分支判断。真正有价值的，是**现在仍然成立的结论**。

### 2. 写得越多越好

交接最怕两种情况：

- 太短，缺关键信息
- 太长，看不出下一步该干嘛

对继续执行最有帮助的，往往是**短、准、可接续**。

### 3. 只写“还剩一点，继续做完”

这句话几乎没用。

你要尽量把“继续做完”翻译成一个明确动作，比如：

- 跑一次 `pnpm build`
- 继续补写 `guide/verification.md`
- 检查 `/guide/foundations/local-vs-cloud/` 的题图观感

## 恢复时怎么做更稳

新线程粘贴摘要后，不要立刻大改，先做这三个动作：

1. 确认目标有没有变
2. 确认文件现状和交接描述一致
3. 从“下一步唯一动作”开始，而不是重新发散

这样可以避免依赖已经压缩、遗漏或变形的旧上下文。

好的交接不是复述历史，而是让下一次打开任务的人立刻知道：现在在哪、下一步干什么、做完怎么验。
