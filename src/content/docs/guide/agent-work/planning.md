直接说“你开始改吧”时，常见问题是：

- 路线想错了
- 范围做大了
- 风险没提前暴露
- 验证方式根本不够

规划就是把“准备怎么做”先拿出来给你看。

规划的意义，是把“我以为你会这么做”变成**可审查的中间产物**。尤其在复杂任务里，你真正批准的是一条执行路径，不只是按下一个“开始按钮”。

## 先出计划在确认什么

当你让 Codex “先出计划”，其实是在确认两件事：

- 确认它有没有真的理解你的目标
- 确认它准备走的路线，你愿不愿意承担

## 一份合格计划至少应包含什么

| 要素 | 作用 |
|---|---|
| 步骤 | 让任务有顺序，不是一股脑开做 |
| 涉及文件或范围 | 提前暴露影响面 |
| 风险与待确认项 | 防止把假设当事实 |
| 验证方式 | 让“完成”可被证明 |

如果只有“改 A，再改 B”，而没有风险和验证，那更接近待办清单，还不算真正的计划。

## 常见误区

### 1. 计划是不是就是把步骤列一下

真正有用的计划，至少还要告诉你：

- 影响哪些文件或区域
- 哪些地方有不确定性
- 做完要怎么证明它真的完成了

### 2. 小任务就永远不需要规划

也不绝对。有些任务虽然改动不大，但如果：

- 你对仓库不熟
- 涉及权限或审批
- 一旦做偏就很难回收

那仍然值得先停一下，让它讲清楚再动手。

### 3. 让它先出计划，会不会只是多一道形式

前提是你真的会审它。如果你让它出计划，却根本不看范围、风险和验证，这一步就会变成形式；但如果你会借此提早发现偏差，返工通常会少很多。

## 什么时候必须先规划

- 涉及多个文件或多个模块
- 你对仓库并不熟
- 需要人工审批后再执行
- 改动可能影响线上行为或团队协作规则
- 你已经感觉“这事做偏会很难收拾”

小型文案改动未必需要正式计划，但中大型任务最好先停一下。

## 拿不准时怎么判断

如果你拿不准要不要先规划，就问自己一句：

> **要是它现在直接开始做，做偏了我会不会很难收拾？**

如果答案是“会”，那就先要计划。

## 推荐的计划请求方式

先让 Codex 出计划，而不是直接开工：

```text
先不要改文件。请先基于当前仓库给出计划，包含：
1. 目标理解
2. 步骤编号
3. 涉及文件
4. 风险或待确认项
5. 每步如何验证
```

更完整的写法见 [先要计划](/prompts/ask-for-a-plan/)。

## 你在审什么

看计划时，不要只看“听起来像不像对的”，而要看这些问题：

1. 它是不是理解了真正目标
2. 影响范围是否合理
3. 有没有跳过明显的前置检查
4. 验证方式是否足够证明完成

很多返工不是因为实现差，而是因为批准了一个模糊计划。

先看计划，通常能在改文件之前把路线和风险讲清楚，成本也更低。

## 如何给计划反馈

你不需要重写整份计划，只需要指出偏差：

```text
保留第 1 步，先不要做第 2 步的重构。
把数据库变更拆成独立步骤。
补上失败时的回滚方案。
先只读分析，不进入实现。
```

这种“小步纠偏”通常比“全部推翻重来”更高效。

## 计划与执行的边界

一个很重要的协作习惯是把两者分开：

- **计划阶段**：允许探索、列选项、暴露不确定性
- **执行阶段**：按已确认路径推进

如果执行中发现前提变了，就回到计划，而不是硬闯。参见 [进度与引导](/guide/agent-work/progress-and-steering/)。

## 高风险任务的计划要多三项

如果任务涉及多文件修改、外部系统、权限配置、自动化脚本或团队规则，计划里还应该额外写清：

| 额外项 | 为什么重要 |
|---|---|
| 权限边界 | 哪些操作只读，哪些需要人工确认 |
| 恢复方式 | 做偏后如何回到安全状态 |
| 分阶段上线 | 先在测试目录、示例项目或小范围验证 |

这类任务不要只写“实现 A、实现 B”。更好的计划会明确哪些步骤先只读分析，哪些步骤可以写文件，哪些步骤必须等你确认。

示例补充：

```text
请把计划分成：
1. 只读分析
2. 最小改动
3. 验证
4. 回退方案

涉及外部系统或批量写入的步骤，先列出来，不要直接执行。
```

## 常见错误

- 计划里没有验证方式
- 未经确认就从计划跳到执行
- 把多个独立目标揉进同一份计划
- 明明需要确认，却只写“我开始做了”
