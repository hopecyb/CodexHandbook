规划的产物是一条可以检查和调整的执行路线。它能帮助你提前发现范围、依赖和验收缺口，但不意味着任务越大就越要反复等待确认。

先根据[任务分级](/prompts/ask-for-a-plan/)决定：直接完成、规划后在授权内执行，还是本轮只做方案。明确要“先给方案，不改文件”的请求应保持只读；明确要求实现的任务则不应只交计划就结束。

## 一份够用的计划

| 要素 | 具体到什么程度 |
|---|---|
| 目标 | 描述完成后的可观察行为 |
| 范围 | 写清相关文件、输入与排除项 |
| 顺序 | 标出真正的依赖，不把每个工具调用当步骤 |
| 验证 | 说明哪些输出或检查能证明完成 |
| 取舍 | 只列尚无答案且影响结果的决定 |

例如，为已有报告增加一个数据分组，可以计划“检查口径→修改汇总与展示→用样本核对总额与分组”。不需要读文件、每次编辑、每次测试都单独请求批准。

## 两种不同的计划请求

**方案尚未确定：**

```text
本轮只读分析，比较两种导出方案的依赖、兼容性与维护成本。
给出建议和需要我决定的取舍，不修改实现。
```

**范围已确定，需要完成实现：**

```text
按已有需求完成 CSV 导出。先检查仓库并说明简短计划，
然后在约定范围内连续实现和验证，不必逐步等待。
如果必须新增服务、改变公开接口或扩大数据访问，先说明具体原因。
```

这两段是本站设计示例。是否出现产品审批弹窗，由实际工具、策略和权限决定。

## 执行中怎样调整

- 发现普通实现细节：更新计划，继续完成授权范围内的工作。
- 原前提不成立：说明证据与影响，提出范围内的替代方案。
- 存在必须由用户决定的取舍：提出具体问题，继续不依赖回答的工作。
- 需要未授权的外部动作：先准备可审阅结果，在动作之前请求相应授权。

不要把“可能会遇到问题”当成停工理由，也不要为了完成计划忽略已经出现的范围变化。

## 如何反馈计划

```text
保留第 1、2 步，去掉重构部分。
本轮只做本地预览，不发布。
验收增加一条：旧文件格式仍能正确读取。
```

反馈只改变明确涉及的内容；未撤销的约束和完成标准继续有效。任务中断时，把当前文件、已完成验证与下一步写进[交接记录](/guide/agent-work/handoff-and-resume/)。

## 完成时回到证据

检查计划中的目标是否真的成立，而不是只看步骤是否全部打勾。没有运行的测试、未检查的预览和未核对的事实都应明确记录。完整流程见[探索—计划—执行—验证](/cases/workflows/explore-plan-execute-verify/)。
