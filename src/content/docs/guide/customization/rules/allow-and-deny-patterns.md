**Rules（规则）** 在配置或项目文件中声明哪些 shell 命令、路径、工具调用**允许或禁止**，减少每次手动点审批，同时防止危险操作自动化。

## 内容

- Allow / Deny 规则如何工作
- 与沙盒、审批弹窗、`AGENTS.md` 的关系
- 团队规则示例

## 规则到底在做什么

如果你觉得“规则”这个词有点抽象，可以先把它看成：提前约定 Codex 哪些事能做，哪些事不能做，别每次都靠临场判断和手点批准。

它的价值主要有两类：

- 减少那些明明每天都会发生、却总要反复确认的低风险操作
- 提前拦住那些不该自动发生的高风险操作

## 规则类型（概念）

| 类型 | 示例 |
|---|---|
| 命令 allowlist | 允许 `npm test`、`git status` |
| 命令 denylist | 禁止 `rm -rf`、`curl \| bash` |
| 路径 | 禁止写 `../`、禁止读 `~/.ssh` |
| 网络 | 禁止出网或仅允许 registry 域名 |

与 [权限矩阵](/guide/reference/permission-matrix/) 对照：规则是**可配置**的 enforcement，矩阵描述**典型默认**。

## 推荐分层

```text
组织托管策略（不可覆盖）
    ↓
项目 rules + AGENTS.md（Git 审查）
    ↓
个人 allowlist 补充（仅本机）
    ↓
单次任务 prompt 约束
```

## 常见误会

### 规则不只是为了少弹窗

很多人第一次听到 allowlist，会下意识觉得它的目标是少弹窗、少打断。

少弹窗只是其中一部分，更重要的是把低风险动作放行，把高风险动作拦住。

### 规则不等于沙盒

沙盒是在限制“最多能碰到哪里”；规则是在约定“哪些动作原则上就不该做”。

两者最好一起用，而不是选一个替代另一个。

### 团队底线不能只放在某个人本机

如果只有你自己的本机规则知道“禁止 push”“禁止碰 `.env`”，那别人依然可能踩进去。

团队底线应该尽量放在能被 review 的地方。

## 团队示例（示意，非复制即用）

**允许：**

- 包管理器安装**项目内**依赖
- 运行文档中的测试脚本

**拒绝：**

- `git push`、`git reset --hard`
- 读写 `.env*`（除非明确任务）
- 向公网 POST 含仓库内容的请求

规则应写在团队可 review 的文件中，而非仅口头约定。

## 常见错误

- Allowlist 过宽（允许 `bash` 等价于允许一切）
- 只 deny 不 allow，审批仍然过多
- 规则与 `AGENTS.md` 矛盾

## 起步建议

刚开始整理规则时，不必一上来就做完整策略。先做这两步就已经够用：

1. 明确列出 3 到 5 条每天常跑、风险低的命令
2. 明确列出几条绝对不希望被自动执行的高风险动作

先把最小边界跑顺，再慢慢细化。

## 安全边界

- 规则**不能**替代 code review 与分支保护
- 恶意 prompt 可能诱导 Agent 尝试绕过规则——保持沙盒默认严格
- 变更规则走 PR，像改 CI 一样对待

好的 allow/deny 规则，是提前把哪些动作合理、哪些动作不该发生说清楚。
