**个人偏好**是你本机跨项目生效的设置：默认模型、主题、审批习惯、个人 Skill 路径等。与仓库内的 `AGENTS.md` 不同，个人偏好**不应**假设队友相同。

## 内容

- 什么该放个人层、什么该放项目层
- 如何与 [Profile](/guide/customization/configuration/profiles/) 配合切换场景
- 避免个人宽松设置泄露到团队仓库

优先级总览：[个性化配置](/guide/customization/) · [作用域与优先级](/guide/customization/agents-md/scope-and-precedence/)

## 为什么要区分这一层

很多人会先把这些东西混在一起：

- 我个人喜欢怎么用
- 这个仓库要求怎么做
- 公司或团队强制怎么做

但这三类如果不分开，后面很容易出现：

- 你自己本机很顺手，队友却完全复现不了
- 你以为规则已经生效，其实只是你本机在兜底
- 你把宽松设置带进了更严肃的项目

## 适合放在个人偏好的内容

| 内容 | 示例 |
|---|---|
| 默认模型与推理档位 | 个人机器性能与套餐 |
| UI 主题、字体、通知 | 桌面 App [设置](/guide/desktop-app/settings/) |
| 个人 MCP（私有工具） | 本机数据库只读（慎授权） |
| 个人 Skill 库路径 | 不与团队 Plugin 冲突 |
| 终端别名、`codex` 启动目录习惯 | 见 [CLI 配置](/guide/cli/configuration/) |

## 不应只放个人层的团队内容

- 代码风格、测试命令、目录结构 → **项目 `AGENTS.md`**
- 强制沙盒策略 → **项目配置或组织托管**
- 客户仓库的合规要求 → **文档 + CI**，不能靠个人记忆

## 推荐实践

1. **工作 / 个人 Profile 分离**：客户项目用严格 Profile，练习项目可宽松
2. **进新仓库先读项目规则**，再决定要不要临时覆盖个人默认
3. **定期清理**个人 MCP 与 Skill，移除不再使用的第三方源
4. 换机或重装时，导出配置清单（不含密钥值）

## 常见误会

### 1. 我平时喜欢的做法，不一定适合直接设成全局默认

如果你的默认习惯比较宽松，到了客户项目或团队项目里，可能就不合适。

### 2. 个人偏好和项目规则谁都差不多？

差很多。  
个人偏好是“我自己习惯这样”，项目规则是“这个仓库大家都应尽量这样”。

### 3. 只看本机没问题，还不够判断这套设置是否合理

更合适的标准是：

- 不污染仓库
- 不依赖只有你自己知道的默认值
- 切到严格项目时不会误伤

## 判断是否该放个人层

拿不准一个设置该不该放个人层时，可以问自己：

1. 这是不是只有我自己在意的习惯？
2. 它会不会影响别人复现结果？
3. 它适不适合带进所有项目？

如果第 2 或第 3 个问题答案偏危险，就别轻易设成全局默认。

个人偏好是为了让你自己用起来更贴手，不是替团队规则兜底，也别把宽松设置一股脑带进所有项目。

## 与记忆功能

产品若提供「记忆」或持久偏好，见 [记忆与持久上下文](/guide/customization/memories-and-persistent-context/)。记忆适合稳定习惯；**项目特定约束仍应以仓库文件为准**。

## 常见错误

- 在个人配置里写死公司 API key
- 个人全局自动批准 shell，处理客户代码
- 队友 clone 仓库后抱怨「规则不生效」——规则从未提交

## 验收清单

- [ ] 能说出个人 vs 项目 vs 组织三层各一例
- [ ] 至少为一个客户项目配置严格 Profile
- [ ] 仓库内无个人密钥
