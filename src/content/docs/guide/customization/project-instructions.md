「项目说明」是 Codex 理解仓库的**静态上下文**，不限于单个文件格式。

## 内容

- 除了 `AGENTS.md`，项目级信息还应该放在哪里
- README、docs、脚本文件之间怎么分工
- 什么信息适合写进仓库，什么只适合留在当前对话里

## 项目上下文的组成

| 来源 | 作用 |
|---|---|
| `AGENTS.md` | 协作规则与命令（权威：本章 AGENTS 系列） |
| `README.md` | 项目是什么、如何启动 |
| `docs/` | 架构、ADR、运行手册 |
| 依赖与脚本 | `package.json`、`Makefile` 等可执行真相 |

Codex 会结合工具读取这些材料；关键是让**真相单一**，README 写的启动命令必须能跑通。

## 基本做法

1. 确保根 `README.md` 有：用途、安装、开发、测试四段
2. 把**重复给 Codex 的说明**沉到 `AGENTS.md`
3. 在任务里用 `@` 指向具体文件，而不是粘贴全文：

```text
按 @AGENTS.md 的测试要求，修复 @src/auth/login.ts 中的空指针。
相关设计见 @docs/auth-flow.md
```

## 为什么重要

常见情况包括：

- README 写的是一套
- docs 写的是另一套
- 真正能跑的命令藏在 `package.json`

这时不只是人会糊涂，Codex 也会糊涂。重点是让仓库里的“项目真相”尽量集中、尽量一致。

## 与「对话上下文」的分工

- **项目说明**：几个月内相对稳定
- **对话上下文**：本次目标、约束、中间结论

长任务中若发现某条规则被反复提及，应**回写**到 `AGENTS.md` 或 `docs/`，而不是在十个线程里复制粘贴。见 [保持上下文聚焦](/guide/context/keep-context-focused/)。

## 常见错误

- README 过时，Codex 按错误命令操作
- 把所有文档塞进一个巨型 `CONTEXT.md`，无人维护
- 敏感信息放在公开仓库说明中

## 常见误会

### 1. 只要我在对话里解释清楚，仓库文档乱一点也没关系

短期可能凑合，长期会越来越乱。

因为你下次还得再解释一遍，别人也看不到你这次说过什么。

### 2. `AGENTS.md` 能解决一切项目说明问题

也不行。

`AGENTS.md` 更适合规则和协作约束，不适合替代项目介绍、架构背景和完整运行说明。

### 3. 文档越多越好

更重要的是：

- 分工清楚
- 内容一致
- 关键命令可运行

## 分工建议

- `README.md`：项目是什么、怎么启动、怎么测试
- `AGENTS.md`：协作规则、禁区、完成定义
- `docs/`：更长的背景、架构、流程说明
- 脚本与配置文件：可执行真相

项目说明的重点，是让 Codex 和人都更容易找到同一份“仓库真相”。文档数量本身不是重点。
