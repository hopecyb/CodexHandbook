很多团队的问题，往往是**把同一条信息放错地方**：本该写进仓库的规则放进聊天，本该做成 Skill 的流程塞进 `AGENTS.md`，本该只读接入的数据却给了高权限 MCP。

这里更关心一个实际问题：

> 当你发现“这件事以后还会重复发生”，应该把它沉到哪一层？

## 简表

| 机制 | 最适合放什么 |
|---|---|
| 单次提示词 | 只对这一次任务生效的目标、约束、验收标准 |
| `AGENTS.md` | 仓库级协作规则与长期约束 |
| 记忆 | 个人偏好或少量非敏感、跨会话重复事实 |
| Skill | 可复用的工作流、检查清单、专项套路 |
| MCP | 访问外部工具、数据源与系统能力 |

如果这张表还不够，再继续往下看。

## 五步判断法

### 1. 只对当前任务有效的信息

这类信息优先放在**本次提示词**里。

适合：

- “这次只改 `docs/`，不要碰代码”
- “输出中文摘要，结尾附一个待确认问题”
- “先分析原因，不要立刻改文件”

不适合：

- 团队长期都要求 `pnpm test`
- 仓库禁改目录
- 每次 PR 审查都要按同一模板输出

这类长期规则应该继续往下沉。

### 2. 这是项目协作规则，还是个人习惯？

如果是**所有协作者都该知道的规则**，放进 [`AGENTS.md`](/guide/customization/agents-md/what-is-agents-md/)。

例如：

- 测试、lint、构建命令
- 哪些目录不能动
- 提交信息或 PR 验收规则
- monorepo 下不同子目录的特殊规范

如果只是**你自己的偏好**，例如“解释用中文”“先给结论再给细节”，更适合放进 [记忆](/guide/customization/memories-and-persistent-context/) 或个人配置。

可以按这个经验法则判断：

- 需要进 PR review 的，优先进仓库
- 别人看不见也没关系的，才考虑个人层

### 3. 这是“规则”，还是“步骤”？

很多文档之所以不好用，是因为把规则和步骤混在一起。

| 如果它属于…… | 更适合 |
|---|---|
| “不要直接 push 到 main” | `AGENTS.md` |
| “Review 时先看测试，再看风险，再看回归” | Skill |
| “发布前跑这 4 个命令” | Skill 或脚本 |
| “只允许访问只读 issue 数据” | MCP + 权限配置 |

判断时先抓这两点：

- **规则**回答“什么能做、什么不能做”
- **步骤**回答“这类事通常怎么做”

能复用的步骤，通常更适合做成 [Skill](/skills/overview/)。

## 常见组合，而不是二选一

成熟团队通常不会只用一个机制，而是组合使用。

### 组合 1：`AGENTS.md` + Skill

适合：代码评审、发版检查、故障排查。

分工：

- `AGENTS.md` 写硬约束：不能自动合并、必须跑哪些检查
- Skill 写流程：怎么审、按什么模板输出、如何分级问题

### 组合 2：Skill + MCP

适合：读工单、查数据库、拉设计稿、生成周报。

分工：

- Skill 定义执行顺序与输出格式
- MCP 提供“能连到哪、能查什么、能改什么”

可以把两者分开看：

> Skill 像作业指导书，MCP 像接进来的工具箱。

### 组合 3：`AGENTS.md` + 记忆

适合：团队规则稳定，但每个人表达习惯不同。

分工：

- `AGENTS.md` 写团队公共规范
- 记忆保留个人偏好，如语言、解释风格、默认输出结构

别反过来做。团队规则不应该只存在某个人的记忆里。

## 一个更实用的判断矩阵

| 问题 | 是 | 否 |
|---|---|---|
| 只影响当前任务？ | 提示词 | 继续判断 |
| 所有人都该遵守？ | `AGENTS.md` / 项目配置 | 继续判断 |
| 是可重复流程？ | Skill | 继续判断 |
| 需要实时外部数据或操作？ | MCP | 继续判断 |
| 只是个人长期偏好？ | 记忆 / 用户配置 | 提示词 |

当一个需求同时落在两列时，通常说明应该**拆层**，而不是硬塞进同一个地方。

## 三个典型例子

### 例 1：团队总忘记跑回归测试

不要只在群里说“记得跑测试”。

更稳的做法：

1. 在 `AGENTS.md` 里写明“涉及业务逻辑改动必须跑 `pnpm test`”
2. 如流程较复杂，再补一个测试执行 Skill
3. 在 CI 做最后兜底

### 例 2：每次做 PR review 都想让 Codex 按同样格式输出

不要把整段模板每次粘一遍。

更稳的做法：

1. 把输出结构做成 Skill
2. 在 `description` 中写清“用户说 review、审查、合并前检查时使用”
3. 如果团队统一使用，再把 Skill 路径写进项目文档

### 例 3：需要读取 Linear 工单再改代码

不要把 API token 粘进对话。

更稳的做法：

1. 用 MCP 接入 Linear
2. 默认只读权限
3. 如要形成固定流程，再用 Skill 规定“先读工单，再看代码，再给方案”

## 最容易踩的坑

### 把 `AGENTS.md` 写成百科全书

结果是硬约束不显眼，真正重要的命令与禁区被淹没。`AGENTS.md` 更适合短、硬、可执行。

### 把 Skill 当“万能收纳箱”

一个 Skill 里同时塞 review、发版、调试、写日报，最后既不容易触发，也不容易维护。

### 把 MCP 当成默认答案

能直接从仓库读到的信息，不必为了“高级”再接一个外部工具。MCP 是能力扩展，不是复杂度奖励。

### 让记忆承载团队事实

谁的账号上记住了，谁离开或换机器后规则就消失。这类信息应该回到仓库。

## 推荐落地顺序

如果团队现在还比较乱，可以按这个顺序收敛：

1. 先写一个最小可用 `AGENTS.md`
2. 把重复三次以上的流程收敛成 Skill
3. 只有在确实需要外部系统时再引入 MCP
4. 最后再整理个人记忆与偏好

这样更容易先把**协作共识**稳定下来，再逐步扩能力。
