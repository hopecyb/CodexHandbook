有效的项目指令像**检查清单**，不像论文。目标是让 Codex 在第一次尝试时就少犯可预见的错误。

## 推荐结构

```md
# 项目指令

## 快速开始（3–5 行）
安装、开发服务器、最常用的测试命令

## 必须遵守
编号列出不可违反的规则

## 代码与目录
命名、放置位置、依赖约定

## 完成定义
怎样算「可以提交」

## 禁止事项
明确写出不要做什么
```

## 写作原则

### 1. 前置硬约束

把「必须」「禁止」放在文件前部。上下文有限时，模型对开头权重更高——与 [上下文优先级](/guide/context/context-priority/) 同一逻辑。

### 2. 命令可复制

写**真实可运行**的命令，不要写「跑一下测试」：

```md
# 好
pnpm test --filter @app/web

# 差
确保测试通过
```

### 3. 可验证的完成标准

```md
## 完成定义
- `pnpm lint` 与 `pnpm test` 无失败
- 新 API 有对应单元测试
- 用户可见改动附上手测步骤（浏览器 + 移动端）
```

### 4. 说明「为什么」仅在一句话内

```md
- 不要改 `generated/`：由代码生成，手改会在下次构建被覆盖
```

过长背景应链接到 `docs/` 正式文档。

## 团队 playbook 片段示例

```md
## PR 与 Git
- 分支命名：`feat/`、`fix/`、`docs/` 前缀
- 一个 PR 只做一件事；大范围重构单独开 PR
- 合并前必须有人工 review diff，即使 Codex 已跑过测试

## 与 Codex 协作
- 大任务先要求「给出计划，等我确认再改代码」
- 涉及数据库迁移时，先输出迁移 SQL 供人工审查
```

## 常见错误

| 错误 | 后果 |
|---|---|
| 堆砌框架百科 | 关键测试命令被忽略 |
| 规则互相矛盾 | 模型随机选一条执行 |
| 只有「要优雅」类空话 | 无法验收 |
| 包含密钥或内网 URL | 泄露风险 |

## 维护节奏

- 每次 CI 命令变更时**同步更新** `AGENTS.md`
- 季度回顾：删除已过时规则
- 新成员 onboarding 的第一项：读 AGENTS.md 并跑通「快速开始」
