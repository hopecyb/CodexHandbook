有效的项目指令更接近**检查清单**。目标是让 Codex 在第一次尝试时就少犯可预见的错误。

第一次写项目指令时，常见问题往往是想法写了很多，真正关键的约束反而不够清楚。

## 内容

- 项目指令应该长什么样
- 什么叫“短、硬、可执行”
- 哪些写法最容易让 Codex 和人都看不明白

## 推荐结构

```md
# 项目指令

## 快速开始（3–5 行）
安装、开发服务器、最常用的测试命令

## 必须遵守
编号列出不可违反的规则

## 代码与目录
命名、放置位置、依赖约定

## 完成定义
怎样算「可以提交」

## 禁止事项
明确写出不要做什么
```

## 写作原则

### 1. 前置硬约束

把「必须」「禁止」放在文件前部。上下文有限时，模型对开头权重更高——与 [上下文优先级](/guide/context/context-priority/) 同一逻辑。

### 2. 命令可复制

写**真实可运行**的命令，不要写「跑一下测试」：

```md
# 好
pnpm test --filter @app/web

# 差
确保测试通过
```

### 3. 可验证的完成标准

```md
## 完成定义
- `pnpm lint` 与 `pnpm test` 无失败
- 新 API 有对应单元测试
- 用户可见改动附上手测步骤（浏览器 + 移动端）
```

### 4. 说明「为什么」尽量压到一句话内

```md
- 不要改 `generated/`：由代码生成，手改会在下次构建被覆盖
```

过长背景应链接到 `docs/` 正式文档。

## 什么叫“好指令”

好指令要让人和 Codex 都能快速抓住：

- 先做什么
- 不能做什么
- 做到什么程度才算完成

如果看完以后仍然不知道该先跑什么命令、哪里不能碰、怎么才算做完，那说明还不够好用。

## 团队 playbook 片段示例

```md
## PR 与 Git
- 分支命名：`feat/`、`fix/`、`docs/` 前缀
- 一个 PR 只做一件事；大范围重构单独开 PR
- 合并前必须有人工 review diff，即使 Codex 已跑过测试

## 与 Codex 协作
- 大任务先要求「给出计划，等我确认再改代码」
- 涉及数据库迁移时，先输出迁移 SQL 供人工审查
```

## 常见错误

| 错误 | 后果 |
|---|---|
| 堆砌框架百科 | 关键测试命令被忽略 |
| 规则互相矛盾 | 模型随机选一条执行 |
| 只有「要优雅」类空话 | 无法验收 |
| 包含密钥或内网 URL | 泄露风险 |

## 常见误会

### 1. 指令不是越详细越好

太散、太长、太像百科，会把真正高优先级的规则淹掉。

### 2. 只写“注意规范”这种话也算指令？

这类话通常不够可执行。  
更合适的写法是直接给出：

- 真正命令
- 明确目录
- 具体完成标准

### 3. 背景说明和执行规则可以随便混写？

也不建议。  
更合适的方式是：

- 规则放前面
- 背景压缩成一句
- 更长解释放到 docs

## 改写时先抓这几点

如果你手上有一份写得很散的项目指令，可以按这个方式收：

1. 把“必须/禁止”提到前面
2. 把空话改成具体命令或检查项
3. 把大段背景删短，改成链接
4. 给出一组最小完成定义

好项目指令不在于写得多，而在于让关键约束、关键命令和完成标准足够清楚，能直接执行。

## 维护节奏

- 每次 CI 命令变更时**同步更新** `AGENTS.md`
- 季度回顾：删除已过时规则
- 新成员 onboarding 的第一项：读 AGENTS.md 并跑通「快速开始」
