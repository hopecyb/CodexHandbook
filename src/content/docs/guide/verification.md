# 验证

很多新手第一次用 Codex，最容易犯的错，是**看到它说完成了，就当成真的完成了**。

验证就是：不看它怎么说，而是看结果到底有没有真的满足你的要求。

Codex 的输出必须可检查。验证不是可选步骤，而是每次任务闭环的一部分。

## 验证到底在看什么

无论你是在改代码、写文档、查资料，最后都要回答同一个问题：

> **这件事现在到底是“看起来差不多”，还是“已经可以交付”？**

很多返工都不是因为模型完全做错，而是因为：

- 改到了不该改的地方
- 漏改了一半
- 说自己查过资料，但来源并不可靠
- 页面能打开，但实际流程没跑通
- 文档写出来了，但不适合新人照着做

所以验证的作用，是**把风险关在交付之前**。

## 常见误区

### 1. 只要能运行，就算完成

“能运行”只说明它没有立刻报错，不代表：

- 逻辑正确
- 范围正确
- 没引入回归
- 符合你原本要的结果

### 2. 模型自己说“已验证”，就可以放心

你要看它**到底做了什么验证**。比如：

- 有没有真的跑测试
- 有没有真的读 diff
- 有没有真的打开产物检查
- 有没有给出可追溯来源

### 3. 验证是不是只有程序员才需要

写文章、做表格、生成配置、整理资料、写 PR 描述，都需要验证。只是验证方式不同。

## 如果还没有自己的流程，可以按这个顺序检查

如果你现在还没有自己的流程，可以先用这个顺序：

1. 看结果是不是偏题了
2. 看改动范围是不是过大
3. 跑能自动跑的检查
4. 最后用人的视角看一遍能不能交付

可以理解成：

- **方向对不对**
- **改得多不多**
- **机器检查过没有**
- **人真的敢接不敢接**

## 不同任务，验证重点不一样

- **改代码**：看 diff，再跑测试，再手动过关键路径
- **写文档**：看是否适合目标读者，链接是否可用，步骤是否真能照做
- **做研究**：看来源是否真实、是否最新、结论有没有超出证据
- **生成配置或脚本**：看环境前提、权限范围、失败后的恢复办法

如果你不知道该从哪一项开始，默认读 [完成定义](/guide/quality/definition-of-done/)。

验证是为了确认这份结果真的能用、敢用、交得出去。
