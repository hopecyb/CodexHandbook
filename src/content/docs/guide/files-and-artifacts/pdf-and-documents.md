PDF 常用于规范、论文、扫描件与导出报告。与纯文本不同，PDF **结构复杂、体积大、不易 diff**，需要单独约定任务方式。

把 PDF 交给 Codex 时，最常见的问题是结构理解不完整，或者你给的范围太大。

## 本页内容

- 如何让 Agent 正确「读」PDF 内容
- 生成或修改 PDF 时的格式与路径约定
- 验收时如何避免「看起来有文件其实打不开」

## 为什么 PDF 特别容易出问题

PDF 比文本文件更麻烦，因为它可能同时包含：

- 扫描图像
- 多栏排版
- 页眉页脚
- 表格
- 图片和文字混排

所以越是说清“看哪一段、要什么结果”，效果通常越稳。

## 读取 PDF

### 推荐做法

1. **指明文件路径**：`docs/spec.pdf` 或 @ 引用（视客户端支持）
2. **说明要什么**：摘要、对照某章节、提取表格数据
3. **页码或章节**：长文档限定范围，节省上下文
4. **敏感内容**：合同、身份证扫描等走 [敏感上下文](/guide/context/sensitive-context/) 流程

### 限制

- 扫描版 PDF 可能需 OCR，结果有误需人工抽查
- 复杂版式、多栏、脚注易丢结构
- 超大 PDF 不要整份塞进一次任务，分段处理，或者先转成 Markdown 提纲

## 常见误会

### 1. 把整份 PDF 丢进去，也不一定能稳定提炼出重点

如果 PDF 很长、结构复杂、还混着扫描页，更稳的做法仍然是：

- 指定范围
- 指定任务
- 分段处理

### 2. 扫描版 PDF 和普通文本 PDF 差很多

扫描版往往要先靠 OCR，OCR 一错，后面的摘要、提取和判断都可能跟着歪。

### 3. 生成出一个 PDF 文件，不等于已经完成

你还得确认：

- 能不能打开
- 文字有没有乱码
- 页数、目录、表格是不是对的
- 中文字体有没有真的嵌进去

## 生成或更新 PDF

| 方式 | 适用 |
|---|---|
| 从 Markdown/LaTeX 编译 | 技术文档、报告（可复现） |
| 从 HTML 打印 | 简单版式 |
| 库生成（如 reportlab） | 程序化票据、标签 |

在 prompt 中写清：

- 输出路径与文件名
- 页面尺寸、语言、字体要求（中文 PDF 特别注意字体嵌入）
- 是否提交 Git（大二进制常用 artifact 或 release）

## 可以直接套用的写法

可以直接这样提：

```text
请只阅读 `docs/spec.pdf` 的第 12-18 页，提取其中的验收标准。
不要总结整份文档。
如果 OCR 或版式识别不确定，请明确标出来。
```

## 与仓库策略

- 大二进制 PDF 考虑 **Git LFS** 或不进仓库
- diff 不可读时，验收靠**打开文件** + 对照 [验证产物](/guide/quality/verify-artifacts/)
- 生成物列表见 [生成物验收](/guide/files-and-artifacts/generated-artifacts/)

## 常见错误

- 要求「改 PDF 里一个字」却不提供可编辑源文件（`.md` / `.tex`）
- 把机密 PDF 放进公共仓库再让 Cloud 处理
- 未打开验收，仅看「文件存在」

## 验收清单

- [ ] PDF 在目标阅读器/打印环境可打开
- [ ] 页数、目录、关键表格与预期一致
- [ ] 仓库体积与 LFS 策略符合团队规范

处理 PDF 时，范围越清楚越稳。生成 PDF 后，也别只看文件在不在，还要确认能正常打开，而且内容真的对。
