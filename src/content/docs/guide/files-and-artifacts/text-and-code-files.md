绝大多数开发任务都落在**文本与代码文件**上：源码、测试、配置、Markdown。本页说明如何限定范围、保持风格一致并安全合并。

让 Codex 改文本或代码文件时，关键是改到对的地方、用对的方式，而且别顺手改多。

## 本页内容

- 如何让改动落在正确路径与编码
- 多文件编辑的组织方式
- 与 formatter、linter 的协调

## 文件类型与注意点

| 类型 | 注意 |
|---|---|
| 源码 `.ts` `.py` 等 | 遵循 `AGENTS.md` 与现有模式 |
| 配置 `.json` `.yaml` `.toml` | 易破坏结构；要求有效语法 |
| 文档 `.md` | 链接相对路径、中英混排规范 |
| 生成代码 | 标明是否应提交或 gitignore |

上下文：[文件与目录上下文](/guide/context/file-and-folder-context/)

## 为什么这类文件最容易出问题

真正容易出问题的地方常常是：

- 写到了不该写的文件
- 为了改一点内容，顺手重写一大片
- 风格和项目现有写法不一致
- 配置文件语法被悄悄弄坏

## 推荐 prompt 结构

```text
目标：<一句话>
允许修改：<路径 glob>
禁止：改 lockfile、改无关目录
风格：与 <示例文件> 一致
完成：列出变更文件 + 运行 <测试命令>
```

见 [好任务的结构](/prompts/task-anatomy/)

## 常见误会

### 1. 只给一句“帮我改这个文件”

这类任务的信息通常不够。

你最好再补几件事：

- 允许改哪些文件
- 不要碰哪些文件
- 风格参考谁
- 做完要怎么验证

### 2. 配置文件和普通文本没什么区别

也不能这么看。

像 `.json`、`.yaml`、`.toml` 这类文件，更常见的问题是结构、缩进、语法被破坏。

### 3. 改得越全面越省事

很多时候，“小范围、可解释、好审查”的改动，比“大面积顺手优化”更稳妥。

## 编码与换行

- 默认 **UTF-8**；特殊编码项目应在 `AGENTS.md` 声明
- 与 `.editorconfig` / `prettier` 一致，避免整文件换行符 diff
- 大文件分段改：@ 具体函数而非整文件重写

## 担心它改多时，可以直接这样限制

如果担心它改多了，就直接要求这三件事：

1. 先说明会影响哪些文件
2. 只改当前任务需要的最小范围
3. 列出改完后的验证动作

## 审查要点

- [审查 diff](/guide/quality/review-diffs/)：逻辑、范围、删除
- [运行测试](/guide/quality/run-tests/)
- 无意引入 `TODO` 占位未实现

## 常见错误

- 「重构整个项目」导致数百文件变动
- 在二进制或 minified 文件上强行文本编辑
- 文档链接写成绝对路径导致站内 404

文本和代码文件最怕改得又多又散，还不好审。把范围、风格和验证方式说清楚，后面会省掉不少来回。
