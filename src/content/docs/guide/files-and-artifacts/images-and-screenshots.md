图像让 Agent **看见**界面问题、设计意图或白板草图。本页涵盖输入（你提供的图）与仓库内图像文件管理；生成新图见 [图像生成](/guide/tools/image-generation/)。

用截图提任务时，最好让它知道你想让它看哪儿，以及为什么那儿有问题。

## 本页内容

- 如何附加截图最有效
- 设计稿 / Figma 导出如何使用
- 图像在仓库与上下文中的体积问题

## 输入图像的场景

| 场景 | 做法 |
|---|---|
| UI bug | 截图 + 标出异常区域文字说明 |
| 设计还原 | 导出 PNG + 写明断点与组件库 |
| 架构白板 | 清晰照片或导出图 + 图例说明 |
| 报错弹窗 | 含完整错误文本，避免只截一角 |

深度：[图像提示](/prompts/prompting-with-images/)

## 图片真正补的是什么

图片最有价值的地方，在于它能直接展示那些只靠文字不太好描述的信息，比如：

- 这个布局到底怎么歪了
- 这个按钮到底挤到哪了
- 这个弹窗到底写了什么

但图片本身不会自动告诉 Codex：

- 你最在意哪一块
- 你期望它怎么改
- 这是“当前情况”还是“目标效果”

所以图片通常还要配一句直接说明。

## 质量要求

- **分辨率**：文字可读，避免模糊缩略图
- **裁剪**：去掉无关桌面、通知栏敏感信息
- **标注**：箭头/圈选可用，但应用文字复述关键点
- **多图**：按「当前 / 期望」配对上传

## 常见误会

### 1. 发了截图，也不代表它会自动看懂问题

截图能提供视觉证据，但你最好还是补一句：

- 问题在哪
- 你想改成什么
- 哪张是当前，哪张是目标

### 2. 图越大越清楚，也不一定越好

过大的原图会带来两个问题：

- 无关信息太多
- 仓库或上下文体积变重

### 3. 只发设计图，信息还是不够

如果是“按图实现”，最好再补上：

- 断点要求
- 组件约束
- 哪些地方允许自由发挥，哪些不允许

## 仓库中的图像

| 实践 | 原因 |
|---|---|
| `assets/` 或 `docs/images/` 统一目录 | 便于维护 |
| WebP/压缩 | 控制 clone 体积 |
| 有意义的文件名 | `login-form-mobile.png` 而非 `image1.png` |
| alt 文本（文档内） | 可访问性 |

## 可以直接套用的写法

可以直接这样写：

```text
第一张图是当前页面，第二张图是期望效果。
请重点看首屏标题区和按钮间距。
不要根据截图猜业务逻辑，只处理视觉和布局。
```

## 隐私与安全

- 截图可能含客户数据、内部 URL、token——先打码
- 不要把含密钥的配置界面发给不可信任务
- [敏感上下文](/guide/context/sensitive-context/)

## 验收

对「按图实现」类任务：

1. 并排对比实现与参考图（或 [浏览器工具](/guide/tools/browser/) 打开页面）
2. 检查响应式与深色模式（若要求）
3. [验证产物](/guide/quality/verify-artifacts/)

## 常见错误

- 只给设计稿不给交互说明
- 4K 原图直接 commit
- 假设模型能读取 Figma 链接而不导出

好截图不只是“有图”。图清楚、重点清楚、期望也清楚，任务才更容易做对。
