---
title: 并行 Agent
description: 同时推进多个 Agent 任务，避免把自己拖进合并冲突和审查混乱。
---

并行 Agent 适合把**本来就能独立推进的工作**拆开，让主线程主要负责协调、验收和合并决策。

如果拆得对，并行能明显缩短等待时间；如果拆得不对，只会更快制造冲突。

## 常见误会

很多人第一次看到“并行 Agent”，会以为它主要就是“更快”。这样理解不算错，但还不够。

前提是：**这些任务本来就能独立成立**。如果它们其实互相依赖，只是被你硬拆开，并行反而会让你更慢，因为后面还要花时间对齐前提、回收结果、处理冲突。

## 什么时候适合并行

| 适合 | 不适合 |
|---|---|
| 两个独立调研任务同时进行 | 多个 Agent 同时改同一核心文件 |
| 一边跑只读分析，一边写文档草稿 | 需求仍在频繁变化、需你持续澄清 |
| 前台页面与后台接口边界清晰 | 一个问题高度依赖另一个结果才可开始 |

常见判断标准：

- **能明确交付物**，才适合并行
- **能先约定边界**，才适合并行
- **能独立验收**，才适合并行

## 主 Agent 负责什么

并行模式里，主 Agent 不用继续亲自做完所有子任务，重点是负责三件事：

1. 明确每个子任务的目标与禁区
2. 跟踪结果是否可验证
3. 在结果冲突时做最终取舍

主 Agent 更像一个小型技术负责人，重点在协调和取舍，不在亲自执行完所有子任务。

## 推荐拆法

### 拆“问题”，不要拆“工序”

更好的拆法：

- Agent A：分析登录失败是否由 token 刷新导致
- Agent B：检查最近两次认证相关改动

较差的拆法：

- Agent A：看一半日志
- Agent B：看另一半日志

前者每个任务都有完整目标；后者只是机械分片，回收成本很高。

### 优先拆成这些类型

- **只读分析**：读代码、读日志、读文档、列风险
- **方案对比**：A/B 实现路线、库选型、权限方案
- **边界清晰的产物**：独立页面、独立文档、独立模块

## 一个委派模板

给并行 Agent 的说明，尽量包含下面四项：

```text
任务：只分析 checkout 流程中的优惠券计算，不改代码。
交付：200 字摘要 + 关键文件路径 + 风险点 + 建议下一步。
边界：不要搜索支付模块以外目录；不要运行写操作命令。
验收：结论必须能回链到文件或日志证据。
```

这比“你去看看这个问题”更有效。

## 三种常见并行模式

### 1. 双路调研

适合：你还不确定哪条路线对。

- Agent A 调研现有实现
- Agent B 调研替代方案
- 主线程比较成本、风险与兼容性

### 2. 分层推进

适合：系统边界已经清晰。

- Agent A 处理文档或提示词层
- Agent B 处理代码或配置层
- 主线程做一致性检查

### 3. 草稿 + 审核

适合：需要先出一个版本，再快速复核。

- Agent A 产出草稿
- Agent B 只做 review，不改
- 主线程决定采用与否

这种模式比较适合文档补全、PR 审查、案例整理。

## 冲突管理

并行里最容易卡住的环节，常常是合并。

### 提前约定这些边界

- 哪些目录由哪个 Agent 负责
- 是否允许改共享配置文件
- 谁拥有最终提交权

### 这些情况要改回串行

- 两个子任务都需要改同一业务流程
- 一个 Agent 的结论持续推翻另一个 Agent 的前提
- 你发现自己花更多时间在“解释上下文”而不是推进任务

当协调成本大于节省的时间，并行就失去意义了。

## 审查与验收

每个并行 Agent 的输出至少应满足一项：

- 能回到具体文件、日志、链接或 diff
- 能明确说明“没做什么”
- 能告诉主线程下一步如何验证

如果交付只有一句“我觉得这里可能有问题”，主线程基本等于白收。

## 常见错误

- 看到任务多就盲目并行，而不是先判断依赖关系
- 多个 Agent 同时修改同一目录，没有所有权约定
- 主线程不验收，直接把子结果拼接成最终答案
- 把并行当成“减少思考”的方式，结果只是放大混乱

并行 Agent 的前提，还是任务彼此独立、可以单独验收，再分别推进。
