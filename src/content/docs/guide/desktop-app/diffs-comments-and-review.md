聊天摘要是 Codex 对工作的解释；Git 差异才是文件实际发生的变化。桌面应用的审查窗格可显示差异、添加逐行评论，并决定暂存、撤销、提交或推送哪些内容。

项目必须位于 Git 仓库中，才能使用完整审查窗格与 `/review`。

## 两层审查

先由你检查变更范围，再调用独立 reviewer 找实现问题：

1. 打开审查窗格，先看文件数量与路径；
2. 选择 **Last turn**，确认本轮到底改了什么；
3. 切换 **Unstaged**、**Staged**、**Commit** 或 **Branch**，确认审查范围；
4. 在输入区运行 `/review`；
5. 选择与基准分支比较、审查未提交改动、指定提交或自定义标准；
6. 阅读按优先级排列的发现，再决定是否修复。

`/review` 的 reviewer 默认只读，不会修改工作树。若随后要求 Codex 修复发现，仍受原有沙箱和审批规则约束。

## 一份可复用的审查标准

```text
请审查当前未提交改动，重点检查：
- 是否超出任务范围；
- 是否存在行为回归、边界条件或安全问题；
- 测试是否覆盖失败路径；
- 文档和实现是否一致。

先列问题，按严重程度排序；每条给出文件、位置、证据和最小修复建议。
若没有发现问题，请明确说明，并列出仍未覆盖的测试风险。
```

## 用逐行评论减少歧义

在可疑行上悬停，选择出现的 **+**，写下具体反馈；全部评论完成后，再发送一条明确指令：

```text
处理我留下的逐行评论。保持改动范围最小，完成后重新运行相关测试并展示新的 diff。
```

有价值的评论应说明风险或验收条件，例如“空数组时这里会返回什么？”；只有“这里不对”通常不够。

## 暂存与撤销

审查窗格可按整个差异、单个文件或单个 hunk 暂存、取消暂存或撤销。撤销会丢弃改动，操作前务必确认它不是任务开始前就存在的用户改动。

验收顺序建议固定为：范围 → 行为 → 测试 → 安全 → 可维护性。更多方法见[审查差异](/guide/quality/review-diffs/)。
