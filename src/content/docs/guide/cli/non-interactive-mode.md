非交互模式让 Codex **无需 TTY 对话**即可完成任务，是开发者把 Agent 接进脚本和 CI 的入口。

简单说，非交互模式不是来回聊天，而是把任务一次性交给它执行。

它更像一次命令式调用。

## 本页内容

- 何时用非交互而非 `codex` 交互会话
- 安全与审批在无人值守时的额外要求
- 与 [配置](/guide/cli/configuration/) 的关系

## 适用场景

| 适合 | 不适合 |
|---|---|
| CI 中跑固定审查提示 | 需要多轮澄清需求 |
|  nightly 文档链接检查 | 探索性重构 |
| 预定义模板的代码生成 | 高歧义产品决策 |

## 核心概念

非交互执行通常：

1. 从参数或 stdin 接收**完整任务说明**
2. 在指定工作目录运行
3. 以退出码表示成功/失败
4. 输出日志或结构化结果供下游消费

**命令名与参数以官方 CLI 文档为准**（常见为 `codex exec` 或等价子命令）；升级 CLI 后应复核 `--help`。

## 最小可用示例（示意）

```bash
# 在仓库根目录，只读审查（示意，参数以官方为准）
codex exec --cwd . "列出相对 main 的 diff 中的安全风险，不要修改文件"
```

实践建议：

- 在 shell 脚本中先 `cd` 到干净的工作副本
- 任务字符串写进 heredoc 或版本化的 `prompts/` 文件
- 捕获退出码，失败时 CI 标红

## 安全设计

无人值守 = **没有你在场点拒绝**：

| 原则 | 做法 |
|---|---|
| 最小权限 | 只读 token、受限沙盒 |
| 无 push | CI 只开 PR 或上传 artifact |
| 固定提示 | 禁止从 PR 描述直接拼接未消毒文本（注入风险） |
| 审计 | 保留日志与 diff artifact |

见 [人工审批模式](/cases/workflows/human-approval-patterns/) 与路线图 `08-developer-platform/non-interactive/`。

## 与交互模式对比

| | 交互模式 | 非交互模式 |
|---|---|---|
| 入口 | `codex` TUI | `exec` / 管道 |
| 人类在环 | 强 | 弱，需事先设计 |
| 适合学习 | 是 | 否 |
| 适合 CI | 否 | 是 |

交互用法：[CLI 交互模式](/guide/cli/interactive-mode/)

## 把交互任务改成非交互任务

不要把一整段聊天历史直接丢进脚本。更稳的做法是把它压成一个小规格：

| 要素 | 写法 |
|---|---|
| 目标 | 这次只做什么 |
| 输入 | 读取哪些文件、diff、日志或 stdin |
| 禁止 | 不改文件、不联网、不 push、不中断 CI 等 |
| 输出 | 文本摘要、JSON、报告文件或退出码 |
| 验收 | 哪些命令必须通过，哪些关键词不能出现 |

非交互提示词要像一张工单：边界清楚、输入完整、失败条件明确。凡是还需要产品判断、设计取舍或权限确认的任务，先留在交互模式里。

## 常见误会

### 1. 非交互模式更高效，所以要先学它吗？

不建议。

对第一次使用的人来说，非交互模式通常太快，也太硬，中间没有多少来回澄清的空间。

### 2. 它和交互模式最大的区别是什么？

最核心的区别可以直接看成：

- **交互模式**：中途还能问、还能改、还能批准
- **非交互模式**：更像一次性执行，适合预先定义好的流程

### 3. 什么情况下我暂时不要碰它？

如果你还在这些阶段，建议先别碰：

- 还不熟提示词怎么写
- 还不知道怎样验收结果
- 还没建立对审批、沙箱、权限的基本判断

非交互模式适合自动化，不太适合第一次摸索。先把交互模式用熟，再谈把它接进脚本。

## 常见错误

- 把交互会话里的长对话历史原样塞进单次 exec
- CI 使用生产凭据与写权限
- 未固定 CLI 版本导致流水线突然行为变化
