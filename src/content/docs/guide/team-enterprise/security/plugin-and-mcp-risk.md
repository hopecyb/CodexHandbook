**Plugin** 与 **MCP 服务器**把 Codex 连接到外部系统：工单、数据库、内部 API。能力越强，[威胁模型](/guide/team-enterprise/security/threat-model/) 中的外泄与越权面越大。本章与 [MCP 概述](/skills/mcp/mcp-overview/)、[Plugins 概述](/skills/plugins/plugins-overview/) 配合阅读。

第一次看到这些词时，不必急着记定义。先抓住一点：一旦让 Codex 连到外部系统，能力会变强，风险也会一起变大。

不管名字叫 Plugin 还是 MCP，核心问题都差不多：

- 它能读什么
- 它能改什么
- 谁来批准
- 出事了怎么追踪

## 内容

- 扩展的风险分类
- 批准清单与版本固定
- 调试与事故时的隔离

## 风险分类

| 类型 | 示例 | 控制 |
|---|---|---|
| 数据读 | MCP 读客户库 | 只读账号、行级权限 |
| 数据写 | 自动关工单、改配置 | 人工审批、双写确认 |
| 网络 | 任意外连 | 出口 allowlist |
| 凭据 | OAuth token 落盘 | 密钥托管、短期 token |
| 供应链 | 第三方 server 更新投毒 | 固定版本、hash 锁定 |

## 团队批准流程（推荐）

```text
申请（用途、数据分级、权限）→ 安全/架构 review
    → 进入「批准清单」仓库或内部目录
    → 固定版本号 + 负责人
    → 季度重审或随 major 升级重审
```

个人实验性 MCP **不应**与生产仓库同一 token。

## 最小实践

1. **默认拒绝**安装未在清单内的远程 MCP
2. **本地 MCP** 仍可能读全盘——用专用 OS 用户或容器
3. **日志**：记录 tool 名与参数摘要（脱敏），见 [Hook 审计](/skills/hooks/hooks-examples/)
4. **Skill 与 MCP 分工**：Skill 说明流程，MCP 执行外联——两者权限取并集，取最严策略

## 常见错误

- 「官方市场」等于「已安全评审」
- 开发环境与生产共用一个 MCP OAuth 应用
- 调试时打开 `DEBUG=*` 把 token 打进 CI 日志

## 常见误会

### 1. Plugin 和 MCP 现在还分不太清，有关系吗？

第一阶段关系不大。

共同点是：  
它们都会让 Codex 接触外部系统，所以都要考虑权限和风险。

### 2. 为什么总在强调“只读优先”？

因为只读通常意味着：

- 更容易试点
- 更容易发现价值
- 出错代价更低

### 3. 这类扩展是不是装上就能直接放心用？

哪怕功能看起来很方便，也仍然要问：

- 它能访问哪些数据
- 它是不是会写回系统
- 它的凭据怎么管

对外部扩展，先看权限和边界，再看功能强不强。

- [ ] 每个生产 MCP 有 owner 与数据分级
