**可接受使用政策（AUP）**把「能不能用 Codex 做这件事」写成组织共识，避免仅靠个人判断。它与 [威胁模型](/guide/team-enterprise/security/threat-model/) 互补：威胁模型讲风险，AUP 讲**行为边界**。

## 内容

- AUP 应覆盖的议题
- 与 HR/合规、技术控制的衔接
- 条款示例起稿（需法务本地化）

## AUP 在管什么

AUP 主要回答的是：就算技术上做得到，这件事在我们团队里允不允许这样做。

它不替代技术策略，而是把组织层面的边界写成大家能看懂、也能执行的规则。

:::caution
以下为**教育性提纲**，不构成法律意见。正式发布前须经法务与合规评审。
:::

## 常见误会

### AUP 也直接关系到一线使用者

很多人会把这类政策文档看成形式要求，觉得和一线使用者没什么关系。

但日常工作里真正会碰到的，往往是这些问题：

- 哪些数据不能丢给 Codex
- 哪些场景必须有人复核
- 哪些扩展和外部连接不能随便接

所以它不只是法务文件，也是实际使用边界。

### 写了政策，不代表团队就真的按这个做

如果政策说“生产变更必须审批”，但工具实际默认就能绕过去，那这份政策很快就会失效。

所以 AUP 更重要的是能和培训、权限、配置、审计对上，而不是单纯写得很全。

## 建议覆盖的议题

| 议题 | 要点 |
|---|---|
| 允许用途 | 开发、文档、研究、内部自动化 |
| 禁止用途 | 未授权访问、骚扰内容、规避安全控制 |
| 数据分级 | 哪些 repo/数据可用；客户 PII 规则 |
| 输出责任 | 人审后合并；不将输出当法律/医疗建议对外 |
| 扩展 | 仅批准清单内 Plugin/MCP |
| 账号 | 禁止共享个人席位；离职回收 |
|  incident | 报告可疑行为的路径 |

## 基本结构

1. **目的与范围**
2. **允许的使用场景**（链到 [能力地图](/guide/start-here/codex-capability-map/)）
3. **禁止的使用场景**
4. **数据与保密**
5. **人类监督要求**（合并、生产变更）
6. **违规后果**（引用现有员工手册）
7. **联系人与更新日期**

## 与技术控制对齐

| AUP 条款 | 技术落实 |
|---|---|
| 不得 exfiltrate 源码 | 网络策略、MCP 批准 |
| 生产变更需审批 | 分支保护、deny `git push` |
| 仅用批准模型 | 组织托管配置 |

## 常见错误

- AUP 写完无人培训
- 与技术 reality 脱节（政策禁止但工具允许）
- 多年不更新，与新功能（Computer Use 等）脱节

## 判断一条 AUP 是否有效

可以先问：

1. 它是不是在回答团队真实会遇到的使用边界
2. 它是不是能落到培训、配置或审批流程里
3. 违反它时，团队是否知道该怎么发现和处理

三条都更接近“是”，这条政策才更可能真正有效。

## 验收清单

- [ ] 员工 onboarding 包含 AUP 确认
- [ ] 与 [团队规则](/guide/customization/rules/team-rules/) 无矛盾
- [ ] 每年或重大功能发布时复审

AUP 的价值，在于把团队对 Codex 的使用边界写清楚，并且和实际控制手段对得上。
