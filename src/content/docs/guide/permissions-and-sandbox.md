安全使用 Codex，需要同时看两层控制：**沙箱决定技术上能碰到哪里，审批策略决定越过当前边界前是否要问你。**

![Codex 沙箱与审批流程：动作先经过沙箱边界，越界时请求人工审批，最终留下验证证据](/diagrams/sandbox-approval-flow-zh-cn.svg)

## 先记住这个区别

| 控制 | 回答的问题 | 典型对象 |
|---|---|---|
| 沙箱 | 这个动作最多能触达哪里？ | 项目文件、项目外路径、系统能力、网络 |
| 审批策略 | 越过当前边界前，要不要先问人？ | 安装依赖、访问网络、写外部目录、启动应用 |
| 任务约束 | 这次工作应该做什么、不该做什么？ | 允许修改的目录、禁止动作、验收命令 |
| 人工审查 | 已经执行的结果是否可接受？ | diff、日志、测试、外部副作用 |

任务约束不能替代沙箱；沙箱也不能替代最终审查。它们分别负责意图、执行边界和结果验收。

## 一次动作如何通过安全边界

Codex 准备执行命令或调用工具时，可以按下面的顺序理解：

1. 先判断动作是否在当前沙箱允许范围内。
2. 在范围内，则执行并记录输出；不一定出现弹窗。
3. 超出范围时，根据审批策略请求许可，或直接被拒绝。
4. 你可以拒绝、要求更窄的动作，或只批准这一次明确操作。
5. 执行后仍要看 diff、测试和外部系统状态，确认结果符合任务目标。

沙箱同样约束 Codex 启动的子进程和命令。不能因为动作发生在脚本内部，就假定它绕过了边界。

## 本地执行与 Cloud 的边界不同

| 环境 | 主要隔离方式 | 网络要点 | 你应检查什么 |
|---|---|---|---|
| App / CLI / IDE 的本地任务 | 操作系统级沙箱与当前审批策略 | 本地任务通常不应默认依赖外网；需要时明确批准或配置 | 工作区范围、命令、项目外路径、联网目的 |
| Cloud 任务 | OpenAI 管理的隔离容器 | 设置阶段可按环境配置联网；Agent 阶段默认关闭网络，除非显式启用 | 仓库、环境配置、允许域名、返回的 diff 与验证证据 |

Cloud 环境中的 secrets 用于设置阶段，并会在 Agent 阶段开始前移除。仍应坚持最小权限，不把无关生产凭据放入任务环境。

## 看到审批请求时，按四步判断

### 1. 对照任务

这一步是否真的服务于当前目标？“可能有用”不足以构成批准理由。

### 2. 对照范围

请求触达的是当前项目、项目外目录、网络，还是系统应用？路径、域名和命令越具体，越容易判断。

### 3. 对照副作用

它只是读取，还是会写文件、安装软件、发送数据、修改远端状态？外部副作用通常比本地可撤销修改需要更谨慎。

### 4. 对照验证与恢复

执行后如何确认成功？失败时能否撤回？如果这两个问题没有答案，先要求 Codex 解释或提出更小的替代方案。

## 一个具体例子：安装依赖

假设 Codex 请求运行：

```bash
pnpm install
```

不要只看命令熟不熟悉。应确认：

- 当前任务确实需要缺失依赖
- 命令在正确的仓库目录执行
- 它需要访问哪个包仓库
- 是否会改动锁文件
- 安装后要运行什么测试或构建

如果只是验证现有代码，而依赖已经安装，可以拒绝并要求先使用现有环境。

## 在提示词里声明边界

可以把可执行范围直接写进任务：

```text
只修改 src/auth 和 tests/auth。
先使用已安装依赖，不要联网或升级版本。
如确需访问项目外路径或网络，先说明目的、目标和最小操作。
完成后运行 pnpm test --filter auth，并汇报命令输出与剩余风险。
```

这段话让意图更清楚，但真正的执行限制仍由沙箱、审批策略和团队托管配置负责。

## 常见误区

- **出现审批弹窗就一定危险**：正常的安装、联网或项目外写入也可能触发审批；关键是必要性和范围。
- **没有弹窗就完全安全**：动作可能本就在沙箱范围内，仍需审查实际改动。
- **批准一次等于永久放开**：批准的持续时间和范围取决于具体产品与策略，应读清请求内容。
- **子 Agent 有另一套权限**：子 Agent 继承主任务的沙箱与权限模式，不会天然获得更高权限。
- **Hooks 可以代替沙箱**：Hook 是额外守护与审计层，不是操作系统强制隔离的替代品。
