第一次选择 Codex 入口时，不必先比较几十项功能。先回答一个问题：**这次工作主要发生在哪里？**

![Codex 客户端选择图：从工作位置出发，选择桌面 App、CLI、IDE 扩展或 Cloud](/diagrams/codex-client-selection-zh-cn.svg)

## 30 秒做出选择

| 工作主要发生在 | 首选入口 | 最适合的交互 |
|---|---|---|
| 本机多个项目、多个并行任务之间 | **桌面 App** | 看任务、审查 diff、处理审批、管理较长工作 |
| 终端、脚本或现有命令行流程里 | **CLI** | 直接给任务、执行命令、组合脚本与自动化 |
| VS Code、兼容编辑器、Xcode 或 JetBrains 中 | **IDE 集成** | 带着编辑器上下文提问、原地修改和审查 |
| 连接的远程仓库与隔离环境里 | **Cloud** | 把任务交给云端运行、并行处理、稍后审查结果 |

没有明确偏好时，从**桌面 App**开始通常最直观；已经长期使用终端或 VS Code，则直接留在熟悉的工作面里更省切换成本。

## 四个入口分别解决什么问题

### 桌面 App：本地工作的控制台

桌面 App 适合需要看清任务状态、文件改动和审批过程的工作。它尤其适合：

- 同时跟进多个任务或项目
- 使用工作树隔离并行修改
- 审查 diff 后继续追问或修正
- 在本机项目上安排需要持续运行的工作

示例：让一个任务修复登录回归，另一个任务只读分析性能瓶颈，最后分别审查结果。

### CLI：把 Codex 放进终端工作流

CLI 适合已经用命令行管理项目的人。它离测试命令、Git 和脚本最近，也便于把相同操作写进团队文档。

```bash
codex
```

示例：在仓库根目录启动 Codex，要求它先运行失败测试、定位根因、做最小修改，再用同一条测试命令复验。

### IDE 集成：围绕当前代码工作

IDE 集成适合问题与“我正在看的文件、选区或 diff”高度相关的场景。当前支持方式分为两类：VS Code、Cursor、Windsurf 等兼容编辑器使用 Codex 扩展；Xcode 与 JetBrains IDE 使用各自的 Codex 集成入口。

示例：选中一个难懂的函数，让 Codex 解释输入输出和异常路径，再要求补一组针对边界条件的测试。

### Cloud：在隔离的远程环境中委托任务

Cloud 适合已连接远程仓库、希望任务离开本机独立运行的场景。云端任务在隔离环境中执行，适合并行探索、较长任务和完成后的集中审查。

示例：把三个互不依赖的仓库问题分别交给云端任务，等待它们返回变更和验证证据，再逐一审查。

## 它们不是四选一

同一个工作流可以跨入口接力：

1. 在 IDE 里围绕当前文件澄清问题。
2. 把需要较长探索的任务交给桌面 App 或 Cloud。
3. 在 CLI 里运行团队约定的检查命令。
4. 回到桌面 App 或代码审查界面确认最终 diff。

选择入口的原则不是“哪个最强”，而是**哪个离当前上下文最近、最容易检查结果**。

## 两个常见场景

### 场景一：第一次修复真实项目里的 bug

优先用桌面 App。你能同时看见任务对话、变更和权限请求；完成一次完整闭环后，再尝试 CLI 或 IDE。

### 场景二：团队已有固定命令和 CI 约定

优先用 CLI，并在 `AGENTS.md` 中记录安装、测试、格式化命令。这样 Codex 在每次任务里都能遵循同一套项目规则。

## 选择后立即验证

不要只确认“客户端能打开”。在一个练习仓库里完成以下闭环：

1. 让 Codex 读取一个文件并解释它。
2. 要求做一处可撤销的小修改。
3. 检查 diff，而不是只看最终回复。
4. 运行一个验证命令。
5. 确认你知道如何拒绝或收窄权限请求。
