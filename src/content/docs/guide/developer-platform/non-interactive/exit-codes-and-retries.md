CI 依赖**进程退出码**判断步骤成败。本章说明 [codex exec](/guide/developer-platform/non-interactive/codex-exec/) 常见语义、重试策略与幂等设计。

## 本页内容

- 退出码与业务「审查未通过」的区别
- 429/网络类错误是否重试
- 如何避免重复执行产生副作用

## 退出码到底在告诉你什么

如果你第一次接触这类内容，可以先把“退出码”理解成：任务跑完后，程序留给脚本和 CI 的一个简短结果。

通常它不会解释很多，只会告诉流水线：

- 这次算成功
- 还是算失败

而“重试”回答的是另一个问题：这次失败，是应该立刻停下，还是值得再给一次机会。

:::note
具体退出码表以官方 CLI 文档为准；下表为集成时的**设计原则**。
:::

## 常见误会

### 失败不只一种

很多新手会把所有非 `0` 都理解成同一类失败。

但实际至少要分清：

- 任务本身跑崩了
- 策略或沙盒把它拦住了
- 外部服务临时抽风了
- 它成功跑完了，只是审查结论“不通过”

这些处理方式不一样，不能全部按重试处理。

### “自动重试”不等于更稳

如果失败原因本来就不会因为重试消失，比如权限不够、规则拦截、prompt 有问题，那重试只是在重复浪费时间和配额。

## 推荐语义（概念）

| 情况 | 建议处理 |
|---|---|
| `0` | 任务完成且满足 prompt 中的成功标准 |
| 非 `0` 且日志含 policy/sandbox 拒绝 | **不要**盲目重试，修配置或 prompt |
| 非 `0` 且 API 429/5xx | 有限次指数退避重试 |
| 审查发现 P0 问题但执行成功 | 用 [结构化输出](/guide/developer-platform/non-interactive/structured-output/) 的 `pass: false` + 脚本 `exit 1` |

「发现了安全问题」不应依赖崩溃式异常，而应**显式**在 JSON 里 `pass: false` 并由包装脚本决定退出码。

## 重试模板（bash）

```bash
max=3
delay=10
for i in $(seq 1 $max); do
  if codex exec --cwd . "$(cat "$PROMPT")"; then
    exit 0
  fi
  code=$?
  if [ "$code" -eq 2 ]; then
    echo "Policy error, not retrying" >&2
    exit "$code"
  fi
  sleep $((delay * i))
done
exit 1
```

将「不可重试」码与官方文档对齐后写入 `case` 分支。

## 幂等与副作用

| 风险 | 缓解 |
|---|---|
| 重复 PR 评论 | 用 check run id 或「已有 bot 评论则更新」 |
| 重复写文件 | exec 默认只读审查；写操作单独 job + 人工门 |
| 重复发通知 | 通知 webhook 带 dedupe key |

## 拿不准时怎么判断

如果你不确定某种失败要不要重试，先问自己：

1. 这个错误像不像临时性的外部波动
2. 就算重跑一遍，会不会产生重复评论、重复写入或重复通知
3. 失败原因是不是其实要靠人改配置、改 prompt 或改权限

更接近第 1 条，才适合有限重试；更接近第 2、3 条，就更应该停下来处理根因。

## 常见错误

- 忽略退出码，CI 始终 green
- 对策略错误无限重试，烧配额
- 重试时未固定 prompt/git sha，结果不可比

先分清“这是临时故障，还是根本不会因重试而变好”，再决定要不要重试。不是所有失败都值得再跑一遍。

## 验收清单

- [ ] CI 对非 0 退出码失败
- [ ] 重试次数与退避有上限
- [ ] 审查「未通过」与「运行崩溃」可区分
- [ ] 日志保留足够排障信息
