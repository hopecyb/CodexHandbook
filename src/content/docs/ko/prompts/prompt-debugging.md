결과가 틀릴 때 흔한 원인은 다음과 같습니다.

- 목표를 검사 가능한 결과로 쓰지 않음
- 제약을 분명히 쓰지 않음
- 컨텍스트가 불완전하거나 오래됨
- 작업이 큰데 먼저 계획을 요청하지 않음

프롬프트 디버깅의 핵심은, 어느 층의 정보가 빠졌는지 찾는 것입니다.

## 먼저 문제가 어디에 있는지 찾기

결과가 어긋났다고 바로 전부 다시 할 필요는 없습니다. 어느 층에서 문제가 났는지 먼저 찾으면 더 수월합니다.

1. 목표가 불분명한가?
2. 범위가 통제되지 않았는가?
3. 컨텍스트가 부족한가?
4. 작업이 너무 큰가?
5. 아니면 도구 경로 자체가 잘못 선택됐는가?

## 결과가 틀리면, 순서대로 묻기

1. 목표가 검사 가능한가?
2. 제약이 분명한가? Agent가 봤는가?
3. 컨텍스트가 오래됐거나 충돌하는가?(압축/이전 스레드)
4. 먼저 계획을 요청해야 하는가?
5. 도구를 잘못 골랐는가?(인터넷이 필요 없는데 검색함)

## 각 항목이 무엇을 점검하는가

### 1. 목표가 검사 가능한가

목표가 “좀 개선해”처럼 모호하면, 결과가 어긋나기 쉽습니다.

### 2. 제약이 분명한가

“너무 많이 함”의 원인은 못하는 것이 아니라, “어디까지만 할지”를 말하지 않은 경우가 많습니다.

### 3. 컨텍스트가 오래됐거나 충돌하는가

특히 긴 스레드에서 흔합니다.

- 앞에서 A를 말했고
- 뒤에서 B를 보완했고
- 지금은 혼합 상태를 들고 있음

### 4. 먼저 계획을 요청해야 하는가

작업이 크면, 바로 실행이 먼저 계획보다 이탈하기 쉽습니다.

### 5. 도구를 잘못 골랐는가

예: 로컬 코드에 집중해야 하는데 외부를 검색하거나, 인용 있는 연구를 원하는데 인상만으로 답함.

## 흔한 오해

### 1. 결과가 틀리면 프롬프트 전체가 폐기된다

많은 경우 작은 보완만으로 됩니다.

- 수락을 분명히 함
- 범위를 줄임
- 먼저 계획을 내게 함

### 2. 디버깅은 프롬프트를 계속 길게 쓰는 것이다

때로는 노이즈를 지우고, 가장 중요한 경계만 남기는 편이 낫습니다.

### 3. 스레드가 길수록 컨텍스트가 많아서 좋다

너무 길면 옛 제약, 오래된 정보, 압축 잔여가 간섭하기 시작합니다.

## 쓸 만한 복구 순서

문제를 궤도에 되돌리려면 이렇게 하세요.

1. 목표를 다시 써 검사 가능하게 함
2. “어디만 고치고, 어디는 건드리지 말지”를 보완
3. 작업이 크면 먼저 계획을 요청
4. 그래도 혼란스러우면 단일 파일 또는 단일 문제 재현으로 축소
5. 그래도 안 되면 새 스레드에서 핵심 경계를 다시 진술

프롬프트 디버깅의 핵심은 말을 더 복잡하게 쓰는 것이 아니라, 어느 층의 핵심 정보가 제대로 전달되지 않았는지 찾는 것입니다.

그래도 실패하면 단일 파일 재현으로 줄이거나, 새 스레드에서 제약을 다시 말하세요.
