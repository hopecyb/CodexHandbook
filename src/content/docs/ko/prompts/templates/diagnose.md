# 진단 템플릿

진단류 작업의 흔한 오해는, 말로는 “먼저 조사”라고 하면서도 실제로는 바로 고치길 기대하는 것입니다.

진단 템플릿의 핵심은 “원인 찾기”와 “손대서 고치기”를 분리하는 것입니다.

## 템플릿

```text
현상: 【오류 메시지, 실패한 테스트, 사용자 보고】
배경: 【최근 변경, 환경, 재현 단계】
입력: @【로그/테스트/관련 코드】
제약: 아직 코드를 바꾸지 말 것. 가능한 근본 원인 2–3개와 검증 방법을 나열.
출력:
1. 가장 가능성 높은 근본 원인(증거 포함)
2. 실행 가능한 검증 단계(명령 또는 체크포인트)
3. 검증이 통과하면 수정 계획 초안(제 확인 후 실행)
```

## 언제 이 템플릿이 맞는가

- 버그가 아직 위치하지 않았을 때
- 테스트가 실패했지만 어느 층이 깨졌는지 모를 때
- 문제가 복잡하다고 느껴 바로 추측 수정을 막고 싶을 때

## 흔한 오해

### 1. 진단은 느리니 바로 고치는 편이 낫다

많은 재작업이 진단을 건너뛰어서 생깁니다.

### 2. 가능한 근본 원인 2–3개를 나열하면 너무 장황하지 않을까

아닙니다. 오히려 무작정 추측하는지 가늠하는 데 도움이 됩니다.

진단 템플릿은 왜 깨졌는지를 먼저 말하게 한 뒤, 어떻게 고칠지를 논의합니다.
