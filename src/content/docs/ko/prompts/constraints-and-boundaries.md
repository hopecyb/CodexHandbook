많은 작업 실패는 목표를 전혀 말하지 않아서가 아니라, **경계가 불분명해서**입니다.

“이 페이지를 고쳐 줘”라고 하면 Codex는 이렇게 이해할 수 있습니다.

- 카피만 고친다
- 스타일도 손대도 된다
- 컴포넌트도 건드려도 된다
- 의존성도 추가해도 된다

당신이 원한 것은 “이 카피만 고치고, 구조는 건드리지 말 것”일 수 있습니다.

제약은 “어디까지 할지”, “절대 건드리면 안 되는 것”에 답합니다.

## 내용

다음과 같은 문제를 막는 데 도움이 됩니다.

- 불필요한 추가 수정
- 월권 작업
- 손대지 말라고 한 계층까지 변경
- 겉으로는 끝났지만 대가가 너무 큼

## 자주 쓰는 제약

제약이 답하는 질문은 “절대 하지 말 일은 무엇인가?”입니다.

- 나열한 파일/디렉터리만 수정
- API 계약 / 데이터베이스를 바꾸지 않음
- 새 의존성을 추가하지 않음
- 네트워크 요청을 하지 않음
- 기존 포매터 설정을 유지

## “목표”와 “제약”을 어떻게 구분할까

- **목표**: 무엇을 만들어 내길 원하는지
- **제약**: 그 일을 할 때 넘으면 안 되는 선

예:

```text
목표: 홈 Hero 카피를 더 분명하게 고친다
제약: 레이아웃을 바꾸지 말 것, 의존성을 추가하지 말 것, CTA 동작을 바꾸지 말 것
```

제약이 없으면 Codex는 “더 분명하게”를 더 큰 개편 작업으로 이해하기 쉽습니다.

## 흔한 오해

### 1. 제약이 너무 많으면 결과가 나빠지지 않을까

많은 경우, 분명한 제약이 오히려 실제 요구에 더 가깝게 만듭니다. 우회가 줄어들기 때문입니다.

### 2. “너무 많이 바꾸지 마”도 제약이다

너무 모호합니다.

더 유용한 예:

- `src/content/docs/...`만 수정
- 컴포넌트를 바꾸지 않음
- 인터페이스를 바꾸지 않음
- 의존성을 설치하지 않음

### 3. 제약은 고위험 작업에만 필요하다

작은 작업에도 필요합니다. 모호한 요구를 흘리듯 말하면 스스로 범위를 키우기 쉽습니다.

## 쓸 만한 작성법

어떻게 쓸지 모르겠다면, 먼저 이 골격을 쓰세요.

```text
제약:
- 【디렉터리/파일】만 수정
- 【컴포넌트 / API / 데이터베이스 / 설정】을 바꾸지 말 것
- 의존성을 추가하지 말 것
- 정보가 부족하면 먼저 묻고, 추측하지 말 것
```

## 제약을 더 자세히 써야 할 때

다음 경우에는 제약을 분명히 적는 편이 좋습니다.

- 레거시가 많은 오래된 프로젝트
- 부분 패치만 원할 때
- 팀이 스타일·아키텍처에 강한 요구가 있을 때
- 권한, 네트워크, 의존성 설치가 관련될 때

목표는 Codex에게 무엇을 할지 말하고, 제약은 어디까지 할지 말합니다.

권한 경계는 제약과 함께 써서 “손쉬운” 월권을 줄이세요. 관련 페이지: [완료 기준 정의](/prompts/define-done/), [권한과 샌드박스](/guide/permissions-and-sandbox/).
