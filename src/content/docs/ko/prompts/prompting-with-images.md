많은 “보고 일하기” 실패는 모델이 못 봐서가 아니라, 이미지만 주고 **무엇을 보라고 할지**를 말하지 않아서입니다.

이미지 프롬프트의 핵심은 Codex가 다음 셋을 세우게 하는 것입니다.

1. 이 이미지가 무엇인지
2. 어디를 주목하길 원하는지
3. 출력이 최종적으로 어떤 작업에 쓰일지

## 이미지 프롬프트가 맞는 장면

| 장면 | 이미지의 역할 |
|---|---|
| UI 버그 조사 | 이상 위치와 상태를 보여 줌 |
| 디자인 복원 | 레이아웃, 계층, 간격, 분위기 참고 |
| 문서용 스크린샷 설명 | 인터페이스를 바탕으로 설명·튜토리얼 작성 |
| 화이트보드/흐름도 정리 | 손그림을 구조화된 설명으로 변환 |
| 현재 vs 기대 비교 | 요구를 추측하지 않고 차이를 식별 |

초점이 “외형·위치·시각 상태”라면 이미지가 긴 글보다 효과적인 경우가 많습니다. 초점이 “비즈니스 규칙”이라면 이미지는 보조 증거에 가깝습니다.

## 이미지 프롬프트의 네 단락 구조

텍스트 프롬프트처럼 구조화하는 것을 권장합니다.

### 1. 이미지 정체

이미지가 무엇인지, 어디서 왔는지 말합니다.

예:

```text
이것은 현재 프로덕션 로그인 페이지 스크린샷이며, iPhone 14 Safari에서 캡처했습니다.
```

### 2. 주목 영역

어디를 보라고 분명히 말하세요. “알아서 문제를 찾아”로 끝내지 마세요.

예:

```text
하단 버튼과 입력 필드 사이 간격, 그리고 키보드가 올라온 뒤 레이아웃 변화를 중점적으로 보세요.
```

### 3. 작업 목표

분석, 재현, 코드 수정, 설명 작성, 대비표 출력 등 무엇을 할지 말합니다.

예:

```text
먼저 가능한 원인을 분석하고, 당장 코드를 바꾸지 마세요. 가장 관련 있을 법한 프론트엔드 파일 2–3개를 주세요.
```

### 4. 출력 형식

어떤 결과를 원하는지 말해, 추상적인 답변을 피합니다.

예:

```text
출력:
1. 이미지에서 관찰한 현상
2. 가능한 원인
3. 확인할 파일 제안
4. 추가로 필요한 스크린샷
```

## 자주 쓰는 세 가지 템플릿

### 1. 보고 문제 찾기

```text
업로드한 것은 현재 페이지 스크린샷입니다. 빨간 박스 영역을 중점적으로 보세요.
먼저 관찰한 이상을 설명한 뒤, 가능한 원인 2–3개를 나열하세요.
아직 코드를 수정하지 마세요.
```

### 2. 보고 구현하기

```text
업로드한 것은 목표 디자인 시안입니다.
이 이미지를 바탕으로 페이지 구조, 핵심 컴포넌트, 반응형 포인트, 시각 스타일을 요약하세요.
구현을 시작하면 구조와 계층 일치를 우선하고, 기능을 임의로 추가하지 마세요.
```

### 3. 현재 vs 기대 비교

```text
이미지 두 장을 올립니다. 첫 번째는 현재 효과, 두 번째는 기대 효과입니다.
레이아웃, 텍스트 계층, 간격, 인터랙션 암시에서의 차이를 비교하고, 수정 우선순위를 주세요.
```

## 더 정확히 보게 하려면 어떤 글을 보완할까

이미지에는 실행 컨텍스트가 부족한 경우가 많아, 다음 정보가 도움이 됩니다.

- 기기 또는 브라우저
- 현재 상태에 hover / focus / 오류 상태가 포함되는지
- 페이지 스크롤 위치
- “현재 효과”인지 “목표 효과”인지
- 기존 디자인 시스템을 따를지

예: “데스크톱 Chrome은 정상인데 iOS Safari에서만 문제”라는 한 문장이, 스크린샷을 더 올리는 것보다 가치 있는 경우가 많습니다.

## 여러 이미지를 잘 주는 법

### “짝 입력”으로 주기

잘 쓰는 방식:

- 현재 이미지
- 기대 이미지

또는:

- 정상 상태
- 이상 상태

설명 없이 이미지를 한꺼번에 올려 Codex가 순서를 추측하게 하지 마세요.

### 이미지마다 역할을 주기

예:

```text
그림 1: 데스크톱 현재 효과
그림 2: 모바일 현재 효과
그림 3: 디자인 시안 목표 효과
```

대응 관계를 정리하기 쉬워집니다.

## 이미지 프롬프트에서 흔히 하는 실수

### “이대로 해”만 말하기

Codex가 이미지에서 모든 요구를 역추론하려다, 당신이 신경 쓰지 않는 디테일까지 필수로 삼기 쉽습니다.

### 부분만 주고 컨텍스트가 없다

부분 스크린샷은 문제 지점은 보여도, 어떤 페이지 상태인지, 반응형 영향인지, 오버레이 장면인지까지는 못 보여 줄 수 있습니다.

### 디자인 시안을 완전한 명세로 착각하기

시안은 외형을 표현하지만, 데이터 출처·경계 조건·인터랙션 로직까지는 담지 못할 수 있습니다. 비즈니스 규칙은 글로 보완해야 합니다.

### 이미지가 수락을 대체한다고 착각하기

보고 구현해도, 최종적으로는 실제 페이지, diff, 브레이크포인트, 사용성을 봐야 합니다. 이미지는 입력이며, 수락 결과가 아닙니다.

## 실용적인 한 가지 경험

Codex가 “디자인 리뷰처럼 이미지를 보기”를 원한다면, 먼저 **관찰**, 그다음 **판단**, 마지막에 **제안**을 하게 하세요.

예:

```text
먼저 이미지에서 관찰한 현상만 설명하고, 결론을 내리지 마세요.
그다음 가장 가능성 높은 원인을 추정하세요.
마지막으로 수정 방향 제안을 주세요.
```

보통 “고쳐 줘”보다 분명하고, 이후 작업도 이어가기 쉽습니다.
