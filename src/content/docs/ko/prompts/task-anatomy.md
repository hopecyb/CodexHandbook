요구사항이 많아지면 작업 요청도 쉽게 흩어집니다. 자료는 충분해도 원하는 결과, 작업 범위, 인수 기준이 뒤섞이면 Codex가 빈칸을 스스로 채워야 합니다.

이 페이지에서는 바로 재사용할 수 있는 작업 요청서를 제시합니다. 각 항목이 해결하는 문제와 작업 설명을 ‘탐색 → 계획 → 실행 → 검증’의 순환 과정에 연결하는 방법을 살펴봅니다.

## 대상 독자

- Codex를 열어 사용할 수는 있지만 “너무 많이 바꿨다”, “끝까지 하지 않았다”, “결과를 판단하기 어렵다”는 문제를 자주 겪는 사람
- 구두로 전달하던 요구사항을 Agent에게 맡기려는 개발자, 창작자, 팀
- 긴 작업의 범위, 권한, 중단 조건을 정의해야 하는 사람

## 작업 요청의 구성

다음 순서로 정리할 수 있습니다.

- 어떤 결과를 원하는가
- 왜 해야 하는가
- 어떤 자료가 필요한가
- 범위는 어디까지인가
- 완료 여부를 어떻게 판단하는가

순서가 꼭 고정되어야 하는 것은 아닙니다. 다만 이 항목들을 분명히 하면 작업을 더 안정적으로 진행할 수 있습니다.

## 권장 템플릿

```text
목표: …… (최종 산출물은 무엇인가?)
배경: …… (왜 중요한가? 현재 상황은 어떤가?)
입력: …… (관련 파일, 링크, 붙여 넣은 내용)
제약: …… (수정 가능한 범위, 문체, 금지 사항)
인수 기준: …… (확인 가능한 완료 조건)
권한 범위: …… (인터넷 사용, 의존성 설치, 설정 변경 가능 여부)
정보가 부족하면: 추측하지 말고 먼저 질문하세요.
```

![작업 설명에서 검증 가능한 결과까지의 순환 과정](/diagrams/task-execution-loop-ko.svg)

그림 왼쪽의 여섯 항목은 프롬프트를 길게 쓰기 위한 것이 아니라 중요한 공백을 줄이기 위한 것입니다. 작업이 시작되면 검증 증거가 다음 단계를 결정합니다. 통과했을 때만 결과를 전달하고, 통과하지 못했다면 실패 정보를 가지고 작업 설명이나 계획으로 돌아갑니다. 무작정 수정을 이어 가지 않습니다.

## 각 항목의 역할

- **목표:** 행동만 있고 결과는 없는 요청을 방지합니다.
- **배경:** 왜 이 일을 하는지 Codex가 이해하도록 돕습니다.
- **입력:** 꼭 확인해야 할 파일, 링크, 자료를 명확히 전달합니다.
- **제약:** 작업 범위를 넘거나 요청하지 않은 부분까지 수정하지 않도록 합니다.
- **인수 기준:** “끝났는가?”를 확인할 수 있는 질문으로 바꿉니다.
- **권한 범위:** 인터넷 사용, 의존성 설치, 설정 변경 가능 여부를 미리 밝힙니다.

## 흔한 오해

### 1. 모든 항목을 길게 채워야 한다

이 템플릿은 빈칸 채우기 문제보다는 점검표에 가깝습니다. 어떤 작업에는 긴 배경 설명이 필요하지 않습니다. 하지만 항목을 생략하면 그만큼 판단에 쓸 근거도 줄어듭니다.

### 2. 목표와 인수 기준은 같다

두 항목은 역할이 다릅니다.

- **목표**는 얻고 싶은 결과를 말합니다.
- **인수 기준**은 그 결과가 실제로 나왔는지 판단하는 방법을 말합니다.

### 3. 입력에는 가진 자료를 모두 붙여 넣어야 한다

자료는 양보다 관련성이 중요합니다. 반드시 확인해야 할 자료가 무엇인지 분명히 전달하세요.

## 최소 작업 템플릿

우선 사용할 수 있는 짧은 요청만 작성하고 싶다면 다음처럼 줄일 수 있습니다.

```text
목표: 무엇을 어떤 상태로 만들 것인가?
입력: 관련 파일이나 페이지는 어디에 있는가?
제약: 어디만 수정할 수 있고 무엇은 건드리면 안 되는가?
인수 기준: 정말 완료됐는지 어떻게 확인할 것인가?
불확실하면: 먼저 질문하세요.
```

## 모호한 요청을 실행 가능한 작업으로 바꾸기

### 원래 요청

```text
문서 홈페이지를 좀 개선해 주세요.
```

이 문장에는 대상 독자, 수정 가능한 범위, “개선되었다”는 판단 기준이 없습니다. Codex가 결과를 내더라도 범위를 넘었는지 판단하기 어렵습니다.

### 실행 가능한 요청

```text
목표: 문서 홈페이지 첫 화면의 문구를 다시 써서 Codex를 처음 접하는 독자가 30초 안에 이 문서가 무엇이고 어디서 시작해야 하는지 알 수 있게 합니다.
배경: 현재 홈페이지는 독자가 이미 Agent, 컨텍스트, Skill을 이해한다고 가정합니다. 첫 진입 안내가 충분히 직접적이지 않습니다.
입력: src/content/docs/guide/index.md
제약: 이 파일만 수정합니다. 내비게이션, 스타일, 컴포넌트는 바꾸지 않습니다. Agent가 처음 등장할 때 쉬운 말로 한 문장 설명을 덧붙입니다.
인수 기준:
- 첫 화면에서 핸드북의 용도, 대상 독자, 첫 번째 읽기 경로를 분명히 설명합니다.
- 기존 frontmatter와 제목 계층을 유지합니다.
- 설명 없이 새 전문 용어를 추가하지 않습니다.
- pnpm build가 통과합니다.
권한 범위: 사이트의 관련 페이지를 읽을 수 있습니다. 인터넷을 사용하거나 의존성을 설치하거나 Git commit을 만들지 않습니다.
정보가 부족하면: 빠진 정보와 수정하려는 범위를 먼저 정리하고 제 확인을 기다리세요.
```

### 예상 실행 과정

1. 먼저 홈페이지와 인접한 진입 페이지를 읽고 현재 문제를 설명합니다.
2. 한 파일에만 적용되는 짧은 계획을 제시합니다.
3. 문구를 수정하고 diff 요약을 보여 줍니다.
4. `pnpm build`를 실행합니다.
5. 네 가지 인수 기준을 하나씩 대조하고 근거를 보고합니다.

## 작업 요청을 점검하는 방법

보내기 전에 스스로 물어보세요.

- 목표가 결과를 설명하는가, 아니면 “개선”, “처리”, “살펴보기” 같은 동작만 나열하는가?
- 입력에 실제로 관련 있는 파일과 자료만 포함했는가?
- 제약에 건드리면 안 되는 내용을 명시했는가?
- 다른 사람도 인수 기준을 보고 ‘통과 / 실패’를 판단할 수 있는가?
- 인터넷 사용, 의존성 설치, 외부 시스템에 쓰기, 코드 커밋에 사전 승인이 필요한가?
- 정보가 부족할 때 Agent는 먼저 질문하고, 조사하고, 아니면 멈춰야 하는가?

작업 규모에 맞춰 템플릿을 줄일 수는 있습니다. 다만 항목 하나를 빼면 그에 해당하는 판단 근거도 줄어듭니다. 파일 하나의 오타를 고칠 때 긴 배경은 필요하지 않지만, 여러 모듈을 옮기는 작업을 목표 한 문장만으로 설명할 수는 없습니다.
