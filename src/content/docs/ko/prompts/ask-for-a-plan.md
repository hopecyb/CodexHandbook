많은 문제는 할 수 없어서가 아니라, **너무 빨리 시작해서**입니다. “고쳐 줘” 한 마디는 탐색·계획·실행을 한꺼번에 섞기 쉽고, 결국 diff를 수동으로 검수하게 됩니다.

이때 더 효과적인 방법은, 요구를 계속 늘리기보다 먼저 계획을 받는 것입니다.

## 언제 반드시 먼저 계획을 받을까

| 상황 | 이유 |
|---|---|
| 여러 파일·모듈에 걸침 | 관련 없는 영역을 건드리기 쉬움 |
| 코드베이스가 낯섦 | 이해한 범위를 먼저 확인 |
| 요구가 아직 흔들림 | 이견을 먼저 드러냄 |
| 승인 후 실행이 필요함 | “실행 권한”과 “방향 논의”를 분리 |
| 고위험 동작이 포함됨 | 롤백·검증 방안을 먼저 확인 |

작은 오타나 한 줄 카피 수정에는 정식 계획이 필수는 아닙니다. 다만 “잘못되면 골치 아프다”고 느껴지면, 잠시 멈추고 계획을 받는 편이 낫습니다.

## 좋은 계획에 최소한 들어갈 것

최소 구성도 다음 네 가지를 덮어야 합니다.

1. 단계
2. 관련 파일 또는 범위
3. 위험 또는 확인 대기 항목
4. 각 단계의 검증 방법

4번이 없으면 “할 일 목록”에 가깝고, 수락 가능한 계획이라고 보기 어렵습니다.

## 자주 쓰는 세 가지 말법

### 초간단판

```text
아직 코드를 바꾸지 마세요. 먼저 3–5단계 계획을 주고 주세요. 어떤 파일을 고칠지, 각 단계를 어떻게 검증할지 포함하세요.
```

적합한 경우: 대략적 방향은 알고 있고, 어떻게 나눌지만 보고 싶을 때.

### 권장판

```text
아직 실행하지 마세요. 현재 저장소를 기준으로 먼저 계획을 주세요. 포함 내용:
1. 목표 이해
2. 단계 번호
3. 관련 파일 또는 디렉터리
4. 위험과 확인 대기 항목
5. 검증 방법

제가 “계획대로 실행”이라고 답하기 전까지 파일을 수정하지 마세요.
```

적합한 경우: 일상 개발, 문서 개편, 프롬프트 재작성, 설정 조정.

### 고위험판

```text
아직 변경하지 마세요. 먼저 계획을 만들고, 다음을 따로 적어 주세요.
- 어느 단계가 회귀를 가장 잘 일으키는지
- 실패 시 어떻게 롤백할지
- 어떤 작업에 제 확인이 필요한지
- 어떤 테스트나 수동 점검으로 완료를 증명할지
```

적합한 경우: 프로덕션 이슈, 권한 설정, 자동화 스크립트, 모듈 간 리팩터.

## 계획은 길수록 좋지 않다

필요한 것은 **승인·궤도 수정·실행**이 가능한 중간 산출물이지, 긴 제안서가 아닙니다.

계획이 쓸 만한지 보려면 다음 세 가지를 확인하세요.

- “2단계는 하지 말고 다른 것으로 바꿔”라고 분명히 말할 수 있는가
- 어떤 핵심 영역을 건드릴지 한눈에 보이는가
- 시작 전에 어떻게 수락할지 알 수 있는가

안 되면 계획이 아직 구체적이지 않은 것입니다.

## 계획을 어떻게 승인할까

전체를 다시 쓸 필요는 없습니다. 동료에게 방향을 주듯 말하면 됩니다.

자주 쓰는 유도 문장:

```text
1·2단계는 유지하고, 3단계는 빼세요.
데이터베이스 변경은 별도 단계로 나누세요.
지금은 읽기 전용 분석만 하고, 구현으로 들어가지 마세요.
계획에 회귀 테스트와 롤백 방안을 추가하세요.
```

“처음부터 다시”보다 컨텍스트를 아끼고, 결과를 궤도에 되돌리기도 쉽습니다.

## “바로 시작”과 비교한 이점

| 먼저 계획 | 바로 시작 |
|---|---|
| 오해를 먼저 발견 | 고친 뒤에야 방향이 틀렸음을 알게 됨 |
| 승인·협업에 유리 | 최종 diff만 수동으로 보게 됨 |
| 하위 작업으로 나누기 쉬움 | 여러 목표가 한 덩어리로 섞이기 쉬움 |
| 검증 방법이 미리 보임 | 끝날 때까지 테스트를 잊기 쉬움 |

많은 워크플로가 “탐색”과 “계획”을 따로 둡니다. [탐색—계획—실행—검증](/cases/workflows/explore-plan-execute-verify/)을 참고하세요.

## 계획에서 흔히 나는 문제

### 동작만 있고 경계가 없다

예: “문서를 업데이트하고 구조를 개선한다”고만 하고, 어떤 디렉터리를 고칠지·어떤 모듈은 건드리지 않을지 없음. 이런 계획은 점점 커지기 쉽습니다.

### 구현만 있고 검증이 없다

예: “컴포넌트 로직 수정, 스타일 업데이트, 코드 커밋”만 있고, 동작이 깨지지 않았음을 어떻게 증명할지 없음.

### 할 일 목록만 있고 확인 대기 항목이 없다

좋은 계획은 불확실성을 인정하며, 모든 전제가 이미 성립한 척하지 않습니다.

## 팀에서 잘 쓰는 약속

`AGENTS.md`에 다음과 같이 명시할 수 있습니다.

```md
- 파일 3개 이상에 걸친 변경은 먼저 계획을 낸다
- 확인 없이 파괴적 명령을 실행하지 않는다
- 계획에는 반드시 검증 방법을 쓴다
```

이렇게 하면 “먼저 계획”이 임시 알림이 아니라 팀 기본값이 됩니다.
