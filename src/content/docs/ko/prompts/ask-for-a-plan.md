계획을 먼저 요청할지는 아직 어떤 결정이 남아 있는지에 달려 있습니다. 범위가 명확하고 되돌리기 쉬운 변경은 바로 실행할 수 있습니다. 진행 경로가 불분명하면 먼저 계획을 세웁니다. 추가 승인이 필요한 구체적인 작업 앞에서는 멈춥니다. 계획을 요청한다는 것이 매 단계마다 사용자 답변을 기다린다는 뜻은 아닙니다.

## 먼저 작업 유형 판단하기

| 유형 | 판단 기준 | 요청할 내용 | 언제 멈출지 |
|---|---|---|---|
| 바로 실행 | 입력, 범위, 완료 기준이 명확하고 변경을 되돌릴 수 있음 | 변경 위치, 완료 조건, 제외 범위를 명시 | 범위를 벗어나거나 필수 정보가 부족할 때 |
| 먼저 계획 | 아키텍처 선택이 있거나 범위가 불분명하거나 여러 단계가 서로 영향을 줌 | 현 상태를 확인한 뒤 경로, 영향, 검증 방법을 제시 | 사용자가 결정해야 할 선택이 있거나 계획을 먼저 검토하겠다고 명시했을 때 |
| 작업에 승인 필요 | 특정 작업이 승인되지 않은 외부 영향을 내거나 실행 권한의 한계에 닿음 | 먼저 검토할 수 있는 결과물을 준비하고 작업, 대상, 영향을 명시 | 그 작업 직전에 멈추되 완료된 준비 작업은 보존 |

“파일이 세 개다”는 보편적인 승인 기준이 아닙니다. 운영 환경 설정 파일 하나도 영향이 클 수 있습니다. 제품의 확인 창과 실제 실행 권한은 [권한과 샌드박스](/ko/guide/permissions-and-sandbox/)를 참고하세요. 이 표를 모든 클라이언트의 권한 설정으로 해석하지 마세요.

## 비교 1: 로컬 문구 수정

작업: README의 오타 두 곳을 수정하고 구조는 바꾸지 않습니다.

**지나치게 자주 멈추는 반례:**

```text
파일을 읽기 전에 계획을 세우고 내 승인을 기다리세요.
읽은 다음에는 수정할 두 곳을 보여 주고 다시 승인을 기다리세요.
한 곳을 고칠 때마다 멈춰서 묻고, 그다음 검사를 할지도 물으세요.
```

이런 대기는 필요한 결정을 더하지 않고, 이미 명확히 승인된 작업만 잘게 나눕니다.

**범위가 명확한 요청:**

```text
README.md 본문에 있는 “帐户” 두 곳을 “账户”로 바꾸세요.
코드 블록, 링크, 다른 내용은 유지하세요. 바로 수정하고 diff를
확인한 뒤 어디를 바꿨는지 보고하세요. 실제 일치 항목이 두 곳이
아니라면 먼저 차이를 설명하고, 문서 전체 교정으로 확대하지 마세요.
```

완료 기준은 정확한 두 곳의 수정과 관련 없는 내용의 보존입니다. 이런 변경에는 보통 새 테스트가 필요하지 않으며, 프로젝트의 기존 규칙에 맞춰 적절히 확인하면 됩니다.

## 비교 2: 사이트 수정 후 게시

작업: 튜토리얼 세 편을 업데이트하고 운영 사이트에 게시합니다. 콘텐츠 준비와 게시의 영향을 분리해야 합니다.

**승인 범위가 불분명한 반례:**

```text
먼저 계획을 작성하고, 웹사이트 전체를 고쳐서 운영 환경에 게시하세요.
```

어떤 콘텐츠를 바꿀지, 어디에 게시할지, 현재 운영 버전을 교체해도 되는지 명시하지 않았습니다.

**구체적인 경계를 제시한 요청:**

```text
이 튜토리얼 세 편을 업데이트하고 관련 내부 링크를 고치세요.
현 상태를 읽고 짧은 계획을 제시한 다음, 이 파일들과 관련 탐색
메뉴 안에서 수정, 빌드, 미리보기 확인까지 단계마다 기다리지 말고
계속 진행하세요. 미리보기, 변경 요약, 검증 결과를 제출하세요.
운영 환경 게시는 아직 승인하지 않았습니다. 준비가 끝나면 게시할
버전, 대상 환경, 되돌리는 방법을 제시하고 게시 작업에 대한
내 확인을 기다리세요.
```

이 경우 로컬 작업을 먼저 마친 뒤 마지막 게시 승인을 요청해야 합니다. 사용자가 구체적인 게시 대상과 작업을 이미 명시적으로 승인했다면 현행 정책에 따라 계속할 수 있는지 판단하세요. 이 예시 문장에 확인 요청이 있다는 이유만으로 같은 승인을 다시 요구하지 마세요.

위 두 비교는 교육용 설계 사례이며, 실제 모델 출력이나 효율 측정 결과가 아닙니다.

## 계획만 세우는 경우

아직 방안을 비교하고 있거나 예산 결정을 내려야 하거나 설계를 먼저 검토하겠다고 명시한 경우에는 계획만 요청할 수 있습니다.

```text
이번에는 방안만 만드세요. 기존 구현을 읽고 두 가지 선택지,
영향 범위, 검증 방법을 제시하세요. 정말로 내가 결정해야 하는
절충안을 짚고 구현은 수정하지 마세요. 방안이 정해진 뒤 실행하세요.
```

이렇게 단계가 명시적으로 제한되었다면 따라야 합니다. 에이전트에게 평소 자율성이 있다고 해서 구현 단계로 넘어갈 수는 없습니다.

## 계획에 남겨야 할 내용

충분한 계획에는 목표, 영향 범위, 단계, 검증, 미해결 선택을 적습니다. 이미 답이 있는 사항을 확인 대기 질문으로 만들 필요는 없습니다. 위험이 낮은 짧은 작업에도 서식에 맞추려고 되돌리기 절을 넣을 필요는 없습니다.

실행 중 새 상황이 생기면 일반적인 구현 세부 사항과 목표 변경을 구분합니다. 원래 범위에서 해결할 수 있는 작은 문제는 처리하고 설명합니다. 새 의존성, 변경 범위 확대, 인터페이스 변경, 새로운 외부 작업이 나타나면 먼저 기존 승인 범위에 포함되는지 판단합니다.

## 프로젝트 규칙에 넣을 수 있는 기본 원칙

```md
- 범위가 명확하고 되돌릴 수 있는 작업은 바로 수행하고 적절히 검증한다.
- 복잡한 작업은 먼저 짧은 계획을 제시한다. 사용자가 먼저 검토하겠다고
  했거나 반드시 결정해야 할 선택이 있을 때만 답변을 기다린다.
- 승인된 범위에서는 단계마다 확인을 반복하지 않고 계속 진행한다.
- 필수 정보가 부족하거나 범위를 벗어나거나 승인되지 않은 작업이
  필요하면 구체적인 문제를 설명한다.
- 로컬 수정 완료를 게시, 메시지 전송, 데이터 삭제의 자동 승인으로
  간주하지 않는다.
```

이는 조정 가능한 작업 방식의 제안이며 시스템 규칙, 조직 정책, 샌드박스를 대체하지 않습니다. [컨텍스트 우선순위](/ko/guide/context/context-priority/), [계획](/ko/guide/agent-work/planning/), [사람의 승인 패턴](/ko/cases/workflows/human-approval-patterns/)도 참고하세요.
