장시간 작업이 흔히 실패하는 방식은 다음과 같습니다.

- 한 번에 너무 많이 하기
- 중간에 체크포인트가 없음
- 스레드가 길어지며 앞뒤 제약이 서로 충돌하기 시작함

장시간 작업의 핵심은 프롬프트를 더 길게 쓰는 것이 아니라, 체크포인트가 있는 작은 단계들로 나누는 것입니다.

장시간 작업은 단계로 나누고, 단계마다 수락을 둡니다.

```text
단계 1: 조사만 하고 방안을 나열(코드 수정 금지)
단계 2: 최소 변경 구현
단계 3: 테스트 보완 및 실행……
각 단계가 끝나면 멈추고 제 확인을 기다리세요.
```

## 왜 장시간 작업이 특히 이탈하기 쉬운가

한꺼번에 여러 종류의 일을 담기 때문입니다.

- 문제 이해
- 방안 설계
- 변경 구현
- 검증 실행
- 인수인계 작성

이 모두를 “한 번에 끝내기”로 섞으면 위험이 크게 올라갑니다.

## 흔한 오해

### 1. 장시간 작업은 짧은 작업을 더 자세히 쓴 것뿐이다

장시간 작업에는 **단계 관리**가 더 필요하며, 배경을 더 쓰는 것만으로는 부족합니다.

### 2. 단계만 나열하면 충분하다

각 단계에는 분명한 출구가 있는 편이 좋습니다. 예:

- 방안만 내고 코드는 수정하지 않음
- 최소 구현만 함
- 테스트와 검증만 보완함

### 3. 한 스레드로 끝까지 가는 것이 항상 낫다

작업이 너무 길면 인수인계·요약·새 스레드로 이어가기가 더 분명한 경우가 많습니다.

## 쓸 만한 분할 사고

장시간 작업을 만나면, 먼저 이 네 단계로 나누어 보세요.

1. 조사: 문제를 이해하고 손대지 않음
2. 계획: 단계, 위험, 검증을 나열
3. 실행: 최소 변경
4. 검증: 점검 실행, 결론 작성, 인수인계 준비

## 더 실용적인 작성법

```text
단계 1: 먼저 조사하고 방안을 나열. 코드 수정 금지. 제 확인을 기다릴 것
단계 2: 최소 변경만. 끝나면 영향 범위를 보고
단계 3: 검증을 보완하고 관련 점검을 실행
단계 4: 변경, 위험, 후속 제안을 요약
```

더 나은 방식은 한 번에 끝내기보다, 각 단계에서 멈춰 점검할 수 있게 하는 것입니다.
