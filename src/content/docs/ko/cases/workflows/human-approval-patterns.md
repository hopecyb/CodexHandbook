승인은 구체적인 행동과 그 영향에 맞춰야 합니다. 작업 권한은 사용자가 무엇을 완료하길 원하는지, 도구 승인은 현재 환경에서 특정 행동을 실행할 수 있는지를 정합니다. 파일 쓰기, 명령 실행, 네트워크 접속이 언제나 매번 질문을 요구하는 것은 아닙니다. 실제 동작은 허가 범위, 도구 정책, 샌드박스에 따라 달라집니다. [공식 안내](https://learn.chatgpt.com/docs/agent-approvals-security)를 보세요.

## 명확히 선택할 수 있는 세 가지 협업 방식

| 방식 | 계속할 수 있는 일 | 기다려야 할 때 |
|---|---|---|
| 읽기 전용 분석 | 읽고 비교해 방안 만들기 | 사용자가 구현을 허가하지 않았다면 수정하지 않음 |
| 허가 범위 내 구현 | 지정 범위 수정, 적절한 검증, 검토 가능한 결과 준비 | 필수 정보가 없거나 범위가 바뀌거나 새 미승인 행동이 필요함 |
| 마지막 행동 별도 승인 | 초안, 빌드, 미리보기, 복구 준비 완료 | 게시, 전송 또는 명시적으로 유보한 행동 앞 |

이는 협업 약속이지 새 제품 모드의 이름이 아닙니다. 명확히 부여된 유효한 권한을 다시 요구하지 마세요. 강제 정책이 대화형 승인을 요구하면 해당 절차를 따릅니다.

## 방식 1: 이번에는 방안만 제시

```text
이번에는 읽기 전용으로 프로젝트를 살펴보고 변경 방안을 제시하세요. 코드를 수정하거나 커밋하지 마세요.
검사가 캐시, 스냅샷, 출력 파일을 쓴다면 먼저 설명하세요. 모든 “테스트”가 읽기 전용이라고 가정하지 마세요.
```

목표가 확정되지 않아 대안을 비교할 때 적합합니다. 읽기 전용 작업에서도 명령의 실제 부작용을 확인해야 합니다. “테스트 실행 가능”과 “디스크에 아무것도 쓰지 않음”을 확인 없이 함께 요구하지 마세요.

## 방식 2: 로컬 작업을 연속해서 완료

```text
이 문서 세 개와 관련 내부 링크를 수정하고 기존 빌드 검사를 실행해도 됩니다.
그 범위에서 매 단계 기다리지 말고 일을 완료하세요. 일반적인 구현 세부 사항은 직접 처리하고 보고하세요.
사이트를 게시하거나 메시지를 보내지 마세요. 필요한 선택이나 범위 밖 행동은 먼저 설명하세요.
```

여기서는 수정과 검증이 이미 허가되어 있어 파일을 쓸 때마다 다시 확인할 필요가 없습니다. 특정 명령의 허용 여부는 여전히 실행 환경에 달려 있으며 프롬프트로 거부를 우회할 수 없습니다.

## 방식 3: 특정 게시 행동 승인

먼저 검토할 수 있는 버전을 완성하고 다음을 제시하세요.

- 게시할 정확한 버전이나 산출물과 검증 결과.
- 대상 환경, 수신자 또는 영향받는 대상.
- 예상되는 외부 효과와 필요한 복구 방법.
- 아직 부족한 권한이나 조건.

“이 버전을 시험 사이트에 게시”하라는 허가는 미래의 모든 버전을 운영 사이트에 게시하라는 허가가 아닙니다. 반대로 동일한 행동이 이미 명확히 승인되었다면 일반 템플릿 때문에 다시 묻지 마세요.

## 거부된 후 계속하기

원래 거부 내용을 보존하고 권한 부족, 정책 금지, 환경 실패를 구별하세요. 작업에 여전히 유효한 더 좁은 방법이 있으면 계속합니다. 도구를 바꾸거나 명령 표기 또는 프롬프트를 바꿔 같은 제한을 우회하지 마세요. 사용자 조치가 정말 필요하면 막힌 행동, 이유, 가능한 다음 단계를 설명하세요.

## 검토자가 확인할 것

범위와 결과가 맞는지, 검증을 실제로 했는지, 외부 영향을 이해했는지 확인합니다. 계획이 있다고 자동 승인되는 것은 아니며 “발견 없음”이 위험 제로를 보장하지도 않습니다.

작업 방식은 [작업 분류](/ko/prompts/ask-for-a-plan/), 지침 충돌은 [컨텍스트 우선순위](/ko/guide/context/context-priority/)를 보세요. 무인 워크플로에는 [중지, 실패, 알림 메커니즘](/ko/skills/automations/scheduled-tasks/)도 필요합니다.
