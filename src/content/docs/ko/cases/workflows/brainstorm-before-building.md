**먼저 브레인스토밍한 뒤 손대기**는 목표가 모호하고 방안이 둘 이상인 작업에 적합합니다: 새 기능, 개편, 콘텐츠 주제, 기술 선정. [탐색—계획—실행—검증](/cases/workflows/explore-plan-execute-verify/)의 ①탐색 단계와 이어지지만, 코드를 바로 읽고 파일을 고치기보다 **발산과 수렴**을 더 강조합니다.

## 이 글이 해결하는 문제

- 언제 먼저 brainstorm할지, 언제 바로 EPXV할지
- 발산 범위를 어떻게 제한해 공허한 대화를 피할지
- 산출물: 옵션 표, 결정 기록, 다음 계획

## 누구에게 적합한가

| 시나리오 | 예시 |
|---|---|
| 제품/기능 | 「사용자에게 내보내기 기능을 추가하고, UI가 세 가지」 |
| 콘텐츠 | 「이 튜토리얼은 누구를 대상으로, 구조를 어떻게 나눌지」 |
| 기술 | 「예약 작업에 큐를 쓸지 cron을 쓸지」 |

## 최소 실행 방법

**단계 A — 발산(시간 제한)**

```text
먼저 어떤 파일도 수정하지 마세요. 「CSV보내기」요구에 대해 구현 경로 3가지를 나열하세요:
각 경로의 장단점, 관련 모듈, 예상 작업량(S/M/L)을 쓰세요.
최종 방안은 고르지 마세요.
```

**단계 B — 수렴**

```text
위 표를 바탕으로 기본 방안 1개와 대안 1개를 권장하세요.
내가 확인해야 할 결정점 2개(형식, 권한)를 설명하세요.
```

**단계 C — 계획으로 진입**

확인 후 [스펙 주도](/cases/workflows/specification-driven-work/) 또는 EPXV의 ②계획으로 이어갑니다.

## 권장 워크플로

```text
제약 명확화(시간, 기술 스택, 변경 불가 부분)
    → 옵션 3–5개 발산(코드 작성 금지)
    → 「가치 / 위험 / 비용」으로 정렬
    → 사람이 방향을 고르거나 정보 보완을 요청
    → 서면 계획 + 실행
```

**타임박스**를 둡니다: 예로 15분 안에 발산을 끝내 토론이 표류하지 않게 합니다.

## 흔한 실수

- brainstorm를 실행으로 착각해 모델이 이미 파일을 고침—「먼저 수정하지 마세요」로 제약
- 옵션이 너무 많고 정렬이 없어 결정 피로
- 기각한 방안을 기록하지 않아 2주 뒤 같은 논쟁 반복
- 제약을 건너뛰어 방안은 아름답지만 실행 불가

## 보안 경계

- 브레인스토밍 단계에서도 민감 파일을 읽을 수 있습니다—`@`로 범위를 정확히 지정하세요
- 컴플라이언스·프라이버시가 걸린 방안은 사람이 법무/보안 검토해야 하며, 모델만으로 결정할 수 없습니다

## 인수 체크리스트

- [ ] 실행 가능한 옵션이 최소 2개와 명확한 권장이 있음
- [ ] 결정점이 표시되어 사람 확인을 기다림
- [ ] 승인되지 않은 저장소 쓰기가 없음
- [ ] 다음 단계가 서면 계획으로 이어질 수 있음
