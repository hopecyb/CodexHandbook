**스펙 주도**는 파일을 대량으로 고치기 전에 짧은 스펙을 준비해 목표, 범위, 인터페이스, 인수 기준을 밝히는 방식입니다. [브레인스토밍](/cases/workflows/brainstorm-before-building/) 뒤에 이어질 수도 있고, 이미 명확해진 요구와 함께 [EPXV](/cases/workflows/explore-plan-execute-verify/)로 바로 들어갈 수도 있습니다.

## 이 페이지의 초점

- 스펙을 얼마나 자세히 써야 충분한지
- Codex가 스펙대로 실행하고 scope를 마음대로 늘리지 않게 하는 방법
- 스펙과 PR 설명, issue의 관계

## 최소 실행 스펙 템플릿

```markdown
## 목표
한 문장의 사용자 가치

## 범위
- 포함: …
- 제외: …

## 인터페이스/동작
- 입력 / 출력 / 오류 상황

## 인수 기준
- [ ] 자동 검증 가능한 항목
- [ ] 사람 검사가 필요한 항목

## 제약
- 변경 불가 모듈, 성능, 호환성
```

템플릿을 저장소 `docs/specs/` 또는 issue 본문에 두고, 작업에서 `@`로 참조할 수 있습니다.

## 권장 워크플로

```text
① 스펙 초안(Codex가 도울 수 있음, 사람이 검토)
② 스펙 확인 → 「스펙대로 실행」이라고 답함
③ 단계별 실행, 각 단계를 인수 항목과 대조
④ 스펙 변경은 반드시 버전 또는 changelog를 명시적으로 갱신
```

프롬프트 예시:

```text
@docs/specs/export-csv.md 를 읽으세요. 먼저 스펙에 맞춰 구현 계획과 위험을 나열하세요.
스펙에 없는 기능은 추가하지 마세요. 내가 확인한 뒤에 코드를 쓰세요.
```

## 테스트 주도와의 협력

스펙의 인수 항목은 가능한 한 **테스트 가능**해야 합니다. 테스트로 쓸 수 있는 것은 먼저 테스트를 쓰세요. [테스트 주도 작업](/cases/workflows/test-driven-work/)을 참고하세요.

## 흔한 실수

- 스펙이 설계 문서처럼 길어 핵심 제약을 찾기 어려움
- 실행 중 범위가 슬며시 커졌는데 스펙을 갱신하지 않음
- 인수 기준이 모호함(「더 쓰기 좋게」)으로 논쟁 유발
- 스펙과 `AGENTS.md` 아키텍처 약속이 충돌

## 보안 경계

- 스펙에 「외부 API 호출 허용」이 명시된 경우에만 네트워크 관련 구현을 허가합니다
- PII 필드 처리는 스펙에 반드시 표시해야 합니다

## 인수 체크리스트

- [ ] 범위 밖 사항이 명확히 제외됨
- [ ] 검사 가능한 인수 기준이 최소 3개
- [ ] 실행 전에 사람 또는 서면 확인이 있음
- [ ] 변경이 스펙 파일에 동기화됨
