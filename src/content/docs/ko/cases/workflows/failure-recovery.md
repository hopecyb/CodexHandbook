**실패 복구**는 작업이 빗나가거나 중단된 뒤, 현장을 수습하고 다시 앞으로 나아가는 방법을 다룹니다. 이 장은 반복 가능한 **감지 → 손실 차단 → 복구 → 회고** 단계를 제시하며, [취소와 복구](/guide/getting-started/undo-and-recover/) 및 [긴 작업 관리](/cases/workflows/long-running-task-management/)와 함께 쓸 수 있습니다.

## 이 페이지의 초점

- 언제 `git stash`, commit 되돌리기, 새 스레드를 열지
- 실패 정보를 다음 라운드 프롬프트에 어떻게 정리할지
- 팀이 재발 문제를 어떻게 기록할지

## 실패 신호

| 신호 | 가능한 동작 |
|---|---|
| 테스트가 대량 실패 | 실행을 멈추고 diff를 축소 |
| 잘못된 디렉터리/브랜치를 수정 | 취소하고 올바른 경로를 다시 `@` |
| 계획과 구현이 크게 어긋남 | 탐색 또는 계획 단계로 복귀 |
| 컨텍스트가 너무 길고 제약을 잊음 | 새 스레드 + 요약 인수인계 |
| 승인/규칙이 반복 거절 | 규칙과 작업이 모순인지 확인 |

## 최소 실행 복구 흐름

```text
1. 계속 수정을 멈춤(「먼저 코드를 쓰지 마세요」라고 명시)
2. 현황 저장: git status / stash / thread ID 기록
3. 5개 이내로 요약: 목표, 한 일, 실패 현상, 가설
4. 선택: 되돌리기 / 범위 축소 / 새 스레드로 계속
5. 성공 후 AGENTS.md 또는 사례 회고에 기록
```

프롬프트 예시:

```text
현재 변경으로 테스트 12개가 실패했습니다. 먼저 계속 고치지 마세요.
최근 commit 3개가 영향을 준 파일을 나열하고, 최소 되돌리기 지점을 제안하며,
더 작은 수정 계획을 주세요.
```

## 권장 워크플로

```text
감지(테스트/사람/CI)
    → 손실 차단(쓰기 중단, 브랜치 격리)
    → 진단(「먼저 진단한 뒤 수정」참고)
    → 작은 걸음으로 재시도
    → 회고 정착
```

여러 Agent 시나리오는 [여러 Agent 협업](/cases/workflows/multi-agent-coordination/)을 참고하세요. 실패 시 어느 하위 작업이 롤백을 담당할지 명확히 해야 합니다.

## 흔한 실수

- 잘못된 방향으로 「조금만 더」패치를 쌓음
- 실패 로그를 저장하지 않아 새 스레드에서 같은 오류 반복
- `git push`를 강제해 상황을 만회하려 함
- 환경(로컬 vs Cloud)을 구분하지 않아 복구 단계가 무효

## 보안 경계

- 복구 작업 자체도 [명령 규칙](/guide/customization/rules/command-rules/)의 제약을 받습니다
- 프로덕션 사고는 먼저 롤백한 뒤 근본 원인을 분석하고, Agent가 프로덕션에 직접 연결해 데이터를 고치게 하지 마세요

## 인수 체크리스트

- [ ] 이번에 선택한 복구 전략과 이유를 설명할 수 있음
- [ ] 저장소가 빌드/테스트 가능한 상태로 돌아옴
- [ ] 실패 원인과 교훈이 기록됨(issue 또는 AGENTS.md)
- [ ] 새 스레드가 필요하면 핵심 제약 요약이 있음
