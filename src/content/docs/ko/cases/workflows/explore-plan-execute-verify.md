이 핸드북이 권장하는 기본 워크플로이며, 「아직 어떻게 할지 모름」에서 「병합해도 됨」까지 이어 가기에 적합합니다.

## 네 단계 개요

```text
① 탐색 Explore   → 현황, 범위, 위험을 파악
② 계획 Plan      → 단계, 파일, 인수 기준(큰 작업은 확인 필요)
③ 실행 Execute   → 코드/문서/설정 수정, 작은 걸음으로 커밋
④ 검증 Verify    → 테스트, diff 검토, 「완료 정의」대조
```

①②를 건너뛰고 바로 ③으로 가지 마세요. 그렇게 하면 「추측 수정」이 되기 쉽습니다. [먼저 진단한 뒤 수정](/cases/workflows/diagnose-before-fixing/)을 참고하세요.

## ① 탐색

**목표:** 먼저 현황을 분명히 한 뒤, 어떻게 고칠지 결정합니다.

프롬프트 예시:

```text
먼저 코드를 수정하지 마세요. @src/auth/ 와 관련 테스트를 읽고, 목록으로 설명하세요:
1. 현재 로그인 흐름
2. Safari 레이아웃 bug와 관련될 수 있는 파일
3. 불확실해서 내가 확인해야 할 한 가지
```

산출물: 문제 진술, 영향 범위, 확인 필요 항목.

## ② 계획

**목표:** 검토 가능한 단계 목록.

```text
방금 탐색을 바탕으로 계획을 주세요: 단계 번호, 관련 파일, 각 단계 검증 방법.
내가 「계획대로 실행」이라고 답하기 전에는 코드를 쓰지 마세요.
```

큰 작업이나 고위험 변경은 먼저 확인을 기다립니다. 작은 작업은 「계획이 3단계 이하면 자동 실행」을 약속한 뒤 [AGENTS.md](/guide/customization/agents-md/writing-effective-instructions/)에 적을 수 있습니다.

## ③ 실행

**목표:** 변경을 작은 걸음으로, 되돌릴 수 있게 유지합니다.

- 한 번에 하위 목표 하나에 집중
- 테스트가 덮을 수 있는 경로를 우선 수정
- 계획 밖 문제가 나오면 **②로 돌아가고** 억지로 밀고 나가지 않음

유도 문구: 「2단계를 실행하세요. 계획을 바꿔야 하면 먼저 멈추고 설명하세요.」

## ④ 검증

**목표:** 「완료 정의」가 충족되었음을 증명합니다.

| 검증 유형 | 방법 |
|---|---|
| 자동 | 단위 테스트, lint, 타입 검사 |
| 사람 | diff 읽기, 핵심 경로 수동 테스트 |
| 산출물 | 스크린샷, 로그 조각, API 응답 |

관련 체크리스트는 [완료 정의](/prompts/define-done/)와 [테스트 실행하기](/guide/quality/run-tests/)를 참고하세요.

## 작업 규모에 맞게 줄이기

| 규모 | 탐색 | 계획 | 실행 | 검증 |
|---|---|---|---|---|
| typo 수정 | 생략 가능 | 구두 1단계 | 짧음 | lint |
| 단일 파일 bug | 가벼움 | 3–5단계 | 중간 | 테스트+diff |
| 교차 모듈 기능 | 필수 | 서면 계획+확인 | 단계별 | 전체 테스트+수동 테스트 |
| 프로덕션 사고 | 진단 우선 | 롤백 방안 먼저 | 극소 걸음 | 모니터링+회고 |

## 흔한 실수

- 계획을 머릿속에만 두고 실행 단계에서 빗나감
- 검증을 「돌아가는 것 같음」만으로 끝냄
- 탐색 부족으로 잘못된 모듈을 수정
