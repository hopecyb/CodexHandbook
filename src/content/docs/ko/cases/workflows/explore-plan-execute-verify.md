이 핸드북이 권장하는 작업 구성 방식으로, '아직 어떻게 할지 모름'에서 '검수 가능'까지 이어집니다. 네 단계가 네 번의 승인을 뜻하지는 않습니다. 범위가 명확한 작은 작업은 연속해서 완료할 수 있습니다. 방법이 정해지지 않았거나 필요한 권한이 없을 때 해당 결정을 기다립니다. 먼저 [작업 수준 나누기](/ko/prompts/ask-for-a-plan/)를 보세요.

## 네 단계 개요

```text
① 탐색 Explore   → 현황, 범위, 위험 파악
② 계획 Plan      → 단계, 파일, 인수 기준, 필요한 선택 정리
③ 실행 Execute   → 승인된 범위에서 코드/문서/설정 수정
④ 검증 Verify    → 테스트, diff 검토, 완료 정의와 대조
```

현황이 불명확하면 추측으로 고치지 않도록 먼저 탐색하고 계획하세요. 대상이 분명한 오타 수정은 네 번의 대화로 나눌 필요가 없습니다. [진단 후 수정](/ko/cases/workflows/diagnose-before-fixing/)도 참고하세요.

## ① 탐색

**목표:** 먼저 현황을 분명히 한 뒤, 어떻게 고칠지 결정합니다.

프롬프트 예시:

```text
먼저 코드를 수정하지 마세요. @src/auth/ 와 관련 테스트를 읽고, 목록으로 설명하세요:
1. 현재 로그인 흐름
2. Safari 레이아웃 bug와 관련될 수 있는 파일
3. 불확실해서 내가 확인해야 할 한 가지
```

산출물: 문제 진술, 영향 범위, 확인 필요 항목.

## ② 계획

**목표:** 검토 가능한 단계 목록.

```text
방금 탐색을 바탕으로 계획을 주세요: 단계 번호, 관련 파일, 각 단계 검증 방법.
내가 「계획대로 실행」이라고 답하기 전에는 코드를 쓰지 마세요.
```

위 프롬프트는 '계획만' 요청한다고 명시했으므로 실행은 기다려야 합니다. 구현이 이미 승인됐다면 짧은 계획을 설명한 뒤 합의된 범위에서 실행과 검증을 연속해서 진행하도록 요청할 수 있습니다. 멈출지는 승인 여부, 필요한 선택, 실제 권한에 달렸지 계획 단계 수에 달린 것이 아닙니다.

## ③ 실행

**목표:** 변경을 작고 되돌릴 수 있게 유지합니다.

- 한 번에 하위 목표 하나에 집중
- 테스트가 적용되는 경로를 우선
- 일반적인 구현 세부 사항은 계획을 갱신하고 계속 진행. 전제나 범위가 바뀌면 ②로 돌아가 새로운 결정이 필요한지 판단

안내 문구: “승인된 범위를 계속 완료하세요. 범위를 넓혀야 한다면 구체적 영향과 선택지를 설명하세요.”

## ④ 검증

**목표:** 「완료 정의」가 충족되었음을 증명합니다.

| 검증 유형 | 방법 |
|---|---|
| 자동 | 단위 테스트, lint, 타입 검사 |
| 사람 | diff 읽기, 핵심 경로 수동 테스트 |
| 산출물 | 스크린샷, 로그 조각, API 응답 |

관련 체크리스트는 [완료 정의](/ko/prompts/define-done/)와 [테스트 실행하기](/ko/guide/quality/run-tests/)를 참고하세요.

## 작업 규모에 맞게 줄이기

| 규모 | 탐색 | 계획 | 실행 | 검증 |
|---|---|---|---|---|
| 오타 수정 | 대상 문구 확인 | 암묵적이어도 됨 | 짧게 | diff를 확인하고 프로젝트 규칙에 따라 검증 |
| 단일 파일 버그 | 간단히 | 3～5단계 | 보통 | 테스트 + diff |
| 모듈 간 기능 | 의존성 명확화 | 문서 계획, 필요한 선택은 확인 대기 | 승인 범위에서 단계별로 완료 | 영향에 맞는 테스트 + 수동 점검 |
| 운영 사고 | 진단 우선 | 롤백 방안 우선 | 아주 작은 단계 | 모니터링 + 사후 분석 |

- 검증을 「돌아가는 것 같음」만으로 끝냄
- 탐색 부족으로 잘못된 모듈을 수정
