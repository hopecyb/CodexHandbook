Codex에게 바로 bug를 고치라고 하면 재작업률이 보통 높습니다. 진단 워크플로는 더 강조합니다: **증상 → 가설 → 증거 → 최소 수정**.

## 언제 쓰는가

- 테스트 실패 원인이 불명
- 프로덕션 알림, 사용자 보고 「간헐적」
- 지난번 수정 후에도 문제가 남음

## 단계

### 1. 변경 동결

```text
먼저 비즈니스 코드를 수정하지 마세요. 나열하세요: 재현 단계, 관련 로그, 최근 관련 commit.
```

### 2. 범위 축소

- 이분: 어느 커밋이 도입했는가?
- 격리: 최소 재현 저장소 또는 테스트 케이스

### 3. 가설 형성

Codex에게 다음을 출력하도록 요청합니다:

```text
가설 A: … 검증 방법: …
가설 B: … 검증 방법: …
```

### 4. 가설 검증(읽기 우선)

대상 테스트를 실행하고, 임시 로그를 추가하며(버릴 수 있는 브랜치), 모니터링을 읽습니다.

### 5. 최소 수정

한 번에 근본 원인 하나만 고칩니다. 「겸사 리팩터」를 피합니다.

### 6. 회귀 검증

원래 실패한 케이스 + 인접 시나리오 + 재발을 막는 테스트.

## 프롬프트 템플릿

```text
「먼저 진단한 뒤 수정」에 따르세요:
1. @path/to/failing-test 와 구현을 읽고 실패 원인을 설명하세요(스택 행 번호 인용)
2. 가설 2개와 읽기 전용으로 검증하는 방법을 제시하세요
3. 내가 가설을 확인한 뒤에 수정을 쓰고, 수정 후 관련 테스트만 실행하세요
```

## EPXV와의 관계

진단은 **탐색** 단계의 심화로 볼 수 있습니다. 계획 단계에서는 “가설이 틀리면 어떻게 되돌릴지”도 분명히 적어야 합니다.

## 흔한 실수

- 재현하지 않고 코드를 수정
- 한 patch에 세 문제를 한꺼번에 고쳐 review 불가
- 임시 로그만 지우고 영구 테스트를 보완하지 않음
