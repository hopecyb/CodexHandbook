**출처가 있는 리서치**는 핵심 결론마다 공식 문서, 논문, 저장소 파일 같은 구체 출처로 돌아갈 수 있어야 하며, 근거 없는 판단만 내놓아서는 안 된다고 요구합니다. 기술 선정, 경쟁 제품 비교, 문헌 리뷰, 정책 해석에 적합합니다.

## 이 페이지의 초점

- [웹 검색](/guide/tools/web-search/) vs 저장소만 읽기를 언제 쓸지
- 인용 형식과 불확실성 표시를 어떻게 요구할지
- [출처 검증](/guide/quality/validate-sources/) 단계와 어떻게 맞출지

## 최소 실행 방법

```text
「이 저장소 시나리오에서 Rust와 Go의 적합성」을 조사하세요:
1. 먼저 평가 차원(성능, 생태계, 팀 숙련도)을 나열
2. 각 결론에 출처 URL 또는 @저장소 내 파일 경로를 붙임
3. 검증할 수 없으면 「확인 필요」로 표시
4. 마지막에 권장과 열린 질문을 제시
코드를 수정하지 마세요.
```

## 권장 워크플로

```text
문제와 제외 항목 정의
    → 출처 수집(검색 / 문서 읽기 / MCP)
    → 비교표 + 장단점
    → 신뢰도와 충돌 출처 표시
    → 사람이 결정하거나 스펙 단계로 진입
```

긴 리서치 작업은 여러 라운드로 나눕니다. [긴 작업 관리](/cases/workflows/long-running-task-management/)를 참고하세요.

## 흔한 실수

- URL을 요구하지 않아 산출물을 재검증할 수 없음
- 오래된 블로그와 공식 문서를 섞고 설명하지 않음
- 리서치 결론을 바로 구현 지시로 쓰고 스펙을 건너뜀
- 기밀 데이터가 있는 파일을 미승인 외부 도구로 업로드

## 보안 경계

- 내부 미공개 자료는 통제되지 않는 MCP로 외부에 내보내면 안 됩니다
- 가격, 버전, 지역 가용성 등 변동이 큰 사실은 [검증 날짜](/guide/start-here/handbook-version-policy/)를 표시해야 합니다

## 인수 체크리스트

- [ ] 핵심 결론에 클릭 가능하거나 추적 가능한 출처가 하나 이상 있음
- [ ] 충돌 정보가 나란히 제시됨
- [ ] 「불확실」항목이 나열되어 있고, 사실처럼 위장되지 않음
- [ ] 민감 데이터가 프롬프트나 로그에 나타나지 않음
