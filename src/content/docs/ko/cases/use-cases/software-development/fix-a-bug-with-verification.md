이 문서는 파일 이름만 바꿔 넣는 프롬프트 템플릿이 아닙니다. 저장소의 실제 시작 코드를 실행해 테스트 하나가 실패하는 것을 확인하고, 참고 수정안이 같은 테스트 묶음을 어떻게 통과시키는지 살펴봅니다.

## 메타 정보

| 항목 | 내용 |
|---|---|
| 대상 독자 | 개발자 |
| 클라이언트 | 로컬 저장소에서 사용하는 CLI 또는 IDE |
| 예상 소요 시간 | 25~45분 |
| 사전 지식 | 터미널에서 Node.js 명령을 실행하고 간단한 JavaScript를 읽을 수 있음 |
| 예제 의존성 | Node.js 내장 `node:test`; 별도 패키지 설치 불필요 |
| 검증 날짜 | 2026-08-25 |

## 1. 목표와 배경

**업무 배경:** 장바구니의 `calculateTotal` 함수는 할인율을 백분율로 입력받습니다. 할인이 없을 때는 결과가 맞지만, `10`을 전달해 10% 할인을 적용하려 하면 함수가 `10`을 비율 값으로 그대로 곱해 음수 금액을 반환합니다.

**목표:** 할인 계산 오류의 원인을 찾고 최소한으로 수정한 뒤, 같은 테스트 묶음으로 실패가 통과로 바뀌었음을 입증합니다.

**성공 기준:**

- 시작 코드의 테스트 3개 중 1개가 일관되게 실패하고, 단언 결과에 ‘기대값 36, 실제값 -360’이 나타납니다.
- 수정 후 테스트 3개가 모두 통과합니다.
- 장바구니 API를 다시 작성하지 않고 할인율의 백분율 변환만 수정합니다.
- ‘수정 후 통과’ 기록과 ‘수정 전 실패’ 기록을 함께 보관해야 하는 이유를 설명할 수 있습니다.

**범위 밖:** 금액 정밀도 라이브러리, 세금, 통화 환산, 의존성 업그레이드, UI.

![검증을 동반한 버그 수정 작업 흐름](/diagrams/verified-bug-fix-workflow-ko.svg)

그림에서 중요한 것은 두 되돌아가기 경로입니다. 관련 테스트가 실패하면 최소 수정 단계로 돌아가고, 전체 회귀 검사나 diff 검토가 실패하면 원인 분석으로 돌아갑니다. 서둘러 테스트를 통과시키려고 단언을 삭제하거나 변경 범위를 넓히지 마세요.

## 2. 준비 자료

전체 학습 순서가 필요하다면 [개발자 학습 경로](/ko/guide/learning-paths/developer/)를 참고하세요. 이 실습을 코드 읽기, 검토, 인수인계 템플릿과 연결하며, 별도의 `work/` 사본에서 연습하도록 안내합니다. 새로 추가된 [2026-09-18 실행 요약](/downloads/developer-path/run-record.json)에는 시작 코드와 참고 해법을 다시 검증한 결과가 있습니다. 아래의 2026-08-25는 원래 사례의 검증 날짜입니다.

예제 디렉터리:

```text
examples/complete-workflows/developer/verified-bug-fix/
├── brief.md
├── starter/
│   ├── cart.js
│   └── cart.test.js
├── prompts/
│   ├── 01-explore.md
│   ├── 02-fix-and-verify.md
│   └── 03-review.md
├── solution/
│   ├── cart.js
│   └── cart.test.js
└── validation.md
```

`starter/`는 의도적으로 버그를 남겨 둔 실습 시작점이고, `solution/`은 별도로 실행할 수 있는 참고 해법입니다. 참고 해법을 직접 수정하며 실습하지 마세요.

## 3. 첫 번째 단계: 실패 재현

저장소 루트에서 실행하세요.

```bash
node --test examples/complete-workflows/developer/verified-bug-fix/starter/cart.test.js
```

예상 결과는 명령이 0이 아닌 종료 코드로 끝나고 테스트 3개 중 1개가 실패하는 것입니다. 핵심 증거는 다음과 비슷합니다.

```text
Expected values to be strictly equal:

-360 !== 36
```

테스트가 실패하지 않는다면 일단 멈추세요. `starter/`의 파일을 실행했는지, Node.js 버전은 무엇인지, 파일이 이미 수정되지는 않았는지 확인합니다. 실패 상태가 안정적으로 재현되지 않으면 원래 문제의 기준선이 되는 증거도 없습니다.

## 4. 두 번째 단계: 읽기 전용 탐색

### 탐색

```text
아직 파일을 수정하지 마세요. 다음 파일을 읽으세요.
- examples/complete-workflows/developer/verified-bug-fix/starter/cart.js
- examples/complete-workflows/developer/verified-bug-fix/starter/cart.test.js

다음 내용을 6개 항목 이내로 설명해 주세요.
1. 어떤 입력에서 실패하는가?
2. 기대값과 실제값은 무엇인가?
3. 계산식에서 백분율과 비율 값은 어떻게 다른가?
4. 최소 수정은 어느 줄에서 해야 하는가?
5. 변경해서는 안 되는 공개 동작은 무엇인가?
6. 수정 후 어떤 검증을 실행해야 하는가?
```

올바른 원인 설명에는 다음 내용이 들어가야 합니다. 호출자는 `10`을 10%라는 뜻으로 전달하지만, 구현은 이를 `subtotal * 10`으로 직접 계산합니다. `100`으로 나누는 변환이 빠져 있습니다.

## 5. 세 번째 단계: 최소 수정 계획 및 실행

```text
starter/cart.js의 할인율 백분율 변환 부분만 수정하세요.
함수 이름, 인자, 테스트 단언, 파일 구조는 바꾸지 말고 의존성도 추가하지 마세요.

수정한 뒤 순서대로 다음을 수행하세요.
1. starter/cart.test.js를 실행합니다.
2. 실제 테스트 결과 요약을 보여 줍니다.
3. 수정한 줄과 수정 이유를 정리합니다.
4. Git 커밋이나 푸시는 하지 않습니다.
```

최소 수정의 핵심은 다음과 같습니다.

```js
const discount = subtotal * (discountPercent / 100);
```

테스트의 `36`을 `-360`으로 바꿔서 통과시키지 마세요. 이는 기대값을 바꾼 것일 뿐, 업무 규칙을 고친 것이 아닙니다.

## 6. 네 번째 단계: 통과 확인

실습 시작 코드를 수정하고 싶지 않다면 참고 해법을 바로 실행해도 됩니다.

```bash
node --test examples/complete-workflows/developer/verified-bug-fix/solution/cart.test.js
```

예상 결과는 테스트 3개가 모두 통과하고 프로세스가 종료 코드 0으로 끝나는 것입니다.

검증 기록에는 적어도 다음 항목이 있어야 합니다.

| 증거 | 답해야 할 질문 |
|---|---|
| 수정 전 실패한 명령 | 원래 문제를 안정적으로 재현할 수 있는가? |
| 실패한 단언 | 테스트가 실제로 이 버그를 검사하는가? |
| 코드 diff | 변경이 원인에만 국한되어 있는가? |
| 수정 후 관련 테스트 | 같은 동작이 이제 올바른가? |
| 더 넓은 범위의 테스트 | 인접 기능을 망가뜨리지 않았는가? |

이 실습 디렉터리에는 테스트 묶음이 하나뿐입니다. 실제 프로젝트에서는 `AGENTS.md`의 지침에 따라 lint, 타입 검사, 전체 테스트도 실행해야 합니다.

## 7. 다섯 번째 단계: 검토

```text
파일은 수정하지 말고 이번 수정을 검토하세요. 먼저 발견 사항을 나열한 뒤 결론을 내려 주세요.
- 테스트 기준을 완화한 것이 아니라 백분율 변환을 실제로 고쳤는가?
- 함수 시그니처나 관계없는 로직이 바뀌었는가?
- 빈 장바구니, 할인 없음, 10% 할인이 모두 테스트로 다뤄지는가?
- 이 사례의 범위 밖에 남는 금액 정밀도 위험은 무엇인가?
```

사람이 직접 확인할 사항도 있습니다. 불필요한 의존성이나 디버그 로그가 추가되지 않았는지, 파일 전체를 포맷하지 않았는지, Git 작업을 하지 않았는지 살펴보세요.

## 8. 실패와 복구

| 문제 | 대응 |
|---|---|
| 시작 코드의 테스트가 실패하지 않음 | `starter/cart.test.js`를 실행했는지 확인하고, 수정되지 않은 시작 코드를 복원합니다. |
| 테스트를 수정한 뒤 통과함 | 테스트 단언을 복원하고 구현의 백분율 변환만 수정합니다. |
| 관련 테스트가 계속 실패함 | 실패 값을 비교하고 `/ 100`을 잘못된 위치에 넣지 않았는지 확인합니다. |
| 전체 테스트에서 새 실패가 발생함 | 원인 분석으로 돌아가 공개 동작과 변경 범위를 확인합니다. |
| 테스트가 간헐적으로 실패함 | 먼저 테스트 환경을 안정화합니다. 한 번 통과한 결과만으로는 증거가 되지 않습니다. |

## 9. 실습을 실제 저장소에 적용하기

예제 경로를 자신의 파일 경로로 바꾸되, 증거를 남기는 구조는 유지하세요.

```text
목표: 【관찰 가능한 잘못된 동작】을 수정합니다.
재현 명령: 【정확한 명령】. 현재 일관되게 실패하는 항목은 【핵심 단언】입니다.
범위: 【구현 파일】과 필요한 테스트만 수정합니다. 리팩터링이나 의존성 업그레이드는 하지 않습니다.
인수 기준: 원래 실패하던 테스트 통과, 새 경계 조건 테스트 통과, 【전체 테스트 명령】 통과, diff에 무관한 변경 없음.
권한: push, 배포, 운영 데이터 변경은 금지합니다. 추가 권한이 필요하면 멈추고 설명합니다.
먼저 읽기 전용으로 원인과 위험을 파악하고, 제가 계획을 확인한 뒤 수정하세요.
```

## 10. 작업 방식으로 정착시키기

- 이런 버그가 반복된다면 `AGENTS.md`에 관련 규칙을 한 줄 추가합니다.
- 실패, 통과, 회귀 검사의 증거를 반드시 기록하게 하는 `regression-guard` Skill로 추출할 수 있습니다.
- 자주 발생하는 경계 조건 테스트는 대화에만 남겨 두지 말고 CI에 추가합니다.
