간단히 말해 Hook은 핵심 지점에 검사나 기록을 자동으로 한 층 넣는 것입니다.

**Hooks**는 Codex 실행 체인의 고정 지점에서 커스텀 로직을 실행하게 합니다. 예: 커밋 전 비밀 스캔, MCP 호출 기록, 위험한 명령 차단. [승인과 샌드박스](/guide/cli/approvals-and-sandbox/)의 정책과 관측 가능성을 보완하는 데 씁니다.

## 내용

- Hooks와 Skill·MCP의 차이
- 전형적인 팀 사용 사례
- Hook 설계 시 보안 원칙

## 팀이 Hook을 쓰는 이유

당장 Hook을 직접 쓰지 않을 계획이어도, 팀에서 흔히 무엇에 쓰는지 알아 두는 편이 좋습니다.

- 왜 어떤 동작이 핵심 지점에서 추가로 한 번 막히는지
- 왜 팀이 「이 검사는 Skill이 아니라 Hook」이라고 말하는지
- 왜 어떤 규칙은 prompt에 쓰지 않고 시스템 노드에 쓰는지

팀에서 「왜 여기에 검사가 하나 더 있나」의 배경은 대개 Hook입니다.

선택 비교: [확장 방식 고르기](/skills/choosing-an-extension-method/)

## Hooks가 하는 일

| 단계(개념) | Hook이 할 수 있는 일 |
|---|---|
| 도구 호출 전 | `rm -rf`, `.env` 유출이 있는 명령 거부 |
| 도구 호출 후 | SIEM에 감사 로그 기록 |
| 세션 종료 | 변경 파일 목록 요약 |
| PR 생성 전 | issue 번호 형식 검사 |

## Skill과 어떻게 구분하나

- **Skill**: Codex에 「이런 작업을 만나면 어떤 절차로 할지」를 알려 줌
- **Hook**: 시스템에 「이 노드에 도달하면 먼저 자동으로 검사하라」고 알려 줌

해결하는 문제가 다릅니다.

- Skill은 워크플로 설명에 가깝고
- Hook은 절차상의 관문이나 관찰점에 가깝습니다

구체 이벤트 이름과 설정 형식은 [공식 Hooks 문서](https://developers.openai.com/codex)를 기준으로 하세요.

## Skill / MCP와의 차이

| | Hooks | Skill | MCP |
|---|---|---|---|
| 트리거 | 시스템 이벤트 | 사용자 또는 모델 호출 | 도구 요청 |
| 목적 | 정책·감사 | 워크플로 설명 | 외부 시스템 |
| 누가 유지 | 플랫폼/팀 인프라 | 제품 또는 엔지니어링 팀 | 통합 개발자 |

## 흔한 오해

### 1. Hook이 승인과 샌드박스를 대체할 수 있다

Hook은 보완 검사 층이며, 유일한 보안 경계로 취급하면 안 됩니다.

### 2. Hook이 많을수록 안전하다

느리고 무겁고 이해하기 어려운 Hook이 많으면 절차만 느려지고 장애 대응이 더 고통스러워집니다.

### 3. Hook에는 복잡한 로직을 넣기 부적합하다

Hook은 다음에 더 적합합니다.

- 빠름
- 결정적
- 테스트하기 쉬움

여기에 복잡한 추론을 한 층 더 얹지 마세요.

## 권장 팀 사용 사례

1. **비밀 유출 탐지**: diff에 AWS key 패턴이 나타나면 차단
2. **라이선스 헤더 검사**: 새 파일에 회사 저작권 고지가 없으면 경고
3. **컴플라이언스 로그**: 누가, 언제, 어느 저장소에 쓰기 작업을 했는지(마스킹)
4. **CI와 정렬**: 로컬 Hook 규칙을 GitHub Action과 가능한 한 같은 출처로

## 먼저 만들 만한 가드레일

Hook은 거대한 “지능형 심판”이 아니라, 좁고 결정적인 장면부터 시작하는 것이 좋습니다.

| Hook 패턴 | 첫 버전 | 성숙한 버전 |
|---|---|---|
| 명령 감사 | 명령, 시간, 작업 디렉터리 기록 | 고위험 명령에 경고 또는 재확인 요구 |
| Secret 스캔 | `.env`, key 파일, 의심 token 편집 시 경고 | 차단하고 처리 방법 제시 |
| 포맷 검사 | 형식 차이 보고 | CI와 같은 formatter 실행 |
| 의존성 검사 | 패키지 파일 변경 시 리뷰 요청 | 취약점/라이선스 정책 연결 |
| 세션 요약 | 변경 파일과 검증 명령 기록 | 인수인계 문서나 PR 템플릿 연결 |

좋은 Hook은 실패할 때 지루합니다. 메시지가 명확하고 영향 범위가 작으며 우회가 기록됩니다.

## 도입 순서

1. 먼저 기록
2. 그다음 확실한 위험만 경고
3. 이후 결정적이고 합의된 규칙만 차단
4. CI 스크립트를 재사용해 로컬/원격 검사가 갈라지지 않게 하기

## 언제 Hook이 적합한가

검사가 다음 두 가지를 만족하면 Hook에 두기 좋습니다.

- 항상 고정 노드에서 발생
- 사람이 매번 수동으로 기억해 할 일이 아님

예: 민감 정보 스캔, 이름 검증, 감사 기록.

## 설계 원칙

- **빠름**: Hook 타임아웃은 도구 호출마다 지연을 만듦
- **결정적**: Hook 안에서 다시 LLM을 호출하지 말 것
- **테스트 가능**: 고정 입력으로 Hook 스크립트를 단위 테스트
- **끌 수 있음**: 긴급 시 팀이 우회할 수 있어야 함(감사 포함)

보안 관점은 로드맵 `11-team-enterprise`를 참고하세요. 개인 사용자는 보통 읽기 전용 로그 Hook부터면 충분합니다.

Hook은 시스템 핵심 노드에 두어 자동 검사하기에 적합합니다. 워크플로 설명이 아니며, 승인을 대체하지도 않습니다.

## 흔한 실수

- Hook 스크립트 자체에 네트워크 쓰기 권한이 있어 새 공격면이 됨
- `AGENTS.md` 규칙과 중복·모순
- Hook 설정을 버전 관리하지 않아 동료 환경이 제각각

## 수락 체크리스트

- [ ] 팀이 가장 필요한 Hook 장면 하나를 설명할 수 있음
- [ ] Hook 실패 시 개발자에게 분명한 오류 메시지가 있음
- [ ] 설정이 코드 검토에 포함됨
