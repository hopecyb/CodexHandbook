여기서는 같은 검사를 언제 트리거해야 하는지를 다룹니다.

**Hook 이벤트**는 시스템이 고정 노드에서 당신이 설정한 로직을 호출하는 시점입니다. 이벤트 유형을 이해해야 도구 호출마다 늦추지 않으면서 [Hooks 개요](/skills/hooks/hooks-overview/)의 「감사·검증」을 설정에 옮길 수 있습니다.

## 내용

- 흔한 이벤트 단계와 적용 장면
- 이벤트와 [명령 규칙](/guide/customization/rules/command-rules/)의 역할 분담
- 설정 시 성능과 실패 전략

## 한 가지 판단 원칙

처음부터 「이 Hook을 구현할 수 있나」를 묻지 마세요.  
먼저 묻으세요. 일이 일어나기 **전에** 막을지, 일어난 **후에** 기록할지?

많은 Hook이 잘못된 위치에 걸리는 이유는 트리거 시점을 잘못 골랐기 때문입니다.

:::note
**이벤트 이름과 필드는 [공식 Hooks 문서](https://developers.openai.com/codex)를 기준으로 하세요.** 아래 표는 개념 그룹입니다. CLI 업그레이드 후 `--help`와 release notes를 확인하세요.
:::

## 이벤트 그룹(개념)

| 단계 | 전형적 이벤트(개념명) | 적합한 일 |
|---|---|---|
| 세션 | `session.start` / `session.end` | 환경 검사, 변경 요약, 감사 꼬리말 기록 |
| 도구 전 | `tool.call.before` / `pre_tool_use` | 위험 명령 차단, 비밀 패턴 스캔 |
| 도구 후 | `tool.call.after` / `post_tool_use` | 구조화 로그, 지표, 마스킹 아카이브 |
| 프롬프트 | `user_prompt.submit` | 정책 스캔 주입, 길이 제한 |
| 산출물 | `artifact.create` | 라이선스 헤더, 파일 유형 화이트리스트 |
| 통합 | `pr.before_create`(지원 시) | Issue 번호, changelog 형식 |

같은 로직을 여러 이벤트에 중복 걸지 마세요. **가장 일찍 차단할 수 있는** 지점을 고르세요.

## 이 단계를 어떻게 이해할까

- **세션류**: 이번 작업이 시작되거나 끝날 때
- **도구 전**: 명령이나 도구가 아직 실제로 실행되지 않음
- **도구 후**: 동작이 이미 발생. 기록·요약·재검사 가능
- **프롬프트류**: 사용자 내용이 방금 제출됨
- **산출물류**: 파일이나 결과가 방금 생성됨

이 계층부터 이해하고, 이벤트 이름을 억지로 외우지 마세요.

## 규칙 엔진과의 관계

```text
사용자 prompt →(선택)prompt Hook
    → 모델이 도구 호출 제안
    → 규칙 엔진 allow/deny
    →(선택)pre_tool Hook → 실행 → post_tool Hook
```

- **규칙**: 선언적·빠름. 알려진 명령 패턴에 적합
- **Hook**: 명령형 스크립트. 복잡한 정책과 외부 시스템에 적합

## 흔한 오해

### 1. 검사만 되면 앞이든 뒤든 비슷하다

많이 다릅니다.

「부작용이 일어나기 전에 막고」 싶다면 가능한 한 더 이른 위치에 거세요.  
동작이 끝난 뒤 `post_tool`에서야 문제를 발견하면 대개 이미 늦습니다.

### 2. 이벤트가 많고 세밀할수록 설정이 전문적이다

설정에서는 「적고 정확」을 추구하세요. 가장 적합한 한 지점에 로직을 먼저 맞게 거세요.

### 3. Hook 이벤트 유형은 기술 세부일 뿐이다

다음에 직접 영향을 줍니다.

- 위험을 제때 막을 수 있는지
- 로그가 유용한지
- 전체 상호작용이 느려지는지

## 실패 전략

| 전략 | 언제 쓸까 |
|---|---|
| `block` | 보안 위반, 컴플라이언스 강성 요구 |
| `warn` | 스타일, 권고성 검사 |
| `log` | 관측만, 차단하지 않음 |

Hook 타임아웃이나 크래시 시 **기본은 안전**이어야 합니다. 프로덕션은 block 또는 fail closed를 선호하고, 조사할 오류를 기록하세요.

## 어디에 걸지 모를 때

어디에 걸지 모르겠다면 이 단순 규칙으로 생각하세요.

- 위험한 동작을 막고 싶다: 선행 이벤트 우선
- 무엇이 일어났는지 기록하고 싶다: 후행 이벤트 우선
- 시작 검사나 마무리 요약: 세션 이벤트 참고

이 판단은 대부분의 설정 장면에 충분합니다.

## 최소 설정 사고방식

1. 이벤트 하나 고르기(권장: `post_tool` 읽기 전용 로그부터)
2. 스크립트 stdin이 JSON 페이로드 수신(도구 이름, 인자 요약, 작업 디렉터리)
3. 종료 코드 `0`은 통과, 비 `0`은 전략에 따라 block/warn
4. 단위 테스트: 고정 JSON fixture로 스크립트 실행

먼저 막을지·기록할지 정한 뒤, Hook을 어느 이벤트에 걸지 결정하세요.

전체 예시는 [Hook 설정 예시](/skills/hooks/hooks-examples/)를 참고하세요.

## 흔한 실수

- `post_tool`에서 본래 `pre_tool`에 있어야 할 차단을 함(부작용이 이미 발생)
- Hook 안에서 LLM이나 느린 네트워크를 호출해 상호작용을 망침
- 이벤트 페이로드에 비밀이 있는데 평문 로그에 기록
- Hook을 버전 관리하지 않아 동료 환경이 제각각
