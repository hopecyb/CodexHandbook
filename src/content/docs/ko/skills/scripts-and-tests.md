Skill을 처음 만들 때 흔한 방법은 모든 것을 `SKILL.md`에 쓰는 것입니다. 간단한 절차에는 괜찮지만, 어떤 단계가 **안정·반복·검증 가능**하게 실행되어야 한다면 스크립트가 순수 텍스트 설명보다 더 신뢰할 수 있습니다.

고정 동작은 스크립트에 맡기고, 판단과 협업 절차는 Skill에 남기세요.

# scripts/와 테스트

어떤 단계가 결정적으로 실행되어야 할 때(테스트 실행, diff 생성, 형식 검증) `scripts/`에 스크립트를 두고, `SKILL.md`에서 언제 호출하는지 설명하세요.

## 예시

```text
my-skill/
├── SKILL.md
└── scripts/
    └── run-checks.sh
```

## 언제 `scripts/`를 고려할까

다음 중 하나라도 만족하면 스크립트를 우선 고려하세요.

- 매번 완전히 같게 실행되어야 함
- 종료 코드 자체가 의미가 있음
- 자연어로 설명하면 매우 장황해짐
- 이후 CI나 다른 도구에서도 재사용하고 싶음

「검사 실행」「diff 생성」「형식 검증」「고정 보고서 내보내기」 같은 동작은 스크립트에 두기 좋습니다.

## 테스트 제안

- 연습용 저장소에서 스크립트를 수동 실행해 종료 코드와 출력을 확인
- Skill로 end-to-end 절차를 트리거해 예상대로 스크립트를 호출하는지 확인
- 팀 장면: CI나 pre-commit에서 스크립트가 여전히 동작하는지 검증

## 흔한 오해

### 1. 스크립트를 쓰면 Skill이 복잡해지니 쓰지 말자

스크립트가 원래 불안정한 단계를 고정하면, 전체는 오히려 더 단순해질 수 있습니다.

### 2. 스크립트가 로컬에서만 돌면 Skill은 문제없다

다음도 봐야 합니다.

- Skill이 올바르게 트리거하는지
- 승인 정책이 막는지
- 팀 환경이나 CI에서도 정상 동작하는지

### 3. 「Skill 테스트」는 스크립트 테스트와 같다

충분하지 않습니다.

스크립트는 한 동작을 테스트하고,  
Skill은 「언제 호출하는지, 어떻게 호출하는지, 출력이 기대에 맞는지」까지 테스트해야 합니다.

## 흔한 검증 순서

처음에는 이 순서로 하세요.

1. 스크립트를 단독 실행
2. 종료 코드와 출력이 분명한지 확인
3. Skill로 전체 절차를 한 번 호출
4. 실제 환경에 더 가까운 곳에서 다시 테스트

「스크립트 자체 고장」과 「Skill 통합 방식이 틀림」을 나누기 쉽습니다.

안정적으로 반복 실행할 동작은 텍스트 설명에만 맡기지 마세요. 스크립트를 먼저 통과시킨 뒤 Skill 호출을 확인하세요.

스크립트는 현재 승인 정책을 상속합니다. [명령 규칙](/guide/customization/rules/command-rules/)과 [Skill 보안](/skills/security/)을 참고하세요.
