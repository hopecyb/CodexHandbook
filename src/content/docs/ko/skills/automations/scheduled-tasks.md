예약 작업에서 정말 어려운 부분은 “몇 시에 실행할지”가 아닙니다. 사람이 지켜보지 않는 매번의 실행에 안정적인 입력, 좁은 권한, 검토 가능한 출력, 중단 조건을 갖추는 일입니다.

![수동 검증에서 예약 실행, 사람의 검토와 조정으로 이어지는 안전한 순환](/diagrams/scheduled-task-safety-loop-ko.svg)

## 대상 독자

- 일간·주간 보고서를 만들거나 문서를 점검하고 PR을 추적하려는 개인 사용자
- 로컬 프로젝트 또는 격리된 worktree에서 유지 관리 작업을 정기적으로 실행해야 하는 개발자
- 권한, 실패 처리, 팀 공유 Skill을 평가하는 유지 관리자

## 지원 범위

| 환경 | 할 수 있는 일 | 주요 제한 |
|---|---|---|
| ChatGPT Web | 실행 생성·관리·조회, 업로드 파일·연결 도구·Skills·Plugins 사용 | 로컬 컴퓨터의 폴더에 직접 접근할 수 없음 |
| ChatGPT 데스크톱 App | 작업 생성·관리, 로컬 프로젝트 또는 Git worktree 선택 가능 | 로컬 파일 작업에는 컴퓨터가 켜져 있고 App이 실행 중이며 프로젝트가 존재해야 함 |
| Codex CLI | 프롬프트, Skill, 스크립트를 준비하고 수동으로 테스트 | Scheduled 관리 화면이 없음 |
| IDE 확장 | 작업 공간에서 명령과 수정 사항을 검증 | Scheduled 관리 화면이 없음 |

## 1. 독립 작업과 채팅 내 작업 중 선택하기

### 독립 Scheduled task

각 실행은 저장된 프롬프트에서 새로 시작하고 Scheduled에 별도 실행으로 기록됩니다. 서로 독립적인 일간·주간 보고서나 프로젝트 상태 점검에 적합합니다. 하나의 작업이 여러 프로젝트를 다룰 수도 있습니다.

### 채팅 내 Scheduled task

일정에 따라 같은 채팅으로 돌아와 기존 맥락을 이어갑니다. 장기 작업을 주기적으로 확인하거나 PR 상태를 추적하고, 연구를 계속하거나 이전 논의를 유지해야 하는 일에 적합합니다.

선택 기준은 간단합니다. 실행할 때마다 “처음부터 다시 시작”해야 하면 독립 작업을, 같은 문제의 맥락을 이어가야 하면 채팅 내 작업을 선택하세요.

## 2. 실행에 필요한 자료 선택하기

### Web에서 실행하기

지속해서 적용할 지침은 작업 프롬프트나 Skill에 적고, 필요한 자료는 업로드 파일, Project 또는 연결된 서비스에 둡니다. Web은 로컬 경로에 직접 접근할 수 없으므로 “내 바탕화면의 latest.csv를 읽어 줘”라고 쓰지 마세요.

### 데스크톱 App에서 로컬 프로젝트 사용하기

Git 저장소에서는 다음 중 선택할 수 있습니다.

- **로컬 프로젝트**: 기본 checkout에서 바로 작업하므로 현재 편집 중인 파일과 충돌할 수 있습니다.
- **전용 worktree**: 백그라운드 수정 사항을 끝나지 않은 작업과 분리합니다. 파일을 수정하는 작업에 적합합니다.

Git 저장소가 아닌 프로젝트는 프로젝트 디렉터리에서 바로 실행됩니다. worktree 작업을 자주 실행하면 작업 트리가 쌓입니다. 필요 없는 실행을 보관 처리해 많은 worktree를 무심코 남기지 않도록 하세요.

## 3. 먼저 수동으로 검증하기

일반 채팅에서 완전히 같은 프롬프트, 모델, 추론 강도, 도구로 먼저 실행합니다. 최소한 다음을 확인하세요.

- 현장에서 추가 설명을 하지 않아도 입력이 명확함
- “변화 없음”이면 조용히 종료함
- 사람이 출력을 빠르게 검토할 수 있음
- 명령, Skill, 연결 도구가 모두 작동함
- 권한이나 자료가 부족하면 추측하지 않고 중단하며 이유를 설명함

처음 몇 차례 예약 실행을 확인한 뒤 프롬프트나 실행 빈도를 조정하세요.

## 4. 바로 고쳐 쓸 수 있는 작업 프롬프트

```text
독립 Scheduled task를 만들어 주세요.

이름: 주간 문서 깨진 링크 점검
시간: 매주 월요일 09:00, 현재 시간대 사용
실행 위치: 현재 Git 프로젝트의 전용 worktree

매번 실행할 일:
1. docs/, src/content/docs/, examples/, public/diagrams/만 읽습니다.
2. pnpm check:links를 실행합니다.
3. 검사가 통과하면 검사한 파일 수와 링크 수만 보고하고 파일은 수정하지 않습니다.
4. 검사가 실패하면 “출처 파일, 깨진 대상, 권장 수정” 형식으로 결과를 나열하고 링크를 자동으로 고치지 않습니다.
5. 인터넷에 연결하지 않고, 의존성을 설치하지 않고, 커밋·push·PR 생성을 하지 않습니다.
6. 명령이 없거나 의존성이 부족하거나 결과가 불확실하면 중단하고 사람의 처리가 필요한 구체적인 사항을 설명합니다.

완료 조건: 검토 가능한 보고서 하나를 출력하면 이번 실행을 끝내고 재시도하지 않습니다.
```

이 프롬프트는 시간, 프로젝트, 읽기 범위, 명령, 성공·실패 경로, 금지 동작, 종료 조건을 모두 명시합니다. 스케줄은 작업을 다시 시작할 뿐, 작업 설명을 대신하지 못합니다.

## 5. 권한과 사람의 검토

예약 작업은 사람이 지켜보지 않는 상태에서 기본 샌드박스 설정으로 실행됩니다.

| 샌드박스 모드 | 흔한 결과 |
|---|---|
| read-only | 파일 수정, 인터넷 연결 또는 로컬 App 제어 호출이 실패함 |
| workspace-write | 작업 공간에는 쓸 수 있지만, 작업 공간 밖 쓰기·인터넷 연결·App 제어는 기본적으로 실패함 |

작업을 완료할 수 있는 가장 좁은 권한부터 시작하세요. 네트워크나 더 넓은 파일 접근이 필요하다면 allowlist를 명시하세요. 한 번의 실패를 없애려고 작업 전체를 높은 권한으로 바꾸지 마세요.

다음에는 사람의 검토를 남겨 두는 편이 좋습니다.

- 외부로 메시지를 보내거나 콘텐츠를 게시할 때
- 운영 환경의 상태를 변경할 때
- PR을 병합하거나 기본 브랜치에 push할 때
- 대량 삭제·마이그레이션·권한 변경을 할 때
- diff가 예상 범위를 벗어나거나 테스트가 실패했을 때

## 6. “변화 없음”, 실패, 중단을 설계하기

반복 실행할 작업에는 세 가지 경로를 정의해야 합니다.

1. **발견 사항 있음**: 근거, 심각도, 다음 조치를 출력합니다.
2. **변화 없음**: 검사 범위를 간단히 보고하고 없는 문제를 만들어 내지 않습니다.
3. **완료 불가**: 부족한 자료나 권한을 설명하고 중단해 사람의 처리를 기다립니다.

채팅 내 주기적 확인 작업에는 종료 조건도 적으세요. 예를 들어 “PR이 병합되거나 닫힘, 같은 오류가 3번 연속 발생, 사람의 승인이 필요할 때 중단”처럼 명시합니다.

## Scheduled task는 이벤트 기반 CI가 아닙니다

`push`, PR 생성, 배포 완료 같은 저장소 이벤트 직후에 반드시 실행해야 한다면 GitHub Actions, CI, webhook 또는 Codex SDK 같은 이벤트 진입점을 사용하세요. “매분 확인”을 정확한 이벤트 트리거로 취급하지 마세요.

## 검수 체크리스트

- [ ] 일반 채팅에서 프롬프트를 처음부터 끝까지 실행해 봄
- [ ] 독립 작업 또는 채팅 내 작업을 선택함
- [ ] Web 자료 또는 로컬 프로젝트를 실행 시점에 사용할 수 있음
- [ ] 기본 샌드박스로 충분하며 추가 권한에는 명확한 이유가 있음
- [ ] 발견 사항, 변화 없음, 실패, 중단 조건을 적음
- [ ] 처음 세 차례 실행을 사람이 표본 검토함
- [ ] 자주 생성되는 worktree의 보관·정리 전략이 있음
- [ ] 중요한 쓰기 작업에는 사람의 확인을 유지함
