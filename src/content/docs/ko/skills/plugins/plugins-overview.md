Plugin은 설치 패키지로 볼 수 있습니다. 이미 구성된 확장 능력 세트를 묶어 남이 바로 설치하게 합니다.

**Plugin(플러그인/커넥터)**은 Skill, MCP 서버, 앱 통합 등을 **설치·업데이트·거버넌스 가능한** 단위로 패키징합니다. 「한 사람이 설정하고 팀 전체가 재사용」에 특히 적합합니다.

## 핵심 차이

| 단독 사용 | Plugin 경유 |
|---|---|
| Skill 디렉터리를 수동 복사 | 원클릭 설치/업그레이드 |
| 각자 MCP JSON 설정 | 사전 서버와 권한 설명 |
| 문서가 흩어짐 | 게시자가 목록과 버전 설명 제공 |

Plugin은 **배포·조합 층**입니다. 능력 자체는 여전히 Skill, MCP, 커넥터에 있습니다. [확장 능력 지도](/skills/capability-map/) 참고.

## Plugin, Skill, MCP의 차이

짧은 버전은 이렇습니다.

- **Skill**: Codex에 「어떤 단계로 할지」를 알려 줌
- **MCP**: Codex에 「어떤 외부 도구를 호출할 수 있는지」를 알려 줌
- **Plugin**: 위 항목을 묶어 설치와 거버넌스를 쉽게 함

많은 혼동은 이 세 층을 같은 것으로 취급하는 데서 옵니다.

## 전형적 구성

```text
Plugin 패키지
├── Skills(선택)
├── MCP 서버 정의(선택)
├── 앱 커넥터 / OAuth 흐름(선택)
└── 메타데이터: 버전, 권한 선언, 변경 로그
```

## 언제 Plugin을 쓸까

| Plugin 사용 | Plugin 미사용 |
|---|---|
| 팀에 Figma/Linear/GitHub 강화 패키지 통일 설치 | 개인 일회성 작은 스크립트 |
| 버전 관리와 롤백이 필요 | `SKILL.md` 하나로 충분 |
| 기업이 화이트리스트 확장만 허용 | 실험 단계 프로토타입 |

## 언제 Plugin을 신경 써야 하나

- 개인 학습·Skill 몇 개만 작성: 당분간 미뤄도 됨
- 팀에 확장 세트를 통일 배포: Plugin을 신경 쓰기 시작

Plugin이 주로 해결하는 것은 「**배포와 거버넌스**」이며, Codex 첫 입문의 필수 항목이 아닙니다.

## 설치와 관리(개념)

1. **공식 마켓 또는 팀 승인 목록**에서 Plugin 선택
2. 권한 설명 읽기: 어떤 저장소를 읽고, 어떤 SaaS에 접근하는지
3. 설치 후 세션 재시작, 도구와 Skill 목록 검증
4. 정기 업데이트; 메이저 버전은 staging 저장소에서 먼저 시험

구체 버튼과 명령은 데스크톱 App / CLI의 현재 UI를 기준으로 하세요.

## 흔한 오해

### 1. Plugin을 설치하면 자동으로 안전하다

Plugin은 능력을 더 편하게 배포할 뿐, 권한이 본래부터 안전한 것은 아닙니다. 여전히 봐야 합니다.

- 무엇에 접근할 수 있는지
- 나를 대신해 외부 동작을 실행하는지
- 출처를 믿을 수 있는지

### 2. 설치할 수 있으면 다 설치할 가치가 있다

팀이 유지·회수·감사할 수 있는 확장만 장기 활성화에 적합합니다.

## 보안과 프라이버시

- 신뢰할 수 있는 출처만 설치. Plugin이 요청하는 OAuth scope 검토
- 「디자인 초안 읽기」와 「메시지 대행 발송」류 권한 구분
- 퇴사·전배 시 커넥터 인가 회수
- [권한과 승인](/guide/foundations/permissions-and-approvals/)과 겹쳐 쓰고, Plugin이 보안을 자체 제공한다고 가정하지 말 것

## Claude Code / 다른 생태계와 비교

제품마다 「Plugin」 의미가 완전히 같지 않습니다. 비교할 때는 **무엇을 패키징했는지, 권한 모델, 오픈소스 감사 가능 여부**를 보세요. [기능 대조](/guide/reference/feature-comparison/).

## 흔한 실수

- 작은 Skill마다 Plugin을 만들어 유지 비용이 폭발
- 설치 후 업데이트하지 않아 보안 수정을 놓침
- 프로덕션 저장소에서 실험적 Plugin 활성화
