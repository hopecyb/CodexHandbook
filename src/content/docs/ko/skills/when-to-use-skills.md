Skill을 처음 접할 때 흔한 질문은, 이 일을 굳이 Skill로 만들 가치가 있는가입니다.

무엇이든 Skill로 만들면 점점 무거워지고, 정리할 것을 정리하지 않으면 같은 말을 수동으로 계속 반복하게 됩니다. 여기서는 언제 절차를 고정할지 판단하는 데 초점을 둡니다.

# 언제 Skills를 쓰는가

## Skill로 묶기에 적합한 경우

- 같은 절차를 수동으로 세 번째 반복할 때
- 자세한 체크리스트가 필요하지만 매번 컨텍스트를 가득 채우고 싶지 않을 때
- 모델이 `description`으로 언제 켤지 자동 판단하게 하고 싶을 때
- 팀이 공유·버전 관리할 워크플로가 필요할 때

## Skill로 만들 조건

다음 두 가지를 동시에 만족하면 Skill로 만들 가치가 큽니다.

- 앞으로도 다시 할 일
- 다음에도 가능한 한 같은 방식으로 하고 싶은 일

많은 Skill은 결국 이런 장면에 모입니다.

- diff 검토
- changelog 생성
- 배포 전 검사
- 문서 배포 절차

복잡하지는 않지만 재사용에 잘 맞습니다.

## 덜 적합한 경우

- 일회성·반복되지 않은 작업
- 매우 짧고 기억하기 쉬운 고정 명령(슬래시 명령 고려)
- 실시간 외부 시스템 상태가 필요하고 변화가 매우 빠름(MCP 고려)

## 흔한 오해

### 1. 중요한 작업이면 Skill로 만들어야 한다

중요하다고 해서 재사용에 적합하다는 뜻은 아닙니다.  
일회성 특수 작업이면 Skill로 만드는 것이 유지 부담만 늘릴 수 있습니다.

### 2. Skill이 많을수록 좋다

경계가 모호한 Skill이 너무 많으면 모델이 잘못 쓰고 팀 유지보수도 더 어려워집니다.

### 3. 외부 시스템에 연결할 수 있으면 먼저 Skill을 만든다

외부 시스템 연결은 대개 MCP 쪽에 가깝습니다. Skill은 「절차」를 담당하고, 외부 시스템을 어떻게 연결할지는 MCP에 맡깁니다.

## 어떻게 시험해 볼까

절차를 정리할 가치가 아직 불확실하면, 이렇게 몇 번 시험해 보세요.

1. 수동으로 두세 번 완료
2. 매번 같은 검사 순서를 반복하는지 관찰
3. 답이 「그렇다」이면 Skill로 정리

이렇게 만든 Skill은 실제 반복에서 나온 것이라 더 탄탄합니다.

## 다른 확장 방식과 비교

| 방식 | 적합한 경우 |
|---|---|
| Skill | 재사용 가능한 절차, 점진적 공개 |
| MCP | 외부 API·데이터 소스 연결 |
| Hooks | 특정 이벤트 지점에서 자동 실행 |
| `AGENTS.md` | 프로젝트급 상시 규칙 |

Skill은 「반복되고, 일관성이 필요하며, 매번 다시 설명하고 싶지 않은」 절차를 정리하기에 더 적합합니다.

확장 방식 선택은 [확장 방식 고르기](/skills/choosing-an-extension-method/)를 참고하세요. 워크플로 정리는 [절차를 Skill로 바꾸기](/cases/workflows/turn-a-workflow-into-a-skill/)를 참고하세요.
