Skill을 처음 접할 때 흔한 오해는 「설치하면 알아서 동작한다」는 것입니다. Skill을 쓴다는 것은 Codex가 미리 적어 둔 작업 루틴대로 일하게 하는 것입니다.

Skill은 당신이 **명시적으로 지명**해 호출할 수도 있고, 적절한 장면에서 모델이 **자동으로 선택**할 수도 있습니다. 두 트리거를 구분하면 조사 경로를 줄일 수 있습니다.

# Skill 사용하기

## 트리거 방식

1. **명시적**: 지원 환경에서 `$skill-name`으로 호출(이름은 frontmatter `name`과 일치)
2. **암시적**: 모델이 `description` 의미로 현재 작업에 맞는지 판단

## 두 트리거를 구분하는 법

- **명시적 트리거**: 「이 Skill을 써」라고 직접 말함
- **암시적 트리거**: 지명하지 않았지만 작업 설명이 적용 장면과 잘 맞음

Skill을 처음 시험할 때는 **명시적 트리거**를 우선하세요. 이렇게 하면 판단하기 쉽습니다.

- Skill이 인식되었는지
- 동작이 기대한 것인지
- 이름과 설명이 맞는지

## 예시

```text
$pr-review 현재 커밋되지 않은 변경을 검토해 주세요
```

또는 자연어: 「팀 습관대로 diff를 검토해 주세요. 테스트에 초점을 맞춰 주세요.」

## 흔한 오해

### 1. Skill을 쓰면 반드시 자동 트리거된다

자동 트리거는 `description`이 얼마나 명확한지, 현재 작업이 적용 장면과 얼마나 비슷한지에 달립니다.

### 2. 자연어 트리거와 `$name` 트리거의 효과는 항상 같다

둘은 완전히 같지 않을 수 있습니다.

`$name`은 더 명확해 검증과 강제 사용에 적합합니다. 자연어는 편리하지만 모델이 잘못된 Skill을 고르거나 아예 쓰지 않을 수 있습니다.

### 3. Skill이 트리거되지 않으면 반드시 Skill에 문제가 있다

다음일 수도 있습니다.

- 이름이 틀림
- `description`이 너무 막연함
- 작업 설명이 트리거 단어를 맞추지 못함

조사할 때 「파일이 있는가」만 보지 말고, 「선택될 도구처럼 쓰여 있는가」도 보세요.

## 흔한 테스트 순서

한 번 통과시키고 싶다면 이렇게 시험하세요.

1. 먼저 `$skill-name`으로 명시 호출
2. 출력이 기대에 맞는지 확인
3. 그다음 `description` 수정
4. 마지막으로 자연어 트리거 테스트

이렇게 하면 「Skill 자체 문제」와 「자동 트리거 조건이 안 맞음」을 나눌 수 있습니다.

## 좋은 description 작성

- 「언제 쓸지」와 「언제 쓰지 말지」를 명확히
- 사용자가 말할 법한 키워드 포함(review, 배포, changelog)
- 「코드 작성을 도와준다」처럼 막연한 표현 피하기
- 핵심 트리거 장면을 **맨 앞**에 쓰기(Skill 목록에 문자 예산이 있음)

## description이 명확한지 판단하기

자주 쓰는 기준은 이렇습니다.  
이 `description` 한 줄을 읽으면 「언제 써야 하고 언제 쓰지 말아야 하는지」를 알 수 있어야 합니다.

한 줄을 읽어도 「뭐든 할 수 있을 것 같다」면 대개 너무 막연한 것입니다.
