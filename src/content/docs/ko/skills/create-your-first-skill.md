이미 작업을 내릴 수는 있지만 아직 Skill을 실제로 만들어 본 적이 없다면, 이 페이지는 첫 Skill의 기본 방법을 다룹니다.

15–30분 안에 **저장소에서 재사용 가능한** Skill을 하나 만드는 편이, 이론을 많이 읽는 것보다 보통 더 직접적입니다. 좋은 출발점은 경계가 분명한 작은 Skill입니다.

## 누구에게 맞나

[첫 작업](/cases/first-task/)을 통과했고, 테스트용 저장소에서 실험할 의향이 있는 사람.

## 왜 `pr-review`부터 추천하나

다음 장점이 있습니다.

- 입력이 비교적 분명함
- 「코드를 바로 고치는」 일보다 위험이 낮음
- 잘 되는지 판단하기 쉬움
- Skill의 트리거 방식과 경계 작성도 함께 익힐 수 있음

작업 루틴을 재사용 가능한 형태로 쓰는 연습에 잘 맞습니다.

## 목표 산출물

`.agents/skills/pr-review/` 아래에 Skill이 있고, 현재 변경에 대해 구조화된 검토 의견을 출력합니다.

## 최소 목표

첫 Skill에서는 다음 세 가지만 먼저 달성하세요.

1. 인식될 수 있을 것
2. 명확한 절차를 안정적으로 실행할 것
3. 위험한 동작을 함부로 하지 않을 것

이 세 가지가 분명해지면 이후 반복이 훨씬 수월합니다.

## 단계

### 1. 디렉터리 만들기

```bash
mkdir -p .agents/skills/pr-review
```

### 2. SKILL.md 작성

```md
---
name: pr-review
description: git diff를 검토하고 차단 이슈, 테스트 공백, 스타일 제안을 나열합니다. 사용자가 review, 검토, 병합 전 검사를 말할 때 사용합니다. 새 기능 작성에는 쓰지 않습니다.
---

# PR 검토

## 입력
- 기본 비교 브랜치: main(없으면 기본 브랜치)

## 절차
1. 변경 파일과 변경 유형 나열(기능/수정/리팩터/문서)
2. 각 논리 변경에 대해: 테스트 부족 여부, API 파괴 여부
3. 비밀, 디버그 로그, 과도한 무관 diff 포함 여부 확인
4. 출력:
   - 🔴 차단: 반드시 수정
   - 🟡 제안: 수정 권장
   - 🟢 통과: AGENTS.md 요구 충족

## 금지
- git push 하지 말 것
- 논의하지 않은 공개 API를 수정하지 말 것
```

### 3. 로컬에서 시험

Codex에서 해당 저장소를 열고 다음을 시도합니다.

```text
$pr-review 현재 커밋되지 않은 변경을 검토해 주세요
```

또는 자연어: 「팀 습관대로 diff를 검토해 주세요. 테스트에 초점을 맞춰 주세요.」

### 4. 명시부터, 그다음 암시

자동 트리거를 바로 테스트하지 마세요.

다음 순서로 시험합니다.

1. 먼저 `$pr-review`로 명시 호출
2. 절차와 출력이 문제없는지 확인
3. 그다음 자연어 트리거 시험

문제 원인이 Skill 내용인지, `description` 트리거 조건인지 구분하기 쉽습니다.

### 5. description 반복

모델이 **전혀 자동 선택하지 않으면** `description`의 트리거 단어를 좁히거나 보강하세요. **오용이 너무 잦으면** 「언제 쓰지 말지」를 추가하세요.

### 6. 커밋해 팀과 공유

```bash
git add .agents/skills/pr-review
git commit -m "docs: add pr-review skill for Codex"
```

팀 README나 `AGENTS.md`에 한 줄 추가: 「병합 전에 `$pr-review`를 쓸 수 있습니다.」

## 흔한 오해

### 1. 첫 Skill은 최대한 완전해야 한다

대개 반대입니다. 첫 Skill은 작고 초점이 분명할수록 가치가 있는지 판단하기 쉽습니다.

### 2. Skill의 핵심은 「똑똑하게」 쓰는 것

더 중요한 것은 **경계가 분명한** 작성입니다.

무엇을 하고 무엇을 하지 않는지가 「멋져 보이는」 것보다 중요합니다.

### 3. Skill이 돌아가기만 하면 성공이다

유용한 Skill은 최소한 다음을 만족해야 합니다.

- 남이 언제 써야 하는지 이해할 수 있음
- 출력에 고정 구조가 있음
- 위험한 조작을 함부로 하지 않음

## 수락 체크리스트

- [ ] `$pr-review`가 통과하고 위험한 git 조작을 하지 않음
- [ ] 출력이 막연한 말이 아니라 등급별 결론을 포함함
- [ ] `description`이 한 문장으로 트리거 장면을 설명함
- [ ] [권한과 승인](/guide/permissions-and-sandbox/)에 맞춰 스크립트 필요 여부를 확인함(이 예시에는 스크립트 없음)

「작고 안정적인」 Skill부터 시작하면, 분명한 작업 루틴을 안정적으로 재사용하기 쉽습니다.
