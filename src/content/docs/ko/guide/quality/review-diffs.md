“diff”는 Codex가 이번에 실제로 어디를 바꿨는지를 말합니다.

처음 검증할 때 많은 사람이 요약만 보고 실제 변경을 보지 않습니다.  
문제를 찾는 핵심은 diff입니다. “이미 완료했습니다”라는 설명은 참고일 뿐입니다.

## diff에서 보는 것

diff는 몇 가지 핵심 질문에 바로 답합니다.

- 실제로 어떤 파일을 바꿨는지
- 변경이 허용한 범위 안에 있는지
- 다른 것을 함께 지우거나 깨뜨렸는지
- 디버그 내용, 키, 임시 코드가 들어갔는지

diff를 읽을 때 중점:

1. 허용 경로만 고쳤는가?
2. 예상치 못한 삭제가 있는가?
3. 네이밍과 스타일이 일치하는가?
4. 키나 디버그 잔여물이 있는가?

제품 측 뷰: [diff, 코멘트와 심사](/ko/guide/desktop-app/diffs-comments-and-review/)

## AI 생성 코드의 품질 점검

**어떤 파일을 바꿨는지**뿐 아니라 변경 내용이 이 프로젝트에 어울리는지도 확인합니다.

| 점검 항목 | 확인할 내용 |
|---|---|
| 이름 | 변수·함수·파일 이름이 의도를 드러내는가? `data`, `temp`, `helper`만 반복하지 않는가? |
| 함수 경계 | 여러 책임을 거대한 함수 하나에 넣지 않았는가? |
| 오류 처리 | 실패 시 유용한 맥락을 주는가? 예외를 무시하지 않는가? |
| 테스트 | 구현만 바꾸지 않고 동작을 증명하는 테스트를 추가했는가? |
| 주석 | 코드를 반복하지 않고 ‘왜’를 설명하는가? |
| 단순화 | 당장 필요하지 않은 추상화를 완성도를 위해 도입하지 않았는가? |

빠르게 검토하려면 Codex에 이 표대로 자기 diff를 다시 살펴보게 하고, 파일을 더 수정하지 말고 위험만 나열하도록 요청하세요.

## 흔한 오해

### 1. 코드 diff를 깊게 못 읽어도 기초 심사는 가능

1단계에서는 시니어처럼 모든 줄을 읽을 필요가 없습니다.  
다음 세 가지만 봐도 가치가 큽니다.

- 어떤 파일을 바꿨는지
- 건드리면 안 되는 곳을 건드렸는지
- 명백히 관련 없는 내용이 늘어났는지

### 2. 파일 하나만 고쳤다고 안전하지는 않음

파일이 적다고 반드시 맞는 것은 아닙니다.  
다만 범위가 작으면 점검과 되돌리기가 더 쉽습니다.

### 3. “작은 변경”도 봐야 함

놓치기 쉬운 문제는 종종 “작은 변경처럼 보이는” 곳에서 납니다.

## 점검 순서

diff를 처음 볼 때 이 순서가 좋습니다.

1. 파일이 몇 개인지
2. 허용 경로를 넘었는지
3. 명백한 오삭제, 임시 로그, 디버그 잔여물이 있는지
4. 스타일과 네이밍이 맞는지

실제로 무엇을 바꿨는지 먼저 보고, 그 내용에 따라 이번 결과를 받을지 정하세요.
