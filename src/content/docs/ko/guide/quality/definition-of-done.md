“완료 정의”의 뜻은 단순합니다. 어느 정도까지 해야 이번이 진짜 완료인지 미리 말하는 것입니다.

이 단계가 없으면 흔히 이런 일이 납니다.

- 당신은 아직 조금 부족하다고 느낌
- Codex는 이미 끝났다고 느낌
- 둘 다 틀리지 않았고, 기준만 맞지 않음

## 왜 이 단계가 중요한가

많은 재작업은 “완료” 기준을 처음부터 분명히 말하지 않은 데서 납니다.

예:

- 문구만 바꾸면 되나, 페이지 미리보기도 정상이어야 하나?
- 빌드만 통과하면 되나, 버튼을 손으로도 눌러 봐야 하나?
- 기능만 되면 되나, 설명 문서도 보강해야 하나?

미리 말하지 않으면 서로 다른 말을 하기 쉽습니다.

개인 최소 완료 정의 예시:

- [ ] diff를 심사함
- [ ] 검증 기준을 항목별로 체크함
- [ ] 테스트 또는 수작업 검증을 마침
- [ ] 키가 저장소에 들어가지 않음
- [ ] 후속 이슈를 기록함

팀 버전은 이후 거버넌스 마일스톤에서 확장합니다.

## 흔한 오해

### 1. 완료 정의가 꼭 형식적이고 복잡해야 하나?

1단계에서는 세 줄만 써도 도움이 됩니다.

- 어디를 고칠지
- 어떻게 검증할지
- 어떤 경우 미완료인지

### 2. “목표”와 같지 않음

이렇게 나누세요.

- **목표**: 어떤 결과를 원하는가
- **완료 정의**: 그 결과에 도달했음을 어떻게 증명하는가

예:

- 목표: 홈 버튼 문구 수정
- 완료 정의: 홈만 수정; 버튼 문구가 새 버전; 페이지 미리보기 정상

### 3. 매번 길게 써야 하나?

아닙니다.

길게보다 분명하게가 더 중요합니다.

## 짧은 템플릿

이 버전도 충분합니다.

```text
완료 기준:
1. 지정 범위만 수정
2. 내가 준 요구에 맞음
3. 검증 단계를 마치고, 어떻게 확인하는지 알려 줌
```

“완료 정의”는 “어느 정도까지면 끝난 것인지”를 분명히 말해, 당신과 Codex의 판단이 어긋나지 않게 합니다.
