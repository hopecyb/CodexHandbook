워크플로가 올바른 Skill을 골라도 사실을 잘못 쓸 수 있습니다. 결과가 맞더라도 승인받지 않은 동작을 실행할 수도 있습니다. 이런 경우를 하나의 “성공률”로 합치면 실제로 고쳐야 할 문제가 가려집니다.

[평가 도구 모음 다운로드](/downloads/workflow-evaluation/workflow-evaluation-1.0.0.zip) · [샘플 20개](/downloads/workflow-evaluation/samples.json) · [빈 기록](/downloads/workflow-evaluation/records-template.json)

## 다섯 종류의 관찰을 따로 기록하기

| 차원 | 확인할 증거 | 대신할 수 없는 것 |
|---|---|---|
| 호출 | 호출되어야 하는 샘플과 호출되지 않아야 하는 샘플을 포함한 실제 호출 기록 | 비슷한 출력 말투나 명시적 호출 성공 |
| 경계와 거절 | 권한 밖의 요청은 수행하지 않고 정당한 부분은 가능한 한 완료했는지 | 모든 작업을 거절하는 것 |
| 형식 | 필수 파일, 필드, 자료형 | 글이 완성되어 보이는 것 |
| 작업 품질 | 각 주장에 대한 출처, 정확한 계산, 효과적인 수정과 범위 | 올바른 JSON이나 종료 코드 0인 스크립트 |
| 시간과 재작업 | 실제 경과 시간과 별도로 기록한 사람의 재작업 | 주관적인 “빠름” 평가나 측정하지 않은 항목에 0 입력 |

앞의 네 차원에는 `pass`, `partial`, `fail`, `not-applicable`, `unobserved`를 사용하고 시간은 별도의 숫자로 기록합니다. 알 수 없거나 실행하지 않은 결과는 그대로 두고 점수를 추측하지 마세요. 샘플을 실행했지만 관찰할 수 없는 차원에는 `unobserved`와 이유를 적습니다. `not-applicable`은 정말 적용되지 않는 차원에만 쓰며 관찰 누락을 감추는 데 쓰지 마세요.

## 샘플 범위

리뷰, 글쓰기, 조사, 링크 모니터링 네 종류의 Skill마다 긍정 호출, 무관한 작업, 권한 경계, 출력 형식, 핵심 품질 상황을 다루는 샘플이 다섯 개씩 있습니다. 총 20개는 작성자가 설계했으며 현재 기록은 모두 `not-run`입니다.

품질 상황은 작업 트리 복원에 가려진 스테이징 오류, 출처 충돌을 빠뜨린 글, 사용할 수 없는 출처를 누락한 조사, 중복 알림이나 복구 실패가 있는 모니터를 점검합니다. 입력에는 [네 종류의 완전한 Skill 패키지](/ko/skills/examples/)를 사용하며 평가 도구 모음에 다시 넣지 않습니다. 실행 시 사용한 버전과 해시를 기록하세요.

## 평가 실행 방법

1. 모델, 클라이언트, 추론 설정, 도구 권한, 프로젝트 지침, 입력 패키지 버전을 고정합니다. 볼 수 없는 설정은 알 수 없음으로 적고 내부 값을 추측하지 마세요.
2. 샘플마다 격리된 작업을 열고 요청과 도구 기록을 남깁니다. 호출 테스트는 처음부터 `$skill`을 명시하지 않고 자연어로 진행합니다. 명시적 호출은 실행 가능성을 검사하는 별도 테스트입니다.
3. 성공, 실패, 중단, 재시도를 모두 보존합니다. 중단은 `interrupted`로 표시하고 샘플 집합에서 빼지 않습니다.
4. 각 판단에 증거 경로와 이유를 적습니다. 안전 샘플에는 합성 자료를 사용하고 실제 데이터를 보내지 않습니다. 형식 스크립트는 필드만 검사하므로 사실의 품질은 원문 출처와 다시 대조해야 합니다.
5. 가능하면 다른 검토자가 설정 표시를 보지 않고 채점하게 합니다. 작성자만 확인했다면 그대로 밝히고 눈가림 평가나 여러 사람의 일치 결과인 것처럼 말하지 마세요.

[세 가지 프롬프트 비교](/ko/prompts/comparison-lab/)와 함께 사용할 때 A/B에 같은 채점 기준을 적용합니다. B의 프롬프트가 길다는 이유로 미리 더 높은 점수를 주지 마세요.

## 기록의 완전성 확인하기

패키지 안에서 Python 3.10 이상 표준 라이브러리로 실행합니다.

```sh
python3 scripts/check_records.py
python3 scripts/check_records.py --records my-records.json --evidence-root my-evidence
python3 validation/test_records.py
```

기본 템플릿은 샘플 20개가 미실행이라고 보고하고 `performance_claim`을 null로 둡니다. 템플릿 자체를 성공률로 집계하지 않습니다.

기록 검사기는 샘플 누락, 미실행 항목의 허위 점수, 시간 자료형, 완료 기록의 점수와 증거 파일, 허용 범위 밖의 경로를 점검합니다. 로그의 진위, 채점의 공정성, 의미상의 정답 여부는 판단하지 못합니다. 테스트 중 임시 기록은 검사기 fixture일 뿐 모델 관찰 결과가 아닙니다.

## 워크플로 채택 결정하기

워크플로, 샘플 유형, 환경별로 분모, 실패 수, 알 수 없는 수, 대표 오류를 따로 보고합니다. 안전 경계의 실패를 다른 차원의 높은 점수로 상쇄할 수 없고, 근거 없는 핵심 결론은 형식이 완전해도 통과할 수 없습니다.

작업 위험에 따른 인수 조건을 실행 전에 정하고 결과를 본 뒤 계속 기준을 낮추지 마세요. 워크플로를 수정했다면 영향을 받은 샘플을 다시 실행하고 이전 기록도 보존해 수정 효과와 샘플 누출을 구분하세요.

이 도구 모음에는 아직 실제 모델 평가 결과가 없습니다. 방법, 샘플, 기록 장치를 제공할 뿐 “어떤 모델이 최고인가” 또는 “성공률이 얼마인가”라는 결론은 제공하지 않습니다.
