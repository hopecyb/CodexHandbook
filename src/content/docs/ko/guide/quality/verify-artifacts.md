여기서 말하는 “산출물”은 작업이 마지막에 넘기는 내용입니다. 예:

- 문서 한 편
- 페이지 하나
- 이미지 한 장
- 표 하나
- 생성된 파일 하나

코드가 맞아 보인다고 산출물도 맞다고 기본 가정하지 마세요.

## 왜 산출물을 따로 검증하나

많은 작업이 넘기는 것은 코드 diff만이 아니라, 사용자가 실제로 보고 쓰는 내용입니다.

산출물을 검증할 때 보통 봅니다.

- 최종물이 쓸 수 있는지
- 표현이 기대에 맞는지
- 남에게 줄 때 어색하거나, 틀리거나, 빠져 보이지 않는지

어떤 문제는 코드 층이 아니라 최종 표현 층에 있습니다.

예:

- 페이지 코드는 도는데 레이아웃이 틀림
- 문안 구조는 맞는데 읽기가 어색함
- 링크 형식은 맞는데 열면 틀림
- 표는 생성됐는데 필드 순서가 사용 습관에 안 맞음

그래서 “생성됐다” ≠ “쓸 수 있다”.

비코드 산출물: 파일을 열고, 링크를 확인하고, 디자인과 대조하고, 문안을 한 번 소리 내어 읽으세요. 페이지: 실제 기기나 브라우저 미리보기 — 생성 코드만 보지 마세요.

## 산출물 유형별 점검

유형에 따라 어떻게 검증할지 정하세요.

- **페이지**: 실제 렌더, 레이아웃, 링크, 인터랙션
- **문서**: 구조, 용어, 가독성, 링크
- **이미지**: 크기, 선명도, 글자, 세부
- **표 또는보내기 파일**: 필드, 순서, 열림 여부, 가독성

## 흔한 오해

### 1. 빌드가 통과해도 페이지에 문제가 없을 뜻은 아님

빌드 통과는 “생성될 수 있다”만 말하고, “모양이 맞고, 내용이 맞고, 인터랙션이 맞다”고는 말하지 않습니다.

### 2. 문서형 내용도 검증이 필요

필요합니다.

특히:

- 제목 계층이 합리적인지
- 링크가 클릭 가능하고 맞는지
- 용어가 앞뒤로 일치하는지
- 문안이 자연스럽고 읽기 좋은지

### 3. 스크린샷만으로는 부족

스크린샷은 대략을 빠르게 보기엔 좋지만, 많은 문제는 실제 파일이나 실제 페이지를 열 때만 드러납니다.

## 바로 적용

이렇게 요구할 수 있습니다.

```text
끝난 뒤 최종 산출물 관점으로 한 번 자체 점검하고, 실제로 무엇을 열어 봤는지, 무엇을 발견했는지, 아직 검증하지 못한 것이 무엇인지 알려 주세요.
```

## 점검 순서

이 순서로 점검하세요.

1. 진짜 산출물을 먼저 연다
2. 검증 요구를 항목별로 대조한다
3. 경험 층의 작은 문제가 있는지 본다

실행된다는 것은 기초가 깨지지 않았다는 뜻일 뿐입니다. 납품할 수 있는지는 최종 사용 효과를 봐야 합니다.
