Agent 작업이 다루는 것은, 작업을 **검증 가능한 완료 상태까지** 가져가는 방법입니다. 언제 먼저 계획을 세울지, 언제 하위 작업을 나눌지, 언제 중간에 궤도 수정을 할지, 언제 인수인계·재개를 할지 — 이 장이 푸는 문제입니다.

이 장은 협업 방식을 다루며, 단일 기능이 아닙니다.

많은 작업의 어려움은 요구를 말하는 데가 아니라, “정말 끝났고 점검할 수 있는” 상태까지 끌고 가는 데 있습니다.

## 이 장이 말하는 것

- 작업이 복잡할 때 어떻게 먼저 계획으로 수렴할지
- 실행 중 빗나감을 발견하면 어떻게 작은 걸음으로 궤도 수정할지
- 어떤 하위 문제를 Subagent에 넘길 가치가 있는지
- 긴 작업이 끊긴 뒤 어떻게 인수인계·재개할지

## 자주 쓰는 프레임

Agent 작업은 대략 네 연속 동작으로 볼 수 있습니다.

```text
먼저 이해 → 이어서 계획 → 실행 중 궤도 수정 → 마지막에 인수인계/마무리
```

중간 단계가 빠지면 흔한 결과는 각각:

- 이해 없음: 방향이 틀림
- 계획 없음: 반쯤 하다 범위가 통제 불능
- 궤도 수정 없음: 고칠수록 더 빗나감
- 인수인계 없음: 긴 작업이 끊긴 뒤 어디까지 했는지 모름

## 흔한 오해

### 1. Agent 작업은 프롬프트를 길게 쓰는 것?

충분하지 않습니다.

프롬프트는 시작점일 뿐이고, 작업 품질을 결정하는 것은 또 있습니다.

- 계획이 있는가
- 중간 궤도 수정이 있는가
- 복잡한 부분을 나눴는가
- 이어갈 수 있는 상태를 남겼는가

### 2. 중간에 방향을 바꾸면 앞이 전부 헛수고?

많은 경우, 실행하면서 범위를 좁히는 것이 정상 실천이며, 처음부터 모든 말을 맞출 필요는 없습니다.

### 3. Subagent로 나누면 무조건 더 효율적?

항상은 아닙니다.

경계가 분명하지 않으면 하위 작업이 늘수록 메인 스레드가 더 어지러워집니다.

## 이 장과 다른 장의 관계

- 완전한 메인 워크플로가 필요하면: [탐색—계획—실행—검증](/cases/workflows/explore-plan-execute-verify/)
- 작업을 분명히 말해야 하면: [프롬프트](/prompts/)
- 컨텍스트 관리가 필요하면: [컨텍스트](/guide/context/)
- 다인/다중 작업 병행이 필요하면: [병렬 Agent](/guide/desktop-app/parallel-agents/)와 [다중 Agent 협업](/cases/workflows/multi-agent-coordination/)

## 먼저 이 최소 흐름을 통과

가장 기본적인 방식으로 작업을 통과시키려면 이 4단계로:

1. 작업을 분명히 말함
2. 복잡하면 먼저 계획을 받게 함
3. 실행 중 결과에 따라 작은 걸음으로 궤도 수정
4. 끝내기 전에 검증 가능한 결과를 요구

이 4단계를 익힌 뒤 Subagent와 인수인계를 배우면 더 자연스럽습니다.

Agent 작업은 계획·실행·궤도 수정·마무리 안에서 작업이 올바른 방향으로 계속 나아가는지를 더 중시합니다.

## 흔한 함정

- Agent를 검색창처럼 쓰고 모호한 목표 한 줄만 줌
- “중간 말 바꾸기”가 전부 뒤집기와 같다고 생각
- 긴 작업인데 인수인계 산출물이 전혀 없음
- 하위 작업을 나눌 때 경계를 주지 않아 메인 스레드가 더 어지러움
