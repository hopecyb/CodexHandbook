“바로 고쳐”라고만 말하면 흔한 문제는 다음과 같습니다.

- 경로를 잘못 잡음
- 범위가 커짐
- 위험이 미리 드러나지 않음
- 검증 방식이 근본적으로 부족함

계획은 “어떻게 할 준비인지”를 먼저 꺼내 보여 주는 일입니다.

계획의 의미는 “당신이 이렇게 할 줄 알았다”를 **심사 가능한 중간 산출물**로 바꾸는 것입니다. 특히 복잡한 작업에서 당신이 승인하는 것은 “시작” 버튼만이 아니라 실행 경로입니다.

## 먼저 계획을 받으면 확인하는 것

Codex에게 “먼저 계획을”이라고 하면, 사실 두 가지를 확인하는 것입니다.

- 목표를 진짜 이해했는지
- 가려는 경로를 당신이 감수할 의향이 있는지

## 합격 계획에 최소한 들어갈 것

| 요소 | 역할 |
|---|---|
| 단계 | 작업에 순서를 주고, 한꺼번에 들이받지 않게 |
| 관련 파일 또는 범위 | 영향면을 미리 드러냄 |
| 위험과 확인 대기 항목 | 가정을 사실로 두지 않게 |
| 검증 방식 | “완료”를 증명 가능하게 |

“A 고치고 B 고친다”만 있고 위험·검증이 없으면 할 일 목록에 가깝고, 진짜 계획은 아닙니다.

## 흔한 함정

### 1. 계획은 단계를 나열하는 것?

진짜 쓸모 있는 계획은 최소한 다음도 말해야 합니다.

- 어떤 파일·영역에 영향이 있는지
- 어디에 불확실성이 있는지
- 끝난 뒤 어떻게 진짜 완료를 증명하는지

### 2. 작은 작업은 계획이 영원히 필요 없다?

절대적이지는 않습니다. 변경이 작아도 다음이면 먼저 멈추고 말하게 할 가치가 있습니다.

- 저장소를 잘 모름
- 권한이나 승인이 관여함
- 빗나가면 수습이 어려움

### 3. 먼저 계획을 받으면 형식만 느는가?

전제는 당신이 실제로 심사하는 것입니다. 계획을 받게 하고도 범위·위험·검증을 보지 않으면 형식이 됩니다. 하지만 그것으로 이탈을 일찍 잡으면 재작업이 보통 많이 줄어듭니다.

## 언제 반드시 먼저 계획하나

- 여러 파일 또는 여러 모듈이 관여
- 저장소를 잘 모름
- 사람 승인 후 실행해야 함
- 변경이 온라인 동작이나 팀 협업 규칙에 영향할 수 있음
- “빗나가면 수습이 어렵다”고 이미 느낌

작은 문안 변경은 정식 계획이 필수는 아니지만, 중·대형 작업은 먼저 멈추는 편이 좋습니다.

## 헷갈릴 때 판단하기

먼저 계획할지 모르겠으면 스스로에게 한 문장만 물으세요.

> **지금 바로 시작하게 두면, 빗나갔을 때 수습이 어려울까?**

답이 “그렇다”면 먼저 계획을 받으세요.

## 권장 계획 요청 방식

직접 시작하지 말고 먼저 계획을 받게 하세요.

```text
먼저 파일은 고치지 마세요. 현재 저장소 기준으로 계획을 주세요. 포함:
1. 목표 이해
2. 단계 번호
3. 관련 파일
4. 위험 또는 확인 대기 항목
5. 단계마다 검증 방법
```

더 완전한 쓰기는 [먼저 계획 받기](/prompts/ask-for-a-plan/)를 보세요.

## 무엇을 심사하나

계획을 볼 때 “맞는 말처럼 들리는가”만 보지 말고 이 질문을 보세요.

1. 진짜 목표를 이해했는가
2. 영향 범위가 합리적인가
3. 명백한 사전 점검을 건너뛰었는가
4. 검증 방식이 완료를 충분히 증명하는가

많은 재작업은 구현이 나빠서가 아니라, 모호한 계획을 승인했기 때문입니다.

계획을 먼저 보면 파일을 고치기 전에 경로와 위험을 분명히 말할 수 있고, 비용도 더 낮습니다.

## 계획에 피드백 주기

계획 전체를 다시 쓸 필요는 없고, 이탈만 지적하세요.

```text
1단계는 유지하고, 2단계 리팩터는 아직 하지 마세요.
DB 변경은 독립 단계로 쪼개세요.
실패 시 롤백 방안을 보완하세요.
먼저 읽기 전용 분석만 하고 구현에 들어가지 마세요.
```

이런 “작은 걸음 궤도 수정”이 “전부 뒤집기”보다 보통 더 효율적입니다.

## 계획과 실행의 경계

중요한 협업 습관은 둘을 나누는 것입니다.

- **계획 단계**: 탐색, 옵션 나열, 불확실성 드러내기 허용
- **실행 단계**: 확인된 경로로 추진

실행 중 전제가 바뀌면 억지로 밀지 말고 계획으로 돌아가세요. [진행과 유도](/guide/agent-work/progress-and-steering/)를 참고하세요.

## 고위험 작업 계획에 세 가지 더하기

여러 파일, 외부 시스템, 권한 설정, 자동화 스크립트, 팀 규칙을 건드리는 작업이라면 계획에 다음을 추가해야 합니다.

| 추가 항목 | 중요한 이유 |
|---|---|
| 권한 경계 | 무엇이 읽기 전용이고 무엇이 사람 확인이 필요한지 |
| 복구 방법 | 방향이 틀렸을 때 안전 상태로 돌아가는 방법 |
| 단계적 적용 | 테스트 디렉터리, 예제 프로젝트, 작은 범위에서 먼저 검증 |

계획은 읽기 전용 분석, 최소 변경, 검증, 롤백으로 나눠 요청하세요. 외부 시스템 쓰기나 일괄 쓰기는 바로 실행하지 말고 먼저 목록화해야 합니다.

## 흔한 실수

- 계획에 검증 방식이 없음
- 확인 없이 계획에서 실행으로 점프
- 독립 목표 여러 개를 한 계획에 뭉침
- 확인이 필요한데도 “시작했습니다”만 씀
