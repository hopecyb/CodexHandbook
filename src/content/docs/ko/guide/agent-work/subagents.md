**Subagent**는 메인 Agent가 특정 하위 문제를 위해 시작하는 **독립 작업 단위**입니다. 상대적으로 격리된 컨텍스트를 갖고, 완료 후 결과를 메인 스레드로 모아 줍니다.

Subagent를 “분명한 작은 작업을, 그 일만 보는 조수에게 따로 맡기는 것”으로 이해하세요. 가치는 “더 멋짐”이 아니라 “더 깨끗하고, 더 집중되며, 병행하기 쉬움”에 있습니다.

## 핵심 개념 하나

| 메인 Agent | Subagent |
|---|---|
| 전역 목표와 사용자 대화를 보유 | 단일 하위 작업에 집중 |
| 컨텍스트에 전체 이력 포함 | 컨텍스트가 더 깨끗해 깊이 파기에 적합 |
| 결과 조율·병합 | 탐색·검색·전문 구현 실행 |

[병렬 Agent](/guide/desktop-app/parallel-agents/)와의 차이: Subagent는 보통 **메인 Agent가 능동적으로 위임**하는 작업 단위이며, 사용자가 창을 여러 개 여는 것과는 다릅니다(제품 구현이 겹칠 수 있으며 현재 UI 기준).

## 언제 나눌 가치가 있나

작업이 크다고 무조건 나누는 것이 아닙니다. 다음을 발견할 때입니다.

- 하위 문제 자체가 따로 깊이 파야 함
- 그 하위 문제가 메인라인과 다른 종류의 일
- 독립 결론을 먼저 받고 돌아오길 원함

이때 Subagent로 나누면, 메인 스레드가 전역과 세부를 동시에 챙기는 것보다 보통 더 안정적입니다.

## 적용 장면

| 적합 | 부적합 |
|---|---|
| 큰 저장소에서 「인증 모듈이 token을 어떻게 검증하는지」 지향 검색 | 사용자와 계속 요구를 주고받아야 함 |
| 두 기술 방안을 병행 조사 | 하위 작업이 같은 파일의 배타 편집에 강하게 의존 |
| 긴 읽기 전용 분석으로 메인 컨텍스트 오염 방지 | 명확한 산출물 없는 「그냥 한번 보기」 |

## 흔한 오해

### 1. Subagent는 많을수록 좋다?

너무 많이 나누면 새 비용이 생깁니다.

- 반환 결과를 더 많이 읽어야 함
- Subagent끼리 결론이 싸울 수 있음
- 조율 비용이 이득보다 클 수 있음

### 2. 작업이 복잡하면 바로 Subagent?

반드시는 아닙니다.  
문제가 강하게 결합되어 자주 확인이 필요하면, 메인 스레드에서 바로 추진하는 편이 더 절약됩니다.

### 3. Subagent가 변경까지 알아서 해 줄까?

위임 방식에 따라 가능하지만, 기본으로 더 안정적인 방법은:

- 먼저 Subagent에 읽기 전용 분석·비교·위치 찾기
- 메인 스레드가 결론을 본 뒤 수정에 들어갈지 결정

## 권장 워크플로

### 1. 메인 Agent가 하위 작업 계약을 분명히

```text
하위 작업: packages/auth 의 session 갱신 로직을 읽기 전용으로 분석.
납품: 1페이지 이내 요약 + 핵심 파일 경로 + 위험 포인트.
금지: 어떤 파일도 수정하지 말고, push 하지 마세요.
```

형식보다 중요한 것은 네 가지를 분명히 하는 것입니다.

- 정확히 무엇만 담당하는지
- 산출이 어떤 모습이어야 하는지
- 어떤 동작을 하면 안 되는지
- 반환 후 누가 결정하는지

### 2. Subagent가 실행하고 구조화 결과를 반환

기대 형식:

```text
## 결론
## 증거(파일:행 번호)
## 권장 다음 단계
## 미해결 문제
```

### 3. 메인 Agent가 병합·결정

메인 스레드(또는 당신)가 어느 경로를 채택할지 정한 뒤, [탐색—계획—실행—검증](/cases/workflows/explore-plan-execute-verify/)의 실행 단계로 들어갑니다.

### 4. 검증

- Subagent 출력이 독립 검증 가능한가(파일을 열어 대조 가능)
- 저장소를 월권 수정하지 않았는가
- 여러 Subagent 결론이 충돌할 때 표시했는가

## 이 조건으로 판단

하위 작업이 아래 3개 중 2개를 만족하면 나누기를 고려하세요.

1. 독립적으로 서술 가능
2. 명확한 산출물이 있음
3. 메인 스레드와 잘게 쪼개진 컨텍스트를 자주 공유할 필요가 없음

## Skill·MCP와의 협력

- **Skill**: 하위 작업의 표준 납품 형식 정의(예: 보안 심사 체크리스트)
- **MCP**: Subagent가 외부 티켓을 읽기 전용 조회, 메인 Agent가 종합 결정

## 흔한 실수

- Subagent 범위가 너무 커 두 번째 메인 Agent가 됨
- 구조화 반환을 요구하지 않아 메인 스레드가 긴 로그를 다시 읽음
- 여러 Subagent가 같은 디렉터리를 동시에 수정

Subagent는 “경계가 분명하고, 납품이 명확하며, 독립 완료 가능한” 하위 문제에 가장 맞으며, 메인 작업 전체를 한 번 더 복제하기엔 맞지 않습니다.
