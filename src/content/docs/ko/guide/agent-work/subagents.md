**서브 에이전트(Subagent)**는 주 Agent가 명확한 하위 문제 하나를 위해 시작하는 독립적인 작업 단위입니다. 자체 컨텍스트에서 작업하고 완료 후 결론과 근거를 주 스레드에 돌려줍니다. 전체적인 결정과 최종 검수 책임은 여전히 주 Agent에게 있습니다.

![Codex 서브 에이전트 구성: 주 Agent가 범위가 명확한 하위 작업을 나누고, 서브 에이전트가 근거를 반환하며, 주 Agent가 이를 종합하고 검증합니다](/diagrams/subagent-orchestration-ko.svg)

## 먼저 세 가지 관계 이해하기

| 영역 | 분리 여부 | 의미 |
|---|---|---|
| 대화 컨텍스트 | 분리됨 | 각 서브 에이전트는 자기 작업에 집중하며 주 스레드의 모든 세부 사항을 가져갈 필요가 없음 |
| 샌드박스와 권한 모드 | 상속됨 | 독립적으로 실행된다는 이유로 더 높은 권한을 얻지 않음 |
| 작업 공간 파일 | 반드시 분리되지는 않음 | 여러 Agent가 같은 작업 공간을 볼 수 있어 동일 파일을 병렬로 쓰면 충돌할 수 있음 |

가장 중요한 점은 **컨텍스트 분리가 파일 분리를 뜻하지는 않는다**는 것입니다. 코드를 병렬 수정하려면 먼저 디렉터리, 구성 요소 또는 worktree 단위로 소유 범위를 나누세요.

## 현재 어디에서 사용할 수 있나

현재 Codex 버전은 기본적으로 서브 에이전트 기능을 제공하며, 데스크톱 App, CLI, IDE의 해당 화면에서 활동을 볼 수 있습니다. 화면 구성은 바뀔 수 있지만 사용 방법의 핵심은 안정적입니다. Codex에 독립적인 하위 작업을 명시적으로 위임하고, 주 스레드에 결과 종합을 맡기세요.

CLI에서는 `/agent`로 스레드를 보거나 전환할 수 있습니다. IDE는 지원 화면에 백그라운드 Agent를 표시하고, 데스크톱 App은 작업 중 스레드 활동을 보여 줍니다. 특정 컨트롤이 보이는지는 현재 클라이언트와 계정 기능에 따라 확인하세요.

## 언제 작업을 나눌 가치가 있나

하위 작업이 다음 세 조건 중 두 가지를 충족한다면 분리를 고려할 만합니다.

1. 주 작업의 세부 사항을 자주 동기화하지 않아도 독립적으로 설명할 수 있습니다.
2. 파일 목록, 테스트 결과, 한 페이지 분량의 결론처럼 명확한 결과물이 있습니다.
3. 다른 작업과 병렬로 진행할 수 있거나, 따로 깊이 조사하면 주 스레드의 잡음을 크게 줄일 수 있습니다.

### 병렬로 처리하기 좋은 일

- 프런트엔드, 백엔드, 테스트 범위를 각각 읽기 전용으로 조사하기
- 서로 의존하지 않는 여러 실패 테스트를 동시에 조사하기
- 두 기술 방안의 근거를 각각 수집하기
- 전문 역할에 보안 검토, 성능 분석, 문서 대조를 맡기기

### 주 스레드에 두기 좋은 일

- 요구 사항이 아직 불분명해 사용자와 계속 대화해야 하는 작업
- 여러 단계가 엄격하게 순서대로 실행되어야 하는 작업
- 수정이 동일한 파일이나 코드 구간에 집중되는 작업
- 완료 기준 없이 “대충 살펴보기”만 요구하는 작업

서브 에이전트는 token 사용량과 결과 종합 비용을 늘립니다. 명확한 스레드 하나로 끝낼 수 있는 작은 작업을 병렬 처리하기 위해 억지로 나눌 필요는 없습니다.

## 주 Agent의 책임은 사라지지 않습니다

주 Agent는 항상 다음 네 가지를 맡아야 합니다.

- 전체 목표, 사용자 제약, 최종 결정
- 하위 작업의 경계와 파일 소유 범위
- 여러 결론이 충돌할 때의 판단
- 결과를 합친 뒤의 테스트, 빌드, 위험 설명

서브 에이전트가 “완료”를 반환하는 것은 하위 작업의 신호일 뿐, 전체 작업의 완료를 입증하지 않습니다.

## 검수할 수 있는 위임 계약 작성하기

다음은 읽기 전용 조사 작업의 예시입니다.

```text
서브 에이전트 하나를 시작해 packages/auth의 session 갱신 로직을 읽기 전용으로 분석하세요.

범위: packages/auth와 해당 테스트. 파일을 수정하지 마세요.
질문: 갱신에 실패한 후에도 이전 token이 다시 사용될 수 있나요?
결과물: 결론, 핵심 파일과 줄 번호, 재현 경로, 권장 테스트.
검증: 모든 결론을 소스 코드나 기존 테스트로 확인할 수 있어야 합니다.
반환: 500자 이내로 정리하고, 수정 여부는 주 스레드가 결정합니다.
```

이 계약에는 담당할 일, 살펴볼 범위, 답할 질문, 금지된 일, 검증 방법, 결정권자가 명시되어 있습니다.

## 세 갈래로 병렬 조사하는 예시

로그인 기능에 간헐적인 회귀가 생겼다면 주 Agent는 다음과 같이 나눌 수 있습니다.

| 하위 작업 | 권한과 범위 | 결과물 |
|---|---|---|
| A: 코드 경로 | `src/auth/` 읽기 전용 | 진입점부터 실패 분기까지의 호출 흐름 |
| B: 테스트 근거 | 테스트와 로그 읽기 전용 | 안정적으로 재현하는 최소 테스트 |
| C: 최근 변경 | 관련 Git 기록 읽기 전용 | 회귀를 일으켰을 가능성이 큰 변경과 그 근거 |

세 결과가 돌아오면 주 Agent는 먼저 근거를 비교한 다음 수정 방향 하나를 선택해야 합니다. A, B, C가 동시에 `src/auth/session.ts`를 수정하게 하지 마세요.

## 병렬 쓰기가 필요할 때 격리하는 방법

충돌을 줄이려면 다음 순서를 우선 적용하세요.

1. 쓰기 작업을 서로 겹치지 않는 디렉터리나 구성 요소로 나눕니다.
2. 병렬 구현에 각각 별도의 worktree나 브랜치를 배정합니다.
3. 각 Agent가 수정할 수 있는 파일 목록을 명시합니다.
4. 주 Agent가 한곳에서 합치고, 합친 뒤 다시 검증합니다.

각 하위 작업의 테스트가 모두 통과해도 합친 결과는 실패할 수 있으므로 최종 검증을 생략해서는 안 됩니다.

## 검수 체크리스트

- 반환 내용이 범위를 넓히지 않고 원래 질문에 답했는가?
- 파일 위치, 로그, 테스트처럼 확인 가능한 근거가 있는가?
- 읽기 전용, 디렉터리, 명령 제한을 지켰는가?
- 여러 결과가 서로 모순되는가? 모순을 명시적으로 해결했는가?
- 결과를 합친 뒤 전체 테스트와 빌드를 다시 실행했는가?
- 해결되지 않은 문제와 남은 위험을 설명했는가?

## 다른 기능과 함께 사용하기

- **Skill**은 코드 검토 체크리스트처럼 하위 작업의 방법과 출력 형식을 고정합니다.
- **MCP**는 서브 에이전트에 통제된 외부 도구나 데이터를 제공합니다.
- **Hook**은 서브 에이전트가 시작하거나 종료하거나 도구를 호출할 때 추가 보호 규칙을 적용합니다.
- **Worktree**는 병렬 파일 수정을 격리합니다. 작업 공간 충돌을 해결하는 수단이며 컨텍스트 문제를 해결하는 것은 아닙니다.
