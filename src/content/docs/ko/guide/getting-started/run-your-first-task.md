아래 예시는 기본이 **데스크톱 App**입니다. CLI/IDE에서도 같은 프롬프트를 쓸 수 있습니다.

많은 사람이 Codex를 처음 쓸 때 「완전한 웹사이트」나 「프로젝트 전체 리팩터」를 바로 시킵니다. 통제를 잃기 쉽습니다.

첫 작업은 작게 하는 편이 더 안전합니다. 전체 흐름을 한 번 도는 일이, 처음부터 크게 하는 것보다 중요합니다.

## 왜 첫 작업이 이렇게 작아야 하나

첫 작업은 이 세 조건을 만족하는 편이 좋습니다.

- 변경 범위가 작음
- 결과를 한눈에 확인할 수 있음
- 잘못해도 철회하기 쉬움

그래서 여기에서는 아주 작은 연습 예를 씁니다.

## 예시 작업

연습 프로젝트에서 Codex에게 말하세요.

```text
목표：hello.md 끝에 「오늘의 연습」 절을 추가하고, 요점 목록 세 줄을 넣는다.
제약：hello.md만 수정. 기존 내용을 삭제하지 말 것. 네트워크 요청을 실행하지 말 것.
수락：파일 끝에 해당 제목과 목록 항목이 정확히 세 개 있어야 한다.
정보가 부족하면 추측하지 말고 먼저 물어볼 것.
```

## 프롬프트 각 부분의 역할

이 프롬프트는 핵심을 나누어 분명히 썼습니다.

- **목표**: 무엇을 할지
- **제약**: 어디를 함부로 고치면 안 되는지
- **수락**: 「무엇을 끝으로 볼지」
- **정보가 부족하면 먼저 물어보기**: 제멋대로 추측하지 않게

고정 템플릿이 아니라, 말하기 쉬운 부분을 분명히 쓴 것입니다.

## 흔한 오해

### 1. 첫 작업이 클수록 진짜 실력을 배운다

처음에는 완전한 루프를 한 번 도는 일이 더 중요하고, 한 번에 일을 키우는 일이 아닙니다.

### 2. 프롬프트를 쓰면 뒤에는 알아서 한다

첫 작업에서는 세 가지를 지켜보세요.

- 범위가 넘치지 않았는지
- 말한 파일에만 손대는지
- 최종 결과가 수락 기준에 맞는지

### 3. 처음에 틀리면 내가 못 쓰는 것이다

첫 작업에는 원래 이런 내용이 포함됩니다.

- 어디가 틀렸는지 발견
- 문제를 지적
- 어떻게 되돌리게 할지 알기

## 실행할 때 주의

1. 짧은 계획을 받게 하거나, 당신이 먼저 계획을 요청
2. 파일 쓰기 승인 시 경로가 맞는지 확인
3. 끝나면 [결과 확인](/guide/getting-started/review-the-result/)으로

## 실행 순서

이 5단계로:

1. 안전한 연습 프로젝트를 고름
2. 파일 하나만 고치는 작은 작업을 줌
3. 승인 전에 어디를 건드릴지 봄
4. 끝난 뒤 범위와 결과를 확인
5. 마음에 안 들면 철회하거나 더 정밀하게 교정

이 5단계를 마치면 협업 리듬이 더 익숙해집니다.

## 끝난 뒤 확인할 것

세 가지를 중점으로:

1. `hello.md`만 고쳤는지
2. 파일 끝에 그 절이 정말 생겼는지
3. 목록 항목이 정확히 세 개인지

세 가지가 맞으면 이번 작은 작업은 대체로 잘 돈 것입니다.

## 잘못했을 때

처음에 틀리는 것은 정상입니다. 이렇게 이어가면 됩니다.

```text
너무 많이 고쳤습니다. 다른 파일 변경은 철회하고, hello.md 수정만 남겨 주세요.
```

또는:

```text
지금은 더 고치지 마세요. 방금 어디를 바꿨는지 알려 주세요.
```

프롬프트 원리: [프롬프트 기초](/prompts/basics/).
