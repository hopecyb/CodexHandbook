IDE 확장의 검토 경험은 「행 단위 완성」과 「완전한 PR review」 사이에 있습니다. 변경이 에디터나 사이드 diff 뷰에 바로 나타나는 경우가 많습니다. 이 페이지는 결과를 안전하게 수락하는 방법을 설명합니다.

IDE에서 “바로 수락할 수 있는 변경”을 봐도, 「한 번에 수락」을 기본 동작으로 삼지 마세요.

## 이 페이지의 내용

- IDE에서 흔한 검토 UI 형태
- 수락·거부·부분 수락 전략
- Git·테스트·PR 흐름과의 연결

## 검토 흐름

1. **범위 보기**: 어떤 파일이 바뀌었나? 요청하지 않은 삭제나 포맷 폭풍이 있나
2. **로직 읽기**: 조건 분기, 오류 처리, 경계 케이스
3. **보안 점검**: 키, 인젝션, 권한 상승, 의존성 독성
4. **검증 실행**: 프로젝트 합의 테스트 / lint(IDE 터미널 또는 작업 스크립트)
5. **결정**: 수락, 수정 요청, 또는 되돌린 뒤 작업 재전송

방법론: [diff 검토](/guide/quality/review-diffs/)

## IDE 고유 조작(개념)

| 조작 | 제안 |
|---|---|
| Inline diff / 고스트 텍스트 | 블록을 확인한 뒤 수락; 한 번에 전부 수락 피하기 |
| 단일 파일 수락 | 위험이 작은 파일(예: 테스트)부터 |
| 거부 후 재시도 | follow-up에 「X만 고치고 Y는 건드리지 말 것」을 명시 |
| Git 연동 | 수락 후에도 `git diff`로 재확인한 뒤 commit |

데스크톱 App의 [diff, 댓글, 검토](/guide/desktop-app/diffs-comments-and-review/) 기능이 더 완전합니다. IDE 측은 **가벼운·고빈도** 검토가 중심입니다.

## 권장 prompt 습관

작업 시작 전에 다음을 넣으세요.

- 수정 허용 경로 glob
- 금지: `git push`, lockfile 수정(명시 요청이 없으면)
- 완료 시: 변경 요약 나열, **자동 commit 금지**

참고: [사람 승인 패턴](/cases/workflows/human-approval-patterns/)

## 흔한 실수

- 녹색 테스트 아이콘만 믿고 직접 실행하지 않음
- 대규모 자동 포맷 diff 안에 로직 변경이 숨음
- 수락 후 바로 push, PR / 브랜치 보호를 건너뜀

## 검수 체크리스트

- [ ] `git status`가 예상 파일과 일치
- [ ] 테스트 통과(로컬 또는 CI)
- [ ] `.env`·token·디버그 `console.log` 잔여 없음
- [ ] 커밋 메시지는 본인이 작성하거나 확인

## 흔한 질문

### 1. 인라인 제안이 작아 보이면 바로 받아도 되나요?

그 습관은 만들지 않는 편이 좋습니다.

문제는 “변경이 크다”보다 “작아 보여서 대충 본다”에 있는 경우가 많습니다.

### 2. 로직 검토가 약하면 무엇을 먼저 보나요?

다음 세 가지만 봐도 이미 가치가 큽니다.

- 원하는 파일만 바뀌었는지
- 지우면 안 되는 것을 지웠는지
- 명백한 디버그 잔여나 스타일 이탈이 있는지

### 3. 수락하면 끝난 건가요?

아직입니다.

수락은 변경을 작업 영역에 넣은 것뿐이며, 이후 검증하고 커밋 여부를 결정해야 합니다.

IDE의 “변경 수락”은 중간 동작이지, 최종 검수가 아닙니다.
