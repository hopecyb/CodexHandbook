IDE 확장은 **작은 범위·고정밀도** 변경에 잘 맞습니다. 코드 한 구간을 선택하고 의도를 말하면, Codex가 인근 컨텍스트에서 수정합니다. 여기서는 선택 영역과 열린 파일로 범위를 조여 잘못된 곳을 고치지 않게 하는 방법을 다룹니다.

선택 영역의 역할은 단순합니다. Codex에게 여기가 초점이라고 알려, 스스로 범위를 키우지 않게 합니다.

## 이 페이지의 내용

- 선택 영역 vs 전체 파일 vs @ 경로를 고르는 법
- 다중 파일 리팩터 시 컨텍스트를 짜는 법
- 「관련 없는 파일을 잔뜩 수정」을 줄이는 법

## 세 가지 한정 방식

| 방식 | 언제 쓰나 | 예시 |
|---|---|---|
| **선택 영역** | 단일 함수·컴포넌트, 오류 스택 근처 | `parseUser()`를 선택하고 빈 값 처리를 요청 |
| **열린 파일** | 파일 안 여러 연관 지점을 이해해야 할 때 | `auth.ts` + `auth.test.ts` 열기 |
| **@ 경로** | 다른 디렉터리·미개방 파일 | `@src/api/client.ts`와 백엔드 타입 맞추기 |

개념 심화: [파일과 폴더 컨텍스트](/guide/context/file-and-folder-context/)

## 최소 사용법

1. **최소 관련 조각**(보통 10–80행)을 선택하고, 프롬프트에 목표와 [완료 정의](/prompts/define-done/)를 분명히 씁니다
2. 호출 쪽이 관여하면 상위 파일 1–2개를 더 열거나 @합니다
3. 「X와 관련 있는 파일만 수정; 수정할 파일을 나열한 뒤 작업」을 요구합니다
4. IDE diff에서 블록 단위로 수락하고, 전부 수락하지 않습니다

## 다중 파일 작업

```text
열기: 구현 파일 + 테스트 파일 + 타입 정의
선택 영역: 선택—진입 함수부터
Prompt: 모듈 경계, 수정 금지 디렉터리 명시
```

큰 리팩터는 [데스크톱 App 작업 트리](/guide/desktop-app/worktrees/)나 [계획 모드](/guide/agent-work/planning/)가 더 낫습니다. IDE는 마무리와 작은 커밋에 더 적합합니다.

## 흔한 질문

### 1. 매번 선택 영역이 필요한가요?

아닙니다. 다만 초점이 작은 구간에 있다는 걸 이미 알면, “이 함수 고쳐 줘”만 보내는 것보다 선택 영역이 보통 더 안전합니다.

### 2. 많이 선택할수록 안전한가요?

너무 크면 범위를 다시 느슨하게 만든 셈이고, 너무 작으면 필요한 컨텍스트가 부족합니다. 실용 기준은 “딱 충분할 만큼”입니다.

### 3. 열린 파일과 `@` 경로의 차이는?

이렇게 나누면 됩니다.

- **열린 파일**: 지금 보고 있는 것을 보여 줌
- **@ 경로**: 특정 파일을 반드시 포함하라고 명시

선택 영역과 열린 파일의 목적은, 관련 없는 범위를 함께 끌고 가지 않는 것입니다.

## 검토와 함께

수락 전에 [diff 검토](/guide/quality/review-diffs/)와 대조하세요.

- 합의한 파일만 바뀌었는지
- 선택 영역 밖 예상치 못한 삭제가 있는지
- 테스트가 새 분기를 커버하는지

제품 측: [IDE 변경 검토](/guide/ide/reviewing-changes/)

## 흔한 실수

| 실수 | 결과 |
|---|---|
| 수천 행 전체 파일 선택 | 컨텍스트 낭비, 변경면이 과도 |
| 선택 없이 「최적화해 줘」만 말함 | 모델이 스스로 범위를 키움 |
| diff를 읽지 않고 제안 전부 수락 | 스타일 드리프트나 보안 취약점 |
