IDE에서 Codex는 프롬프트만 읽는 것이 아니라 **에디터 상태**도 자동으로 받습니다. CLI 대비 IDE의 핵심 이점입니다. 컨텍스트가 어디서 오는지 알면 “파일을 열었는데도 못 본다”는 좌절을 줄일 수 있습니다.

IDE의 Codex는 당신이 한 말만 보는 게 아니라, 지금 에디터에서 보고 있는 내용도 참고합니다.

## 이 페이지의 내용

- IDE가 자동으로 붙이는 컨텍스트
- @ 파일·선택 영역·AGENTS.md와의 겹침
- 노이즈를 줄이고 적중률을 높이는 방법

## 컨텍스트 출처(개념 층위)

| 출처 | 누가 제어 | 전형적 내용 |
|---|---|---|
| 워크스페이스 루트 | 연 폴더 | 프로젝트 구조, `AGENTS.md`, 설정 파일 |
| 현재 열린 파일 | 에디터 탭 | 편집 중인 소스 |
| 선택 영역 | 하이라이트한 코드 | 함수, 오류 조각 |
| 명시적 @ | 대화에서 @한 경로 | 다른 디렉터리 파일, 문서 |
| 프로젝트 규칙 | 저장소의 `AGENTS.md` 등 | 코딩 규약, 테스트 명령 |

우선순위와 충돌 처리는 [컨텍스트 우선순위](/guide/context/context-priority/)를 보세요.

## 권장 워크플로

1. **워크스페이스 루트로 저장소를 연다**. 하위 폴더만 열지 마세요(monorepo 예외는 팀 문서 참고)
2. 국소 로직을 고칠 때는 **관련 코드를 먼저 선택한 뒤** 작업을 설명 → [선택 영역과 열린 파일](/guide/ide/selected-code-and-open-files/)
3. 모듈을 넘는 작업은 `@`로 관련 파일을 지정하세요. 「알아서 찾을 것」이라고 가정하지 마세요
4. 긴 세션은 주기적으로 [컨텍스트를 압축](/guide/context/compaction/)하거나 새 스레드를 엽니다

## CLI와의 차이

| | IDE 확장 | CLI |
|---|---|---|
| 파일 인식 | 강함(열면 바로 컨텍스트) | `--cwd`와 도구로 디스크 읽기 필요 |
| 선택 영역 | 기본 지원 | 붙여넣기나 경로 지정 필요 |
| 적합 | 행 단위 수정, 코드 설명 | 스크립트, CI, GUI 없는 환경 |

## 흔한 질문

### 1. 파일을 열었는데도 원하는 대로 안 고치면?

“파일을 열었다”가 “초점이 충분히 명확하다”와 같지는 않습니다.

작업 범위가 모호하면, 다른 관련 내용을 보거나 가장 관심 조각을 놓칠 수 있습니다.

### 2. 연 파일이 많을수록 좋나요?

관련 없는 파일을 너무 많이 열면 컨텍스트가 시끄러워지고 초점이 희석됩니다.

### 3. IDE가 컨텍스트를 자동으로 주니 설명을 줄여도 되나요?

자동 컨텍스트는 도움이 되지만, 작업 설명을 대체하지 않습니다.  
목표·제한·완료 기준은 여전히 직접 밝혀야 합니다.

IDE 컨텍스트는 돕지만 추측을 대신하지는 않습니다. 파일 범위가 정확할수록 결과가 대체로 안정적입니다.

## 민감 정보

키가 들어 있는 `.env`를 에디터 전면에 오래 두지 마세요. [민감 컨텍스트](/guide/context/sensitive-context/)를 보세요.

로그·고객 데이터는 붙여넣기 전에 마스킹하세요. IDE가 규정을 대신 판단해 주지는 않습니다.

## 흔한 실수

- 단일 파일 모드(워크스페이스 없음)에서 `AGENTS.md`를 읽기를 기대
- 관련 없는 큰 파일을 수십 개 열어 컨텍스트 창을 잠식
- 「이 함수」라고만 말하고 선택·@를 하지 않음

## 검수 체크리스트

- [ ] 워크스페이스 루트가 올바름
- [ ] 작업 관련 파일 1–3개가 열려 있거나 @됨
- [ ] `AGENTS.md`의 테스트 명령이 IDE 터미널과 일치
