일반 챗봇과의 가장 큰 차이는 **도구**로 일을 한다는 점입니다.

파일은 고치는 장소이고, 명령은 동작을 하는 방식이며, 도구는 손을 대는 입구입니다.

Codex는 **도구**로 실제 세계에 작용합니다.

- 프로젝트 파일 읽기/쓰기
- 터미널에서 명령 실행(권한·샌드박스 정책이 허용할 때)
- 웹 검색·브라우저 열기 등(제품 능력·정책에 따름)

## 세 단어를 먼저 나누기

| 단어 | 의미 |
|---|---|
| 파일 | 프로젝트의 실제 내용. 코드·문서·설정 등 |
| 명령 | 터미널에서 실행하는 한 단계. 빌드·테스트·검색 등 |
| 도구 | 파일 읽기·수정·명령 실행·웹 검색에 쓰는 능력 입구 |

다른 각도로는:

- **파일**은 재료
- **명령**은 동작
- **도구**는 재료를 집고 동작을 하는 기구

## 흔한 작업 과정

작업을 주면 Codex가 흔히 하는 일:

1. 관련 파일을 몇 개 읽어 프로젝트 구조를 파악
2. 필요하면 텍스트 검색·디렉터리 열기·설정 확인
3. 결과 검증이 필요하면 테스트나 빌드 같은 명령 실행
4. 파일을 고친 뒤 변경을 당신에게 검토하도록 넘김

「파일을 읽겠다」「명령을 실행하겠다」는 말이 보이면, 대개 작업에 필요한 정상 단계입니다.

## 흔한 오해

### 1. 명령을 실행할 수 있으니 무엇이든 할 수 있나?

반드시 그렇지는 않습니다.

가능한지는 다음에 달립니다.

- 현재 제품 입구가 준 도구
- 샌드박스 허용 여부
- 이 단계에 승인이 필요한지
- 팀 정책의 추가 제한

### 2. 명령을 덜 돌리고 파일만 고치는 편이 빠른가?

반드시 그렇지는 않습니다.

검사 명령을 한 번 돌리면 문제를 더 일찍 잡을 수 있습니다. 코드를 고친 뒤 테스트를 돌리는 편이, 나중에 깨진 것을 발견하는 것보다 안정적입니다.

### 3. 명령을 모르면?

당장 이해가 안 되면 바로 물으세요.

```text
이 명령은 무엇을 하나요? 무엇을 바꾸나요? 실행하지 않으면 어떻게 되나요?
```

## 간단한 판단법

파일을 읽고·고치고·명령을 실행하려 할 때 세 가지를 먼저 보세요.

1. 이 단계가 내 목표와 관련 있는가?
2. 영향 범위가 기대한 디렉터리·파일인가?
3. 잘못되면 쉽게 철회할 수 있는가?

셋 중 하나에 답이 없으면 먼저 설명하게 하세요.

## 사용 원칙

1. **최소 필요 범위**: 디렉터리·파일을 지정하고 「저장소 전체를 마음대로」를 피합니다
2. **위험 명령은 승인**: 삭제·푸시·시스템 설정 변경 등
3. **도구 선택에는 방법이 있습니다**: [도구 선택](/guide/tools/tool-selection/)

제품 입구마다 도구 패널과 확인 방식이 다르며, 세부는 각 제품 매뉴얼을 보세요.

Codex는 「말하기」만이 아니라 파일·명령·도구로 실제로 손을 댑니다. 범위와 위험을 지켜보세요.
