PDF는 규격, 논문, 스캔본,보내기 보고서에 자주 씁니다. 순수 텍스트와 달리 PDF는 **구조가 복잡하고, 용량이 크며, diff하기 어려워** 작업 방식을 따로 약속해야 합니다.

PDF를 Codex에 넘길 때 가장 흔한 문제는 구조 이해가 불완전하거나, 준 범위가 너무 큰 것입니다.

## 이 페이지 내용

- Agent가 PDF 내용을 올바르게 「읽게」 하는 법
- PDF를 생성·수정할 때의 형식·경로 약속
- 검증 시 「파일은 있는데 열리지 않음」을 피하는 법

## 왜 PDF가 특히 틀리기 쉬운가

PDF는 텍스트보다 더 번거롭습니다. 동시에 포함할 수 있기 때문입니다.

- 스캔 이미지
- 다단 조판
- 머리글·바닥글
- 표
- 이미지와 글자 혼재

그래서 “어느 구간을 보고, 어떤 결과가 필요한지”를 분명히 할수록 보통 더 안정적입니다.

## PDF 읽기

### 권장 실천

1. **파일 경로를 명시**: `docs/spec.pdf` 또는 @ 참조(클라이언트 지원에 따름)
2. **무엇을 원하는지 설명**: 요약, 특정 장 대조, 표 데이터 추출
3. **페이지 또는 장**: 긴 문서는 범위를 한정해 컨텍스트를 절약
4. **민감 내용**: 계약, 신분증 스캔 등은 [민감 컨텍스트](/guide/context/sensitive-context/) 흐름

### 제한

- 스캔 PDF는 OCR이 필요할 수 있으며, 결과는 사람이 표본 점검
- 복잡한 판형·다단·각주는 구조를 잃기 쉬움
- 초대형 PDF를 한 작업에 통째로 넣지 말고 구간 처리하거나, 먼저 Markdown 개요로 변환

## 흔한 오해

### 1. PDF 전체를 넣어도 핵심을 안정적으로 뽑아 주나?

PDF가 길고, 구조가 복잡하고, 스캔 페이지가 섞이면 더 안정적인 방법은 여전히:

- 범위 지정
- 작업 지정
- 구간 처리

### 2. 스캔 PDF와 일반 텍스트 PDF는 많이 다름

스캔본은 보통 OCR에 먼저 의존하며, OCR이 틀리면 뒤 요약·추출·판단도 함께 빗나갈 수 있습니다.

### 3. PDF 파일을 하나 만들었다고 완료인가?

다음도 확인해야 합니다.

- 열 수 있는지
- 글자가 깨지지 않았는지
- 페이지 수·목차·표가 맞는지
- 한글 글꼴이 정말 임베드됐는지

## PDF 생성·갱신

| 방식 | 적합 |
|---|---|
| Markdown/LaTeX에서 컴파일 | 기술 문서, 보고서(재현 가능) |
| HTML 인쇄 | 단순 판형 |
| 라이브러리 생성(예: reportlab) | 프로그램식 영수증, 라벨 |

prompt에 분명히:

- 출력 경로와 파일명
- 페이지 크기, 언어, 글꼴 요구(한글 PDF는 글꼴 임베드에 특히 주의)
- Git에 커밋할지(큰 바이너리는 보통 artifact 또는 release)

## 바로 쓸 수 있는 쓰기

이렇게 요청하세요.

```text
`docs/spec.pdf` 의 12–18페이지만 읽고, 그안의 검증 기준을 추출하세요.
문서 전체를 요약하지 마세요.
OCR이나 판형 인식이 불확실하면 명시하세요.
```

## 저장소 전략과의 관계

- 큰 바이너리 PDF는 **Git LFS** 또는 저장소 밖
- diff가 읽히지 않으면 검증은 **파일 열기** + [산출물 검증](/guide/quality/verify-artifacts/) 대조
- 생성물 목록은 [생성물 검증](/guide/files-and-artifacts/generated-artifacts/)

## 흔한 실수

- 「PDF에서 글자 하나 고쳐」라고 하면서 편집 가능 원본(`.md` / `.tex`)을 주지 않음
- 기밀 PDF를 공개 저장소에 넣고 Cloud로 처리
- 열어 검증하지 않고 「파일 존재」만 봄

## 검증 체크리스트

- [ ] 목표 리더/인쇄 환경에서 PDF가 열림
- [ ] 페이지 수·목차·핵심 표가 기대와 일치
- [ ] 저장소 용량과 LFS 정책이 팀 규범에 맞음

PDF를 다룰 때는 범위가 분명할수록 안정적입니다. PDF를 생성한 뒤에도 파일 유무만 보지 말고, 정상 열림과 내용이 진짜 맞는지 확인하세요.
