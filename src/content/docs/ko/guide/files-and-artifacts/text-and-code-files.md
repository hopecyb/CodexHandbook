대부분의 개발 작업은 **텍스트와 코드 파일**에 떨어집니다. 소스, 테스트, 설정, Markdown. 이 페이지는 범위를 한정하고, 스타일을 맞추며, 안전하게 병합하는 방법을 설명합니다.

Codex에 텍스트·코드 파일을 고치게 할 때 핵심은, 맞는 곳을·맞는 방식으로 고치고, 함께 너무 많이 고치지 않는 것입니다.

## 이 페이지 내용

- 변경이 올바른 경로·인코딩에 떨어지게 하는 법
- 다중 파일 편집을 조직하는 방식
- formatter·linter와의 조율

## 파일 유형과 주의점

| 유형 | 주의 |
|---|---|
| 소스 `.ts` `.py` 등 | `AGENTS.md`와 기존 패턴을 따름 |
| 설정 `.json` `.yaml` `.toml` | 구조가 깨지기 쉬움; 유효 문법 요구 |
| 문서 `.md` | 링크 상대 경로, 한·영 혼용 규범 |
| 생성 코드 | 커밋할지 gitignore할지 명시 |

컨텍스트: [파일과 폴더 컨텍스트](/ko/guide/context/file-and-folder-context/)

## 왜 이런 파일이 가장 틀리기 쉬운가

진짜 문제가 나기 쉬운 곳은 종종:

- 건드리면 안 되는 파일에 씀
- 조금만 고치려다 큰 덩어리를 함께 다시 씀
- 스타일이 프로젝트 기존 쓰기와 불일치
- 설정 파일 문법이 몰래 깨짐

## 권장 prompt 구조

```text
목표: <한 문장>
허용 수정: <경로 glob>
금지: lockfile 수정, 무관 디렉터리 수정
스타일: <예시 파일>과 일치
완료: 변경 파일 목록 + <테스트 명령> 실행
```

[좋은 작업의 구조](/ko/prompts/task-anatomy/)를 참고하세요.

## 흔한 오해

### 1. “이 파일 고쳐 줘” 한 줄만

이런 작업은 정보가 보통 부족합니다.

다음을 더하세요.

- 어떤 파일을 고칠 수 있는지
- 어떤 파일을 건드리면 안 되는지
- 스타일 참고는 누구인지
- 끝난 뒤 어떻게 검증하는지

### 2. 설정 파일과 일반 텍스트는 같다?

그렇게 보면 안 됩니다.

`.json`, `.yaml`, `.toml`은 구조·들여쓰기·문법이 깨지는 문제가 더 흔합니다.

### 3. 더 포괄적으로 고칠수록 편하다?

많은 경우 “작은 범위, 설명 가능, 심사하기 쉬운” 변경이 “대면적 편의 최적화”보다 안정적입니다.

## 인코딩과 줄바꿈

- 기본 **UTF-8**; 특수 인코딩 프로젝트는 `AGENTS.md`에 선언
- `.editorconfig` / `prettier`와 일치해 파일 전체 줄바꿈 diff를 피함
- 큰 파일은 구간 수정: 전체 재작성보다 구체 함수를 @

## 너무 많이 고칠까 걱정될 때

범위를 이렇게 제한하세요.

1. 먼저 어떤 파일에 영향이 있는지 설명
2. 현재 작업에 필요한 최소 범위만 수정
3. 수정 후 검증 동작을 나열

## 심사 요점

- [diff 심사](/ko/guide/quality/review-diffs/): 논리, 범위, 삭제
- [테스트 실행](/ko/guide/quality/run-tests/)
- 구현 없는 `TODO` 자리표시자를 의도치 않게 도입하지 않음

## 흔한 실수

- 「프로젝트 전체 리팩터」로 수백 파일 변경
- 바이너리·minified 파일에 억지로 텍스트 편집
- 문서 링크를 절대 경로로 써 사이트 내 404

텍스트·코드 파일이 가장 싫어하는 것은 많고 흩어져 심사하기 어려운 변경입니다. 범위·스타일·검증을 분명히 하면 이후 왕복이 많이 줄어듭니다.
