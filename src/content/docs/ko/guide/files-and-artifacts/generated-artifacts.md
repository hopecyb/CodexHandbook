Agent가 작업을 마칠 때 보고서, 스크립트, 정적 사이트, 테스트 데이터 등 **생성물**을 새로 만들 수 있습니다. 익숙한 코드 심사 경로를 거치지 않을 수 있어, 별도의 검증 습관이 필요합니다.

파일이 Codex가 새로 생성했다고, 바로 쓸 수 있다는 뜻은 아닙니다.

## 이 페이지 내용

- 생성물과 「기존 코드 수정」의 검증 차이
- 체크리스트
- 언제 거부하고 재작업을 요구할지

## 생성물 유형

| 유형 | 검증 중점 |
|---|---|
| 스크립트 `.sh` `.py` | 실행 가능, 무해, 멱등 |
| 보고서 `.md` `.html` | 사실 정확, 링크 유효 |
| 빌드 출력 `dist/` | gitignore 해야 하는지 |
| 테스트 fixture | 실제 PII 없음 |
| 설정 템플릿 | 기본 약한 비밀번호 없음 |

## 여기서 “생성물”이란

여기의 “생성물”은:

- 새로 써 준 파일
-보내 준 보고서
- 빌드해 준 페이지·디렉터리·패키지

“기존 코드 몇 줄만 고친 것”과 다릅니다. 실제 내용을 놓치기 더 쉽습니다.

## 검증 흐름

```text
1. 산출물을 연다(Agent 글 요약만 보지 않음)
2. 작업의 「완료 정의」와 대조
3. 관련 테스트 또는 미리보기 명령 실행
4. 경로·권한·용량 점검
5. 결정: 수락 / 국소 수정 / 폐기 후 재작업
```

방법: [산출물 검증](/guide/quality/verify-artifacts/), [완료 정의](/guide/quality/definition-of-done/)

## 흔한 오해

### 1. “완료했다”고 해도 실제 산출물을 봐야 함

요약은 “자신이 무엇을 했다고 생각하는지”만 말하고, 파일을 열어 “실제 산출물 모습”을 확인하는 일을 대체하지 않습니다.

### 2. 새 파일이 옛 파일 수정보다 항상 안전한가?

새 파일에도 있을 수 있습니다.

- 잘못된 내용
- 불필요한 의존성
- 정보 유출
- 저장소에 커밋하면 안 되는 큰 파일

### 3. 돌아갈 수 있으면 커밋할 가치가 있다?

어떤 생성물은 로컬 임시용이며 Git에 넣으면 안 됩니다.

## Git과의 관계

- 어떤 생성물을 **커밋할지**, 어떤 것을 `.gitignore`할지 명시
- 한 PR에 megabytes 빌드 캐시를 섞지 않음
- 큰 산출물은 CI artifact 또는 외부 저장소

## 자주 쓰는 검증 순서

생성물 묶음을 막 받았을 때:

1. 어떤 파일이 생성됐는지 먼저 확인
2. 가장 중요한 산출물을 열기
3. 허용 디렉터리에 떨어졌는지 보기
4. 저장소에 커밋해야 하는지 보기
5. 수락·수정·재작업을 결정

## 신뢰할 수 없는 생성물

신뢰하지 않는 저장소나 외부 데이터 구동 작업에서는:

- 실행 전에 스크립트를 먼저 읽기
- `curl | bash`, 난독화 payload에 주의
- 샌드박스나 컨테이너에서 미리보기

생성물은 “이미 생성됨”만 보면 안 됩니다. 최소한 열어 보고, 검증하고, 커밋 여부도 알아야 합니다.

## 흔한 실수

- Agent bullet summary만 보고 파일을 열지 않음
- 일회성 디버그 출력을 main에 커밋
- HTML 보고서에 추적 픽셀이나 미심사 외부 스크립트

## 검증 체크리스트

- [ ] 모든 새 파일 경로가 허용 범위 안
- [ ] 열어 주요 내용을 훑어봄
- [ ] 자동화 점검(lint/test/link check)을 돌림
- [ ] secrets 없음, 불필요 생성 디렉터리 없음
