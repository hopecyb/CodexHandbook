프레젠테이션(PPT, Keynote, Google Slides, Marp/Reveal 등)은 **서사 구조**와 **시각 일관성**을 중시합니다. Agent는 개요와 초안에 강하고, 마스터와 브랜드 규범은 사람이 잡는 편이 맞습니다.

Codex로 발표 자료를 만들 때 가장 가치 있는 것은 구조·페이지 순서·설명 논리를 먼저 짜는 것이며, 최종 마무리는 당신이 닫아야 합니다.

## 이 페이지 내용

- Codex로 슬라이드를 만들 때의 권장 워크플로
- 서로 다른 형식(`.pptx`, Markdown 슬라이드)의 취사
- 「페이지마다 스타일이 제각각」을 피하는 법

## 먼저 납품 형식을 정함

| 형식 | 적합 |
|---|---|
| Marp / Slidev / reveal.md | 개발자, 버전 관리에 친화 |
| `.pptx` | 비즈니스 보고, 고객과 공유 |
| Google Slides | 실시간 협업(보통보내기 또는 MCP) |
| PDF보내기 | 읽기 전용 배포 |

작업 시작에 형식을 고정해, Agent가 여러 도구 체인을 섞지 않게 하세요.

최종 납품 대상에 따라:

- 고객·상사·동료가 바로 열어 고침: 보통 `.pptx`
- 코드와 함께 버전 관리: 보통 Markdown 슬라이드
- 읽기 전용만: 보통 최종 PDF보내기

## 권장 워크플로

```text
1. 개요: 청중, 시간, 핵심 메시지 3–5개
2. 페이지마다 제목 + bullet 3개, 발표 메모 요점
3. 도구를 정해 초안 생성
4. 사람이 마스터·차트·데이터 출처 조정
5. PDF로보내 리허설·시간 측정
```

[탐색—계획—실행—검증](/cases/workflows/explore-plan-execute-verify/)과 같습니다. 개요 단계를 먼저 검증한 뒤 세부를 채웁니다.

## 왜 발표 자료는 구조를 먼저 잡아야 하나

구조를 먼저 잡지 않으면 Codex가 페이지를 많이 깔기 쉽지만 내용은:

- 순서가 흐트러짐
- 페이지 수가 통제 불능
- 페이지마다 독립 포스터처럼 보여 한 보고서로 안 보임

보통 이 3층으로 가면 더 안정적입니다.

1. 먼저 “이 발표가 무엇을 분명히 말해야 하는지”
2. 이어서 “각 페이지가 어느 핵심 한 줄을 담당하는지”
3. 마지막에 Agent가 문안·차트 설명·발표 메모를 채우게

## 흔한 오해

### 1. PPT가 화려할수록 전달력이 세다?

많은 경우 이해를 좌우하는 것은:

- 제목이 한 문장으로 초점을 말하는지
- 페이지 사이에 추진 관계가 있는지
- 데이터에 출처가 있는지

### 2. Agent가 초안 전체를 만들면 사람 검수가 필요 없다?

아닙니다.  
다음은 반드시 사람이 한 번 보는 편이 좋습니다.

- 회사 브랜드와 마스터
- 핵심 결론
- 숫자와 차트
- 대외 발송 버전

### 3. 한 페이지에 내용이 가득할수록 정보가 충분하다?

보통 말하기가 더 어렵습니다.  
bullet·그림·결론이 너무 많으면 청중이 초점을 한 번에 잡기 어렵습니다.

## 자주 쓰는 제작 순서

지금 Codex에 발표 자료를 맡기려면 이 순서로 요구하세요.

1. 청중이 누구인지
2. 발표 시간
3. 상대가 가져가길 바라는 3가지
4. 먼저 개요를 받게
5. 개요 확인 후 각 페이지를 펼치게
6. 마지막에 발표 메모·시각 요구·보내기 형식

이 순서면 보통 더 잘 잡힙니다. 구조 → 문안 → 스타일.

## Prompt 요점

- **청중**: 기술 동료 vs 경영진 — 용어 깊이
- **페이지 상한**: 80페이지 군더더기 방지
- **브랜드**: 주색, logo 경로, clipart 금지(회사 규범이 있으면)
- **데이터 차트**: 데이터 출처 파일을 명시하고, 스크린샷 날조가 아니라 갱신 가능하게

요구를 이런 톤으로도 말할 수 있습니다.

> “먼저 10페이지 이내 개요를 만들어 주세요. 청중은 비기술 경영진이고, 페이지마다 핵심 결론 하나만, 마지막에 발표 메모를 보강하세요.”

이런 요구가 “고급스러운 PPT 하나”보다 계속 다듬을 수 있는 버전을 내기 쉽습니다.

이미지 요구는 [이미지와 스크린샷](/guide/files-and-artifacts/images-and-screenshots/), 순수 생성 이미지는 [이미지 생성](/guide/tools/image-generation/)을 보세요.

## 검증

- 프로젝션 해상도에서 글자 크기 가독
- 애니메이션은 적절히(과하면 유지보수 어려움)
- 숫자가 [출처 검증](/guide/quality/validate-sources/)과 일치
- 발표 메모가 충분한지(필요하면)

## Codex에 맡기기 좋은 것 / 당신이 결정할 것

| Codex에 더 맞음 | 사람이 잡는 편이 좋음 |
|---|---|
| 개요를 페이지로 쪼개기 | 최종 결론 표현 |
| 페이지 제목 초안 | 브랜드 일관성 |
| 발표 메모 초안 | 민감 데이터 |
| 차트 설명 문안 | 대외 배포 버전 |

이렇게 나누면 보통 시간이 줄고, 품질도 막기 쉽습니다.

## 흔한 실수

- 개요 없이 「분기 보고 PPT 하나」
- `.pptx` 바이너리만 반복 손보고 Markdown 원본을 남기지 않음
- 차트 데이터가 저장소 CSV와 불일치
- Agent에게 구조·디자인·결론·데이터 정의를 한 번에 맡김

## 검증 체크리스트

- [ ] 개요를 사람이 확인한 뒤 전문 생성
- [ ] 목표 재생 환경에서 열어 글꼴 깨짐 없음
- [ ] 핵심 데이터가 원천 파일로 추적 가능
