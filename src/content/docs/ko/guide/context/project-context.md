“프로젝트 컨텍스트”는 이 프로젝트에서 장기적으로 안정적이며, 많은 작업에서 반복해 쓰는 배경 정보입니다.

예를 들어:

- 디렉터리 구조를 어떻게 짜는지
- 자주 쓰는 명령이 무엇인지
- 코드 스타일 규약이 무엇인지
- 함부로 고치면 안 되는 파일이 무엇인지
- 끝난 뒤 어떻게 검수하는지

이런 정보를 매번 임시로 말하면 피곤하고 빠지기 쉽습니다.

## 구체적으로 무엇을 말하나요

프로젝트 컨텍스트는 “이 프로젝트에서 장기적으로 기본 협업하는 방식”의 설명으로 볼 수 있습니다.

이번 작업의 구체적 목표를 설명하지는 않습니다. 대신 Codex에 미리 알려 줍니다.

- 이 저장소가 평소 어떻게 조직되는지
- 어떤 습관이 오래 유효한지
- 어떤 경계를 건드리지 않는 편이 좋은지
- 끝난 뒤 보통 어떻게 검증하는지

그러면 프로젝트에 들어올 때마다 팀 습관을 처음부터 추측하지 않아도 됩니다.

## 왜 여기서 문제가 생기기 쉬운가

많은 사람이 Codex를 처음 쓸 때, 모든 요구를 현재 작업에 몰아넣습니다.

단기에는 되는 것처럼 보이지만, 곧 다음이 생깁니다.

- 매번 다시 설명해야 함
- 작업마다 말이 달라짐
- 핵심 규칙을 잊음
- 대화가 길어지면 정작 중요한 배경이 안 보임

처리 방식은 두 층으로 나눌 수 있습니다.

- **장기 유효한 규칙**은 프로젝트 컨텍스트에 둡니다
- **이번 작업의 특수 요구**는 현재 프롬프트에 씁니다

## 현재 작업과 어떻게 구분하나요

가장 단순한 두 층:

- **프로젝트 컨텍스트**: 이 프로젝트는 평소 이렇게 한다
- **작업 프롬프트**: 이번에 구체적으로 무엇을 하라

예를 들어:

- “컴포넌트는 통일해 `src/components/`에 둔다” → 프로젝트 컨텍스트
- “이번엔 홈페이지 banner 문구만 고친다” → 현재 작업

## 흔한 오해

### 1. 프로젝트 컨텍스트는 길수록 좋나요

진짜 가치 있는 것은:

- 장기 유효
- 여러 작업에서 쓰임
- 말하지 않으면 함정에 빠지기 쉬움

일회성 세부까지 넣으면 프로젝트 설명 자체가 노이즈가 됩니다.

### 2. 매번 작업에서만 분명히 하면 프로젝트 컨텍스트는 필요 없나요

단기에는 되지만 장기에는 피곤합니다.

곧 다음을 겪습니다.

- 같은 말을 매번 반복
- 작업마다 표기가 달라짐
- 어떤 규칙은 이번엔 말하고 다음엔 잊음

### 3. 프로젝트 컨텍스트가 너무 경직해지지 않나요

장기 기본 규칙으로 두면 됩니다. 절대 못 바꾸는 명령으로 두지 마세요.

진짜 특수 요구는 여전히 현재 작업에 써야 합니다.

## 흔한 배치 위치

안정된 규약은 프로젝트 설명에 둡니다. 예: `AGENTS.md` 또는 제품이 제공하는 프로젝트 지시.

- 디렉터리 구조
- 자주 쓰는 명령
- 코드 스타일
- 금지 사항

작업 프롬프트에는 **이번 차이**만 쓰고, 반복되는 긴 배경은 프로젝트급으로 내립니다. 구성 심화는 이후 `06-customization` 마일스톤에서 다룹니다.

## 프로젝트 컨텍스트에 넣을지 판단

설명이 다음 두 조건을 만족하면 프로젝트 컨텍스트를 고려할 가치가 있습니다.

1. 다음에 쓸 가능성이 큼
2. 잊으면 반복해서 틀리거나 시간을 낭비함

## 정리할 때 우선 넣을 것

우선 내릴 유형은 보통:

- 자주 쓰는 명령
- 디렉터리 규약
- 코드 스타일
- 수정 금지 구역
- 기본 검증 방식

다음에 쓸 가능성이 큰 설명은 프로젝트 컨텍스트에 내리고, 매번 다시 치지 마세요.
