함부로 보이거나, 복사되거나, 외부로 나가거나, 작업 기록에 오래 남기 싫은 내용은 먼저 민감 정보로 다루세요.

## 왜 먼저 판단해야 하나요

많은 보안 문제는 고의 위반이 아니라, 그 순간 “일단 문제를 풀자”는 생각에서 납니다.

예를 들어:

- 문제 해결을 위해 `.env` 전체를 붙여넣음
- 이해시키려고 고객 원본 데이터를 붙여넣음
- 편의를 위해 실제 토큰이 든 오류 원문을 그대로 붙여넣음

당장은 편해 보이지만, 사후에 가장 고치기 어렵습니다.

Codex에 주지 마세요(연습·프로덕션):

- API 키, 비밀번호, 세션 Cookie
- 마스킹하지 않은 고객 데이터, 주민등록번호 등
- 계약상 외부 전달이 금지된 미공개 내부 자료

자리 표시자를 쓰세요: `YOUR_API_KEY`. 이미 유출됐다면 조직 절차에 따라 키를 교체하세요.

## 확신이 없을 때

어떤 내용이 민감한지 모르면, 먼저 스스로 두 가지를 물으세요.

1. 관련 없는 사람이 보면 위험이 있는가?
2. 작업 기록에 오래 남으면 불안한가?

하나라도 “예”이면 먼저 민감 정보로 다루세요.

## “괜찮겠지”에 기대지 마세요

도구형 AI를 처음 쓸 때 많은 사람이 본능적으로 생각합니다.

- “잠깐만 붙여넣는 거야”
- “봐 달라고만 하는 거야”
- “이 파일이 진짜로 나가진 않을 거야”

정보가 이미 작업 흐름에 들어갔다면 민감 정보로 다루세요. 보안 통제는 사전에 두는 편이 좋습니다.

## 놓치기 쉬운 내용

비밀번호와 키 외에도 다음이 자주 민감합니다.

- 고객 명단
- 휴대폰 번호, 이메일, 주민등록번호
- 내부 스크린샷, 미공개 방안
- 실제 프로덕션 주소나 접근 토큰이 든 설정 파일

즉, 민감 정보는 `sk-...` 키 한 줄만이 아닙니다.

## 마스킹은 어느 정도면 충분한가

모든 정보를 지울 필요는 없습니다. “문제 해결에 필요한 최소 정보”를 남기면 됩니다.

다음 생각으로 처리하세요.

- 구조는 유지
- 실제 값은 교체
- 신원 식별은 제거
- 현재 문제와 무관한 필드는 삭제

예를 들어 남길 수 있는 것:

- 필드 이름
- 오류 유형
- 호출 순서

다음을 바꿔 넣으세요.

- 실제 키
- 실제 이메일
- 실제 휴대폰 번호
- 실제 고객 이름

## 꼭 제공해야 할 때

더 안전한 방법:

- 키를 가짜 값이나 자리 표시자로 교체
- 실제 사용자 데이터를 마스킹
- 문제 점검에 정말 필요한 필드만 유지
- 현상만 설명할 수 있으면 원본 민감 내용 전체를 붙이지 않기

예를 들어:

```text
실제 API Key는 YOUR_API_KEY로, 실제 이메일은 user@example.com으로 바꾼다.
```

## 이미 실수로 넘겼다면

위험 수준에 따라:

1. 추가 확산을 먼저 멈춤
2. 키·비밀번호·토큰을 즉시 교체
3. 조직 절차에 따라 보고하고 보완

문제를 풀 때는 기본으로 “점검에 필요한 최소 정보”만 주세요. 마스킹할 수 있으면 마스킹하고, 자리 표시자를 쓸 수 있으면 쓰세요.
