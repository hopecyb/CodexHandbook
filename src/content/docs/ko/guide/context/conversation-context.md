“대화 컨텍스트”는 같은 작업에서 앞에서 Codex와 나눈 말이 뒤에 계속 영향을 준다는 뜻입니다. 도움이 되기도 하고, 위험이 되기도 합니다.

## 왜 유용한가

같은 스레드는 다음을 누적합니다.

- 목표와 제한
- 중간에 나온 결론
- 이미 실행한 단계
- 도구 출력의 핵심 정보

앞에서 “홈페이지만 고치고 백엔드는 건드리지 말 것”을 이미 말했다면, 뒤에서 매 문장마다 반복할 필요는 보통 없습니다.

## 왜 문제가 되기도 하는가

흔한 문제는: **옛 정보가 자동으로 무효화되지 않는다**는 점입니다.

흔한 경우:

- 앞에서 준 제한을 뒤에서는 스스로 잊고 바꿈
- 작업 방향이 바뀌었는데도 옛 컨텍스트를 따라 계속 이야기함
- 앞의 임시 결론이 나중에 틀렸는데도 뒤 판단에 영향을 줌

핵심은 대화를 길게 끄는 것이 아니라, 길어질수록 능동적으로 매듭짓는 것입니다.

## 언제 핵심 제약을 다시 말해야 하나요

앞에서 말했더라도, 핵심 지점에서는 다시 말하는 편이 좋습니다. 예를 들어:

- 실제로 파일을 고치기 직전
- 작업 방향이 바뀐 뒤
- 대화가 이미 길어진 뒤
- 어떤 경계를 무시하기 시작했을 때

특히 다음 정보는 다시 말할 가치가 큽니다.

- 어떤 파일만 고칠지
- 무엇을 하지 말지
- 완료 기준이 무엇인지
- 어떤 제한이 여전히 유효한지

## 흔한 오해

### 1. 같은 스레드가 길수록 더 편한가요?

꼭 그렇지는 않습니다.

주제가 줄곧 같다면 긴 스레드는 편리합니다.  
작업 방향이 바뀌었는데 옛 스레드를 이어 쓰면, 새 작업이 빗나가기 쉽습니다.

### 2. 이미 말했는데 왜 또 틀리나요?

앞 정보가 뒤의 더 많은 내용에 희석됐거나, 현재 작업과 잘 맞지 않을 수 있습니다.

이때 “알잖아”만 말하기보다, 여전히 중요한 제약을 다시 말하는 편이 효과적입니다.

### 3. 언제 새 스레드를 여나요

다음 기준으로 판단하세요.

- 목표가 이미 바뀜
- 원래 문제가 끝남
- 이 대화가 스스로도 어수선해 보임

이때는 억지로 이어 쓰기보다 새 스레드가 보통 더 깨끗합니다.

## 주제가 바뀔 때

주제가 바뀌면:

1. 새 스레드를 엽니다
2. 여전히 유효한 제약 요약만 붙여넣습니다
3. 이미 낡은 배경은 옮기지 않습니다

원래 스레드에 남을 때도, 짧은 “재정렬 설명”을 먼저 보낼 수 있습니다. 예를 들어:

```text
지금부터는 홈페이지 개편만 논의한다. 앞의 백엔드 API 내용은 이어받지 않는다. 이번에도 문구와 스타일만 고치고, 데이터 구조는 바꾸지 않는다.
```

같은 스레드는 기억을 이어 주지만, 옛 짐도 함께 가져갑니다. 주제가 바뀌면 능동적으로 매듭지으세요.
