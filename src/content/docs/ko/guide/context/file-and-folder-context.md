“조금만 고쳐 줘”라고만 하지 말고, Codex가 어떤 파일을 보고 어떤 파일을 보지 말아야 하는지도 말하세요.

문제가 어떤 디렉터리에 있는지는 이미 알 수 있지만, 범위를 밝히지 않으면 Codex가 관련 없는 파일까지 끌어올 수 있습니다.

## 범위가 중요한 이유

범위가 너무 크면 다음이 함께 나타납니다.

- 관련 없는 파일을 많이 읽음
- 컨텍스트가 불필요 정보로 잠식됨
- 비슷한 다른 파일도 목표로 삼음
- 변경 범위가 기대를 넘음

파일·폴더 컨텍스트의 역할은 경계를 그려 주는 것입니다.

## 왜 파일 범위를 분명히 해야 하나요

사무실에 사람을 데리고 자료를 찾는다고 생각해 보세요.

- “찾아 봐”라고만 하면 반 층을 다 뒤질 수 있음
- “세 번째 장롱의 파란 폴더만 보라”고 하면 효율이 훨씬 높음

Codex도 같습니다. 범위가 분명할수록 추측으로 빈칸을 메울 필요가 줄어듭니다.

## 간단한 예시

관련 경로를 명시합니다.

```text
src/components/Button.tsx와 그 테스트 파일만 읽고, 저장소 전체를 스캔하지 말 것.
```

이 문장은 동시에 말합니다.

- 어디를 볼지
- 어디를 보지 말지
- 스스로 범위를 키우지 말지

## 흔한 오해

### 1. 관련 파일은 많을수록 좋나요?

너무 적으면 추측하게 되고, 너무 많으면 초점이 희석됩니다.  
더 나은 방법은: **현재 작업을 끝내는 데 정말 필요한 부분만** 주는 것입니다.

### 2. 관련 파일을 모르면?

먼저 범위를 좁히게 하되, 목적을 분명히 하세요. 예를 들어:

```text
로그인 버튼 스타일과 관련 있는 파일을 먼저 찾고, 아직 수정은 하지 말 것.
```

먼저 위치를 잡고 실행하는 편이, 처음부터 “전 저장소 검색하며 손대는” 것보다 보통 더 안전합니다.

### 3. 범위를 지정하지 않아도 알아서 찾지 않나요?

찾을 수는 있지만 대가는 보통:

- 더 많이 읽음
- 느려짐
- 비슷한 파일을 끌어오기 쉬움
- 예상하지 못한 곳을 고칠 수 있음

### 4. 디렉터리와 파일을 모두 말해야 하나요

필수는 아니지만, 구체적일수록 좋습니다.

- 파일을 알면: 파일을 직접 지정
- 대략 구역만 알면: 디렉터리를 먼저 지정
- 전혀 모르면: 먼저 위치 파악과 설명만 맡김

## 프롬프트에 보완하면 좋은 세 가지

범위를 넘을까 걱정되면 프롬프트에 다음을 넣으세요.

1. 어떤 파일·디렉터리만 볼지
2. 어디를 스캔하지 말지
3. 수정 전에 영향 파일을 먼저 밝히게 할지

IDE에서는 현재 워크스페이스 루트가 맞는지 확인하세요.

## 바로 쓸 수 있는 쓰기

이런 쓰기를 쓸 수 있습니다.

```text
먼저 `src/pages/home/`와 `src/components/Hero.tsx`만 보라.
`backend/`와 `scripts/`는 스캔하지 말 것.
다른 파일이 더 필요하면, 왜 필요한지 먼저 말하고 계속하라.
```

Codex에 파일 범위를 지정하는 것은, 추측·노이즈·오수정을 줄이는 일입니다.
