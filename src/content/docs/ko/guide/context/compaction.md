“컨텍스트 압축”은 대화가 너무 길어지면, 시스템이 앞 내용을 더 짧은 버전으로 줄여 계속 남기는 것으로 이해할 수 있습니다. 목적은 작업을 이어 가게 하는 것이고, 대가는 **세부가 사라질 수 있다**는 점입니다.

## 왜 결과에 영향을 주나요

많은 초보자는 기본으로 이렇게 생각합니다.

“앞에서 한 말은 계속 완전하게 기억할 것이다.”

실제로는 항상 그렇지 않습니다.  
긴 작업이 압축에 들어가면, 보통 더 쉽게 사라지는 것은:

- 아주 세밀한 작은 제한
- 임시이지만 중요한 예외
- 앞에서 지정한 파일 화이트리스트
- 검수 기준의 변두리 조건

압축은 오류가 아니라, 당신이 맞춰 줘야 하는 메커니즘입니다.

## 압축 후 다시 말해야 할 것

압축은 세부를 잃습니다. 핵심 제약·검수 기준·파일 화이트리스트는 압축 후 **다시 선언**하거나 프로젝트 설명에 쓰세요.

특히 다음을 우선 재선언하세요.

- 어떤 파일만 수정 허용인지
- 무엇을 절대 건드리지 말아야 하는지
- 무엇을 완료로 볼지
- 현재 어디까지 끝났는지

## 흔한 오해

### 1. 압축은 “전부 잊는다”는 뜻인가요

더 정확히는, 줄기는 남기지만 모든 세부가 그대로 남는다고 보장하지는 않습니다.

### 2. 매번 처음부터 다시 말해야 하나요

그럴 필요는 없습니다.

가장 중요하고, 잃기 쉽고, 틀리면 안 되는 부분만 다시 설명하면 보통 충분합니다.

### 3. “아직 기억하겠지”라고 걸면 안 되는 정보는?

보통 이런 것들입니다.

- 파일 범위
- 금지 항목
- 검수 기준
- 확인한 중요 결정

## 압축 후 보완

작업이 이미 길면, 중간에 짧은 요약을 스스로 쓸 수 있습니다. 예를 들어:

```text
현재 유효한 제약:
1. docs 디렉터리만 수정
2. 라우트 구조는 바꾸지 말 것
3. 완료 기준은 홈페이지 문구 갱신과 빌드 통과
```

긴 대화 전체에 의존하는 것보다 더 안정적입니다.

개념 층: [Token, 컨텍스트, 압축](/ko/guide/foundations/tokens-context-and-compaction/)

긴 작업에서 가장 중요한 제한은 한 번만 말하지 마세요. 압축 뒤에는 중요한 규칙을 능동적으로 다시 말하는 편이 낫습니다.
