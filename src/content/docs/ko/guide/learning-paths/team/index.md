결과를 확인할 수 있는 범위가 제한된 작업 하나로 시작하세요. 2주 동안 사용 범위를 넓힐 가치가 있는지 판단할 근거를 모읍니다. 여기서 2주는 근무일 열흘을 뜻합니다. 작업량이 부족하면 기간을 늘리고, 날짜가 지났다는 이유만으로 성공을 선언하지 마세요.

[2주 파일럿 템플릿 묶음 다운로드](/downloads/two-week-pilot/two-week-pilot-1.0.0.zip) · [사용 안내](/downloads/two-week-pilot/README.md) · [열흘 일정](/downloads/two-week-pilot/templates/06-schedule.md)

## 시작 전: 작업과 책임자 정하기

[Issue 분류 제안](/ko/cases/use-cases/team-automation/issue-triage-suggestions/) 또는 [로컬 링크 검사](/ko/cases/use-cases/team-automation/scheduled-link-check/)로 시작해 보세요. 먼저 합성 입력으로 수동 실행하고, 사람의 검토와 로컬 출력을 유지하세요.

책임자, 실행자, 검토자, 시스템 관리자, 보안 담당자와 대체 인력을 정하세요. 겸직할 수 있지만 외부 쓰기나 보안 사고에 관한 결정에는 독립 검토가 필요합니다. 아직 검토자가 없으면 합성 입력과 로컬 초안으로 범위를 제한하고 작성자 자체 점검으로 기록하세요.

사전 조건: 로그 저장, 결과 판단, 실행 중단 방법을 알고 허용되는 데이터와 동작을 설명할 수 있어야 합니다. 권한이 불명확하면 로컬 준비만 먼저 마치고 생산 시스템으로 스스로 확대하지 마세요.

## D1–D2: 계획서를 만들고 수동으로 끝까지 실행하기

[파일럿 계획서](/downloads/two-week-pilot/templates/01-charter.md)와 [작업 목록](/downloads/two-week-pilot/templates/02-tasks.csv)에 업무 문제, 수동 기준, 입력 범위, 허용 동작, 제외 항목, 검토 방법, 중단 조건, 기록 보존 방법을 적으세요.

실행 전에 정확성의 구체적인 기준을 정하세요. '80%만 통과하면 출시' 같은 일률적인 문턱을 사용하지 마세요. 위험이 큰 결과는 건별로 검토하고, 나머지 작업의 표본 추출 방법과 이유는 계획서에 적으세요.

완료 조건: 수동 실행 한 번에 입력, 출력, 실제 검사, 책임자가 모두 있습니다. 팀이 성공, 실패, 일시 중지를 구분할 수 있습니다. 그다음 제한된 표본 실행으로 넘어갑니다.

## D3–D5: 실행을 기록하고 첫 회고하기

[검토표](/downloads/two-week-pilot/templates/03-review.csv)에 실행, 실패, 중단, 입력 버전, 구성, 근거와 수락·수정·거부 이유를 매번 남기세요.

[워크플로 평가 방법](/ko/guide/quality/workflow-evaluation/)에 따라 트리거, 경계, 형식, 품질을 따로 살피세요. 모델 대기 시간과 사람의 재작업 시간도 분리해 기록하세요. 수동 기준과 비교할 때는 작업 난도와 입력이 비슷한지 확인하고 비교할 수 없는 부분은 미상으로 남기세요.

D5에는 실패 유형과 표본 검토 범위를 확인하세요. 심각한 경계 문제가 있으면 일시 중지하고 재현 및 회귀 사례를 추가하세요. 실패 기록을 지우거나 기준을 낮춰 문제를 감추지 마세요.

완료 조건: 첫 결과에 다시 확인할 수 있는 검토 기록이 있고, 각 문제에 담당자와 처리 상태가 있습니다. 심각한 문제가 해결되지 않았다면 이 단계에 머무르세요.

## D6–D8: 제한적으로 확대하고 복구 연습하기

승인된 범위 안에서 표본이나 작업 유형을 늘리세요. 한 번에 중요한 요인 하나만 바꾸고 권한 확대, 모델 교체, 작업 변경을 동시에 하지 마세요. 원인을 구분할 수 있도록 구성 버전을 기록하세요.

[사고 및 복구 템플릿](/downloads/two-week-pilot/templates/04-incident.md)으로 작업 일시 중지, 활성 프로세스와 대기열 확인, 증거 보존, 알려진 정상 버전 복원과 재검증을 연습하세요. 새 실행을 멈춰도 이미 일어난 외부 영향은 되돌아가지 않습니다.

먼저 격리된 디렉터리에서 [실패 복구 실습](/ko/guide/reference/troubleshooting/failure-recovery-lab/)을 할 수 있습니다. 실제 예약 실행, 권한 회수, 메시지 전달을 시험하지 않았다면 미시험으로 기록하세요. 로컬 연습이 운영 환경 복구의 증거는 아닙니다.

완료 조건: 누가 중단하고, 중단을 어떻게 확인하며, 중복 제거 상태를 어떻게 보존하고, 언제 다시 시작할 수 있는지 설명할 수 있습니다. 다음은 독립 검토와 결정입니다.

## D9–D10: 확대, 계속, 중단 결정하기

검토자가 중요 결과, 표본 편향, 미해결 문제를 확인하고 [파일럿 결정 문서](/downloads/two-week-pilot/templates/05-decision.md)를 작성합니다.

| 결정 | 설명할 내용 |
|---|---|
| 제한적 확대 | 근거가 뒷받침하는 작업, 인력, 권한; 지속 표본 검토와 복구 책임 |
| 파일럿 계속 | 부족한 표본 또는 복구 근거, 책임자, 다음 회고 날짜 |
| 중단 | 예약 실행 비활성화, 권한 처리, 기록 보존, 미완료 이벤트 처리 방법 |

D1 기준을 항목별로 설명하고, 좋은 평균 점수로 심각한 오류를 상쇄하지 마세요. 독립 검토가 없거나 표본이 부족하거나 기준과 비교할 수 없다면 한계를 명시하고 팀 생산성 향상을 주장하지 마세요.

완료 조건: 책임자, 근거, 범위, 다음 단계를 적은 결정이 있습니다. 확대하더라도 검증된 작업과 조건에만 적용되며 모든 구성원이 모든 일을 자동으로 수행할 권한을 받는 것은 아닙니다.

## 템플릿 검토 방법

작성자는 [탁상 연습 세 가지](/downloads/two-week-pilot/references/tabletop-review.md)를 했습니다. 결과는 정확하지만 권한을 넘은 경우, 표본 부족, 예약 실행을 끈 뒤에도 전달되지 않은 이벤트가 남은 경우입니다. 템플릿이 결정 지점을 다루는지 확인하기 위한 것이며 실제 팀 사례나 2주 운영 성과가 아닙니다.

나중에 프로젝트 규칙을 바꿀 때는 [프로젝트 구성](/ko/guide/customization/)과 [완료 정의](/ko/guide/quality/definition-of-done/)를 읽고 파일럿에서 배운 구체적인 요구를 공유 절차에 반영하세요.
