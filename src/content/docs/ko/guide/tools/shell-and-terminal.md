터미널은 Codex가 동작을 실행하는 가장 직접적인 방식 중 하나라 효율이 높고, 그만큼 위험을 이해해야 합니다.

## 왜 강력하면서도 위험한가

파일 도구는 주로 텍스트를 다루고, 터미널은 시스템과 실행 환경을 직접 조작합니다.

터미널에 들어가면 흔한 동작이 읽기만이 아니라 다음이 될 수 있습니다.

- 설치
- 빌드
- 테스트
- 삭제
- 커밋
- 푸시

쓰기 전에 어디를 바꿀지 먼저 파악하세요.

터미널은 강력하고 위험합니다. 원칙:

- 승인 전에 명령을 이해함
- `rm -rf`, 강제 푸시, ssh 설정 변경 등은 완전히 이해하고 필요할 때만
- 검증 명령을 검증 기준에 씀

제품 진입점: [통합 터미널](/ko/guide/desktop-app/integrated-terminal/)

## 왜 터미널 위험이 더 높은가

“제안만”이 아니라 실제로 동작을 실행하기 때문입니다.

예:

- 의존성 설치
- 파일 삭제
- 테스트 실행
- 설정 재작성
- 코드 푸시

명령을 이해하지 못하면 먼저 묻고, 허용할지 결정하세요.

## 터미널이 잘 맞는 경우

다음에 맞습니다.

- 테스트 실행
- 빌드 실행
- 파일 상태 조회
- 프로젝트에 있는 스크립트 실행

다음만 원하면 터미널이 첫 선택은 아닐 수 있습니다.

- 페이지가 어떻게 보이는지
- 최신 공개 자료 조회
- 알려진 텍스트 한두 곳 수정

## 흔한 오해

### 1. 명령을 몰라도 터미널을 전혀 못 쓰나?

처음부터 많은 명령을 쓸 필요는 없지만, 최소한 이해해야 합니다.

- 이 명령이 대략 무엇을 하려는지
- 파일이나 시스템을 바꾸는지
- 현재 작업과 진짜 관련인지

### 2. 테스트 명령이면 항상 안전하다?

그렇게 보면 안 됩니다.  
대부분의 테스트는 위험이 낮지만 여전히:

- 많은 파일을 쓰는지
- 네트워킹하는지
- 모르는 스크립트를 호출하는지

### 3. 이해가 안 되면?

바로 물으세요. 예:

```text
이 명령은 무엇을 하나요? 무엇을 수정하나요? 실행하지 않으면 어떤 영향이 있나요?
```

## 바로 쓸 수 있는 쓰기

한 줄을 더하세요.

```text
명령을 실행하기 전에 용도, 파일 쓰기 여부, 네트워킹 여부, 실패 후 복구 방법을 설명하세요.
```

실행 전에 이 명령이 어디를 바꾸는지 먼저 확인하세요.
