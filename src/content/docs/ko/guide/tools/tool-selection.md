“도구 선택”은, 이 일을 어떤 방식으로 하면 효과적이고 안전한지를 말합니다.

도구를 고를 때는 작업 유형으로 판단하는 편이 보통 더 분명합니다.

## 도구를 고를 때 보는 것

주로 다음을 봅니다.

- 현재 작업에 가장 가까운 것
- 최소 비용으로 결과를 얻는 것
- 위험이 가장 낮고 점검하기 쉬운 것

같은 목표라도 도구를 잘못 고르면 완전히 실패하지는 않아도, 더 느리고 우회하며 사고도 나기 쉽습니다.

| 필요 | 우선 |
|---|---|
| 저장소 안 파일 수정 | 파일 도구 |
| 테스트/빌드 실행 | 터미널 |
| 공개 사실 조회 | Web 검색 |
| 실제 페이지 상태 보기 | 브라우저(심화) |

프롬프트에 허용·금지 도구를 분명히 써, 무단 외부망이나 의존성 난설치를 줄이세요.

## 헷갈릴 때 고르는 법

잠깐 헷갈리면 이 순서로:

1. 로컬 프로젝트를 다루는지, 외부 사실을 찾는지
2. “동작을 실행”해야 하는지, “결과만 보면” 되는지
3. 어느 도구가 최소 범위로 이 단계를 끝낼지

예:

- 코드 변경을 보려면 → 파일
- 빌드 통과를 확인하려면 → 터미널
- 웹이 지금 어떻게 보이는지 → 브라우저
- 최신 공개 정보 → Web 검색

## 흔한 오해

### 1. 도구는 강할수록 좋다?

강한 도구는 보통:

- 영향 범위가 더 큼
- 위험이 더 높음
- 무엇을 하는지 더 이해해야 함

### 2. 터미널이 다 되니 터미널을 우선?

페이지가 어떻게 보이는지만 확인하면 브라우저가 보통 더 직접적입니다.  
공개 버전 번호만 찾으면 Web 검색이 명령을 여기저기 돌리는 것보다 맞습니다.

### 3. 고를 줄 모르면?

이 규칙으로:

- **프로젝트 내용 읽기·수정** → 파일
- **명령·빌드 검증** → 터미널
- **공개 사실 조회** → 검색
- **페이지 실제 표현** → 브라우저

### 4. 한 작업에 도구 하나만?

많은 실제 작업은 조합합니다. 예:

- 먼저 파일 읽고, 이어서 빌드
- 먼저 공개 사실 검색하고, 문서로 돌아와 고침
- 먼저 브라우저로 페이지를 보고, 코드에서 수정

핵심은 단계마다 더 맞는 도구를 쓰는 것이며, “하나만 고른다”에 집착할 필요는 없습니다.

## 바로 쓸 수 있는 쓰기

작업에 한 줄을 더하세요.

```text
파일과 터미널을 우선하고, 네트워킹 검색은 하지 마세요. 브라우저로 페이지를 점검해야 하면 먼저 이유를 설명하세요.
```

가장 작고 작업에 가까운 도구를 먼저 고르고, 처음부터 영향 범위가 가장 큰 도구를 쓰지 마세요.
