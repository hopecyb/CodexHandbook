효과적인 프로젝트 지침은 **체크리스트**에 가깝습니다. 목표는 Codex가 첫 시도에서 예측 가능한 실수를 줄이게 하는 것입니다.

프로젝트 지침을 처음 쓸 때 흔한 문제는, 생각은 많이 썼는데 정작 핵심 제약이 분명하지 않은 것입니다.

## 내용

- 프로젝트 지침이 어떤 모습이어야 하는지
- “짧고, 단단하고, 실행 가능”의 의미
- Codex와 사람 모두 헷갈리게 만드는 쓰기

## 권장 구조

```md
# 프로젝트 지침

## 빠른 시작(3–5줄)
설치, 개발 서버, 가장 자주 쓰는 테스트 명령

## 반드시 준수
위반하면 안 되는 규칙을 번호로 나열

## 코드와 디렉터리
네이밍, 배치 위치, 의존성 규약

## 완료 정의
「커밋해도 됨」의 기준

## 금지 사항
하지 말아야 할 일을 명확히
```

## 작성 원칙

### 1. 하드 제약을 앞에

「필수」「금지」를 파일 앞쪽에 둡니다. 컨텍스트가 제한될 때 모델은 앞부분에 더 큰 가중을 둡니다 — [컨텍스트 우선순위](/ko/guide/context/context-priority/)와 같은 논리입니다.

### 2. 명령은 복사 가능하게

**실제로 실행되는** 명령을 쓰고, 「테스트 한 번 돌려」라고만 쓰지 마세요.

```md
# 좋음
pnpm test --filter @app/web

# 나쁨
테스트가 통과하는지 확인
```

### 3. 검증 가능한 완료 기준

```md
## 완료 정의
- `pnpm lint`와 `pnpm test` 실패 없음
- 새 API에 대응 단위 테스트 있음
- 사용자에게 보이는 변경에는 수작업 테스트 단계(브라우저 + 모바일)첨부
```

### 4. 「왜」는 한 문장 안으로

```md
- `generated/`를 수정하지 마세요: 코드 생성물이며, 손 수정은 다음 빌드에서 덮입니다
```

긴 배경은 `docs/` 정식 문서로 링크하세요.

## “좋은 지침”이란

좋은 지침은 사람과 Codex가 빠르게 잡게 해야 합니다.

- 먼저 무엇을 할지
- 무엇을 하면 안 되는지
- 어느 정도까지면 완료인지

읽고도 먼저 돌릴 명령·건드리면 안 되는 곳·완료 기준이 안 보이면 아직 쓰기 어렵습니다.

## 팀 playbook 조각 예시

```md
## PR와 Git
- 브랜치 이름: `feat/`, `fix/`, `docs/` 접두사
- PR 하나에는 일 하나만; 대규모 리팩터는 별도 PR
- 머지 전 사람이 diff를 review해야 함 — Codex가 테스트를 돌렸어도

## Codex와 협업
- 큰 작업은 먼저 「계획만 내고, 확인 후 코드 수정」을 요구
- DB 마이그레이션이 있으면 먼저 마이그레이션 SQL을 출력해 사람이 심사
```

## 흔한 실수

| 실수 | 결과 |
|---|---|
| 프레임워크 백과를 쌓음 | 핵심 테스트 명령이 무시됨 |
| 규칙이 서로 모순 | 모델이 임의로 하나 선택 |
| 「우아하게」류 공허한 말만 | 검증 불가 |
| 키나 사내 URL 포함 | 유출 위험 |

## 흔한 오해

### 1. 지침은 상세할수록 좋다?

너무 흩어지고, 길고, 백과처럼 되면 진짜 고우선 규칙이 묻힙니다.

### 2. “규범에 주의”만 써도 지침인가?

보통은 실행 가능하지 않습니다.  
더 맞는 쓰기는 다음을 직접 주는 것입니다.

- 실제 명령
- 명확한 디렉터리
- 구체적 완료 기준

### 3. 배경 설명과 실행 규칙을 아무렇게 섞어도 되나?

권장하지 않습니다.  
더 맞는 방식은 다음과 같습니다.

- 규칙은 앞에
- 배경은 한 문장으로 압축
- 긴 설명은 docs로

## 다시 쓸 때 먼저 잡을 점

흩어진 프로젝트 지침이 있으면 이렇게 모으세요.

1. “필수/금지”를 앞으로
2. 공허한 말을 구체 명령·검사 항목으로
3. 긴 배경을 줄이고 링크로
4. 최소 완료 정의 한 세트를 제시

좋은 프로젝트 지침은 양이 아니라, 핵심 제약·핵심 명령·완료 기준이 분명하고 바로 실행 가능한지에 있습니다.

## 유지 리듬

- CI 명령이 바뀔 때마다 `AGENTS.md`를 **동기 갱신**
- 분기마다 회고: 낡은 규칙 삭제
- 신규 onboarding 첫 항목: AGENTS.md를 읽고 「빠른 시작」을 통과

## 한 번의 작업에서 프로젝트 규칙으로

좋은 프롬프트를 모두 `AGENTS.md`에 넣을 필요는 없습니다. 먼저 어느 층이 소유할지 판단하세요.

| 반복되는 내용 | 더 나은 위치 |
|---|---|
| “generated 디렉터리는 수정하지 말 것” | `AGENTS.md`의 금지 사항 |
| “매 PR을 고정 형식으로 리뷰” | Skill 또는 프롬프트 템플릿 |
| “파일 작성 후 자동 포맷” | Hook |
| “코딩 전 Linear/Jira 읽기” | MCP + 해당 Skill |
| “중국어 설명을 선호” | 기억 또는 개인 선호 |

`AGENTS.md`는 오래가고 공유되며 검증 가능한 규칙에 가장 적합합니다. 절차는 Skill로, 자동 검사는 Hook으로, 외부 접근은 MCP로 옮길 수 있습니다.
