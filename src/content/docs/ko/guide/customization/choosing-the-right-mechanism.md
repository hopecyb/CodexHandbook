많은 팀의 문제는 **같은 정보를 잘못된 곳에 두는 것**입니다. 저장소에 있어야 할 규칙을 채팅에 넣고, Skill이 될 흐름을 `AGENTS.md`에 쑤셔 넣고, 읽기 전용으로 붙여야 할 데이터에 고권한 MCP를 줍니다.

여기서 더 중요한 실무 질문은 이겁니다.

> “이 일이 앞으로 또 반복될 것 같다”고 느낄 때, 어느 계층으로 내려둘까?

## 요약 표

| 메커니즘 | 가장 잘 맞는 내용 |
|---|---|
| 단발 프롬프트 | 이번 작업에만 유효한 목표·제약·검증 기준 |
| `AGENTS.md` | 저장소급 협업 규칙과 장기 제약 |
| 기억 | 개인 선호, 또는 비민감·세션 간 반복 사실 소량 |
| Skill | 재사용 가능한 워크플로, 체크리스트, 전문 루틴 |
| MCP | 외부 도구·데이터 소스·시스템 능력 접근 |

이 표만으로 부족하면 아래로 이어 읽으세요.

## 다섯 단계 판단법

### 1. 현재 작업에만 유효한 정보

이런 정보는 **이번 프롬프트**에 우선 둡니다.

적합:

- “이번엔 `docs/`만 고치고 코드는 건드리지 마”
- “한국어 요약을 내고, 끝에 확인 질문 하나 붙여”
- “먼저 원인 분석하고, 당장 파일은 고치지 마”

부적합:

- 팀이 장기적으로 `pnpm test`를 요구함
- 저장소에서 수정 금지인 디렉터리
- 매번 PR 리뷰가 같은 템플릿으로 나와야 함

이런 장기 규칙은 아래로 더 내려둡니다.

### 2. 프로젝트 협업 규칙인가, 개인 습관인가?

**모든 협업자가 알아야 할 규칙**이면 [`AGENTS.md`](/guide/customization/agents-md/what-is-agents-md/)에 둡니다.

예:

- 테스트·lint·빌드 명령
- 건드리면 안 되는 디렉터리
- 커밋 메시지 또는 PR 검증 규칙
- monorepo 하위 디렉터리별 특수 규범

**당신만의 선호**라면 — 예: “설명은 한국어”, “결론 먼저 세부 나중” — [기억](/guide/customization/memories-and-persistent-context/)이나 개인 설정이 더 맞습니다.

경험 법칙:

- PR review에 들어갈 내용은 저장소를 우선
- 남이 못 봐도 괜찮은 내용만 개인 계층을 고려

### 3. “규칙”인가, “단계”인가?

문서가 쓰기 어려워지는 이유는 규칙과 단계를 섞기 때문입니다.

| 성격 | 더 적합 |
|---|---|
| “main에 바로 push 하지 마” | `AGENTS.md` |
| “Review는 테스트 → 위험 → 회귀 순으로” | Skill |
| “배포 전에 이 4개 명령 실행” | Skill 또는 스크립트 |
| “읽기 전용 issue 데이터만 허용” | MCP + 권한 설정 |

판단 시 이 두 가지를 먼저 잡으세요.

- **규칙**은 “무엇을 할 수 있고, 무엇을 못 하는지”에 답합니다
- **단계**는 “이런 일을 보통 어떻게 하는지”에 답합니다

재사용 가능한 단계는 보통 [Skill](/skills/overview/)이 더 맞습니다.

## 흔한 조합 — 둘 중 하나가 아님

성숙한 팀은 한 메커니즘만 쓰지 않고 조합합니다.

### 조합 1: `AGENTS.md` + Skill

적합: 코드 리뷰, 릴리스 점검, 장애 조사.

역할 분담:

- `AGENTS.md`에 하드 제약: 자동 머지 금지, 반드시 돌릴 검사
- Skill에 흐름: 어떻게 심사하는지, 어떤 템플릿으로 출력하는지, 이슈를 어떻게 등급 나누는지

### 조합 2: Skill + MCP

적합: 티켓 읽기, DB 조회, 디자인 파일 가져오기, 주간 보고 생성.

역할 분담:

- Skill이 실행 순서와 출력 형식을 정의
- MCP가 “어디에 연결·무엇을 조회·무엇을 변경”할 수 있는지 제공

이렇게 나눠 보세요.

> Skill은 작업 지시서, MCP는 연결해 둔 도구상자입니다.

### 조합 3: `AGENTS.md` + 기억

적합: 팀 규칙은 안정적인데 사람마다 표현 습관이 다른 경우.

역할 분담:

- `AGENTS.md`에 팀 공통 규범
- 기억에 개인 선호(언어, 설명 스타일, 기본 출력 구조)

반대로 하지 마세요. 팀 규칙이 누군가의 기억에만 있으면 안 됩니다.

## 더 실용적인 판단 매트릭스

| 질문 | 예 | 아니오 |
|---|---|---|
| 현재 작업에만 영향? | 프롬프트 | 계속 판단 |
| 모두가 지켜야 함? | `AGENTS.md` / 프로젝트 설정 | 계속 판단 |
| 반복 가능한 흐름? | Skill | 계속 판단 |
| 실시간 외부 데이터·조작 필요? | MCP | 계속 판단 |
| 개인 장기 선호만? | 기억 / 사용자 설정 | 프롬프트 |

한 요구가 두 열에 동시에 걸리면, 보통은 **계층을 쪼개야** 하며 한곳에 억지로 넣으면 안 됩니다.

## 세 가지 전형 예시

### 예 1: 팀이 회귀 테스트를 자꾸 깜빡함

채팅에서 “테스트 돌리자”고만 말하지 마세요.

더 안정적인 방법:

1. `AGENTS.md`에 “비즈니스 로직 변경 시 `pnpm test` 필수”를 명시
2. 흐름이 복잡하면 테스트 실행 Skill을 추가
3. CI로 최종 안전망을 둠

### 예 2: PR review마다 같은 형식으로 출력하고 싶음

긴 템플릿을 매번 붙여 넣지 마세요.

더 안정적인 방법:

1. 출력 구조를 Skill로 만듦
2. `description`에 “사용자가 review·심사·머지 전 점검을 말할 때 사용”을 명확히 씀
3. 팀이 통일해 쓰면 Skill 경로를 프로젝트 문서에 적음

### 예 3: Linear 티켓을 읽고 코드를 고쳐야 함

API token을 대화에 붙여 넣지 마세요.

더 안정적인 방법:

1. MCP로 Linear를 연결
2. 기본은 읽기 전용 권한
3. 고정 흐름이 필요하면 Skill로 “먼저 티켓 → 코드 → 방안”을 규정

## 가장 흔한 함정

### `AGENTS.md`를 백과사전처럼 쓰기

하드 제약이 눈에 안 띄고, 중요한 명령·금지구역이 묻힙니다. `AGENTS.md`는 짧고, 단단하고, 실행 가능해야 합니다.

### Skill을 “만능 수납함”으로 쓰기

한 Skill에 review·배포·디버그·일지를 한꺼번에 넣으면 트리거도 어렵고 유지보수도 어렵습니다.

### MCP를 기본 답으로 삼기

저장소에서 바로 읽을 수 있는 정보에 “고급”을 위해 외부 도구를 또 붙일 필요는 없습니다. MCP는 능력 확장이지, 복잡도 보상이 아닙니다.

### 기억에 팀 사실을 싣기

누구 계정에 기억됐는지에 따라, 떠나가거나 기기를 바꾸면 규칙이 사라집니다. 이런 정보는 저장소로 돌려보내야 합니다.

## 권장 착수 순서

팀이 아직 어수선하다면 이 순서로 수렴하세요.

1. 최소 가용 `AGENTS.md`부터 작성
2. 세 번 이상 반복된 흐름을 Skill로 수렴
3. 외부 시스템이 정말 필요할 때만 MCP 도입
4. 마지막에 개인 기억과 선호 정리

**협업 합의**를 먼저 안정시킨 뒤 능력을 넓히기 쉽습니다.
