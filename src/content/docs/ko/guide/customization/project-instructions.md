「프로젝트 설명」은 Codex가 저장소를 이해하는 **정적 컨텍스트**이며, 단일 파일 형식에 한정되지 않습니다.

## 내용

- `AGENTS.md` 외에 프로젝트급 정보를 어디에 둘지
- README, docs, 스크립트 파일 사이의 역할 분담
- 어떤 정보는 저장소에, 어떤 정보는 현재 대화에만 둘지

## 프로젝트 컨텍스트의 구성

| 출처 | 역할 |
|---|---|
| `AGENTS.md` | 협업 규칙과 명령(권위: 이 장의 AGENTS 시리즈) |
| `README.md` | 프로젝트가 무엇인지, 어떻게 시작하는지 |
| `docs/` | 아키텍처, ADR, 운영 핸드북 |
| 의존성과 스크립트 | `package.json`, `Makefile` 등 실행 가능한 진실 |

Codex는 도구로 이런 자료를 읽습니다. 핵심은 **진실이 하나**여야 한다는 점입니다. README의 시작 명령은 실제로 돌아가야 합니다.

## 기본 실천

1. 루트 `README.md`에 용도·설치·개발·테스트 네 구간이 있게 함
2. **Codex에 반복해서 주는 설명**을 `AGENTS.md`로 내림
3. 작업에서 전문을 붙여 넣기보다 `@`로 구체 파일을 가리킴:

```text
@AGENTS.md 의 테스트 요구에 맞춰 @src/auth/login.ts 의 null 포인터를 고쳐 주세요.
관련 설계는 @docs/auth-flow.md 를 보세요.
```

## 왜 중요한가

흔한 상황은 이렇습니다.

- README는 한 세트
- docs는 다른 세트
- 실제로 도는 명령은 `package.json`에 숨김

이때는 사람뿐 아니라 Codex도 헷갈립니다. 저장소의 “프로젝트 진실”을 되도록 모으고, 되도록 일치시키는 것이 핵심입니다.

## 「대화 컨텍스트」와의 역할 분담

- **프로젝트 설명**: 수개월 동안 비교적 안정적
- **대화 컨텍스트**: 이번 목표, 제약, 중간 결론

긴 작업 중 어떤 규칙이 반복해서 언급되면, 열 개의 스레드에 복사하지 말고 `AGENTS.md`나 `docs/`에 **되돌려 쓰세요**. [컨텍스트를 집중 유지하기](/guide/context/keep-context-focused/)를 참고하세요.

## 흔한 실수

- README가 낡아 Codex가 잘못된 명령으로 동작
- 모든 문서를 거대한 `CONTEXT.md` 하나에 넣고 아무도 유지하지 않음
- 민감 정보를 공개 저장소 설명에 둠

## 흔한 오해

### 1. 대화에서만 잘 설명하면 저장소 문서가 좀 어지러워도 된다?

단기에는 버틸 수 있어도, 장기에는 점점 더 어지러워집니다.

다음에 또 설명해야 하고, 다른 사람은 이번 설명을 보지 못합니다.

### 2. `AGENTS.md`가 모든 프로젝트 설명 문제를 해결한다?

그것도 아닙니다.

`AGENTS.md`는 규칙과 협업 제약에 맞고, 프로젝트 소개·아키텍처 배경·완전한 운영 설명을 대체하기엔 맞지 않습니다.

### 3. 문서가 많을수록 좋다?

더 중요한 것은 다음과 같습니다.

- 역할 분담이 분명함
- 내용이 일치함
- 핵심 명령이 실행 가능함

## 역할 분담 제안

- `README.md`: 프로젝트가 무엇인지, 어떻게 시작·테스트하는지
- `AGENTS.md`: 협업 규칙, 금지구역, 완료 정의
- `docs/`: 더 긴 배경, 아키텍처, 프로세스 설명
- 스크립트와 설정 파일: 실행 가능한 진실

프로젝트 설명의 핵심은 Codex와 사람이 같은 “저장소 진실”을 더 쉽게 찾게 하는 것입니다. 문서 개수 자체는 핵심이 아닙니다.
