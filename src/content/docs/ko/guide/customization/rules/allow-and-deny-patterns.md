**Rules(규칙)**는 설정이나 프로젝트 파일에서 어떤 shell 명령·경로·도구 호출을 **허용하거나 금지**할지 선언합니다. 매번 수동 승인을 줄이면서, 위험한 조작이 자동화되지 않게 합니다.

## 내용

- Allow / Deny 규칙이 어떻게 동작하는지
- 샌드박스, 승인 팝업, `AGENTS.md`와의 관계
- 팀 규칙 예시

## 규칙이 실제로 하는 일

“규칙”이 추상적으로 느껴지면, Codex가 무엇을 할 수 있고 무엇을 못 하는지 미리 약속해 두고, 매번 현장 판단과 수동 승인에만 의존하지 않게 한다고 보면 됩니다.

가치는 크게 두 가지입니다.

- 매일 일어나지만 매번 확인해야 했던 저위험 조작을 줄임
- 자동으로 일어나면 안 되는 고위험 조작을 미리 막음

## 규칙 유형(개념)

| 유형 | 예시 |
|---|---|
| 명령 allowlist | `npm test`, `git status` 허용 |
| 명령 denylist | `rm -rf`, `curl \| bash` 금지 |
| 경로 | `../` 쓰기 금지, `~/.ssh` 읽기 금지 |
| 네트워크 | 외부망 금지 또는 registry 도메인만 허용 |

[권한 매트릭스](/ko/guide/reference/permission-matrix/)와 대조하세요. 규칙은 **설정 가능한** enforcement이고, 매트릭스는 **전형적 기본값**을 설명합니다.

## 권장 계층

```text
조직 호스팅 정책(덮어쓸 수 없음)
    ↓
프로젝트 rules + AGENTS.md(Git 심사)
    ↓
개인 allowlist 보완(로컬만)
    ↓
단발 작업 prompt 제약
```

## 흔한 오해

### 규칙은 팝업을 줄이려고만 있는 것이 아님

allowlist를 처음 들으면 목표를 “팝업·중단을 줄이는 것”으로만 생각하기 쉽습니다.

팝업을 줄이는 것은 일부일 뿐이고, 더 중요한 것은 저위험은 통과시키고 고위험은 막는 것입니다.

### 규칙 ≠ 샌드박스

샌드박스는 “최대 어디까지 닿을 수 있는지”를 제한하고, 규칙은 “원칙적으로 어떤 동작을 하면 안 되는지”를 약속합니다.

둘을 함께 쓰는 편이 맞고, 하나로 다른 하나를 대체하지 마세요.

### 팀 하한선을 누군가의 로컬에만 두지 마세요

“push 금지”, “`.env` 건드리지 마”가 당신 로컬 규칙에만 있으면 다른 사람은 여전히 밟을 수 있습니다.

팀 하한선은 review 가능한 곳에 두는 편이 맞습니다.

## 팀 예시(예시이며 그대로 복붙용이 아님)

**허용:**

- 패키지 매니저로 **프로젝트 안** 의존성 설치
- 문서에 있는 테스트 스크립트 실행

**거부:**

- `git push`, `git reset --hard`
- `.env*` 읽기/쓰기(명시적 작업이 아니면)
- 저장소 내용을 담은 요청을 공망에 POST

규칙은 구두 약속이 아니라, 팀이 review할 수 있는 파일에 쓰세요.

## 흔한 실수

- Allowlist가 너무 넓음(`bash` 허용 ≈ 전부 허용)
- deny만 하고 allow가 없어 승인이 여전히 많음
- 규칙과 `AGENTS.md`가 모순

## 시작 제안

규칙을 막 정리할 때 처음부터 완전한 정책이 필요하진 않습니다. 이 두 단계면 충분합니다.

1. 매일 자주 돌리고 위험이 낮은 명령 3–5개를 명시
2. 절대 자동 실행되면 안 되는 고위험 동작을 몇 개 명시

최소 경계를 먼저 안정시킨 뒤 세분화하세요.

## 보안 경계

- 규칙은 code review와 브랜치 보호를 **대체하지 않음**
- 악성 prompt가 Agent에게 규칙 우회를 유도할 수 있음 — 샌드박스 기본을 엄격하게
- 규칙 변경은 CI를 바꾸듯 PR로

좋은 allow/deny 규칙은, 어떤 동작이 합리적이고 어떤 동작이 일어나면 안 되는지 미리 분명히 말해 둡니다.
