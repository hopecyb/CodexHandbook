팀이 Codex를 쓸 때 **규칙 정책**은 다음을 답합니다. 어떤 제약이 회사 전체에서 통일인지, 어떤 제약이 저장소 유지인지, 개인이 완화할 수 있는지. 이 장은 [명령 규칙](/guide/customization/rules/command-rules/)과 [허용과 거부 패턴](/guide/customization/rules/allow-and-deny-patterns/)의 거버넌스 관점입니다.

## 내용

- 조직 호스팅 정책 vs 프로젝트 규칙 vs 개인 선호
- 규칙 변경이 심사·배포를 어떻게 거치는지
- `AGENTS.md`, Hooks, CI와의 협력

## 팀 규칙 정책의 역할

팀 규칙 정책이 답하는 것은, 어떤 경계를 회사가 통일하고, 어떤 경계를 프로젝트가 정하며, 어떤 것이 개인 습관인지입니다.

이 계층이 흐리면 두 문제가 쉽게 납니다.

- 팀 전체가 같아야 할 규칙이 누군가의 PC에만 살아 있음
- 일시적 편의의 개인 설정이 팀 표준으로 오인됨

## 누구에게 맞나

| 역할 | 관심사 |
|---|---|
| 엔지니어링 리더 | 하한선 deny, 감사 요구 |
| 저장소 유지자 | 프로젝트 allowlist, 테스트 명령 |
| 개인 개발자 | 정책이 허용하는 범위의 로컬 보완 |

## 흔한 오해

### 팀 규칙은 통일할수록 항상 좋은가?

어떤 경계(예: 고위험 deny)는 조직 전체에서 통일해야 합니다.

하지만 모든 저장소를 억지로 똑같이 맞추면, 규칙이 너무 넓거나 좁아져 결국 아무도 믿지 않게 됩니다.

핵심은 조직·프로젝트·개인 계층의 경계를 나누는 것이지, 모든 규칙을 한 모양으로 만드는 것이 아닙니다.

### 개인 보완이 팀 하한선을 약화하면 안 됨

로컬에 편의 설정을 더할 수는 있지만, 팀·조직이 이미 정한 하한선을 우회하면 안 됩니다.

겉으로는 “로컬이 더 효율적”이어도, 협업에 지뢰를 묻는 일입니다.

## 권장 계층 모델

```text
L1 조직 호스팅(Managed)     → 프로젝트/개인이 덮을 수 없음
L2 팀 템플릿 저장소            → 새 저장소가 상속하는 rules 조각
L3 프로젝트 rules + AGENTS.md  → Git PR 심사
L4 개인 설정                → 로컬만, L1을 약화하면 안 됨
L5 단발 작업 prompt         → 임시 조이기는 가능, 임시 완화는 L1 제한
```

[AGENTS.md 범위](/guide/customization/agents-md/scope-and-precedence/)와 대조하세요. **규칙은 실행 enforcement에 가깝고, AGENTS.md는 동작 설명에 가깝습니다.** 둘은 일치해야 하며, 서로 모순된 요구를 따로 쓰지 마세요.

## 기본 실천

1. **「절대 불허」 목록(deny)부터**: `git push --force`, `~/.ssh` 읽기, 저장소 내용을 공망에 POST
2. **「일상 허용」 목록(allow)**: 테스트, lint, 읽기 전용 git
3. **호스팅으로 L1 배포**(조직이 Managed configuration을 켠 경우)
4. **각 서비스/Monorepo 서브패키지**는 L3를 추가할 수 있으나 L1과 충돌하면 안 됨
5. **분기 회고**: 승인 로그의 반복 「오차단」「오허용」을 규칙 PR로 되돌림

## 권장 워크플로: 규칙 변경

```text
제안(issue 또는 RFC)→ 보안/플랫폼 review → PR로 규칙 파일 수정
    → staging 저장소에서 전형 작업 시범 → 머지 → 공지 + 핸드북 페이지 갱신
```

큰 변경(예: 외부망 허용)은 [Hooks 감사](/skills/hooks/hooks-overview/)와 [acceptable use](/guide/team-enterprise/governance/acceptable-use/)를 함께 갱신하세요.

## Hooks·CI와 정렬

| 메커니즘 | 역할 |
|---|---|
| 규칙 | 실행 전 허용/거부 |
| Hooks | 복잡한 검증, 로그, 컴플라이언스 형식 |
| CI | 머지 게이트, 로컬 규칙과 동일 원천 스크립트 |

세 로직을 각자 쓰지 마세요. **단일 진실 원천**(예: `tools/codex-rules.json`)을 CLI와 CI가 함께 참조하는 편이 좋습니다.

## 흔한 실수

- 「push 하지 마」만 구두로 하고 규칙 파일은 갱신하지 않음
- 개인 로컬에서 샌드박스를 완화한 뒤 스크린샷을 「팀 표준」으로 씀
- Monorepo 하위 요구가 다른데 너무 넓은 전역 allowlist를 공유
- 규칙 변경 공지가 없어 동료가 갑자기 승인 대량 실패

## 규칙을 어느 계층에 둘지

이 세 질문을 보세요.

1. 모든 저장소가 지켜야 하는 하한선인가
2. 현재 프로젝트에만 성립하는가
3. 내가 편하려고 하는 개인 보완인가

보통 각각:

- 조직 계층
- 프로젝트 계층
- 개인 계층

## 보안 경계

- 규칙은 [위협 모델](/guide/team-enterprise/security/threat-model/)과 사건 대응 흐름을 대체하지 않음
- 규제 대상 데이터면 규칙과 데이터 등급·보존 정책을 함께 심사
- 긴급 우회에는 **감사 기록**과 사후 회고가 필요

## 검증 체크리스트

- [ ] 본 조직의 L1–L3 역할 분담을 그릴 수 있음
- [ ] 저장소 규칙 파일에 명확한 owner와 review 요구가 있음
- [ ] `AGENTS.md`, Hooks, CI와 서로 모순 없음
- [ ] 「오차단」 피드백 채널(issue 템플릿 또는 내부 양식)이 있음

팀 규칙 정책에서 가장 중요한 것은 “누가 어느 계층의 경계를 정하는지”를 먼저 나눈 뒤, 규칙을 어떻게 쓸지 정하는 것입니다.
