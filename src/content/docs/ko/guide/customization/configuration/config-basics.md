설정 파일은 로컬이나 프로젝트에서 **Codex 동작을 통일**하게 해, 세션마다 모델·승인 수준·샌드박스 정책을 다시 고르지 않아도 됩니다.

## 이 페이지 내용

- 설정을 어디에 두고, 프로젝트급과 사용자급이 어떻게 겹치는지
- 가장 자주 바꾸는 항목: 모델, 승인, 샌드박스, 기본 작업 디렉터리
- `AGENTS.md`와의 경계: 설정은 「능력 스위치」, AGENTS는 「프로젝트에서 코드를 어떻게 쓰는지」

## 설정이 실제로 관장하는 것

설정은 Codex의 **기본 작업 습관**에 가깝습니다.

예:

- 기본으로 어떤 모델을 쓸지
- 기본으로 보안 경계를 얼마나 조일지
- 기본으로 어느 디렉터리에서 일할지

한 번의 임시 요구가 아니라, 대부분의 경우 어떻게 시작할지입니다.

## 설정 계층

| 계층 | 전형 위치 | 내용 |
|---|---|---|
| 사용자급 | `~/.codex/` 아래 설정(구체 파일명은 공식 문서 기준) | 기본 모델, 개인 승인 습관 |
| 프로젝트급 | 저장소 안 설정 조각 또는 `codex` 관련 프로젝트 파일 | 팀이 공유하는 샌드박스/도구 정책 |
| 호스팅 | 조직이 배포 | 개인이 덮을 수 없는 강제 항목 |

**쉽게 바뀌는 사실**(경로, 필드명, TOML 키)은 [OpenAI Codex 문서](https://developers.openai.com/codex)를 따르세요. 이 페이지는 개념과 결정 방식만 설명합니다.

## 흔한 오해

### 설정은 많을수록 전문적이다?

설정 파일을 처음 보면 가능한 것을 다 넣고 싶어집니다.

초보자에게는 보통 고빈도 몇 항목만 고정하면 됩니다. 예:

- 기본 모델
- 기본 승인/샌드박스 정책
- 기본 작업 디렉터리

이 몇 가지를 먼저 안정시키는 편이, 모든 필드를 한 번에 연구하는 것보다 낫습니다.

### 설정 = 프로젝트 규칙?

“모든 협업자가 지켜야 하는” 요구라면 보통 `AGENTS.md`나 프로젝트 문서가 맞고, 로컬 설정에만 두면 안 됩니다.

예:

- 커밋 전에 돌릴 검사
- 수정하면 안 되는 디렉터리
- 자동 push 하면 안 되는 작업 유형

이런 것은 개인 설정만으로 유지하면 안 됩니다.

## 자주 바꾸는 설정 의도

### 모델과 추론

- 일상 개발: 속도와 품질의 균형
- 복잡한 리팩터: 더 강한 추론 모델(요금제가 지원하면)
- 스크립트/CI: 고정 모델로 재현성

개념 배경: [모델과 추론](/ko/guide/foundations/models-and-reasoning/)

### 승인과 샌드박스

| 의도 | 설정 방향 |
|---|---|
| 초보/신뢰하지 않는 저장소 | 더 엄격한 승인, 네트워크·쓰기 범위 제한 |
| 신뢰하는 개인 프로젝트 | 안전 전제에서 중단을 줄일 수 있음 |
| 기업 저장소 | 호스팅 정책을 따르고 임의로 완화하지 않음 |

개념 배경: [권한과 승인](/ko/guide/foundations/permissions-and-approvals/), [샌드박스와 네트워크](/ko/guide/foundations/sandbox-and-network/)

### CLI와 App 일관성

같은 계정에서 CLI와 데스크톱 App은 **같은 보안 기준선**을 목표로 하세요. 「CLI는 전권, App은 엄격」 이중 기준을 피하세요.

## 최소 가용 실천

1. 공식 「Configuration」 장을 읽고 현재 버전의 파일 경로를 확인
2. 한 항목만 바꿈: 예 기본 샌드박스 모드, 일주일 관찰 후 조정
3. 팀 공유 항목은 저장소 문서에, 개인 선호는 로컬에
4. `AGENTS.md`에는 「이 프로젝트와 함께 Codex를 어떻게 쓸지」를 쓰고, 설정 전체를 복사하지 않음

## 어디에 둘지 판단하기

설정·`AGENTS.md`·작업 프롬프트 중 어디에 둘지 모르겠으면 이 질문을 보세요.

1. 대부분의 작업에 쓰는 기본 습관인가
2. 나만이 신경 쓰는 선호인가
3. 프로젝트 전체가 함께 지켜야 하는 규칙인가

대개:

- 기본 습관 → 설정
- 개인 선호 → 개인 계층
- 팀 합의 → 저장소

## 흔한 실수

- 편의를 위해 모든 승인을 끄고 프로덕션 데이터 디렉터리에서 프로젝트를 염
- API 키를 설정 파일에 쓰고 Git에 커밋
- 문서의 설정 키가 설치 버전과 불일치(CLI 업그레이드 후 미확인)

## 보안 경계

설정 파일에는 **경로 화이트리스트, 네트워크 정책, MCP 서버 목록**이 있을 수 있습니다. 변경 전에 「악성 prompt가 이 설정을 이용할 수 있는가」를 상상하세요. 기업 환경은 관리자가 배포해야 하며, 개인이 호스팅 정책을 우회하지 마세요.

설정은 거의 매번 반복해서 고르는 기본 항목에 맞고, 모든 규칙을 설정 파일에 쑤셔 넣을 필요는 없습니다.
