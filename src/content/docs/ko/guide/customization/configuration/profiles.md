**Profile(설정 묶음)**은 이름 있는 설정 세트(모델 + 샌드박스 + 승인 등)를 저장해, 장면마다 한 번에 전환하게 합니다. 매번 설정을 손으로 바꿀 필요가 없습니다.

## 이 글에서 다루는 것

- Profile과 「기본 설정 변경」의 차이
- 흔한 Profile 나누기
- 팀이 Profile 정의를 어떻게 공유하는지

## Profile이 관장하는 것

“설정”이 기본 작업 습관이라면, **Profile**은 “장면별 프리셋 묶음”입니다.

이렇게 보면 됩니다.

- 평소 개발용 한 세트
- 신뢰하지 않는 저장소용 한 세트
- 읽기 전용 심사용 한 세트
- CI 자동 작업용 한 세트

매번 스위치 여러 개를 임시로 고칠 필요가 없습니다.

## 전형 Profile 예시

| Profile 이름 | 의도 | 특징(개념) |
|---|---|---|
| `daily` | 일상 개발 | 균형 모델, 표준 샌드박스 |
| `strict` | 신뢰하지 않는 저장소 | 강한 승인, 네트워크 제한 |
| `review-only` | 읽기 전용 심사 | 쓰기 금지 또는 읽기만 허용 |
| `ci` | 파이프라인 | 고정 모델, 비대화형, push 없음 |

구체 필드는 [설정 항목 참고](/guide/reference/configuration-reference/)를 보세요.

## 사용 방식(개념)

1. 공식 문서에서 Profile 문법을 확인(`config.toml`의 `[profiles.name]` 또는 동등 구조와 관련될 수 있음)
2. Profile을 만들고 이름을 붙임
3. 시작 시 지정: `codex --profile strict`(명령은 `--help` 기준)
4. README에 「기여자는 `daily` 권장, CI는 `ci`」를 명시

CLI 세부: [CLI 설정](/guide/cli/configuration/)

## 흔한 오해

### Profile은 많을수록 유연하다?

처음에는 세분 장면마다 Profile을 만들고 싶어져, 이름이 열 개가 넘고 차이도 기억 못 하게 됩니다.

보통 가장 자주 쓰는 2–4개만 남기면 됩니다.

- 일상 개발
- 엄격 모드
- 읽기 전용 심사
- CI

위험 경계를 분명히 나눌 수 있으면 됩니다.

### Profile은 사고를 대체하는 스위치가 아님

어떤 Profile로 전환해도, 이후 모든 작업이 절대 안전하거나 절대 적합하다는 뜻은 아닙니다.

흔한 시작 상태를 바꿔 줄 뿐이며, 구체 작업은 여전히 현재 저장소와 위험 판단과 맞춰야 합니다.

## AGENTS.md와의 역할 분담

| | Profile | AGENTS.md |
|---|---|---|
| 관장 | 능력 스위치, 모델, 샌드박스 | 이 프로젝트에서 어떻게 쓰는가 |
| Git 커밋 | 선택(프로젝트급 profile 조각) | 예 |
| 개인/팀 | 개인 profile은 로컬 가능; 팀 profile은 PR | 팀 |

## 흔한 실수

- 저장소마다 Profile 10개를 만들고 아무도 유지하지 않음
- `ci` Profile이 여전히 `git push`를 허용
- Profile 이름과 문서가 불일치해 신입이 잘못 씀

## 시작 제안

Profile을 막 쓰기 시작하면 이렇게 하세요.

1. 먼저 `daily`를 기본 묶음으로 유지
2. `strict`를 추가해 익숙하지 않거나 위험이 큰 저장소에 대응
3. 팀에 자동화가 있으면 `ci`를 따로 추가

이미 대부분의 흔한 경우를 커버합니다.

Profile의 가치는 위험 장면마다, 이미 정리해 둔 기본 조합으로 빠르게 전환하는 데 있습니다.
