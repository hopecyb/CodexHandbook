핸드북의 명령·권한·가격·제품 기능은 버전에 따라 바뀝니다. **검증**은 독자가 문서대로 했을 때 결과가 예측 가능하게 합니다.

## 이 페이지 내용

문서 유지에 처음 참여하면 “문제가 안 보여”를 “이미 검증했다”로 착각하기 쉽습니다.

기술 핸드북에서는 둘이 많이 다릅니다.

- 전자는 주관적으로 맞아 보임
- 후자는 현재 버전·환경·단계로 실제로 시험했음

여기서 푸는 것은 “맞아 보임”을 “지금 맞다는 증거가 있음”으로 올리는 방법입니다.

## “검증”이 점검하는 것

“기술 내용 검증”은 글이 매끄러운지만 보는 것이 아니라, 독자가 오늘 따라 해도 정말 되는지 확인하는 일입니다.

특히 중요한 이유는 많은 내용이 영원히 안정적이지 않기 때문입니다. 예:

- 명령이 바뀜
- 메뉴 위치가 바뀜
- 권한 기본값이 조정됨
- 제품 능력과 가용 범위가 갱신됨

그래서 검증은 편집 결벽이 아니라, 독자가 낡은 문서를 따라 함정에 빠지지 않게 하는 일입니다.

## 상태 의미

| 상태 | 의미 |
|---|---|
| `planned` | 기획됨, 아직 미작성 |
| `draft` | 작성 중, 아직 완전 확정 아님 |
| `review` | 내용 완료, 재검토 대기 |
| `verified` | 표시된 근거로 검증됨 |
| `outdated` | 제품 변화 후 갱신 필요 |
| `archived` | 역사 보존, 주 탐색에 넣지 않음 |

## 흔한 오해

### 편집 상태와 검증 방법은 별개의 필드입니다

`editorialStatus`는 작성 및 검토 진행 상태를 기록합니다. `verification.kind`는 실제로 수행한 검증 종류를 기록합니다. `verified`라는 표시만으로 예제가 실행되었다고 추론할 수 없습니다.

| 검증 방법 | 뒷받침할 수 있는 결론 | 필수 근거 |
|---|---|---|
| `editorial` | 구조·표현 또는 사이트 내부 참조를 검토함 | 검토 요약과 날짜 |
| `source-checked` | 명시한 범위의 사실이 출처와 일치함 | 구체적인 출처 링크, 요약, 날짜 |
| `run-tested` | 기록된 환경에서 예제를 실행함 | 환경, 실행 및 검토 기록, 요약, 날짜 |

`run-tested`는 모든 플랫폼에서의 동작을 보장하지 않습니다. 요약에는 검증한 것과 검증하지 않은 것을 밝혀야 합니다. 독립 계산을 통한 자체 점검을 두 번째 사람의 검토라고 할 수 없습니다. 근거가 없는 옛 기록은 `legacyVerification`에 보관하며 새로운 검증 상태로 자동 해석하지 않습니다.

```yaml
editorialStatus: review
verification:
  kind: editorial
  checkedAt: "2026-09-18"
  summary: 구조와 사이트 내부 링크를 확인했습니다. 예제는 아직 실행하지 않았습니다.
```

출처 확인과 예제 실행에는 `evidence` 목록을 사용하며 각 항목에 `label`과 `href`를 넣습니다. 실행 기록에는 `environment`도 작성해 OS, 관련 클라이언트 버전, 의존성 버전을 명시합니다. 환경이나 근거 링크가 없는 실행 기록은 빌드에서 거부합니다. 링크가 존재한다는 사실만으로 근거가 충분한 것은 아닙니다. 유지 관리자가 기록을 읽어야 합니다.

### 커뮤니티 글은 이해를 돕지만 사실 검증을 대체하지 않음

커뮤니티 글 등은 어떤 주제를 보강할지 찾는 데 좋습니다.

하지만 다음이 관여하면:

- 명령 이름
- 권한 동작
- 제품 진입점
- 가격, 할당량, 지역 차이

공식 문서나 현재 실제 실행 결과로 돌아가야 합니다.

### 검증은 문장 하나만 보는 일이 아님

문장마다 맞아 보여도 이어지면 성립하지 않을 수 있습니다. 예:

- 적용 제품과 실제 페이지가 불일치
- 단계 순서가 틀림
- 기본 전제가 쓰이지 않음
- 제목이 약속한 범위가 본문이 실제로 검증한 범위보다 큼

그래서 문구만 훑지 말고 “전체 작업 흐름”을 따라 검증하세요.

## 검증 체크리스트

1. **범위 표시**: 제품(App/CLI/IDE/Cloud), OS, CLI 버전
2. **단계별 재현**: 처음부터 또는 깨끗한 worktree로 한 번 따라 함
3. **공식 근거**: 제품 관련 사실에는 구체적인 공식 출처를 덧붙입니다. 안정적인 방법 연습에서는 실제 입력과 확인 기록을 사용하고 공식 보증을 꾸며내지 않습니다
4. **커뮤니티 출처**: 커뮤니티 자료를 빌려도 주제 참고만, 사실은 공식 기준
5. **날짜 갱신**: `verification.checkedAt`에는 실제 확인한 날짜만 적습니다. 옛 날짜를 일괄 갱신해 재검토한 것처럼 보이게 하지 않습니다
6. **독립 재검토**: `verified`는 작성자 외의 다른 사람이 확인하는 것을 권장

## 검증 순서

이 순서가 빠뜨리기 가장 적습니다.

1. 페이지가 말하는 제품·진입점·장면을 먼저 확인
2. 글의 단계를 처음부터 한 번 따라 함
3. 공식 문서로 쉽게 바뀌는 정보를 대조
4. 불확실하거나 재현하지 못한 곳을 강등 처리
5. 마지막에 상태와 날짜를 갱신

증거가 부족하면 `verified`를 미리 쓰지 말고 `review`를 유지하세요.

## 쉽게 바뀌는 정보

다음은 분기마다 또는 major 릴리스에 맞춰 재검증:

- 명령·서브커맨드 이름, flags
- 권한 기본값과 샌드박스 동작
- 요금제, 모델 이름, 지역 가용성
- MCP/Hook 이벤트 이름

## 실패 시

- 실제에 맞춰 `review`, `draft`, `outdated`로 강등
- PR에 어느 단계가 공식과 다른지 설명
- 큰 편차는 issue를 열고 `outdated`로 표시
