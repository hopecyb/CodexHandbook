핸드북의 명령·권한·가격·제품 기능은 버전에 따라 바뀝니다. **검증**은 독자가 문서대로 했을 때 결과가 예측 가능하게 합니다.

## 이 페이지 내용

문서 유지에 처음 참여하면 “문제가 안 보여”를 “이미 검증했다”로 착각하기 쉽습니다.

기술 핸드북에서는 둘이 많이 다릅니다.

- 전자는 주관적으로 맞아 보임
- 후자는 현재 버전·환경·단계로 실제로 시험했음

여기서 푸는 것은 “맞아 보임”을 “지금 맞다는 증거가 있음”으로 올리는 방법입니다.

## “검증”이 점검하는 것

“기술 내용 검증”은 글이 매끄러운지만 보는 것이 아니라, 독자가 오늘 따라 해도 정말 되는지 확인하는 일입니다.

특히 중요한 이유는 많은 내용이 영원히 안정적이지 않기 때문입니다. 예:

- 명령이 바뀜
- 메뉴 위치가 바뀜
- 권한 기본값이 조정됨
- 제품 능력과 가용 범위가 갱신됨

그래서 검증은 편집 결벽이 아니라, 독자가 낡은 문서를 따라 함정에 빠지지 않게 하는 일입니다.

## 상태 의미

| 상태 | 의미 |
|---|---|
| `planned` | 기획됨, 아직 미작성 |
| `draft` | 작성 중, 아직 완전 확정 아님 |
| `review` | 내용 완료, 재검토 대기 |
| `verified` | 표시된 근거로 검증됨 |
| `outdated` | 제품 변화 후 갱신 필요 |
| `archived` | 역사 보존, 주 탐색에 넣지 않음 |

## 흔한 오해

### `verified`는 확신이 아니라 증거

어조가 아니라 증거 상태입니다.

재현을 했고, 공식 근거를 대조했고, 페이지 범위와 날짜가 맞을 때만 `verified`에 적합합니다.

### 커뮤니티 글은 이해를 돕지만 사실 검증을 대체하지 않음

커뮤니티 글 등은 어떤 주제를 보강할지 찾는 데 좋습니다.

하지만 다음이 관여하면:

- 명령 이름
- 권한 동작
- 제품 진입점
- 가격, 할당량, 지역 차이

공식 문서나 현재 실제 실행 결과로 돌아가야 합니다.

### 검증은 문장 하나만 보는 일이 아님

문장마다 맞아 보여도 이어지면 성립하지 않을 수 있습니다. 예:

- 적용 제품과 실제 페이지가 불일치
- 단계 순서가 틀림
- 기본 전제가 쓰이지 않음
- 제목이 약속한 범위가 본문이 실제로 검증한 범위보다 큼

그래서 글면만 훑지 말고 “전체 조작 체인”으로 검증하세요.

## 검증 체크리스트

1. **범위 표시**: 제품(App/CLI/IDE/Cloud), OS, CLI 버전
2. **단계별 재현**: 처음부터 또는 깨끗한 worktree로 한 번 따라 함
3. **공식 근거**: OpenAI 공식 문서 또는 헬프 센터 링크 최소 하나
4. **커뮤니티 출처**: 커뮤니티 자료를 빌려도 주제 참고만, 사실은 공식 기준
5. **날짜 갱신**: 푸터 `최근 검증: YYYY-MM-DD`
6. **독립 재검토**: `verified`는 비작성자 2인 확인 권장

## 검증 순서

이 순서가 빠뜨리기 가장 적습니다.

1. 페이지가 말하는 제품·진입점·장면을 먼저 확인
2. 글의 단계를 처음부터 한 번 따라 함
3. 공식 문서로 쉽게 바뀌는 정보를 대조
4. 불확실하거나 재현하지 못한 곳을 강등 처리
5. 마지막에 상태와 날짜를 갱신

증거가 부족하면 `verified`를 미리 쓰지 말고 `review`를 유지하세요.

## 쉽게 바뀌는 정보

다음은 분기마다 또는 major 릴리스에 맞춰 재검증:

- 명령·서브커맨드 이름, flags
- 권한 기본값과 샌드박스 동작
- 요금제, 모델 이름, 지역 가용성
- MCP/Hook 이벤트 이름

## 실패 시

- 실제에 맞춰 `review`, `draft`, `outdated`로 강등
- PR에 어느 단계가 공식과 다른지 설명
- 큰 편차는 issue를 열고 `outdated`로 표시
