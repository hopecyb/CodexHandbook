이 페이지는 `src/content/docs/`에 **가이드형** 페이지(순수 사례·순수 참고표가 아님)를 추가하거나 다시 쓰는 방법을 설명합니다.

## 이 페이지 내용

흔한 막힘:

- 가이드 한 페이지가 어떤 모습이어야 할지 모름
- “튜토리얼”인지 “규범”인지 “목차 요약”인지 헷갈림
- 초보자에게 진짜 도움이 되게 쓰는 법을 모름

이 질문들을 나눠 설명해, 이후 유지하기 쉽고 독자도 읽을 수 있는 가이드 페이지를 쓰게 합니다.

## 가이드 페이지의 역할

여기의 “가이드 페이지”는 자료를 쌓아 두면 끝이 아닙니다. 독자가 “이 주제가 있다”에서 “언제 쓰고, 먼저 무엇을 보고, 어떤 함정을 피할지 대략 안다”로 가게 해야 합니다.

그래서 지식점 목록이나 명령 목록만이 아니라, 다음에 어떻게 이어갈지도 알려야 합니다.

## Frontmatter

```yaml
---
title: 페이지 제목
description: 이 글이 푸는 문제를 한 문장으로
---
```

선택적으로 문말에 통일 푸터(기존 페이지와 동일):

```markdown
---

**상태:** planned | draft | review | verified | outdated | archived
**적용 제품:** App / CLI / IDE / Cloud
**최근 검증:** YYYY-MM-DD
```

## 권장 구조

[외부 자료 통합 템플릿](/docs/planning/external-source-integration.md#6-추천页面模板)의 소절을 골라 쓰세요. 흔한 조합:

- 페이지가 푸는 문제
- 누구에게 맞는지
- 최소 가용 실천
- 권장 워크플로
- 흔한 실수
- 보안 경계
- 검증 체크리스트
- 참고 출처

제품 조작 페이지는 단계 중심, 개념 페이지는 표·도식 중심일 수 있습니다.

## 흔한 오해

### 모든 페이지를 백과로 쓰면 안 됨

가이드를 처음 쓸 때 아는 내용을 다 쑤셔 넣기 쉽고, 초점이 사라집니다.

더 흔한 쓰기는:

- 페이지가 주로 푸는 문제를 먼저
- 독자가 가장 오해하기 쉬운 점을 다음
- 쓸 만한 실천이나 판단법을 제시

모든 세부를 한 번에 채우는 것보다 신입에게 보통 더 도움이 됩니다.

### 자기가 쓸 줄 아는 것만으로는 부족, 남이 어떻게 읽는지도

당신은 맥락을 알지만, 처음 온 독자는 모릅니다.

다리 정보를 의도적으로 보강하세요.

- 누구에게 맞는지
- 읽은 뒤 무엇을 해결할 수 있는지
- 먼저 손대려면 어디를 잡을지

### 가이드 페이지가 공식 문서를 대체하지 않음

커뮤니티 핸드북은 이해·연결·착수를 돕지만, 바뀌는 사실은 공식 문서로 돌아가 검증해야 합니다.

## 교차 링크

- 사이트 내 링크는 루트 경로: `/cases/workflows/explore-plan-execute-verify/`
- 권위 페이지로 링크하고 긴 반복을 피함
- 새 페이지는 장 `index.md`와 `astro.config.mjs` sidebar에 등록

## 어조

- 한국어, 실무자 대상(합니다체)
- 불확실성을 인정(「공식 문서 기준」)
- 「만능 프롬프트」 서사를 쓰지 않음

## 작성 순서

이 순서로:

1. 페이지가 진짜 푸는 문제를 먼저
2. 독자가 가장 오해하거나 건너뛰기 쉬운 점
3. 최소 가용 실천·워크플로·판단법
4. 마지막에 교차 링크와 참고 출처

## 검증

PR 전에 [기술 내용 검증](/guide/contributing/verify-technical-content/)을 읽으세요. 명령·가격·권한 등 쉽게 바뀌는 정보는 반드시 재확인합니다.

좋은 가이드 페이지는 “자료를 다 썼는지”가 아니라, 처음 온 독자가 왜 있는지·먼저 무엇을 볼지·다음에 어디로 갈지를 알게 하는 데 있습니다.
