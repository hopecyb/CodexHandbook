“프로젝트”와 “작업”은 단순해 보이지만, 처음 쓸 때 쉽게 혼동합니다. 프로젝트는 지금 다루는 파일이나 저장소이고, 작업은 이번에 Codex에게 맡기는 구체적 일입니다.

예를 들어:

- 문서 사이트 저장소 → 프로젝트
- “홈페이지 용어를 더 이해하기 쉽게 고쳐 줘” → 작업

이 구분이 중요한 이유는 데스크톱 App에 항상 두 층이 함께 존재하기 때문입니다.

- 지금 어느 프로젝트에서 일하는가
- 이번에 구체적으로 무엇을 시킬 것인가

## 프로젝트

- 연습용 디렉터리나 저장소 루트를 추가합니다
- 한 번에 한 프로젝트에 집중해 컨텍스트가 섞이지 않게 합니다

“프로젝트”는 이번 협업의 **작업장**으로 보면 됩니다.  
작업장이 틀리면 이후 문제가 연쇄적으로 빗나갑니다.

## 작업

- 완전한 프롬프트로 작업을 시작합니다
- 계획과 도구 호출을 관찰합니다
- 필요할 때 승인하거나 거부합니다

“작업”은 이번에 준 **구체적 위임**입니다.  
위임이 명확할수록 Codex가 추측하며 진행하기 어렵습니다.

개념 대조: [스레드, 작업, 프로젝트](/guide/foundations/threads-tasks-and-projects/)

## 흔한 오해

### 1. 왜 프로젝트를 먼저 고르고, 바로 질문하면 안 되나요?

Codex가 이번엔 어떤 파일·어떤 저장소를 대상으로 일하는지 알아야 하기 때문입니다.

프로젝트를 잘못 고르면 “파일을 못 본다”, “다른 곳을 고친다” 같은 문제가 늘어납니다.

### 2. 한 프로젝트에 여러 작업을 둘 수 있나요?

가능합니다.  
더 안전한 방식은 다음과 같습니다.

- 같은 프로젝트 안에서
- 한 번에 하나의 명확한 작업
- 끝난 뒤 다음 작업을 연다

이렇게 하면 컨텍스트가 덜 섞입니다.

### 3. 작업을 처음 어떻게 말해야 하나요?

다음 세 가지를 가능한 한 넣으세요.

- 목표
- 범위 제한
- 완료 기준

### 4. 큰 요구는 한 작업에 넣어야 하나요?

범위가 크면 더 안전한 방법은 다음과 같습니다.

- 프로젝트는 그대로 두고
- 여러 작업으로 나눕니다
- 각 작업은 하나의 명확한 목표만 다룹니다

## 자주 쓰는 순서

데스크톱 App에서 처음 일할 때는 다음 순서를 권합니다.

1. 프로젝트가 맞는지 확인합니다
2. 작업 목표가 주요 한 가지만 말하는지 확인합니다
3. 범위 제한과 완료 기준을 보완합니다
4. 시작한 뒤 계획·도구 호출·변경 결과에 집중합니다
