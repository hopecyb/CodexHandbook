병렬 Agent는 **원래 독립적으로 진행할 수 있는 일**을 나누어, 메인 스레드가 조율·검수·병합 결정에 집중하게 하는 데 적합합니다.

나눔이 적절하면 대기 시간을 크게 줄일 수 있습니다. 나눔이 잘못되면 충돌만 더 빨리 만듭니다.

## 흔한 오해

많은 사람이 “병렬 Agent”를 처음 보면 “더 빠르다”가 핵심이라고 생각합니다. 틀린 말은 아니지만 충분하지 않습니다.

전제는 **그 작업들이 원래 독립적으로 성립한다**는 것입니다. 실제로는 서로 의존하는데 억지로 나누면, 전제 맞추기·결과 회수·충돌 처리에 시간이 들어가 오히려 느려집니다.

## 언제 병렬이 적합한가

| 적합 | 부적합 |
|---|---|
| 독립된 조사 작업 두 개를 동시에 진행 | 여러 Agent가 같은 핵심 파일을 동시에 수정 |
| 읽기 전용 분석을 돌리면서 문서 초안을 작성 | 요구가 자주 바뀌어 계속 명확화가 필요 |
| 프론트 페이지와 백엔드 API 경계가 분명 | 한 문제가 다른 결과에 크게 의존해야 시작할 수 있음 |

자주 쓰는 판단 기준:

- **산출물을 명확히 정의할 수 있을 때** 병렬이 적합합니다
- **경계를 먼저 합의할 수 있을 때** 병렬이 적합합니다
- **독립적으로 검증할 수 있을 때** 병렬이 적합합니다

## 메인 Agent의 역할

병렬 모드에서 메인 Agent는 모든 하위 작업을 직접 끝낼 필요가 없습니다. 다음 세 가지에 집중합니다.

1. 각 하위 작업의 목표와 금지 구역을 명확히 합니다
2. 결과가 검증 가능한지 추적합니다
3. 결과가 충돌할 때 최종 선택을 합니다

메인 Agent는 작은 기술 책임자에 가깝습니다. 직접 실행보다 조율과 선택이 중심입니다.

## 권장 나누는 법

### “공정”이 아니라 “문제”를 나눕니다

더 나은 나눔:

- Agent A: 로그인 실패가 token 새로고침 때문인지 분석
- Agent B: 최근 두 번의 인증 관련 변경 점검

나쁜 나눔:

- Agent A: 로그 절반 보기
- Agent B: 로그 나머지 절반 보기

전자는 각 작업에 완전한 목표가 있습니다. 후자는 기계적 분할이라 회수 비용이 큽니다.

### 우선 이런 유형으로 나눕니다

- **읽기 전용 분석**: 코드·로그·문서 읽기, 위험 목록
- **방안 비교**: A/B 구현 경로, 라이브러리 선정, 권한 방안
- **경계가 분명한 산출물**: 독립 페이지, 독립 문서, 독립 모듈

## 위임 템플릿

병렬 Agent에 주는 설명에는 다음 네 항목을 넣으세요.

```text
작업: checkout 흐름의 쿠폰 계산만 분석하고, 코드는 수정하지 말 것.
산출: 200자 요약 + 핵심 파일 경로 + 위험 지점 + 다음 단계 제안.
경계: 결제 모듈 밖 디렉터리는 검색하지 말 것; 쓰기 명령은 실행하지 말 것.
검수: 결론은 파일 또는 로그 증거로 되돌아갈 수 있어야 함.
```

“이 문제 좀 봐 줘”보다 훨씬 효과적입니다.

## 세 가지 흔한 병렬 패턴

### 1. 이중 경로 조사

적합: 어느 경로가 맞는지 아직 불확실할 때.

- Agent A가 기존 구현을 조사
- Agent B가 대안을 조사
- 메인 스레드가 비용·위험·호환성을 비교

### 2. 계층 진행

적합: 시스템 경계가 이미 분명할 때.

- Agent A가 문서 또는 프롬프트 계층을 처리
- Agent B가 코드 또는 설정 계층을 처리
- 메인 스레드가 일관성 점검

### 3. 초안 + 검토

적합: 먼저 한 버전을 만든 뒤 빠르게 재검토할 때.

- Agent A가 초안을 만듦
- Agent B는 review만 하고 수정하지 않음
- 메인 스레드가 채택 여부를 결정

문서 보완, PR 검토, 사례 정리에 잘 맞습니다.

## 충돌 관리

병렬에서 가장 자주 막히는 지점은 병합입니다.

### 미리 정할 경계

- 어느 디렉터리를 어느 Agent가 담당하는가
- 공유 설정 파일 수정을 허용하는가
- 최종 커밋 권한은 누구에게 있는가

### 이런 경우 직렬로 되돌리세요

- 두 하위 작업이 같은 비즈니스 흐름을 모두 수정해야 함
- 한 Agent의 결론이 다른 Agent의 전제를 계속 뒤집음
- “컨텍스트 설명”에 쓰는 시간이 작업 진행보다 많아짐

조율 비용이 절약한 시간보다 크면 병렬의 의미가 사라집니다.

## 검토와 검수

각 병렬 Agent의 출력은 최소한 다음 중 하나를 충족해야 합니다.

- 구체적 파일·로그·링크·diff로 되돌아갈 수 있음
- “하지 않은 것”을 명확히 밝힘
- 메인 스레드에 다음 검증 방법을 알려 줌

산출이 “여기가 문제일 수도 있다” 한 문장이면 메인 스레드는 거의 빈손으로 받은 것과 같습니다.

## 흔한 실수

- 의존을 먼저 보지 않고 작업이 많다는 이유만으로 병렬화
- 소유권 합의 없이 여러 Agent가 같은 디렉터리를 동시에 수정
- 메인 스레드가 검수하지 않고 하위 결과를 바로 이어 붙임
- 병렬을 “생각 줄이기”로 써 혼란만 키움

병렬 Agent의 전제는 여전히, 작업이 서로 독립적이고 따로 검증할 수 있어야 한다는 점입니다.
