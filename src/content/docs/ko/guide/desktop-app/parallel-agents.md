병렬 작업의 기본 단위는 각각 독립적인 컨텍스트, 메시지, 결과, 목표를 가진 채팅입니다. 단순히 “단계가 많다”는 이유로 병렬로 나누는 것이 아닙니다. **작업이 서로 독립적이고 파일 경계가 분명하며 각각 따로 검증할 수 있을 때** 병렬 진행에 적합합니다.

![기본 채팅이 독립된 작업을 여러 하위 Agent에 맡기고 근거와 충돌을 종합하는 흐름도](/illustrations/flow-subagents.webp)

## 병렬로 진행할 수 있는지 먼저 판단하기

| 병렬 진행에 적합 | 순서대로 진행해야 함 |
|---|---|
| 읽기 전용 조사 두 건 | 뒤의 작업이 앞선 작업의 결론에 의존함 |
| 코드와 문서의 작업 디렉터리가 겹치지 않음 | 같은 핵심 파일을 동시에 수정함 |
| 두 가지 방안의 시제품을 각각 만듦 | 요구 사항이 아직 자주 바뀜 |
| 각 작업에 독립적인 테스트가 있음 | 통합한 뒤에야 옳고 그름을 알 수 있음 |

공식 문서는 두 채팅이 같은 데이터 소스에 동시에 쓰지 않도록 권고합니다. 코드를 병렬로 수정할 때는 서로 다른 Git worktree를 사용하세요.

## 간단한 작업부터 복잡한 작업까지

### 1. 읽기 전용 작업부터 병렬로 진행

```text
작업: 인증 모듈에서 가장 최근 발생한 실패만 분석하고 파일은 수정하지 않습니다.
범위: src/auth/**와 관련 테스트.
결과물: 근본 원인 가설, 근거 파일 경로, 여전히 불확실한 점,
권장 검증 명령.
```

읽기 전용 작업은 병합 충돌을 일으키지 않으므로 처음 연습할 때 적합합니다.

### 2. 그다음 쓰기 작업을 병렬로 진행

각 채팅의 목표, 담당 파일, 수정 금지 영역, 완료 기준을 명확히 적습니다.

```text
목표: 인증 오류 코드 문서를 보강합니다.
담당 범위: docs/auth/**만 수정합니다.
금지 범위: src/**, 잠금 파일, 공유 설정은 수정하지 않습니다.
완료 기준: pnpm check:links를 실행하고 결과를 보고합니다.
```

코드를 수정하는 채팅은 독립된 [작업 트리](/ko/guide/desktop-app/worktrees/)에서 진행하세요. 공유 설정은 기본 채팅이나 지정된 단일 담당자만 수정하도록 합니다.

### 3. 마지막에 결과를 통합

결과를 그대로 이어 붙이지 마세요. 기본 채팅에서 다음을 확인해야 합니다.

1. 각 작업이 정해진 경계 안에서 완료되었는가?
2. 근거와 테스트를 재현할 수 있는가?
3. 서로 다른 결론이 충돌하지 않는가?
4. 병합 후 통합 테스트를 다시 실행해야 하는가?

## 장기 작업과 Goal 모드

데스크톱 앱, CLI 또는 IDE에서 `/goal`을 입력하면 Goal 모드를 시작할 수 있습니다. 목표에는 원하는 결과, 제약 조건, 검증 기준을 포함해야 합니다. 채팅마다 목표는 독립적입니다. 병렬 실행한다고 샌드박스나 권한이 넓어지지는 않으며, 판단이 필요한 작업에서는 여전히 일시 중지됩니다.

더 세밀한 도구 수준의 작업 분배는 [하위 Agent](/ko/guide/agent-work/subagents/)를 참고하세요.
