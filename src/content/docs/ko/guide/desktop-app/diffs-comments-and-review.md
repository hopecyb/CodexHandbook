채팅 요약은 Codex가 수행한 작업에 대한 설명이고, Git diff는 파일에 실제로 생긴 변경 사항입니다. 데스크톱 앱의 검토 창에서는 diff를 보고, 줄별 댓글을 달고, 어떤 내용을 스테이징·되돌리기·커밋·푸시할지 결정할 수 있습니다.

전체 검토 창과 `/review`를 사용하려면 프로젝트가 Git 저장소에 있어야 합니다.

## 두 단계로 검토하기

먼저 변경 범위를 직접 확인한 다음, 독립적인 reviewer를 호출해 구현상의 문제를 찾습니다.

1. 검토 창을 열고 파일 수와 경로를 먼저 확인합니다.
2. **Last turn**을 선택해 이번 턴에서 실제로 무엇이 바뀌었는지 확인합니다.
3. **Unstaged**, **Staged**, **Commit**, **Branch** 중 하나로 전환해 검토 범위를 확인합니다.
4. 입력창에서 `/review`를 실행합니다.
5. 기준 브랜치와 비교, 커밋하지 않은 변경 사항 검토, 특정 커밋 검토, 맞춤 기준 중 하나를 선택합니다.
6. 우선순위에 따라 정렬된 발견 사항을 읽고 수정 여부를 결정합니다.

`/review`의 reviewer는 기본적으로 읽기 전용이며 작업 트리를 수정하지 않습니다. 이후 Codex에 발견 사항을 수정하도록 요청하더라도 기존 샌드박스 및 승인 규칙이 그대로 적용됩니다.

## 재사용할 수 있는 검토 기준

```text
현재 커밋하지 않은 변경 사항을 검토해 주세요. 특히 다음을 확인하세요.
- 작업 범위를 벗어난 변경이 있는지
- 동작 회귀, 경계 조건 또는 보안 문제가 있는지
- 테스트가 실패 경로를 다루는지
- 문서와 구현이 일치하는지

문제가 있다면 심각도순으로 먼저 나열하고, 각각의 파일·위치·근거·최소 수정안을 제시하세요.
문제가 없다면 명확히 말하고, 아직 테스트하지 않은 위험도 나열하세요.
```

## 줄별 댓글로 모호함 줄이기

의심스러운 줄에 마우스를 올리고 나타나는 **+**를 선택해 구체적인 피드백을 남깁니다. 댓글을 모두 작성한 뒤에는 다음처럼 명확한 지시를 한 번에 보냅니다.

```text
제가 남긴 줄별 댓글을 처리해 주세요. 변경 범위를 최소로 유지하고, 완료 후 관련 테스트를 다시 실행한 다음 새로운 diff를 보여 주세요.
```

유용한 댓글에는 위험이나 승인 조건이 드러나야 합니다. 예를 들어 “빈 배열일 때 여기서는 무엇을 반환하나요?”는 도움이 되지만, “여기가 틀렸어요”만으로는 보통 부족합니다.

## 스테이징과 되돌리기

검토 창에서 전체 diff, 개별 파일 또는 개별 hunk 단위로 스테이징하거나 스테이징을 취소하고 변경을 되돌릴 수 있습니다. 되돌리기는 변경 사항을 버리므로, 작업 시작 전부터 있던 사용자 변경 사항이 아닌지 먼저 확인해야 합니다.

승인 순서는 **범위 → 동작 → 테스트 → 보안 → 유지보수성**으로 고정하는 편이 좋습니다. 자세한 방법은 [diff 검토](/ko/guide/quality/review-diffs/)를 참고하세요.
