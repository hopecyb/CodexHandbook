## 검토 흐름

1. diff 뷰를 열고 파일별로 살펴봅니다
2. 변경이 합의한 범위 안에 있는지 확인합니다
3. 의심되는 곳에 질문하거나 댓글을 답니다(UI가 지원하면)
4. 수락, 거부, 또는 수정을 요청합니다

방법: [diff 검토](/guide/quality/review-diffs/)

## 내용

데스크톱 App에서 변경은 주로 diff 뷰에서 봅니다. 대화 영역이 아닙니다.

채팅 영역은 “그것이 한 말”이고, diff 뷰는 “실제로 일어난 일”입니다.

## 흔한 오해

### 1. 댓글은 팀 협업에서만 쓰나요?

혼자 써도 댓글이나 추문은 유용합니다. 최소한 “여기를 왜 고쳤는지”를 명확히 할 수 있습니다.

### 2. 잘못 고쳤는지 확신이 없으면?

처음부터 결론을 내릴 필요는 없습니다. 의심 지점을 먼저 지적하고 설명을 요청하는 편이, 혼자 추측하는 것보다 안전합니다.

### 3. 수락 전에 최소한 무엇을 봐야 하나요?

최소한 다음 세 가지를 보세요.

- 어떤 파일이 바뀌었는지
- 허용 범위를 넘지 않았는지
- 명백히 없어선 안 될 삭제나 잔여물이 있는지

### 4. 전문 reviewer가 아니면 문제를 못 보나요?

가장 직접적인 질문부터 보면 됩니다.

- 건드리면 안 되는 곳을 고쳤는가
- 아직 중요해 보이는 것을 삭제했는가
- A를 했다고 말하는데, diff에 정말 A만 있는가

## 검토 순서

diff를 볼 때마다 헷갈린다면, 먼저 이 순서를 고정하세요.

1. 몇 개 파일이 바뀌었는지 봅니다
2. 각 파일 변경이 작업과 관련 있는지 봅니다
3. 범위 밖 수정이 있는지 봅니다
4. 마지막에 세부 표현·형식·국소 구현을 봅니다

처음부터 작은 변경에 끌려가지 않기 쉽습니다.

## 댓글에 더 가치 있는 내용

댓글은 완벽할 필요가 없습니다. 더 가치 있는 유형은 다음과 같습니다.

- “여기를 왜 고쳐야 하나요?”
- “이번 범위를 넘은 것 아닌가요?”
- “원래 동작에 영향을 줄 수 있어 보입니다. 설명해 줄 수 있나요?”
- “이 구간에 검증 방법을 보완할 수 있나요?”

“문제가 있다”보다 다음 수정을 밀어주기 쉽습니다.

이 페이지에서 반복해서 볼 가치가 있는 것은 여전히 diff 뷰입니다.
