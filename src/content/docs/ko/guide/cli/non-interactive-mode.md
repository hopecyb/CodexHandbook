비대화형 모드에서는 Codex가 **TTY 대화 없이** 작업을 완료할 수 있습니다. 개발자가 Agent를 스크립트와 CI에 연결할 때 사용하는 진입점입니다.

간단히 말해, 비대화형 모드는 메시지를 주고받으며 대화하는 방식이 아니라 작업 전체를 한 번에 전달해 실행하는 방식입니다.

명령 한 번을 호출하는 것에 더 가깝습니다.

## 이 페이지에서 다루는 내용

- `codex` 대화형 세션 대신 비대화형 모드를 사용할 때
- 사람 없이 실행할 때 필요한 추가 보안 및 승인 설계
- [설정](/ko/guide/cli/configuration/)과의 관계

## 적합한 사용 사례

| 적합 | 부적합 |
|---|---|
| CI에서 고정된 검토 프롬프트 실행 | 요구 사항을 여러 차례 질문하며 구체화해야 하는 일 |
| 야간 문서 링크 검사 | 탐색적인 리팩터링 |
| 미리 정의된 템플릿에 따른 코드 생성 | 모호성이 큰 제품 결정 |

## 핵심 개념

비대화형 실행은 보통 다음과 같이 진행됩니다.

1. 인수 또는 stdin으로 **완전한 작업 설명**을 받습니다.
2. 지정된 작업 디렉터리에서 실행합니다.
3. 종료 코드로 성공 또는 실패를 나타냅니다.
4. 후속 단계에서 사용할 로그나 구조화된 결과를 출력합니다.

현재 비대화형 진입점은 `codex exec`입니다. CLI를 업그레이드한 뒤에도 스크립트가 사용하는 인수를 `codex exec --help`로 다시 확인하세요.

## 최소 실행 예시(설명용)

```bash
# 저장소 루트에서 읽기 전용 검토 한 번 실행
codex exec --cd . "main 대비 diff의 보안 위험을 나열하세요. 파일은 수정하지 마세요."
```

`codex exec`는 기본적으로 읽기 전용 샌드박스를 사용합니다. 실행 중 진행 상황은 `stderr`에, Agent의 최종 응답은 `stdout`에 기록되므로 최종 결과를 후속 단계로 리디렉션할 수 있습니다.

```bash
codex exec --cd . "최근 커밋 10개의 릴리스 노트를 작성하세요." > release-notes.md
```

실무 권고:

- 셸 스크립트에서 먼저 깨끗한 작업 복사본으로 `cd`합니다.
- 작업 문자열은 heredoc이나 버전 관리되는 `prompts/` 파일에 작성합니다.
- 종료 코드를 수집하고, 실패하면 CI에서 실패로 표시합니다.

## 보안 설계

무인 실행에서는 **옆에서 직접 거부 버튼을 누를 사람이 없습니다**.

| 원칙 | 방법 |
|---|---|
| 최소 권한 | 읽기 전용 token과 제한된 샌드박스 사용 |
| push 금지 | CI에서는 PR만 열거나 artifact만 업로드 |
| 고정된 프롬프트 | PR 설명의 검증되지 않은 텍스트를 그대로 이어 붙이지 않음(프롬프트 주입 위험) |
| 감사 가능성 | 로그와 diff artifact를 보관 |

[사람의 승인 패턴](/ko/cases/workflows/human-approval-patterns/)과 로드맵의 `08-developer-platform/non-interactive/`를 참고하세요.

## 대화형 모드와 비교

| | 대화형 모드 | 비대화형 모드 |
|---|---|---|
| 진입점 | `codex` TUI | `exec` / 파이프 |
| 사람의 개입 | 많음 | 적음. 사전 설계가 필요 |
| 학습에 적합 | 예 | 아니요 |
| CI에 적합 | 아니요 | 예 |

대화형 사용법은 [CLI 대화형 모드](/ko/guide/cli/interactive-mode/)를 참고하세요.

## 대화형 작업을 비대화형 작업으로 바꾸기

긴 채팅 기록을 그대로 스크립트에 넣지 마세요. 간단한 작업 명세로 압축하는 편이 안정적입니다.

| 요소 | 작성 방법 |
|---|---|
| 목표 | 이번 실행에서 할 일만 적기 |
| 입력 | 읽을 파일, diff, 로그 또는 stdin 지정 |
| 금지 사항 | 파일 수정, 네트워크 사용, push, CI 중단 등 금지할 것 명시 |
| 출력 | 텍스트 요약, JSON, 보고서 파일 또는 종료 코드 |
| 검증 | 반드시 통과해야 할 명령과 나타나면 안 되는 키워드 |

비대화형 프롬프트는 작업 티켓처럼 경계가 분명하고 입력이 완전하며 실패 조건이 명확해야 합니다. 제품 판단, 설계상의 선택, 권한 확인이 더 필요한 작업은 우선 대화형 모드에서 진행하세요.

## 흔한 오해

### 1. 비대화형 모드가 더 효율적이니 먼저 배워야 하나요?

권장하지 않습니다.

처음 사용하는 사람에게는 비대화형 모드가 보통 너무 빠르고 경직되어 있으며, 중간에 질문을 주고받으며 요구를 명확히 할 여지가 적습니다.

### 2. 대화형 모드와 가장 큰 차이는 무엇인가요?

핵심 차이는 다음과 같습니다.

- **대화형 모드**: 도중에 질문하고, 수정하고, 승인할 수 있습니다.
- **비대화형 모드**: 한 번에 실행하는 방식에 가까우므로 미리 정의된 절차에 적합합니다.

### 3. 언제는 아직 사용하지 않는 편이 좋은가요?

다음 중 하나에 해당한다면 우선 사용을 미루는 편이 좋습니다.

- 프롬프트 작성법이 아직 익숙하지 않습니다.
- 결과를 어떻게 검증해야 할지 모릅니다.
- 승인, 샌드박스, 권한에 대한 기본 판단 기준이 없습니다.

비대화형 모드는 자동화에 적합하지만 처음 탐색할 때는 적합하지 않습니다. 먼저 대화형 모드에 익숙해진 다음 스크립트에 연결하세요.

## 흔한 실수

- 대화형 세션의 긴 채팅 기록을 그대로 한 번의 `exec`에 넣기
- CI에서 운영 환경 자격 증명과 쓰기 권한 사용하기
- CLI 버전을 고정하지 않아 파이프라인 동작이 갑자기 바뀌게 하기
