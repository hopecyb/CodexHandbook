“환경 변수”는 두 극단으로 가기 쉽습니다. 너무 저수준이라고 느끼거나, 모든 설정을 넣을 수 있다고 생각하는 것입니다. 직접 말하면, 환경 변수는 런타임에 값을 프로그램에 넘기는 방법이며, 민감 정보와 스위치에 특히 맞습니다.

환경 변수는 **키 주입, 스위치 덮어쓰기, CI 적응**에 자주 쓰이며, 민감 값을 설정 파일이나 Git에 쓰지 않게 합니다. 이 페이지는 개념 색인입니다. 구체 변수 이름은 [공식 문서](https://developers.openai.com/codex)와 `codex --help`를 기준으로 합니다.

## 이 페이지 내용

- 어떤 것을 config 파일 대신 환경 변수로 둘지
- 사용자급, 프로젝트급, Cloud Secrets, CI의 역할 분담
- 흔한 이름 짓기와 유출 위험

## 판단 방식

값이 다음 중 하나라도 만족하면 환경 변수를 우선 고려하세요.

- Git에 쓰고 싶지 않음
- 머신, 사용자, 환경에 따라 바뀜
- 이번 실행에만 적용하고 싶음

그래서 token, 임시 스위치, CI 주입 값이 자주 환경 변수를 타고, 하드코딩하지 않습니다.

설정 키 개념은 [설정 항목 참고](/ko/guide/reference/configuration-reference/)；Cloud는 [Secrets와 변수](/ko/guide/web-and-cloud/secrets-and-variables/)를 보세요.

## 환경 변수에 넣기 좋은 내용

| 유형 | 예시 의도 | 하지 말 것 |
|---|---|---|
| 인증 token | API key, GitHub PAT | 저장소에 커밋 |
| 임시 스위치 | 디버그 로그 수준 | 장기 업무 설정 |
| CI 주입 | 읽기 전용 리뷰 모드 | 프로덕션 쓰기 권한 token |
| MCP 하위 프로세스 | 서드파티 서비스 key | `AGENTS.md`에 평문 |

## 환경 변수를 만능 서랍으로 쓰지 마세요

많은 팀이 쓰다 보면 “넣을 수 있으니 환경 변수에 넣자”로 빗나갑니다.

더 안전한 방법은 구분하는 것입니다.

- **민감 값, 런타임 차이**：환경 변수
- **팀의 장기 약속**：설정 파일 또는 문서
- **워크플로 규칙**：`AGENTS.md` 또는 Skill

이후 장애를 분석할 때도 어디를 볼지 알기 쉽습니다.

## `.env`는 무엇인가

환경 변수를 처음 만날 때 가장 먼저 보는 것이 종종 `.env` 파일입니다. 오해도 여기서 잘 납니다.

`.env`는 또 다른 설정 센터가 아닙니다. 많은 도구가 로컬 개발을 위해 제공하는 **환경 변수를 일괄 로드**하는 방법일 뿐입니다.

이렇게 이해하세요.

- 환경 변수는 “값 자체”
- `.env`는 “로컬에서 그 값을 담는 흔한 컨테이너”

그래서:

- `.env`가 편하다고 안전한 것은 아님
- `.env.example`은 예시 이름을 두고, 실제 키는 두지 않음
- 배포나 CI에서는 보통 Secret 관리자를 탐

## 환경 변수만으로 부족한 내용

- 코딩 규범, 디렉터리 구조 → `AGENTS.md`
- 팀이 합의한 모델 기본값 → 프로젝트 설정(키가 아닌 부분)
- 복잡한 allowlist → [규칙](/ko/guide/customization/rules/allow-and-deny-patterns/)

## 흔한 오해

### 1. 환경 변수에 모든 설정을 넣기에는 맞지 않다

“값”을 두기에는 맞지만, 팀 규칙 전체와 장기 설명을 담기에는 맞지 않습니다.

### 2. `.env`에 쓰면 안전한가?

`.env`가 커밋되고, 화면 공유에 보이고, 로그에 찍히면 똑같이 유출됩니다.

### 3. `unset`하면 위험이 완전히 사라지나?

위험은 다음에 남을 수 있습니다.

- shell 이력
- 하위 프로세스 상속
- 로그
- 이전에 저장된 파일이나 스크린샷

### 4. 로컬에서 `.env`를 쓰니 온라인도 `.env`를 넘기면 되나?

많은 경우 그렇지 않습니다. CI, Cloud, 호스팅 플랫폼에서는 더 흔한 방법이 다음과 같습니다.

- 플랫폼 백엔드에 Secret 구성
- 런타임에 환경 변수 주입
- 실제 값을 저장소 파일에 두지 않음

## 계층과 우선순위(개념)

```text
조직 강제 정책(있으면)
    ↓ 덮어씀
Shell / CI가 주입한 환경 변수
    ↓ 설정 파일과 병합(구체 규칙은 공식 기준)
사용자급 / 프로젝트급 config 파일
```

같은 키가 여러 곳에 있으면 **공식 문서의 우선순위**를 따릅니다. 장애 분석 때는 「유효 설정」을 출력하거나 로그를 보세요.

## 자주 쓰는 판단 순서

처음 구성할 때 이 순서로 판단하세요.

1. 이 값이 민감한가
2. 개인 로컬용인가, CI / Cloud용인가
3. 장기 보관이 필요한가, 이번 실행에만 있는가
4. 로컬 환경 변수, CI Secret, Cloud Secret 중 어디에 둘까

“값은 맞는데 위치가 틀린” 문제를 줄입니다.

## 흔한 시나리오

| 시나리오 | 더 안전한 방법 |
|---|---|
| 본기에서 서드파티 API 디버깅 | 로컬 환경 변수 또는 `.env`, 커밋 무시 |
| 팀이 공유하는 예시 설정 | `.env.example` 커밋, 실제 값은 커밋하지 않음 |
| GitHub Actions / CI | 플랫폼 Secret |
| Cloud 작업이 사설 서비스를 호출 | Cloud Secret |
| MCP 서버가 key를 읽어야 함 | 부모 프로세스 환경 변수 또는 Secret 주입 |

잠깐 헷갈리면 이 원칙으로：실제 키는 가능하면 일반 파일 내용으로 저장소에 오래 두지 마세요.

## 자주 쓰는 장면

### 로컬 개발

`~/.zshrc` 또는 direnv `.envrc`에서 개인 token을 export——`.env`를 **커밋하지 마세요**.

### CLI 비대화형

CI가 secret store로 변수를 주입한 뒤 `codex exec`를 실행. [비대화형 모드](/ko/guide/cli/non-interactive-mode/)를 보세요.

### MCP 서버

MCP 프로세스는 종종 부모 프로세스 환경을 상속합니다. 설정에서 값을 하드코딩하지 말고 `$VAR`를 참조하세요. [MCP 연결](/ko/skills/mcp/connect-an-mcp-server/)을 보세요.

### Cloud

저장소급 Secrets를 Cloud 콘솔에서 구성하고, 이름이 작업 안 참조과 일치하게 하세요.

환경 변수는 바뀌고, 민감하며, 런타임에만 필요한 값을 두는 데 맞습니다. 장기 규칙이나 설명을 담는 용도가 아닙니다.

## 보안 체크리스트

- [ ] `.env`가 `.gitignore`에 있음
- [ ] 로그 출력 전 token 마스킹
- [ ] 유출된 key 로테이션
- [ ] 최소 권한 scope(읽기 전용 CI token 등)

## 흔한 실수

- `.env.example`에 실제 key를 채워 커밋
- 화면 공유 중 `export`로 token이 보임
- `unset` 후 하위 프로세스가 안전하다고 가정——프로세스 트리를 확인해야 함
