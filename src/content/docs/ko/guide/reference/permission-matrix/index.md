“권한 매트릭스”는 일반 사용자에게도 유용합니다. 같은 한 마디인데, 입구에 따라 Codex의 반응이 왜 다른지를 주로 설명합니다.

다른 **조작**이 다른 **제품 입구**에서는 다른 승인·샌드박스 동작을 트리거합니다. 이 매트릭스는 팀이 “무엇을 반드시 사람이 동의해야 하는지”를 맞추는 데 도움이 되며, **위험과 행동 대조표**이지 법률 컴플라이언스 조항이 아닙니다. 기본값은 [공식 문서](https://developers.openai.com/codex)와 조직 호스팅 정책을 따릅니다.

## 이 표가 보는 것

승인, 제한, 거부를 처음 만나면 본능적으로 이렇게 생각하기 쉽습니다.

- 모델이 고장 났다
- 내가 잘못 말했다
- 왜 어제는 되고 오늘은 안 되나

많은 차이는 사실 현재 입구, 정책, 위험 등급이 다르기 때문입니다.

## 핵심

모든 “이 일을 해 줘”가 같은 위험이 아닙니다.

예:

- 파일 하나 읽기
- 파일 하나 고치기
- 명령 하나 실행
- 외망 연결
- 코드 push

모두 “작업 실행”처럼 보이지만 위험 수준은 같지 않습니다. 그래서 제품이 다른 곳에 다른 승인, 제한, 차단을 둡니다.

개념 기초：[권한과 승인](/guide/foundations/permissions-and-approvals/)

## 조작 위험 등급

| 등급 | 조작 예시 | 기본 기대 |
|---|---|---|
| L0 읽기 | 프로젝트 안 텍스트 읽기, 코드 검색 | 보통 자동 |
| L1 쓰기 | 프로젝트 파일 수정, 포맷팅 | 확인 또는 샌드박스 안 자동이 흔함 |
| L2 실행 | shell, 패키지 매니저, 테스트 | 확인이 많은 편 |
| L3 출망 | curl, npm registry, API | 엄격 확인 또는 금지 |
| L4 경계 초과 | 프로젝트 밖 경로 쓰기, git push, DB 삭제 | 차단 또는 강한 확인 |
| L5 GUI | Computer Use, 시스템 대화상자 | 최고 민감, 기본 꺼짐이 흔함 |

## 읽는 법

처음에는 칸마다 외울 필요 없습니다. 이렇게 쓰세요.

- 이번 작업이 어느 종류의 조작인지 먼저 판단
- 그 조작이 현재 입구에서 보통 막히는지 봄
- 설명을 보탤지, 승인을 기다릴지, 더 맞는 입구로 바꿀지 결정

이 표로 미리 판단할 수도 있습니다.

## 매트릭스(개념 — 전형적 기본)

**Y** = 흔한 경우 명시적 동의 또는 정책 제한 · **A** = 신뢰 설정에서 자동 가능 · **—** = 버전/정책에 따름 · **N** = 보통 불허

| 조작 | 데스크톱 App | CLI 대화형 | IDE | Cloud |
|---|---|---|---|---|
| 저장소 파일 읽기 | A | A | A | A |
| 저장소 안 파일 쓰기 | Y/A | Y | Y/A | Y/A |
| 테스트 명령 실행 | Y/A | Y | Y/A | Y/A |
| 전역 의존성 설치 | Y | Y | Y | Y |
| 공망 접근 | Y | Y | Y | Y |
| `.env` 등 민감 파일 읽기 | Y | Y | Y | Y |
| `git commit` | Y | Y | Y | Y |
| `git push` | Y | Y | Y | Y |
| 프로젝트 밖 경로 쓰기 | N/Y | N/Y | N/Y | N |
| MCP 서드파티 도구 | Y | Y | Y | Y |
| 브라우저로 URL 열기 | Y | — | — | Y |
| Computer Use | Y/— | — | — | — |

설명:

- **Cloud**는 원격 샌드박스에서 돌며, 노트북 파일 시스템에 접근할 수 없음
- **IDE**는 App과 비슷하지만 UI 승인 형태가 다름
- **호스팅 정책**이 전부 Y 또는 N으로 강제할 수 있음

## 흔한 오해

### 1. 할 수 있는지는 모델이 원하는지만으로 정해지지 않는다

결과에 영향을 주는 것은 종종 다음입니다.

- 현재 입구가 허용하는지
- 현재 정책이 통과시키는지
- 현재 권한이 충분한지

### 2. Cloud가 반드시 더 자유롭거나 더 안전한 것은 아니다

안전한지는 샌드박스, 네트워크, Secrets, 브랜치 보호, 승인 정책이 함께 갖춰졌는지에 달립니다.

### 3. 규칙을 썼다고 위험이 자동으로 사라지지 않는다

문서 규칙, 승인 정책, 기술 제한, 사람 재검토를 자주 함께 씁니다.

### 4. 막혔다고 내가 잘못한 것은 아니다

많은 경우 의미는 다음입니다.

- 이 단계의 위험이 더 높음
- 현재 입구가 이 일에 맞지 않음
- 더 명확한 승인이 필요하거나, 더 가벼운 방법으로 바꿔야 함

## 설정과 문서로 어떻게 내리나

| 메커니즘 | 역할 |
|---|---|
| 샌드박스 모드 | Agent가 「하고 싶어도」 L3/L4를 제한 |
| 승인 정책 | L1–L3에서 팝업 여부 제어 |
| `AGENTS.md` | 프로젝트급 금지 항목 선언(예: push 금지) |
| 브랜치 보호 | GitHub 측에서 미 review 머지 차단 |
| Hooks | 커밋 전 자동 검사(로드맵 Hooks 페이지) |

[사람 승인 패턴](/cases/workflows/human-approval-patterns/) · [설정 참고](/guide/reference/configuration-reference/)

## 경계를 높여야 할 때

어떤 동작이 다음 중 하나라도 만족하면 경계를 높이세요.

- 파일을 바꿈
- 명령을 실행함
- 외망에 접근함
- 민감 정보에 닿음
- 결과를 저장소 밖으로 보냄

L 몇인지를 외울 필요는 없지만, 한눈 보고 끝낼 위험 수준은 아니라는 점은 알아야 합니다.

권한 매트릭스는 주로 예단 도구입니다. 이 단계가 왜 막히는지, 더 조심해야 하는지, 더 가벼운 방법으로 바꿔야 하는지를 미리 판단합니다.

## 팀 권장 전략(예시)

| 시나리오 | 제안 |
|---|---|
| 오픈소스 연습 저장소 | 표준 샌드박스 + 테스트 명령 허용 |
| 회사 monorepo | 엄격 + push 금지 + PR은 반드시 사람 검토 |
| CI `codex exec` | 읽기 전용 또는 디렉터리 한정 + push 없음 |
| Cloud 프로덕션 관련 | Secrets 최소화 + 브랜치 보호 |

## 흔한 오해(표)

| 오해 | 사실 |
|---|---|
| 「Cloud가 더 안전하다」 | secrets, review, 네트워크 정책에 달림 |
| 「IDE는 shell을 돌리지 않는다」 | Agent 도구로 실행할 수 있음 |
| 「push 금지를 쓰면 절대 push하지 않는다」 | 샌드박스 + Git 권한 + 사람 검토 다층이 필요 |
