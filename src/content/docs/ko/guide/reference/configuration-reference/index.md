“설정 항목 참고” 페이지는 키, 계층, 덮어쓰기 관계가 많아 처음부터 혼란스럽기 쉽습니다. 먼저 한 질문을 분명히 하면 훨씬 이해하기 쉽습니다.

> **어떤 동작은 설정을 바꿔야 하고, 어떤 것은 설정으로 풀면 안 되는가?**

설정 파일은 **모델, 샌드박스, 승인, MCP** 같은 동작을 통일하는 데 자주 씁니다. 이 페이지는 **개념 색인**입니다. 구체 파일 경로, TOML/YAML 키 이름은 [OpenAI Codex 문서](https://developers.openai.com/codex)와 설치한 버전을 반드시 따르세요.

## 하나의 판단 원칙

설정에는 보통 “**장기적으로 동작에 영향을 주고 싶은**” 것을 둡니다. 다음을 넣기에는 맞지 않습니다.

- 민감 값
- 팀 규칙 전문
- 임시 일회성 작업 설명

세 종류로 나누면 더 분명합니다.

- **장기 동작 선호**：보통 설정에
- **구체 작업 요구**：보통 프롬프트 / `AGENTS.md` / Skill에
- **민감 값**：보통 환경 변수나 Secret에

잠깐 헷갈리면 이것만 생각하세요. Codex의 장기 습관을 바꾸는가, 이번 작업을 설명하는가?

- 장기 습관은 보통 설정으로
- 현재 작업 설명은 보통 프롬프트, `AGENTS.md`, 작업 설명으로

## 설정 계층

| 계층 | 위치(개념) | 전형 내용 |
|---|---|---|
| 사용자급 | `~/.codex/` 등 | 기본 모델, 개인 승인 습관 |
| 프로젝트급 | 저장소 안 설정 파일 | 팀 샌드박스, MCP 목록 |
| 환경 변수 | Shell / CI 주입 | 키, 임시 스위치 |
| 호스팅 | 조직 배포 | 덮어쓸 수 없는 강제 정책 |

## 각 계층이 관리하는 것

- **사용자급**：당신 개인의 기본 습관
- **프로젝트급**：이 저장소가 공유하길 바라는 기본 동작
- **환경 변수**：런타임에 임시로 넣는 값
- **호스팅 정책**：조직이 정해 두어 로컬에서 바꿀 수 없는 부분

처음에는 “누가 반드시 누구를 덮는지”를 외울 필요 없이, 각 층이 대략 무엇을 관리하는지만 알면 됩니다.

- 사용자급：“내가 평소 이렇게 쓰고 싶다”
- 프로젝트급：“이 저장소는 모두가 되도록 이렇게 쓰길 바란다”
- 환경 변수：“이번 실행에 임시로 넣는 값”
- 호스팅 정책：“조직이 이미 정해 둔 경계”

입문：[설정 기초](/guide/customization/configuration/config-basics/) · 터미널 중심：[CLI 설정](/guide/cli/configuration/)

## 설정 영역 색인(개념)

### 모델과 추론

| 의도 | 설명 |
|---|---|
| 기본 모델 | 새 세션이 쓰는 모델 ID |
| 추론 강도 / reasoning | 복잡한 작업 등급(지원 시) |
| 온도 등 샘플링 | 보통 기본 유지, 스크립트화 시 고정 |

배경：[모델과 추론](/guide/foundations/models-and-reasoning/)

### 샌드박스와 네트워크

| 의도 | 설명 |
|---|---|
| 파일 시스템 범위 | 쓸 수 있는 경로, 프로젝트 밖 쓰기 허용 여부 |
| 네트워크 접근 | 금지 / 제한 / 허용 |
| 출구 도메인 | 허용 목록(지원 시) |

배경：[샌드박스와 네트워크](/guide/foundations/sandbox-and-network/)

### 승인 정책

| 의도 | 설명 |
|---|---|
| shell 실행 전 | 항상 묻기 / 신뢰 목록 / 자동(고위험) |
| 파일 쓰기 전 | 위와 같음 |
| MCP 도구 호출 | 서버 또는 도구 단위 |

배경：[권한과 승인](/guide/foundations/permissions-and-approvals/) · 매트릭스：[권한 매트릭스](/guide/reference/permission-matrix/)

### 워크스페이스와 CLI

| 의도 | 설명 |
|---|---|
| 기본 `cwd` | 시작 디렉터리 |
| 비대화형 기본 | exec용 승인과 샌드박스 |
| 로그 수준 | 장애 분석 시 올림 |

### MCP 서버

| 의도 | 설명 |
|---|---|
| 서버 목록 | 명령, URL, 전송 방식 |
| 환경 변수 주입 | MCP 프로세스에 묶고, Git에는 넣지 않음 |

[MCP 연결](/skills/mcp/connect-an-mcp-server/)

### IDE / App 확장

일부 항목은 확장 설정 UI에만 있으며, CLI와 같은 사용자 설정 백엔드를 공유할 수 있습니다——제품 설명을 따릅니다.

[IDE 설정](/guide/ide/settings/) · [데스크톱 App 설정](/guide/desktop-app/settings/)

## 흔한 오해

### 1. 설정할 수 있는 모든 것을 설정 파일에 넣어야 하는 것은 아니다

다음에 두는 편이 더 맞는 내용도 있습니다.

- `AGENTS.md`
- 환경 변수
- Skill
- 현재 작업 설명

설정은 만능 컨테이너가 아닙니다.

### 2. 처음부터 모든 설정 키를 이해할 필요 없다

대부분 사람은 처음에 이것만 이해하면 됩니다.

- 모델
- 샌드박스
- 승인
- MCP

이 네 종류가 실제 질문의 대부분을 덮습니다.

### 3. 프로젝트급 설정을 하면 팀 문서를 완전히 대체할 수 있나?

설정은 “시스템 동작 기본값”을 표현하기에 맞습니다. “왜 이렇게 하는지, 언제 하면 안 되는지” 같은 설명을 대체하기에는 맞지 않습니다.

### 4. 공식 설정 키가 많아도 한 번에 다 배울 필요 없다

대부분 사람이 처음에 만나는 것은 기본적으로 이 네 종류입니다.

- 기본 모델
- 샌드박스 범위
- 승인 정책
- MCP 연결

이 네 종류를 이해하면, 입문 단계 문제의 대부분을 덮을 수 있습니다.

## 환경 변수와의 관계

| 유형 | 어디에 |
|---|---|
| API key, token | 환경 변수 또는 Secret 관리자 |
| 비민감 스위치 | 환경 변수 또는 설정 |
| 코딩 규범 | `AGENTS.md`, config가 아님 |

## 설정에 넣을지 판단하기

“이걸 설정에 써야 하나”가 헷갈리면, 먼저 이 네 문장으로 판단하세요.

1. 장기 기본으로 적용되길 원하는가?
2. 민감 정보인가?
3. 개인 습관인가, 프로젝트 공유 규칙인가?
4. 시스템 동작을 조율하는가, 이번 작업만 설명하는가?

이 네 문장으로 보면, 위치를 잘못 두기 어렵습니다.

## 동작을 바꿀 때 판단법

“Codex 동작을 조정하고 싶다”면 아래로 판단하세요.

1. 장기 기본 동작인가, 이번 작업의 임시 요구인가?
2. 민감 값인가, 일반 설정인가?
3. 개인 선호인가, 프로젝트 공유 규칙인가?

이렇게 보면 보통 다음에 둘지 정해집니다.

- 설정 파일
- 환경 변수
- `AGENTS.md`
- Skill
- 현재 프롬프트

## 흔한 시나리오

초보자가 가장 헷갈리기 쉬운 경우입니다.

| 하고 싶은 일 | 보통 어디에 |
|---|---|
| 어떤 모델을 장기 고정 | 사용자급 또는 프로젝트급 설정 |
| 팀이 코드 수정 전 테스트 실행을 요구 | `AGENTS.md` |
| 이번 작업은 `docs/`만 수정 허용 | 현재 프롬프트 |
| API key / token | 환경 변수 또는 Secret |
| 어떤 MCP 서비스에 연결 | 프로젝트 설정 + 환경 변수 |

설정 키 이름 목록만 보는 것보다 이렇게 보는 편이 정리하기 쉽습니다.

Cloud Secrets：[Secrets와 환경 변수](/guide/web-and-cloud/secrets-and-variables/)

## 변경 규율

1. 한 번에 한 종류 설정만 바꾸고, 일주일 관찰
2. 프로젝트급 변경은 PR review를 탐
3. CLI 업그레이드 후 공식 migration 설명을 diff
4. 키를 설정 파일에 써 Git에 커밋하지 않음

설정은 주로 장기 기본 동작을 두고, 민감 값은 두지 않으며, 작업 설명과 팀 규칙을 대체하지 않습니다.

## 흔한 실수

- 문서의 키 이름이 옛 CLI와 맞지 않음
- 개인 본기에서 샌드박스를 완화한 채 고객 저장소에 씀
- `AGENTS.md` 지시와 모순(설정은 허용인데 문서는 금지)
