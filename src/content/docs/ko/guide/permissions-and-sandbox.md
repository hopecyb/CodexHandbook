Codex를 안전하게 사용하려면 두 제어 계층을 함께 봐야 합니다. **샌드박스는 기술적으로 접근할 수 있는 범위를 정하고, 승인 정책은 현재 경계를 넘기 전에 사용자에게 질문할지를 정합니다.**

![Codex 샌드박스와 승인 흐름: 동작은 샌드박스 경계를 거치고 경계를 넘으면 사람에게 승인을 요청하며 마지막에 검증 증거를 남김](/diagrams/sandbox-approval-flow-ko.svg)

## 먼저 기억할 차이

| 제어 | 답하는 질문 | 대표 대상 |
|---|---|---|
| 샌드박스 | 이 동작이 최대 어디까지 접근할 수 있는가? | 프로젝트 파일, 프로젝트 밖 경로, 시스템 기능, 네트워크 |
| 승인 정책 | 현재 경계를 넘기 전에 사람에게 물어야 하는가? | 의존성 설치, 네트워크 접근, 외부 디렉터리 쓰기, 앱 실행 |
| 작업 제약 | 이번 작업에서 무엇을 하고 하지 말아야 하는가? | 수정 허용 디렉터리, 금지 동작, 검증 명령 |
| 사람의 검토 | 실행된 결과를 받아들일 수 있는가? | diff, 로그, 테스트, 외부 부작용 |

작업 제약은 샌드박스를 대신할 수 없고, 샌드박스도 최종 검토를 대신할 수 없습니다. 각각 의도, 실행 경계, 결과 인수를 담당합니다.

## 하나의 동작이 안전 경계를 통과하는 과정

Codex가 명령 실행이나 도구 호출을 준비할 때 다음 순서로 이해할 수 있습니다.

1. 동작이 현재 샌드박스의 허용 범위 안인지 판단합니다.
2. 범위 안이면 실행하고 출력을 기록합니다. 팝업이 반드시 나타나는 것은 아닙니다.
3. 범위를 넘으면 승인 정책에 따라 허가를 요청하거나 바로 거부됩니다.
4. 사용자는 거부하거나 더 좁은 동작을 요구하거나 명시된 이번 동작만 승인할 수 있습니다.
5. 실행 뒤에도 diff, 테스트, 외부 시스템 상태를 확인해 결과가 작업 목표를 만족하는지 검증합니다.

샌드박스는 Codex가 시작한 하위 프로세스와 명령에도 적용됩니다. 스크립트 안에서 실행된다는 이유로 경계를 우회한다고 가정하지 마세요.

## 로컬 실행과 Cloud의 경계는 다릅니다

| 환경 | 주요 격리 방식 | 네트워크 핵심 | 확인할 내용 |
|---|---|---|---|
| App / CLI / IDE의 로컬 작업 | 운영 체제 수준 샌드박스와 현재 승인 정책 | 로컬 작업은 보통 외부망 의존을 기본 전제로 하지 않음. 필요하면 명시적으로 승인하거나 설정 | 작업 공간 범위, 명령, 프로젝트 밖 경로, 네트워크 목적 |
| Cloud 작업 | OpenAI 관리 격리 컨테이너 | 설정 단계는 환경 설정에 따라 네트워크 사용 가능. Agent 단계는 명시적으로 켜지 않으면 기본 차단 | 저장소, 환경 설정, 허용 도메인, 반환된 diff와 검증 증거 |

Cloud 환경의 Secrets는 설정 단계에서만 사용하며 Agent 단계가 시작되기 전에 제거됩니다. 최소 권한을 지키고 무관한 프로덕션 자격 증명을 작업 환경에 넣지 마세요.

## 승인 요청을 볼 때 네 단계로 판단하기

### 1. 작업과 대조하기

이 단계가 현재 목표에 실제로 필요한지 확인합니다. “도움이 될 수 있다”는 이유만으로는 승인하지 않습니다.

### 2. 범위와 대조하기

현재 프로젝트, 프로젝트 밖 디렉터리, 네트워크, 시스템 앱 중 무엇에 접근하는지 확인합니다. 경로, 도메인, 명령이 구체적일수록 판단하기 쉽습니다.

### 3. 부작용과 대조하기

읽기만 하는지, 파일 쓰기, 소프트웨어 설치, 데이터 전송, 원격 상태 변경이 있는지 확인합니다. 외부 부작용은 되돌릴 수 있는 로컬 변경보다 더 신중하게 다룹니다.

### 4. 검증과 복구 확인하기

성공 여부를 어떻게 확인하고 실패하면 어떻게 되돌릴지 묻습니다. 답이 없으면 먼저 Codex에 설명이나 더 작은 대안을 요구합니다.

## 구체적 예: 의존성 설치

Codex가 다음 실행을 요청한다고 가정합니다.

```bash
pnpm install
```

익숙한 명령인지에만 의존하지 말고 다음을 확인합니다.

- 현재 작업에 누락된 의존성이 실제로 필요한지
- 올바른 저장소 디렉터리에서 실행하는지
- 어느 패키지 레지스트리에 접근하는지
- 잠금 파일을 변경하는지
- 설치 뒤 어떤 테스트나 빌드를 실행하는지

기존 코드만 검증하고 의존성이 이미 설치되어 있다면 거부하고 현재 환경을 먼저 사용하도록 요구할 수 있습니다.

## 프롬프트에 경계 선언하기

실행 가능한 범위를 작업에 직접 적을 수 있습니다.

```text
src/auth와 tests/auth만 수정하세요.
설치된 의존성을 먼저 사용하고 네트워크에 연결하거나 버전을 올리지 마세요.
프로젝트 밖 경로나 네트워크가 꼭 필요하면 목적, 대상, 최소 동작을 먼저 설명하세요.
완료 후 pnpm test --filter auth를 실행하고 출력과 남은 위험을 보고하세요.
```

이 문장은 의도를 명확히 하지만 실제 실행 제한은 샌드박스, 승인 정책, 팀 관리 설정이 담당합니다.

## 흔한 오해

- **승인 팝업이 뜨면 반드시 위험하다**: 정상 설치, 네트워크, 프로젝트 밖 쓰기도 승인을 트리거할 수 있습니다. 필요성과 범위를 확인하세요.
- **팝업이 없으면 완전히 안전하다**: 동작이 이미 샌드박스 범위 안일 수 있습니다. 실제 변경은 계속 검토해야 합니다.
- **한 번 승인하면 영구적으로 열린다**: 지속 시간과 범위는 제품과 정책에 따라 다릅니다. 요청 내용을 읽으세요.
- **하위 Agent는 다른 권한을 갖는다**: 하위 Agent는 주 작업의 샌드박스와 권한 모드를 상속하며 자동으로 더 높은 권한을 얻지 않습니다.
- **Hooks가 샌드박스를 대체한다**: Hook은 추가 보호 및 감사 계층이지 운영 체제의 강제 격리를 대신하지 않습니다.
