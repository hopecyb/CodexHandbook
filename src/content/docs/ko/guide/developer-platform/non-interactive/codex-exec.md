대화형 `codex`가 대화하며 일을 하는 편이라면, **`codex exec`**는 작업을 한 번에 맡기고, 끝나면 결과를 돌려주는 쪽에 가깝습니다.

[비대화형 모드](/guide/cli/non-interactive-mode/)의 핵심입니다. 주고 채팅도, 중간에 확인도 없고, 프로세스가 끝나면 결과나 실패 상태를 줍니다. 이 장은 [개발자 플랫폼](/guide/developer-platform/) 통합 담당자를 향하며, Codex를 스크립트나 CI에 처음 붙이려는 독자에게도 특히 맞습니다.

## 이 페이지 내용

- `exec`와 대화형 `codex`의 차이
- 최소 명령 형태와 작업 디렉터리
- 무인 운영 시 승인·샌드박스 요구사항

## `exec`가 하는 일

`codex exec`는 이렇게 이해하면 됩니다.

- 일회성 작업 지시서를 낸다
- 끝나면 결과를 돌려준다

지시서가 명확하면 그 설명대로 실행하고, 끝나면 결과를 주고 종료합니다.

그래서 다음 시나리오에 가장 맞습니다.

- 작업 경계가 이미 고정됨
- 중간에 오고 가며 확인할 필요가 없음
- 이후에도 안정적으로 반복 실행하고 싶음

## 왜 존재하는가

CI에서 Codex와 채팅하지 않고, 중간에 열 번 물어보기를 기대하지도 않습니다.

그래서 `codex exec`의 적용 시나리오는 보통 다음과 같습니다.

- 코드 리뷰 자동화
- 스케줄 작업
- 배치 스크립트
- 파이프라인 안의 단발 분석·생성 단계

“**작업 경계가 이미 명확한**” 시나리오에 맞습니다. 아직 모호하게 탐색 중이라면 대화형 모드가 보통 더 낫습니다.

:::note
**명령 이름과 파라미터는 공식 CLI를 기준으로 합니다.** 업그레이드 후 `codex --help`와 `codex exec --help`로 다시 확인하세요.
:::

## 최소 사용법

```bash
cd /path/to/repo
codex exec --cwd . "읽기 전용：현재 브랜치와 main의 diff를 비교해, 보안 위험이 가장 큰 3가지를 나열하고, 파일은 수정하지 마세요"
```

원칙:

- Shell 스크립트에서 먼저 깨끗한 worktree로 `cd`
- 프롬프트는 저장소 `prompts/` 또는 heredoc에 두어 shell 이스케이프 오류를 피함
- CI에서는 **종료 코드**로 성패를 판정

## 가장 놓치기 쉬운 현실

대화형 모드에서는 “그게 아니에요”라고 한 문장 더 보탤 수 있습니다.  
`exec` 모드에서는 **첫 지시가 틀리면 한 라운드 전체가 빗나갈 수 있습니다**.

그래서 `exec` 프롬프트를 쓸 때는 평소보다 더 분명히 적으세요.

- 무엇을 할지
- 무엇을 하지 말지
- 출력 형식이 무엇인지
- 무엇을 완료로 볼지
- 실패 시 어떻게 종료하길 원하는지

## 흔한 오해

### `exec`는 고정 작업에 더 맞습니다

처음에는 “CLI의 고급 모드”로 이해하기 쉽습니다.

더 정확한 이해는, **안정적으로 반복 실행**하는 데 맞다는 것입니다.

### 짧다고 해서 명확한 것은 아닙니다

대화형 모드에서는 조금 모호해도 나중에 보완할 수 있습니다.

`exec`에서는 짧은 프롬프트가 경계·제한·성공 기준을 빼먹으면, 우아한 게 아니라 통제하기 더 어려워지기 쉽습니다.

## 권장 워크플로

```text
저장소 준비(checkout、install、읽기 전용 token)
    → 프롬프트 버전 고정(git sha)
    → codex exec
    → stdout / artifact 수집
    → 비 0이면 CI 실패, 무한 재시도하지 않음
```

[스크립트와 파이프라인](/guide/developer-platform/non-interactive/scripts-and-pipelines/)과 이어집니다.

## 무엇으로 볼 수 있는가

- 스크립트화 가능한 단발 작업 명령
- 스크립트, CI, 스케줄 작업에 넣기 적합

그래서 많은 팀이 `make review`, GitHub Actions, cron, 내부 플랫폼 버튼 뒤에 붙입니다.

## 대화형 모드와 비교

| | `codex` 대화형 | `codex exec` |
|---|---|---|
| 확인 질문 | 여러 라운드 가능 | 한 번에 명확히 |
| 승인 | 사람이 자리에 있음 | 사전 정책을 더 조여야 함 |
| 적합 | 학습, 탐색 | CI, cron |

## 헷갈릴 때 고르는 법

- 요구사항이 아직 흔들리고 자주 말을 바꿀 수 있음：대화형 모드를 우선
- 작업이 이미 템플릿으로 고정되어 안정적으로 반복만 하면 됨：그때 `codex exec`

`codex exec`는 “이미 명확하고, 나중에 다시 돌리고 싶은” 작업에 가장 맞습니다. 아직 생각하며 말을 바꾸고 있다면, 비대화형 흐름에 급히 넣지 마세요.

## 흔한 실수

- 긴 채팅 이력을 단발 exec에 넣는 것
- CI에 쓰기 권한 token을 쓰고, 프롬프트에 소독하지 않은 PR 본문이 들어가는 것
- CLI 버전을 고정하지 않아 파이프라인이 갑자기 실패하는 것
- 비영 종료 코드를 무시하고 green으로 표시하는 것
- 사람 판단이 필요한 복잡한 작업을 무인 흐름에 억지로 넣는 것
