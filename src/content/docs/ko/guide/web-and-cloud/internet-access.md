Cloud 작업은 종종 **출망**이 필요합니다. npm/PyPI 패키지 받기, API 접근, 서브모듈 클론 등입니다. 동시에 인터넷 접근은 **데이터 유출**의 고위험면이기도 합니다. Agent가 저장소나 Secrets의 내용을 외부 서비스로 가져갈 수도 있기 때문입니다.

## 내용

- Cloud 환경이 기본적으로 인터넷에 접근할 수 있는지
- 언제 열고, 노출을 어떻게 최소화할지
- 로컬 샌드박스, Secrets 정책과의 조합

## 기본 경계

“네트워킹이 필요”하다고 “무제한 네트워킹이 필요”한 것은 아닙니다.

많은 사람이 이것을 양자택일로 봅니다.

- 아예 네트워킹 불가
- 편의를 위해 전부 개방

더 흔한 방법은, 작업에 필요한 네트워크 능력만 주고 남는 네트워크 능력은 주지 않는 것입니다.

## 두 층의 「네트워크」

| 층 | 의미 |
|---|---|
| Cloud 환경 출망 | 원격 머신이 공망 또는 사내 API에 접근할 수 있는지 |
| Agent 도구 네트워킹 | 세션 안의 web search, curl 등(클라이언트마다 정책이 다름) |

이 페이지는 **Cloud 환경**에 초점을 둡니다. 일반 개념은 [샌드박스와 네트워크](/guide/foundations/sandbox-and-network/)를 보세요.

## 로컬에서 된다고 Cloud에서도 되는 것은 아닙니다

로컬에서 네트워킹이 되는 이유는 다음과 같을 수 있습니다.

- 컴퓨터에서 이미 어떤 서비스에 로그인됨
- 로컬에 `.npmrc`, SSH key, 프록시 설정이 있음
- 회사 VPN 안에 있음

하지만 Cloud는 이런 조건을 기본으로 상속하지 않습니다. 그래서 “로컬에서 `npm install`이 된다”가 “Cloud에서도 된다”를 의미하지는 않습니다.

## 출망이 필요한 전형 시나리오

- 의존성 설치：`npm install`, `pip install`, `go mod download`
- 사설 registry 받기([Secrets](/guide/web-and-cloud/secrets-and-variables/) 필요)
- 서드파티 API 호출(결제, 지도, LLM 게이트웨이 등)
- 서브모듈 클론 또는 빌드 리소스 다운로드

## 판단 원칙

어떤 네트워킹 동작이 이번 작업에 필수가 아니면, 먼저 열지 마세요.

예:

- 의존성 설치를 위해 패키지 소스에 접근：보통 필수
- 무관한 사이트에 접근하거나 추가 리소스를 다운로드：보통 불필요

## 권장 전략

### 기본은 조이고, 필요하면 연다

1. [Cloud 환경](/guide/web-and-cloud/cloud-environments/)에서 현재 네트워크 정책 확인
2. **필수 도메인**을 목록으로 만듦(패키지 매니저, 회사 API). 「전망 개방」을 피함
3. `AGENTS.md`에 허용 URL과, 키를 프롬프트에 쓰지 말 것을 명시
4. 테스트 작업으로 검증：의존성은 설치되고, 무관한 사이트는 접근 불가(제품이 세분 정책을 지원하면)

### Secrets와의 역할 분담

| 내용 | 어디에 |
|---|---|
| API key, token | Cloud Secrets, 저장소에 넣지 않음 |
| 허용 API 베이스 URL | 문서 또는 환경 변수 이름(값 아님) |
| 프록시 / 미러 URL | 팀 표준 설정 |

## 흔한 오해

### 1. 네트워킹은 “조금 편할 뿐”이지 보안 문제가 아니다

네트워킹이 되면 동시에 다음이 됩니다.

- 의존성 다운로드 문제
- 자격 증명 사용 문제
- 데이터 외부 전송 문제

### 2. Secret을 프롬프트에 쓰지 않으면 절대 안전하다

환경이 Secret을 읽을 수 있고, 결과를 외부 서비스로 보낼 수 있으면 위험은 여전히 있습니다.

### 3. web search와 Cloud 출망은 같다

하나는 원격 환경 층의 네트워크 접근 능력이고, 하나는 세션 도구 층의 네트워킹 능력입니다. 장애 분석 때 섞지 마세요.

### 데이터 유출 방어

- 프로덕션 DB 연결 문자열을 작업 설명에 넣지 마세요
- Agent가 `.env`, 키 파일 내용을 외부로 보내려는지 검토하세요
- 신뢰할 수 없는 저장소에서 첫 Cloud 실행 시 **출망 금지 또는 읽기 전용 샌드박스**로 시험하세요

## 로컬 개발과 맞추기

로컬에서 `curl`이 된다고 Cloud에서도 되는 것은 아닙니다. 흔한 「Cloud 빨강」원인:

| 현상 | 가능한 원인 |
|---|---|
| 의존성 설치 실패 | 출망 금지 또는 registry 인증 필요 |
| 서브모듈을 못 받음 | SSH key가 Secrets에 주입되지 않음 |
| 사내 API 타임아웃 | Cloud가 회사 VPN 밖에 있음 |

해결 방향：HTTPS + token으로 바꾸기, 도달 가능한 미러 제공, 또는 Cloud가 사내 리소스를 지원하지 않는다고 문서에 명시.

## 흔한 실수

- 편의를 위해 출망을 전역 개방한 채, Secrets가 있는 프로덕션 저장소에서 제한 없는 작업을 돌림
- Cloud와 노트북이 같은 `.npmrc`를 공유한다고 가정(푸시하지 않았거나 Secret 미구성)
- 「네트워킹 필요」와 「web search 도구 필요」를 혼동
- 설치가 실패하고 나서야 Cloud에 로컬 로그인 상태가 없음을 처음 깨달음

## 검수 체크리스트

- [ ] 해당 저장소 Cloud 작업에 필수인 출구 도메인/서비스를 나열
- [ ] Secrets가 구성되었고 Git에 커밋되지 않음
- [ ] 테스트 브랜치에서 설치 + 테스트 전체 한 번 통과
- [ ] 팀이 네트워킹 프롬프트에 넣으면 안 되는 데이터를 앎
