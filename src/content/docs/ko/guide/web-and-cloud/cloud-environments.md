“Cloud 환경”은 Codex가 원격에서 작업을 실행할 때 쓰는 작업 머신입니다.

OS, 언어 버전, 툴체인, 네트워크 정책, 어느 저장소 브랜치를 받았는지까지 결과에 직접 영향을 줍니다. 이 층은 흔한 질문을 설명합니다.

> **왜 로컬에서는 되는데 Cloud에서는 실패하나?**

## 내용

- Cloud 환경과 로컬 개발기의 차이
- 환경이 GitHub 저장소·브랜치와 어떻게 묶이는지
- 팀이 재현 가능한 Cloud 설정을 어떻게 유지하는지

## 먼저 볼 것

먼저 이 세 가지를 보세요.

- Cloud는 “지금 컴퓨터의 모든 것”을 읽지 않습니다. 원격 환경에 있는 것만 봅니다
- Cloud도 “의존성이 있는지, 버전이 맞는지, 네트워크가 통하는지” 같은 현실 문제에 부딪힙니다
- 로컬에서 커밋·푸시하지 않은 것은 Cloud가 기본적으로 보지 못합니다

Cloud를 먼저 “다른 머신에서 일하는 것”으로 이해하면 됩니다.

## 핵심 개념

```text
GitHub 저장소(어떤 브랜치)
        ↓ clone / checkout
Cloud 환경 인스턴스(컨테이너 또는 VM, 제품 기준)
        ↓
Agent가 작업 실행：의존성 설치、코드 수정、테스트、푸시
```

[GitHub 연결](/guide/web-and-cloud/connect-github/)과 함께 쓰세요. 환경은 노트북에 푸시하지 않은 commit에 **접근할 수 없습니다**.

## 로컬과 Cloud의 차이

- **로컬 작업**：Codex가 눈앞에서, 지금 이 컴퓨터를 중심으로 일함
- **Cloud 작업**：Codex를 원격 머신에 보내 일함

Cloud를 처음 쓸 때 흔한 혼란도 여기서 옵니다.

- “왜 로컬에서 방금 고친 파일이 안 보이지?”
- “왜 내 컴퓨터에 전역으로 깐 도구가 없지?”
- “왜 본기기에서 연 DB에 연결이 안 되지?”

대부분은 **그 원격 머신에 원래 그런 것이 없기 때문**입니다. 문제는 환경 자체에 있습니다.

## 환경에 들어가는 것(개념 층)

| 구성 요소 | 설명 |
|---|---|
| 베이스 이미지 | OS, 흔한 빌드 도구 |
| 런타임 | Node, Python, Go 등(이미지와 작업에 따라) |
| 작업 디렉터리 | 클론 후 저장소 경로 |
| 네트워크 정책 | 출망 허용 여부, 접근 가능한 도메인 |
| 자격 증명 주입 | [Secrets와 변수](/guide/web-and-cloud/secrets-and-variables/) |

구체 이미지 목록과 커스텀 방식은 [공식 Cloud 문서](https://developers.openai.com/codex)를 기준으로 합니다.

## 흔한 오해

### 1. Cloud가 본기 환경을 자동으로 상속한다고 생각함

그렇지 않습니다.

본기에 깐 Node, Python, Homebrew, Chrome, DB 클라이언트는 “로컬에 있다”고 Cloud에 자동으로 나타나지 않습니다.

### 2. 저장소를 푸시하면 모든 준비가 끝난다고 생각함

저장소 코드는 시작점일 뿐입니다. 작업 성공은 다음에 달립니다.

- 의존성을 어떻게 설치할지
- 시작·테스트 명령이 무엇인지
- 어떤 Secret이 필요한지
- 네트워크 정책이 외부 리소스 접근을 허용하는지

### 3. Cloud 실패가 Codex가 못해서라고 생각함

많은 Cloud 실패는 환경이 갖춰지지 않아서이지, 작업을 못해서가 아닙니다.

장애 분석 순서는 이렇게 할 수 있습니다.

1. 저장소와 브랜치가 맞는지
2. 의존성과 런타임 버전이 맞는지
3. Secret과 네트워크를 쓸 수 있는지
4. 작업 프롬프트가 분명한지

## 권장 설정 흐름

1. **테스트 저장소**에서 첫 Cloud 작업을 끝내고, 의존성 설치 명령을 기록
2. 반복 단계를 저장소 문서에 씀(`README`, `AGENTS.md`, 또는 공식 지원 environment 설정 파일)
3. [Secrets](/guide/web-and-cloud/secrets-and-variables/) 구성(사설 registry, API key)
4. [인터넷 접근](/guide/web-and-cloud/internet-access/) 정책이 보안 요구에 맞는지 확인
5. 같은 환경 템플릿으로 issue → PR 루프를 검증

## 언제 Cloud가 맞나

이렇게 판단하세요.

- 컴퓨터 위 프로젝트만 고치고 바로 결과를 보고 싶음：먼저 로컬
- 작업을 걸어 두고 싶고, 팀이 통일 환경을 쓰며, 원격으로 GitHub에 붙고 싶음：그때 Cloud

로컬 워크플로가 아직 안 익숙하면, 문제를 급히 “Cloud 설정 문제”로 올리지 마세요.

## 로컬 환경과 맞추기

「로컬은 초록, Cloud는 빨강」을 피하세요.

| 실천 | 이유 |
|---|---|
| 의존성 버전 잠금(lockfile) | 재현 가능한 설치 |
| `AGENTS.md`에 설치·테스트 명령 명시 | Agent가 추측하지 않음 |
| CI와 Cloud가 비슷한 Node/Python 버전 사용 | 버전 드리프트 감소 |
| 큰 파일은 Git LFS 또는 빌드 시 다운로드 | 클론 크기 통제 |

## 수명 주기

전형적인 Cloud 작업 한 번:

1. 환경 인스턴스 **생성/재사용**
2. **준비**：clone, 브랜치 checkout, 의존성 설치
3. **실행**：Agent가 코드 수정, 명령 실행
4. **산출**：브랜치 푸시, PR, 로그 artifact
5. **폐기 또는 회수**(정책은 제품마다 다름)

장시간 작업은 [데스크톱 App 알림](/guide/desktop-app/notifications/)이나 모바일에서 후속할 수 있습니다.

## 흔한 실수

- Cloud에 프로젝트 사설 monorepo의 전체 툴체인이 미리 있다고 가정
- `localhost` 서비스(DB, mock API)에 의존하는데 환경에 제공하지 않음
- 처음부터 프로덕션 저장소에서 경계 없는 작업을 돌림
- “환경 문제”를 “모델 능력 문제”로 오판

## 보안 경계

- 환경은 **반신뢰**로 보세요. 여전히 code review와 브랜치 보호가 필요합니다
- 프로덕션 DB 연결 문자열은 Secrets로만 주입하고, 프롬프트에 넣지 마세요
- 쓰지 않는 환경 템플릿과 Secrets를 주기적으로 정리하세요
