Cloud 작업은 사설 API, 패키지 저장소, 데이터베이스에 접근해야 하는 경우가 많습니다. 이때 쓰는 자격 증명은 **Secrets와 환경 변수**로 주입하세요. 코드, 프롬프트, issue, 채팅 기록, Git 이력에 쓰지 마세요.

## 내용

- Secrets와 일반 환경 변수의 차이
- Cloud 콘솔 / 저장소 설정에서 구성하는 방법
- GitHub Actions Secrets와의 관계

## Secret과 환경 변수 구분

이렇게 구분하면 됩니다.

- **Secret**：아무나 보면 안 되는 값. API Key, DB 비밀번호, 개인 키 등
- **환경 변수**：프로그램이 읽는 설정 항목. 민감한 것도 있고 아닌 것도 있음

모든 환경 변수가 Secret은 아니지만, Secret은 안전한 주입 경로를 타는 편이 좋고, 하드코딩하면 안 됩니다.

## 개념 구분

| 유형 | 내용 예시 | 저장 요구 |
|---|---|---|
| **Secret** | API key, 개인 키, DB 비밀번호 | 암호화 저장, UI 마스킹, 로그에 넣지 않음 |
| **변수** | `NODE_ENV=production`, 기능 스위치 | 비암호화 가능, 그래도 업무 전략 유출은 피함 |
| **저장소 안 `.env`** | 로컬 개발용 | **커밋하지 마세요**；Cloud는 콘솔 Secrets로 대체 |

민감 컨텍스트 총칙：[민감 컨텍스트](/guide/context/sensitive-context/)

## 흔한 오해

### 1. “키를 잠깐만 붙여 넣으면 괜찮지 않나?”

위험이 큽니다. 키를 다음 곳에 붙이면:

- 대화
- issue
- PR 설명
- shell 이력
- Git 커밋

로그, 알림, 스크린샷, 이력 버전, 다른 협업자에게 퍼질 수 있습니다.

### 2. “`.env`에 쓰고 커밋하면 Cloud가 읽지 않나?”

`.env`는 로컬 개발에 더 맞고, 버전 저장소에 커밋하기에는 맞지 않습니다. Cloud에서는 플랫폼이 제공하는 Secret 관리를 우선하세요.

### 3. “Secret 이름은 아무거나, 값만 맞으면 되지?”

많은 작업 실패는 값 자체가 아니라 여기입니다.

- 이름 오타
- 스코프가 틀림
- 코드가 다른 변수 이름을 읽음

그래서 문서, 코드, Cloud 설정의 이름을 통일하는 편이 좋습니다.

## 구성 원칙

1. **최소 권한**：Secret마다 한 종류의 작업만 가능하게
2. **저장소/환경별 격리**：staging과 production 분리
3. **로테이션**：token을 주기적으로 갱신, 옛 작업 무효화는 감수
4. **감사**：누가 어떤 Secret을 추가/수정했는지 기록(팀 프로세스)
5. **절대 에코하지 않음**：작업 로그와 PR 댓글에 Secret 값을 찍지 않음

## 최소 구성 흐름

이 순서로 처리하세요.

1. 작업이 실제로 접근해야 하는 외부 서비스를 먼저 나열
2. 이번 작업에 필요한 Secret만 준비하고, 처음부터 프로덕션 전권한을 주지 않음
3. 문서에 “어떤 이름의 Secret이 필요한지”만 쓰고, 값은 쓰지 않음
4. 테스트 작업을 한 번 돌려 읽을 수 있는지 검증
5. 그다음 실제 작업

## 권장 워크플로

```text
1. Cloud / GitHub 설정에 Secret 추가(이름은 대문자 스네이크, 예: NPM_TOKEN)
2. AGENTS.md에 「NPM_TOKEN이 있어야 사설 패키지를 설치할 수 있다」고 쓰고, 값은 쓰지 않음
3. Cloud 작업을 시작하고, 환경이 읽을 수 있는지 확인(실패하면 이름 철자와 스코프 확인)
4. CI는 GitHub Actions Secrets를 쓰고, Cloud 이름과 맞춰 문서화하기 쉽게
```

[GitHub 통합](/guide/integrations/github/)과 함께 쓸 때는, Agent가 issue 본문에서 키를 복사하게 하지 말고 플랫폼 네이티브 Secrets를 우선하세요.

## 언제 Secret으로 볼까

어떤 값을 Secret으로 둘지 모르겠다면, 먼저 스스로에게 물어보세요.

- 이 값이 유출되면 금전, 데이터, 권한, 업무 위험이 생기는가?

답이 “예”라면, 공개 문서, 프롬프트, 채팅 기록, 저장소에 두면 안 됩니다.

## 인터넷 접근과 Secrets

일부 작업은 출망해 패키지를 받거나 API를 호출해야 합니다.

- 출망 정책은 조직 보안 규정을 따름
- 출망이 가능해도 프롬프트에 Bearer token을 붙이지 않음
- 신뢰할 수 없는 저장소에서는 프로덕션 Secrets 읽기를 기본 금지

## 흔한 실수

| 실수 | 위험 |
|---|---|
| `.env`를 저장소에 커밋 | 영구 유출 |
| issue/작업 설명에 key를 붙임 | 로그·알림으로 확산 |
| 실험 작업에 프로덕션 Secret 사용 | 프로덕션 데이터 오동작 |
| Secret 이름과 코드가 불일치 | 작업이 조용히 실패 |
| 편의를 위해 관리자 권한 token을 바로 줌 | 통제면이 너무 큼 |

## 검수 체크리스트

- [ ] 저장소에 하드코딩 키 없음(secret scanner 사용 가능)
- [ ] Cloud Secrets 목록이 문서의 이름과 일치
- [ ] 작업 실패 로그에 Secret 평문이 없음
- [ ] 퇴사/로테이션 프로세스가 정의됨
