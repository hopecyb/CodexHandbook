**위임**은 작업을 Cloud에 맡겨 원격 환경에서 실행하는 것입니다. **후속**은 작업 중·종료 후 진행을 보고, 컨텍스트를 보태고, 위험한 동작을 승인하고, 수정을 요구하는 것입니다. “자리를 떠나도 계속 추진”하는 핵심 워크플로입니다.

## 내용

- 로컬이 아니라 Cloud에 위임할 때
- 입구별로 위임이 어떻게 다른지
- 「던져 두고 잊기」를 피하는 효과적 후속

## 이런 흐름이 어떻게 가나

Cloud 작업은 대략 이런 과정에 가깝습니다.

- 먼저 작업을 분명히 말함
- 원격에서 실행이 시작됨
- 중간에 제약 한 줄이나 승인이 필요할 수 있음
- 끝난 뒤에도 diff, PR을 보고 계속할지 결정함

Cloud는 실행 장소만 원격으로 바꿉니다. 이후 후속과 판단은 여전히 당신입니다.

## 누구에게 맞나

| 시나리오 | 권장 |
|---|---|
| 장시간 빌드/테스트 | Cloud에 위임하고, 로컬은 다른 일 |
| 출퇴근/회의 사이 | 폰에서 상태 확인, 핵심 단계 승인 |
| 표준화 환경이 필요 | Cloud + [환경 설정](/guide/web-and-cloud/cloud-environments/) |
| 빠른 로컬 시행착오 | [데스크톱 App](/guide/desktop-app/) 또는 [IDE](/guide/ide/local-task-workflow/) 우선 |

## 언제 위임이 맞나

위임할지 모르겠다면 이렇게 고르세요.

- 작업이 아직 반복 실험 중이고 보며 고치고 싶음：먼저 로컬
- 오래 돌리고 싶고, 컴퓨터를 떠나고 싶고, 통일 환경에 맡기고 싶음：그때 Cloud

## 위임 전 확인

- [ ] [GitHub 연결됨](/guide/web-and-cloud/connect-github/), 대상 브랜치 전략이 분명함
- [ ] 작업 설명에 목표, 범위, 금지 항목, 검수 방식이 있음([좋은 작업의 구조](/prompts/task-anatomy/))
- [ ] 필수인데 푸시하지 않은 로컬 commit이 있으면 먼저 push하거나 로컬에서 함
- [ ] Secrets / [출망 요구](/guide/web-and-cloud/internet-access/)가 준비됨

## 흔한 오해

### 1. 위임하면 더 볼 필요 없다

가장 시간을 낭비하는 방식입니다. 방향이 빗나가면 늦게 발견할수록 재작업이 커집니다.

### 2. 후속은 “진행을 재촉하는 것”이다

더 가치 있는 후속은 이런 동작입니다.

- 빠진 컨텍스트를 보탬
- 범위를 조임
- 통과시키면 안 되는 위험 동작을 거부
- 끝난 뒤 계속 수정을 요구

### 3. 위임과 로컬은 대립한다

흔한 실제 흐름은 이렇습니다.  
**먼저 로컬에서 탐색하고, 장시간 작업은 위임하고, 마지막은 로컬에서 마무리.**

## 입구별 위임(개념)

| 입구 | 특징 |
|---|---|
| [데스크톱 App · 로컬과 클라우드 작업](/guide/desktop-app/local-and-cloud-tasks/) | 같은 프로젝트 뷰에서 로컬/Cloud 전환 |
| [IDE · 클라우드 작업](/guide/ide/cloud-task-workflow/) | 에디터에서 선택한 코드와 연 파일 컨텍스트를 가져감 |
| Web / 모바일 | 가벼운 확인, 승인, 후속 한 줄 |

구체 버튼과 이름은 현재 제품을 기준으로 합니다.

## 권장 후속 리듬

```text
위임 시작 → 환경 기동 확인 →(선택)중간에 로그 확인
    → 위험 동작 지점에서 승인 → 작업 완료 후 diff/PR 확인
    → 불만족：추가 지시 또는 새 후속 작업
```

이 동작 순서로 하세요.  
**보낸 뒤, 최소한 “중간 한 번 + 종료 한 번”은 보세요.**

### 중간 개입

- **컨텍스트 보태기**：파일이나 제약을 빠뜨렸을 때 후속 메시지로 설명. 작업을 새로 열어 이력을 잃지 않게
- **범위 조이기**：빗나가면 「X 수정을 멈추고 Y만 하라」고 명시
- **승인**：[사람 승인 패턴](/cases/workflows/human-approval-patterns/)——한 박자 늦더라도, 모르는 shell을 일괄 통과시키지 마세요

### 종료 후

- [PR 만들기](/guide/web-and-cloud/create-pull-requests/) 흐름에서 diff 검토
- [Cloud 코드 리뷰](/guide/web-and-cloud/code-review/) 또는 로컬에서 브랜치 checkout 후 검증
- 계속 수정이 필요하면：같은 PR에 위임을 추가하거나 로컬에서 인수

## 알림과 함께

[데스크톱 알림](/guide/desktop-app/notifications/) 또는 모바일 푸시를 켜서, 오래 승인자가 없어 작업이 멈추지 않게 하세요. 팀은 프로덕션 관련 저장소를 언제 누가 승인할 수 있는지 약속해야 합니다.

## 흔한 실수

- 위임 문구가 너무 모호해 Cloud가 스스로 「이해」하며 광범위 리팩터
- 로컬에서 반쯤 고치고 커밋하지 않은 채, Cloud가 원격 main에서 시작하게 함
- 중간에 전혀 보지 않고 끝날 때야 방향 오류를 발견해 환경 시간을 낭비
- PR에 「LGTM」만 쓰고 테스트를 돌리지 않음
- “원격 실행”을 “원격이 책임진다”로 오해

## 검수 체크리스트

- [ ] 최소 한 입구에서 Cloud 작업을 시작하고 끝낼 수 있음
- [ ] 작업 중에 유효한 제약을 한 줄 추가할 수 있음
- [ ] PR 또는 브랜치를 내고, 사람이 diff를 검토함
