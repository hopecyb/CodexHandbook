위임은 문제를 맡겨 두고 잊는 일이 아닙니다. 목표, 제약, 환경, 완료 기준을 독립적인 Cloud 대화에 전달하는 일입니다. 작업은 백그라운드에서 실행될 수 있으며, 로그를 확인하고 맥락을 추가하거나 수정을 요청한 뒤 마지막에 diff를 검토할 수 있습니다.

## 위임하기 좋은 경우

- 빌드나 테스트에 시간이 오래 걸립니다.
- 입력이 이미 원격 저장소에 있습니다.
- 스크립트로 환경을 다시 만들 수 있습니다.
- 현재 작업과 독립적으로 진행할 수 있습니다.
- 결과를 바로 병합하지 않고 검토할 계획입니다.

로컬의 커밋하지 않은 상태, 로컬 서비스, 지속적인 사람의 조작이 필요한 작업은 우선 로컬에서 진행하세요.

## 완전한 위임 요청의 예

```text
목표: #42에서 로그인 요청이 30초 후에도 연결을 해제하지 않는 문제를 고칩니다.
시작점: acme/api의 fix/42-timeout 브랜치.
범위: packages/auth/** 및 관련 테스트.
금지: 의존성 업그레이드, 공개 API 변경, main 푸시.
검증: pnpm test --filter auth; pnpm typecheck.
완료: 근본 원인, diff, 실행 명령과 종료 결과를 보여 주세요. 자동 병합은 하지 마세요.
```

시작한 뒤 환경과 브랜치가 맞는지 먼저 확인하세요. 실행 중에는 전제가 빠졌거나 방향이 어긋난 경우에 후속 지시를 보냅니다.

```text
추가 제약: 전역 HTTP client를 수정하지 마세요. 수정 범위는 auth adapter로 제한합니다.
이 제약이 현재 방안을 어떻게 바꾸는지 먼저 설명한 뒤 계속하세요.
```

같은 대화에는 기존 맥락이 남으므로 같은 목표를 조정하는 데 적합합니다. 완전히 독립된 목표라면 새 대화를 여세요. 병렬 작업이 같은 브랜치나 파일 집합에 동시에 쓰지 않도록 하세요.

## 결과가 나온 뒤

1. 요약과 전체 diff를 읽습니다.
2. 변경된 경로를 허용 범위와 비교합니다.
3. 각 검증 명령의 실제 출력을 확인합니다.
4. 실패했거나 실행되지 않은 항목은 설명을 요청합니다.
5. 수정이 필요하면 같은 대화에서 구체적으로 후속 요청을 합니다.
6. 기준을 만족하면 PR을 만들고 CI와 사람이 검토하도록 합니다.

Cloud 작업은 Web, IDE, GitHub, GitLab(Beta), Linear, Slack에서 시작할 수 있습니다. 공식 Cloud 페이지는 Codex CLI에서 작업을 시작하고 검토할 수도 있다고 설명합니다. 어느 입구에서 시작하든 저장소, 환경, 네트워크, 검토의 경계는 같습니다.

## 실패 후 후속 요청

단순히 '다시 시도'라고만 하지 마세요. 실패 근거와 다음 단계를 제시합니다.

```text
테스트가 retry.test.ts:48에서 실패했습니다. 먼저 이 실패가 이번 변경으로 발생했는지 설명하세요.
그렇다면 해당 회귀만 수정하고 auth 테스트를 다시 실행하세요.
그렇지 않다면 실패 상태를 유지하고 기록에 명확히 남기세요.
```
