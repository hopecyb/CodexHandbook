Cloud 워크플로를 처음 쓸 때 흔한 상황은, 작업은 끝났는데 변경이 아직 검사·토론하기 쉬운 상태가 아닌 것입니다. 팀 협업에서는 이 단계를 보통 **Pull Request**로 끝냅니다.

PR은 검토할 수 있는 변경 신청입니다.

무엇을 바꿨는지, 왜 바꿨는지, 테스트했는지가 한곳에 모여 review할 수 있게 됩니다. Cloud 작업이 팀에 납품될 때도 여기로 떨어집니다.

## 내용

- 클라우드 작업에서 PR까지의 엔드투엔드 기대
- PR 설명에 무엇을 넣어 사람과 CI가 검수하기 쉽게 할지
- 언제 PR을 자동으로 열면 안 되는지

## 언제 PR을 열까

변경을 다른 사람이 봐야 하고, CI가 돌아야 하며, 결국 메인 브랜치에 머지해야 한다면, “브랜치에서 이미 고쳤다”에서 멈추지 말고 **검토 가능한 PR**까지 이어 가세요.

## 권장 워크플로

```text
GitHub 연결 → issue/목표 명확화 → Cloud 작업(계획 확인)→ 브랜치 푸시 → PR 열기 → 사람 review + CI → 머지
```

선행：[GitHub 연결](/guide/web-and-cloud/connect-github/)

## 처음부터 자동 머지를 권하지 않는 이유

PR의 역할은 사람과 시스템에 검사 입구를 남기는 것이지, 코드만 올리는 것이 아닙니다.

흔한 방법은 다음과 같습니다.

- Codex가 PR을 열 수 있음
- 머지 여부는 사람이 결정

작업 방향이 빗나가도, 사람 검사라는 한 단계가 남습니다.

## 작업 프롬프트 요점

```text
목표：#42에 적힌 로그인 타임아웃 문제 수정
브랜치：fix/42-login-timeout
범위：packages/auth와 관련 테스트만
완료：main으로 PR을 열고, 머지하지 마세요
PR 설명에 포함：원인、변경 요약、테스트 명령과 결과、위험과 롤백
```

[완료 정의](/prompts/define-done/)와 [좋은 작업의 구조](/prompts/task-anatomy/)와 맞춥니다.

## 좋은 PR이 최소로 답해야 할 네 질문

1. 왜 이 일을 바꿨는가?
2. 구체적으로 어디를 바꿨는가?
3. 어떻게 검증했는가?
4. 위험, 제한, 미커버 상황은 무엇인가?

PR 설명이 이 네 가지를 덮지 않으면, 검토자가 컨텍스트를 스스로 채워야 합니다.

## PR 품질 체크리스트

- [ ] 제목이 「무엇을 했는지」를 말하고, 「코드 업데이트」가 아님
- [ ] issue 번호 연결
- [ ] CI 통과 또는 알려진 실패 원인 설명
- [ ] diff 줄 수가 팀이 받아들일 범위；너무 크면 PR 분할
- [ ] 키 없음, 무관한 포맷팅 폭풍 없음
- [ ] 스크린샷 또는 로그(UI/행동 변경 시)

## 사람 게이트

Codex가 PR을 열 수 있어도, **머지**는 기본으로 사람이 합니다(또는 통제된 bot + 브랜치 보호):

[사람 승인 패턴](/cases/workflows/human-approval-patterns/)을 보세요.

## 흔한 오해

### 1. 관련 없는 변경을 한 PR에 몰아넣음

다른 사람이 보기 어렵고, 되돌리기도 어렵습니다.

### 2. “고쳤다”만 말하고 검증 방법을 말하지 않음

상대는 “정말 테스트했는지”인지 “느낌상 괜찮을 것 같은지” 모릅니다.

### 3. Codex가 메인 브랜치를 바로 건드림

개인 실험에서는 한 단계를 줄일 수 있지만, 협업 저장소에서는 위험이 너무 큽니다.

## Review 자동화와 함께

- Skill 또는 CI의 `codex exec`로 **보완 리뷰 댓글**을 달 수 있음
- 자동 머지는 별도 거버넌스 정책이 필요하며, 초보자 기본 경로에는 넣지 않음

## 흔한 실수

- PR에 관련 없는 기능이 여러 개
- 설명에 「AI가 생성한 수정」만 있고 테스트 설명이 없음
- review를 우회해 main에 바로 머지
