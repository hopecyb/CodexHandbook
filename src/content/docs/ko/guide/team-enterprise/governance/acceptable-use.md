**허용 가능한 사용 정책(AUP)**는 「이 일을 Codex로 해도 되는가」를 조직 합의로 써서, 개인 판단에만 기대지 않게 합니다. [위협 모델](/guide/team-enterprise/security/threat-model/)과 보완 관계입니다. 위협 모델은 위험을, AUP는 **행동 경계**를 말합니다.

## 내용

- AUP가 다뤄야 할 주제
- HR/컴플라이언스, 기술 통제와의 연결
- 조항 예시 초안(법무 현지화 필요)

## AUP가 관리하는 것

AUP가 주로 답하는 질문은, 기술적으로 가능해도 우리 팀에서 그렇게 해도 되는가입니다.

기술 정책을 대체하지 않고, 조직 수준의 경계를 모두가 읽고 실행할 수 있는 규칙으로 씁니다.

:::caution
아래는 **교육용 개요**이며 법률 의견이 아닙니다. 정식 배포 전 법무·컴플라이언스 검토가 필요합니다.
:::

## 흔한 오해

### AUP는 현장 사용자와도 직접 관련됩니다

많은 사람이 이런 정책 문서를 형식 요건으로만 보고, 현장 사용자와는 무관하다고 생각합니다.

하지만 일상에서 실제로 부딪히는 것은 보통 이런 질문입니다.

- 어떤 데이터를 Codex에 넣으면 안 되는가
- 어떤 시나리오는 반드시 사람이 재검토해야 하는가
- 어떤 확장과 외부 연결을 마음대로 붙이면 안 되는가

그래서 법무 문서만이 아니라, 실제 사용 경계이기도 합니다.

### 정책을 썼다고 팀이 그대로 하는 것은 아닙니다

정책이 “프로덕션 변경은 승인이 필요하다”고 해도, 도구가 기본으로 우회할 수 있으면 그 정책은 곧 무력화됩니다.

그래서 AUP에서 더 중요한 것은 교육, 권한, 설정, 감사와 맞물리는 것이며, 단순히 조항이 많은 것이 아닙니다.

## 다루면 좋은 주제

| 주제 | 요점 |
|---|---|
| 허용 용도 | 개발, 문서, 리서치, 내부 자동화 |
| 금지 용도 | 무단 접근, 괴롭힘 콘텐츠, 보안 통제 우회 |
| 데이터 등급 | 어떤 repo/데이터를 쓸 수 있는지；고객 PII 규칙 |
| 출력 책임 | 사람 검토 후 머지；출력을 법률/의료 조언으로 대외 사용하지 않음 |
| 확장 | 승인 목록 안의 Plugin/MCP만 |
| 계정 | 개인 좌석 공유 금지；퇴사 시 회수 |
| incident | 의심 행위 보고 경로 |

## 기본 구조

1. **목적과 범위**
2. **허용 사용 시나리오**([능력 지도](/guide/start-here/codex-capability-map/)로 연결)
3. **금지 사용 시나리오**
4. **데이터와 기밀**
5. **사람 감독 요구**(머지, 프로덕션 변경)
6. **위반 결과**(기존 직원 핸드북 인용)
7. **연락처와 갱신일**

## 기술 통제와 맞추기

| AUP 조항 | 기술 이행 |
|---|---|
| 소스 코드 exfiltrate 금지 | 네트워크 정책, MCP 승인 |
| 프로덕션 변경은 승인 필요 | 브랜치 보호, `git push` deny |
| 승인된 모델만 사용 | 조직 호스팅 설정 |

## 흔한 실수

- AUP를 쓰고 교육을 하지 않음
- 기술 reality와 단절(정책은 금지인데 도구는 허용)
- 수년 동안 갱신하지 않아 새 기능(Computer Use 등)과 단절

## AUP가 유효한지 판단하는 법

먼저 물어보세요.

1. 팀이 실제로 만나는 사용 경계에 답하고 있는가
2. 교육, 설정, 승인 흐름으로 내려갈 수 있는가
3. 위반했을 때 팀이 발견·처리 방법을 아는가

세 가지가 “예”에 가까울수록 그 정책이 실제로 유효할 가능성이 큽니다.

## 검수 체크리스트

- [ ] 직원 onboarding에 AUP 확인이 포함됨
- [ ] [팀 규칙](/guide/customization/rules/team-rules/)과 모순 없음
- [ ] 매년 또는 주요 기능 출시 시 재검토

AUP의 가치는 팀이 Codex를 쓰는 경계를 분명히 쓰고, 실제 통제 수단과 맞추는 데 있습니다.
