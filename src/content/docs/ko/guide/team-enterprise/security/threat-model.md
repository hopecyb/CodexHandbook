“위협 모델”을 쉽게 말하면, 위험을 미리 생각하는 일입니다.

> **Codex가 우리 코드, 명령, 외부 도구에 정말 붙으면, 무엇이 가장 잘 잘못될 수 있는가?**

**위협 모델**은 그 일을 쪼개서 분명히 보는 것입니다. Codex는 “또 하나의 채팅창”이 아니라 **코드를 읽고, 명령을 실행하고, 외부 도구를 호출**할 수 있습니다. 이 장은 주요 위험면을 먼저 펼치고, 구체 통제 항목은 [권한 매트릭스](/guide/reference/permission-matrix/)와 [샌드박스](/guide/foundations/sandbox-and-network/)를 보세요.

## 내용

- 자산과 신뢰 경계
- 전형적인 위협과 완화 방향
- 규칙, Hooks, CI와의 역할 분담

## “보안 담당자 일”로만 두지 마세요

개발, 플랫폼, 문서, 프로젝트 책임자라면 이 일도 직접 관련됩니다. 팀에서 실제로 문제가 나기 쉬운 것은 이런 구체 시나리오입니다.

- 과도한 권한 token을 자동화에 넘김
- 신뢰할 수 없는 입력 위에서 Agent가 고위험 동작을 바로 함
- 어떤 데이터를 볼 수 있고 무엇을 밖으로 내면 안 되는지 모름
- 확장을 들일 때 기능만 보고 권한·출처는 보지 않음

위협 모델의 가치는, 일이 나기 전에 팀이 경계를 먼저 분명히 하는 데 있습니다.

## 자산과 경계

| 자산 | 예시 |
|---|---|
| 소스 코드와 IP | 비공개 저장소, 미공개 설계 |
| 자격 증명 | API key, `.env`, 클라우드 IAM |
| 사용자 데이터 | PII, 고객 이슈 내용 |
| 인프라 | CI, 프로덕션 배포 파이프라인 |

**신뢰 경계：** 모델과 확장은 기본적으로 **완전히 신뢰할 수 없는** 쪽에 있습니다. 사람 검토와 정책이 경계에서 enforcement합니다.

## 두 가지 핵심 질문

팀 수준 연결 전에 먼저 물어보세요.

1. 가장 잃기 싫은 것은 무엇인가?
2. Codex가 잘못하기를 가장 두려워하는 동작은 무엇인가?

첫 질문은 “중요 자산”을, 두 번째 질문은 “위험한 동작”을 가려 줍니다. 많은 통제 전략이 이 두 질문 주위로 펼쳐집니다.

## 한 시나리오

이런 시나리오를 보세요.

- Codex가 비공개 저장소를 읽을 수 있음
- 권한이 있는 이슈 시스템에 접근할 수 있음
- shell 명령을 실행할 수 있음
- 결과를 댓글 영역에 다시 보낼 수 있음

이때 더 주목할 것은 다음입니다.

- 보면 안 되는 내용을 보게 되는가
- 하면 안 되는 동작을 하는가
- 내부에만 있어야 할 정보를 밖으로 가져가는가

문제를 이 수준에 두면, 위협 모델은 출시 전 위험 점검표에 더 가까워집니다.

## 위협 개요

| 위협 | 설명 | 완화 방향 |
|---|---|---|
| 프롬프트 주입 | 악성 issue/웹페이지가 권한 초과를 유도 | 입력 소독, 읽기 전용 CI, [주입 특집](/guide/team-enterprise/security/prompt-injection/) |
| 과도한 권한 | token·샌드박스가 너무 넓음 | 최소 권한, 브랜치 보호 |
| 데이터 유출 | 명령/MCP가 저장소 내용을 밖으로 전달 | 네트워크 정책, DLP, 감사 Hook |
| 악성 확장 | 검토하지 않은 Plugin/MCP | [확장 위험](/guide/team-enterprise/security/plugin-and-mcp-risk/) |
| 공급망 | 의존성·스크립트 오염 | 기존 SCA, code review와 결합 |
| 오동작 | Agent가 DB를 지우고, 잘못 push | 명령 deny, push 없는 CI |

## 위협 모델에 우선 넣을 경우

어떤 능력이 다음 두 가지를 동시에 만족하면, 위협 모델에 우선 넣으세요.

- 중요 자산에 닿을 수 있음
- 실제 동작을 실행할 수 있음

예: 비공개 저장소 읽기, 프로덕션 API 접근, 쓰기 권한이 있는 MCP 호출, 코드 자동 푸시.

## 처음 정착할 때 욕심내지 마세요

많은 팀이 보안 거버넌스를 들으면 문서·프로세스·정책을 한 번에 다 채우려다, 결국 아무것도 정착시키지 못합니다.

Codex를 처음 붙이는 팀은 보통 가장 직접적인 몇 가지만 해도 충분합니다.

1. 가장 중요한 자산 3종류를 먼저 나열
2. Agent가 잘못하면 안 되는 동작 3종류를 나열
3. 이 6가지에 각각 가장 직접적인 통제 수단을 붙임

예:

- 프로덕션 DB 데이터 유출이 걱정되면, 먼저 프로덕션 자격 증명과 내보내기 경로를 제한
- 메인 브랜치 오푸시가 걱정되면, 먼저 브랜치 보호와 승인 추가
- 웹페이지나 issue에 끌려갈까 걱정되면, 먼저 외부 입력과 읽기 전용 review 흐름을 조임

완전한 것은 아니지만, 아무도 따르지 않는 큰 문서를 쓰는 것보다 보통 더 쓸모 있습니다.

## 권장 계층 통제

```text
L1 신원과 테넌트(SSO、그룹)
L2 조직 호스팅 설정과 모델 정책
L3 저장소 rules + AGENTS.md
L4 샌드박스 / 승인 / Hooks
L5 사람 review와 브랜치 보호
```

## 흔한 실수

- 교육만 하고 기술 통제는 쓰지 않음
- 「모델이 충분히 똑똑해서」 실수하지 않을 거라 가정
- 프로덕션 키가 Agent가 쓸 수 있는 경로에 나타남
- 모든 위험을 “사람 review면 된다” 한 문장으로 압착

## 최소 버전

먼저 이 세 가지를 세우세요.

- 고위험 동작은 승인 필요
- 고민감 데이터는 기본으로 주지 않음
- 자동화 흐름은 기본 읽기 전용

이 세 가지를 먼저 잡으면, 많은 팀 수준 위험을 이미 낮출 수 있습니다. 세분 거버넌스는 나중에 천천히 보완해도 늦지 않습니다.
