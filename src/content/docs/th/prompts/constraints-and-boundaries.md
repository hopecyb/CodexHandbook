งานจำนวนมากล้มเหลวไม่ใช่เพราะไม่ระบุเป้าหมายเลย แต่เพราะ **ขอบเขตไม่ชัดเจน**

เมื่อคุณพูดว่า “ช่วยแก้หน้านี้หน่อย” Codex อาจตีความว่า:

- แก้เฉพาะข้อความ
- ปรับสไตล์พ่วงไปด้วยได้
- แก้คอมโพเนนต์ได้
- เพิ่ม dependency ได้

ทั้งที่คุณอาจต้องการเพียง “แก้ข้อความย่อหน้านี้เท่านั้น ห้ามแตะโครงสร้าง”

ข้อจำกัดตอบว่า งานนี้ควรไปไกลเพียงใด และอะไรที่ห้ามแตะโดยเด็ดขาด

## เนื้อหา

หน้านี้ช่วยหลีกเลี่ยงปัญหาต่อไปนี้:

- แก้ส่วนอื่นพ่วงไปด้วย
- ดำเนินการเกินสิทธิ์
- แก้ชั้นที่คุณไม่ได้ตั้งใจให้แตะ
- ดูเหมือนงานเสร็จ แต่มีต้นทุนสูงเกินไป

## ข้อจำกัดที่ใช้บ่อย

ข้อจำกัดตอบคำถามว่า “ห้ามทำอะไรโดยเด็ดขาด”

- แก้เฉพาะไฟล์/ไดเรกทอรีที่ระบุ
- ห้ามเปลี่ยน API contract / ห้ามเปลี่ยนฐานข้อมูล
- ห้ามเพิ่ม dependency ใหม่
- ห้ามส่งคำขอผ่านเครือข่าย
- คงการตั้งค่าเครื่องมือจัดรูปแบบเดิม

## แยก “เป้าหมาย” กับ “ข้อจำกัด” อย่างไร

- **เป้าหมาย**: คุณต้องการให้ทำอะไรให้สำเร็จ
- **ข้อจำกัด**: ขณะทำงานนั้น ห้ามข้ามเส้นใด

ตัวอย่าง:

```text
เป้าหมาย: ปรับข้อความ Hero บนหน้าแรกให้ชัดเจนขึ้น
ข้อจำกัด: ห้ามเปลี่ยน layout ห้ามเพิ่ม dependency และห้ามแก้พฤติกรรม CTA
```

หากไม่มีข้อจำกัด Codex อาจตีความ “ทำให้ชัดเจนขึ้น” เป็นงาน redesign ที่ใหญ่กว่า

## ความเข้าใจผิดที่พบบ่อย

### 1. ข้อจำกัดมากเกินไปจะทำให้ผลลัพธ์แย่ลงหรือไม่

หลายครั้งข้อจำกัดที่ชัดเจนกลับทำให้ผลลัพธ์ตรงกับความต้องการจริงมากขึ้น เพราะลดการออกนอกทาง

### 2. “อย่าแก้เยอะเกินไป” นับเป็นข้อจำกัดแล้ว

ถ้อยคำแบบนี้คลุมเครือเกินไป

สิ่งที่มีประโยชน์กว่าคือ:

- แก้เฉพาะ `src/content/docs/...`
- ห้ามแก้คอมโพเนนต์
- ห้ามแก้อินเทอร์เฟซ
- ห้ามติดตั้ง dependency

### 3. ต้องมีข้อจำกัดเฉพาะงานความเสี่ยงสูง

งานเล็กก็ต้องมีเช่นกัน เพราะเรามักพูดคำขอคลุมเครือง่าย ๆ แล้วปล่อยให้ Codex ขยายขอบเขตเอง

## รูปแบบที่เพียงพอ

หากยังไม่รู้ว่าจะเขียนอย่างไร ให้เริ่มด้วยโครงนี้:

```text
ข้อจำกัด:
- แก้เฉพาะ【ไดเรกทอรี/ไฟล์】
- ห้ามแก้【คอมโพเนนต์ / API / ฐานข้อมูล / การตั้งค่า】
- ห้ามเพิ่ม dependency
- หากข้อมูลไม่พอ ให้ถามก่อน อย่าเดา
```

## เมื่อใดควรระบุข้อจำกัดให้ละเอียดขึ้น

ควรเขียนข้อจำกัดต่อไปนี้ให้ชัดในสถานการณ์เหล่านี้:

- โปรเจกต์เก่าที่มีภาระทางเทคนิคสะสมมาก
- คุณต้องการแก้เฉพาะจุด
- ทีมมีข้อกำหนดตายตัวด้านรูปแบบหรือสถาปัตยกรรม
- เกี่ยวข้องกับสิทธิ์ การเชื่อมต่ออินเทอร์เน็ต หรือการติดตั้ง dependency

เป้าหมายบอก Codex ว่าต้องทำอะไร ส่วนข้อจำกัดบอกว่าควรหยุดที่ใด

ควรเขียนขอบเขตสิทธิ์ร่วมกับข้อจำกัด เพื่อลดการดำเนินการเกินสิทธิ์แบบพ่วงไปด้วย ดู [กำหนดเกณฑ์ว่าเสร็จ](/th/prompts/define-done/) และ [สิทธิ์และ sandbox](/th/guide/permissions-and-sandbox/)
