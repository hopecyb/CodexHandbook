เมื่อมอบหมายงาน หลายคนบอกว่า “ต้องการอะไร” แต่ไม่ได้อธิบายว่า “ทำถึงระดับใดจึงถือว่าเสร็จ” สุดท้ายจึงต้องใช้ความรู้สึกตัดสินว่างานเสร็จหรือยัง

เกณฑ์ว่าเสร็จก็คือวิธีที่คุณจะใช้ตรวจผลลัพธ์

เกณฑ์การยอมรับต้อง **สังเกตได้**:

- ไม่ดี: “คุณภาพโค้ดดีขึ้น”
- ดี: “`npm test` ผ่าน คอมโพเนนต์ `Button` รองรับ `disabled` และภาพหน้าจอ Storybook ตรงกับแบบ”

## ทำไมหลายงานจึงสรุปไม่ได้ว่าเสร็จจริงหรือยัง

หลายครั้งเป็นเพราะนำเป้าหมายกับเกณฑ์ว่าเสร็จมาปะปนกัน

- **เป้าหมาย**: ผลลัพธ์ที่คุณต้องการ
- **เกณฑ์ว่าเสร็จ**: วิธีที่คุณใช้ยืนยันว่าได้ผลลัพธ์นั้นจริง

ตัวอย่างเช่น “แก้ Bug นี้” คือเป้าหมาย  
ส่วน “ยืนยันการแก้ได้อย่างสม่ำเสมอ การทดสอบที่เกี่ยวข้องผ่าน และไม่มี error ใหม่ในคอนโซล” ใกล้เคียงกับเกณฑ์ว่าเสร็จมากกว่า

## ความเข้าใจผิดที่พบบ่อย

### 1. ผลลัพธ์ดูใกล้เคียงก็ถือว่าเสร็จ

เรื่องนี้สร้างปัญหาแฝงได้ง่ายที่สุดในงานเล็ก “ดูใกล้เคียง” มักทำให้พลาดการทดสอบ edge case และผลข้างเคียง

### 2. เกณฑ์ว่าเสร็จคือการเขียนคำชมผลลัพธ์เพิ่มอีกสองสามประโยค

เกณฑ์ว่าเสร็จต้องตรวจสอบได้ ไม่ใช่เขียนเหมือนคำกล่าวสรุป

### 3. บิลด์ผ่านเท่ากับเสร็จ

ไม่เสมอไป

โดยทั่วไปบิลด์ผ่านเป็นเพียงหนึ่งจุดตรวจ ไม่ได้หมายความว่า:

- ฟังก์ชันทำงานถูกต้องจริง
- ไม่เกินขอบเขต
- ข้อความเหมาะกับผู้อ่าน
- แหล่งข้อมูลได้รับการตรวจสอบ

## รูปแบบที่ใช้บ่อย

หากยังไม่รู้ว่าจะเขียนอย่างไร ให้เริ่มเลือกจากสามประเภทนี้:

- **ตรวจฟังก์ชัน**: พฤติกรรมของผลลัพธ์เป็นไปตามคาดหรือไม่
- **ตรวจทางเทคนิค**: build / test / lint ผ่านหรือไม่
- **ตรวจขอบเขต**: แก้เฉพาะขอบเขตที่ตกลงไว้หรือไม่

ตัวอย่าง:

```text
เกณฑ์การยอมรับ:
- แก้เฉพาะข้อความหน้าแรก docs โดยไม่แก้ layout และคอมโพเนนต์
- `pnpm build` ผ่าน
- ข้อความส่วนแรกเหมาะกับผู้เริ่มต้นมากขึ้น และไม่ตั้งสมมติฐานว่าผู้อ่านเข้าใจศัพท์อยู่แล้ว
```

## วิธีตัดสิน

หลังเขียนเสร็จ ให้ถามตัวเองว่า:

> **หากส่งให้คนอื่นตอนนี้ เขาสามารถใช้ข้อมูลนี้ตัดสินว่า “ผ่าน” หรือ “ไม่ผ่าน” ได้หรือไม่**

หากไม่ได้ แสดงว่ายังเขียนคลุมเครือเกินไป

สรุปคือ อย่าปล่อยให้คำถามว่า “เสร็จหรือยัง” ต้องอาศัยการเดา

เขียนคำสั่งตรวจสอบลงในเกณฑ์ เพื่อให้ Agent มีแนวโน้มจะรันเองมากขึ้น: [รันการทดสอบ](/th/guide/quality/)
