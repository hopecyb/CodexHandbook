ควรวางแผนก่อนหรือไม่ ขึ้นอยู่กับว่างานนั้นยังขาดการตัดสินใจอะไร การแก้ไขที่มีขอบเขตชัดเจนและย้อนกลับได้ง่ายสามารถลงมือทันที หากแนวทางยังไม่ชัดให้วางแผนก่อน และหากการกระทำหนึ่งต้องใช้อำนาจเพิ่มเติม ให้หยุดก่อนลงมือ การมีแผนไม่ได้หมายความว่าต้องรอคำตอบจากผู้ใช้ในทุกขั้น

## เริ่มจากจำแนกประเภทงาน

| ประเภท | เกณฑ์พิจารณา | สิ่งที่ควรระบุ | ควรหยุดเมื่อใด |
|---|---|---|---|
| ลงมือทันที | อินพุต ขอบเขต และเกณฑ์การยอมรับชัดเจน การแก้ไขย้อนกลับได้ | ระบุว่าจะแก้ที่ใด เงื่อนไขว่าเสร็จ และสิ่งที่ไม่รวม | พบสิ่งที่เกินขอบเขตหรือขาดข้อมูลจำเป็น |
| วางแผนก่อน | ต้องเลือกสถาปัตยกรรม ขอบเขตไม่ชัด หรือมีหลายขั้นที่กระทบกัน | ตรวจสภาพปัจจุบันก่อน แล้วระบุแนวทาง ผลกระทบ และวิธีตรวจสอบ | มีข้อแลกเปลี่ยนที่ผู้ใช้ต้องตัดสินใจ หรือผู้ใช้ขอตรวจแผนก่อนอย่างชัดเจน |
| การกระทำต้องอนุมัติ | กำลังจะสร้างผลกระทบภายนอกที่ยังไม่ได้รับอนุญาต หรือแตะข้อจำกัดด้านสิทธิ์การลงมือ | ทำสิ่งส่งมอบที่ตรวจทานได้ก่อน แล้วระบุการกระทำ เป้าหมาย และผลกระทบให้ชัด | ก่อนการกระทำนั้น โดยเก็บงานเตรียมการที่เสร็จแล้วไว้ |

“เกี่ยวข้องกับสามไฟล์” ไม่ใช่เกณฑ์อนุมัติสากล เพราะไฟล์ตั้งค่า production เพียงไฟล์เดียวก็อาจส่งผลมากได้ ดูป๊อปอัปของผลิตภัณฑ์และสิทธิ์การลงมือจริงได้ที่ [สิทธิ์และ sandbox](/th/guide/permissions-and-sandbox/) อย่าใช้ตารางนี้แทนการตั้งค่าสิทธิ์ของทุกไคลเอนต์

## เปรียบเทียบที่หนึ่ง: แก้ข้อความในเครื่อง

งาน: แก้คำผิดสองจุดใน README โดยไม่ปรับโครงสร้าง

**ตัวอย่างที่ไม่ดีเพราะหยุดมากเกินไป:**

```text
เขียนแผนก่อน แล้วรอให้ฉันอนุมัติจึงค่อยอ่านไฟล์
หลังอ่านเสร็จ ให้ระบุสองจุดที่จะเปลี่ยน แล้วรออนุมัติก่อนแก้
แก้แต่ละจุดแล้วหยุดถามฉัน จากนั้นถามอีกครั้งว่าจะตรวจสอบหรือไม่
```

การรอเหล่านี้ไม่ได้ช่วยให้ได้การตัดสินใจที่จำเป็นเพิ่มขึ้น แต่ทำให้งานที่ได้รับอนุญาตชัดเจนแล้วขาดตอน

**วิธีเขียนเมื่อขอบเขตชัดเจน:**

```text
เปลี่ยน “帐户” เป็น “账户” ให้เหมือนกันในสองจุดของเนื้อหา README.md เท่านั้น
คง code block ลิงก์ และเนื้อหาอื่นไว้ ทำให้เสร็จทันที ตรวจ diff และรายงานว่าแก้ที่ใด
หากจำนวนที่พบจริงไม่ใช่สองจุด ให้อธิบายความต่างก่อน อย่าขยายงานเป็นการขัดเกลาทั้งไฟล์
```

เกณฑ์การยอมรับคือแก้สองจุดได้ถูกต้องและเนื้อหาที่ไม่เกี่ยวข้องไม่เปลี่ยน งานลักษณะนี้มักไม่ต้องเพิ่มการทดสอบใหม่ เพียงตรวจสอบให้เหมาะสมตามกฎที่โปรเจกต์มีอยู่

## เปรียบเทียบที่สอง: แก้เว็บไซต์และเผยแพร่

งาน: อัปเดตบทช่วยสอนสามบทแล้วเผยแพร่ขึ้นเว็บไซต์ production กรณีนี้ต้องแยกการเตรียมเนื้อหาออกจากผลกระทบของการเผยแพร่

**ตัวอย่างที่ไม่ดีเพราะการอนุญาตไม่ชัด:**

```text
เขียนแผนก่อน แล้วแก้เว็บไซต์ทั้งหมดและนำขึ้นใช้งาน
```

ข้อความนี้ไม่ระบุว่าจะเปลี่ยนเนื้อหาใด เผยแพร่ไปที่ใด หรืออนุญาตให้แทนที่เวอร์ชันออนไลน์หรือไม่

**วิธีเขียนที่มีขอบเขตชัดเจน:**

```text
อัปเดตบทช่วยสอนสามบทนี้และแก้ลิงก์ภายในที่เกี่ยวข้อง อ่านสภาพปัจจุบันก่อนแล้วเสนอแผนสั้น ๆ
แก้ไข บิลด์ และตรวจพรีวิวอย่างต่อเนื่องภายในไฟล์เหล่านี้และส่วนการนำทางที่เกี่ยวข้อง โดยไม่ต้องรอทีละขั้น
ส่งมอบพรีวิว สรุปการเปลี่ยนแปลง และผลการตรวจสอบ แต่ยังไม่อนุญาตให้เผยแพร่ขึ้น production
เมื่อเตรียมเสร็จ ให้ระบุเวอร์ชันที่จะเผยแพร่ สภาพแวดล้อมเป้าหมาย และวิธีย้อนกลับ แล้วรอให้ฉันยืนยันการเผยแพร่
```

ในกรณีนี้ควรทำงานในเครื่องให้เสร็จก่อน แล้วจึงขออนุญาตเผยแพร่ขั้นสุดท้าย หากผู้ใช้อนุญาตเป้าหมายและการเผยแพร่ที่เจาะจงไว้ชัดเจนแล้ว ให้พิจารณาตามนโยบายปัจจุบันว่าสามารถทำต่อได้หรือไม่ อย่าขออนุญาตเดิมซ้ำเพียงเพราะเทมเพลตนี้มีข้อความให้ยืนยัน

ตัวอย่างเปรียบเทียบทั้งสองชุดเป็นการออกแบบเพื่อการสอน ไม่ใช่ผลลัพธ์จริงของโมเดลหรือการวัดประสิทธิภาพ

## เมื่อใดควรทำเฉพาะแผน

หากยังเปรียบเทียบแนวทาง ต้องตัดสินใจเรื่องงบประมาณ หรือต้องการตรวจแบบก่อนอย่างชัดเจน คุณสามารถจำกัดให้ทำเฉพาะแผนได้:

```text
รอบนี้ทำเฉพาะข้อเสนอ อ่าน implementation ปัจจุบัน แล้วให้สองทางเลือก ขอบเขตผลกระทบ และวิธีตรวจรับ
ชี้เฉพาะข้อแลกเปลี่ยนที่ฉันต้องตัดสินใจจริง ๆ โดยไม่แก้ implementation เมื่อเลือกแนวทางแล้วจึงค่อยลงมือ
```

ต้องปฏิบัติตามข้อจำกัดของระยะงานที่ระบุชัดนี้ ไม่ควรกระโดดไปลงมือเพียงเพราะโดยทั่วไป Agent ทำงานได้อย่างอิสระ

## แผนควรมีอะไร

แผนที่เพียงพอควรระบุเป้าหมาย ขอบเขตผลกระทบ ขั้นตอน การตรวจสอบ และข้อแลกเปลี่ยนที่ยังไม่คลี่คลาย คำตอบที่รู้อยู่แล้วไม่จำเป็นต้องเปลี่ยนเป็นคำถามรอยืนยัน และงานสั้นที่ไม่มีความเสี่ยงก็ไม่ต้องเพิ่มหัวข้อย้อนกลับเพียงเพื่อให้ครบเทมเพลต

หากพบสถานการณ์ใหม่ระหว่างลงมือ ให้แยกระหว่างรายละเอียด implementation ทั่วไปกับการเปลี่ยนเป้าหมาย ปัญหาเล็กที่แก้ได้ภายในขอบเขตเดิมให้จัดการต่อและอธิบายไว้ แต่หากต้องเพิ่ม dependency ขยายการแก้ไข เปลี่ยนอินเทอร์เฟซ หรือทำการกระทำภายนอกแบบใหม่ ให้ตรวจสอบก่อนว่ายังอยู่ในขอบเขตที่ได้รับอนุญาตหรือไม่

## กฎเริ่มต้นที่เขียนไว้ในข้อตกลงของโปรเจกต์ได้

```md
- งานที่มีขอบเขตชัดเจนและย้อนกลับได้ ให้ลงมือทันทีพร้อมตรวจสอบอย่างเหมาะสม
- งานซับซ้อนให้เขียนแผนสั้น ๆ ก่อน รอคำตอบเฉพาะเมื่อผู้ใช้ขอตรวจแผนก่อนหรือมีข้อแลกเปลี่ยนที่จำเป็น
- ทำงานต่อเนื่องภายในขอบเขตที่ได้รับอนุญาต โดยไม่ขอยืนยันซ้ำทีละขั้น
- เมื่อขาดข้อมูลสำคัญ เกินขอบเขตงาน หรือแตะการกระทำที่ยังไม่ได้รับอนุญาต ให้อธิบายปัญหาอย่างเจาะจง
- อย่าถือว่า “แก้ไขในเครื่องเสร็จแล้ว” เท่ากับได้รับอนุญาตให้เผยแพร่ ส่งข้อความ หรือลบข้อมูลโดยอัตโนมัติ
```
