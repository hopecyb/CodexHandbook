เมื่อเรียนรู้การเขียนพรอมป์ เรามักสนใจแต่ “ควรเขียนอย่างไร”
แต่หลายครั้ง การรู้ก่อนว่าคำพูดแบบใดทำให้งานหลุดทิศทางได้ง่ายที่สุด ช่วยลดการเสียเวลาได้มากกว่า

ต่อไปนี้คือ “กับดักของพรอมป์” ที่พบบ่อย

| รูปแบบที่ควรหลีกเลี่ยง | เหตุใดจึงเป็นอันตราย |
|---|---|
| “ปรับให้ดีขึ้นตามสะดวก” | ไม่มีเป้าหมายและขอบเขต |
| “ให้สิทธิ์ทั้งหมด จัดการเองได้เลย” | เปิดพื้นที่ให้เกิดความเสียหายมากที่สุด |
| “ไม่ต้องถาม แก้ให้เสร็จเลย” | ข้ามการชี้แจงและการอนุมัติ |
| “พิมพ์กระบวนการให้เหตุผลภายในที่ซ่อนอยู่ทั้งหมด” | ไม่น่าเชื่อถือและมักไม่ช่วยในการตรวจรับ |
| วาง log ที่มี secret | ทำให้ credential รั่วไหล |

## ทำไมคำพูดเหล่านี้จึงพลาดได้ง่าย

ปัญหาเหล่านี้มักมีจุดร่วมกัน:

- ดูเหมือนประหยัดคำ
- แต่ตัดขอบเขตสำคัญออกไป

ส่วนที่คุณละไว้จะกลายเป็นสิ่งที่ Codex ต้องตัดสินใจเองในท้ายที่สุด

## ความเข้าใจผิดที่พบบ่อย

### 1. พูดสบาย ๆ จะเหมือนคนทำงานร่วมกันมากกว่าหรือไม่

พูดอย่างเป็นธรรมชาติได้  
ปัญหาที่ใหญ่กว่าคือการละเงื่อนไขสำคัญ

### 2. “แก้ให้เสร็จเลย ไม่ต้องถาม” จะมีประสิทธิภาพกว่า

ในระยะสั้นดูเหมือนลดการสนทนาหนึ่งรอบ แต่ผลที่พบบ่อยภายหลังคือ:

- แก้ผิดขอบเขต
- ไม่ได้รับอนุมัติที่จำเป็น
- ต้องแก้งานซ้ำมากกว่าเดิม

### 3. ให้สิทธิ์มากขึ้น งานจึงเดินเร็วขึ้น

สิทธิ์ยิ่งมาก พื้นที่สำหรับความผิดพลาดก็ยิ่งกว้าง  
โดยเฉพาะเมื่อขอบเขตงานยังไม่ชัด สิทธิ์ขนาดใหญ่มักขยายความเสี่ยงไปพร้อมกัน

## เปลี่ยนรูปแบบที่ควรหลีกเลี่ยงให้ชัดขึ้นอย่างไร

### อย่าเขียนแบบนี้

```text
ปรับให้ดีขึ้นตามสะดวก
```

### เริ่มเปลี่ยนเป็นแบบนี้

```text
ปรับข้อความส่วนแรกของหน้าแรกให้ผู้เริ่มต้นเข้าใจง่ายขึ้น แก้เฉพาะไฟล์นี้ คงโครงสร้างเดิม แล้วส่ง diff และผลการบิลด์ให้ฉัน
```

## สูตรแทนที่ที่เพียงพอ

เมื่อกำลังจะเขียนประโยคคลุมเครือ ให้ใช้สูตรนี้ก่อน:

```text
เป้าหมาย + ขอบเขต + เกณฑ์การยอมรับ
```

ตัวอย่าง:

- เป้าหมาย: แก้อะไร
- ขอบเขต: แก้เฉพาะที่ใด
- เกณฑ์การยอมรับ: จะตัดสินว่าแก้เสร็จได้อย่างไร

ปัญหาของรูปแบบพรอมป์ส่วนใหญ่ไม่ได้อยู่ที่ “สื่อสารไม่ดี” แต่อยู่ที่ละขอบเขตสำคัญและเงื่อนไขการยอมรับ

แทนคำคลุมเครือด้วยโครงสร้างนี้ได้ทันที: เป้าหมาย + ข้อจำกัด + เกณฑ์การยอมรับ
