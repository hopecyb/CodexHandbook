เมื่อข้อกำหนดมีข้อมูลมาก มักเขียนออกมากระจัดกระจาย แม้มีข้อมูลจำนวนมาก แต่ผลลัพธ์ ขอบเขต และเกณฑ์การยอมรับกลับปะปนกัน ทำให้ Codex ต้องเติมช่องว่างเอง

หน้านี้มีใบงานที่นำไปใช้ซ้ำได้ทันที คุณจะเห็นว่าแต่ละส่วนแก้ปัญหาอะไร และคำอธิบายงานเชื่อมเข้าสู่วงจร “สำรวจ วางแผน ลงมือ ตรวจสอบ” อย่างไร

## เหมาะกับใคร

- ผู้อ่านที่เปิดใช้ Codex ได้แล้ว แต่มักพบปัญหา “แก้มากเกินไป” “ทำไม่เสร็จ” หรือ “ตัดสินผลลัพธ์ไม่ได้”
- นักพัฒนา ครีเอเตอร์ และทีมที่ต้องการส่งต่อข้อกำหนดจากการพูดให้ Agent ลงมือ
- ผู้ที่ต้องกำหนดขอบเขต สิทธิ์ และเงื่อนไขให้หยุดสำหรับงานระยะยาว

## โครงสร้างงาน

คุณสามารถจัดลำดับได้ดังนี้:

- ต้องการผลลัพธ์อะไร
- ทำไปทำไม
- ต้องใช้ข้อมูลหรือวัสดุใด
- ขอบเขตอยู่ที่ใด
- จะตัดสินว่าเสร็จได้อย่างไร

ลำดับไม่จำเป็นต้องตายตัว แต่เมื่ออธิบายเรื่องเหล่านี้ชัด งานจะมีเสถียรภาพขึ้นมาก

## เทมเพลตที่แนะนำ

```text
เป้าหมาย: …… (สิ่งส่งมอบสุดท้ายคืออะไร)
บริบท: …… (เหตุใดจึงสำคัญ สภาพปัจจุบันเป็นอย่างไร)
อินพุต: …… (ไฟล์/ลิงก์/เนื้อหาที่วางให้)
ข้อจำกัด: …… (ขอบเขตที่แก้ได้ รูปแบบ สิ่งต้องห้าม)
เกณฑ์การยอมรับ: …… (เงื่อนไขว่าเสร็จที่ตรวจสอบได้)
ขอบเขตสิทธิ์: …… (เชื่อมต่ออินเทอร์เน็ต ติดตั้ง dependency หรือแก้การตั้งค่าได้หรือไม่)
เมื่อข้อมูลไม่พอ: ให้ถามก่อน อย่าเดา
```

![วงจรจากคำอธิบายงานไปสู่ผลลัพธ์ที่ตรวจสอบได้](/illustrations/flow-task-loop.webp)

หกรายการทางซ้ายของภาพไม่ได้มีไว้ทำให้พรอมป์ยาวขึ้น แต่มีไว้ลดช่องว่างสำคัญ เมื่องานเข้าสู่ขั้นลงมือ หลักฐานจากการตรวจสอบจะกำหนดขั้นถัดไป: ผ่านแล้วจึงส่งมอบ หากไม่ผ่าน ให้กลับไปที่คำอธิบายงานหรือแผนพร้อมข้อมูลความล้มเหลว แทนที่จะแก้ต่อแบบไร้ทิศทาง

## หน้าที่ของแต่ละส่วน

- **เป้าหมาย**: ป้องกันไม่ให้งานมีเพียงการกระทำแต่ไม่มีผลลัพธ์
- **บริบท**: ช่วยให้ Codex เข้าใจว่าทำไมจึงต้องทำเช่นนั้น
- **อินพุต**: ส่งไฟล์ ลิงก์ และวัสดุที่ต้องดูจริง ๆ ให้พร้อมใช้งาน
- **ข้อจำกัด**: ป้องกันการล้ำขอบเขตและการแก้ส่วนอื่นพ่วงไปด้วย
- **เกณฑ์การยอมรับ**: ทำให้คำถามว่า “เสร็จหรือยัง” ตรวจสอบได้
- **ขอบเขตสิทธิ์**: ระบุล่วงหน้าว่าเชื่อมต่ออินเทอร์เน็ต ติดตั้ง dependency หรือแก้การตั้งค่าได้หรือไม่

## ความเข้าใจผิดที่พบบ่อย

### 1. ต้องเขียนทุกส่วนให้เต็ม

เทมเพลตนี้คล้ายรายการตรวจสอบมากกว่าแบบเติมคำ  
งานบางอย่างไม่ต้องมีบริบทยาว แต่เมื่อตัดออกก็จะมีข้อมูลประกอบการตัดสินใจน้อยลง

### 2. เป้าหมายกับเกณฑ์การยอมรับไม่ใช่เรื่องเดียวกัน

ทั้งสองอย่างไม่เหมือนกัน

- **เป้าหมาย** บอกว่าคุณต้องการผลลัพธ์อะไร
- **เกณฑ์การยอมรับ** บอกว่าคุณจะตัดสินได้อย่างไรว่าทำสำเร็จจริง

### 3. อินพุตคือการวางข้อมูลทั้งหมดลงไป

อินพุตไม่ใช่ยิ่งมากยิ่งดี ความเกี่ยวข้องสำคัญกว่า  
หัวใจคือระบุ “ข้อมูลที่จำเป็นต้องดู” ให้ชัดเจน

## เทมเพลตงานขั้นต่ำ

หากต้องการเริ่มจากเวอร์ชันที่ใช้ได้ ให้ย่อเป็นดังนี้:

```text
เป้าหมาย: ทำอะไรให้อยู่ในสภาพใด
อินพุต: ไฟล์หรือหน้าที่เกี่ยวข้องอยู่ที่นี่
ข้อจำกัด: แก้ได้เฉพาะที่ใด และห้ามแตะอะไร
เกณฑ์การยอมรับ: ฉันจะตรวจได้อย่างไรว่าทำเสร็จจริง
เมื่อไม่แน่ใจ: ให้ถามก่อน
```

## จากคำขอคลุมเครือสู่งานที่ลงมือได้

### คำขอเดิม

```text
ช่วยปรับหน้าแรกของเอกสารให้ดีขึ้นหน่อย
```

ประโยคนี้ไม่ได้ระบุกลุ่มผู้อ่าน ขอบเขตที่แก้ได้ หรือว่า “ดีขึ้น” หมายถึงอะไร ต่อให้ Codex สร้างเนื้อหาออกมา คุณก็ยากจะตัดสินว่าเกินขอบเขตหรือไม่

### เวอร์ชันที่ลงมือได้

```text
เป้าหมาย: เขียนข้อความส่วนแรกของหน้าแรกเอกสารใหม่ เพื่อให้ผู้ที่เพิ่งรู้จัก Codex เข้าใจภายใน 30 วินาทีว่านี่คืออะไรและควรเริ่มจากที่ใด
บริบท: หน้าแรกปัจจุบันตั้งสมมติฐานว่าผู้อ่านเข้าใจ Agent บริบท และ Skill อยู่แล้ว คำอธิบายทางเข้าจึงไม่ตรงไปตรงมา
อินพุต: src/content/docs/guide/index.md
ข้อจำกัด: แก้เฉพาะไฟล์นี้ ห้ามแก้การนำทาง สไตล์ และคอมโพเนนต์ เมื่อกล่าวถึง Agent ครั้งแรก ให้เพิ่มคำอธิบายภาษาง่ายหนึ่งประโยค
เกณฑ์การยอมรับ:
- ส่วนแรกอธิบายวัตถุประสงค์ของคู่มือ กลุ่มผู้อ่าน และจุดเริ่มอ่านอย่างชัดเจน
- คง frontmatter และลำดับชั้นหัวข้อเดิม
- ไม่เพิ่มศัพท์เฉพาะที่ไม่มีคำอธิบาย
- pnpm build ผ่าน
ขอบเขตสิทธิ์: อนุญาตให้อ่านหน้าที่เกี่ยวข้องภายในเว็บไซต์ ห้ามเชื่อมต่ออินเทอร์เน็ต ติดตั้ง dependency หรือสร้าง Git commit
เมื่อข้อมูลไม่พอ: ให้ระบุข้อมูลที่ขาดและขอบเขตที่ตั้งใจแก้ก่อน แล้วรอให้ฉันยืนยัน
```

### กระบวนการทำงานที่คาดหวัง

1. อ่านหน้าแรกและหน้าทางเข้าที่อยู่ติดกันก่อน แล้วอธิบายปัญหาปัจจุบัน
2. เสนอแผนสั้น ๆ ที่เกี่ยวข้องกับไฟล์เดียว
3. แก้ข้อความและแสดงสรุป diff
4. รัน `pnpm build`
5. รายงานหลักฐานเทียบกับเกณฑ์การยอมรับทั้งสี่ข้อทีละข้อ

## วิธีตรวจคำอธิบายงานของตนเอง

ก่อนส่ง ให้ถามตัวเองว่า:

- เป้าหมายอธิบายผลลัพธ์ หรือมีเพียงคำกริยาอย่าง “ปรับปรุง จัดการ ดูให้หน่อย”
- อินพุตมีเฉพาะไฟล์และข้อมูลที่เกี่ยวข้องจริงหรือไม่
- ข้อจำกัดระบุสิ่งที่ห้ามแตะหรือไม่
- คนอื่นสามารถใช้เกณฑ์การยอมรับเพื่อตัดสิน “ผ่าน / ไม่ผ่าน” ได้หรือไม่
- ต้องอนุญาตการเชื่อมต่ออินเทอร์เน็ต การติดตั้ง dependency การเขียนข้อมูลภายนอก และการ commit โค้ดล่วงหน้าหรือไม่
- เมื่อข้อมูลไม่พอ Agent ควรถามก่อน ตรวจสอบก่อน หรือหยุด

คุณย่อเทมเพลตตามขนาดงานได้ แต่การตัดแต่ละส่วนออกหมายถึงมีข้อมูลประกอบการตัดสินใจน้อยลงหนึ่งประเภท การแก้ typo ในไฟล์เดียวไม่ต้องมีบริบทยาว แต่การย้ายข้ามโมดูลไม่ควรมีเพียงเป้าหมายหนึ่งประโยค
