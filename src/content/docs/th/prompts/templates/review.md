งานตรวจทานมักหลุดทิศทางตรงที่กลายเป็น “แก้ให้พ่วงไปด้วย” ตั้งแต่ต้น

การหาปัญหาก่อน แล้วค่อยตัดสินใจว่าจะแก้หรือไม่ จะปลอดภัยกว่า

## เทมเพลต

```text
โปรดตรวจ diff ปัจจุบันเทียบกับ【main/branch เป้าหมาย】โดยยังไม่แก้โค้ด
มิติการตรวจ:
1. เกินขอบเขต【issue/ข้อกำหนด】หรือไม่
2. ข้อผิดพลาดด้าน logic, edge case และ error handling
3. ความปลอดภัย (secret, injection, สิทธิ์)
4. การทดสอบและเอกสารสอดคล้องกับการเปลี่ยนแปลงหรือไม่
ส่งรายการแบบแบ่งระดับ: 🔴 บล็อก / 🟡 แนะนำ / 🟢 ผ่าน โดยแต่ละรายการระบุไฟล์และหมายเลขบรรทัด
```

## เมื่อใดควรใช้เทมเพลตนี้

- รีวิว PR
- รีวิว diff
- ตรวจความเสี่ยงของการเปลี่ยนแปลงเอกสารหรือการตั้งค่าหนึ่งรอบ

## ความเข้าใจผิดที่พบบ่อย

### 1. การตรวจทานคือให้แสดงความคิดเห็นเล็กน้อย

พูดให้แม่นกว่าคือ ให้ค้นหาปัญหาตามโครงสร้าง

### 2. ไม่มี Bug ชัดเจนเท่ากับผ่าน

การตรวจทานควรดูด้วยว่า:

- เกินขอบเขตหรือไม่
- การทดสอบและเอกสารตามทันหรือไม่
- มีปัญหาด้านความปลอดภัยและขอบเขตหรือไม่

หัวใจของเทมเพลตตรวจทานคือเปิดเผยความเสี่ยงตามมิติคงที่ ไม่ใช่ประเมินกว้าง ๆ ว่า “ดีหรือไม่ดี”
