ความเข้าใจผิดที่พบบ่อยในงานวินิจฉัยคือ แม้จะพูดว่า “ตรวจสอบก่อน” แต่จริง ๆ กลับคาดให้แก้ทันที

หัวใจของเทมเพลตวินิจฉัยคือแยก “หาสาเหตุ” ออกจาก “ลงมือแก้”

## เทมเพลต

```text
อาการ: 【ข้อความ error การทดสอบที่ล้มเหลว รายงานจากผู้ใช้】
บริบท: 【การเปลี่ยนแปลงล่าสุด สภาพแวดล้อม ขั้นตอนทำซ้ำ】
อินพุต: @【log/การทดสอบ/โค้ดที่เกี่ยวข้อง】
ข้อจำกัด: ยังไม่แก้โค้ด ระบุสาเหตุรากที่เป็นไปได้ 2–3 ข้อพร้อมวิธีตรวจสอบ
ผลลัพธ์:
1. สาเหตุรากที่เป็นไปได้มากที่สุด (พร้อมหลักฐาน)
2. ขั้นตอนตรวจสอบที่ลงมือได้ (คำสั่งหรือจุดตรวจ)
3. หากตรวจสอบผ่าน ให้ร่างแผนแก้ไข (รอฉันยืนยันก่อนลงมือ)
```

## เมื่อใดควรใช้เทมเพลตนี้

- ยังหาตำแหน่ง Bug ไม่ได้
- การทดสอบแดง แต่ไม่รู้ว่าชั้นใดเสีย
- คุณสงสัยว่าปัญหาซับซ้อนและไม่ต้องการให้เดาวิธีแก้ทันที

## ความเข้าใจผิดที่พบบ่อย

### 1. วินิจฉัยช้า แก้ทันทีดีกว่า

งานที่ต้องกลับมาแก้ซ้ำจำนวนมากเกิดจากการข้ามขั้นวินิจฉัย

### 2. ระบุสาเหตุรากที่เป็นไปได้ 2–3 ข้อจะเยิ่นเย้อเกินไปหรือไม่

ไม่ วิธีนี้ช่วยให้เห็นว่า Agent กำลังเดาสุ่มหรือไม่

เทมเพลตวินิจฉัยให้ Agent อธิบายก่อนว่าทำไมจึงเสีย แล้วค่อยคุยว่าจะซ่อมอย่างไร
