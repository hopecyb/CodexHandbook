เมื่อเห็นคำว่า “เทมเพลต” มักมีปฏิกิริยาสองแบบ:

- รู้สึกว่าเทมเพลตตายตัวเกินไป จึงไม่อยากใช้
- คัดลอกทั้งหมดทันที โดยไม่แยกว่าส่วนใดต้องแก้

หน้าที่หลักของเทมเพลตคือช่วยไม่ให้คุณลืมส่วนสำคัญ ไม่ได้คิดแทนคุณ

เป้าหมายของหน้าเทมเพลตคือรักษาโครงสร้างงาน ไม่ใช่สร้างคำตอบที่ถูกต้องเพียงหนึ่งเดียว

## วิธีใช้เทมเพลต

ใช้ได้ตามขั้นตอนนี้:

1. เลือกประเภทเทมเพลตที่ใกล้เคียงกับงานที่สุด
2. แทนเนื้อหาตัวยึด `【】` ด้วยงานจริงของคุณ
3. ลบส่วนที่ไม่เกี่ยวข้อง
4. เพิ่มข้อจำกัดและเกณฑ์การยอมรับเฉพาะของงานครั้งนี้

เทมเพลตคล้ายโครงนั่งร้าน ไม่ใช่คำตอบมาตรฐาน

| เทมเพลต | สถานการณ์ที่เหมาะสม |
|---|---|
| [ทำความเข้าใจ](/th/prompts/templates/understand/) | อ่าน codebase เอกสาร หรือข้อมูล เพื่อสร้างความเข้าใจก่อน |
| [สร้าง](/th/prompts/templates/create/) | สร้างฟังก์ชัน เนื้อหา หรือสิ่งส่งมอบจากศูนย์ |
| [แก้ไข](/th/prompts/templates/change/) | ปรับปรุงสิ่งที่มีอยู่โดยมีขอบเขต |
| [วินิจฉัย](/th/prompts/templates/diagnose/) | หาสาเหตุรากของปัญหา โดยยังไม่แก้โค้ด |
| [ตรวจทาน](/th/prompts/templates/review/) | ตรวจ diff, PR หรือการเปลี่ยนแปลงเอกสาร |
| [วิจัย](/th/prompts/templates/research/) | ค้นคว้าและเปรียบเทียบพร้อมแหล่งอ้างอิง |
| [ทำงานอัตโนมัติ](/th/prompts/templates/automate/) | งานซ้ำ สคริปต์ และขั้นตอนที่ทำงานโดยไม่มีผู้ดูแล |

## ยกระดับจากเทมเพลตเป็น workflow

พรอมป์บางอย่างใช้ครั้งเดียวก็พอ ส่วนบางอย่างเกิดซ้ำและควรพัฒนาต่อ

| งานที่เกิดซ้ำ | เริ่มทำเป็น | เมื่อเสถียรแล้ว ยกระดับเป็น |
|---|---|---|
| เตรียม PR | เทมเพลตตรวจทาน/แก้ไข | Skill ที่ให้รายการตรวจสอบตายตัว |
| สร้างเอกสาร API | เทมเพลตสร้าง/แก้ไข | Skill + สคริปต์เอกสาร |
| เพิ่ม test coverage | เทมเพลตแก้ไข | Skill + ข้อตกลงคำสั่งทดสอบ |
| ตรวจหาปัญหาประสิทธิภาพ | เทมเพลตวินิจฉัย | Agent ย่อยหรือ Skill เฉพาะทาง |
| ตรวจรูปแบบทุกครั้งที่เขียนไฟล์ | ไม่เหมาะที่จะพึ่งเทมเพลตอย่างเดียว | Hook |
| อ่าน ticket ภายนอกแล้วแก้โค้ด | เทมเพลตวิจัย | MCP + Skill |

เทมเพลตเหมาะกับ “มนุษย์เป็นผู้เริ่มงาน” Skill เหมาะกับ “ทำงานประเภทเดียวกันซ้ำตามขั้นตอนคงที่” Hook เหมาะกับ “ต้องตรวจอัตโนมัติเมื่อถึงจุดหนึ่ง” และ MCP เหมาะกับ “ต้องเชื่อมระบบภายนอก”

## ตัดสินอย่างรวดเร็ว: งานนี้ควรเขียนเป็นอะไร

เริ่มจากถามสี่ข้อ:

1. งานนี้ทำเพียงครั้งเดียวหรือไม่
2. หากทำอีกครั้ง ขั้นตอนจะเหมือนเดิมเป็นส่วนใหญ่หรือไม่
3. ผลลัพธ์มีรายการตรวจสอบหรือรูปแบบตายตัวหรือไม่
4. ต้องใช้ระบบภายนอก สคริปต์ หรือการดักตรวจอัตโนมัติหรือไม่

| ผลการพิจารณา | รูปแบบที่แนะนำ |
|---|---|
| ทำครั้งเดียวและยังต้องอภิปราย | เขียนพรอมป์ฉบับเต็มโดยตรง |
| ทำซ้ำบ่อยแต่ยังปรับอยู่ | ทำเป็นเทมเพลต |
| workflow เสถียรและรูปแบบผลลัพธ์ตายตัว | ทำเป็น Skill |
| ต้องการอีกบทบาทอิสระเพื่อเจาะลึก | แยกให้ Agent ย่อย |
| ต้องอ่านระบบภายนอก | เชื่อม MCP และให้สิทธิ์อ่านอย่างเดียวก่อน |
| ต้องตรวจทุกครั้งเมื่อถึงจุดหนึ่ง | ทำเป็น Hook |
| ต้องแจกให้ทีมใช้แบบเดียวกัน | แพ็กเป็น Plugin |

พรอมป์ไม่ได้ยิ่งยาวยิ่งดี สิ่งที่ควรนำกลับมาใช้จริงคืองานที่คุณตรวจสอบซ้ำแล้ว มีขอบเขตชัด และมีเกณฑ์การยอมรับชัดเจน

## ความเข้าใจผิดที่พบบ่อย

### 1. เทมเพลตมีไว้คัดลอกตามเดิม

หากไม่เปลี่ยนตัวยึดและไม่ลบส่วนที่ไม่เกี่ยวข้อง เทมเพลตจะทำให้งานว่างเปล่าเสียเอง

### 2. แค่ใช้เทมเพลต พรอมป์ก็เป็นมืออาชีพโดยอัตโนมัติ

เทมเพลตช่วยรักษาโครงสร้างได้เท่านั้น ไม่สามารถตัดสินใจแทนคุณว่า:

- เป้าหมายจริงคืออะไร
- ควรกำหนดข้อจำกัดไว้ที่ใด
- ควรเขียนเกณฑ์การยอมรับอย่างไร

### 3. เทมเพลตยิ่งครบยิ่งดี

สำหรับผู้เริ่มต้น เทมเพลตควร “เพียงพอแต่ไม่เทอะทะ”

เลือกประเภทเทมเพลตให้ถูกก่อน แล้วปรับเป็นงานของคุณ อย่าใช้ตัวเทมเพลตเป็นงานโดยตรง
