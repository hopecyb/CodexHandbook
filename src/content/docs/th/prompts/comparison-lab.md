คุณค่าของการเปรียบเทียบคือการค้นหาว่าข้อกำหนดใดส่งผลต่อสิ่งส่งมอบ ไม่ใช่พิสูจน์ว่าพรอมป์ยิ่งยาวยิ่งดี หน้านี้มีอินพุตคงที่สามชุดและบันทึกการรันจริง 12 ครั้งซึ่งเสร็จเมื่อวันที่ 18 กันยายน 2026 ตัวอย่างชุดนี้แสดงความแตกต่างด้านหลักฐานการส่งมอบเป็นหลัก และยังไม่เพียงพอที่จะพิสูจน์ผลทั่วไป

## งานสามชุด วิธีเปรียบเทียบเดียวกัน

A/B ในแต่ละชุดใช้อินพุตเดียวกันและขอบเขตเครื่องมือเท่ากัน B คงงานทั้งหมดของ A ไว้ แล้วเพิ่มข้อกำหนดการยอมรับที่ชัดเจนหนึ่งชุด จึงไม่ควรสรุปว่าผลลัพธ์เกิดจากคำหรือประโยคใดเพียงอย่างเดียว

| งาน | อินพุตคงที่ | ข้อกำหนดที่เพิ่มใน B | สิ่งที่สังเกตเป็นหลัก |
|---|---|---|---|
| รายงานยอดขายประจำสัปดาห์ | CSV สังเคราะห์ 46 แถวและพจนานุกรมข้อมูล | ตัดสินทีละแถว อธิบายความผิดปกติ และมีบันทึกตรวจสอบแยก | นอกจากตัวเลขถูกต้องแล้ว ย้อนตรวจ refund รายการซ้ำ และฐานเป็นศูนย์ได้หรือไม่ |
| บทความอ้างอิงแหล่งข้อมูล | ข้อมูลสังเคราะห์สามชุดที่ตั้งใจให้ขัดแย้งกัน | ตารางข้อเท็จจริง รายการเรื่องค้าง และไม่เลือกข้างเองเมื่อข้อมูลขัดแย้ง | คงสิ่งที่ยังไม่ทราบไว้หรือไม่ และแหล่งข้อมูลรองรับข้อความเฉพาะหรือไม่ |
| การแก้ Bug | implementation ตะกร้าสินค้าและการทดสอบเดิม | การทดสอบเดิมแดงก่อนแก้ เขียวหลังแก้ พร้อม log และความแตกต่าง | ตรวจสอบจริงหรือไม่ และไม่ได้แก้การทดสอบเพื่อหลบข้อผิดพลาด |

[รายงานประจำสัปดาห์ A](/downloads/prompt-comparisons/cases/sales/A.md) / [B](/downloads/prompt-comparisons/cases/sales/B.md) · [บทความ A](/downloads/prompt-comparisons/cases/article/A.md) / [B](/downloads/prompt-comparisons/cases/article/B.md) · [Bug A](/downloads/prompt-comparisons/cases/bug/A.md) / [B](/downloads/prompt-comparisons/cases/bug/B.md)

A อาจตรวจข้อมูลและรันการทดสอบเอง ส่วน B ก็อาจล้มเหลวได้ อย่าถือสิ่งที่คาดไว้เป็นผลลัพธ์

## มิติการให้คะแนนร่วมกันห้าด้าน

A/B ใช้ [rubric.json](/downloads/prompt-comparisons/rubric.json) เดียวกัน ได้แก่ ความถูกต้องของงาน การย้อนตรวจหลักฐาน การควบคุมขอบเขต การจัดการความไม่แน่นอน และการทำซ้ำได้ แต่ละด้านให้ 0 เมื่อไม่ผ่าน 1 เมื่อผ่านบางส่วน และ 2 เมื่อผ่านพร้อมย้อนตรวจได้ หากไม่ได้รันหรือตัดสินไม่ได้ให้ใช้ null

คะแนนต้องเชื่อมโยงกับหลักฐานที่เจาะจง รายงานประจำสัปดาห์ไม่ควรได้คะแนนสูงเพียงเพราะเขียนลื่นไหล บทความไม่ควรถือว่าข้อเท็จจริงถูกต้องเพียงเพราะมีลิงก์ และโค้ดไม่ควรถือว่าตรวจสอบแล้วเพียงเพราะอ้างว่า “การทดสอบผ่าน” อย่าใช้คะแนนเฉลี่ยเดียวกลบข้อผิดพลาดสำคัญด้านข้อเท็จจริง

## การรันจริง 12 ครั้งในครั้งนี้

[ดาวน์โหลดผลลัพธ์และ log](/downloads/prompt-comparison-results/prompt-comparison-results-1.0.0.zip) · [คะแนนรายข้อและเวลาที่ใช้](/downloads/prompt-comparison-results/review.md) · [เงื่อนไขการเก็บตัวอย่าง](/downloads/prompt-comparison-results/README.md)

แต่ละชุดรันตามลำดับ A1 → B1 → B2 → A2 โดยในแต่ละรอบรันงานต่างกันสามงานพร้อมกัน แต่ละครั้งสร้างบริบท Agent และไดเรกทอรีทำงานใหม่ ไม่ให้คำตอบสำหรับการให้คะแนน ไม่มีการ override โมเดลและการตั้งค่า reasoning อย่างชัดเจน จึงไม่ทราบป้ายกำกับที่ใช้จริง การแยกไดเรกทอรีอาศัยข้อจำกัดในคำสั่ง ไม่ใช่การแยกระดับระบบปฏิบัติการ Main Agent ตรวจทานแบบไม่ปกปิดป้ายกำกับ และไม่มีผู้ให้คะแนนอิสระที่เป็นมนุษย์

| งาน | สิ่งที่สังเกตจาก A สองครั้ง | สิ่งที่สังเกตจาก B สองครั้ง | ครั้งนี้บอกอะไรได้ |
|---|---|---|---|
| รายงานยอดขายประจำสัปดาห์ | ตัวเลข บัญชีรายการ และการจัดการความผิดปกติถูกต้อง พร้อมตรวจทานเอง | ตัวเลขถูกต้องและมีคำอธิบายการตรวจเพิ่ม แต่ครั้งหนึ่งไม่ได้เก็บคำสั่งคำนวณทั้งหมด | ข้อกำหนดที่เพิ่มไม่รับประกันว่า log จะครบ |
| บทความอ้างอิงแหล่งข้อมูล | ข้อเท็จจริง แหล่งข้อมูล และความขัดแย้งถูกต้อง พร้อมส่งเนื้อหาบทความ | คงขอบเขตข้อเท็จจริงเช่นกัน และส่งตารางข้อเท็จจริงกับรายการเรื่องค้างเพิ่ม | มีวัสดุสำหรับใช้ตรวจทานเพิ่มขึ้น |
| การแก้ Bug | ไม่แก้การทดสอบเดิม และหลังแก้ผ่าน 3 รายการ แต่ไม่ได้เก็บ log ความล้มเหลวก่อนแก้ | เก็บทั้งการทดสอบเดิมที่ล้มเหลวและผลสำเร็จหลังแก้ พร้อม exit code และความแตกต่าง | สายโซ่การตรวจสอบครบขึ้น แต่ทั้งสี่ครั้งไม่ได้บันทึกเวอร์ชัน Node ของรอบนั้น |

ตารางฉบับเต็มแสดงคะแนนห้าด้านตั้งแต่ 0–2 แยกกัน โดยไม่คำนวณอันดับรวม บทความ A ไม่มีตารางข้อเท็จจริงจึงกระทบเกณฑ์ “ทำซ้ำได้” ที่กำหนดไว้ แต่ไม่ได้หมายความว่าเนื้อหาบทความผิด ส่วน Bug A/B ได้คะแนนทำซ้ำได้เพียงบางส่วนเท่ากันแต่ด้วยเหตุผลต่างกัน จึงดูเฉพาะคะแนนไม่ได้

แฮชของอินพุตและข้อความงานทั้งหมดคงเดิม การตรวจทานภายหลังคำนวณ CSV ยอดขายใหม่ และใช้การทดสอบเดิมที่ไม่ถูกแก้ตรวจการแก้ Bug ทั้งสี่ชุด [บันทึกการตรวจทาน](/downloads/prompt-comparison-results/reviewer-checks.json) ถูกเก็บแยกจาก log ที่ Agent ในการทดลองรันเอง

## ต้องเก็บความล้มเหลวและข้อจำกัดไว้ด้วย

- พรอมป์ร่วมของงานยอดขายระบุพจนานุกรมเป็น `data-dictionary.md` แต่ไฟล์จริงอยู่ที่ `input/data-dictionary.md` ทั้งสี่ครั้งพบ path error ก่อนแล้วจึงกู้คืนได้ นี่เป็นข้อบกพร่องของวัสดุ ไม่ควรโยงกับข้อกำหนดการยอมรับของ A/B เพื่อคงอินพุตที่ freeze ไว้ จึงไม่ได้แก้พรอมป์ระหว่างชุดนี้
- คำสั่ง Python ของ `run-07` มีเพียงสรุปและไม่ได้เก็บโค้ดทั้งหมด แพ็กเกจผลลัพธ์คงช่องว่างนี้ตามจริง ไม่ได้เติมย้อนหลังว่า “มีบันทึกครบในตอนนั้น”
- log ถูกจัดเรียงโดย Agent เอง ไม่ใช่การ export audit จากแพลตฟอร์มแบบครบถ้วน สำเนาสาธารณะแทนที่เฉพาะ absolute path ในเครื่อง และเก็บแฮชของไฟล์ต้นฉบับกับไฟล์สาธารณะแยกกัน
- เวลาที่ใช้รวมการรอเครื่องมือและการบันทึก log และงานถูกรันพร้อมกัน ไม่มี baseline จากมนุษย์หรือการวัดค่าใช้จ่าย ไม่ทราบป้ายกำกับโมเดลและการตั้งค่า reasoning จึงใช้จัดอันดับความเร็วของโมเดลหรือเวลาที่ประหยัดไม่ได้

แต่ละตัวแปรของแต่ละงานรันเพียงสองครั้ง การให้คะแนนไม่ปกปิดป้ายกำกับ และข้อกำหนดการให้คะแนนบางส่วนซ้ำกับสิ่งที่ B ย้ำเตือน หน้านี้แสดงความแตกต่างของสิ่งส่งมอบและหลักฐานการตรวจสอบ โดยไม่เผยแพร่อัตราความสำเร็จทั่วไป และไม่อ้างว่า “B ชนะ” หรือ “ยิ่งยาวยิ่งดี”

## รันและบันทึกด้วยตนเอง

1. สร้างไดเรกทอรีทำงานแยกสำหรับ A/B คัดลอกอินพุตเดียวกันและตรวจแฮช โดยไม่ให้คำตอบอ้างอิงสำหรับการให้คะแนนแก่โมเดล
2. ใช้งานใหม่ทั้งหมด กำหนดโมเดล การตั้งค่า reasoning ไคลเอนต์ ขอบเขตเครื่องมือ และเวลาสูงสุดให้คงที่ บันทึกการตั้งค่าที่ไม่ทราบตามจริง การรันสองครั้งต้องไม่แชร์ผลจากครั้งก่อน
3. กำหนดจำนวนครั้งและเงื่อนไขหยุดล่วงหน้า สลับลำดับ A→B กับ B→A เก็บความล้มเหลว การหยุดชะงัก และการลองใหม่ ไม่ใช่เก็บเฉพาะผลลัพธ์ที่ดีที่สุด
4. บันทึก path ผลลัพธ์จริง ป้ายกำกับโมเดล สภาพแวดล้อม เวลาที่ใช้ ข้อผิดพลาดของเครื่องมือ และแฮชอินพุต บันทึกเวลาแก้งานด้วยมนุษย์แยกต่างหาก และอย่าใส่ศูนย์เมื่อไม่ได้รัน
5. ให้คะแนนทีละรายการด้วยมาตรฐานเดียวกัน และปกปิดป้ายกำกับตัวแปรก่อนตรวจทานเมื่อทำได้ เปรียบเทียบแต่ละมิติและประเภทความล้มเหลว แล้วจึงพิจารณาว่าข้อกำหนดที่เพิ่มคุ้มค่าหรือไม่

ข้อสังเกตจำนวนเล็กน้อยสะท้อนเฉพาะอินพุตและสภาพแวดล้อมครั้งนี้ ไม่สามารถสรุปอัตราความสำเร็จทั่วไป และไม่ควรเขียนความสัมพันธ์เป็นเหตุและผลว่าประโยคใดทำให้ผลดีขึ้น

## สิ่งที่ตรวจสอบแล้วและยังต้องตรวจสอบ

รันการตรวจวัสดุได้ดังนี้:

```sh
python3 scripts/check_materials.py
```

ตรวจแล้วว่าไฟล์อินพุตคงที่เก้าไฟล์ พรอมป์ A/B แบบเพิ่มเติมสามชุด และบันทึกว่างไม่มีคะแนนที่แต่งขึ้น สคริปต์นี้ไม่เรียกโมเดลและไม่ทดสอบผลของพรอมป์

มีบันทึกการรัน 12 ครั้ง คะแนนรายข้อ และเวลาที่ใช้แล้ว แต่ยังขาดป้ายกำกับโมเดลจริง log แพลตฟอร์มฉบับเต็ม และการตรวจอิสระโดยมนุษย์ ในแพ็กเกจผลลัพธ์ยังมี `python3 scripts/check_results.py` สำหรับตรวจผลลัพธ์ที่บันทึกไว้อีกครั้ง โดยไม่รันโมเดลซ้ำ ดูแบบฝึกหัดต้นฉบับฉบับเต็มได้ที่ [รายงานประจำสัปดาห์](/th/cases/analyze-a-spreadsheet/), [บทความ](/th/cases/write-an-article/) และ [เส้นทางสำหรับนักพัฒนา](/th/guide/learning-paths/developer/)
