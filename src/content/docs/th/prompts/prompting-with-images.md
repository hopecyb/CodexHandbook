งาน “ดูภาพแล้วทำ” จำนวนมากล้มเหลว ไม่ใช่เพราะโมเดลมองไม่เห็น แต่เพราะให้เพียงภาพโดย **ไม่ได้บอกว่าต้องการให้ดูอะไรในภาพ**

หัวใจของพรอมป์ภาพคือช่วยให้ Codex เข้าใจสามเรื่องนี้:

1. ภาพนี้คืออะไร
2. คุณต้องการให้สนใจส่วนใด
3. ผลลัพธ์สุดท้ายต้องใช้กับงานอะไร

## สถานการณ์ที่เหมาะกับพรอมป์ภาพ

| สถานการณ์ | หน้าที่ของภาพ |
|---|---|
| ตรวจหา UI Bug | ช่วยให้ Codex เห็นตำแหน่งและสถานะที่ผิดปกติ |
| ทำตามแบบดีไซน์ | เป็นข้อมูลอ้างอิงด้าน layout ลำดับชั้น spacing และบรรยากาศ |
| อธิบายภาพหน้าจอในเอกสาร | ให้เขียนคำอธิบายหรือบทช่วยสอนจากอินเทอร์เฟซ |
| จัดระเบียบไวต์บอร์ด/flowchart | เปลี่ยนภาพวาดมือเป็นคำอธิบายที่มีโครงสร้าง |
| เปรียบเทียบปัจจุบันกับที่คาดหวัง | ช่วยระบุความแตกต่างโดยไม่ต้องเดาข้อกำหนด |

หากงานมุ่งที่ “รูปลักษณ์ ตำแหน่ง หรือสถานะทางภาพ” รูปภาพมักมีประสิทธิภาพกว่าข้อความยาว แต่หากมุ่งที่ “กฎธุรกิจ” รูปภาพเป็นได้เพียงหลักฐานประกอบ

## โครงสร้างพรอมป์ภาพสี่ส่วน

ควรรักษาโครงสร้างเช่นเดียวกับพรอมป์ข้อความ:

### 1. ระบุภาพ

บอกว่าภาพนี้คืออะไรและมาจากที่ใด

ตัวอย่าง:

```text
นี่คือภาพหน้าจอหน้าเข้าสู่ระบบใน production จาก Safari บน iPhone 14
```

### 2. พื้นที่ที่ต้องสนใจ

ชี้ให้ชัดว่าต้องการให้ดูส่วนใด อย่าจบเพียง “หาปัญหาเอง”

ตัวอย่าง:

```text
เน้นดูระยะห่างระหว่างปุ่มด้านล่างกับช่องกรอกข้อมูล รวมถึงการเปลี่ยนแปลงของ layout เมื่อคีย์บอร์ดเปิด
```

### 3. เป้าหมายของงาน

ระบุว่าต้องการให้ทำอะไร เช่น วิเคราะห์ ทำซ้ำปัญหา แก้โค้ด เขียนคำอธิบาย หรือสร้างตารางเปรียบเทียบ

ตัวอย่าง:

```text
วิเคราะห์สาเหตุที่เป็นไปได้ก่อน อย่าเพิ่งแก้โค้ด ระบุไฟล์ frontend ที่น่าจะเกี่ยวข้องมากที่สุด 2–3 ไฟล์
```

### 4. รูปแบบผลลัพธ์

บอกว่าต้องการผลลัพธ์ใด เพื่อหลีกเลี่ยงคำตอบกว้าง ๆ

ตัวอย่าง:

```text
ผลลัพธ์:
1. สิ่งที่คุณสังเกตเห็นในภาพ
2. สาเหตุที่เป็นไปได้
3. ไฟล์ที่แนะนำให้ตรวจ
4. ภาพหน้าจอเพิ่มเติมที่ต้องการจากฉัน
```

## เทมเพลตที่ใช้บ่อยสามแบบ

### 1. ดูภาพเพื่อหาปัญหา

```text
ฉันอัปโหลดภาพหน้าจอของหน้าปัจจุบัน ให้เน้นดูบริเวณกรอบสีแดง
อธิบายความผิดปกติที่สังเกตเห็นก่อน แล้วระบุสาเหตุที่เป็นไปได้ 2–3 ข้อ
ยังไม่ต้องแก้โค้ด
```

### 2. ทำตามภาพ

```text
ฉันอัปโหลดแบบดีไซน์เป้าหมาย
สรุปโครงสร้างหน้า คอมโพเนนต์หลัก ประเด็น responsive และสไตล์ภาพจากภาพนี้
หากเริ่ม implementation ให้รักษาโครงสร้างและลำดับชั้นให้ตรงกันเป็นอันดับแรก อย่าเพิ่มฟังก์ชันเอง
```

### 3. เปรียบเทียบปัจจุบันกับที่คาดหวัง

```text
ฉันจะอัปโหลดสองภาพ ภาพแรกคือผลปัจจุบัน ภาพที่สองคือผลที่คาดหวัง
เปรียบเทียบความแตกต่างด้าน layout ลำดับชั้นข้อความ spacing และสิ่งบ่งชี้การโต้ตอบ พร้อมจัดลำดับความสำคัญในการแก้
```

## ควรเพิ่มข้อความอะไรเพื่อให้ดูภาพแม่นขึ้น

ภาพมักไม่มีบริบทขณะรัน ดังนั้นข้อมูลต่อไปนี้จึงมีประโยชน์:

- อุปกรณ์หรือเบราว์เซอร์
- สถานะปัจจุบันมี hover / focus / error state หรือไม่
- ตำแหน่งการเลื่อนหน้า
- เป็น “ผลปัจจุบัน” หรือ “ผลเป้าหมาย”
- ต้องทำตาม design system ที่มีอยู่หรือไม่

ประโยค “ทำงานปกติบน Chrome เดสก์ท็อป มีปัญหาเฉพาะ iOS Safari” มักมีคุณค่ามากกว่าภาพหน้าจออีกหนึ่งภาพ

## วิธีให้หลายภาพที่ดีที่สุด

### ให้เป็น “คู่”

รูปแบบที่ใช้ได้ดีคือ:

- ภาพปัจจุบัน
- ภาพที่คาดหวัง

หรือ:

- สถานะปกติ
- สถานะผิดปกติ

อย่าอัปโหลดภาพจำนวนมากโดยไม่มีคำอธิบาย แล้วให้ Codex เดาลำดับเอง

### กำหนดบทบาทให้แต่ละภาพ

ตัวอย่าง:

```text
ภาพ 1: ผลปัจจุบันบนเดสก์ท็อป
ภาพ 2: ผลปัจจุบันบนมือถือ
ภาพ 3: ผลเป้าหมายตามแบบดีไซน์
```

วิธีนี้ช่วยให้ Codex จัดความสัมพันธ์ที่สอดคล้องกันได้ง่ายขึ้น

## ข้อผิดพลาดที่พบบ่อยที่สุดในการเขียนพรอมป์ภาพ

### บอกเพียง “ทำตามนี้”

Codex จะพยายามอนุมานข้อกำหนดทั้งหมดจากภาพ และมักถือรายละเอียดที่คุณไม่ได้สนใจเป็นข้อบังคับด้วย

### ให้เฉพาะภาพบางส่วนโดยไม่มีบริบท

ภาพครอปช่วยให้เห็นจุดปัญหา แต่อาจไม่บอกว่านี่คือสถานะใดของหน้า ได้รับผลจาก responsive หรือไม่ หรืออยู่ในสถานการณ์ modal หรือไม่

### ถือแบบดีไซน์เป็นข้อกำหนดฉบับสมบูรณ์

แบบดีไซน์สื่อรูปลักษณ์ได้ แต่อาจไม่สื่อแหล่งข้อมูล edge case หรือ logic การโต้ตอบ จึงยังต้องเสริมกฎธุรกิจเป็นข้อความ

### เข้าใจผิดว่าภาพแทนเกณฑ์การยอมรับได้

แม้เป็นงานทำตามภาพ สุดท้ายยังต้องตรวจหน้าจริง diff พฤติกรรมตาม breakpoint และความสามารถในการใช้งาน ภาพคืออินพุต ไม่ใช่ผลการตรวจรับ

## เคล็ดลับที่ใช้ได้จริง

หากต้องการให้ Codex “ดูภาพเหมือนการรีวิวดีไซน์” ให้ทำ **การสังเกต** ก่อน ตามด้วย **การตัดสิน** และสุดท้ายจึง **เสนอแนะ**

ตัวอย่าง:

```text
อธิบายเฉพาะสิ่งที่สังเกตเห็นในภาพก่อน โดยยังไม่สรุป
จากนั้นค่อยตั้งสมมติฐานถึงสาเหตุที่เป็นไปได้มากที่สุด
สุดท้ายเสนอแนวทางแก้ไข
```

วิธีนี้ชัดกว่าคำว่า “ช่วยแก้ให้หน่อย” และทำงานต่อได้ง่ายกว่า
