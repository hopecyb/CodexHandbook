งานระยะยาวมักล้มเหลวในรูปแบบต่อไปนี้:

- ทำมากเกินไปในครั้งเดียว
- ไม่มีจุดตรวจระหว่างทาง
- เมื่อ thread ยาวขึ้น ข้อจำกัดช่วงต้นกับช่วงท้ายเริ่มขัดกัน

หัวใจของงานระยะยาวไม่ใช่การเขียนพรอมป์ให้ยาวขึ้น แต่คือการแบ่งงานเป็นระยะเล็ก ๆ ที่มีจุดตรวจ

แบ่งงานระยะยาวเป็นช่วง และมีเกณฑ์การยอมรับในแต่ละช่วง:

```text
ระยะ 1: ค้นคว้าและระบุแนวทางเท่านั้น (ไม่แก้โค้ด)
ระยะ 2: ทำการเปลี่ยนแปลงขั้นต่ำ
ระยะ 3: เพิ่มการทดสอบและรัน……
เมื่อจบแต่ละระยะ ให้หยุดรอฉันยืนยันก่อน
```

## ทำไมงานระยะยาวจึงหลุดทิศทางได้ง่าย

เพราะมักมีงานหลายประเภทพร้อมกัน:

- ทำความเข้าใจปัญหา
- ออกแบบแนวทาง
- ลงมือแก้ไข
- รันการตรวจสอบ
- เขียนคำอธิบายส่งต่องาน

หากทั้งหมดถูกรวมไว้ในคำสั่ง “ทำให้เสร็จทีเดียว” ความเสี่ยงจะสูงขึ้นอย่างเห็นได้ชัด

## ความเข้าใจผิดที่พบบ่อย

### 1. งานระยะยาวไม่ใช่แค่งานสั้นที่เขียนละเอียดขึ้น

งานระยะยาวต้อง **จัดการเป็นช่วง** มากกว่าเดิม ไม่สามารถพึ่งเพียงบริบทที่ยาวขึ้นได้

### 2. แค่ระบุแต่ละระยะยังไม่พอ

แต่ละระยะควรมีจุดสิ้นสุดที่ชัดเจน เช่น:

- เสนอแนวทางเท่านั้น ไม่แก้โค้ด
- ทำเฉพาะ implementation ขั้นต่ำ
- เพิ่มเฉพาะการทดสอบและการตรวจสอบ

### 3. ใช้ thread เดียวจนจบไม่จำเป็นต้องดีกว่า

เมื่องานยาวเกินไป การส่งต่องาน สรุป และเปิด thread ใหม่เพื่อทำต่อมักชัดเจนกว่า

## วิธีแบ่งระยะที่เพียงพอ

เมื่อเจองานระยะยาว ให้เริ่มแบ่งเป็นสี่ช่วง:

1. ค้นคว้า: ทำความเข้าใจปัญหาโดยยังไม่ลงมือ
2. วางแผน: ระบุขั้นตอน ความเสี่ยง และการตรวจสอบ
3. ลงมือ: ทำการเปลี่ยนแปลงขั้นต่ำ
4. ตรวจสอบ: รันการตรวจ เขียนข้อสรุป และเตรียมส่งต่องาน

## รูปแบบที่ใช้งานได้จริงกว่า

```text
ระยะ 1: ค้นคว้าและระบุแนวทางก่อน ไม่แก้โค้ด แล้วรอฉันยืนยัน
ระยะ 2: ทำเฉพาะการเปลี่ยนแปลงขั้นต่ำ เมื่อเสร็จให้รายงานขอบเขตผลกระทบ
ระยะ 3: เพิ่มการตรวจสอบและรันการตรวจที่เกี่ยวข้อง
ระยะ 4: สรุปการเปลี่ยนแปลง ความเสี่ยง และข้อเสนอแนะขั้นถัดไป
```

วิธีที่เหมาะกว่าคือทำให้แต่ละช่วงหยุดเพื่อตรวจได้ แทนที่จะทำรวดเดียวจนจบ
