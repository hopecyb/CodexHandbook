คำสั่ง สิทธิ์ ราคา และฟีเจอร์ผลิตภัณฑ์ใน handbook เปลี่ยนตามเวอร์ชันได้ **การตรวจสอบ** ทำให้ผู้อ่านคาดการณ์ผลลัพธ์ได้เมื่อทำตามเอกสาร

## เนื้อหาในหน้านี้

ผู้ร่วมดูแลเอกสารครั้งแรกจำนวนมากถือว่า “ดูแล้วไม่พบปัญหา” เท่ากับ “ตรวจสอบแล้ว”

แต่สำหรับคู่มือทางเทคนิค สองอย่างนี้ต่างกันมาก:

- อย่างแรกเป็นเพียงความรู้สึกส่วนตัวว่าน่าจะถูก
- อย่างหลังหมายถึงคุณได้ทดลองกับเวอร์ชัน สภาพแวดล้อม และขั้นตอนปัจจุบันจริง

หน้านี้อธิบายวิธียกระดับ “ดูเหมือนถูก” ให้เป็น “มีหลักฐานว่ายังถูกอยู่ในปัจจุบัน”

## “การตรวจสอบ” ตรวจอะไร

“การตรวจสอบเนื้อหาทางเทคนิค” ไม่ได้ดูเพียงว่าข้อความอ่านลื่นหรือไม่ แต่ยืนยันว่าหากผู้อ่านทำตาม วันนี้ยังทำสำเร็จจริง

เรื่องนี้สำคัญเป็นพิเศษ เพราะเนื้อหาหลายอย่างไม่ได้คงที่ตลอดไป เช่น:

- คำสั่งอาจเปลี่ยน
- ตำแหน่งเมนูอาจย้าย
- ค่าตั้งต้นของสิทธิ์อาจปรับ
- ความสามารถและขอบเขตการใช้งานของผลิตภัณฑ์อาจอัปเดต

ดังนั้น การตรวจสอบไม่ใช่ความเคร่งครัดด้านบรรณาธิการเกินจำเป็น แต่ช่วยไม่ให้ผู้อ่านทำตามเอกสารเก่าแล้วเกิดปัญหา

## ความหมายของสถานะ

| สถานะ | ความหมาย |
|---|---|
| `planned` | วางแผนแล้ว แต่ยังไม่ได้เขียน |
| `draft` | กำลังเขียน ยังไม่เสร็จสมบูรณ์ |
| `review` | เนื้อหาเสร็จแล้ว รอตรวจทาน |
| `verified` | ตรวจสอบตามหลักฐานที่ระบุแล้ว |
| `outdated` | ต้องอัปเดตหลังผลิตภัณฑ์เปลี่ยน |
| `archived` | เก็บไว้เป็นประวัติ ไม่แสดงใน navigation หลัก |

## ความเข้าใจผิดที่พบบ่อย

### สถานะการแก้ไขกับวิธีตรวจสอบเป็นคนละ field

`editorialStatus` บันทึกความคืบหน้าการเขียนและตรวจทาน ส่วน `verification.kind` บันทึกประเภทการตรวจที่ทำจริง ผู้อ่านไม่ควรสรุปจาก `verified` ว่าตัวอย่างถูกรันแล้ว

| วิธีตรวจสอบ | ข้อสรุปที่รองรับ | หลักฐานที่ต้องมี |
|---|---|---|
| `editorial` | ตรวจโครงสร้าง ถ้อยคำ หรือลิงก์ภายในแล้ว | สรุปการตรวจและวันที่ |
| `source-checked` | ข้อเท็จจริงในขอบเขตที่ระบุตรงกับแหล่งข้อมูล | ลิงก์แหล่งข้อมูลเฉพาะ สรุป และวันที่ |
| `run-tested` | รันตัวอย่างในสภาพแวดล้อมที่บันทึกไว้แล้ว | สภาพแวดล้อม บันทึกการรันและตรวจทาน สรุป และวันที่ |

`run-tested` ไม่รับประกันว่าจะใช้ได้กับทุกแพลตฟอร์ม สรุปต้องระบุว่าตรวจอะไรและไม่ได้ตรวจอะไร การตรวจซ้ำด้วยการคำนวณอิสระโดยผู้เขียนคนเดียวก็ไม่นับเป็นการตรวจทานโดยผู้เขียนคนที่สอง ระเบียนเก่าที่ไม่มีหลักฐานให้เก็บไว้ใน `legacyVerification` และห้ามอนุมานเป็นสถานะการตรวจแบบใหม่โดยอัตโนมัติ

```yaml
editorialStatus: review
verification:
  kind: editorial
  checkedAt: "2026-09-18"
  summary: ตรวจโครงสร้างและลิงก์ภายในแล้ว แต่ยังไม่ได้รันตัวอย่างจริง
```

การตรวจแหล่งข้อมูลและการรันจริงใช้รายการ `evidence` โดยแต่ละรายการมี `label` และ `href` สำหรับการรันจริงให้เพิ่ม `environment` เพื่อระบุระบบ เวอร์ชันไคลเอนต์ที่เกี่ยวข้อง และเวอร์ชัน dependency ให้ชัดเจน build จะปฏิเสธระเบียนการรันจริงที่ไม่มีสภาพแวดล้อมหรือลิงก์หลักฐาน การมีลิงก์เพียงอย่างเดียวยังไม่แปลว่าหลักฐานเพียงพอ ผู้ดูแลต้องอ่านระเบียนด้วย

### บทความชุมชนช่วยให้เข้าใจได้ แต่แทนการตรวจสอบข้อเท็จจริงไม่ได้

บทความหรือข้อมูลจากชุมชนเหมาะสำหรับช่วยค้นหาว่าควรเพิ่มหัวข้อใด

แต่หากเกี่ยวข้องกับ:

- ชื่อคำสั่ง
- พฤติกรรมของสิทธิ์
- ช่องทางเข้าใช้ผลิตภัณฑ์
- ราคา โควตา และความแตกต่างตามภูมิภาค

ยังต้องกลับไปตรวจสอบกับเอกสารทางการหรือผลการรันจริงในปัจจุบัน

### การตรวจสอบไม่ใช่การดูทีละประโยค

บางครั้งแต่ละประโยคดูถูกต้อง แต่เมื่อนำมาต่อกันกลับใช้ไม่ได้ เช่น:

- ผลิตภัณฑ์ที่ระบุไม่ตรงกับหน้าจริง
- ลำดับขั้นตอนไม่ถูกต้อง
- ไม่ได้เขียนเงื่อนไขตั้งต้นโดยปริยาย
- ชื่อหน้าสัญญาเนื้อหากว้างกว่าขอบเขตที่ตรวจจริง

จึงต้องตรวจ “กระบวนการทำงานทั้งหมด” ไม่ใช่เพียงกวาดดูถ้อยคำ

## เช็กลิสต์การตรวจสอบ

1. **ระบุขอบเขต**: ผลิตภัณฑ์ (App/CLI/IDE/Cloud), OS และเวอร์ชัน CLI
2. **ทำซ้ำทีละขั้น**: ทำตามตั้งแต่ต้นหรือจาก worktree ที่สะอาด
3. **หลักฐานทางการ**: แนบแหล่งข้อมูลทางการเฉพาะสำหรับข้อเท็จจริงของผลิตภัณฑ์ ส่วนแบบฝึกวิธีการที่คงที่ให้ใช้อินพุตจริงและบันทึกการตรวจ ห้ามอ้างการรับรองทางการที่ไม่มีจริง
4. **แหล่งข้อมูลชุมชน**: หากอ้างอิงข้อมูลชุมชน ให้ใช้เป็นแนวทางเลือกหัวข้อเท่านั้น และยึดแหล่งทางการสำหรับข้อเท็จจริง
5. **วันที่อัปเดต**: `verification.checkedAt` ต้องเป็นวันที่ตรวจจริง ห้ามอัปเดตวันที่เก่าพร้อมกันเพื่อให้ดูเหมือนตรวจใหม่
6. **การตรวจทานอิสระ**: สถานะ `verified` ควรให้บุคคลที่สองซึ่งไม่ใช่ผู้เขียนยืนยัน

## ลำดับการตรวจสอบ

ลำดับต่อไปนี้ช่วยลดการตกหล่น:

1. ยืนยันก่อนว่าหน้ากล่าวถึงผลิตภัณฑ์ ช่องทางเข้า และสถานการณ์ใด
2. ทำตามขั้นตอนในเนื้อหาตั้งแต่ต้น
3. เทียบกับเอกสารทางการเพื่อตรวจข้อมูลที่เปลี่ยนแปลงง่าย
4. ลดระดับส่วนที่ไม่แน่ใจหรือทำซ้ำไม่ได้
5. จากนั้นจึงอัปเดตสถานะและวันที่

ควรคงสถานะ `review` ไว้ก่อน ดีกว่าเปลี่ยนเป็น `verified` ทั้งที่หลักฐานยังไม่เพียงพอ

## ข้อมูลที่เปลี่ยนแปลงง่าย

รายการต่อไปนี้ต้องตรวจใหม่ทุกไตรมาสหรือเมื่อมี major release:

- ชื่อคำสั่ง คำสั่งย่อย และ flags
- ค่าตั้งต้นของสิทธิ์และพฤติกรรมของแซนด์บ็อกซ์
- แพ็กเกจบริการ ชื่อโมเดล และการรองรับตามภูมิภาค
- ชื่อ event ของ MCP/Hook

## เมื่อการตรวจสอบไม่ผ่าน

- ลดระดับตามจริงเป็น `review`, `draft` หรือ `outdated`
- อธิบายใน PR ว่าขั้นตอนใดไม่ตรงกับเอกสารทางการ
- หากต่างกันมาก ให้เปิด issue และติดป้าย `outdated`
