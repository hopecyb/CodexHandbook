คำสั่ง สิทธิ์ ราคา และความสามารถของผลิตภัณฑ์อาจเปลี่ยนไปในแต่ละเวอร์ชัน การตรวจสอบข้อมูลทางเทคนิคควรช่วยให้ผู้อ่านเข้าใจว่าข้อสรุปใดมีหลักฐานปัจจุบัน ใช้กับสภาพแวดล้อมใด และส่วนใดที่ยังต้องตรวจสอบเอง

## เป้าหมายการตรวจสอบ

การตรวจสอบไม่ใช่แค่ทำให้ข้อความอ่านลื่น ข้อเท็จจริงสำคัญต้องตรงกับผลิตภัณฑ์ปัจจุบัน ขั้นตอนต้องทำได้ในสภาพแวดล้อมที่ระบุ และข้อสรุปต้องไม่เกินขอบเขตที่หลักฐานรองรับ

## ลำดับความสำคัญของหลักฐาน

1. ใช้เอกสารทางการของ OpenAI ก่อนสำหรับพฤติกรรม พารามิเตอร์ และข้อจำกัดของผลิตภัณฑ์
2. ตัวอย่างที่ระบุว่า “รันแล้ว” ต้องมีผลลัพธ์จริงและข้อมูลสภาพแวดล้อม
3. บทความชุมชนช่วยค้นหาหัวข้อได้ แต่แทนแหล่งทางการหรือการรันจริงไม่ได้
4. ลิงก์เปิดได้ไม่ได้แปลว่าเนื้อหานั้นรองรับข้อสรุป ต้องอ่านแหล่งข้อมูล
5. เมื่อยืนยันไม่ได้ ให้ระบุความไม่แน่นอนโดยตรงแทนการคาดเดา

## ขอบเขตที่ต้องบันทึก

- ผลิตภัณฑ์ที่ใช้ได้: App, CLI, IDE หรือ Cloud
- ระบบปฏิบัติการ ไคลเอนต์ และเวอร์ชันของ dependency สำคัญ
- ขั้นตอนที่ทำจริงและวิธีตรวจผลลัพธ์
- แพลตฟอร์ม ช่องทางเข้า และกรณีขอบที่ไม่ได้ครอบคลุม
- หน้าของแหล่งข้อมูลโดยตรง ไม่ใช่เพียงหน้าแรกของเว็บไซต์

## ลำดับการตรวจสอบ

1. ระบุผลิตภัณฑ์ ช่องทางเข้า และสถานการณ์ที่หน้าอธิบาย
2. เทียบข้อเท็จจริงที่เปลี่ยนง่ายกับเอกสารทางการปัจจุบัน
3. หากหน้าระบุว่าขั้นตอนรันได้ ให้ทำตั้งแต่ต้นในสภาพแวดล้อมสะอาด
4. จำกัดขอบเขตของข้อสรุปที่ยังไม่ได้ทดสอบหรือไม่แน่นอน และระบุข้อจำกัดในเนื้อหา
5. ตรวจลิงก์ภายใน ลิงก์ภายนอก และเงื่อนไขเบื้องต้นที่ผู้อ่านต้องมี

## ข้อมูลที่เปลี่ยนบ่อย

หลังผลิตภัณฑ์ออกเวอร์ชันสำคัญ ให้ตรวจหัวข้อต่อไปนี้ก่อน:

- คำสั่ง คำสั่งย่อย และ flags
- สิทธิ์เริ่มต้นและพฤติกรรม sandbox
- แพ็กเกจ ชื่อโมเดล ราคา โควตา และการให้บริการตามภูมิภาค
- MCP, Hooks และ interface การเชื่อมต่ออื่น
- ตำแหน่งเมนู ชื่อปุ่ม และช่องทางเข้าสู่ผลิตภัณฑ์

## เมื่อยืนยันไม่ได้

อย่าเขียนข้อสันนิษฐานเป็นข้อเท็จจริง ให้ลบรายละเอียดที่ล้าสมัย เขียนใหม่โดยเน้นวิธีที่คงที่ หรือบันทึกคำถามไว้ใน PR หรือ issue สำหรับพฤติกรรม ราคา และนโยบายปัจจุบัน ให้ยึดแหล่งข้อมูลทางการ
