ตัวอย่างพรอมต์เก็บไว้ที่ [`examples/prompts/`](https://github.com/hopecyb/CodexHandbook/tree/main/examples/prompts) ในราก repository และมีลิงก์อ้างอิงจากเนื้อหา handbook ดูข้อกำหนดการออกแบบที่ [ระบบพรอมต์ Skill และกรณีศึกษา](https://github.com/hopecyb/CodexHandbook/blob/main/docs/planning/examples-system.md)

## เนื้อหาในหน้านี้

จุดที่มักติด ได้แก่:

- ไม่รู้ว่า “พรอมต์แบบใดควรได้รับการรวบรวม”
- ไม่รู้ว่าต้องใช้รูปแบบใดจึงให้ผู้อื่นนำไปใช้ซ้ำได้โดยตรง

หน้านี้อธิบายวิธีส่งตัวอย่างที่ **ผู้อื่นนำไปทดลอง เรียนรู้ และทำซ้ำได้จริง**

## เกณฑ์การรวบรวม

สิ่งที่รวบรวมคือ “ตัวอย่างที่ทำซ้ำได้ พร้อมบริบท ขอบเขต และเกณฑ์การยอมรับ” ไม่ใช่เพียงเศษไอเดีย

ตัวอย่างพรอมต์ที่ดีต้องตอบอย่างน้อยสามข้อ:

- ใช้เมื่อใด
- ควรเขียนพรอมต์ว่าอย่างไร
- หลังใช้แล้วจะตัดสินได้อย่างไรว่าทำสำเร็จ

หากเป็นเพียงข้อความที่ดูฉลาด แต่ผู้อื่นไม่รู้เงื่อนไขตั้งต้นและวิธีตรวจรับ ก็เป็นบันทึกมากกว่าตัวอย่าง

## การตั้งชื่อไฟล์

```text
examples/prompts/<category>/<slug>.md
```

ตัวอย่าง `category`: `development`, `research`, `meta-workflows`, `team`

## Metadata ที่ต้องมี (YAML frontmatter)

```yaml
---
id: prompt.fix-bug-with-tests
title: แก้ Bug และเพิ่มการทดสอบ
content_type: prompt
audience: [beginner, developer]
difficulty: beginner
products: [app, cli, ide]
capabilities: [planning, file-editing, testing]
status: draft
last_verified: YYYY-MM-DD
---
```

## หัวข้อที่ต้องมีในเนื้อหา

1. **สถานการณ์การใช้งาน**
2. **การเตรียมก่อนใช้** (สิทธิ์ branch และไฟล์บริบท)
3. **พรอมต์ฉบับแนะนำ** (ฉบับเต็มที่คัดลอกได้)
4. **เกณฑ์การยอมรับ** (เช็กลิสต์ที่ตรวจได้อย่างเป็นกลาง)
5. **รูปแบบความล้มเหลวที่พบบ่อย**
6. **หน้า handbook ที่เกี่ยวข้อง** (ลิงก์ไปยัง `src/content/docs/`)

ส่วนเสริม: ฉบับย่อ การแยกอธิบายเพื่อการสอน และตัวแปรที่แทนค่าได้

## ความเข้าใจผิดที่พบบ่อย

### อย่าเขียนจนประเด็นสำคัญกระจัดกระจาย

ผู้ร่วมเขียนบางคนเขียนภูมิหลัง ทฤษฎี และคำอธิบายต่อยอดจำนวนมาก จนพรอมต์ที่คัดลอกไปใช้ได้จริงถูกซ่อนไว้ตรงกลาง

รูปแบบที่มั่นคงกว่าคือ:

- เขียนพรอมต์ฉบับแนะนำให้ครบก่อน
- จากนั้นเพิ่มเงื่อนไขตั้งต้น ตัวแปร และรูปแบบความล้มเหลว
- สุดท้ายจึงเพิ่มเนื้อหาอธิบาย

### ใช้เองครั้งเดียวยังไม่ถือว่าเป็นตัวอย่างที่สมบูรณ์

คุณรู้ว่าในตอนนั้นสมมติอะไรไว้ในใจ แต่ผู้อ่านไม่รู้

จึงต้องเขียนเงื่อนไขเหล่านั้นออกมา เช่น:

- ใช้กับช่องทางผลิตภัณฑ์ใด
- ต้องใช้ไฟล์ ภาพหน้าจอ หรือบริบทใด
- โดยค่าเริ่มต้น อนุญาตให้แก้ไฟล์ รันคำสั่ง หรือใช้อินเทอร์เน็ตหรือไม่

### อย่าใส่ข้อมูลละเอียดอ่อนจริงในตัวอย่าง

หากตัวอย่างมี token บัญชี ลิงก์ภายใน หรือข้อมูลลูกค้าจริง ตัวอย่างนั้นไม่เหมาะกับ repository สาธารณะ

ตัวอย่างต้องสอนวิธีการ ไม่ใช่เปิดเผยสภาพแวดล้อม production ของคุณ

## ตัวอย่างเกณฑ์การยอมรับ

```markdown
## เกณฑ์การยอมรับ

- [ ] การทดสอบที่เคยล้มเหลวผ่านแล้ว
- [ ] ชุดการทดสอบในขอบเขตที่กำหนดผ่านแล้ว
- [ ] diff มีเฉพาะไฟล์ที่เกี่ยวข้องกับงาน
- [ ] ไม่ได้รัน git push
```

## เกณฑ์คุณภาพ

- เป้าหมายและนิยามว่าเสร็จชัดเจน
- มีคำอธิบายขอบเขตสิทธิ์และความปลอดภัย
- ไม่มีคีย์จริงหรือ PII
- สถานะ `verified` ต้องผ่าน [การตรวจทานอิสระ](/th/guide/contributing/verify-technical-content/)

## ขั้นตอนการส่ง

ลำดับต่อไปนี้มักมั่นคงกว่า:

1. ระบุก่อนว่าตัวอย่างนี้แก้งานจริงประเภทใด
2. เขียนพรอมต์ฉบับที่ผู้อื่นคัดลอกได้โดยตรง
3. ให้เงื่อนไขตั้งต้นและขอบเขตที่จำเป็นขั้นต่ำ
4. เขียนให้ชัดว่า “สำเร็จหมายถึงอะไร”
5. สุดท้ายตรวจว่ามีข้อมูลละเอียดอ่อนรั่วไหลหรือวางไฟล์ผิดไดเรกทอรีหรือไม่
