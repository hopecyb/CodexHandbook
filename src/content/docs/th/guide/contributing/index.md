**Codex Handbook** เป็นเว็บไซต์เอกสารที่ชุมชนช่วยกันดูแล เรายินดีต้อนรับการแก้ข้อผิดพลาด เพิ่มหน้าใหม่ เพิ่มกรณีศึกษาที่ทำซ้ำได้ และตัวอย่างพรอมต์ใน [examples/](https://github.com/hopecyb/CodexHandbook/tree/main/examples)

## เนื้อหาในหน้านี้

- ประเภทและช่องทางการมีส่วนร่วม
- มาตรฐานการเขียนและการตรวจสอบ
- สิ่งที่คาดหวังจาก PR และการเผยแพร่

## การมีส่วนร่วมแบบใดมีคุณค่ามากที่สุด

หากพบสิ่งต่อไปนี้ในเว็บไซต์:

- จุดที่คุณอ่านเองแล้วยังไม่เข้าใจ
- มีทางเข้าในสารบัญ แต่เนื้อหายังนำทางไม่เพียงพอ
- คำสั่ง ภาพหน้าจอ หรือคำอธิบายล้าสมัยแล้ว

สิ่งเหล่านี้เป็นเบาะแสที่มีคุณค่าสำหรับการมีส่วนร่วม

คุณไม่จำเป็นต้องเป็น “ผู้รู้มากที่สุดในสาขานี้” ก่อนจึงจะช่วยได้ การปรับปรุงที่มีประโยชน์จริงจำนวนมากมาจากผู้เริ่มต้นที่ชี้ว่า “ตรงนี้สมมติว่าผู้อ่านรู้อยู่แล้ว แต่ฉันยังไม่เข้าใจ”

## ประเภทการมีส่วนร่วม

| ประเภท | คำอธิบาย | คู่มือ |

| หน้าคู่มือใหม่ | เนื้อหาในบทภายใต้ `src/content/docs/` | [เขียนหน้าคู่มือ](/th/guide/contributing/write-a-guide/) |

| ตัวอย่างพรอมต์ | `examples/prompts/` | [เพิ่มตัวอย่างพรอมต์](/th/guide/contributing/add-a-prompt-example/) |

## ความเข้าใจผิดที่พบบ่อย

### การมีส่วนร่วมไม่จำเป็นต้องเขียนบทใหญ่ใหม่ทั้งบท

ผู้ร่วมเขียนครั้งแรกจำนวนมากคิดว่า “การมีส่วนร่วม” หมายถึงต้องเพิ่มเนื้อหาชุดใหญ่ครบถ้วน

ความจริงแล้ว สิ่งต่อไปนี้ล้วนมีคุณค่า:

- เพิ่มคำอธิบายหนึ่งย่อหน้าให้ผู้เริ่มต้นเข้าใจ
- แก้ถ้อยคำที่ทำให้เข้าใจผิด
- เพิ่มทางเข้าสารบัญที่ตกหล่น
- ลดระดับคำสั่งที่ล้าสมัยหรือระบุวันที่กำกับ

### “ฉันไม่ใช่ผู้เชี่ยวชาญ” ไม่ได้แปลว่า “ข้อเสนอแนะของฉันไม่มีประโยชน์”

หากกลุ่มผู้อ่านเป้าหมายมีผู้เริ่มต้น จุดที่คุณติดขณะอ่านก็คือสัญญาณที่มีคุณค่า

เงื่อนไขคือ ต้องอธิบายปัญหาให้เจาะจงและพยายามปรับให้ชัดขึ้น ไม่ใช่เพียงทิ้งข้อความว่า “ตรงนี้ไม่เข้าใจ”

## หลักการพื้นฐาน

1. **ภาษาจีนตัวย่อใน `root` เป็นต้นฉบับ** เว้นแต่ระบุไว้เป็นอย่างอื่น
2. **ห้ามคัดลอก** เนื้อหาจากบทสอนภายนอก ดู [แผนรวมแหล่งข้อมูลภายนอก](https://github.com/hopecyb/CodexHandbook/blob/main/docs/planning/external-source-integration.md)
3. **ข้อเท็จจริงที่เปลี่ยนแปลงง่าย** ต้องระบุวันที่ `ตรวจสอบล่าสุด`
4. หน้าใหม่ต้องมี frontmatter เส้นทางไฟล์ และลิงก์ข้ามหน้าที่ถูกต้อง
5. sidebar ของสี่โมดูลปัจจุบันอ่านไดเรกทอรีโดยอัตโนมัติ หลังเพิ่มไฟล์ให้รัน build และตรวจว่าลำดับกับทางเข้าถูกต้อง

## หากมีส่วนร่วมครั้งแรก ให้เริ่มแบบนี้

ลำดับเริ่มต้นที่มั่นคงที่สุดคือ:

1. เลือกจุดหนึ่งที่คุณเพิ่งติดจริง
2. พิจารณาว่าควรแก้ข้อความ เพิ่มหน้า เพิ่มตัวอย่าง หรือตรวจสอบข้อมูลล้าสมัย
3. แก้เฉพาะส่วนเล็กนั้น แต่ระบุเงื่อนไขตั้งต้นและมุมมองของผู้อ่านให้ชัด
4. รัน build เพื่อยืนยันว่าโครงสร้างเว็บไซต์ไม่เสียหาย

วิธีนี้สำเร็จง่ายกว่าและตรวจทานง่ายกว่าการปรับทั้งบทครั้งใหญ่ตั้งแต่ต้น

## การพัฒนาในเครื่อง

```bash
source ~/.nvm/nvm.sh && nvm use 22
pnpm install
pnpm dev
```

ก่อน merge ให้รัน:

```bash
pnpm build
```

## จรรยาบรรณ

- เคารพผลงานของผู้อื่น อภิปรายที่ประเด็น ไม่โจมตีบุคคล
- ห้าม commit คีย์จริงหรือข้อมูลลูกค้า
- ก่อน refactor ขนาดใหญ่ ให้หารือผ่าน issue หรือ RFC

การมีส่วนร่วมครั้งแรกไม่ต้องเน้นปริมาณ เพียงอธิบายจุดที่ผู้เริ่มต้นติดจริงให้ชัด และยืนยันว่า build ผ่าน ก็มีคุณค่ามากแล้ว
