เมื่อเลือกช่องทางเข้าใช้ Codex ครั้งแรก ไม่ต้องเทียบฟีเจอร์นับสิบรายการ ให้ตอบคำถามเดียวก่อนว่า **งานครั้งนี้เกิดขึ้นที่ไหนเป็นหลัก**

![แผนภาพเลือกไคลเอนต์ Codex: เริ่มจากตำแหน่งที่ทำงาน แล้วเลือก Desktop App, CLI, ส่วนขยาย IDE หรือ Cloud](/illustrations/flow-client-selection.webp)

## เลือกได้ภายใน 30 วินาที

| งานเกิดขึ้นที่ | ช่องทางหลัก | รูปแบบการโต้ตอบที่เหมาะที่สุด |
|---|---|---|
| หลายโปรเจกต์และหลายงานขนานบนเครื่อง | **Desktop App** | ดูงาน ตรวจ diff จัดการการอนุมัติ และดูแลงานระยะยาว |
| เทอร์มินัล สคริปต์ หรือเวิร์กโฟลว์บรรทัดคำสั่งเดิม | **CLI** | มอบหมายงานโดยตรง รันคำสั่ง และประกอบสคริปต์กับระบบอัตโนมัติ |
| VS Code, เอดิเตอร์ที่เข้ากันได้, Xcode หรือ JetBrains | **การเชื่อมต่อ IDE** | ถามโดยใช้บริบทจากเอดิเตอร์ แก้ไขและตรวจสอบในจุดเดิม |
| Repository ระยะไกลที่เชื่อมต่อและสภาพแวดล้อมแยก | **Cloud** | มอบหมายให้รันบน Cloud ทำงานขนาน และกลับมาตรวจผลภายหลัง |

หากยังไม่มีความชอบชัดเจน เริ่มจาก **Desktop App** มักเข้าใจง่ายที่สุด แต่ถ้าใช้เทอร์มินัลหรือ VS Code เป็นประจำอยู่แล้ว การทำงานในพื้นที่คุ้นเคยจะลดต้นทุนการสลับบริบท

## ช่องทางทั้งสี่แก้ปัญหาอะไร

### Desktop App: ศูนย์ควบคุมงานในเครื่อง

Desktop App เหมาะกับงานที่ต้องเห็นสถานะงาน การเปลี่ยนแปลงไฟล์ และขั้นตอนอนุมัติชัดเจน โดยเฉพาะเมื่อคุณต้อง:

- ติดตามหลายงานหรือหลายโปรเจกต์พร้อมกัน
- ใช้ Worktree แยกการแก้ไขขนานกัน
- ตรวจ diff แล้วถามต่อหรือแก้ไขเพิ่มเติม
- จัดงานที่ต้องทำต่อเนื่องบนโปรเจกต์ในเครื่อง

ตัวอย่าง: ให้งานหนึ่งแก้ regression ของการเข้าสู่ระบบ อีกงานวิเคราะห์คอขวดด้านประสิทธิภาพแบบอ่านอย่างเดียว แล้วตรวจผลแยกกัน

### CLI: นำ Codex เข้าเวิร์กโฟลว์เทอร์มินัล

CLI เหมาะกับผู้ที่จัดการโปรเจกต์ผ่านบรรทัดคำสั่งอยู่แล้ว เพราะอยู่ใกล้คำสั่งทดสอบ Git และสคริปต์ที่สุด และบันทึกขั้นตอนเดียวกันไว้ในเอกสารทีมได้ง่าย

```bash
codex
```

ตัวอย่าง: เปิด Codex ที่ราก Repository ให้รันการทดสอบที่ล้มเหลวก่อน หาสาเหตุ แก้เท่าที่จำเป็น แล้วตรวจซ้ำด้วยคำสั่งทดสอบเดิม

### การเชื่อมต่อ IDE: ทำงานรอบโค้ดปัจจุบัน

การเชื่อมต่อ IDE เหมาะกับคำถามที่สัมพันธ์อย่างมากกับ “ไฟล์ ส่วนที่เลือก หรือ diff ที่กำลังดู” ปัจจุบันมีสองรูปแบบ: VS Code, Cursor, Windsurf และเอดิเตอร์ที่เข้ากันได้ใช้ส่วนขยาย Codex ส่วน Xcode และ JetBrains IDE ใช้ช่องทางเชื่อมต่อ Codex ของตนเอง

ตัวอย่าง: เลือกฟังก์ชันที่เข้าใจยาก ให้ Codex อธิบายอินพุต เอาต์พุต และเส้นทางข้อผิดพลาด จากนั้นให้เพิ่มชุดทดสอบกรณีขอบเขต

### Cloud: มอบหมายงานในสภาพแวดล้อมระยะไกลที่แยกออกมา

Cloud เหมาะเมื่อเชื่อมต่อ Repository ระยะไกลแล้วและต้องการให้งานทำงานแยกจากเครื่องของคุณ งานบน Cloud ทำงานในสภาพแวดล้อมแยก จึงเหมาะกับการสำรวจขนาน งานที่ใช้เวลานาน และการรวมตรวจผลหลังเสร็จ

ตัวอย่าง: มอบปัญหาใน Repository สามเรื่องที่ไม่พึ่งกันให้สามงานบน Cloud รอรับการเปลี่ยนแปลงและหลักฐานการตรวจสอบ แล้วตรวจทีละงาน

## ไม่จำเป็นต้องเลือกเพียงหนึ่งในสี่

เวิร์กโฟลว์เดียวส่งต่องานข้ามช่องทางได้:

1. ชี้แจงปัญหารอบไฟล์ปัจจุบันใน IDE
2. มอบงานที่ต้องสำรวจนานให้ Desktop App หรือ Cloud
3. รันคำสั่งตรวจสอบตามข้อตกลงทีมใน CLI
4. กลับไปยืนยัน diff สุดท้ายใน Desktop App หรือหน้าตรวจโค้ด

หลักการเลือกไม่ใช่ “อันไหนเก่งที่สุด” แต่คือ **อันไหนใกล้บริบทปัจจุบันและตรวจผลได้ง่ายที่สุด**

## สองสถานการณ์ที่พบบ่อย

### สถานการณ์ที่หนึ่ง: แก้ bug ในโปรเจกต์จริงครั้งแรก

ควรใช้ Desktop App ก่อน เพราะมองเห็นบทสนทนาของงาน การเปลี่ยนแปลง และคำขอสิทธิ์พร้อมกัน เมื่อทำครบวงจรหนึ่งครั้งแล้วค่อยลอง CLI หรือ IDE

### สถานการณ์ที่สอง: ทีมมีคำสั่งและข้อตกลง CI แน่นอนแล้ว

ควรใช้ CLI และบันทึกคำสั่งติดตั้ง ทดสอบ และจัดรูปแบบไว้ใน `AGENTS.md` เพื่อให้ Codex ทำตามกฎโปรเจกต์ชุดเดียวกันทุกครั้ง

## ตรวจสอบทันทีหลังเลือก

อย่ายืนยันเพียงว่า “เปิดไคลเอนต์ได้” ให้ทำวงจรต่อไปนี้ใน Repository สำหรับฝึก:

1. ให้ Codex อ่านและอธิบายไฟล์หนึ่งไฟล์
2. ขอการแก้ไขเล็ก ๆ ที่ย้อนกลับได้
3. ตรวจ diff ไม่ใช่อ่านเฉพาะคำตอบสุดท้าย
4. รันคำสั่งตรวจสอบหนึ่งคำสั่ง
5. ยืนยันว่าคุณรู้วิธีปฏิเสธหรือจำกัดคำขอสิทธิ์
