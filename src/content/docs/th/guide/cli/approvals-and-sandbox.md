ใน CLI Agent สามารถ **อ่านไฟล์ เขียนไฟล์ รัน shell และอาจเชื่อมต่อเครือข่าย** การอนุมัติและ sandbox คือวาล์วนิรภัยระหว่างคุณกับระบบอัตโนมัติ หากตั้งค่าไม่เหมาะสม อาจมีหน้าต่างถามซ้ำ ๆ ระหว่างโต้ตอบ หรือความเสี่ยงหลุดการควบคุมเมื่อ CI ทำงานแบบไร้ผู้ดูแล

## เนื้อหาในหน้านี้

- หน้าต่างอนุมัติกำลังถามอะไร และควรเลือกอย่างไร
- ระดับ sandbox ส่งผลต่อไฟล์และเครือข่ายอย่างไร
- ทีมจะจัดนโยบายระหว่าง CLI กับ `AGENTS.md` ให้ตรงกันอย่างไร

## การอนุมัติกับ sandbox ควบคุมอะไรต่างกัน

จำง่าย ๆ ว่า:

- **การอนุมัติ** ถามคุณว่า “จะให้ทำขั้นตอนนี้ต่อหรือไม่”
- **Sandbox** จำกัดว่า “ถึงให้ทำต่อ จะเข้าถึงได้ไกลแค่ไหน”

ทั้งสองอย่างทำงานร่วมกันและส่งผลโดยตรงว่า CLI จะระมัดระวังเพียงใด หรือเปิดขอบเขตกว้างเกินไป

แนวคิดพื้นฐาน: [สิทธิ์และการอนุมัติ](/th/guide/foundations/permissions-and-approvals/) · [Sandbox และเครือข่าย](/th/guide/foundations/sandbox-and-network/)

## การอนุมัติเกิดขึ้นเมื่อใด

จุดกระตุ้นทั่วไป (ขึ้นอยู่กับผลิตภัณฑ์จริง):

| ประเภทการกระทำ | ความเสี่ยง | แนวโน้มเริ่มต้น |
|---|---|---|
| เขียนไฟล์ในโปรเจกต์ | ปานกลาง | มักต้องยืนยัน |
| เขียนพาธนอกโปรเจกต์ | สูง | ควรปฏิเสธหรือยืนยันอย่างเข้มงวด |
| รัน shell | สูง | ตรวจและยืนยันเนื้อหาคำสั่ง |
| เชื่อมต่อเครือข่าย / curl | สูง | ยืนยันปลายทางและข้อมูล |
| เรียกเครื่องมือ MCP | ขึ้นอยู่กับเซิร์ฟเวอร์ | ควบคุมตามเครื่องมือ |

ระหว่างโต้ตอบ อาจมีตัวเลือกอย่าง **อนุญาตครั้งเดียว / อนุญาตทั้งเซสชัน / ปฏิเสธ** (ชื่อแตกต่างตามเวอร์ชัน) **อย่ากด “อนุญาตเสมอ” ให้คำสั่งที่คุณไม่เข้าใจ**

## ระดับ Sandbox (เชิงแนวคิด)

| เจตนาของระดับ | เหมาะกับ |
|---|---|
| เข้มงวด / อ่านอย่างเดียว | ตรวจโค้ดที่ไม่น่าเชื่อถือ หรือตรวจ CI แบบอ่านอย่างเดียว |
| มาตรฐาน | repository สำหรับงานพัฒนาประจำวัน |
| ผ่อนคลาย | สภาพแวดล้อมส่วนตัวที่เชื่อถือได้และสอดคล้องกับนโยบายบริษัท |

Sandbox อาจจำกัด:

- ขอบเขตไดเรกทอรีที่เขียนได้
- การเข้าถึงโปรเจกต์อื่นใน `$HOME`
- ความสามารถของ process ลูกและเครือข่าย

จุดตั้งค่า: [การตั้งค่า CLI](/th/guide/cli/configuration/) · ตาราง: [เมทริกซ์สิทธิ์](/th/guide/reference/permission-matrix/)

## แบบโต้ตอบเทียบกับไม่โต้ตอบ

| โหมด | ลักษณะการอนุมัติ |
|---|---|
| `codex` แบบโต้ตอบ | มีคนอยู่และตัดสินใจทีละรายการได้ |
| `exec` แบบไม่โต้ตอบ | ไม่มีคุณอยู่ ต้องจำกัด sandbox และกำหนด prompt ล่วงหน้า |

สิ่งที่ต้องอ่านสำหรับ CI: [โหมดไม่โต้ตอบ](/th/guide/cli/non-interactive-mode/) · [รูปแบบการอนุมัติโดยมนุษย์](/th/cases/workflows/human-approval-patterns/)

หลักการ CI ที่แนะนำ:

- อ่านอย่างเดียวหรือจำกัดพาธที่เขียนได้
- ห้ามใช้ `curl` อัปโหลดเนื้อหา repository โดยพลการ
- เมื่อล้มเหลวให้ออกด้วยสถานะไม่ใช่ศูนย์และเก็บ log ไว้

## ความสัมพันธ์กับกฎ allow/deny

โปรเจกต์ประกาศ “คำสั่งที่คาดหมายได้” ใน [กฎอนุญาตและปฏิเสธ](/th/guide/customization/rules/allow-and-deny-patterns/) ได้ **กฎต้องตรงกับพฤติกรรมจริงของผลิตภัณฑ์** มิฉะนั้น Agent อาจยังถูกบล็อก หรือกลับเปิดกว้างเกินไป

## ข้อผิดพลาดที่พบบ่อย

- เปิด “อนุมัติ shell ทั้งหมดอัตโนมัติ” ทั่วเครื่อง แล้วนำไปใช้กับ repository ของลูกค้า
- เผลออนุมัติคำสั่งประเภท `sudo` ลบฐานข้อมูล หรือแก้ `~/.ssh`
- ใช้ค่าผ่อนคลายใน CI เหมือนเครื่องพัฒนา
- คิดว่า sandbox แทน code review ได้—มันป้องกันการทำงานผิดพลาด แต่ไม่ป้องกัน prompt injection ที่เป็นอันตราย

## ความเข้าใจผิดที่พบบ่อย

### มีหน้าต่างถามบ่อยไม่ได้แปลว่าตั้งค่าผิดเสมอไป

หากเพิ่งเริ่มเรียน CLI การถูกถามมากหน่อยกลับปลอดภัยกว่า เพราะบังคับให้คุณเข้าใจว่าแต่ละขั้นตอนทำอะไร

สิ่งที่ควรระวังจริงคือคุณเริ่มกดอนุมัติโดยไม่อ่าน ไม่ใช่ระบบถามมากเกินไป

### ผ่อนคลายครั้งหนึ่ง ไม่ได้แปลว่าจะปลอดภัยตลอดไป

บางคนเปิดกฎกว้างมากเพื่อความสะดวกครั้งแรก แล้วใช้ค่าเดิมต่อใน repository และงานอื่น

ปัญหาคือขอบเขตความปลอดภัยควรเปลี่ยนตามความเสี่ยงของงาน ไม่ควรถือว่าครั้งนี้ไม่มีปัญหาเพียงเพราะครั้งก่อนสะดวก

## เช็กลิสต์ตรวจรับ

- [ ] อธิบายได้ว่าคำขออนุมัติล่าสุดกำลังทำอะไร
- [ ] รู้ว่าต้องเปลี่ยนระดับ sandbox ที่ใดและเปิดเซสชันใหม่อย่างไร
- [ ] เอกสารทีมระบุว่าคำสั่งใดห้ามใช้ และคำสั่งใดคาดว่าจะอนุมัติอัตโนมัติได้

ในช่วงเริ่มต้น ตั้งค่าการอนุมัติและ sandbox ของ CLI ให้ค่อนข้างระมัดระวังมักมั่นคงกว่า เมื่อเข้าใจจริงว่ากำลังเปิดสิทธิ์อะไร ค่อยผ่อนคลายทีละน้อยก็ยังไม่สาย
