โหมดไม่โต้ตอบทำให้ Codex ทำงานได้ **โดยไม่ต้องสนทนาผ่าน TTY** และเป็นจุดที่นักพัฒนาใช้เชื่อม Agent เข้ากับสคริปต์และ CI

กล่าวง่าย ๆ คือโหมดไม่โต้ตอบไม่ได้คุยไปกลับ แต่ส่งงานให้ทำครั้งเดียว

ลักษณะคล้ายการเรียกคำสั่งหนึ่งครั้ง

## เนื้อหาในหน้านี้

- เมื่อใดควรใช้โหมดไม่โต้ตอบแทนเซสชัน `codex` แบบโต้ตอบ
- ข้อกำหนดด้านความปลอดภัยและการอนุมัติเพิ่มเติมเมื่องานไร้ผู้ดูแล
- ความสัมพันธ์กับ [การตั้งค่า](/th/guide/cli/configuration/)

## สถานการณ์ที่เหมาะสม

| เหมาะ | ไม่เหมาะ |
|---|---|
| รัน prompt review ที่กำหนดไว้ใน CI | ต้องชี้แจงความต้องการหลายรอบ |
| ตรวจลิงก์เอกสารทุกคืน | refactor เชิงสำรวจ |
| สร้างโค้ดจากแม่แบบที่กำหนดไว้ | การตัดสินใจผลิตภัณฑ์ที่คลุมเครือสูง |

## แนวคิดหลัก

การรันแบบไม่โต้ตอบโดยทั่วไปจะ:

1. รับ **คำอธิบายงานฉบับเต็ม** จากพารามิเตอร์หรือ stdin
2. รันในไดเรกทอรีทำงานที่ระบุ
3. ใช้ exit code แสดงความสำเร็จ/ล้มเหลว
4. ส่ง log หรือผลลัพธ์แบบมีโครงสร้างให้ขั้นตอนถัดไปใช้

จุดเข้าแบบไม่โต้ตอบปัจจุบันคือ `codex exec` หลังอัปเกรด CLI ควรรัน `codex exec --help` เพื่อตรวจพารามิเตอร์ที่สคริปต์ใช้อีกครั้ง

## ตัวอย่างขั้นต่ำ (เพื่อสาธิต)

```bash
# รัน review แบบอ่านอย่างเดียวหนึ่งครั้งที่ราก repository
codex exec --cd . "ระบุความเสี่ยงด้านความปลอดภัยใน diff เทียบกับ main โดยไม่แก้ไขไฟล์"
```

`codex exec` ใช้ sandbox แบบอ่านอย่างเดียวโดยปริยาย ระหว่างรันจะเขียนความคืบหน้าไป `stderr` และเขียนคำตอบสุดท้ายของ Agent ไป `stdout` จึงเปลี่ยนเส้นทางเฉพาะผลลัพธ์สุดท้ายให้ขั้นตอนถัดไปได้อย่างปลอดภัย:

```bash
codex exec --cd . "สร้างบันทึกประจำรุ่นจาก 10 commit ล่าสุด" > release-notes.md
```

คำแนะนำในการใช้งาน:

- ใน shell script ให้ `cd` ไปยัง working copy ที่สะอาดก่อน
- เก็บสตริงงานใน heredoc หรือไฟล์ `prompts/` ที่มี version control
- จับ exit code และให้ CI แสดงสถานะล้มเหลวเมื่อผิดพลาด

## การออกแบบความปลอดภัย

ไร้ผู้ดูแล = **ไม่มีคุณอยู่เพื่อกดปฏิเสธ**:

| หลักการ | วิธีทำ |
|---|---|
| สิทธิ์ต่ำสุด | token แบบอ่านอย่างเดียวและ sandbox ที่จำกัด |
| ห้าม push | ให้ CI เปิดเฉพาะ PR หรืออัปโหลด artifact |
| Prompt คงที่ | ห้ามนำข้อความที่ยังไม่ผ่านการกรองจากคำอธิบาย PR มาต่อโดยตรง (เสี่ยง injection) |
| การตรวจสอบย้อนหลัง | เก็บ log และ diff artifact |

ดู [รูปแบบการอนุมัติโดยมนุษย์](/th/cases/workflows/human-approval-patterns/) และ roadmap `08-developer-platform/non-interactive/`

## เปรียบเทียบกับโหมดโต้ตอบ

| | โหมดโต้ตอบ | โหมดไม่โต้ตอบ |
|---|---|---|
| จุดเข้า | TUI `codex` | `exec` / pipeline |
| มนุษย์อยู่ในวงจร | มาก | น้อย ต้องออกแบบล่วงหน้า |
| เหมาะกับการเรียนรู้ | ใช่ | ไม่ |
| เหมาะกับ CI | ไม่ | ใช่ |

วิธีใช้แบบโต้ตอบ: [โหมดโต้ตอบของ CLI](/th/guide/cli/interactive-mode/)

## เปลี่ยนงานแบบโต้ตอบเป็นงานแบบไม่โต้ตอบ

อย่านำประวัติการสนทนาทั้งหมดใส่สคริปต์โดยตรง วิธีที่มั่นคงกว่าคือย่อให้เป็นข้อกำหนดขนาดเล็ก:

| องค์ประกอบ | วิธีเขียน |
|---|---|
| เป้าหมาย | ครั้งนี้ทำอะไรเพียงอย่างเดียว |
| อินพุต | อ่านไฟล์ diff, log หรือ stdin ใดบ้าง |
| ข้อห้าม | ห้ามแก้ไฟล์ ห้ามเชื่อมเครือข่าย ห้าม push ห้ามขัดจังหวะ CI เป็นต้น |
| เอาต์พุต | สรุปข้อความ JSON ไฟล์รายงาน หรือ exit code |
| การตรวจรับ | คำสั่งใดต้องผ่าน และคำสำคัญใดห้ามปรากฏ |

Prompt แบบไม่โต้ตอบควรเหมือนใบงาน: ขอบเขตชัด อินพุตครบ และเงื่อนไขล้มเหลวชัด งานใดที่ยังต้องใช้วิจารณญาณด้านผลิตภัณฑ์ ข้อแลกเปลี่ยนด้านการออกแบบ หรือการยืนยันสิทธิ์ ควรอยู่ในโหมดโต้ตอบก่อน

## ความเข้าใจผิดที่พบบ่อย

### 1. โหมดไม่โต้ตอบมีประสิทธิภาพกว่า จึงควรเรียนก่อนหรือไม่

ไม่แนะนำ

สำหรับผู้ใช้ครั้งแรก โหมดไม่โต้ตอบมักเร็วและตายตัวเกินไป มีพื้นที่ให้ชี้แจงไปมาระหว่างทางน้อย

### 2. ต่างจากโหมดโต้ตอบมากที่สุดตรงไหน

ความต่างหลักสรุปได้ว่า:

- **โหมดโต้ตอบ**: ถาม แก้ และอนุมัติระหว่างทางได้
- **โหมดไม่โต้ตอบ**: คล้ายการรันครั้งเดียว เหมาะกับกระบวนการที่กำหนดไว้ล่วงหน้า

### 3. กรณีใดที่ยังไม่ควรใช้

หากยังอยู่ในช่วงเหล่านี้ แนะนำให้รอก่อน:

- ยังไม่คุ้นกับการเขียน prompt
- ยังไม่รู้วิธีตรวจรับผลลัพธ์
- ยังไม่มีความเข้าใจพื้นฐานเรื่องการอนุมัติ sandbox และสิทธิ์

โหมดไม่โต้ตอบเหมาะกับระบบอัตโนมัติ แต่ไม่เหมาะกับการลองครั้งแรก ใช้โหมดโต้ตอบให้คล่องก่อน แล้วค่อยเชื่อมเข้ากับสคริปต์

## ข้อผิดพลาดที่พบบ่อย

- ใส่ประวัติการสนทนายาวจากเซสชันแบบโต้ตอบลงใน exec ครั้งเดียวตามเดิม
- ใช้ข้อมูลรับรองระบบจริงและสิทธิ์เขียนใน CI
- ไม่ตรึงเวอร์ชัน CLI จนพฤติกรรม pipeline เปลี่ยนกะทันหัน
