การตั้งค่า CLI กำหนด **โมเดลเริ่มต้น ไดเรกทอรีทำงาน ระดับความเข้มงวดของการอนุมัติ เซิร์ฟเวอร์ MCP** และอื่น ๆ แนวคิดสอดคล้องกับ [พื้นฐานการตั้งค่า](/th/guide/customization/configuration/config-basics/) แต่หน้านี้เน้นรายการที่ผู้ใช้เทอร์มินัลปรับบ่อย

## เนื้อหาในหน้านี้

เมื่อพบการตั้งค่า CLI ครั้งแรก หลายคนคิดว่าเป็น “แผงตั้งค่าขั้นสูง” ซึ่งก่อให้เกิดความเข้าใจผิดสองแบบ:

- คิดว่าไม่ตั้งค่าก็ไม่เป็นไร แต่ต้องเลือกค่าเดิมซ้ำด้วยตนเองทุกครั้งที่เริ่ม
- คิดว่ายิ่งตั้งค่ามากยิ่งดูเป็นมืออาชีพ จึงรวมความชอบส่วนตัว กฎทีม และการทดลองชั่วคราวไว้ที่เดียวจนตรวจสอบปัญหายาก

ประเด็นหลักคือการแยกว่า **ค่าใดควรกำหนดถาวร และค่าใดควรเปลี่ยนเพียงชั่วคราว**

## การตั้งค่า CLI ควบคุมอะไร

มองการตั้งค่า CLI เป็น “นิสัยการทำงานเริ่มต้นของ Codex ในเทอร์มินัล” ได้

- การตั้งค่าโมเดล: กำหนดว่าโดยปริยายจะใช้ใครทำงาน
- Sandbox และการอนุมัติ: กำหนดว่าโดยปริยายทำได้ถึงขั้นใด และขั้นใดต้องให้คุณยืนยัน
- ไดเรกทอรีทำงาน: กำหนดว่าโดยปริยายทำงานในโปรเจกต์ใด
- MCP และส่วนขยาย: กำหนดว่ามีความสามารถภายนอกใดให้ใช้โดยปริยาย

แม้ไม่ตั้งค่าอะไร Codex ก็ยังทำงานได้ เพียงแต่คุณต้องเลือกค่าเดิมซ้ำบ่อยขึ้น

## เก็บการตั้งค่าไว้ที่ใด

| ระดับ | การใช้งาน |
|---|---|
| ผู้ใช้ | ค่าเริ่มต้นส่วนบุคคล ใช้ข้ามโปรเจกต์ |
| โปรเจกต์ | นโยบายร่วมของทีม (ต้องตรวจทานก่อน commit) |
| ตัวแปรสภาพแวดล้อม | ฉีด secret และสวิตช์ใน CI |

**พาธและชื่อไฟล์** เปลี่ยนได้ตามเวอร์ชัน CLI ให้ยึด [เอกสารอย่างเป็นทางการ](https://developers.openai.com/codex) เป็นหลัก โดยทั่วไปเป็น `config.toml` หรือไฟล์เทียบเท่าในไดเรกทอรีผู้ใช้

## ความเข้าใจผิดที่พบบ่อย

### ไม่ใช่ทุกค่าควรเขียนลงในโปรเจกต์

ผู้เริ่มต้นมักรวม “โมเดลเริ่มต้นที่ฉันชอบ” “พาธในเครื่องฉัน” และ “นโยบายอนุมัติที่ทั้งทีมต้องทำตาม” เข้าด้วยกัน

แบ่งให้ชัดกว่าได้ดังนี้:

- ความชอบส่วนตัวระยะยาว เก็บระดับผู้ใช้
- สิ่งที่ทุกคนใน repository นี้ควรใช้ตรงกัน เก็บระดับโปรเจกต์
- สิ่งที่ฉีดชั่วคราวเฉพาะ CI สคริปต์ หรือการรันครั้งหนึ่ง เก็บในตัวแปรสภาพแวดล้อม

### การตั้งค่าไม่ได้เปิดสิทธิ์ทันที

การเขียนนโยบายลงในค่าตั้งไม่ได้หมายความว่าทุกการกระทำในอนาคตจะผ่านโดยไม่มีเงื่อนไข พฤติกรรมจริงยังขึ้นอยู่กับจุดเข้าผลิตภัณฑ์ สภาพแวดล้อม นโยบายที่จัดการจากส่วนกลาง และเนื้อหางาน

ดังนั้น การตั้งค่าเป็นแนวโน้มเริ่มต้น ไม่ใช่สิทธิพิเศษถาวร

## รายการที่ปรับบ่อย

### โมเดลเริ่มต้นและระดับการให้เหตุผล

ส่งผลต่อความเร็ว ต้นทุน และอัตราสำเร็จของงานซับซ้อน ในงานสคริปต์แนะนำให้ **ตรึงโมเดล** เพื่อเปรียบเทียบ log ได้

### Sandbox และเครือข่าย

| เจตนาการตั้งค่า | คำอธิบาย |
|---|---|
| เข้มงวด | เหมาะกับ repository ที่ไม่น่าเชื่อถือ |
| มาตรฐาน | งานพัฒนาประจำวัน |
| ผ่อนคลาย | เฉพาะสภาพแวดล้อมส่วนตัวที่เชื่อถือได้และตรงตามนโยบายบริษัท |

แนวคิด: [Sandbox และเครือข่าย](/th/guide/foundations/sandbox-and-network/)

### นโยบายการอนุมัติ

CLI อาจถามก่อนรัน shell เขียนดิสก์ หรือเชื่อมต่อเครือข่าย ทีมควรระบุใน `AGENTS.md` ว่าคำสั่งใดคาดว่าจะอนุมัติอัตโนมัติได้—และจะมีผลเมื่อสอดคล้องกับพฤติกรรมจริงของผลิตภัณฑ์เท่านั้น

### รายการเซิร์ฟเวอร์ MCP

ใช้ค่าตั้งร่วมกับ [เชื่อมต่อเซิร์ฟเวอร์ MCP](/th/skills/mcp/connect-an-mcp-server/) และต้องเริ่มเซสชันใหม่หลังเปลี่ยน

## ลำดับการตั้งค่าที่เพียงพอ

เมื่อเริ่มใช้ ไม่ต้องศึกษาทุกฟิลด์ทันที ทำตามลำดับนี้จะง่ายกว่า:

1. ตรึงโมเดลที่ใช้บ่อยที่สุดก่อน
2. ยืนยันว่าไดเรกทอรีทำงานเริ่มต้นคือโปรเจกต์ปัจจุบัน
3. ตัดสินใจว่าการอนุมัติและ sandbox ควรระมัดระวังหรือผ่อนคลายเพียงใด
4. ค่อยเพิ่ม MCP ระบบอัตโนมัติ หรือส่วนขยายขั้นสูง

ลำดับนี้ใช้เพราะสองข้อแรกเกี่ยวกับการใช้งานประจำวันมากกว่า ส่วนสองข้อหลังเกี่ยวกับการควบคุมความเสี่ยงมากกว่า

## ทำให้โปรเจกต์กับ CLI สอดคล้องกัน

หลีกเลี่ยงกรณี “รันใน App ได้ แต่ล้มเหลวใน CI”:

1. ระบุเวอร์ชัน CLI ขั้นต่ำที่แนะนำใน README
2. เก็บเฉพาะค่าที่เป็น **ฉันทามติของทีม** ในการตั้งค่าระดับโปรเจกต์
3. ห้ามเก็บ secret ใน repository

## การแก้ปัญหา

| อาการ | ตรวจสอบ |
|---|---|
| การตั้งค่าไม่มีผล | แก้ผิดระดับหรือไม่ ต้องเริ่มใหม่หรือไม่ |
| MCP ไม่โหลด | ไวยากรณ์ JSON/TOML และพาธ |
| ขออนุมัติบ่อยเกินไป | โหมด sandbox และ allowlist |

เพิ่มเติม: [แก้ปัญหา CLI](/th/guide/cli/troubleshooting/)

ให้มองการตั้งค่า CLI เป็น “นิสัยการทำงานเริ่มต้น” และตรึงเฉพาะสิ่งที่คุณ **เลือกซ้ำแทบทุกครั้ง** ความสามารถขั้นสูงค่อยเพิ่มภายหลังได้
