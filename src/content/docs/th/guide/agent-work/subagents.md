**Agent ย่อย (Subagent)** คือหน่วยงานอิสระที่ Agent หลักเริ่มขึ้นเพื่อแก้ปัญหาย่อยที่ชัดเจน มีบริบทของตนเอง และเมื่อเสร็จจะส่งข้อสรุปกับหลักฐานกลับเธรดหลัก ส่วน Agent หลักยังรับผิดชอบการตัดสินใจโดยรวมและการตรวจรับขั้นสุดท้าย

![สถาปัตยกรรมการประสาน Agent ย่อยของ Codex: Agent หลักมอบหมายงานย่อยที่มีขอบเขต Agent ย่อยส่งหลักฐานกลับ และ Agent หลักรวบรวมพร้อมตรวจสอบ](/illustrations/flow-subagents.webp)

## ทำความเข้าใจความสัมพันธ์สามชั้นก่อน

| ชั้น | แยกจากกันหรือไม่ | ความหมาย |
|---|---|---|
| บริบทการสนทนา | แยก | Agent ย่อยแต่ละตัวจดจ่อกับงานของตน โดยไม่ต้องรับรายละเอียดทั้งหมดจากเธรดหลัก |
| Sandbox และโหมดสิทธิ์ | สืบทอด | Agent ย่อยไม่ได้สิทธิ์สูงขึ้นเพียงเพราะทำงานอิสระ |
| ไฟล์ใน workspace | ไม่เสมอไป | Agent หลายตัวอาจเห็น workspace เดียวกัน การเขียนไฟล์เดียวกันแบบขนานจะขัดแย้งกัน |

ประโยคสำคัญที่สุดคือ: **การแยกบริบทไม่เท่ากับการแยกไฟล์** หากจะแก้โค้ดแบบขนาน ให้แบ่งเจ้าของตามไดเรกทอรี คอมโพเนนต์ หรือ worktree ก่อน

## ใช้ได้ที่ใดในปัจจุบัน

Codex รุ่นปัจจุบันมีความสามารถ Agent ย่อยเป็นค่าเริ่มต้น และดูสถานะได้จาก UI ที่เกี่ยวข้องใน App บนเดสก์ท็อป, CLI และ IDE รายละเอียด UI อาจเปลี่ยน แต่แนวทางใช้งานที่คงที่คือ ขอให้ Codex มอบหมายงานย่อยอิสระอย่างชัดเจน และให้เธรดหลักเป็นผู้รวบรวมผล

ใน CLI ใช้ `/agent` เพื่อดูหรือสลับเธรดได้ IDE แสดง Agent เบื้องหลังใน UI ที่รองรับ และ App บนเดสก์ท็อปจะแสดงกิจกรรมของเธรดในงาน การมองเห็นตัวควบคุมใดขึ้นอยู่กับไคลเอนต์และความสามารถของบัญชีในขณะนั้น

## เมื่อใดควรแยกงาน

หากงานย่อยตรงอย่างน้อยสองในสามข้อต่อไปนี้ ควรพิจารณาแยก:

1. อธิบายแยกได้ โดยไม่ต้องซิงก์รายละเอียดของงานหลักบ่อย ๆ
2. มีสิ่งส่งมอบชัดเจน เช่น รายการไฟล์ ผลทดสอบ หรือข้อสรุปหนึ่งหน้า
3. ทำขนานกับงานอื่นได้ หรือการเจาะลึกแยกจะลดสัญญาณรบกวนในเธรดหลักได้มาก

### งานที่เหมาะกับการทำแบบขนาน

- ตรวจโครงสร้าง frontend, backend และความครอบคลุมของการทดสอบแบบอ่านอย่างเดียวแยกกัน
- ตรวจสอบการทดสอบที่ล้มเหลวหลายรายการซึ่งไม่พึ่งพากันพร้อมกัน
- รวบรวมหลักฐานของแนวทางเทคนิคสองแบบแยกกัน
- ให้บทบาทเฉพาะทำ security review, performance analysis หรือ documentation check

### งานที่ควรอยู่ในเธรดหลักมากกว่า

- ความต้องการยังไม่ชัดและต้องสนทนากับผู้ใช้อย่างต่อเนื่อง
- หลายขั้นตอนต้องทำตามลำดับอย่างเคร่งครัด
- การแก้ไขกระจุกอยู่ในไฟล์เดียวหรือโค้ดส่วนเดียว
- งานย่อยไม่มีเกณฑ์เสร็จที่ชัด เป็นเพียง “ลองดูคร่าว ๆ”

Agent ย่อยเพิ่มการใช้ token และต้นทุนในการรวบรวมผล งานเล็กที่ทำให้เสร็จได้ในเธรดเดียวอย่างชัดเจน ไม่จำเป็นต้องทำขนานเพียงเพื่อให้ได้ทำขนาน

## ความรับผิดชอบของ Agent หลักยังคงอยู่

Agent หลักควรเก็บสี่เรื่องนี้ไว้เสมอ:

- เป้าหมายโดยรวม ข้อจำกัดของผู้ใช้ และการตัดสินใจสุดท้าย
- ขอบเขตงานย่อยและเจ้าของไฟล์
- การตัดสินใจเมื่อข้อสรุปหลายชุดขัดแย้งกัน
- การทดสอบ การ build และคำอธิบายความเสี่ยงหลังรวมงาน

Agent ย่อยที่ส่งกลับว่า “เสร็จแล้ว” เป็นเพียงสัญญาณว่างานย่อยเสร็จ ไม่ใช่หลักฐานว่างานทั้งหมดเสร็จแล้ว

## เขียนสัญญามอบหมายที่ตรวจรับได้

ตัวอย่างงานตรวจสอบแบบอ่านอย่างเดียว:

```text
เริ่ม Agent ย่อยหนึ่งตัวเพื่อวิเคราะห์ logic การ refresh session ใน packages/auth แบบอ่านอย่างเดียว

ขอบเขต: packages/auth และ test ที่เกี่ยวข้อง ห้ามแก้ไฟล์
คำถาม: หลัง refresh ล้มเหลว token เก่ายังอาจถูกใช้ซ้ำหรือไม่
สิ่งส่งมอบ: ข้อสรุป ไฟล์และเลขบรรทัดสำคัญ เส้นทางทำซ้ำ และ test ที่แนะนำ
การตรวจสอบ: ทุกข้อสรุปต้องตรวจเทียบได้จาก source code หรือ test ที่มีอยู่
ผลตอบกลับ: ไม่เกิน 500 คำ และให้เธรดหลักตัดสินใจว่าจะแก้หรือไม่
```

ข้อความนี้ระบุหกเรื่องชัดเจน: รับผิดชอบอะไร ดูที่ไหน ตอบอะไร ห้ามอะไร ตรวจอย่างไร และใครเป็นผู้ตัดสินใจ

## ตัวอย่างการทำขนานสามทาง

สมมติว่าฟีเจอร์เข้าสู่ระบบเกิด regression เป็นครั้งคราว Agent หลักอาจแยกงานดังนี้:

| งานย่อย | สิทธิ์และขอบเขต | สิ่งส่งมอบ |
|---|---|---|
| A: เส้นทางโค้ด | อ่านอย่างเดียวใน `src/auth/` | call chain จากทางเข้าถึง branch ที่ล้มเหลว |
| B: หลักฐานจาก test | อ่าน test และ log อย่างเดียว | test ขั้นต่ำที่ทำซ้ำได้เสถียร |
| C: การเปลี่ยนแปลงล่าสุด | อ่านประวัติ Git ที่เกี่ยวข้องอย่างเดียว | การเปลี่ยนแปลงที่น่าจะทำให้เกิด regression มากที่สุดพร้อมเหตุผล |

หลังผลทั้งสามกลับมา Agent หลักควรเปรียบเทียบหลักฐานก่อนเลือกแนวทางแก้ อย่าให้ A, B และ C แก้ `src/auth/session.ts` พร้อมกัน

## แยกงานอย่างไรเมื่อต้องเขียนแบบขนาน

ลดความขัดแย้งตามลำดับนี้:

1. แยกงานเขียนไปยังไดเรกทอรีหรือคอมโพเนนต์ที่ไม่ทับซ้อนกัน
2. จัดสรร worktree หรือ branch แยกสำหรับ implementation แบบขนาน
3. ระบุรายการไฟล์ที่ Agent แต่ละตัวแก้ได้อย่างชัดเจน
4. ให้ Agent หลักรวมงาน และรันการตรวจสอบใหม่หลังรวม

แม้ test ของแต่ละงานย่อยจะผ่าน เมื่อนำมารวมกันยังอาจล้มเหลว จึงห้ามข้ามการตรวจสอบขั้นสุดท้าย

## เช็กลิสต์ตรวจรับ

- ผลตอบกลับตอบคำถามเดิมหรือขยายขอบเขตออกไป
- มีหลักฐานที่ตรวจได้ เช่น ตำแหน่งไฟล์ log หรือ test หรือไม่
- ปฏิบัติตามข้อจำกัดแบบอ่านอย่างเดียว ไดเรกทอรี หรือคำสั่งหรือไม่
- ผลลัพธ์หลายชุดขัดแย้งกันหรือไม่ และจัดการความขัดแย้งนั้นอย่างชัดเจนแล้วหรือยัง
- รัน test และ build แบบเต็มอีกครั้งหลังรวมแล้วหรือยัง
- ระบุปัญหาที่ยังไม่แก้และความเสี่ยงคงเหลือหรือไม่

## ใช้ร่วมกับความสามารถอื่น

- **Skill** กำหนดวิธีและรูปแบบเอาต์พุตของงานย่อยให้คงที่ เช่น เช็กลิสต์ code review
- **MCP** ให้ Agent ย่อยเข้าถึงเครื่องมือหรือข้อมูลภายนอกอย่างมีการควบคุม
- **Hook** เพิ่มกฎป้องกันเมื่อ Agent ย่อยเริ่ม หยุด หรือเรียกเครื่องมือ
- **Worktree** แยกการแก้ไฟล์แบบขนาน โดยแก้ความขัดแย้งใน workspace ไม่ใช่ปัญหาบริบท
