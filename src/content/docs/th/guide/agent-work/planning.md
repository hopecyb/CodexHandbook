ผลลัพธ์ของการวางแผนคือเส้นทางดำเนินงานที่ตรวจและปรับได้ ช่วยให้พบช่องโหว่ด้านขอบเขต การพึ่งพา และเกณฑ์ยอมรับล่วงหน้า แต่ไม่ได้หมายความว่ายิ่งงานใหญ่ยิ่งต้องหยุดรอยืนยันซ้ำ ๆ

เริ่มจากใช้ [การแบ่งระดับงาน](/th/prompts/ask-for-a-plan/) เพื่อตัดสินใจว่าจะทำให้เสร็จทันที วางแผนแล้วลงมือภายในสิทธิ์ที่มี หรือรอบนี้ทำเฉพาะข้อเสนอ คำขอที่ระบุชัดว่า “เสนอแผนก่อน ห้ามแก้ไฟล์” ต้องคงเป็นแบบอ่านอย่างเดียว ส่วนงานที่ขอให้นำไปใช้จริงไม่ควรจบเพียงการส่งแผน

## แผนที่เพียงพอต่อการใช้งาน

| องค์ประกอบ | ต้องละเอียดเพียงใด |
|---|---|
| เป้าหมาย | อธิบายพฤติกรรมที่สังเกตได้หลังทำเสร็จ |
| ขอบเขต | ระบุไฟล์ อินพุต และสิ่งที่ไม่รวมให้ชัด |
| ลำดับ | ระบุการพึ่งพาที่แท้จริง ไม่ถือทุกการเรียกเครื่องมือเป็นหนึ่งขั้นตอน |
| การตรวจสอบ | ระบุเอาต์พุตหรือการตรวจที่พิสูจน์ได้ว่างานเสร็จ |
| ข้อแลกเปลี่ยน | ระบุเฉพาะการตัดสินใจที่ยังไม่มีคำตอบและมีผลต่อผลลัพธ์ |

ตัวอย่างเช่น หากเพิ่มการจัดกลุ่มข้อมูลให้รายงานเดิม อาจวางแผนว่า “ตรวจนิยามข้อมูล → แก้การสรุปและการแสดงผล → ใช้ตัวอย่างตรวจยอดรวมและแต่ละกลุ่ม” ไม่จำเป็นต้องขออนุมัติแยกทุกครั้งที่อ่านไฟล์ แก้ไข หรือทดสอบ

## คำขอแผนสองแบบที่ต่างกัน

**ยังไม่กำหนดแนวทาง:**

```text
รอบนี้วิเคราะห์แบบอ่านอย่างเดียว เปรียบเทียบการพึ่งพา ความเข้ากันได้ และค่าบำรุงรักษาของวิธีส่งออกสองแบบ
เสนอคำแนะนำและข้อแลกเปลี่ยนที่ฉันต้องตัดสินใจ โดยไม่แก้ implementation
```

**กำหนดขอบเขตแล้วและต้องนำไปใช้ให้เสร็จ:**

```text
ทำ CSV export ให้เสร็จตามข้อกำหนดที่มี ตรวจ repository และสรุปแผนสั้น ๆ ก่อน
จากนั้นนำไปใช้และตรวจสอบต่อเนื่องภายในขอบเขตที่ตกลง โดยไม่ต้องหยุดรอทีละขั้น
หากจำเป็นต้องเพิ่ม service เปลี่ยน public interface หรือขยายการเข้าถึงข้อมูล ให้ระบุเหตุผลที่ชัดเจนก่อน
```

ข้อความทั้งสองเป็นตัวอย่างที่ออกแบบสำหรับเว็บไซต์นี้ การปรากฏของหน้าต่างอนุมัติในผลิตภัณฑ์ขึ้นอยู่กับเครื่องมือ นโยบาย และสิทธิ์จริง

## ปรับแผนระหว่างดำเนินการอย่างไร

- พบรายละเอียด implementation ทั่วไป: อัปเดตแผนและทำงานในขอบเขตที่ได้รับอนุญาตต่อให้เสร็จ
- สมมติฐานเดิมไม่จริง: แสดงหลักฐานและผลกระทบ แล้วเสนอทางเลือกภายในขอบเขต
- มีข้อแลกเปลี่ยนที่ผู้ใช้ต้องตัดสินใจ: ถามคำถามเฉพาะเจาะจง และทำส่วนที่ไม่ต้องรอคำตอบต่อ
- ต้องทำการกระทำภายนอกที่ยังไม่ได้รับอนุญาต: เตรียมผลลัพธ์ที่ตรวจทานได้ก่อน แล้วขอสิทธิ์ที่เกี่ยวข้องก่อนลงมือ

อย่าถือว่า “อาจเจอปัญหา” เป็นเหตุให้หยุดงาน และอย่าฝืนทำตามแผนจนมองข้ามการเปลี่ยนแปลงขอบเขตที่เกิดขึ้นแล้ว

## วิธีให้ข้อเสนอแนะต่อแผน

```text
คงขั้นตอนที่ 1 และ 2 ไว้ ตัดส่วน refactor ออก
รอบนี้ทำเฉพาะ local preview ไม่ publish
เพิ่มเกณฑ์ยอมรับหนึ่งข้อ: ยังอ่านรูปแบบไฟล์เก่าได้ถูกต้อง
```

ข้อเสนอแนะจะเปลี่ยนเฉพาะส่วนที่ระบุชัด ข้อจำกัดและเกณฑ์เสร็จสิ้นที่ไม่ได้ยกเลิกยังคงมีผล เมื่องานหยุดชะงัก ให้บันทึกไฟล์ปัจจุบัน การตรวจสอบที่ทำเสร็จแล้ว และขั้นตอนถัดไปไว้ใน [บันทึกส่งต่องาน](/th/guide/agent-work/handoff-and-resume/)

## เมื่อเสร็จแล้วให้กลับมาดูหลักฐาน

ตรวจว่าเป้าหมายในแผนเป็นจริงแล้ว ไม่ใช่ดูเพียงว่าติ๊กครบทุกขั้นตอนหรือไม่ การทดสอบที่ไม่ได้รัน หน้าตัวอย่างที่ไม่ได้ตรวจ และข้อเท็จจริงที่ไม่ได้ยืนยัน ต้องบันทึกไว้อย่างชัดเจน ดูกระบวนการฉบับเต็มที่ [สำรวจ—วางแผน—ลงมือ—ตรวจสอบ](/th/cases/workflows/explore-plan-execute-verify/)
