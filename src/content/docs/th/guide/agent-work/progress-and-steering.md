เมื่อทิศทางเริ่มคลาดระหว่างดำเนินงาน ปฏิกิริยาที่พบบ่อยมักมีเพียงสองแบบ:

- ไม่พูดอะไรและปล่อยให้ทำผิดต่อไป
- บอกว่า “หยุด เริ่มใหม่ทั้งหมด”

วิธีที่ใช้ได้บ่อยกว่าคือ **กำกับทิศทาง** ต่อเนื่องระหว่างทำงาน เก็บส่วนที่ถูกไว้และแก้เฉพาะส่วนที่คลาด

## การกำกับทิศทางทำอะไร

“การกำกับทิศทาง” ในที่นี้คือการเสริมว่าขั้นตอนปัจจุบันควรเดินต่ออย่างไร เช่น:

- ส่วนใดถูกแล้ว ให้เก็บไว้
- ส่วนใดเริ่มคลาด ให้หยุด
- ต่อไปให้ทำขั้นตอนไหนก่อน

## “การกำกับทิศทาง” คืออะไร

การกำกับทิศทางคือการ **ปรับทิศเฉพาะจุด** จากสถานะดำเนินงานปัจจุบัน

มักจำเป็นในกรณีเหล่านี้:

- เข้าใจเป้าหมายถูก แต่ลำดับขั้นตอนไม่เหมาะ
- ทำถูกไปครึ่งหนึ่งแล้วและไม่ต้องการรื้อทั้งหมด
- คุณเพิ่งให้ข้อมูลใหม่ จึงต้องปรับการกระทำถัดไป
- คุณเห็นว่ากำลังจะเข้าสู่การ refactor หรือขยายเนื้อหาที่ไม่จำเป็น

## แม่แบบที่ใช้บ่อยที่สุด

คำสั่งกำกับทิศทางกลางงานสั้นมากได้:

```text
หยุดที่ขั้นตอนปัจจุบัน เก็บ A และ B ไว้ ยกเลิกทิศทางการแก้ C ขั้นตอนถัดไปทำเฉพาะ D และอย่าเริ่ม E
```

คำสั่งประเภทนี้มีองค์ประกอบสำคัญสี่ข้อ:

1. หยุดตรงไหน
2. เก็บอะไรไว้
3. ยกเลิกอะไร
4. ขั้นตอนถัดไปทำอะไรเพียงอย่างเดียว

## ความเข้าใจผิดที่พบบ่อย

### 1. เมื่อพบว่าคลาด ควรหยุดทั้งหมดแล้วเริ่มใหม่หรือไม่

หากครึ่งหนึ่งถูกต้องแล้ว การรื้อทั้งหมดมักหมายความว่า:

- คุณต้องอธิบายพื้นหลังใหม่
- ส่วนที่ตรงกันแล้วถูกทิ้งไปด้วย
- รอบใหม่อาจคลาดอีกครั้ง

### 2. แค่บอกว่า “ไม่ถูก” ก็ควรรู้เองว่าผิดตรงไหน

โดยทั่วไปยังไม่พอ

วิธีที่มีประสิทธิภาพกว่าคือระบุให้ชัดว่า:

- เก็บอะไรไว้
- ยกเลิกอะไร
- ตอนนี้ให้อะไรมาก่อน

### 3. การกำกับทิศทางกับการวางแผนใหม่เหมือนกันหรือไม่

- **การกำกับทิศทาง**: เส้นทางโดยรวมถูก แก้เฉพาะจุด
- **การวางแผนใหม่**: เป้าหมาย สมมติฐาน หรือขอบเขตผลกระทบเปลี่ยนแล้ว

## เหตุใดการปรับทีละน้อยจึงมีประสิทธิภาพกว่า

| ปรับทีละน้อย | รื้อทำใหม่ |
|---|---|
| เก็บงานที่ตรงกันแล้ว | ทิ้งส่วนที่ทำถูกไปด้วย |
| ใช้บริบทน้อยกว่า | ต้องอธิบายพื้นหลังใหม่ |
| ควบคุมขอบเขตง่ายกว่า | คลาดอีกครั้งได้ง่าย |
| คล้ายการทำงานร่วมกันจริง | คล้ายสั่งงานซ้ำ |

## เมื่อใดควรกำกับทิศทาง และเมื่อใดควรกลับไปวางแผน

ใช้หลักนี้ตัดสินได้:

- **แค่ลำดับผิด ขอบเขตกว้างเกิน หรือรูปแบบเอาต์พุตผิด**: กำกับทิศทางก่อน
- **เป้าหมาย สมมติฐาน หรือขอบเขตผลกระทบเปลี่ยน**: กลับไปวางแผน

## วิธีการกำกับทิศทางที่พบบ่อยสามแบบ

### 1. ลดขอบเขต

เมื่อเริ่มทำใหญ่เกินไป:

```text
ตอนนี้จัดการเฉพาะหน้าเข้าสู่ระบบ อย่าขยายไปยังขั้นตอนสมัครและกู้คืนรหัสผ่าน
```

### 2. ปรับลำดับ

เมื่อสิ่งที่ทำไม่ผิด แต่ลำดับไม่เหมาะ:

```text
เพิ่มการตรวจสอบและการทดสอบก่อน แล้วค่อยแก้ implementation ต่อ
```

### 3. เปลี่ยนรูปแบบเอาต์พุต

เมื่อต้องการดูการวิเคราะห์ก่อนลงมือจริง:

```text
ยังไม่ต้องแก้ไฟล์ ทำตารางเปรียบเทียบความแตกต่างระหว่างแนวทางปัจจุบันกับแนวทางที่คุณแนะนำก่อน
```

## คำสั่งกำกับทิศทางที่ดีควรมีอะไร

- จุดที่ต้องหยุดตอนนี้
- ส่วนที่ต้องเก็บไว้
- ทิศทางที่ห้ามทำต่อ
- ลำดับความสำคัญใหม่
- อนุญาตให้ทำต่อหรือไม่

ประโยคต่อไปนี้ชัดเจนพอ:

```text
คงข้อวินิจฉัยสาเหตุของปัญหาไว้ แต่ยังไม่ต้อง refactor ขั้นตอนถัดไปเสนอเฉพาะวิธีแก้ขั้นต่ำและขั้นตอนตรวจสอบ
```

## เมื่อใดควรกลับไป “วางแผนใหม่”

การกำกับทิศทางเหมาะกับความคลาดเคลื่อนเฉพาะจุด แต่กรณีต่อไปนี้ควรกลับไปที่ [การวางแผน](/th/guide/agent-work/planning/):

- เป้าหมายของงานเปลี่ยนไป
- ข้อมูลใหม่หักล้างสมมติฐานเดิม
- ขอบเขตผลกระทบขยายชัดเจน
- คุณปรับทิศติดต่อกันสองสามครั้งแล้วยังคลาดอยู่

หากปัญหาไม่ใช่ความคลาดเคลื่อนเฉพาะจุดแล้ว ให้กลับสู่ขั้นวางแผนโดยตรง

## ข้อผิดพลาดที่พบบ่อย

- บอกเพียงว่า “ไม่ถูก” โดยไม่ระบุว่าตรงไหน
- ให้ “ตัดสินใจเองว่าจะแก้อย่างไร” แต่ไม่กำหนดลำดับความสำคัญ
- ต้องการหยุดเพียงหนึ่งขั้น แต่ใช้คำที่ทำให้เริ่มทำใหม่ทั้งหมด
- งานกลายเป็นงานใหม่แล้ว แต่ยังพยายามฝืนต่อด้วยคำอธิบายเสริมหนึ่งประโยค

เมื่อพบความคลาดระหว่างดำเนินงาน ใช้คำสั่งสั้น ๆ ระบุว่า “เก็บอะไร หยุดอะไร และขั้นตอนถัดไปทำอะไรเพียงอย่างเดียว”
