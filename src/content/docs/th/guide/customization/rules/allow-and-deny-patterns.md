**Rules (กฎ)** ใช้ระบุในไฟล์การตั้งค่าหรือไฟล์โปรเจกต์ว่า Agent ได้รับอนุญาตหรือถูกห้ามไม่ให้ใช้คำสั่ง shell เข้าถึงพาธ หรือเรียกเครื่องมือใดบ้าง เพื่อลดการกดอนุมัติด้วยตนเองทุกครั้ง พร้อมป้องกันไม่ให้การดำเนินการที่เป็นอันตรายทำงานโดยอัตโนมัติ

## เนื้อหา

- วิธีทำงานของกฎ Allow / Deny
- ความสัมพันธ์กับ Sandbox หน้าต่างอนุมัติ และ `AGENTS.md`
- ตัวอย่างกฎสำหรับทีม

## กฎทำอะไรจริง ๆ

หากคำว่า “กฎ” ยังฟังดูเป็นนามธรรม ให้เริ่มจากมองว่าเป็นการตกลงล่วงหน้าว่า Codex ทำอะไรได้และทำอะไรไม่ได้ จึงไม่ต้องพึ่งการตัดสินใจเฉพาะหน้าและการกดอนุมัติด้วยตนเองทุกครั้ง

กฎมีประโยชน์หลักสองด้าน:

- ลดการยืนยันซ้ำสำหรับการดำเนินการความเสี่ยงต่ำที่เกิดขึ้นทุกวัน
- สกัดกั้นการดำเนินการความเสี่ยงสูงที่ไม่ควรเกิดขึ้นโดยอัตโนมัติไว้ล่วงหน้า

## ประเภทของกฎ (เชิงแนวคิด)

| ประเภท | ตัวอย่าง |
|---|---|
| allowlist ของคำสั่ง | อนุญาต `npm test` และ `git status` |
| denylist ของคำสั่ง | ห้าม `rm -rf` และ `curl \| bash` |
| พาธ | ห้ามเขียนไปยัง `../` และห้ามอ่าน `~/.ssh` |
| เครือข่าย | ห้ามออกอินเทอร์เน็ต หรืออนุญาตเฉพาะโดเมน registry |

เปรียบเทียบกับ [เมทริกซ์สิทธิ์](/th/guide/reference/permission-matrix/): กฎคือ **กลไกบังคับใช้ที่กำหนดค่าได้** ส่วนเมทริกซ์อธิบาย **ค่าเริ่มต้นโดยทั่วไป**

## การแบ่งชั้นที่แนะนำ

```text
นโยบายที่องค์กรจัดการ (เขียนทับไม่ได้)
    ↓
rules ของโปรเจกต์ + AGENTS.md (Review ผ่าน Git)
    ↓
allowlist ส่วนบุคคลเพิ่มเติม (เฉพาะเครื่องนี้)
    ↓
ข้อจำกัดในพรอมต์สำหรับงานครั้งเดียว
```

## ความเข้าใจผิดที่พบบ่อย

### กฎไม่ได้มีไว้เพียงเพื่อลดหน้าต่างอนุมัติ

เมื่อได้ยินคำว่า allowlist ครั้งแรก หลายคนมักคิดทันทีว่าเป้าหมายคือการลดหน้าต่างอนุมัติและลดการขัดจังหวะ

การมีหน้าต่างน้อยลงเป็นเพียงประโยชน์ส่วนหนึ่ง สิ่งสำคัญกว่าคือการปล่อยผ่านการดำเนินการความเสี่ยงต่ำ และสกัดกั้นการดำเนินการความเสี่ยงสูง

### กฎไม่ใช่ Sandbox

Sandbox จำกัดว่า “เข้าถึงได้ไกลที่สุดแค่ไหน” ส่วนกฎกำหนดว่า “โดยหลักแล้วไม่ควรทำการดำเนินการใด”

ควรใช้ทั้งสองอย่างร่วมกัน ไม่ใช่เลือกอย่างหนึ่งมาแทนอีกอย่าง

### ข้อกำหนดขั้นต่ำของทีมไม่ควรอยู่เฉพาะในเครื่องของคนใดคนหนึ่ง

หากข้อห้าม “ห้าม push” และ “ห้ามแตะ `.env`” ถูกบันทึกไว้เฉพาะในกฎบนเครื่องของคุณ คนอื่นก็ยังอาจพลาดทำสิ่งเหล่านี้ได้

ควรวางข้อกำหนดขั้นต่ำของทีมไว้ในตำแหน่งที่ Review ได้ให้มากที่สุด

## ตัวอย่างสำหรับทีม (เพื่อประกอบแนวคิด ไม่ควรคัดลอกไปใช้ทันที)

**อนุญาต:**

- ให้ Package Manager ติดตั้ง Dependency **ภายในโปรเจกต์**
- รันสคริปต์ทดสอบที่ระบุในเอกสาร

**ปฏิเสธ:**

- `git push` และ `git reset --hard`
- อ่านหรือเขียน `.env*` (เว้นแต่งานจะระบุอย่างชัดเจน)
- ส่งคำขอ POST ที่มีเนื้อหาจาก repository ไปยังอินเทอร์เน็ตสาธารณะ

ควรเขียนกฎไว้ในไฟล์ที่ทีม Review ได้ ไม่ใช่ตกลงกันด้วยวาจาเท่านั้น

## ข้อผิดพลาดที่พบบ่อย

- Allowlist กว้างเกินไป (การอนุญาต `bash` เท่ากับอนุญาตทุกอย่าง)
- ใช้เฉพาะ deny โดยไม่มี allow ทำให้ยังต้องอนุมัติมากเกินไป
- กฎขัดแย้งกับ `AGENTS.md`

## คำแนะนำสำหรับการเริ่มต้น

เมื่อเริ่มจัดระเบียบกฎ ไม่จำเป็นต้องสร้างนโยบายฉบับสมบูรณ์ทันที เพียงเริ่มจากสองขั้นตอนนี้ก็เพียงพอแล้ว:

1. ระบุคำสั่งความเสี่ยงต่ำที่ใช้ทุกวันอย่างชัดเจน 3 ถึง 5 รายการ
2. ระบุการดำเนินการความเสี่ยงสูงที่ไม่ต้องการให้ทำโดยอัตโนมัติอย่างเด็ดขาดสักสองสามรายการ

เริ่มจากทำให้ขอบเขตขั้นต่ำใช้งานได้ราบรื่น แล้วค่อยปรับให้ละเอียดขึ้น

## ขอบเขตความปลอดภัย

- กฎ **ไม่สามารถ** แทนที่ Code Review และการป้องกัน branch ได้
- พรอมต์ประสงค์ร้ายอาจชักนำให้ Agent พยายามหลบเลี่ยงกฎ ดังนั้นให้คงค่าเริ่มต้นของ Sandbox ไว้ในระดับเข้มงวด
- เปลี่ยนกฎผ่าน PR และปฏิบัติต่อการเปลี่ยนแปลงเช่นเดียวกับการแก้ CI

กฎ allow/deny ที่ดีคือการระบุไว้ล่วงหน้าอย่างชัดเจนว่าการดำเนินการใดสมเหตุสมผล และการดำเนินการใดไม่ควรเกิดขึ้น
