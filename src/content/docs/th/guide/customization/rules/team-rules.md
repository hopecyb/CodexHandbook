เมื่อทีมใช้ Codex **กลยุทธ์กฎ**จะตอบว่า ข้อจำกัดใดต้องใช้ร่วมกันทั้งบริษัท ข้อจำกัดใดให้รีโพซิทอรีดูแล และบุคคลยังผ่อนปรนได้หรือไม่ บทนี้นำเสนอ [กฎคำสั่ง](/th/guide/customization/rules/command-rules/) และ [รูปแบบการอนุญาตและปฏิเสธ](/th/guide/customization/rules/allow-and-deny-patterns/) จากมุมมองด้านการกำกับดูแล

## เนื้อหา

- นโยบายแบบ Managed ขององค์กร vs กฎของโปรเจกต์ vs การตั้งค่าส่วนบุคคล
- กระบวนการตรวจทานและเผยแพร่การเปลี่ยนแปลงกฎ
- การทำงานร่วมกับ `AGENTS.md`, Hook และ CI

## กลยุทธ์กฎสำหรับทีมมีไว้ทำอะไร

กลยุทธ์กฎสำหรับทีมตอบว่า ขอบเขตใดบริษัทควรกำหนดให้เป็นมาตรฐานเดียวกัน ขอบเขตใดให้แต่ละโปรเจกต์กำหนดเอง และขอบเขตใดเป็นเพียงความเคยชินส่วนบุคคล

หากแบ่งชั้นนี้ไม่ชัดเจน ปัญหาสองแบบต่อไปนี้จะเกิดขึ้นได้ง่าย:

- กฎที่ควรใช้ร่วมกันทั้งทีมกลับมีอยู่ในคอมพิวเตอร์ของใครบางคนเท่านั้น
- การตั้งค่าส่วนบุคคลที่ทำขึ้นเพื่อความสะดวกชั่วคราวกลับถูกเข้าใจผิดว่าเป็นมาตรฐานของทีม

## เหมาะกับใคร

| บทบาท | ประเด็นที่ให้ความสำคัญ |
|---|---|
| หัวหน้าฝ่ายวิศวกรรม | deny ขั้นต่ำและข้อกำหนดด้านการตรวจสอบ |
| ผู้ดูแลรีโพซิทอรี | allowlist ของโปรเจกต์และคำสั่งทดสอบ |
| นักพัฒนารายบุคคล | การตั้งค่าเพิ่มเติมในเครื่องภายในขอบเขตที่นโยบายอนุญาต |

## ความเข้าใจผิดที่พบบ่อย

### กฎสำหรับทีมไม่จำเป็นต้องยิ่งเป็นหนึ่งเดียวกันมากเท่าไรก็ยิ่งดี

ขอบเขตบางอย่างควรใช้ร่วมกันทั้งองค์กรจริง เช่น deny สำหรับการกระทำความเสี่ยงสูง

แต่หากบังคับให้ทุกรีโพซิทอรีใช้กฎเหมือนกันทุกประการ ก็จะเกิดอีกปัญหาหนึ่ง คือกฎกว้างหรือแคบเกินไป จนสุดท้ายไม่มีใครเชื่อถือกฎนั้นจริง ๆ

ดังนั้นสิ่งสำคัญคือแยกขอบเขตระดับองค์กร ระดับโปรเจกต์ และระดับบุคคลให้ชัดเจน ไม่ใช่ทำให้กฎทั้งหมดมีรูปแบบเดียวกัน

### การตั้งค่าส่วนบุคคลไม่ควรลดความเข้มงวดขั้นต่ำของทีม

คุณเพิ่มการตั้งค่าเพื่อความสะดวกในคอมพิวเตอร์ของตนเองได้ ตราบใดที่ไม่หลีกเลี่ยงข้อกำหนดขั้นต่ำที่ทีมหรือองค์กรกำหนดไว้แล้ว

ไม่เช่นนั้น สิ่งที่ภายนอกดูเหมือน “ทำงานในเครื่องได้มีประสิทธิภาพขึ้น” แท้จริงแล้วกำลังวางกับระเบิดไว้ในการทำงานร่วมกัน

## โมเดลการแบ่งชั้นที่แนะนำ

```text
L1 การจัดการโดยองค์กร (Managed)      → โปรเจกต์/บุคคล override ไม่ได้
L2 รีโพซิทอรีเทมเพลตของทีม          → ส่วนของ rules ที่รีโพซิทอรีใหม่สืบทอด
L3 rules ของโปรเจกต์ + AGENTS.md     → ตรวจทานผ่าน Git PR
L4 การกำหนดค่าส่วนบุคคล              → เฉพาะเครื่อง ห้ามลดความเข้มงวดของ L1
L5 พรอมต์สำหรับงานครั้งเดียว          → เพิ่มความเข้มงวดชั่วคราวได้ แต่การผ่อนปรนชั่วคราวยังถูก L1 จำกัด
```

ให้นึกเทียบกับ [ขอบเขตของ AGENTS.md](/th/guide/customization/agents-md/scope-and-precedence/): **กฎเน้น enforcement ระหว่างการดำเนินการ ส่วน AGENTS.md เน้นคำอธิบายพฤติกรรม** ทั้งสองส่วนควรสอดคล้องกัน และไม่ควรเขียนข้อกำหนดคนละชุดจนขัดแย้งกัน

## แนวทางพื้นฐาน

1. **เขียนรายการ “ห้ามทำโดยเด็ดขาด” ก่อน** (deny): `git push --force`, อ่าน `~/.ssh`, ส่งเนื้อหารีโพซิทอรีไปยังอินเทอร์เน็ตสาธารณะด้วย POST
2. **จากนั้นเขียนรายการ “อนุญาตในงานประจำ”** (allow): การทดสอบ, lint, git แบบอ่านอย่างเดียว
3. **เผยแพร่ L1 แบบ Managed** (หากองค์กรเปิดใช้ Managed configuration แล้ว)
4. **แต่ละ service/แพ็กเกจย่อยใน Monorepo** เพิ่ม L3 ได้ แต่ต้องไม่ขัดแย้งกับ L1
5. **ทบทวนรายไตรมาส**: นำรายการ “บล็อกผิด” และ “ปล่อยผ่านผิด” ที่เกิดซ้ำในบันทึกการอนุมัติกลับไปปรับปรุงผ่าน PR ของกฎ

## workflow ที่แนะนำ: การเปลี่ยนแปลงกฎ

```text
ข้อเสนอ (issue หรือ RFC) → Review โดยทีมความปลอดภัย/แพลตฟอร์ม → PR แก้ไขไฟล์กฎ
    → ทดลองรันงานตัวอย่างในรีโพซิทอรี staging → merge → ประกาศ + อัปเดตหน้าคู่มือ
```

การเปลี่ยนแปลงครั้งใหญ่ (เช่น เปิดการเชื่อมต่อเครือข่ายออกภายนอก) ควรอัปเดต [การตรวจสอบด้วย Hook](/th/skills/hooks/hooks-overview/) และ [acceptable use](/th/guide/team-enterprise/governance/acceptable-use/) ไปพร้อมกัน

## ทำให้สอดคล้องกับ Hook และ CI

| กลไก | หน้าที่ |
|---|---|
| กฎ | อนุญาต/ปฏิเสธก่อนดำเนินการ |
| Hook | การตรวจสอบที่ซับซ้อน บันทึก และรูปแบบการปฏิบัติตามข้อกำหนด |
| CI | ประตูควบคุมก่อน merge และสคริปต์ที่ใช้แหล่งเดียวกับกฎในเครื่อง |

หลีกเลี่ยงการเขียนตรรกะสามชุดแยกกัน ให้ใช้ **แหล่งอ้างอิงหลักเพียงแหล่งเดียว** (เช่น `tools/codex-rules.json`) ที่ CLI และ CI อ้างอิงร่วมกันเป็นลำดับแรก

## ข้อผิดพลาดที่พบบ่อย

- ตกลงกันด้วยวาจาเพียงว่า “ห้าม push” แต่ไม่อัปเดตไฟล์กฎ
- หลังผ่อนปรนแซนด์บ็อกซ์ในเครื่องส่วนตัวแล้ว นำภาพหน้าจอมาอ้างเป็น “มาตรฐานของทีม”
- โปรเจกต์ย่อยใน Monorepo มีความต้องการต่างกัน แต่กลับใช้ allowlist ส่วนกลางชุดเดียวที่กว้างเกินไป
- เปลี่ยนกฎโดยไม่ประกาศ ทำให้เพื่อนร่วมทีมพบว่าการอนุมัติจำนวนมากล้มเหลวอย่างกะทันหัน

## ตัดสินใจว่ากฎควรอยู่ชั้นใด

พิจารณาจากคำถามสามข้อต่อไปนี้:

1. กฎนี้เป็นข้อกำหนดขั้นต่ำที่ทุกรีโพซิทอรีต้องปฏิบัติตามหรือไม่
2. กฎนี้ใช้กับโปรเจกต์ปัจจุบันเท่านั้นหรือไม่
3. กฎนี้เป็นเพียงสิ่งที่ฉันเพิ่มเพื่อให้ตนเองทำงานสะดวกขึ้นหรือไม่

โดยทั่วไปจะตรงกับ:

- ระดับองค์กร
- ระดับโปรเจกต์
- ระดับบุคคล

## ขอบเขตความปลอดภัย

- กฎไม่สามารถแทนที่ [โมเดลภัยคุกคาม](/th/guide/team-enterprise/security/threat-model/) และกระบวนการตอบสนองต่อเหตุการณ์ได้
- เมื่อเกี่ยวข้องกับข้อมูลที่อยู่ภายใต้ข้อกำกับ ต้องตรวจทานกฎร่วมกับการจัดชั้นข้อมูลและนโยบายการเก็บรักษา
- การข้ามข้อกำหนดในกรณีฉุกเฉินต้องมี **บันทึกการตรวจสอบ** และการทบทวนย้อนหลัง

## รายการตรวจรับ

- [ ] วาดภาพการแบ่งหน้าที่ L1–L3 ขององค์กรได้
- [ ] ไฟล์กฎในรีโพซิทอรีมีผู้รับผิดชอบและข้อกำหนด Review ที่ชัดเจน
- [ ] ไม่ขัดแย้งกันระหว่าง `AGENTS.md`, Hook และ CI
- [ ] มีช่องทางรับข้อเสนอแนะเรื่อง “บล็อกผิด” (เทมเพลต issue หรือแบบฟอร์มภายใน)

สิ่งสำคัญที่สุดของกลยุทธ์กฎสำหรับทีมคือแยกให้ชัดก่อนว่า “ใครเป็นผู้กำหนดขอบเขตแต่ละชั้น” แล้วจึงตัดสินใจว่าจะเขียนกฎอย่างไร
