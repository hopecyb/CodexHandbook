`AGENTS.md` คือ **คำสั่งโปรเจกต์ในรูปแบบ Markdown** ที่วางไว้ในรีโพซิทอรี (หรือไดเรกทอรีย่อย) Codex จะอ่านเมื่อเข้าสู่โปรเจกต์ เพื่อให้รูปแบบการเขียนโค้ด ข้อกำหนดการทดสอบ มาตรฐานการ commit และข้อห้ามสอดคล้องกัน

ให้มอง `AGENTS.md` เป็นคู่มือที่บอกว่า “โปรเจกต์นี้ต้องการให้ Codex ทำงานร่วมกันอย่างไร”

มันไม่ใช่เอกสารสถาปัตยกรรมระดับสูงหรือคู่มือฉบับเต็มสำหรับพนักงานใหม่ที่เป็นมนุษย์ แต่เป็นกฎการทำงานร่วมกันในโปรเจกต์สำหรับ Codex

![ภาพประกอบ: ภาพตัดขวางของโครงสร้างไดเรกทอรีในรีโพซิทอรี มีคู่มือวางอยู่ที่ไดเรกทอรีรากและมีโน้ตเล็กติดอยู่ตามไดเรกทอรีย่อย ผู้ช่วยตัวเล็กอ่านคู่มือก่อนแล้วจึงอ่านโน้ตที่อยู่ใกล้ที่สุด](/illustrations/agents-md.webp)

## แนวคิดหลักหนึ่งข้อ

ให้มองว่าเป็น **คู่มือปฐมนิเทศเพื่อนร่วมงานใหม่ฉบับย่อ**: เขียนเฉพาะ “วิธีทำงานในรีโพซิทอรีนี้” ไม่ต้องเขียนประวัติบริษัท

| เหมาะจะเขียนใน AGENTS.md | ไม่เหมาะจะเขียน |
|---|---|
| วิธีรันการทดสอบ lint และ build | เอกสาร API ฉบับเต็ม (ควรลิงก์ไปยังเอกสารทางการ) |
| ข้อตกลงเรื่องไดเรกทอรีและรูปแบบการตั้งชื่อ | ประวัติการตัดสินใจด้านการออกแบบยาวหลายพันบรรทัด |
| ข้อห้าม (เช่น ห้ามแก้ `main` หรือ commit คีย์ลับ) | ความต้องการชั่วคราวที่ต่างกันในแต่ละงาน |
| ข้อความ commit และรายการตรวจสอบ PR | ความชอบส่วนตัวที่ไม่เกี่ยวกับโค้ด |

## วิธีเริ่มต้นแบบใช้งานได้จริง

สร้าง `AGENTS.md` ที่ไดเรกทอรีรากของรีโพซิทอรี:

```md
# คำสั่งของโปรเจกต์

## การ build และการทดสอบ
- ติดตั้ง: `pnpm install`
- ทดสอบ: `pnpm test` (ต้องรันหลังแก้ตรรกะ)
- ตรวจสอบประเภท: `pnpm typecheck`

## รูปแบบโค้ด
- ใช้โหมดเข้มงวดของ TypeScript
- วาง component ใหม่ใน `src/components/` และใช้ชื่อไฟล์แบบ PascalCase

## ข้อห้าม
- ห้ามแก้ `pnpm-lock.yaml` เว้นแต่ dependency เปลี่ยน
- ห้าม commit `.env` หรือคีย์ API
- ห้ามรัน `git push` โดยไม่ได้รับการยืนยัน

## นิยามของคำว่าเสร็จ
- การทดสอบที่เกี่ยวข้องผ่าน
- ไม่มีข้อผิดพลาด lint ใหม่
- อธิบายขั้นตอนการตรวจสอบในคำอธิบาย PR
```

เมื่อบันทึกแล้ว ในงานใหม่ให้เขียนเฉพาะ **สิ่งที่ต่างออกไปในครั้งนี้** เช่น “แก้ปัญหาเลย์เอาต์ของหน้าเข้าสู่ระบบบน Safari และตรวจรับตาม AGENTS.md”

## ความเข้าใจผิดที่พบบ่อย

### 1. ฉันต้องบอกกฎเหล่านี้ซ้ำเองทุกครั้งหรือไม่

โดยทั่วไปไม่ต้อง  
นี่คือหนึ่งในเหตุผลที่มี `AGENTS.md`:
นำ **กฎของโปรเจกต์ที่คงที่** ไปไว้ในไฟล์นี้ เพื่อไม่ต้องอธิบายซ้ำทุกครั้งที่เริ่มงานใหม่

### 2. หมายความว่า “ถ้าฉันเขียนไว้ Codex จะทำตามร้อยเปอร์เซ็นต์” ใช่ไหม

`AGENTS.md` สำคัญมาก แต่ยังต้องทำงานร่วมกับสิ่งต่อไปนี้:

- ข้อกำหนดที่ระบุชัดเจนในงานครั้งนี้
- กลไกการกำหนดสิทธิ์และการอนุมัติของผลิตภัณฑ์
- นโยบาย Sandbox เครือข่าย และทีม

พูดให้แม่นยำกว่านั้นคือ ไฟล์นี้ช่วยให้ทำงานไปในทิศทางเดียวกัน แต่ไม่ใช่กลไกบังคับที่ครอบคลุมทุกกรณี

### 3. ถ้าฉันไม่ใช่โปรแกรมเมอร์ ยังต้องสนใจไฟล์นี้หรือไม่

ควรเข้าใจแนวคิดพื้นฐาน  
แม้คุณจะไม่ได้เขียนโค้ดเอง ตราบใดที่ให้ Codex ดูแลโปรเจกต์อย่างต่อเนื่อง `AGENTS.md` ก็ช่วยลดการอธิบายซ้ำและลดโอกาสที่งานจะออกนอกทิศทางได้

## ควรวางไว้ที่ไหน

| ตำแหน่ง | ขอบเขตการใช้งาน |
|---|---|
| `AGENTS.md` ที่รากของรีโพซิทอรี | ใช้เป็นค่าเริ่มต้นสำหรับทั้งโปรเจกต์ |
| `AGENTS.md` ในไดเรกทอรีย่อย | ใช้กับไดเรกทอรีนั้นและเส้นทางย่อย (พบบ่อยใน monorepo) |
| คำสั่งระดับผู้ใช้ | ใช้การตั้งค่าส่วนบุคคลหรือค่ากำหนดส่วนกลาง อย่าปะปนกับคำสั่งของโปรเจกต์ |

ดูการจัดการขอบเขตและข้อขัดแย้งที่ [ขอบเขตและลำดับความสำคัญ](/th/guide/customization/agents-md/scope-and-precedence/)

## ต่างจาก Skill และคำสั่งแบบ slash อย่างไร

| กลไก | ลักษณะสำคัญ | การใช้งานทั่วไป |
|---|---|---|
| AGENTS.md | กฎถาวรของโปรเจกต์ที่มีผลโดยไม่ต้องเรียกใช้ | รูปแบบ การทดสอบ ข้อห้าม |
| Skill | แพ็กเกจ workflow ที่นำกลับมาใช้ได้ (`SKILL.md`) | รายการตรวจสอบก่อน release และกระบวนการ Review เฉพาะทาง |
| คำสั่งแบบ slash | ทางลัดที่คุณเรียกใช้เอง | `/review` และ workflow แบบครั้งเดียว |

ใช้ `AGENTS.md` สำหรับกฎของโปรเจกต์ ส่วน **ชุดขั้นตอนที่ทำซ้ำและแชร์ได้** เหมาะจะสร้างเป็น [Skill](/th/skills/overview/) มากกว่า

## จะตัดสินใจได้อย่างไรว่าควรเขียนไว้ที่ไหน

หากไม่แน่ใจว่าควรเขียนข้อความหนึ่งไว้ที่ใด ให้ใช้หลักนี้:

- **กฎนี้ใช้ได้ในระยะยาว**: เหมาะจะเขียนใน `AGENTS.md`
- **นี่เป็นเพียงข้อกำหนดพิเศษสำหรับงานครั้งนี้**: เขียนในพรอมป์ของงานปัจจุบัน
- **นี่เป็นชุดขั้นตอนที่นำกลับมาใช้ซ้ำได้**: พิจารณาสร้างเป็น Skill

ตัวอย่าง:

- “รีโพซิทอรีนี้ใช้ `pnpm test` สำหรับการตรวจสอบทุกครั้ง” -> เหมาะจะใส่ใน `AGENTS.md`
- “ครั้งนี้แก้เฉพาะหน้าเข้าสู่ระบบ ห้ามแตะหน้าลงทะเบียน” -> เหมาะจะเขียนในงานปัจจุบัน
- “ก่อน release ให้รันกระบวนการตรวจสอบชุดเดิมทุกครั้ง” -> เหมาะจะสร้างเป็น Skill มากกว่า

## ข้อผิดพลาดที่พบบ่อย

- ไฟล์ยาวเกินไปจนโมเดลอ่านได้เพียงครึ่งแรก—**วางข้อจำกัดที่ต้องทำตามไว้ใน 30 บรรทัดแรก**
- เขียนคำสั่งที่มีความเสี่ยงสูงอย่าง “push อัตโนมัติเสมอ” ซึ่งขัดกับ [สิทธิ์และการอนุมัติ](/th/guide/foundations/permissions-and-approvals/)
- ไม่มีใครในทีมดูแล ทำให้เอกสารไม่ตรงกับคำสั่งสคริปต์ที่ใช้จริง

## ขอบเขตด้านความปลอดภัย

`AGENTS.md` **ใช้แทน** Sandbox และการอนุมัติไม่ได้ แม้จะเขียนว่า “รันคำสั่งใดก็ได้อย่างอิสระ” ผลิตภัณฑ์ก็ยังอาจขอให้คุณยืนยัน และนโยบายที่ทีมจัดการจากส่วนกลางอาจจำกัดให้เข้มงวดยิ่งขึ้น

`AGENTS.md` มีหน้าที่บอก Codex ว่า “โปรเจกต์นี้ทำงานตามปกติอย่างไร” ไม่ใช่บอกแทนคุณว่างานครั้งนี้ต้องทำอะไรโดยเฉพาะ
