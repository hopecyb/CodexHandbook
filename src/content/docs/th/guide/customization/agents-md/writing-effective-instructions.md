คำสั่งระดับโปรเจกต์ที่มีประสิทธิภาพควรมีลักษณะใกล้เคียงกับ **รายการตรวจสอบ** เป้าหมายคือช่วยลดข้อผิดพลาดที่คาดการณ์ได้ของ Codex ตั้งแต่การลองครั้งแรก

เมื่อเขียนคำสั่งระดับโปรเจกต์เป็นครั้งแรก ปัญหาที่พบบ่อยคือเขียนแนวคิดไว้มากมาย แต่กลับอธิบายข้อจำกัดสำคัญได้ไม่ชัดเจนพอ

## เนื้อหา

- คำสั่งระดับโปรเจกต์ควรมีหน้าตาอย่างไร
- “กระชับ ชัดเจน และลงมือทำได้” หมายถึงอะไร
- รูปแบบการเขียนใดทำให้ทั้ง Codex และคนอ่านสับสนได้ง่ายที่สุด

## โครงสร้างที่แนะนำ

```md
# คำสั่งระดับโปรเจกต์

## เริ่มต้นอย่างรวดเร็ว (3–5 บรรทัด)
การติดตั้ง เซิร์ฟเวอร์สำหรับการพัฒนา และคำสั่งทดสอบที่ใช้บ่อยที่สุด

## ต้องปฏิบัติตาม
แจกแจงกฎที่ห้ามฝ่าฝืนเป็นข้อ ๆ

## โค้ดและไดเรกทอรี
การตั้งชื่อ ตำแหน่งที่จัดวาง และข้อตกลงเรื่อง dependency

## นิยามของคำว่าเสร็จ
เงื่อนไขที่ถือว่า “พร้อม commit”

## ข้อห้าม
ระบุให้ชัดเจนว่าอะไรที่ห้ามทำ
```

## หลักการเขียน

### 1. วางข้อจำกัดตายตัวไว้ก่อน

วางข้อกำหนดประเภท “ต้อง” และ “ห้าม” ไว้ช่วงต้นของไฟล์ เมื่อบริบทมีจำกัด โมเดลจะให้น้ำหนักกับเนื้อหาช่วงต้นมากกว่า ซึ่งเป็นหลักเดียวกับ [ลำดับความสำคัญของบริบท](/th/guide/context/context-priority/)

### 2. คำสั่งต้องคัดลอกไปรันได้

เขียนคำสั่งที่ **รันได้จริง** อย่าเขียนเพียงว่า “รันทดสอบสักหน่อย”:

```md
# ดี
pnpm test --filter @app/web

# ไม่ดี
ตรวจให้แน่ใจว่าการทดสอบผ่าน
```

### 3. เกณฑ์เสร็จสิ้นที่ตรวจสอบได้

```md
## นิยามของคำว่าเสร็จ
- `pnpm lint` และ `pnpm test` ต้องทำงานผ่านโดยไม่มีข้อผิดพลาด
- API ใหม่ต้องมี unit test ที่สอดคล้องกัน
- การเปลี่ยนแปลงที่ผู้ใช้มองเห็นต้องแนบขั้นตอนทดสอบด้วยตนเอง (เบราว์เซอร์ + อุปกรณ์เคลื่อนที่)
```

### 4. อธิบาย “เหตุผล” ให้จบภายในหนึ่งประโยคเท่าที่ทำได้

```md
- ห้ามแก้ไข `generated/`: ไดเรกทอรีนี้สร้างจากโค้ด การแก้ด้วยมือจะถูกเขียนทับในการ build ครั้งถัดไป
```

หากต้องอธิบายภูมิหลังยาวกว่านี้ ควรลิงก์ไปยังเอกสารอย่างเป็นทางการใน `docs/`

## “คำสั่งที่ดี” คืออะไร

คำสั่งที่ดีต้องช่วยให้ทั้งคนและ Codex เข้าใจประเด็นเหล่านี้ได้อย่างรวดเร็ว:

- ต้องทำอะไรก่อน
- ห้ามทำอะไร
- ต้องทำถึงระดับใดจึงจะถือว่าเสร็จ

หากอ่านจบแล้วยังไม่รู้ว่าควรรันคำสั่งใดก่อน ห้ามแตะส่วนไหน หรือเงื่อนไขใดจึงถือว่างานเสร็จ แสดงว่าคำสั่งนั้นยังใช้งานได้ไม่ดีพอ

## ตัวอย่างบางส่วนจาก playbook ของทีม

```md
## PR และ Git
- ตั้งชื่อ branch ด้วยคำนำหน้า `feat/`, `fix/` หรือ `docs/`
- หนึ่ง PR ทำเพียงเรื่องเดียว การ refactor ขนาดใหญ่ให้เปิด PR แยก
- ก่อน merge ต้องมีคน Review diff แม้ Codex จะรันทดสอบแล้วก็ตาม

## การทำงานร่วมกับ Codex
- สำหรับงานใหญ่ ให้ขอ “เสนอแผนและรอให้ฉันยืนยันก่อนแก้โค้ด”
- หากเกี่ยวข้องกับการ migrate ฐานข้อมูล ให้แสดง SQL สำหรับ migration เพื่อให้คนตรวจสอบก่อน
```

## ข้อผิดพลาดที่พบบ่อย

| ข้อผิดพลาด | ผลที่ตามมา |
|---|---|
| ใส่เนื้อหาเชิงสารานุกรมของเฟรมเวิร์กมากเกินไป | คำสั่งทดสอบสำคัญถูกมองข้าม |
| กฎขัดแย้งกันเอง | โมเดลสุ่มเลือกกฎหนึ่งข้อไปปฏิบัติ |
| มีแต่คำกว้าง ๆ อย่าง “ต้องสวยงาม” | ไม่สามารถตรวจรับงานได้ |
| ใส่ secret หรือ URL ภายในองค์กร | เสี่ยงต่อการรั่วไหล |

## ความเข้าใจผิดที่พบบ่อย

### 1. คำสั่งไม่ได้ยิ่งละเอียดยิ่งดี

เนื้อหาที่กระจัดกระจาย ยาวเกินไป และคล้ายสารานุกรมมากเกินไป จะกลบกฎที่มีลำดับความสำคัญสูงจริง ๆ

### 2. เขียนเพียงว่า “ใส่ใจมาตรฐาน” ก็นับเป็นคำสั่งหรือไม่

ข้อความลักษณะนี้มักไม่ชัดเจนพอที่จะนำไปปฏิบัติ  
วิธีเขียนที่เหมาะสมกว่าคือระบุสิ่งต่อไปนี้โดยตรง:

- คำสั่งจริง
- ไดเรกทอรีที่ชัดเจน
- เกณฑ์เสร็จสิ้นที่เฉพาะเจาะจง

### 3. เขียนคำอธิบายภูมิหลังปะปนกับกฎการปฏิบัติได้ตามใจหรือไม่

ไม่แนะนำเช่นกัน  
แนวทางที่เหมาะสมกว่าคือ:

- วางกฎไว้ก่อน
- ย่อภูมิหลังให้เหลือหนึ่งประโยค
- นำคำอธิบายที่ยาวกว่านั้นไปไว้ใน docs

## เมื่อลงมือเขียนใหม่ ให้เริ่มจากประเด็นเหล่านี้

หากมีคำสั่งระดับโปรเจกต์ที่เขียนไว้อย่างกระจัดกระจาย คุณสามารถจัดระเบียบด้วยวิธีต่อไปนี้:

1. ย้ายข้อกำหนดประเภท “ต้อง/ห้าม” มาไว้ด้านหน้า
2. เปลี่ยนคำกว้าง ๆ ให้เป็นคำสั่งหรือรายการตรวจสอบที่เฉพาะเจาะจง
3. ย่อคำอธิบายภูมิหลังยาว ๆ แล้วเปลี่ยนเป็นลิงก์
4. กำหนดนิยามขั้นต่ำของคำว่าเสร็จ

## กลั่นสิ่งที่เรียนรู้จากงานหนึ่งครั้งให้เป็นกฎของโปรเจกต์

ไม่ใช่ทุกพรอมป์ที่ดีจะต้องนำไปใส่ใน `AGENTS.md` โดยตรง แนวทางที่มั่นคงกว่าคือพิจารณาก่อนว่าเนื้อหานั้นอยู่ในระดับใด:

| เนื้อหาที่เกิดซ้ำ | วิธีเก็บเป็นแนวปฏิบัติที่เหมาะสมกว่า |
|---|---|
| “ห้ามแก้ไดเรกทอรี generated ในคลังนี้” | ข้อห้ามใน `AGENTS.md` |
| “Review ตามรูปแบบตายตัวก่อนเปิด PR ทุกครั้ง” | Skill หรือเทมเพลตพรอมป์ |
| “จัดรูปแบบอัตโนมัติหลังเขียนไฟล์” | Hook |
| “อ่าน Linear/Jira ก่อนเมื่อตรวจสอบ ticket” | MCP + Skill ที่เกี่ยวข้อง |
| “โดยส่วนตัวฉันชอบคำอธิบายภาษาจีน” | หน่วยความจำหรือการตั้งค่าส่วนบุคคล |

`AGENTS.md` เหมาะที่สุดสำหรับกฎระยะยาวที่ทีมใช้ร่วมกันและตรวจสอบได้ เนื้อหาเชิงกระบวนการสามารถย้ายไปไว้ใน Skill ให้ Hook รับผิดชอบการตรวจสอบอัตโนมัติ และให้ MCP รับผิดชอบการเข้าถึงระบบภายนอก

คำสั่งระดับโปรเจกต์ที่ดีไม่ได้วัดจากปริมาณเนื้อหา แต่ต้องทำให้ข้อจำกัดสำคัญ คำสั่งสำคัญ และเกณฑ์เสร็จสิ้นชัดเจนเพียงพอที่จะนำไปปฏิบัติได้ทันที

## รอบการบำรุงรักษา

- **อัปเดต** `AGENTS.md` ให้สอดคล้องทุกครั้งที่คำสั่ง CI เปลี่ยน
- ทบทวนทุกไตรมาส: ลบกฎที่ล้าสมัย
- งานแรกในการ onboarding สมาชิกใหม่: อ่าน AGENTS.md และทำตามส่วน “เริ่มต้นอย่างรวดเร็ว” ให้สำเร็จ
