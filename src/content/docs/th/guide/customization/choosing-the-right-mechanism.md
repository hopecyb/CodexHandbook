ปัญหาของหลายทีมมักเกิดจาก **วางข้อมูลชิ้นเดียวกันไว้ผิดที่**: กฎที่ควรอยู่ในรีโพซิทอรีกลับอยู่ในแชต เวิร์กโฟลว์ที่ควรทำเป็น Skill กลับถูกยัดไว้ใน `AGENTS.md` ส่วนข้อมูลที่ควรเชื่อมต่อแบบอ่านอย่างเดียวกลับเข้าถึงผ่าน MCP ที่มีสิทธิ์สูง

หน้านี้มุ่งตอบคำถามเชิงปฏิบัติข้อหนึ่ง:

> เมื่อพบว่า “เรื่องนี้จะเกิดซ้ำอีกในอนาคต” ควรจัดเก็บไว้ในชั้นใด

## ตารางสรุป

| กลไก | เหมาะสำหรับเก็บอะไร |
|---|---|
| พรอมป์ครั้งเดียว | เป้าหมาย ข้อจำกัด และเกณฑ์ตรวจรับที่ใช้กับงานครั้งนี้เท่านั้น |
| `AGENTS.md` | กฎการทำงานร่วมกันระดับรีโพซิทอรีและข้อจำกัดระยะยาว |
| หน่วยความจำ | ความชอบส่วนบุคคลหรือข้อเท็จจริงที่ไม่อ่อนไหวจำนวนเล็กน้อยซึ่งใช้ซ้ำข้ามเซสชัน |
| Skill | เวิร์กโฟลว์ รายการตรวจสอบ และแนวทางเฉพาะทางที่นำกลับมาใช้ได้ |
| MCP | การเข้าถึงเครื่องมือภายนอก แหล่งข้อมูล และความสามารถของระบบ |

หากตารางนี้ยังไม่พอ ให้พิจารณาต่อไปตามขั้นตอนด้านล่าง

## วิธีตัดสินในห้าขั้น

### 1. ข้อมูลที่ใช้ได้กับงานปัจจุบันเท่านั้น

ข้อมูลประเภทนี้ควรอยู่ใน **พรอมป์ของงานครั้งนี้** ก่อน

เหมาะสำหรับ:

- “ครั้งนี้แก้เฉพาะ `docs/` ห้ามแตะโค้ด”
- “ส่งสรุปเป็นภาษาจีน และปิดท้ายด้วยหนึ่งคำถามที่ต้องยืนยัน”
- “วิเคราะห์สาเหตุก่อน อย่าเพิ่งแก้ไฟล์”

ไม่เหมาะสำหรับ:

- ทีมกำหนดให้รัน `pnpm test` เป็นข้อบังคับระยะยาว
- ไดเรกทอรีที่ห้ามแก้ในรีโพซิทอรี
- PR Review ทุกครั้งต้องส่งผลลัพธ์ตามเทมเพลตเดียวกัน

กฎระยะยาวเหล่านี้ควรย้ายไปเก็บในชั้นที่ถาวรกว่านี้

### 2. นี่คือกฎการทำงานร่วมกันของโปรเจกต์ หรือนิสัยส่วนบุคคล

หากเป็น **กฎที่ผู้ร่วมงานทุกคนควรรู้** ให้ใส่ไว้ใน [`AGENTS.md`](/th/guide/customization/agents-md/what-is-agents-md/)

ตัวอย่างเช่น:

- คำสั่งทดสอบ lint และ build
- ไดเรกทอรีที่ห้ามแก้
- กฎการเขียนข้อความ commit หรือการตรวจรับ PR
- ข้อกำหนดเฉพาะของแต่ละไดเรกทอรีย่อยใน monorepo

หากเป็นเพียง **ความชอบส่วนตัวของคุณ** เช่น “อธิบายเป็นภาษาจีน” หรือ “บอกข้อสรุปก่อนแล้วค่อยให้รายละเอียด” ควรเก็บไว้ใน [หน่วยความจำ](/th/guide/customization/memories-and-persistent-context/) หรือการตั้งค่าส่วนบุคคลมากกว่า

ใช้หลักง่าย ๆ นี้ช่วยตัดสินได้:

- สิ่งที่ควรผ่าน PR Review ให้เก็บในรีโพซิทอรีก่อน
- เฉพาะสิ่งที่ไม่เป็นไรหากคนอื่นมองไม่เห็น จึงค่อยพิจารณาเก็บไว้ในชั้นส่วนบุคคล

### 3. นี่คือ “กฎ” หรือ “ขั้นตอน”

เอกสารจำนวนมากใช้งานยาก เพราะนำกฎกับขั้นตอนมาปะปนกัน

| หากเป็นเรื่องเกี่ยวกับ… | ควรเก็บไว้ใน |
|---|---|
| “ห้าม push ไปที่ main โดยตรง” | `AGENTS.md` |
| “เมื่อ Review ให้ดูการทดสอบก่อน จากนั้นดูความเสี่ยง แล้วจึงดู regression” | Skill |
| “ก่อน release ให้รันคำสั่ง 4 รายการนี้” | Skill หรือสคริปต์ |
| “อนุญาตให้เข้าถึงเฉพาะข้อมูล issue แบบอ่านอย่างเดียว” | MCP + การตั้งค่าสิทธิ์ |

ขณะตัดสิน ให้จับประเด็นสองข้อนี้ก่อน:

- **กฎ** ตอบว่า “ทำอะไรได้ และทำอะไรไม่ได้”
- **ขั้นตอน** ตอบว่า “โดยทั่วไปงานประเภทนี้ควรทำอย่างไร”

ขั้นตอนที่นำกลับมาใช้ได้มักเหมาะจะทำเป็น [Skill](/th/skills/overview/)

## ใช้ร่วมกัน ไม่ใช่เลือกอย่างใดอย่างหนึ่ง

ทีมที่มีระบบมักไม่ใช้เพียงกลไกเดียว แต่ใช้หลายกลไกร่วมกัน

### ชุดที่ 1: `AGENTS.md` + Skill

เหมาะสำหรับ: การตรวจทานโค้ด การตรวจก่อน release และการวิเคราะห์ปัญหา

การแบ่งหน้าที่:

- `AGENTS.md` ระบุข้อจำกัดตายตัว เช่น ห้าม merge อัตโนมัติ และต้องรันการตรวจใดบ้าง
- Skill ระบุเวิร์กโฟลว์ เช่น ตรวจอย่างไร ส่งผลตามเทมเพลตใด และจัดระดับปัญหาอย่างไร

### ชุดที่ 2: Skill + MCP

เหมาะสำหรับ: อ่าน ticket ตรวจฐานข้อมูล ดึงไฟล์ออกแบบ และสร้างรายงานประจำสัปดาห์

การแบ่งหน้าที่:

- Skill กำหนดลำดับการทำงานและรูปแบบเอาต์พุต
- MCP กำหนดว่า “เชื่อมต่อที่ใด ค้นหาอะไรได้ และแก้ไขอะไรได้”

มองสองอย่างนี้แยกจากกันได้ดังนี้:

> Skill เปรียบเสมือนคู่มือปฏิบัติงาน ส่วน MCP เปรียบเสมือนกล่องเครื่องมือที่เชื่อมต่อเข้ามา

### ชุดที่ 3: `AGENTS.md` + หน่วยความจำ

เหมาะสำหรับ: กฎของทีมคงที่ แต่แต่ละคนมีรูปแบบการสื่อสารต่างกัน

การแบ่งหน้าที่:

- `AGENTS.md` ระบุมาตรฐานร่วมของทีม
- หน่วยความจำเก็บความชอบส่วนบุคคล เช่น ภาษา รูปแบบคำอธิบาย และโครงสร้างเอาต์พุตเริ่มต้น

อย่าทำกลับกัน กฎของทีมไม่ควรอยู่ในหน่วยความจำของใครคนใดคนหนึ่งเท่านั้น

## เมทริกซ์ช่วยตัดสินที่ใช้งานได้จริง

| คำถาม | ใช่ | ไม่ใช่ |
|---|---|---|
| มีผลเฉพาะงานปัจจุบันหรือไม่ | พรอมป์ | พิจารณาต่อ |
| ทุกคนควรปฏิบัติตามหรือไม่ | `AGENTS.md` / การตั้งค่าโปรเจกต์ | พิจารณาต่อ |
| เป็นเวิร์กโฟลว์ที่ทำซ้ำได้หรือไม่ | Skill | พิจารณาต่อ |
| ต้องใช้ข้อมูลภายนอกแบบเรียลไทม์หรือดำเนินการกับระบบภายนอกหรือไม่ | MCP | พิจารณาต่อ |
| เป็นเพียงความชอบส่วนบุคคลระยะยาวหรือไม่ | หน่วยความจำ / การตั้งค่าผู้ใช้ | พรอมป์ |

เมื่อความต้องการหนึ่งเข้าข่ายพร้อมกันสองคอลัมน์ มักหมายความว่าควร **แยกเป็นหลายชั้น** ไม่ใช่ฝืนยัดไว้ในที่เดียว

## ตัวอย่างทั่วไปสามกรณี

### ตัวอย่างที่ 1: ทีมมักลืมรันการทดสอบ regression

อย่าเพียงบอกในแชตกลุ่มว่า “อย่าลืมรันการทดสอบ”

วิธีที่มั่นคงกว่า:

1. ระบุใน `AGENTS.md` ว่า “การเปลี่ยนแปลงที่กระทบตรรกะธุรกิจต้องรัน `pnpm test`”
2. หากขั้นตอนซับซ้อน ให้เพิ่ม Skill สำหรับรันการทดสอบ
3. ใช้ CI เป็นด่านสุดท้าย

### ตัวอย่างที่ 2: ต้องการให้ Codex ส่งผลลัพธ์รูปแบบเดิมทุกครั้งที่ทำ PR Review

อย่าคัดลอกเทมเพลตทั้งชุดมาวางใหม่ทุกครั้ง

วิธีที่มั่นคงกว่า:

1. ทำโครงสร้างเอาต์พุตเป็น Skill
2. ระบุใน `description` ให้ชัดว่า “ใช้เมื่อผู้ใช้พูดว่า Review, ตรวจทาน หรือขอตรวจก่อน merge”
3. หากทั้งทีมใช้ร่วมกัน ให้เขียนพาธของ Skill ไว้ในเอกสารโปรเจกต์

### ตัวอย่างที่ 3: ต้องอ่าน ticket ใน Linear ก่อนแก้โค้ด

อย่าวาง API token ลงในบทสนทนา

วิธีที่มั่นคงกว่า:

1. เชื่อมต่อ Linear ด้วย MCP
2. ใช้สิทธิ์อ่านอย่างเดียวเป็นค่าเริ่มต้น
3. หากต้องการเวิร์กโฟลว์ตายตัว ให้ใช้ Skill กำหนดว่า “อ่าน ticket ก่อน จากนั้นดูโค้ด แล้วจึงเสนอแนวทาง”

## จุดที่พลาดได้ง่ายที่สุด

### เขียน `AGENTS.md` ให้เป็นสารานุกรม

ผลคือข้อจำกัดตายตัวไม่เด่น และคำสั่งสำคัญกับพื้นที่ต้องห้ามถูกข้อมูลส่วนอื่นกลบ `AGENTS.md` ควรกระชับ ตรงไปตรงมา และนำไปปฏิบัติได้

### ใช้ Skill เป็น “กล่องเก็บสารพัดอย่าง”

หาก Skill เดียวรวมทั้ง Review, release, debugging และเขียนรายงานประจำวัน สุดท้ายจะทั้งทริกเกอร์ยากและดูแลยาก

### ถือว่า MCP คือคำตอบเริ่มต้น

ข้อมูลที่อ่านได้จากรีโพซิทอรีโดยตรงไม่จำเป็นต้องเชื่อมเครื่องมือภายนอกเพิ่มเพียงเพื่อให้ดู “ล้ำสมัย” MCP มีไว้ขยายความสามารถ ไม่ใช่ให้รางวัลกับความซับซ้อน

### ให้หน่วยความจำแบกรับข้อเท็จจริงของทีม

กฎจะอยู่กับบัญชีของคนที่บันทึกไว้ และหายไปเมื่อคนนั้นออกจากทีมหรือเปลี่ยนเครื่อง ข้อมูลประเภทนี้ควรกลับมาอยู่ในรีโพซิทอรี

## ลำดับการนำไปใช้ที่แนะนำ

หากตอนนี้การจัดการของทีมยังค่อนข้างสับสน ให้ค่อย ๆ จัดระเบียบตามลำดับนี้:

1. เขียน `AGENTS.md` ฉบับเล็กที่สุดที่ใช้งานได้ก่อน
2. รวบเวิร์กโฟลว์ที่ทำซ้ำตั้งแต่สามครั้งขึ้นไปให้เป็น Skill
3. เพิ่ม MCP เฉพาะเมื่อจำเป็นต้องใช้ระบบภายนอกจริง ๆ
4. จัดระเบียบหน่วยความจำและความชอบส่วนบุคคลเป็นขั้นตอนสุดท้าย

ลำดับนี้ช่วยให้ **ฉันทามติในการทำงานร่วมกัน** มั่นคงก่อน แล้วจึงค่อยขยายความสามารถทีละขั้น
