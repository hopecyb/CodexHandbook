ไคลเอนต์ Codex บางตัวรองรับ **หน่วยความจำ (Memory)** ซึ่งเก็บความชอบหรือข้อเท็จจริงที่คุณยืนยันระหว่างการสนทนาหลายครั้งไว้ใช้ในเซสชันถัดไป ฟีเจอร์นี้ทำงานเสริมกับ `AGENTS.md` และการกำหนดค่าโปรเจกต์ แต่ **ใช้แทน** แนวปฏิบัติของทีมที่ควบคุมเวอร์ชันไม่ได้

## เนื้อหา

- อะไรควรและไม่ควรเก็บในหน่วยความจำ
- ลำดับความสำคัญเมื่อเทียบกับ AGENTS.md, ฟีเจอร์ Memories และคำสั่งระดับโปรเจกต์
- วิธีจัดการเนื้อหาในหน่วยความจำสำหรับบุคคลและทีม

## หน่วยความจำเหมาะสำหรับทำอะไร

มองหน่วยความจำได้ว่าเป็นวิธีที่ **Codex ช่วยจำเรื่องซึ่งคุณต้องพูดซ้ำอยู่เสมอ แต่ไม่คุ้มจะอธิบายใหม่ทุกครั้ง**

ตัวอย่างเช่น:

- คุณต้องการคำอธิบายเป็นภาษาจีน
- คุณชอบให้สรุปข้อสรุปก่อน แล้วค่อยลงรายละเอียด
- ในโปรเจกต์หนึ่ง คำว่า “แบ็กเอนด์” หมายถึงไดเรกทอรีใดโดยปริยาย

หน่วยความจำจึงคล้าย “ความชอบส่วนบุคคลระยะยาวและข้อเท็จจริงที่คงที่เพียงเล็กน้อย” มากกว่าจะเป็นคู่มือโปรเจกต์หรือตู้นิรภัยเก็บความลับ

## อะไรเหมาะจะเก็บในหน่วยความจำ

| เหมาะ | ไม่เหมาะ |
|---|---|
| ความชอบส่วนบุคคลในการเขียนโค้ด (ภาษาของคอมเมนต์ รูปแบบการเยื้อง) | คีย์ Production, token |
| ชื่อเรียกย่อของโปรเจกต์ที่ต้องอธิบายซ้ำ (“แบ็กเอนด์หมายถึง `services/api`”) | สถานะงาน sprint ที่เปลี่ยนแปลงอยู่เสมอ |
| ข้อเท็จจริงที่ไม่อ่อนไหวซึ่งคุณสั่งชัดเจนว่า “โปรดจำไว้” | แนวปฏิบัติของทีมที่ควรอยู่ใน Git |

แนวปฏิบัติระดับทีมควรอยู่ใน **`AGENTS.md` หรือการกำหนดค่าโปรเจกต์** เพื่อให้ Review ได้และช่วยให้สมาชิกใหม่เริ่มงานได้ง่าย ดู [ขอบเขตและลำดับความสำคัญ](/th/guide/customization/agents-md/scope-and-precedence/)

## ความเข้าใจผิดที่พบบ่อย

### หน่วยความจำไม่ได้ “จำทุกอย่างให้คุณตลอดไป”

หลายคนเข้าใจผิดว่า เมื่อพูดเรื่องหนึ่งไปเพียงครั้งเดียว Codex จะจดจำเรื่องนั้นได้ตลอดไปอย่างครบถ้วนและเสถียร

ความเข้าใจที่แม่นยำกว่าคือ หน่วยความจำเป็นชั้นเสริมที่ช่วยลดการอธิบายซ้ำ แต่ใช้แทนเอกสารและข้อมูลทางการในรีโพซิทอรีไม่ได้

### หน่วยความจำไม่เหมาะสำหรับเก็บข้อตกลงร่วมกันของทีม

หากกฎข้อหนึ่งมีเพียงหน่วยความจำในบัญชีของคุณที่รู้ คนอื่นก็จะมองไม่เห็นและ Review ไม่ได้

เนื้อหาประเภทนี้ควรกลับไปอยู่ใน:

- `AGENTS.md`
- เอกสารโปรเจกต์
- ไฟล์การกำหนดค่า

### หน่วยความจำไม่ใช่ที่เก็บข้อมูลอ่อนไหว

แม้ไคลเอนต์บางตัวจะรองรับหน่วยความจำ คุณก็ไม่ควรฝากข้อมูลต่อไปนี้ไว้ให้เก็บรักษาระยะยาว:

- token
- ข้อมูลลูกค้า
- บัญชีภายใน
- ข้อมูลธุรกิจที่ยังไม่เปิดเผย

## เปรียบเทียบกับกลไกที่เกี่ยวข้อง

| กลไก | ใครมองเห็น | วิธีเปลี่ยนแปลง |
|---|---|---|
| พรอมต์ครั้งเดียว | งานปัจจุบัน | คุณพิมพ์ |
| หน่วยความจำ | โดยทั่วไปมีเพียงบัญชีหรือ Workspace ของคุณ | ยืนยันในบทสนทนาหรือจัดการจากหน้าการตั้งค่า |
| `AGENTS.md` | ผู้ร่วมงานทุกคนในรีโพซิทอรี | Git PR |
| การกำหนดค่าโปรเจกต์ | ตามลำดับชั้นการกำหนดค่า | ไฟล์ + นโยบายที่ผู้ดูแลระบบจัดการ |

## ควรแบ่งข้อมูลไว้แต่ละชั้นอย่างไร

ปัญหา “ยิ่งใช้หน่วยความจำยิ่งยุ่ง” จำนวนมากไม่ได้เกิดจากตัวฟีเจอร์ แต่เกิดจากการยัดข้อมูลที่มีอายุใช้งานและระดับการมองเห็นต่างกันไว้ในที่เดียว

| ประเภทข้อมูล | ตำแหน่งที่เหมาะกว่า |
|---|---|
| ความชอบด้านการสื่อสารส่วนบุคคลที่ฉันต้องบอกซ้ำ | หน่วยความจำ |
| กฎที่ทุกคนในทีมต้องปฏิบัติตาม | `AGENTS.md` หรือการกำหนดค่าโปรเจกต์ |
| ข้อตกลงพิเศษของไดเรกทอรีหนึ่ง | คำอธิบายโปรเจกต์ระดับไดเรกทอรีหรือไฟล์กฎ |
| เป้าหมายชั่วคราวของงานหนึ่ง | พรอมต์หรือ issue ปัจจุบัน |
| ขั้นตอนที่ต้องนำกลับมาใช้ | Skill หรือเทมเพลตพรอมต์ |
| การตรวจสอบที่ต้องทำโดยอัตโนมัติ | Hook |

เกณฑ์ตัดสินมีเพียงว่าใครต้องมองเห็น ข้อมูลเปลี่ยนบ่อยแค่ไหน และต้องผ่าน Review โค้ดหรือไม่ ข้อตกลงของทีมต้องอยู่ในรีโพซิทอรี ส่วนพฤติกรรมส่วนตัวจึงเหมาะกับหน่วยความจำ

## วิธีใช้ที่แนะนำ

1. **เขียนลงรีโพซิทอรีก่อน**: คำสั่งทดสอบ โครงสร้างไดเรกทอรี และข้อห้าม push ไม่ควรอยู่ในหน่วยความจำเพียงอย่างเดียว
2. **ใช้หน่วยความจำเก็บความชอบส่วนบุคคล**: เช่น “อธิบายเป็นภาษาจีน” หรือ “เขียนคอมเมนต์ของ diff เป็นภาษาอังกฤษ”
3. **ทำความสะอาดเป็นระยะ**: ลบหน่วยความจำที่ล้าสมัยหลังสถาปัตยกรรมโปรเจกต์เปลี่ยนแปลงครั้งใหญ่
4. **โปรเจกต์ที่อ่อนไหว**: ปิดหรือจำกัดหน่วยความจำ เพื่อหลีกเลี่ยงบริบทรั่วไหลข้ามโปรเจกต์

## จะตัดสินได้อย่างไรว่าควรเก็บในหน่วยความจำ

หากไม่แน่ใจว่าควรเก็บข้อมูลหนึ่งไว้ในหน่วยความจำหรือไม่ ลองถามตัวเองก่อน:

1. นี่เป็นความชอบส่วนตัวที่ฉันต้องพูดซ้ำบ่อยหรือไม่
2. นี่เป็นข้อเท็จจริงที่ค่อนข้างคงที่ในช่วงระยะหนึ่งหรือไม่
3. แม้คนอื่นจะมองไม่เห็นข้อมูลนี้ ก็จะไม่กระทบการทำงานร่วมกันของทีมหรือไม่

เมื่อทั้งสามข้อมีแนวโน้มเป็น “ใช่” จึงค่อยถือว่าเหมาะจะเก็บในหน่วยความจำ

## ขอบเขตความปลอดภัย

- อย่าให้หน่วยความจำกลายเป็น **ช่องทางลับ** สำหรับเลี่ยงข้อห้ามใน `AGENTS.md`
- อย่าเก็บข้อมูลลูกค้า ข้อมูลรับรอง หรือข้อมูลการเงินที่ยังไม่เปิดเผยไว้ในหน่วยความจำ
- สภาพแวดล้อมองค์กรอาจปิดฟีเจอร์หน่วยความจำ โปรดปฏิบัติตามนโยบายที่ผู้ดูแลระบบกำหนด

## ข้อผิดพลาดที่พบบ่อย

- เก็บ “รายการ epic ที่ต้องทำให้เสร็จในสัปดาห์นี้” ไว้ในหน่วยความจำเพียงแห่งเดียว ทำให้ผู้ร่วมงานมองไม่เห็น
- เมื่อหน่วยความจำขัดแย้งกับ `AGENTS.md` กลับไม่อัปเดตด้านใดเลย
- เข้าใจผิดว่าหน่วยความจำหมายถึง “โมเดลจำรีโพซิทอรีทั้งหมดได้ตลอดไป”

หน่วยความจำเหมาะที่สุดสำหรับ “ความชอบส่วนบุคคลที่ต้องพูดซ้ำอยู่เสมอและข้อเท็จจริงที่คงที่เพียงเล็กน้อย” ไม่เหมาะจะใช้แทนเอกสารรีโพซิทอรี กฎของทีม หรือการจัดการข้อมูลอ่อนไหว
