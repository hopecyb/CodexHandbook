Codex ไม่ได้อาศัยเพียง “ครั้งนี้จะถามอย่างไร” แต่ยังใช้ **การตั้งค่าถาวร** เพื่อจดจำข้อตกลงของคุณและทีม บทนี้ช่วยแยกว่าข้อกำหนดใดควรอยู่ในบทสนทนา และข้อกำหนดใดควรจัดเก็บไว้ในโปรเจกต์

หากคุณเริ่มพูดเรื่องเดิมซ้ำ ๆ เช่น “ห้ามแก้ไดเรกทอรีนี้” “รันการทดสอบก่อน” หรือ “ใช้โมเดลนี้เป็นค่าเริ่มต้น” บทนี้จะช่วยจัดการปัญหาประเภทนั้น

## เนื้อหา

- ความชอบส่วนบุคคล คำอธิบายโปรเจกต์ กฎของทีม และพรอมป์ชั่วคราว—**สิ่งใดมีผลเหนือสิ่งใด**
- สิ่งที่ควรและไม่ควรเขียนใน `AGENTS.md`
- ควรจัดการไฟล์การตั้งค่าและนโยบายการอนุมัติ/Sandbox ไว้ที่ชั้นใด

## เหมาะสำหรับใคร

| ผู้อ่าน | แนะนำให้อ่านก่อน |
|---|---|
| เพิ่งทำงานแรกสำเร็จ | [คำอธิบายโปรเจกต์](/th/guide/customization/project-instructions/) |
| ต้องการบันทึกมาตรฐานการทำงานร่วมกันไว้ในรีโพซิทอรี | [AGENTS.md คืออะไร](/th/guide/customization/agents-md/what-is-agents-md/) |
| ต้องการให้พฤติกรรมของ CLI/App เป็นมาตรฐานเดียวกัน | [พื้นฐานการตั้งค่า](/th/guide/customization/configuration/config-basics/) |

## บทนี้กำลังแก้ปัญหาอะไร

หลังใช้ Codex ไปสักระยะ หลายคนจะพบปัญหาประเภทเดียวกัน: เขียนกฎไว้ไม่น้อย แต่รู้สึกว่ากฎทำงานไม่ครบถ้วน หรือกฎจากหลายจุดขัดแย้งกันเอง

บทนี้มุ่งอธิบายวิธีจัดวางกฎการทำงานร่วมกันเป็นชั้นให้เหมาะสม:

- สิ่งใดเป็นนิสัยส่วนบุคคลของฉัน
- สิ่งใดเป็นกฎร่วมของรีโพซิทอรี
- สิ่งใดเป็นขอบเขตตายตัวระดับองค์กร
- สิ่งใดเป็นเพียงข้อกำหนดชั่วคราวของงานครั้งนี้

หากแบ่งชั้นไม่ชัดเจน มักเกิดสถานการณ์ที่ “เขียนไว้มากมาย แต่กลับไม่ทำงานในเวลาที่ควรทำงาน”

## การแบ่งชั้นทั่วไป (เชิงแนวคิด)

การเข้าใจการแบ่งชั้นช่วยลดความสับสนแบบ “เขียนกฎไว้แล้ว แต่กฎไม่ทำงาน” ไคลเอนต์ ความสามารถที่องค์กรบริหารจัดการ และรายละเอียดการนำไปใช้ในแต่ละเวอร์ชันอาจแตกต่างกัน แต่โดยทั่วไปให้เริ่มทำความเข้าใจจากชั้นต่อไปนี้:

```text
1. นโยบายที่องค์กร/ทีมบริหารจัดการ (หากมีการบังคับใช้)
2. AGENTS.md ระดับโปรเจกต์ / คำสั่งระดับโปรเจกต์ (ภายในรีโพซิทอรี)
3. การตั้งค่าและความชอบระดับผู้ใช้ (เช่น ~/.codex ในเครื่อง)
4. ข้อกำหนดชั่วคราวและการอ้างอิงด้วย @ ในงานปัจจุบัน
```

**หลักการ:** ยิ่งใกล้กับ “ข้อบังคับขององค์กร” มากเท่าไร ก็ยิ่งไม่ควรถูกผ่อนปรนโดยงานครั้งเดียวตามอำเภอใจ ส่วนชั้นที่ใกล้กับ “งานปัจจุบัน” จะยืดหยุ่นกว่า แต่ก็หายไปเมื่อเซสชันสิ้นสุดได้ง่ายกว่า ส่วน precedence ที่แน่นอนให้ยึดตามไคลเอนต์ปัจจุบันและเอกสารทางการ

## ความเข้าใจผิดที่พบบ่อย

### 1. หากเขียนพรอมป์เป็น ก็ไม่จำเป็นต้องตั้งค่าระยะยาวใช่ไหม

อาจพอใช้ได้สำหรับงานสั้น แต่เมื่อเริ่มทำงานร่วมกันอย่างต่อเนื่อง คุณจะยิ่งต้องการจัดเก็บข้อกำหนดที่พูดซ้ำไว้ในชั้นถาวรมากขึ้น

### 2. ใส่กฎทุกอย่างไว้ใน `AGENTS.md` ก็พอใช่ไหม

ไม่ถูกต้องเช่นกัน  
บางอย่างเหมาะจะเก็บไว้ใน:

- ความชอบส่วนบุคคล
- ไฟล์การตั้งค่า
- นโยบายที่องค์กรบริหารจัดการ
- พรอมป์ของงานปัจจุบัน

### 3. การตั้งค่าไม่ใช่ยิ่งมากยิ่งดี

หากการตั้งค่ากระจัดกระจาย กฎยาวเกินไป และลำดับชั้นสับสน ทั้งคนและเครื่องมือจะยิ่งตัดสินใจได้ยากว่าควรทำตามสิ่งใด

## ลำดับที่แนะนำ

เมื่อจัดระเบียบกฎการทำงานร่วมกันของ Codex อย่างเป็นระบบเป็นครั้งแรก ให้ทำตามลำดับนี้:

1. จัดระเบียบกฎของโปรเจกต์ก่อน
2. จากนั้นเพิ่ม `AGENTS.md`
3. แยกความชอบส่วนบุคคลออกมา
4. สุดท้ายจึงจัดการไฟล์การตั้งค่าและการควบคุมกฎที่ละเอียดขึ้น

วิธีนี้สับสนน้อยกว่าการเริ่มต้นด้วยการแก้คีย์การตั้งค่าจำนวนมากพร้อมกัน

กฎไม่จำเป็นต้องมีจำนวนมาก สิ่งสำคัญกว่าคือวางไว้ให้ถูกที่

## ข้อผิดพลาดที่พบบ่อย

- ใส่เอกสารสถาปัตยกรรมฉบับยาวไว้ใน `AGENTS.md` จนข้อจำกัดสำคัญถูกกลบ
- เขียนมาตรฐานของทีมซ้ำในบทสนทนา แต่ไม่ commit เข้ารีโพซิทอรี ทำให้ผู้ร่วมงานได้รับประสบการณ์ไม่สอดคล้องกัน
- ผ่อนปรน Sandbox ในเครื่องส่วนตัว แต่กลับสมมติว่าเพื่อนร่วมทีมมีสิทธิ์แบบเดียวกันในรีโพซิทอรีที่ใช้ร่วมกัน
