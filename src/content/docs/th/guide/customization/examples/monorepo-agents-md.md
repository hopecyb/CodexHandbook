ใน Monorepo มีหลาย app แพ็กเกจที่ใช้ร่วมกัน และหลาย technology stack อยู่ร่วมกัน การรวมทุกอย่างไว้ใน `AGENTS.md` ขนาดใหญ่เพียงไฟล์เดียวทำให้ Agent **แก้ผิดแพ็กเกจ** หรือรันการทดสอบผิดชุดได้ง่าย หน้านี้นำเสนอรูปแบบ **คำอธิบายแบบแบ่งชั้น** ที่นำกลับไปใช้ได้ (เป็นเพียงตัวอย่าง โปรดปรับให้เหมาะกับ repository ของคุณ)

## หน้านี้กล่าวถึงอะไร

- จะแบ่งหน้าที่เขียนคำสั่งระหว่างไดเรกทอรีรากกับแพ็กเกจย่อยอย่างไร
- จะทำให้ไฟล์ @ และข้อจำกัดของพาธสอดคล้องกับขอบเขตแพ็กเกจอย่างไร
- จะทำให้คำสั่งตรงกับสภาพแวดล้อม CI / Cloud อย่างไร

## เหตุใด repository ประเภทนี้จึงต้องมีคำอธิบายแบบแบ่งชั้นมากกว่า

หาก repository ทั่วไปเหมือนห้องพักหนึ่งห้อง Monorepo ก็เหมือนอาคารทั้งหลัง

ในอาคารมีหลายห้อง หลายผู้อยู่อาศัย และกฎที่ต่างกัน  
หากติดคำอธิบายรวมที่ยาวมากไว้เพียงแผ่นเดียวตรงทางเข้า Codex อาจเจอปัญหาได้ง่ายสองแบบ:

- มองเห็นกฎทั้งหมด แต่ไม่รู้ว่าตอนนี้ต้องทำตามกฎระดับใด
- ตั้งใจแก้เพียงแพ็กเกจเดียว แต่กลับเผลอไปเปลี่ยนส่วนอื่นด้วย

หัวใจสำคัญคือทำให้กฎชัดเจนไปพร้อมกับขอบเขตของไดเรกทอรี ไม่ใช่เพิ่มไฟล์ `AGENTS.md` หลายชุดแบบกลไก

## โครงสร้างที่แนะนำ (ตัวอย่าง)

```text
repo-root/
  AGENTS.md              # ส่วนกลาง: กลยุทธ์ branch, มาตรฐาน commit, ข้อห้าม
  apps/web/AGENTS.md     # frontend: framework, คำสั่งทดสอบ, ข้อตกลงการกำหนดเส้นทาง
  apps/api/AGENTS.md     # backend: รูปแบบ API, วินัยด้าน migration
  packages/shared/       # อาจลิงก์จากเอกสารระดับรากเท่านั้น หรือเพิ่มคำอธิบายย่อยสั้น ๆ
```

`AGENTS.md` ที่รากควรมี:

- ไดเรกทอรีใดที่ **ห้าม** Agent แก้ไข (เช่น `infra/prod/`)
- **ผู้รับผิดชอบหรือลิงก์เอกสาร** ของแต่ละแพ็กเกจย่อย
- คำสั่งติดตั้งส่วนกลาง: รัน `pnpm install` ที่ราก

## ความเข้าใจผิดที่พบบ่อย

### 1. เมื่อมีไดเรกทอรีมากขึ้น อย่ากองคำอธิบายทั้งหมดไว้ที่ราก

หลายคนที่เขียนคำสั่งสำหรับ monorepo เป็นครั้งแรกมักใส่ข้อจำกัดทั้งหมดไว้ใน `AGENTS.md` ที่รากโดยไม่รู้ตัว

ผลที่ตามมาคือ:

- ไฟล์ยาวมาก
- กฎที่เกี่ยวข้องกับงานปัจจุบันจริง ๆ ไม่เด่นชัด
- ข้อตกลงเฉพาะของแพ็กเกจย่อยถูกกลบได้ง่าย

แนวทางที่มั่นคงกว่ามักเป็นดังนี้: เขียนกติการ่วมของทั้ง repository ไว้ที่ราก และเขียนกฎเฉพาะส่วนไว้ในแต่ละแพ็กเกจย่อย

### คำอธิบายของแพ็กเกจย่อยมีไว้เพื่อลดขอบเขตการแก้ผิด ไม่ใช่ทำซ้ำกฎระดับราก

หากคำสั่งพัฒนา คำสั่งทดสอบ และข้อจำกัดของ `apps/web` กับ `apps/api` แตกต่างกัน การเขียนความแตกต่างเหล่านี้ไว้ในไดเรกทอรีของแต่ละส่วนจะช่วยให้ Codex หลงทางน้อยลง

## ตัวอย่างส่วนหนึ่งของ AGENTS.md สำหรับแพ็กเกจย่อย

```markdown
## ขอบเขต
แก้ไขเฉพาะ `apps/web/**` เว้นแต่งานจะระบุชัดว่าต้องแก้ข้ามแพ็กเกจ

## การพัฒนา
- ติดตั้ง: รัน `pnpm install` ที่ราก repository
- พัฒนา: `pnpm --filter web dev`
- ทดสอบ: `pnpm --filter web test`
- ตรวจสอบชนิด: `pnpm --filter web typecheck`

## การพึ่งพา
นำเข้าชนิดข้อมูลที่ใช้ร่วมกันจาก `@acme/shared` อย่าคัดลอกแล้ววาง
```

## ใช้ร่วมกับ prompt ของงาน

เมื่อ refactor ข้ามแพ็กเกจ ให้ **ระบุพาธอย่างชัดเจน**:

```text
เป้าหมาย: ใช้ API client ใหม่ใน apps/web
แก้ไขได้: apps/web/**, packages/api-client/**
ห้าม: แก้ service ฝั่ง backend ใน apps/api โดยตรง
เกณฑ์ยอมรับ: pnpm --filter web test && pnpm --filter api-client test
```

## Cloud และ CI

Monorepo บน Cloud มักล้มเหลวเพราะ **ไม่ได้ติดตั้งที่ราก** หรือใช้ filter ผิด ควรระบุสิ่งต่อไปนี้ไว้ใน `AGENTS.md` ที่ราก:

- ไดเรกทอรีทำงานเริ่มต้นคือรากของ repository
- คำสั่ง filter สำหรับงานของแพ็กเกจเดียว
- กลยุทธ์ cache (หากใช้ turborepo/nx ให้ระบุ task graph)

[สภาพแวดล้อม Cloud](/th/guide/web-and-cloud/cloud-environments/)

## ข้อผิดพลาดที่พบบ่อย

- เขียนคำอธิบายไว้เฉพาะใน `apps/web` แต่ Agent กลับแก้ lockfile ที่รากโดยไร้ขอบเขต
- คำสั่งทดสอบของแต่ละแพ็กเกจไม่เหมือนกันและไม่มีการบันทึกไว้ในเอกสาร
- AGENTS.md ของแพ็กเกจย่อยขัดแย้งกับเอกสารระดับราก

## จะตัดสินใจอย่างไรว่าควรเขียนไว้ที่รากหรือในแพ็กเกจย่อย

หากไม่แน่ใจว่าคำอธิบายข้อหนึ่งควรเขียนไว้ที่รากหรือในแพ็กเกจย่อย ให้ลองถามคำถามเหล่านี้ก่อน:

1. นี่เป็นกติการ่วมที่ทุกแพ็กเกจต้องทำตามหรือไม่
2. กฎนี้ใช้ได้เฉพาะกับไดเรกทอรีใดไดเรกทอรีหนึ่งหรือไม่
3. หากวางกฎนี้ผิดที่ จะทำให้ Agent แก้ไขผิดขอบเขตหรือไม่

หากใกล้เคียงข้อ 1 มากกว่า ให้วางไว้ที่ราก แต่หากใกล้เคียงข้อ 2 หรือ 3 ควรวางไว้ในแพ็กเกจย่อยมากกว่า
