“คำอธิบายโปรเจกต์” คือ **บริบทคงที่** ที่ช่วยให้ Codex เข้าใจรีโพซิทอรี โดยไม่จำกัดอยู่ที่ไฟล์รูปแบบใดรูปแบบหนึ่ง

## เนื้อหา

- นอกจาก `AGENTS.md` แล้ว ข้อมูลระดับโปรเจกต์ควรอยู่ที่ใด
- README, docs และไฟล์สคริปต์ควรแบ่งหน้าที่กันอย่างไร
- ข้อมูลใดเหมาะจะเขียนลงรีโพซิทอรี และข้อมูลใดควรอยู่เฉพาะในบทสนทนาปัจจุบัน

## องค์ประกอบของบริบทโปรเจกต์

| แหล่งที่มา | หน้าที่ |
|---|---|
| `AGENTS.md` | กฎและคำสั่งสำหรับการทำงานร่วมกัน (แหล่งอ้างอิงหลัก: ชุดบทความ AGENTS ในบทนี้) |
| `README.md` | โปรเจกต์คืออะไรและเริ่มใช้งานอย่างไร |
| `docs/` | สถาปัตยกรรม ADR และคู่มือปฏิบัติงาน |
| Dependency และสคริปต์ | ข้อเท็จจริงที่เรียกใช้งานได้ เช่น `package.json` และ `Makefile` |

Codex จะใช้เครื่องมืออ่านข้อมูลเหล่านี้ประกอบกัน สิ่งสำคัญคือรักษา **แหล่งข้อมูลจริงเพียงชุดเดียว** คำสั่งเริ่มต้นใน README ต้องรันได้จริง

## วิธีพื้นฐาน

1. ตรวจให้แน่ใจว่า `README.md` ที่ root มีสี่ส่วน ได้แก่ วัตถุประสงค์ การติดตั้ง การพัฒนา และการทดสอบ
2. ย้าย **คำอธิบายที่ต้องบอก Codex ซ้ำ** ลงใน `AGENTS.md`
3. ใช้ `@` ชี้ไปยังไฟล์ที่เจาะจงในงาน แทนการวางเนื้อหาทั้งหมด:

```text
ปฏิบัติตามข้อกำหนดการทดสอบใน @AGENTS.md แล้วแก้ null pointer ใน @src/auth/login.ts
ดูการออกแบบที่เกี่ยวข้องได้ที่ @docs/auth-flow.md
```

## ทำไมเรื่องนี้จึงสำคัญ

สถานการณ์ที่พบบ่อย ได้แก่:

- README อธิบายไว้อย่างหนึ่ง
- docs อธิบายไว้อีกอย่างหนึ่ง
- คำสั่งที่รันได้จริงซ่อนอยู่ใน `package.json`

เมื่อเป็นเช่นนี้ ไม่ใช่แค่คนที่สับสน Codex ก็สับสนเช่นกัน ประเด็นสำคัญคือทำให้ “ข้อเท็จจริงของโปรเจกต์” ในรีโพซิทอรีรวมศูนย์และสอดคล้องกันมากที่สุด

## แบ่งหน้าที่กับ “บริบทการสนทนา”

- **คำอธิบายโปรเจกต์**: ค่อนข้างคงที่ตลอดช่วงหลายเดือน
- **บริบทการสนทนา**: เป้าหมาย ข้อจำกัด และข้อสรุประหว่างทางของงานนี้

หากพบว่ากฎข้อหนึ่งถูกกล่าวซ้ำในงานระยะยาว ควร **เขียนกลับ** ไปยัง `AGENTS.md` หรือ `docs/` แทนการคัดลอกไปวางในสิบเธรด ดู [รักษาบริบทให้มุ่งประเด็น](/th/guide/context/keep-context-focused/)

## ข้อผิดพลาดที่พบบ่อย

- README ล้าสมัย ทำให้ Codex ทำงานตามคำสั่งที่ผิด
- ยัดเอกสารทั้งหมดไว้ใน `CONTEXT.md` ขนาดมหึมาเพียงไฟล์เดียวโดยไม่มีใครดูแล
- ใส่ข้อมูลอ่อนไหวไว้ในคำอธิบายของรีโพซิทอรีสาธารณะ

## ความเข้าใจผิดที่พบบ่อย

### 1. ตราบใดที่ฉันอธิบายชัดเจนในบทสนทนา เอกสารในรีโพซิทอรีจะยุ่งเหยิงบ้างก็ไม่เป็นไร

อาจพอใช้ได้ในระยะสั้น แต่จะยิ่งยุ่งเหยิงขึ้นเรื่อย ๆ ในระยะยาว

เพราะครั้งหน้าคุณต้องอธิบายใหม่อีกครั้ง และคนอื่นก็มองไม่เห็นสิ่งที่คุณพูดไว้ครั้งนี้

### 2. `AGENTS.md` แก้ปัญหาคำอธิบายโปรเจกต์ได้ทุกอย่าง

ไม่ได้เช่นกัน

`AGENTS.md` เหมาะสำหรับกฎและข้อจำกัดในการทำงานร่วมกันมากกว่า ไม่เหมาะจะใช้แทนบทนำโปรเจกต์ ภูมิหลังสถาปัตยกรรม และคำอธิบายการใช้งานฉบับเต็ม

### 3. ยิ่งมีเอกสารมากยิ่งดี

สิ่งที่สำคัญกว่าคือ:

- แบ่งหน้าที่ชัดเจน
- เนื้อหาสอดคล้องกัน
- คำสั่งสำคัญรันได้จริง

## คำแนะนำในการแบ่งหน้าที่

- `README.md`: โปรเจกต์คืออะไร เริ่มอย่างไร และทดสอบอย่างไร
- `AGENTS.md`: กฎการทำงานร่วมกัน พื้นที่ห้ามแตะ และนิยามของคำว่าเสร็จ
- `docs/`: ภูมิหลัง สถาปัตยกรรม และคำอธิบายกระบวนการที่ยาวกว่า
- สคริปต์และไฟล์การกำหนดค่า: ข้อเท็จจริงที่เรียกใช้งานได้

หัวใจของคำอธิบายโปรเจกต์คือทำให้ทั้ง Codex และคนค้นพบ “ข้อเท็จจริงของรีโพซิทอรี” ชุดเดียวกันได้ง่ายขึ้น จำนวนเอกสารไม่ใช่ประเด็นสำคัญในตัวมันเอง
