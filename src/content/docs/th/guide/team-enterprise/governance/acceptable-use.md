**นโยบายการใช้งานที่ยอมรับได้ (AUP)** ทำให้คำถามว่า “ใช้ Codex ทำเรื่องนี้ได้หรือไม่” กลายเป็นข้อตกลงร่วมขององค์กร แทนการพึ่งดุลยพินิจส่วนบุคคลเพียงอย่างเดียว โดยเสริมกับ [โมเดลภัยคุกคาม](/th/guide/team-enterprise/security/threat-model/): โมเดลภัยคุกคามอธิบายความเสี่ยง ส่วน AUP กำหนด **ขอบเขตพฤติกรรม**

## เนื้อหา

- ประเด็นที่ AUP ควรครอบคลุม
- การเชื่อมกับ HR/Compliance และการควบคุมทางเทคนิค
- ตัวอย่างร่างข้อกำหนด ซึ่งต้องให้ฝ่ายกฎหมายปรับให้เหมาะกับท้องถิ่น

## AUP ควบคุมอะไร

AUP ตอบคำถามหลักว่า แม้ในทางเทคนิคจะทำได้ ทีมของเราอนุญาตให้ทำเช่นนั้นหรือไม่

AUP ไม่ได้แทนนโยบายทางเทคนิค แต่เขียนขอบเขตระดับองค์กรให้ทุกคนเข้าใจและปฏิบัติตามได้

:::caution
เนื้อหาต่อไปนี้เป็นเพียง **โครงร่างเพื่อการศึกษา** ไม่ใช่คำปรึกษาทางกฎหมาย ก่อนประกาศใช้จริงต้องผ่านการตรวจของฝ่ายกฎหมายและ Compliance
:::

## ความเข้าใจผิดที่พบบ่อย

### AUP เกี่ยวข้องโดยตรงกับผู้ใช้งานหน้างาน

หลายคนมองเอกสารนโยบายแบบนี้เป็นเพียงข้อกำหนดเชิงพิธีการ และคิดว่าไม่เกี่ยวกับผู้ใช้งานหน้างาน

แต่ในการทำงานประจำวัน มักพบคำถามเหล่านี้จริง:

- ข้อมูลใดห้ามส่งให้ Codex
- สถานการณ์ใดต้องมีมนุษย์ตรวจทาน
- ส่วนขยายและการเชื่อมต่อภายนอกใดห้ามต่อโดยพลการ

ดังนั้น AUP ไม่ได้เป็นเพียงเอกสารฝ่ายกฎหมาย แต่เป็นขอบเขตการใช้งานจริงด้วย

### มีนโยบายแล้ว ไม่ได้แปลว่าทีมจะทำตามจริง

หากนโยบายระบุว่า “การเปลี่ยนแปลง production ต้องได้รับอนุมัติ” แต่ค่าเริ่มต้นของเครื่องมือกลับข้ามขั้นตอนนี้ได้ นโยบายจะหมดความหมายอย่างรวดเร็ว

AUP จึงควรสอดคล้องกับการฝึกอบรม สิทธิ์ การกำหนดค่า และการตรวจสอบ มากกว่ามุ่งเขียนให้ครอบคลุมทุกอย่างบนกระดาษ

## ประเด็นที่แนะนำให้ครอบคลุม

| ประเด็น | สาระสำคัญ |
|---|---|
| การใช้งานที่อนุญาต | การพัฒนา เอกสาร การวิจัย และระบบอัตโนมัติภายใน |
| การใช้งานที่ห้าม | การเข้าถึงโดยไม่ได้รับอนุญาต เนื้อหาคุกคาม และการหลีกเลี่ยงมาตรการความปลอดภัย |
| การจัดระดับข้อมูล | repository/ข้อมูลใดใช้ได้ และกฎเกี่ยวกับ PII ของลูกค้า |
| ความรับผิดชอบต่อผลลัพธ์ | ตรวจโดยมนุษย์ก่อน merge และไม่นำผลลัพธ์ไปใช้ภายนอกเป็นคำแนะนำทางกฎหมายหรือการแพทย์ |
| ส่วนขยาย | ใช้เฉพาะ Plugin/MCP ในรายการที่อนุมัติ |
| บัญชี | ห้ามใช้สิทธิ์ส่วนบุคคลร่วมกัน และเรียกคืนสิทธิ์เมื่อพนักงานออก |
| เหตุการณ์ | ช่องทางรายงานพฤติกรรมน่าสงสัย |

## โครงสร้างพื้นฐาน

1. **วัตถุประสงค์และขอบเขต**
2. **กรณีใช้งานที่อนุญาต** (เชื่อมไปยัง [แผนผังความสามารถ](/th/guide/start-here/codex-capability-map/))
3. **กรณีใช้งานที่ห้าม**
4. **ข้อมูลและการรักษาความลับ**
5. **ข้อกำหนดการกำกับดูแลโดยมนุษย์** (การ merge และการเปลี่ยนแปลง production)
6. **ผลของการฝ่าฝืน** (อ้างอิงคู่มือพนักงานที่มีอยู่)
7. **ผู้ติดต่อและวันที่อัปเดต**

## ทำให้สอดคล้องกับการควบคุมทางเทคนิค

| ข้อกำหนด AUP | การบังคับใช้ทางเทคนิค |
|---|---|
| ห้ามนำซอร์สโค้ดออกนอกระบบ | นโยบายเครือข่ายและการอนุมัติ MCP |
| การเปลี่ยนแปลง production ต้องได้รับอนุมัติ | การป้องกัน branch และ deny `git push` |
| ใช้เฉพาะโมเดลที่อนุมัติ | การกำหนดค่าที่องค์กรจัดการ |

## ข้อผิดพลาดที่พบบ่อย

- เขียน AUP แล้วแต่ไม่ฝึกอบรมใคร
- ไม่สอดคล้องกับความเป็นจริงทางเทคนิค นโยบายห้ามแต่เครื่องมืออนุญาต
- ไม่อัปเดตหลายปีจนตามฟีเจอร์ใหม่ เช่น Computer Use ไม่ทัน

## วิธีประเมินว่า AUP ใช้ได้ผลหรือไม่

เริ่มจากถามว่า:

1. นโยบายตอบขอบเขตการใช้งานที่ทีมพบจริงหรือไม่
2. นโยบายเชื่อมไปยังการฝึกอบรม การกำหนดค่า หรือกระบวนการอนุมัติได้หรือไม่
3. เมื่อมีการฝ่าฝืน ทีมรู้หรือไม่ว่าจะตรวจพบและจัดการอย่างไร

ยิ่งทั้งสามข้อมีคำตอบใกล้เคียง “ใช่” นโยบายก็ยิ่งมีโอกาสใช้ได้ผลจริง

## เช็กลิสต์ตรวจรับ

- [ ] onboarding ของพนักงานมีการรับทราบ AUP
- [ ] ไม่ขัดกับ [กฎของทีม](/th/guide/customization/rules/team-rules/)
- [ ] ทบทวนทุกปีหรือเมื่อมีฟีเจอร์สำคัญออกใหม่

คุณค่าของ AUP คือการระบุขอบเขตการใช้ Codex ของทีมให้ชัดเจน และทำให้สอดคล้องกับมาตรการควบคุมที่ใช้จริง
