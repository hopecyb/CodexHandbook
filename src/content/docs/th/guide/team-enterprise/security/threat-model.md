กล่าวอย่างง่าย “โมเดลภัยคุกคาม” คือการคิดถึงความเสี่ยงไว้ล่วงหน้า:

> **หาก Codex เชื่อมกับโค้ด คำสั่ง และเครื่องมือภายนอกของเราจริง เหตุการณ์ใดมีโอกาสเกิดขึ้นมากที่สุด**

**โมเดลภัยคุกคาม** แยกเรื่องนี้ออกมาให้เห็นชัด Codex ไม่ใช่เพียง “หน้าต่างแชตอีกอัน” แต่ยัง **อ่านโค้ด รันคำสั่ง และเรียกเครื่องมือภายนอก** ได้ บทนี้ปูภาพพื้นที่เสี่ยงหลัก ส่วนมาตรการเฉพาะดูได้ที่ [เมทริกซ์สิทธิ์](/th/guide/reference/permission-matrix/) และ [แซนด์บ็อกซ์](/th/guide/foundations/sandbox-and-network/)

## เนื้อหา

- สินทรัพย์และขอบเขตความไว้วางใจ
- ภัยคุกคามทั่วไปและแนวทางบรรเทา
- การแบ่งหน้าที่ระหว่างกฎ, Hooks และ CI

## เหตุใดเรื่องนี้ไม่ใช่ “งานของทีมความปลอดภัย” เท่านั้น

หากคุณเป็นนักพัฒนา ทีมแพลตฟอร์ม ผู้เขียนเอกสาร หรือผู้รับผิดชอบโครงการ เรื่องนี้เกี่ยวข้องโดยตรง ปัญหาที่เกิดขึ้นจริงในทีมมักเป็นสถานการณ์เหล่านี้:

- มอบ token ที่มีสิทธิ์สูงเกินไปให้ระบบอัตโนมัติ
- ให้ Agent ดำเนินการความเสี่ยงสูงกับอินพุตที่ไม่น่าเชื่อถือโดยตรง
- ไม่รู้ว่าข้อมูลใดดูได้และข้อมูลใดห้ามนำออก
- เลือกส่วนขยายจากฟังก์ชันเพียงอย่างเดียว โดยไม่ดูสิทธิ์และที่มา

คุณค่าของโมเดลภัยคุกคามคือช่วยให้ทีมกำหนดขอบเขตก่อนเกิดเหตุ

## สินทรัพย์และขอบเขต

| สินทรัพย์ | ตัวอย่าง |
|---|---|
| ซอร์สโค้ดและ IP | repository ส่วนตัวและงานออกแบบที่ยังไม่เผยแพร่ |
| ข้อมูลประจำตัว | API key, `.env` และ cloud IAM |
| ข้อมูลผู้ใช้ | PII และเนื้อหา ticket ของลูกค้า |
| โครงสร้างพื้นฐาน | CI และ pipeline สำหรับ deploy production |

**ขอบเขตความไว้วางใจ:** โดยค่าเริ่มต้นให้ถือว่าโมเดลและส่วนขยายอยู่ฝั่งที่ **เชื่อถือได้ไม่เต็มที่** ส่วนการตรวจโดยมนุษย์และนโยบายทำหน้าที่บังคับใช้ที่ขอบเขต

## คำถามหลักสองข้อ

ก่อนเชื่อมต่อในระดับทีม ให้ถามว่า:

1. สิ่งใดที่เรากลัวสูญเสียมากที่สุด
2. การกระทำผิดพลาดใดของ Codex ที่เรากังวลที่สุด

คำถามแรกช่วยระบุ “สินทรัพย์สำคัญ” ส่วนคำถามที่สองช่วยระบุ “การกระทำอันตราย” มาตรการควบคุมจำนวนมากสร้างขึ้นรอบสองคำถามนี้

## ตัวอย่างสถานการณ์

พิจารณาสถานการณ์นี้:

- Codex อ่าน repository ส่วนตัวได้
- เข้าถึงระบบ ticket ที่มีสิทธิ์ได้
- รันคำสั่ง shell ได้
- ส่งผลลัพธ์กลับไปยังส่วนความคิดเห็นได้

สิ่งที่ควรให้ความสำคัญคือ:

- จะเห็นเนื้อหาที่ไม่ควรเห็นหรือไม่
- จะทำสิ่งที่ไม่ควรทำหรือไม่
- จะนำข้อมูลที่ควรอยู่ภายในออกไปหรือไม่

เมื่อมองปัญหาในระดับนี้ โมเดลภัยคุกคามจะใกล้เคียงเช็กลิสต์ความเสี่ยงก่อนเปิดใช้งานจริง

## ภาพรวมภัยคุกคาม

| ภัยคุกคาม | คำอธิบาย | แนวทางบรรเทา |
|---|---|---|
| Prompt injection | issue/หน้าเว็บที่เป็นอันตรายชักจูงให้ใช้สิทธิ์เกินขอบเขต | ทำความสะอาดอินพุต, CI แบบอ่านอย่างเดียว, [หัวข้อ Injection](/th/guide/team-enterprise/security/prompt-injection/) |
| สิทธิ์มากเกินไป | token หรือแซนด์บ็อกซ์กว้างเกินไป | สิทธิ์ขั้นต่ำและการป้องกัน branch |
| ข้อมูลรั่วไหล | คำสั่ง/MCP ส่งเนื้อหา repository ออกไป | นโยบายเครือข่าย, DLP และ Hook ตรวจสอบ |
| ส่วนขยายอันตราย | Plugin/MCP ที่ไม่ผ่านการตรวจ | [ความเสี่ยงของส่วนขยาย](/th/guide/team-enterprise/security/plugin-and-mcp-risk/) |
| Supply chain | dependency และสคริปต์ถูกแทรกโค้ดอันตราย | ใช้ร่วมกับ SCA และ Code review ที่มีอยู่ |
| การทำงานผิดพลาด | Agent ลบฐานข้อมูลหรือ push ผิด | deny คำสั่งและ CI ที่ไม่มีสิทธิ์ push |

## กรณีที่ควรใส่ในโมเดลภัยคุกคามก่อน

หากความสามารถหนึ่งตรงตามสองข้อต่อไปนี้พร้อมกัน ควรนำเข้าโมเดลภัยคุกคามก่อน:

- เข้าถึงสินทรัพย์สำคัญได้
- ดำเนินการจริงได้

เช่น อ่าน repository ส่วนตัว เข้าถึง production API เรียก MCP ที่มีสิทธิ์เขียน หรือ push โค้ดอัตโนมัติ

## ครั้งแรกไม่ต้องพยายามทำทุกอย่าง

หลายทีมได้ยินคำว่าการกำกับดูแลความปลอดภัยแล้วพยายามเติมเอกสาร กระบวนการ และนโยบายทั้งหมดในครั้งเดียว สุดท้ายกลับไม่มีอะไรนำไปใช้จริง

สำหรับทีมที่เริ่มใช้ Codex ครั้งแรก โดยทั่วไปทำเรื่องตรงไปตรงมาเหล่านี้ก่อนก็เพียงพอ:

1. ระบุสินทรัพย์สำคัญที่สุด 3 ประเภท
2. ระบุการกระทำผิดพลาด 3 ประเภทที่ไม่ต้องการให้ Agent ทำมากที่สุด
3. กำหนดมาตรการควบคุมที่ตรงที่สุดให้ทั้ง 6 รายการ

ตัวอย่าง:

- หากกลัวข้อมูลฐาน production รั่ว ให้จำกัดข้อมูลประจำตัว production และเส้นทางส่งออกก่อน
- หากกลัว push ไป main ผิด ให้เพิ่มการป้องกัน branch และการอนุมัติก่อน
- หากกลัวหน้าเว็บหรือ issue ชี้นำผิด ให้จำกัดอินพุตภายนอกและใช้กระบวนการ Review แบบอ่านอย่างเดียวก่อน

วิธีนี้ยังไม่สมบูรณ์ แต่โดยทั่วไปมีประโยชน์กว่าเอกสารขนาดใหญ่ที่ไม่มีใครปฏิบัติตาม

## การควบคุมแบบหลายชั้นที่แนะนำ

```text
L1 ตัวตนและ tenant (SSO, กลุ่ม)
L2 การกำหนดค่าที่องค์กรจัดการและนโยบายโมเดล
L3 กฎของ repository + AGENTS.md
L4 แซนด์บ็อกซ์ / การอนุมัติ / Hooks
L5 Review โดยมนุษย์และการป้องกัน branch
```

## ข้อผิดพลาดที่พบบ่อย

- ฝึกอบรมอย่างเดียวโดยไม่มีการควบคุมทางเทคนิค
- สมมติว่า “โมเดลฉลาดพอ” จึงไม่ผิดพลาด
- วาง production secret ในพาธที่ Agent เขียนได้
- ลดความเสี่ยงทั้งหมดเหลือเพียงคำว่า “ให้มนุษย์ Review ก็พอ”

## เวอร์ชันขั้นต่ำ

เริ่มจากสามเรื่องนี้:

- การดำเนินการความเสี่ยงสูงต้องได้รับอนุมัติ
- ไม่ให้ข้อมูลอ่อนไหวสูงโดยค่าเริ่มต้น
- กระบวนการอัตโนมัติเป็นแบบอ่านอย่างเดียวโดยค่าเริ่มต้น

เมื่อสามเรื่องนี้มั่นคง ความเสี่ยงระดับทีมจำนวนมากจะลดลง แล้วจึงค่อยเพิ่มรายละเอียดด้านการกำกับดูแลภายหลัง
