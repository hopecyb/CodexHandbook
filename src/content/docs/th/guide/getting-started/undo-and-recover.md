เมื่อใช้ Codex ครั้งแรก หลายคนกังวลที่สุดว่า ถ้า Codex แก้ผิด จะย้อนกลับได้หรือไม่

ส่วนใหญ่ย้อนกลับได้ แต่ควรใช้วิธีที่ปลอดภัย

เมื่อผลลัพธ์เกินขอบเขตหรือคุณภาพไม่พอ:

1. ใช้ความสามารถเลิกทำหรือคืนค่าการเปลี่ยนแปลงของไคลเอนต์ โดยยึด UI ปัจจุบัน
2. หากโปรเจกต์อยู่ภายใต้ Git ให้ทิ้งการเปลี่ยนแปลงใน working tree ด้วยวิธีที่คุณคุ้นเคย ผู้เริ่มต้นยังไม่ต้องใช้ Git ก็ได้ โดยพึ่งไดเรกทอรีฝึก
3. เปิดเธรดใหม่ ลดขอบเขตข้อจำกัด แล้วลองอีกครั้ง

หลายครั้งการลดขอบเขตล่วงหน้าช่วยประหยัดงาน เช่น แก้เพียงไม่กี่ไฟล์ ระบุข้อห้ามให้ชัด และอ่านแผนก่อนดำเนินการ

![ภาพประกอบ: ลูกศรกรอกลับล้อมกองสแนปช็อตเวอร์ชัน โดยเวอร์ชันเก่าเลื่อนกลับเข้าที่ และมีตาข่ายนิรภัยด้านล่างรองรับหน้ากระดาษที่ยับ](/illustrations/undo-and-recover.webp)

## แยกความต่างระหว่าง “เลิกทำ” กับ “กู้คืน”

- **เลิกทำ**: ย้อนการเปลี่ยนแปลงล่าสุดที่ไม่พอใจ
- **กู้คืน**: นำโปรเจกต์กลับสู่สถานะที่คุณยืนยันว่าปลอดภัย

หากฝึกกับไฟล์เล็กหนึ่งไฟล์ การเลิกทำมักไม่ยาก สถานการณ์ที่ยุ่งยากกว่าคือ:

- Codex แก้มากกว่าหนึ่งไฟล์
- หลังจากนั้นคุณแก้เนื้อหาเองเพิ่มเติม
- คุณจำไม่ได้แล้วว่าส่วนใดใครเป็นคนแก้

หยุดการแก้ไขต่อก่อน แล้วจำกัดขอบเขตผลกระทบ

## ลำดับรับมือเมื่อทำผิดครั้งแรก

1. หยุดการแก้ไขต่อ อย่าตกใจแล้วสั่งให้ Codex แก้เพิ่ม
2. ยืนยันก่อนว่า Codex แก้ไฟล์ใดบ้าง
3. หากใช้การเลิกทำในผลิตภัณฑ์ได้ ให้เลือกวิธีนั้นก่อน
4. หากโปรเจกต์อยู่ภายใต้ Git อยู่แล้ว จึงใช้วิธีย้อนกลับด้วย Git ที่คุณคุ้นเคย
5. เมื่อกลับสู่สถานะปลอดภัยแล้ว ค่อยสั่งใหม่ให้ชัดเจนกว่าเดิม

## หากยังไม่คุ้นกับ Git ให้เริ่มแบบนี้

ผู้เริ่มต้นจำนวนมากกลัวคำว่า “กู้คืน” เพราะคิดว่าต้องรู้คำสั่ง Git มากมายก่อน แต่ช่วงแรกไม่จำเป็น

เริ่มได้ดังนี้:

- ฝึกในไดเรกทอรีฝึก
- ให้ Codex แก้ไฟล์เล็กเพียงไฟล์เดียวต่อครั้ง
- หากไม่พอใจผลลัพธ์ ให้เลิกทำโดยตรง

เมื่อเริ่มทำโปรเจกต์จริง ค่อยเรียนการย้อนกลับด้วย Git อย่างเป็นระบบ

## ป้องกันสำคัญกว่าแก้ภายหลัง

แนวทางต่อไปนี้ลดโอกาสที่ “แก้ผิดแล้วเก็บกวาดยาก” ได้ชัดเจน:

- ระบุชัดว่า “แก้เฉพาะไฟล์ใด”
- ให้ Codex เสนอแผนก่อน แล้วจึงดำเนินการ
- ตรวจหลังจบแต่ละขั้น อย่าสะสมการเปลี่ยนแปลงจำนวนมากแล้วค่อยดูพร้อมกัน
- ยืนยันก่อนการดำเนินการความเสี่ยงสูง

## ใช้จุดกู้คืนเป็นเครื่องมือสำรวจ

การกู้คืนไม่ได้มีไว้แก้ความผิดพลาดเท่านั้น คุณสร้างจุดกู้คืนก่อนทดลองแนวทางต่าง ๆ ได้ด้วย

สถานการณ์ที่ควรสร้างจุดกู้คืนก่อน:

- ต้องเปรียบเทียบแนวทางติดตั้งสองแบบ
- จะให้ Agent รีแฟกเตอร์ขอบเขตกว้าง
- จะทดลองสคริปต์อัตโนมัติหรือการแทนที่จำนวนมาก
- ไม่แน่ใจว่าความต้องการจะเปลี่ยนทิศเร็วหรือไม่

จังหวะที่ปลอดภัยกว่าคือ:

```text
ยืนยันสถานะปลอดภัยปัจจุบัน
→ ให้ Codex ระบุไฟล์ที่จะได้รับผลกระทบ
→ สร้างจุดกู้คืนหรือยืนยันสถานะ Git
→ ดำเนินการในขอบเขตเล็ก
→ ตรวจ diff และตรวจสอบผลลัพธ์
→ ตัดสินใจว่าจะเก็บ ย้อนกลับ หรือเปลี่ยนแนวทาง
```

หากไคลเอนต์รองรับ checkpoint หรือ replay ให้ใช้ความสามารถในตัวผลิตภัณฑ์ก่อน หากโปรเจกต์อยู่ภายใต้ Git ก็ใช้ branch, stash หรือ commit เล็กเป็นจุดกู้คืนได้ สิ่งสำคัญไม่ใช่การจำคำสั่ง แต่คืออย่าขยายการเปลี่ยนแปลงต่อเมื่อยังมองขอบเขตผลกระทบไม่ชัด

การทำผิดไม่น่ากลัว สิ่งที่ยุ่งยากกว่าคือแก้ต่อทั้งที่ยังไม่เห็นขอบเขตการเปลี่ยนแปลงชัดเจน
