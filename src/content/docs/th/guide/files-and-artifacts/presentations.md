งานนำเสนอ เช่น PPT, Keynote, Google Slides และ Marp/Reveal เน้น **โครงเรื่อง** กับ **ความสอดคล้องทางภาพ** Agent ทำโครงร่างและ draft แรกได้ดี แต่ master และ brand guideline ยังต้องให้มนุษย์ตรวจ

คุณค่าหลักของการใช้ Codex ทำงานนำเสนอคือช่วยวางโครงสร้าง ลำดับหน้า และ logic การเล่าเรื่อง ส่วนฉบับสุดท้ายยังต้องให้คุณเก็บรายละเอียดเอง

## เนื้อหาในหน้านี้

- Workflow ที่แนะนำเมื่อใช้ Codex ทำสไลด์
- ข้อแลกเปลี่ยนระหว่าง `.pptx` กับสไลด์ Markdown
- ป้องกันไม่ให้ “แต่ละหน้าดูคนละสไตล์” อย่างไร

## กำหนดรูปแบบส่งมอบก่อน

| รูปแบบ | เหมาะกับ |
|---|---|
| Marp / Slidev / reveal.md | นักพัฒนาและ version control |
| `.pptx` | รายงานธุรกิจและแชร์กับลูกค้า |
| Google Slides | การร่วมมือแบบ real-time มักผ่านการส่งออกหรือ MCP |
| ส่งออก PDF | แจกจ่ายแบบอ่านอย่างเดียว |

กำหนดรูปแบบตายตัวตั้งแต่ต้นงาน เพื่อไม่ให้ Agent ผสม toolchain หลายแบบ

เลือกตามผู้รับงานสุดท้าย:

- ให้ลูกค้า ผู้บริหาร หรือเพื่อนร่วมงานเปิดและแก้โดยตรง: มักใช้ `.pptx`
- ต้อง version control ร่วมกับโค้ด: มักใช้สไลด์ Markdown
- แจกจ่ายเพื่ออ่านอย่างเดียว: มักส่งออกเป็น PDF

## Workflow ที่แนะนำ

```text
1. โครงร่าง: ผู้ฟัง ระยะเวลา และสารหลัก 3-5 ข้อ
2. หัวข้อแต่ละหน้า + 3 bullet พร้อมประเด็น speaker notes
3. เลือกเครื่องมือและสร้าง draft แรก
4. ปรับ master แผนภูมิ และแหล่งข้อมูลด้วยคน
5. ส่งออก PDF แล้วซ้อมพร้อมจับเวลา
```

สอดคล้องกับ [สำรวจ—วางแผน—ลงมือ—ตรวจสอบ](/th/cases/workflows/explore-plan-execute-verify/): ตรวจรับโครงร่างก่อนเติมรายละเอียด

## ทำไมควบคุมโครงสร้างก่อน

หากไม่กำหนดโครงสร้าง Codex อาจสร้างหลายหน้าโดยตรง แต่เนื้อหามัก:

- ลำดับสับสน
- จำนวนหน้าควบคุมไม่ได้
- แต่ละหน้าดูเป็นโปสเตอร์แยก ไม่ใช่รายงานชุดเดียว

ให้ทำตามสามชั้นนี้:

1. กำหนดก่อนว่า “งานนำเสนอนี้ต้องอธิบายอะไรให้ชัด”
2. กำหนดว่า “แต่ละหน้ารับผิดชอบสารหลักประโยคใด”
3. แล้วจึงให้ Agent ช่วยเติมข้อความ คำอธิบายแผนภูมิ และ speaker notes

## ความเข้าใจผิดที่พบบ่อย

### 1. PPT สวยหวือหวาเท่ากับสื่อสารได้ดีกว่าหรือไม่

สิ่งที่ส่งผลต่อความเข้าใจจริงมักเป็น:

- หัวข้อสรุปประเด็นได้ในประโยคเดียวหรือไม่
- แต่ละหน้าพาเรื่องเดินหน้าหรือไม่
- ข้อมูลมีแหล่งที่มาหรือไม่

### 2. Agent สร้าง draft ทั้งชุดได้ จึงไม่ต้องให้คนตรวจหรือไม่

ยังต้องตรวจ  
อย่างน้อยควรให้คนตรวจส่วนเหล่านี้:

- แบรนด์และ master ของบริษัท
- ข้อสรุปสำคัญ
- ตัวเลขและแผนภูมิ
- เวอร์ชันที่ส่งภายนอก

### 3. ยิ่งใส่เนื้อหาเต็มหน้า ยิ่งมีข้อมูลครบหรือไม่

โดยทั่วไปจะยิ่งนำเสนอยาก  
หากหน้าเดียวมี bullet รูป และข้อสรุปมากเกินไป ผู้ชมจะจับประเด็นได้ยาก

## ลำดับการสร้างที่ใช้บ่อย

หากต้องการให้ Codex ช่วยทำงานนำเสนอตอนนี้ ให้ระบุตามลำดับ:

1. ผู้ฟังคือใคร
2. ระยะเวลานำเสนอ
3. สามประเด็นที่ต้องการให้ผู้ฟังจดจำ
4. ขอเฉพาะโครงร่างก่อน
5. ยืนยันโครงร่างแล้วจึงขยายแต่ละหน้า
6. สุดท้ายจึงเพิ่ม speaker notes ข้อกำหนดภาพ และรูปแบบส่งออก

ลำดับนี้ควบคุมงานได้ง่ายกว่า: โครงสร้างก่อน ข้อความต่อมา และสไตล์ท้ายสุด

## จุดสำคัญของ Prompt

- **ผู้ฟัง**: เพื่อนร่วมงานสายเทคนิคกับผู้บริหารต้องใช้ศัพท์ลึกต่างกัน
- **จำนวนหน้าสูงสุด**: ป้องกันข้อความฟุ่มเฟือย 80 หน้า
- **แบรนด์**: สีหลัก พาธ logo และห้าม clipart หากบริษัทมีกฎ
- **แผนภูมิข้อมูล**: ระบุไฟล์แหล่งข้อมูล และขอให้แก้ไขอัปเดตได้แทนการแต่งภาพ screenshot

ระบุ requirement ได้ตรง ๆ เช่น:

> “ช่วยทำโครงร่างไม่เกิน 10 หน้า ผู้ฟังคือผู้บริหารที่ไม่ใช่สายเทคนิค แต่ละหน้าให้มีข้อสรุปหลักเพียงข้อเดียว และเพิ่ม speaker notes ตอนท้าย”

วิธีนี้มักได้เวอร์ชันที่ปรับต่อได้ง่ายกว่าคำว่า “ทำ PPT ให้ดูพรีเมียม”

ดู requirement รูปภาพที่ [รูปภาพและภาพหน้าจอ](/th/guide/files-and-artifacts/images-and-screenshots/) และการสร้างภาพล้วนที่ [การสร้างรูปภาพ](/th/guide/tools/image-generation/)

## การตรวจรับ

- ขนาดตัวอักษรอ่านได้บนความละเอียดของโปรเจกเตอร์
- ใช้ animation พอเหมาะ เพราะมากเกินไปดูแลยาก
- ตัวเลขตรงกับ [แหล่งข้อมูลที่ตรวจสอบ](/th/guide/quality/validate-sources/)
- speaker notes เพียงพอหรือไม่ หากต้องใช้

## งานใดเหมาะให้ Codex ทำ และงานใดควรให้คุณตัดสิน

| เหมาะให้ Codex ทำ | ควรให้มนุษย์ตรวจ |
|---|---|
| แบ่งหน้าจากโครงร่าง | ถ้อยคำข้อสรุปสุดท้าย |
| Draft หัวข้อหน้า | ความสอดคล้องของแบรนด์ |
| Draft speaker notes | ข้อมูลอ่อนไหว |
| ข้อความอธิบายแผนภูมิ | เวอร์ชันเผยแพร่ภายนอก |

การแบ่งงานแบบนี้มักประหยัดเวลาและควบคุมคุณภาพสุดท้ายได้ง่ายกว่า

## ข้อผิดพลาดที่พบบ่อย

- ขอ “ทำ PPT รายงานไตรมาส” โดยไม่มีโครงร่าง
- แก้ binary `.pptx` ด้วยมือซ้ำ ๆ แต่ไม่เก็บ source Markdown
- ข้อมูลในแผนภูมิไม่ตรงกับ CSV ใน repository
- ให้ Agent ตัดสินโครงสร้าง ดีไซน์ ข้อสรุป และนิยามข้อมูลพร้อมกัน
