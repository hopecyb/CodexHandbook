รูปภาพช่วยให้ Agent **มองเห็น** ปัญหาอินเทอร์เฟซ เจตนาการออกแบบ หรือภาพร่างบนไวท์บอร์ด หน้านี้ครอบคลุมทั้ง input ที่คุณให้และการจัดการไฟล์รูปภาพใน repository ส่วนการสร้างภาพใหม่ ดู [การสร้างรูปภาพ](/th/guide/tools/image-generation/)

เมื่อมอบงานด้วยภาพหน้าจอ ควรบอกว่าต้องการให้ดูตรงไหน และทำไมส่วนนั้นจึงเป็นปัญหา

## เนื้อหาในหน้านี้

- แนบภาพหน้าจออย่างไรให้มีประสิทธิภาพ
- ใช้ design mockup หรือไฟล์ส่งออกจาก Figma อย่างไร
- ปัญหาขนาดของรูปภาพใน repository และบริบท

## กรณีใช้ภาพเป็น input

| กรณี | วิธีทำ |
|---|---|
| UI bug | ภาพหน้าจอ + คำอธิบายข้อความที่ระบุบริเวณผิดปกติ |
| ทำตามดีไซน์ | ส่งออก PNG + ระบุ breakpoint และ component library |
| ไวท์บอร์ดสถาปัตยกรรม | ภาพถ่ายชัดหรือไฟล์ส่งออก + คำอธิบายสัญลักษณ์ |
| กล่องข้อความ error | ให้เห็นข้อความ error ครบ อย่าตัดเหลือเพียงมุมเดียว |

อ่านเชิงลึกที่ [การเขียน prompt ด้วยรูปภาพ](/th/prompts/prompting-with-images/)

## รูปภาพเพิ่มข้อมูลอะไรจริง ๆ

รูปภาพมีคุณค่าที่แสดงข้อมูลซึ่งอธิบายด้วยข้อความได้ยาก เช่น:

- layout เบี้ยวอย่างไร
- ปุ่มถูกเบียดไปตรงไหน
- กล่องข้อความเขียนว่าอะไร

แต่รูปภาพเพียงอย่างเดียวไม่ได้บอก Codex โดยอัตโนมัติว่า:

- คุณให้ความสำคัญกับส่วนใด
- คาดหวังให้แก้อย่างไร
- ภาพนี้คือ “สถานะปัจจุบัน” หรือ “ผลลัพธ์เป้าหมาย”

จึงควรแนบคำอธิบายตรงไปตรงมากับภาพ

## ข้อกำหนดด้านคุณภาพ

- **ความละเอียด**: ข้อความต้องอ่านได้ หลีกเลี่ยง thumbnail ที่เบลอ
- **การครอป**: ตัด desktop ที่ไม่เกี่ยวข้องและข้อมูลอ่อนไหวในแถบแจ้งเตือนออก
- **การทำเครื่องหมาย**: ใช้ลูกศรหรือวงกลมได้ แต่ควรอธิบายจุดสำคัญเป็นข้อความด้วย
- **หลายภาพ**: อัปโหลดเป็นคู่ “ปัจจุบัน / เป้าหมาย”

## ความเข้าใจผิดที่พบบ่อย

### 1. ส่งภาพหน้าจอแล้ว ไม่ได้แปลว่าระบบจะเข้าใจปัญหาเอง

ภาพหน้าจอให้หลักฐานทางสายตา แต่ควรเสริมว่า:

- ปัญหาอยู่ตรงไหน
- ต้องการให้แก้เป็นอะไร
- ภาพใดคือปัจจุบัน ภาพใดคือเป้าหมาย

### 2. ภาพยิ่งใหญ่ยิ่งชัด ไม่ได้แปลว่ายิ่งดี

ภาพต้นฉบับขนาดใหญ่เกินไปทำให้:

- มีข้อมูลไม่เกี่ยวข้องมาก
- repository หรือบริบทหนักขึ้น

### 3. ส่งเฉพาะภาพดีไซน์ก็ยังไม่พอ

หากต้อง “ทำตามภาพ” ควรเพิ่ม:

- ข้อกำหนด breakpoint
- ข้อจำกัด component
- ส่วนใดปรับได้อิสระและส่วนใดห้ามปรับ

## รูปภาพใน repository

| แนวปฏิบัติ | เหตุผล |
|---|---|
| รวมไว้ใน `assets/` หรือ `docs/images/` | ดูแลรักษาง่าย |
| WebP/บีบอัด | ควบคุมขนาด clone |
| ชื่อไฟล์สื่อความหมาย | ใช้ `login-form-mobile.png` แทน `image1.png` |
| alt text ในเอกสาร | การเข้าถึง |

## ข้อความที่นำไปใช้ได้ทันที

ใช้ข้อความนี้ได้โดยตรง:

```text
ภาพแรกคือหน้าปัจจุบัน ภาพที่สองคือผลลัพธ์เป้าหมาย
ให้เน้นบริเวณหัวเรื่องบนหน้าจอแรกและระยะห่างของปุ่ม
อย่าเดา business logic จากภาพหน้าจอ ให้แก้เฉพาะภาพและ layout
```

## ความเป็นส่วนตัวและความปลอดภัย

- ภาพหน้าจออาจมีข้อมูลลูกค้า URL ภายใน หรือ token ให้ปิดบังก่อน
- อย่าส่งหน้าจอ config ที่มี secret ให้กับงานที่ไม่น่าเชื่อถือ
- [บริบทอ่อนไหว](/th/guide/context/sensitive-context/)

## การตรวจรับ

สำหรับงาน “ทำตามภาพ”:

1. เปรียบเทียบ implementation กับภาพอ้างอิงข้างกัน หรือเปิดหน้าด้วย [เครื่องมือเบราว์เซอร์](/th/guide/tools/browser/)
2. ตรวจ responsive layout และ dark mode หากกำหนด
3. [ตรวจสอบ artifact](/th/guide/quality/verify-artifacts/)

## ข้อผิดพลาดที่พบบ่อย

- ให้เฉพาะ design mockup โดยไม่อธิบาย interaction
- commit ภาพต้นฉบับ 4K โดยตรง
- สมมติว่าโมเดลอ่านลิงก์ Figma ได้โดยไม่ส่งออก

ภาพหน้าจอที่ดีไม่ใช่เพียง “มีรูป” งานจะมีโอกาสถูกต้องมากขึ้นเมื่อภาพชัด จุดสำคัญชัด และความคาดหวังชัด
