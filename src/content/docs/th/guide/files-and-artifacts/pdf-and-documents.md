PDF มักใช้กับ specification, paper, เอกสารสแกน และรายงานส่งออก ต่างจากข้อความล้วนตรงที่ PDF **มีโครงสร้างซับซ้อน ขนาดใหญ่ และ diff ยาก** จึงต้องกำหนดวิธีทำงานแยก

เมื่อส่ง PDF ให้ Codex ปัญหาที่พบบ่อยคือเข้าใจโครงสร้างไม่ครบ หรือขอบเขตกว้างเกินไป

## เนื้อหาในหน้านี้

- ให้ Agent “อ่าน” เนื้อหา PDF อย่างถูกต้องอย่างไร
- กำหนดรูปแบบและพาธเมื่อสร้างหรือแก้ PDF อย่างไร
- ป้องกันกรณี “ดูเหมือนมีไฟล์แต่เปิดไม่ได้” ตอนตรวจรับอย่างไร

## ทำไม PDF จึงเกิดปัญหาง่าย

PDF อาจมีหลายอย่างพร้อมกัน:

- ภาพสแกน
- layout หลายคอลัมน์
- header และ footer
- ตาราง
- รูปภาพและข้อความผสมกัน

ยิ่งระบุชัดว่า “ดูส่วนใด ต้องการผลลัพธ์อะไร” ผลลัพธ์มักยิ่งเสถียร

## อ่าน PDF

### วิธีที่แนะนำ

1. **ระบุพาธไฟล์**: `docs/spec.pdf` หรืออ้างด้วย @ ตามที่ไคลเอนต์รองรับ
2. **ระบุสิ่งที่ต้องการ**: สรุป เปรียบเทียบบท หรือดึงข้อมูลตาราง
3. **เลขหน้าหรือบท**: จำกัดขอบเขตเอกสารยาวเพื่อประหยัดบริบท
4. **เนื้อหาอ่อนไหว**: สัญญา สแกนบัตรประชาชน และข้อมูลคล้ายกันต้องใช้ขั้นตอน [บริบทอ่อนไหว](/th/guide/context/sensitive-context/)

### ข้อจำกัด

- PDF สแกนอาจต้องใช้ OCR ผลลัพธ์อาจผิดและต้องสุ่มตรวจด้วยคน
- layout ซับซ้อน หลายคอลัมน์ และ footnote อาจเสียโครงสร้าง
- อย่าใส่ PDF ขนาดใหญ่มากทั้งฉบับในงานเดียว ให้แบ่งส่วนหรือแปลงเป็นโครงร่าง Markdown ก่อน

## ความเข้าใจผิดที่พบบ่อย

### 1. ส่ง PDF ทั้งฉบับไม่ได้แปลว่าจะสกัดประเด็นสำคัญได้เสถียร

หาก PDF ยาว ซับซ้อน และมีหน้าสแกน วิธีที่มั่นคงกว่าคือ:

- ระบุขอบเขต
- ระบุงาน
- แบ่งทำเป็นส่วน

### 2. PDF สแกนต่างจาก PDF ข้อความมาก

ไฟล์สแกนมักต้องผ่าน OCR ก่อน หาก OCR ผิด การสรุป ดึงข้อมูล และตัดสินหลังจากนั้นก็อาจผิดตาม

### 3. สร้างไฟล์ PDF ได้ไม่ได้แปลว่างานเสร็จ

ยังต้องยืนยันว่า:

- เปิดได้หรือไม่
- ข้อความมีอักขระผิดหรือไม่
- จำนวนหน้า สารบัญ และตารางถูกหรือไม่
- ฟอนต์ภาษาจีนถูกฝังจริงหรือไม่

## สร้างหรืออัปเดต PDF

| วิธี | เหมาะกับ |
|---|---|
| Compile จาก Markdown/LaTeX | เอกสารเทคนิคและรายงานที่สร้างซ้ำได้ |
| Print จาก HTML | layout แบบง่าย |
| สร้างด้วย library เช่น reportlab | ใบเสร็จและป้ายแบบ programmatic |

ระบุใน prompt:

- output path และชื่อไฟล์
- ขนาดหน้า ภาษา และฟอนต์ โดย PDF ภาษาจีนต้องใส่ใจการฝังฟอนต์เป็นพิเศษ
- ต้อง commit เข้า Git หรือไม่ โดย binary ใหญ่มักใช้ artifact หรือ release

## ข้อความที่นำไปใช้ได้ทันที

มอบหมายได้โดยตรงดังนี้:

```text
โปรดอ่านเฉพาะหน้า 12-18 ของ `docs/spec.pdf` และดึงเกณฑ์ตรวจรับ
อย่าสรุปเอกสารทั้งฉบับ
หาก OCR หรือการอ่าน layout ไม่แน่นอน ให้ระบุอย่างชัดเจน
```

## ความสัมพันธ์กับนโยบาย repository

- พิจารณาใช้ **Git LFS** หรือไม่เก็บ PDF binary ขนาดใหญ่ใน repository
- เมื่อ diff อ่านไม่ได้ ให้ตรวจรับด้วยการ **เปิดไฟล์** + เทียบกับ [การตรวจสอบ artifact](/th/guide/quality/verify-artifacts/)
- ดูรายการสิ่งที่สร้างได้ที่ [การตรวจรับ artifact ที่สร้าง](/th/guide/files-and-artifacts/generated-artifacts/)

## ข้อผิดพลาดที่พบบ่อย

- ขอให้ “แก้อักษรหนึ่งตัวใน PDF” แต่ไม่ให้ source ที่แก้ได้ เช่น `.md` / `.tex`
- ใส่ PDF ลับใน public repository แล้วให้ Cloud จัดการ
- ไม่เปิดตรวจรับ และดูเพียงว่า “มีไฟล์”

## Checklist การตรวจรับ

- [ ] เปิด PDF ได้ใน reader หรือสภาพแวดล้อมพิมพ์เป้าหมาย
- [ ] จำนวนหน้า สารบัญ และตารางสำคัญตรงตามคาด
- [ ] ขนาด repository และนโยบาย LFS ตรงตามมาตรฐานทีม

เมื่อจัดการ PDF ยิ่งขอบเขตชัด ผลยิ่งเสถียร หลังสร้าง PDF อย่าดูเพียงว่ามีไฟล์ ต้องยืนยันว่าเปิดได้และเนื้อหาถูกต้องจริง
