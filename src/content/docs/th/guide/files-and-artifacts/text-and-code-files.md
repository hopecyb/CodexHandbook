งานพัฒนาส่วนใหญ่อยู่ใน **ไฟล์ข้อความและโค้ด** ได้แก่ source code, test, config และ Markdown หน้านี้อธิบายวิธีจำกัดขอบเขต รักษารูปแบบให้สอดคล้อง และ merge อย่างปลอดภัย

เมื่อให้ Codex แก้ไฟล์ข้อความหรือโค้ด สิ่งสำคัญคือต้องแก้ถูกที่ ด้วยวิธีที่ถูก และไม่แก้ส่วนเกิน

## เนื้อหาในหน้านี้

- ทำให้การแก้ไขอยู่ในพาธและ encoding ที่ถูกต้องอย่างไร
- จัดงานแก้หลายไฟล์อย่างไร
- ทำงานร่วมกับ formatter และ linter อย่างไร

## ประเภทไฟล์และข้อควรระวัง

| ประเภท | ข้อควรระวัง |
|---|---|
| Source code เช่น `.ts`, `.py` | ทำตาม `AGENTS.md` และรูปแบบเดิม |
| Config เช่น `.json`, `.yaml`, `.toml` | โครงสร้างเสียได้ง่าย ต้องมี syntax ที่ถูกต้อง |
| เอกสาร `.md` | พาธลิงก์สัมพัทธ์ และรูปแบบข้อความหลายภาษา |
| Generated code | ระบุว่าควร commit หรือ gitignore |

บริบท: [บริบทไฟล์และโฟลเดอร์](/th/guide/context/file-and-folder-context/)

## ทำไมไฟล์ประเภทนี้จึงผิดพลาดง่าย

จุดที่มักเกิดปัญหา:

- เขียนลงไฟล์ที่ไม่ควรแก้
- ต้องการแก้นิดเดียว แต่เขียนใหม่เป็นบริเวณกว้าง
- รูปแบบไม่ตรงกับโปรเจกต์
- ทำ syntax ของไฟล์ config เสียโดยไม่รู้ตัว

## โครงสร้าง prompt ที่แนะนำ

```text
เป้าหมาย: <หนึ่งประโยค>
อนุญาตให้แก้: <path glob>
ห้าม: แก้ lockfile หรือไดเรกทอรีที่ไม่เกี่ยวข้อง
รูปแบบ: ให้ตรงกับ <ไฟล์ตัวอย่าง>
เสร็จเมื่อ: ระบุไฟล์ที่เปลี่ยน + รัน <คำสั่งทดสอบ>
```

ดู [โครงสร้างของงานที่ดี](/th/prompts/task-anatomy/)

## ความเข้าใจผิดที่พบบ่อย

### 1. บอกเพียง “ช่วยแก้ไฟล์นี้”

ข้อมูลมักไม่พอ

ควรเพิ่มว่า:

- แก้ไฟล์ใดได้
- ห้ามแตะไฟล์ใด
- ใช้ไฟล์ใดเป็นตัวอย่างรูปแบบ
- ตรวจสอบหลังเสร็จอย่างไร

### 2. ไฟล์ config ไม่ต่างจากข้อความทั่วไป

มองแบบนั้นไม่ได้

ไฟล์อย่าง `.json`, `.yaml` และ `.toml` มักเกิดปัญหาที่โครงสร้าง การเยื้อง และ syntax

### 3. แก้ให้ครอบคลุมยิ่งประหยัดเวลา

หลายกรณี การเปลี่ยนแปลงที่เล็ก อธิบายได้ และตรวจง่าย มั่นคงกว่าการ “ปรับปรุงไปพร้อมกัน” ในวงกว้าง

## Encoding และ line ending

- ใช้ **UTF-8** โดยค่าเริ่มต้น โปรเจกต์ที่ใช้ encoding พิเศษควรระบุใน `AGENTS.md`
- ให้ตรงกับ `.editorconfig` / `prettier` เพื่อไม่ให้เกิด diff ทั้งไฟล์จาก line ending
- แก้ไฟล์ใหญ่เป็นส่วน ๆ โดยอ้างฟังก์ชันเฉพาะ ไม่เขียนใหม่ทั้งไฟล์

## เมื่อกังวลว่าจะแก้มากเกินไป

กำหนดสามข้อโดยตรง:

1. อธิบายก่อนว่าจะกระทบไฟล์ใด
2. แก้เฉพาะขอบเขตขั้นต่ำที่งานต้องใช้
3. ระบุการตรวจสอบหลังแก้

## จุดตรวจทาน

- [ตรวจทาน diff](/th/guide/quality/review-diffs/): logic, ขอบเขต และการลบ
- [รันการทดสอบ](/th/guide/quality/run-tests/)
- อย่าเพิ่ม placeholder `TODO` ที่ยังไม่ implement โดยไม่ตั้งใจ

## ข้อผิดพลาดที่พบบ่อย

- “Refactor ทั้งโปรเจกต์” จนเปลี่ยนหลายร้อยไฟล์
- บังคับแก้ binary หรือไฟล์ minified แบบข้อความ
- ใช้ absolute path ในลิงก์เอกสารจนเกิด 404 ภายในเว็บไซต์

ไฟล์ข้อความและโค้ดเสี่ยงที่สุดเมื่อแก้กว้าง กระจัดกระจาย และตรวจยาก ระบุขอบเขต รูปแบบ และวิธีตรวจสอบให้ชัด จะลดการแก้กลับไปมาได้มาก
