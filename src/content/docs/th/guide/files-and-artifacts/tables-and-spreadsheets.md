งานตารางเป็นตัวอย่างที่ผิดได้โดยไม่สังเกต หาก delimiter, encoding, header, formula หรือรูปแบบวันที่ผิดอย่างใดอย่างหนึ่ง ระบบ downstream อาจเสียทั้งหมด

## เนื้อหาในหน้านี้

- ให้ Codex อ่านและเขียน CSV / Excel อย่างปลอดภัยอย่างไร
- โครงสร้าง prompt สำหรับงานวิเคราะห์ข้อมูล
- ตรวจตัวเลขและจำนวนแถวอย่างไร

## เลือกรูปแบบ

| รูปแบบ | ข้อดี | ข้อควรระวัง |
|---|---|---|
| CSV | เป็นข้อความ diff ได้ และใช้ทั่วไป | encoding เช่น UTF-8 BOM, delimiter และการ escape เครื่องหมายคำพูด |
| TSV | ลดปัญหา comma ชนกัน | เหมือน CSV |
| XLSX | หลาย sheet และ formula | เป็น binary, diff ยาก ต้องอ่านเขียนด้วย library |
| Google Sheets | ทำงานร่วมกัน | มักผ่าน MCP หรือส่งออก CSV |

ข้อมูลขนาดเล็กที่ต้องเข้า Git: **เลือก CSV/TSV ก่อน** รายงานซับซ้อน: **ข้อมูลต้นทาง CSV + สคริปต์สร้าง XLSX**

ให้ดูสามข้อนี้ก่อน:

- ต้อง diff ติดตาม และสร้างซ้ำได้: เลือก CSV / TSV
- ต้องส่งให้ผู้ใช้ Excel: ค่อยส่งออก XLSX
- อย่าปะปน “รูปแบบดูผลสุดท้าย” กับ “รูปแบบ source ที่เหมาะกับ automation”

## อ่านและวิเคราะห์

โครงสร้าง prompt ที่แนะนำ:

```text
ไฟล์: data/sales_2025.csv
Encoding: UTF-8
งาน: สรุป revenue ตาม region แล้วเขียน summary.csv
ข้อจำกัด: ห้ามแก้ไฟล์ต้นฉบับ ให้ค่าว่างเป็น 0 และเก็บทศนิยม 2 ตำแหน่ง
การตรวจรับ: พิมพ์ 5 แถวแรก + จำนวนแถวทั้งหมด
```

บริบท: [บริบทไฟล์และโฟลเดอร์](/th/guide/context/file-and-folder-context/)

## ทำไมงานตารางจึงผิดได้โดยไม่สังเกต

จุดที่เกิดปัญหาจริงมักเป็น:

- วันที่ถูกมองเป็นข้อความหรือวันที่
- ค่าว่างนับเป็น 0 ข้าม หรือ error
- คอลัมน์ใดเป็น unique identifier
- ทศนิยมและจำนวนเงินต้องปัดหรือไม่
- แก้ไฟล์ต้นฉบับได้หรือไม่

หากไม่ระบุ Codex อาจ “ดูเหมือนทำเสร็จ” แต่ผลลัพธ์ไม่น่าเชื่อถือ

## เขียนและทำความสะอาด

- ระบุ **ชื่อ ลำดับ และ type ของคอลัมน์** โดยใช้ ISO 8601 สำหรับวันที่
- ประมวลผลตารางใหญ่เป็น batch เพื่อไม่ให้ใช้หน่วยความจำเกิน
- เขียนกฎ deduplication และ merge key ลงในงาน อย่าให้ Agent เดา “primary key”

## ความเข้าใจผิดที่พบบ่อย

### 1. เปิดไฟล์ได้แปลว่าประมวลผลถูกแล้ว

ไม่ใช่

ในงานตาราง “เปิดได้” กับ “ข้อมูลไม่เสีย” เป็นคนละเรื่อง

### 2. ดูปกติใน Excel แปลว่าไม่มีปัญหาแน่นอน

ข้อผิดพลาดบางอย่างจะปรากฏเมื่อระบบ downstream ใช้ เช่น:

- encoding ผิด
- ลำดับคอลัมน์เปลี่ยน
- type ตัวเลขเปลี่ยน
- formula ถูกแทนด้วยค่าคงที่

### 3. ให้ Agent ตัดสินค่าว่าง วันที่ และ primary key เองได้

โดยทั่วไปไม่แนะนำ

ยิ่งระบุกฎเหล่านี้ชัด ผลยิ่งเสถียร

## เมื่อมอบหมายงานตาราง ให้ระบุห้าข้อนี้

พยายามสรุป requirement เป็น 5 ข้อนี้:

1. ไฟล์ input คืออะไร
2. ไฟล์ output ชื่ออะไร
3. ต้องเก็บ สรุป หรือทำความสะอาดคอลัมน์ใด
4. จัดการค่าว่าง วันที่ และค่าซ้ำอย่างไร
5. ตรวจสอบผลอย่างไร

ชัดเจนกว่าการบอกเพียง “ช่วยจัด Excel นี้ให้หน่อย” มาก

หากใช้ Python ให้ใช้ `pandas` อ่านเขียน หากใช้ Node ให้ใช้ `csv-parse` / `xlsx` และกำหนด library มาตรฐานของโปรเจกต์ใน `AGENTS.md`

## การตรวจสอบ

- ตรวจจำนวนแถวและผลรวมเทียบกับข้อมูลต้นทาง
- เปิดใน Excel เพื่อตรวจว่าวันที่ไม่กลายเป็นตัวเลข
- [ตรวจสอบ artifact](/th/guide/quality/verify-artifacts/): สุ่มเทียบข้อมูล

สำหรับงานตาราง สิ่งสำคัญกว่าคือระบุคอลัมน์ type กฎ และการตรวจรับให้ชัด

## ข้อผิดพลาดที่พบบ่อย

- เปิด CSV ภาษาจีนใน Excel แล้วอักขระผิด เพราะไม่มี BOM หรือ encoding ผิด
- ไม่อธิบายการปัดเศษของผลรวม floating point
- แก้ formula ใน Excel แต่ไม่บันทึกเป็นสคริปต์ที่สร้างซ้ำได้

## Checklist การตรวจรับ

- [ ] ชื่อและ type คอลัมน์ตรงกับข้อตกลงของผู้ใช้ downstream
- [ ] ผลรวมและตัวอย่างตรงกับการตรวจด้วยคนหรือ SQL
- [ ] ไม่เขียนทับไฟล์ต้นฉบับโดยไม่ตั้งใจ หรือเห็นการเปลี่ยนแปลงใน diff
