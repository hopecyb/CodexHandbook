เมื่อ Agent ทำงานเสร็จ อาจสร้างรายงาน สคริปต์ เว็บไซต์ static ข้อมูลทดสอบ และ **artifact** อื่น ๆ ซึ่งอาจไม่ผ่านเส้นทาง code review ที่คุณคุ้นเคย จึงต้องมีวิธีตรวจรับแยกต่างหาก

การที่ Codex สร้างไฟล์ใหม่ ไม่ได้แปลว่าไฟล์นั้นพร้อมใช้งานทันที

## เนื้อหาในหน้านี้

- ความต่างของการตรวจรับ artifact กับ “การแก้โค้ดเดิม”
- Checklist
- เมื่อใดควรปฏิเสธหรือขอให้ทำใหม่

## ประเภท artifact

| ประเภท | จุดตรวจรับ |
|---|---|
| สคริปต์ `.sh`, `.py` | รันได้ ปลอดภัย และ idempotent |
| รายงาน `.md`, `.html` | ข้อเท็จจริงถูก ลิงก์ใช้ได้ |
| Build output `dist/` | ควรอยู่ใน gitignore หรือไม่ |
| Test fixture | ไม่มี PII จริง |
| Config template | ไม่มีรหัสผ่านเริ่มต้นที่อ่อนแอ |

## “Artifact” ในที่นี้คืออะไร

ได้แก่:

- ไฟล์ใหม่ที่ระบบเขียนให้
- รายงานที่ระบบส่งออกให้
- หน้า ไดเรกทอรี หรือแพ็กเกจที่ระบบ build ให้

สิ่งเหล่านี้ต่างจาก “แก้โค้ดเดิมไม่กี่บรรทัด” เพราะคุณอาจมองข้ามเนื้อหาจริงได้ง่ายกว่า

## ขั้นตอนตรวจรับ

```text
1. เปิด artifact อย่าดูเพียงสรุปข้อความของ Agent
2. เทียบกับ “definition of done” ในงาน
3. รันคำสั่งทดสอบหรือ preview ที่เกี่ยวข้อง
4. ตรวจพาธ สิทธิ์ และขนาด
5. ตัดสินใจ: ยอมรับ / แก้บางส่วน / ทิ้งและทำใหม่
```

วิธีการ: [ตรวจสอบ artifact](/th/guide/quality/verify-artifacts/) และ [definition of done](/th/guide/quality/definition-of-done/)

## ความเข้าใจผิดที่พบบ่อย

### 1. แม้ระบบบอกว่า “เสร็จแล้ว” ก็ต้องดู artifact จริง

สรุปบอกได้เพียงว่า “ระบบคิดว่าทำอะไร” แต่แทนการเปิดไฟล์เพื่อตรวจว่า “artifact จริงเป็นอย่างไร” ไม่ได้

### 2. ไฟล์ใหม่ไม่ได้ปลอดภัยกว่าไฟล์เดิมเสมอ

ไฟล์ใหม่ก็อาจมี:

- เนื้อหาผิด
- dependency ที่ไม่จำเป็น
- ข้อมูลรั่ว
- ไฟล์ใหญ่ที่ไม่ควร commit เข้า repository

### 3. แม้รันได้ ก็อาจไม่ควร commit

artifact บางอย่างเหมาะกับการใช้ชั่วคราวในเครื่องเท่านั้น ไม่เหมาะกับ Git

## ความสัมพันธ์กับ Git

- ระบุว่า artifact ใด **ควร commit** และรายการใดควรอยู่ใน `.gitignore`
- หลีกเลี่ยง build cache ขนาดหลาย megabyte ปะปนใน PR
- ใช้ CI artifact หรือ external storage สำหรับ artifact ขนาดใหญ่

## ลำดับตรวจรับที่ใช้บ่อย

เมื่อได้รับ artifact หลายรายการ:

1. ยืนยันก่อนว่าสร้างไฟล์อะไรบ้าง
2. เปิด artifact ที่สำคัญที่สุด
3. ตรวจว่าอยู่ในไดเรกทอรีที่อนุญาต
4. ตรวจว่าควร commit เข้า repository หรือไม่
5. แล้วจึงตัดสินใจว่าจะยอมรับ แก้ หรือทำใหม่

## Artifact ที่ไม่น่าเชื่อถือ

สำหรับงานจาก repository หรือข้อมูลภายนอกที่ไม่น่าเชื่อถือ:

- อ่านสคริปต์ก่อนรัน
- ระวัง `curl | bash` และ payload ที่ทำให้อ่านยาก
- preview ใน sandbox หรือ container

อย่าตรวจเพียงว่า “สร้างแล้ว” อย่างน้อยต้องเปิด ดู ตรวจสอบ และรู้ว่าควร commit หรือไม่

## ข้อผิดพลาดที่พบบ่อย

- ดูเพียง bullet summary ของ Agent โดยไม่เปิดไฟล์
- commit debug output ชั่วคราวเข้า main
- รายงาน HTML มี tracking pixel หรือสคริปต์ภายนอกที่ยังไม่ตรวจ

## Checklist การตรวจรับ

- [ ] พาธของทุกไฟล์ใหม่อยู่ในขอบเขตที่อนุญาต
- [ ] เปิดและอ่านเนื้อหาหลักโดยคร่าว
- [ ] รันการตรวจอัตโนมัติ เช่น lint, test หรือ link check แล้ว
- [ ] ไม่มี secret และไม่มีไดเรกทอรีที่สร้างเกินจำเป็น
