**เครื่องมือเบราว์เซอร์** ช่วยให้ Agent เข้าถึงเว็บจริงในสภาพแวดล้อมควบคุมได้ เช่น อ่าน DOM จับภาพหน้าจอ และบางครั้งโต้ตอบอย่างง่าย เหมาะกับการตรวจรับ Frontend ตรวจลิงก์เอกสาร และเทียบแบบออกแบบ แต่ไม่ใช่สิ่งทดแทนการตรวจสอบความปลอดภัย และไม่ควรใช้ควบคุมระบบหลังบ้าน Production โดยไม่มีข้อจำกัด

เครื่องมือนี้ต่างจาก Search: Search ใช้ค้นข้อมูลบนเว็บ ส่วนเครื่องมือเบราว์เซอร์ใช้เปิดหน้าเว็บจริง

## เหมาะกับปัญหาแบบใด

มักใช้ตอบคำถามต่อไปนี้:

- ตอนนี้หน้าตาเพจจริงเป็นอย่างไร
- กดปุ่มนี้แล้วเกิดอะไรขึ้น
- Layout เสียเมื่อแสดงที่ความกว้างจริงหรือไม่

การอ่านโค้ดหรือคำอธิบายอย่างเดียวมักไม่พอสำหรับคำถามเหล่านี้ ต้องเปิดหน้าเว็บจริง

## เนื้อหาในหน้านี้

- เครื่องมือเบราว์เซอร์ทำอะไรได้และไม่ได้
- ความต่างจาก Web Search และ Computer Use
- วิธีให้สิทธิ์และกำหนดขอบเขตอย่างปลอดภัย

## ภาพรวมความสามารถ

| เหมาะ | ไม่เหมาะ |
|---|---|
| เปิดหน้า Local dev server เพื่อตรวจ Layout | Crawl เว็บไซต์ที่ ToS จำกัดแบบจำนวนมาก |
| ตรวจลิงก์เอกสารสาธารณะว่าเป็น 404 หรือไม่ | เข้าสู่ระบบที่ไม่ได้รับอนุญาตโดยอัตโนมัติ |
| เทียบหน้าคงที่กับ Implementation | แทน Framework ทดสอบ E2E แบบเต็ม |
| อ่านข้อความที่เห็นบนหน้าเพื่อช่วย Debug | จัดการเว็บไซต์ที่ต้องยืนยันมนุษย์ซับซ้อน |

พื้นฐานการเลือก: [การเลือกเครื่องมือ](/th/guide/tools/tool-selection/)

## เทียบกับเครื่องมืออื่น

| เครื่องมือ | อินพุต | เอาต์พุต |
|---|---|---|
| Web Search | คำค้น | สรุปและลิงก์ |
| เบราว์เซอร์ | URL / ที่อยู่ในเครื่อง | โครงสร้างหน้า ภาพหน้าจอ ผลการโต้ตอบ |
| Computer Use | GUI ทั้งหน้าจอ | ควบคุมแอปใดก็ได้ (หนักกว่าและอ่อนไหวกว่า) |

## ความเข้าใจผิดที่พบบ่อย

### 1. เครื่องมือเบราว์เซอร์ไม่ใช่สิ่งทดแทนการทดสอบอัตโนมัติ

ช่วยตรวจหน้า จับภาพ และกดโต้ตอบบางอย่างได้ แต่แทนระบบทดสอบแบบเต็มไม่ได้

### 2. เปิดหน้าได้ไม่ได้แปลว่าหน้าไม่มีปัญหา

เปิดได้เพียงยืนยันว่า “มีหน้าอยู่” ยังต้องตรวจ Layout ข้อความ การโต้ตอบ และลิงก์ต่อ

### 3. ควรใช้เมื่อใด

สถานการณ์ที่พบบ่อย:

- ตรวจปัญหา Layout ของหน้าในเครื่อง
- ตรวจว่าลิงก์เป็น 404 หรือไม่
- เทียบทิศทางหลักของหน้ากับแบบออกแบบ
- ยืนยันว่า “โค้ดดูถูกแล้ว แต่หน้าเว็บจริงถูกด้วยหรือไม่”

## เกณฑ์ตัดสิน

หากคำถามคือ:

- “Render จริงแล้วเป็นอย่างไร”
- “บนหน้าเห็นอะไรจริง”
- “หลังโต้ตอบแล้วหน้าแสดงผลตอบกลับอย่างไร”

เครื่องมือเบราว์เซอร์มักเหมาะกว่าการวิเคราะห์ข้อความล้วน

## เวิร์กโฟลว์ที่แนะนำ

1. **Frontend ในเครื่อง**: รัน `npm run dev` ก่อน แล้วให้ `http://localhost:PORT/path`
2. **ระบุงานชัด**: “ตรวจว่าแบบฟอร์มเข้าสู่ระบบล้นที่ความกว้าง 375px หรือไม่” แทน “ดูหน้าเว็บให้หน่อย”
3. **กำหนดขอบเขต**: ห้ามเข้าถึงอินเทอร์เน็ต ห้ามส่งแบบฟอร์มไป Production
4. **ตรวจรับ**: เทียบกับ [ตรวจสอบ Artifact](/th/guide/quality/verify-artifacts/) และภาพหน้าจอ

## ข้อความที่ใช้ได้ทันที

```text
เข้าถึงเฉพาะ http://localhost:4321/guide/foundations/local-vs-cloud/ แล้วตรวจ Layout เหนือรอยพับและภาพหลัก
ห้ามเข้าถึงอินเทอร์เน็ตและห้ามส่งแบบฟอร์มใด ๆ
หากพบปัญหา ให้แสดงหลักฐานภาพหน้าจอและคำแนะนำการแก้ไข
```

## ขอบเขตความปลอดภัย

- ให้ถือโดยค่าเริ่มต้นว่าเบราว์เซอร์เข้าถึง **ทุกอย่างที่เครื่องหรือสภาพแวดล้อมของคุณเข้าถึงได้** รวมถึง Admin ภายใน
- ระบุในงานว่า `เข้าถึงเฉพาะ localhost` หรือใส่ Allowlist โดเมน
- อย่ารันงานจาก Repository ที่ไม่น่าเชื่อถือใน Profile เบราว์เซอร์ที่เข้าสู่ระบบบัญชีส่วนตัวอยู่
- นโยบายเบราว์เซอร์ใน Cloud ขึ้นอยู่กับ [สภาพแวดล้อม Cloud](/th/guide/web-and-cloud/cloud-environments/) และนโยบายเครือข่าย

แนวคิดการอนุมัติ: [สิทธิ์และการอนุมัติ](/th/guide/foundations/permissions-and-approvals/)

## ข้อผิดพลาดที่พบบ่อย

- ให้ URL Production โดยไม่จำกัดเป็นอ่านอย่างเดียว
- ถือว่าภาพหน้าจอเบราว์เซอร์คือ “การทดสอบผ่าน” โดยไม่รันการทดสอบอัตโนมัติ
- สับสนกับ Web Search: Search แทนการตรวจ Render จริงไม่ได้

## รายการตรวจรับ

- [ ] ระบุขอบเขตการเข้าถึงตายตัวในพรอมต์
- [ ] ปัญหาภาพสำคัญมีภาพหน้าจอหรือคำอธิบาย
- [ ] ผลสอดคล้องกับ Unit/E2E test หรือบันทึกความต่างที่ทราบแล้ว
