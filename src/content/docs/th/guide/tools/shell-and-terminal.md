เทอร์มินัลเป็นหนึ่งในวิธีที่ตรงที่สุดในการให้ Codex ลงมือทำ จึงมีประสิทธิภาพสูงและยิ่งต้องเข้าใจความเสี่ยง

## ทำไมจึงทั้งทรงพลังและอันตราย

เครื่องมือไฟล์จัดการข้อความเป็นหลัก ส่วนเทอร์มินัลควบคุมระบบปฏิบัติการและสภาพแวดล้อมทำงานโดยตรง

เมื่อใช้เทอร์มินัล การกระทำทั่วไปไม่ได้มีเพียงอ่าน แต่อาจเป็น:

- ติดตั้ง
- Build
- ทดสอบ
- ลบ
- Commit
- Push

ก่อนใช้ ให้รู้ก่อนว่าจะเปลี่ยนตรงไหน

หลักการ:

- อ่านคำสั่งให้เข้าใจก่อนอนุมัติ
- ห้าม `rm -rf`, Force Push, แก้การตั้งค่า ssh และการกระทำคล้ายกัน เว้นแต่เข้าใจทั้งหมดและจำเป็นจริง
- ใส่คำสั่งตรวจสอบไว้ในเกณฑ์ยอมรับ

ช่องทางผลิตภัณฑ์: [เทอร์มินัลในตัว](/th/guide/desktop-app/integrated-terminal/)

## ทำไมเทอร์มินัลมีความเสี่ยงสูงกว่า

เพราะไม่ได้เพียง “ให้คำแนะนำ” แต่ลงมือทำจริง เช่น:

- ติดตั้ง Dependency
- ลบไฟล์
- รันการทดสอบ
- เขียนการตั้งค่าทับ
- Push โค้ด

ถ้าไม่เข้าใจคำสั่ง ให้ถามก่อนแล้วค่อยตัดสินใจอนุญาต

## เมื่อใดควรใช้เทอร์มินัล

เหมาะกับ:

- รันการทดสอบ
- รัน Build
- ตรวจสถานะไฟล์
- รันสคริปต์ที่มีอยู่ในโปรเจกต์

ถ้าต้องการเพียง:

- ดูว่าหน้ามีลักษณะอย่างไร
- ค้นข้อมูลสาธารณะล่าสุด
- แก้ข้อความที่รู้อยู่แล้วหนึ่งหรือสองจุด

เทอร์มินัลอาจไม่ใช่ตัวเลือกแรก

## ความเข้าใจผิดที่พบบ่อย

### 1. ไม่รู้คำสั่งก็ไม่ได้แปลว่าใช้เทอร์มินัลไม่ได้เลย

ช่วงแรกไม่ต้องเขียนคำสั่งจำนวนมากเป็น แต่อย่างน้อยต้องอ่านออกว่า:

- คำสั่งนี้ต้องการทำอะไรโดยคร่าว
- จะเปลี่ยนไฟล์หรือระบบหรือไม่
- เกี่ยวข้องกับงานปัจจุบันจริงหรือไม่

### 2. คำสั่งทดสอบปลอดภัยเสมอหรือไม่

คิดเช่นนั้นไม่ได้ แม้คำสั่งทดสอบส่วนใหญ่มีความเสี่ยงต่ำ แต่ยังต้องดูว่า:

- เขียนไฟล์จำนวนมากหรือไม่
- เชื่อมต่อเครือข่ายหรือไม่
- เรียกสคริปต์ที่คุณไม่เข้าใจหรือไม่

### 3. ถ้าอ่านไม่เข้าใจควรทำอย่างไร

ถามต่อได้โดยตรง เช่น:

```text
คำสั่งนี้ทำอะไร จะเปลี่ยนแปลงอะไรบ้าง และถ้าไม่รันจะมีผลอย่างไร
```

## ข้อความที่นำไปใช้ได้ทันที

```text
ก่อนรันคำสั่ง ให้อธิบายวัตถุประสงค์ จะเขียนไฟล์หรือเชื่อมต่อเครือข่ายหรือไม่ และจะกู้คืนอย่างไรหากล้มเหลว
```

ยืนยันก่อนรันเสมอว่าคำสั่งจะเปลี่ยนตรงไหน
