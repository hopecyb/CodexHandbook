GitHub คือพื้นที่ทำงานร่วมกันด้านโค้ดที่พบบ่อยที่สุดสำหรับ Codex งาน Cloud การตรวจ PR, Actions และการ push จากเครื่อง ล้วนอยู่บน branch และสิทธิ์ชุดเดียวกัน

หน้านี้อธิบายหลัก ๆ ว่า Codex เชื่อมเข้ากับเวิร์กโฟลว์ “รีโพซิทอรีโค้ด branch, PR และ Review” อย่างไร

แม้คุณไม่ใช่นักพัฒนาอาวุโส ก็เริ่มจากดูว่าสิ่งเหล่านี้จัดการเรื่องใด:

- เก็บโค้ดไว้ที่ไหน
- เสนอการเปลี่ยนแปลงให้ผู้อื่นดูอย่างไร
- การตรวจทานและ merge เกิดขึ้นอย่างไร

## แผนผังความสามารถ

| ความสามารถ | ช่องทางทั่วไป | ตำแหน่งในคู่มือ |
|---|---|---|
| เชื่อมรีโพซิทอรีระยะไกล | การตั้งค่า Cloud | [เชื่อม GitHub](/th/guide/web-and-cloud/connect-github/) |
| แก้โค้ดบนคลาวด์และเปิด PR | งาน Cloud | [สร้าง Pull Request](/th/guide/web-and-cloud/create-pull-requests/) |
| ตรวจ diff ในเครื่อง | เดสก์ท็อป App / IDE | [diff และความคิดเห็น](/th/guide/desktop-app/diffs-comments-and-review/) |
| เรียก Codex ใน CI | GitHub Actions | แผนงาน `08-developer-platform/ci-cd/` |
| ตรวจทานและแสดงความคิดเห็นใน PR อัตโนมัติ | Actions + exec | [โหมดไม่โต้ตอบ](/th/guide/cli/non-interactive-mode/) |

## มาตรฐานทีมที่แนะนำ

```md
## GitHub × Codex (ใส่ใน AGENTS.md ได้)

- ป้องกัน branch เริ่มต้น main; Codex push เฉพาะ feature branch
- PR ต้องเชื่อม issue; คำอธิบายต้องมีรายละเอียดการทดสอบ
- ห้าม Codex merge PR เว้นแต่ release bot ได้รับอนุญาตอย่างชัดเจน
- ใช้ GitHub Secrets / environment secrets สำหรับคีย์ ห้ามใส่ใน prompt
```

## Cloud เทียบกับ Git ในเครื่อง

| | clone ในเครื่อง | Cloud |
|---|---|---|
| แหล่งโค้ด | เวิร์กสเปซบนเครื่องของคุณ | clone จากระยะไกล |
| commit ที่ยังไม่ push | มองเห็น | มองไม่เห็น ต้อง push ก่อน |
| สภาพแวดล้อม | เวอร์ชัน Node/ระบบของคุณ | environment image ที่กำหนดค่าไว้ |
| เหมาะกับ | การพัฒนาประจำวัน | งานระยะยาวแบบอะซิงโครนัสและ build มาตรฐาน |

## เวิร์กโฟลว์ Review

1. Codex หรือคนเปิด PR
2. คนอ่าน diff หรือใช้ Skill `$pr-review`
3. CI เรียกการทดสอบ
4. ใช้ความคิดเห็นขับเคลื่อนการแก้ไข โดยสร้างงาน Codex ใหม่ว่า “จัดการเฉพาะความคิดเห็น review”
5. คนเป็นผู้ merge

## ความเข้าใจผิดที่พบบ่อย

### 1. การผสานกับ GitHub ไม่ได้แปลว่า “ให้ Codex พัฒนาแทนฉันอัตโนมัติ”

การใช้งานที่พบบ่อยกว่าคือ:

- อ่านบริบทรีโพซิทอรี
- ช่วยจัดระเบียบ diff หรือ review
- ช่วยเปิด PR และแก้ตามความคิดเห็น

### 2. หากยังไม่เข้าใจคำว่า PR และ Review ควรทำอย่างไร

เริ่มจากเข้าใจคร่าว ๆ ว่า:

- **PR**: เสนอการเปลี่ยนแปลงอย่างเป็นทางการเพื่อให้ผู้อื่นตรวจ
- **Review**: ผู้อื่นเข้ามาตรวจการเปลี่ยนแปลงนั้น

เท่านี้ก็เพียงพอสำหรับเนื้อหาส่วนใหญ่ในหน้านี้

### 3. เมื่อเริ่มใช้การผสานกับ GitHub สิ่งสำคัญที่สุดคือต้องแยกเรื่องนี้ก่อน

สิ่งแรกที่ต้องแยกไม่ใช่ token หรือ Actions แต่คือ:

> **การเปลี่ยนแปลงในเครื่อง รีโพซิทอรีบนคลาวด์ และการตรวจ PR เป็นคนละเรื่องกัน**

หัวใจของการผสานกับ GitHub คือให้ Codex เข้าไปอยู่ในเวิร์กโฟลว์ทำงานร่วมกันด้านโค้ดที่มีอยู่

## ความปลอดภัย

- ลด scope ของ GitHub Token ให้เหลือน้อยที่สุด
- ระวังรูปแบบ Actions ที่ละเอียดอ่อน เช่น `pull_request_target` ซึ่งเป็นพื้นผิวสำหรับ injection
- การเรียกระบบอัตโนมัติบน PR จาก fork ต้องมีนโยบายแยกเพิ่มเติม

## ข้อผิดพลาดที่พบบ่อย

- งาน Cloud สมมติว่ามีการเปลี่ยนแปลงในเครื่องที่ยังไม่ได้ commit
- ให้ Codex ทำตามคำสั่งที่ยังไม่ sanitize ในคำอธิบาย PR ซึ่งเสี่ยง prompt injection
- รวมการฟอร์แมตกับการแก้ฟีเจอร์ไว้ใน PR เดียว
