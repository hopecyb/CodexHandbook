บันทึกข้อผิดพลาดไว้ก่อน จากนั้นระบุว่าความล้มเหลวเกิดที่ชั้นใด แล้วจึงเปลี่ยนเพียงตัวแปรเดียวและรันซ้ำ หน้านี้ใช้ชุดอินพุตตายตัวห้าชุดเพื่อสาธิตกระบวนการดังกล่าว ผู้เขียนจงใจสร้างความผิดพลาดขึ้น และ log มาจากการรันผ่านบรรทัดคำสั่งจริง ไม่ได้อ้างว่าเป็นเหตุขัดข้องของลูกค้าจริง

[ดาวน์โหลดชุดฝึกกู้คืนฉบับสมบูรณ์](/downloads/failure-recovery/failure-recovery-1.0.0.zip) · [README](/downloads/failure-recovery/README.md)

## จำลองปัญหาหนึ่งครั้งก่อน

ต้องใช้ไลบรารีมาตรฐานของ Python 3.10+ โดยไม่ต้องมีบัญชีหรือเครือข่าย รันคำสั่งต่อไปนี้ในไดเรกทอรีหลังแตกไฟล์:

```sh
python3 scripts/reproduce.py --output my-recovery-logs
```

ไดเรกทอรีเอาต์พุตต้องยังไม่มีอยู่ เพื่อป้องกันการเขียนทับหลักฐานเดิม สคริปต์ทำงานในสำเนาชั่วคราว ก่อนแก้ไข ความล้มเหลวทั้งห้าชุดควรมี exit code ที่ไม่ใช่ศูนย์ และหลังแก้ไขทั้งหมดควรเป็น 0 โดยอินพุตต้นฉบับไม่เปลี่ยน log ของแต่ละชุดประกอบด้วยคำสั่ง exit code, standard output และข้อผิดพลาด ส่วนพาธชั่วคราวจะถูกทำให้เป็นรูปแบบเดียวกันคือ `<WORK>`

## 1. hash ของแหล่งที่มาไม่ตรงกัน

**อาการ:** `FAIL: Source changed: P` และออกด้วยรหัส 1

**การวินิจฉัย:** ไฟล์แหล่งที่มาที่ตรึงไว้มีข้อความซึ่งเขียนเพิ่มโดยผิดพลาด แต่ดัชนีแหล่งที่มาไม่เปลี่ยน ต้องตรวจเทียบกับข้อมูลต้นฉบับก่อน และห้ามอัปเดต hash โดยตรงเพียงเพื่อให้การตรวจสอบผ่าน

**การแก้ไขเพียงอย่างเดียว:** คืนค่าไบต์ต้นฉบับที่ทราบแน่ชัดของไฟล์แหล่งที่มานี้ โดยไม่เปลี่ยนข้อมูล บทความ หรือดัชนีรายการอื่น รันซ้ำแล้วออกด้วยรหัส 0

[log เมื่อยังล้มเหลว](/downloads/failure-recovery/validation/01-source-changed-before.json) · [log หลังการกู้คืน](/downloads/failure-recovery/validation/01-source-changed-after.json)

หากข้อมูลจริงมีการอัปเดต ต้องตรวจสอบเวอร์ชัน เนื้อหา และข้อสรุปใหม่ พร้อมเก็บบันทึกแหล่งที่มาชุดใหม่ การคืนไฟล์เก่าในตัวอย่างนี้ใช้ได้เฉพาะเมื่อยืนยันแล้วว่าเป็นการแก้ไขผิดเท่านั้น

## 2. การอ้างอิงในเนื้อหาไม่มีอยู่ในตารางข้อเท็จจริง

**อาการ:** `FAIL: Unmapped or unused claim ID` และออกด้วยรหัส 1

**การวินิจฉัย:** ในเนื้อหาเขียน F1 ผิดเป็น F99 แต่ตารางข้อเท็จจริงไม่มี F99 เมื่อตรวจย้อนกลับไปยัง P1 แล้ว ยืนยันว่าประโยคนี้ยังคงตรงกับ F1

**การแก้ไขเพียงอย่างเดียว:** เปลี่ยนเฉพาะหมายเลขที่เขียนผิดกลับเป็น F1 แล้วรันซ้ำจนออกด้วยรหัส 0 อย่าสร้างระเบียนใหม่ในตารางข้อเท็จจริงเพื่อกลบการอ้างอิงที่ไม่รู้ที่มา

[log เมื่อยังล้มเหลว](/downloads/failure-recovery/validation/02-unmapped-citation-before.json) · [log หลังการกู้คืน](/downloads/failure-recovery/validation/02-unmapped-citation-after.json)

หมายเลขที่ถูกต้องไม่ได้พิสูจน์ว่าข้อความมีแหล่งที่มารองรับ ยังต้องตรวจทีละประโยค ดูรายละเอียดที่ [Skill สำหรับการเขียน](/th/skills/examples/writing-skill/)

## 3. ข้อเสนอการคัดแยกไม่ตรงกับอินพุต

**อาการ:** `FAIL: Stale input hash` และออกด้วยรหัส 1

**การวินิจฉัย:** hash ของอินพุตในข้อเสนอไม่ตรงกับ Issue ตายตัวปัจจุบัน แบบฝึกนี้ทำให้ hash ในข้อเสนอเสียโดยตั้งใจ เพื่อเรียกการตรวจสอบการผูกอินพุต

**การแก้ไขเพียงอย่างเดียว:** แทนที่ด้วยข้อเสนออ้างอิงฉบับสมบูรณ์ที่ตรวจเทียบกับอินพุตปัจจุบันแล้ว โดยไม่เปลี่ยนอินพุตและ schema จากนั้นรันซ้ำจนออกด้วยรหัส 0 ไม่มีการรันโมเดลเพื่อคัดแยกใหม่ และไม่ได้เพียงคำนวณ hash ใหม่เพื่อใช้ข้อสรุปเก่า

[log เมื่อยังล้มเหลว](/downloads/failure-recovery/validation/03-stale-proposal-before.json) · [log หลังการกู้คืน](/downloads/failure-recovery/validation/03-stale-proposal-after.json)

เมื่อเนื้อหาของ Issue จริงเปลี่ยนแปลง ต้องวิเคราะห์ใหม่ว่าความเปลี่ยนแปลงนั้นส่งผลต่อข้อสรุปอย่างไร ดู [กรณีศึกษาการคัดแยก Issue](/th/cases/use-cases/team-automation/issue-triage-suggestions/)

## 4. ใช้ไฟล์สถานะเดียวกันกับอีกไดเรกทอรีหนึ่ง

**อาการ:** `State version/site mismatch` และออกด้วยรหัส 3

**การวินิจฉัย:** สถานะผูกอยู่กับไซต์ fixed แต่คำสั่งชี้ `--site` ไปยัง broken ข้อผิดพลาดเกิดขึ้นในการตรวจขอบเขต ไม่ใช่เพราะลิงก์หยุดทำงานกะทันหัน

**การแก้ไขเพียงอย่างเดียว:** เปลี่ยนเฉพาะ `--site` ให้กลับไปยังไดเรกทอรีเดิม โดยคงไฟล์สถานะและพารามิเตอร์อื่นไว้ รันซ้ำแล้วออกด้วยรหัส 0 และการเรียกที่ผิดพลาดไม่ได้เขียนทับสถานะเดิม

[log เมื่อยังล้มเหลว](/downloads/failure-recovery/validation/04-wrong-site-scope-before.json) · [log หลังการกู้คืน](/downloads/failure-recovery/validation/04-wrong-site-scope-after.json)

หากต้องการติดตามอีกไซต์หนึ่งจริง ให้สร้างสถานะแยกสำหรับไซต์นั้น อย่าลบสถานะเก่าเพื่อหลีกเลี่ยงการป้องกันขอบเขต

## 5. JSON สถานะเสียหาย

**อาการ:** แยกวิเคราะห์ JSON ไม่สำเร็จ ตัวรันรายงาน stopped และออกด้วยรหัส 3

**การวินิจฉัย:** ไฟล์สถานะถูกตัดจนไม่สมบูรณ์ จึงไม่สามารถอ่านประวัติและ baseline สำหรับการขจัดรายการซ้ำได้อย่างปลอดภัย เมื่อโปรแกรมปฏิเสธการทำงาน โปรแกรมจะเก็บเนื้อหาที่เสียหายไว้และไม่แอบรีเซ็ตให้ว่าง

**การแก้ไขเพียงอย่างเดียว:** กู้คืนข้อมูลสำรองที่ทราบว่าใช้ได้และบันทึกไว้ก่อนเริ่มแบบฝึกครั้งนี้ โดยไม่เปลี่ยนคำสั่งและไซต์ รันซ้ำแล้วออกด้วยรหัส 0

[log เมื่อยังล้มเหลว](/downloads/failure-recovery/validation/05-corrupt-state-before.json) · [log หลังการกู้คืน](/downloads/failure-recovery/validation/05-corrupt-state-after.json)

หากไม่มีข้อมูลสำรอง ให้เก็บไฟล์ที่เสียหายไว้ก่อน ตรวจบันทึกการรัน แล้วจึงสร้างใหม่ด้วยตนเอง การลบสถานะโดยตรงอาจทำให้เหตุการณ์ที่รอส่งสูญหายและสร้างรายการซ้ำ ดูรายละเอียดที่ [Skill สำหรับระบบอัตโนมัติ](/th/skills/examples/automation-skill/)

## นำไปใช้กับงานของคุณ

บันทึกเวอร์ชันอินพุต คำสั่งที่รันจริง และข้อความผิดพลาดทั้งหมด ระบุว่าเป็นปัญหาด้านอินพุต โครงสร้าง ขอบเขต หรือสถานะ เขียนสาเหตุหนึ่งข้อที่ต้องตรวจสอบ เปลี่ยนเฉพาะตัวแปรที่เกี่ยวข้อง รันซ้ำด้วยการตรวจสอบเดิม และเก็บผลลัพธ์ไว้ หลังจากกู้คืนแล้ว ยังต้องตรวจว่าเป้าหมายเดิมสำเร็จหรือไม่ ไม่ใช่ดูเพียง exit code

แบบฝึกเหล่านี้ไม่ครอบคลุมความล้มเหลวในการเข้าสู่ระบบจริง กรณีที่ Skill ของไคลเอนต์ไม่ทำงาน ข้อจำกัดเครือข่าย หรือปัญหาการอนุมัติ หากพบปัญหาเหล่านี้ ให้กลับไปที่ [ดัชนีแก้ปัญหาตามอาการ](/th/guide/reference/troubleshooting/) เก็บข้อมูลของสภาพแวดล้อมจริงไว้ และอย่านำอาการจากสคริปต์ในหน้านี้ไปอ้างเป็นการรับประกันพฤติกรรมของไคลเอนต์
