“ตัวแปรสภาพแวดล้อม” มักทำให้ผู้ใช้เข้าใจไปสุดทางสองด้าน คือมองว่าเป็นเรื่องระดับล่างเกินไป หรือคิดว่าสามารถใส่การกำหนดค่าทุกอย่างไว้ในนั้นได้ พูดให้ตรงที่สุด ตัวแปรสภาพแวดล้อมคือวิธีส่งค่าให้โปรแกรมขณะรัน ซึ่งเหมาะอย่างยิ่งกับข้อมูลละเอียดอ่อนและสวิตช์ต่าง ๆ

ตัวแปรสภาพแวดล้อมมักใช้เพื่อ **ฉีดคีย์ เขียนทับสวิตช์ และปรับให้เข้ากับ CI** โดยไม่เขียนค่าที่ละเอียดอ่อนลงในไฟล์กำหนดค่าหรือ Git หน้านี้เป็นดัชนีเชิงแนวคิด ส่วนชื่อตัวแปรที่เจาะจงให้ยึด [เอกสารอย่างเป็นทางการ](https://developers.openai.com/codex) และ `codex --help` เป็นหลัก

## เนื้อหาในหน้านี้

- สิ่งใดควรใช้ตัวแปรสภาพแวดล้อมแทนไฟล์ config
- ระดับผู้ใช้ ระดับโปรเจกต์ Cloud Secrets และ CI แบ่งหน้าที่กันอย่างไร
- รูปแบบการตั้งชื่อและความเสี่ยงในการรั่วไหลที่พบบ่อย

## วิธีตัดสินใจ

หากค่าหนึ่งตรงกับเงื่อนไขข้อใดข้อหนึ่งต่อไปนี้ ให้พิจารณาใช้ตัวแปรสภาพแวดล้อมก่อน:

- ไม่ต้องการเขียนลงใน Git
- ค่าเปลี่ยนไปตามเครื่อง ผู้ใช้ หรือสภาพแวดล้อม
- ต้องการให้มีผลเฉพาะการรันครั้งนี้

นี่คือเหตุผลที่ token สวิตช์ชั่วคราว และค่าที่ฉีดผ่าน CI มักใช้ตัวแปรสภาพแวดล้อมแทนการเขียนค่าตายตัวโดยตรง

แนวคิดเกี่ยวกับคีย์การกำหนดค่าดูได้ที่ [ข้อมูลอ้างอิงการกำหนดค่า](/th/guide/reference/configuration-reference/) ส่วน Cloud ดู [Secrets และตัวแปร](/th/guide/web-and-cloud/secrets-and-variables/)

## เนื้อหาที่เหมาะกับตัวแปรสภาพแวดล้อม

| ประเภท | ตัวอย่างวัตถุประสงค์ | สิ่งที่ไม่ควรทำ |
|---|---|---|
| token สำหรับการยืนยันตัวตน | API key, GitHub PAT | commit ลงในรีโพซิทอรี |
| สวิตช์ชั่วคราว | ระดับล็อกสำหรับการดีบัก | ใช้เป็นการกำหนดค่าธุรกิจระยะยาว |
| การฉีดค่าผ่าน CI | โหมด Review แบบอ่านอย่างเดียว | token ที่มีสิทธิ์เขียนในระบบจริง |
| โปรเซสย่อย MCP | key ของบริการภายนอก | เขียนเป็นข้อความธรรมดาใน `AGENTS.md` |

## อย่าใช้ตัวแปรสภาพแวดล้อมเป็นลิ้นชักสารพัดอย่าง

หลายทีมใช้งานไปสักระยะแล้วเริ่มออกนอกทางว่า “ในเมื่อใส่ได้ ก็ใส่ไว้ในตัวแปรสภาพแวดล้อมทั้งหมด”

แนวทางที่มั่นคงกว่าคือแยกให้ชัดเจน:

- **ค่าที่ละเอียดอ่อนและความแตกต่างขณะรัน**: ตัวแปรสภาพแวดล้อม
- **ข้อตกลงระยะยาวของทีม**: ไฟล์กำหนดค่าหรือเอกสาร
- **กฎของเวิร์กโฟลว์**: `AGENTS.md` หรือ Skill

เมื่อต้องแก้ปัญหาในภายหลัง คุณจะรู้ได้ง่ายขึ้นว่าควรค้นหาจากที่ใด

## `.env` คืออะไรกันแน่

เมื่อเริ่มใช้ตัวแปรสภาพแวดล้อม ผู้ใช้จำนวนมากมักพบไฟล์ `.env` เป็นอย่างแรก และจุดนี้ก็เกิดความเข้าใจผิดได้ง่ายที่สุดเช่นกัน

`.env` ไม่ใช่ศูนย์กลางการกำหนดค่าอีกประเภทหนึ่ง แต่เป็นเพียงวิธี **โหลดตัวแปรสภาพแวดล้อมหลายค่าพร้อมกัน** ที่เครื่องมือจำนวนมากจัดเตรียมไว้เพื่อความสะดวกในการพัฒนาภายในเครื่อง

ทำความเข้าใจได้ดังนี้:

- ตัวแปรสภาพแวดล้อมคือ “ค่าจริง”
- `.env` คือ “ที่เก็บค่าดังกล่าวรูปแบบหนึ่งที่นิยมใช้ภายในเครื่อง”

ดังนั้น:

- `.env` สะดวก แต่ไม่ได้หมายความว่าปลอดภัย
- `.env.example` มีไว้ใส่ชื่อตัวอย่าง ไม่ควรใส่คีย์จริง
- เมื่อนำขึ้นใช้งานจริงหรือเข้า CI โดยทั่วไปยังควรใช้ตัวจัดการ Secret

## เนื้อหาที่ไม่ควรพึ่งตัวแปรสภาพแวดล้อมเพียงอย่างเดียว

- มาตรฐานการเขียนโค้ดและโครงสร้างไดเรกทอรี → `AGENTS.md`
- โมเดลเริ่มต้นที่ทีมตกลงใช้ร่วมกัน → การกำหนดค่าโปรเจกต์ (ส่วนที่ไม่ใช่คีย์)
- รายการที่อนุญาตซึ่งซับซ้อน → [กฎ](/th/guide/customization/rules/allow-and-deny-patterns/)

## ความเข้าใจผิดที่พบบ่อย

### 1. ตัวแปรสภาพแวดล้อมไม่เหมาะสำหรับเก็บการกำหนดค่าทั้งหมด

ตัวแปรสภาพแวดล้อมเหมาะมากสำหรับเก็บ “ค่า” แต่ไม่เหมาะกับการรองรับกฎทั้งชุดของทีมและคำอธิบายระยะยาว

### 2. เขียนลงใน `.env` แล้วปลอดภัยใช่ไหม

หาก `.env` ถูก commit ถูกมองเห็นระหว่างแชร์หน้าจอ หรือถูกพิมพ์ลงในล็อก ข้อมูลก็ยังรั่วไหลได้

### 3. หลังจาก `unset` แล้วจะไม่มีความเสี่ยงอย่างแน่นอนใช่ไหม

ความเสี่ยงอาจยังคงอยู่ใน:

- ประวัติ shell
- การสืบทอดค่าไปยังโปรเซสย่อย
- ล็อก
- ไฟล์หรือภาพหน้าจอที่บันทึกไว้ก่อนหน้านี้

### 4. เมื่อใช้ `.env` ภายในเครื่องได้ ระบบจริงก็ส่งไฟล์ `.env` แบบเดียวกันได้ใช่ไหม

หลายกรณีไม่ได้เป็นเช่นนั้น ใน CI, Cloud และแพลตฟอร์มที่มีการจัดการ แนวทางที่พบบ่อยกว่าคือ:

- กำหนด Secret ในส่วนจัดการของแพลตฟอร์ม
- ฉีดตัวแปรสภาพแวดล้อมขณะรัน
- ไม่เก็บค่าจริงลงในไฟล์ของรีโพซิทอรี

## ลำดับชั้นและลำดับความสำคัญ (เชิงแนวคิด)

```text
นโยบายบังคับขององค์กร (หากมี)
    ↓ เขียนทับ
ตัวแปรสภาพแวดล้อมที่ฉีดผ่าน Shell / CI
    ↓ ผสานกับไฟล์กำหนดค่า (ให้ยึดกฎที่ระบุไว้อย่างเป็นทางการ)
ไฟล์ config ระดับผู้ใช้ / ระดับโปรเจกต์
```

เมื่อกำหนดคีย์เดียวกันไว้หลายตำแหน่ง ให้ยึด **ลำดับความสำคัญที่เอกสารอย่างเป็นทางการระบุ** เมื่อต้องแก้ปัญหา ให้แสดง “การกำหนดค่าที่มีผลจริง” หรือตรวจสอบล็อก

## ลำดับการตัดสินใจที่ใช้บ่อย

เมื่อเริ่มกำหนดค่า ให้พิจารณาตามลำดับนี้:

1. ค่านี้เป็นข้อมูลละเอียดอ่อนหรือไม่
2. ใช้ภายในเครื่องส่วนบุคคล หรือใช้กับ CI / Cloud
3. ต้องเก็บไว้ระยะยาว หรือมีอยู่เฉพาะระหว่างการรันครั้งนี้
4. ควรใส่ไว้ในตัวแปรสภาพแวดล้อมภายในเครื่อง CI Secret หรือ Cloud Secret

ลำดับนี้ช่วยหลีกเลี่ยงปัญหา “ค่าเหมาะสม แต่ใส่ผิดตำแหน่ง”

## สถานการณ์ที่พบบ่อย

| สถานการณ์ | แนวทางที่มั่นคงกว่า |
|---|---|
| ดีบัก API ภายนอกบนเครื่องของตนเอง | ตัวแปรสภาพแวดล้อมภายในเครื่องหรือ `.env` และละเว้นไม่ให้ commit |
| แชร์ตัวอย่างการกำหนดค่ากับทีม | commit `.env.example` แต่ไม่ commit ค่าจริง |
| GitHub Actions / CI | Secret ของแพลตฟอร์ม |
| งาน Cloud เรียกใช้บริการส่วนตัว | Cloud Secret |
| เซิร์ฟเวอร์ MCP ต้องอ่าน key | ตัวแปรสภาพแวดล้อมของโปรเซสแม่หรือการฉีด Secret |

หากยังแยกไม่ออก ให้ใช้หลักการนี้: พยายามอย่าเก็บคีย์จริงไว้เป็นข้อความธรรมดาในไฟล์ของรีโพซิทอรีเป็นเวลานาน

## กรณีใช้งานทั่วไป

### การพัฒนาภายในเครื่อง

ส่งออก token ส่วนบุคคลใน `~/.zshrc` หรือ `.envrc` ของ direnv และ **อย่า commit** `.env`

### CLI แบบไม่โต้ตอบ

CI ฉีดตัวแปรผ่าน secret store แล้วจึงรัน `codex exec` ดู [โหมดไม่โต้ตอบ](/th/guide/cli/non-interactive-mode/)

### เซิร์ฟเวอร์ MCP

โปรเซส MCP มักสืบทอดสภาพแวดล้อมจากโปรเซสแม่ ให้อ้างอิง `$VAR` ในการกำหนดค่าแทนการเขียนค่าตายตัว ดู [เชื่อมต่อ MCP](/th/skills/mcp/connect-an-mcp-server/)

### Cloud

กำหนด Secrets ระดับรีโพซิทอรีในคอนโซล Cloud โดยให้ชื่อตรงกับการอ้างอิงภายในงาน

ตัวแปรสภาพแวดล้อมเหมาะสำหรับค่าที่เปลี่ยนแปลง เป็นข้อมูลละเอียดอ่อน หรือจำเป็นเฉพาะขณะรัน ไม่ควรใช้รองรับกฎหรือคำอธิบายระยะยาว

## รายการตรวจความปลอดภัย

- [ ] `.env` อยู่ใน `.gitignore`
- [ ] ปกปิด token ก่อนพิมพ์ลงในล็อก
- [ ] หมุนเวียน key ที่เคยรั่วไหล
- [ ] ใช้ scope ที่มีสิทธิ์น้อยที่สุด (เช่น token สำหรับ CI แบบอ่านอย่างเดียว)

## ข้อผิดพลาดที่พบบ่อย

- ใส่ key จริงใน `.env.example` แล้ว commit
- ใช้ `export` ที่แสดง token ให้เห็นระหว่างแชร์หน้าจอ
- สมมติว่าโปรเซสย่อยปลอดภัยหลัง `unset` — ต้องตรวจสอบแผนผังโปรเซส
