หน้าอย่าง “ข้อมูลอ้างอิงการกำหนดค่า” อาจทำให้สับสนได้ตั้งแต่แรก เพราะเต็มไปด้วยคีย์ ลำดับชั้น และความสัมพันธ์ของการเขียนทับ แต่หากตอบคำถามต่อไปนี้ให้ชัดก่อน เนื้อหาจะเข้าใจง่ายขึ้นมาก:

> **พฤติกรรมใดควรปรับผ่านการกำหนดค่า และพฤติกรรมใดไม่ควรแก้ด้วยการกำหนดค่า?**

ไฟล์กำหนดค่ามักใช้เพื่อทำให้พฤติกรรมด้าน **โมเดล แซนด์บ็อกซ์ การอนุมัติ และ MCP** เป็นไปในแนวทางเดียวกัน หน้านี้เป็น **ดัชนีเชิงแนวคิด** ส่วนพาธไฟล์และชื่อคีย์ TOML/YAML ที่เจาะจงต้องยึด [เอกสาร OpenAI Codex](https://developers.openai.com/codex) และเวอร์ชันที่คุณติดตั้งเป็นหลัก

## หลักการตัดสินใจหนึ่งข้อ

โดยทั่วไป ควรใส่สิ่งที่ “**ต้องการให้ส่งผลต่อพฤติกรรมในระยะยาว**” ไว้ในการกำหนดค่า และไม่ควรใช้การกำหนดค่าเก็บเนื้อหาต่อไปนี้:

- ค่าที่ละเอียดอ่อน
- กฎของทีมฉบับเต็ม
- คำอธิบายงานชั่วคราวที่ใช้เพียงครั้งเดียว

แบ่งออกเป็นสามประเภทแล้วจะเห็นภาพได้ชัดขึ้น:

- **ค่ากำหนดพฤติกรรมระยะยาว** โดยทั่วไปใส่ไว้ในการกำหนดค่า
- **ข้อกำหนดของงานเฉพาะ** โดยทั่วไปใส่ไว้ในพรอมต์ / `AGENTS.md` / Skill
- **ค่าที่ละเอียดอ่อน** โดยทั่วไปใส่ไว้ในตัวแปรสภาพแวดล้อมหรือ Secret

หากยังแยกไม่ออก ให้ถามตัวเองเพียงเรื่องเดียว: คุณกำลังเปลี่ยนนิสัยระยะยาวของ Codex หรือกำลังอธิบายงานครั้งนี้?

- นิสัยระยะยาวโดยทั่วไปใส่ไว้ในการกำหนดค่า
- คำอธิบายงานปัจจุบันโดยทั่วไปใส่ไว้ในพรอมต์ `AGENTS.md` หรือคำอธิบายงาน

## ลำดับชั้นของการกำหนดค่า

| ระดับ | ตำแหน่ง (เชิงแนวคิด) | เนื้อหาทั่วไป |
|---|---|---|
| ระดับผู้ใช้ | `~/.codex/` เป็นต้น | โมเดลเริ่มต้น ลักษณะการอนุมัติส่วนบุคคล |
| ระดับโปรเจกต์ | ไฟล์กำหนดค่าภายในรีโพซิทอรี | แซนด์บ็อกซ์ของทีม รายการ MCP |
| ตัวแปรสภาพแวดล้อม | ฉีดค่าผ่าน Shell / CI | คีย์ สวิตช์ชั่วคราว |
| แบบมีการจัดการ | องค์กรเป็นผู้กำหนด | นโยบายบังคับที่เขียนทับไม่ได้ |

## แต่ละระดับควบคุมอะไร

- **ระดับผู้ใช้**: ค่าเริ่มต้นที่คุณเลือกใช้เป็นการส่วนตัว
- **ระดับโปรเจกต์**: พฤติกรรมเริ่มต้นที่รีโพซิทอรีนี้ต้องการให้ทุกคนใช้ร่วมกัน
- **ตัวแปรสภาพแวดล้อม**: ค่าที่ใส่เข้ามาชั่วคราวขณะรัน
- **นโยบายแบบมีการจัดการ**: ส่วนที่องค์กรกำหนดตายตัวและคุณแก้ไขจากเครื่องของตนเองไม่ได้

เมื่อเริ่มศึกษา คุณยังไม่จำเป็นต้องท่องว่า “ระดับใดต้องเขียนทับระดับใด” เพียงรู้คร่าว ๆ ว่าแต่ละระดับควบคุมอะไรก็เพียงพอแล้ว:

- ระดับผู้ใช้: “โดยปกติฉันชอบใช้งานแบบนี้เป็นการส่วนตัว”
- ระดับโปรเจกต์: “รีโพซิทอรีนี้ต้องการให้ทุกคนพยายามใช้งานแบบนี้”
- ตัวแปรสภาพแวดล้อม: “ค่าที่ใส่เข้ามาชั่วคราวสำหรับการรันครั้งนี้”
- นโยบายแบบมีการจัดการ: “ขอบเขตที่องค์กรกำหนดไว้ให้แล้ว”

เริ่มต้น: [พื้นฐานการกำหนดค่า](/th/guide/customization/configuration/config-basics/) · เน้นการใช้งานผ่านเทอร์มินัล: [การกำหนดค่า CLI](/th/guide/cli/configuration/)

## ดัชนีขอบเขตการกำหนดค่า (เชิงแนวคิด)

## ความเข้าใจผิดที่พบบ่อย

### 1. ไม่ใช่ทุกสิ่งที่กำหนดค่าได้จะควรใส่ในไฟล์กำหนดค่า

เนื้อหาบางประเภทเหมาะกับตำแหน่งต่อไปนี้มากกว่า:

- `AGENTS.md`
- ตัวแปรสภาพแวดล้อม
- Skill
- คำอธิบายงานปัจจุบัน

การกำหนดค่าไม่ใช่ที่เก็บสารพัดอย่าง

### 2. ไม่จำเป็นต้องเข้าใจคีย์การกำหนดค่าทุกคีย์ตั้งแต่แรก

ผู้ใช้ส่วนใหญ่เพียงต้องเริ่มจากการทำความเข้าใจเรื่องต่อไปนี้:

- โมเดล
- แซนด์บ็อกซ์
- การอนุมัติ
- MCP

สี่ประเภทนี้ครอบคลุมคำถามที่เกิดขึ้นจริงได้เกือบทั้งหมดแล้ว

### 3. เมื่อตั้งค่าระดับโปรเจกต์แล้ว สามารถใช้แทนเอกสารของทีมได้ทั้งหมดหรือไม่

การกำหนดค่าเหมาะกับการแสดง “ค่าเริ่มต้นของพฤติกรรมระบบ” แต่ไม่เหมาะจะใช้แทนคำอธิบายประเภท “เหตุใดจึงทำเช่นนี้ และเมื่อใดที่ไม่ควรทำ”

### 4. แม้เอกสารอย่างเป็นทางการจะมีคีย์การกำหนดค่าจำนวนมาก ก็ไม่จำเป็นต้องเรียนรู้ทั้งหมดในครั้งเดียว

สิ่งที่ผู้ใช้ส่วนใหญ่มักพบก่อนมีอยู่สี่ประเภทหลัก:

- โมเดลเริ่มต้น
- ขอบเขตแซนด์บ็อกซ์
- นโยบายการอนุมัติ
- การเชื่อมต่อ MCP

เมื่อเข้าใจสี่ประเภทนี้แล้ว ก็ครอบคลุมคำถามส่วนใหญ่ในช่วงเริ่มต้นได้

## ความสัมพันธ์กับตัวแปรสภาพแวดล้อม

| ประเภท | ควรใส่ไว้ที่ใด |
|---|---|
| API key, token | ตัวแปรสภาพแวดล้อมหรือตัวจัดการ Secret |
| สวิตช์ที่ไม่ละเอียดอ่อน | ตัวแปรสภาพแวดล้อมหรือการกำหนดค่า |
| มาตรฐานการเขียนโค้ด | `AGENTS.md` ไม่ใช่ config |

## วิธีตัดสินใจว่าควรใส่ในการกำหนดค่าหรือไม่

เมื่อสงสัยว่า “สิ่งนี้ควรเขียนไว้ในการกำหนดค่าหรือไม่” ให้ใช้คำถาม 4 ข้อต่อไปนี้ช่วยตัดสินใจก่อน:

1. ต้องการให้สิ่งนี้มีผลเป็นค่าเริ่มต้นในระยะยาวหรือไม่
2. สิ่งนี้เป็นข้อมูลละเอียดอ่อนหรือไม่
3. สิ่งนี้เป็นความเคยชินส่วนบุคคลของฉัน หรือเป็นกฎที่โปรเจกต์ใช้ร่วมกัน
4. สิ่งนี้ปรับพฤติกรรมของระบบ หรือเพียงอธิบายงานครั้งนี้

เมื่อพิจารณาตาม 4 ข้อนี้ โดยทั่วไปก็จะวางสิ่งต่าง ๆ ไว้ถูกตำแหน่งได้ง่ายขึ้น

## วิธีตัดสินใจเมื่อต้องปรับพฤติกรรม

เมื่อมีความต้องการที่จะ “ปรับพฤติกรรมของ Codex” ให้พิจารณาประเด็นต่อไปนี้:

1. นี่คือพฤติกรรมเริ่มต้นระยะยาว หรือข้อกำหนดชั่วคราวของงานครั้งนี้
2. นี่คือค่าที่ละเอียดอ่อน หรือการกำหนดค่าทั่วไป
3. นี่คือค่ากำหนดส่วนบุคคล หรือกฎที่โปรเจกต์ใช้ร่วมกัน

จากนั้นจะตัดสินได้ว่าสิ่งนี้ควรอยู่ใน:

- ไฟล์กำหนดค่า
- ตัวแปรสภาพแวดล้อม
- `AGENTS.md`
- Skill
- พรอมต์ปัจจุบัน

## สถานการณ์ที่พบบ่อย

ผู้เริ่มต้นมักตัดสินใจได้ยากที่สุดในสถานการณ์ต่อไปนี้:

| สิ่งที่ต้องการทำ | โดยทั่วไปควรใส่ไว้ที่ใด |
|---|---|
| ต้องการกำหนดโมเดลหนึ่งเป็นค่าเริ่มต้นในระยะยาว | การกำหนดค่าระดับผู้ใช้หรือระดับโปรเจกต์ |
| ทีมกำหนดให้รันการทดสอบก่อนแก้ไขโค้ด | `AGENTS.md` |
| งานครั้งนี้อนุญาตให้แก้ไขเฉพาะ `docs/` | พรอมต์ปัจจุบัน |
| API key / token | ตัวแปรสภาพแวดล้อมหรือ Secret |
| เชื่อมต่อบริการ MCP | การกำหนดค่าโปรเจกต์ + ตัวแปรสภาพแวดล้อม |

การพิจารณาเช่นนี้ทำให้เห็นภาพได้ง่ายกว่าการจ้องดูรายการชื่อคีย์การกำหนดค่าเพียงอย่างเดียว

Cloud Secrets: [Secrets และตัวแปรสภาพแวดล้อม](/th/guide/web-and-cloud/secrets-and-variables/)

## วินัยในการเปลี่ยนแปลง

1. เปลี่ยนการกำหนดค่าครั้งละหนึ่งประเภท แล้วสังเกตผลเป็นเวลาหนึ่งสัปดาห์
2. การเปลี่ยนแปลงระดับโปรเจกต์ต้องผ่าน Review ใน PR
3. หลังอัปเกรด CLI ให้ diff คำอธิบาย migration อย่างเป็นทางการ
4. อย่าเขียนคีย์ลงในไฟล์กำหนดค่าแล้ว commit เข้า Git

การกำหนดค่ามีไว้เก็บพฤติกรรมเริ่มต้นระยะยาว ไม่ใช้เก็บค่าที่ละเอียดอ่อน และไม่ใช้แทนคำอธิบายงานหรือกฎของทีม
