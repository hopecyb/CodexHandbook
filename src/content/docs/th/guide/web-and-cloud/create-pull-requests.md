เมื่องาน Cloud เสร็จ ให้ตรวจสรุปและ diff ก่อน เมื่อผลลัพธ์ตรงตามขอบเขตและเกณฑ์ตรวจสอบแล้วจึงสร้าง Pull Request หากยังไม่ตรง ให้แก้ต่อในแชตเดิม

## จากงานสู่ PR

```text
เลือกสภาพแวดล้อมและ branch เริ่มต้น
  → รันงาน Cloud
  → Review สรุป, log และ diff
  → ติดตามแก้ไขเมื่อจำเป็น
  → Create Pull Request
  → CI + Review เสริมจาก Codex + Review โดยมนุษย์
  → มนุษย์ตัดสินใจว่าจะ merge หรือไม่
```

ระบุในพรอมต์ว่า “สร้าง PR แต่ห้าม merge” แต่อย่าพึ่งข้อจำกัดภาษาธรรมชาติเพียงอย่างเดียว repository ควรเปิดการป้องกัน branch และ required checks ด้วย

## Template งานที่นำกลับมาใช้ได้

```text
เป้าหมาย: แก้ regression ใน #42 ที่ทำให้การเข้าสู่ระบบหมดเวลา
จุดเริ่มต้น: main
ขอบเขต: เฉพาะ packages/auth/** และการทดสอบที่เกี่ยวข้อง
ห้าม: อัปเกรด dependency, แก้ public API หรือเขียนตรงไปยัง main
การตรวจสอบ: pnpm test --filter auth; pnpm typecheck
การส่งมอบ: สร้าง PR ไปยัง main แต่ห้าม merge
คำอธิบาย PR ต้องมีสาเหตุหลัก สรุปการเปลี่ยนแปลง คำสั่งและผลการทดสอบ ความเสี่ยง และวิธีย้อนกลับ
```

## ตรวจสอบก่อนสร้าง

- [ ] commit เริ่มต้นถูกต้อง และไม่มีอินพุตในเครื่องที่ยังไม่ push ตกหล่น
- [ ] diff มีเฉพาะขอบเขตงาน
- [ ] ชื่อ branch ใหม่สื่อความหมายและไม่เขียนทับงานของผู้อื่น
- [ ] รันทดสอบจริง และสรุปไม่ได้ซ่อนความล้มเหลว
- [ ] ไม่มีข้อมูลประจำตัว log ชั่วคราว cache หรือการจัดรูปแบบที่ไม่เกี่ยวข้อง
- [ ] แยกการเปลี่ยนแปลงขนาดใหญ่ออกเป็น PR ที่ Review แยกกันได้

## คำอธิบาย PR ต้องตอบอย่างน้อย

1. เหตุใดจึงต้องแก้
2. แก้อะไรจริง
3. ตรวจสอบอย่างไร รวมคำสั่งและผลลัพธ์
4. ความเสี่ยง ข้อจำกัด และวิธีย้อนกลับ
5. สิ่งใดระบุชัดว่าไม่ได้ทำ

การเปลี่ยนแปลง UI ต้องมีภาพหน้าจอจริง การเปลี่ยนพฤติกรรมต้องมีขั้นตอนทำซ้ำ และการย้ายระบบต้องอธิบาย compatibility กับการย้อนกลับ

## หลังสร้าง

รอ required checks ใช้ `@codex review` ขอ Review เพิ่มเติม แล้วให้ผู้ที่มีบริบทตรวจ diff หลัก หากต้องแก้ ให้นำความคิดเห็นที่ชัดเจนกลับไปยัง branch ของ PR เดิม อย่าสร้าง branch ที่ไม่เกี่ยวข้องอีกอันจนเกิดผลลัพธ์ซ้ำซ้อน

การเปิด PR กับการ merge เป็นขอบเขตสิทธิ์คนละส่วน Cloud สร้าง PR ได้ ไม่ได้หมายความว่าควรข้ามนโยบาย merge ของทีม
