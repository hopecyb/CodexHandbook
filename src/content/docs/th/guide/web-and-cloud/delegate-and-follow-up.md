การมอบหมายไม่ใช่ “โยนปัญหาออกไป” แต่คือการส่งเป้าหมาย ข้อจำกัด สภาพแวดล้อม และนิยามความเสร็จให้แชต Cloud อิสระ งานทำเบื้องหลังได้ คุณดู log เพิ่มบริบท ขอแก้ไข และตรวจ diff ขั้นสุดท้ายได้

## งานแบบใดเหมาะกับการมอบหมาย

- ต้อง build หรือทดสอบเป็นเวลานาน
- อินพุตอยู่ใน remote repository แล้ว
- สร้างสภาพแวดล้อมใหม่ด้วยสคริปต์ได้
- งานเดินหน้าแยกจากงานปัจจุบันได้
- คุณพร้อม Review ผลลัพธ์ภายหลัง แทนการ merge ทันที

งานที่พึ่งสถานะในเครื่องซึ่งยังไม่ commit บริการบนเครื่อง หรือการควบคุมจากมนุษย์อย่างต่อเนื่อง ควรทำในเครื่องก่อน

## ตัวอย่างการมอบหมายที่ครบถ้วน

```text
เป้าหมาย: แก้ปัญหาใน #42 ที่ connection ของคำขอเข้าสู่ระบบยังไม่ถูกปล่อยหลัง 30 วินาที
จุดเริ่มต้น: branch fix/42-timeout ของ acme/api
ขอบเขต: packages/auth/** และการทดสอบที่เกี่ยวข้อง
ห้าม: อัปเกรด dependency, แก้ public API หรือ push ไป main
การตรวจสอบ: pnpm test --filter auth; pnpm typecheck
เสร็จเมื่อ: แสดงสาเหตุหลัก, diff, คำสั่งและผลการออก ห้าม merge อัตโนมัติ
```

หลังเริ่มงาน ให้ยืนยันว่าสภาพแวดล้อมและ branch ถูกต้อง ระหว่างรัน ให้ติดตามเฉพาะเมื่อพบว่าสมมติฐานขาดหายหรือทิศทางคลาดเคลื่อน:

```text
ข้อจำกัดเพิ่มเติม: ห้ามแก้ HTTP client ส่วนกลาง ให้จำกัดการแก้ไว้ที่ auth adapter
อธิบายก่อนว่าข้อจำกัดนี้เปลี่ยนแนวทางปัจจุบันอย่างไร แล้วจึงทำต่อ
```

แชตเดิมเก็บบริบทที่มีอยู่ จึงเหมาะกับการแก้ทิศทางของเป้าหมายเดิม เป้าหมายที่เป็นอิสระทั้งหมดควรเปิดแชตใหม่ งานคู่ขนานไม่ควรเขียน branch หรือชุดไฟล์เดียวกัน

## เมื่อผลลัพธ์พร้อม

1. อ่านสรุปและ diff ทั้งหมด
2. เทียบกับพาธที่งานอนุญาต
3. ดูผลลัพธ์จริงของคำสั่งตรวจสอบแต่ละคำสั่ง
4. ขอคำอธิบายสำหรับรายการที่ล้มเหลวหรือไม่ได้รัน
5. หากต้องแก้ ให้คำสั่งติดตามที่ชัดเจนในแชตเดิม
6. เมื่อผ่านเกณฑ์ ให้สร้าง PR แล้วส่งต่อให้ CI และการ Review โดยมนุษย์

เริ่ม Cloud ได้จาก Web, IDE, GitHub, GitLab (Beta), Linear หรือ Slack เอกสาร Cloud ทางการยังระบุว่าเริ่มและ Review งานจาก Codex CLI ได้ จุดเข้าใช้งานที่ต่างกันไม่เปลี่ยนขอบเขตของ repository สภาพแวดล้อม เครือข่าย และการ Review

## วิธีติดตามเมื่อล้มเหลว

อย่าพูดเพียงว่า “ลองใหม่” ให้ระบุหลักฐานความล้มเหลวและขั้นถัดไป:

```text
การทดสอบล้มเหลวที่ retry.test.ts:48 อธิบายก่อนว่าความล้มเหลวเกิดจากการเปลี่ยนแปลงครั้งนี้หรือไม่
หากใช่ ให้แก้เฉพาะ regression นี้แล้วรันทดสอบ auth ใหม่ หากไม่ใช่ ให้คงความล้มเหลวไว้และบันทึกให้ชัดเจน
```
