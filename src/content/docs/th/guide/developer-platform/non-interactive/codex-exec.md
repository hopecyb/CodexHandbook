หาก `codex` แบบโต้ตอบคือการคุยไปทำไป **`codex exec`** ก็ใกล้เคียงกับการมอบงานครั้งเดียว รอจนรันเสร็จ แล้วรับผลลัพธ์กลับมา

นี่คือแกนหลักของ [โหมดไม่โต้ตอบ](/th/guide/cli/non-interactive-mode/): ไม่มีการคุยกลับไปกลับมา ไม่มีการชี้แจงระหว่างทำ เมื่อ process จบจะคืนผลลัพธ์หรือสถานะล้มเหลว บทนี้เหมาะกับผู้ทำ integration ใน [แพลตฟอร์มนักพัฒนา](/th/guide/developer-platform/) และผู้ที่ต้องการเชื่อม Codex เข้ากับสคริปต์หรือ CI เป็นครั้งแรก

## เนื้อหาในหน้านี้

- ความต่างระหว่าง `exec` กับ `codex` แบบโต้ตอบ
- รูปแบบคำสั่งขั้นต่ำและ working directory
- ข้อกำหนดด้านการอนุมัติและ sandbox เมื่อไม่มีผู้เฝ้าดู

## `exec` ทำอะไร

มอง `codex exec` ได้ว่า:

- ส่งใบงานครั้งเดียว
- รันเสร็จแล้วคืนผลลัพธ์

เมื่อเขียนใบงานชัดเจน ระบบจะทำตามคำอธิบาย คืนผล แล้วจบ

จึงเหมาะที่สุดเมื่อ:

- ขอบเขตงานกำหนดแล้ว
- ไม่ต้องชี้แจงระหว่างทาง
- ต้องการรันซ้ำอย่างสม่ำเสมอภายหลัง

กล่าวคือ เหมาะกับงานที่กำหนดขอบเขตไว้ชัดเจน

## ทำไมจึงมีคำสั่งนี้

ใน CI คุณจะไม่คุยกับ Codex และไม่ควรคาดหวังให้ระบบหยุดถามกลางทางหลายครั้ง

ดังนั้น `codex exec` มักใช้กับ:

- ระบบตรวจทานโค้ดอัตโนมัติ
- งานตามกำหนดเวลา
- สคริปต์ batch processing
- ขั้นวิเคราะห์หรือสร้างผลลัพธ์ครั้งเดียวใน pipeline

เหมาะกับกรณีที่ **ระบุขอบเขตงานชัดเจนแล้ว** หากยังสำรวจอย่างคลุมเครือ โหมดโต้ตอบมักเหมาะกว่า

:::note
**ให้ยึดชื่อคำสั่งและพารามิเตอร์จาก CLI ทางการ** หลังอัปเกรด ให้รัน `codex --help` และ `codex exec --help` เพื่อตรวจอีกครั้ง
:::

## วิธีขั้นต่ำที่ใช้ได้

```bash
cd /path/to/repo
codex exec --cd . "อ่านอย่างเดียว: เปรียบเทียบ diff ของ branch ปัจจุบันกับ main ระบุความเสี่ยงด้านความปลอดภัยสูงสุด 3 ข้อ และห้ามแก้ไฟล์"
```

โดยค่าเริ่มต้น คำสั่งทำงานใน sandbox แบบอ่านอย่างเดียว หากต้องอนุญาตให้เขียน workspace ให้ระบุ:

```bash
codex exec --cd . --sandbox workspace-write "แก้การทดสอบที่ล้มเหลว โดยแก้เฉพาะ src/auth และ tests/auth"
```

ความคืบหน้าเขียนไปที่ `stderr` และคำตอบสุดท้ายเขียนไปที่ `stdout` หากเครื่องต้องใช้ event stream ทั้งหมด ให้ใช้ `--json` หากต้องการเพียงไฟล์ข้อความสุดท้าย ให้ใช้ `-o` / `--output-last-message` และเมื่อจำเป็นต้องมี field คงที่จึงเพิ่ม `--output-schema`

หลักการ:

- ใน shell script ให้ `cd` ไปยัง worktree ที่สะอาดก่อน
- เก็บ Prompt ใน `prompts/` ของ repository หรือ heredoc เพื่อเลี่ยงปัญหา shell escaping
- ให้ CI ตัดสินสำเร็จหรือล้มเหลวจาก **exit code**

## ข้อเท็จจริงที่มักถูกมองข้าม

ในโหมดโต้ตอบ คุณยังเสริมได้ว่า “ไม่ได้หมายถึงแบบนี้”  
แต่ในโหมด `exec` หาก **บอกผิดตั้งแต่ครั้งแรก งานทั้งรอบอาจออกนอกทิศทาง**

ดังนั้น prompt ของ `exec` ต้องชัดกว่าปกติในเรื่อง:

- ต้องทำอะไร
- ห้ามทำอะไร
- รูปแบบ output เป็นอย่างไร
- เสร็จเมื่อไร
- เมื่อล้มเหลวควรออกอย่างไร

## ความเข้าใจผิดที่พบบ่อย

### `exec` เหมาะกับงานคงที่มากกว่า

ผู้ใช้ครั้งแรกมักมองว่าเป็น “โหมดขั้นสูงของ CLI”

ความเข้าใจที่ตรงกว่าคือ เหมาะสำหรับ **รันงานเดิมซ้ำอย่างสม่ำเสมอ**

### งานสั้นไม่ได้แปลว่าชัดเจน

ในโหมดโต้ตอบ หากบอกไม่ชัด คุณยังเสริมภายหลังได้

แต่ใน `exec` prompt สั้นที่ตัดขอบเขต ข้อจำกัด และเกณฑ์สำเร็จออก ไม่ได้เรียบง่ายกว่า แต่ควบคุมยากกว่า

## Workflow ที่แนะนำ

```text
เตรียม repository (checkout, install, token แบบอ่านอย่างเดียว)
    → ตรึงเวอร์ชัน prompt (git sha)
    → codex exec
    → เก็บ stdout / artifact
    → หากไม่ใช่ 0 ให้ CI ล้มเหลว และอย่าลองใหม่ไม่จำกัด
```

อ่านต่อที่ [สคริปต์และ pipeline](/th/guide/developer-platform/non-interactive/scripts-and-pipelines/)

## มองคำสั่งนี้เป็นอะไรได้บ้าง

- คำสั่งงานครั้งเดียวที่เขียนสคริปต์ได้
- เหมาะสำหรับสคริปต์ CI หรืองานตามกำหนดเวลา

นี่คือเหตุผลที่หลายทีมนำไปไว้หลัง `make review`, GitHub Actions, cron หรือปุ่มบนแพลตฟอร์มภายใน

## เปรียบเทียบกับโหมดโต้ตอบ

| | `codex` แบบโต้ตอบ | `codex exec` |
|---|---|---|
| ชี้แจงคำถาม | ทำได้หลายรอบ | ต้องบอกให้ครบในครั้งเดียว |
| การอนุมัติ | มีมนุษย์อยู่ | ต้องจำกัดนโยบายล่วงหน้า |
| เหมาะกับ | เรียนรู้ สำรวจ | CI, cron |

## หากไม่แน่ใจควรเลือกอย่างไร

- ยังสำรวจ requirement และอาจเปลี่ยนคำสั่งบ่อย: ใช้โหมดโต้ตอบก่อน
- งานถูกกำหนดเป็น template แล้วและต้องการรันซ้ำอย่างสม่ำเสมอ: ใช้ `codex exec`

`codex exec` เหมาะกับงานที่ “ระบุชัดแล้วและต้องการรันซ้ำ” หากยังคิดไปเปลี่ยนไป อย่าเพิ่งใส่ลงในขั้นตอนแบบไม่โต้ตอบ

## ข้อผิดพลาดที่พบบ่อย

- ใส่ประวัติแชตยาวลงใน exec ครั้งเดียว
- CI ใช้ token สิทธิ์เขียน และ prompt มีเนื้อหา PR ที่ยังไม่ sanitize
- ไม่ตรึงเวอร์ชัน CLI จน pipeline ล้มเหลวกะทันหัน
- เพิกเฉย exit code ที่ไม่ใช่ศูนย์ แต่ยังทำเครื่องหมาย green
- ยัดงานซับซ้อนที่ต้องใช้วิจารณญาณของมนุษย์ลงในขั้นตอนอัตโนมัติ

## ขอบเขตความปลอดภัย

- ไม่มีผู้เฝ้าดู = [การอนุมัติโดยมนุษย์](/th/cases/workflows/human-approval-patterns/) อ่อนลง จึงควรอ่านอย่างเดียวโดยค่าเริ่มต้น
- ดู [credential ที่ปลอดภัย](/th/guide/developer-platform/ci-cd/code-review-automation/#สิทธิ์และความปลอดภัย) ซึ่งเป็นการอ้างอิงในบทเดียวกัน

- [ ] log ไม่มี secret หรือ PII
- [ ] sandbox และกฎเท่ากันหรือเข้มกว่าการพัฒนาแบบโต้ตอบ
