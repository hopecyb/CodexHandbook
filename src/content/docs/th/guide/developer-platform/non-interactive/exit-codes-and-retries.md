CI ใช้ **process exit code** ตัดสินว่าขั้นตอนสำเร็จหรือล้มเหลว บทนี้อธิบายความหมายทั่วไป กลยุทธ์ลองใหม่ และการออกแบบแบบ idempotent สำหรับ [codex exec](/th/guide/developer-platform/non-interactive/codex-exec/)

## เนื้อหาในหน้านี้

- ความต่างระหว่าง exit code กับข้อสรุปทางธุรกิจว่า “การตรวจไม่ผ่าน”
- ควรลองใหม่เมื่อเกิด 429 หรือปัญหาเครือข่ายหรือไม่
- ป้องกันผลข้างเคียงจากการทำซ้ำอย่างไร

## Exit code บอกอะไร

หากเพิ่งพบแนวคิดนี้ ให้มอง “exit code” เป็นผลลัพธ์สั้น ๆ ที่โปรแกรมทิ้งไว้ให้สคริปต์และ CI หลังงานจบ

โดยทั่วไปไม่ได้อธิบายมาก เพียงบอก pipeline ว่า:

- ครั้งนี้สำเร็จ
- หรือครั้งนี้ล้มเหลว

ส่วน “การลองใหม่” ตอบอีกคำถามหนึ่งว่า ความล้มเหลวครั้งนี้ควรหยุดทันที หรือควรให้โอกาสอีกครั้ง

:::note
ให้ยึดตาราง exit code จากเอกสาร CLI ทางการ ตารางต่อไปนี้เป็น **หลักการออกแบบ** สำหรับ integration
:::

## ความเข้าใจผิดที่พบบ่อย

### ความล้มเหลวมีหลายประเภท

ผู้เริ่มต้นจำนวนมากมองค่าที่ไม่ใช่ `0` ว่าเป็นความล้มเหลวแบบเดียวกัน

แต่ในทางปฏิบัติ อย่างน้อยต้องแยก:

- งานล้มเหลวระหว่างรัน
- ถูกนโยบายหรือ sandbox ขวาง
- บริการภายนอกขัดข้องชั่วคราว
- รันสำเร็จ แต่ข้อสรุปการตรวจคือ “ไม่ผ่าน”

แต่ละกรณีจัดการต่างกัน และไม่ควรลองใหม่ทั้งหมด

### “ลองใหม่อัตโนมัติ” ไม่ได้เสถียรกว่าเสมอ

หากสาเหตุจะไม่หายไปเมื่อรันซ้ำ เช่น สิทธิ์ไม่พอ ถูกกฎขวาง หรือ prompt มีปัญหา การลองใหม่เพียงเสียเวลาและโควตาซ้ำ

## ความหมายที่แนะนำในเชิงแนวคิด

| สถานการณ์ | วิธีจัดการที่แนะนำ |
|---|---|
| `0` | process ของ `codex exec` ทำงานสำเร็จ ส่วนธุรกิจผ่านหรือไม่ให้ดู structured result |
| ไม่ใช่ `0` และ log แสดงการปฏิเสธจาก policy/sandbox | **อย่า** ลองใหม่โดยไม่วิเคราะห์ ให้แก้ config หรือ prompt |
| ไม่ใช่ `0` และ runner ยืนยันว่าเป็นปัญหาเครือข่ายหรือบริการชั่วคราว | ลองใหม่แบบถอยห่างจำนวนจำกัด |
| การตรวจพบปัญหา P0 แต่ process สำเร็จ | ใช้ `pass: false` ใน [Structured output](/th/guide/developer-platform/non-interactive/structured-output/) แล้วให้สคริปต์ `exit 1` |

การ “พบปัญหาความปลอดภัย” ไม่ควรอาศัย exception แบบ crash แต่ควร **ระบุอย่างชัดเจน** ว่า `pass: false` ใน JSON แล้วให้ wrapper script ตัดสิน exit code

## Template จับ exit code ใน bash

```bash
#!/usr/bin/env bash
set -uo pipefail

log_file="${RUNNER_TEMP:-/tmp}/codex-exec.stderr.log"
codex exec --cd . "$(cat "$PROMPT")" 2>"$log_file"
code=$?

if [ "$code" -ne 0 ]; then
  cat "$log_file" >&2
  exit "$code"
fi
```

อย่าตั้งชื่อความหมายให้เลขที่เอกสารทางการไม่ได้กำหนด เช่น สมมติว่า `2` หมายถึง policy failure เสมอ เมื่อต้องลองใหม่ ให้ runner ชั้นนอกตัดสินจากประเภท error ที่ระบุได้อย่างเสถียร และจำกัดจำนวนครั้ง เวลารวม และผลข้างเคียง

## Idempotency และผลข้างเคียง

| ความเสี่ยง | วิธีลด |
|---|---|
| แสดงความคิดเห็นใน PR ซ้ำ | ใช้ check run id หรือ “หากมีความคิดเห็น bot แล้วให้อัปเดต” |
| เขียนไฟล์ซ้ำ | ให้ exec ตรวจแบบอ่านอย่างเดียวโดยค่าเริ่มต้น ส่วนการเขียนใช้ job แยก + gate ของมนุษย์ |
| ส่งการแจ้งเตือนซ้ำ | ใส่ dedupe key ใน notification webhook |

## หากไม่แน่ใจควรตัดสินอย่างไร

หากไม่แน่ใจว่าความล้มเหลวควรลองใหม่หรือไม่ ให้ถาม:

1. error ดูเหมือนความผันผวนภายนอกชั่วคราวหรือไม่
2. หากรันซ้ำ จะสร้างความคิดเห็น การเขียน หรือการแจ้งเตือนซ้ำหรือไม่
3. สาเหตุจริงต้องให้คนแก้ config, prompt หรือสิทธิ์หรือไม่

หากใกล้เคียงข้อ 1 จึงเหมาะกับการลองใหม่แบบจำกัด หากใกล้ข้อ 2 หรือ 3 ควรหยุดและแก้สาเหตุหลัก

## ข้อผิดพลาดที่พบบ่อย

- ไม่สนใจ exit code ทำให้ CI เป็น green เสมอ
- ลองใหม่ไม่จำกัดเมื่อเกิด policy error จนเสียโควตา
- ไม่ตรึง prompt/git sha ขณะลองใหม่ ทำให้เปรียบเทียบผลไม่ได้

ให้แยกก่อนว่า “นี่เป็นปัญหาชั่วคราว หรือเป็นปัญหาที่รันซ้ำก็ไม่ดีขึ้น” แล้วจึงตัดสินใจ ไม่ใช่ทุกความล้มเหลวที่ควรรันอีกครั้ง

## Checklist การตรวจรับ

- [ ] CI ล้มเหลวเมื่อ exit code ไม่ใช่ 0
- [ ] จำนวน retry และระยะถอยห่างมีขีดจำกัด
- [ ] แยก “การตรวจไม่ผ่าน” ออกจาก “process ล้มเหลว” ได้
- [ ] log มีข้อมูลเพียงพอสำหรับแก้ปัญหา
