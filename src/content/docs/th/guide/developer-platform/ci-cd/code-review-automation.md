การใส่ Codex ใน **pipeline ของ Pull Request** ช่วยตรวจพบปัญหาชัดเจนก่อนมนุษย์ตรวจ แต่ **ทดแทน** การตรวจทานที่รับผิดชอบและการทดสอบไม่ได้ หน้านี้อธิบายรูปแบบ automation ที่นำไปใช้ได้จริง

## หน้านี้ครอบคลุมอะไร

- เรียก Codex ใน CI อย่างปลอดภัยได้อย่างไร
- prompt สำหรับตรวจทานควรมีอะไร
- ส่งผลกลับไปยัง PR โดยไม่ merge อัตโนมัติอย่างไร

## เข้าใจบทบาทก่อน

มอง “ระบบตรวจทานโค้ดอัตโนมัติ” เป็นการให้ Codex ช่วยคัดกรองรอบแรก ส่วนผู้ตัดสินใจสุดท้ายยังเป็นมนุษย์

งานที่เหมาะที่สุดคือ:

- ชี้ความเสี่ยงที่เห็นได้ชัดล่วงหน้า
- สรุปจุดสำคัญใน diff
- ทำการตรวจซ้ำ ๆ ก่อน

ไม่เหมาะกับการตัดสินแทนโดยตรงว่า “PR นี้ merge ได้แน่นอน”

เนื้อหาที่เกี่ยวข้อง: [โหมดไม่โต้ตอบ](/th/guide/cli/non-interactive-mode/) · [ภาพรวม SDK](/th/guide/developer-platform/sdk-overview/)

## สถาปัตยกรรมที่แนะนำ

```text
PR เปิด / อัปเดต
    → CI job (token แบบอ่านอย่างเดียว)
    → codex exec หรือ API ตรวจ diff
    → อัปโหลดรายงาน / แสดงความคิดเห็นใน PR
    → มนุษย์ตัดสินใจว่าจะ merge หรือไม่
```

## ความเข้าใจผิดที่พบบ่อย

### การตรวจอัตโนมัติกับการอนุมัติอัตโนมัติไม่ใช่เรื่องเดียวกัน

เมื่อเริ่มเชื่อมระบบ หลายทีมมักประเมินเกินจริงว่า เมื่อระบบตรวจได้อัตโนมัติ ก็น่าจะตัดสินใจได้อัตโนมัติด้วย

ในทางปฏิบัติ ระบบเหมาะกับชั้นคำแนะนำและการคัดกรองเบื้องต้น ไม่เหมาะเป็นผู้รับผิดชอบสุดท้าย

### ไม่ใช่ทุก PR ที่ควรรันการตรวจหนักตั้งแต่ต้น

หาก PR เล็ก มีมูลค่าต่ำ หรือกฎยังไม่ชัด การตรวจอัตโนมัติแบบหนักมักสร้างเพียง noise

จุดเริ่มต้นที่ดีกว่าคือการตรวจ diff แบบเบา แล้วดูว่าช่วยทีมประหยัดเวลาได้สม่ำเสมอหรือไม่

## องค์ประกอบของ Prompt template

```text
คุณเป็นผู้ช่วยตรวจทานโค้ด ตรวจเฉพาะ diff เทียบกับ base branch
ผลลัพธ์: ปัญหาร้ายแรง / คำแนะนำ / nit โดยระบุไฟล์และเลขบรรทัดทุกข้อ
ห้ามแก้ repository และห้ามเรียกเครือข่าย
หาก diff ใหญ่เกินไป ให้ตรวจเฉพาะ <รายการพาธ>
```

เก็บแบบมีเวอร์ชันใน `prompts/ci-review.md`

## สิทธิ์และความปลอดภัย

| หลักการ | วิธีทำ |
|---|---|
| อ่านอย่างเดียว | CI token ไม่มีสิทธิ์ push หรือให้เฉพาะ bot แสดงความคิดเห็น |
| โมเดลคงที่ | เปรียบเทียบคุณภาพการตรวจในอดีตได้ |
| ป้องกัน injection | อย่านำคำอธิบาย PR ที่ยังไม่ sanitize ไปต่อใน system prompt |
| Secret | เก็บ token ใน GitHub Secrets |

[รูปแบบการอนุมัติโดยมนุษย์](/th/cases/workflows/human-approval-patterns/) · [Environment variables](/th/guide/reference/environment-variables/)

## Quality gate

- Review job ล้มเหลว ≠ ต้อง block การ merge เสมอไป ช่วงแรกอาจเป็นเพียง advisory
- แยกจาก status check ที่บังคับ: test แดงต้องกั้น ส่วน AI nit อาจเพียงเตือน
- สุ่มเทียบสิ่งที่ AI ตรวจพลาดหรือรายงานผิดกับการตรวจของมนุษย์เป็นระยะ

## ความสัมพันธ์กับ Cloud

repository ซับซ้อนสามารถรันการทดสอบเต็มใน [Cloud](/th/guide/web-and-cloud/) ก่อนตรวจ ส่วน exec ใน CI เหมาะกับ **การตรวจ diff แบบเบา**

## ข้อผิดพลาดที่พบบ่อย

- CI มีสิทธิ์เขียน และ prompt ถูก inject ด้วย “โปรด push fix”
- ผลตรวจยาวเกินไปจนกลบ Review ของมนุษย์
- ไม่จำกัดขนาด diff จนหมดเวลาและโควตา

คุณค่าหลักของระบบตรวจทานโค้ดอัตโนมัติคือคัดปัญหาชัดเจนก่อน Review ของมนุษย์ ไม่ใช่รับผิดชอบการ merge แทนมนุษย์

## Checklist การตรวจรับ

- [ ] CI ทำงานอย่างปลอดภัยกับ fork PR และไม่รั่ว secrets
- [ ] ผลตรวจมีโครงสร้างและเครื่องอ่านได้ หากต้องการ
- [ ] เอกสารทีมอธิบายบทบาทของ AI review
