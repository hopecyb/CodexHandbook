การใช้ Codex อย่างปลอดภัยต้องดูการควบคุมสองชั้นพร้อมกัน: **Sandbox กำหนดว่าในทางเทคนิคเข้าถึงได้ถึงไหน ส่วนนโยบายอนุมัติกำหนดว่าต้องถามคุณก่อนข้ามขอบเขตปัจจุบันหรือไม่**

![ขั้นตอน Sandbox และการอนุมัติของ Codex: การกระทำผ่านขอบเขต Sandbox ก่อน เมื่อจะข้ามขอบเขตจึงขออนุมัติจากมนุษย์ และสุดท้ายทิ้งหลักฐานการตรวจสอบไว้](/illustrations/flow-sandbox-approval.webp)

## จำความแตกต่างนี้ก่อน

| การควบคุม | คำถามที่ตอบ | สิ่งที่เกี่ยวข้องโดยทั่วไป |
|---|---|---|
| Sandbox | การกระทำนี้เข้าถึงได้ไกลที่สุดแค่ไหน | ไฟล์โปรเจกต์ เส้นทางนอกโปรเจกต์ ความสามารถระบบ เครือข่าย |
| นโยบายอนุมัติ | ต้องถามคนก่อนข้ามขอบเขตปัจจุบันหรือไม่ | ติดตั้ง Dependency เข้าถึงเครือข่าย เขียนไดเรกทอรีภายนอก เปิดแอป |
| ข้อจำกัดของงาน | งานนี้ควรและไม่ควรทำอะไร | ไดเรกทอรีที่แก้ได้ การกระทำต้องห้าม คำสั่งตรวจรับ |
| การตรวจโดยมนุษย์ | ผลที่ทำไปยอมรับได้หรือไม่ | diff, log, การทดสอบ, ผลกระทบภายนอก |

ข้อจำกัดของงานแทน Sandbox ไม่ได้ และ Sandbox ก็แทนการตรวจขั้นสุดท้ายไม่ได้ แต่ละอย่างดูแลเจตนา ขอบเขตการทำงาน และการตรวจรับผลลัพธ์ต่างกัน

## การกระทำหนึ่งผ่านขอบเขตความปลอดภัยอย่างไร

เมื่อ Codex เตรียมรันคำสั่งหรือเรียกเครื่องมือ ให้เข้าใจตามลำดับนี้:

1. ตรวจว่าการกระทำอยู่ในขอบเขตที่ Sandbox ปัจจุบันอนุญาตหรือไม่
2. ถ้าอยู่ในขอบเขต จะทำงานและบันทึกเอาต์พุต โดยอาจไม่มีหน้าต่างถาม
3. ถ้าเกินขอบเขต จะขออนุญาตตามนโยบายอนุมัติหรือถูกปฏิเสธทันที
4. คุณปฏิเสธ ขอการกระทำที่แคบลง หรืออนุมัติเฉพาะการกระทำชัดเจนครั้งนี้ได้
5. หลังทำงานยังต้องตรวจ diff การทดสอบ และสถานะระบบภายนอก เพื่อยืนยันว่าผลตรงตามเป้าหมาย

Sandbox จำกัด Process ลูกและคำสั่งที่ Codex เปิดด้วย อย่าคิดว่าการกระทำในสคริปต์จะข้ามขอบเขตได้

## ขอบเขตงานในเครื่องกับ Cloud ต่างกัน

| สภาพแวดล้อม | วิธีแยกหลัก | ประเด็นเครือข่าย | สิ่งที่ควรตรวจ |
|---|---|---|---|
| งานในเครื่องของ App / CLI / IDE | Sandbox ระดับระบบปฏิบัติการและนโยบายอนุมัติปัจจุบัน | โดยทั่วไปงานในเครื่องไม่ควรพึ่งอินเทอร์เน็ตโดยอัตโนมัติ เมื่อจำเป็นให้อนุมัติหรือกำหนดค่าอย่างชัดเจน | ขอบเขต Workspace คำสั่ง เส้นทางนอกโปรเจกต์ จุดประสงค์การเชื่อมต่อ |
| งาน Cloud | Container แยกที่ OpenAI จัดการ | ขั้นตั้งค่ากำหนดให้เชื่อมต่อได้ตามสภาพแวดล้อม ส่วนขั้น Agent ปิดเครือข่ายโดยค่าเริ่มต้น เว้นแต่เปิดไว้อย่างชัดเจน | Repository การตั้งค่าสภาพแวดล้อม โดเมนที่อนุญาต diff และหลักฐานการตรวจสอบที่ส่งกลับ |

Secrets ในสภาพแวดล้อม Cloud ใช้สำหรับขั้นตั้งค่าและจะถูกนำออกก่อนเริ่มขั้น Agent ถึงอย่างนั้นยังควรใช้สิทธิ์ขั้นต่ำและไม่ใส่ข้อมูลรับรอง Production ที่ไม่เกี่ยวข้องในสภาพแวดล้อมงาน

## เมื่อเห็นคำขออนุมัติ ให้พิจารณาสี่ขั้น

### 1. เทียบกับงาน

ขั้นตอนนี้ช่วยเป้าหมายปัจจุบันจริงหรือไม่ คำว่า “อาจมีประโยชน์” ยังไม่ใช่เหตุผลเพียงพอให้ออนุมัติ

### 2. เทียบกับขอบเขต

คำขอจะเข้าถึงโปรเจกต์ปัจจุบัน ไดเรกทอรีภายนอก เครือข่าย หรือแอประบบ ยิ่งระบุเส้นทาง โดเมน และคำสั่งชัด ก็ยิ่งตัดสินใจง่าย

### 3. เทียบกับผลข้างเคียง

เป็นเพียงการอ่าน หรือจะเขียนไฟล์ ติดตั้งซอฟต์แวร์ ส่งข้อมูล หรือเปลี่ยนสถานะระยะไกล ผลข้างเคียงภายนอกมักต้องระวังกว่าการแก้ไขในเครื่องที่ย้อนกลับได้

### 4. เทียบกับการตรวจสอบและกู้คืน

หลังทำจะยืนยันความสำเร็จอย่างไร หากล้มเหลวย้อนกลับได้หรือไม่ ถ้ายังไม่มีคำตอบ ให้ Codex อธิบายหรือเสนอทางเลือกที่เล็กกว่าก่อน

## ตัวอย่างเฉพาะ: ติดตั้ง Dependency

สมมติ Codex ขอรัน:

```bash
pnpm install
```

อย่าดูเพียงว่าคุ้นคำสั่งหรือไม่ ควรยืนยันว่า:

- งานปัจจุบันต้องใช้ Dependency ที่ขาดอยู่จริง
- คำสั่งทำงานในไดเรกทอรี Repository ที่ถูกต้อง
- ต้องเข้าถึง Package Registry ใด
- จะเปลี่ยน Lockfile หรือไม่
- หลังติดตั้งจะรันการทดสอบหรือ Build ใด

หากต้องการเพียงตรวจโค้ดเดิมและติดตั้ง Dependency ไว้แล้ว คุณปฏิเสธและขอให้ใช้สภาพแวดล้อมปัจจุบันก่อนได้

## ระบุขอบเขตในพรอมต์

เขียนขอบเขตที่ทำได้ลงในงานโดยตรง:

```text
แก้เฉพาะ src/auth และ tests/auth
ใช้ Dependency ที่ติดตั้งแล้วก่อน ห้ามเชื่อมต่อเครือข่ายหรืออัปเกรดเวอร์ชัน
หากจำเป็นต้องเข้าถึงเส้นทางนอกโปรเจกต์หรือเครือข่าย ให้อธิบายจุดประสงค์ เป้าหมาย และการกระทำขั้นต่ำก่อน
เมื่อเสร็จ ให้รัน pnpm test --filter auth และรายงานเอาต์พุตของคำสั่งกับความเสี่ยงที่เหลือ
```

ข้อความนี้ทำให้เจตนาชัดขึ้น แต่ข้อจำกัดการทำงานจริงยังอยู่ภายใต้ Sandbox นโยบายอนุมัติ และการตั้งค่าที่ทีมบริหาร

## ความเข้าใจผิดที่พบบ่อย

- **มีหน้าต่างอนุมัติแปลว่าอันตรายเสมอ**: การติดตั้ง การเชื่อมต่อ หรือการเขียนนอกโปรเจกต์ตามปกติก็อาจขออนุมัติ ประเด็นคือความจำเป็นและขอบเขต
- **ไม่มีหน้าต่างแปลว่าปลอดภัยทั้งหมด**: การกระทำอาจอยู่ในขอบเขต Sandbox อยู่แล้ว แต่ยังต้องตรวจสิ่งที่เปลี่ยนจริง
- **อนุมัติครั้งเดียวเท่ากับเปิดถาวร**: ระยะเวลาและขอบเขตขึ้นอยู่กับผลิตภัณฑ์และนโยบาย ต้องอ่านคำขอให้ชัด
- **Agent ย่อยมีสิทธิ์อีกชุด**: Agent ย่อยรับช่วงโหมด Sandbox และสิทธิ์จากงานหลัก ไม่ได้มีสิทธิ์สูงกว่าโดยธรรมชาติ
- **Hooks ใช้แทน Sandbox ได้**: Hook เป็นชั้นเฝ้าระวังและตรวจสอบเพิ่มเติม ไม่ใช่สิ่งทดแทนการแยกแบบบังคับของระบบปฏิบัติการ
