คำว่า “โปรเจกต์” และ “งาน” ดูเรียบง่าย แต่สับสนได้ง่ายเมื่อใช้ครั้งแรก โปรเจกต์คือชุดไฟล์หรือ repository ที่กำลังทำ ส่วนงานคือสิ่งที่คุณขอให้ Codex ทำในครั้งนี้

ตัวอย่าง:

- repository ของเว็บไซต์เอกสาร → โปรเจกต์
- “ปรับศัพท์บนหน้าแรกให้อ่านง่ายขึ้น” → งาน

แนวคิดคู่นี้สำคัญ เพราะ Desktop App มีสองระดับอยู่พร้อมกันเสมอ:

- ตอนนี้คุณกำลังทำงานในโปรเจกต์ใด
- ครั้งนี้คุณต้องการให้ทำอะไร

## โปรเจกต์

- เพิ่มไดเรกทอรีฝึกหรือรากของ repository
- จดจ่อครั้งละหนึ่งโปรเจกต์เพื่อลดบริบทปะปน

มอง “โปรเจกต์” เป็น **พื้นที่ทำงาน** ของการร่วมมือครั้งนี้  
หากเลือกพื้นที่ผิด ปัญหาหลังจากนั้นก็มักผิดตามไปด้วย

## งาน

- เริ่มงานด้วยพรอมต์ที่ครบถ้วน
- สังเกตแผนและการเรียกใช้เครื่องมือ
- อนุมัติหรือปฏิเสธเมื่อจำเป็น

“งาน” คือ **สิ่งที่มอบหมายอย่างเฉพาะเจาะจง** ในครั้งนี้  
ยิ่งมอบหมายชัด Codex ก็ยิ่งต้องเดาระหว่างทำน้อยลง

เปรียบเทียบแนวคิดที่ [Thread งาน และโปรเจกต์](/th/guide/foundations/threads-tasks-and-projects/)

## ความเข้าใจผิดที่พบบ่อย

### 1. ทำไมต้องเลือกโปรเจกต์ก่อน เริ่มถามเลยไม่ได้หรือ

เพราะ Codex ต้องรู้ว่าครั้งนี้กำลังทำงานกับไฟล์หรือ repository ใด

หากเลือกโปรเจกต์ผิด ปัญหาอย่าง “ทำไมมองไม่เห็นไฟล์” หรือ “ทำไมไปแก้ที่อื่น” จะเกิดบ่อยขึ้น

### 2. หนึ่งโปรเจกต์มีหลายงานได้หรือไม่

ได้  
แนวทางที่มั่นคงกว่าคือ:

- อยู่ในโปรเจกต์เดียวกัน
- ทำครั้งละหนึ่งงานที่ชัดเจน
- เสร็จแล้วค่อยเปิดงานถัดไป

วิธีนี้ลดโอกาสที่บริบทจะปะปน

### 3. ตอนเริ่มงานควรบอกอะไร

พยายามใส่ข้อมูลสามประเภท:

- เป้าหมาย
- ขอบเขตข้อจำกัด
- เกณฑ์ว่าเสร็จเมื่อไร

### 4. requirement ขนาดใหญ่ควรอยู่ในงานเดียวหรือไม่

หากงานครอบคลุมกว้าง วิธีที่มั่นคงกว่าคือ:

- ใช้โปรเจกต์เดิม
- แบ่งเป็นหลายงาน
- แต่ละงานแก้เป้าหมายที่ชัดเจนเพียงหนึ่งอย่าง

## ลำดับที่ใช้บ่อย

เมื่อทำงานใน Desktop App ครั้งแรก ให้ทำตามลำดับนี้:

1. ยืนยันว่าเลือกโปรเจกต์ถูก
2. ยืนยันว่าเป้าหมายของงานมีเรื่องหลักเพียงเรื่องเดียว
3. เพิ่มขอบเขตข้อจำกัดและเกณฑ์เสร็จ
4. หลังเริ่ม ให้เน้นดูแผน การเรียกใช้เครื่องมือ และผลการเปลี่ยนแปลง
