ครั้งแรกที่อ่านหน้านี้อาจรู้สึกเป็นนามธรรม แต่ไม่ต้องเข้าใจกลไกระดับล่างก่อน โมเดลไม่ได้มีความจำไม่จำกัด เมื่อเนื้อหามาก กระจัดกระจาย หรือยืดยาว โมเดลอาจจับประเด็นไม่ได้ และข้อจำกัดสำคัญที่กล่าวไว้ก่อนหน้าอาจค่อย ๆ เลือน

คำสามคำที่เกี่ยวข้องคือ Token, บริบท และการบีบอัด

**Token** คือหน่วยวัดข้อความที่โมเดลประมวลผล **Context window** คือขีดจำกัดข้อมูลที่ใช้ได้อย่างมีประสิทธิภาพในครั้งหนึ่ง

เมื่อบทสนทนาหรือไฟล์มากเกินไป ระบบอาจทำ **การบีบอัด (compaction)** โดยเก็บสรุปและทิ้งรายละเอียด หลังบีบอัด Agent อาจ “ลืม” ข้อจำกัดช่วงต้น

![ภาพประกอบ: ม้วนบทสนทนายาวเข้าสู่เครื่องบีบอัด กลายเป็นการ์ดสรุปสั้นที่พอดีกับหน้าต่างจำกัด](/illustrations/tokens-compaction.webp)

## แยกสามคำนี้

มองได้ดังนี้:

- **Token**: “หน่วยขนาด” ของข้อมูลที่โมเดลประมวลผล
- **Context window**: ความจุข้อมูลที่โมเดลพกติดไปได้ในครั้งนี้
- **การบีบอัด**: เมื่อเนื้อหามาก ระบบย่อบทสนทนาก่อนหน้าเป็นสรุปเพื่อสร้างพื้นที่ทำงานต่อ

ปัญหาคือ **สรุปไม่สามารถเก็บรายละเอียดทั้งหมด**

เมื่อบทสนทนายาว requirement ที่กล่าวเพียงครั้งเดียวและไม่ได้ย้ำภายหลังจึงมีโอกาสถูกลดความสำคัญมากขึ้น

## ความเข้าใจผิดที่พบบ่อย

### 1. เมื่อเคยบอกครั้งหนึ่ง ระบบควรจำตลอดหรือไม่

หากข้อความนั้นอยู่ไกลในบทสนทนาและไม่ปรากฏในข้อมูลสำคัญปัจจุบัน ภายหลังอาจถูกบีบอัดออก

### 2. ยิ่งมีบริบทมากยิ่งเสถียรหรือไม่

บริบทที่เกี่ยวข้องมากขึ้นช่วยได้ แต่ข้อมูลไม่เกี่ยวข้องมากเกินไปทำให้:

- ประเด็นสำคัญไม่ชัด
- ข้อจำกัดสำคัญถูกกลบง่ายขึ้น

### 3. การบีบอัดแปลว่าโมเดลเสียหรือไม่

การบีบอัดเป็นการจัดการทรัพยากร เมื่อข้อมูลมากเกินไป ระบบต้องเก็บเวอร์ชันที่ย่อกว่าเพื่อเดินหน้าต่อ

## เมื่อเกิดกรณีนี้ควรทำอย่างไร

หากกังวลว่า requirement สำคัญจะถูกลืม:

- เขียนข้อจำกัดสำคัญซ้ำในข้อความปัจจุบัน
- เขียนกฎระยะยาวลงในคำอธิบายโปรเจกต์หรือเอกสารคงที่
- เมื่อเปลี่ยนหัวข้อชัดเจน ให้เปิดงานหรือ thread ใหม่
- อย่าบอก edge case สำคัญเพียงครั้งเดียว

## แนวปฏิบัติ

- ใส่ข้อจำกัดสำคัญในข้อความปัจจุบันหรือคำอธิบายโปรเจกต์ อย่าฝังไว้เพียงในบทสนทนาเก่ามาก
- เปิด thread ใหม่เมื่อเปลี่ยนหัวข้อ
