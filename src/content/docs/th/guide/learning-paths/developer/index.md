ใช้แบบฝึกตะกร้าสินค้าขนาดเล็กชุดเดียวทำงานสี่อย่าง: อธิบายโค้ด แก้ข้อผิดพลาด ตรวจ diff และส่งต่อหลักฐาน คุณไม่จำเป็นต้องเรียนทุกไคลเอนต์ การกำหนดค่า หรือความสามารถหลาย Agent ก่อน

ข้อกำหนดเบื้องต้น: อ่าน JavaScript พื้นฐานได้ และเรียกการทดสอบ Node.js ในเทอร์มินัลภายในเครื่อง สภาพแวดล้อมอ้างอิงคือ Node.js 22.16.0 โดยไม่ต้องติดตั้ง dependency บุคคลที่สาม เลือกใช้ CLI, IDE หรือช่องทางที่เข้าถึงไฟล์และเทอร์มินัลในเครื่องได้ พฤติกรรมการทดสอบกำหนดโดย Node.js

## เตรียมโค้ดและไดเรกทอรีบันทึก

ใช้ `examples/complete-workflows/developer/verified-bug-fix/` จาก [รีโพซิทอรีต้นฉบับของคู่มือ](https://github.com/hopecyb/CodexHandbook) อ่าน `brief.md` กับ `README.md` ก่อน โดยยังไม่ดู `solution/` ขั้นตอนสอนฉบับเต็มอยู่ที่ [แก้ Bug พร้อมการตรวจสอบ](/th/cases/use-cases/software-development/fix-a-bug-with-verification/)

ทำงานในไดเรกทอรีแบบฝึกนั้น:

```sh
# work/ ต้องยังไม่มีอยู่ หากมีแบบฝึกของคุณแล้ว ให้ใช้ชื่อใหม่และอย่าเขียนทับ
cp -R starter work
mkdir -p evidence
```

แก้ใน `work/` และเก็บ `starter/` ซึ่งเป็นสถานะล้มเหลวต้นฉบับ กับ `solution/` ซึ่งเป็นคำตอบอ้างอิง บันทึกเทมเพลตด้านล่างแยกไว้ใน `evidence/` เทมเพลตคู่มือที่ดาวน์โหลดไม่มีโค้ดฉบับเต็ม จึงต้องใช้ร่วมกับแบบฝึกจากรีโพซิทอรีข้างต้น

| Milestone | ก่อนเริ่ม | ผลลัพธ์ | เงื่อนไขว่าเสร็จ |
|---|---|---|---|
| 1. อ่านโค้ด | brief และ starter | code-map.md | อินพุต เส้นทางข้อมูล ความล้มเหลว และต้นเหตุมีหลักฐานจากไฟล์ |
| 2. แก้และตรวจสอบ | ต้นเหตุและการทดสอบที่ยังไม่แก้ | work/cart.js, red.txt, green.txt | ทำให้ล้มเหลวซ้ำก่อน แล้วผ่านด้วยชุดทดสอบเดียวกัน |
| 3. ตรวจ diff | การเปลี่ยนแปลงและเอาต์พุตทดสอบสองครั้ง | review.md และ diff ของ implementation | ไม่แก้ค่าที่คาดหวัง ไม่เปลี่ยน API และไม่มีการเปลี่ยนแปลงที่ไม่เกี่ยวข้อง |
| 4. ส่งต่อ | หลักฐานสามขั้นแรกที่เสร็จแล้ว | handoff.md | ผู้รับช่วงหาไฟล์ปัจจุบันและเรียกขั้นถัดไปซ้ำได้ |

## 1. อ่านโค้ดก่อน แล้วสร้างแผนผังที่ตรวจสอบได้

[ดาวน์โหลดเทมเพลตอ่านโค้ด](/downloads/developer-path/code-map-template.md) ให้ Codex อ่าน `brief.md`, `starter/cart.js` และ `starter/cart.test.js` แล้วอธิบายแบบอ่านอย่างเดียวก่อน ได้แก่ จุดเข้า เส้นทางข้อมูล อินพุตที่กระตุ้น ค่าจริงกับค่าที่คาดหวัง บรรทัดต้นเหตุ และข้อจำกัดขอบเขต

เขียนผลลง `evidence/code-map.md` แบบฝึกนี้มีไฟล์แกนหลักเพียงสองไฟล์ จึงไม่ต้องสร้างแผนภาพสถาปัตยกรรมซับซ้อน เงื่อนไขว่าเสร็จ: อธิบายได้ว่า `10` หมายถึงสิบเปอร์เซ็นต์ ทำไม implementation ที่ผิดจึงคำนวณยอดย่อย 40 เป็นยอดรวม -360 และค่าที่ถูกต้องควรเป็น 36

ใช้ [เอกสารอ้างอิงการอ่านของผู้เขียน](/downloads/developer-path/code-map-reference.md) ตรวจได้ แต่ข้อสรุปของคุณยังต้องย้อนกลับไปดูโค้ดจริง เมื่อผ่านแล้วจึงแก้ implementation

## 2. เก็บผลแดง แล้วแก้ให้น้อยที่สุด

เรียกคำสั่งทั้งหมดต่อไปนี้ในไดเรกทอรี `verified-bug-fix/`:

```sh
node --test work/cart.test.js > evidence/red.txt 2>&1
```

คำสั่งนี้ควรคืน exit code 1 และมีหนึ่งรายการล้มเหลวจากสามรายการ เปิด `evidence/red.txt` แล้วยืนยันว่าการทดสอบส่วนลดแสดงค่าจริง -360 และค่าที่คาดหวัง 36 หากผ่านทั้งหมด ให้ตรวจว่าเผลอใช้คำตอบอ้างอิงหรือแก้ไฟล์ล่วงหน้าหรือไม่ อย่าทำต่อโดยสมมติว่าทำผลแดงซ้ำแล้ว

คำอธิบายงานกำหนดขอบเขตการทำงานทั้งหมดได้โดยตรง:

```text
อ้างอิง brief.md และ evidence/code-map.md แล้วแก้เฉพาะการแปลงเปอร์เซ็นต์ใน work/cart.js
คง function signature และ assertion ใน work/cart.test.js ไว้ ห้ามเพิ่ม dependency และห้าม refactor
เมื่อเสร็จ ให้เรียก node --test work/cart.test.js แล้วบันทึกเอาต์พุตจริงลง evidence/green.txt
หากผลไม่ตรงตามคาด ให้เก็บหลักฐานความล้มเหลวและหาสาเหตุ ห้ามแก้ assertion เพื่อให้ตรงกับ implementation
ส่งมอบคำอธิบายการแก้ไขและผลทดสอบ ห้าม commit หรือ push
```

เงื่อนไขว่าเสร็จ: การทดสอบเดิมทั้งสามผ่าน exit code เป็น 0 และแก้เฉพาะต้นเหตุ หากคำสั่งทดสอบล้มเหลวก็ยังอาจสร้าง log ได้ จึงห้ามถือว่า “มี green.txt แล้ว” แปลว่าการทดสอบผ่าน

## 3. ตรวจ diff และสิ่งที่ตกหล่น

[ดาวน์โหลดเทมเพลตตรวจทาน](/downloads/developer-path/review-template.md) แล้วกรอกขอบเขตเปรียบเทียบจริง สำหรับแบบฝึกนี้คือ `starter/` ที่เก็บไว้เทียบกับ `work/` ของคุณ ไม่ใช่เปรียบเทียบกับ main โดยอัตโนมัติ และไม่ขึ้นอยู่กับว่ารีโพซิทอรีมีการเปลี่ยนแปลงที่ยังไม่ได้ commit หรือไม่

```sh
diff -u starter/cart.js work/cart.js
diff -u starter/cart.test.js work/cart.test.js
```

คำสั่งแรกควรแสดง diff การแปลงเปอร์เซ็นต์ โดย exit code 1 หมายถึงมีความต่าง ไม่ใช่คำสั่งเสีย คำสั่งที่สองควรไม่มีเอาต์พุตและ exit code เป็น 0 ให้ Codex ตรวจแบบอ่านอย่างเดียวจาก diff จริงกับ log แดง-เขียว แล้วเขียนข้อค้นพบ หลักฐาน สิ่งที่ยังไม่ครอบคลุม และการตัดสินใจลง `evidence/review.md`

เงื่อนไขว่าเสร็จ: ไม่ผ่อนการทดสอบ API ไม่เปลี่ยน และไม่มี dependency เพิ่มหรือการแก้ที่ไม่เกี่ยวข้อง ระบุให้ชัดว่าแบบฝึกยังไม่ครอบคลุมความแม่นยำของสกุลเงิน ภาษี และอินพุตผิดกฎหมาย อย่าเขียนว่าปลอดภัยในโปรดักชันเพียงเพราะการทดสอบสามรายการผ่าน เทียบกับ [เอกสารอ้างอิงการตรวจของผู้เขียน](/downloads/developer-path/review-reference.md) ได้

## 4. เขียนเอกสารส่งต่อ แล้วกู้บริบทจากไฟล์

[ดาวน์โหลดเทมเพลตส่งต่อ](/downloads/developer-path/handoff-template.md) แล้วเขียนไดเรกทอรีปัจจุบัน ไฟล์ที่แก้ ข้อจำกัดที่ยังมีผล พาธหลักฐาน คำสั่งขั้นถัดไป และผลที่คาดไว้ลง `evidence/handoff.md` ในโปรเจกต์ Git จริงยังต้องบันทึก branch, commit และสถานะ working tree ปัจจุบัน

งานแบบอ่านอย่างเดียวหลังส่งต่อเขียนได้ดังนี้:

```text
อ่าน evidence/handoff.md แล้วตรวจว่าไฟล์ปัจจุบันใน work/ ตรงกับคำอธิบายส่งต่อหรือไม่
เรียก node --test work/cart.test.js จากรากแบบฝึก แล้วบันทึก exit code และสรุปจริง
เปรียบเทียบ implementation และการทดสอบระหว่าง work กับ starter หากสถานะต่างกัน ให้ระบุความต่างและอย่าใช้ผลผ่านเดิม
ห้ามแก้โค้ดอีก ห้าม commit และห้าม push
```

ทำในงานใหม่หรือให้ผู้ร่วมงานอีกคนตรวจซ้ำได้ การเปิดงานใหม่ด้วยตัวเองนับเป็นเพียงการฝึกกู้บริบท อย่าระบุว่าเป็นการตรวจจากคนอิสระ ดูรูปแบบอ้างอิงที่ [บันทึกส่งต่อของผู้เขียน](/downloads/developer-path/handoff-reference.md)

เงื่อนไขว่าเสร็จ: ใช้เพียงไฟล์ส่งต่อก็หาโค้ด การทดสอบ และขอบเขตได้ พร้อมเรียกผลปัจจุบันจริง หากยังไม่ได้ทำรอบนี้ ให้เก็บสถานะ “รอผู้รับช่วงตรวจสอบ” ในบันทึก

## เมื่อมีปัญหาให้ย้อนกลับไปขั้นใด

- หาไฟล์ไม่พบ: ยืนยันไดเรกทอรีปัจจุบันของเทอร์มินัลและว่า `work/` มีอยู่ แล้วกลับไปขั้นเตรียม
- ไม่มีผลแดง: ตรวจจุดเริ่มต้นและการทดสอบต้นฉบับ อย่าใช้ผลเขียวของคำตอบอ้างอิงแทนการทำซ้ำ
- ผ่านหลังแก้การทดสอบ: คืน assertion เดิม แล้วกลับไปวิเคราะห์ต้นเหตุ
- พบการเปลี่ยนแปลงที่ไม่เกี่ยวข้อง: เก็บ diff ก่อน ลดขอบเขตการแก้ แล้วเรียกการทดสอบใหม่
- เอกสารส่งต่อไม่ตรงกับไฟล์: ยึดไฟล์ปัจจุบันเป็นหลัก อัปเดตบันทึกแล้วจึงทำต่อ

เมื่อนำไปใช้กับโปรเจกต์จริง ให้เพิ่ม lint, type check และการทดสอบเต็มชุดตามข้อกำหนดรีโพซิทอรีจากโครงสร้างหลักฐานนี้ ความจำเป็นและคำสั่งต้องพิจารณาจากเอกสารโปรเจกต์จริง แบบฝึกนี้ไม่มีการตรวจเพิ่มเติมเหล่านั้นและไม่สร้างบันทึกผ่านปลอม
