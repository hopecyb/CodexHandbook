“diff” คือรายละเอียดว่า Codex แก้ส่วนใดบ้างในครั้งนี้

เมื่อยอมรับงานครั้งแรก หลายคนอ่านเพียงสรุปที่ Codex เขียนโดยไม่ดูการเปลี่ยนแปลงจริง  
การพบปัญหายังต้องพึ่ง diff เป็นหลัก ส่วนคำอธิบายว่า “ฉันทำเสร็จแล้ว” ใช้ได้เพียงประกอบ

## diff แสดงอะไร

diff ตอบคำถามสำคัญได้โดยตรง:

- Codex แก้ไฟล์ใดบ้าง
- การเปลี่ยนแปลงอยู่ในขอบเขตที่คุณอนุญาตหรือไม่
- ลบหรือทำส่วนอื่นเสียโดยไม่ตั้งใจหรือไม่
- มีเนื้อหา debug คีย์ หรือโค้ดชั่วคราวติดมาหรือไม่

เมื่ออ่าน diff ให้เน้น:

1. แก้เฉพาะพาธที่อนุญาตหรือไม่
2. มีการลบโดยไม่ตั้งใจหรือไม่
3. ชื่อและสไตล์สอดคล้องกันหรือไม่
4. มีคีย์หรือสิ่งตกค้างจาก debug หรือไม่

มุมมองในผลิตภัณฑ์: [diff ความคิดเห็น และการตรวจทาน](/th/guide/desktop-app/diffs-comments-and-review/)

## ตรวจคุณภาพโค้ดที่ AI สร้าง

นอกจากดูว่า “แก้ไฟล์ใด” ให้ดูด้วยว่าการแก้มีลักษณะเหมือนคนในโปรเจกต์นี้เขียนหรือไม่:

| จุดตรวจ | ดูอะไร |
|---|---|
| การตั้งชื่อ | ตัวแปร ฟังก์ชัน และชื่อไฟล์สื่อเจตนาหรือไม่ แทนที่จะใช้ `data`, `temp`, `helper` เต็มไปหมด |
| ขอบเขตฟังก์ชัน | รวมหลายความรับผิดชอบไว้ในฟังก์ชันใหญ่เดียวหรือไม่ |
| การจัดการข้อผิดพลาด | เมื่อล้มเหลวมีบริบทที่มีประโยชน์หรือไม่ และกลืน exception หรือไม่ |
| การทดสอบ | เพิ่มการทดสอบที่พิสูจน์พฤติกรรมหรือไม่ แทนการแก้เฉพาะ implementation |
| comment | อธิบาย “ทำไม” หรือเพียงทวนโค้ด |
| ความเรียบง่าย | เพิ่ม abstraction ที่ยังไม่จำเป็นเพียงเพื่อให้ดูครบหรือไม่ |

หากต้องการตรวจอย่างรวดเร็ว ให้ Codex ตรวจ diff ของตนเองตามตารางนี้อีกครั้ง และสั่งให้แสดงเฉพาะความเสี่ยงโดยไม่แก้ไฟล์ต่อ

## ความเข้าใจผิดที่พบบ่อย

### 1. แม้อ่าน code diff ไม่เป็น ก็ตรวจพื้นฐานก่อนได้

ช่วงแรกไม่ต้องอ่านทุกบรรทัดเหมือนนักพัฒนาอาวุโส  
เพียงดูสามเรื่องนี้ก็มีคุณค่า:

- แก้ไฟล์ใดบ้าง
- แก้ส่วนที่ไม่ควรแก้หรือไม่
- มีเนื้อหาที่ไม่เกี่ยวข้องเพิ่มมาอย่างชัดเจนหรือไม่

### 2. แก้เพียงไฟล์เดียวไม่ได้แปลว่าปลอดภัยเสมอ

ไฟล์น้อยไม่ได้แปลว่าแก้ถูก  
แต่ขอบเขตเล็กตรวจง่ายกว่าและย้อนกลับง่ายกว่าอย่างน้อย

### 3. แม้ “แก้เล็กน้อย” ก็ยังต้องดู

จุดที่ดูเหมือน “แก้เล็กน้อย” มักเป็นจุดที่มองข้ามปัญหาได้ง่าย

## ลำดับการตรวจ

เมื่อดู diff ครั้งแรก ให้ทำตามลำดับนี้:

1. ดูว่าแก้กี่ไฟล์
2. ดูว่าเกินพาธที่อนุญาตหรือไม่
3. ดูว่ามีการลบผิด log ชั่วคราว หรือสิ่งตกค้างจาก debug หรือไม่
4. ดูว่าสไตล์และการตั้งชื่อสอดคล้องหรือไม่

ดูก่อนว่าแก้อะไรจริง แล้วจึงตัดสินจากเนื้อหาการเปลี่ยนแปลงว่าจะยอมรับผลลัพธ์หรือไม่
