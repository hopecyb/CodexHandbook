ถามให้ชัดก่อนว่ากำลังบันทึกอะไร: โควตาบัญชีเหลือเท่าใด การเรียก API ครั้งหนึ่งมีค่าใช้จ่ายเท่าใด รอนานเท่าใด หรือคนใช้เวลาแก้ซ้ำเท่าใด รายการเหล่านี้ใช้คนละหน่วยและแทนกันไม่ได้

[ดาวน์โหลดเทมเพลตบันทึก](/downloads/usage-log/usage-log-1.0.0.zip) · [คำแนะนำการกรอก](/downloads/usage-log/README.md)

## แยกบัญชีสี่ประเภท

| ตัวชี้วัด | หลักฐานที่ใช้บันทึก | การตีความผิดที่พบบ่อย |
|---|---|---|
| โควตาการสมัครสมาชิก | ช่วงเวลา สัดส่วนที่เหลือ และเวลารีเซ็ตที่ UI ปัจจุบันแสดง | แปลงเปอร์เซ็นต์ที่เหลือเป็นดอลลาร์หรือจำนวนงานตายตัวโดยตรง |
| ค่า API | การใช้งานจริงครั้งนั้น โมเดล และราคาที่ใช้; ตรวจใบเรียกเก็บเงิน | ใช้ราคาการสมัครสมาชิกแทนอัตรา API หรือถือค่าประมาณเป็นยอดหักจริง |
| เวลารอ | เวลาเริ่มและจบ คิว และการลองใหม่ของงานเดียวกัน | บันทึกเฉพาะรอบสุดท้ายที่สำเร็จ และละเวลาในรอบล้มเหลว |
| แรงงานคน | จับเวลาการตรวจและการแก้ซ้ำแยกกัน | ถือเวลารอโมเดลทั้งหมดเป็นแรงงานที่ประหยัดได้ |

คำอธิบายราคาทางการระบุว่า การใช้งานของงานขึ้นกับโมเดล บริบท การให้เหตุผล เครื่องมือ และแคช การประมาณจากจำนวนข้อความไม่ใช่ขีดจำกัดตายตัว ให้ยึดแผงการใช้งานสำหรับโควตาปัจจุบัน และดูเซสชัน CLI ด้วย `/status`; การใช้ API key คิดตามอัตรา API [คำอธิบายทางการ](https://learn.chatgpt.com/docs/pricing)

ภาพรวมโควตาอาจรวมงานอื่นและการรีเซ็ตช่วงเวลา อย่าใช้ “ก่อนกับหลังลดไป 5%” สรุปว่างานนี้ใช้ 5% ตายตัว และอย่าใช้ข้อมูลนั้นรับรองผู้อ่านว่าทำได้อีกกี่ครั้ง

## ก่อนประมาณ API ให้ยืนยันหลักเกณฑ์การคิดเงิน

ตรวจราคาตามโมเดล ประเภทอินพุต/แคช/เอาต์พุต และเงื่อนไขบริการ แล้วคำนวณจากการใช้งานจริง หากมีรายการคิดเงินอื่นให้รวมแยก หน้านี้ไม่จัดทำตารางราคาโมเดลตายตัวอีกชุด [ราคา API](https://developers.openai.com/api/docs/pricing)

reasoning token คิดราคาแบบ output token เมื่อสรุปยอด ให้ตรวจว่าฟิลด์รวมส่วนการให้เหตุผลแล้วหรือยังเพื่อไม่ให้บวกซ้ำ และตรวจว่าโมเดลนั้นรองรับระดับการให้เหตุผลที่เลือกหรือไม่ [คำอธิบายโมเดลการให้เหตุผล](https://developers.openai.com/api/docs/guides/reasoning)

ตัวอย่างเพื่อการสอน: สมมติอินพุต 10000 token เอาต์พุต 2000 token ไม่มีแคชหรือค่าใช้จ่ายอื่น และใช้อัตรา **สมมติ** 2 ดอลลาร์ต่อหนึ่งล้าน input token กับ 10 ดอลลาร์ต่อหนึ่งล้าน output token ค่าประมาณคือ 0.04 ดอลลาร์ ตัวอย่างนี้แสดงเพียงการแปลงหน่วย ไม่ตรงกับราคาโมเดลหรือใบเรียกเก็บเงินจริงใด

## เปรียบเทียบการตั้งค่าด้วยงานชุดเดียวกัน

เลือกชุดงานที่มีเกณฑ์ยอมรับชัดเจน แล้วสร้าง baseline ด้วยการตั้งค่าที่ใช้อยู่ คงอินพุต สิทธิ์เครื่องมือ คำอธิบายโปรเจกต์ และวิธีประเมินให้เหมือนกัน โดยเปลี่ยนปัจจัยหลักของโมเดลหรือการให้เหตุผลเพียงหนึ่งอย่างต่อครั้ง

เปรียบเทียบความถูกต้อง ขอบเขต หลักฐาน และงานแก้ซ้ำทีละรายการ ไม่ใช่ดูเพียงความเร็วตอบ หากการตั้งค่าที่เบากว่าไม่ผ่านเกณฑ์อย่างสม่ำเสมอ ให้ตรวจว่าความล้มเหลวมาจากข้อมูลขาด ขอบเขตไม่ชัด หรือการให้เหตุผลไม่พอ แล้วจึงตัดสินใจเพิ่มการตั้งค่า การตั้งค่าที่สูงขึ้นแทนการตรวจแหล่งข้อมูลและการทดสอบไม่ได้

นี่คือคำแนะนำการประเมินของคู่มือ ไม่ใช่ผลทดลองว่าโมเดลใดชนะเสมอ ใช้ [สื่อเปรียบเทียบพรอมต์สามชุด](/th/prompts/comparison-lab/) กับ [ตัวอย่างประเมินเวิร์กโฟลว์](/th/guide/quality/workflow-evaluation/) เพื่อบันทึกข้อสังเกตของคุณได้

## บันทึกเงื่อนไขการเก็บตัวอย่าง

[ตารางการทำงาน](/downloads/usage-log/runs.csv) บันทึก hash อินพุต ป้ายโมเดลจริง ไคลเอนต์ การตั้งค่าการให้เหตุผล ช่องทางคิดค่าบริการ เวลา การลองใหม่ ผลลัพธ์ และหลักฐานค่าใช้จ่าย ส่วน [ตารางภาพรวมโควตา](/downloads/usage-log/allowance-snapshots.csv) บันทึกช่วงเวลาและเวลารีเซ็ตแยกกัน

เก็บทั้งความล้มเหลวและการหยุดชะงัก และบันทึกการตรวจของคนแยกจากงานแก้ซ้ำ ปล่อยฟิลด์ที่ไม่ทราบว่างและอธิบาย อย่าใส่ 0 เพื่อแสร้งว่าไม่มีการใช้ ใช้นามแฝงบัญชี และอย่าใส่คีย์ บัญชี หรือ log ส่วนตัวในสื่อสาธารณะ

ตารางดาวน์โหลดปัจจุบันไม่มีแถวผลวัดจริง หากไม่มี baseline ของคนที่ตรงกัน อย่าคำนวณสัดส่วนที่ประหยัดได้ หากไม่มีตัวอย่างซ้ำ อย่าอ้างว่ามีข้อได้เปรียบด้านความเร็วอย่างสม่ำเสมอ แม้เวลารอโมเดลสั้นลง แต่อาจไม่คุ้มหากมีงานแก้ซ้ำมากขึ้น

## ทำอย่างไรเมื่อใกล้ถึงขีดจำกัด

เก็บผลลัพธ์ปัจจุบัน เรื่องที่ยังไม่ตัดสิน และจุดกู้คืนก่อน แล้วตรวจว่างานติดอยู่กับการลองซ้ำหรืออ่านข้อมูลที่ไม่เกี่ยวข้องหรือไม่ ลดขอบเขตที่ไม่จำเป็นตามเป้าหมาย แต่คงเกณฑ์คุณภาพและความปลอดภัยไว้ อย่าตัดการตรวจสำคัญเพียงเพื่อทำให้เสร็จก่อนโควตาหมด

หากต้องทำต่อ ให้ตรวจโควตาและช่องทางคิดค่าบริการปัจจุบันของคุณก่อนเลือก หน้านี้จะไม่เปลี่ยนไปคิดค่า API ซื้อโควตา หรือแก้การตั้งค่าบัญชีโดยอัตโนมัติ ทีมใช้ [เส้นทางทดลองสองสัปดาห์](/th/guide/learning-paths/team/) เพื่อบันทึกเหตุผลการเลือกและเงื่อนไขย้อนกลับได้

ดูโมเดลปัจจุบัน ความต่างของช่องทาง และคำแนะนำตามงาน: [การเลือกโมเดล: หาโมเดลเริ่มต้นตามงาน](/th/guide/reference/model-selection/)
