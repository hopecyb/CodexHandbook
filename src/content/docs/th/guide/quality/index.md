ข้อผิดพลาดที่ผู้เริ่มต้นใช้ Codex ครั้งแรกทำได้ง่ายที่สุดคือ **เห็น Codex บอกว่าเสร็จแล้ว แล้วถือว่าเสร็จจริง**

การตรวจสอบหมายถึงไม่ดูเพียงคำพูด แต่ดูว่าผลลัพธ์ตรงตามข้อกำหนดจริงหรือไม่

เอาต์พุตของ Codex ต้องตรวจได้ การตรวจสอบไม่ใช่ขั้นเสริม แต่เป็นส่วนหนึ่งของวงจรทุกงาน

![ภาพประกอบ: ใช้แว่นขยายตรวจบรรทัดเพิ่มและลบใน diff ข้าง ๆ มีเช็กลิสต์ยอมรับและหลอดทดลอง โดยหนึ่งรายการทำเครื่องหมายว่ารอดำเนินการ](/illustrations/verification.webp)

## การตรวจสอบดูอะไร

ไม่ว่าคุณแก้โค้ด เขียนเอกสาร หรือค้นข้อมูล สุดท้ายต้องตอบคำถามเดียวกัน:

> **ตอนนี้งานนี้เพียง “ดูเกือบได้” หรือ “ส่งมอบได้แล้ว”**

งานแก้ซ้ำจำนวนมากไม่ได้เกิดจากโมเดลทำผิดทั้งหมด แต่เกิดจาก:

- แก้ส่วนที่ไม่ควรแก้
- แก้ไม่ครบครึ่งหนึ่ง
- อ้างว่าค้นข้อมูลแล้ว แต่แหล่งข้อมูลไม่น่าเชื่อถือ
- หน้าเปิดได้ แต่เวิร์กโฟลว์จริงทำไม่ครบ
- เขียนเอกสารแล้ว แต่ผู้เริ่มต้นทำตามไม่ได้

หน้าที่ของการตรวจสอบคือ **กักความเสี่ยงไว้ก่อนส่งมอบ**

## ความเข้าใจผิดที่พบบ่อย

### 1. เรียกได้ก็ถือว่าเสร็จ

“เรียกได้” บอกเพียงว่าไม่เกิดข้อผิดพลาดทันที ไม่ได้แปลว่า:

- ตรรกะถูกต้อง
- ขอบเขตถูกต้อง
- ไม่เกิด regression
- ตรงกับผลลัพธ์เดิมที่คุณต้องการ

### 2. โมเดลบอกเองว่า “ตรวจแล้ว” ก็วางใจได้

คุณต้องดูว่า **ตรวจอะไรจริง** เช่น:

- เรียกการทดสอบจริงหรือไม่
- อ่าน diff จริงหรือไม่
- เปิดอาร์ติแฟกต์ตรวจจริงหรือไม่
- ให้แหล่งข้อมูลที่ตรวจย้อนหลังได้หรือไม่

### 3. เฉพาะโปรแกรมเมอร์เท่านั้นที่ต้องตรวจสอบหรือไม่

การเขียนบทความ ทำสเปรดชีต สร้างการกำหนดค่า จัดข้อมูล และเขียนคำอธิบาย PR ล้วนต้องตรวจสอบ เพียงใช้วิธีต่างกัน

## หากยังไม่มีเวิร์กโฟลว์ของตนเอง ให้ตรวจตามลำดับนี้

1. ดูว่าผลลัพธ์หลุดประเด็นหรือไม่
2. ดูว่าขอบเขตการเปลี่ยนแปลงใหญ่เกินไปหรือไม่
3. เรียกการตรวจอัตโนมัติที่มี
4. สุดท้ายให้คนดูว่าส่งมอบได้จริงหรือไม่

มองได้ว่าเป็น:

- **ทิศทางถูกหรือไม่**
- **แก้มากเกินไปหรือไม่**
- **เครื่องตรวจแล้วหรือยัง**
- **คนกล้ารับต่อจริงหรือไม่**

## หัวข้อหลัก

- [ตรวจ diff](/th/guide/quality/review-diffs/) — อ่าน diff เพื่อยืนยันขอบเขตและความเสี่ยง
- [เรียกการทดสอบ](/th/guide/quality/run-tests/) — regression อัตโนมัติ
- [ตรวจอาร์ติแฟกต์](/th/guide/quality/verify-artifacts/) — เอกสาร การกำหนดค่า และผลลัพธ์ที่สร้างขึ้น
- [ตรวจแหล่งข้อมูล](/th/guide/quality/validate-sources/) — ข้อสรุปจากการวิจัยตรวจย้อนหลังได้
- [จัดการความไม่แน่นอน](/th/guide/quality/handle-uncertainty/) — ทำอย่างไรเมื่อโมเดลไม่แน่ใจ
- [นิยามของคำว่าเสร็จ](/th/guide/quality/definition-of-done/) — อะไรเรียกว่า “ทำเสร็จแล้ว”
- [การใช้งาน เวลา และการเลือกโมเดล](/th/guide/quality/usage-time-and-model-choice/)
- [การประเมินเวิร์กโฟลว์ด้วยตัวอย่าง 20 รายการ](/th/guide/quality/workflow-evaluation/)

## งานต่างกัน จุดตรวจต่างกัน

- **แก้โค้ด**: ดู diff เรียกการทดสอบ แล้วตรวจเส้นทางสำคัญด้วยมือ
- **เขียนเอกสาร**: ดูว่าเหมาะกับผู้อ่านเป้าหมายหรือไม่ ลิงก์ใช้ได้หรือไม่ และทำตามขั้นตอนได้จริงหรือไม่
- **ทำวิจัย**: ดูว่าแหล่งข้อมูลมีจริงและเป็นปัจจุบันหรือไม่ และข้อสรุปเกินหลักฐานหรือไม่
- **สร้างการกำหนดค่าหรือสคริปต์**: ดูข้อกำหนดสภาพแวดล้อม ขอบเขตสิทธิ์ และวิธีกู้คืนหลังล้มเหลว

หากไม่รู้ว่าจะเริ่มจากข้อใด ให้อ่าน [นิยามของคำว่าเสร็จ](/th/guide/quality/definition-of-done/) ก่อน

การตรวจสอบมีไว้เพื่อยืนยันว่าผลลัพธ์นี้ใช้ได้จริง กล้าใช้ และส่งมอบได้
