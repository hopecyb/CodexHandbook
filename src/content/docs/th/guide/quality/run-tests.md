หลังแก้แล้ว ต้องมีวิธียืนยันว่าไม่ได้เสียหายอย่างชัดเจน

“หลักฐาน” นี้อาจเป็นการทดสอบอัตโนมัติ การ build สำเร็จ หรือขั้นตอนตรวจด้วยมือที่ชัดเจน

## การทดสอบต้องตอบอะไร

การทดสอบตอบคำถามที่ตรงไปตรงมาว่า:

> **คุณรู้ได้อย่างไรว่าการเปลี่ยนแปลงครั้งนี้ไม่ได้ทำส่วนอื่นเสียไปด้วย**

หากไม่มีการตรวจ ผลลัพธ์สุดท้ายมักเพียง “ดูเกือบได้”

เขียนคำสั่งทดสอบไว้ในเกณฑ์ยอมรับของพรอมต์ หากรีโพซิทอรีไม่มีการทดสอบ อย่างน้อยให้กำหนดว่าคำสั่งเริ่มระบบหรือ build ต้องสำเร็จ หรือให้ขั้นตอนตรวจด้วยมือ

คำว่า “เสร็จ” โดยไม่มีการตรวจสอบมักเป็นเพียงความเห็นส่วนบุคคล

## ความเข้าใจผิดที่พบบ่อย

### 1. ไม่ใช่เฉพาะโปรแกรมเมอร์ที่ต้องสนใจการตรวจสอบ

แม้งานหลักคือแก้เอกสาร หน้าเว็บ การกำหนดค่า หรือเนื้อหา ก็ต้องมีวิธีตรวจที่ตรงกัน

### 2. แม้รีโพซิทอรีไม่มีการทดสอบ ก็ยังต้องยอมรับงาน

หากไม่มีการทดสอบอัตโนมัติ ให้เพิ่มอย่างน้อยหนึ่งอย่าง:

- build สำเร็จ
- เริ่มระบบสำเร็จ
- ขั้นตอนตรวจด้วยมือที่ชัดเจน

### 3. “แก้เพียงเล็กน้อย” ก็ข้ามการตรวจไม่ได้โดยอัตโนมัติ

การแก้เล็กอาจมีผลข้างเคียง โดยเฉพาะเมื่อคุณยังไม่คุ้นโปรเจกต์

## ลำดับการตรวจสอบ

หากยังไม่รู้ว่าจะเริ่มที่ใด ให้ทำตามลำดับนี้:

1. หากมีการทดสอบที่เกี่ยวข้อง ให้เรียกก่อน
2. หากไม่มีการทดสอบ ให้ build หรือเริ่มระบบ
3. หากยังไม่พอ ให้เพิ่มขั้นตอนตรวจด้วยมือขั้นต่ำ

เป้าหมายคือหลีกเลี่ยงการส่งมอบโดยไม่ตรวจเลย ไม่ใช่ทำ coverage ให้เต็มทั้งหมดในครั้งเดียว

## ประโยคที่ใส่ในพรอมต์ได้ทันที

ในงานแรก เติมประโยคนี้ได้:

```text
เมื่อเสร็จ โปรดเรียกการตรวจสอบที่เกี่ยวข้อง; หากไม่มีการทดสอบอัตโนมัติ ให้บอกขั้นตอนตรวจด้วยมือขั้นต่ำ
```

วิธีนี้ช่วยไม่ให้ข้ามการตรวจทั้งหมด แม้รีโพซิทอรีมีการทดสอบไม่สมบูรณ์

## เพิ่มอีกประโยคเมื่อจำเป็น

เติมได้ว่า:

```text
บอกฉันว่าคุณเรียกการตรวจสอบใดจริง; หากเรียกไม่ได้ ให้ระบุเหตุผลชัดเจนและอย่าถือว่าผ่านโดยอัตโนมัติ
```

การตรวจอาจเบาได้ แต่ขาดไม่ได้ มิฉะนั้นคำว่า “เสร็จ” จะยืนยันได้ยาก
