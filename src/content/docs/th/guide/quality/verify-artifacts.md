“อาร์ติแฟกต์” ในที่นี้หมายถึงเนื้อหาที่ส่งมอบเมื่อจบงาน เช่น:

- เอกสารหนึ่งฉบับ
- หน้าเว็บหนึ่งหน้า
- รูปภาพหนึ่งภาพ
- สเปรดชีตหนึ่งไฟล์
- ไฟล์ที่สร้างขึ้นหนึ่งไฟล์

อย่าถือว่าอาร์ติแฟกต์ถูกต้องเพียงเพราะโค้ดดูเหมือนถูก

## ทำไมต้องตรวจอาร์ติแฟกต์แยก

สิ่งส่งมอบของหลายงานไม่ได้มีเพียง code diff แต่รวมเนื้อหาที่ผู้ใช้จะเห็นและใช้จริง

เมื่อตรวจอาร์ติแฟกต์ มักต้องดูว่า:

- ผลลัพธ์สุดท้ายใช้ได้หรือไม่
- การนำเสนอตรงตามที่คาดหรือไม่
- เมื่อส่งให้คนอื่นจะดูขัด ผิด หรือไม่ครบหรือไม่

บางงานมีปัญหาที่ชั้นการนำเสนอสุดท้าย ไม่ใช่ชั้นโค้ด

ตัวอย่าง:

- โค้ดหน้าเว็บเรียกได้ แต่เลย์เอาต์ผิด
- โครงสร้างข้อความถูก แต่อ่านไม่เป็นธรรมชาติ
- รูปแบบลิงก์ถูก แต่ปลายทางผิด
- สร้างตารางแล้ว แต่ลำดับฟิลด์ไม่ตรงวิธีใช้งาน

ดังนั้น “สร้างแล้ว” ไม่ได้แปลว่า “ใช้ได้”

สำหรับอาร์ติแฟกต์ที่ไม่ใช่โค้ด ให้เปิดไฟล์ ตรวจลิงก์ เทียบดีไซน์ และอ่านเนื้อหาออกเสียง สำหรับหน้าเว็บ ให้ดูตัวอย่างในอุปกรณ์จริงหรือเบราว์เซอร์ ไม่ใช่ดูเพียงโค้ดที่สร้าง

## ตรวจตามประเภทอาร์ติแฟกต์

- **หน้าเว็บ**: ดูการ render จริง เลย์เอาต์ ลิงก์ และการโต้ตอบ
- **เอกสาร**: ดูโครงสร้าง คำศัพท์ ความอ่านง่าย และลิงก์
- **รูปภาพ**: ดูขนาด ความคมชัด ข้อความ และรายละเอียด
- **สเปรดชีตหรือไฟล์ส่งออก**: ดูฟิลด์ ลำดับ การเปิดได้ และความอ่านง่าย

## ความเข้าใจผิดที่พบบ่อย

### 1. build ผ่านไม่ได้แปลว่าหน้าเว็บไม่มีปัญหา

build ผ่านบอกเพียงว่า “สร้างได้” ไม่ได้บอกว่า “หน้าตาถูก เนื้อหาถูก และการโต้ตอบถูก”

### 2. เนื้อหาประเภทเอกสารก็ต้องตรวจเช่นกัน

ต้องตรวจ

โดยเฉพาะเรื่องเหล่านี้:

- ลำดับหัวข้อสมเหตุสมผลหรือไม่
- ลิงก์คลิกได้และถูกต้องหรือไม่
- คำศัพท์สอดคล้องกันหรือไม่
- เนื้อหาเป็นธรรมชาติและอ่านง่ายหรือไม่

### 3. ดูเพียงภาพหน้าจอยังไม่พอ

ภาพหน้าจอเหมาะกับการดูภาพรวมเร็ว ๆ แต่หลายปัญหาจะพบเมื่อเปิดไฟล์หรือหน้าเว็บจริงเท่านั้น

## ใช้ได้ทันที

ขอได้โดยตรงว่า:

```text
เมื่อเสร็จ โปรดตรวจด้วยมุมมองของอาร์ติแฟกต์สุดท้าย แล้วบอกว่าคุณเปิดตรวจอะไรจริง พบอะไร และยังไม่ได้ตรวจส่วนใด
```

## ลำดับการตรวจ

1. เปิดอาร์ติแฟกต์จริงก่อน
2. เทียบกับข้อกำหนดยอมรับทีละข้อ
3. ดูปัญหาเล็กด้านประสบการณ์ใช้งาน

เรียกได้บอกเพียงว่าพื้นฐานไม่เสีย ส่วนจะส่งมอบได้หรือไม่ต้องดูผลการใช้งานสุดท้าย
