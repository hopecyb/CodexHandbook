เวิร์กโฟลว์อาจเลือก Skill ถูกแต่เขียนข้อเท็จจริงผิด หรือผลลัพธ์อาจถูกแต่ดำเนินการที่ไม่ได้รับอนุญาต การรวมกรณีเหล่านี้เป็น “อัตราสำเร็จ” เดียวอาจซ่อนปัญหาที่ต้องแก้จริง

[ดาวน์โหลดชุดเครื่องมือประเมิน](/downloads/workflow-evaluation/workflow-evaluation-1.0.0.zip) · [ตัวอย่าง 20 รายการ](/downloads/workflow-evaluation/samples.json) · [บันทึกเปล่า](/downloads/workflow-evaluation/records-template.json)

## บันทึกข้อสังเกตห้าประเภทแยกกัน

| มิติ | ดูหลักฐานใด | ใช้อะไรแทนไม่ได้ |
|---|---|---|
| Trigger | ร่องรอยการเรียกจริง ตัวอย่างที่ควรและไม่ควร trigger | โทนเอาต์พุตคล้ายกัน หรือการเรียกแบบ explicit สำเร็จ |
| ขอบเขตและการปฏิเสธ | ไม่ทำคำขอเกินสิทธิ์ แต่ยังทำส่วนที่ถูกต้องให้ได้มากที่สุด | ปฏิเสธทุกงาน |
| รูปแบบ | ไฟล์ ฟิลด์ และ type ที่จำเป็น | ข้อความดูครบถ้วน |
| คุณภาพงาน | แหล่งข้อมูลรองรับทีละข้อ การคำนวณถูก การแก้มีผล และ coverage | JSON ถูกไวยากรณ์หรือสคริปต์คืน 0 |
| เวลาและงานแก้ซ้ำ | wall-clock time จริงและบันทึกงานแก้ซ้ำของคนแยกต่างหาก | ความรู้สึกว่า “เร็ว” หรือใส่ 0 ให้สิ่งที่ไม่ได้วัด |

สี่รายการแรกใช้ pass/partial/fail/not-applicable/unobserved ส่วนเวลาบันทึกเป็นตัวเลขแยก ต้องเก็บสถานะที่ไม่ทราบและยังไม่ได้เรียกไว้ ไม่เดาคะแนนล่วงหน้า มิติที่เรียกแล้วแต่สังเกตไม่ได้ให้ใช้ unobserved พร้อมเหตุผล; not-applicable ใช้เฉพาะมิติที่ไม่เกี่ยวข้องจริง ห้ามใช้ซ่อนสิ่งที่ไม่ได้สังเกต

## ตัวอย่างครอบคลุมอะไร

Skill สี่ประเภท ได้แก่ การตรวจทาน การเขียน การวิจัย และการเฝ้าดูลิงก์ มีประเภทละห้ารายการ: ตัวอย่าง trigger เชิงบวก งานที่ไม่เกี่ยวข้อง ขอบเขตสิทธิ์ รูปแบบเอาต์พุต และสถานการณ์คุณภาพสำคัญ รวม 20 รายการ ซึ่งผู้เขียนออกแบบไว้ทั้งหมด และบันทึกปัจจุบันเป็น `not-run` ทุกกรณี

สถานการณ์คุณภาพตรวจตามลำดับว่า ความผิดพลาดที่ stage ไว้ถูกการคืนค่าใน working tree บังหรือไม่ บทความทำความขัดแย้งของแหล่งข้อมูลหายหรือไม่ งานวิจัยละแหล่งข้อมูลที่เข้าถึงไม่ได้หรือไม่ และระบบเฝ้าดูแจ้งซ้ำหรือจัดการการกู้คืนหรือไม่ อินพุตใช้ [ชุด Skill สี่ประเภทฉบับเต็ม](/th/skills/examples/) ชุดประเมินไม่บรรจุซ้ำ จึงต้องบันทึกเวอร์ชันและ hash ที่ใช้เมื่อเรียก

## ทำการประเมินหนึ่งครั้งอย่างไร

1. ตรึงโมเดล ไคลเอนต์ การตั้งค่าการให้เหตุผล สิทธิ์เครื่องมือ คำอธิบายโปรเจกต์ และเวอร์ชันชุดอินพุต ค่าที่มองไม่เห็นให้บันทึกเป็นไม่ทราบ อย่าเดาค่าเบื้องหลัง
2. เปิดงานแยกสำหรับแต่ละตัวอย่าง และเก็บคำขอกับบันทึกเครื่องมือ การทดสอบ trigger ให้ใช้ภาษาธรรมชาติ โดยไม่เรียก `$skill` ชัดเจนล่วงหน้า; การทดสอบเรียกแบบ explicit เป็นการตรวจความสามารถในการทำงาน
3. เก็บทั้งความสำเร็จ ความล้มเหลว การหยุดชะงัก และการลองใหม่ ใช้ `interrupted` สำหรับการหยุดชะงัก และห้ามลบออกจากชุดตัวอย่าง
4. เขียนพาธหลักฐานและเหตุผลของแต่ละการตัดสิน ตัวอย่างความปลอดภัยใช้ข้อมูลสังเคราะห์และไม่ส่งข้อมูลจริง; สคริปต์รูปแบบช่วยตรวจฟิลด์เท่านั้น ส่วนคุณภาพข้อเท็จจริงยังต้องย้อนตรวจต้นฉบับ
5. หากทำได้ ให้ผู้ตรวจอีกคนซ่อนป้ายการกำหนดค่าแล้วให้คะแนน หากมีเพียงผู้เขียนตรวจเอง ให้ระบุตามจริง อย่าอ้างว่าเป็น blind review หรือข้อสรุปที่หลายคนเห็นตรงกัน

เมื่อใช้ร่วมกับ [การเปรียบเทียบพรอมต์สามชุด](/th/prompts/comparison-lab/) ให้ A/B ใช้เกณฑ์ให้คะแนนเดียวกัน อย่าให้คะแนน B สูงกว่าล่วงหน้าเพียงเพราะพรอมต์ยาวกว่า

## ตรวจว่าบันทึกครบหรือไม่

เรียกในชุดเครื่องมือด้วย Python 3.10+ standard library:

```sh
python3 scripts/check_records.py
python3 scripts/check_records.py --records my-records.json --evidence-root my-evidence
python3 validation/test_records.py
```

เทมเพลตเริ่มต้นจะรายงานว่ายังไม่เรียก 20 รายการ และ `performance_claim` เป็น null โดยไม่คำนวณเทมเพลตเป็นอัตราสำเร็จ

ตัวตรวจบันทึกตรวจว่าตัวอย่างไม่หาย รายการที่ยังไม่เรียกไม่มีคะแนนปลอม type ของเวลาถูกต้อง รายการที่เสร็จมีคะแนนและไฟล์หลักฐาน และพาธไม่ออกนอกขอบเขต แต่ไม่สามารถตัดสินว่า log เป็นของจริง คะแนนยุติธรรม หรือความหมายถูกต้อง บันทึกชั่วคราวในการทดสอบเป็นเพียง fixture ของ validator ไม่ใช่ข้อสังเกตจากโมเดล

## ตัดสินใจนำไปใช้อย่างไร

รายงานตัวหาร จำนวนความล้มเหลว จำนวนที่ไม่ทราบ และข้อผิดพลาดทั่วไป แยกตามเวิร์กโฟลว์ ประเภทตัวอย่าง และสภาพแวดล้อม ความล้มเหลวด้านขอบเขตความปลอดภัยใช้คะแนนสูงในมิติอื่นชดเชยไม่ได้ และข้อสรุปสำคัญที่ไม่มีหลักฐานก็ผ่านเพียงเพราะรูปแบบครบไม่ได้

กำหนดเงื่อนไขยอมรับตามความเสี่ยงของงานก่อนเรียก อย่าลดเกณฑ์ซ้ำหลังเห็นผล เมื่อแก้เวิร์กโฟลว์ ให้เรียกตัวอย่างที่ได้รับผลกระทบใหม่และเก็บบันทึกเก่า เพื่อแยกการแก้ปัญหาออกจากการรั่วของตัวอย่าง

ชุดเครื่องมือนี้ยังไม่มีผลประเมินโมเดลจริง สิ่งที่ให้คือวิธีประเมิน ตัวอย่าง และกลไกบันทึก ไม่ได้ให้ข้อสรุปว่า “โมเดลใดดีที่สุด” หรือ “อัตราสำเร็จเท่าใด”
