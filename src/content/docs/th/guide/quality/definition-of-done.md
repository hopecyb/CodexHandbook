“นิยามของคำว่าเสร็จ” หมายถึงการระบุล่วงหน้าว่าต้องทำถึงระดับใด งานครั้งนี้จึงจะถือว่าเสร็จจริง

หากไม่มีขั้นนี้ มักเกิดสถานการณ์ว่า:

- คุณคิดว่ายังขาดอีกเล็กน้อย
- Codex คิดว่าทำเสร็จแล้ว
- ทั้งสองฝ่ายไม่ได้ผิด เพียงใช้มาตรฐานไม่ตรงกัน

## ทำไมขั้นนี้จึงสำคัญ

งานแก้ซ้ำจำนวนมากเกิดจากไม่ได้กำหนดมาตรฐานคำว่า “เสร็จ” ให้ชัดตั้งแต่ต้น

ตัวอย่าง:

- แก้ข้อความก็พอ หรือต้องดูตัวอย่างหน้าเว็บให้ปกติด้วย
- build ผ่านก็พอ หรือต้องตรวจด้วยมือว่าปุ่มคลิกได้
- ฟีเจอร์ใช้ได้ก็พอ หรือต้องเพิ่มเอกสารอธิบายด้วย

หากไม่ระบุล่วงหน้า สุดท้ายแต่ละฝ่ายจะตีความต่างกันง่าย

ตัวอย่างนิยามขั้นต่ำสำหรับบุคคล:

- [ ] ตรวจ diff แล้ว
- [ ] ติ๊กเกณฑ์ยอมรับครบทุกข้อ
- [ ] ทดสอบหรือตรวจด้วยมือแล้ว
- [ ] ไม่มีคีย์เข้ารีโพซิทอรี
- [ ] บันทึกเรื่องที่ต้องติดตามแล้ว

เวอร์ชันสำหรับทีมจะขยายใน milestone ด้านการกำกับดูแลภายหลัง

## ความเข้าใจผิดที่พบบ่อย

### 1. นิยามของคำว่าเสร็จไม่จำเป็นต้องเป็นทางการหรือซับซ้อน

ช่วงแรกเขียนเพียงสามข้อก็มีประโยชน์:

- แก้ที่ใด
- ยอมรับอย่างไร
- กรณีใดถือว่ายังไม่เสร็จ

### 2. ไม่ใช่สิ่งเดียวกับ “เป้าหมาย”

แยกได้ดังนี้:

- **เป้าหมาย**: คุณต้องการผลลัพธ์ใด
- **นิยามของคำว่าเสร็จ**: พิสูจน์อย่างไรว่าบรรลุผลลัพธ์แล้ว

ตัวอย่าง:

- เป้าหมาย: แก้ข้อความปุ่มหน้าแรก
- นิยามของคำว่าเสร็จ: แก้เฉพาะหน้าแรก; ข้อความปุ่มเป็นเวอร์ชันใหม่; ตัวอย่างหน้าแสดงผลปกติ

### 3. ไม่ต้องเขียนยาวทุกครั้ง

ไม่ต้อง

ความชัดเจนสำคัญกว่าความยาว

## เทมเพลตย่อ

เริ่มจากเวอร์ชันนี้ได้:

```text
เกณฑ์ว่าเสร็จ:
1. แก้เฉพาะขอบเขตที่ระบุ
2. ผลลัพธ์ตรงตามข้อกำหนดที่ฉันให้
3. ทำขั้นตอนตรวจสอบเสร็จ และบอกฉันว่าตรวจอย่างไร
```

“นิยามของคำว่าเสร็จ” ทำให้ชัดว่าต้องไปถึงระดับใดจึงถือว่าทำเสร็จ เพื่อไม่ให้วิจารณญาณของคุณกับ Codex ไม่ตรงกัน
