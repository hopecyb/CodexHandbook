IDE เหมาะกับการอ่านสรุปและ diff ที่โฟกัสได้รวดเร็วข้างซอร์สโค้ด แต่ “การเปลี่ยนแปลงปรากฏในเอดิเตอร์” ไม่ได้แปลว่าผ่านการยอมรับแล้ว ให้ตรวจ diff ก่อน เรียกการทดสอบ แล้วจึงตัดสินใจว่าจะเก็บส่วนใด

## ตรวจงานในเครื่องให้ครบหนึ่งรอบ

1. อ่านสรุปผล แต่อย่าใช้สรุปแทน diff
2. ขยาย changed lines แล้วตรวจทุกไฟล์ที่ได้รับผลกระทบ
3. เก็บการแก้ไขที่ต้องการ และขอให้แก้ต่อสำหรับส่วนที่เกินขอบเขต
4. เรียก `/review` ในช่องป้อนข้อความ
5. เลือกเปรียบเทียบกับ base branch หรือตรวจการเปลี่ยนแปลงที่ยังไม่ได้ commit
6. เรียกการทดสอบและการตรวจแบบสแตติกของโปรเจกต์ในเทอร์มินัล IDE
7. ยืนยันสถานะอีกครั้งด้วยเครื่องมือ Git

`/review` จะแสดงเฉพาะเมื่อโปรเจกต์ที่เปิดเป็น Git repository โดยรายงานปัญหาเรียงตามลำดับความสำคัญและไม่แก้ working tree ใน IDE เลือกได้ว่า:

- **Review against a base branch**: เปรียบเทียบ branch ปัจจุบันกับ base branch ที่เลือก
- **Review uncommitted changes**: ตรวจการเปลี่ยนแปลงใน working tree ปัจจุบัน

ค่าเริ่มต้นจะแสดงผลในแชตปัจจุบัน ตั้ง `chatgpt.reviewDelivery` เป็น `detached` เพื่อเริ่มแชตตรวจทานแยกต่างหาก

## ตัวอย่าง: กำหนดเกณฑ์ให้ reviewer ชัดเจน

```text
ตรวจการเปลี่ยนแปลงปัจจุบันที่ยังไม่ได้ commit ให้เน้นหาข้อบกพร่องที่ทำให้พฤติกรรมผิด ข้อมูลเสียหาย หรือเกิดปัญหาความปลอดภัย
ไม่ต้องรายงานความชอบด้านสไตล์ล้วน ๆ ทุกข้อที่พบต้องระบุตำแหน่งไฟล์ เงื่อนไขกระตุ้น และผลกระทบที่ตรวจสอบได้
หากไม่พบปัญหา ให้ระบุช่องว่างการทดสอบที่ยังเหลือ
```

## เช็กลิสต์ยอมรับงาน

- [ ] ไฟล์ที่เปลี่ยนตรงกับขอบเขตที่งานอนุญาต
- [ ] ไม่มีการลบโดยไม่ตั้งใจ การฟอร์แมตทั้งไฟล์ หรือไฟล์ละเอียดอ่อน
- [ ] ครอบคลุมเส้นทางความล้มเหลวและกรณีขอบ
- [ ] การทดสอบ lint และ type check ผ่านตามข้อกำหนดโปรเจกต์
- [ ] แก้ข้อค้นพบสำคัญจาก reviewer แล้ว หรือยอมรับความเสี่ยงอย่างชัดเจน
- [ ] ผล `git diff --check` และ `git status --short` ปกติ

หากต้องแสดงความคิดเห็นรายบรรทัด stage หรือเลิกทำเป็น hunk ให้ไปที่ [diff ความคิดเห็น และการตรวจทาน](/th/guide/desktop-app/diffs-comments-and-review/) ในเดสก์ท็อป App ดูวิธีทั่วไปที่ [ตรวจ diff](/th/guide/quality/review-diffs/)
