“บริบทระดับโปรเจกต์” คือข้อมูลพื้นฐานที่คงที่ในระยะยาวและใช้ซ้ำกับหลายงานในโปรเจกต์นี้

ตัวอย่างเช่น:

- จัดโครงสร้างไดเรกทอรีอย่างไร
- ใช้คำสั่งใดเป็นประจำ
- มีข้อตกลงด้านสไตล์โค้ดอะไรบ้าง
- ไฟล์ใดไม่ควรแก้โดยพลการ
- หลังทำเสร็จต้องตรวจสอบด้วยวิธีใด

หากต้องอธิบายข้อมูลเหล่านี้ใหม่ทุกครั้ง นอกจากเหนื่อยแล้วยังตกหล่นได้ง่าย

## หมายถึงอะไรโดยเฉพาะ

บริบทระดับโปรเจกต์เปรียบเสมือนคำอธิบายว่า “โปรเจกต์นี้ทำงานร่วมกันตามค่าเริ่มต้นอย่างไรในระยะยาว”

บริบทนี้ไม่ได้อธิบายว่างานครั้งนี้ต้องทำอะไร แต่บอก Codex ล่วงหน้าว่า:

- โดยปกติ repository นี้จัดโครงสร้างอย่างไร
- แนวปฏิบัติใดมีผลในระยะยาว
- ขอบเขตใดไม่ควรแตะ
- โดยทั่วไปต้องตรวจสอบงานอย่างไรเมื่อเสร็จ

ด้วยวิธีนี้ ทุกครั้งที่ Codex เข้ามาในโปรเจกต์ ก็ไม่ต้องเดาแนวปฏิบัติของทีมใหม่ตั้งแต่ต้น

## ทำไมจึงเกิดปัญหาได้ง่าย

เมื่อเริ่มใช้ Codex หลายคนจะใส่ requirement ทั้งหมดไว้ในงานปัจจุบัน

ระยะสั้นอาจดูว่าใช้ได้ แต่ไม่นานจะเกิดปัญหาเหล่านี้:

- ต้องอธิบายใหม่ทุกครั้ง
- แต่ละงานใช้ถ้อยคำไม่เหมือนกัน
- กฎสำคัญบางข้อถูกลืม
- เมื่อบทสนทนายาว ภูมิหลังที่สำคัญจริงกลับไม่เด่น

แยกวิธีจัดการได้เป็นสองประเภท:

- ใส่ **กฎที่มีผลในระยะยาว** ไว้ในบริบทระดับโปรเจกต์
- เขียน **ข้อกำหนดเฉพาะของงานครั้งนี้** ไว้ในพรอมต์ปัจจุบัน

## แยกจากงานปัจจุบันอย่างไร

วิธีแบ่งที่ง่ายที่สุดมีสองชั้น:

- **บริบทระดับโปรเจกต์**: โดยปกติโปรเจกต์นี้ทำงานด้วยวิธีนี้
- **พรอมต์ของงาน**: ครั้งนี้ต้องการให้ทำอะไรโดยเฉพาะ

ตัวอย่าง:

- “เก็บคอมโพเนนต์ทั้งหมดไว้ใน `src/components/`” -> บริบทระดับโปรเจกต์
- “ครั้งนี้แก้เฉพาะข้อความ banner บนหน้าแรก” -> งานปัจจุบัน

## ความเข้าใจผิดที่พบบ่อย

### 1. ยิ่งเขียนบริบทระดับโปรเจกต์มากยิ่งดีหรือไม่

ข้อมูลที่มีคุณค่าจริงต้อง:

- มีผลในระยะยาว
- ใช้ซ้ำในหลายงาน
- หากไม่ระบุจะเกิดข้อผิดพลาดได้ง่าย

หากใส่รายละเอียดที่ใช้ครั้งเดียวทั้งหมด คำอธิบายโปรเจกต์เองก็จะกลายเป็นข้อมูลรบกวน

### 2. หากอธิบายในแต่ละงานชัดแล้ว ก็ไม่ต้องมีบริบทระดับโปรเจกต์

ระยะสั้นทำได้ แต่ระยะยาวจะเหนื่อยมาก

คุณจะพบปัญหาเหล่านี้อย่างรวดเร็ว:

- ต้องพูดซ้ำทุกครั้ง
- แต่ละงานเขียนไม่เหมือนกัน
- งานนี้ระบุกฎแล้ว แต่งานครั้งหน้าลืม

### 3. บริบทระดับโปรเจกต์จะจำกัดมากเกินไปหรือไม่

ไม่ หากมองว่าเป็นกฎเริ่มต้นระยะยาว ไม่ใช่คำสั่งตายตัวที่แก้ไม่ได้

ข้อกำหนดพิเศษจริงยังควรเขียนไว้ในงานปัจจุบัน

## ตำแหน่งที่ใช้บ่อย

ใส่ข้อตกลงที่คงที่ไว้ในคำอธิบายโปรเจกต์ เช่น `AGENTS.md` หรือคำสั่งระดับโปรเจกต์ที่ผลิตภัณฑ์รองรับ:

- โครงสร้างไดเรกทอรี
- คำสั่งที่ใช้บ่อย
- สไตล์โค้ด
- สิ่งต้องห้าม

พรอมต์ของงานควรเขียนเฉพาะ **ความแตกต่างของครั้งนี้** ส่วนภูมิหลังยาวที่ใช้ซ้ำให้ย้ายไปไว้ระดับโปรเจกต์ รายละเอียดเชิงลึกด้านการตั้งค่าอยู่ใน milestone `06-customization` ถัดไป

## ตัดสินอย่างไรว่าควรใส่ในบริบทระดับโปรเจกต์

หากคำอธิบายหนึ่งตรงตามสองเงื่อนไขนี้ ก็ควรพิจารณาใส่ไว้ในบริบทระดับโปรเจกต์:

1. ครั้งหน้ามีโอกาสสูงว่าจะใช้อีก
2. หากลืมจะเกิดข้อผิดพลาดซ้ำหรือเสียเวลา

## ควรจัดเก็บอะไรก่อน

โดยทั่วไปให้จัดเก็บข้อมูลประเภทต่อไปนี้ก่อน:

- คำสั่งที่ใช้บ่อย
- ข้อตกลงเรื่องไดเรกทอรี
- สไตล์โค้ด
- พื้นที่ห้ามแก้
- วิธีตรวจสอบตามค่าเริ่มต้น

คำอธิบายใดที่ครั้งหน้ามีโอกาสสูงว่าจะใช้อีก ก็ควรย้ายไปไว้ในบริบทระดับโปรเจกต์ ไม่ต้องพิมพ์ใหม่ทุกครั้ง
