“การย่อบริบท” หมายถึง เมื่อบทสนทนายาวเกินไป ระบบจะย่อเนื้อหาก่อนหน้าเป็นฉบับสั้นแล้วเก็บไว้เพื่อทำงานต่อ จุดประสงค์คือให้งานดำเนินต่อได้ แต่สิ่งที่ต้องแลกคือ **รายละเอียดบางส่วนอาจหายไป**

## ทำไมจึงกระทบผลลัพธ์

ผู้เริ่มต้นจำนวนมากมักคิดว่า:

“เมื่อพูดไปแล้ว Codex ก็ควรจำได้ครบถ้วนตลอด”

ความจริงไม่เป็นเช่นนั้นเสมอไป  
เมื่องานยาวเข้าสู่การย่อบริบท รายละเอียดต่อไปนี้มักสูญหายได้ง่ายกว่า:

- ข้อจำกัดย่อยที่ละเอียดมาก
- ข้อยกเว้นชั่วคราวแต่สำคัญ
- รายการไฟล์ที่อนุญาตซึ่งคุณระบุไว้ก่อนหน้า
- เงื่อนไขย่อยในเกณฑ์การยอมรับ

ดังนั้น การย่อบริบทไม่ใช่ข้อผิดพลาด แต่เป็นกลไกที่ต้องอาศัยความร่วมมือจากคุณ

## หลังย่อบริบทควรย้ำอะไรที่สุด

การย่ออาจทำรายละเอียดหาย ควร **ย้ำอีกครั้ง** ถึงข้อจำกัดสำคัญ เกณฑ์การยอมรับ และรายการไฟล์ที่อนุญาต หรือบันทึกไว้ในคำอธิบายโปรเจกต์

ควรย้ำข้อมูลประเภทต่อไปนี้ก่อน:

- อนุญาตให้แก้ไฟล์ใดบ้าง
- ห้ามแตะเนื้อหาใดโดยเด็ดขาด
- เกณฑ์ว่าเสร็จคืออะไร
- ขณะนี้ทำถึงขั้นตอนไหนแล้ว

## ความเข้าใจผิดที่พบบ่อย

### 1. การย่อหมายความว่า “Codex ลืมทุกอย่าง” หรือไม่

พูดให้แม่นยำกว่าคือ ระบบจะเก็บแกนหลักไว้ แต่ไม่รับประกันว่ารายละเอียดย่อยทั้งหมดจะคงอยู่เหมือนเดิม

### 2. ไม่ต้องเล่าใหม่ทั้งหมดทุกครั้ง

ไม่จำเป็น

โดยทั่วไป แค่ย้ำส่วนที่สำคัญที่สุด สูญหายง่ายที่สุด และผิดไม่ได้ก็เพียงพอ

### 3. ข้อมูลใดไม่ควรเสี่ยงคิดว่า Codex “น่าจะยังจำได้”

โดยทั่วไปคือข้อมูลเหล่านี้:

- ขอบเขตไฟล์
- สิ่งต้องห้าม
- เกณฑ์การยอมรับ
- การตัดสินใจสำคัญที่คุณยืนยันแล้ว

## วิธีแก้หลังย่อบริบท

หากงานยาวมากแล้ว คุณสามารถเขียนสรุปสั้น ๆ ระหว่างทางได้ เช่น:

```text
ข้อจำกัดที่ยังมีผล:
1. แก้เฉพาะไดเรกทอรี docs
2. ห้ามปรับโครงสร้าง routing
3. เกณฑ์ว่าเสร็จคือข้อความหน้าแรกได้รับการอัปเดตและ build ผ่าน
```

วิธีนี้มั่นคงกว่าการพึ่งบทสนทนายาวทั้งหมดต่อไป

แนวคิดพื้นฐาน: [โทเค็น บริบท และการย่อบริบท](/th/guide/foundations/tokens-context-and-compaction/)

สำหรับงานยาว อย่าระบุข้อจำกัดสำคัญเพียงครั้งเดียว หลังย่อบริบทควรย้ำกฎสำคัญอีกครั้งอย่างชัดเจน
