เนื้อหาใดก็ตามที่คุณไม่ต้องการให้ผู้อื่นเห็น คัดลอก ส่งต่อ หรือเก็บไว้ในประวัติงานระยะยาว ควรถือเป็นข้อมูลละเอียดอ่อนตั้งแต่แรก

## ทำไมต้องประเมินก่อน

ปัญหาด้านความปลอดภัยจำนวนมากไม่ได้เกิดจากการจงใจฝ่าฝืน แต่เกิดจากตอนนั้นคิดเพียงว่า “แก้ปัญหาให้เสร็จก่อน”

ตัวอย่างเช่น:

- วางไฟล์ `.env` ทั้งไฟล์เพื่อ debug
- วางข้อมูลดิบของลูกค้าเพื่อให้ Codex เข้าใจ
- เพื่อความสะดวก จึงวางข้อความ error ที่มี token จริงแบบไม่แก้ไข

วิธีเหล่านี้อาจดูสะดวกในขณะนั้น แต่ภายหลังมักแก้ไขได้ยากที่สุด

อย่าส่งข้อมูลต่อไปนี้ให้ Codex ไม่ว่าจะใช้ฝึกหรือใช้ใน production:

- API key รหัสผ่าน และ session Cookie
- ข้อมูลลูกค้าที่ยังไม่ปกปิด หมายเลขบัตรประชาชน และข้อมูลลักษณะเดียวกัน
- เอกสารภายในที่ยังไม่เปิดเผยและสัญญาห้ามส่งต่อ

ใช้ placeholder เช่น `YOUR_API_KEY` หากข้อมูลรั่วไหลแล้ว ให้หมุนเวียนคีย์ตามกระบวนการขององค์กร

## หากไม่แน่ใจ ควรประเมินอย่างไร

หากไม่แน่ใจว่าเนื้อหาบางส่วนละเอียดอ่อนหรือไม่ ให้ถามตัวเองสองข้อก่อน:

1. หากคนที่ไม่เกี่ยวข้องเห็นเนื้อหานี้ จะมีความเสี่ยงหรือไม่
2. หากเนื้อหานี้อยู่ในประวัติงานระยะยาว ฉันจะกังวลหรือไม่

หากตอบว่า “ใช่” แม้เพียงข้อเดียว ให้จัดการเป็นข้อมูลละเอียดอ่อนก่อน

## อย่าพึ่งคำว่า “น่าจะไม่เป็นไร”

เมื่อใช้ AI ที่เรียกเครื่องมือได้เป็นครั้งแรก หลายคนมักคิดว่า:

- “ฉันแค่วางไว้ชั่วคราว”
- “Codex แค่ช่วยดูให้”
- “ไฟล์นี้คงไม่ได้ถูกส่งออกไปจริง”

แต่ทันทีที่ข้อมูลเข้าสู่กระบวนการของงาน ก็ควรจัดการเป็นข้อมูลละเอียดอ่อน การควบคุมความปลอดภัยควรทำล่วงหน้า

## เนื้อหาที่มักถูกมองข้าม

นอกจากรหัสผ่านและคีย์แล้ว สิ่งต่อไปนี้ก็มักเป็นข้อมูลละเอียดอ่อน:

- รายชื่อลูกค้า
- หมายเลขโทรศัพท์ อีเมล และหมายเลขบัตรประชาชน
- ภาพหน้าจอภายในและแผนงานที่ยังไม่เผยแพร่
- ไฟล์การตั้งค่าที่มีที่อยู่ production หรือ access token จริง

กล่าวคือ ข้อมูลละเอียดอ่อนไม่ได้มีเพียงคีย์รูปแบบ `sk-...`

## ต้องปกปิดข้อมูลแค่ไหนจึงเพียงพอ

ไม่จำเป็นต้องลบข้อมูลทั้งหมด แต่ต้องเก็บไว้เฉพาะ “ข้อมูลขั้นต่ำที่จำเป็นต่อการแก้ปัญหา”

ใช้แนวทางนี้:

- คงโครงสร้างไว้
- แทนค่าจริง
- ลบข้อมูลระบุตัวตน
- ลบ field ที่ไม่เกี่ยวข้องกับปัญหาปัจจุบัน

ตัวอย่างข้อมูลที่เก็บไว้ได้:

- ชื่อ field
- ประเภท error
- ลำดับการเรียก

แต่ให้แทนข้อมูลต่อไปนี้:

- คีย์จริง
- อีเมลจริง
- หมายเลขโทรศัพท์จริง
- ชื่อลูกค้าจริง

## หากจำเป็นต้องให้ข้อมูล ทำอย่างไรจึงปลอดภัยกว่า

แนวทางที่ปลอดภัยกว่า:

- แทนคีย์ด้วยค่าปลอมหรือ placeholder
- ปกปิดข้อมูลผู้ใช้จริง
- เก็บเฉพาะ field ที่จำเป็นจริงต่อการตรวจปัญหา
- หากอธิบายอาการได้ ให้หลีกเลี่ยงการวางข้อมูลดิบที่ละเอียดอ่อนทั้งส่วน

ตัวอย่าง:

```text
แทน API Key จริงด้วย YOUR_API_KEY และแทนอีเมลจริงด้วย user@example.com
```

## หากส่งข้อมูลออกไปโดยไม่ตั้งใจแล้ว

จัดการตามระดับความเสี่ยง:

1. หยุดการกระจายต่อทันที
2. หมุนเวียนคีย์ รหัสผ่าน หรือ token ทันที
3. รายงานและแก้ไขตามกระบวนการขององค์กร

เมื่อแก้ปัญหา ให้ส่งเฉพาะ “ข้อมูลขั้นต่ำที่จำเป็นต่อการตรวจปัญหา” เป็นค่าเริ่มต้น ปกปิดได้ให้ปกปิด แทนด้วย placeholder ได้ให้แทน
