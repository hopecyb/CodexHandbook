นี่ไม่ใช่เทมเพลตพรอมป์ที่เพียงเปลี่ยนชื่อไฟล์แล้วถือว่าเสร็จ คุณจะใช้โค้ดเริ่มต้นจริงใน repository เห็นการทดสอบล้มเหลวหนึ่งรายการก่อน แล้วตรวจว่าการแก้อ้างอิงทำให้การทดสอบชุดเดิมผ่านได้อย่างไร

## ข้อมูลเมตา

| ฟิลด์ | เนื้อหา |
|---|---|
| ผู้อ่านที่เหมาะสม | นักพัฒนา |
| ไคลเอนต์ | CLI หรือ IDE (repository ในเครื่อง) |
| เวลาโดยประมาณ | 25–45 นาที |
| ความรู้เบื้องต้น | รันคำสั่ง Node.js หนึ่งคำสั่งใน terminal ได้ และอ่าน JavaScript พื้นฐานได้ |
| dependency ของตัวอย่าง | `node:test` ที่มากับ Node.js ไม่ต้องติดตั้งแพ็กเกจภายนอก |
| วันที่ยืนยัน | 2026-08-25 |

## 1. เป้าหมายและบริบท

**บริบทธุรกิจ:** `calculateTotal` ของรถเข็นรับเปอร์เซ็นต์ส่วนลด เมื่อไม่มีส่วนลดผลลัพธ์ถูกต้อง แต่เมื่อส่ง `10` เพื่อหมายถึงลด 10% ฟังก์ชันกลับนำ `10` ไปคูณเป็นอัตราส่วนโดยตรง จึงได้ค่าติดลบ

**เป้าหมาย:** หาเหตุคำนวณส่วนลดผิด แก้ให้น้อยที่สุด และใช้การทดสอบชุดเดิมพิสูจน์ว่าปัญหาเปลี่ยนจากไฟแดงเป็นไฟเขียว

**เกณฑ์ความสำเร็จ:**

- การทดสอบเริ่มต้นล้มเหลวอย่างเสถียร 1 รายการ โดย assertion แสดง “คาดหวัง 36 แต่ได้ -360”
- หลังแก้ การทดสอบทั้ง 3 รายการผ่าน
- การแก้เปลี่ยนเฉพาะการแปลงเปอร์เซ็นต์ส่วนลด และไม่เขียน API รถเข็นใหม่
- อธิบายได้ว่าเหตุใดต้องเก็บ “ไฟเขียวหลังแก้” คู่กับ “ไฟแดงก่อนแก้”

**นอกขอบเขต:** library ความแม่นยำด้านการเงิน ภาษี การแปลงสกุลเงิน การอัปเกรด dependency และ UI

![เวิร์กโฟลว์แก้ Bug พร้อมการยืนยันผล](/illustrations/flow-bug-fix.webp)

สิ่งสำคัญที่สุดในภาพคือเส้นทางย้อนกลับสองเส้น: เมื่อการทดสอบที่เกี่ยวข้องล้มเหลว ให้กลับไปแก้ขั้นต่ำ เมื่อ regression ทั้งชุดหรือการตรวจ diff ล้มเหลว ให้กลับไปวิเคราะห์สาเหตุต้นตอ อย่าลบ assertion หรือขยายการแก้เพียงเพื่อให้เขียวเร็วขึ้น

## 2. สื่อเตรียมพร้อม

หากต้องการลำดับเรียนแบบเต็ม ให้ใช้[เส้นทางนักพัฒนา](/th/guide/learning-paths/developer/) ซึ่งเชื่อมแบบฝึกนี้กับการอ่านโค้ด การตรวจ และเทมเพลตส่งต่องาน พร้อมกำหนดให้ฝึกในสำเนา `work/` แยกต่างหาก [สรุปการรัน 2026-09-18](/downloads/developer-path/run-record.json) ที่เพิ่มใหม่บันทึกการยืนยันจุดเริ่มและคำตอบอีกครั้ง ส่วนวันที่ 2026-08-25 ด้านล่างคือวันที่ยืนยันกรณีเดิม

ไดเรกทอรีตัวอย่าง:

```text
examples/complete-workflows/developer/verified-bug-fix/
├── brief.md
├── starter/
│   ├── cart.js
│   └── cart.test.js
├── prompts/
│   ├── 01-explore.md
│   ├── 02-fix-and-verify.md
│   └── 03-review.md
├── solution/
│   ├── cart.js
│   └── cart.test.js
└── validation.md
```

`starter/` คือจุดเริ่มฝึกและจงใจมี Bug หนึ่งรายการ ส่วน `solution/` คือคำตอบอ้างอิงที่รันแยกได้ อย่าฝึกโดยแก้บนคำตอบอ้างอิงโดยตรง

## 3. ขั้นแรก: ทำซ้ำไฟแดง

รันที่รากของ repository:

```bash
node --test examples/complete-workflows/developer/verified-bug-fix/starter/cart.test.js
```

ผลที่คาด: คำสั่งออกด้วยสถานะไม่เป็นศูนย์ และการทดสอบ 1 จาก 3 รายการล้มเหลว หลักฐานสำคัญมีลักษณะดังนี้:

```text
Expected values to be strictly equal:

-360 !== 36
```

หากการทดสอบไม่ล้มเหลว ให้หยุดก่อน ตรวจว่ารันจาก `starter/` ตรวจเวอร์ชัน Node.js และดูว่าไฟล์ถูกแก้ล่วงหน้าหรือไม่ หากไม่มีไฟแดงที่เสถียร ก็ไม่มีหลักฐานฐานของปัญหาเดิม

## 4. ขั้นที่สอง: สำรวจแบบอ่านอย่างเดียว

### สำรวจ

```text
ยังไม่ต้องแก้ไฟล์ อ่าน:
- examples/complete-workflows/developer/verified-bug-fix/starter/cart.js
- examples/complete-workflows/developer/verified-bug-fix/starter/cart.test.js

อธิบายไม่เกิน 6 ข้อ:
1. อินพุตใดทำให้ล้มเหลว
2. ค่าที่คาดหวังและค่าจริง
3. ความต่างระหว่างเปอร์เซ็นต์กับอัตราส่วนในสูตร
4. การแก้ขั้นต่ำควรอยู่ที่บรรทัดใด
5. พฤติกรรมสาธารณะใดห้ามเปลี่ยน
6. หลังแก้ต้องรันการยืนยันใดบ้าง
```

คำอธิบายสาเหตุต้นตอที่ผ่านเกณฑ์ควรระบุว่า ฝั่งเรียกส่ง `10` เพื่อหมายถึง 10% แต่ implementation คำนวณ `subtotal * 10` โดยตรง จึงขาดการหาร `100`

## 5. ขั้นที่สาม: วางแผนและลงมือแก้ขั้นต่ำ

```text
แก้เฉพาะการแปลงเปอร์เซ็นต์ส่วนลดใน starter/cart.js
ห้ามเปลี่ยนชื่อฟังก์ชัน พารามิเตอร์ assertion ของการทดสอบ หรือโครงสร้างไฟล์ และห้ามเพิ่ม dependency

หลังแก้ ให้ทำตามลำดับ:
1. รัน starter/cart.test.js
2. แสดงสรุปการทดสอบจริง
3. สรุปบรรทัดที่แก้และเหตุผล
4. ห้าม commit หรือ push Git
```

หัวใจของการแก้ขั้นต่ำคือ:

```js
const discount = subtotal * (discountPercent / 100);
```

อย่าเปลี่ยน `36` ในการทดสอบเป็น `-360` เพื่อให้ไฟเขียว เพราะนั่นเป็นเพียงการเขียนค่าที่คาดหวังใหม่ ไม่ได้แก้กฎธุรกิจ

## 6. ขั้นที่สี่: ยืนยันไฟเขียว

หากไม่ต้องการแก้จุดเริ่มฝึก คุณรันคำตอบอ้างอิงโดยตรงได้:

```bash
node --test examples/complete-workflows/developer/verified-bug-fix/solution/cart.test.js
```

ผลที่คาด: การทดสอบทั้ง 3 รายการผ่าน และโปรเซสออกด้วยสถานะ 0

บันทึกการยืนยันควรมีอย่างน้อย:

| หลักฐาน | คำถามที่ต้องตอบ |
|---|---|
| คำสั่งที่ล้มเหลวก่อนแก้ | ทำซ้ำปัญหาเดิมได้อย่างเสถียรหรือไม่ |
| assertion ที่ล้มเหลว | การทดสอบครอบคลุม Bug นี้จริงหรือไม่ |
| code diff | การเปลี่ยนแปลงแตะเฉพาะสาเหตุต้นตอหรือไม่ |
| การทดสอบที่เกี่ยวข้องหลังแก้ | พฤติกรรมเดียวกันถูกต้องแล้วหรือไม่ |
| การทดสอบขอบเขตกว้างขึ้น | ฟังก์ชันข้างเคียงเสียหรือไม่ |

ไดเรกทอรีแบบฝึกนี้มีการทดสอบเพียงชุดเดียว ในโปรเจกต์จริงยังต้องรัน lint, type check และการทดสอบทั้งชุดตาม `AGENTS.md`

## 7. ขั้นที่ห้า: Review

```text
ตรวจการแก้ครั้งนี้โดยไม่แก้ไฟล์ ให้แสดง findings ก่อน แล้วค่อยสรุป:
- แก้การแปลงเปอร์เซ็นต์จริงหรือเพียงผ่อนการทดสอบ
- เปลี่ยน function signature หรือตรรกะที่ไม่เกี่ยวข้องหรือไม่
- ครอบคลุมรถเข็นว่าง ไม่มีส่วนลด และส่วนลด 10% หรือไม่
- ยังมีความเสี่ยงด้านความแม่นยำของยอดเงินใดที่อยู่นอกขอบเขตกรณีนี้
```

คนยังต้องยืนยันว่าไม่มี dependency เพิ่มเติม log สำหรับ debug การ format ทั้งไฟล์ หรือการดำเนินการ Git

## 8. ความล้มเหลวและการกู้คืน

| ปัญหา | วิธีจัดการ |
|---|---|
| การทดสอบเริ่มต้นไม่ล้มเหลว | ยืนยันว่ารัน `starter/cart.test.js` และคืนจุดเริ่มที่ยังไม่แก้ |
| แก้การทดสอบแล้วจึงเขียว | คืน assertion ของการทดสอบ แล้วแก้เฉพาะการแปลงเปอร์เซ็นต์ใน implementation |
| การทดสอบที่เกี่ยวข้องยังล้มเหลว | เปรียบเทียบค่าที่ล้มเหลว และตรวจว่าวาง `/ 100` ผิดตำแหน่งหรือไม่ |
| การทดสอบทั้งชุดมีความล้มเหลวใหม่ | กลับไปวิเคราะห์สาเหตุต้นตอ แล้วตรวจพฤติกรรมสาธารณะและขอบเขตการเปลี่ยนแปลง |
| การทดสอบล้มเหลวเป็นครั้งคราว | ทำให้สภาพแวดล้อมทดสอบเสถียรก่อน ห้ามใช้ไฟเขียวครั้งเดียวเป็นหลักฐาน |

## 9. ย้ายจากแบบฝึกไปยัง repository จริง

เปลี่ยนพาธตัวอย่างเป็นไฟล์ของคุณ แต่คงโครงสร้างหลักฐานไว้:

```text
เป้าหมาย: แก้【พฤติกรรมผิดที่สังเกตได้】
คำสั่งทำซ้ำ: 【คำสั่งที่แน่นอน】 ปัจจุบันล้มเหลวอย่างเสถียรที่【assertion สำคัญ】
ขอบเขต: แก้เฉพาะ【ไฟล์ implementation】และการทดสอบที่จำเป็น ห้าม refactor หรืออัปเกรด dependency
การยอมรับ: การทดสอบเดิมที่ล้มเหลวผ่าน การทดสอบขอบเขตใหม่ผ่าน 【คำสั่งทั้งชุด】ผ่าน และ diff ไม่มีการเปลี่ยนแปลงที่ไม่เกี่ยวข้อง
สิทธิ์: ห้าม push เผยแพร่ หรือแก้ข้อมูล production หากต้องใช้สิทธิ์เพิ่มเติม ให้หยุดและอธิบายก่อน
เริ่มจากระบุต้นเหตุและความเสี่ยงแบบอ่านอย่างเดียว รอฉันยืนยันแผนแล้วค่อยแก้
```

## 10. เก็บเป็นความรู้ใช้ซ้ำ

- หาก bug ประเภทนี้เกิดซ้ำ ให้เพิ่มข้อตกลงหนึ่งข้อใน `AGENTS.md`
- สกัดเป็น Skill `regression-guard` ได้ โดยบังคับให้บันทึกหลักฐานไฟแดง ไฟเขียว และ regression
- เพิ่มการทดสอบขอบเขตที่เกิดบ่อยเข้า CI แทนการเก็บไว้เฉพาะในบทสนทนา
