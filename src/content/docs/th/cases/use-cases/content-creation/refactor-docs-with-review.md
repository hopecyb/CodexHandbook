กรณีนี้แสดงงานประเภท **วิศวกรรมเนื้อหา** ได้แก่ Markdown หลายไฟล์ การตั้งค่า sidebar และการยืนยันด้วย build แม้ tech stack จะคล้ายคู่มือนี้ แต่สถานการณ์นำไปใช้กับเว็บไซต์ static ใดก็ได้

## ข้อมูลเมตา

| รายการ | ค่า |
|---|---|
| ด้านงาน | การสร้างเนื้อหา / วิศวกรรมเอกสาร |
| ทางเข้า | CLI หรือ IDE |
| ความเสี่ยง | ปานกลาง (ลิงก์และ navigation จำนวนมาก) |
| ระยะเวลา | 1～3 ชั่วโมง (ขึ้นอยู่กับขนาด) |

คำอธิบายเทมเพลต: [เทมเพลตกรณีศึกษา](/th/cases/use-cases/case-study-template/)

## บริบท

หลังเพิ่มบทใหม่ในเว็บไซต์เอกสาร ต้องทำดังนี้:

1. อัปเดต slug ของ sidebar ใน `astro.config`
2. แก้ relative link ในเนื้อหา
3. ให้ `npm run build` ผ่านโดยไม่มีข้อผิดพลาด

คนมักตกหล่น slug งานนี้จึงเหมาะให้ Agent **ทำตาม checklist + ยอมรับด้วย build**

## การเตรียมพร้อม

- [ ] git branch สะอาด
- [ ] รัน `npm run build` ในเครื่องได้
- [ ] แสดงพาธหน้าใหม่และตำแหน่งเป้าหมายใน sidebar

## พรอมป์งาน (ตัวอย่าง)

```text
เป้าหมาย: เพิ่ม environment-variables.md ใน 12-reference และเชื่อมเข้ากับ sidebar และลิงก์ใน index
ข้อจำกัด: แก้เฉพาะ src/content/docs และ astro.config.mjs ห้ามอัปเกรด dependency
การยอมรับ: npm run build สำเร็จ และไม่มี dead link
ขั้นตอน: แก้ config ก่อน แล้วเขียน md สุดท้ายอัปเดต 12-reference/index.md
```

## จุดสำคัญในการลงมือ

- **config ก่อนเนื้อหา**: ป้องกัน build แจ้ง missing slug
- commit ครั้งละ 3～5 ไฟล์เพื่อให้ review ง่าย
- ใช้ [สำรวจ—วางแผน—ลงมือ—ยืนยันผล](/th/cases/workflows/explore-plan-execute-verify/)

## การตรวจ

- [ ] slug ทุกรายการใน sidebar มีไฟล์ตรงกัน
- [ ] ลิงก์ภายในเว็บไซต์ใช้รูปแบบ relative path ตามมาตรฐาน
- [ ] log ของ build ไม่มีคำเตือน Starlight (หากทีมกำหนดให้ไม่มีคำเตือน)

## การกู้คืนเมื่อผิดพลาด

| ปัญหา | วิธีจัดการ |
|---|---|
| Sidebar แจ้ง slug ผิด | เทียบเอกสาร Astro แล้วแก้ slug หรือเพิ่ม md |
| dead link | ใช้ `grep` หาพาธเป้าหมาย แล้วแก้ลิงก์หรือเพิ่มหน้า |
| build OOM | แบ่งแก้เป็นชุด และเพิ่มหน่วยความจำ Node ในเครื่อง |

## ทบทวน

- เมื่อทำงานประเภท “บทใหม่ + sidebar” เป็นครั้งที่สาม ควรจัดเป็น Skill
- ทำเครื่องหมายรายการที่เสร็จใน ROADMAP เพื่อไม่ให้เอกสารกับแผนไม่ตรงกัน
