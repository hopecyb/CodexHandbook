**ระดมความคิดก่อนลงมือ** เหมาะกับงานที่เป้าหมายยังคลุมเครือหรือมีมากกว่าหนึ่งแนวทาง เช่น ฟีเจอร์ใหม่ การออกแบบใหม่ การเลือกหัวข้อเนื้อหา และการเลือกเทคโนโลยี วิธีนี้เชื่อมกับช่วง ① สำรวจของ [สำรวจ—วางแผน—ลงมือ—ยืนยันผล](/th/cases/workflows/explore-plan-execute-verify/) แต่เน้น **ขยายและคัดทางเลือก** มากกว่าการอ่านโค้ดแล้วแก้ไฟล์ทันที

## หน้านี้แก้ปัญหาอะไร

- เมื่อใดควร brainstorm ก่อน และเมื่อใดควรเข้า EPXV ทันที
- จำกัดขอบเขตการแตกแนวคิดอย่างไรไม่ให้คุยลอย ๆ
- ผลงานที่ได้: ตารางทางเลือก บันทึกการตัดสินใจ และแผนขั้นถัดไป

## เหมาะกับใคร

| สถานการณ์ | ตัวอย่าง |
|---|---|
| ผลิตภัณฑ์/ฟีเจอร์ | “เพิ่มฟังก์ชัน export ให้ผู้ใช้ มี UI ได้สามแบบ” |
| เนื้อหา | “บทเรียนนี้เขียนให้ใคร และควรแบ่งโครงอย่างไร” |
| เทคนิค | “ใช้ queue หรือ cron สำหรับงานตามกำหนดเวลา” |

## วิธีขั้นต่ำที่ใช้ได้

**ช่วง A — ขยายทางเลือก (จำกัดเวลา)**

```text
ยังไม่ต้องแก้ไฟล์ใด ๆ สำหรับข้อกำหนด “export CSV” ให้แสดงแนวทาง implementation 3 แบบ
แต่ละแบบระบุข้อดี ข้อเสีย โมดูลที่เกี่ยวข้อง และปริมาณงานโดยประมาณ (S/M/L)
ยังไม่ต้องเลือกแนวทางสุดท้าย
```

**ช่วง B — คัดแนวทาง**

```text
จากตารางด้านบน แนะนำแนวทางเริ่มต้น 1 แบบและทางเลือกสำรอง 1 แบบ
ระบุจุดตัดสินใจ 2 ข้อที่ต้องให้ฉันยืนยัน (รูปแบบและสิทธิ์)
```

**ช่วง C — เข้าสู่การวางแผน**

หลังยืนยันแล้ว ให้ต่อด้วย [งานที่ขับเคลื่อนด้วย specification](/th/cases/workflows/specification-driven-work/) หรือช่วง ② วางแผนของ EPXV

## เวิร์กโฟลว์ที่แนะนำ

```text
กำหนดข้อจำกัดให้ชัด (เวลา, tech stack, ส่วนที่ห้ามแก้)
    → ขยายเป็น 3–5 ทางเลือก (ห้ามเขียนโค้ด)
    → เรียงตาม “คุณค่า / ความเสี่ยง / ต้นทุน”
    → คนเลือกทิศทางหรือขอข้อมูลเพิ่ม
    → แผนลายลักษณ์อักษร + ลงมือ
```

กำหนด **timebox** เช่น ระดมทางเลือกให้เสร็จภายใน 15 นาที เพื่อไม่ให้การสนทนาหลุดทิศ

## ข้อผิดพลาดที่พบบ่อย

- ใช้ brainstorm เป็นการลงมือจนโมเดลเริ่มแก้ไฟล์แล้ว ให้จำกัดด้วย “ยังไม่ต้องแก้”
- ทางเลือกมากเกินไปและไม่จัดลำดับ ทำให้ตัดสินใจล้า
- ไม่บันทึกแนวทางที่ปฏิเสธ จึงถกเรื่องเดิมอีกในสองสัปดาห์
- ข้ามข้อจำกัด ทำให้แนวทางดูสวยแต่ใช้จริงไม่ได้

## ขอบเขตความปลอดภัย

- ช่วงระดมความคิดยังอาจอ่านไฟล์อ่อนไหว ให้ใช้ `@` อ้างขอบเขตอย่างแม่นยำ
- แนวทางที่เกี่ยวกับ compliance หรือ privacy ต้องผ่านการตรวจด้านกฎหมาย/ความปลอดภัยโดยคน ห้ามให้โมเดลตัดสินเอง

## Checklist การยอมรับ

- [ ] มีทางเลือกที่ใช้ได้อย่างน้อย 2 แบบและคำแนะนำชัดเจน
- [ ] ระบุจุดตัดสินใจแล้วและรอคนยืนยัน
- [ ] ไม่มีการเขียน repository ที่ไม่ได้รับอนุญาต
- [ ] ขั้นถัดไปเชื่อมต่อเป็นแผนลายลักษณ์อักษรได้
