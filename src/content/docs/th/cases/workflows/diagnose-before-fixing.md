การให้ Codex เริ่มแก้ bug ทันทีมักทำให้ต้องแก้ซ้ำสูง เวิร์กโฟลว์วินิจฉัยเน้นลำดับ **อาการ → สมมติฐาน → หลักฐาน → การแก้ขั้นต่ำ**

## เมื่อใดควรใช้

- ยังไม่ทราบสาเหตุที่การทดสอบล้มเหลว
- การแจ้งเตือน production หรือผู้ใช้รายงานว่า “เกิดเป็นครั้งคราว”
- ปัญหายังอยู่หลังการแก้ครั้งก่อน

## ขั้นตอน

### 1. หยุดการเปลี่ยนแปลง

```text
ยังไม่ต้องแก้โค้ดธุรกิจ ให้แสดงขั้นตอนทำซ้ำ log ที่เกี่ยวข้อง และ commit ล่าสุดที่เกี่ยวข้อง
```

### 2. ลดขอบเขต

- bisect: commit ใดเป็นจุดเริ่มปัญหา
- แยก: repository หรือตัวอย่างทดสอบที่เล็กที่สุดซึ่งทำซ้ำได้

### 3. สร้างสมมติฐาน

ให้ Codex ส่งออก:

```text
สมมติฐาน A: … วิธีตรวจ: …
สมมติฐาน B: … วิธีตรวจ: …
```

### 4. ตรวจสมมติฐาน (ให้ความสำคัญกับการอ่านอย่างเดียว)

รันการทดสอบเฉพาะ เพิ่ม log ชั่วคราว (ใน branch ที่ทิ้งได้) และอ่าน monitoring

### 5. แก้ให้น้อยที่สุด

แก้สาเหตุต้นตอครั้งละหนึ่งอย่าง หลีกเลี่ยง “ถือโอกาส refactor”

### 6. ยืนยัน regression

กรณีเดิมที่ล้มเหลว + สถานการณ์ข้างเคียง + การทดสอบป้องกันเกิดซ้ำ

## เทมเพลตพรอมป์

```text
ทำตาม “วินิจฉัยก่อนแก้”:
1. อ่าน @path/to/failing-test และ implementation แล้วอธิบายสาเหตุ (อ้างหมายเลขบรรทัดใน stack)
2. เสนอสมมติฐาน 2 ข้อและวิธีตรวจแบบอ่านอย่างเดียว
3. รอฉันยืนยันสมมติฐานแล้วค่อยเขียนการแก้ จากนั้นรันเฉพาะการทดสอบที่เกี่ยวข้อง
```

## ความสัมพันธ์กับ EPXV

การวินิจฉัยถือเป็นช่วง **สำรวจ** ที่ลึกขึ้น เมื่อถึงช่วงวางแผน ยังต้องเขียนให้ชัดว่า “หากสมมติฐานผิด จะย้อนกลับอย่างไร”

## ข้อผิดพลาดที่พบบ่อย

- แก้โค้ดก่อนทำซ้ำปัญหา
- patch ครั้งเดียวแก้สามปัญหา ทำให้ review ไม่ได้
- ลบ log ชั่วคราวแต่ไม่เพิ่มการทดสอบถาวร
