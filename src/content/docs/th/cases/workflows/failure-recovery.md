**การกู้คืนจากความล้มเหลว** อธิบายวิธีควบคุมสถานการณ์เมื่องานหลุดทิศหรือหยุดชะงัก แล้วจึงเดินหน้าต่อ บทนี้ให้ขั้นตอนที่ทำซ้ำได้คือ **ตรวจพบ → จำกัดความเสียหาย → กู้คืน → ทบทวน** และใช้ร่วมกับ [ย้อนกลับและกู้คืน](/th/guide/getting-started/undo-and-recover/) รวมถึง [จัดการงานระยะยาว](/th/cases/workflows/long-running-task-management/) ได้

![ภาพประกอบ: คนกับผู้ช่วยตัวเล็กค่อย ๆ สร้างหอคอยบล็อกที่ล้มไปครึ่งหนึ่งใหม่ตาม checklist โดยลูกศรย้อนกลับนำบล็อกหนึ่งก้อนคืนสู่ฐานที่มั่นคง](/illustrations/failure-recovery.webp)

## ประเด็นสำคัญของหน้านี้

- เมื่อใดควรใช้ `git stash` ย้อน commit หรือเปิด thread ใหม่
- จัดข้อมูลความล้มเหลวลงพรอมป์รอบถัดไปอย่างไร
- ทีมบันทึกปัญหาที่เกิดซ้ำอย่างไร

## สัญญาณความล้มเหลว

| สัญญาณ | การดำเนินการที่เป็นไปได้ |
|---|---|
| การทดสอบล้มเหลวเป็นวงกว้าง | หยุดลงมือและลดขนาด diff |
| แก้ผิดไดเรกทอรี/branch | ย้อนกลับแล้วใช้ `@` อ้างพาธที่ถูกต้องใหม่ |
| แผนกับ implementation ต่างกันมาก | กลับไปช่วงสำรวจหรือวางแผน |
| บริบทยาวเกินไปและลืมข้อจำกัด | thread ใหม่ + สรุปส่งต่อ |
| การอนุมัติ/กติกาปฏิเสธซ้ำ | ตรวจว่ากติกาขัดกับงานหรือไม่ |

## กระบวนการกู้คืนขั้นต่ำ

```text
1. หยุดแก้ต่อ (บอกชัดว่า “ยังไม่ต้องเขียนโค้ด”)
2. เก็บสถานะ: git status / stash / บันทึก thread ID
3. สรุปไม่เกิน 5 ข้อ: เป้าหมาย สิ่งที่ทำแล้ว อาการล้มเหลว สมมติฐาน
4. เลือก: ย้อนกลับ / ลดขอบเขต / ทำต่อใน thread ใหม่
5. เมื่อสำเร็จ ให้บันทึกใน AGENTS.md หรือการทบทวนกรณีศึกษา
```

ตัวอย่างพรอมป์:

```text
การเปลี่ยนแปลงปัจจุบันทำให้การทดสอบ 12 รายการล้มเหลว ยังไม่ต้องแก้ต่อ
แสดงไฟล์ที่ได้รับผลจาก commit ล่าสุด 3 รายการ เสนอจุดย้อนกลับที่เล็กที่สุด
และให้แผนแก้ที่ขอบเขตเล็กลง
```

## เวิร์กโฟลว์ที่แนะนำ

```text
ตรวจพบ (การทดสอบ/คน/CI)
    → จำกัดความเสียหาย (หยุดเขียน แยก branch)
    → วินิจฉัย (ดู “วินิจฉัยก่อนแก้”)
    → ลองใหม่ทีละน้อย
    → ทบทวนและเก็บความรู้
```

กรณี Agent หลายตัวดู [การทำงานร่วมกันของ Agent หลายตัว](/th/cases/workflows/multi-agent-coordination/) เมื่อเกิดความล้มเหลว ต้องระบุว่ารายการย่อยใดรับผิดชอบการ rollback

## ข้อผิดพลาดที่พบบ่อย

- “เพิ่มอีกนิด” ในทิศทางที่ผิดจน patch ทับซ้อน
- ไม่เก็บ log ความล้มเหลว ทำให้ thread ใหม่ทำผิดซ้ำ
- บังคับ `git push` เพื่อกู้สถานการณ์
- ไม่แยกสภาพแวดล้อม (เครื่อง local เทียบกับ Cloud) ทำให้ขั้นตอนกู้คืนใช้ไม่ได้

## ขอบเขตความปลอดภัย

- การกู้คืนเองยังอยู่ใต้ [กติกาคำสั่ง](/th/guide/customization/rules/command-rules/)
- เหตุ production ให้ rollback ก่อนแล้วค่อยวิเคราะห์สาเหตุต้นตอ อย่าให้ Agent เชื่อมต่อ production เพื่อแก้ข้อมูลโดยตรง

## Checklist การยอมรับ

- [ ] อธิบายกลยุทธ์กู้คืนที่เลือกและเหตุผลได้
- [ ] repository กลับสู่สถานะที่ build/ทดสอบได้
- [ ] บันทึกสาเหตุและบทเรียนแล้ว (issue หรือ AGENTS.md)
- [ ] หากต้องเปิด thread ใหม่ มีสรุปข้อจำกัดสำคัญ
