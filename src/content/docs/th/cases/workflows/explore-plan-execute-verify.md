นี่คือวิธีจัดงานที่คู่มือนี้แนะนำ เหมาะตั้งแต่ “ยังไม่ชัดว่าต้องทำอย่างไร” ไปจนถึง “พร้อมรับมอบ” สี่ช่วงไม่ได้หมายถึงต้องอนุมัติสี่ครั้ง งานเล็กที่ขอบเขตชัดทำต่อเนื่องได้ ให้รอการตัดสินใจเฉพาะเมื่อแนวทางยังไม่ชัดหรือขาดสิทธิ์ที่จำเป็น เริ่มจาก[การแบ่งระดับงาน](/th/prompts/ask-for-a-plan/)

## ภาพรวมสี่ช่วง

```text
① สำรวจ Explore    → เข้าใจสถานะปัจจุบัน ขอบเขต และความเสี่ยง
② วางแผน Plan      → ขั้นตอน ไฟล์ เกณฑ์ยอมรับ และทางเลือกที่จำเป็น
③ ลงมือ Execute    → แก้โค้ด/เอกสาร/การตั้งค่าภายในขอบเขตที่อนุญาต
④ ยืนยันผล Verify  → ทดสอบ ตรวจ diff และเทียบ “นิยามเสร็จสมบูรณ์”
```

เมื่อสถานะปัจจุบันไม่ชัด ให้สำรวจและวางแผนก่อนเพื่อไม่แก้จากการเดา ส่วนการแก้คำผิดที่ชัดเจนไม่ต้องแบ่งเป็นการโต้ตอบสี่รอบ ดู [วินิจฉัยก่อนแก้](/th/cases/workflows/diagnose-before-fixing/)

## ① สำรวจ

**เป้าหมาย:** อธิบายสถานะปัจจุบันให้ชัดก่อนตัดสินใจว่าจะเปลี่ยนอย่างไร

ตัวอย่างพรอมป์:

```text
ยังไม่ต้องแก้โค้ด อ่าน @src/auth/ และการทดสอบที่เกี่ยวข้อง แล้วอธิบายเป็นรายการ:
1. ขั้นตอน login ปัจจุบัน
2. ไฟล์ที่อาจเกี่ยวข้องกับ bug เลย์เอาต์ใน Safari
3. หนึ่งเรื่องที่ยังไม่แน่ใจและต้องให้ฉันยืนยัน
```

ผลงาน: คำอธิบายปัญหา ขอบเขตผลกระทบ และรายการรอยืนยัน

## ② วางแผน

**เป้าหมาย:** รายการขั้นตอนที่ตรวจได้

```text
จากการสำรวจเมื่อครู่ ให้เสนอแผนที่มีหมายเลขขั้นตอน ไฟล์ที่เกี่ยวข้อง และวิธียืนยันแต่ละขั้น
ห้ามเขียนโค้ดก่อนฉันตอบว่า “ทำตามแผน”
```

พรอมป์นี้จำกัดชัดว่า “ทำเฉพาะแผน” จึงต้องรอ หากงานได้รับอนุญาตให้ implement แล้ว ให้เปลี่ยนเป็น “อธิบายแผนสั้น ๆ ก่อน แล้วลงมือและยืนยันต่อเนื่องในขอบเขตที่ตกลง” การหยุดหรือไม่ขึ้นกับสิทธิ์ ทางเลือกที่จำเป็น และ permission จริง ไม่ได้ขึ้นกับจำนวนขั้นในแผน

## ③ ลงมือ

**เป้าหมาย:** ให้การเปลี่ยนแปลงเล็กและย้อนกลับได้

- มุ่งทีละเป้าหมายย่อย
- ให้ความสำคัญกับเส้นทางที่การทดสอบครอบคลุม
- เมื่อเจอรายละเอียด implementation ทั่วไป ให้อัปเดตแผนแล้วทำต่อ แต่หากสมมติฐานหรือขอบเขตเปลี่ยน ให้กลับไปช่วง ② เพื่อตัดสินใจว่าต้องมีการยืนยันใหม่หรือไม่

ประโยคแนะนำ: “ทำขอบเขตที่อนุญาตต่อให้เสร็จ หากต้องขยายขอบเขต ให้อธิบายผลกระทบและทางเลือกที่ชัดเจน”

## ④ ยืนยันผล

**เป้าหมาย:** พิสูจน์ว่าเป็นไปตาม “นิยามเสร็จสมบูรณ์”

| ประเภทการยืนยัน | วิธีทำ |
|---|---|
| อัตโนมัติ | unit test, lint, type check |
| คนตรวจ | อ่าน diff และทดสอบเส้นทางสำคัญด้วยมือ |
| ผลงาน | ภาพหน้าจอ ช่วง log และ API response |

ดู checklist ที่ [นิยามเสร็จสมบูรณ์](/th/prompts/define-done/) และ [รันการทดสอบ](/th/guide/quality/run-tests/)

## ปรับตามขนาดงาน

| ขนาด | สำรวจ | วางแผน | ลงมือ | ยืนยันผล |
|---|---|---|---|---|
| แก้ typo | ตรวจข้อความเป้าหมาย | อาจไม่ต้องเขียน | สั้น | ตรวจ diff และยืนยันตามกติกาโปรเจกต์ |
| bug ไฟล์เดียว | เบา | 3–5 ขั้น | ปานกลาง | ทดสอบ + diff |
| ฟีเจอร์ข้ามโมดูล | ระบุ dependency | แผนลายลักษณ์อักษร และรอยืนยันทางเลือกที่จำเป็น | ทำเป็นช่วงภายในขอบเขตที่อนุญาต | ทดสอบตามผลกระทบ + ทดสอบด้วยมือ |
| เหตุ production | วินิจฉัยก่อน | วางแผน rollback ก่อน | ทีละขั้นเล็กมาก | monitoring + ทบทวน |
