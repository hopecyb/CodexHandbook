**เริ่มจากผลงาน** หมายถึงอธิบายรูปแบบและตำแหน่งของสิ่งที่ต้องส่งให้ชัดก่อน แล้วให้ Codex ย้อนหาขั้นตอน เหมาะกับงานที่มีเอาต์พุตชัดเจน เช่น เอกสาร Markdown, OpenAPI, สคริปต์ migration หรือโครงสไลด์ และใช้ร่วมกับ [งานที่ขับเคลื่อนด้วย specification](/th/cases/workflows/specification-driven-work/) ได้

## ประเด็นสำคัญของหน้านี้

- อธิบายโครงสร้างผลงานแทนรายละเอียดกระบวนการอย่างไร
- ตรวจความสอดคล้องของผลงานหลายไฟล์
- ให้สอดคล้องกับความสามารถ [ไฟล์และผลงาน](/th/guide/files-and-artifacts/)

## วิธีขั้นต่ำที่ใช้ได้

```text
ผลงานเป้าหมาย:
- docs/api/auth.md (มี 3 หัวข้อ: ภาพรวม endpoint และ error code)
- รูปแบบสอดคล้องกับ @docs/api/users.md

แสดงโครงสารบัญและประเด็นของแต่ละหัวข้อก่อน ยังไม่ต้องเขียนฉบับเต็ม
รอฉันยืนยันแล้วค่อยสร้าง พร้อมตรวจเองว่าลิงก์ภายในใช้ได้
```

## เวิร์กโฟลว์ที่แนะนำ

```text
กำหนดรายการผลงาน (พาธ + รูปแบบ + ตัวอย่างอ้างอิง)
    → โครงร่างหรือไฟล์ skeleton
    → คนยืนยัน
    → เติมเนื้อหา + cross-link
    → ยืนยันผล (lint, ตรวจลิงก์, preview)
```

สำหรับผลงานที่มองเห็นได้ สามารถขอภาพหน้าจอหรือคำอธิบาย preview ดู [ยืนยันผลงาน](/th/guide/quality/verify-artifacts/)

## ข้อผิดพลาดที่พบบ่อย

- พาธผลงานไม่ตรงกับข้อตกลงของ repository (วางผิดไดเรกทอรี)
- สร้างเพียงไฟล์เดียวและลืมอัปเดต navigation กับ index
- ไม่เทียบกับตัวอย่าง ทำให้รูปแบบไม่ต่อเนื่อง
- ผลงาน binary (pptx/docx) ไม่อธิบายวิธีเปิดตรวจด้วยคน

## ขอบเขตความปลอดภัย

- หากผลงานมีเนื้อหาลิขสิทธิ์ของบุคคลที่สาม ต้องให้คนตรวจ compliance
- ห้ามเขียนทับพาธการตั้งค่า production ให้สร้างบน branch หรือใต้ `draft/` ก่อน

## Checklist การยอมรับ

- [ ] ไฟล์ที่ระบุทั้งหมดมีอยู่และเปิดได้
- [ ] รูปแบบตรงกับตัวอย่างอ้างอิง
- [ ] ลิงก์/สารบัญ/Frontmatter ถูกต้อง
- [ ] ตรงตาม [นิยามเสร็จสมบูรณ์](/th/prompts/define-done/)
