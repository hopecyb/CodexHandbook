**การวิจัยพร้อมแหล่งอ้างอิง** กำหนดให้ข้อสรุปสำคัญทุกข้อย้อนกลับไปยังแหล่งข้อมูลที่เจาะจงได้ เช่น เอกสารทางการ งานวิจัย หรือไฟล์ใน repository แทนการให้ความเห็นที่ไม่มีหลักฐานเพียงประโยคเดียว เหมาะกับการเลือกเทคโนโลยี เปรียบเทียบคู่แข่ง ทบทวนวรรณกรรม และตีความนโยบาย

## ประเด็นสำคัญของหน้านี้

- เมื่อใดควรใช้ [การค้นเว็บ](/th/guide/tools/web-search/) เทียบกับอ่าน repository อย่างเดียว
- กำหนดรูปแบบอ้างอิงและป้ายความไม่แน่นอนอย่างไร
- ทำงานร่วมกับขั้น [ยืนยันแหล่งข้อมูล](/th/guide/quality/validate-sources/) อย่างไร

## วิธีขั้นต่ำที่ใช้ได้

```text
วิจัย “ความเหมาะสมของ Rust และ Go ในสถานการณ์ของ repository นี้”:
1. แสดงมิติประเมินก่อน (ประสิทธิภาพ ecosystem ความคุ้นเคยของทีม)
2. ทุกข้อสรุปมี URL แหล่งข้อมูลหรือพาธไฟล์ใน repository ที่ขึ้นต้นด้วย @
3. รายการที่ยืนยันไม่ได้ให้ระบุ “รอยืนยัน”
4. สุดท้ายให้คำแนะนำและคำถามที่ยังเปิดอยู่
ห้ามแก้โค้ด
```

## เวิร์กโฟลว์ที่แนะนำ

```text
กำหนดคำถามและสิ่งที่ตัดออก
    → รวบรวมแหล่งข้อมูล (ค้น / อ่านเอกสาร / MCP)
    → ตารางเปรียบเทียบ + ข้อดีข้อเสีย
    → ระบุระดับความเชื่อมั่นและแหล่งข้อมูลที่ขัดกัน
    → คนตัดสินหรือเข้าสู่ช่วง specification
```

แบ่งงานวิจัยยาวเป็นหลายรอบ ดู [จัดการงานระยะยาว](/th/cases/workflows/long-running-task-management/)

## ข้อผิดพลาดที่พบบ่อย

- ไม่ขอ URL ทำให้ตรวจผลงานซ้ำไม่ได้
- ใช้บล็อกเก่าปะปนกับเอกสารทางการโดยไม่อธิบาย
- ใช้ข้อสรุปวิจัยเป็นคำสั่ง implement โดยตรงและข้าม specification
- อัปโหลดไฟล์ที่มีข้อมูลลับไปยังเครื่องมือภายนอกที่ไม่ได้รับอนุญาต

## ขอบเขตความปลอดภัย

- ห้ามส่งข้อมูลภายในที่ยังไม่เผยแพร่ออกผ่าน MCP ที่ควบคุมไม่ได้
- ข้อเท็จจริงที่เปลี่ยนง่าย เช่น ราคา เวอร์ชัน และพื้นที่ให้บริการ ต้องระบุ [วันที่ยืนยัน](/th/guide/start-here/handbook-version-policy/)

## Checklist การยอมรับ

- [ ] ข้อสรุปสำคัญมีแหล่งข้อมูลที่คลิกหรือย้อนตรวจได้อย่างน้อยหนึ่งรายการ
- [ ] แสดงข้อมูลที่ขัดกันคู่กันแล้ว
- [ ] แสดงรายการ “ไม่แน่นอน” และไม่ปลอมเป็นข้อเท็จจริง
- [ ] ไม่มีข้อมูลอ่อนไหวในพรอมป์หรือ log
