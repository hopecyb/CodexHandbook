**งานแบบ test-driven** (TDD หรือ “เขียนการทดสอบก่อน”) คือทำให้การทดสอบล้มเหลวก่อน แล้วใช้ implementation ขั้นต่ำเปลี่ยนให้ผ่าน เหมาะกับ codebase ที่มีระบบทดสอบอยู่แล้ว และเกี่ยวข้องโดยตรงกับสถานการณ์อย่าง [การแก้ Bug พร้อมการยืนยันผล](/th/cases/use-cases/software-development/fix-a-bug-with-verification/)

## ประเด็นสำคัญของหน้านี้

- เมื่อใดควรกำหนดให้ “เขียน/รันการทดสอบก่อน”
- เขียนพรอมป์อย่างไรไม่ให้ Codex ข้ามขั้นทดสอบ
- กลยุทธ์ย้อนกลับเมื่อการทดสอบล้มเหลว

## เหมาะกับใคร

- repository ที่มี unit/integration test อยู่แล้ว
- regression bug การเปลี่ยนพฤติกรรม API และ refactor

สถานการณ์ที่ไม่เหมาะ ได้แก่ prototype ที่ไม่มีระบบทดสอบ และการแก้ข้อความครั้งเดียวในเว็บไซต์เนื้อหาล้วน งานเหล่านี้เหมาะกับการใช้ [EPXV](/th/cases/workflows/explore-plan-execute-verify/) เพื่อตรวจด้วยคนมากกว่า

## วิธีขั้นต่ำที่ใช้ได้

```text
1. เขียนการทดสอบที่ล้มเหลวสำหรับพฤติกรรมที่คาด (หรือระบุการทดสอบเดิมที่ล้มเหลว)
2. implement เฉพาะโค้ดขั้นต่ำที่ทำให้การทดสอบนี้ผ่าน
3. รันชุดทดสอบที่เกี่ยวข้อง แล้วรันทั้งชุด
4. ห้ามลบ assertion หรือ mock ตรรกะจริงเพียงเพื่อให้การทดสอบผ่าน
```

พรอมป์:

```text
ทำตาม TDD: เขียนการทดสอบที่ล้มเหลวสำหรับพฤติกรรม “อินพุตว่างคืน []” ใน @src/foo.ts ก่อน
รันยืนยันว่าล้มเหลวแล้วค่อยแก้ implementation แต่ละขั้นให้รันเฉพาะไฟล์ทดสอบที่เกี่ยวข้อง
```

## เวิร์กโฟลว์ที่แนะนำ

| ช่วง | ผลงาน |
|---|---|
| แดง | การทดสอบที่ล้มเหลว + คำอธิบายสาเหตุ |
| เขียว | implementation ขั้นต่ำ + การทดสอบผ่าน |
| Refactor | จัดโค้ดภายใต้การคุ้มครองของการทดสอบ (เป็นขั้นแยกได้) |

ใช้ร่วมกับ [วินิจฉัยก่อนแก้](/th/cases/workflows/diagnose-before-fixing/) โดยอ่าน assertion ที่ล้มเหลวและ stack ก่อนแก้ implementation

## ข้อผิดพลาดที่พบบ่อย

- อ้างว่าเสร็จโดยไม่รันการทดสอบ
- แก้การทดสอบให้ยอมตาม implementation ที่ผิด
- รันเพียงการทดสอบเดียวแต่ประกาศว่าเขียวทั้งหมด
- รันชุด E2E ที่ช้าทั้งหมดซ้ำ ๆ ให้ใช้ `-t` หรือตัวกรองระดับไฟล์

## ขอบเขตความปลอดภัย

- คำสั่งทดสอบต้องอยู่ในขอบเขตที่ [กติกาคำสั่ง](/th/guide/customization/rules/command-rules/) อนุญาต
- หาก integration test แตะ production API ต้องห้ามไว้ใน specification หรือเปลี่ยนเป็น mock

## Checklist การยอมรับ

- [ ] มีหลักฐานการทดสอบจากล้มเหลว → ผ่าน (log หรือ CI)
- [ ] การทดสอบทั้งชุดหรือขอบเขตที่ตกลงผ่าน
- [ ] diff ไม่มีการลบการทดสอบที่ไม่เกี่ยวข้อง
- [ ] สอดคล้องกับ [นิยามเสร็จสมบูรณ์](/th/prompts/define-done/)
