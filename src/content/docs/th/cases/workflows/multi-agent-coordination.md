Agent หลายตัวเหมาะกับปัญหาย่อยที่ทำพร้อมกันได้และพึ่งพากันน้อย ไม่เหมาะกับการแก้ไฟล์เดียวกันพร้อมกันโดยไม่มีผู้ประสานงาน

## เมื่อใดควรแยกงาน

| เหมาะ | ไม่เหมาะ |
|---|---|
| วิจัยสไตล์ frontend และสัญญา backend API พร้อมกัน | สองคนแก้ฟังก์ชันเดียวกัน |
| ตัวหนึ่งรันทดสอบ อีกตัวเขียนเอกสาร | แชร์ mutable state โดยไม่มี lock |
| สำรวจแนวทาง implementation หลายแบบ | dependency ตามลำดับที่ยังไม่ชัด |

ดูความสามารถผลิตภัณฑ์ที่ [Agent แบบขนาน](/th/guide/desktop-app/parallel-agents/) และ [Agent ย่อย](/th/guide/agent-work/subagents/)

## รูปแบบการทำงานร่วมกัน

### รูปแบบ A: สำรวจแบบขนาน แล้วให้คนเลือกแนวทาง

```text
Agent 1: ข้อดี ข้อเสีย และปริมาณงานของแนวทาง A
Agent 2: ข้อดี ข้อเสีย และปริมาณงานของแนวทาง B
คุณ: เลือกหนึ่งแนวทาง แล้วเปิด Agent ตัวเดียวให้ลงมือ
```

### รูปแบบ B: Pipeline

```text
Agent สำรวจ → ส่งออกแผน → Agent ลงมือ (thread ใหม่ พร้อมสรุปแผน)
```

ใช้ [ส่งต่อและทำต่อ](/th/guide/agent-work/handoff-and-resume/) เพื่อส่งสรุปที่มีโครงสร้าง อย่าวางบทสนทนาทั้งหมด

### รูปแบบ C: แยกด้วย worktree

ให้ Agent แต่ละตัวแก้คนละ branch ใน [git worktree](/th/guide/desktop-app/worktrees/) แล้วให้คน merge ในตอนท้าย

## กติกาการประสานงาน (แนะนำให้เขียนใน AGENTS.md)

- กำหนดขอบเขตไดเรกทอรีของ Agent แต่ละตัวให้ชัดเจน
- ห้าม `git push` พร้อมกัน
- รัน CI ชุดเดียวกันก่อน merge
- ให้คนแก้ conflict ห้ามให้ Agent เดา

## การยอมรับ

- [ ] Agent ย่อยแต่ละตัวมี “นิยามเสร็จสมบูรณ์” แยกกัน
- [ ] หลัง merge การทดสอบทั้งชุดผ่าน
- [ ] diff ย้อนกลับไปยังคำอธิบายงานย่อยที่เกี่ยวข้องได้

## ข้อผิดพลาดที่พบบ่อย

- ให้ Agent สามตัวแก้ `package.json` พร้อมกัน
- ไม่มีขั้นสรุป จึงไม่รู้ว่าควรเชื่อข้อสรุปของใคร
