การอนุมัติควรผูกกับการดำเนินการและผลกระทบที่เจาะจง การอนุญาตงานบอกว่าผู้ใช้ต้องการให้ทำอะไร ส่วนการอนุมัติเครื่องมือกำหนดว่าการดำเนินการหนึ่งรันในสภาพแวดล้อมปัจจุบันได้หรือไม่ การเขียนไฟล์ รันคำสั่ง หรือเชื่อมต่อเครือข่ายไม่ได้หมายความว่าต้องถามทุกครั้งโดยธรรมชาติ พฤติกรรมจริงขึ้นกับขอบเขตที่อนุญาต นโยบายเครื่องมือ และ sandbox ร่วมกัน [คำอธิบายทางการ](https://learn.chatgpt.com/docs/agent-approvals-security)

## รูปแบบการทำงานร่วมกันสามแบบที่เลือกให้ชัดได้

| รูปแบบ | ทำอะไรต่อได้ | เมื่อใดต้องรอ |
|---|---|---|
| วิเคราะห์แบบอ่านอย่างเดียว | อ่าน เปรียบเทียบ และสร้างแนวทาง | เมื่อผู้ใช้ยังไม่อนุญาตให้ implement ห้ามแก้ implementation |
| ลงมือภายในขอบเขตที่อนุญาต | แก้ขอบเขตที่กำหนด ยืนยันตามสมควร และเตรียมผลงานให้ตรวจ | เมื่อขาดข้อมูลจำเป็น ขอบเขตเปลี่ยน หรือเกิดการดำเนินการใหม่ที่ยังไม่อนุญาต |
| อนุมัติการดำเนินการสุดท้ายแยกต่างหาก | ทำร่าง build, preview และเตรียม rollback ให้เสร็จ | ก่อนเผยแพร่ ส่ง หรือการดำเนินการอื่นที่ตกลงให้สงวนไว้ |

สิ่งเหล่านี้เป็นข้อตกลงการทำงานร่วมกัน ไม่ใช่ชื่อโหมดผลิตภัณฑ์ใหม่ เมื่อมีสิทธิ์ชัดเจนและยังใช้ได้ อย่าขอสิทธิ์เดิมซ้ำ หากนโยบายบังคับจริงกำหนดให้มีการอนุมัติแบบโต้ตอบ ก็ให้ทำตามกลไกปัจจุบัน

## รูปแบบที่หนึ่ง: รอบนี้ทำเฉพาะแนวทาง

```text
รอบนี้อ่านอย่างเดียว: ตรวจโปรเจกต์และเสนอแนวทางแก้ ห้ามแก้โค้ดหรือ commit
หากการตรวจใดจะเขียน cache, snapshot หรือไฟล์เอาต์พุต ให้แจ้งก่อน อย่าถือว่า “การทดสอบ” อ่านอย่างเดียวเสมอ
```

เหมาะกับช่วงที่เป้าหมายยังไม่ชัดและต้องเปรียบเทียบแนวทาง งานอ่านอย่างเดียวยังต้องคำนึงถึงผลข้างเคียงจริงของคำสั่ง ห้ามเขียน “รันการทดสอบได้” คู่กับ “ห้ามเขียนดิสก์ทุกกรณี” โดยไม่ตรวจข้อขัดแย้ง

## รูปแบบที่สอง: ทำงานในเครื่องต่อเนื่องให้เสร็จ

```text
อนุญาตให้แก้เอกสารสามฉบับนี้และ internal link ที่เกี่ยวข้อง พร้อมรันการตรวจ build ที่มีอยู่
ทำต่อเนื่องให้เสร็จในขอบเขตนี้ และจัดการรายละเอียด implementation ทั่วไปเองแล้วรายงาน
ห้ามเผยแพร่เว็บไซต์หรือส่งข้อความ หากมีทางเลือกที่จำเป็นหรือการดำเนินการนอกขอบเขต ให้แจ้งก่อน
```

ที่นี่อนุญาตการแก้และยืนยันแล้ว จึงไม่ต้องยืนยันอีกก่อนเขียนทุกไฟล์ ส่วนคำสั่งใดรันได้หรือไม่ยังขึ้นกับสภาพแวดล้อม ห้ามใช้พรอมป์เพื่อหลีกเลี่ยงการปฏิเสธ

## รูปแบบที่สาม: อนุมัติการเผยแพร่ที่เจาะจง

ทำเวอร์ชันที่ตรวจได้ให้เสร็จก่อน แล้วระบุ:

- เวอร์ชันหรือผลงานที่จะเผยแพร่ พร้อมผลการยืนยัน
- สภาพแวดล้อมเป้าหมาย ผู้รับ หรือผู้ได้รับผลกระทบ
- ผลภายนอกที่คาดและวิธีกู้คืนที่จำเป็น
- สิทธิ์หรือเงื่อนไขที่ยังขาด

การอนุมัติ “เผยแพร่เวอร์ชันนี้ไปเว็บไซต์ทดสอบ” ไม่เท่ากับอนุมัติให้เผยแพร่ทุกเวอร์ชันในอนาคตไป production ในทางกลับกัน หากอนุมัติการดำเนินการเดียวกันไว้อย่างชัดเจนแล้ว ก็ไม่ควรขอซ้ำเพียงเพราะเทมเพลตทั่วไปกำหนดไว้

## ทำต่ออย่างไรหลังถูกปฏิเสธ

เก็บข้อความปฏิเสธต้นฉบับ และแยกให้ออกว่าเป็นการขาดสิทธิ์ นโยบายห้าม หรือสภาพแวดล้อมล้มเหลว หากลดขอบเขตโดยที่งานยังคงใช้ได้ ให้ทำต่อ ห้ามเปลี่ยนเครื่องมือ เปลี่ยนการสะกดคำสั่ง หรือเขียนพรอมป์ใหม่เพื่อหลบข้อจำกัดเดียวกัน หากจำเป็นต้องให้ผู้ใช้ดำเนินการจริง ให้ระบุการดำเนินการที่ถูกขวาง เหตุผล และขั้นถัดไปที่เลือกได้

## ผู้ตรวจควรตรวจอะไร

ตัดสินว่าขอบเขตตรงกับผลลัพธ์หรือไม่ การยืนยันเกิดขึ้นจริงหรือไม่ และเข้าใจผลภายนอกแล้วหรือไม่ ห้ามถือว่า “มีแผน” คืออนุมัติอัตโนมัติ และห้ามถือว่า “ไม่มี findings” คือรับประกันความเสี่ยงเป็นศูนย์
