คำถามแรกเมื่อเลือก Hook ไม่ใช่ “เขียนสคริปต์อย่างไร” แต่คือ “จัดการก่อนหรือหลังผลข้างเคียงเกิดขึ้น” หากวาง event ผิดจุด ต่อให้สคริปต์สมบูรณ์ก็อาจทำได้เพียงรายงานภายหลัง

![วงจรชีวิต Codex Hook และ event สำคัญ](/illustrations/flow-hook-lifecycle.webp)

## รายการ event ปัจจุบัน

| event | เกิดเมื่อใด | matcher กรองอะไร | การใช้งานทั่วไป |
|---|---|---|---|
| `SessionStart` | session หรือการกลับมาทำงานเริ่มขึ้น | `startup`, `resume`, `clear`, `compact` | คำอธิบายสภาพแวดล้อมและกู้คืนบริบท |
| `SubagentStart` | Agent ย่อยเริ่มทำงาน | ประเภท Agent ย่อย | เพิ่มข้อจำกัดให้ Agent ย่อย |
| `UserPromptSubmit` | ผู้ใช้ส่งพรอมป์ | ไม่รองรับ การตั้งค่าจะถูกละเว้น | สแกน secret และเพิ่มบริบทการพัฒนา |
| `PreToolUse` | ก่อนเครื่องมือในเครื่องที่รองรับทำงาน | ชื่อเครื่องมือ | ปฏิเสธหรือแก้การเรียก |
| `PermissionRequest` | Codex กำลังจะขออนุมัติ | ชื่อเครื่องมือ | อนุญาต ปฏิเสธ หรือส่งกลับไปยังขั้นตอนอนุมัติปกติ |
| `PostToolUse` | หลังเครื่องมือในเครื่องที่รองรับส่งผลกลับ | ชื่อเครื่องมือ | บันทึกผลและให้ feedback สำหรับ reasoning ต่อไป |
| `PreCompact` | ก่อนบีบอัดบริบท | `manual` / `auto` | เก็บสถานะก่อนบีบอัด |
| `PostCompact` | หลังบีบอัดบริบท | `manual` / `auto` | เติมบริบทจำเป็นกลับคืน |
| `SubagentStop` | Agent ย่อยกำลังจะจบ | ประเภท Agent ย่อย | ขอให้ตรวจเพิ่มอีกหนึ่งรอบ |
| `Stop` | รอบงานหลักกำลังจะจบ | ไม่รองรับ การตั้งค่าจะถูกละเว้น | ให้ thread หลักตรวจสอบต่อ |
| `SessionEnd` | thread หลักจบ | ปัจจุบันคือ `other` | log ปิดงานแบบรวดเร็ว และไม่รันกับ Agent ย่อย |

## matcher ของเครื่องมือ

ค่าที่พบบ่อย ได้แก่:

```text
Bash
^apply_patch$
Edit|Write
mcp__filesystem__read_file
mcp__filesystem__.*
```

Shell และคำสั่ง unified execution จะจับคู่เป็น `Bash` ส่วน `apply_patch` จับคู่ด้วย alias `Edit` หรือ `Write` ได้ MCP และเครื่องมือฟังก์ชันในเครื่องอื่นจับคู่ตามชื่อเครื่องมือจริง

## event สามประเภทที่สับสนง่ายที่สุด

### PreToolUse

อินพุตมี `tool_name`, `tool_use_id` และ `tool_input` เฉพาะเครื่องมือ สามารถทำสิ่งต่อไปนี้:

- `permissionDecision: "deny"`: หยุดการเรียกเครื่องมือที่รองรับ
- `permissionDecision: "allow"` + `updatedInput`: แก้อินพุตของเครื่องมือที่รองรับ
- `additionalContext`: ไม่บล็อก แต่เพิ่มบริบทให้โมเดล

ข้อความ stdout ทั่วไปจะถูกละเว้น ต้องส่ง JSON ตามนิยามทางการ exit code `2` พร้อม stderr ก็ใช้บล็อกและให้เหตุผลได้

### PermissionRequest

ทริกเกอร์เฉพาะเมื่อ Codex กำลังจะขออนุมัติเดิมอยู่แล้ว เช่น การยกระดับ shell หรือเครือข่ายที่มีการจัดการ สามารถ allow, deny หรือไม่ตัดสินใจเพื่อให้ UI อนุมัติปกติทำงานต่อ อย่าใช้แทนนโยบายเครื่องมือทั่วไปของ `PreToolUse`

### PostToolUse

เครื่องมือทำงานแล้ว และจะทริกเกอร์แม้ Bash ออกด้วยค่าที่ไม่ใช่ศูนย์ การส่ง block หรือ exit `2` ในจุดนี้ทำได้เพียงเปลี่ยน feedback และให้โมเดลจัดการต่อ ไม่สามารถย้อนคำสั่ง การเขียนไฟล์ หรือการกระทำภายนอกได้

## Stop ไม่ใช่ปุ่ม “ห้ามจบ”

`decision: "block"` ของ `Stop` หมายถึงสร้างพรอมป์ให้ทำต่อโดยอัตโนมัติตาม reason เพื่อให้ Codex ทำอีกหนึ่งรอบ ไม่ได้ย้อนผลข้างเคียงจากเครื่องมือที่เสร็จแล้ว สคริปต์ต้องตรวจ `stop_hook_active` เพื่อหลีกเลี่ยงการทำต่อไม่รู้จบ

## แบบฝึกหัดเลือก event

| ความต้องการ | เลือก | เหตุผล |
|---|---|---|
| ป้องกันการเขียน token ที่น่าสงสัยลงไฟล์ | `PreToolUse` จับคู่ `apply_patch|Edit|Write` | ต้องจัดการก่อนเขียน |
| เก็บสถิติอัตราความล้มเหลวของ shell | `PostToolUse` จับคู่ `Bash` | ต้องใช้ผล exit |
| บันทึกการตัดสินใจสำคัญก่อนบีบอัดบริบทอัตโนมัติ | `PreCompact` | เกิดก่อนการบีบอัด |
| ไม่ให้ปิดงานก่อนรันการทดสอบครบ | `Stop` | ต้องให้รอบงานปัจจุบันทำต่อ |
| ส่งคำขอเครือข่าย 30 วินาทีเมื่อ thread หลักจบ | ไม่เหมาะกับ `SessionEnd` | สูงสุด 3 วินาที และไม่ควรใส่งานยาวใน event ปิดงาน |
