Hooks ช่วยให้คุณรันสคริปต์คำสั่งหรือเครื่องมือจากเซิร์ฟเวอร์ MCP ที่เชื่อมต่อแล้วใน Agent loop ของ Codex การใช้งานทั่วไป ได้แก่ สแกน secret ในพรอมป์ กำหนดนโยบายการเรียกเครื่องมือ บันทึก audit สรุป session และตรวจสอบก่อนหยุด

![วงจรชีวิต Codex Hook: session, รอบงาน, การเรียกเครื่องมือ, การบีบอัด และ event ของ Agent ย่อย](/illustrations/flow-hook-lifecycle.webp)

ความแตกต่างที่สำคัญที่สุดในภาพคือ `PreToolUse` สามารถปฏิเสธหรือแก้อินพุตก่อนเครื่องมือในเครื่องที่รองรับทำงาน ส่วน `PostToolUse` เกิดหลังเครื่องมือทำงานเสร็จ จึงย้อนผลข้างเคียงที่เกิดแล้วไม่ได้

## การตั้งค่ามาจากที่ใด

Codex จะค้นหาข้างชั้นการตั้งค่าที่ใช้งานอยู่:

- `~/.codex/hooks.json`
- `[hooks]` ใน `~/.codex/config.toml`
- `<repo>/.codex/hooks.json`
- `[hooks]` ใน `<repo>/.codex/config.toml`
- Hook ที่มากับ Plugin ซึ่งเปิดใช้งานแล้ว
- managed Hook ที่ผู้ดูแลส่งผ่านระบบ MDM, Cloud หรือ `requirements.toml`

`.codex/` ระดับโปรเจกต์จะโหลดเฉพาะเมื่อโปรเจกต์ได้รับความเชื่อถือ Hook ที่ตรงกันจากหลายแหล่งจะรันร่วมกัน การตั้งค่าความสำคัญสูงไม่ได้แทน Hook ชั้นต่ำกว่าทั้งชุด

หากชั้นการตั้งค่าเดียวกันมีทั้ง `hooks.json` และ `[hooks]` แบบ inline ระบบจะรวมเข้าด้วยกันและแสดงคำเตือนตอนเริ่ม ควรเลือกวิธีเขียนเพียงแบบเดียวต่อหนึ่งชั้น

## ต้องตรวจ Hook ที่ไม่ได้รับการจัดการ

Codex บันทึกความเชื่อถือตาม hash ของนิยาม Hook Hook ที่ไม่ได้รับการจัดการซึ่งเพิ่มใหม่หรือแก้ไขจะถูกทำเครื่องหมายว่ารอตรวจและข้ามไป จนกว่าผู้ใช้จะเชื่อถือนิยามใหม่

ใน CLI ใช้ `/hooks` เพื่อดูแหล่งที่มา ตรวจการเปลี่ยนแปลง เชื่อถือ หรือปิด Hook ที่ไม่ได้รับการจัดการแต่ละรายการ Hook ที่มากับ Plugin ใช้ขั้นตอนความเชื่อถือเดียวกัน Managed Hook ได้รับความเชื่อถือจากนโยบายองค์กรและผู้ใช้ปิดใน Hook browser ส่วนตัวไม่ได้

## ตัวประมวลผลที่รันได้สองแบบ

| ตัวประมวลผล | การใช้งาน | ขอบเขตสำคัญ |
|---|---|---|
| `command` | รันสคริปต์ในเครื่อง โดยรับ event JSON จาก stdin | ตัวสคริปต์มีความสามารถของ process ในเครื่อง ต้องตรวจ dependency และผลลัพธ์ |
| `mcp_tool` | เรียกเครื่องมือในเซิร์ฟเวอร์ MCP ที่เชื่อมต่อแล้ว | ไม่เริ่มหรือเชื่อมเซิร์ฟเวอร์ใหม่เอง และไม่รองรับ `SessionEnd` |

ตามคำอธิบายทางการปัจจุบัน ตัวประมวลผล `prompt` และ `agent` parse ได้แต่จะถูกข้าม จึงไม่ควรเขียนใน config ที่ต้องรันจริง

## พฤติกรรมขณะรัน

- command Hook หลายรายการที่ตรงกันจะเริ่มพร้อมกัน Hook หนึ่งหยุด Hook อื่นที่ตรงกันและเริ่มไปแล้วไม่ได้
- ค่าเริ่มต้น `timeout` ของ Hook ส่วนใหญ่คือ 600 วินาที ส่วน `SessionEnd` เริ่มต้น 1 วินาทีและสูงสุด 3 วินาที สคริปต์เฝ้าระวัง production ยังคงควรกำหนด timeout ที่สั้นกว่าอย่างชัดเจน
- working directory ของ command Hook คือ `cwd` ของ session สคริปต์รีโพซิทอรีควร resolve จาก Git root เพื่อไม่ให้ relative path หาไม่พบเมื่อเริ่มจากไดเรกทอรีย่อย
- Hook แบบ async เหมาะกับ log และการวิเคราะห์ แต่บล็อก อนุมัติ แก้ไข หรือควบคุมการกระทำที่ทริกเกอร์ไม่ได้

## ความสัมพันธ์กับชั้นความปลอดภัยอื่น

| ชั้น | รับผิดชอบอะไร |
|---|---|
| sandbox | ขอบเขตความสามารถด้านไฟล์ เครือข่าย และระบบ |
| การอนุมัติ | ให้มนุษย์ตัดสินใจก่อนการกระทำความเสี่ยงสูง |
| กฎคำสั่ง | allow/deny รูปแบบคำสั่งที่รู้จักแบบ declarative |
| Hook | รัน logic กำหนดเองที่ทดสอบได้ ณ จุดวงจรชีวิต |
| สิทธิ์ฝั่งเซิร์ฟเวอร์ | ระบบภายนอกอนุญาตให้อ่านเขียนอะไรในท้ายที่สุด |

ความครอบคลุมเครื่องมือของ Hook ไม่ใช่ขอบเขตความปลอดภัยที่สมบูรณ์ เอกสารทางการระบุชัดว่า path ของเครื่องมือเฉพาะบางชนิดอาจข้าม path Hook เริ่มต้น และ Hosted tool (เช่น WebSearch) ก็ไม่ผ่าน `PreToolUse` / `PostToolUse` ในเครื่อง

## ลำดับการนำมาใช้

1. ใช้ `PostToolUse` หรือ `SessionEnd` ทำ log ที่ลบข้อมูลละเอียดอ่อนก่อน แล้วสังเกตพฤติกรรมจริง
2. ใช้ `systemMessage` หรือบริบทเพิ่มเติมเตือนปัญหาที่มีความมั่นใจสูง
3. บล็อกใน `PreToolUse` เฉพาะเมื่อกฎแน่นอน สคริปต์มี fixture และยอมรับ false positive ได้
4. จัด Hook ให้สอดคล้องกับ CI, pre-commit และสิทธิ์ฝั่งเซิร์ฟเวอร์ เพื่อไม่ให้เกิดนโยบายสามชุดที่ขัดกัน

## อ้างอิงเครื่องมือภายนอก

หากไม่ต้องการเขียนสคริปต์เฝ้าระวังจากศูนย์ สามารถประเมิน [HOL Guard](https://github.com/hashgraph-online/hol-guard) เป็นตัวเลือกได้ เป็นโปรเจกต์โอเพนซอร์สภายนอกภายใต้ใบอนุญาต Apache-2.0 ตาม [คำอธิบาย integration Codex 3.x](https://hol.org/guard/docs/guard/codex-harness) ตัวติดตั้งจะลงทะเบียน Hook เช่น `PreToolUse` และ `PermissionRequest` และใช้ startup shim กับ proxy MCP บางส่วน เพื่อปฏิเสธ แจ้งเตือน หรือส่งต่อให้มนุษย์อนุมัติคำสั่ง shell การอ่านข้อมูลละเอียดอ่อน การเรียก MCP และการจัดการแพ็กเกจบน path ที่รองรับตามนโยบายในเครื่อง ไม่ได้หยุดทุกอย่างเพื่อรอการยืนยันเสมอ Guard Cloud เป็นบริการแบบชำระเงินที่เลือกใช้แยกต่างหาก การป้องกันในเครื่องไม่ต้องเข้าสู่ระบบ Cloud

นี่ไม่ใช่เครื่องมือทางการของ OpenAI และเว็บไซต์นี้ไม่ได้ทดสอบอัตราการบล็อกหรือความปลอดภัยโดยอิสระ ก่อนทดลอง ให้รัน `hol-guard install codex --dry-run` ตรวจการแก้ `~/.codex/config.toml`, คำสั่งเริ่ม และการตั้งค่า MCP จากนั้นตรวจ [ความครอบคลุมและพฤติกรรมความล้มเหลว](https://github.com/hashgraph-online/hol-guard/blob/main/docs/guard/harness-support.md) ของเวอร์ชันปัจจุบัน พร้อมทดลองกรณี Hook error, timeout หรือรูปแบบผลลัพธ์ผิดที่อาจปล่อยผ่าน รวมถึงขั้นตอนถอนการติดตั้งและย้อนกลับ เช่นเดียวกับ Hook ที่เขียนเอง เครื่องมือนี้อยู่ภายใต้ขอบเขตความครอบคลุมเครื่องมือของ Codex และแทน sandbox, least privilege, การจัดการ secret หรือการควบคุมฝั่งเซิร์ฟเวอร์ไม่ได้

## รายการตรวจรับ

- [ ] ชื่อ event มาจากรายการทางการปัจจุบัน
- [ ] matcher ครอบคลุมเฉพาะเครื่องมือหรือแหล่งที่จำเป็น
- [ ] สคริปต์มีการทดสอบอินพุตคงที่และข้อความ error ที่อ่านได้
- [ ] log ไม่เก็บ token, พรอมป์ฉบับเต็ม หรือพารามิเตอร์เครื่องมือที่ละเอียดอ่อน
- [ ] ทดลอง path เมื่อ Hook ล้มเหลว timeout และปิดใช้งานแล้ว
- [ ] ทีมเข้าใจความหมายของการเปลี่ยนความเชื่อถือใน `/hooks`
