**Skill** คือไดเรกทอรีที่มี `SKILL.md` (และอาจมีสคริปต์กับเอกสารอ้างอิง) ใช้บรรจุขั้นตอนตายตัวเป็นความสามารถที่ Codex **เรียกใช้อัตโนมัติหรืออย่างชัดเจน** ได้

Skill เหมาะกับวิธีทำงานที่เกิดซ้ำแล้วและจะนำกลับมาใช้อีก

![ภาพประกอบ: workflow ที่สำเร็จถูกใส่ลงในกล่องเครื่องมือ แล้วคัดลอกแจกให้ Agent หลายตัวนำกลับมาใช้](/illustrations/skills-toolkit.webp)

## แนวคิดหลัก

### ต่างจากคำสั่ง slash อย่างไร

| | คำสั่ง slash | Skill |
|---|---|---|
| การทริกเกอร์ | คุณพิมพ์ `/xxx` | คุณเรียกด้วย `$name` หรือโมเดลจับคู่จากคำอธิบาย |
| บริบท | โดยทั่วไปขยายทันที | **การเปิดเผยแบบค่อยเป็นค่อยไป**: ปกติใช้พื้นที่เพียงชื่อ+คำอธิบาย และอ่านฉบับเต็มเมื่อเลือกใช้ |
| เหมาะกับ | จุดเข้าที่ตายตัว ใช้บ่อย และจำได้ | workflow ยาว ต้องใช้เอกสาร และต้องการให้โมเดลตัดสินใจเองว่าเมื่อใดควรใช้ |

### การเปิดเผยแบบค่อยเป็นค่อยไป

เมื่อ Codex เริ่มทำงาน จะเห็นเพียง **name, description และ path** ของแต่ละ Skill และจะโหลด `SKILL.md` ฉบับเต็มเมื่อเลือกใช้เท่านั้น ดังนั้นเนื้อหาสามารถมีรายการตรวจสอบโดยละเอียดได้โดยไม่ต้องกังวลว่าจะกินบริบททั้งหมด

ข้อควรระวัง: รายการ Skill มี **งบประมาณอักขระเริ่มต้น** (ประมาณส่วนเล็ก ๆ ของบริบท) ควรวางสถานการณ์ทริกเกอร์หลักไว้ **ช่วงต้น** ของ `description` เพื่อป้องกันการจับคู่ล้มเหลวเมื่อข้อความถูกตัด

## โครงสร้างไดเรกทอรี Skill

```text
my-skill/
├── SKILL.md          # จำเป็น
├── scripts/          # ไม่บังคับ: ขั้นตอนแบบกำหนดแน่นอน
└── references/       # ไม่บังคับ: เอกสารอ้างอิงยาว
```

ตัวอย่าง `SKILL.md` ขั้นต่ำ:

```md
---
name: pr-review
description: ตรวจ diff ของ branch ปัจจุบันเทียบกับ main แล้วระบุความเสี่ยงและช่องว่างการทดสอบ ใช้เมื่อผู้ใช้ขอ review, ตรวจ PR หรือตรวจก่อน merge
---

## ขั้นตอน
1. อ่าน diff เทียบกับ main
2. แยกตามไฟล์: ข้อผิดพลาดด้าน logic ความปลอดภัย ประสิทธิภาพ และการทดสอบ
3. ส่งรายการแบบแบ่งระดับ: บล็อก / แนะนำ / nit
4. ห้าม push หรือ merge อัตโนมัติ
```

## ตำแหน่งจัดเก็บ

| ประเภท | ตำแหน่งทั่วไป | คำอธิบาย |
|---|---|---|
| Skill ของโปรเจกต์ | `.agents/skills/<name>/` | ไปกับรีโพซิทอรีและแชร์ในทีม |
| Skill ของผู้ใช้ | ไดเรกทอรี skills ของผู้ใช้ (ดูเอกสารทางการ) | ใช้ส่วนตัวข้ามโปรเจกต์ |
| ชุดคัดสรรทางการ | ติดตั้งผ่านตัวติดตั้ง | path จัดการโดยตัวติดตั้ง อย่าสับสนกับไดเรกทอรีที่เขียนเอง |

**อย่า** คัดลอก path ผิดจากบทช่วยสอนที่ล้าสมัยหรือสร้างฟิลด์ `trigger:` ที่ไม่มีจริง ให้ยึด [เอกสาร Skills ทางการ](https://developers.openai.com/codex/skills) เป็นหลัก

## วิธีทริกเกอร์

1. **แบบชัดเจน**: ในสภาพแวดล้อมที่รองรับ ให้เรียกด้วย `$skill-name` (ชื่อตรงกับ `name` ใน frontmatter)
2. **แบบโดยนัย**: โมเดลตัดสินจากความหมายของ `description` ว่าเหมาะกับงานปัจจุบันหรือไม่

หลักการเขียน `description` ที่ดี:

- ระบุให้ชัดว่า “ใช้เมื่อใด” และ “ไม่ใช้เมื่อใด”
- ใส่คำที่ผู้ใช้อาจพูด เช่น review, release, changelog
- หลีกเลี่ยงคำกว้าง ๆ อย่าง “ช่วยผู้ใช้เขียนโค้ด”

## workflow ที่แนะนำ

1. พบว่า workflow หนึ่งเกิดซ้ำหลายครั้ง
2. ร่าง `SKILL.md` โดยเริ่มจากขั้นตอนข้อความล้วน
3. ลองใช้ `$name` และการจับคู่โดยนัยกับงานเล็ก
4. เพิ่ม `scripts/` เมื่อจำเป็นต้องให้ผลลัพธ์กำหนดแน่นอน
5. commit ไปยัง `.agents/skills/` และเปิด PR ให้ทีม

ลงมือฝึก: [สร้าง Skill แรก](/th/skills/create-your-first-skill/)

## ข้อสงสัยที่พบบ่อย

### 1. Skill ต่างจากพรอมป์อย่างไร

- **พรอมป์**: สิ่งที่คุณบอกชั่วคราวสำหรับงานครั้งนี้
- **Skill**: workflow ที่นำกลับมาใช้กับงานคล้ายกันในอนาคตได้

### 2. ต้องเรียนเขียน Skill ตั้งแต่เริ่มหรือไม่

ไม่ต้อง เริ่มจากอธิบายงานทั่วไปให้ชัดก่อน เมื่อ workflow หนึ่งเกิดซ้ำหลายครั้ง จึงค่อยพิจารณาทำเป็น Skill

### 3. Skill เหมือนคำสั่ง slash หรือไม่

ไม่เหมือนกันทั้งหมด คำสั่ง slash คล้ายทางลัด ส่วน Skill คล้ายแพ็กเกจงานที่มีคำอธิบายและขั้นตอนครบถ้วน

Skill ไม่จำเป็นสำหรับการเริ่มต้น แต่เหมาะกับการจัดระเบียบ workflow ที่เกิดซ้ำแล้ว

## ขอบเขตความปลอดภัย

- สคริปต์และการเรียก MCP ใน Skill ใช้นโยบายอนุมัติปัจจุบัน
- ห้าม hard-code secret ใน Skill ให้ใช้ environment variable หรือการยืนยันตัวตนของ MCP
- ทีมควรตรวจทาน Skill ภายนอกเหมือนตรวจ dependency package

## ข้อผิดพลาดที่พบบ่อย

- `description` ยาวหรือกว้างเกินไป ทำให้ไม่เคยทริกเกอร์หรือทริกเกอร์ผิด
- ใส่ workflow ที่ไม่เกี่ยวข้องกันสิบแบบไว้ใน Skill เดียว
- ใช้สคริปต์แทนขั้นตอนที่อธิบายเป็นข้อความได้ชัดเจน ทำให้ดูแลยาก
