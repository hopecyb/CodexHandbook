MCP เปลี่ยน “โมเดลต้องการใช้ความสามารถภายนอก” ให้เป็นการเรียกเครื่องมือแบบมีโครงสร้าง เหมาะสำหรับเชื่อมเอกสารภายนอก เบราว์เซอร์ Figma ระบบ ticket หรือบริการภายใน

![ภาพประกอบ: ผู้ช่วยตัวเล็กเชื่อมกับศูนย์กลางอะแดปเตอร์ สายมาตรฐานต่อไปยังฐานข้อมูล ปฏิทิน บอร์ด ticket และ cloud drive](/illustrations/mcp-overview.webp)

## สายการเรียกหนึ่งรอบ

```text
Codex ในงาน
  -> MCP client (จัดให้โดย Codex host)
  -> MCP server (process ในเครื่องหรือบริการระยะไกล)
  -> ระบบภายนอก (เอกสาร ดีไซน์ ticket และ API ภายใน)
  -> ส่งผลลัพธ์แบบมีโครงสร้างกลับสู่งาน
```

| ส่วนประกอบ | รับผิดชอบอะไร | ไม่รับผิดชอบอะไร |
|---|---|---|
| Codex host | อ่าน config เชื่อมเซิร์ฟเวอร์ และให้เครื่องมือแก่ Agent | ไม่กำหนดสิทธิ์ธุรกิจแทนเซิร์ฟเวอร์ |
| MCP server | นิยามเครื่องมือ การยืนยันตัวตน พารามิเตอร์ และผลลัพธ์แบบมีโครงสร้าง | ไม่รับประกันความปลอดภัยของเครื่องมือโดยอัตโนมัติ |
| Skill | กำหนดว่าใช้เครื่องมือเมื่อใดและตามขั้นตอนใด | ไม่สร้างการเชื่อมต่อเครือข่าย |
| Plugin | รวมและแจกจ่าย Skills, connectors, MCP และความสามารถอื่น | ไม่ใช่โปรโตคอลเครื่องมืออีกแบบ |

## วิธีเชื่อมเซิร์ฟเวอร์ที่รองรับปัจจุบัน

### STDIO

Codex เริ่ม process ในเครื่องและสื่อสารผ่าน standard input/output เหมาะกับเครื่องมือพัฒนาในเครื่องและบริการที่รันเฉพาะเครื่องปัจจุบัน

ความเสี่ยงหลัก: process นี้รับสภาพแวดล้อมการทำงานของเครื่อง จึงต้องตรวจคำสั่ง แหล่ง dependency และ environment variable ที่ส่งต่อ

### Streamable HTTP

Codex เชื่อมไปยังที่อยู่ระยะไกล เอกสารทางการปัจจุบันยืนยันว่ารองรับ Bearer token, OAuth และการยืนยันตัวตนด้วย session ChatGPT สำหรับเซิร์ฟเวอร์ first-party ที่เชื่อถือได้

ความเสี่ยงหลัก: บริการระยะไกลจะได้รับพารามิเตอร์เครื่องมือ ต้องยืนยัน TLS, ตัวตน, log, การเก็บข้อมูล และสิทธิ์เครื่องมือ

## MCP, Skill และ Plugin ใช้ร่วมกันอย่างไร

ใช้ “ตรวจ ticket ความสำคัญสูงทุกสัปดาห์” เป็นตัวอย่าง:

| ชั้น | เนื้อหา |
|---|---|
| MCP | มีเครื่องมืออย่าง `search_issues` และ `get_issue` |
| Skill | กำหนดเงื่อนไขคัดกรอง ข้อกำหนดหลักฐาน และรูปแบบรายงาน |
| Plugin | ให้ทีมติดตั้ง Skill, connector และนิยาม MCP |
| Scheduled task | รันงานที่ตรวจสอบแล้วตามเวลาตายตัว |

แต่ละส่วนมีหน้าที่ตั้งฉากกัน ไม่ใช่บันไดอัปเกรดจากต่ำไปสูง ดูความสัมพันธ์ทั้งหมดที่ [แผนที่ความสามารถส่วนขยาย](/th/skills/capability-map/)

## เมื่อใดคุ้มค่าที่จะเชื่อม MCP

| คุ้มค่า | ยังไม่คุ้มค่า |
|---|---|
| ค้นระบบภายนอกเดียวกันซ้ำ ๆ | ค้นหน้าเว็บสาธารณะครั้งเดียว |
| ต้องใช้พารามิเตอร์และผลลัพธ์เครื่องมือแบบมีโครงสร้าง | การทำงานกับไฟล์ในรีโพซิทอรีเพียงพอแล้ว |
| ต้องใช้ OAuth หรือควบคุมเครื่องมืออย่างละเอียด | มีแต่ write API สิทธิ์สูงและไม่มีสภาพแวดล้อมทดสอบ |
| ทีมต้องนำการเชื่อมต่อเดียวกันกลับมาใช้ | ตรวจแหล่งที่มาของเซิร์ฟเวอร์ไม่ได้ |

## ระดับความปลอดภัย

1. **ทดลองแบบ read-only**: เอกสารสาธารณะหรือ tenant ทดสอบ เปิดใช้เฉพาะเครื่องมือค้นหา
2. **ตรวจระดับทีม**: จำกัดโปรเจกต์ บทบาท และ allowlist เครื่องมือ พร้อมบันทึกความล้มเหลวและเวลาที่ใช้
3. **เขียนแบบจำกัด**: การเขียนขอบเขตเล็กที่ย้อนกลับได้ โดยคงการอนุมัติจากมนุษย์
4. **รันภายใต้การกำกับ**: ถอนสิทธิ์ได้ ตรวจ config ได้ log ลบข้อมูลละเอียดอ่อน และแยกตามสภาพแวดล้อม

อย่าเขียน token ลงพรอมป์ Git หรือ static HTTP header ให้ใช้ OAuth, `bearer_token_env_var` หรือการส่งต่อ environment variable ก่อน

## รายการตรวจก่อนเชื่อม

- [ ] ตรวจแหล่งที่มา เวอร์ชัน และคำสั่งเริ่มเซิร์ฟเวอร์ได้
- [ ] แยกรายการเครื่องมืออ่านและเขียนแล้ว
- [ ] ใช้ tenant ทดสอบหรือบัญชีสิทธิ์น้อยที่สุด
- [ ] ทราบว่าพารามิเตอร์และผลลัพธ์ใดจะเข้า log ระยะไกล
- [ ] การเขียนมี path สำหรับอนุมัติ ย้อนกลับ และ audit
- [ ] ทีมรู้วิธีปิดเซิร์ฟเวอร์และถอนสิทธิ์
