ปัญหา MCP มักถูกรวมเป็นคำว่า “เครื่องมือใช้ไม่ได้” วิธีที่เร็วกว่าคือหาก่อนว่าล้มเหลวในชั้นใด แล้วเปลี่ยนทีละตัวแปร

![ภาพประกอบ: ภาพตัดโปร่งใสสี่ชั้น ได้แก่ config, transport, การยืนยันตัวตน และเครื่องมือ ผู้ช่วยตัวเล็กใช้ไฟฉายตรวจทีละชั้น โดยกำลังซ่อมท่อขาดในชั้นหนึ่ง](/illustrations/mcp-debugging.webp)

## เก็บหลักฐานสี่รายการก่อน

```bash
codex mcp list
codex mcp --help
node --version   # เฉพาะเมื่อเซิร์ฟเวอร์ STDIO ใช้ Node.js
python3 --version # เฉพาะเมื่อเซิร์ฟเวอร์ STDIO ใช้ Python
```

บันทึกเพิ่มเติม: ชื่อเซิร์ฟเวอร์ ใช้ STDIO หรือ Streamable HTTP, error ต้นฉบับ และเกิดใน Desktop App/CLI/IDE ใด อย่าบันทึก token ฉบับเต็ม

## แยกวินิจฉัยสี่ชั้น

| ชั้น | อาการทั่วไป | ตรวจอะไรก่อน |
|---|---|---|
| config | เซิร์ฟเวอร์ไม่อยู่ในรายการ | path ไฟล์ ไวยากรณ์ TOML ชื่อเซิร์ฟเวอร์ และ `enabled` |
| เริ่ม/เชื่อมต่อ | initialization timeout | คำสั่ง STDIO และ PATH หรือ HTTP URL, TLS และ proxy |
| การยืนยันตัวตน | 401/403 หรือขอเข้าสู่ระบบ | สถานะ OAuth, environment variable ของ token และ scope |
| เครื่องมือ | เซิร์ฟเวอร์ออนไลน์แต่เรียกไม่สำเร็จ | ชื่อเครื่องมือ พารามิเตอร์ allowlist และ timeout เครื่องมือ |

## 1. ยืนยันว่า config ถูกอ่านจริง

- ไฟล์ระดับผู้ใช้คือ `~/.codex/config.toml`
- ไฟล์ระดับโปรเจกต์คือ `.codex/config.toml` และโหลดเฉพาะในโปรเจกต์ที่เชื่อถือได้
- Desktop App, CLI และ IDE แชร์ config บน Codex host เดียวกัน อย่าสร้างสำเนาสามชุดที่ค่อย ๆ ต่างกัน
- ใช้ `codex mcp list` หรือ `/mcp` ใน session ดูสถานะจริง อย่าถือว่า “ไฟล์มีอยู่” เป็นหลักฐานความสำเร็จ

## 2. เซิร์ฟเวอร์ STDIO เริ่มไม่สำเร็จ

ตรวจว่า `command` อยู่ใน PATH, เวอร์ชัน runtime ตรงตามข้อกำหนดเซิร์ฟเวอร์, `cwd` มีอยู่ และแหล่ง dependency เชื่อถือได้

การรันคำสั่งเริ่มโดยตรงพิสูจน์ได้เพียงว่า “executable เริ่มได้” เมื่อ MCP server รออินพุตโปรโตคอล การดูเหมือนไม่จบอาจเป็นเรื่องปกติ อย่าถือเป็นการทดสอบเรียกเครื่องมือแบบเต็ม

พิจารณาเพิ่ม `startup_timeout_sec` เฉพาะเมื่อ initialization ช้าจริง ค่าเริ่มต้นคือ 10 วินาที การเพิ่มเป็นค่ามากโดยไม่ตรวจจะเพียงซ่อนคำสั่งที่ผิด

## 3. เชื่อม Streamable HTTP ไม่สำเร็จ

ตรวจตามลำดับ:

1. URL และ TLS certificate
2. proxy ของบริษัทหรือ VPN
3. environment variable ที่ `bearer_token_env_var` ชี้อยู่มีหรือไม่
4. OAuth ต้องรัน `codex mcp login <server-name>` ใหม่หรือไม่
5. log ฝั่งเซิร์ฟเวอร์ได้รับคำขอ initialization หรือไม่

อย่าเปลี่ยน token เป็นค่า static `http_headers` เพื่อ “แก้ปัญหาชั่วคราว” เพราะเข้าไฟล์ config และภาพหน้าจอได้ง่าย

## 4. เซิร์ฟเวอร์ออนไลน์แต่เครื่องมือใช้ไม่ได้

| อาการ | ตรวจอะไร |
|---|---|
| เครื่องมือไม่ปรากฏเลย | `enabled_tools` / `disabled_tools` และรายการเครื่องมือที่เซิร์ฟเวอร์ส่งกลับ |
| Tool not found | เวอร์ชันเซิร์ฟเวอร์ การเปลี่ยนชื่อเครื่องมือ และ session ยังถือรายการเก่าหรือไม่ |
| ตรวจพารามิเตอร์ไม่ผ่าน | เทียบกับ schema เครื่องมือ อย่าเดาฟิลด์จากพรอมป์เก่า |
| เรียก timeout | ลดขอบเขต query แล้วตรวจ `tool_timeout_sec`; ค่าเริ่มต้น 60 วินาที |
| ผลลัพธ์ว่าง | ใช้บัญชีเดียวกันตรวจขอบเขตข้อมูลและเงื่อนไขกรองในระบบต้นทาง |

## พรอมป์ทำซ้ำขั้นต่ำ

```text
ตรวจเฉพาะเซิร์ฟเวอร์ MCP <server-name>:
1. รายงานชื่อเครื่องมือที่มองเห็นในขณะนี้;
2. เรียก <readonly-tool> โดยใช้เฉพาะ <minimal-arguments>;
3. คงประเภท error และข้อความเซิร์ฟเวอร์ตามเดิม แต่ซ่อน credential;
4. ห้ามเรียกเซิร์ฟเวอร์อื่นและห้ามเขียนข้อมูล
```

## เกณฑ์การยอมรับเมื่อแก้ปัญหาเสร็จ

- [ ] สถานะใน `codex mcp list` ตรงตามคาด
- [ ] เครื่องมือ read-only หนึ่งรายการทำงานสำเร็จด้วยพารามิเตอร์ขั้นต่ำ
- [ ] ระบุสาเหตุรากในชั้นที่เจาะจง ไม่ใช่ “หายหลัง restart”
- [ ] ถอน token ชั่วคราว debug log และสิทธิ์กว้างแล้ว
- [ ] อัปเดต config ทีมและคำอธิบายการแก้แล้ว
