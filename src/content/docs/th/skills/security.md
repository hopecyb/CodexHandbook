Skill ไม่ได้เป็นเพียงเทมเพลตพรอมป์อีกหนึ่งชุด

Skill มีผลต่อวิธีทำงานของ Codex และบางครั้งมีสคริปต์หรือทรัพยากรเพิ่มเติม

ดังนั้นเมื่อแหล่งที่มาไม่น่าเชื่อถือ เนื้อหาไม่ได้รับการตรวจ หรือเวอร์ชันคลาดเคลื่อน ความเสี่ยงก็แทบไม่ต่ำกว่า MCP หน้านี้อธิบายวิธีที่ทีม **เลือก ติดตั้ง อัปเกรด และ audit** Skill

![ภาพประกอบ: แพ็กเกจ Skill ถูกส่งมาตามสายพาน ก่อนติดตั้งมีแว่นขยายตรวจแหล่งที่มา โล่ยืนยัน ประตูสิทธิ์ล็อก และเก็บเวอร์ชันเก่าไว้สำหรับย้อนกลับ](/illustrations/skills-security.webp)

## เนื้อหา

- Skill แบบใดไม่ควรติดตั้ง
- การ pin เวอร์ชันและตรวจทานการเปลี่ยนแปลง
- ความสัมพันธ์กับการแจกจ่ายผ่าน Plugin

## ทำไมผู้ใช้ทั่วไปก็ต้องรู้

หากคุณทำสิ่งเหล่านี้:

- ติดตั้ง Skill ที่ผู้อื่นแชร์
- อ้าง Skill ของทีมในโปรเจกต์
- อัปเกรด Skill ที่มีอยู่
- แนะนำ Skill ให้เพื่อนร่วมงาน

คุณก็มีส่วนในสายการแพร่กระจายความเสี่ยงแล้ว

ความปลอดภัยของ Skill พึ่งเพียง “มีผู้ดูแลรวมศูนย์” ไม่ได้ ผู้ใช้ทุกคนต้องมีวิจารณญาณพื้นฐาน

พื้นฐาน: [ภาพรวม Skill](/th/skills/overview/) · [สร้าง Skill แรก](/th/skills/create-your-first-skill/)

## โมเดลภัยคุกคาม (ฉบับย่อ)

| ความเสี่ยง | ลักษณะ |
|---|---|
| Skill ประสงค์ร้าย | ชักนำให้เปิดเผย secret หรือรัน shell ที่ทำลายข้อมูล |
| สิทธิ์มากเกินไป | อ่านหรือเขียน path ที่ไม่ควรแตะ |
| supply chain | พึ่งรีโพซิทอรี Skill ภายนอกที่ถูกแก้ไขโดยมิชอบ |
| Skill ล้าสมัย | ใช้กับ CLI ใหม่ไม่ได้และทำงานผิดปกติ |

## ต้องตรวจอะไรก่อนติดตั้ง

เมื่อพบ Skill ให้เริ่มจากถามสามเรื่อง:

1. มาจากที่ใด
2. จะทำให้ Codex ทำอะไรเพิ่ม
3. คุณอ่าน `SKILL.md` และสคริปต์ที่แนบมาเข้าใจหรือไม่

หากตอบไม่ได้สองในสามข้อ ก็ไม่เหมาะจะใส่ในโปรเจกต์จริงโดยตรง

## หลักการติดตั้ง

1. **แหล่งที่มา**: ให้ความสำคัญกับ marketplace ทางการและ Git ภายในบริษัท ระวัง gist ที่ไม่ระบุตัวตน
2. **อ่าน**: เปิด `SKILL.md` และสคริปต์แนบก่อนติดตั้ง ตรวจว่าขอสิทธิ์ผิดปกติหรือไม่
3. **แยก**: แยกไดเรกทอรี Skill ของโปรเจกต์ลูกค้ากับการทดลองส่วนตัว
4. **ใช้น้อยที่สุด**: หาก Skill เดียวแก้ปัญหาได้ อย่าซ้อนสิบรายการ

## ความเข้าใจผิดที่พบบ่อย

### 1. Skill เป็นเพียงคำอธิบายข้อความ จึงไม่มีความเสี่ยงจริง

Skill มีผลต่อ workflow การเลือกเครื่องมือ และวิธีรันสคริปต์ ความเสี่ยงจึงไม่ใช่เพียง “น้ำเสียงเปลี่ยนไป”

### 2. Skill ที่คนอื่นใช้กันมากใส่โปรเจกต์ production ได้ทันที

ผู้อื่นใช้ได้ไม่ได้หมายความว่าเหมาะกับรีโพซิทอรี ขอบเขตสิทธิ์ และกฎทีมของคุณ

### 3. อัปเกรด Skill คล้ายอัปเกรดเอกสารหนึ่งไฟล์

สำหรับทีม การอัปเกรด Skill คือการอัปเกรดพฤติกรรมอัตโนมัติ จึงควรจริงจังเท่าการอัปเกรด dependency

## เวอร์ชันและการอัปเกรด

| แนวปฏิบัติ | คำอธิบาย |
|---|---|
| Pin เวอร์ชัน | บันทึกชื่อ Skill + commit/tag ในเอกสารทีม |
| ตรวจทานการเปลี่ยนแปลง | ให้การอัปเดต Skill ผ่าน PR เหมือนอัปเกรด dependency |
| changelog | ดูแล release note ของชุด Skill ทีม |
| ย้อนกลับ | เก็บสำเนาเวอร์ชันก่อนหน้า และสลับกลับอย่างรวดเร็วเมื่อมีปัญหา |

Plugin สามารถแพ็กและแจก Skill แบบรวมศูนย์: [ภาพรวม Plugins](/th/skills/plugins/plugins-overview/)

## แนวปฏิบัติของทีม

หาก Skill หนึ่งจะถูกหลายคนนำกลับมาใช้ในระยะยาว อย่าปล่อยให้อยู่ในรูป “มีใครส่ง path ทางแชต”  
วิธีที่เหมาะกว่าคือ:

- มีแหล่งที่มาตายตัว
- มีบันทึกเวอร์ชัน
- มีคำอธิบายการอัปเกรด
- มี path ย้อนกลับ

## ความสัมพันธ์กับการเรียก `$skill`

เมื่อผู้ใช้เรียกด้วย `$name` อย่างชัดเจน เจตนาจะชัดกว่า ส่วนเมื่อ **โมเดลเลือก Skill อัตโนมัติ** ควรจำกัดรายการและสถานการณ์ที่ใช้ได้ใน `AGENTS.md`

## รายการกำกับดูแลของทีม

- [ ] allowlist แหล่ง Skill ที่ติดตั้งได้
- [ ] onboarding พนักงานใหม่ติดตั้งเฉพาะ “แพ็กเกจพื้นฐาน”
- [ ] ตรวจทุกไตรมาสว่ายังต้องใช้ Skill ใด
- [ ] สอดคล้องกับ [กฎอนุญาตและปฏิเสธ](/th/guide/customization/rules/allow-and-deny-patterns/)

## ข้อผิดพลาดที่พบบ่อย

- ติดตั้ง “Skill สารพัดประโยชน์คลิกเดียว” จากลิงก์แชต
- `AGENTS.md` ของรีโพซิทอรี production อ้าง Skill จาก path ส่วนตัว
- ไม่รัน smoke task หลังอัปเกรด
- เชื่อถือพฤติกรรมโดยไม่เปิดดู `SKILL.md`
