เมื่อเริ่มสร้าง Skill วิธีที่พบบ่อยคือเขียนทุกอย่างลง `SKILL.md` workflow ง่ายสามารถทำเช่นนี้ได้ แต่เมื่อขั้นตอนใดต้องรันอย่าง **เสถียร ทำซ้ำได้ และตรวจสอบได้** สคริปต์จะเชื่อถือได้กว่าคำอธิบายข้อความล้วน

ให้สคริปต์ทำการกระทำตายตัว ส่วนการตัดสินและ workflow การทำงานร่วมกันคงไว้ใน Skill

เมื่อขั้นตอนหนึ่งต้องทำแบบกำหนดแน่นอน (รันการทดสอบ สร้าง diff ตรวจรูปแบบ) ให้มีสคริปต์ใน `scripts/` และอธิบายใน `SKILL.md` ว่าควรเรียกเมื่อใด

![ภาพประกอบ: ผู้ช่วยตัวเล็กส่งขั้นตอนซ้ำให้เครื่องจักรทำ (สคริปต์แบบกำหนดแน่นอน) ผลลัพธ์ผ่านด่านทดสอบ ไฟเขียวแสดงว่าผ่าน ส่วนไฟแดงกำลังถูกแก้](/illustrations/skills-scripts.webp)

## ตัวอย่าง

```text
my-skill/
├── SKILL.md
└── scripts/
    └── run-checks.sh
```

## เมื่อใดควรพิจารณา `scripts/`

หากขั้นตอนหนึ่งตรงกับข้อใดข้อหนึ่งต่อไปนี้ ควรพิจารณาสคริปต์ก่อน:

- ทุกครั้งควรรันเหมือนกันทั้งหมด
- exit code มีความหมายในตัวเอง
- การอธิบายด้วยภาษาธรรมชาติจะเยิ่นเย้อ
- ต้องการให้ CI หรือเครื่องมืออื่นนำกลับไปใช้ได้ในอนาคต

การกระทำอย่าง “รันการตรวจ” “สร้าง diff” “ตรวจรูปแบบ” และ “export รายงานตายตัว” เหมาะจะใส่ในสคริปต์

## คำแนะนำด้านการทดสอบ

- รันสคริปต์ด้วยตนเองในรีโพซิทอรีฝึก เพื่อยืนยัน exit code และผลลัพธ์
- ทริกเกอร์ workflow แบบ end-to-end ผ่าน Skill แล้วตรวจว่าสคริปต์ถูกเรียกตามคาด
- ในบริบททีม ให้ตรวจใน CI หรือ pre-commit ว่าสคริปต์ยังใช้ได้

## ความเข้าใจผิดที่พบบ่อย

### 1. การเพิ่มสคริปต์ทำให้ Skill ซับซ้อน จึงไม่ควรใช้

หากสคริปต์ทำให้ขั้นตอนที่ไม่เสถียรกลายเป็นตายตัว ภาพรวมจะง่ายขึ้น

### 2. สคริปต์รันในเครื่องได้ แสดงว่า Skill ไม่มีปัญหาแน่นอน

ยังต้องตรวจว่า:

- Skill ทริกเกอร์สคริปต์ถูกต้องหรือไม่
- นโยบายอนุมัติจะบล็อกหรือไม่
- ยังรันได้ในสภาพแวดล้อมทีมหรือ CI หรือไม่

### 3. “ทดสอบ Skill” คือทดสอบสคริปต์

ยังไม่พอ

การทดสอบสคริปต์ตรวจการกระทำหนึ่งอย่าง  
ส่วน Skill ต้องตรวจด้วยว่า “เรียกเมื่อใด เรียกอย่างไร และผลลัพธ์ตรงตามคาดหรือไม่”

## ลำดับตรวจสอบที่ใช้บ่อย

เมื่อเริ่มทำ ให้ทำตามลำดับนี้:

1. รันสคริปต์แยกก่อน
2. ตรวจว่า exit code และผลลัพธ์ชัดเจนหรือไม่
3. ให้ Skill เรียก workflow เต็มหนึ่งครั้ง
4. ทดสอบอีกครั้งในสภาพแวดล้อมที่ใกล้ของจริงกว่า

วิธีนี้ช่วยแยก “ตัวสคริปต์เสีย” ออกจาก “วิธี integrate Skill ไม่ถูกต้อง” ได้ง่ายขึ้น

การกระทำที่ต้องทำซ้ำอย่างเสถียรไม่ควรพึ่งเพียงคำอธิบายข้อความ ทำให้สคริปต์รันได้ก่อน แล้วจึงยืนยันว่า Skill เรียกถูกต้อง
