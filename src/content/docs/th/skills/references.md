`references/` เหมาะสำหรับข้อมูลยาวที่ไม่จำเป็นต้องขยายทันทีทุกครั้ง ช่วยไม่ให้ workflow หลักยาวและยุ่งเหยิง

หน้าที่ไม่ได้มีเพียง “เพิ่มเอกสารอีกสองสามไฟล์” แต่คือแยกข้อมูลที่ **ไม่ต้องอ่านทันทีทุกครั้ง แต่มีประโยชน์จริงในบางขั้น** ไว้ แล้วอ่านเมื่อจำเป็น

เมื่อเนื้อหา `SKILL.md` ยาวเกินไป ให้ย้ายมาตรฐานโดยละเอียด คำอธิบาย API และรายการตรวจสอบไปยัง `references/` แล้วอ้างอิงตามต้องการในขั้นตอน

## ตัวอย่าง

```text
my-skill/
├── SKILL.md
└── references/
    ├── style-guide.md
    └── api-contracts.md
```

เขียนใน `SKILL.md` ว่า:

```md
เมื่อตรวจสไตล์โค้ด ให้อ่าน references/style-guide.md แล้วตรวจตามกฎภายใน
```

## ทำหน้าที่อะไร

- `SKILL.md` รับผิดชอบ workflow หลัก
- `references/` รับผิดชอบ “ข้อมูลที่จะเปิดเมื่อจำเป็น”

มองอย่างง่ายได้ว่า:

- `SKILL.md` คือคำอธิบายงาน
- `references/` คือตู้ข้อมูล

วิธีนี้ช่วยไม่ให้ข้อมูลพื้นหลังจำนวนมากท่วมผู้อ่านตั้งแต่เปิด Skill และยังค้นหาหลักฐานได้เมื่อต้องการรายละเอียด

## เมื่อใดควรแยก `references/`
หาก `SKILL.md` เริ่มมีสถานการณ์ต่อไปนี้ ให้พิจารณาแยก:

- คำอธิบายมาตรฐานยาวกินพื้นที่ทุกครั้ง
- มีเอกสารอ้างอิงหลายหัวข้อปะปนกัน
- วัสดุพื้นหลังขัดจังหวะ workflow หลักจนอ่านครั้งแรกจับประเด็นยาก

Skill แรกไม่จำเป็นต้องมี `references/`  
ลำดับที่พบบ่อยคือ **ทำให้รันได้ก่อน แล้วค่อยแยกเมื่อเนื้อหายาวขึ้นจริง**
## ความเข้าใจผิดที่พบบ่อย

### 1. `references/` ไม่ใช่แค่คัดลอกเนื้อหาบางส่วนออกไป

หน้าที่สำคัญกว่าคือทำให้ workflow หลักสั้น ชัด และรันได้ก่อน

### 2. เอกสารอ้างอิงไม่ได้ยิ่งมากยิ่งดี

หากใส่ทุกอย่างลง `references/` ก็เพียงย้ายความสับสนจากไฟล์เดียวไปหลายไฟล์

### 3. เมื่อมี `references/` แล้ว `SKILL.md` เขียนสั้นมากได้

ไม่ได้ workflow หลักยังควรอยู่ใน `SKILL.md` มิฉะนั้นผู้อ่านครั้งแรกก็ยังไม่รู้ว่าต้องทำอย่างไร

## หลักการ

- เก็บ workflow หลักไว้ใน `SKILL.md` และโหลดเอกสารอ้างอิงเมื่อต้องการ
- หนึ่งไฟล์เน้นหนึ่งหัวข้อ เพื่อให้ดูแลง่าย
- หลีกเลี่ยงการทำซ้ำขั้นตอนจาก SKILL.md ใน references
