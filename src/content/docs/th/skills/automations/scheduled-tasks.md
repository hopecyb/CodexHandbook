ส่วนที่ยากจริงของงานตามกำหนดเวลาไม่ใช่ “รันกี่โมง” แต่คือทำให้การรันแบบไม่มีผู้ดูแลแต่ละครั้งมีอินพุตเสถียร สิทธิ์แคบ ผลลัพธ์ที่ตรวจได้ และเงื่อนไขหยุด

![วงจรปลอดภัยจากการตรวจด้วยตนเอง ไปสู่การรันตามเวลา การตรวจโดยมนุษย์ และการปรับ](/illustrations/flow-scheduled-safety.webp)

## เหมาะกับใคร

- ผู้ใช้รายบุคคลที่ต้องการสร้างรายงาน ตรวจเอกสาร หรือติดตาม PR รายวันหรือรายสัปดาห์
- นักพัฒนาที่ต้องรันงานดูแลเป็นคาบในโปรเจกต์ในเครื่องหรือ worktree ที่แยก
- ผู้ดูแลที่รับผิดชอบประเมินสิทธิ์ การจัดการความล้มเหลว และ Skill ที่แชร์ในทีม

## ขอบเขตการรองรับ

| พื้นผิว | ทำอะไรได้ | ข้อจำกัดสำคัญ |
|---|---|---|
| ChatGPT Web | สร้าง จัดการ และดูการรัน ใช้ไฟล์อัปโหลด เครื่องมือเชื่อมต่อ Skills และ Plugins | เข้าถึงโฟลเดอร์ในเครื่องโดยตรงไม่ได้ |
| ChatGPT Desktop App | สร้างและจัดการ เลือกโปรเจกต์ในเครื่องหรือ Git worktree ได้ | งานไฟล์ในเครื่องต้องเปิดเครื่อง App ทำงาน และโปรเจกต์ยังอยู่ |
| Codex CLI | เตรียมและทดสอบพรอมป์ Skill และสคริปต์ด้วยตนเอง | ไม่มีอินเทอร์เฟซจัดการ Scheduled task |
| IDE extension | ตรวจคำสั่งและการแก้ไขใน workspace | ไม่มีอินเทอร์เฟซจัดการ Scheduled task |

## 1. เลือก task แยกหรือ task ในแชต

### Scheduled task แบบแยก

แต่ละรอบเริ่มจากพรอมป์ที่บันทึกไว้ และปรากฏเป็นการรันแยกใน Scheduled เหมาะกับรายงานรายวัน รายสัปดาห์ และการตรวจสุขภาพโปรเจกต์ที่เป็นอิสระต่อกัน task เดียวอาจครอบคลุมหลายโปรเจกต์ได้

### Scheduled task ในแชต

กลับมาที่แชตเดิมตามเวลาและใช้บริบทที่มีอยู่ เหมาะกับการ polling งานระยะยาว ติดตามสถานะ PR วิจัยต่อเนื่อง หรืองานที่ต้องเก็บการอภิปรายครั้งก่อน

เกณฑ์เลือก: หากแต่ละรอบควร “เริ่มใหม่” ให้เลือก task แยก หากต้องต่อบริบทของปัญหาเดิม ให้เลือก task ในแชต

## 2. เลือกวัสดุสำหรับรัน

### รันบน Web

เขียนคำสั่งที่ทนทานไว้ในพรอมป์ task หรือ Skill และวางข้อมูลที่ต้องใช้ในไฟล์อัปโหลด Project หรือบริการที่เชื่อมต่อ อย่าเขียนว่า “อ่าน latest.csv บนเดสก์ท็อปของฉัน” เพราะ Web เข้าถึง path ในเครื่องโดยตรงไม่ได้

### ใช้โปรเจกต์ในเครื่องจาก Desktop App

รีโพซิทอรี Git เลือกได้ดังนี้:

- **โปรเจกต์ในเครื่อง**: ทำงานใน main checkout โดยตรง และอาจแตะไฟล์ที่คุณกำลังแก้
- **worktree เฉพาะ**: แยกการแก้เบื้องหลังจากงานที่ยังไม่เสร็จ เหมาะกับ task ที่แก้ไฟล์

โปรเจกต์ที่ไม่ใช่ Git จะรันในไดเรกทอรีโปรเจกต์โดยตรง task worktree ความถี่สูงสะสม working tree ได้ ให้ archive การรันที่ไม่ต้องใช้แล้วเพื่อไม่ให้เก็บ worktree จำนวนมากโดยไม่ตั้งใจ

## 3. ตรวจด้วยตนเองก่อน

รันพรอมป์ โมเดล reasoning effort และเครื่องมือชุดเดียวกันในแชตทั่วไปก่อน อย่างน้อยต้องยืนยันว่า:

- อินพุตยังชัดเมื่อไม่มีคำอธิบายเฉพาะหน้า
- เมื่อ “ไม่มีการเปลี่ยนแปลง” จะจบเงียบ ๆ
- มนุษย์ตรวจผลลัพธ์ได้รวดเร็ว
- คำสั่ง Skill และเครื่องมือเชื่อมต่อทำงาน
- เมื่อขาดสิทธิ์หรือวัสดุ จะหยุดและอธิบายแทนการเดา

ตรวจการรันตามเวลาช่วงแรก แล้วจึงปรับพรอมป์หรือความถี่

## 4. พรอมป์ task ที่นำไปปรับได้ทันที

```text
โปรดสร้าง Scheduled task แบบแยก:

ชื่อ: ตรวจลิงก์เสียในเอกสารประจำสัปดาห์
เวลา: ทุกวันจันทร์ 09:00 ใช้เขตเวลาปัจจุบัน
ตำแหน่งรัน: worktree เฉพาะของโปรเจกต์ Git ปัจจุบัน

ในแต่ละรอบให้ทำดังนี้:
1. อ่านเฉพาะ docs/, src/content/docs/, examples/ และ public/diagrams/
2. รัน pnpm check:links
3. หากการตรวจผ่าน ให้รายงานเฉพาะจำนวนไฟล์และลิงก์ที่ตรวจ โดยไม่แก้ไฟล์
4. หากการตรวจล้มเหลว ให้ระบุผลตาม “ไฟล์ต้นทาง เป้าหมายที่ใช้ไม่ได้ วิธีแก้ที่แนะนำ” และอย่าแก้ลิงก์อัตโนมัติ
5. ห้ามเชื่อมต่ออินเทอร์เน็ต ติดตั้ง dependency, commit, push หรือสร้าง PR
6. หากไม่มีคำสั่ง ขาด dependency หรือผลไม่แน่นอน ให้หยุดและอธิบายรายการที่ต้องให้มนุษย์จัดการอย่างเจาะจง

เงื่อนไขว่าเสร็จ: จบรอบหลังส่งรายงานที่ตรวจทานได้หนึ่งฉบับ และไม่ลองซ้ำ
```

พรอมป์นี้ระบุเวลา โปรเจกต์ ขอบเขตการอ่าน คำสั่ง branch สำเร็จ/ล้มเหลว การกระทำต้องห้าม และเงื่อนไขจบครบถ้วน การกำหนดเวลามีหน้าที่เพียงทริกเกอร์อีกครั้ง แทนคำอธิบายงานไม่ได้

## 5. สิทธิ์และการตรวจโดยมนุษย์

งานตามกำหนดเวลารันโดยไม่มีผู้ดูแล และใช้การตั้งค่า sandbox เริ่มต้น

| โหมด sandbox | ผลทั่วไป |
|---|---|
| read-only | การแก้ไฟล์ เชื่อมต่ออินเทอร์เน็ต หรือควบคุม App ในเครื่องล้มเหลว |
| workspace-write | เขียน workspace ได้ การเขียนนอก workspace เชื่อมต่ออินเทอร์เน็ต หรือควบคุม App ล้มเหลวเป็นค่าเริ่มต้น |

เริ่มจากสิทธิ์ที่แคบที่สุดแต่ทำงานสำเร็จ เมื่อต้องใช้เครือข่ายหรือเข้าถึงไฟล์กว้างขึ้น ให้ระบุ allowlist ชัดเจน อย่าเพิ่มสิทธิ์ทั้ง task เพียงเพื่อกำจัดความล้มเหลวครั้งเดียว

ควรคงการตรวจโดยมนุษย์ไว้สำหรับ:

- ส่งข้อความหรือเผยแพร่เนื้อหาภายนอก
- เปลี่ยนสถานะ production
- merge PR หรือ push main branch
- ลบจำนวนมาก ย้ายข้อมูล หรือแก้สิทธิ์
- diff เกินขอบเขตที่คาด หรือการทดสอบล้มเหลว

## 6. ออกแบบ “ไม่มีการเปลี่ยนแปลง” ความล้มเหลว และการหยุด

task ที่ทนทานต้องนิยามสาม path:

1. **พบสิ่งใหม่**: ส่งหลักฐาน ระดับความรุนแรง และขั้นถัดไป
2. **ไม่มีการเปลี่ยนแปลง**: รายงานขอบเขตการตรวจสั้น ๆ โดยไม่สร้างปัญหาปลอม
3. **ทำไม่สำเร็จ**: อธิบายวัสดุ/สิทธิ์ที่ขาด หยุด และรอมนุษย์

การ polling ในแชตยังต้องมีเงื่อนไขยุติ เช่น “หยุดเมื่อ PR merge, ปิด, พบ error เดิมติดต่อกัน 3 ครั้ง หรือต้องให้มนุษย์อนุมัติ”

## Scheduled task ไม่ใช่ CI ที่ขับเคลื่อนด้วย event

หาก task ต้องรันทันทีหลังเกิด event ของรีโพซิทอรี เช่น `push`, สร้าง PR หรือเผยแพร่เสร็จ ให้ใช้ GitHub Actions, CI, webhook หรือ Codex SDK เป็นจุดเข้า อย่าใช้ “poll ทุกนาที” แทน event trigger ที่แม่นยำ

## รายการตรวจรับ

- [ ] รันพรอมป์ครบถ้วนในแชตทั่วไปแล้ว
- [ ] เลือก task แยกหรือ task ในแชตแล้ว
- [ ] วัสดุ Web หรือโปรเจกต์ในเครื่องพร้อมใช้ตอนรัน
- [ ] sandbox เริ่มต้นเพียงพอ และมีเหตุผลชัดสำหรับสิทธิ์เพิ่ม
- [ ] ระบุ path เมื่อพบสิ่งใหม่ ไม่มีการเปลี่ยนแปลง ล้มเหลว และเงื่อนไขหยุด
- [ ] มนุษย์สุ่มตรวจสามรอบแรกแล้ว
- [ ] worktree ความถี่สูงมีกลยุทธ์ archive และ cleanup
- [ ] การเขียนสำคัญยังต้องให้มนุษย์ยืนยัน
