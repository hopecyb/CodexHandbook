เมื่อเพิ่งรู้จัก Skill ความเข้าใจผิดที่พบบ่อยคือ “ติดตั้งแล้วจะทำงานเอง” การใช้ Skill คือการให้ Codex ทำงานตามรูปแบบที่เขียนไว้ล่วงหน้า

คุณสามารถ **ระบุชื่อ** Skill เพื่อเรียกใช้โดยตรง หรือโมเดลอาจ **เลือกใช้อัตโนมัติ** ในสถานการณ์ที่เหมาะสม การแยกสองวิธีนี้ให้ออกช่วยลดเวลาแก้ปัญหา

![ภาพประกอบ: วิธีเรียกใช้สองแบบวางคู่กัน ด้านซ้ายมือชี้เลือกกล่องเครื่องมือโดยตรง (เรียกใช้อย่างชัดเจน) ด้านขวาผู้ช่วยอ่านป้ายแล้วเลือกกล่องเครื่องมือที่ตรงกันเอง (ทริกเกอร์โดยนัย)](/illustrations/skills-trigger.webp)

## วิธีทริกเกอร์

1. **แบบชัดเจน**: ในสภาพแวดล้อมที่รองรับ ให้เรียกด้วย `$skill-name` (ชื่อตรงกับ `name` ใน frontmatter)
2. **แบบโดยนัย**: โมเดลตัดสินจากความหมายของ `description` ว่าเหมาะกับงานปัจจุบันหรือไม่

## แยกสองวิธีทริกเกอร์อย่างไร

- **ทริกเกอร์แบบชัดเจน**: คุณบอกตรง ๆ ว่า “ใช้ Skill นี้”
- **ทริกเกอร์แบบโดยนัย**: คุณไม่ได้ระบุชื่อ แต่คำอธิบายงานตรงกับสถานการณ์ที่ Skill เหมาะสม

เมื่อเริ่มทดลอง Skill แนะนำให้ใช้ **แบบชัดเจน** ก่อน เพราะตรวจได้ง่ายกว่าเรื่องต่อไปนี้:

- ระบบรู้จัก Skill หรือไม่
- พฤติกรรมเป็นไปตามที่คาดหรือไม่
- ชื่อและคำอธิบายเขียนถูกหรือไม่

## ตัวอย่าง

```text
$pr-review โปรดตรวจการเปลี่ยนแปลงที่ยังไม่ได้ commit ของฉัน
```

หรือใช้ภาษาธรรมชาติ: “ตรวจ diff ตามแนวทางของทีม โดยเน้นการทดสอบ”

## ความเข้าใจผิดที่พบบ่อย

### 1. เขียน Skill แล้วจะทริกเกอร์อัตโนมัติเสมอ

การทริกเกอร์อัตโนมัติขึ้นกับความชัดเจนของ `description` และงานปัจจุบันคล้ายสถานการณ์ใช้งานมากพอหรือไม่

### 2. การทริกเกอร์ด้วยภาษาธรรมชาติกับ `$name` ให้ผลเหมือนกันเสมอ

ไม่จำเป็นต้องเหมือนกันทั้งหมด

`$name` ชัดเจนกว่า เหมาะสำหรับตรวจสอบและบังคับใช้ ภาษาธรรมชาติสะดวกกว่า แต่บางครั้งโมเดลอาจเลือก Skill ผิดหรือไม่เลือกเลย

### 3. Skill ไม่ทริกเกอร์ แสดงว่าตัว Skill มีปัญหาแน่นอน

อาจเป็นเพียงเพราะ:

- ชื่อไม่ถูกต้อง
- `description` กว้างเกินไป
- คำอธิบายงานไม่ตรงคำทริกเกอร์

ดังนั้นเมื่อแก้ปัญหา อย่าดูเพียงว่า “ไฟล์มีอยู่หรือไม่” แต่ต้องดูด้วยว่า “เขียนให้ดูเหมือนเครื่องมือที่ระบบจะเลือกใช้หรือไม่”

## ลำดับทดสอบที่ใช้บ่อย

หากต้องการให้รันผ่านก่อน ให้ลองดังนี้:

1. เรียกด้วย `$skill-name` อย่างชัดเจน
2. ตรวจว่าผลลัพธ์ตรงตามคาดหรือไม่
3. ปรับ `description`
4. สุดท้ายจึงทดสอบว่าภาษาธรรมชาติทริกเกอร์ได้หรือไม่

วิธีนี้แยก “ตัว Skill มีปัญหา” ออกจาก “เงื่อนไขทริกเกอร์อัตโนมัติเขียนไม่ดี” ได้

## เขียน description ให้ดี

- ระบุว่า “ใช้เมื่อใด” และ “ไม่ใช้เมื่อใด” ให้ชัด
- ใส่คำที่ผู้ใช้อาจพูด เช่น review, release, changelog
- หลีกเลี่ยงคำกว้าง ๆ อย่าง “ช่วยผู้ใช้เขียนโค้ด”
- วางสถานการณ์ทริกเกอร์หลักไว้ **ช่วงต้น** (รายการ Skill มีงบประมาณอักขระ)

## ตัดสินอย่างไรว่า description ชัดเจน

เกณฑ์ที่ใช้บ่อยคือ:  
อ่าน `description` ประโยคนี้แล้วรู้ว่า “เมื่อใดควรใช้ และเมื่อใดไม่ควรใช้”

หากอ่านแล้วรู้สึกว่า “ดูเหมือนทำได้ทุกอย่าง” แสดงว่ากว้างเกินไป
