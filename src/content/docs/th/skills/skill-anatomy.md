เมื่อเห็นไดเรกทอรี Skill ครั้งแรก ความรู้สึกที่พบบ่อยคือ “รู้จักทุกโฟลเดอร์ แต่ไม่รู้ว่าทำไมต้องจัดแบบนี้”

หน้านี้อธิบายวิธีแยก “workflow หลัก คำอธิบายยาว เทมเพลต และสคริปต์” ออกจากกัน เพื่อไม่ให้ทุกอย่างถูกรวมไว้ในไฟล์เดียว

วิธีนี้อ่าน แก้ และนำกลับมาใช้ได้ง่ายกว่า และลดความสับสนเมื่อเนื้อหายาวขึ้น

![ภาพประกอบ: โฟลเดอร์เปิดออกเหมือนตู้หลายชั้น ด้านบนเป็นการ์ดคำสั่งหลัก ด้านล่างมีลิ้นชักเอกสารอ้างอิง เทมเพลต และสคริปต์สามช่อง ผู้ช่วยหยิบเฉพาะชั้นที่ต้องใช้](/illustrations/skills-anatomy.webp)

## โครงสร้างไดเรกทอรี

```text
my-skill/
├── SKILL.md          # จำเป็น
├── scripts/          # ไม่บังคับ: ขั้นตอนแบบกำหนดแน่นอน
├── references/       # ไม่บังคับ: เอกสารอ้างอิงยาว
└── templates/        # ไม่บังคับ: เทมเพลตผลลัพธ์
```

## แต่ละชั้นทำอะไร

- `SKILL.md`: คู่มือหลัก บอก Codex ก่อนว่า “นี่คืออะไร ใช้เมื่อใด และทำตามขั้นตอนใด”
- `references/`: ตู้เก็บข้อมูลยาว ไม่ยัดความรู้พื้นหลังทั้งหมดไว้ในไฟล์หลัก
- `templates/`: โครงผลลัพธ์พร้อมใช้ ลดการคิดสดทุกครั้ง
- `scripts/`: ให้สคริปต์ทำขั้นตอนที่กำหนดแน่นอนได้ แทนการอธิบายทั้งหมดด้วยภาษาธรรมชาติ

ช่วงแรกอาจมีเพียง `SKILL.md` ไฟล์เดียวก็ได้  
เมื่อซับซ้อนขึ้นจริงจึงค่อยแยก `references/`, `templates/` และ `scripts/`

## โหลดเมื่อต้องการ แทนการใส่ทั้งหมดพร้อมกัน

Skill ที่ดูแลได้มักแบ่งเป็นสามชั้น:

| ชั้น | ใส่อะไร | ใช้เมื่อใด |
|---|---|---|
| metadata | ชื่อ คำอธิบาย และสถานการณ์ทริกเกอร์ | ให้ Codex ตัดสินว่าควรใช้หรือไม่ |
| คำอธิบายหลัก | ขั้นตอนบังคับ ข้อห้าม และนิยามว่าเสร็จ | อ่านก่อนหลัง Skill ถูกทริกเกอร์ |
| ไฟล์แนบ | เทมเพลต เอกสารอ้างอิง สคริปต์ และตัวอย่าง | เปิดหรือรันเฉพาะเมื่องานต้องใช้จริง |

ข้อดีคือปกติแสดงเพียงคำอธิบายทริกเกอร์สั้น ๆ และโหลดรายละเอียดเมื่อลงมือจริง ยิ่งมี Skill มาก การแบ่งชั้นยิ่งสำคัญ

## ตัวอย่าง SKILL.md ขั้นต่ำ

```md
---
name: pr-review
description: ตรวจ diff ของ branch ปัจจุบันเทียบกับ main แล้วระบุความเสี่ยงและช่องว่างการทดสอบ ใช้เมื่อผู้ใช้ขอ review, ตรวจ PR หรือตรวจก่อน merge
---

## ขั้นตอน
1. อ่าน diff เทียบกับ main
2. แยกตามไฟล์: ข้อผิดพลาดด้าน logic ความปลอดภัย ประสิทธิภาพ และการทดสอบ
3. ส่งรายการแบบแบ่งระดับ: บล็อก / แนะนำ / nit
4. ห้าม push หรือ merge อัตโนมัติ
```

## ความเข้าใจผิดที่พบบ่อย

### 1. ต้องสร้างทุกไดเรกทอรีให้ครบตั้งแต่ต้น

Skill ที่ดีจำนวนมากเริ่มจาก `SKILL.md` เพียงไฟล์เดียว แล้วค่อยแยกไดเรกทอรีอื่นเมื่อมีการนำกลับมาใช้มากขึ้น

### 2. `references/` มีไว้ใส่เนื้อหาเพิ่ม

หัวใจไม่ใช่ “ใส่ให้มาก” แต่คือย้ายคำอธิบายยาวที่ไม่ควรแย่งความสนใจจาก workflow หลักไปอ่านเมื่อต้องการ

### 3. หลีกเลี่ยง `scripts/` ถ้าไม่จำเป็น

หากขั้นตอนหนึ่งควรเสถียร กำหนดแน่นอน และทำซ้ำได้ การเขียนเป็นสคริปต์มักเชื่อถือได้กว่าการอธิบายด้วยภาษาธรรมชาติซ้ำ ๆ

## หน้าที่ของแต่ละไดเรกทอรี

| ไดเรกทอรี | การใช้งาน |
|---|---|
| `SKILL.md` | workflow หลัก เงื่อนไขทริกเกอร์ และข้อห้าม |
| `references/` | เอกสารยาว มาตรฐาน และคำอธิบาย API |
| `templates/` | รูปแบบผลลัพธ์และโครงรายงาน |
| `scripts/` | คำสั่งและการตรวจแบบกำหนดแน่นอน |

## เมื่อใดควรแยกไดเรกทอรี

ใช้คำถามต่อไปนี้ตามลำดับ:

1. workflow หลักยาวจนอ่านครั้งแรกไม่ไหวหรือไม่
2. มีข้อมูลส่วนใหญ่ที่ไม่ต้องดูทุกครั้งหรือไม่
3. มีรูปแบบผลลัพธ์ตายตัวที่เกิดซ้ำหรือไม่
4. มีขั้นตอนใดเสถียรพอจะทำเป็นสคริปต์หรือไม่

หากตอบ “ใช่” หนึ่งหรือสองข้อ ก็เริ่มแยกได้

## จากเทมเพลตเติบโตเป็น Skill

หลายทีมไม่ได้เริ่มจาก “ออกแบบ Skill” แต่มีพรอมป์ที่คัดลอกซ้ำก่อน แล้วพัฒนาตามลำดับนี้:

| ระยะ | รูปแบบ | เมื่อใดควรยกระดับ |
|---|---|---|
| พรอมป์ครั้งเดียว | เขียนในบทสนทนาปัจจุบัน | ใช้ครั้งเดียว ไม่ต้องนำกลับมาใช้ |
| เทมเพลต | ใส่ในเทมเพลตพรอมป์หรือเอกสารทีม | งานประเภทเดียวกันเกิดซ้ำ แต่ขั้นตอนยังปรับอยู่ |
| Skill ไฟล์เดียว | `SKILL.md` หนึ่งไฟล์ | workflow เสถียรและเงื่อนไขทริกเกอร์ชัดเจน |
| ไดเรกทอรี Skill เต็มรูปแบบ | `SKILL.md` + `templates/` + `references/` + `scripts/` | รูปแบบผลลัพธ์ เอกสารอ้างอิงยาว และการตรวจแบบกำหนดแน่นอนเสถียรแล้ว |

อย่ารีบเปลี่ยนทุกเทมเพลตเป็น Skill สิ่งที่ควรบันทึกจริงคืองานที่เกิดซ้ำแล้ว มีเกณฑ์ความสำเร็จชัด และทีมยินดีทำตาม workflow เดียวกัน

## ส่วนประกอบที่พบบ่อยใน Skill ที่นำกลับมาใช้ได้

| ส่วนประกอบ | เหมาะใส่อะไร |
|---|---|
| คำอธิบายหลัก | เงื่อนไขทริกเกอร์ ขั้นตอนทำงาน ข้อห้าม และนิยามว่าเสร็จ |
| เทมเพลต | ผลตรวจ PR โครงสร้างเอกสาร รูปแบบรายงานความเสี่ยง |
| เอกสารอ้างอิง | มาตรฐานโค้ด glossary กฎโดเมน และคำอธิบาย API |
| สคริปต์ | วิเคราะห์ความซับซ้อน ตรวจลิงก์ สถิติ test coverage และตรวจรูปแบบ |

Skill ที่ดีไม่ใช่เพียง “prompt ที่ยาวกว่า” แต่แยก workflow ที่นำกลับมาใช้ได้เป็นส่วนที่อ่าน ทดสอบ และดูแลได้

เริ่มจากทำให้ `SKILL.md` รันได้ก่อน เมื่อซับซ้อนขึ้นจริง จึงค่อยแยกข้อมูล เทมเพลต และสคริปต์ออกทีละส่วน
