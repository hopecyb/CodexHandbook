เมื่อมีกลไกส่วนขยายมากขึ้น ข้อผิดพลาดที่พบบ่อยที่สุดคือเลือกศัพท์เทคนิคก่อน แล้วค่อยหาปัญหามาใส่ วิธีที่มั่นคงกว่าคือเริ่มจากถามว่า: **ฉันต้องการเก็บอะไรไว้ หรือทำให้อะไรเกิดขึ้นโดยอัตโนมัติ**

ชื่อที่มักสับสนกันมากที่สุดคือ:

- พรอมป์
- AGENTS.md
- Skill
- MCP
- Plugin
- Scheduled task

แม้ทั้งหมดจะ “ขยาย Codex” เหมือนกัน แต่บางครั้งพรอมป์หนึ่งประโยคก็พอ และบางครั้งจึงจำเป็นต้องใช้กลไกที่หนักกว่า

## แผนผังการเลือก

![แผนผังเลือกวิธีขยาย Codex](/illustrations/map-extension-selection.webp)

นี่ไม่ใช่ decision tree แบบเลือกได้อย่างเดียว workflow ที่สมบูรณ์อาจใช้ `AGENTS.md`, Skill และ MCP พร้อมกัน แผนผังนี้มีไว้ป้องกันไม่ให้กลไกหนึ่งรับหน้าที่ที่ไม่ถนัด

## คำถามตัดสินเจ็ดข้อ

### 1. กระทบเฉพาะงานปัจจุบันหรือไม่

เริ่มด้วยพรอมป์ ระบุเป้าหมาย อินพุต ขอบเขต เกณฑ์การยอมรับ และสิทธิ์ให้ชัด มีต้นทุนต่ำที่สุดและสังเกตปัญหาจริงได้ง่ายที่สุด

### 2. ต้องปฏิบัติทุกครั้งเมื่อเข้ามาในรีโพซิทอรีนี้หรือไม่

เขียนใน `AGENTS.md` เช่น คำสั่งทดสอบ สไตล์โค้ด ไดเรกทอรีที่ห้ามแก้ และกฎการติดตั้ง dependency อย่าใส่ความต้องการครั้งเดียวไว้ในกฎโปรเจกต์ระยะยาว

### 3. งานประเภทเดียวกันมีขั้นตอนและผลลัพธ์ที่เสถียรหรือไม่

ทำเป็น Skill เพราะ Skill เหมาะกับการเก็บคำอธิบายที่นำกลับมาใช้ได้ พร้อมเทมเพลต เอกสารอ้างอิง asset หรือสคริปต์ช่วยตามต้องการ หาก workflow ยังไม่มีเกณฑ์ความสำเร็จตายตัว ให้ทดลองด้วยพรอมป์ต่อไปก่อน

### 4. ต้องใช้ข้อมูลหรือการกระทำนอกรีโพซิทอรีหรือไม่

ประเมิน MCP หรือ Connector เริ่มจากระบุเครื่องมือและข้อมูลที่ต้องใช้จริง แล้วให้สิทธิ์อ่านอย่างเดียว ขอบเขตเล็กที่สุด และการตั้งค่าที่ audit ได้ก่อน หากแก้ได้ด้วยไฟล์ในเครื่องหรือคำสั่งที่มีอยู่ ก็ไม่จำเป็นต้องเพิ่มการเชื่อมต่อภายนอก

### 5. ต้องตรวจ ณ จุดวงจรชีวิตที่ตายตัวหรือไม่

ใช้ Hook เช่น ตรวจคำสั่งอันตรายก่อนเรียกเครื่องมือ สแกน patch หลังเขียน หรือบันทึกสรุปเมื่อ session จบ Hook รันอัตโนมัติ จึงต้องทดสอบ timeout ความล้มเหลว และ false positive

### 6. ต้องแจกความสามารถหนึ่งชุดให้ผู้อื่นแบบเดียวกันหรือไม่

พิจารณา Plugin ซึ่งเป็นชั้นรวมและแจกจ่าย สามารถมี Skills, connectors, MCP, Hooks และเทมเพลต Scheduled task การติดตั้ง Plugin ไม่ได้หมายความว่าเชื่อถือการเชื่อมต่อ สคริปต์ หรือ Hook ภายในโดยอัตโนมัติ

### 7. งานรันด้วยตนเองได้เสถียรแล้วและต้องทำซ้ำตามเวลาหรือไม่

จึงค่อยสร้าง Scheduled task ตรวจพรอมป์ Skill สิทธิ์ และรูปแบบผลลัพธ์ในงานทั่วไปก่อน หลังเริ่มกำหนดเวลา ให้ตรวจการรันช่วงแรก และคงประตูการเผยแพร่หรือ merge โดยมนุษย์ไว้

## เปรียบเทียบตามสถานการณ์

| สถานการณ์ | ชุดที่แนะนำ |
|---|---|
| ทำมาตรฐานการทดสอบและ commit | AGENTS.md |
| รายการตรวจก่อน merge ทุกครั้ง | Skill `pr-review` |
| ดึงบริบท ticket จาก Linear | MCP + พรอมป์งาน |
| รายงาน dependency ประจำสัปดาห์ | Scheduled task → เปิด draft issue |
| สแกน secret ใน patch หลังเขียนไฟล์ | Hook หรือ CI; สถานการณ์ความเสี่ยงสูงใช้ทั้งคู่ |
| ให้ทีมติดตั้ง workflow ตรวจทานและเครื่องมือ GitHub ชุดเดียวกัน | Plugin (ตรวจสิทธิ์และ Hooks ก่อนติดตั้ง) |
| สร้างรายงานความเสี่ยง dependency ทุกสัปดาห์ | Skill ที่ตรวจสอบแล้ว + Scheduled task + การตรวจโดยมนุษย์ |
| ตรวจความปลอดภัย การทดสอบ และความสามารถในการดูแลพร้อมกัน | Agent ย่อยแบบอ่านอย่างเดียวหลายตัว แล้วให้ Main Agent สรุป |

## รูปแบบที่ควรหลีกเลี่ยง

- **Skill บวม**: ติดตั้ง Skill หลายสิบรายการที่ `description` แข่งขันกันจับคู่
- **ใช้ MCP เป็นค้อนสารพัด**: งานที่ใช้ `git` ได้กลับบังคับต่อ API
- **กำหนดเวลาโดยไม่มีเกณฑ์การยอมรับ**: แก้โค้ดตามเวลาโดยไม่มีเงื่อนไขจบ หลักฐานการรัน และการตรวจโดยมนุษย์
- **สร้างของซ้ำ**: มี Connector ทางการอยู่แล้วแต่ยังสร้าง MCP เอง
- **วางกฎผิดที่**: เขียนความต้องการครั้งเดียวลง `AGENTS.md` ทำให้งานต่อ ๆ ไปติดข้อจำกัดเก่า
- **Hook ทำงานหนักเกินไป**: ใส่ workflow ธุรกิจที่กินเวลาลงในการเรียกเครื่องมือทุกครั้ง ทำให้งานทั่วไปช้าหรือถูกบล็อกผิด

## คำถามที่พบบ่อย

### 1. ควรติดตั้ง Plugin และต่อ MCP ตั้งแต่เริ่มหรือไม่

หลายปัญหาแก้ได้ด้วยการใช้พรอมป์ การควบคุมขอบเขต และ `AGENTS.md` ให้ดีก่อน

### 2. งานต้องเกิดซ้ำกี่ครั้งจึงคุ้มทำเป็น Skill

ไม่มีตัวเลขตายตัว จำนวนครั้งเป็นเพียงสัญญาณ สิ่งสำคัญกว่าคือขั้นตอนเสถียรหรือไม่ เกณฑ์ความสำเร็จชัดหรือไม่ และต้นทุนความล้มเหลวคุ้มค่ากับการตรวจอัตโนมัติหรือไม่

### 3. เมื่อใช้ครั้งแรก ปกติควรเริ่มจากวิธีใด

ส่วนใหญ่เริ่มจากสามประเภทนี้:

- พรอมป์
- `AGENTS.md`
- Skill

โดยทั่วไปยังไม่ต้องเริ่มด้วย MCP หรือระบบอัตโนมัติแบบไม่มีผู้ดูแล

หัวใจไม่ได้อยู่ที่กลไกขั้นสูงเพียงใด แต่อยู่ที่หน้าที่ตรงกันหรือไม่ สิทธิ์น้อยที่สุดหรือไม่ และผลลัพธ์ตรวจสอบได้หรือไม่

## แบบฝึกหัดลงมือขั้นต่ำ

ใช้ “ตรวจ diff ปัจจุบันก่อน merge” เป็นตัวอย่าง:

1. รันด้วยพรอมป์สองครั้งก่อน แล้วบันทึกรายการตรวจที่ต้องอธิบายซ้ำทุกครั้ง
2. เขียนคำสั่งตายตัวของรีโพซิทอรีลงใน `AGENTS.md` เช่น `pnpm test` และห้ามแก้ไดเรกทอรี generated
3. เขียนขั้นตอนตรวจ ระดับความรุนแรง และรูปแบบผลลัพธ์เป็น Skill `pr-review`
4. เพิ่ม MCP/Connector เฉพาะเมื่อต้องใช้คอมเมนต์ GitHub PR หรือสถานะ CI
5. เพิ่ม Hook หรือ Scheduled task เฉพาะเมื่อต้องตรวจอัตโนมัติในเหตุการณ์ตายตัว
6. เมื่อหลายทีมต้องติดตั้ง จึงค่อยแพ็กความสามารถเหล่านี้เป็น Plugin

ทุกครั้งที่เพิ่มหนึ่งชั้น ให้ตอบสามเรื่องใหม่: เพิ่มสิทธิ์อะไร ตรวจสอบอย่างไร และปิดหรือย้อนกลับอย่างไร
