หากคุณมอบหมายงานได้แล้วแต่ยังไม่เคยสร้าง Skill จริง หน้านี้อธิบายวิธีพื้นฐานในการทำ Skill แรก

การใช้เวลา 15–30 นาทีสร้าง Skill ที่ **นำกลับมาใช้ในรีโพซิทอรีได้** มักตรงไปตรงมากว่าการอ่านทฤษฎีจำนวนมาก จุดเริ่มต้นที่ดีคือ Skill ขนาดเล็กที่มีขอบเขตชัดเจน

![ภาพประกอบ: ผู้ช่วยตัวเล็กประกอบ Skill แรกบนโต๊ะทำงานเหมือนชุดประกอบ ใส่การ์ดคำสั่ง ใช้แว่นขยายตรวจ diff ทำเครื่องหมายรายการตรวจสอบ และปักธงเล็กบนโฟลเดอร์ที่เสร็จแล้ว](/illustrations/skills-first-skill.webp)

## เหมาะกับใคร

ผู้ที่รัน [งานแรก](/th/cases/first-task/) ได้แล้วและพร้อมทดลองในรีโพซิทอรีทดสอบ

## ทำไมจึงแนะนำให้เริ่มจาก `pr-review`

เพราะมีข้อดีหลายอย่าง:

- อินพุตค่อนข้างชัด
- ความเสี่ยงต่ำกว่า “แก้โค้ดทันที”
- ตัดสินได้ง่ายว่าใช้ได้ดีหรือไม่
- ช่วยให้เข้าใจวิธีทริกเกอร์ Skill และการเขียนขอบเขตไปพร้อมกัน

จึงเหมาะสำหรับฝึกเปลี่ยนรูปแบบการทำงานหนึ่งชุดให้เป็นสิ่งที่นำกลับมาใช้ได้

## ผลลัพธ์เป้าหมาย

มี Skill ที่ `.agents/skills/pr-review/` ซึ่งส่งผลตรวจทานการเปลี่ยนแปลงปัจจุบันอย่างมีโครงสร้างได้

## เป้าหมายขั้นต่ำ

สำหรับ Skill แรก ให้ทำสามเรื่องนี้ก่อน:

1. ระบบรู้จัก Skill
2. ทำ workflow ที่ชัดเจนหนึ่งชุดได้อย่างสม่ำเสมอ
3. ไม่ดำเนินการอันตรายพ่วงไปด้วย

เมื่อสามข้อนี้ชัดเจน การปรับปรุงภายหลังจะง่ายขึ้นมาก

## ขั้นตอน

### 1. สร้างไดเรกทอรี

```bash
mkdir -p .agents/skills/pr-review
```

### 2. เขียน SKILL.md

```md
---
name: pr-review
description: ตรวจ git diff แล้วระบุปัญหาที่บล็อก ช่องว่างการทดสอบ และข้อเสนอแนะด้านสไตล์ ใช้เมื่อผู้ใช้พูดถึง review, การตรวจทาน หรือการตรวจก่อน merge ไม่ใช้สำหรับเขียนฟีเจอร์ใหม่
---

# ตรวจ PR

## อินพุต
- branch เริ่มต้นสำหรับเปรียบเทียบ: main (หากไม่มี ให้ใช้ branch เริ่มต้น)

## workflow
1. ระบุไฟล์ที่เปลี่ยนและประเภทการเปลี่ยน (ฟีเจอร์/การแก้ไข/refactor/เอกสาร)
2. สำหรับการเปลี่ยน logic แต่ละรายการ: ขาดการทดสอบหรือไม่ และทำลาย API หรือไม่
3. ตรวจ secret, debug log และ diff ขนาดใหญ่ที่ไม่เกี่ยวข้อง
4. ผลลัพธ์:
   - 🔴 บล็อก: ต้องแก้
   - 🟡 แนะนำ: ควรแก้
   - 🟢 ผ่าน: เป็นไปตามข้อกำหนด AGENTS.md

## ข้อห้าม
- ห้าม git push
- ห้ามแก้ public API ที่ยังไม่ได้หารือ
```

### 3. ทดลองใช้ในเครื่อง

เปิดรีโพซิทอรีนี้ใน Codex แล้วลอง:

```text
$pr-review โปรดตรวจการเปลี่ยนแปลงที่ยังไม่ได้ commit ของฉัน
```

หรือใช้ภาษาธรรมชาติ: “ตรวจ diff ตามแนวทางของทีม โดยเน้นการทดสอบ”

### 4. ทดสอบแบบชัดเจนก่อนแบบโดยนัย

อย่าเริ่มจากทดสอบการทริกเกอร์อัตโนมัติทันที

ให้ลองตามลำดับนี้:

1. เรียกด้วย `$pr-review` อย่างชัดเจนก่อน
2. ยืนยันว่า workflow และผลลัพธ์ถูกต้อง
3. จากนั้นค่อยทดสอบการทริกเกอร์ด้วยภาษาธรรมชาติ

วิธีนี้ช่วยแยกว่าปัญหาอยู่ที่เนื้อหา Skill หรือเงื่อนไขทริกเกอร์ใน `description` ไม่ชัดพอ

### 5. ปรับ description

หากโมเดล **ไม่เคยเลือกใช้อัตโนมัติ** ให้เจาะจงขึ้นหรือเพิ่มคำทริกเกอร์ใน `description` หาก **เลือกใช้ผิดบ่อยเกินไป** ให้เพิ่มว่า “ไม่ใช้เมื่อใด”

### 6. commit เพื่อแชร์กับทีม

```bash
git add .agents/skills/pr-review
git commit -m "docs: add pr-review skill for Codex"
```

เพิ่มหนึ่งประโยคใน README ของทีมหรือ `AGENTS.md`: “ก่อน merge สามารถใช้ `$pr-review`”

## ความเข้าใจผิดที่พบบ่อย

### 1. Skill แรกควรครบถ้วนที่สุด

หลายครั้งตรงกันข้าม Skill แรกยิ่งเล็กและเฉพาะเจาะจง ยิ่งตัดสินคุณค่าได้ง่าย

### 2. หัวใจของ Skill ไม่ใช่เขียนให้ “ฉลาด”

สิ่งสำคัญกว่าคือ **มีขอบเขตชัดเจน**

ควรระบุสิ่งที่ต้องทำและห้ามทำให้ชัด แทนที่จะพยายาม “ดูเก่ง”

### 3. Skill รันได้ก็ถือว่าสำเร็จ

Skill ที่มีประโยชน์อย่างน้อยต้อง:

- ผู้อื่นเข้าใจว่าเมื่อใดควรใช้
- ผลลัพธ์มีโครงสร้างตายตัว
- ไม่ดำเนินการอันตรายพ่วงไปด้วย

## รายการตรวจรับ

- [ ] `$pr-review` รันได้โดยไม่ทำคำสั่ง git อันตราย
- [ ] ผลลัพธ์มีข้อสรุปแบ่งระดับ ไม่ใช่ความเห็นกว้าง ๆ
- [ ] `description` อธิบายสถานการณ์ทริกเกอร์ได้ในหนึ่งประโยค
- [ ] ตรวจความต้องการสคริปต์เทียบกับ [สิทธิ์และการอนุมัติ](/th/guide/permissions-and-sandbox/) แล้ว (ตัวอย่างนี้ไม่มีสคริปต์)

การเริ่มจาก Skill ที่ “เล็กและเสถียร” ช่วยให้ workflow ที่ชัดเจนนำกลับมาใช้ได้อย่างสม่ำเสมอมากกว่า
