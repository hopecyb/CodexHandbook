**先头脑风暴再动手**适合目标模糊、方案不止一种的任务：新功能、改版、内容选题、技术选型。它与 [探索—计划—执行—验证](/09-workflows/explore-plan-execute-verify/) 的①探索阶段衔接，但更强调**发散与收敛**，而不是立刻读代码改文件。

## 这篇解决什么问题

- 何时值得先 brainstorm，何时直接 EPXV
- 如何限制发散范围，避免空聊
- 产出物：选项表、决策记录、下一步计划

## 适合谁

| 场景 | 示例 |
|---|---|
| 产品/功能 | 「给用户加一个导出功能，有三种 UI」 |
| 内容 | 「这篇教程面向谁、结构怎么分」 |
| 技术 | 「用队列还是 cron 做定时任务」 |

## 最小可用做法

**阶段 A — 发散（限时）**

```text
先不要改任何文件。针对「导出 CSV」需求，列出 3 种实现路径：
各写优缺点、涉及模块、预估工作量（S/M/L）。
不要选最终方案。
```

**阶段 B — 收敛**

```text
根据上表，推荐 1 个默认方案和 1 个备选；
说明需要我确认的 2 个决策点（格式、权限）。
```

**阶段 C — 进入计划**

确认后接 [规格驱动](/09-workflows/specification-driven-work/) 或 EPXV 的②计划。

## 推荐工作流

```text
明确约束（时间、技术栈、不可改动部分）
    → 发散 3–5 个选项（禁止写代码）
    → 按「价值 / 风险 / 成本」排序
    → 人工选方向或要求补充信息
    → 书面计划 + 执行
```

设定**时间盒**：例如 15 分钟内完成发散，防止讨论漂移。

## 常见错误

- 把 brainstorm 当成执行，模型已开始改文件——用「先不要改」约束
- 选项过多无排序，决策疲劳
- 未记录已否决方案，两周后重复争论
- 跳过约束，方案 beautiful 但不可落地

## 安全边界

- 头脑风暴阶段仍可能读取敏感文件——用 `@` 精确引用范围
- 涉及合规、隐私的方案需人工法务/安全评审，不能仅模型拍板

## 验收清单

- [ ] 至少有 2 个可行选项与明确推荐
- [ ] 决策点已标出，等待人工确认
- [ ] 无未授权的仓库写入
- [ ] 下一步可衔接书面计划
