是否先要计划，取决于任务还缺什么决定。范围明确、容易撤回的修改可以直接执行；路线不清时先规划；需要额外授权的具体动作在执行前停下来。计划本身不等于要求每一步都等用户回复。

## 先判断属于哪一类

| 类型 | 判断依据 | 推荐交代 | 何时暂停 |
|---|---|---|---|
| 直接执行 | 输入、范围、验收明确，修改可撤回 | 说明改哪里、完成条件和排除项 | 遇到超范围或必要信息缺失 |
| 先规划 | 存在架构选择、范围不清或多个相互影响的步骤 | 先查现状，列路线、影响和验证 | 有必须由用户决定的取舍，或用户明确要求先审计划 |
| 动作需审批 | 即将产生未授权的外部影响或触及执行权限限制 | 先完成可审阅产物，列出具体动作、对象与影响 | 在该动作之前；保留已完成准备工作 |

“涉及三个文件”不是通用审批阈值；一个文件的生产配置也可能影响很大。产品弹窗与实际执行权限见[权限与沙箱](/guide/permissions-and-sandbox/)，不要把本表当成所有客户端的权限配置。

## 对照一：本地文案修改

任务：修正 README 两处错字，不调整结构。

**过度暂停的设计反例：**

```text
先列计划，等我批准再读文件。
读完后先列准备修改的两处，等我批准再修改。
每改一处都停下问我，然后再问是否检查。
```

这些等待没有补充必要决策，只拆散了一项已明确授权的任务。

**范围明确的写法：**

```text
把 README.md 中“帐户”统一改成“账户”，只改正文中的这两处。
保留代码块、链接和其他内容。直接完成并检查 diff，报告改了哪里。
如果实际匹配数量不是两处，先说明差异；不要扩展为全文润色。
```

验收是两处准确修改与无关内容未变。这类变更通常不需要新增测试；按项目现有规则做适当检查即可。

## 对照二：改站点并发布

任务：更新三篇教程，并发布到生产站点。这里要分开内容准备与发布影响。

**授权不清的设计反例：**

```text
先写一个计划，然后把网站全部改好上线。
```

它没有说清要改哪些内容、发布到哪里、是否允许替换线上版本。

**具体边界的写法：**

```text
更新这三篇教程并修正相关内链。先读现状，给出简短计划，
在这些文件和相关导航内连续完成修改、构建与预览检查，不必逐步等待。
交付预览、变更摘要和验证结果；发布生产站点尚未授权。
准备完成后列出将发布的版本、目标环境及回退方式，等我确认发布动作。
```

这时应该完成本地工作，再请求最后的发布授权。如果用户已经明确授权了具体发布目标与动作，应结合当前策略判断是否可以继续，不能仅因为这段模板有确认文字就重复索要同一授权。

以上两组均为教学设计对照，不是实际模型输出或效率测量。

## 什么情况下只做计划

你还在比较方案、需要预算决定，或明确希望先审设计时，可以限定只做计划：

```text
本轮只做方案。阅读现有实现，给出两种选择、影响范围和验收方式。
指出真正需要我决定的取舍，不修改实现。待方案确定后再进入执行。
```

这种明确阶段限制应被遵守，不能因为代理通常有自主性就跳到实现。

## 计划里保留什么

一份够用的计划写清目标、影响范围、步骤、验证，以及尚未解决的取舍。已知答案不必变成待确认问题；没有风险的短任务也不必为了套模板增加回滚章节。

执行途中出现新情况时，区分普通实现细节与目标变化。能在原范围内解决的小问题继续处理并说明；新增依赖、扩大改动、变更接口或触及新的外部动作时，先判断是否仍在授权内。

## 可写进项目约定的默认规则

```md
- 范围明确且可撤回的任务直接执行，并完成适当验证。
- 复杂任务先列简短计划；只有用户要求先审或存在必要取舍时等待回复。
- 已授权范围内连续推进，不逐步重复确认。
- 缺少关键资料、超出任务范围或触及未授权动作时，说明具体问题。
- 不把“完成本地修改”视为自动获得发布、发送消息或删除数据的授权。
```

这是可调整的工作方式建议，不代替系统、组织策略和沙箱。相关说明见[上下文优先级](/guide/context/context-priority/)、[规划](/guide/agent-work/planning/)与[人工审批模式](/cases/workflows/human-approval-patterns/)。
