---
title: 先要计划
description: 在 Codex 动手之前，先让它把步骤、风险和验证方式讲清楚。
---

很多问题不是做不了，只是**开始得太快**。一句“帮我修一下”很容易把探索、计划、执行揉在一起，最后只能在 diff 里被动验收。

这时更有效的做法，是先让它给出计划，不要继续把需求越写越长。

## 什么时候一定要先要计划

| 场景 | 为什么 |
|---|---|
| 跨多个文件或模块 | 容易误伤无关区域 |
| 你对代码库不熟 | 先确认它理解的范围 |
| 需求还在摇摆 | 把分歧先暴露出来 |
| 需要你审批后再执行 | 把“执行授权”与“思路讨论”分开 |
| 涉及高风险动作 | 先看回滚与验证方案 |

小 typo 或单点文案改动未必需要正式计划，但只要你觉得“这件事做偏会很麻烦”，就值得先停一下。

## 一个好计划至少应包含什么

最低配版本也应覆盖这四项：

1. 步骤
2. 涉及文件或范围
3. 风险或待确认点
4. 每步如何验证

如果少了第 4 项，这更像“待办清单”，还不太算可验收的计划。

## 三种常用提法

### 极简版

```text
先不要改代码。先给我一个 3-5 步的计划，说明会改哪些文件、每步如何验证。
```

适合：你已经知道大致方向，只想看它会怎么拆。

### 推荐版

```text
先不要执行。请先基于当前仓库给出计划，包含：
1. 目标理解
2. 步骤编号
3. 涉及文件或目录
4. 风险与待确认项
5. 验证方式

在我回复“按计划执行”之前不要修改文件。
```

适合：日常开发、文档改造、提示词重写、配置调整。

### 高风险版

```text
先不要做改动。先产出一个计划，并单独说明：
- 哪一步最容易引入回归
- 如果失败如何回滚
- 哪些操作需要我确认
- 哪些测试或人工检查能证明完成
```

适合：生产问题、权限配置、自动化脚本、跨模块重构。

## 计划不是越长越好

你要的是一个**能审批、能纠偏、能执行**的中间产物，不是一篇长方案。

判断计划是否可用，可以看三点：

- 你能不能明确说出“第 2 步不做，改成别的”
- 你能不能一眼看出它会动到哪些关键区域
- 你能不能在开始前知道如何验收

如果做不到，说明计划还不够具体。

## 你可以怎么批计划

不需要整段重写，只要像带同事一样给方向即可。

常见引导句：

```text
保留第 1、2 步，去掉第 3 步。
把数据库改动拆成单独一步。
先只做只读分析，不要进入实现。
计划里补上回归测试和回滚方案。
```

这比“重来一次”更省上下文，也更容易把结果拉回正轨。

## 与“直接开始做”相比，有什么收益

| 先要计划 | 直接开始 |
|---|---|
| 能先发现误解 | 常在改完后才发现方向错了 |
| 便于审批与协作 | 你只能被动看最终 diff |
| 有利于拆成子任务 | 容易把多个目标揉在一起 |
| 验证方式提前可见 | 常常做到最后才想起测试 |

很多工作流都会把“探索”和“计划”单独拿出来。见 [探索—计划—执行—验证](/cases/workflows/explore-plan-execute-verify/)。

## 计划最容易出的问题

### 只有动作，没有边界

例如“更新文档并优化结构”，但没说改哪些目录、不改哪些模块。这样的计划很容易越做越大。

### 只有实现，没有验证

例如“修改组件逻辑、更新样式、提交代码”，却没写怎么证明行为没坏。

### 只有任务列表，没有待确认项

好的计划会承认不确定性，不会假装所有前提都已经成立。

## 一个团队内很好用的约定

你们可以在 `AGENTS.md` 里明确写出：

```md
- 涉及 3 个以上文件的改动，先出计划
- 未经确认不要执行破坏性命令
- 计划必须写验证方式
```

这样“先要计划”就不再是临时提醒，而会变成团队默认做法。
