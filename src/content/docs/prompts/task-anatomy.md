提需求时，信息一多就容易写散，结果是材料很多，但重点不清楚，Codex 也更容易误解。

这里整理了一条任务里常见的几个组成部分。

## 任务结构

可以按下面这个顺序组织：

- 结果是什么
- 为什么要做
- 需要哪些材料
- 边界在哪里
- 怎么判断完成

顺序不必完全固定，但这几项说清楚后，任务会稳很多。

## 推荐模板

```text
目标：……（最终产物是什么）
背景：……（为何重要、现状）
输入：……（相关文件/链接/粘贴内容）
约束：……（可改范围、风格、禁止事项）
验收标准：……（可检查的完成条件）
权限边界：……（可否联网、可否装依赖、可否改配置）
信息不足时：先提问，不要猜测。
```

## 每一段的作用

- **目标**：防止任务只有动作，没有结果
- **背景**：帮助 Codex 理解为什么这样做
- **输入**：把它真正需要看的文件、链接、素材交到手边
- **约束**：防止越界和顺手多改
- **验收标准**：让“做完了没”变成可检查的事情
- **权限边界**：提前说清能不能联网、装依赖、改配置

## 常见误解

### 1. 每一段都必须写满

这个模板更接近检查表，不是填空题。  
有些任务不需要长背景，但省略之后也会少掉一部分判断依据。

### 2. 目标和验收不是一回事

两者不是一回事。

- **目标**说的是你想得到什么结果
- **验收**说的是你怎么判断它真的做到了

### 3. 输入就是把一堆资料全贴上来

输入不是越多越好，相关更重要。  
关键是把“必须看的材料”明确交给它。

## 最小任务模板

如果只想先写出能用的版本，可以缩成这样：

```text
目标：把什么做成什么样
输入：相关文件或页面在这里
约束：只能改哪里，不能碰什么
验收：我怎么检查你真的做完了
不确定时：先问
```

## 示例

```text
目标：把 docs 首页第一屏文案改得更适合初学者理解
输入：src/content/docs/guide/index.md
约束：只改这一个文件，不改样式，不新增组件
验收：保留现有结构；文案更口语化；pnpm build 通过
不确定时：先提出你的理解和改动范围，再动手
```

这套结构主要是为了减少猜测，也让验收更直接。模板可以按需删减，但删掉哪一段，就要接受少掉哪一部分信息。
