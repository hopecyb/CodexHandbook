提需求时，信息一多就容易写散：材料不少，但结果、边界和验收混在一起，Codex 只能自己补空白。

这页提供一张可以直接复用的任务单。你会看到每一部分解决什么问题，以及任务说明怎样进入“探索、计划、执行、验证”的闭环。

## 适合谁

- 已经能打开 Codex，但常遇到“改多了”“没做完”或“结果无法判断”的读者
- 准备把口头需求交给 Agent 执行的开发者、创作者和团队
- 需要为长任务定义范围、权限和停下条件的人

## 任务结构

可以按下面这个顺序组织：

- 结果是什么
- 为什么要做
- 需要哪些材料
- 边界在哪里
- 怎么判断完成

顺序不必完全固定，但这几项说清楚后，任务会稳很多。

## 推荐模板

```text
目标：……（最终产物是什么）
背景：……（为何重要、现状）
输入：……（相关文件/链接/粘贴内容）
约束：……（可改范围、风格、禁止事项）
验收标准：……（可检查的完成条件）
权限边界：……（可否联网、可否装依赖、可否改配置）
信息不足时：先提问，不要猜测。
```

![从任务说明到可验证结果的闭环](/diagrams/task-execution-loop-zh-cn.svg)

图中的左侧六项不是为了把提示词写长，而是为了减少关键空白。任务进入执行后，验证证据会决定下一步：通过才交付；不通过就带着失败信息返回任务说明或计划，而不是继续盲目修改。

## 每一段的作用

- **目标**：防止任务只有动作，没有结果
- **背景**：帮助 Codex 理解为什么这样做
- **输入**：把它真正需要看的文件、链接、素材交到手边
- **约束**：防止越界和顺手多改
- **验收标准**：让“做完了没”变成可检查的事情
- **权限边界**：提前说清能不能联网、装依赖、改配置

## 常见误解

### 1. 每一段都必须写满

这个模板更接近检查表，不是填空题。  
有些任务不需要长背景，但省略之后也会少掉一部分判断依据。

### 2. 目标和验收不是一回事

两者不是一回事。

- **目标**说的是你想得到什么结果
- **验收**说的是你怎么判断它真的做到了

### 3. 输入就是把一堆资料全贴上来

输入不是越多越好，相关更重要。  
关键是把“必须看的材料”明确交给它。

## 最小任务模板

如果只想先写出能用的版本，可以缩成这样：

```text
目标：把什么做成什么样
输入：相关文件或页面在这里
约束：只能改哪里，不能碰什么
验收：我怎么检查你真的做完了
不确定时：先问
```

## 从模糊请求到可执行任务

### 原始请求

```text
帮我优化一下文档首页。
```

这句话没有说明目标读者、可修改范围和“优化后怎样算更好”。Codex 即使产出内容，你也很难判断它是否越界。

### 可执行版本

```text
目标：重写文档首页第一屏文案，让第一次接触 Codex 的读者能在 30 秒内知道这是什么、从哪里开始。
背景：当前首页默认读者已经理解 Agent、上下文和 Skill，入口说明不够直接。
输入：src/content/docs/guide/index.md
约束：只修改这个文件；不改导航、样式和组件；首次出现 Agent 时补一句通俗解释。
验收标准：
- 首屏明确说明手册用途、目标读者和第一个阅读入口
- 保留现有 frontmatter 与标题层级
- 不新增未经解释的专业术语
- pnpm build 通过
权限边界：允许读取站内相关页面；不联网、不安装依赖、不提交 Git commit。
信息不足时：先列出缺少的信息和拟修改范围，等我确认。
```

### 预期执行过程

1. 先读取首页和相邻入口页，说明当前问题。
2. 给出只涉及一个文件的短计划。
3. 修改文案并展示 diff 摘要。
4. 运行 `pnpm build`。
5. 对照四条验收标准逐项报告证据。

## 如何检查自己的任务说明

发送前问自己：

- 目标描述的是结果，还是只有“优化、处理、看看”等动作？
- 输入是否只包含真正相关的文件和材料？
- 约束是否说明了哪些内容不能碰？
- 验收条件能否由另一个人判断“通过 / 不通过”？
- 联网、安装依赖、外部写入和提交代码是否需要提前授权？
- 信息不足时，Agent 应该先问、先查还是停止？

模板可以按任务规模删减，但删掉一段，就意味着少了一类判断依据。单文件 typo 不需要长背景；跨模块迁移不能只有一句目标。
