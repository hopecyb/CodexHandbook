title: 提示词反模式
description: 应避免的模糊、越权和隐藏推理要求。
---

学提示词时，很容易把注意力都放在“应该怎么写”。
但很多时候，先知道哪些说法最容易把任务带偏，反而更省弯路。

这里列几种常见的“提示词坑”。

| 反模式 | 为什么有害 |
|---|---|
| 「随便优化一下」 | 无目标、无边界 |
| 「拥有全部权限，自己看着办」 | 事故面最大 |
| 「不要问我，直接改完」 | 跳过澄清与审批 |
| 「把你的隐藏推理过程全部打印出来」 | 不可靠且通常无助于验收 |
| 粘贴含密钥的日志 | 泄露凭据 |

## 为什么这些说法特别容易翻车

这些问题通常有一个共同点：

- 看起来省字
- 实际上把关键边界省掉了

你省掉的那部分，最后就会变成 Codex 需要自己判断的部分。

## 常见误区

### 1. 说得随意一点，会不会更像真人协作

自然说话没问题。  
更大的问题是把关键条件说没了。

### 2. “直接改完，别问我”会更高效

短期看像是少一次对话，后面常见的结果是：

- 改错范围
- 没拿到必要审批
- 最后返工更多

### 3. 要权限大一点，事情才推进得快

权限越大，误操作面也越大。  
尤其在任务边界还没想清楚的时候，大权限通常只会把风险一起放大。

## 反模式怎么换成更清楚的说法

### 不要这样写

```text
随便优化一下
```

### 可以先改成这样

```text
把首页第一屏文案改得更适合初学者理解，只改这个文件，保留现有结构，改完给我 diff 和构建结果。
```

## 一个够用的替换公式

当你发现自己快写出模糊句子时，先套这个公式：

```text
目标 + 范围 + 验收
```

比如：

- 目标：改什么
- 范围：只改哪里
- 验收：怎么判断改完了

大多数提示词反模式，问题不在“表达不好”，而在于把关键边界和验收条件省掉了。

可以直接用结构替换模糊词：目标 + 约束 + 验收。
