# 提示词模板

看到“模板”时，常见的反应有两种：

- 要么觉得模板太死，不想用
- 要么直接照抄，结果连里面哪些该改都没分清

模板的主要作用，是帮你少漏关键段落，不会替你思考。

模板页面的目标是保住任务结构，不是替你生成唯一正确答案。

## 模板怎么用

可以这样用：

1. 先选和任务最接近的模板类型
2. 把 `【】` 占位内容替换成你自己的真实任务
3. 删除不相关的段
4. 补上这次任务特有的约束和验收

模板更像脚手架，不是标准答案。

| 模板 | 适用场景 |
|---|---|
| [理解](/prompts/templates/understand/) | 读代码库、文档或资料，先建立认知 |
| [创建](/prompts/templates/create/) | 从零实现功能、文稿或产物 |
| [修改](/prompts/templates/change/) | 在现有基础上迭代改动 |
| [诊断](/prompts/templates/diagnose/) | 定位问题根因，先不改代码 |
| [审查](/prompts/templates/review/) | 审查 diff、PR 或文档变更 |
| [研究](/prompts/templates/research/) | 带引用的调研与对比 |
| [自动化](/prompts/templates/automate/) | 重复任务、脚本与无人值守流程 |

## 从模板升级为工作流

有些提示词用一次就够；有些会反复出现，应该继续沉淀。

| 反复出现的任务 | 先做成 | 稳定后可以升级为 |
|---|---|---|
| PR 准备 | 审查/修改模板 | Skill，输出固定检查清单 |
| API 文档生成 | 创建/修改模板 | Skill + 文档脚本 |
| 扩展测试覆盖 | 修改模板 | Skill + 测试命令约定 |
| 性能优化排查 | 诊断模板 | 子 Agent 或专项 Skill |
| 每次写文件都要检查格式 | 不适合只靠模板 | Hook |
| 查外部工单再改代码 | 研究模板 | MCP + Skill |

模板适合“人主动发起”；Skill 适合“同类任务反复按固定流程做”；Hook 适合“到了节点必须自动检查”；MCP 适合“需要接外部系统”。

## 快速判断：这个任务该写成什么

可以先问 4 个问题：

1. 这件事是不是只做一次？
2. 下次再做时，步骤会不会基本一样？
3. 结果是否有固定检查清单或输出格式？
4. 是否需要外部系统、脚本或自动拦截？

| 判断结果 | 推荐形态 |
|---|---|
| 只做一次，仍需讨论 | 直接写完整提示词 |
| 经常重复，但还在调整 | 做成模板 |
| 流程稳定，输出格式固定 | 做成 Skill |
| 需要另一个独立角色深挖 | 拆给子 Agent |
| 需要读外部系统 | 接 MCP，并优先只读 |
| 每次到某个节点都必须检查 | 做 Hook |
| 要发给团队统一使用 | 打包成 Plugin |

提示词不是越长越好。真正值得复用的，是那些已经被你反复验证过、边界清楚、验收标准明确的任务。

## 常见误区

### 1. 模板就是拿来原样复制的

如果不改占位内容、不删不相关段落，模板反而会把任务写空。

### 2. 只要用了模板，提示词自然就专业了

模板只能帮你保住结构，不能替你决定：

- 真实目标是什么
- 约束应该划到哪
- 验收该怎么写

### 3. 模板越全越好

对新手来说，模板保持“够用但不臃肿”就可以。

先选对模板类型，再把它改成自己的任务；不要把模板本身直接当任务。
