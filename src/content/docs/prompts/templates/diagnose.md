# 诊断模板

诊断类任务常见的误区，是嘴上说“先排查”，实际还是默认它直接修。

诊断模板的重点，是把“找原因”和“动手修”拆开。

## 模板

```text
现象：【错误信息、失败测试、用户报告】
背景：【最近变更、环境、复现步骤】
输入：@【日志/测试/相关代码】
约束：先不要改代码；列出 2–3 个可能根因及验证方法。
输出：
1. 最可能根因（附证据）
2. 可执行的验证步骤（命令或检查点）
3. 若验证通过，修复计划草案（等我确认再执行）
```

## 什么时候适合用这个模板

- bug 还没定位
- 测试红了，但不知道哪层坏了
- 你怀疑问题复杂，不想让它直接猜修

## 常见误区

### 1. 诊断太慢，不如直接改

很多返工就是因为跳过了诊断。

### 2. 列 2–3 个可能根因会不会太啰嗦

不会，这反而能帮你看出它是不是在乱猜。

诊断模板先要求它说明为什么会坏，再讨论怎么改。
