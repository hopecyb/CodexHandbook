很多“看图做事”失败，问题不在模型没看见，而在于只给了图，**没说明希望它从图里看什么**。

图像提示的重点，是帮 Codex 建立这三件事：

1. 这张图是什么
2. 你希望它关注哪里
3. 输出最终要服务什么任务

## 适合用图像提示的场景

| 场景 | 图像作用 |
|---|---|
| UI bug 排查 | 让 Codex 看到异常位置与状态 |
| 设计还原 | 提供布局、层级、间距、氛围参考 |
| 文档解释截图 | 让它基于界面写说明或教程 |
| 白板/流程图整理 | 把手写图转成结构化描述 |
| 对比当前与期望 | 帮助它识别差异，而不是猜需求 |

如果任务重点在“外观、位置、视觉状态”，图片通常比长段文字更有效；如果重点在“业务规则”，图片更多只能当辅助证据。

## 图像提示的四段结构

推荐和文字提示一样，也保持结构化：

### 1. 图像身份

告诉它这张图是什么、来自哪里。

例如：

```text
这是当前生产环境的登录页截图，来自 iPhone 14 Safari。
```

### 2. 关注区域

明确指出你希望它看哪里，不要丢一句“你自己找问题”就结束。

例如：

```text
重点关注底部按钮和输入框之间的间距，以及键盘弹出后的布局变化。
```

### 3. 任务目标

说明你要它做什么：分析、复现、改代码、写说明、输出对比表。

例如：

```text
先分析可能原因，不要立刻改代码。给出 2-3 个最可能相关的前端文件。
```

### 4. 输出格式

告诉它你要什么结果，避免泛泛而谈。

例如：

```text
输出：
1. 你从图里观察到的现象
2. 可能原因
3. 建议检查的文件
4. 还需要我补的截图
```

## 三种常用模板

### 1. 看图找问题

```text
我上传的是当前页面截图。重点看红框区域。
请先描述你观察到的异常，再列出 2-3 个可能原因。
先不要修改代码。
```

### 2. 按图实现

```text
我上传的是目标设计稿。
请根据这张图总结页面结构、关键组件、响应式要点和视觉风格。
如果开始实现，请优先保持结构和层级一致，不要自行增加功能。
```

### 3. 当前 vs 期望 对比

```text
我会上传两张图：第一张是当前效果，第二张是期望效果。
请对比两者在布局、文字层级、间距和交互暗示上的差异，并给出修复优先级。
```

## 想让它看得更准，要补哪些文字

图片本身常常缺少运行上下文，所以这些信息很有帮助：

- 设备或浏览器
- 当前状态是否包含 hover / focus / 错误态
- 页面滚动位置
- 这是“当前效果”还是“目标效果”
- 是否还原既有设计系统

例如“桌面端 Chrome 正常，只有 iOS Safari 出现问题”这句话，常常比再多一张截图更有价值。

## 多张图怎么给最好

### 做“成对输入”

比较好用的方式是：

- 当前图
- 期望图

或者：

- 正常状态
- 异常状态

不要一口气上传一堆没有说明的图片，让 Codex 自己猜顺序。

### 给每张图一个角色

例如：

```text
图 1：桌面端当前效果
图 2：移动端当前效果
图 3：设计稿目标效果
```

这样它更容易把对应关系梳理清楚。

## 图像提示最容易犯的错

### 只说“按这个做”

这会让 Codex 试图从图里反推所有要求，结果经常把你并不在意的细节也当成必须项。

### 只给局部，不给上下文

局部截图能看出问题点，但未必能看出这是哪个页面状态、是否受响应式影响、是不是弹层场景。

### 把设计图当成完整规格

设计稿能表达外观，但未必能表达数据来源、边界条件、交互逻辑。业务规则仍需文字补充。

### 误以为图片能替代验收

即使是按图实现，最终仍要看真实页面、diff、断点表现和可用性。图片是输入，不是验收结果。

## 一条实用经验

如果你希望 Codex“像设计评审一样看图”，就让它先做**观察**，再做**判断**，最后才做**建议**。

例如：

```text
先只描述你从图里观察到的现象，不要下结论。
然后再推测最可能的原因。
最后给出建议的修改方向。
```

这通常比一句“帮我修”更清楚，后面也更容易往下做。
