title: 定义完成标准
description: 写出可检查的完成条件。
---

很多人提任务时，会把“我要什么”说出来，却没把“做到什么程度算完成”说清楚。结果就是事情到底做完没有，只能凭感觉。

完成标准，其实就是你准备怎么验结果。

验收标准必须 **可观察**：

- 差：「代码质量提高」
- 好：「`npm test` 通过；`Button` 组件支持 `disabled`；故事书截图与设计一致」

## 为什么很多任务最后会说不清到底做完没

很多时候，是目标和完成标准混在了一起。

- **目标**：你想得到什么结果
- **完成标准**：你怎么确认这个结果真的达到了

比如“修好这个 bug”是目标；  
“能稳定复现修复、相关测试通过、没有引入新的控制台报错”才更接近完成标准。

## 常见误区

### 1. 只要结果看起来差不多，就算完成

这在小任务里最容易埋坑。“看起来差不多”经常会漏掉测试、边界情况和副作用。

### 2. 完成标准就是多写几句夸结果的话

完成标准要能检查，不是写得像总结发言。

### 3. 构建通过就等于完成

不一定。

构建通过一般只是其中一个检查点，不代表：

- 功能真的对了
- 范围没超
- 文案适合读者
- 来源核验过

## 一种常用写法

如果一时不知道怎么写，可以先从这 3 类里选：

- **功能检查**：结果行为是否符合预期
- **技术检查**：构建 / 测试 / lint 是否通过
- **范围检查**：是否只改了约定范围

比如：

```text
验收标准：
- 只改 docs 首页文案，不改布局与组件
- `pnpm build` 通过
- 首屏文案更适合初学者理解，不再默认读者懂术语
```

## 判断方法

写完后可以问自己一句：

> **如果现在交给另一个人，他能不能据此判断“过”还是“不过”？**

如果不能，多半还是写得太虚。

说到底，就是别让“到底算不算做完”只能靠猜。
