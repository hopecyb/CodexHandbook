很多任务失败，问题不在目标完全没说，而在**边界不清**。

你说“帮我改一下这个页面”，Codex 可能会理解成：

- 只改文案
- 可以顺手改样式
- 可以动组件
- 可以加依赖

而你想要的，可能只是“只改这一段文案，不许碰结构”。

约束回答的是：这件事做到哪一步为止，什么绝对不要碰。

## 内容

它主要帮你避免这些问题：

- 顺手多改
- 越权操作
- 改到你没打算让它碰的层
- 看起来完成了，但代价太大

## 常用约束

约束回答的是：“哪些事绝对不要做？”

- 只改列出的文件/目录
- 不改 API 契约 / 不改数据库
- 不添加新依赖
- 不发起网络请求
- 保持现有格式化工具配置

## 怎么区分“目标”和“约束”

- **目标**：你想要它做成什么
- **约束**：它做这件事时不能越过哪些线

比如：

```text
目标：把首页 Hero 文案改得更清楚
约束：不要改布局，不要新增依赖，不要修改 CTA 行为
```

没有约束时，Codex 很可能会把“改得更清楚”理解成一个更大的改版任务。

## 常见误区

### 1. 约束会不会限制太多，让结果变差

很多时候，清楚的约束反而会让结果更贴近你的真实需求，因为它少走弯路。

### 2. “别改太多”已经算约束了

这类说法太模糊。

更有用的是：

- 只改 `src/content/docs/...`
- 不改组件
- 不改接口
- 不装依赖

### 3. 约束只在高风险任务里才需要

小任务也同样需要，因为这时候很容易顺口说一句模糊需求，让它自己扩大发挥。

## 一个够用的写法

如果一时不知道怎么写，可以先直接用这个骨架：

```text
约束：
- 只改【目录/文件】
- 不要改【组件 / API / 数据库 / 配置】
- 不要新增依赖
- 信息不够时先问，不要猜
```

## 什么时候约束要写得更细

下面这些情况，约束最好明确写出来：

- 老项目、历史包袱多
- 你只想做局部修补
- 团队对风格或架构有硬要求
- 涉及权限、联网、安装依赖

目标告诉 Codex 要做什么，约束告诉它做到哪里为止。

权限边界最好和约束一起写，减少“顺手”越权。相关页见 [定义完成标准](/prompts/define-done/) 和 [权限与沙箱](/guide/permissions-and-sandbox/)。
