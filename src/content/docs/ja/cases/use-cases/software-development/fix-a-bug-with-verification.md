これはファイル名を置き換えるだけのプロンプトテンプレートではありません。リポジトリにある実際の開始コードを使い、まずテスト失敗を確認し、同じテストが参考修正によって通過する過程を追います。

## メタ情報

| 項目 | 内容 |
|---|---|
| 対象読者 | 開発者 |
| クライアント | CLI または IDE（ローカルリポジトリ） |
| 想定時間 | 25〜45 分 |
| 前提知識 | ターミナルで Node.js コマンドを 1 つ実行し、簡単な JavaScript を読めること |
| サンプルの依存関係 | Node.js 組み込みの `node:test`。外部パッケージは不要 |
| 検証日 | 2026-08-25 |

## 1. 目標と背景

**業務背景：** ショッピングカートの `calculateTotal` は割引率を受け取ります。割引なしでは正しく動きますが、`10` を 10% として渡すと、関数が `10` をそのまま倍率として扱い、負の値を生成します。

**目標：** 割引計算の誤りを特定し、最小修正を行い、同じテストで問題が RED から GREEN へ変わることを示します。

**成功基準：**

- 開始テストが安定して 1 件失敗し、アサーションが「期待値 36、実際値 -360」を示す
- 修正後に 3 件のテストがすべて通過する
- 修正は割引率の変換だけに限定し、ショッピングカート API を書き換えない
- 「修正後に GREEN」だけでなく「修正前に RED」も保存すべき理由を説明できる

**範囲外：** 金額精度ライブラリ、税、通貨換算、依存関係の更新、UI。

![検証付き Bug 修正ワークフロー](/diagrams/verified-bug-fix-workflow-ja.svg)

図で重要なのは 2 つの戻り経路です。関連テストが失敗したら最小修正へ戻り、全回帰または diff レビューが失敗したら根本原因分析へ戻ります。早く GREEN にするためにアサーションを削除したり、変更範囲を広げたりしないでください。

## 2. 準備する資料

サンプルのディレクトリ：

```text
examples/complete-workflows/developer/verified-bug-fix/
├── brief.md
├── starter/
│   ├── cart.js
│   └── cart.test.js
├── prompts/
│   ├── 01-explore.md
│   ├── 02-fix-and-verify.md
│   └── 03-review.md
├── solution/
│   ├── cart.js
│   └── cart.test.js
└── validation.md
```

`starter/` は意図的に Bug を残した練習の開始点、`solution/` は独立して実行できる参考解答です。参考解答を直接使って練習しないでください。

## 3. 第 1 歩：RED を再現する

リポジトリのルートで実行します。

```bash
node --test examples/complete-workflows/developer/verified-bug-fix/starter/cart.test.js
```

期待される結果：コマンドは非ゼロで終了し、3 件中 1 件が失敗します。重要な証拠は次のようになります。

```text
Expected values to be strictly equal:

-360 !== 36
```

テストが失敗しない場合は停止してください。`starter/` を実行しているか、Node.js のバージョン、ファイルが事前に変更されていないかを確認します。安定した RED がなければ、元の問題の基準となる証拠もありません。

## 4. 第 2 歩：読み取り専用で探索する

### 探索

```text
まずファイルを変更しないでください。次を読んでください。
- examples/complete-workflows/developer/verified-bug-fix/starter/cart.js
- examples/complete-workflows/developer/verified-bug-fix/starter/cart.test.js

次の 6 点以内で説明してください。
1. どの入力が失敗を引き起こすか
2. 期待値と実際値
3. パーセントと倍率の式での違い
4. 最小修正を置くべき行
5. 変更してはいけない公開動作
6. 修正後に実行すべき検証
```

適切な根本原因の説明では、呼び出し側の `10` が 10% を表すのに、実装が `subtotal * 10` を直接計算し、`/ 100` の変換を欠いていることを指摘します。

## 5. 第 3 歩：計画して最小修正を実行する

```text
starter/cart.js の割引率変換だけを変更してください。
関数名、引数、テストのアサーション、ファイル構造は変更せず、依存関係も追加しないでください。

修正後、次の順で実行してください。
1. starter/cart.test.js を実行する
2. 実際のテスト概要を表示する
3. 変更した行と理由をまとめる
4. Git の commit や push はしない
```

最小修正の中心は次の行です。

```js
const discount = subtotal * (discountPercent / 100);
```

テストの `36` を `-360` に変更して GREEN にしないでください。それは期待値を書き換えただけで、業務ルールを修正していません。

## 6. 第 4 歩：GREEN を検証する

練習の開始点を変更したくない場合は、参考解答を直接実行できます。

```bash
node --test examples/complete-workflows/developer/verified-bug-fix/solution/cart.test.js
```

期待される結果：3 件のテストがすべて通過し、プロセスの終了コードは 0 です。

検証記録には少なくとも次を含めます。

| 証拠 | 答えるべき質問 |
|---|---|
| 修正前の失敗コマンド | 元の問題を安定して再現できるか？ |
| 失敗したアサーション | テストは本当にこの Bug を対象にしているか？ |
| コード diff | 変更は根本原因だけに触れているか？ |
| 修正後の関連テスト | 同じ動作は今、正しくなったか？ |
| より広い範囲のテスト | 周辺機能を壊していないか？ |

この練習ディレクトリには 1 組のテストしかありません。実際のプロジェクトでは、`AGENTS.md` に従って lint、型チェック、全テストを実行します。

## 7. 第 5 歩：Review

```text
この修正をレビューしてください。ファイルは変更せず、まず findings を列挙してから結論を出してください。
- 割引率の変換を本当に修正しているか。テストを緩めていないか
- 関数シグネチャや無関係なロジックを変更していないか
- 空のカート、割引なし、10% 割引をすべてカバーしているか
- このケースの範囲外に残る金額精度のリスクは何か
```

人のレビューでは、追加依存関係、デバッグログ、ファイル全体の整形、Git 操作がないことも確認します。

## 8. 失敗と回復

| 問題 | 対処 |
|---|---|
| 開始テストが失敗しない | `starter/cart.test.js` を実行しているか確認し、変更前の開始点を復元する |
| テストを変更したら GREEN になった | テストのアサーションを復元し、実装の割引率変換だけを変更する |
| 関連テストがまだ失敗する | 失敗値を比較し、`/ 100` の位置を確認する |
| 全テストで新しい失敗が出る | 根本原因分析に戻り、公開動作と変更範囲を確認する |
| テストが時々失敗する | まずテスト環境を安定させ、1 回の GREEN を証拠にしない |

## 9. 練習から実際のリポジトリへ移す

サンプルのパスを自分のファイルへ置き換えます。ただし、証拠の構造は維持してください。

```text
目標：【観測可能な誤動作】を修正する。
再現コマンド：【正確なコマンド】。現在の安定した失敗は【重要なアサーション】。
範囲：【実装ファイル】と必要なテストだけを変更する。リファクタリングや依存関係更新はしない。
受け入れ：元の失敗テスト、新しい境界テスト、【全テストコマンド】が通過し、diff に無関係な変更がない。
権限：push、公開、本番データの変更は禁止。追加権限が必要なら停止して説明する。
まず読み取り専用で根本原因とリスクを特定し、私が計画を確認してから変更する。
```

## 10. 蓄積

- 同種の Bug が繰り返す場合は `AGENTS.md` に規約を追加する
- `regression-guard` Skill として抽出し、RED、GREEN、回帰の証拠を必須にする
- 頻出する境界テストを会話だけに残さず CI に追加する
