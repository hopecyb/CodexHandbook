**仕様駆動**は、大量のファイル変更の前に、目標、範囲、インターフェース、受け入れ基準を記した短い仕様を準備することです。[ブレインストーム](/cases/workflows/brainstorm-before-building/) の後に接続でき、すでに明確化された要件と組み合わせて [EPXV](/cases/workflows/explore-plan-execute-verify/) に直接入ることもできます。

## このページの重点

- 仕様はどの程度の詳細が十分か
- Codex に仕様どおり実行させ、勝手にスコープを広げない方法
- 仕様と PR 説明、issue の関係

## 最小限の仕様テンプレート

```markdown
## 目標
一言でユーザー価値

## 範囲
- 含む：…
- 含まない：…

## インターフェース/動作
- 入力 / 出力 / エラー状況

## 受け入れ基準
- [ ] 自動検証可能な項目
- [ ] 人間による確認が必要な項目

## 制約
- 変更不可モジュール、パフォーマンス、互換性
```

テンプレートをリポジトリ `docs/specs/` または issue 本文に置き、タスクで `@` 参照する。

## 推奨ワークフロー

```text
① 仕様の起草（Codex が支援可、人間がレビュー）
② 仕様の確認 → 「仕様どおり実行」と返信
③ 段階的実行、各ステップで受け入れ項目と照合
④ 仕様変更は版番号または changelog を明示的に更新
```

プロンプト例：

```text
@docs/specs/export-csv.md を読んでください。まず仕様に照らして実装計画とリスクを列挙してください。
仕様に列挙されていない機能は追加しないでください。確認後にコードを書いてください。
```

## テスト駆動との連携

仕様の受け入れ項目はできるだけ**テスト可能**にする。テストに書けるものは先にテストを書く。[テスト駆動の作業](/cases/workflows/test-driven-work/) を参照。

## よくある誤り

- 仕様が設計ドキュメントのように長く、重要な制約が見つけにくい
- 実行中にスコープが静かに拡大し、仕様が更新されない
- 受け入れ基準が曖昧（「もっと使いやすい」）で議論になる
- 仕様が `AGENTS.md` のアーキテクチャ規約と矛盾する

## 安全境界

- 仕様に明記された「外部 API の呼び出し許可」のみネットワーク関連実装を許可する
- PII を扱うフィールドは仕様で処理方法を明記する

## 受け入れチェックリスト

- [ ] 範囲外の事項が明確に除外されている
- [ ] 少なくとも 3 条の検査可能な受け入れ基準がある
- [ ] 実行前に人間または文書による確認がある
- [ ] 変更が仕様ファイルに同期されている
