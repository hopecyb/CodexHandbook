**失敗からの回復**は、タスクが軌道を外れたり途中で止まったあと、状況を安定させる方法を扱います。本章は **検知 → 損失停止 → 回復 → 事後分析** の反復手順を示し、[取り消しと回復](/guide/getting-started/undo-and-recover/) および [長時間タスク管理](/cases/workflows/long-running-task-management/) と組み合わせます。

## 本ページの内容

- いつ `git stash`、コミット revert、新スレッドを使うか
- 失敗情報を次のプロンプトにどうまとめるか
- チームが繰り返し問題を記録する方法

## 失敗のシグナル

| シグナル | 可能な対応 |
|---|---|
| テストが広範囲で失敗 | 実行停止。diff を狭める |
| 誤ったディレクトリ／ブランチ | 取り消し。正しいパスを再 `@` |
| 計画と実装が大きく乖離 | 探索または計画に戻る |
| コンテキスト過長で制約忘却 | 新スレッド + 要約引き継ぎ |
| 承認／ルールが繰り返し拒否 | ルールとタスクの矛盾を確認 |

## 最小限の回復フロー

```text
1. さらなる変更を止める（「まだコードを書かないで」と明示）
2. 状態保存：git status / stash / スレッド ID 記録
3. 5 項目以内で要約：目標、ここまでの作業、失敗症状、仮説
4. 選択：ロールバック / 範囲縮小 / 新スレッドで継続
5. 成功後、AGENTS.md または事例の事後分析に書く
```

プロンプト例：

```text
現在の変更でテストが 12 件失敗した。まだ直し続けないで。
直近 3 コミットの影響ファイルを列挙し、最小のロールバック点を提案し、
より小さな修正計画を出して。
```

## 推奨ワークフロー

```text
検知（テスト / 人 / CI）
    → 損失停止（書き込み停止、ブランチ分離）
    → 診断（「修正前に診断」を参照）
    → 小さなステップで再試行
    → 教訓を記録
```

マルチ Agent： [マルチ Agent 協調](/cases/workflows/multi-agent-coordination/)——失敗時はどのサブタスクがロールバック責任か明確に。

## よくあるミス

- パッチを逆方向に積み重ねる
- 失敗ログを保存せず、新スレッドで同じエラー
- 救済のため `git push` を強行
- 環境（ローカル vs Cloud）を区別しない——回復手順が無効に

## 安全境界

- 回復自体も [コマンドルール](/guide/customization/rules/command-rules/) で制約
- 本番インシデント：先にロールバック、原因分析は後——Agent に本番データを直接直させない

## 受け入れチェックリスト

- [ ] 選んだ回復戦略と理由を説明できる
- [ ] リポジトリが再ビルド・再テスト可能な状態
- [ ] 失敗原因と教訓を記録（issue または AGENTS.md）
- [ ] 新スレッドが必要なら重要制約の要約を含む
