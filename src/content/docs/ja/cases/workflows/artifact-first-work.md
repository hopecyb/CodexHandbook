**成果物優先**は、まず成果物の形と配置を明確にし、Codex にステップを逆算させる方法です。Markdown ドキュメント、OpenAPI、マイグレーションスクリプト、スライドアウトラインなど出力が明確なタスクに適し、[仕様駆動](/cases/workflows/specification-driven-work/) と組み合わせても使えます。

## このページの重点

- プロセスの詳細ではなく成果物構造の記述方法
- 複数ファイル成果物の一貫性チェック
- [ファイルと成果物](/guide/files-and-artifacts/) 機能との整合

## 最小限の実践方法

```text
目標成果物：
- docs/api/auth.md（3 セクション：概要、エンドポイント、エラーコード）
- スタイルは @docs/api/users.md と一致

まず目次アウトラインと各節の要点を出力してください。全文は書かないでください。
確認後に生成し、内部リンクが有効か自己チェックしてください。
```

## 推奨ワークフロー

```text
成果物リストの定義（パス + 形式 + サンプル参照）
    → アウトラインまたは骨格ファイル
    → 人間による確認
    → 内容の充填 + 相互リンク
    → 検証（lint、リンクチェック、プレビュー）
```

視覚的成果物にはスクリーンショットまたはプレビュー説明を要求できる。[成果物の検証](/guide/quality/verify-artifacts/) を参照。

## よくある誤り

- 成果物パスがリポジトリ規約と不一致（誤ったディレクトリに配置）
- 単一ファイルのみ生成し、ナビゲーションと index 更新を無視
- サンプルと照合せず、スタイルが不統一
- バイナリ成果物（pptx/docx）の人間による開封・受け入れ方法を説明しない

## 安全境界

- 生成物に第三者の著作権コンテンツが含まれる場合、人間によるコンプライアンスチェックが必要
- 本番設定パスを上書きせず、まずブランチまたは `draft/` で成果物を作成する

## 受け入れチェックリスト

- [ ] 宣言されたすべてのファイルが存在し、開ける
- [ ] 形式と参照サンプルが一致する
- [ ] リンク/目次/Frontmatter が有効
- [ ] [完了の定義](/prompts/define-done/) に合致する
