Codex にいきなり bug 修正をさせると、手戻り率は通常高くなります。診断ワークフローは **症状 → 仮説 → 証拠 → 最小修正** をより重視します。

## いつ使うか

- テスト失敗の原因が不明
- 本番アラート、ユーザー報告の「偶発」
- 前回の修正後も問題が残る

## ステップ

### 1. 変更を凍結

```text
まだビジネスコードを変更しないでください。再現手順、関連ログ、最近の関連 commit を列挙してください。
```

### 2. 範囲を絞る

- 二分探索：どの commit で導入されたか？
- 分離：最小再現リポジトリまたはテストケース

### 3. 仮説を形成

Codex に次を出力させる：

```text
仮説 A：… 検証方法：…
仮説 B：… 検証方法：…
```

### 4. 仮説を検証（読み取り優先）

対象テストの実行、一時ログの追加（破棄可能なブランチ）、監視の読解。

### 5. 最小修正

一度に 1 つの根本原因のみ修正する。「ついでにリファクタリング」は避ける。

### 6. 回帰検証

元の失敗ケース + 隣接シナリオ + 再発防止テスト。

## プロンプトテンプレート

```text
「診断してから修正」に従ってください：
1. @path/to/failing-test と実装を読み、失敗原因を説明する（スタックの行番号を引用）
2. 2 つの仮説と読み取り専用での検証方法を提示する
3. 仮説確認後に修正を書き、修正後は関連テストのみ実行する
```

## EPXV との関係

診断は **探索** 段階の深化版と見なせる。計画段階では「仮説が誤っていた場合のロールバック方法」も明記する。

## よくある誤り

- 再現せずにコードを変更する
- 1 つの patch で 3 つの問題を同時に修正し、review 不能になる
- 一時ログを削除するが恒久テストを追加しない
