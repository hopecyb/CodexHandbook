**構築前にブレインストーム**は、目標が曖昧で案が複数あるタスクに適します：新機能、リデザイン、コンテンツ選題、技術選定。[探索—計画—実行—検証](/ja/cases/workflows/explore-plan-execute-verify/) の①探索段階と接続しますが、すぐにコードを読んでファイルを変更するのではなく、**発散と収束**をより重視します。

## このページが解決する問題

- いつ先に brainstorm する価値があり、いつ直接 EPXV するか
- 発散範囲をどう制限し、空談を避けるか
- 成果物：オプション表、意思決定記録、次のステップ計画

## 誰に適するか

| シナリオ | 例 |
|---|---|
| プロダクト/機能 | 「ユーザーにエクスポート機能を追加、UI は 3 種類」 |
| コンテンツ | 「このチュートリアルの対象読者と構成の分け方」 |
| 技術 | 「キューと cron のどちらで定期タスクを実装するか」 |

## 最小限の実践方法

**段階 A — 発散（時間制限）**

```text
まだファイルを変更しないでください。「CSV エクスポート」要件について、3 つの実装経路を列挙してください：
各経路に長所短所、関与モジュール、工数見積もり（S/M/L）を書いてください。
最終案は選ばないでください。
```

**段階 B — 収束**

```text
上表に基づき、デフォルト案 1 つと代替案 1 つを推奨してください。
確認が必要な 2 つの意思決定点（形式、権限）を説明してください。
```

**段階 C — 計画へ進む**

確認後、[仕様駆動](/ja/cases/workflows/specification-driven-work/) または EPXV の②計画に接続する。

## 推奨ワークフロー

```text
制約の明確化（時間、技術スタック、変更不可部分）
    → 3–5 オプションの発散（コード禁止）
    → 「価値 / リスク / コスト」でソート
    → 人間が方向を選択するか追加情報を要求
    → 文書化された計画 + 実行
```

**タイムボックス**を設定する：例えば 15 分以内に発散を完了し、議論の漂流を防ぐ。

## よくある誤り

- brainstorm を実行と混同し、モデルがファイル変更を始める——「まだ変更しない」で制約する
- オプションが多すぎてソートされず、意思決定疲労になる
- 却下した案を記録せず、2 週間後に同じ議論を繰り返す
- 制約をスキップし、美しいが実現不可能な案になる

## 安全境界

- ブレインストーム段階でも機密ファイルを読む可能性がある——`@` で範囲を正確に参照する
- コンプライアンス、プライバシーに関わる案は人間の法務/セキュリティレビューが必要。モデルのみで決定してはならない

## 受け入れチェックリスト

- [ ] 少なくとも 2 つの実行可能オプションと明確な推奨がある
- [ ] 意思決定点が標示され、人間の確認を待っている
- [ ] 未承認のリポジトリ書き込みがない
- [ ] 次のステップが文書化された計画に接続できる
