承認は不可逆な操作を人間に残します。本ページは一般的なパターンをまとめます。

## 承認の段階

```text
自動安全ゾーン（読み取り、分析、計画）
    ↓
プロンプト確認ゾーン（ファイル書き込み、コマンド実行、ネットワーク）
    ↓
人の必須ゾーン（push、データ削除、外部送信、本番設定変更）
```

具体的なダイアログ挙動は [製品入口](/guide/) により異なりますが、原則は同じです。

## パターン 1：先に計画、後で実行

```text
ルール：私が「計画を承認」と言うまでリポジトリファイルを変更しない。
```

向く場面：不慣れなコードベース、本番関連、大きな diff。

## パターン 2：コマンドホワイトリスト

[AGENTS.md](/guide/customization/agents-md/writing-effective-instructions/) に：

```md
再確認なしで許可：pnpm test、pnpm lint、git status、git diff
毎回確認：git push、npm publish、database migrate
```

ホストポリシーと矛盾する場合は**より厳しい**方が優先。

## パターン 3：二段階マージ

1. Codex がドラフト PR またはローカルブランチを開く
2. 人が CI + レビュー後にマージ

Cloud：[プルリクエストを作成する](/guide/web-and-cloud/create-pull-requests/)。

## パターン 4：読み取り専用偵察

```text
今回は読み取り専用：ファイル読み取り、テスト実行、ローカル API への curl は可；
ディスク書き込みや git commit は不可。
```

監査、未知プロジェクトの学習、本番診断向け。

## いつ拒否してやり直すか

| シグナル | 提案 |
|---|---|
| 計画が目標と合わない | 実行を拒否。計画の改訂を要求 |
| 範囲が膨らむ | 停止。タスク分割 |
| テストがスキップされた | マージ拒否。検証を要求 |
| コマンドの説明ができない | 拒否。説明を要求 |

## Automations との関係

無人タスクでも人の確認ポイントを設計——[定期とバックグラウンドタスク](/skills/automations/scheduled-tasks/)。

## よくあるミス

- リスクを忘れた「常に許可」
- 承認の形だけ——diff を読まない
- 明示モードの代わりに口頭の「ミスしないで」

## 受け入れチェックリスト

- [ ] タスク開始前に承認モードを宣言
- [ ] 高リスク操作に第二者レビューまたは CI ゲート
- [ ] `git push` などにチーム統一ポリシー
