**出典付きリサーチ**ワークフローは、結論が**出典**（公式ドキュメント、論文、リポジトリファイル）に戻れることを重視し、モデルの自信ある捏造ではありません。技術選定、競合比較、文献レビュー、政策解釈に適しています。

## このページが解決する問題

- [ウェブ検索](/guide/tools/web-search/) と読み取り専用リポジトリの使い分け
- 引用形式と不確実性の表記の求め方
- [出典の検証](/guide/quality/validate-sources/) との連携

## 最小限の実践方法

```text
「本リポジトリのシナリオにおける Rust と Go の適性」をリサーチしてください：
1. まず評価軸を列挙する（パフォーマンス、エコシステム、チームの習熟度）
2. 各結論に出典 URL または @リポジトリ内ファイルパスを付ける
3. 検証できないものは「要確認」と表記する
4. 最後に推奨と未解決の質問を提示する
コードは変更しないでください。
```

## 推奨ワークフロー

```text
問題と除外項目の定義
    → 出典の収集（検索 / ドキュメント読解 / MCP）
    → 比較表 + 長所短所
    → 信頼度と矛盾する出典の表記
    → 人間が決定するか仕様段階へ進む
```

長いリサーチタスクは複数ラウンドに分割する。[長タスク管理](/prompts/long-running-tasks/) を参照。

## よくある誤り

- URL を要求せず、成果物が照合不能になる
- 古いブログと公式ドキュメントを混在させて説明しない
- リサーチ結論を直接実装指示として使い、仕様をスキップする
- 機密データを含むファイルを未承認の外部ツールにアップロードする

## 安全境界

- 内部未公開資料は制御されていない MCP 経由で外部送信してはならない
- 価格、バージョン、地域の利用可否など変動しやすい事実には [検証日](/guide/start-here/handbook-version-policy/) を付ける

## 受け入れチェックリスト

- [ ] 主要結論に少なくとも 1 つのクリック可能または追跡可能な出典がある
- [ ] 矛盾する情報が並列に提示されている
- [ ] 「不確実」な項目が列挙され、事実のふりをしていない
- [ ] 機密データが prompt やログに現れていない
