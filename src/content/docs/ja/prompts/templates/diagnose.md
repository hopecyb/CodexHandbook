# 診断テンプレート

診断タスクのよくある誤解は、口では「先に調査」と言いながら、実際は直す前提で進めることです。

診断テンプレートの要点は、「原因を探す」と「手を動かして直す」を分けることです。

## テンプレート

```text
現象：【エラーメッセージ、失敗テスト、ユーザー報告】
背景：【最近の変更、環境、再現手順】
入力：@【ログ／テスト／関連コード】
制約：先にコードは変更しない。考えられる根因を 2〜3 個と、その検証方法を列挙。
出力：
1. 最もありそうな根因（根拠付き）
2. 実行可能な検証手順（コマンドまたはチェックポイント）
3. 検証が通った場合の修正計画案（実行は私の確認後）
```

## いつこのテンプレートが向くか

- バグの位置がまだ不明
- テストが赤いが、どの層が壊れたか分からない
- 複雑そうで、いきなり当て修正させたくない

## よくある誤解

### 1. 診断は遅い。いきなり直した方が早い

診断を飛ばした手戻りが多いです。

### 2. 根因候補を 2〜3 個挙げるのは冗長

むしろ、推測で当てているかが見えます。

診断テンプレートは、なぜ壊れたかを説明させてから、どう直すかを議論します。
