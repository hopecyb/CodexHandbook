多くの問題は「できない」のではなく、**始めすぎ**です。「直して」と一言言うと、探索・計画・実行が混ざり、最後は diff を見ながら受動的に受け入れることになりがちです。

このとき有効なのは、要件をどんどん長くするのではなく、先に計画を出させることです。

## いつ必ず先に計画を求めるか

| 場面 | 理由 |
|---|---|
| 複数ファイル・モジュールにまたがる | 無関係な領域を誤って傷つけやすい |
| コードベースに不慣れ | まず理解範囲を確認する |
| 要件がまだ揺れている | 食い違いを先に表面化させる |
| 承認後に実行してほしい | 「実行の許可」と「方針の議論」を分ける |
| 高リスクな操作を含む | ロールバックと検証案を先に見る |

typo や単一の文言変更に正式な計画は不要かもしれませんが、「外れると面倒」と感じたら、一度止める価値があります。

## 良い計画に最低限含めるべきもの

最低限でも次の4点をカバーします。

1. 手順
2. 対象ファイルまたは範囲
3. リスクまたは要確認事項
4. 各ステップの検証方法

4 が欠けると、まだ検収可能な計画というより「ToDo リスト」に近いです。

## 3つのよく使う言い回し

### 極簡版

```text
まだコードは変更しないで。3〜5 ステップの計画を出し、どのファイルを変えるか、各ステップをどう検証するかを説明して。
```

向いている場面：大まかな方向は分かっており、どう分解するかだけ見たい。

### 推奨版

```text
まだ実行しないで。現在のリポジトリを踏まえて計画を出して。次を含めて：
1. 目標の理解
2. 番号付き手順
3. 対象ファイルまたはディレクトリ
4. リスクと要確認事項
5. 検証方法

「計画どおり実行して」と返すまでファイルを変更しないで。
```

向いている場面：日常の開発、ドキュメント改修、プロンプト書き換え、設定調整。

### 高リスク版

```text
まだ変更しないで。計画を出し、別途次も説明して：
- どのステップが回帰を入れやすいか
- 失敗したときのロールバック方法
- どの操作に私の確認が必要か
- 完了を証明するテストや手動チェック
```

向いている場面：本番障害、権限設定、自動化スクリプト、モジュール横断のリファクタリング。

## 計画は長いほど良いわけではない

必要なのは**承認でき、軌道修正でき、実行できる**中間成果物であり、長い方案書ではありません。

計画が使えるかは次の3点で判断できます。

- 「ステップ2はやらず別の方法に」と明確に言えるか
- どの重要領域に手を入れるか一目で分かるか
- 始める前にどう検収するか分かるか

できなければ、まだ具体性が足りません。

## 計画へのフィードバックの仕方

全文書き直す必要はありません。同僚に方向を示すように十分です。

よく使う指示文：

```text
ステップ1・2は残し、3は外して。
DB 変更は別ステップに分けて。
まずは読み取り専用の分析だけ。実装には入らないで。
計画に回帰テストとロールバック案を足して。
```

「やり直し」よりコンテキストを節約し、結果を軌道に戻しやすくなります。

## 「すぐ始める」と比べた利点

| 先に計画 | すぐ始める |
|---|---|
| 誤解を先に発見できる | 直してから方向が違うと気づく |
| 承認・協業しやすい | 最終 diff を見るだけになる |
| サブタスクに分割しやすい | 複数目標が混ざりやすい |
| 検証方法が先に見える | 最後にテストを思い出しがち |

多くのワークフローは「探索」と「計画」を分けます。 [探索—計画—実行—検証](/cases/workflows/explore-plan-execute-verify/) を参照。

## 計画でよくある問題

### 動作だけで境界がない

例：「ドキュメントを更新して構造を最適化」とだけ書き、どのディレクトリを変え、どのモジュールは触らないかがない。こういう計画は膨らみやすいです。

### 実装だけで検証がない

例：「コンポーネントロジック変更、スタイル更新、コミット」とだけで、挙動が壊れていない証拠がない。

### タスク一覧だけで要確認事項がない

良い計画は不確実性を認め、前提がすべて成立しているふりをしません。

## チームで使いやすい約束

`AGENTS.md` に次を書いておくとよいです。

```md
- 3 ファイル以上の変更は先に計画を出す
- 確認なしに破壊的コマンドを実行しない
- 計画には検証方法を書く
```

こうすると「先に計画」が一時的な注意ではなく、チームのデフォルトになります。
