要件を書くと情報が増え、散らばりやすく、材料は多いのに要点が不明瞭になり、Codex も誤解しやすくなります。

ここではタスクに含まれることが多い構成要素を整理します。

## タスクの構造

次の順で整理できます。

- 結果は何か
- なぜやるか
- どんな材料が必要か
- 境界はどこか
- 完了をどう判断するか

順序は固定でなくてよいですが、これらを言い切るとタスクは安定します。

## 推奨テンプレート

```text
目標：……（最終成果物は何か）
背景：……（なぜ重要か、現状）
入力：……（関連ファイル／リンク／貼り付け内容）
制約：……（変更可能範囲、スタイル、禁止事項）
受け入れ基準：……（検査可能な完了条件）
権限の境界：……（ネット可否、依存追加可否、設定変更可否）
情報不足時：先に質問し、推測しない。
```

## 各段落の役割

- **目標**：動作だけで結果がないタスクを防ぐ
- **背景**：なぜそうするかを Codex が理解する助けになる
- **入力**：本当に見るべきファイル・リンク・素材を渡す
- **制約**：越境やついでの多変更を防ぐ
- **受け入れ基準**：「終わったか」を検査可能にする
- **権限の境界**：ネット・依存・設定変更の可否を先に言う

## よくある誤解

### 1. 各段落を必ず埋め尽くす

このテンプレートはチェックリストに近く、穴埋め問題ではありません。  
背景が短くてよいタスクもありますが、省略すると判断材料が減ります。

### 2. 目標と受け入れは同じではない

- **目標**：得たい結果
- **受け入れ**：本当に達したとどう判断するか

### 3. 入力は資料を全部貼ればよい

多いより関連が重要です。  
「必ず見る材料」を明示して渡すことが要点です。

## 最小タスクテンプレート

まず使える版だけ書くなら、次に縮められます。

```text
目標：何をどの状態にするか
入力：関連ファイルまたはページはここ
制約：どこだけ変更可、何を触らないか
受け入れ：完了したと私がどう確認するか
不確かなとき：先に質問
```

## 例

```text
目標：docs トップのファーストビュー文言を初心者向けに分かりやすくする
入力：src/content/docs/guide/index.md
制約：このファイルだけ変更。スタイル変更なし。新規コンポーネントなし
受け入れ：既存構造を維持。文言はより口語的に。pnpm build が通る
不確かなとき：理解と変更範囲を先に提示してから着手
```

この構造は推測を減らし、受け入れを直接的にします。テンプレートは削ってよいですが、削った段落の情報は失われると受け入れてください。
