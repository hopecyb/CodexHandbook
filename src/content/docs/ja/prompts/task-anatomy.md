依頼に含める情報が増えると、説明が散らかりやすくなります。材料は多くても、結果、境界、受け入れ基準が混在していると、Codex は空白を自分で補うしかありません。

このページでは、そのまま再利用できるタスク票を示します。各項目がどの問題を解決するか、そしてタスクの説明が「調査、計画、実行、検証」のループにどう入るかを確認できます。

## 対象読者

- Codex を開いて使えるものの、「変更しすぎた」「完了していない」「結果を判断できない」と感じることが多い人
- 口頭で伝えていた要件を Agent に実行させたい開発者、制作者、チーム
- 長時間タスクの範囲、権限、停止条件を定義する必要がある人

## タスクの構造

次の順序で整理できます。

- 求める結果
- 実施する理由
- 必要な材料
- 守るべき境界
- 完了の判断方法

順序を厳密に固定する必要はありません。ただし、この 5 点が明確になると、タスクは大幅に安定します。

## 推奨テンプレート

```text
目標：……（最終成果物は何か）
背景：……（なぜ重要か、現状はどうか）
入力：……（関連ファイル / リンク / 貼り付けた内容）
制約：……（変更可能な範囲、スタイル、禁止事項）
受け入れ基準：……（確認可能な完了条件）
権限の境界：……（ネットワーク接続、依存関係のインストール、設定変更が可能か）
情報が不足している場合：推測せず、先に質問してください。
```

![タスク説明から検証可能な結果までのループ](/diagrams/task-execution-loop-ja.svg)

図の左側にある 6 項目は、プロンプトを長くするためではなく、重要な空白を減らすためのものです。実行に入った後は、検証の証拠が次の行動を決めます。合格した場合だけ成果物を渡し、不合格なら失敗情報を添えてタスク説明または計画に戻ります。むやみに変更を続けてはいけません。

## 各項目の役割

- **目標**：タスクに操作だけがあり、結果がない状態を防ぐ
- **背景**：なぜその方法を採るのか、Codex が理解できるようにする
- **入力**：実際に確認すべきファイル、リンク、素材を手元に渡す
- **制約**：範囲外への変更や、ついでの修正を防ぐ
- **受け入れ基準**：「完了したか」を確認可能な状態にする
- **権限の境界**：ネットワーク接続、依存関係のインストール、設定変更が可能かを事前に明確にする

## よくある誤解

### 1. すべての項目を詳しく埋める必要がある

このテンプレートは穴埋め問題ではなく、チェックリストに近いものです。  
長い背景が不要なタスクもありますが、省略すれば判断材料が一つ減ることには変わりません。

### 2. 目標と受け入れ基準は同じもの

同じではありません。

- **目標**は、どのような結果を得たいかを示します
- **受け入れ基準**は、その結果が本当に得られたとどう判断するかを示します

### 3. 入力とは、大量の資料をすべて貼り付けること

入力は、多ければよいわけではありません。量より関連性が重要です。  
「必ず確認すべき材料」を明示して渡すことがポイントです。

## 最小タスクテンプレート

まず実用的な形にしたいだけなら、次のように短縮できます。

```text
目標：何をどのような状態にするか
入力：関連するファイルまたはページ
制約：変更できる場所と、触れてはいけない場所
受け入れ：本当に完了したと、どのように確認するか
不明点がある場合：先に質問する
```

## 曖昧な依頼を実行可能なタスクに変える

### 元の依頼

```text
ドキュメントのトップページを改善してください。
```

この一文では、対象読者、変更可能な範囲、「改善後に何をもって良しとするか」が示されていません。Codex が成果物を作っても、範囲を越えたかどうかを判断するのは困難です。

### 実行可能な形

```text
目標：ドキュメントのトップページのファーストビューを書き直し、Codex を初めて知る読者が 30 秒以内に、
      何のためのページで、どこから始めればよいか理解できるようにする。
背景：現在のトップページは、読者が Agent、コンテキスト、Skill をすでに理解している前提で、入口の説明が直接的ではない。
入力：src/content/docs/guide/index.md
制約：このファイルだけを変更する。ナビゲーション、スタイル、コンポーネントは変更しない。
      Agent という用語の初出時に、平易な説明を一文追加する。
受け入れ基準：
- ファーストビューに、ハンドブックの用途、対象読者、最初に読む入口が明記されている
- 既存の frontmatter と見出し階層が保たれている
- 説明のない専門用語を追加していない
- pnpm build が成功する
権限の境界：サイト内の関連ページは読み取り可能。ネットワーク接続、依存関係のインストール、Git commit は行わない。
情報が不足している場合：不足情報と変更予定範囲を先に列挙し、確認を待つ。
```

### 想定する実行プロセス

1. トップページと隣接する入口ページを読み、現在の問題を説明する。
2. 1 ファイルだけを対象とした短い計画を示す。
3. 文面を変更し、diff の要約を提示する。
4. `pnpm build` を実行する。
5. 4 つの受け入れ基準について、証拠を一つずつ報告する。

## 自分のタスク説明を確認する方法

送信前に、次の点を自問してください。

- 目標は結果を説明しているか、それとも「改善する、処理する、確認する」といった操作だけになっていないか？
- 入力には本当に関連するファイルと材料だけが含まれているか？
- 制約に、触れてはいけない内容が示されているか？
- 別の人でも受け入れ条件を「合格 / 不合格」と判断できるか？
- ネットワーク接続、依存関係のインストール、外部への書き込み、コードの commit に事前承認が必要か？
- 情報が不足している場合、Agent は先に質問する、先に調べる、停止する、のどれを選ぶべきか？

テンプレートはタスクの規模に合わせて省略できます。ただし、項目を一つ削るたびに、判断材料も一種類減ります。1 ファイルの typo 修正に長い背景は不要ですが、複数モジュールの移行を一文の目標だけで依頼することはできません。
