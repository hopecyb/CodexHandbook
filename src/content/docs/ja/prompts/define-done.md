「何が欲しいか」は言うのに「どこまでできたら完了か」を書かない人が多く、終わったかどうかは感覚頼みになります。

完了基準は、結果をどう検証するか、です。

受け入れ基準は **観察可能** でなければなりません。

- 悪い例：「コード品質が向上」
- 良い例：「`npm test` が通る。`Button` が `disabled` をサポート。Storybook のスクリーンショットがデザインと一致」

## なぜ「終わったか」が曖昧になりやすいか

目標と完了基準が混ざっていることが多いです。

- **目標**：得たい結果
- **完了基準**：その結果に本当に達したとどう確認するか

「このバグを直す」は目標です。  
「再現手順で安定して直る、関連テストが通る、新しいコンソールエラーがない」に近いのが完了基準です。

## よくある誤解

### 1. だいたい合っていれば完了

小さなタスクで陥りやすいです。「だいたい」はテスト・境界・副作用を見落としがちです。

### 2. 完了基準は結果を褒める長文

検査可能であることが要点で、総括スピーチではありません。

### 3. ビルドが通れば完了

必ずしもそうではありません。

ビルド成功はチェックの一つに過ぎず、次は保証しません。

- 機能が本当に正しい
- 範囲を超えていない
- 文言が読者に合っている
- 出典を検証した

## よく使う書き方

書き方に迷ったら、次の3類から選べます。

- **機能チェック**：挙動が期待どおりか
- **技術チェック**：ビルド／テスト／lint が通るか
- **範囲チェック**：約束した範囲だけ変えたか

例：

```text
受け入れ基準：
- docs トップの文言だけ変更。レイアウトとコンポーネントは変更しない
- `pnpm build` が通る
- ファーストビュー文言が初心者向けになり、用語に詳しい読者前提ではない
```

## 判断方法

書いたあと、自分に聞いてください。

> **今ほかの人に渡しても、「合格／不合格」をこれで判断できるか？**

できなければ、まだ抽象的すぎる可能性が高いです。

要するに、「完了したか」を推測頼みにしないことです。

検証コマンドを基準に書くと、Agent が自ら実行しやすくなります：[テストの実行](/guide/verification/)
