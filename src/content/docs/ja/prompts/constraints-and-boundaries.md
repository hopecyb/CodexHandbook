多くの失敗は目標が全く無いのではなく、**境界が不明**なことにあります。

「このページを直して」と言うと、Codex は次のように解釈し得ます。

- 文言だけ
- ついでにスタイルも
- コンポーネントも触る
- 依存を追加する

あなたが望むのは「この段落の文言だけ、構造は触らない」かもしれません。

制約が答えるのは：どこまでやるか、何は絶対に触らないか、です。

## 内容

主に次を防ぎます。

- ついでの多変更
- 権限外の操作
- 触るつもりのない層への変更
- 見た目は完了だがコストが大きい

## よく使う制約

制約は「絶対にしてはいけないことは？」に答えます。

- 列挙したファイル／ディレクトリだけ変更
- API 契約・DB は変更しない
- 新規依存を追加しない
- ネットワークリクエストを出さない
- 既存のフォーマッタ設定を維持

## 「目標」と「制約」の違い

- **目標**：何を実現したいか
- **制約**：その過程で越えてはいけない線

例：

```text
目標：トップ Hero の文言をより分かりやすくする
制約：レイアウトは変えない。新規依存なし。CTA の挙動は変えない
```

制約がないと、「より分かりやすく」を大規模リデザインと解釈されやすいです。

## よくある誤解

### 1. 制約が多いと結果が悪くなる

多くの場合、明確な制約の方が本当のニーズに近づき、遠回りが減ります。

### 2. 「あまり変えないで」は制約になっている

曖昧すぎます。

有用なのは次のような具体性です。

- `src/content/docs/...` だけ
- コンポーネントは触らない
- インターフェースは触らない
- 依存は入れない

### 3. 制約は高リスクタスクだけ

小さなタスクでも必要です。曖昧な一言で範囲が広がりやすいからです。

## 十分使える書き方

書き方に迷ったら、この骨組みから始められます。

```text
制約：
- 【ディレクトリ／ファイル】だけ変更
- 【コンポーネント／API／DB／設定】は変更しない
- 新規依存を追加しない
- 情報が足りなければ先に質問、推測しない
```

## 制約を細かく書くべきとき

次のような場合は明示がよいです。

- レガシーが多いプロジェクト
- 局所修正だけしたい
- スタイルやアーキテクチャに硬いルールがある
- 権限・ネット・依存インストールに関わる

目標は何をするか、制約はどこまでで止めるかを伝えます。

権限の境界は制約と一緒に書くと、「ついで」の越権を減らせます。関連：[完了基準の定義](/prompts/define-done/)、[権限とサンドボックス](/guide/permissions-and-sandbox/)。
