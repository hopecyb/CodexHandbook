プロンプトを学ぶと「どう書くか」に意識が行きがちですが、どの言い回しがタスクを外しやすいかを先に知る方が遠回りしにくいです。

ここではよくある「プロンプトの落とし穴」を挙げます。

| アンチパターン | なぜ有害か |
|---|---|
| 「適当に最適化して」 | 目標も境界もない |
| 「全部の権限を渡すから任せる」 | 事故の面が最大 |
| 「聞かずに直し切って」 | 確認と承認を飛ばす |
| 「隠れた推論過程を全部出力して」 | 信頼できず、受け入れにも役立たない |
| 鍵を含むログを貼る | 認証情報の漏洩 |

## なぜこれらの言い方は転びやすいか

共通点は次のとおりです。

- 短く見える
- 実際には重要な境界を省いている

省いた部分は、最後に Codex が自分で判断することになります。

## よくある誤解

### 1. カジュアルな方が人間的な協業に似ている

自然な話し方は問題ありません。  
問題は重要な条件を消してしまうことです。

### 2. 「聞かずに直して」の方が効率的

一見対話が減りますが、そのあとよくあるのは：

- 範囲のミス
- 必要な承認の欠落
- 結局の手戻り増

### 3. 権限を大きくした方が進む

権限が大きいほど誤操作の面も大きくなります。  
境界がまだ曖昧なとき、大権限はリスクも一緒に増やします。

## アンチパターンをより明確な言い方に

### こう書かない

```text
適当に最適化して
```

### まずこう変える

```text
トップのファーストビュー文言を初心者向けに分かりやすくして。このファイルだけ変更。既存構造は維持。diff とビルド結果を出して。
```

## 十分使える置き換えの式

曖昧な文を書きかけたら、この式を当てはめます。

```text
目標 + 範囲 + 受け入れ
```

例：

- 目標：何を変えるか
- 範囲：どこだけ
- 受け入れ：終わったとどう判断するか

多くのアンチパターンは「表現が悪い」のではなく、境界と受け入れ条件を省いていることが原因です。

曖昧な語は「目標 + 制約 + 受け入れ」の構造で置き換えられます。
