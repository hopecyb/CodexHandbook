「画像を見て作業する」失敗の多くは、モデルが見えていないのではなく、画像だけ渡して**図のどこに何を見てほしいか**を書いていないことにあります。

画像プロンプトの要点は、Codex に次の3点を伝えることです。

1. この画像は何か
2. どこに注目してほしいか
3. 最終的にどんなタスクのためか

## 画像プロンプトが向く場面

| 場面 | 画像の役割 |
|---|---|
| UI バグ調査 | 異常の位置と状態を見せる |
| デザイン再現 | レイアウト、階層、余白、雰囲気の参考 |
| ドキュメント用スクリーンショット | 画面に基づく説明・チュートリアル |
| ホワイトボード／フロー図の整理 | 手書きを構造化した説明に変換 |
| 現状と期待の比較 | 差分を推測ではなく特定する |

「見た目・位置・視覚状態」が主なら画像は長文より有効です。「ビジネスルール」が主なら画像は補助証拠にとどまります。

## 画像プロンプトの4段構成

文字プロンプトと同様、構造化を保つのがおすすめです。

### 1. 画像の身份

何の画像か、どこからかを伝えます。

例：

```text
これは本番環境のログインページのスクリーンショットで、iPhone 14 の Safari からです。
```

### 2. 注目領域

どこを見てほしいか明示し、「自分で問題を探して」で終わらせない。

例：

```text
下部ボタンと入力欄の間隔、およびキーボード表示時のレイアウト変化に注目して。
```

### 3. タスク目標

何をしてほしいか：分析、再現、コード変更、説明作成、比較表の出力など。

例：

```text
まず原因を分析し、すぐにはコードを変えないで。関連しそうなフロントエンドファイルを 2〜3 個挙げて。
```

### 4. 出力形式

欲しい結果を指定し、漠然とした回答を避ける。

例：

```text
出力：
1. 画像から観察した現象
2. 考えられる原因
3. 確認すべきファイルの提案
4. 追加で欲しいスクリーンショット
```

## 3つのよく使うテンプレート

### 1. 画像で問題を探す

```text
アップロードしたのは現在のページのスクリーンショットです。赤枠の領域に注目して。
まず観察した異常を説明し、考えられる原因を 2〜3 個挙げて。
まだコードは変更しないで。
```

### 2. 画像どおりに実装

```text
アップロードしたのは目標のデザイン稿です。
この図からページ構造、主要コンポーネント、レスポンシブの要点、視覚スタイルをまとめて。
実装に入るなら、構造と階層の一致を優先し、機能を勝手に足さないで。
```

### 3. 現状 vs 期待の比較

```text
2 枚アップロードします。1 枚目は現状、2 枚目は期待です。
レイアウト、文字の階層、余白、インタラクションの示唆の差を比較し、修正の優先度を出して。
```

## 精度を上げるために足す文字情報

画像だけでは実行コンテキストが欠けがちなので、次が役立ちます。

- デバイスまたはブラウザ
- hover / focus / エラー状態を含むか
- ページのスクロール位置
- 「現状」か「目標」か
- 既存デザインシステムへの準拠か

「デスクトップ Chrome は正常で、iOS Safari だけ問題」は、画像を何枚足すより価値があることが多いです。

## 複数画像の渡し方

### ペアで渡す

使いやすいのは次のような組み合わせです。

- 現状の図
- 期待の図

または：

- 正常状態
- 異常状態

説明なしに大量アップロードして順序を推測させない。

### 各画像に役割を付ける

例：

```text
図 1：デスクトップの現状
図 2：モバイルの現状
図 3：デザイン稿の目標
```

対応関係を整理しやすくなります。

## 画像プロンプトでよくある失敗

### 「これどおりにやって」だけ

Codex が図から要件を全部逆算し、気にしていない細部まで必須扱いしがちです。

### 局所だけで文脈なし

どのページ状態か、レスポンシブの影響か、モーダルかが分からないことがあります。

### デザイン図を完全仕様とみなす

見た目は伝わっても、データソース・境界条件・インタラクションロジックは文字補足が必要です。

### 画像が受け入れを代替できると思う

図どおり実装しても、実ページ・diff・ブレークポイント・使いやすさの確認は必要です。画像は入力であり、検収結果ではありません。

## 実用的なコツ

デザインレビューのように見てほしいなら、**観察**→**判断**→**提案**の順にさせます。

例：

```text
まず画像から観察した現象だけを述べ、結論はまだ出さないで。
そのあと最もありそうな原因を推測して。
最後に修正の方向性を提案して。
```

「直して」より明確で、次の作業に進みやすいです。
