拡張の仕組みが増えるほど、最初に技術名を選んでから問題を当てはめる間違いが起きやすくなります。より確実な順序は、**何を残したいのか、または何を自動で起こしたいのか**を先に問うことです。

混同しやすい名前は次のとおりです。

- プロンプト
- AGENTS.md
- Skill
- MCP
- Plugin
- Scheduled task

どれも Codex を拡張しますが、一行のプロンプトで足りる場合もあれば、より重い仕組みが必要な場合もあります。

## 選択図

![Codex の拡張方式の選択図](/diagrams/extension-selection-map-ja.svg)

これは排他的な決定木ではありません。成熟したワークフローでは `AGENTS.md`、Skill、MCP を同時に使うこともあります。この図の目的は、各方式に得意でない責務を負わせないことです。

## 7 つの判断質問

### 1. 現在のタスクだけに影響するか？

まずプロンプトを使います。目標、入力、範囲、受け入れ条件、権限を明確に書く方法が最も低コストで、実際の問題も観察しやすいからです。

### 2. リポジトリに入るたび必ず守る必要があるか？

`AGENTS.md` に書きます。テストコマンド、コードスタイル、変更禁止ディレクトリ、依存関係のインストール規則などが例です。一度限りの要件を長期的なプロジェクトルールに入れないでください。

### 3. 同種のタスクに安定した手順と出力があるか？

Skill にします。Skill は再利用できる説明を保存し、必要に応じてテンプレート、参考資料、アセット、補助スクリプトを含められます。成功条件が固まっていないフローは、まずプロンプトで試します。

### 4. リポジトリ外のデータや操作が必要か？

MCP または Connector を評価します。本当に必要なツールとデータを列挙し、読み取り専用、最小範囲、監査可能な設定を優先します。ローカルファイルや既存コマンドで解決できるなら、外部接続を追加する必要はありません。

### 5. 固定されたライフサイクルの地点で検査する必要があるか？

Hook を使います。たとえばツール呼び出し前の危険コマンド確認、書き込み後のパッチスキャン、セッション終了時の要約記録です。Hook は自動で動くため、タイムアウト、失敗、誤検知を必ずテストします。

### 6. 複数の能力をまとめて他の人へ配布する必要があるか？

Plugin を検討します。Plugin は組み合わせと配布の層であり、Skills、Connector、MCP、Hooks、Scheduled task のテンプレートを含められます。Plugin のインストールは、内部の接続、スクリプト、Hook を自動的に信頼することを意味しません。

### 7. タスクを手動で安定実行でき、時間単位で繰り返す必要があるか？

その段階で Scheduled task を作ります。通常のタスクでプロンプト、Skill、権限、出力形式を検証してからスケジュールし、最初の数回の実行を確認し、公開やマージには人のゲートを残します。

## シナリオ対照

| シナリオ | 推奨する組み合わせ |
|---|---|
| テストとコミット規約を統一 | AGENTS.md |
| 毎回のマージ前レビュー | Skill `pr-review` |
| Linear からチケットのコンテキストを取得 | MCP + タスクプロンプト |
| 週次の依存関係レポート | Scheduled task → 下書き issue 作成 |
| ファイル書き込み後にパッチ内の秘密情報をスキャン | Hook または CI。高リスクなら両方 |
| チーム共通のレビュー手順と GitHub ツールを配布 | Plugin（インストール前に権限と Hooks をレビュー） |
| 毎週の依存リスクレポート | 検証済み Skill + Scheduled task + 人的レビュー |
| セキュリティ、テスト、保守性を並行レビュー | 複数の読み取り専用サブ Agent、メイン Agent が集約 |

## コストの次元

| 仕組み | 作成コスト | 保守コスト | セキュリティリスク |
|---|---|---|---|
| プロンプト | 低 | 低 | 低 |
| AGENTS.md | 中 | 中 | 低 |
| Skill | 中 | 中 | 低〜中 |
| MCP | 高 | 高 | 中〜高 |
| Hook | 中 | 中〜高 | 中〜高 |
| Plugin | 低（インストール）/高（自作） | 中〜高 | 中〜高 |
| Scheduled task | 中 | 高 | 高 |

## アンチパターン

- **Skill の肥大化**：数十個の Skill を入れ、description が互いのマッチを奪う
- **MCP 万能ハンマー**：`git` で足りる処理を API 化する
- **受け入れ条件のないスケジュール**：終了条件、実行証拠、人的レビューなしにコードを定期変更する
- **車輪の再発明**：公式 Connector があるのに MCP を自作する
- **ルールの配置ミス**：一度限りの要件を `AGENTS.md` に入れ、以後のすべてのタスクに古い制約を持ち込む
- **Hook の過負荷**：時間のかかる業務フローを毎回のツール呼び出しに入れ、日常のタスクを遅くする

## よくある質問

### 1. 最初から Plugin や MCP を入れるべき？

多くの問題は、まずプロンプト、範囲制御、`AGENTS.md` を適切に使うことで解決します。

### 2. 何回繰り返したら Skill にするべき？

固定の回数はありません。回数は一つのシグナルに過ぎず、手順が安定しているか、成功条件が明確か、失敗コストに対して自動検査の価値があるかが重要です。

### 3. 初めて使うときは、どの方式から始める？

多くの場合、次の 3 つのいずれかです。

- プロンプト
- `AGENTS.md`
- Skill

最初から MCP や無人自動化を導入する必要はないことが多いです。

重要なのは仕組みの見た目の高度さではなく、責務が合っていること、権限が最小であること、結果を検証できることです。

## 最小の実践例

「現在の diff をマージ前にレビューする」場合を例にします。

1. まずプロンプトで 2 回実行し、毎回説明し直す検査項目を記録する。
2. `pnpm test` などの固定コマンドと生成ディレクトリの変更禁止を `AGENTS.md` に書く。
3. レビュー手順、重大度、出力形式を `pr-review` Skill にする。
4. GitHub の PR コメントや CI 状態が必要な場合だけ MCP/Connector を追加する。
5. 固定イベントで自動検査する必要がある場合だけ Hook または Scheduled task を追加する。
6. 複数チームがインストールする段階で、これらの能力を Plugin にまとめる。

層を一つ追加するたびに、追加された権限、検証方法、停止またはロールバック方法を確認します。
