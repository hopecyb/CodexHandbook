Skill を初めて使うとき、よくある疑問は「これをわざわざ Skill にする価値があるか」です。

何でも Skill にすると重くなり、固めるべきものを固めないと同じことを繰り返し手動で説明することになります。ここではいつフローを固定化すべきかの判断を扱います。

# いつ Skill を使うか

## Skill としてパッケージ化に向いている場合

- 同じフローを 3 回目に手動で繰り返している
- 詳細なチェックリストが必要だが、毎回コンテキストを占有したくない
- モデルに `description` から自動判断して有効化してほしい
- チームで共有・バージョン管理されたワークフローが必要

## Skill にする条件

次の 2 つを同時に満たすなら、Skill 化を検討する価値が高い：

- 今後もまたやる
- 次回もできるだけ同じやり方にしたい

多くの Skill は次のようなシーンに落ち着く：

- diff のレビュー
- changelog の生成
- リリース前チェック
- ドキュメント公開フロー

複雑ではないが、再利用に向いているタスクです。

## あまり向いていない場合

- 一度きりで、二度と繰り返さないタスク
- 極めて短く、覚えている固定コマンド（スラッシュコマンドを検討）
- リアルタイムの外部システム状態が必要で変化が極めて速い（MCP を検討）

## よくある誤解

### 1. 重要なタスクなら Skill にすべき

重要であることと、再利用に適していることは別です。  
一度きりの特殊タスクを Skill にすると、保守負担が増えるだけかもしれません。

### 2. Skill は多いほどよい

境界が曖昧な Skill が多すぎると、モデルの誤用やチームの保守が難しくなります。

### 3. 外部システムに繋げられるなら Skill を先にすべき

外部システム接続は多くの場合 MCP の問題であり、Skill が担うのは「フロー」です。外部システムの接続方法は MCP に任せます。

## 試し方

フローを固める価値があるかまだ不明なら、次のように数回試せます：

1. 手動で 2〜3 回完了する
2. 毎回同じチェック順序を繰り返しているか観察する
3. 答えが「はい」なら Skill にまとめる

こうして作った Skill は、空想ではなく実際の繰り返しから生まれるため、より堅実です。

## 他の拡張方式との比較

| 方式 | 向いている用途 |
|---|---|
| Skill | 再利用可能なフロー、段階的開示 |
| MCP | 外部 API とデータソースへの接続 |
| Hooks | 特定イベントポイントでの自動実行 |
| `AGENTS.md` | プロジェクトレベルの常駐ルール |

Skill は「繰り返す・一貫させたい・毎回説明し直したくない」フローの固定化に向いています。

拡張方式の選定は [拡張方式の選び方](/skills/choosing-an-extension-method/)。ワークフローの Skill 化は [フローを Skill にする](/cases/workflows/turn-a-workflow-into-a-skill/)。
