Skill を初めて使うとき、よくある誤解は「入れたら自動で効く」ことです。Skill を使うとは、Codex に事前に書いた作業の型に従わせることです。

Skill は**明示的に指定**して呼び出すことも、適切な場面でモデルが**自動選択**することもあります。この 2 つのトリガー方式を区別すると、トラブルシュートが楽になります。

# Skill を使う

## トリガー方式

1. **明示的**：対応環境で `$skill-name` で呼び出し（名前は frontmatter の `name` と一致）
2. **暗黙的**：モデルが `description` の意味から現在のタスクに適用するか判断

## 2 つのトリガー方式の区別

- **明示的トリガー**：「この Skill を使って」と直接言う
- **暗黙的トリガー**：指定しないが、タスク説明が適用シーンに似ている

Skill を試し始めるときは、**明示的トリガー**を優先することを推奨。次を判断しやすくなります：

- Skill が認識されたか
- 挙動が期待どおりか
- 名前と説明が正しいか

## 例

```text
$pr-review 現在の未コミット変更をレビューしてください
```

または自然言語：「チームの慣習に沿って diff をレビューし、テストを重点的に見てください。」

## よくある誤解

### 1. Skill を書けば必ず自動トリガーされる

自動トリガーは `description` の明確さと、現在のタスクが適用シーンに十分似ているかに依存します。

### 2. 自然言語トリガーと `$name` トリガーは必ず同じ効果

必ずしも同じではありません。

`$name` の方が明確で、検証と強制使用に向いています。自然言語は便利ですが、モデルが Skill を選び間違えたり、使わなかったりすることがあります。

### 3. Skill がトリガーされないのは Skill の問題

次の可能性もあります：

- 名前が違う
- `description` が広すぎる
- タスク説明がトリガー語に当たっていない

トラブルシュートでは「ファイルがあるか」だけでなく「選ばれそうなツールとして書けているか」も見てください。

## よくあるテスト順序

まず一度通すなら、次の順で試せます：

1. まず `$skill-name` で明示呼び出し
2. 出力が期待どおりか確認
3. `description` を修正
4. 最後に自然言語でトリガーできるかテスト

「Skill 自体の問題」と「自動トリガー条件の問題」を分けて見られます。

## description の書き方

- 「いつ使う」「いつ使わない」を明確に
- ユーザーが言いそうなキーワードを含める（review、リリース、changelog）
- 漠然とした「ユーザーのコードを手伝う」は避ける
- 核心となるトリガーシーンを**先頭に**（Skill リストに文字数予算あり）

## description が明確かの判断基準

よく使われる基準：  
この `description` を読めば「いつ使い、いつ使わないか」がわかる。

読んでも「何でもできそう」と感じるなら、おそらく広すぎます。
