最初はすべてを `SKILL.md` に書きたくなります。単純なフローではそれで足りますが、**安定・反復・検証可能**に実行すべきステップがあるなら、文章よりスクリプトが信頼できます。

固定動作はスクリプトに、判断と協業フローは Skill に残します。

# scripts/ とテスト

ステップを決定的に実行する必要があるとき（テスト実行、diff 生成、形式検証）、`scripts/` にスクリプトを置き、`SKILL.md` でいつ呼ぶかを書きます。

## 例

```text
my-skill/
├── SKILL.md
└── scripts/
    └── run-checks.sh
```

## いつ scripts/ を検討するか

次のいずれかに当てはまればスクリプトが有力です。

- 毎回まったく同じ実行が必要
- 終了コード自体に意味がある
- 自然言語だと冗長
- 後で CI などでも再利用したい

「チェック実行」「diff 生成」「形式検証」「固定レポート出力」などに向きます。

## テストの提案

- 練習リポジトリで手動実行し、終了コードと出力を確認
- Skill 経由で E2E をトリガーし、期待どおり呼ばれるか確認
- チーム：CI や pre-commit でまだ動くか確認

## よくある誤解

### 1. スクリプトは Skill を複雑にするから避ける

不安定なステップを固定できれば、全体はむしろ単純になることが多いです。

### 2. ローカルで動けば Skill も問題ない

次も確認：

- Skill が正しくトリガーするか
- 承認ポリシーがブロックしないか
- チーム環境や CI でも動くか

### 3. 「Skill のテスト」＝スクリプトのテスト

不十分です。

スクリプトは1動作、Skill はいつ・どう呼ぶか・出力が期待どおりかをテストします。

## 推奨検証順序

1. スクリプト単体実行
2. 終了コードと出力の明確さ
3. Skill 経由でフルフロー1回
4. 実環境に近い場所で再テスト

「スクリプト不良」と「Skill 統合不良」を分けられます。

安定反復が必要な動作は文章だけに頼らない。スクリプトを先に通し、その後 Skill 呼び出しを確認。

スクリプトは現在の承認ポリシーを継承。[コマンドルール](/guide/customization/rules/command-rules/) と [Skill セキュリティ](/skills/security/) を参照。
