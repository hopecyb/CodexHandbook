タスクの出し方は分かるが Skill をまだ作っていない人向けに、最初の Skill の基本手順を説明します。

15〜30 分で**リポジトリで再利用できる** Skill を作る方が、大量の理論を先に読むより直接的です。境界がはっきりした小さな Skill が良い起点です。

## 向いている人

[最初のタスク](/cases/first-task/) を完了し、テスト用リポジトリで試す意思がある人。

## なぜ `pr-review` から始めるか

- 入力が比較的明確
- 「直接コード変更」よりリスクが低い
- 使えるか判断しやすい
- Skill のトリガーと境界の書き方の練習になる

ワークフローを再利用可能な形に書く練習に向いています。

## 目標成果

`.agents/skills/pr-review/` に、現在の変更に対して構造化レビューを出す Skill があること。

## 最低目標

最初の Skill で次の3点を満たす：

1. 認識される
2. 明確なフローを安定実行する
3. 危険な動作をついでにしない

## 手順

### 1. ディレクトリ作成

```bash
mkdir -p .agents/skills/pr-review
```

### 2. SKILL.md を書く

```md
---
name: pr-review
description: git diff をレビューし、ブロック事項・テスト不足・スタイル提案を列挙。ユーザーが review、レビュー、マージ前チェックを言ったときに使う。新機能実装には使わない。
---

# PR レビュー

## 入力
- デフォルト比較ブランチ：main（なければデフォルトブランチ）

## フロー
1. 変更ファイルと変更種別（機能／修正／リファクタ／ドキュメント）を列挙
2. 各ロジック変更について：テスト不足、API 破壊の有無
3. 鍵、デバッグログ、過大な無関係 diff の有無を確認
4. 出力：
   - 🔴 ブロック：必須修正
   - 🟡 提案：修正推奨
   - 🟢 合格：AGENTS.md 要件を満たす

## 禁止
- git push しない
- 未議論の公開 API を変更しない
```

### 3. ローカルで試す

Codex でリポジトリを開き：

```text
$pr-review 未コミットの変更をレビューして
```

または自然言語：「チームの慣習で diff をレビューして。テストを重点的に。」

### 4. 明示を先に、暗黙は後

自動トリガーをいきなり試さない。順序：

1. `$pr-review` で明示呼び出し
2. フローと出力を確認
3. 自然言語トリガーを試す

Skill 内容の問題と `description` のトリガー条件の問題を分けやすくなります。

### 5. description を反復

モデルが**自動選択しない**なら、トリガー語を足す・絞る。**誤用が多い**なら「いつ使わない」を追加。

### 6. チーム共有にコミット

```bash
git add .agents/skills/pr-review
git commit -m "docs: add pr-review skill for Codex"
```

チーム README または `AGENTS.md` に：「マージ前に `$pr-review` が使える」と一行。

## よくある誤解

### 1. 最初の Skill はできるだけ多機能に

逆のことが多い。小さく焦点を絞った方が価値を判断しやすい。

### 2. Skill の要点は「賢く見せる」こと

**境界が明確**なことが重要。何をする／しないかが「すごそう」より大事。

### 3. 動けば成功

有用な Skill は少なくとも：

- いつ使うか他人が分かる
- 出力に固定構造がある
- 危険操作をついでにしない

## 受け入れチェックリスト

- [ ] `$pr-review` が動き、危険な git 操作をしない
- [ ] 出力に段階付き結論があり、漠然とした感想だけではない
- [ ] `description` が一文でトリガーシーンを説明
- [ ] [権限と承認](/guide/permissions-and-sandbox/) を確認（本例はスクリプトなし）

「小さく安定した」Skill から始めると、明確なワークフローを安定再利用しやすいです。
