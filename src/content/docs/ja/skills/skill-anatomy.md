Skill ディレクトリを初めて見ると、フォルダは見覚えがあっても、なぜこう配置するか分かりにくいことがあります。

本ページでは「主フロー・長文資料・テンプレート・スクリプト」を分け、1 ファイルに詰め込まない方法を説明します。

読みやすく、直しやすく、再利用しやすくなり、肥大化時の混乱も減ります。

# Skill の構造

## ディレクトリ構成

```text
my-skill/
├── SKILL.md          # 必須
├── scripts/          # 任意：決定的なステップ
├── references/       # 任意：長い参考ドキュメント
└── templates/        # 任意：出力テンプレート
```

## 各層の役割

- `SKILL.md`：主マニュアル——何か、いつ使うか、どの手順か
- `references/`：長い参考棚。背景を主ファイルに全部詰めない
- `templates/`：出力の骨組み。毎回即興しない
- `scripts/`：決定的なステップはスクリプトに任せ、自然言語だけにしない

最初は `SKILL.md` だけで十分なことも多いです。  
複雑になったら `references/`、`templates/`、`scripts/` に分割します。

## SKILL.md の最小例

```md
---
name: pr-review
description: 現在ブランチと main の diff をレビューし、リスクとテスト不足を示す。ユーザーが review、PR レビュー、マージ前チェックを求めたときに使う。
---

## 手順
1. main との diff を取得
2. ファイルごとに分類：ロジックエラー、セキュリティ、パフォーマンス、テスト
3. 段階付きリストを出力：ブロック / 提案 / nit
4. 自動 push やマージはしない
```

## よくある誤解

### 1. 初日から全ディレクトリを作る必要がある

多くの良い Skill は `SKILL.md` だけから始め、再利用が増えると他を追加します。

### 2. references/ は「もっと書くため」

要点は、常に主フローに載せない長文を別に置くことです。

### 3. できれば scripts/ は避ける

安定・決定的・反復可能なステップは、繰り返しの自然言語よりスクリプトの方が信頼しやすいことが多いです。

## ディレクトリの役割

| ディレクトリ | 用途 |
|---|---|
| `SKILL.md` | 主フロー、トリガー、禁止事項 |
| `references/` | 長文、規約、API メモ |
| `templates/` | 出力形式、レポート骨組み |
| `scripts/` | 決定的なコマンドとチェック |

## いつディレクトリを分けるか

次の順で自問します。

1. 主フローが一度に読めないほど長いか
2. 毎回不要な大きな資料があるか
3. 繰り返す固定出力形式があるか
4. スクリプト化に十分安定したステップがあるか

1〜2 個「はい」なら分割を検討。

まず `SKILL.md` で回し、複雑になったら references・templates・scripts を分けます。
