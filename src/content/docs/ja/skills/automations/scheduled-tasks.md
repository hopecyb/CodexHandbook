Scheduled task で本当に難しいのは「何時に実行するか」ではありません。無人実行のたびに、安定した入力、狭い権限、レビュー可能な出力、停止条件をそろえることです。

![手動検証から定期実行、人的レビュー、調整までの安全な循環](/diagrams/scheduled-task-safety-loop-ja.svg)

## 対象読者

- 日次・週次レポート、ドキュメント確認、PR のフォローを定期実行したい個人ユーザー
- ローカルプロジェクトや隔離 worktree で保守タスクを定期実行する開発者
- 権限、失敗処理、チーム共有 Skill を評価するメンテナー

## 対応範囲

| 表面 | できること | 主な制限 |
|---|---|---|
| ChatGPT Web | 実行の作成、管理、確認。アップロードファイル、接続ツール、Skills、Plugins を利用 | ローカルフォルダーには直接アクセスできない |
| ChatGPT デスクトップ App | 作成、管理。ローカルプロジェクトまたは Git worktree を選択可能 | ローカルファイルのタスクには、マシンの起動、App の実行、プロジェクトの存在が必要 |
| Codex CLI | プロンプト、Skill、スクリプトを準備し、手動でテスト | Scheduled の管理画面はない |
| IDE 拡張 | ワークスペースでコマンドと変更を検証 | Scheduled の管理画面はない |

## 1. 独立タスクとチャット内タスクを選ぶ

### 独立 Scheduled task

毎回、保存したプロンプトから開始し、独立した実行として Scheduled に入ります。日報、週報、プロジェクトのヘルスチェックなど、互いに独立した処理に向きます。1 つのタスクで複数プロジェクトを対象にすることもできます。

### チャット内 Scheduled task

予定に従って同じチャットに戻り、既存のコンテキストを引き継ぎます。長時間タスクのポーリング、PR の状態確認、継続的な調査、前回の議論を残す必要がある作業に向きます。

選択基準は単純です。毎回「最初から始める」なら独立タスク、同じ問題のコンテキストを続けるならチャット内タスクを選びます。

## 2. 実行材料を選ぶ

### Web で実行する

耐久性のある指示をタスクプロンプトまたは Skill に書き、必要な資料をアップロードファイル、Project、接続サービスに置きます。「デスクトップの latest.csv を読んで」のように書かないでください。Web はローカルパスに直接アクセスできません。

### デスクトップ App でローカルプロジェクトを使う

Git リポジトリでは次を選べます。

- **ローカルプロジェクト**：メイン checkout で直接作業するため、編集中のファイルに触れる可能性があります。
- **専用 worktree**：バックグラウンドの変更を未完了の作業から分離でき、ファイルを変更するタスクに向きます。

Git でないプロジェクトはプロジェクトディレクトリで直接実行します。頻繁な worktree タスクは作業ツリーを蓄積するため、不要な実行をアーカイブし、意図せず大量の worktree を残さないようにします。

## 3. 先に手動で検証する

通常のチャットで、同じプロンプト、モデル、推論強度、ツールを使って先に実行します。少なくとも次を確認してください。

- その場で説明を足さなくても入力が明確である
- 「変更なし」の場合は静かに終了する
- 出力を人がすばやくレビューできる
- コマンド、Skill、接続ツールが動作する
- 権限や材料が不足したとき、推測せず停止して説明する

最初の数回の定期実行を確認してから、プロンプトや頻度を調整します。

## 4. そのまま書き換えられるタスクプロンプト

```text
独立した Scheduled task を作成してください。

名前：週次ドキュメントのデッドリンク確認
時刻：毎週月曜 09:00、現在のタイムゾーンを使用
実行場所：現在の Git プロジェクト専用 worktree

毎回実行すること：
1. docs/、src/content/docs/、examples/、public/diagrams/ だけを読む。
2. pnpm check:links を実行する。
3. 検査に成功したら、検査したファイル数とリンク数だけを報告し、変更しない。
4. 失敗したら「元ファイル、失効した対象、修正案」を列挙し、自動修正しない。
5. ネットワーク接続、依存関係のインストール、commit、push、PR 作成をしない。
6. コマンドが存在しない、依存関係が不足している、または結果が不確かな場合は停止し、必要な手動対応を説明する。

完了条件：レビュー可能なレポートを出力して終了し、同じ処理を繰り返さない。
```

ここでは時刻、プロジェクト、読み取り範囲、コマンド、成功・失敗時の分岐、禁止事項、終了条件をすべて指定しています。スケジューラーは再実行を担当するだけで、タスクの定義を代替しません。

## 5. 権限と人的レビュー

Scheduled task は無人で実行され、デフォルトのサンドボックス設定を使います。

| サンドボックスモード | 典型的な結果 |
|---|---|
| read-only | ファイル変更、ネットワーク接続、本機 App の操作は失敗する |
| workspace-write | ワークスペース内は書き込める。ワークスペース外、ネットワーク、App 操作はデフォルトで失敗する |

タスクを完了できる最小の権限から始めます。ネットワークや広いファイルアクセスが必要なら、明示的な allowlist を使い、一度の失敗を消すために全面的な高権限へ変更しないでください。

人的レビューを残すべき対象は次のとおりです。

- 外部へのメッセージ送信や公開
- 本番状態の変更
- PR のマージや main への push
- 大量削除、移行、権限変更
- diff が想定を超えた場合やテスト失敗時

## 6. 「変更なし」、失敗、停止を設計する

耐久性のあるタスクには次の 3 つの経路が必要です。

1. **発見あり**：証拠、重要度、次の手順を出力する。
2. **変更なし**：検査範囲だけを簡潔に報告し、疑似的な問題を作らない。
3. **完了不能**：不足している材料や権限を説明し、人の対応を待って停止する。

チャット内のポーリングには、「PR がマージまたはクローズされた、同じエラーが 3 回続いた、人的承認が必要になったら停止する」のような終了条件も書きます。

## Scheduled task はイベント駆動 CI ではない

`push`、PR 作成、公開完了などのリポジトリイベント直後に実行する必要がある場合は、GitHub Actions、CI、webhook、Codex SDK などのイベント入口を使います。「毎分ポーリング」を正確なイベントトリガーとして扱わないでください。

## 受け入れチェックリスト

- [ ] プロンプトを通常のチャットで最後まで実行した
- [ ] 独立タスクまたはチャット内タスクを選択した
- [ ] Web の資料またはローカルプロジェクトが実行時に利用できる
- [ ] デフォルトサンドボックスで足り、追加権限には明確な理由がある
- [ ] 発見あり、変更なし、失敗、停止の条件を書いた
- [ ] 最初の 3 回を人が確認した
- [ ] 高頻度 worktree のアーカイブと整理方針がある
- [ ] 重要な書き込みには人の確認を残した
