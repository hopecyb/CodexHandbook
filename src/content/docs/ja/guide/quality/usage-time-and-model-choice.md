まず何を記録するのかを明確にします。アカウントの残り利用枠、API 呼び出しの費用、待ち時間、人が確認や手直しに費やした時間は、単位が異なり、互いの代わりにはなりません。

[記録用テンプレートをダウンロード](/downloads/usage-log/usage-log-1.0.0.zip) · [記入方法](/downloads/usage-log/README.md)

## 四つの記録を分ける

| 指標 | 記録の根拠 | よくある誤解 |
|---|---|---|
| サブスクリプションの利用枠 | 現在の画面に表示された期間、残り割合、リセット時刻 | 残り割合をそのままドルや固定回数のタスクに換算する |
| API 費用 | 呼び出し時の実際の使用量、モデル、適用料金と請求内容 | サブスクリプション料金を API 単価として使う、または見積もりを実請求とみなす |
| 待ち時間 | 同じタスクの開始、終了、待機列、再試行 | 最後の成功分だけを記録し、失敗にかかった時間を除く |
| 人の作業 | 確認と手直しを別々に計測 | モデルを待った時間のすべてを人件費の削減とみなす |

[公式の料金説明](https://learn.chatgpt.com/docs/pricing)によると、タスクの使用量はモデル、コンテキスト、推論、ツール、キャッシュに左右されます。メッセージ数の目安は固定の上限ではありません。現在の利用枠は使用量画面で確認し、CLI セッションでは `/status` を使えます。API キーによる使用には API 料金が適用されます。

利用枠のスナップショットには、ほかのタスクの消費や期間のリセットが混ざることがあります。前後で 5% 減っただけで「このタスクは毎回 5% 消費する」と断定したり、あと何回実行できると約束したりしないでください。

## API 費用の見積もり前に課金の単位を確認する

モデル、入力・キャッシュ・出力の区分、サービス条件に応じた料金を確認し、実際の使用量で計算します。ほかの課金項目があれば別に加えます。この手引きでは独自の固定料金表を維持しません。[API 料金](https://developers.openai.com/api/docs/pricing)を参照してください。

推論 token は出力 token として課金されます。使用量の欄に推論分がすでに含まれていないか確認し、二重計上を避けてください。選択できる推論レベルも、対象モデルが対応しているか[推論モデルの説明](https://developers.openai.com/api/docs/guides/reasoning)で確認します。

教材用の計算例：入力 10,000 token、出力 2,000 token、キャッシュやその他の費用なしとします。入力 100 万 token 当たり 2 ドル、出力 100 万 token 当たり 10 ドルという**架空**の料金なら、見積もりは 0.04 ドルです。これは単位換算を示すだけで、実際のモデル価格や請求額ではありません。

## 同じタスク群で設定を比較する

明確な受け入れ条件のあるタスクを選び、現在使える設定で基準を作ります。入力、ツール権限、プロジェクト指示、評価方法をそろえ、モデルか推論設定の主要な要素を一度に一つだけ変えます。

正確さ、権限の境界、証拠、手直しを項目ごとに比較し、応答速度だけで判断しないでください。軽い設定で安定して条件を満たせない場合は、資料不足、範囲の曖昧さ、推論不足のどれが原因かを調べてから設定を上げます。高い設定でも出典の確認やテストは省けません。

これは本手引きが勧める評価方法であり、特定のモデルが必ず勝つという実測結果ではありません。[三組のプロンプト比較](/ja/prompts/comparison-lab/)と[ワークフロー評価サンプル](/ja/guide/quality/workflow-evaluation/)を使って観察を記録できます。

## サンプルの条件を記録する

[実行記録表](/downloads/usage-log/runs.csv)には、入力ハッシュ、実際のモデル名、クライアント、推論設定、課金経路、時間、再試行、結果、費用の証拠を記入します。[利用枠スナップショット表](/downloads/usage-log/allowance-snapshots.csv)には、期間とリセット時刻を別に記入します。

失敗と中断も残します。人による確認と手直しは別々に記録します。不明な欄は空欄にして理由を書き、消費がなかったかのように 0 を入れないでください。アカウントは別名を使い、公開資料に鍵、アカウント情報、私的なログを含めないでください。

現在のダウンロード表に実測行はありません。比較可能な人の作業基準がなければ時間削減率を計算せず、反復サンプルがなければ安定した速度優位を主張しないでください。モデルの待ち時間が短くても、手直しが増えれば採用する価値がない場合があります。

## 制限に近づいたとき

現在の成果、未解決事項、再開方法を保存します。タスクが再試行を繰り返したり、無関係の資料を読んだりしていないか確認します。目標に合わせて不要な範囲を絞りつつ、品質と安全の受け入れ条件は残します。利用枠が尽きる前に終えるためだけに重要な確認を省かないでください。

続ける必要がある場合は、現在の利用枠と課金経路を確認してから選びます。この記事は API 課金への自動切り替え、クレジットの購入、アカウント設定の変更を行いません。チームでは[2 週間の試行パス](/ja/guide/learning-paths/team/)を使い、選択理由と元に戻す条件を記録できます。
