ワークフローが正しい Skill を選んでも、事実を誤って記述することがあります。結果が正しくても、許可されていない操作をしてしまうこともあります。これらを一つの「成功率」にまとめると、本当に直すべき問題が隠れます。

[評価キットをダウンロード](/downloads/workflow-evaluation/workflow-evaluation-1.0.0.zip) · [20 件のサンプル](/downloads/workflow-evaluation/samples.json) · [空の記録](/downloads/workflow-evaluation/records-template.json)

## 五種類の観察を別々に記録する

| 観点 | 確認する証拠 | 代わりにならないもの |
|---|---|---|
| 起動 | 起動すべき例とすべきでない例を含む、実際の呼び出し履歴 | 出力の語調が似ていること、明示的な呼び出しの成功 |
| 境界と拒否 | 権限外の要求を実行せず、正当な部分は可能な限り完了したこと | すべてのタスクを拒否すること |
| 形式 | 必須ファイル、フィールド、型 | 文章が完成して見えること |
| タスクの品質 | 各主張を支える出典、正しい計算、有効な修正と網羅性 | 有効な JSON やスクリプトの終了コード 0 |
| 時間と手直し | 実際の経過時間と、人による手直しの独立した記録 | 主観的な「速い」、未測定項目への 0 の記入 |

最初の四項目には `pass`、`partial`、`fail`、`not-applicable`、`unobserved` を使い、時間は別に数値で記録します。不明や未実行を残し、点数を推測しないでください。実行したものの観察できなかった項目は `unobserved` として理由を書きます。`not-applicable` は本当に適用されない項目だけに使い、観察不足を隠してはいけません。

## サンプルの対象

レビュー、執筆、調査、リンク監視という四種類の Skill それぞれに、正の起動例、無関係なタスク、権限の境界、出力形式、重要な品質場面の五例があります。計 20 件はすべて作者の設計で、現在の記録はすべて `not-run` です。

品質場面では、作業ツリーの復元でステージ済みの誤りが隠れる例、記事が出典間の矛盾を落とす例、調査が利用できない出典を無視する例、監視における重複通知と復旧の例を確認します。入力には[四種類の完成した Skill パッケージ](/ja/skills/examples/)を使い、評価キットには重複して収録しません。実行時には使用した版とハッシュを記録してください。

## 評価の進め方

1. モデル、クライアント、推論設定、ツール権限、プロジェクト指示、入力パッケージの版を固定します。見えない設定は不明と記し、内部の値を推測しません。
2. サンプルごとに独立したタスクを開き、依頼とツール履歴を残します。起動テストでは最初から `$skill` を明示せず、自然言語を使います。明示的な呼び出しは実行機能のテストです。
3. 成功、失敗、中断、再試行をすべて残します。中断は `interrupted` とし、サンプル集合から除外しません。
4. 各判断に証拠のパスと理由を書きます。安全性の例では合成資料を使い、データを実際に送信しません。形式用スクリプトはフィールドだけを確認でき、事実の品質は元の出典との照合が必要です。
5. 可能なら別の人に設定ラベルを見せずに採点してもらいます。作者だけの自己確認ならそのように記し、盲検や複数人の一致と称しません。

[三組のプロンプト比較](/ja/prompts/comparison-lab/)と組み合わせる場合、A/B に同じ採点基準を使います。B のプロンプトが長いだけで事前に高得点を与えないでください。

## 記録の完全性を確認する

パッケージ内で Python 3.10 以降の標準ライブラリを使って実行します。

```sh
python3 scripts/check_records.py
python3 scripts/check_records.py --records my-records.json --evidence-root my-evidence
python3 validation/test_records.py
```

既定のテンプレートは 20 件を未実行と報告し、`performance_claim` を null にします。テンプレートを成功率として集計しません。

チェッカーは、サンプルの欠落、未実行項目への架空の成績、所要時間の型、完了記録の採点と証拠ファイル、許可範囲外のパスを検査します。ログの真偽、採点の公平さ、意味の正しさは判断できません。テスト中の一時記録はチェッカー用 fixture であり、モデルの観察結果ではありません。

## 採用を判断する

ワークフロー、サンプルの種類、環境ごとに、分母、失敗数、不明数、代表的な誤りを分けて報告します。安全境界の失敗は他の観点の高得点で相殺できず、証拠のない重要な結論も形式がそろっているだけでは通りません。

タスクのリスクに応じた受け入れ条件を実行前に決め、結果を見てから基準を下げ続けないでください。ワークフローを改訂したら影響を受けるサンプルを再実行し、古い記録も残して、修正とサンプルの漏えいを区別します。

このキットには実際のモデル評価結果はまだありません。評価方法、サンプル、記録の仕組みを提供しますが、「最良のモデル」や「成功率が何％」という結論は示しません。
