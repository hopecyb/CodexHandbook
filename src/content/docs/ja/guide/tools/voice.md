一部の Codex クライアントは**音声**をサポートしています。タスクを話したり、返答の要約を聞いたりできます。手が塞がっているときや、考えを素早く口述したいときに向いています。**秘密鍵を読み上げる用途には向かず**、書面による検証記録の代替にもなりません。

音声は方向性の表現、背景の補足、素早いフォローアップに向きます。精密で検索可能、再確認可能な詳細が必要なときは、文字に戻る必要があります。

## 本ページの内容

- 音声が向いているタスクの形
- 文字プロンプトとの組み合わせ方
- プライバシーと精度への注意

## 適用シナリオ

| 向いている | 向いていない |
|---|---|
| 高レベルな目標の口述、ブレインストーミング | 変数名レベルまで精密なコード指示 |
| モバイルでの短いフォローアップ | API key、パスワードの読み上げ |
| アクセシビリティのニーズ | 検索可能で diff 可能な仕様ドキュメント |

口述後は、Codex に**理解の復唱**または文字版の計画生成をさせ、確認してから進めましょう。[計画の依頼](/prompts/ask-for-a-plan/) を参照。

## 音声が向いていること

音声の主な利点は次のとおりです。

- 速い
- 手を使わない
- 頭の中の考えを先に吐き出すのに向いている

よくある問題は次のとおりです。

- 抜けやすい
- 聞き間違えやすい
- 精密なパス、変数名、コマンドライン引数の載せ方には向かない

一般的なやり方は、まず口述で方向性を伝え、その後文字で確認を補うことです。

## 使用上の提案

1. 静かな環境で短い文に分け、「目標 / 制約 / 完了基準」を段階的に話す
2. ファイルパスやブランチ名は**タイピングに切り替える**か、Agent に綴りを復唱させる
3. 機密プロジェクトでは音声のクラウド処理をオフにする（製品がローカル / 無効化オプションを提供している場合）
4. 重要な決定は issue や PR に文字で残す

## よくある誤解

### 1. 音声はタイピングを完全に代替できる？

できません。  
次の内容は、やはりタイピングがよいです。

- ファイルパス
- ブランチ名
- コマンド
- 引数
- 完了基準

### 2. 詳しく話せば話すほど、必ずしもミスが減るわけではない

構造のない長い口述は、かえって要点が散らばりやすくなります。

### 3. 音声返答は結果レビューの代替になる？

なりません。  
音声要約は大意を素早く把握するのに役立ちますが、変更内容、ファイル、diff、テスト結果の確認は、文字と成果物そのものに戻る必要があります。

## よく使う話し方の順序

音声でタスクを依頼するときは、次の順序が使いやすいです。

1. 何をしたいか
2. 何をしてはいけないか
3. 完了後にどう検証するか

話し終えたら、文字版に整理して確認してもらいましょう。

## プライバシー

- 音声はクラウドで文字起こしされる場合がある。顧客 PII や認証情報は読み上げない
- 公共の場では周囲の聞き取りに注意する
- チームポリシーで、録音系機能による機密コード名の処理が禁止されている場合がある

## マルチモーダルとの関係

- **画像入力**：デザイン稿、スクリーンショット → [画像プロンプト](/prompts/prompting-with-images/)
- **音声入力**：本ページ
- **出力**：主にコード、ファイル、文字 diff。音声要約はレビューの代替にならない

## よくあるミス

- 構造のない長文口述で、Agent が制約を見落とす
- 音声だけで大量のコード変更を受け入れ、diff を見ない
- 音声でマスキングされていない本番障害の詳細を話す

音声は開始とフォローアップに向きます。精密な指示、機密情報の扱い、最終検証の代替には向きません。
