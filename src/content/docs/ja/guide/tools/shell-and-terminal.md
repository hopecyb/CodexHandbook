ターミナルは Codex に動作を実行させる最も直接的な方法のひとつです。効率は高い一方で、リスクを理解する必要もあります。

## なぜ強力であり、同時に危険なのか

ファイルツールは主にテキストを扱います。ターミナルは OS と実行環境を直接操作します。

ターミナルに入ると、よくある操作は読み取りだけでなく、次のようなものになり得ます。

- インストール
- ビルド
- テスト
- 削除
- コミット
- プッシュ

使う前に、どこを変更するのかを把握しておきましょう。

ターミナルは強力で危険でもあります。原則は次のとおりです。

- 承認前にコマンドを読み解く
- `rm -rf`、強制プッシュ、ssh 設定の変更などは、完全に理解していて必要な場合を除き禁止する
- 検証コマンドを完了基準に書き込む

製品の入口：[統合ターミナル](/ja/guide/desktop-app/integrated-terminal/)

## なぜターミナルのリスクが高いのか

「提案する」だけでなく、実際に動作を実行するからです。

たとえば次のようなことが起こり得ます。

- 依存関係のインストール
- ファイルの削除
- テストの実行
- 設定の書き換え
- コードのプッシュ

コマンドが読めないときは、先に内容を確認してから許可するかどうかを決めましょう。

## ターミナルが向いている場面

次のような作業にはターミナルが向いています。

- テストの実行
- ビルドの実行
- ファイル状態の確認
- プロジェクト既存スクリプトの実行

一方、次のような目的だけなら、ターミナルが第一選択とは限りません。

- ページの見た目を確認したい
- 最新の公開資料を調べたい
- 既知のテキストを 1〜2 か所修正したい

## よくある誤解

### 1. コマンドがわからなくても、ターミナルは完全に使えないわけではない

最初から多くのコマンドを書ける必要はありませんが、少なくとも次は読み取れることが大切です。

- このコマンドがおおよそ何をしようとしているか
- ファイルやシステムを変更するかどうか
- 現在のタスクに本当に関係があるか

### 2. テストコマンドなら必ず安全？

そうとも限りません。  
多くのテストコマンドはリスクが低いですが、それでも次を確認してください。

- 大量のファイルを書き込むか
- ネットワークに接続するか
- よくわからないスクリプトを呼び出すか

### 3. 読めないときはどうする？

次のように直接たずねられます。

```text
このコマンドは何をしますか？何を変更しますか？実行しなければどんな影響がありますか？
```

## そのまま使える書き方

次の一文を足せます。

```text
コマンドを実行する前に、用途、ファイル書き込みの有無、ネットワーク接続の有無、失敗時の復旧方法を説明すること。
```

実行前に、そのコマンドがどこを変更するのかを確認しましょう。
