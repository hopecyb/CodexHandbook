CLI では Agent が **ファイルの読み書き、shell 実行、場合によってはネットワーク接続** ができます。承認とサンドボックスは、あなたと自動化のあいだの安全弁です。設定が不適切だと、対話では承認が多すぎるか、CI の無人実行でリスクが制御不能になります。

## 本ページの内容

- 承認ダイアログが何を聞いているか、どう選ぶか
- サンドボックス段階がファイルとネットワークに与える影響
- チームが CLI と `AGENTS.md` で方針を揃える方法

## 承認とサンドボックスがそれぞれ管理すること

覚え方は次のとおりです。

- **承認**：「この一歩を続けるか？」と聞く
- **サンドボックス**：「続けても、どこまで触れるか？」を制限する

両方が組み合わさり、CLI が保守的か、境界が広すぎるかを左右します。

概念の基礎：[権限と承認](/ja/guide/foundations/permissions-and-approvals/) · [サンドボックスとネットワーク](/ja/guide/foundations/sandbox-and-network/)

## 承認が起きるタイミング

典型的なトリガー（具体は製品を正とする）：

| 操作種別 | リスク | デフォルト傾向 |
|---|---|---|
| プロジェクト内ファイル書き込み | 中 | しばしば確認が必要 |
| プロジェクト外パス書き込み | 高 | 拒否または厳格確認 |
| shell 実行 | 高 | コマンド内容を確認 |
| ネットワーク / curl | 高 | 宛先とデータを確認 |
| MCP ツール呼び出し | サーバー次第 | ツール単位 |

対話時は **一度許可 / セッション許可 / 拒否** などの選択肢があります（名称はバージョンで異なる）。**内容がわからないコマンドに「常に許可」は押さないでください。**

## サンドボックス段階（概念）

| 段階の意図 | 向く場面 |
|---|---|
| 厳格 / 読み取り専用 | 信頼できないコードのレビュー、CI の読み取り専用レビュー |
| 標準 | 日常の開発リポジトリ |
| 緩和 | 個人の信頼環境。会社方針に合致すること |

サンドボックスが制限しうるもの：

- 書き込み可能ディレクトリの範囲
- `$HOME` 内の他プロジェクトへのアクセス可否
- 子プロセスとネットワーク能力

設定入口：[CLI 設定](/ja/guide/cli/configuration/) · マトリクス：[権限マトリクス](/ja/guide/reference/permission-matrix/)

## 対話 vs 非対話

| モード | 承認の特徴 |
|---|---|
| 対話 `codex` | 人がその場にいる。1 件ずつ判断 |
| 非対話 `exec` | 人がいない。事前にサンドボックスを絞り、プロンプトを固定 |

CI 必読：[非対話モード](/ja/guide/cli/non-interactive-mode/) · [人間承認パターン](/ja/cases/workflows/human-approval-patterns/)

推奨 CI 原則：

- 読み取り専用または書き込みパス限定
- 任意の `curl` でリポジトリ内容をアップロードしない
- 失敗時は非ゼロ終了。ログを保持

## allow/deny ルールとの関係

プロジェクトは [許可と拒否パターン](/ja/guide/customization/rules/allow-and-deny-patterns/) で「想定されるコマンド」を宣言できます。**ルールは実際の製品挙動と一致している必要があります**。そうでなければ、Agent は依然としてブロックされるか、逆に広すぎることになります。

## よくあるミス

- ローカルで shell を「すべて自動承認」したまま顧客リポジトリを扱う
- `sudo`、DB 削除、`~/.ssh` 変更などを誤って承認
- CI に開発機と同じ緩和設定を使う
- サンドボックスがコードレビューの代わりだと思う——誤操作は防げても、悪意あるプロンプト注入は防げない

## よくある誤解

### ダイアログが多い = 設定がおかしいとは限らない

CLI を学び始めたばかりなら、承認が多い方が安全なことも多く、各ステップを理解するきっかけになります。

本当に警戒すべきは、内容を見ずに承認し始めることであり、「聞かれすぎる」ことではありません。

### 一度緩めたからといって、以後も安全とは限らない

初回の手間を避けるためにルールを広げ、別リポジトリや別タスクでも同じ設定を使い続ける人がいます。

安全境界はタスクのリスクに合わせるべきで、前回が楽だったからといって今回も問題ないとは限りません。
