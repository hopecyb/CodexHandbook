**Rules（ルール）**は設定またはプロジェクトファイルで、どの shell コマンド、パス、ツール呼び出しを**許可または拒否**するかを宣言します。毎回手動承認を減らしつつ、危険操作の自動化を防ぎます。

## 内容

- Allow / Deny ルールの動作
- サンドボックス、承認ダイアログ、`AGENTS.md` との関係
- チームルール例

## ルールがすること

「ルール」が抽象的なら、先にこう考えてください：Codex に何ができ、何ができないかを事前に約束し、毎回の判断と手動承認に頼らない。

価値は二つ：

- 毎日起きる低リスク操作の繰り返し確認を減らす
- 自動化すべきでない高リスク操作を先に止める

## ルールの種類（概念）

| 種類 | 例 |
|---|---|
| コマンド allowlist | `npm test`、`git status` を許可 |
| コマンド denylist | `rm -rf`、`curl \| bash` を禁止 |
| パス | `../` への書き込み禁止、`~/.ssh` 読み取り禁止 |
| ネットワーク | 外向き通信禁止または registry ドメインのみ |

[権限マトリクス](/guide/reference/permission-matrix/) と対照：ルールは**設定可能な** enforcement。マトリクスは**典型的なデフォルト**を述べる。

## 推奨層分け

```text
組織マネージド方針（上書き不可）
    ↓
プロジェクト rules + AGENTS.md（Git レビュー）
    ↓
個人 allowlist 補足（本機のみ）
    ↓
単発タスク prompt 制約
```

## よくある誤解

### ルールはダイアログを減らすためだけではない

allowlist の目的を「割り込み削減」とだけ考えがちです。低リスクを通し、高リスクを止ぐことが本質です。

### ルール＝サンドボックスではない

サンドボックスは「どこまで触れるか」を制限。ルールは「原則として何をしないか」を約束。両方使い、一方で代替しない。

### チームの底線を個人本機だけに置かない

自分の本機だけが「push 禁止」「`.env` 禁止」を知っていると、他人は踏み込めます。チーム底線は review 可能な場所に。

## チーム例（示意。コピー即用ではない）

**許可：**

- パッケージマネージャで**プロジェクト内**依存をインストール
- 文書のテストスクリプトを実行

**拒否：**

- `git push`、`git reset --hard`
- `.env*` の読み書き（明示タスク以外）
- リポジトリ内容を含む公網 POST

ルールはチームが review できるファイルに。口頭だけにしない。

## よくあるミス

- allowlist が広すぎ（`bash` 許可は実質すべて許可）
- deny だけで allow しない——依然大量承認
- ルールと `AGENTS.md` が矛盾

## 始め方の提案

最初から完全策略は不要。次の二步で十分：

1. 毎日よく走らせる低リスクコマンドを3〜5個明示
2. 絶対に自動実行したくない高リスク動作を数条明示

最小境界を先に通してから細化。

## セキュリティ境界

- ルールは**code review とブランチ保護の代替ではない**
- 悪意ある prompt がルール迂回を試みる可能性——サンドボックスはデフォルト厳格を維持
- ルール変更は PR で。CI 変更と同様に扱う

良い allow/deny ルールは、どの動作が妥当で、どれが起きてほしくないかを事前に明確にすることです。
