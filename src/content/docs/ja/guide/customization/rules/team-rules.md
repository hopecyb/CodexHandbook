チームで Codex を使うとき、**ルール方針**は次を答えます：どの制約を全社統一し、どれをリポジトリに任せ、個人が緩められるか。本章は [コマンドルール](/ja/guide/customization/rules/command-rules/) と [許可と拒否パターン](/ja/guide/customization/rules/allow-and-deny-patterns/) のガバナンス視点です。

## 内容

- 組織マネージド方針 vs プロジェクトルール vs 個人好み
- ルール変更のレビューとリリース
- `AGENTS.md`、Hooks、CI との連携

## チームルール方針の役割

どの境界を会社が統一し、プロジェクトが決め、個人習慣だけかを答えます。

層が曖昧だと：

- チーム全体で揃えるべきルールが個人 PC にだけ存在
- 一時的な個人設定がチーム標準と誤認される

## 対象読者

| 役割 | 関心点 |
|---|---|
| エンジニアリング責任者 | 底線 deny、監査要求 |
| リポジトリメンテナ | プロジェクト allowlist、テストコマンド |
| 個人開発者 | 方針許容範囲内の本機補足 |

## よくある誤解

### チームルールは統一ほど良いわけではない

高リスク deny などは組織統一が妥当です。すべてのリポジトリを無理に同一化すると、ルールが広すぎ／狭すぎて誰も信じなくなることもあります。組織層、プロジェクト層、個人層の境界を分けることが要点です。

### 個人補足はチーム底線を弱めない

本機で便利設定を足しても、組織・チームが定めた底線を迂回しない。表面上は「本機が効率的」、実際は協業の地雷です。

## 推奨層分けモデル

```text
L1 組織マネージド（Managed）     → プロジェクト／個人が上書き不可
L2 チームテンプレートリポジトリ    → 新リポジトリが継承する rules 片段
L3 プロジェクト rules + AGENTS.md  → Git PR レビュー
L4 個人設定                        → 本機のみ。L1 を弱めない
L5 単発タスク prompt                → 一時的な厳格化は可。緩和は L1 に制限
```

[AGENTS.md スコープ](/ja/guide/customization/agents-md/scope-and-precedence/) と対で覚える：**ルールは実行 enforcement 寄り、AGENTS.md は行動説明寄り**。一致させ、矛盾する要求を別々に書かない。

## 基本手順

1. **まず「絶対に許可しない」リスト（deny）**：`git push --force`、`~/.ssh` 読み取り、リポジトリ内容の公網 POST
2. **次に「日常許可」リスト（allow）**：テスト、lint、読み取り専用 git
3. **L1 をマネージド配布**（組織が Managed configuration を有効化している場合）
4. **各サービス／Monorepo サブパッケージ**は L3 を追加可。L1 と衝突不可
5. **四半期レビュー**：承認ログの「誤拦」「誤放」をルール PR に還流

## 推奨ワークフロー：ルール変更

```text
提案（issue または RFC）→ セキュリティ／プラットフォーム review → PR でルールファイル変更
    → staging リポジトリで典型タスク試走 → マージ → 告知 + ハンドブック更新
```

大変更（例：ネットワーク外向き開放）は [Hooks 監査](/ja/skills/hooks/hooks-overview/) と [acceptable use](/ja/guide/team-enterprise/governance/acceptable-use/) も同期更新。

## Hooks、CI との整合

| 仕組み | 役割 |
|---|---|
| ルール | 実行前の許可／拒否 |
| Hooks | 複雑検証、ログ、コンプライアンス形式 |
| CI | マージゲート、ローカルルールと同源スクリプト |

三套ロジックを別々に書かない。**単一の真実源**（例：`tools/codex-rules.json`）を CLI と CI が共通参照を優先。

## よくあるミス

- 口頭だけ「push しない」。ルールファイル未更新
- 個人本機でサンドボックス緩和し、スクリーンショットを「チーム標準」にする
- Monorepo サブプロジェクト要件が違うのに、過度に広いグローバル allowlist を共用
- ルール変更の告知なし。仲間が突然大量承認失敗

## ルールをどの層に置くか

1. すべてのリポジトリで守るべき底線か？
2. 現在プロジェクトにだけ成立するか？
3. 個人の手癖のための補足か？

通常：組織層、プロジェクト層、個人層に対応します。

## セキュリティ境界

- ルールは [脅威モデル](/ja/guide/team-enterprise/security/threat-model/) とインシデント対応の代替ではない
- 規制データでは、ルールをデータ分類・保持方針と一緒にレビュー
- 緊急迂回は**監査記録**と事後レビューが必要

## 受け入れチェックリスト

- [ ] 自組織の L1〜L3 分担を描ける
- [ ] リポジトリ内ルールファイルに明確な owner と review 要求がある
- [ ] `AGENTS.md`、Hooks、CI と相互矛盾なし
- [ ] 「誤拦」フィードバックの経路（issue テンプレートまたは内部フォーム）がある

チームルール方針で最も重要なのは、先に「誰がどの層の境界を決めるか」を分け、それからルールを書くことです。
