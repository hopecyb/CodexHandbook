設定ファイルで、本機またはプロジェクトごとに**Codex の挙動を統一**できます。毎セッションモデル、承認レベル、サンドボックス方針を繰り返し設定する必要がありません。

## 本ページの内容

- 設定の置き場所、プロジェクト級とユーザー級の重ね合わせ
- よく変える項目：モデル、承認、サンドボックス、デフォルト作業ディレクトリ
- `AGENTS.md` との境界：設定は「能力スイッチ」、AGENTS は「プロジェクトでどうコードを書くか」

## 設定が管理すること

設定は Codex の**デフォルトの働き方**に近いものです。

例：

- デフォルトモデル
- セキュリティ境界をどれだけ厳しくするか
- デフォルトでどのディレクトリで働くか

単発タスクの一時要求ではなく、多くの場合のデフォルト開始状態を管理します。

## 設定の層

| 層 | 典型位置 | 内容 |
|---|---|---|
| ユーザー級 | `~/.codex/` 下の設定（具体ファイル名は公式を基準に） | デフォルトモデル、個人の承認習慣 |
| プロジェクト級 | リポジトリ内設定片段または `codex` 関連プロジェクトファイル | チーム共有のサンドボックス／ツール方針 |
| マネージド | 組織配布 | 個人が上書きできない強制項目 |

**易変な事実**（パス、フィールド名、TOML キー）は [OpenAI Codex ドキュメント](https://developers.openai.com/codex) を基準に。本ページは概念と判断方法を述べます。

## よくある誤解

### 設定が多いほどプロフェッショナルではない

初見では全部設定したくなりますが、初心者は高頻度の数項目で十分なことが多いです。

- デフォルトモデル
- デフォルト承認／サンドボックス方針
- デフォルト作業ディレクトリ

これらを先に安定させ、全フィールドを一度に研究するより現実的です。

### 設定＝プロジェクトルールではない

「すべての協業者が守るべき」要求は、通常 `AGENTS.md` やプロジェクト文書向き。個人本機設定だけでは維持すべきではありません。

例：

- コミット前に走らせるチェック
- 変更禁止ディレクトリ
- 自動 push できないタスク種別

これらを個人設定だけで維持しない。

## よく変える設定の意図

### モデルと推論

- 日常開発：速度と品質のバランス
- 複雑リファクタ：より強い推論モデル（プラン次第）
- スクリプト／CI：再現性のためモデル固定

背景：[モデルと推論](/guide/foundations/models-and-reasoning/)

### 承認とサンドボックス

| 意図 | 設定の方向 |
|---|---|
| 初心者／信頼しないリポジトリ | より厳格な承認、ネットワークと書き込み範囲を制限 |
| 信頼できる個人プロジェクト | 安全前提で割り込みを減らせる |
| 企業リポジトリ | マネージド方針に従い、独自に緩めない |

背景：[権限と承認](/guide/foundations/permissions-and-approvals/)、[サンドボックスとネットワーク](/guide/foundations/sandbox-and-network/)

### CLI と App の一貫性

同一アカウントで CLI とデスクトップ App は**同じセキュリティ基線**を目指す。「CLI は全権限、App は厳格」の二重基準を避ける。

## 最小実用手順

1. 公式「Configuration」章で現行バージョンのファイルパスを確認
2. 一項目だけ変更（例：デフォルトサンドボックスモード）し、一週間観察してから調整
3. チーム共有項目はリポジトリ文書へ。個人好みは本機に残す
4. `AGENTS.md` には「このプロジェクトで Codex をどう使うか」の推奨を書き、設定全文をコピーしない

## どこに置くかの判断

迷ったら：

1. ほとんどのタスクで使うデフォルト習慣か？
2. 自分だけの好みか？
3. プロジェクト全体の共通ルールか？

多くの場合：

- デフォルト習慣 → 設定
- 個人好み → 個人層
- チーム合意 → リポジトリ

## よくあるミス

- 手間削減のため全承認を無効化し、本番データディレクトリでプロジェクトを開く
- API 秘密鍵を設定ファイルに書いて Git コミット
- 文書の設定キーがインストールバージョンと不一致（CLI 更新後に未再確認）

## セキュリティ境界

設定ファイルには**パス許可リスト、ネットワーク方針、MCP サーバーリスト**が含まれる場合があります。変更前に「悪意ある prompt がこの設定を悪用できるか」を想像。企業環境は管理者配布。個人がマネージド方針を迂回しない。

設定はほぼ毎回選び直すデフォルト項目向き。すべてのルールを設定ファイルに詰め込む必要はありません。
