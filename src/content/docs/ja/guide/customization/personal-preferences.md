**個人の好み**は本機でプロジェクト横断に効く設定です：デフォルトモデル、テーマ、承認習慣、個人 Skill パスなど。リポジトリ内の `AGENTS.md` と違い、個人の好みはチームメイトと同じとは**仮定しない**でください。

## 内容

- 個人層とプロジェクト層に何を置くか
- [Profile](/guide/customization/configuration/profiles/) との連携でシーン切替
- 個人の緩い設定がチームリポジトリに漏れないようにする

優先順位の全体像：[カスタマイズ](/guide/customization/) · [スコープと優先順位](/guide/customization/agents-md/scope-and-precedence/)

## なぜこの層を分けるか

多くの人は最初、次を混ぜます。

- 個人の好みの使い方
- このリポジトリの要求
- 会社・チームの強制

分けないと後から：

- 自分の本機は快適だが、仲間は再現できない
- ルールが効いていると思ったが、本機設定がカバーしていただけ
- 緩い設定をより厳しいプロジェクトに持ち込む

## 個人の好みに向く内容

| 内容 | 例 |
|---|---|
| デフォルトモデルと推論段階 | 個人マシンの性能とプラン |
| UI テーマ、フォント、通知 | デスクトップ App [設定](/guide/desktop-app/settings/) |
| 個人 MCP（私有ツール） | 本機 DB 読み取り専用（慎重に権限付与） |
| 個人 Skill ライブラリパス | チーム Plugin と競合しない |
| ターミナルエイリアス、`codex` 起動ディレクトリ習慣 | [CLI 設定](/guide/cli/configuration/) を参照 |

## 個人層だけに置くべきでないチーム内容

- コードスタイル、テストコマンド、ディレクトリ構造 → **プロジェクト `AGENTS.md`**
- 強制サンドボックス方針 → **プロジェクト設定または組織マネージド**
- 顧客リポジトリのコンプライアンス要求 → **文書 + CI**。個人の記憶に頼らない

## 推奨実践

1. **仕事用 / 個人用 Profile を分離**：顧客プロジェクトは厳格 Profile、練習は緩め可
2. **新リポジトリでは先にプロジェクトルールを読み**、個人デフォルトを一時上書きするか判断
3. **個人 MCP と Skill を定期整理**、使わない第三者ソースを削除
4. 端末変更・再インストール時は設定一覧をエクスポート（秘密値は含めない）

## よくある誤解

### 1. 普段の好みをそのままグローバルデフォルトにしてよい？

好みが緩いと、顧客・チームプロジェクトでは不適切なことがあります。

### 2. 個人の好みとプロジェクトルールは大差ない？

大きく違います。個人の好みは「自分はこうしたい」、プロジェクトルールは「このリポジトリでは皆こうすべき」です。

### 3. 本機で問題ない＝設定が妥当？

より適切な基準は：

- リポジトリを汚さない
- 自分だけ知っているデフォルトに依存しない
- 厳格プロジェクトに切り替えたとき誤爆しない

## 個人層に置くべきかの判断

迷ったら次を自問：

1. 自分だけが気にする習慣か？
2. 他人の結果再現に影響するか？
3. すべてのプロジェクトに持ち込むべきか？

2 または 3 が危険寄りなら、安易にグローバルデフォルトにしない。

個人の好みは自分を楽にするためのもの。チームルールの代替でも、緩い設定を全プロジェクトに持ち込む手段でもない。

## メモリ機能との関係

製品が「メモリ」や永続好みを提供する場合は [メモリと永続コンテキスト](/guide/customization/memories-and-persistent-context/) を参照。メモリは安定した習慣向き。**プロジェクト固有の制約はリポジトリファイルが基準**です。

## よくあるミス

- 個人設定に会社 API key を固定
- 個人グローバルで shell を自動承認し、顧客コードを処理
- 仲間が「ルールが効かない」と言う——ルールが一度もコミットされていない
