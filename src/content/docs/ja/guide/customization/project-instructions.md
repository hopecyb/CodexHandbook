「プロジェクト説明」は Codex がリポジトリを理解するための**静的コンテキスト**で、単一ファイル形式に限りません。

## 内容

- `AGENTS.md` 以外にプロジェクト情報をどこに置くか
- README、docs、スクリプトファイルの分担
- リポジトリに書くべき情報と、会話だけに残す情報

## プロジェクトコンテキストの構成

| ソース | 役割 |
|---|---|
| `AGENTS.md` | 協業ルールとコマンド（権威：本章 AGENTS シリーズ） |
| `README.md` | プロジェクト概要と起動方法 |
| `docs/` | アーキテクチャ、ADR、運用手順 |
| 依存とスクリプト | `package.json`、`Makefile` など実行可能な真実 |

Codex はツールでこれらを読みます。重要なのは**真実を一つに**すること。README の起動コマンドは実際に動く必要があります。

## 基本手順

1. ルート `README.md` に用途、インストール、開発、テストの四段を用意
2. **Codex に繰り返し伝える説明**は `AGENTS.md` に沈める
3. タスクでは全文貼り付けではなく `@` で具体ファイルを指す：

```text
@AGENTS.md のテスト要件に従い、@src/auth/login.ts のヌルポインタを修正。
設計は @docs/auth-flow.md を参照。
```

## なぜ重要か

よくある状況：

- README は一套
- docs は另一套
- 実際に動くコマンドは `package.json` に隠れている

人が混乱するだけでなく、Codex も混乱します。リポジトリ内の「プロジェクトの真実」を集中・一貫させることが要点です。

## 「会話コンテキスト」との分担

- **プロジェクト説明**：数ヶ月単位で比較的安定
- **会話コンテキスト**：今回の目標、制約、途中結論

長いタスクで同じルールを繰り返し言うなら、十個のスレッドにコピペするのではなく `AGENTS.md` や `docs/` に**書き戻す**。[コンテキストを絞る](/ja/guide/context/keep-context-focused/) を参照。

## よくあるミス

- README が古く、Codex が誤コマンドで動く
- すべての文書を巨大 `CONTEXT.md` に詰め、誰も保守しない
- 機密情報を公開リポジトリの説明に置く

## よくある誤解

### 1. 会話で十分説明すれば、リポジトリ文書が乱れても大丈夫？

短期は足りることもありますが、長期はどんどん乱れます。次回また説明が必要で、今回の発言は他の人に見えません。

### 2. `AGENTS.md` がすべてのプロジェクト説明を解決する？

そうでもありません。`AGENTS.md` はルールと協業制約向きで、プロジェクト紹介、アーキテクチャ背景、完全な運用説明の代替には向きません。

### 3. 文書は多いほど良い？

重要なのは：

- 分担が明確
- 内容が一致
- 主要コマンドが実行可能

プロジェクト説明の要点は、Codex と人が同じ「リポジトリの真実」を見つけやすくすること。文書の数自体が目的ではありません。

## 分担の提案

- `README.md`：何のプロジェクトか、起動、テスト方法
- `AGENTS.md`：協業ルール、禁止領域、完了の定義
- `docs/`：より長い背景、アーキテクチャ、プロセス説明
- スクリプトと設定ファイル：実行可能な真実

## 受け入れチェックリスト

- [ ] 新規 clone（または Codex）が README + AGENTS.md でテストまで通せる
- [ ] タスク prompt は @ 参照中心で、長い背景の繰り返しを避ける
