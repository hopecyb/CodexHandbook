多くのチームの問題は、**同じ情報を間違った場所に置く**ことです。リポジトリに書くべきルールをチャットに入れ、Skill にすべき手順を `AGENTS.md` に詰め、読み取り専用でよいデータに高権限 MCP を渡す。

ここでは実務的な問いに焦点を当てます。

> 「これは今後も繰り返す」と分かったとき、どの層に沈めるべきか？

## 簡易表

| 仕組み | 最適な内容 |
|---|---|
| 単発 prompt | 今回のタスクだけに効く目標、制約、受け入れ基準 |
| `AGENTS.md` | リポジトリレベルの協業ルールと長期制約 |
| メモリ | 個人の好み、または少量の非機密・セッション横断の反復事実 |
| Skill | 再利用可能なワークフロー、チェックリスト、専門パターン |
| MCP | 外部ツール、データソース、システム能力へのアクセス |

この表で足りなければ、以下を続けて読んでください。

## 五段階の判断法

### 1. 現在タスクにだけ有効な情報

こうした情報は**今回の prompt** を優先します。

向いている例：

- 「今回は `docs/` だけ。コードは触らない」
- 「中国語要約を出力し、末尾に確認事項を1つ付ける」
- 「先に原因を分析。すぐにファイルを変えない」

向いていない例：

- チームが常に `pnpm test` を要求
- リポジトリの変更禁止ディレクトリ
- 毎回 PR レビューで同じテンプレート出力

こうした長期ルールは、さらに下の層へ。

### 2. プロジェクト協業ルールか、個人の習慣か？

**すべての協業者が知るべきルール**なら [`AGENTS.md`](/ja/guide/customization/agents-md/what-is-agents-md/) に。

例：

- テスト、lint、ビルドコマンド
- 触らないディレクトリ
- コミットメッセージや PR 受け入れルール
- monorepo でサブディレクトリごとの特別規範

**自分だけの好み**（説明は日本語、結論を先に）なら [メモリ](/ja/guide/customization/memories-and-persistent-context/) や個人設定が向きます。

経験則：

- PR review に載せるべきものはリポジトリ優先
- 他人に見えなくても困らないものだけ個人層を検討

### 3. 「ルール」か「手順」か？

多くのドキュメントが使いにくいのは、ルールと手順を混ぜるからです。

| 性質 | 向く場所 |
|---|---|
| 「main へ直接 push しない」 | `AGENTS.md` |
| 「Review では先にテスト、次にリスク、最後に回帰」 | Skill |
| 「リリース前にこの4コマンドを実行」 | Skill またはスクリプト |
| 「読み取り専用 issue データのみ許可」 | MCP + 権限設定 |

判断の軸：

- **ルール**は「何ができる／できないか」
- **手順**は「この種のことは通常どう進めるか」

再利用できる手順は [Skill](/ja/skills/overview/) が向きます。

## よくある組み合わせ（二者択一ではない）

成熟したチームは単一仕組みではなく組み合わせます。

### 組み合わせ 1：`AGENTS.md` + Skill

向く場面：コードレビュー、リリースチェック、障害調査。

分担：

- `AGENTS.md` にハード制約：自動マージ禁止、必須チェック
- Skill に手順：どうレビューするか、テンプレート、重要度分類

### 組み合わせ 2：Skill + MCP

向く場面：チケット読取、DB 照会、デザイン取得、週報生成。

分担：

- Skill が実行順序と出力形式を定義
- MCP が「どこに繋ぐか、何を見る／変えるか」を提供

分けて考えると：

> Skill は作業指導書、MCP は接続されたツールボックス。

### 組み合わせ 3：`AGENTS.md` + メモリ

向く場面：チームルールは安定、各人の表現習慣は異なる。

分担：

- `AGENTS.md` にチーム共通規範
- メモリに個人の好み（言語、説明スタイル、デフォルト出力構造）

逆は避ける。チームルールを個人のメモリだけに置かない。

## 実用的な判断マトリクス

| 問い | はい | いいえ |
|---|---|---|
| 現在タスクだけに影響？ | prompt | 続けて判断 |
| 全員が守るべき？ | `AGENTS.md` / プロジェクト設定 | 続けて判断 |
| 反復可能なプロセス？ | Skill | 続けて判断 |
| リアルタイム外部データ／操作が必要？ | MCP | 続けて判断 |
| 個人の長期好みだけ？ | メモリ / ユーザー設定 | prompt |

要件が両列に当てはまるときは、**層を分ける**サインです。一箇所に無理に詰めない。

## 三つの典型例

### 例 1：チームが回帰テストを忘れがち

チャットで「テスト忘れず」と言うだけでは不十分です。

より安定したやり方：

1. `AGENTS.md` に「ビジネスロジック変更時は `pnpm test` 必須」と明記
2. 手順が複雑ならテスト実行 Skill を追加
3. CI で最終的に担保

### 例 2：PR review を毎回同じ形式で

テンプレート全文を毎回貼らない。

より安定したやり方：

1. 出力構造を Skill にする
2. `description` に「review、審査、マージ前チェックで使う」と書く
3. チーム共通なら Skill パスをプロジェクト文書に記載

### 例 3：Linear チケットを読んでからコード変更

API Token を会話に貼らない。

より安定したやり方：

1. MCP で Linear 接続
2. デフォルトは読み取り専用
3. 固定フローなら Skill で「先にチケット、次にコード、最後に案」を規定

## よく踏む落とし穴

### `AGENTS.md` を百科事典にする

ハード制約が目立たず、重要コマンドと禁止領域が埋もれる。`AGENTS.md` は短く、硬く、実行可能に。

### Skill を「万能収納箱」にする

一つの Skill に review、リリース、デバッグ、日報を全部入れると、トリガーも保守も難しくなる。

### MCP をデフォルト回答にする

リポジトリから読める情報に、わざわざ外部ツールは不要。MCP は能力拡張であり、複雑さのご褒美ではない。

### メモリにチーム事実を載せる

誰のアカウントに覚えられているかで、退職や端末変更でルールが消える。リポジトリに戻す。

## 推奨導入順序

チームがまだ乱れているなら、次の順で収束できます。

1. まず最小限の `AGENTS.md`
2. 三回以上繰り返す手順を Skill に集約
3. 外部システムが本当に必要なときだけ MCP
4. 最後に個人メモリと好みを整理

先に**協業の合意**を安定させ、能力拡張はその後が楽です。
