効果的なプロジェクト指示は**チェックリスト**に近いものです。目標は、Codex が初回試行で予見可能なミスを減らすことです。

初めて書くときの問題は、考えを書きすぎて本当の制約が不明確になることです。

## 内容

- プロジェクト指示の望ましい形
- 「短く、硬く、実行可能」の意味
- Codex と人が読みにくくする書き方

## 推奨構造

```md
# プロジェクト指示

## クイックスタート（3〜5行）
インストール、開発サーバー、最もよく使うテストコマンド

## 必ず守る
番号付きで破れないルール

## コードとディレクトリ
命名、配置、依存の約束

## 完了の定義
「コミット可能」の基準

## 禁止事項
やらないことを明示
```

## 執筆原則

### 1. ハード制約を前に

「必須」「禁止」をファイル前半に。コンテキストが限られるとき、モデルは冒頭を重く扱う——[コンテキスト優先順位](/guide/context/context-priority/) と同じ論理。

### 2. コマンドはコピー可能に

**実際に動く**コマンドを書く。「テストを走らせる」のような曖昧表現は避ける：

```md
# 良い
pnpm test --filter @app/web

# 悪い
テストが通ることを確認
```

### 3. 検証可能な完了基準

```md
## 完了の定義
- `pnpm lint` と `pnpm test` が失敗なし
- 新 API に対応する単体テスト
- ユーザーに見える変更には手動確認手順（ブラウザ + モバイル）
```

### 4. 「なぜ」は一文に圧縮

```md
- `generated/` は変更しない：コード生成物。手変更は次ビルドで上書きされる
```

長い背景は `docs/` の正式文書へリンク。

## 「良い指示」とは

人と Codex が素早く掴めるもの：

- 先に何をするか
- 何をしないか
- どこまでで完了か

読後も「先に何のコマンドを走らせ、どこを触らず、どうなったら完了か」が分からなければ、まだ使いにくいです。

## チーム playbook 片段例

```md
## PR と Git
- ブランチ命名：`feat/`、`fix/`、`docs/` プレフィックス
- 1 PR 1 件事。大規模リファクタは別 PR
- マージ前に必ず人が diff を review。Codex がテスト済みでも

## Codex との協業
- 大タスクは先に「計画を出し、確認後にコード変更」
- DB マイグレーション時は先に SQL を出力し人が審査
```

## よくあるミス

| ミス | 結果 |
|---|---|
| フレームワーク百科を詰める | 重要テストコマンドが無視される |
| ルールが相互矛盾 | モデルがランダムに一つを選ぶ |
| 「品質を保つ」など空虚な表現 | 受け入れ不可 |
| 秘密鍵や社内 URL を含む | 漏洩リスク |

## よくある誤解

### 1. 指示は詳細ほど良いわけではない

散らばり、長さ、百科事典風は、本当に高優先のルールを埋もれさせます。

### 2. 「規範に注意」だけで指示になる？

通常は実行可能でない。具体コマンド、明確ディレクトリ、完了基準を書く。

### 3. 背景説明と実行ルールを混ぜてよい？

推奨しません。ルールを前に、背景は一文、長い説明は docs へ。

## 散らかった指示を直すとき

1. 「必須／禁止」を前に移す
2. 空虚表現を具体コマンドやチェック項目に
3. 長い背景を短くしリンクに
4. 最小完了定義を与える

良いプロジェクト指示は量ではなく、重要制約、重要コマンド、完了基準が十分明確で直接実行できることです。

## 保守リズム

- CI コマンド変更時に**同期して** `AGENTS.md` を更新
- 四半期レビュー：古いルールを削除
- 新人 onboarding の最初：`AGENTS.md` を読み「クイックスタート」を通す
