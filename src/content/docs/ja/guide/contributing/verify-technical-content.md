ハンドブック内のコマンド、権限、価格、製品機能はバージョンとともに変わります。**検証**は、読者がドキュメントどおりに操作したとき結果が予測可能であることを保証します。

## 本ページの内容

ドキュメント保守に初めて参加する人は、「問題なさそうに見える」を「すでに検証済み」と混同しがちです。

技術ハンドブックでは、この二つは大きく違います。

- 前者は主観的に正しそう、というだけ
- 後者は現行バージョン、現行環境、現行手順で実際に試した、という意味

ここでは「正しそう」を「今も正しいという証拠がある」状態へ上げる方法を説明します。

## 「検証」が確認していること

「技術コンテンツの検証」とは、文章が通るかだけでなく、読者が今日それに従えば本当にできるかを確認することです。

特に重要なのは、次のような内容は永続的に安定しないからです。

- コマンドが変わる
- メニュー位置が変わる
- 権限のデフォルトが調整される
- 製品能力と利用可能範囲が更新される

検証は編集の潔癖ではなく、古いドキュメントの通りに踏んでハマるのを防ぐためのものです。

## 状態の意味

| 状態 | 意味 |
|---|---|
| `planned` | 計画済み、未執筆 |
| `draft` | 執筆中、未確定 |
| `review` | 内容は完成、再確認待ち |
| `verified` | 記載根拠どおりに検証済み |
| `outdated` | 製品変更後に更新が必要 |
| `archived` | 履歴として保持、主ナビには出さない |

## よくある誤解

### 編集状態と検証方法は別の項目です

`editorialStatus` は執筆とレビューの進捗を記録します。`verification.kind` は実際に行った確認の種類を記録します。`verified` という表示だけでは、サンプルを実行したとは判断できません。

| 検証方法 | 裏付けられる結論 | 必須の根拠 |
|---|---|---|
| `editorial` | 構成、表現、またはサイト内参照を確認した | 確認内容の要約と日付 |
| `source-checked` | 明示した範囲の事実が出典と一致する | 具体的な出典リンク、要約、日付 |
| `run-tested` | 記録した環境でサンプルを実行した | 環境、実行とレビューの記録、要約、日付 |

`run-tested` はすべてのプラットフォームでの動作を保証しません。要約には検証したことと検証していないことを明記します。独立した計算による自己確認を、著者以外の人によるレビューと呼んではいけません。根拠のない古い記録は `legacyVerification` に残し、新しい検証状態のいずれかに自動的に読み替えません。

```yaml
editorialStatus: review
verification:
  kind: editorial
  checkedAt: "2026-09-18"
  summary: 構成とサイト内リンクを確認済み。サンプルはまだ実行していません。
```

出典確認と実行には `evidence` リストを使い、各項目に `label` と `href` を含めます。実行にはさらに `environment` を記入し、OS、関連するクライアントと依存関係のバージョンを明示します。環境または根拠リンクが欠けた実行記録はビルドで拒否されます。リンクが存在するだけでは根拠として十分とはいえず、保守担当者が記録を読む必要があります。

### コミュニティ記事は理解に役立つが、事実検証の代わりにはならない

コミュニティ記事などは、補うべきテーマを見つけるのに適しています。

ただし次に関わる場合は、公式ドキュメントまたは現行の実行結果に戻ります。

- コマンド名
- 権限の挙動
- 製品入口
- 価格、クォータ、地域差

### 検証は一文ずつの確認だけでは足りない

一文ずつ見れば問題なくても、つなげると成立しないことがあります。例：

- 対象製品と実際のページ内容が一致しない
- 手順の順序が誤っている
- デフォルト前提が書かれていない
- タイトルの約束が本文で実際に検証した範囲を超えている

だから「操作の一連の流れ」として検証し、字面だけを走査しないでください。

## 検証チェックリスト

1. **範囲の明示**：製品（App/CLI/IDE/Cloud）、OS、CLI バージョン
2. **手順どおり再現**：ゼロから、またはクリーンな worktree で一通り試す
3. **公式根拠**：製品に関する事実には具体的な公式情報を示す。安定した方法の演習では実際の入力と確認記録を使い、公式のお墨付きを装わない
4. **コミュニティ出典**：コミュニティ資料を参考にする場合はテーマ参考にとどめ、事実は公式を正とする
5. **日付の更新**：`verification.checkedAt` には実際に確認した日だけを書く。古い日付を一括更新して再確認済みと見せかけない
6. **独立再確認**：`verified` は著者以外の第二者確認を推奨

## 検証の順序

次の順が漏れにくいです。

1. まずページがどの製品、どの入口、どのシーンを扱うか確認する
2. 文中の手順を最初から一通り試す
3. 変わりやすい情報を公式ドキュメントと照合する
4. 不確実・未再現の箇所は格下げする
5. 最後に状態と日付を更新する

証拠が足りないうちに `verified` と書くより、`review` のままにしておく方がよいです。

## 変わりやすい情報

以下は四半期ごと、または major リリースのたびに再検証が必要です。

- コマンドとサブコマンド名、flags
- 権限デフォルトとサンドボックスの挙動
- プラン、モデル名、地域での利用可否
- MCP/Hook のイベント名

## 失敗したとき

- 実態に合わせて `review`、`draft`、`outdated` に格下げする
- PR でどの手順が公式と食い違うか説明する
- 大きな乖離は issue を開き `outdated` を付ける
