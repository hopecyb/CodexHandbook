並行処理の基本単位は、独立したコンテキスト、メッセージ、結果、目標を持つチャットです。「手順が多い」ことではなく、**タスクが互いに独立し、ファイル境界が明確で、個別に検収できる**場合に並行処理が適しています。

![メインスレッドが独立したタスクを複数の子 Agent へ割り当て、証拠と競合を集約するオーケストレーション図](/diagrams/subagent-orchestration-ja.svg)

## 並行できるかを先に判断する

| 並行できる | 順番に進める |
|---|---|
| 二つの読み取り専用調査 | 後のタスクが前の結論に依存する |
| コードと文書のディレクトリが重ならない | 同じ主要ファイルを同時に変更する |
| 二つの案をそれぞれ prototype にする | 要件がまだ頻繁に変わる |
| 各タスクに独立したテストがある | 統合して初めて正否を判断できる |

公式ガイドでは、二つのチャットに同じデータソースを書き込ませないよう推奨しています。並行してコーディングする場合は、異なる Git worktree を使ってください。

## 簡単な方法から複雑な方法へ

### 1. 最初は読み取り専用タスクを並行する

```text
タスク：認証モジュールで最近発生した失敗だけを分析し、ファイルは変更しない。
範囲：src/auth/** と対応するテスト。
成果物：根本原因の仮説、証拠のパス、未確定事項、推奨する検証コマンド。
```

読み取り専用タスクは merge conflict を作らないため、最初の練習に適しています。

### 2. 次に書き込みタスクを並行する

各チャットに目標、ファイルの所有範囲、禁止範囲、検収を明記します。

```text
目標：認証エラーコードの文書を追加する。
所有範囲：docs/auth/** のみ。
禁止範囲：src/**、lockfile、共有設定は変更しない。
検収：pnpm check:links を実行して結果を報告する。
```

コーディング用チャットは独立した [worktree](/ja/guide/desktop-app/worktrees/) で実行します。共有設定はメインチャットまたは指定した一人の所有者だけが変更します。

### 3. 最後にまとめて回収する

結果をそのまま連結してはいけません。メインチャットは次を確認します。

1. 各タスクが境界どおりに引き渡されたか。
2. 証拠とテストを再現できるか。
3. 異なる結論が競合していないか。
4. merge 後に統合テストを再実行する必要があるか。

## 長時間タスクと Goal モード

デスクトップ App、CLI、IDE で `/goal` を入力すると Goal モードを開始できます。目標には結果、制約、検証基準を含めます。各チャットの目標は独立しています。並行実行してもサンドボックスや権限は広がらず、判断が必要な操作では引き続き停止します。

より細かなツール単位のオーケストレーションは[子 Agent](/ja/guide/agent-work/subagents/)を参照してください。
