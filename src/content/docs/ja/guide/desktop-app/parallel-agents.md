並列 Agent は、**もともと独立して進められる作業**を分割し、メインスレッドが調整、検収、マージ判断に集中するのに向いています。

分割が適切なら、並列化で待ち時間を大きく短縮できます。不適切なら、コンフリクトを早く生むだけです。

## よくある誤解

多くの人が「並列 Agent」を初めて見たとき、「速くなる」ことが主目的だと思いがちです。間違いではありませんが、それだけでは不十分です。

前提は、**これらのタスクがもともと独立して成立すること**です。実際には相互依存しているのに無理に分割すると、前提のすり合わせ、結果の回収、コンフリクト処理に時間を取られ、かえって遅くなります。

## いつ並列が適しているか

| 適している | 適していない |
|---|---|
| 2 つの独立した調査タスクを同時進行 | 複数の Agent が同じコアファイルを同時に変更 |
| 読み取り専用の分析を走らせながら、ドキュメントの下書きを書く | 要件が頻繁に変わり、継続的な明確化が必要 |
| フロントエンドとバックエンド API の境界が明確 | 1 つの問題が別の結果に強く依存して初めて着手できる |

よくある判断基準：

- **成果物を明確に定義できる**ときに並列が向く
- **境界を先に合意できる**ときに並列が向く
- **独立して検証できる**ときに並列が向く

## メイン Agent の役割

並列モードでは、メイン Agent はすべてのサブタスクを自分で実行する必要はありません。次の 3 点に集中します。

1. 各サブタスクの目標と禁止事項を明確にする
2. 結果が検証可能か追跡する
3. 結果が衝突したときに最終判断を下す

メイン Agent は小さなテックリードに近く、実行よりも調整と判断が中心です。

## おすすめの分割方法

### 「工程」ではなく「問題」を分割する

より良い分割：

- Agent A：ログイン失敗が token の更新によるものか分析する
- Agent B：直近 2 回の認証関連の変更を確認する

あまり良くない分割：

- Agent A：ログの半分を見る
- Agent B：もう半分を見る

前者は各タスクに完全な目標があります。後者は機械的な分割にすぎず、回収コストが高くなります。

### 次のタイプへの分割を優先する

- **読み取り専用の分析**：コード、ログ、ドキュメントの読解、リスクの列挙
- **案の比較**：A/B 実装ルート、ライブラリ選定、権限スキーム
- **境界が明確な成果物**：独立したページ、独立したドキュメント、独立したモジュール

## 委任テンプレート

並列 Agent への指示には、次の 4 項目を含めるのが望ましいです。

```text
タスク：checkout フロー内のクーポン計算のみを分析し、コードは変更しない。
成果物：200 字の要約 + 主要ファイルパス + リスクポイント + 推奨する次のステップ。
境界：支払いモジュール以外のディレクトリを検索しない。書き込み操作のコマンドは実行しない。
検証：結論は必ずファイルまたはログの証拠に紐づけられること。
```

「この問題を見てきて」より効果的です。

## 3 つの一般的な並列パターン

### 1. 二方向調査

向いている場面：どのルートが正しいかまだ確信がないとき。

- Agent A が既存実装を調査
- Agent B が代替案を調査
- メインスレッドがコスト、リスク、互換性を比較

### 2. レイヤー別の進行

向いている場面：システム境界がすでに明確なとき。

- Agent A がドキュメントまたはプロンプト層を担当
- Agent B がコードまたは設定層を担当
- メインスレッドが一貫性を確認

### 3. 下書き + レビュー

向いている場面：まず 1 版を出して、素早く再確認したいとき。

- Agent A が下書きを作成
- Agent B はレビューのみで変更しない
- メインスレッドが採用するか判断

ドキュメントの補完、PR レビュー、事例整理に向いています。

## コンフリクト管理

並列で最も詰まりやすいのは、しばしばマージの段階です。

### 事前に合意すべき境界

- どのディレクトリをどの Agent が担当するか
- 共有設定ファイルの変更を許可するか
- 最終コミット権を誰が持つか

### 直列に戻すべき状況

- 2 つのサブタスクが同じビジネスフローを変更する必要がある
- 1 つの Agent の結論が、もう 1 つの Agent の前提を継続的に覆している
- タスクを進めるより「コンテキストの説明」に時間を取られている

調整コストが節約時間を上回ったら、並列の意味はなくなります。

## レビューと検収

各並列 Agent の出力は、少なくとも次のいずれかを満たすべきです。

- 具体的なファイル、ログ、リンク、または diff に戻れる
- 「何をしなかったか」を明確に説明できる
- メインスレッドに次の検証方法を伝えられる

「ここに問題があるかもしれない」という 1 文だけでは、メインスレッドにとってほぼ無意味です。

## よくある間違い

- 依存関係を判断せず、タスクが多いから盲目的に並列化する
- 所有権の合意なしに、複数の Agent が同じディレクトリを同時に変更する
- メインスレッドが検収せず、サブ結果をそのまま最終回答にする
- 並列を「考える量を減らす」手段とみなし、混乱だけを増幅する

並列 Agent の前提は、タスクが互いに独立し、個別に検証でき、それぞれ進められることです。
