Codex の連携価値は、ツールを 1 つ増やすことだけではありません。Agent を、すでに使っている協業の流れ——コードホスティング、チケット、通知、社内プラットフォーム、ナレッジベース——に組み込むことです。

着手前に、次をはっきりさせた方がよいです。

- 誰がこの自動化チェーンを起動できるか
- Codex が何を読み、何を書き戻せるか
- 失敗したとき誰が知り、誰が責任を持ち、どうロールバックするか

## 連携が変えること

「連携」とは、**Codex をチャット窓口だけでなく、普段使っているシステムの中で動かす** ことだと考えてください。

例えば：

- GitHub で PR を読み、コメントする
- チケットの背景を読み、対応案を出す
- タスク完了後に結果をチャットツールへ送る

連携が変えるのは、Codex が実ワークフローに入れるかどうかです。

## よくある誤解

### 連携は多いほどよいわけではない

初めて連携するチームは、GitHub、Jira、Slack、ナレッジベース、内部 API を一度に全部つなごうとしがちです。

初回パイロットでは、**最短で価値が見える 1 本のチェーンだけ** が向いています。

理由は現実的です。

- つなぐほど権限境界が説明しにくくなる
- 失敗時にどの段階か特定しにくくなる
- チームがシステムを信頼しなくなる

### 「自動実行できる」=「最初から自動実行すべき」ではない

連携で衝動的になりやすいのは、最初から状態変更、コード変更、通知、マージまで自動化することです。

一般的な始め方は次のとおりです。

- まず読み取り
- 次に提案を生成
- そのうえで人の確認
- 最後に自動書き戻しを検討

こうすると境界と責任を説明しやすくなります。

## 連携前に答える 3 つの問い

### 1. データを読むのか、システム状態を変えるのか？

| 種類 | リスク | 推奨 |
|---|---|---|
| 読み取り専用 | 比較的低 | ここから始める |
| 下書き / コメント生成 | 中 | 人のレビューを足す |
| 状態変更 / PR 作成 / メッセージ送信 | 高 | 権限制限 + 監査 + ロールバック |

多くのチームは最初から「自動変更」したがりますが、第一歩は **読み取って提案する** だけで十分なことが多いです。

### 2. 同期利用か、非同期自動化か？

| シーン | 向く方式 |
|---|---|
| セッション内で Codex に issue を調べさせる | MCP / 対話タスク |
| PR オープン時に自動レビュー下書き | Cloud / CI / Automation |
| 毎日定時でステータス集計 | 定期タスク / バックグラウンド自動化 |

同じシステムでも接続方法は複数あり、無理に 1 つに統一する必要はありません。

### 3. 人を助けるのか、人の代わりに決めるのか？

Codex はデフォルトで **提案レイヤー** に置くのがおすすめです。

例：

- PR review コメントの下書きは自動生成してよい
- issue 要約の整理は自動化してよい
- デフォルトでマージ、本番設定変更、高リスクチケットの自動クローズは非推奨

## 一般的な連携タイプ

### GitHub とコードホスティング

最も一般的で成熟した類型です。

向くこと：

- クラウドタスクでリポジトリを読み、ブランチを切り、PR を出す
- CI で非対話レビューを走らせる
- review comment を起点に再修正

入口：[GitHub 連携](/guide/integrations/github/) と [Web と Cloud](/guide/web-and-cloud/)。

### チケットとプロジェクト管理

Linear、Jira、Trello、社内要件システムなど。

向くこと：

- コード変更前に issue 背景を読む
- ラベルやステータスで振り分け案を出す
- イテレーション進捗を集計

この類型は **読み取り専用 MCP + Skill フロー** で始めるのが向いています。

### チャットと通知

Slack、メール、企業 IM など。

向くこと：

- タスク完了、失敗、承認待ちの通知
- 日報、週報、変更サマリーの定期配信

注意：通知だけを唯一の監査源にしない。重要タスクはログとチケット記録を残す。

### 社内プラットフォームとナレッジベース

開発者ポータル、Runbook、内部 API、ドキュメントサイトなど。

向くこと：

- チーム規約や当番マニュアルをコンテキストに接続
- 固定境界内で内部能力を呼び出す

この類型で重要なのは **権限の階層化と内容の信頼性** です。

## 着手前の判断

「この連携を先にやる価値があるか」を素早く見るなら、次の 3 つです。

1. チーム内で既に繰り返し発生している作業か
2. 読み取りと整理だけで先に価値が出るか
3. 結果が完璧でなくても、人が簡単にフォローできるか

3 つとも yes なら、第一候補になりやすいです。

## おすすめの導入順

初めて連携するなら、リスクの低い順がおすすめです。

1. 外部ソースを 1 つだけ読み取り接続
2. Codex に要約や提案だけさせ、直接実行しない
3. 人の承認と通知を足す
4. 最後に外部システムへの自動書き戻しを検討

先に価値を検証してから、権限を広げられます。

## 最小の連携案

「PR レビュー下書きの自動生成」を例にすると：

1. GitHub がタスクを起動
2. Codex が diff と関連ルールを読む
3. コメント下書きまたはチェックリストを出力
4. 人が確認してから採用するか決める

「自動でコードを直して自動マージ」より、導入しやすく、チームの信頼も得やすいです。

## リスク管理チェックリスト

- [ ] 各連携の owner を明確にする
- [ ] 読み取り / コメント / 書き戻しの 3 段階権限を分ける
- [ ] 1 回のタスクで何を読み、何を書いたか追跡できる
- [ ] 失敗時に通知があり、偶然気づくに頼らない
- [ ] 機密データを扱う場合はセキュリティ評価を通す

初回連携では、Codex に「見る」「提案する」役割から始める方が、「変える」「実行する」より現実的です。
