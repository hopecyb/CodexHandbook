**委任**とは、タスクを Cloud のリモート環境で実行させることです。**フォローアップ**とは、タスクの実行中または終了後に進捗を確認し、コンテキストを補い、危険な操作を承認し、修正を求めることです。これは「席を離れても前進できる」コアワークフローです。

## 内容

- いつローカルではなく Cloud に委任するか
- 各入口から委任を開始する際の違い
- 効果的なフォローアップの方法、「投げっぱなし」を避ける

## このフローの進め方

Cloud タスクは次のプロセスに近いです：

- まずタスクを明確に説明する
- リモートで実行が始まる
- 途中で制約の補足や承認が必要になることがある
- 終了後は diff、PR を確認し、続行するか判断する

Cloud は実行場所をリモートに変えるだけで、その後のフォローアップと判断はあなた次第です。

## 誰に向いているか

| シナリオ | 推奨 |
|---|---|
| 長時間のビルド/テスト | Cloud に委任し、ローカルで他の作業を続ける |
| 通勤/会議の合間 | スマホで状態確認、重要ステップを承認 |
| 標準化された環境が必要 | Cloud + [環境設定](/guide/web-and-cloud/cloud-environments/) |
| ローカルでの素早い試行錯誤 | まず [デスクトップ App](/guide/desktop-app/) または [IDE](/guide/ide/local-task-workflow/) |

## いつ委任すべきか

委任すべきか迷ったら、次の考え方で選べます：

- タスクがまだ試行錯誤中で、見ながら変更したい：まずローカル
- タスクが長時間かかる、PC を離れたい、統一環境に任せたい：Cloud に委任

## 委任前チェック

- [ ] [GitHub 接続済み](/guide/web-and-cloud/connect-github/)、対象ブランチ戦略が明確
- [ ] タスク説明に目標、範囲、禁止事項、検証方法を含む（[良いタスクの構造](/prompts/task-anatomy/) を参照）
- [ ] 未プッシュのローカル commit が必須なら、先に push するかローカルで実施
- [ ] Secrets / [外部ネットワーク要件](/guide/web-and-cloud/internet-access/) が準備済み

## よくある誤解

### 1. 委任したらもう見なくていい

これが最も時間の無駄です。タスクの方向がずれると、発見が遅いほど手戻りが増えます。

### 2. フォローアップは「進捗を催促する」こと

より価値のあるフォローアップは次の行動です：

- 漏れたコンテキストを補う
- 範囲を絞る
- 許可すべきでない危険な操作を拒否
- 終了後に修正を求める

### 3. 委任とローカルは対立関係

よくある実際のフローは：  
**まずローカルで探索し、長時間タスクを委任し、最後にローカルで仕上げる。**

## 各入口からの委任（概念）

| 入口 | 特徴 |
|---|---|
| [デスクトップ App · ローカルとクラウドタスク](/guide/desktop-app/local-and-cloud-tasks/) | 同一プロジェクトビューでローカル/Cloud を切り替え |
| [IDE · クラウドタスク](/guide/ide/cloud-task-workflow/) | エディタの選択コードと開いているファイルのコンテキストを持ち込む |
| Web / モバイル | 軽量な確認、承認、一言フォローアップ |

具体的なボタンと名称は現行製品に準拠してください。

## 推奨フォローアップのリズム

```text
委任開始 → 環境起動を確認 →（任意）途中でログを確認
    → 危険操作の承認 → タスク完了後に diff/PR を確認
    → 不満足なら：追加指示または新規フォローアップタスク
```

次の行動順序で進められます：  
**委任後は、少なくとも「途中一回 + 終了一回」は確認する。**

### 途中介入

- **コンテキスト補足**：ファイルや制約の漏れに気づいたら、フォローアップメッセージで説明し、タスクを開き直して履歴を失わない
- **範囲の絞り込み**：タスクがずれたら「X の変更を止め、Y だけ実行」と明確に
- **承認**：[人間承認パターン](/cases/workflows/human-approval-patterns/) を参照——未知の shell を一括承認するより、一歩遅くてもよい

### 終了後

- [PR 作成](/guide/web-and-cloud/create-pull-requests/) フローで diff をレビュー
- [Cloud コードレビュー](/guide/web-and-cloud/code-review/) またはローカル checkout でブランチを検証
- さらに変更が必要：同一 PR に追加委任、またはローカルで引き継ぎ

## 通知との連携

[デスクトップ通知](/guide/desktop-app/notifications/) またはモバイルプッシュを有効にし、長時間承認待ちでタスクが停止するのを防ぐ。チームでは、どの時間帯に本番関連リポジトリを承認できる人がいるか合意する。

## よくあるエラー

- 委任内容が曖昧で、Cloud が独自に「理解」して大規模リファクタリング
- ローカルで半分変更済み未コミットなのに、Cloud にリモート main から着手させる
- 途中確認をせず、終了時に方向の誤りに気づき、環境時間を無駄にする
- PR に「LGTM」とだけ書き、テストを実行しない
- 「リモート実行」を「リモートが責任を持つ」と誤解

## 検証チェックリスト

- [ ] 少なくとも一つの入口から Cloud タスクを正常に開始・完了できる
- [ ] タスク実行中に有効な制約を追加できる
- [ ] PR またはブランチが成果物としてあり、人の diff レビューを経ている
