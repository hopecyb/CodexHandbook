委任は「問題を投げる」ことではありません。目標、制約、環境、完了基準を独立した Cloud チャットへ渡すことです。タスクはバックグラウンドで実行できます。ログを確認し、コンテキストを追加し、修正を依頼し、最後に diff をレビューできます。

## 委任に適した場合

- 長時間のビルドまたはテストが必要
- 入力がすでにリモートリポジトリにある
- スクリプトで環境を再構築できる
- 現在の作業と独立して進められる
- 結果を直接 merge せず、完了後にレビューする

ローカルの未コミット状態、ローカルサービス、継続的な人の操作に依存するタスクは、まずローカルに残します。

## 完全な委任の例

```text
目標：#42 のログインリクエストが 30 秒後も接続を解放しない問題を修正する。
開始点：acme/api の fix/42-timeout ブランチ。
範囲：packages/auth/** と対応するテスト。
禁止：依存関係の更新、公開 API の変更、main への push。
検証：pnpm test --filter auth、pnpm typecheck。
完了：根本原因、diff、コマンドと終了結果を表示し、自動 merge はしない。
```

開始後、環境とブランチが正しいことを先に確認します。実行中の follow-up は、前提不足または方向のずれが見つかった場合だけ行います。

```text
追加の制約：グローバル HTTP client は変更せず、修正を auth adapter に限定してください。
これが現在の方針をどう変えるかを先に説明してから続けてください。
```

同じチャットには既存のコンテキストが残るため、同じ目標の修正に適しています。完全に独立した目標には別のチャットを使ってください。並行タスクに同じブランチまたはファイル群を書き込ませないでください。

## 結果が出た後

1. 要約と完全な diff を読む。
2. タスクで許可したパスと照合する。
3. 各検証コマンドの実際の出力を確認する。
4. 失敗または未実行の項目について説明を求める。
5. 修正が必要な場合は、同じチャットで具体的な follow-up を送る。
6. 基準を満たしたら PR を作成し、CI と人によるレビューへ引き継ぐ。

Cloud タスクは Web、IDE、GitHub、GitLab（Beta）、Linear、Slack から開始できます。公式 Cloud ページでは、Codex CLI から作業を開始、レビューできることも説明されています。入口が異なっても、リポジトリ、環境、ネットワーク、レビューの境界は変わりません。

## 失敗時の follow-up

単に「もう一度試して」と言わず、失敗の証拠と次の手順を伝えます。

```text
テストは retry.test.ts:48 で失敗しました。まず今回の変更が原因かを説明してください。
原因であれば、その回帰だけを修正して auth テストを再実行してください。原因でなければ、失敗を残して明確に記録してください。
```
