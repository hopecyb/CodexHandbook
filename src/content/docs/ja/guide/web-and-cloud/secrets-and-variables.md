Cloud タスクはプライベート API、パッケージリポジトリ、データベースへのアクセスを必要とすることがよくあります。ここで使う認証情報は **Secrets と環境変数** で注入し、コード、プロンプト、issue、チャット履歴、Git 履歴には書かないでください。

## 内容

- Secret と通常の環境変数の違い
- Cloud コンソール / リポジトリ設定での設定方法
- GitHub Actions Secrets との関係

## Secret と環境変数の区別

次のように区別できます：

- **Secret**：誰にも見られてはいけない値。API Key、データベースパスワード、秘密鍵など
- **環境変数**：プログラムが読む設定項目。機密性のあるものもあれば、ないものもある

すべての環境変数が Secret というわけではありませんが、Secret は安全な注入メカニズムを通すべきで、直接ハードコードしないでください。

## 概念の区別

| 種類 | 内容の例 | 保存要件 |
|---|---|---|
| **Secret** | API key、秘密鍵、データベースパスワード | 暗号化保存、UI でマスク、ログに出さない |
| **変数** | `NODE_ENV=production`、機能フラグ | 非暗号化でもよいが、ビジネス戦略の漏洩は避ける |
| **リポジトリ内 `.env`** | ローカル開発用 | **コミットしない**。Cloud ではコンソール Secrets で代替 |

機密コンテキストの総則：[機密コンテキスト](/guide/context/sensitive-context/)

## よくある誤解

### 1. 「一時的に key を貼るだけなら、大した問題ないでしょ？」

リスクは大きいです。key を次の場所に貼った瞬間：

- 会話
- issue
- PR 説明
- shell 履歴
- Git コミット

ログ、通知、スクリーンショット、履歴バージョン、その他の協力者に拡散される可能性があります。

### 2. 「`.env` に書いてコミットすれば、Cloud が読める？」

`.env` はローカル開発向きで、バージョン管理にコミットするのには向きません。Cloud では、プラットフォーム提供の Secret 管理機能を優先してください。

### 3. 「Secret の名前は適当でいい、値が合っていれば？」

多くのタスク失敗は、値そのものではなく次の問題です：

- 名前のスペルミス
- スコープが合っていない
- コードが別の変数名を読んでいる

ドキュメント、コード、Cloud 設定の命名は統一するのがよいです。

## 設定原則

1. **最小権限**：各 Secret は一種類のタスクを完了するのに十分な権限だけ
2. **リポジトリ/環境ごとに分離**：staging と production を分ける
3. **ローテーション**：token を定期的に更新し、古いタスクの失効は許容
4. **監査**：誰がどの Secret を追加/変更したか記録（チームプロセス）
5. **決して再表示しない**：タスクログと PR コメントに Secret 値を出力しない

## 最小設定フロー

次の順序で進められます：

1. タスクが実際にどの外部サービスにアクセスする必要があるかリストアップ
2. 今回のタスクに必要な Secret だけ準備し、最初から本番の全権限を与えない
3. ドキュメントに「どの名前の Secret が必要か」を書き、値は書かない
4. テストタスクを一度実行し、読み取り可能か検証
5. 本番タスクに進む

## 推奨ワークフロー

```text
1. Cloud / GitHub 設定で Secret を追加（名前は大文字スネークケース、例：NPM_TOKEN）
2. AGENTS.md に「プライベートパッケージのインストールには NPM_TOKEN が必要」と記載し、値は書かない
3. Cloud タスクを開始し、環境が読み取れるか確認（失敗時は名前のスペルとスコープを確認）
4. CI は GitHub Actions Secrets を使用し、Cloud と命名を揃えてドキュメント化しやすくする
```

[GitHub 統合](/guide/integrations/github/) と併用する場合、Agent に issue 本文からキーをコピーさせるのではなく、プラットフォームネイティブの Secrets を優先してください。

## いつ Secret として扱うべきか

ある値を Secret にすべきか迷ったら、次を自問してください：

- この値が漏洩したら、金銭、データ、権限、ビジネスリスクが生じるか？

答えが「はい」なら、公開ドキュメント、プロンプト、チャット履歴、リポジトリに置くべきではありません。

## インターネットアクセスと Secrets

一部のタスクは外部ネットワークでパッケージを取得したり API を呼んだりする必要があります：

- 外部ネットワークポリシーは組織のセキュリティ規定に従う
- 外部ネットワークが許可されていても、プロンプトに Bearer token を貼らない
- 信頼できないリポジトリでは、デフォルトで本番 Secrets の読み取りを禁止

## よくあるエラー

| エラー | リスク |
|---|---|
| `.env` をリポジトリに commit | 永久漏洩 |
| issue/タスク説明に key を貼る | ログと通知への拡散 |
| 本番 Secret を実験タスクに使用 | 本番データの誤操作 |
| Secret 名とコードが不一致 | タスクが静かに失敗 |
| 手間を省いて管理者権限 token を渡す | 制御不能な影響範囲 |

## 検証チェックリスト

- [ ] リポジトリ内にハードコードされたキーがない（secret scanner 利用可）
- [ ] Cloud Secrets リストとドキュメントの名前が一致
- [ ] タスク失敗ログに Secret 平文が含まれていない
- [ ] 退職/ローテーションプロセスが定義済み
