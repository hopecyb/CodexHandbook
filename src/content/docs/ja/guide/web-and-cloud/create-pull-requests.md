初めて Cloud ワークフローを使うと、タスクは完了しているのに変更が確認・議論しやすい状態に入っていない、ということがよくあります。チームコラボレーションでは、この段階を **Pull Request** で担います。

PR はレビュー可能な変更申請です。

何を変更したか、なぜ変更したか、テストしたかを、review できる一か所に集約します。Cloud タスクのチームへの引き渡しも、ここに着地します。

## 内容

- クラウドタスクから PR までのエンドツーエンドの期待
- PR 説明に含めるべき内容（人と CI の検証のため）
- 自動で PR を開くべきでない場合

## いつ PR を開くか

変更を他の人が見る必要がある、CI を走らせる必要がある、最終的にメインブランチにマージする必要があるなら、「ブランチで変更済み」で止めず、**レビュー可能な PR** まで進めてください。

## 推奨ワークフロー

```text
GitHub 接続 → issue/目標を明確化 → Cloud タスク（計画確認）→ ブランチをプッシュ → PR を開く → 人の review + CI → マージ
```

前提：[GitHub に接続](/guide/web-and-cloud/connect-github/)

## 最初から自動マージしない理由

PR はコードをプッシュするだけでなく、人とシステムにチェックの入口を与えるためのものです。

一般的なやり方：

- Codex が PR を開くのを手伝える
- マージするかどうかは人が決める

こうすれば、タスクの方向がずれても、人のチェックという関門が残ります。

## タスクプロンプトの要点

```text
目標：#42 で説明されているログインタイムアウト問題を修正
ブランチ：fix/42-login-timeout
範囲：packages/auth と関連テストのみ
完了：main へ PR を開く、マージはしない
PR 説明に含める：理由、変更概要、テストコマンドと結果、リスクとロールバック
```

[完了の定義](/prompts/define-done/) と [良いタスクの構造](/prompts/task-anatomy/) と一致させてください。

## 良い PR が最低限答えるべき 4 つの質問

1. なぜこの変更をしたのか？
2. 具体的にどこを変更したのか？
3. どう検証したのか？
4. 残るリスク、制限、未カバー領域は何か？

PR 説明がこの 4 点をカバーしていないと、レビュアーがコンテキストを自分で補う必要があります。

## PR 品質チェックリスト

- [ ] タイトルが「何をしたか」を説明し、「コードを更新」ではない
- [ ] 関連 issue 番号を記載
- [ ] CI が通過、または既知の失敗理由を説明
- [ ] diff 行数がチームの許容範囲内。大きすぎる場合は PR を分割
- [ ] キーなし、無関係なフォーマット変更の嵐なし
- [ ] スクリーンショットまたはログ（UI/動作変更時）

## よくある誤解

### 1. 無関係な複数の変更を 1 つの PR に詰め込む

レビューが難しく、ロールバックも困難になります。

### 2. 「修正済み」とだけ書き、検証方法を書かない

相手は「本当にテストした」のか「たぶん大丈夫」なのか判断できません。

### 3. Codex にメインブランチを直接触らせる

個人実験なら手間が省けるかもしれませんが、コラボレーションリポジトリではリスクが高すぎます。

## Review 自動化との連携

- Skill または CI の `codex exec` で**補足レビューコメント**を追加可能
- 自動マージは別途ガバナンスポリシーが必要。初心者のデフォルトパスには含めない

KimYx0207 CX-10 は Review/PR 専用。具体的な能力は公式に準拠してください。

## よくあるエラー

- PR に無関係な複数機能を含める
- 説明に「AI 生成の変更」とだけ書き、テスト説明がない
- review を迂回して main に直接マージ
