# 検証

Codex を初めて使う人が陥りやすいミスは、**「完了した」と言われたら本当に完了だと思うこと** です。

検証とは、言葉ではなく、結果が要件を満たしているかを見ることです。

Codex の出力は必ず確認可能であるべきです。検証は任意ではなく、毎回のタスク閉じの一部です。

## 検証で見ていること

コード変更でも、ドキュメント作成でも、調査でも、最後に答える問いは同じです。

> **これは「だいたい合っていそう」なのか、「もう渡せる」状態なのか？**

多くの手戻りは、モデルが完全に間違ったからではなく、次のような理由です。

- 触るべきでない場所を変えた
- 半分しか変えていない
- 調べたと言うが出典が信頼できない
- ページは開くがフローが通らない
- ドキュメントは書けたが、初心者がそのまま使えない

検証の役割は、**リスクを納品前に閉じ込めること** です。

## よくある誤解

### 1. 動けば完了

「動く」は即時エラーがないだけで、次を意味しません。

- ロジックが正しい
- 範囲が正しい
- 回帰を入れていない
- 本来の結果に合っている

### 2. モデルが「検証済み」と言えば安心できる

**何を検証したか** を見てください。例えば：

- 本当にテストを走らせたか
- 本当に diff を読んだか
- 本当に成果物を開いて確認したか
- 追跡可能な出典を示したか

### 3. 検証はプログラマーだけのもの

記事、表、設定生成、資料整理、PR 説明文にも検証は必要です。方法が違うだけです。

## まだ自分のフローがないなら、この順で見る

まだ手順がなければ、次の順が使えます。

1. 結果が論点から外れていないか
2. 変更範囲が大きすぎないか
3. 自動で回せるチェックを回す
4. 最後に人の目で渡せるか見る

次のように理解できます。

- **方向は合っているか**
- **変更は多すぎないか**
- **機械チェックは通ったか**
- **人が本当に受け取れるか**

## タスクごとに検証の重点は違う

- **コード変更**：diff → テスト → 重要パスを手動確認
- **ドキュメント作成**：読者に合うか、リンクは有効か、手順は再現できるか
- **調査**：出典は本物か、最新か、証拠を超えていないか
- **設定やスクリプト生成**：環境前提、権限範囲、失敗時の復旧

どこから始めるかわからなければ、まず [完了の定義](/guide/quality/definition-of-done/) を読んでください。

検証は、結果が本当に使え、安心して渡せるかを確かめるためのものです。
