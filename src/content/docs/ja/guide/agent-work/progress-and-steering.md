実行の途中でよくある反応は、だいたい次の二つだけです。

- 何も言わず、ずれたまま進めさせる
- 「止めて、全部やり直し」

より一般的なやり方は、実行中に**誘導**し続け、合っている部分を残し、ずれた部分だけ直すことです。

## 誘導がしていること

ここでの「誘導」は、今のステップをどう進めるかを補足することです。例えば次のような内容です。

- どの部分は正しいので残すか
- どの部分がずれ始めたので止めるか
- 次にどのステップを優先するか

## 「誘導」とは何か

誘導は、現在の実行状態への**局所的な方向修正**です。

たいてい次のようなときに必要になります。

- 目標の理解は合っているが、手順の順序が良くない
- 半分は合っているので、全部はやりたくない
- 新しい情報を足したので、以降の動きを調整したい
- 不要なリファクタや拡張に入りそうだと感じた

## 最もよく使うテンプレート

途中の誘導は非常に短くて構いません。

```text
今のステップで止まる。A と B は残す。C への変更方針は取り消す。次は D だけやる。E は始めない。
```

この指示には四つの重要部品があります。

1. どこで止めるか
2. 何を残すか
3. 何をやめるか
4. 次に何だけをやるか

## よくある誤解

### 1. ずれたら全部止めてやり直すべき？

半分合っているなら、全部倒すとたいてい次が起きます。

- 背景を再度説明する必要がある
- すでに揃った部分も一緒に失う
- 次のラウンドでもまたずれる可能性がある

### 2. 「違う」と言えば、どこが違うか分かるはず？

たいてい足りません。

より効くのは、次を明確にすることです。

- 何を残すか
- 何をやめるか
- 今何を優先するか

### 3. 誘導と再計画は同じ？

- **誘導**：ルートはおおむね正しく、局所だけ直す
- **再計画**：目標・前提・影響範囲が変わった

## 小さな軌道修正が効く理由

| 小さな軌道修正 | やり直し |
|---|---|
| すでに揃った作業を残す | 合っていた部分も一緒に失う |
| コンテキストを節約 | 背景の再説明が必要 |
| 範囲を制御しやすい | 再び漂流しやすい |
| 実際の協業に近い | 注文の繰り返しに近い |

## いつ誘導し、いつ計画に戻るか

次のように判断できます。

- **順序・範囲・出力形式だけの問題**：先に誘導
- **目標・前提・影響範囲が変わった**：計画に戻る

## 三つのよくある誘導パターン

### 1. 範囲を絞る

やりすぎ始めたとき：

```text
まずログインページだけ扱う。登録とパスワード再設定フローには広げない。
```

### 2. 順序を変える

やること自体は合っているが、前後が合わないとき：

```text
実装を続ける前に、先に検証とテストを足す。
```

### 3. 出力形式を変える

分析を先に見たい、まだ手を付けたくないとき：

```text
まだファイルは変更しない。現行案と提案案の違いを比較表で出して。
```

## 良い誘導に含めたいこと

- 今止める位置
- 残す部分
- 続けない方向
- 新しい優先順位
- 実行を続けてよいかどうか

次の一文は比較的明確です。

```text
原因の判断は残す。ただしリファクタにはまだ入らない。次は最小修正案と検証ステップだけ足す。
```

## 「再計画」に戻るべきとき

誘導は局所的なずれ向けですが、次の場合は [計画](/guide/agent-work/planning/) に戻る価値があります。

- タスクの目標自体が変わった
- 新情報が当初の前提を覆した
- 影響範囲が明らかに広がった
- 二〜三回軌道修正しても、まだ漂流している

問題が局所偏差ではなくなったら、誘導で無理に続けず計画段階へ戻ります。

## よくあるミス

- 「違う」とだけ言い、どこが違うか言わない
- 優先順位を渡さず「自分で直し方を決めて」と言う
- 一歩止めたいだけなのに、全面やり直しを引き起こす言い方をする
- すでに新しいタスクなのに、一言の補足で無理に続けようとする

実行中にずれを見つけたら、短い指示で「何を残す・何を止める・次に何だけやるか」を伝えられます。
