Agent ワークが扱うのは、タスクを**検証可能な完了状態まで届ける**方法です。いつ先に計画するか、いつサブタスクに分けるか、途中でどう軌道修正するか、いつ引き継ぎと再開が必要か——この章で扱う問題はこれらです。

この章は個別機能の説明ではなく、**協業のやり方**を論じます。

多くのタスクで難しいのは要件を口に出すことではなく、**本当に終わって確認できる状態**まで持っていくことです。

## この章で扱うこと

- タスクが複雑なとき、どう計画に収束させるか
- 実行中に方向がずれたとき、どう小さく軌道修正するか
- どのサブ問題を子 Agent に分ける価値があるか
- 長いタスクが中断したあと、どう引き継ぎと再開するか

## よく使うフレームワーク

Agent ワークは、おおよそ次の四つの連続動作として捉えられます。

```text
まず理解 → 次に計画 → 実行中に軌道修正 → 最後に引き継ぎ／仕上げ
```

途中のステップを欠くと、よくある結果は次のとおりです。

- 理解を欠く：方向を間違える
- 計画を欠く：半ばで範囲が制御不能になる
- 軌道修正を欠く：直すほどずれる
- 引き継ぎを欠く：長いタスクが途切れたあと、どこまで進んだか分からなくなる

## よくある誤解

### 1. Agent ワークはプロンプトを長く書くこと

それだけでは足りません。

プロンプトは起点に過ぎず、タスクの質を決めるのはほかにもあります。

- 計画があるか
- 途中で軌道修正しているか
- 複雑な部分を分けているか
- 続けられる状態が残っているか

### 2. 途中で方向を変えたら、それまでが無駄だった

多くの場合、実行しながら範囲を絞るのは正常なやり方です。最初の一回ですべてを言い当てる必要はありません。

### 3. 子 Agent に分けると必ず効率が上がる

そうとも限りません。

境界をはっきり言わないと、サブタスクが増えるほどメインスレッドが乱れます。

## まず通す最小フロー

基本的な方法でタスクを一度通したいだけなら、次の 4 ステップで十分です。

1. タスクをはっきり伝える
2. 複雑なら先に計画を出させる
3. 実行中、結果に応じて小さく軌道修正する
4. 終わる前に検証可能な結果を求める

この 4 ステップが滑らかになってから、子 Agent と引き継ぎを学ぶと自然です。

Agent ワークの本質は、計画・実行・軌道修正・仕上げの各段で、タスクが正しい方向に進み続けるかどうかです。

## よくあるミス

- Agent を検索ボックス扱いし、曖昧な目標を一言だけ渡す
- 「途中で口を変えた」＝最初からやり直し、と考える
- 長いタスクなのに引き継ぎ成果物が一切ない
- サブタスクを分けるとき境界を渡さず、メインスレッドがますます乱れる
