**子 Agent（Subagent）** は、主 Agent が明確なサブ問題のために起動する独立した作業単位です。子 Agent はそれぞれ独自のコンテキストを持ち、完了すると結論と証拠をメインスレッドへ返します。全体に関わる判断と最終検収は、引き続き主 Agent が担います。

![Codex の子 Agent オーケストレーション構成：主 Agent が境界の明確なサブタスクを委任し、子 Agent が証拠を返し、主 Agent が集約して検証する](/diagrams/subagent-orchestration-ja.svg)

## まず三つの層の関係を理解する

| 層 | 分離されるか | 意味 |
|---|---|---|
| 会話コンテキスト | はい | 各子 Agent は自分のタスクに集中でき、メインスレッドの詳細をすべて引き継ぐ必要はありません |
| サンドボックスと権限モード | 継承 | 子 Agent は独立して動作しても、より高い権限を得ることはありません |
| ワークスペースのファイル | 必ずしも分離されない | 複数の Agent が同じワークスペースを見る場合があり、同じファイルを並行して編集すると競合します |

最も重要なのは、**コンテキストの分離はファイルの分離を意味しない**という点です。コードを並行して変更する場合は、あらかじめディレクトリ、コンポーネント、または worktree 単位で所有範囲を分けてください。

## 現在利用できる場所

現在の Codex では子 Agent 機能が標準で提供され、デスクトップ App、CLI、IDE の対応する画面で活動を確認できます。画面の細部は変わる可能性がありますが、安定した使い方は、独立したサブタスクを委任するよう Codex に明示し、メインスレッドに集約を担当させることです。

CLI では `/agent` を使ってスレッドの確認や切り替えができます。IDE では対応する画面にバックグラウンド Agent が表示され、デスクトップ App ではタスク内のスレッド活動を確認できます。特定のコントロールが表示されるかどうかは、現在のクライアントとアカウントの機能に依存します。

## 分割する価値があるとき

サブタスクが次の三条件のうち二つを満たすなら、分割を検討する価値があります。

1. 独立して説明でき、メインの詳細を頻繁に同期する必要がない。
2. ファイル一覧、テスト結果、1 ページの結論など、明確な成果物がある。
3. ほかのタスクと並行できる、または個別に深掘りすることでメインスレッドのノイズを大幅に減らせる。

### 並行処理に向く作業

- フロントエンド、バックエンド、テストカバレッジをそれぞれ読み取り専用で調査する
- 相互に依存しない複数の失敗テストを並行して調べる
- 二つの技術案について別々に証拠を収集する
- 専門的な役割にセキュリティレビュー、性能分析、ドキュメント確認を依頼する

### メインスレッドに残す方がよい作業

- 要件がまだ明確でなく、ユーザーとの継続的な対話が必要
- 複数の手順を厳密に順番どおり進める必要がある
- 変更が同じファイルや同じコード部分に集中している
- 完了条件が明確でなく、単に「適当に見ておいて」というタスク

子 Agent を使うと token の消費と集約のコストが増えます。一つの明確なスレッドで完了できる小さなタスクを、並行化のためだけに分割する必要はありません。

## 主 Agent の責任はなくならない

主 Agent は常に次の四つを保持する必要があります。

- 全体目標、ユーザーの制約、最終判断
- サブタスクの境界とファイルの所有範囲
- 複数の結論が競合したときの判断
- 統合後のテスト、ビルド、リスクの説明

子 Agent からの「完了」という報告はサブタスクの状態を示すだけであり、タスク全体の完了を証明するものではありません。

## 検収可能な委任契約を書く

次は、読み取り専用の調査タスクの例です。

```text
子 Agent を一つ起動し、packages/auth の session 更新ロジックを読み取り専用で分析してください。

範囲：packages/auth と対応するテスト。ファイルは変更しないこと。
質問：更新に失敗した後、古い token が再利用される可能性はあるか。
成果物：結論、主要なファイルと行番号、再現手順、推奨テスト。
検証：各結論はソースコードまたは既存テストで確認できること。
返却：500 字以内にまとめ、変更するかどうかはメインスレッドが判断する。
```

この契約では、担当範囲、確認場所、回答する問題、禁止事項、検証方法、判断者という六つの要素が明確になっています。

## 三つのタスクを並行する例

ログイン機能で断続的な回帰が発生した場合、主 Agent は次のように分割できます。

| サブタスク | 権限と範囲 | 成果物 |
|---|---|---|
| A：コード経路 | `src/auth/` を読み取り専用で確認 | エントリポイントから失敗分岐までの呼び出し経路 |
| B：テストの証拠 | テストとログを読み取り専用で確認 | 安定して再現できる最小テスト |
| C：最近の変更 | 関連する Git 履歴を読み取り専用で確認 | 回帰を引き起こした可能性が最も高い変更とその根拠 |

三つの結果が返ったら、主 Agent はまず証拠を比較してから、修正方針を一つ選びます。A、B、C に `src/auth/session.ts` を同時に変更させてはいけません。

## 並行して書き込む必要がある場合の分離方法

次の順序で競合を減らしてください。

1. 書き込みタスクを、重複しないディレクトリまたはコンポーネントに分ける。
2. 並行する実装ごとに独立した worktree またはブランチを割り当てる。
3. 各 Agent が変更できるファイルの一覧を明示する。
4. 主 Agent がまとめて統合し、統合後に検証を再実行する。

各サブタスクのテストが個別に通っていても、統合後の組み合わせでは失敗する可能性があります。そのため、最終検証を省略することはできません。

## 検収チェックリスト

- 返却内容が範囲を広げず、元の質問に答えているか
- ファイル位置、ログ、テストなど、確認可能な証拠が添えられているか
- 読み取り専用、ディレクトリ、コマンドなどの制約を守っているか
- 複数の結果に矛盾がないか。矛盾がある場合、明示的に処理されているか
- 統合後に完全なテストとビルドを再実行したか
- 未解決の問題と残存リスクを説明しているか

## ほかの機能との組み合わせ

- **Skill** は、コードレビューのチェックリストなど、サブタスクの手順と出力形式を定型化します。
- **MCP** は、子 Agent に制御された外部ツールやデータを提供します。
- **Hook** は、子 Agent の開始、停止、ツール呼び出しのタイミングでガードルールを追加します。
- **worktree** は並行するファイル変更を分離します。解決するのはワークスペースの競合であり、コンテキストの問題ではありません。
