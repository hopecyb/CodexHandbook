計画とは、確認して調整できる実行経路です。範囲、依存関係、受け入れ条件の不足を早期に見つけられますが、タスクが大きいからといって確認待ちを繰り返す必要はありません。

まず[タスクの分類](/ja/prompts/ask-for-a-plan/)に従い、直接完了するか、計画後に既存の権限内で実行するか、今回は提案のみとするか決めます。「先に案を示し、ファイルは変更しない」という明示的な依頼は読み取り専用です。実装依頼なら計画だけで終えてはいけません。

![イラスト：小さなアシスタントがホワイトボードに手順の計画を描き、作業前に人が一つの手順を指して修正を求める](/illustrations/agent-planning.webp)

## 十分な計画に必要なもの

| 要素 | 具体化する内容 |
|---|---|
| 目標 | 完了後に観察できる動作 |
| 範囲 | 関連ファイル、入力、除外事項 |
| 順序 | 実際の依存関係。ツール呼び出しを毎回別の段階にしない |
| 検証 | 完了を示す出力や確認方法 |
| 判断 | 結果に影響する未解決の決定だけ |

既存のレポートにデータのグループ分けを追加するなら、「定義を確認→集計と表示を変更→サンプルで合計とグループを照合」と計画できます。ファイルを読むたび、編集するたび、テストするたびに別の承認を求める必要はありません。

## 異なる2種類の計画依頼

**方法がまだ決まっていない場合：**

```text
今回は読み取り専用で、2つのエクスポート案の依存関係、互換性、保守費用を比較してください。
推奨案と私が決めるべき点を示し、実装は変更しないでください。
```

**範囲が決まり、実装が必要な場合：**

```text
既存の要件に従ってCSVエクスポートを完成させてください。まずリポジトリを確認して短い計画を示し、
合意済みの範囲で実装と検証を続けてください。各段階で待つ必要はありません。
新しいサービス、公開インターフェースの変更、データアクセスの拡大が必要なら、先に具体的な理由を説明してください。
```

これらは本サイトが作成した例です。製品の承認ダイアログが表示されるかは、実際のツール、方針、権限によります。

## 実行中の調整

- 普通の実装上の詳細が判明したら、計画を更新し、権限内で続ける。
- 前提が誤っていたら、根拠と影響を示し、範囲内の代替案を出す。
- ユーザーが決める必要のある取捨選択は、具体的に質問し、回答に依存しない作業を続ける。
- 未承認の外部操作が必要なら、確認可能な結果を準備し、操作前に権限を求める。

「問題が起きるかもしれない」だけで止めず、実際の範囲変更を無視して計画に固執もしないでください。

## 計画へのフィードバック

```text
手順1と2は残し、リファクタリングは外してください。
今回はローカルプレビューだけにし、公開しないでください。
古いファイル形式も正しく読めることを受け入れ条件に追加してください。
```

フィードバックは明示した部分だけを変更します。取り消していない制約と完了条件は引き続き有効です。中断時は、現在のファイル、完了した検証、次の手順を[引き継ぎ記録](/ja/guide/agent-work/handoff-and-resume/)に残します。

## 完了時は証拠に戻る

手順をすべてチェックしたかではなく、計画の目標が実際に成立するか確認します。未実行のテスト、未確認のプレビュー、未検証の事実を明記してください。全体の流れは[調査→計画→実行→検証](/ja/cases/workflows/explore-plan-execute-verify/)を参照してください。
