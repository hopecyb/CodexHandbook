Codex を初めて使うとき、多くの人が最も心配するのは「間違えたら戻れるか？」です。

多くの場合戻れますが、安全な方法で戻すのがよいです。

結果が範囲外、または品質が不十分なとき：

1. クライアントが提供する取り消し / 変更復元機能を使う（現行 UI が基準）
2. プロジェクトが Git 下にある場合：慣れた方法で作業ツリーの変更を破棄（初心者は Git を使わず、練習ディレクトリに依存してもよい）
3. 新しいスレッドを開き、制約を厳しくして再試行

多くの場合、事前に範囲を小さくしておく方が楽です。例えば少数ファイルだけ、禁止事項を明記、計画を先に見てから実行。

## 「取り消し」と「復元」の区別

- **取り消し**：さきほどの不満な変更を戻す
- **復元**：プロジェクトを安全と確認した状態に戻す

小さなファイル 1 つの練習なら、取り消しは難しくありません。より面倒なのは次の場合です。

- 複数ファイルを変更した
- その後自分でも手動変更した
- どの部分が誰の変更か覚えていない

まず変更を続けず、影響範囲を狭めてください。

## 初回で間違えたときの処理順序

1. まず変更を続けない。慌ててさらに変更させない
2. まずどのファイルを変更したか確認する
3. 製品内の取り消しが使えるなら、それを優先する
4. プロジェクトがもともと Git 下なら、慣れた Git 方法で戻す
5. 安全な状態に戻ったら、より明確な指示を出し直す

## Git に不慣れな場合の対処

多くの初心者は「復元」という言葉に驚き、多くの Git コマンドを先に覚える必要があると思いがちです。最初はそうである必要はありません。

まず次のようにできます。

- 練習ディレクトリで練習する
- 一度に 1 つの小さなファイルだけ変更させる
- 結果に不満なら直接取り消す

本番プロジェクトを扱い始めたら、Git での戻し方を体系的に学べばよいです。

## 予防は事後対応より重要

次のやり方は、「間違えたあと片付けにくい」確率を明らかに下げます。

- 「どのファイルだけ変更するか」を明記する
- 先に計画を出させ、実行はその後
- 1 ステップごとに確認し、多くの変更をまとめて見ない
- 高リスク操作の前に確認する

間違えること自体は怖くありません。変更範囲を見ずに変更を続ける方が、より面倒です。
