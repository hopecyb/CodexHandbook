以下の例はデフォルトで **デスクトップ App** を想定しています。CLI/IDE でも同じプロンプトが使えます。

多くの人が Codex を初めて使うとき、「完全なサイトを作って」や「プロジェクト全体をリファクタリングして」と言いたくなります。すぐに制御不能になりやすいです。

最初のタスクは小さくする方が安定します。最初から大きくするより、一連のフローを通す方が重要です。

## なぜ最初のタスクはこれほど小さくするか

最初のタスクは次の 3 条件を満たすのがよいです。

- 変更範囲が小さい
- 結果が一目で確認できる
- 間違えても取り消しやすい

ここではとても小さな練習例を使います。

## 例タスク

練習プロジェクトで Codex に次のように伝えます。

```text
目標：hello.md の末尾に「今日の練習」セクションを追加し、3 行の要点リストを含める。
制約：hello.md のみ変更。既存内容は削除しない。ネットワークリクエストは実行しない。
検証：ファイル末尾にその見出しとちょうど 3 つのリスト項目が現れること。
情報が不足している場合は推測せず、先に質問すること。
```

## プロンプト各部分の役割

このプロンプトは重要な点を分けて明確に書いています。

- **目標**：何をするか
- **制約**：どこを勝手に変更してはいけないか
- **検証**：「完了」の定義
- **情報が不足している場合は先に質問**：推測を防ぐ

固定テンプレートではなく、最も説明しにくい部分を明確にしただけです。

## よくある誤解

### 1. 最初のタスクが大きいほど、本当のスキルが身につく

最初に重要なのは完全なループを一度通すことであり、一度に大きくすることではありません。

### 2. プロンプトを書いたら、あとは任せればよい

最初のタスクでは、次の 3 点を見守ることが重要です。

- 範囲が超えていないか
- 指定したファイルで作業しているか
- 最終結果が検証条件を満たしているか

### 3. 最初に間違えたら、使い方がわからない証拠

最初のタスクには本来、次が含まれます。

- どこが間違っているかを発見する
- 問題を指摘できる
- どう取り戻すかを知る

## 実行時の注意

1. 短い計画を出させる（または自分から計画を求める）
2. ファイル書き込みの承認時にパスが正しいか確認する
3. 完了後 [結果の確認](/ja/guide/getting-started/review-the-result/) へ進む

## 実行順序

次の 5 ステップで進められます。

1. 安全な練習プロジェクトを選ぶ
2. 1 ファイルだけを変更する小さなタスクを出す
3. 承認前にどこを変更するか確認する
4. 完了後に範囲と結果を確認する
5. 不満なら取り消すか、精密に修正を続ける

この 5 ステップを終えると、協業のリズムがより身につきます。

## 完了後に確認すべきこと

次の 3 点に注目してください。

1. `hello.md` だけを変更したか
2. ファイル末尾に本当にそのセクションが追加されたか
3. リスト項目の数がちょうど 3 つか

この 3 点が正しければ、今回の小さなタスクは概ね成功です。

## 間違えた場合

最初に間違えるのは普通です。次のように続けられます。

```text
変更しすぎました。他のファイルへの変更は取り消し、hello.md の変更だけ残してください。
```

または：

```text
まだ変更を続けないでください。さきほどどこを変更したか教えてください。
```

プロンプトの原理：[プロンプトの基礎](/ja/prompts/basics/)。
