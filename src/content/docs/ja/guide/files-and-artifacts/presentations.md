プレゼンテーション（PPT、Keynote、Google Slides、Marp/Reveal など）は **物語の構成** と **視覚的一貫性** が重要です。Agent は骨子と初稿が得意ですが、マスターとブランド規約は人の確認が必要です。

Codex で発表資料を作る価値は、まず構成・ページ順・話の流れを組み立てることにあり、最終稿は自分で仕上げる前提が現実的です。

## 本ページの内容

- Codex でスライドを作る推奨ワークフロー
- 形式（`.pptx`、Markdown スライド）の使い分け
- 「ページごとにスタイルがバラバラ」を避ける方法

## まず納品形式を決める

| 形式 | 向く用途 |
|---|---|
| Marp / Slidev / reveal.md | 開発者、バージョン管理しやすい |
| `.pptx` | ビジネス報告、顧客共有 |
| Google Slides | リアルタイム共同編集（多くはエクスポートまたは MCP 経由） |
| PDF エクスポート | 読み取り専用配布 |

タスク冒頭で形式を固定し、Agent が複数ツールチェーンを混ぜないようにします。

最終的な受け手で選びます。

- 顧客、上司、同僚がそのまま開いて直す：多くは `.pptx`
- コードと一緒にバージョン管理：多くは Markdown スライド
- 読むだけの配布版：最終的に PDF エクスポート

## 推奨ワークフロー

```text
1. 骨子：聴衆、時間、核となるメッセージ 3〜5 個
2. 各ページのタイトル + bullet 3 つ、ノートに話す要点
3. ツールを選んで初稿を生成
4. 人手でマスター、図表、データ出典を調整
5. PDF をエクスポートしてリハーサルで時間計測
```

[探索—計画—実行—検証](/cases/workflows/explore-plan-execute-verify/) と同様、骨子段階で先に検証してから詳細を埋めます。

## なぜ発表資料は先に構成を抑えるべきか

構成を先に抑えないと、Codex はページを一気に増やしがちですが、内容も次のように崩れやすくなります。

- 順序が乱れる
- ページ数が制御不能になる
- 各ページが独立したポスターのようになり、一つの報告に見えない

通常は次の 3 層で進めると安定します。

1. まず「この発表で何を伝えるか」を決める
2. 次に「各ページが担う核心メッセージ」を決める
3. 最後に Agent に文案、図表説明、発表者ノートを書かせる

## よくある誤解

### 1. 派手な PPT ほど伝わりやすい？

多くの場合、理解に効くのは次です。

- タイトルが一文で要点を言えるか
- ページ間に前進関係があるか
- データに出典があるか

### 2. Agent が初稿全体を出せるなら、人手確認は不要？

それも違います。  
次は必ず人が見るべき部分です。

- 会社ブランドとマスター
- 重要な結論
- 数値と図表
- 外部送付版

### 3. 1 ページに詰め込むほど情報量が増える？

通常は話しにくくなります。  
bullet、図、結論を 1 ページに詰めすぎると、聴衆は要点を掴みにくくなります。

## よく使う作成順序

いま Codex に発表資料を作らせるなら、次の順で要件を出すとよいです。

1. 聴衆は誰か
2. 発表時間はどれくらいか
3. 相手に持ち帰ってほしい 3 点は何か
4. まず骨子を出してもらう
5. 骨子確認後に各ページを展開
6. 最後に発表者ノート、ビジュアル要件、エクスポート形式を足す

この順なら、構成 → 文案 → スタイルとエクスポートの順で収まりやすくなります。

## プロンプトの要点

- **聴衆**：技術者か経営層かで用語の深さが変わる
- **ページ上限**：80 ページの冗長資料を防ぐ
- **ブランド**：メインカラー、logo パス、clipart 禁止（社内規約がある場合）
- **データ図**：データソースファイルを明記し、スクリーンショットの捏造ではなく更新可能にする

次のような言い方も有効です。

> 「まず 10 ページ以内の骨子を作ってください。聴衆は非技術の経営層です。各ページは核心結論を 1 つだけにし、最後に発表者ノートを足してください。」

「かっこいい PPT を作って」より、磨き続けやすい初稿になりやすいです。

画像要件は [画像とスクリーンショット](/guide/files-and-artifacts/images-and-screenshots/)。純粋な画像生成は [画像生成](/guide/tools/image-generation/)。

## 検証

- 投影解像度で文字サイズが読めるか
- アニメーションは控えめに（多すぎると保守が難しい）
- 数値が [出典の確認](/guide/quality/validate-sources/) と一致するか
- 発表者ノートが十分か（必要な場合）

## Codex に任せやすいことと、自分で決めること

| Codex に任せやすい | 人手で決めるべき |
|---|---|
| 骨子のページ分割 | 最終結論の言い回し |
| ページタイトル初稿 | ブランド一貫性 |
| 発表者ノート初稿 | 機微データ |
| 図表説明文案 | 外部公開版 |

この分担だと時間を節約しつつ、品質も止めやすくなります。

## よくある失敗

- 骨子なしで「四半期報告 PPT を作って」と依頼する
- `.pptx` バイナリを手直しし続け、Markdown ソースを残さない
- 図表データがリポジトリの CSV と一致しない
- 構成・デザイン・結論・データ定義を一度に Agent に任せる

## 検証チェックリスト

- [ ] 骨子を人手で確認してから全文を生成した
- [ ] 再生環境で開いてフォント崩れがない
- [ ] 重要データがソースファイルまで追跡できる
