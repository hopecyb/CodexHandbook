Agent がタスクを完了すると、レポート、スクリプト、静的サイト、テストデータなどの **生成物** ができます。これらは慣れ親しんだコードレビュー経路を通らないこともあるため、別の検証習慣が必要です。

Codex が新しく作ったファイルだからといって、そのまま使えるとは限りません。

## 本ページの内容

- 生成物と「既存コードの変更」の検証の違い
- チェックリスト
- いつ拒否し、やり直しを求めるか

## 生成物のタイプ

| タイプ | 検証の重点 |
|---|---|
| スクリプト `.sh` `.py` | 実行可能、無害、べき等 |
| レポート `.md` `.html` | 事実の正確さ、リンク有効性 |
| ビルド出力 `dist/` | gitignore すべきか |
| テストフィクスチャ | 実 PII がないか |
| 設定テンプレート | デフォルト弱パスワードがないか |

## ここでいう「生成物」とは

ここでの「生成物」とは次を指します。

- 新しく書かれたファイル
- エクスポートされたレポート
- ビルドされたページ、ディレクトリ、パッケージ

これらは「既存コードを数行直しただけ」とは違い、実内容を見落としやすいです。

## 検証フロー

```text
1. 成果物を開く（Agent の文字要約だけを見ない）
2. タスクの「完了の定義」と照合する
3. 関連テストまたはプレビューコマンドを実行する
4. パス、権限、サイズを確認する
5. 判断：受け入れ / 部分修正 / 破棄してやり直し
```

方法：[成果物の検証](/ja/guide/quality/verify-artifacts/)、[完了の定義](/ja/guide/quality/definition-of-done/)

## よくある誤解

### 1. 「完了した」と言われても、実物は見る

要約は「何をしたつもりか」を示すだけで、実際の成果物の形を代わりには確認できません。

### 2. 新規ファイルの方が既存変更より安全、とは限らない

新規ファイルにも次があり得ます。

- 誤った内容
- 余分な依存
- 情報漏えい
- リポジトリに入れるべきでない大きなファイル

### 3. 動けばコミット価値がある、とは限らない

一部の生成物はローカル一時利用向けで、Git には向きません。

## Git との関係

- どの生成物を **コミット** し、どれを `.gitignore` するかを明示する
- 1 つの PR に megabytes 級のビルドキャッシュを混ぜない
- 大きな成果物は CI artifact や外部ストレージを使う

## よく使う検証順序

生成物を受け取った直後は、次の順で見るとよいです。

1. 何のファイルができたか確認する
2. いちばん重要な成果物を開く
3. 許可ディレクトリに置かれているか見る
4. リポジトリにコミットすべきか判断する
5. 受け入れ、修正、やり直しを決める

## 信頼できない生成物

信頼できないリポジトリや外部データ駆動のタスクでは：

- 実行前にスクリプトを読む
- `curl | bash`、難読化 payload に注意する
- サンドボックスまたはコンテナでプレビューする

生成物は「できた」だけでは不十分です。開いて、検証して、コミットすべきかまで判断してください。

## よくある失敗

- Agent の bullet 要約だけ見て、ファイルを開かない
- 一度きりのデバッグ出力を main にコミットする
- HTML レポートにトラッキングピクセルや未審査の外部スクリプトがある

## 検証チェックリスト

- [ ] 各新規ファイルのパスが許可範囲内
- [ ] 開いて主要内容をざっと読んだ
- [ ] 自動チェック（lint/test/link check）を実行した
- [ ] secrets や余分な生成ディレクトリがない
