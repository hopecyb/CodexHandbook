Codex の主な成果は、多くの場合 **リポジトリ内のファイル変更** または **新しく生成された成果物**（ドキュメント、画像、設定）です。本セクションでは、ファイルタイプごとのベストプラクティスを説明し、「生成されたが使えない」事態を避ける方法を示します。

同じ「ファイル」でも、タイプによって伝え方と検証方法が異なります。

「コードを直す」「表を処理する」「スクリーンショットを生成する」「PPT をエクスポートする」はどれもファイルタスクのように見えますが、最も失敗しやすいポイントはそれぞれ違います。

## この章で説明すること

この章では主に次の 3 点を扱います。

- タスクをどう明確に伝えるか
- どこで静かに間違いやすいか
- 最後にどう検証するか

つまり、機能一覧ではなく、ファイルタイプ別の操作ガイドに近い内容です。

## 共通原則

1. **パスを明確に**：プロンプトで出力パスと命名を書く
2. **形式の約束**：拡張子、エンコーディング（UTF-8）、改行をプロジェクトと揃える
3. **サイズへの配慮**：大きなバイナリは Git に入れない、または LFS/CDN を使う
4. **手動検証**：生成 ≠ 完了。[完了の定義](/guide/quality/definition-of-done/) と照合する
5. **機微データ**：[機密コンテキスト](/guide/context/sensitive-context/) を参照

## よくある誤解

### 1. ファイルが生成されたからといって、タスクが完了したわけではない

多くのファイル系タスクの問題は「生成されたかどうか」ではなく、次にあります。

- 形式が正しいか
- 内容が正確か
- パスが正しいか
- 下流で引き続き使えるか

### 2. ファイルタイプが違っても、伝え方はだいたい同じ？

そうでもありません。  
たとえば：

- コードファイルは範囲、ロジック、テストが重要
- 表は列、型、集計ルールが重要
- 画像は視覚的内容とサイズが重要
- ドキュメントは構成、トーン、事実が重要

### 3. 最後に開ければ、問題ない？

そう考えてはいけません。  
「開ける」は最低限の一歩にすぎず、コミット・公開・納品に適しているとは限りません。

## 推奨する読み順

Codex で初めてファイルを扱うときは、次の順で読むとよいです。

1. いまのタスクに最も近いファイルタイプを見つける
2. そのタイプで失敗しやすい点を確認する
3. 対応する検証方法を見る

こうすると、章全体の情報に一度に押しつぶされにくくなります。

## ツールとの関係

- ファイルの読み書き：ファイルツール + ターミナル
- 画像の参照：[画像プロンプト](/prompts/prompting-with-images/)
- ページの確認：[ブラウザツール](/guide/tools/browser/)
- 画像の生成：[画像生成](/guide/tools/image-generation/)

ファイル系タスクでは、結果は出ているのに形式・ルール・内容が静かにずれている、ということがよくあります。
