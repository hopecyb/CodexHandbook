PDF は仕様書、論文、スキャン、エクスポートレポートでよく使われます。プレーンテキストと違い、PDF は **構造が複雑でサイズが大きく、diff しにくい** ため、タスクの進め方を別途決める必要があります。

Codex に PDF を渡すとき、よくある問題は構造理解の欠落か、範囲の指定が広すぎることです。

## 本ページの内容

- Agent に PDF 内容を正しく「読ませる」方法
- PDF の生成・更新時の形式とパス約束
- 検証で「ファイルはあるが開けない」を避ける方法

## なぜ PDF は特に失敗しやすいか

PDF はテキストファイルより扱いが難しく、次が混在することがあります。

- スキャン画像
- 多段組レイアウト
- ヘッダー・フッター
- 表
- 画像と文字の混在

「どの部分を見て、何を返してほしいか」をはっきり書くほど、結果は安定しやすくなります。

## PDF の読み取り

### 推奨做法

1. **ファイルパスを指定**：`docs/spec.pdf` または @ 参照（クライアント対応による）
2. **欲しい結果を説明**：要約、特定章との照合、表データの抽出
3. **ページまたは章**：長文は範囲を限定し、コンテキストを節約
4. **機微内容**：契約書、身分証スキャンなどは [機密コンテキスト](/guide/context/sensitive-context/) の手順に従う

### 制限

- スキャン版 PDF は OCR が必要な場合があり、誤認識は人手で spot check が必要
- 複雑な版式、多段組、脚注で構造が失われやすい
- 超大容量 PDF は一度のタスクに丸ごと入れない。分割するか、先に Markdown 骨子に変換する

## よくある誤解

### 1. PDF を丸ごと渡せば、安定して要点を抽出できる

長く、構造が複雑で、スキャン頁が混ざるほど、次の方が安定します。

- 範囲を指定する
- タスクを指定する
- 分割して処理する

### 2. スキャン版 PDF と通常のテキスト PDF は大きく違う

スキャン版はまず OCR が必要で、OCR が外れると要約・抽出・判断までずれます。

### 3. PDF ファイルが生成されたからといって完了ではない

次も確認してください。

- 開けるか
- 文字化けがないか
- ページ数、目次、表が正しいか
- 日本語フォントが実際に埋め込まれているか

## PDF の生成・更新

| 方法 | 向く用途 |
|---|---|
| Markdown/LaTeX からコンパイル | 技術文書、レポート（再現可能） |
| HTML から印刷 | 単純な版式 |
| ライブラリ生成（例：reportlab） | プログラム的な帳票、ラベル |

プロンプトでは次を明記してください。

- 出力パスとファイル名
- ページサイズ、言語、フォント要件（日本語 PDF はフォント埋め込みに注意）
- Git にコミットするか（大きなバイナリは artifact や release が一般的）

## そのまま使える書き方

次のように依頼できます。

```text
`docs/spec.pdf` の 12〜18 ページだけを読み、そこにある受入基準を抽出してください。
文書全体は要約しないでください。
OCR や版式認識に不確実性がある場合は、明示してください。
```

## リポジトリ方針との関係

- 大きな PDF バイナリは **Git LFS** を検討するか、リポジトリ外に置く
- diff が読めないときは、**ファイルを開く** + [成果物の検証](/guide/quality/verify-artifacts/) で確認
- 生成物一覧は [生成物の検証](/guide/files-and-artifacts/generated-artifacts/) を参照

## よくある失敗

- 「PDF の 1 文字だけ直して」と言いながら、編集可能なソース（`.md` / `.tex`）を渡さない
- 機密 PDF を公開リポジトリに入れてから Cloud で処理する
- 開いて検証せず、「ファイルがある」だけで済ませる

## 検証チェックリスト

- [ ] 対象の閲覧・印刷環境で PDF が開ける
- [ ] ページ数、目次、主要な表が期待どおり
- [ ] リポジトリサイズと LFS 方針がチーム規約に合う

PDF では、範囲が明確なほど安定します。生成後も、ファイルの存在だけでなく、正常に開けて内容が本当に正しいかを確認してください。
