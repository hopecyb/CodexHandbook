表形式タスクは静かに壊れやすい典型です。区切り文字、エンコーディング、ヘッダー、数式、日付形式のどれか一つでも外れると、下流がすべて崩れます。

## 本ページの内容

- Codex に CSV / Excel を安全に読み書きさせる方法
- データ分析タスクのプロンプト構造
- 数値と行数の検証方法

## 形式の選択

| 形式 | 利点 | 注意 |
|---|---|---|
| CSV | テキストで diff 可能、汎用 | エンコーディング（UTF-8 BOM）、区切り、引用符のエスケープ |
| TSV | カンマ衝突が少ない | CSV と同様 |
| XLSX | 複数シート、数式 | バイナリで diff 困難。ライブラリで読み書き |
| Google Sheets | 共同編集 | 多くは MCP 経由または CSV エクスポート |

小さなデータで Git に入れるなら：**CSV/TSV を優先**。複雑なレポートなら：**ソースは CSV + XLSX 生成スクリプト**。

まず次の 3 点を確認してください。

- diff・追跡・再現が必要なら：CSV / TSV を優先
- Excel に慣れた人へ渡すなら：その後 XLSX をエクスポート
- 「最終閲覧形式」と「自動処理に最適なソース形式」を混同しない

## 読み取りと分析

推奨プロンプト構造：

```text
ファイル：data/sales_2025.csv
エンコーディング：UTF-8
タスク：region ごとに revenue を集計し、summary.csv を出力
制約：元ファイルは変更しない。空値は 0 扱い。小数点以下 2 桁
検証：先頭 5 行と総行数を表示
```

コンテキスト：[ファイルとディレクトリのコンテキスト](/guide/context/file-and-folder-context/)

## なぜ表タスクは静かに壊れやすいか

実際に問題になりやすいのは次です。

- 日付をテキストと日付のどちらとして扱うか
- 空値を 0、スキップ、エラーのどれにするか
- どの列が一意識別子か
- 小数と金額を四捨五入するか
- 元ファイルを変更してよいか

これらを書かないと、Codex も「完了したように見える」が信頼できない結果になり得ます。

## 書き込みとクレンジング

- **列名、順序、型** を明示する（日付は ISO 8601）
- 大きな表は分割処理し、一度に読み込んでメモリ不足にしない
- 重複排除、結合キーをタスク説明に書き、Agent に「主キー」を推測させない

## よくある誤解

### 1. 最後にファイルが開ければ、処理は正しい

違います。

表タスクでは「開ける」と「データが壊れていない」は別問題です。

### 2. Excel で見て問題なければ、必ず正しい

次のような問題は、後段のシステムで初めて表面化することがあります。

- エンコーディング不一致
- 列順の変更
- 数値型の変化
- 数式が結果値に固定化される

### 3. 空値・日付・主キーは Agent に任せればよい

通常はおすすめしません。

この種のルールは明示するほど結果が安定します。

## 表タスクを渡すときに書く 5 点

要件は次の 5 点にまとめるとよいです。

1. 入力ファイルは何か
2. 出力ファイル名は何か
3. どの列を保持・集計・クレンジングするか
4. 空値、日付、重複をどう扱うか
5. 結果をどう検証するか

「この Excel を整理して」だけより、はるかに安定します。

Python なら `pandas` で読み書き。Node なら `csv-parse` / `xlsx` など。`AGENTS.md` でプロジェクト標準ライブラリを約束してください。

## 検証との関係

- 行数、合計がソースデータと突合できるか
- Excel で日付が数値扱いになっていないか
- [成果物の検証](/guide/quality/verify-artifacts/)：サンプル比較

表タスクでは、列・型・ルール・検証方法をはっきり書くことが重要です。

## よくある失敗

- Excel で CSV を開いて文字化け（BOM 不足やエンコーディング誤り）
- 浮動小数の合計誤差について四捨五入ルールを書かない
- Excel で数式を直すが、再現可能なスクリプトとして保存しない

## 検証チェックリスト

- [ ] 列名と型が下流の利用側の約束に合う
- [ ] 合計/サンプルが人手または SQL と一致
- [ ] 元ファイルが意図せず上書きされていない（または diff で見える）
