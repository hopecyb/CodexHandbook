画像は Agent に UI の問題、デザイン意図、ホワイトボードのラフを **見せる** 手段になります。本ページは入力（あなたが渡す画像）とリポジトリ内画像の管理を扱います。新規画像の生成は [画像生成](/guide/tools/image-generation/) を参照してください。

スクリーンショットでタスクを出すときは、どこを見てほしいか、なぜそこが問題かを伝えるとよいです。

## 本ページの内容

- スクリーンショットを効果的に添付する方法
- デザイン稿 / Figma エクスポートの使い方
- リポジトリとコンテキストでの画像サイズ問題

## 入力画像のシーン

| シーン | やり方 |
|---|---|
| UI の不具合 | スクリーンショット + 異常箇所の文字説明 |
| デザイン再現 | PNG エクスポート + ブレークポイントとコンポーネントライブラリを明記 |
| アーキテクチャのホワイトボード | 鮮明な写真またはエクスポート + 凡例 |
| エラーダイアログ | エラーテキスト全体を含める。一部だけ切らない |

詳細：[画像プロンプト](/prompts/prompting-with-images/)

## 画像が補うもの

画像の価値は、文字だけでは説明しにくい情報を直接示せる点にあります。たとえば：

- レイアウトがどう崩れているか
- ボタンがどこに押しつぶされているか
- ダイアログに何と書いてあるか

ただし画像だけでは Codex に次は自動では伝わりません。

- いちばん気にしている箇所
- どう直してほしいか
- これが「現状」か「目標」か

そのため、画像には通常、一文の説明を添えます。

## 品質要件

- **解像度**：文字が読めること。ぼやけたサムネイルは避ける
- **トリミング**：無関係なデスクトップ、通知バーの機微情報を除く
- **注釈**：矢印や丸囲みは可。ただし要点は文字でも書き直す
- **複数枚**：「現状 / 期待」をペアでアップロード

## よくある誤解

### 1. スクリーンショットを送れば、自動で問題を理解してくれる

スクリーンショットは視覚的証拠になりますが、次も補うとよいです。

- 問題の場所
- 目指す状態
- どれが現状で、どれが目標か

### 2. 大きいほど必ずしも良いわけではない

過大な原寸画像は次の 2 点を招きます。

- 無関係な情報が増える
- リポジトリやコンテキストが重くなる

### 3. デザイン図だけではまだ足りない

「図どおりに実装」なら、次も添えてください。

- ブレークポイント要件
- コンポーネント制約
- 自由にしてよい箇所と、してはいけない箇所

## リポジトリ内の画像

| 実践 | 理由 |
|---|---|
| `assets/` または `docs/images/` に統一 | 保守しやすい |
| WebP / 圧縮 | clone サイズを抑える |
| 意味のあるファイル名 | `image1.png` ではなく `login-form-mobile.png` |
| alt テキスト（ドキュメント内） | アクセシビリティ |

## そのまま使える書き方

次のように書けます。

```text
1 枚目は現在のページ、2 枚目は期待する見た目です。
ファーストビューの見出しエリアとボタン間隔を重点的に見てください。
スクリーンショットから業務ロジックを推測せず、見た目とレイアウトだけを扱ってください。
```

## プライバシーと安全

- スクリーンショットに顧客データ、内部 URL、token が含まれることがある。先にマスクする
- 秘密鍵のある設定画面を信頼できないタスクに送らない
- [機密コンテキスト](/guide/context/sensitive-context/)

## よくある失敗

- デザイン稿だけ渡してインタラクション説明がない
- 4K 原寸をそのまま commit する
- Figma リンクを読めると想定してエクスポートしない

良いスクリーンショットは「画像がある」だけでは足りません。画像・重点・期待の 3 つがはっきりしていると、タスクは成功しやすくなります。
