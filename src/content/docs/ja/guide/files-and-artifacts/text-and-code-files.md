開発タスクの大半は **テキストとコードファイル** に収まります：ソース、テスト、設定、Markdown。本ページでは、範囲を限定し、スタイルを揃え、安全にマージする方法を説明します。

Codex にテキストやコードファイルを直させるときの要点は、正しい場所を正しい方法で直し、ついでに余計な変更をしないことです。

## 本ページの内容

- 変更を正しいパスとエンコーディングに収める方法
- 複数ファイル編集の進め方
- formatter、linter との調整

## ファイルタイプと注意点

| タイプ | 注意 |
|---|---|
| ソース `.ts` `.py` など | `AGENTS.md` と既存パターンに従う |
| 設定 `.json` `.yaml` `.toml` | 構造を壊しやすい。有効な構文を要求する |
| ドキュメント `.md` | リンクは相対パス、日英混在の規約 |
| 生成コード | コミット対象か gitignore 対象かを明示する |

コンテキスト：[ファイルとディレクトリのコンテキスト](/ja/guide/context/file-and-folder-context/)

## なぜこのタイプが失敗しやすいか

実際に問題になりやすいのは次のような点です。

- 触るべきでないファイルを書き換える
- 少し直すつもりが、大きな範囲を書き直す
- プロジェクトの既存スタイルと合わない
- 設定ファイルの構文を静かに壊す

## 推奨プロンプト構造

```text
目標：<一文>
変更可：<パス glob>
禁止：lockfile の変更、無関係ディレクトリの変更
スタイル：<サンプルファイル> と一致
完了：変更ファイル一覧 + <テストコマンド> の実行
```

[良いタスクの構造](/ja/prompts/task-anatomy/) を参照。

## よくある誤解

### 1. 「このファイルを直して」と一言だけ

この程度の情報では足りないことが多いです。

次も補うとよいです。

- 変更してよいファイル
- 触らないファイル
- スタイルの参考
- 完了後の検証方法

### 2. 設定ファイルは普通のテキストと同じ

そうは見えません。

`.json`、`.yaml`、`.toml` では、構造・インデント・構文が壊れる問題がより多いです。

### 3. 広く直すほど楽

多くの場合、「小さく、説明しやすく、レビューしやすい」変更の方が、「広範囲のついで最適化」より安全です。

## エンコーディングと改行

- デフォルトは **UTF-8**。特殊エンコーディングのプロジェクトは `AGENTS.md` に明記する
- `.editorconfig` / `prettier` と揃え、ファイル全体の改行差分を避ける
- 大きなファイルは分割して変更：@ で関数を指定し、ファイル全体を書き直さない

## 変更が広がるのが心配なときの制限

心配なら、次の 3 点を直接要求してください。

1. 先に影響するファイルを説明する
2. いまのタスクに必要な最小範囲だけ変更する
3. 変更後の検証手順を列挙する

## レビューの要点

- [差分のレビュー](/ja/guide/quality/review-diffs/)：ロジック、範囲、削除
- [テストの実行](/ja/guide/quality/run-tests/)
- 意図せず `TODO` プレースホルダーだけ残していないか

## よくある失敗

- 「プロジェクト全体をリファクタリング」で数百ファイルが変わる
- バイナリや minified ファイルを無理にテキスト編集する
- ドキュメントリンクを絶対パスにしてサイト内 404 になる

テキストとコードファイルは、変更が多く散らばり、レビューも難しくなりやすいです。範囲・スタイル・検証方法を先に言っておくと、往復がかなり減ります。
