IDE では、Codex はプロンプトだけでなく、**エディターの状態**も自動で取得します。これが IDE の CLI に対する中核的な利点です。コンテキストの出所を理解すると、「ファイルは開いているのに見ていない」というもどかしさを減らせます。

IDE の Codex は、あなたが書いた内容だけでなく、エディターで今見ている内容も参照します。

## 本ページの内容

- IDE が自動で付与するコンテキスト
- @ ファイル、選択範囲、`AGENTS.md` との重ね合わせ
- ノイズを減らし、命中率を上げる方法

## コンテキストの出所（概念の層）

| 出所 | 誰が制御 | 典型的な内容 |
|---|---|---|
| ワークスペースのルート | 開いたフォルダ | プロジェクト構造、`AGENTS.md`、設定ファイル |
| 現在開いているファイル | エディターのタブ | 編集中のソース |
| 選択範囲 | ハイライトしたコード | 関数、エラー付近の断片 |
| 明示的な @ | 会話で @ したパス | ディレクトリをまたぐファイル、ドキュメント |
| プロジェクトルール | リポジトリ内の `AGENTS.md` など | コーディング規約、テストコマンド |

優先順位と衝突処理は [コンテキストの優先順位](/guide/context/context-priority/) を参照。

## 推奨ワークフロー

1. **ワークスペースのルートでリポジトリを開く**。サブフォルダだけを開かない（monorepo の例外はチームドキュメント参照）
2. 局所ロジックを直すときは、**関連コードを選択してから**タスクを説明 → [選択範囲と開いているファイル](/guide/ide/selected-code-and-open-files/)
3. モジュールをまたぐタスクは `@` で重要ファイルを指定し、「自分で探してくれる」と仮定しない
4. 長いセッションでは定期的に [コンテキストの圧縮](/guide/context/compaction/) するか、新しいスレッドを開く

## CLI との違い

| | IDE 拡張 | CLI |
|---|---|---|
| ファイル認識 | 強い（開いていればコンテキスト） | `--cwd` とツールによる読み取りが必要 |
| 選択範囲 | ネイティブ対応 | 貼り付けまたはパス指定が必要 |
| 向いている作業 | 行単位の修正、コードの説明 | スクリプト、CI、GUI のない環境 |

## よくある疑問

### 1. ファイルは開いているのに、思った通りに直してくれないのはなぜ？

「開いている」ことと「焦点が十分に明確」であることは別です。

タスクの範囲がまだ曖昧だと、別の関連箇所を見に行ったり、最も気になる断片を捉えられないことがあります。

### 2. 開いているファイルは多いほどよいか？

無関係なファイルを開きすぎると、コンテキストがうるさくなり、焦点が薄まります。

### 3. IDE が自動でコンテキストを持つから、説明は省略できるか？

自動コンテキストは助けになりますが、タスク説明の代わりにはなりません。  
タスクの目標、制約、完了基準は自分で明確に書く必要があります。

IDE のコンテキストは助けますが、推測はしません。ファイル範囲が正確なほど、結果は安定しやすくなります。

## 機密情報

鍵を含む `.env` をエディターの前面に長く開いたままにしない。[機密コンテキスト](/guide/context/sensitive-context/) を参照。

ログや顧客データは貼り付け前にマスキングしてください。IDE はコンプライアンスを自動判定しません。

## よくある間違い

- ワークスペースなしの単一ファイルモードで `AGENTS.md` を読めると期待する
- 無関係な大きなファイルを十数個開き、コンテキストウィンドウを圧迫する
- 「この関数」と口頭だけで、選択も @ もしない

## 受け入れチェックリスト

- [ ] ワークスペースのルートが正しい
- [ ] タスク関連の 1〜3 ファイルを開いているか @ している
- [ ] `AGENTS.md` のテストコマンドが IDE ターミナルと一致している
