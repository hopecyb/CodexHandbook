IDE 拡張のレビュー体験は「行内補完」と「完全な PR review」の中間にあります。変更はしばしばエディターまたはサイドの diff ビューに直接表示されます。本ページでは、結果を安全に受け入れる方法を説明します。

IDE で「そのまま受け入れられる変更」が見えても、「一括受け入れ」をデフォルトにしないでください。

## 本ページの内容

- IDE でよくあるレビュー UI の形
- 受け入れ、拒否、部分受け入れの方針
- Git、テスト、PR フローとの接続

## レビューフロー

1. **範囲を確認**：どのファイルが変わったか。依頼していない削除やフォーマットの嵐がないか
2. **ロジックを読む**：条件分岐、エラー処理、境界ケース
3. **セキュリティを確認**：鍵、インジェクション、権限昇格、依存の改ざん
4. **検証を実行**：プロジェクト合意のテスト / lint（IDE ターミナルまたはタスクスクリプト）
5. **判断**：受け入れ、修正を依頼、または取り消してタスクを再送

方法論：[diff のレビュー](/guide/quality/review-diffs/)

## IDE 特有の操作（概念）

| 操作 | 推奨 |
|---|---|
| Inline diff / ゴーストテキスト | ブロックごとに確認してから受け入れ。一括受け入れを避ける |
| 単一ファイルの受け入れ | リスクの小さいファイル（例：テスト）から |
| 拒否して再試行 | follow-up で「X だけ変更、Y は触らない」と明示 |
| Git 連携 | 受け入れ後も `git diff` で再確認してから commit |

デスクトップ App の [差分、コメント、レビュー](/guide/desktop-app/diffs-comments-and-review/) はより充実。IDE 側は**軽量で高頻度**のレビューが中心です。

## 推奨プロンプト習慣

タスク開始時に書き込む：

- 変更を許可するパスの glob
- 禁止：`git push`、lockfile の変更（明示要求時を除く）
- 完了時：変更概要を列挙し、**自動 commit しない**

[手動承認パターン](/cases/workflows/human-approval-patterns/) を参照。

## よくある間違い

- 緑のテストアイコンを信じ、自分では実行していない
- 大規模な自動フォーマット diff にロジック変更を紛れ込ませる
- 受け入れ後すぐ push し、PR / ブランチ保護を経由しない

## 受け入れチェックリスト

- [ ] `git status` が想定ファイルと一致
- [ ] テスト合格（ローカルまたは CI）
- [ ] `.env`、token、デバッグ用 `console.log` の残存なし
- [ ] コミットメッセージを自分で書いた、または確認した

## よくある疑問

### 1. 行内提案が小さく見えるから、そのまま受け入れてよいか？

その習慣は避けた方がよいです。

問題は「変更が大きい」ことだけではなく、「小さく見えるからちゃんと見なかった」ことにあります。

### 2. ロジックのレビューが苦手。まず何を見るとよいか？

次の 3 点だけでも十分な価値があります。

- 意図したファイルだけが変わっているか
- 消すべきでないものを削除していないか
- 明らかなデバッグ残りやスタイルのずれがないか

### 3. 受け入れたら完了か？

まだです。

受け入れは変更をワークスペースに入れただけで、その後の検証とコミット判断が残ります。

IDE の「変更を受け入れる」は中間アクションであり、最終検証ではありません。
