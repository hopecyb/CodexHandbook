「直して」と言うだけでなく、Codex にどのファイルを見るべきか、どれを見ないべきかも伝えてください。

問題が特定のディレクトリにあることは分かっていても、範囲を説明しないと、Codex は無関係なファイルまで引き込む可能性があります。

## なぜ範囲が重要か

範囲が大きすぎると、よくある問題が一緒に起きます。

- 無関係なファイルを大量に読む
- コンテキストが無関係な情報に占有される
- 似た別ファイルを対象と誤認する
- 変更範囲が想定を超える

ファイルとディレクトリのコンテキストの役割は、境界を示すことです。

## なぜファイル範囲を明確にするか

誰かをオフィスに案内して資料を探してもらう場面に似ています。

- 「探して」と言うと、半フロアを漁るかもしれない
- 「3 番目の棚の青いフォルダだけ見て」と言うと、はるかに効率的

Codex も同じです。範囲が明確だと、推測で補完する必要が減ります。

## 簡単な例

関連パスを明示します。

```text
src/components/Button.tsx とそのテストファイルだけ読んでください。リポジトリ全体はスキャンしないでください。
```

この一文は同時に次を示しています。

- どこを見るか
- どこを見ないか
- 範囲を自分で広げないこと

## よくある誤解

### 1. 関連ファイルは多いほど良い？

少ないと推測に頼り、多いと要点が薄まります。  
より適切なのは、**現在のタスクを完了するために本当に必要な部分だけ** を渡すことです。

### 2. 関連ファイルの場所が分からないときは？

まず範囲を絞ってもらうこともできますが、目的を明確にしてください。例：

```text
まずログインボタンのスタイルに関連するファイルを見つけてください。まだ変更はしないでください。
```

先に特定してから実行する方が、いきなり「リポジトリ全体を検索してついでに直す」より安定します。

### 3. 範囲を指定しなくても、自分で探す？

探すことはできますが、代わりに次が起きやすくなります。

- より多く読む
- 遅くなる
- 似たファイルも巻き込みやすい
- 想定外の場所を変更しやすい

### 4. ディレクトリとファイルの両方を言う必要がある？

必ずしもそうではありませんが、具体的にできるだけ具体的に。

- どのファイルか分かっている：ファイルを直接指定
- おおよその領域だけ分かる：まずディレクトリを指定
- まったく不明：まず特定と説明だけ依頼

## プロンプトに足すとよい 3 つのこと

変更が多すぎると心配なら、プロンプトに次の 3 点を直接足せます。

1. 見るべきファイルまたはディレクトリ
2. スキャンしない場所
3. 変更前に影響するファイルを説明すること

IDE では、現在のワークスペースルートが正しいか確認してください。

## そのまま使える書き方

次のような書き方をそのまま使えます。

```text
まず `src/pages/home/` と `src/components/Hero.tsx` だけ見てください。
`backend/` と `scripts/` はスキャンしないでください。
他のファイルが必要なら、なぜ必要か先に伝えてから続けてください。
```

Codex にファイル範囲を示すことは、推測、ノイズ、誤変更を減らすことです。
