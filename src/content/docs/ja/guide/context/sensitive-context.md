見られたり、コピーされたり、外部に送られたり、タスク記録に長期残ることを望まない内容は、まず機密情報として扱ってください。

## なぜ先に判断する必要があるか

多くのセキュリティ問題は、意図的な違反ではなく、「まず問題を解決しよう」と考えた瞬間に起きます。

たとえば：

- トラブルシュートのために `.env` 全体を貼り付ける
- 理解させるために顧客の生データをそのまま貼る
- 手間を省くために、実トークン入りのエラー原文をそのまま貼る

これらはその瞬間は便利に見えますが、後から修正するのが最も難しいことが多いです。

Codex に提供しないもの（練習でも本番でも）：

- API キー、パスワード、セッション Cookie
- 未脱敏の顧客データ、身分証番号など
- 内部未公開で、契約上外部共有が禁止されている資料

プレースホルダーを使います：`YOUR_API_KEY`。すでに漏洩した場合は、組織の手順に従って鍵をローテーションしてください。

## 迷ったときの判断方法

ある内容が機密に該当するか迷ったら、まず次の 2 つの問いを自分にしてください。

1. 無関係な人に見られたらリスクがあるか？
2. タスク記録に長期残ったら不安になるか？

どちらか一つでも「はい」なら、まず機密情報として扱ってください。

## 「たぶん大丈夫」と頼らない

ツール型 AI を初めて使う人は、無意識に次のように考えがちです。

- 「一時的に貼るだけ」
- 「見てもらうだけ」
- 「このファイルは本当に外に出ない」

しかし情報がタスクの流れに入った時点で、機密情報として扱うべきです。安全制御は事前に置く方がよいです。

## 見落とされやすい内容

パスワードと鍵以外にも、次はしばしば機密に該当します。

- 顧客リスト
- 携帯番号、メール、身分証番号
- 内部スクリーンショット、未公開の企画
- 実本番アドレスやアクセストークン入りの設定ファイル

つまり、機密情報は `sk-...` 形式の鍵だけではありません。

## どの程度脱敏すれば十分か

すべてを消す必要はなく、「問題解決に必要な最小限の情報」を残すことが重要です。

次の考え方で処理できます。

- 構造を残す
- 実値を置き換える
- 個人を特定できる情報を除く
- 現在の問題と無関係なフィールドを削除する

たとえば次は残せます。

- フィールド名
- エラーの種類
- 呼び出し順序

次は置き換えます。

- 実鍵
- 実メール
- 実携帯番号
- 実顧客名

## どうしても提供が必要なとき

より安全な方法：

- 実鍵を偽値やプレースホルダーに置き換える
- 実ユーザーデータを脱敏する
- 問題の切り分けに本当に必要なフィールドだけ残す
- 現象を説明できるなら、生の機密内容を丸ごと貼らない

例：

```text
実 API Key を YOUR_API_KEY に、実メールを user@example.com に置き換えてください。
```

## うっかり渡した場合

リスクレベルに応じて対処します。

1. まず拡散を止める
2. 鍵、パスワード、トークンを即座にローテーションする
3. 組織の手順に従って報告・是正する

問題解決時は、デフォルトで「切り分けに必要な最小限の情報」だけを渡してください。脱敏できるなら脱敏し、プレースホルダーにできるならプレースホルダーにしてください。
