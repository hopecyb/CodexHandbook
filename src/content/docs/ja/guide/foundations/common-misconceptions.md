Codex を最初からうまく使えない人の多くは、操作がわからないのではなく、最初から期待の置き方がずれています。

たとえば：

- 検索エンジンのように、質問すれば正解がそのまま返ってくるはずだと思う
- 外注の同僚のように、一度伝えれば細部まで全部考えてくれるはずだと思う
- モデルが強ければ、チェック、テスト、人的判断を省略できるはずだと思う

これらの誤解がすぐに失敗につながるとは限りませんが、数ラウンド使ううちに「不安定なのでは」と感じ始めやすいです。問題はしばしばモデルそのものではなく、最初から期待がずれていることにあります。

## まず理解を正す

Codex は手を動かせるが、道案内はあなたが必要な実行型アシスタントに近いです。

次のものではありません。

- 正しさを自動保証するブラックボックス
- コンテキスト不要の読心者
- 結果の責任を肩代わりしてくれる装置

伝え方が明確なほど安定し、細部をすべて推測に任せるほど失望しやすくなります。

| 誤解 | より実態に近い理解 |
|---|---|
| 「自動で正しくなる」 | 候補を生成する。検収はあなたの役割 |
| 「プロンプトは玄妙なほどよい」 | 明確な目標、制約、検収基準のほうが重要 |
| 「権限を全部与えたほうが速い」 | 権限を広げるほど事故の範囲も広がる |
| 「一つの長いセッションですべて片付く」 | 古いコンテキストが新しいタスクを汚染する |
| 「Cloud のほうが必ず安全」 | 安全は場所ではなく、ポリシー、鍵、レビュー次第 |
| 「ハンドブックに書いてあれば公式」 | OpenAI ドキュメントが基準。ハンドブックは学習用 |

## いちばん踏みやすい三つの落とし穴

### 「答えられる」と「完了できる」を混同する

もっともらしく説明しても、ファイルを正しく直した、検証を実行した、依存関係を整理したとは限りません。

返信の文章だけを見るのは不十分です。次も確認してください。

- 実際に何を変更したか
- 重要なステップを本当に実行したか
- 「検証すべき」部分まで済ませたか

### 「たくさんできる」と「一度にたくさんやるべき」を混同する

初心者に多いのは、一つのメッセージで調査、設計、実装、テスト、リリースまで任せる書き方です。

絶対にダメというわけではありませんが、コンテキストが混ざりやすくなります。「まず理解、次に変更、最後に検証」と分けたほうが安定します。

### 「時間を節約」と「判断を省略」を混同する

Codex の価値は、反復作業、情報整理、実行コストの削減にあります。常識的判断、リスク評価、最終検収を省略するためのものではありません。

## こう自分に問いかける

Codex を誤用していないか不安なら、次の三つを確認してください。

1. 曖昧な願いを投げるだけでなく、目標をはっきり伝えているか
2. 自分で判断してくれると決めつけず、境界を伝えているか
3. そのまま受け取るのではなく、結果を確認する準備があるか

この三つのどれか一つでも欠けると、問題が起きる確率は明らかに上がります。

Codex は強力ですが、明確な目標と境界の中でこそ力を発揮します。理解と判断を代わりにはしません。
