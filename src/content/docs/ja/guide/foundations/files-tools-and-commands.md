普通のチャットボットとの最大の違いは、**ツール** を通じて実際に作業することです。

ファイルは変更の対象、コマンドは動作の手段、ツールは手を動かすための入口です。

Codex は **ツール** を通じて現実世界に作用します。

- プロジェクトファイルの読み取り・書き込み
- ターミナルでのコマンド実行（権限とサンドボックスポリシーが許す場合）
- ウェブ検索、ブラウザ操作など（製品能力とポリシーによる）

## 三つの用語を分けて理解する

| 用語 | 意味 |
|---|---|
| ファイル | プロジェクト内の実体。コード、ドキュメント、設定など |
| コマンド | ターミナルで実行する一歩の動作。ビルド、テスト、検索など |
| ツール | Codex がファイル読み取り、変更、コマンド実行、ウェブ検索に使う能力の入口 |

別の見方もできます。

- **ファイル** は材料
- **コマンド** は動作
- **ツール** は材料を扱い動作を行う器具

## よくある作業の流れ

タスクを渡すと、Codex はだいたい次のことを行います。

1. 関連ファイルをいくつか読み、プロジェクト構造を把握する
2. 必要に応じてテキスト検索、ディレクトリの確認、設定の参照を行う
3. 結果を検証する必要があれば、テストやビルドなどのコマンドを実行する
4. ファイルを変更したうえで、差分をあなたに確認してもらう

「ファイルを読みたい」「コマンドを実行したい」と出てきたら、多くの場合タスクに必要な正常なステップです。

## よくある誤解

### 1. コマンドを実行できるなら、何でもできるのでは？

必ずしもそうではありません。

できるかどうかは次にも依存します。

- 現在の製品入口でどのツールが使えるか
- サンドボックスが許可しているか
- このステップに承認が必要か
- チームポリシーに追加制限があるか

### 2. コマンドは少なく、直接ファイルを直したほうが速いのでは？

必ずしもそうではありません。

チェック用のコマンドを走らせたほうが、問題に早く気づけることもあります。コード変更後にテストを実行するほうが、後から壊れに気づくより安定します。

### 3. コマンドがわからない場合は？

いったん理解できなくても、次のように聞けます。

```text
このコマンドは何をしますか？何を変更しますか？実行しなければどうなりますか？
```

## 簡単な判断法

Codex がファイルの読み取り、変更、コマンド実行をしようとしたら、次の三問で判断してください。

1. このステップは自分の目標に関係があるか？
2. 影響範囲は想定どおりのディレクトリやファイルか？
3. 失敗した場合、簡単に取り消せるか？

三問のどれか一つでも答えられなければ、先に説明を求めてください。

## 利用の原則

1. **必要最小限の範囲**：ディレクトリとファイルを指定し、「リポジトリ全体を適当に変更」は避ける
2. **危険なコマンドは承認が必要**：削除、プッシュ、システム設定の変更など
3. **ツール選択には方針がある**：[ツール選択](/guide/tools/tool-selection/) を参照

製品入口によってツールパネルと確認方法は異なります。詳細は各製品ガイドを参照してください。

Codex は「言う」だけではなく、ファイル、コマンド、ツールを通じて実際に手を動かします。だから範囲とリスクを常に見ておく必要があります。
