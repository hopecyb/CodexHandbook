**Plugin** と **MCP サーバー**は Codex を外部システム（チケット、DB、内部 API）に接続します。能力が強いほど、[脅威モデル](/guide/team-enterprise/security/threat-model/) の漏洩と越権面も大きくなります。[MCP 概要](/skills/mcp/mcp-overview/)、[Plugins 概要](/skills/plugins/plugins-overview/) と併読。

初見では定義を急がず、一点を押さえてください：Codex を外部システムに繋ぐと、能力とリスクが同時に増えます。

名前が Plugin でも MCP でも、核心問いは同じ：

- 何を読めるか
- 何を変えられるか
- 誰が承認するか
- 事故時にどう追跡するか

## 内容

- 拡張のリスク分類
- 承認リストとバージョン固定
- デバッグとインシデント時の隔離

## リスク分類

| 種類 | 例 | 制御 |
|---|---|---|
| データ読取 | MCP が顧客 DB を読む | 読み取り専用アカウント、行レベル権限 |
| データ書込 | チケット自動クローズ、設定変更 | 人工承認、二重確認 |
| ネットワーク | 任意外向き通信 | 出口 allowlist |
| 資格情報 | OAuth token のディスク保存 | 秘密管理、短期 token |
| サプライチェーン | 第三者 server 更新への混入 | バージョン固定、hash ロック |

## チーム承認フロー（推奨）

```text
申請（用途、データ分類、権限）→ セキュリティ/アーキテクチャ review
    → 「承認リスト」リポジトリまたは内部ディレクトリへ
    → バージョン固定 + 責任者
    → 四半期再審または major 更新時に再審
```

個人実験 MCP は本番リポジトリと**同一 token を使わない**。

## 最小実践

1. **デフォルト拒否**：リスト外リモート MCP はインストールしない
2. **ローカル MCP** も全ディスク読取可能——専用 OS ユーザーまたはコンテナ
3. **ログ**：tool 名とパラメータ要約（脱敏）。[Hook 監査](/skills/hooks/hooks-examples/) を参照
4. **Skill と MCP 分担**：Skill は手順、MCP は外部接続——権限は和集合、最も厳しい方針を採用

## よくあるミス

- 「公式マーケット」＝「セキュリティ審査済み」
- 開発と本番で同一 MCP OAuth アプリ
- デバッグで `DEBUG=*` を開き token を CI ログに出力

## よくある誤解

### 1. Plugin と MCP がまだ分からないが問題ある？

第一段階では大きな問題ではありません。共通点は Codex が外部システムに触れるため、権限とリスクを考える必要があることです。

### 2. なぜ「読み取り専用優先」を強調する？

読み取り専用は通常：

- 試行が容易
- 価値発見が容易
- 失敗コストが低い

### 3. 入れたらすぐ安心できる？

便利に見えても：

- どのデータにアクセスするか
- システムへ書き戻すか
- 資格情報をどう管理するか

外部拡張は、機能の強さより先に権限と境界を見る。
