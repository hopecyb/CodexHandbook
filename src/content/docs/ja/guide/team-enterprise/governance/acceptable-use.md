**acceptable use 政策（AUP）**は「Codex でこれをやっていいか」を組織合意として書き、個人判断だけに頼らないものです。[脅威モデル](/guide/team-enterprise/security/threat-model/) と補完：脅威モデルはリスク、AUP は**行動境界**です。

## 内容

- AUP がカバーすべき論点
- HR/コンプライアンス、技術制御との接続
- 条項例の起案（法務ローカライズ必須）

## AUP が管理すること

技術的に可能でも、チーム内で許可するかを答えます。

技術方針の代替ではなく、組織境界を読みやすく実行可能なルールにします。

:::caution
以下は**教育用提纲**。法的助言ではありません。正式公開前に法務とコンプライアンスレビュー必須。
:::

## よくある誤解

### AUP は現場利用者にも直結する

形式文書と思われがちですが、日常で触れる問いは：

- どのデータを Codex に渡せないか
- どのシーンで人の复核が必須か
- どの拡張と外部接続を安易に使えないか

法務文書であると同時に、実際の利用境界です。

### 政策を書いた＝チームが従う

「本番変更は承認必須」と書いても、ツールがデフォルトで迂回できるなら政策はすぐ無効化されます。

AUP は研修、権限、設定、監査と対応させることが重要。網羅性だけでは不十分です。

## カバーすべき論点

| 論点 | 要点 |
|---|---|
| 許可用途 | 開発、文書、調査、内部自動化 |
| 禁止用途 | 未承認アクセス、嫌がらせコンテンツ、セキュリティ制御回避 |
| データ分類 | どの repo/データが使えるか。顧客 PII ルール |
| 出力責任 | 人が review 後マージ。出力を対外の法律/医療助言としない |
| 拡張 | 承認リスト内 Plugin/MCP のみ |
| アカウント | 個人シート共有禁止。退職時回収 |
| incident | 不審行為の報告経路 |

## 基本構造

1. **目的と範囲**
2. **許可シーン**（[能力マップ](/guide/start-here/codex-capability-map/) へリンク）
3. **禁止シーン**
4. **データと機密**
5. **人間監督要求**（マージ、本番変更）
6. **違反時の措置**（既存社員ハンドブック参照）
7. **連絡先と更新日**

## 技術制御との整合

| AUP 条項 | 技術実装 |
|---|---|
| ソース exfiltration 禁止 | ネットワーク方針、MCP 承認 |
| 本番変更は承認必須 | ブランチ保護、`git push` deny |
| 承認モデルのみ使用 | 組織マネージド設定 |

## よくあるミス

- AUP 作成後に研修なし
- 技術 reality と乖離（政策禁止だがツール許可）
- 多年未更新。新機能（Computer Use 等）と乖離

## 有効な AUP の判断

1. チームが実際に直面する利用境界に答えているか
2. 研修、設定、承認フローに落ちるか
3. 違反時に発見・対応方法が分かるか

三つとも「はい」寄りなら、より実効性が高いです。

## 受け入れチェックリスト

- [ ] onboarding に AUP 確認を含む
- [ ] [チームルール](/guide/customization/rules/team-rules/) と矛盾なし
- [ ] 年次または重大機能リリース時に再審

AUP の価値は、Codex 利用境界を明確にし、実際の制御手段と対応させることです。
