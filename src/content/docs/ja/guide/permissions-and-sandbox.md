Codex を安全に使うには、2 つの制御を同時に確認します。**サンドボックスは技術的に到達できる範囲を決め、承認ポリシーは現在の境界を越える前にユーザーへ確認するかを決めます。**

![Codex のサンドボックスと承認フロー：動作はサンドボックス境界で判断され、越境時に人の承認を求め、最後に検証証拠を残す](/diagrams/sandbox-approval-flow-ja.svg)

## 最初に区別すること

| 制御 | 答える質問 | 代表的な対象 |
|---|---|---|
| サンドボックス | この動作は最大でどこまで到達できるか？ | プロジェクトファイル、外部パス、システム機能、ネットワーク |
| 承認ポリシー | 現在の境界を越える前に人へ確認するか？ | 依存関係のインストール、ネットワーク、外部ディレクトリへの書き込み、アプリ起動 |
| タスク制約 | 今回何を行い、何を行わないか？ | 変更可能なディレクトリ、禁止操作、検証コマンド |
| 人によるレビュー | 実行済みの結果を受け入れられるか？ | diff、ログ、テスト、外部への副作用 |

タスク制約はサンドボックスの代わりにならず、サンドボックスも最終レビューの代わりにはなりません。それぞれ意図、実行境界、結果の受け入れを担当します。

## 1 つの動作が安全境界を通る流れ

Codex がコマンド実行やツール呼び出しを準備するときは、次の順序で考えます。

1. 動作が現在のサンドボックスで許可されているか判断する。
2. 範囲内なら実行して出力を記録する。確認画面が出るとは限らない。
3. 範囲外なら、承認ポリシーに従って許可を求めるか、直接拒否される。
4. ユーザーは拒否、範囲の縮小、または明示された 1 回の操作だけを承認できる。
5. 実行後も diff、テスト、外部システムの状態を確認し、タスク目標を満たすか検証する。

サンドボックスは Codex が起動した子プロセスやコマンドにも適用されます。スクリプト内の動作だから境界を回避できるとは考えないでください。

## ローカル実行と Cloud では境界が異なる

| 環境 | 主な隔離方式 | ネットワークの要点 | 確認事項 |
|---|---|---|---|
| App / CLI / IDE のローカルタスク | OS レベルのサンドボックスと現在の承認ポリシー | 通常、外部ネットワークへの依存を前提にしない。必要なら明示的に承認または設定 | ワークスペース範囲、コマンド、外部パス、接続目的 |
| Cloud タスク | OpenAI が管理する隔離コンテナ | セットアップ段階は環境設定に従って接続可能。Agent 段階は明示的に有効化しない限り既定で無効 | リポジトリ、環境設定、許可ドメイン、返された diff と検証証拠 |

Cloud 環境の Secrets はセットアップ段階だけで使用され、Agent 段階が始まる前に削除されます。最小権限を維持し、無関係な本番認証情報をタスク環境へ入れないでください。

## 承認要求を 4 段階で判断する

### 1. タスクと照合する

この手順は現在の目標に本当に必要ですか。「役に立つかもしれない」だけでは承認理由になりません。

### 2. 範囲と照合する

対象は現在のプロジェクト、外部ディレクトリ、ネットワーク、システムアプリのどれですか。パス、ドメイン、コマンドが具体的ほど判断しやすくなります。

### 3. 副作用と照合する

読み取りだけか、ファイル書き込み、ソフトウェア導入、データ送信、リモート状態の変更を伴うかを確認します。外部への副作用は、元に戻せるローカル変更より慎重に扱います。

### 4. 検証と復旧を確認する

成功をどう確認し、失敗時にどう戻しますか。答えがなければ、先に Codex へ説明またはより小さな代替案を求めます。

## 具体例：依存関係のインストール

Codex が次の実行を求めたとします。

```bash
pnpm install
```

見慣れたコマンドかどうかだけで判断せず、次を確認します。

- 現在のタスクで不足した依存関係が本当に必要か
- 正しいリポジトリディレクトリで実行するか
- どのパッケージレジストリへ接続するか
- ロックファイルを変更するか
- インストール後に実行するテストまたはビルドは何か

既存コードの検証だけで依存関係がすでに導入済みなら、拒否して現在の環境を先に使うよう求められます。

## プロンプトで境界を宣言する

実行可能な範囲をタスクに直接記述できます。

```text
src/auth と tests/auth だけを変更してください。
導入済みの依存関係を先に使い、ネットワーク接続やバージョン更新は行わないでください。
プロジェクト外のパスやネットワークが必要なら、目的、対象、最小操作を先に説明してください。
完了後に pnpm test --filter auth を実行し、出力と残存リスクを報告してください。
```

この記述で意図は明確になりますが、実際の実行制限はサンドボックス、承認ポリシー、チームの管理設定が担当します。

## よくある誤解

- **承認画面が出た操作は必ず危険**：通常のインストール、ネットワーク、プロジェクト外への書き込みでも出ます。必要性と範囲で判断します。
- **画面が出なければ完全に安全**：動作がサンドボックス内にあるだけかもしれません。実際の変更は引き続きレビューします。
- **1 回の承認で永久に許可される**：期間と範囲は製品とポリシーによります。要求内容を確認します。
- **子 Agent は別の権限を持つ**：子 Agent は主タスクのサンドボックスと権限モードを継承し、自然に高い権限を得ることはありません。
- **Hooks はサンドボックスの代わりになる**：Hook は追加のガードと監査レイヤーであり、OS による強制隔離の代替ではありません。
