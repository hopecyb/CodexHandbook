初めて Codex の入口を選ぶとき、何十項目もの機能を比較する必要はありません。まず、**今回の作業は主にどこで行うか**を考えてください。

![Codex クライアント選択図：作業場所からデスクトップ App、CLI、IDE 統合、Cloud を選ぶ](/diagrams/codex-client-selection-ja.svg)

## 30 秒で選ぶ

| 主な作業場所 | 第一候補 | 最適な操作方法 |
|---|---|---|
| ローカルの複数プロジェクトや並列タスク | **デスクトップ App** | タスク確認、diff レビュー、承認、長時間作業の管理 |
| ターミナル、スクリプト、既存のコマンドラインフロー | **CLI** | タスクの指示、コマンド実行、スクリプトと自動化の組み合わせ |
| VS Code、互換エディタ、Xcode、JetBrains | **IDE 統合** | エディタのコンテキストを含む質問、その場での変更とレビュー |
| 接続済みのリモートリポジトリと隔離環境 | **Cloud** | クラウドへのタスク委任、並列処理、後からの結果レビュー |

特に希望がなければ、**デスクトップ App** が最も直感的な開始点です。ターミナルや VS Code を日常的に使っているなら、慣れた作業面に留まる方が切り替えコストを抑えられます。

## 4 つの入口が解決する問題

### デスクトップ App：ローカル作業のコントロールセンター

デスクトップ App は、タスクの状態、ファイル変更、承認プロセスを明確に確認したい作業に適しています。特に次の用途に向いています。

- 複数のタスクやプロジェクトを同時に追跡する
- worktree で並列変更を分離する
- diff をレビューしてから追加質問や修正を行う
- ローカルプロジェクトで継続的に実行する作業を管理する

例：1 つのタスクでログインの回帰を修正し、別のタスクではパフォーマンスのボトルネックを読み取り専用で分析し、それぞれの結果を個別にレビューします。

### CLI：Codex をターミナルフローに組み込む

CLI は、すでにコマンドラインでプロジェクトを管理している人に適しています。テストコマンド、Git、スクリプトに近く、同じ操作をチーム文書へ記録しやすい点が利点です。

```bash
codex
```

例：リポジトリのルートで Codex を起動し、失敗するテストの実行、根本原因の特定、最小修正、同じテストコマンドによる再検証を順に依頼します。

### IDE 統合：現在のコードを中心に作業する

IDE 統合は、問題が「今見ているファイル、選択範囲、diff」と強く結び付く場合に適しています。現在の対応方法は 2 種類です。VS Code、Cursor、Windsurf などの互換エディタでは Codex 拡張を使い、Xcode と JetBrains IDE ではそれぞれ専用の Codex 統合入口を使います。

例：理解しにくい関数を選択し、入出力と例外経路を Codex に説明させてから、境界条件のテストを追加するよう依頼します。

### Cloud：隔離されたリモート環境へ委任する

Cloud は、リモートリポジトリが接続済みで、タスクをローカルマシンから切り離して実行したい場合に適しています。クラウドタスクは隔離環境で実行されるため、並列探索、長時間タスク、完了後の集中レビューに向いています。

例：互いに独立した 3 つのリポジトリ課題を別々のクラウドタスクへ委任し、変更と検証証拠が返ったら 1 件ずつレビューします。

## 4 つから 1 つだけを選ぶ必要はない

同じワークフローを複数の入口で引き継げます。

1. IDE で現在のファイルに関する問題を明確にする。
2. 長い探索が必要な作業をデスクトップ App または Cloud に委任する。
3. CLI でチーム標準のチェックコマンドを実行する。
4. デスクトップ App またはコードレビュー画面で最終 diff を確認する。

「どれが最も強いか」ではなく、**どれが現在のコンテキストに近く、結果を最も確認しやすいか**で選びます。

## よくある 2 つの場面

### 場面 1：実際のプロジェクトで初めて bug を修正する

まずデスクトップ App を使います。タスク会話、変更、権限要求を同時に確認できます。完全な閉ループを 1 回経験してから、CLI や IDE を試してください。

### 場面 2：チームに固定コマンドと CI 規約がある

CLI を優先し、インストール、テスト、フォーマットのコマンドを `AGENTS.md` に記録します。これにより Codex は毎回同じプロジェクトルールに従えます。

## 選択後すぐに検証する

クライアントが「起動する」だけでは不十分です。練習用リポジトリで次の閉ループを完了してください。

1. Codex にファイルを読み取って説明させる。
2. 元に戻せる小さな変更を依頼する。
3. 最終回答だけでなく diff を確認する。
4. 検証コマンドを実行する。
5. 権限要求を拒否または縮小する方法を理解しているか確認する。

完全な比較は [機能比較](/ja/guide/reference/feature-comparison/) を、安全境界は [権限とサンドボックス](/ja/guide/permissions-and-sandbox/) を参照してください。
