CI は**プロセス終了コード**でステップの成否を判断します。本章は [codex exec](/guide/developer-platform/non-interactive/codex-exec/) の一般的な意味、再試行方針、冪等設計を説明します。

## 本ページの内容

- 終了コードと業務上の「レビュー不合格」の区別
- 429/ネットワーク系エラーを再試行するか
- 重複実行による副作用の回避

## 終了コードが伝えること

「終了コード」は：タスク終了後、プログラムがスクリプトと CI に残す短い結果です。

通常は詳しく説明せず：

- 今回は成功
- それとも失敗

「再試行」は別の問い：今回の失敗は即停止すべきか、もう一度試す価値があるか。

:::note
具体終了コード表は公式 CLI ドキュメントを基準に。下表は統合時の**設計原則**です。
:::

## よくある誤解

### 失敗は一種類ではない

非 `0` をすべて同じ失敗と見がちですが、少なくとも分ける：

- タスク自体のクラッシュ
- 方針やサンドボックスによる遮断
- 外部サービスの一時障害
- 実行は成功したがレビュー結論が「不合格」

扱いは異なり、すべて再試行対象ではありません。

### 「自動再試行」＝より安定ではない

権限不足、ルール遮断、prompt 問題など、再試行しても消えない失敗に再試行すると、時間とクォータを浪費します。

## 推奨意味（概念）

| 状況 | 推奨処理 |
|---|---|
| `0` | タスク完了かつ prompt の成功基準を満たす |
| 非 `0` かつログに policy/sandbox 拒否 | **盲目的に再試行しない**。設定または prompt を修正 |
| 非 `0` かつ API 429/5xx | 限回数の指数バックオフ再試行 |
| P0 問題を発見したが実行は成功 | [構造化出力](/guide/developer-platform/non-interactive/structured-output/) の `pass: false` + スクリプトで `exit 1` |

「セキュリティ問題を発見」はクラッシュ例外に頼らず、JSON で**明示的に** `pass: false` とし、ラッパースクリプトが終了コードを決める。

## 再試行テンプレート（bash）

```bash
max=3
delay=10
for i in $(seq 1 $max); do
  if codex exec --cwd . "$(cat "$PROMPT")"; then
    exit 0
  fi
  code=$?
  if [ "$code" -eq 2 ]; then
    echo "Policy error, not retrying" >&2
    exit "$code"
  fi
  sleep $((delay * i))
done
exit 1
```

「再試行不可」コードは公式ドキュメントと整合後、`case` 分岐に書き込む。

## 冪等と副作用

| リスク | 緩和 |
|---|---|
| PR コメント重複 | check run id または「既存 bot コメントがあれば更新」 |
| ファイル重複書き込み | exec はデフォルト読み取り専用レビュー。書き込みは別 job + 人工ゲート |
| 通知重複 | 通知 webhook に dedupe key |

## 迷ったときの判断

1. 一時的な外部障害のように見えるか
2. 再実行で重複コメント、重複書き込み、重複通知が起きるか
3. 失敗原因は人が設定、prompt、権限を直すべき類か

1 に近ければ限回数再試行。2・3 に近ければ根因対応で止める。

## よくあるミス

- 終了コード無視で CI が常に green
- 方針エラーを無限再試行しクォータ消費
- 再試行時に prompt/git sha 未固定で結果が比較不能

先に「一時障害か、再試行しても直らないか」を分ける。すべての失敗が再実行の価値があるわけではありません。

## 受け入れチェックリスト

- [ ] CI が非ゼロ終了コードで失敗
- [ ] 再試行回数とバックオフに上限
- [ ] レビュー「不合格」と「実行クラッシュ」を区別できる
- [ ] ログに十分な障害情報を保持
