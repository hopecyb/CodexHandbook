自動化を初めて組むと、Codex に「それらしい文章」を出させる前提にしがちです。人が読むには足りますが、スクリプトには不向きです。

構造化出力が解くことは単純です：Codex に規定フォーマットで返させること。

非対話タスクが自由文だけだと、下流は「通過か失敗か」「何件見つかったか」「深刻度は何か」を自動判断しにくいです。構造化出力は結果を機械処理向きにします。

## 本ページの内容

- いつ JSON / Markdown 表 / 固定フィールドを要求するか
- Prompt で schema をどう定義するか
- 解析失敗時のフォールバック

## よくある誤解

### 構造化出力は次のステップが受け取るため

JSON、schema は工程上のこだわりではなく、次がスクリプトで成否判定、ボットがコメント、ダッシュボード表示するなら安定フォーマットが必要だからです。

### 形式が安定＝結論が正確

構造化出力は「要求した形に見える」ことを保証するだけで、タスク理解の正しさは自動保証しません。出力インターフェースの問題を解き、タスク定義と結果検証の代替ではありません。

## 単純な区別

- 自由文：人向け
- 構造化出力：プログラム向け

次が `jq`、スクリプト、ダッシュボード、ゲートルール、自動コメントボットなら、毎回自由な自然言語だけに頼らない。

## 最小実用手順

Prompt 末尾にフォーマット要求を固定：

```text
…（タスク本文）…

出力要求：
- JSON オブジェクトのみ出力。markdown コードフェンスは不要
- フィールド：{"pass": boolean, "findings": [{"severity":"P0|P1|P2", "file":"", "message":""}]}
- 問題なしなら findings は空配列
```

Shell 解析（示意）：

```bash
result=$(codex exec --cwd . "$(cat prompts/structured-review.md)")
echo "$result" | jq -e '.pass == true'
```

## よくある落とし穴

### 1. 「JSON を出力」とだけ言い「JSON だけ」と言わない

モデルが先に説明し、その後 JSON——解析が壊れます。

### 2. 今日と明日でフィールド名が違う

スクリプトがフィールドに依存するなら、schema はインターフェースとして保守。

### 3. 構造化出力で曖昧問題を全部解決できると思う

解くのは「形式の安定」。タスク定義が曖昧なら、JSON も安定して曖昧な結果を返します。

## 推奨ワークフロー

```text
schema 定義（バージョン v1）
    → prompt が schema ファイルを参照 @schemas/review-output.json
    → exec 実行
    → jq / カスタム validator で検証
    → 不合格なら exit 1
```

大きな出力はファイルパスフィールドを要求し、Agent が `artifacts/` に書き、CI が artifact をアップロード。

## 判断方法

出力を「次のプログラム」が消費するなら構造化を。人が読んで議論するなら自由文で自然。

結果をプログラムに渡し続ける限り、約束したフィールドで安定返却させるべきです。

## SDK との比較

| | CLI + JSON prompt | SDK |
|---|---|---|
| 統合コスト | 低 | 中 |
| 型安全 | 約束 + 検証 | SDK 型を利用可 |
| 向く用途 | CI スクリプト | マルチテナントサービス |

[SDK 概要](/guide/developer-platform/sdk-overview/) を参照。

## よくあるミス

- モデル出力に説明文が混ざり JSON 解析失敗——prompt で「JSON のみ」を強調
- Schema 変更でバージョン未更新。旧 CI が誤解析
- 秘密鍵を JSON フィールドでログに返す
- 解析失敗時の明確な終了挙動が未設計

## 受け入れチェックリスト

- [ ] schema ファイルまたはフィールド文書がある
- [ ] CI が解析失敗を明示的に失敗扱い
- [ ] サンプル出力が `fixtures/` に回帰用保存
- [ ] [終了コード](/guide/developer-platform/non-interactive/exit-codes-and-retries/) 方針と一致
