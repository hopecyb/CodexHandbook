一組の資料から記事を書き、編集可能なプレゼンテーションにして、次回も使えるタスク指示を保存する。各段階でファイルが残るので、それを使って完了を判断できる。

Codex でローカルフォルダーを開ける必要がある。スライドを作るには PPTX を生成できるツールと、それを開けるプレゼンテーションソフトも必要。具体的な環境は事例を参照し、すべてのクライアントに同じツールを要求しない。ファイル操作に慣れていない場合は、先に[ファイルを扱う](/ja/guide/learning-paths/beginner/02-work-with-files/)を終える。

## ルートと資料

| 段階 | 前提となる入力 | この段階の成果物 | 次の段階 |
|---|---|---|---|
| 1. 根拠を整理する | 3つの合成資料と出典索引 | 事実表、矛盾と不足の一覧 | 記事を書く |
| 2. 執筆と修正 | 事実表、読者、構成案 | 記事、主張対応表、修正記録 | スライドを作る |
| 3. スライドを作る | 記事、主張対応表、発表の目的 | 8枚の PPTX、8枚のプレビュー、ノートと確認記録 | 再利用手順を保存する |
| 4. 再利用手順を保存する | 前3段階の成果と経験 | タスクのテンプレート、受け入れ表、1回の転用記録 | 新しい資料でも試す |

[記事演習パッケージをダウンロード](/downloads/source-backed-article/source-backed-article-1.0.0.zip) · [スライド演習パッケージをダウンロード](/downloads/article-to-slides/article-to-slides-1.0.0.zip)

どちらのパッケージも単独で使える。連続して学ぶ場合、段階3ではできるだけ自分が完成させた記事を使う。スライドパッケージの `input/` は記事が未完成の場合や比較用の参考入力。製品、人物、インタビューはすべて合成した教材である。

## 1. 根拠を整理し、矛盾を残す

記事パッケージを展開し、`brief.md`、`sources/index.csv`、そこに記された3つの資料を読む。[記事事例の最初の段階](/ja/cases/write-an-article/#1-まず事実と矛盾を整理する)に沿って整理し、すぐに本文を書き始めない。

出力は記事パッケージの `my-output/` に置き、元資料を残す。事実表には資料 ID、節、裏づけられる主張、証拠の種類を書く。資料だけでは解決できない問題は `unresolved.md` に列挙する。

P3 と C2 の診断のデフォルト設定に関する矛盾を見つけ、どちらか一方を勝手に最終回答にしなければ完了。合成インタビューは合成であると明記し、資料にない精度や時間短縮の数値を作らない。

資料が開けない、または番号が合わない場合は、まずファイルと索引を復元する。ファイル名から内容を推測しない。確認できたら次へ進む。

## 2. 記事を書き、出典に照らして修正する

前段階の事実表と未解決一覧を使う。[記事事例](/ja/cases/write-an-article/)に沿い、読者を決めて構成案を作り、定めた範囲で続けて執筆した後、事実と表現を修正する。

`article.md`、`claim-map.csv`、`unresolved.md` と修正記録を提出する。事実の修正を最低1件、表現の修正を最低1件示す。参考パッケージには意図して作った初稿と実際のテキスト diff があるが、設計された反例をモデルの実際の失敗と呼んではいけない。

重要な事実の出典を特定でき、筆者の提案と資料に裏づけられた事実を分け、診断上の矛盾が残っていれば完了。Python が使えるなら事例の構造チェックを実行できる。合格しても一文ずつ出典が結論を支えるか判断する。

これらを次の入力として残す。記事は参考稿と異なってよいが、重要な制約を落としてはいけない。

## 3. 記事を8枚のスライドにする

完成した記事と事実表を用いる。[スライド事例](/ja/cases/create-a-slide-deck/)に沿って読者、約5分の目的、8枚の流れを決める。まず表紙と制限事項のページでレイアウトを確かめ、残りを作る。

記事と事実表をスライド作業の入力ディレクトリにコピーし、自分の版だと明記する。自分の記事を引用しながら参考稿の結論をすべて無条件に引き継がない。

8枚の PPTX、8枚のプレビュー、各ページの説明、検証記録を提出する。記録したプレゼンテーションソフトで開け、重要な文字を編集でき、各ページの中国語表示とテキスト枠からのはみ出しを確認したことが完了条件。短くまとめても資料の矛盾は明確に残す。

PPTX ツールがなければ構成案を保存し、不足する機能を記録する。この段階は未完了とし、ツールのある環境で続ける。完了後、再利用へ進む。

## 4. 次回再利用できるタスク指示を保存する

確認済みの記事とスライドから始める。次のテンプレートに沿って、実際に使った方法を `workflow.md` に書く。最後の「続けて」という指示だけを保存しない。

```md
# 資料から発表へ

## 今回のタスク
- 読者と目的：
- 入力ディレクトリ、出典索引、変更禁止の元ファイル：
- 出力ディレクトリと必要な形式：

## 順序
1. 本文の前に事実、推論、矛盾、不足を列挙する。
2. 読者と構造を決め、続けて執筆し、出典と照らして修正する。
3. 記事を8枚に圧縮し、表紙と制限事項を先に確認する。
4. ネイティブテキスト、中国語フォント、全プレビュー、ノートを確認する。

## 受け入れ
- 重要な事実は元資料にたどれ、未解決事項が見える。
- 筆者の提案と製品の事実を区別し、合成資料を実際の証言に見せない。
- PPTX は開いて編集できる。各ページを確認し、ソフトとフォント環境を記録する。
- 実施した確認と未実施の確認を明記し、提出先はローカルにとどめる。

## 今回の経験
- 実際の問題、変更点、復元を確認した方法：
- 次回も使える手順：
- 次回あらためて確認すべき事実と環境：
```

次に小さな転用を行う。読者を「初めて試す個人の著者」から「資料のレビューを準備する同僚」に変え、同じ出典のまま構成案だけを作り直す。`reuse-check.md` に題名、重点、順序の変化と、変わらない事実上の制約を書く。これはテンプレートの適応を確認する演習であり、新たな事実調査の完了を意味しない。

他の人が `workflow.md` から入力・出力と完了基準を探せ、転用記録に具体的な差分があり、元の読者向けの記事をそのまま書き続けていなければ完了。順序が安定したら[ワークフローを Skill にする](/ja/cases/workflows/turn-a-workflow-into-a-skill/)を読む。[執筆 Skill の例](/ja/skills/examples/writing-skill/)には文体例、事実表、矛盾への対処を再利用できる完全なパッケージがある。構造チェックは人による事実確認の代わりにはならない。

## 任意：数値が明確なタスクから始める

オフィス分析に関心が強ければ、先に[売上週報](/ja/cases/analyze-a-spreadsheet/)を行う。CSV、返金と重複行、参考集計、独立した確認スクリプトを含む。終了後、「重要な数値を独立して計算し、異常の基準を明記する」を自分の受け入れ表に追加できる。架空の製品記事に無理に混ぜる必要はない。

パス全体を終えたら、元資料、記事と事実表、編集可能なスライド、検証記録、再利用手順が残る。リンクを読むだけ、あるいは参考解答をダウンロードするだけでは完了しない。
