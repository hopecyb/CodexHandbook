「環境変数」は二極端に誤解されがちです：底层すぎる、またはすべての設定を入れる万能箱。単純に言えば、実行時にプログラムへ値を渡す方法で、秘密情報とスイッチに特に向きます。

環境変数は**秘密鍵注入、スイッチ上書き、CI 適合**によく使われ、機密値を設定ファイルや Git に書かないための手段です。本ページは概念索引。具体変数名は [公式ドキュメント](https://developers.openai.com/codex) と `codex --help` を基準にしてください。

## 本ページの内容

- config ファイルではなく環境変数にすべきもの
- ユーザー級、プロジェクト級、Cloud Secrets、CI の分担
- よくある命名と漏洩リスク

## 判断方法

次のいずれかなら環境変数を優先検討：

- Git に書きたくない
- マシン、ユーザー、環境で値が変わる
- 今回の実行だけ有効にしたい

Token、一時スイッチ、CI 注入値が環境変数経路になりがちな理由です。

設定キーの概念は [設定項目リファレンス](/guide/reference/configuration-reference/)。Cloud は [Secrets と変数](/guide/web-and-cloud/secrets-and-variables/)。

## 環境変数に向く内容

| 種類 | 意図例 | しないこと |
|---|---|---|
| 認証 Token | API key、GitHub PAT | リポジトリへコミット |
| 一時スイッチ | デバッグログレベル | 長期ビジネス設定 |
| CI 注入 | 読み取り専用レビューモード | 本番書き込み権限 token |
| MCP 子プロセス | 第三者サービス key | `AGENTS.md` に平文記載 |

## 環境変数を万能引き出しにしない

「入れられるから全部環境変数」は危険です。

- **秘密値、実行時差異**：環境変数
- **チーム長期約束**：設定ファイルまたは文書
- **ワークフロールール**：`AGENTS.md` または Skill

障害時にどこを見るか分かりやすくなります。

## `.env` とは

初見でよく出る `.env` は、多くのツールがローカル開発を楽にするための**環境変数一括ロード**方法です。

- 環境変数は「値そのもの」
- `.env` は「ローカルに値を入れる常见容器」

`.env` は便利だが安全ではない。`.env.example` は例示名用で実秘密は入れない。本番や CI では Secret マネージャが一般的です。

## 環境変数だけでは不十分な内容

- コーディング規範、ディレクトリ構造 → `AGENTS.md`
- チーム合意のモデルデフォルト → プロジェクト設定（非秘密部分）
- 複雑 allowlist → [ルール](/guide/customization/rules/allow-and-deny-patterns/)

## よくある誤解

### 1. すべての設定を環境変数に入れるべきではない

「値」向き。「チームルール全文」や長期説明の容器ではない。

### 2. `.env` に書けば安全？

コミット、画面共有、ログ出力で漏洩します。

### 3. `unset` したら絶対安全？

shell 履歴、子プロセス継承、ログ、過去保存ファイル、スクリーンショットに残る可能性があります。

### 4. ローカル `.env` を本番でもそのまま渡せる？

CI、Cloud、マネージドプラットフォームでは、バックエンドで Secret 設定し実行時注入し、実値をリポジトリファイルに落とさない方が一般的です。

## 層と優先順位（概念）

```text
組織強制方針（あれば）
    ↓ 上書き
Shell / CI 注入の環境変数
    ↓ 設定ファイルとマージ（具体ルールは公式を基準に）
ユーザー級 / プロジェクト級 config ファイル
```

同一キーが複数箇所にあるときは**公式が説明する優先順位**を基準に。障害時は「有効設定」を出力またはログ確認。

## 判断の常用順序

1. この値は秘密か？
2. 個人ローカル用か、CI / Cloud 用か？
3. 長期保存か、今回実行だけか？
4. ローカル環境変数、CI Secret、Cloud Secret のどれか？

「値は正しいが置き場所が違う」問題を減らせます。

## よくあるシーン

| シーン | より安定したやり方 |
|---|---|
| 本機で第三者 API デバッグ | ローカル環境変数または `.env`、コミット除外 |
| チーム共有例示設定 | `.env.example` をコミット。実値はコミットしない |
| GitHub Actions / CI | プラットフォーム Secret |
| Cloud タスクが私有サービス呼び出し | Cloud Secret |
| MCP サーバーが key を読む | 親プロセス環境変数または Secret 注入 |

迷ったら：実秘密は可能な限りリポジトリの普通のファイル内容として長期残さない。

## よくあるシーン（詳細）

### ローカル開発

`~/.zshrc` または direnv `.envrc` で個人 token を export——**`.env` を commit しない**。

### CLI 非対話

CI が secret store から変数注入後 `codex exec`。[非対話モード](/guide/cli/non-interactive-mode/) を参照。

### MCP サーバー

MCP プロセスは親プロセス環境を継承しがち。設定では値を直書きせず `$VAR` を参照。[MCP 接続](/skills/mcp/connect-an-mcp-server/)。

### Cloud

リポジトリ級 Secrets を Cloud コンソールで設定。名前とタスク内参照を一致させる。

環境変数は変わりやすい、秘密、実行時だけ必要な値向き。長期ルールや説明の容器ではありません。

## セキュリティチェックリスト

- [ ] `.env` が `.gitignore` にある
- [ ] ログ出力前に token を脱敏
- [ ] 漏洩した key をローテーション
- [ ] 最小権限 scope（読み取り専用 CI token 等）

## よくあるミス

- `.env.example` に実 key を入れてコミット
- 画面共有中に `export` で token が見える
- `unset` 後も子プロセスが安全と仮定——プロセスツリーを確認
