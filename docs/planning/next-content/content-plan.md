# 内容产品规划

## 目标与假设

目标：让中文读者能从一个真实需求出发，找到材料，执行任务，核对结果，并把成功过程用于下次工作。

默认优先个人初学者与创作者，开发者路径复用已有较强的技术内容，团队作为进阶路径。依据是首页已承诺多角色覆盖，而非编程案例和三条角色路径的完成度不足。没有用户研究证明受众比例；发布后用完成练习的反馈校正。

本轮是编辑与产品规划，不承诺固定工期，也不要求引入登录、付费、在线 Agent 执行或社区后台。

## 三类阅读需求

| 需求 | 用户问题 | 首个动作 | 成功证据 |
|---|---|---|---|
| 完成任务 | 我现在要一份周报/文章/演示稿 | 选案例，拿输入材料 | 交付物满足检查表 |
| 系统学习 | 我是新手，怎么逐步学会 | 选路径，从第一步开始 | 每个里程碑都有可展示产物 |
| 定点查阅 | 为什么 Skill 没触发/这个权限是什么 | 搜索或进参考目录 | 找到答案及下一步操作 |

推荐首页优先展示第一类，第二、三类保持直接入口。三种布局见原型首页的方向切换。

## 信息架构

不迁移现有四模块 URL。导航名称可以更贴近动作，模块本身继续作为内容的稳定归属。

```text
首页 /
├─ 开始学习 → /guide/learning-paths/
│  ├─ 初学者 → 保留五步，补练习材料与验收
│  ├─ 创作者 → 研究 → 文章 → 演示稿 → 复用
│  ├─ 开发者 → 读代码 → 修复 → 审查 → 交接
│  └─ 团队 → 试点 → 规则 → 抽检 → 推广
├─ 实战案例 → /cases/
│  ├─ 任务筛选：办公分析 / 内容创作 / 软件开发 / 团队自动化
│  ├─ 状态：示例流程 / 材料齐备 / 已实跑（明确环境）
│  └─ 详情：目标 → 材料 → 步骤 → 结果 → 验证 → 恢复
├─ 模板与 Skills（下拉，导航分组，不新建重复正文）
│  ├─ 提示词 → /prompts/templates/
│  └─ Skills → /skills/examples/
├─ 查手册 → /guide/reference/；保留 /guide/ 完整目录
└─ 资源（次级）
   ├─ AI 路线图
   ├─ 宠物与主题
   ├─ 价格参考（先修正）
   └─ 内容更新与参与贡献
```

搜索常驻；移动端保留搜索、展开导航和明确返回入口。参考手册侧栏保留完整层级，学习路径内则只展示当前步骤与相关知识。

## 内容关系与重复处理

一个概念只保留一篇权威解释。案例可引用概念，不复制安装说明；Skill 可引用同一输入样本，不复制案例故事；路径只编排练习顺序。

| 现有入口 | 下一版处理 | URL 策略 |
|---|---|---|
| `/cases/analyze-a-spreadsheet/` | 原位升级为周报完整练习 | 保留 |
| `/cases/write-an-article/` | 原位升级为来源可回查的文章练习 | 保留 |
| `/cases/create-a-slide-deck/` | 原位升级为演示稿完整练习 | 保留 |
| `/cases/fix-a-bug/` | 保留简短入口，突出权威案例 | 保留，链接现有完整案例 |
| `/skills/examples/` | 从链接清单升级为示例包目录 | 保留 |
| `/guide/learning-paths/{role}/` | 增加产物里程碑和前置条件 | 保留 |
| `/guide/reference/troubleshooting/` | 症状优先索引，链接详细排查步骤 | 保留 |
| `/guide/updates/` | 新增面向读者的内容变化记录 | 新建，不宣称产品官方更新日志 |

删除或合并页面前检查内链、外链入口和多语言映射；需要迁移时建立明确重定向。先处理中文，翻译在中文案例实跑后同步，不把缺失翻译静默冒充本地化内容。

## 发布门槛

每批可以独立发布，但不得只把标题、空下载按钮和 planned 页批量上线。T05 依赖至少一个完成的案例包；路径中的未完成节点显示预告或隐藏，不伪装可学习。

第一批门槛：T01—T05 完成；周报案例真实运行一次，独立复核一次；有明确环境；首页和案例库能找到它。

第二批门槛：文章和演示稿可下载、来源齐全、图文经过视觉检查；创作者路径连续可走；开发者路径链接已存在的资产；高风险机制描述完成复核。

第三批门槛：四个 Skill 包均含触发正反例；失败示例可重现；自动化默认先观察结果，写操作单独设边界。

第四批门槛：评估方法不依赖无依据的统一成功率；团队模板可直接填写；变更记录可追溯。工期应在第一批完成后以实际作者和复核速度估算。

## 内容元数据设计

现有的 planned/draft/review/verified/outdated/archived 先保留作为编辑状态，新增独立字段，不把所有旧 verified 自动转换为已实跑。

```yaml
contentType: case # guide | reference | prompt | skill | case | path
audiences: [creator, beginner]
task: data-analysis
level: beginner
estimatedMinutes: 30 # 编辑预估，实际范围需记录
outputs: [markdown, csv]
editorialStatus: review
verification:
  kind: editorial # editorial | source-checked | run-tested
  checkedAt: 2026-09-18
  environment: null # run-tested 时必须填写客户端/版本/OS/依赖
  evidence: [] # run-tested 时必须链接运行证据与复核记录
assets: [] # 每项记录路径、用途、许可、版本
canonicalTopic: null
```

实施时扩展 `src/content.config.ts`，通过组件渲染状态，避免文末自由文本和 frontmatter 双源长期分叉。日期可见但不等于可靠性评分。相同页面允许有「来源已核对、示例未实跑」的不同子状态。

## 维护与衡量

建议维护节奏，不自动创建定时任务：价格等高波动信息过期就显示待复核；客户端/配置按产品变化复核；方法论按读者反馈更新。频率由维护能力决定，不承诺每日实时。

每个案例由作者提供材料，另一位复核者检查输出和关键来源；无法安排独立复核时明确标注作者自检。下载文件保留版本与许可，使用合成数据或可再分发资料。

第一批上线后先找 5 位目标读者做定性任务测试：能否找到材料、完成练习、判断结果。记录阻塞点，不把 5 人结果宣传为统计性成功率。需要行为分析时另行设计最少化事件和隐私说明；本轮没有部署任何追踪。

优先观察「从首页进入任务」「拿到材料」「完成检查表」「报告失败原因」。页面数量、浏览量和停留时间只能作为辅助，不直接代表学会了。
