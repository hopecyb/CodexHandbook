# 深化审查：从页面数量转向学习完成度

## 范围和方法

在前一份报告基础上，对全体 281 页做结构盘点，并继续深读任务授权、上下文、Skill 示例、自动化、团队治理等主题。`content-inventory.csv` 的标记是自动提取的复核线索；占位符、短文或旧核验日期本身不构成缺陷。结构盘点不代替全部产品事实重新核验。

新增统计：61 页正文含 H1；14 页含本次规则识别出的输入占位符；9 页出现「骨架」；6 页仍有明确延期承诺。不能把这四组加总当成有问题页面数，同一页可能命中多组。

## 补充发现

### A. 任务分级应先于「每一步停下来」

证据：`prompts/long-running-tasks.md` 的第一段模板要求「每阶段结束先停下来等我确认」；`prompts/anti-patterns.md` 把「不要问我，直接改完」列为反模式；写作案例建议逐节暂停确认。

问题不在于设置检查点，而在于缺少适用条件。对范围已明确的低风险编辑，这会教读者增加不必要的交互；对外部发布和授权变更，又不能单靠「别问」处理权限边界。

规划：在提示词基础及计划页增加三类任务表，区分任务澄清、方案选择与动作授权。明确「开始前给出边界 + 连续执行 + 最后验收」也是有效工作方式。阶段检查点用于高不确定性或高返工成本的环节，不要求所有工作每阶段等待。

验收：给出同一任务的两种版本——明确的小改动直接完成；范围不清的重构先探索再对齐。任何权限要求仍按具体客户端和组织策略说明。

### B. 审查 Skill 的输入契约存在歧义

证据：`skills/examples/review-skill.md` 默认比较分支 main；同页试用请求是「当前未提交的改动」。这是两个不同的审查范围，骨架未交代如何选择。

影响：照搬示例可能漏掉当前工作区或错误地把整条分支改动当成用户要求。仅给「阻断 / 建议 / 通过」也不足以定位证据。

规划：在 PR 审查 Skill 包明确 staged、unstaged、指定基线三种输入；显式请求覆盖默认值；输出文件、行号、触发条件、影响和验证建议。加一个同时包含已提交与未提交改动的测试 fixture。

### C. 团队自动化还缺实施证据

证据：Issue 分流案例列出 JSON schema，但写成含 `bool` 的说明性片段；未给可执行 schema 与历史样本。页面使用 3 个 fixture 和一致率大于 80% 作为上线判断。

判断：这是教学示意，不是成熟上线评估。3 个样本中超过 80% 实际要求全部命中，且无法覆盖类别不均衡和新情形。不能把这个小样本判断泛化为可靠性保证。

规划：提供合法 JSON Schema、脱敏 fixtures、按标签和风险类型分层的样本、未知类别拒答案例；先只读建议模式，人工抽检后再讨论写操作。质量阈值由组织按错误代价设定，不编造万能百分比。

### D. 上下文优先级需要单一权威解释

证据：`guide/context/context-priority.md` 同时说「当前任务提示词对本次范围最优先」和「项目级安全禁令应始终遵守」。另有 AGENTS.md 作用域与优先级专题。

判断：这些建议缺少适用层级，读者可能把任务范围变更、仓库约定、管理员强制策略混为一谈。不能仅凭这一段断定所有客户端的真实优先级。

规划：此页保留任务上下文的更新方法，指令层级统一链接到一篇有官方依据的权威页；提供「同级新请求」「目录作用域」「管理员限制」三个独立例子，分别注明适用环境。

### E. 开发者平台需更明确地区分产品边界

证据：SDK 概览使用语言无关的认证、远程 runner、artifact URL 等泛化概念，来源只写「OpenAI Codex SDK reference」，没有精确的包名、最小可运行例子和相应版本。

判断：目前能作为集成思路阅读，但不足以保证读者可以按文接入。不能从「API / SDK 都存在」推导它们共享完整能力与结果结构。

规划：先列出目标 SDK/服务名称与官方入口，再按验证过的一条路径做最小例子，其他能力标为设计模式或待核验。安排为参考内容的复核任务，优先级高于新增更多平台概念页。

## 保留、强化、合并和暂缓

| 主题族 | 决策 | 原因与动作 |
|---|---|---|
| 从这里开始、快速上手、初学者路径 | 保留职责，减少重复引导 | 入口分流、安装执行、练习编排各有价值；明确一条主 CTA |
| 上下文总览、细分上下文 | 保留总览，统一机制解释 | 总览只解释导航；产品层级由权威专题负责 |
| 验证、质量、产物验收 | 保留并交叉引用 | 通用完成定义与文件格式检查不同；减少重复的原则段落 |
| 短案例与完整场景案例 | 入口页导向完整案例 | 参考现有 Bug 修复入口，不再维护两套相近教程 |
| Skill、MCP、Hook、Plugin、自动化 | 保留 | 正交能力关系已经较完整；补可运行组合例子 |
| 长任务、多 Agent | 深化 | 增加分工产物、冲突实例、汇总验收；不把并行数当成绩 |
| 产品安装、CLI、IDE、Cloud | 按波动性复核 | 用兼容性和版本标记维护，避免再写重复入口教程 |
| 团队、安全、治理 | 保留并补操作材料 | AUP、角色、审计目前偏概念；先做两周小团队试点 |
| 时间线 | 保留次级位置 | 统一事件口径，连接练习；不扩成新闻流 |
| 主题、宠物 | 保留资源区 | 补适用版本、来源和恢复；可转成有教学价值的制作案例 |
| 价格比较 | 修正后再扩充 | 估算与报价边界优先于视觉和地区数量 |
| 独立作品展、社区论坛、学习账号 | 暂缓 | 尚无证据说明值得承担运营和登录成本 |

## 编辑深度标准

不用字数衡量深度。入口页可以很短；参考页可以密集；案例必须让读者找到实际输入、执行动作、检查结果和失败出口。

对反复出现的「常见误会」段落逐页判断：能揭示具体误操作就保留，仅重复开头原则就压缩。新增的文字预算优先留给真实例子和边界条件。
